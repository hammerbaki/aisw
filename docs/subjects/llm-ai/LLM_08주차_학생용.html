에이전트 구현과 SDD 실전

실습 자료 이 주차 키트 파일 보기 · 내려받기

이번 주차의 목표는 에이전트 루프를 두 번 만드는 것입니다. 한 번은 생각, 행동, 관찰을 반복하는 ReAct 루프를 골격 위에서 직접 완성하여 원리를 확인하고, 한 번은 같은 에이전트를 Claude Agent SDK(Software Development Kit, 소프트웨어 개발 도구 모음)로 재구현하여 두 방식이 각각 무엇을 맡는지 비교합니다. Claude Code를 움직이는 것과 같은 인프라로 자기 에이전트를 만드는 주차입니다. 후반부에는 확정한 개인 프로젝트 주제로 Charter(프로젝트 헌장)와 Spec(요구사항 명세) 작성을 시작합니다.

이 주차의 기술은 에이전트 루프 구현입니다. 앞선 주차에서 사용하기만 했던 반복 구조를 이번에는 직접 구현합니다.

graph LR
    P["<b>프롬프트 엔지니어링</b><br/>무엇을 말할까"] --> C["<b>컨텍스트 엔지니어링</b><br/>무엇을 보여줄까<br/><i>CLAUDE.md</i>"] --> H["<b>하네스 엔지니어링</b><br/>어떤 환경을 만들까<br/><i>MCP·Skill·Hook</i>"] --> L["<b>루프 엔지니어링</b><br/>어떻게 반복시킬까<br/><i>에이전트·자동화</i>"]
단계 이 주차 기술(에이전트 루프 구현)의 역할
프롬프트 ReAct의 출력 서식을 강제하는 시스템 프롬프트가 루프의 규약입니다. 예: “행동: vat_calc” 서식을 지키게 하는 문장이 파싱 성공률을 좌우함
컨텍스트 관찰의 재주입이 곧 컨텍스트 축적입니다. 예: 매 단계의 관찰 결과가 프롬프트 끝에 쌓여 다음 판단의 근거가 됨
하네스 파싱, 인자 검증, 단계 상한이 모델을 감싸는 실행 계층입니다. 예: MAX_STEPS 상한이 무한 반복을 차단하고, 도구 실행은 코드가 검증 후 수행함
루프 반복 구조 자체를 설계하는 것이 이 주차의 주제입니다. 예: Claude Code가 파일을 읽고 고치고 다시 확인하는 반복이 오늘 만드는 while문의 대형판

학습 목표

  • ReAct 루프(생각, 행동, 관찰의 반복)를 직접 구현하여 에이전트가 실제로 무엇인지 설명할 수 있습니다.
    • 예시: 모델 출력 파싱과 관찰 재주입을 완성해 2단계 도구 연쇄(부가세 계산 후 할인 적용)를 동작시킴
    • 장점: 면접 질문 “에이전트가 무엇인가”에 프레임워크 이름이 아니라 구현 경험으로 답할 수 있음
  • Mock 어댑터로 에이전트 루프를 API 없이 검증할 수 있습니다.
    • 예시: 정해진 각본을 돌려주는 Mock을 주입해 루프 로직만 몇 초 만에 반복 검증
    • 장점: 비용·비결정성 없이 에이전트를 테스트하는 현업 표준 기법의 적용 범위 확장
  • Claude Agent SDK로 같은 에이전트를 재구현하고 직접 구현과의 분담을 비교할 수 있습니다.
    • 예시: 직접 쓰던 파싱·루프·재주입 코드가 SDK에서 무엇으로 대체되는지 대조표 작성
    • 장점: 원리를 직접 구현으로 익히고 같은 것을 도구로 재구현한 경험을 코드 실물 두 벌로 증명
  • 프로젝트 Charter를 작성하여 만들 것과 만들지 않을 것을 확정할 수 있습니다.
    • 예시: 사용자, 문제, 핵심 기능 2~3개, 배포 형태, 범위 밖 선언을 한 장으로 정리
    • 장점: 기업의 프로젝트 킥오프 문서와 같은 구조를 포트폴리오로 확보
  • 요구사항을 EARS(Easy Approach to Requirements Syntax, 정형 요구사항 문형) 형식으로 명세할 수 있습니다.
    • 예시: “만약 외부 API가 실패하면, 시스템은 오류를 알리고 재시도를 안내해야 한다”처럼 조건과 행위를 분리
    • 장점: 모호한 요구를 검증 가능한 문장으로 바꾸는 능력은 AI에게 일을 시킬 때도 그대로 쓰임

1. ReAct 루프의 구조

도구 사용을 배울 때 관찰한 사이클(호출 결정, 실행, 결과 재주입, 재판단)에서, 판단의 형식과 재주입은 API가 정해 주었습니다. stop_reason이 tool_use가 되고, 결과를 tool_result 블록으로 넣는 규약이 이미 있었습니다. 오늘은 그 규약까지 직접 만듭니다. 모델에게는 순수한 텍스트 서식만 주고, 파싱과 반복을 전부 우리 코드가 담당합니다. API가 대신해 주던 일이 실제로 무엇인지 확인하는 것이 목적입니다.

ReAct는 2022년 야오(Yao) 등이 제안한 에이전트 구성 방식으로, 모델이 생각(Thought)을 말로 정리하고, 행동(Action)을 하나 고르고, 그 행동의 관찰(Observation) 결과를 받아 다음 생각을 잇는 반복 구조입니다. 오늘날 에이전트 프레임워크 대부분이 이 구조의 변형입니다.

graph LR
    T["생각<br/>다음에 무엇을 할까"] --> A["행동<br/>도구 하나 선택"] --> O["관찰<br/>도구 실행 결과"] --> T
    A -->|"행동: finish"| F["최종 답"]

구현에 필요한 부품은 네 가지입니다. ① 출력 서식을 강제하는 시스템 프롬프트(생각:, 행동:, 입력:의 세 줄) ② 모델 출력에서 행동과 입력을 골라내는 파싱 ③ 행동을 실행하고 관찰을 만드는 도구 실행부(인자 검증, 오류의 문자열 반환은 도구 사용에서 배운 원칙 그대로) ④ 관찰을 프롬프트에 붙여 반복하는 루프와 단계 상한(MAX_STEPS). 모델이 서식을 벗어날 가능성은 항상 있으므로, 파싱 실패를 최종 답으로 취급하는 폴백도 둡니다. 루프는 앞서 만든 클린 아키텍처 구조(비즈니스 로직은 인터페이스에만 의존하고 실제 호출은 어댑터가 담당하는 구조) 위에서 돌며, 어댑터(Mock 또는 Claude)를 갈아 끼울 수 있습니다.

[확인 1] 도구 사용 API의 사이클과 오늘 만드는 ReAct 루프에서, 같은 역할을 하는 짝은 무엇입니까? (힌트: tool_use 블록과 tool_result 블록이 각각 무엇으로 대체되는지 봅니다.)

배포된 10주차 에이전트 키트를 개인 폴더의 week10/에 복사하고 실습기록.md를 준비합니다. react/react_agent.py에는 도구 2종(부가세, 할인)과 루프의 골격이 있고, 완성할 곳은 TODO 2곳입니다.

  1. 파일을 읽고 네 부품(서식 프롬프트, 파싱, 도구 실행부, 루프)이 코드의 어디에 있는지 확인합니다. 완성 전에 실행하면 어떻게 되는지 먼저 봅니다.

    python react/react_agent.py mock

  2. parse_action을 독스트링의 ①②③ 구성대로 완성합니다. Claude Code에 맡길 때는 대상을 지정합니다.

    @react/react_agent.py 의 parse_action을 독스트링의 ①②③대로 완성하라. 다른 부분은 건드리지 말라.

  3. 루프 안의 관찰 재주입 TODO를 주석의 형식대로 완성합니다(두 줄입니다. 직접 타이핑을 권장합니다).

    python react/react_agent.py mock

    세 단계의 모델 출력, 관찰, 최종 답이 출력되면 루프가 완성된 것입니다. API 키 없이 루프 로직이 검증되었다는 점을 기록합니다.

3. 실습 2: 실제 모델로 ReAct 실행

  1. 어댑터를 Claude로 바꿔 같은 질문을 실행합니다.

    python react/react_agent.py ask "100만원 노트북, 부가세 포함가에서 20% 할인하면?"

    각 단계의 생각, 행동, 관찰을 실습기록.md에 순서대로 기록합니다. Mock 각본과 실제 모델의 경로가 달랐다면 그 차이도 기록합니다.

  2. 도구가 필요 없는 질문(“부가세가 무엇인지 설명해줘”)을 던져, 모델이 바로 finish를 고르는지 관찰합니다.

  3. 자기 변형 단계: 두 도구를 조합해야 답할 수 있는 자기 질문 하나를 만들어 실행하고, 단계 수와 성공 여부를 기록합니다.

  4. 실행 중 모델이 서식을 벗어나는 출력을 냈다면(파싱 폴백 발동), 그 출력을 기록해 둡니다. 없었다면 시스템 프롬프트의 서식 규칙 문장을 하나 지우고 재실행해 서식이 흔들리는지 실험해 본 뒤 되돌립니다.

4. Claude Agent SDK

직접 구현에서 작성한 코드의 대부분은 과업(계산)이 아니라 루프 운영 코드였습니다. 서식 프롬프트, 파싱, 재주입, 단계 상한이 그것입니다. Claude Agent SDK는 이 운영 코드를 통째로 제공하는 라이브러리입니다. Claude Code의 에이전트 루프를 움직이는 것과 같은 인프라를 파이썬에서 그대로 쓰는 것으로, 우리가 쓰는 코드는 도구 정의와 질문뿐입니다.

직접 구현(react_agent.py)에서 내가 만든 것 SDK(sdk_agent.py)에서는
서식 시스템 프롬프트와 파싱 없음. 네이티브 tool use로 대체
관찰 재주입과 while 루프 query() 안에 내장
MAX_STEPS 단계 상한 max_turns 옵션 한 줄
도구 함수와 인자 검증 동일하게 내가 작성 (@tool 데코레이터)
어댑터(모델 교체) model 옵션

주목할 점은 도구 함수와 검증만은 SDK에서도 그대로 우리 몫이라는 것입니다. 반복되는 연결·처리 코드는 도구가 대신 맡아 주지만, 무엇을 연결하고 무엇을 검증할지는 설계자의 일로 남습니다. 직접 구현이 원리를, SDK가 실무 생산성을 담당하는 분담입니다.

5. 실습 3: SDK 재구현 실행과 대조

sdk/sdk_agent.py는 같은 에이전트의 SDK 재구현 완성본입니다.

  1. 파일을 열어 4장의 표와 대조하며 읽습니다. 직접 구현판에서 내가 쓴 코드 중 SDK판에서 사라진 것 3가지와 남은 것 1가지를 실습기록.md에 기록합니다.

  2. 같은 질문으로 실행하고 출력을 관찰합니다.

    python sdk/sdk_agent.py "100만원 노트북, 부가세 포함가에서 20% 할인하면?"

    출력되는 메시지 흐름에서 도구 호출과 결과, 최종 답을 찾아 직접 구현판의 단계 출력과 비교합니다.

  3. 자기 변형 단계: 도구 설명 문장을 한 곳 고치거나 실습 2의 자기 질문을 실행해, 직접 구현판과 결과·단계 수를 비교해 기록합니다.

[확인 5] 사라진 것 3가지와 남은 것 1가지의 대조가 기록되었다.

[확인 6] 직접 구현과 SDK는 각각 언제 선택합니까? (힌트: 통제가 필요한 경우와 속도가 필요한 경우를 나눠 봅니다.)

6. 프로젝트 착수: Charter

지금부터는 확정한 개인 프로젝트 주제를 문서로 굳힙니다. 개발방법론에서 배운 문서 우선 원칙의 적용이며, 첫 문서가 Charter(프로젝트 헌장: 무엇을 왜 만드는지 한 장으로 확정하는 문서)입니다. Charter의 역할은 두 가지입니다. 만들 것을 확정하는 것, 그리고 만들지 않을 것을 선언하는 것입니다. 범위 밖 선언이 없으면 프로젝트 범위가 학기 말까지 계속 늘어납니다.

확장 설계서의 주제 절(주제, 사용자와 핵심 기능, 배포 형태)이 그대로 Charter의 입력물입니다. 백지에서 시작하지 않습니다.

이 절차는 리버스 엔지니어링에서 소개한 명세 주도 개발(SDD, Spec-Driven Development)에 해당합니다. 요구를 명세로 먼저 확정하고, 그 명세가 구현, 검증, 문서 갱신의 절차 전체를 주도하게 하는 방법론입니다. AI 협업에서 이 방법론의 중요성은 다음과 같이 정리됩니다. AI는 제공된 명세의 품질만큼 정확하게 동작하므로, 명세가 AI 출력을 통제하는 직접 수단이 됩니다. 이 과목의 문서 사슬(Charter로 범위 확정, Spec으로 검증 가능한 요구 작성, 구현, 코드-문서 동기화 게이트)이 SDD의 실행 절차입니다.

명칭이 유사한 방법론과의 구분은 다음과 같습니다.

약어 이름 주도 관계 이 과목에서
TDD 테스트 주도 개발 먼저 쓴 테스트가 구현을 주도한다 증강코딩 실습으로 수행
SDD 명세 주도 개발 먼저 확정한 명세가 개발 절차 전체를 주도한다 Charter·Spec·동기화 게이트로 수행
DDD 도메인 주도 설계(Domain-Driven Design) 업무 영역의 모델이 소프트웨어 설계를 주도한다 대규모 복잡 도메인용 설계 방법론으로 이 과목의 범위 밖. 클린 아키텍처의 인접 분야에 해당함

두 방법론이 이 과목의 개발 절차에서 결합되는 구조는 다음과 같습니다. Spec의 EARS 문장이 테스트로 변환되는 지점이 두 방법론의 접점입니다.

graph LR
    subgraph SDD["SDD: 명세가 절차 전체를 주도"]
        C["Charter<br/>범위 확정"] --> S["Spec<br/>EARS 요구사항·검증 방법"]
        subgraph TDD["TDD: 테스트가 구현을 주도"]
            T["테스트 작성<br/>(요구사항의 실행형)"] --> I["구현"] --> V["검증 통과"]
        end
        S --> T
        V --> Y["동기화 게이트<br/>코드와 문서의 일치 확인"]
    end

8. 명세의 문형: Spec과 EARS

Charter가 무엇을 왜 만드는지라면, Spec(Requirement Spec, 요구사항 명세)은 시스템이 정확히 어떻게 동작해야 하는지의 목록입니다. 요구사항 문장은 리버스 엔지니어링에서 연습한 EARS 문형으로 씁니다. 조건과 행위를 분리하는 그 문형이 여기서 본편으로 재사용됩니다. 문형 참조표는 키트의 charter/Spec_양식.md에 있습니다.

EARS로 쓴 요구사항의 가치는 검증 가능성입니다. “만약 검색 유사도가 문턱 미만이면, 시스템은 답변을 거절해야 한다”는 문장은 그대로 테스트 케이스가 됩니다. 요구사항마다 검증 방법(무엇으로 확인하는가)을 한 칸씩 붙이는 이유이며, 다음 단계인 평가(Evals) 주제로 이어지는 연결 고리입니다.

9. 실습 5: EARS 요구사항 착수

charter/Spec_양식.md를 week10/Spec.md로 복사하여 착수합니다.

  1. 자기 프로젝트의 기능 요구사항 R1~R3을 EARS 문형으로 쓰고, 각각 검증 방법을 한 줄씩 붙입니다. 사건 구동(Event-driven) 유형과 원치 않는 동작(Unwanted behaviour) 유형을 각 1개 이상 포함합니다. (사건 구동 예: “사용자가 저장을 요청하면, 시스템은 파일 이름을 검증해야 한다” / 원치 않는 동작 예: “입력이 비어 있으면, 시스템은 저장을 거부하고 사유를 표시해야 한다”)

  2. 쓴 문장을 Claude Code에 검토시킵니다.

    @week10/Spec.md 의 R1~R3이 EARS 문형(조건과 행위의 분리)에 맞는지 검토하고, 모호한 단어가 있으면 지적하라. 고쳐 쓰지는 말라.

    지적을 읽고 최종 문장은 자기 손으로 고칩니다.

  3. 완결된 명세 실물을 참고하려면 키트의 charter/참고예제_luckydraw/를 엽니다. 단일 HTML 앱 하나에 붙은 명세 4종(PRD 제품 요구사항 문서, TRD 기술 요구사항 문서, REQUIREMENTS, ANALYSIS)으로, 이 과목의 Charter·Spec 2종 체계를 문서 유형별로 더 잘게 나눈 확장형입니다. REQUIREMENTS의 문장 몇 개를 EARS 문형과 대조해 보는 것이 좋은 연습이 됩니다.

  2. 검증: R1~R7 중 하나를 골라 실제 검증 실물을 만듭니다(과제_검증.md). 테스트 코드 1개 또는 수동 검증 절차 1건(입력, 기대 동작, 확인 방법의 3줄)
  3. 의도 기록: EARS로 다듬는 과정에서 모호했던 문장 2건의 고치기 전후와 이유(의도기록.md)

채점은 요구사항 개수가 아니라 문장의 검증 가능성(조건 분리, 측정 가능한 기준)을 중심으로 합니다.
