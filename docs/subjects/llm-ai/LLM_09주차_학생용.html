검증·평가와 업무 자동화

실습 자료 이 주차 키트 파일 보기 · 내려받기

이 주차는 사람이 눈으로 확인하던 검증을 측정 가능한 시스템으로 바꾸고, 그 검증을 자동으로 실행되는 절차로 묶습니다. 1부에서는 산출물 품질을 정답셋과 자동 채점으로 재고, Claude를 심판(Judge)으로 세워 규칙 채점의 빈틈을 보완하며, 배포 전 점검을 전담하는 읽기 전용 검토자를 정의 파일로 직접 만들어 심어 둔 위반으로 성능을 확인합니다. 2부에서는 claude -p 헤드리스 모드와 훅(Hook)으로 검증을 자동 실행하고, 점검을 통과했을 때만 배포가 실행되는 파이프라인을 구성한 뒤, 개인 프로젝트 스프린트와 발표 준비로 마칩니다. 공식 문서는 서브에이전트 문서와 CLI 참조 문서입니다.

이 주차의 기술은 평가(Evals)와 검토자 분리, 그리고 자동화 파이프라인입니다. 검증을 측정 가능한 시스템으로 옮기고, 지금까지 다룬 부품(명령, 훅, 점검, 배포)을 사람 없이 이어지는 절차로 연결합니다.

graph LR
    P["<b>프롬프트 엔지니어링</b><br/>무엇을 말할까"] --> C["<b>컨텍스트 엔지니어링</b><br/>무엇을 보여줄까<br/><i>CLAUDE.md</i>"] --> H["<b>하네스 엔지니어링</b><br/>어떤 환경을 만들까<br/><i>MCP·Skill·Hook</i>"] --> L["<b>루프 엔지니어링</b><br/>어떻게 반복시킬까<br/><i>에이전트·자동화</i>"]
단계 이 주차 기술(평가·검토자 분리와 자동화 파이프라인)의 역할
프롬프트 심판에게 주는 채점 기준과 헤드리스 지시는 사람이 보완할 수 없으므로 완결되어야 합니다. 예: “근거 없는 절차를 지어내면 탈락”이라는 기준 한 줄과 “오류가 없으면 ’이상 없음’만 출력하라”는 예외 지정이 뒤 단계의 판정을 안정시킴
컨텍스트 검토는 격리된 컨텍스트에서 하고, 파이프는 앞 명령의 출력을 컨텍스트로 공급합니다. 예: 산출물을 만든 대화 안에서 “잘했는지 봐줘”라고 묻는 자기 검증은 이전 대화의 영향을 받지만, cat 로그 \| claude -p는 로그 파일을 통째로 컨텍스트에 실어 보냄
하네스 정의 파일의 tools 목록과 훅·점검 스크립트가 권한과 절차를 물리적으로 강제합니다. 예: Write가 없는 검토자는 지적만 할 수 있고, 종료 코드 1을 내는 점검 스크립트는 배포 단계를 실행되지 못하게 막음
루프 자동 반복의 통과·정지 조건이 곧 평가이며, 재시도 상한이 무한 반복을 차단합니다. 예: 배포 파이프라인이 점검 통과일 때만 다음 단계로 가고, 3회 실패 시 멈춰 사람에게 넘김

학습 목표

  • 정답셋 기반 자동 채점과 Judge 채점의 분담을 설명할 수 있습니다.
    • 예시: 규칙 채점이 놓친 옳은 답과 잘못 통과시킨 그럴듯한 오답을 불일치 표에서 짚기
    • 장점: “AI 품질을 무엇으로 측정했는가”에 두 채점의 실측 비교로 답할 수 있음. 이 과목의 취업 차별화 축
  • 커스텀 서브에이전트를 정의 파일로 작성하고 tools 목록으로 권한을 경계 지을 수 있습니다.
    • 예시: tools에서 Write와 Edit를 제외해 읽기 전용 검토자를 만들고 /agents로 확인
    • 장점: 정의 파일 하나가 그대로 포트폴리오 산출물이 됨
  • 배포 전 점검(API 키 노출, XSS, 금지 파일)을 검토자에게 맡기고 심어 둔 위반으로 성능을 검증할 수 있습니다.
    • 예시: 의도 위반 3건 중 몇 건을 찾고 오탐이 없는지 판정 기록을 남기기
    • 장점: 산출물을 URL로 공유하기 전의 안전 점검을 자동화하고 “검토 AI도 측정한다”고 말할 수 있는 실전 습관
  • claude -p 헤드리스 모드를 파이프와 종료 코드로 다른 명령과 연결할 수 있습니다.
    • 예시: cat 서버로그.txt | claude -p "오류 요약"의 결과를 파일로 남기고 실패 시 분기 처리
    • 장점: AI를 대화 상대가 아니라 파이프라인 부품으로 쓰는 능력은 자동화 직무의 차별점
  • PostToolUse 훅으로 검증을 자동 실행할 수 있습니다.
    • 예시: 파일 수정마다 문법 검사가 자동으로 돌고 실패 보고가 Claude에게 전달되어 스스로 고침
    • 장점: “가드레일은 훅에” 원칙을 설정 실물로 증명할 수 있음
  • 점검 통과 시에만 배포되는 배포 파이프라인을 구성하고 재시도 상한의 역할을 설명할 수 있습니다.
    • 예시: 키 노출 검사와 금지 파일 검사가 통과해야 wrangler 배포가 실행되는 스크립트, 3회 실패 시 멈추는 반복
    • 장점: 실무 CI/CD(Continuous Integration/Deployment, 지속 통합·배포)의 핵심 구조를 최소 실물로 경험
  • 코드-문서 동기화 게이트와 크로스 테스트로 프로젝트 품질을 점검하고 발표를 준비할 수 있습니다.
    • 예시: Spec 요구사항과 구현의 어긋난 곳을 표로 찾고, 동료가 사용자로서 시험한 결과를 반영
    • 장점: 혼자 만든 소프트웨어의 품질을 제3자 관점으로 끌어올리는 실무 절차

1. 평가의 구성: 규칙 채점과 Judge 채점

지금까지의 검증은 테스트 코드로 함수를 확인하고 챗봇 응답을 직접 읽는 방식이었습니다. 응답이 수백 건 규모가 되면 수작업 확인은 불가능하므로, 평가(Evals: AI 산출물의 품질을 정답셋과 채점기로 측정하는 체계)를 사용합니다.

구성은 세 부품입니다. 정답셋(대표 질문과 기대 답의 목록), 채점기, 그리고 측정 기록입니다. 채점기의 첫 단계는 규칙 채점입니다. 프롬프트 실험에서 쓴 정확도 측정이 이에 해당합니다. 키워드 포함 여부 같은 규칙은 빠르고 공짜지만 융통성이 없습니다. 표현만 다른 옳은 답을 탈락시키고, 키워드만 걸친 오답을 통과시킵니다.

이 한계를 보완하는 것이 LLM as Judge(LLM을 심판으로 세우는 채점. 이 과목에서는 Claude를 심판으로 씁니다)입니다. 채점 기준을 프롬프트로 주고 판정과 이유를 받습니다. 융통성이 생기는 대신 비용과 비결정성이 생기므로, 실무에서는 규칙 채점을 기본으로 깔고 규칙이 판정하기 어려운 축(사실성, 어조, 근거)에 Judge를 씁니다. 심판에게는 두 원칙이 있습니다. 기준을 명시할 것(기준이 없으면 심판은 그때그때 인상만으로 점수를 매깁니다), 그리고 산출물을 만든 대화와 격리할 것. 같은 세션 안에서 “방금 답 잘했는지 평가해줘”라고 묻는 자기 검증은 이전 대화의 영향을 받아 신뢰하기 어렵다는 것을 컨텍스트 오염 실험에서 이미 다뤘습니다.

2. 자동 채점과 Judge 채점 관찰

두 채점의 차이는 실측으로 보아야 감이 잡힙니다. 이 장은 완성된 평가 러너의 결과를 관찰하는 것으로 진행하고, 검토자 정의 작성에 실습 시간을 집중합니다. 배포된 9주차 검증 키트를 개인 폴더의 week09/에 복사하고 실습기록.md를 준비합니다. evals/에는 학과 FAQ 챗봇의 정답셋 6건과 응답 로그, 완성된 평가 러너가 있습니다.

교수가 규칙 채점만 실행한 결과와 Judge를 포함한 결과를 차례로 보이고, 학생은 두 표와 불일치 문항을 대조하여 기록합니다.

python evals/eval_runner.py --rule-only
python evals/eval_runner.py

불일치 문항의 응답과 정답셋을 함께 읽으며 어느 채점이 옳았는지 한 줄씩 판단해 기록합니다. 이어서 eval_runner.py의 JUDGE_SYSTEM(채점 기준)에서 기준 세 가지 중 하나를 지운 뒤 재실행하면 판정이 어떻게 달라지는지 보입니다. 근거 없는 단정을 금지하는 기준을 지우면, 지어낸 절차를 담은 응답이 통과로 바뀌는 것이 전형적인 관찰 결과입니다. 심판의 품질은 곧 기준 프롬프트의 품질이라는 점, 그리고 실무 평가 파이프라인에서 채점 기준 문서가 코드처럼 리뷰·버전 관리된다는 점을 이 관찰에서 확인합니다. 관찰 결과는 week09/실습기록.md에 남깁니다.

3. 커스텀 서브에이전트 정의

Judge는 응답 한 건씩을 채점했습니다. 폴더 전체를 뒤져 문제를 찾는 검토 업무에는 도구를 쓰는 일꾼이 필요합니다. 확장 기능 지도에서 다룬 서브에이전트(격리된 컨텍스트에서 작업하고 요약만 반환하는 전담 일꾼)를 이제 직접 만듭니다.

커스텀 서브에이전트는 마크다운 정의 파일 하나로 만듭니다. 프로젝트의 .claude/agents/이름.md에 두며, 머리(front matter, 문서 최상단 --- 사이의 메타데이터 블록)에 name, description, tools를 적고 본문에 임무 프롬프트를 씁니다. 스킬 작성에서 다룬 원칙이 그대로 적용됩니다. description은 호출 판단의 근거이고, 규칙에는 이유를 붙이고, 환각 방지 지침을 내장합니다.

정의 파일에서 가장 중요한 항목은 tools 목록입니다. 검토자에게 Read, Glob, Grep만 주고 Write와 Edit를 빼면, 검토자는 지적만 할 수 있고 코드를 고칠 수 없습니다. “검토와 수정의 분리”를 부탁이 아니라 권한으로 강제하는 것이며, 확장 기능 지도의 강제력 사다리에서 다룬 구분(지시는 요청, 구조는 강제)이 정의 파일 안에서 재현되는 지점입니다.

이번에 만들 검토자의 임무는 배포 전 점검입니다. 배포 카드의 필수 점검 2가지(학과 API 키 비공개, XSS 소독)에 금지 파일 점검(.env 등)을 더한 세 항목을, 배포 직전 폴더에서 찾아 심각도와 위치로 보고하는 일꾼입니다. XSS(Cross-Site Scripting, 교차 사이트 스크립팅)는 웹페이지에 악성 스크립트를 심어 방문자 브라우저에서 실행시키는 공격이며, 정의와 점검 예는 배포 카드의 점검 절에 있습니다. 산출물을 실제 URL로 공유하는 이 수업의 방침에서, 매 배포 전에 돌릴 실전 부품이 됩니다.

4. 실습: 배포 전 점검 검토자 작성

week09/ 폴더에서 Claude Code를 실행하고 진행합니다. 키트의 reviewer/검토자_골격.md를 참고하되, 정의 파일은 직접 작성합니다.

5. 검토자 성능 검증

검토자도 AI 산출물이므로 그대로 믿지 않습니다. 성능을 재는 방법은 평가와 같습니다. 정답을 알고 있는 재료에 투입해 몇 건을 찾는지 세는 것입니다. 키트의 deploy-check/site/는 배포 직전 폴더의 샘플로, 의도된 위반 3건이 심어져 있고 정상 파일 2건이 섞여 있습니다. 찾아야 할 것을 다 찾는가(누락), 멀쩡한 것을 위반이라 하는가(오탐)의 두 축이 판정 기준입니다. 누락의 축은 검색기 실습에서 잰 재현율(recall)이고, 오탐의 축은 정밀도(precision)입니다.

참고: 정밀도는 “위반이라고 보고한 것 중 실제 위반의 비율”입니다. LLM 동작 원리에서 다룬 양자화의 “정밀도”(수치 표현의 세밀함)와는 다른 뜻입니다. 재현율과 정밀도는 검색·평가 분야의 표준 지표이지만, 이 과목에서는 “누락 없이 찾는가, 엉뚱한 것을 잡지 않는가”라는 두 질문으로 이해하면 충분합니다.

7. 번들 스킬 /code-review와 비교

Claude Code에는 검토 스킬이 이미 들어 있습니다. 명령어 카드에서 예고한 번들 스킬 /code-review입니다. 시간 관계상 이 비교는 요점만 정리합니다. 같은 재료에 /code-review deploy-check/site/를 실행하면, 범용 검토자는 넓게 보지만 우리 배포 점검 3항목을 우리 기준(심각도, 위치)으로 강제하지는 않습니다. 전담 검토자는 좁은 대신 그 기준을 강제합니다. 확장 기능 지도에서 다룬 “범용 부품과 내 부품의 분담”이 검토 영역에서 반복되는 것이며, 실제 실행 비교는 과제로 각자 확인합니다.

여기까지가 검증·평가입니다. 2부에서는 이 검토자와 결정적 점검을 사람이 지켜보지 않아도 도는 하나의 절차로 묶습니다.

8. 헤드리스 모드와 파이프 조합

명령어 카드의 1부에서 소개한 헤드리스 모드(headless mode, 화면 없이 명령 한 줄로 실행하는 모드)가 2부의 중심 수단입니다. 헤드리스는 코드 문법이나 표의 머리글(header)과는 무관한 관용어로, “머리(head), 곧 화면이 없다”는 뜻입니다. 모니터 없이 도는 서버(headless server), 창을 띄우지 않고 실행되는 브라우저(headless browser)에서 쓰던 표현이 그대로 온 것입니다. Claude Code에서는 대화 화면을 열지 않고 명령 한 번으로 실행하고 종료하는 방식을 가리킵니다. claude -p "요청"은 대화 없이 한 번 답하고 종료하므로 스크립트와 스케줄러에 넣을 수 있습니다. 유닉스 파이프와 결합하면 앞 명령의 출력이 그대로 컨텍스트가 됩니다.

cat 서버로그.txt | claude -p "오류를 원인별로 묶어 3줄로 요약하라"

자동화에서는 사람이 중간에 보완할 수 없으므로 두 가지가 중요해집니다. 첫째, 프롬프트의 완결성입니다. 정상 경우와 예외 경우(오류 없음, 빈 입력)의 출력 형식까지 지시에 담아야 뒤 단계가 안정적으로 이어받습니다. 둘째, 종료 코드입니다. 리눅스의 모든 명령은 종료 시 숫자 코드를 남기며(성공 0, 실패 그 외), 직전 명령의 코드는 $?로 읽습니다. 파이프라인의 각 단계는 이 코드로 성공 여부를 알리고, 다음 단계는 이 코드를 보고 진행과 중단을 결정합니다. 이렇게 만든 스크립트를 cron(리눅스의 정기 실행 스케줄러)에 등록하면 무인 반복이 됩니다(등록은 관찰로 봅니다). 상세는 CLI 참조 문서가 원전입니다.

9. 수집·요약·통지 파이프라인 관찰

파이프라인의 골격은 교수 실행으로 흐름을 확인하고, 종료 코드 분기 완성은 과제로 각자 마무리합니다. 배포된 9주차 자동화 키트를 개인 폴더의 week09/에 복사하고 실습기록.md를 준비합니다.

pipeline/서버로그.txt에는 연결 끊김, 시간 초과, 디스크 부족 같은 오류가 섞여 있습니다. pipeline/ 폴더에서 파이프라인을 실행해 요약과 종료 코드를 함께 봅니다.

bash pipeline.sh
cat 요약.md
echo $?

요약이 로그의 실제 오류와 일치하는지, 근거 없는 내용이 섞이지는 않았는지 대조하여 기록합니다(자동화에서도 산출물 검증은 사람의 일입니다). pipeline.sh에는 claude 명령의 종료 코드가 0이 아닐 때 “요약 실패: 수동 확인 필요”를 기록하고 종료 코드 1로 끝나는 분기를 넣는 TODO가 있습니다. 분기의 골격은 다음과 같으며, 완성은 과제로 수행합니다. if [ $? -ne 0 ]는 직전 명령의 종료 코드가 0이 아니면(실패하면) 분기하는 셸 문법입니다.

if [ $? -ne 0 ]; then
    echo "요약 실패: 수동 확인 필요" > 요약.md
    exit 1
fi

요약 프롬프트에 “오류가 없으면 ’이상 없음’만 출력하라”가 들어 있는 이유는, 사람이 없는 파이프라인에서 예외 경우의 출력 형식도 미리 고정해야 뒤 단계(파일 기록, 통지, 판정)가 흔들리지 않기 때문입니다. 실무 자동화 장애의 흔한 원인이 “AI 출력 형식이 어느 날 달라짐”이며, 예외 경우 형식 고정과 종료 코드 검사가 이를 먼저 걸러 내는 장치입니다.

10. 훅 기반 자동 검증

파이프라인이 밖에서 절차를 잇는 자동화라면, 훅은 Claude Code의 작업 안에 검증을 심는 자동화입니다. 확장 기능 지도에서 정리한 “가드레일은 훅에”를 이제 설정 실물로 만듭니다. 훅 문서가 원전이며, 이번에 쓸 시점은 PostToolUse(도구 실행 직후)입니다.

키트의 hooks/훅_설정예시.md에 있는 설정을 프로젝트의 .claude/settings.json에 넣으면, 파일을 쓰거나 고칠 때마다 문법 검사가 자동 실행됩니다. 같은 문서의 통지형 훅 절은 검사 결과를 메신저로 내보내는 확장(심화 선택)을 다룹니다. 중요한 성질은 두 가지입니다. 훅은 지시가 아니라 이벤트마다 반드시 실행되는 강제라는 것, 그리고 훅이 실패를 보고하면(종료 코드 2와 오류 출력) 그 내용이 Claude에게 전달되어 스스로 대처한다는 것입니다. 정상 통과(종료 코드 0)의 출력은 화면 기록용이며 Claude에게 전달되지 않습니다.

12. 배포 파이프라인

산출물을 실제 URL로 공유하는 이 수업의 배포 절차를 자동화로 완성합니다. 지금까지 배포 전 점검은 손으로 했습니다. 배포 카드의 점검 2종을 확인하고, 검토자 서브에이전트를 투입했습니다. 배포 파이프라인은 이 점검을 스크립트로 묶어, 점검을 통과했을 때만 배포가 실행되게 만듭니다.

구조는 종료 코드의 연쇄입니다. ① 키 노출 검사(grep): 발견되면 종료 코드 1로 중단 ② 금지 파일 검사: .env가 있으면 중단 ③ 두 검사를 통과했을 때만 npx wrangler pages deploy(첫 배포 실습에서 쓴 Cloudflare 배포 명령) 실행. 결정적 검사(grep)가 1차 점검이고, 배포 전 점검 검토자(deploy-checker)는 규칙으로 잡기 어려운 부분을 보는 2차 층으로 병행합니다. 1부의 검토자 성능 검증에서 내린 결론이 파이프라인 설계로 이어지는 지점입니다.

같은 구조를 저장소 이벤트(push)에 걸면 CI/CD가 됩니다. GitHub Actions 연동으로 원격 저장소에서 같은 점검·배포가 자동 실행되는 것은 관찰로 봅니다.

14. 재시도 상한 안전장치 관찰

무인 자동화의 남은 질문은 “실패하면 어떻게 되는가”입니다. 실패를 만나면 다시 시도하되, 상한 없이 반복하면 비용과 시간이 무한히 늘어납니다. 기본 안전장치가 재시도 상한(MAX_RETRIES)입니다. 생성과 검증을 반복하다 상한에 도달하면 멈추고 사람에게 넘깁니다.

이 장은 관찰로 진행합니다. 키트의 retry/retry_loop.py를 두 시나리오로 실행하면 종료 코드가 갈립니다.

python retry/retry_loop.py success
echo $?
python retry/retry_loop.py fail
echo $?

success는 0, fail은 1로 끝납니다. 코드를 열어 생성기와 검증기 역할을 코드의 어느 부분이 맡고 있는지, 실제 자동화에서는 각각 무엇이 들어갈 자리인지 한 줄씩 기록합니다. 생성기 자리에는 AI 생성 호출(claude -p, API), 검증기 자리에는 pytest나 배포 전 점검이 들어갑니다. 실패 시나리오의 마지막 줄(수동 개입 요청)이 사람이 루프의 일부로 남는 지점입니다.

문제 해결. /agents에 검토자가 안 보이면 파일 위치(.claude/agents/deploy-checker.md)와 front matter 구문(— 두 줄 사이)을 확인하고 세션을 재시작합니다. 검토자가 파일을 수정하려 들면 tools 목록에 Write나 Edit가 들어가지 않았는지 확인합니다. Judge 실행이 API 문제로 막히면 --rule-only로 규칙 채점만 보고 Judge 비교는 교수 화면을 관찰합니다. claude -p가 파이프에서 멈춰 있으면 로그인 상태와 네트워크를 확인합니다. 훅이 실행되지 않으면 settings.json의 JSON 문법(쉼표, 따옴표)과 세션 재시작 여부를 확인합니다. wrangler 로그인 화면이 열리지 않는 환경이면 배포는 대시보드 업로드로 대체합니다(배포 카드). 종료 코드가 항상 0으로 보이면 echo $?를 명령 직후에 바로 실행했는지 확인합니다(다른 명령을 끼우면 그 명령의 코드가 읽힙니다).

15. 프로젝트 스프린트와 발표 준비

남은 시간은 개인 프로젝트 스프린트(정해진 시간 안에 집중해 작업을 끝내는 방식)와 발표 준비입니다. 스프린트 시작 전에 중간 점검 게이트로 코드-문서 동기화(sync) 를 수행합니다. 구현이 진행되면 코드와 문서(Charter, Spec, README)는 반드시 어긋나기 시작하며, 어긋난 문서는 실제 구현과 다른 내용을 안내하므로 오히려 혼란을 일으킵니다. 개발방법론의 문서 업데이트 병행 지침을 반드시 거쳐야 하는 점검 단계로 만든 것입니다.

수업 안에서는 다음 순서로 진행합니다.

  1. 확장 설계서와 Spec에서 정한 이번 주 작업을 구현하며 스프린트를 진행하고, 완성된 정적 산출물이 생기면 13장의 파이프라인으로 배포합니다.
  2. 발표 준비: 배포 URL, 검증 코드(deploy-checker 정의와 훅 설정), 방법론 산출물(Charter, Spec)을 한자리에 모으고, 시연할 시나리오 3가지(정상, 경계값, 비정상 입력)를 초안으로 적습니다. 이렇게 모은 발표·검증 산출물은 그대로 면접 답변의 소재로 연결됩니다.

코드-문서 동기화 점검(sync)과 짝과의 크로스 테스트는 발표 준비와 함께 과제·자율 활동으로 이어집니다. 키트의 sync/sync_체크리스트.md로 Spec의 R1~R3(이상)과 구현 상태를 대조하고, 크로스테스트_기록표.md의 시나리오 3가지로 짝의 산출물(가능하면 배포 URL)을 시험해 기록표를 주고받습니다. 받은 기록은 발표 시연과 다음 스프린트의 입력물이 됩니다.

17. 과제

다음 수업 전까지 week09/과제/에 제출합니다. 프로젝트 폴더에 산출물이 아직 적으면 개인 프로젝트 폴더나 공용 재료(키트의 site/를 복사해 자기 손으로 위반을 추가·제거한 판, 첫 배포 실습의 게임 폴더)로 수행합니다.

  1. 배포 전 점검 적용(week09/과제/). deploy-checker를 자기 프로젝트 폴더에 투입한 점검 보고서와 지적 항목의 처리 계획을 과제_점검보고.md에 적고, 위반이 없었다면 통과 보고와 점검 범위를 기록합니다. 검토자 성능 재검증으로 자기 폴더에 위반 1건을 일부러 심어 검토자가 잡는지 확인한 뒤 제거하고, 심은 위반·발견 여부·오탐 여부의 3줄을 과제_재검증.md에 남깁니다.
    • 의도 기록: Spec의 품질 요구사항(배포 조건)과 점검 항목의 대응 관계, 그리고 Claude에게 “이 Spec의 검증 방법에서 빈틈을 세 가지 찾아 지적하라”라고 요청해 받은 지적 중 반영한 것 1건(week09/과제/의도기록.md)
  2. 파이프라인·배포 완성(week09/과제/). 9장의 pipeline.sh에 종료 코드 분기를 완성하고 정상 실행에서 종료 코드가 0인지 확인합니다. 자기 프로젝트용으로 조정한 deploy.sh(자기 검사 1개 이상 추가)와, 이 파이프라인으로 배포한 최신 URL을 과제_배포기록.md에 기록합니다. 위반을 일부러 넣었을 때 중단되는 출력과 정리 후 통과되는 출력을 각 1회 붙입니다.
    • 의도 기록: 추가한 검사의 선택 이유와, 발표에서 시연할 시나리오 초안 3줄(week09/과제/의도기록.md)
  3. 동기화 점검과 크로스 테스트(week09/과제/). sync/sync_체크리스트.md를 week09/sync점검.md로 복사해 Spec의 R1~R3(이상)과 구현 상태를 대조하고, 어긋난 곳마다 코드 수정인지 문서 수정인지 조치를 정해 실행합니다. 짝과 산출물을 교환해 크로스테스트_기록표.md의 시나리오 3가지(정상, 경계값, 비정상 입력)로 시험하고 기록표를 주고받습니다.

채점은 보고서 분량이나 검사 개수가 아니라 판정 기록의 정직성(누락·오탐을 숨기지 않았는가)과 중단·통과 증빙의 실재성을 중심으로 합니다.
