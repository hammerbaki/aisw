하네스와 루프 엔지니어링

실습 자료 이 주차 키트 파일 보기 · 내려받기

지난주에 만든 RAG 챗봇 rag_chat.py는 질문마다 검색을 돌렸습니다. 코드가 무조건 검색을 실행하고 그 결과를 프롬프트에 붙였습니다. 이 수업에서는 그 판단을 AI에게 넘깁니다. 검색기를 도구로 등록해 두고, 부를지 말지를 AI가 정하게 합니다(하네스). 그리고 도구가 실패했을 때 프로그램이 멈추지 않고 오류를 돌려보내 AI가 다시 시도하게 만듭니다(루프). 마지막으로 반복 절차는 스킬로, 도구는 MCP로 포장해 내 스크립트 밖에서도 쓰게 합니다.

진행은 세 부분입니다. ① 도구 사용: 도구 정의와 도구 요청 · 결과가 오가는 모양을 보고, RAG 검색기를 AI가 스스로 부르는 도구로 만들어 도구 설명이 호출 판단을 어떻게 바꾸는지 봅니다(실습 1). ② 루프: 검증 없는 계산 도구가 어떻게 실패하는지 겪고, 검증과 폴백을 붙여 AI가 대처하게 만든 뒤, 루프의 세 형태와 평가를 봅니다(실습 2). ③ 부품으로 포장: 부품 지도를 보고, 점검 절차를 스킬로 만들고, 계산 도구를 MCP 서버로 포장해 Claude Code에 연결합니다(실습 3 · 4). 시작은 수업마다 같습니다. 환경 접속과 자료 받기(0장)입니다.

0. 시작하기: 환경 접속, 자료 받기, API 연동 · RAG 되짚기

수업은 수업마다 같은 순서로 시작합니다. 서버에 접속하고, 터미널 2개를 배치하고, Claude Code가 동작하는지 점검하고, week07 자료를 받습니다. 처음이거나 절차를 잊었어도 이 장만 따라오면 실습을 시작할 수 있습니다.

0-1. 실습 환경 접속과 점검

앞선 수업에서 갖춘 환경을 그대로 다시 엽니다. 처음이거나 절차를 잊었다면 아래 「ssh로 서버 첫 접속」부터 봅니다.

  1. 서버 접속. PowerShell에서 ssh 아이디@서버주소(비밀번호는 쳐도 안 보임). 프롬프트가 [아이디@실습서버 ~]$로 바뀌면 성공. VS Code Remote-SSH를 쓰면 같은 프롬프트가 VS Code 터미널에 뜹니다.
  2. 터미널 2개 배치. 터미널 1 = Claude Code(지시하는 창), 터미널 2 = 서버 명령(슬라이드의 [서버 터미널]). 나란히 열고 Claude Code는 닫지 않은 채 오갑니다. 두 터미널의 현재 폴더는 각각 따로 바뀝니다. 한쪽에서 cd를 해도 다른 쪽은 움직이지 않습니다. 강의안의 배지 [서버 터미널]이 터미널 2이고, claude가 떠 있는 동안의 입력은 [Claude Code 안]입니다.
  3. 환경을 점검합니다. claude 버전 → API 키 → 모델 순서로, 아래 명령을 그대로 칩니다.
서버 터미널 
   claude --version
   echo ${ANTHROPIC_API_KEY:0:8}
   2.x.x  (버전 숫자는 달라도 됩니다)
   sk-ant-a  (빈 줄이면 키 없음 → cat ~/*.txt의 키를 등록)
Claude Code 안 
   > /status
     Model: haiku
   > /exit

비밀번호를 잊었으면 손을 들어 알립니다. Remote-SSH가 안 되면 PowerShell 창 2개로 진행합니다. Model이 haiku가 아니면 /model에서 다시 선택합니다. 이 모델은 Claude Code 대화의 모델입니다. 도구 챗봇과 계산 도구가 부르는 API 모델은 환경변수 COURSE_MODEL(없으면 키트 코드의 기본값 claude-haiku-4-5-20251001)입니다. echo 줄이 빈 줄이면 cat ~/*.txt의 키를 ~/.bashrc에 등록합니다. 도구 챗봇과 계산 도구가 이 키로 API를 부릅니다. 앞 8자 sk-ant-a는 모든 키가 같은 접두어라 비밀이 아니고, 그 뒤는 화면에 출력하지 않습니다.

ssh로 서버 첫 접속: 내 PC에서 서버 안으로. 처음이거나 잊은 사람만 봅니다.

  1. PowerShell을 엽니다. 시작 검색 “Windows PowerShell” 또는 Win+X → 터미널.
  2. ssh 아이디@서버주소. 아이디 = 이름 영문 약자+성 (예: 홍길동 → gdhong). 계정 목록은 덱의 「접속 · 첫 접속」 장에 있습니다.
  3. 처음이면 yes 입력. continue connecting? 질문은 첫 접속에만 나옵니다.
  4. 비밀번호 입력. 쳐도 화면에 안 보이는 게 정상. 끊기면 다시 ssh부터.
  5. 초기 비밀번호라면 passwd로 변경. 초기 비밀번호는 전원 공통이니 반드시 바꿉니다.
내 PC · PowerShell → 서버 접속 
   PS C:\Users\이름> ssh 아이디@서버주소
   ... continue connecting? (yes/no)? yes  # 첫 접속에만
   아이디@서버주소's password:  # 입력해도 안 보임
   [아이디@실습서버 ~]$  # 접속 성공!
   [아이디@실습서버 ~]$ passwd
   # 현재 비밀번호 → 새 비밀번호 2번 → updated successfully
  • 확인 1 프롬프트가 내 위치를 알려줍니다 PS C:\Users\이름> = 내 PC, [아이디@실습서버 ~]$ = 서버.

Remote-SSH 확장 설치와 서버 연결.

  1. VS Code 설치 (최초 1회). code.visualstudio.com에서 기본값으로 설치합니다.

1-1. 왜 도구이고 왜 루프인가

지난주의 RAG 챗봇 rag_chat.py와 이번 주의 도구 챗봇은 같은 검색기를 씁니다. 달라지는 것은 아래 두 가지입니다.

지난주까지 이번 주
검색을 누가 정하나 코드가 정합니다. “안녕하세요”라고 인사만 해도 먼저 검색해, 관계없는 청크 3개가 근거로 붙습니다 AI가 도구 설명(description)을 보고 정합니다. 인사에는 바로 답하고, 학과 FAQ 질문에만 검색 도구를 부릅니다
실패하면 어떻게 되나 정해진 순서로 한 번 실행하고 끝납니다. 결과를 코드가 검사해 AI에게 돌려보내는 단계가 없습니다 코드가 도구 인자를 검사해, 잘못되면(예: 음수 금액) 오류를 tool_result로 돌려보냅니다. AI가 오류를 읽고 사과 · 대안을 만듭니다. 코드가 판정하고 AI가 다시 하는 이 반복이 검증 · 폴백 루프입니다

검증 · 폴백 루프는 AI가 판정하는 도구 호출 루프, 다른 AI가 판정하는 판정자 루프와 함께 루프 엔지니어링에서 다룹니다. 활용 예. Claude Code도 파일 읽기 · 명령 실행을 도구로 부르고, 실패하면 오류를 읽고 다시 시도합니다. 이번 주에는 그 구조를 내 코드로 만듭니다.

핵심. 하네스는 AI를 감싸는 코드 층입니다. 무엇을 할 수 있는지(도구)와 무엇을 하면 안 되는지(검증)를 코드가 정합니다.

1-2. 이번 주차에 배우는 네 가지

1 · 2는 우리가 직접 짠 챗봇 프로그램을 고치고, 3 · 4는 이미 만들어진 Claude Code에 작업 설명서와 계산 도구를 더해 줍니다. 흐름은 도구 사용 → 검색기 도구화 → 도구 설계 · 루프 → 검증과 폴백 → 부품 지도 → 스킬 → MCP입니다.

  1. 도구 사용: 검색할지는 AI가, 실행은 코드가. 검색기의 이름 · 용도 설명 · 받을 값의 형식(입력 스키마)을 AI에게 알립니다. AI가 검색을 요청하면(tool_use) 코드가 실행해 결과를 돌려줍니다(tool_result).
  2. 검증과 폴백: 실패를 오류 메시지로 알린다. AI가 만든 값(예: 음수 금액)도 사용자 입력처럼 코드가 검사합니다. 잘못된 값이면 멈추지 않고, 결과 대신 오류 메시지를 AI에게 돌려줍니다(폴백). AI가 오류를 읽고 사과하거나 대안을 냅니다.
  3. 스킬: 필요할 때만 읽히는 작업 설명서. 자주 쓰는 점검 절차를 SKILL.md 한 장에 적어 /이름으로 부릅니다. 언제 쓰는지(description) · 이유를 붙인 규칙 · 지어내지 말라는 지시를 담습니다. 고정 테스트와 흔한 잘못 3가지(안티패턴)로 점검합니다.

2. 도구 사용: AI가 부를지 정하고, 코드가 실행한다

2-1. 판단은 모델에게, 실행은 코드가

  1. 판단을 모델에게 넘기는 구조 (tool use). API 호출에 도구 목록(이름 · 설명 · 입력 스키마)을 함께 보내면, 모델이 답을 직접 만들지 도구를 부를지 판단합니다. OpenAI · Google Gemini는 같은 기능을 function calling(함수 호출)이라 부릅니다.
  2. 실행 주체는 코드. 모델은 “이 도구를 이 인자로 불러 달라”고 요청만 하고, 실제 실행은 우리 코드가 합니다. 무엇이 실행될 수 있는지를 코드가 최종 결정하는 것이 보안의 기초입니다.
  3. faq_tool_chat.py가 이 사이클을 돈다. ask()가 ①~④를 반복하고, 도구 실행은 handle_tool_use()가 맡습니다. Claude Code의 파일 읽기와 명령 실행도 같은 사이클입니다.
순서 방향 무엇이 오가나
① 코드 → AI 질문과 도구 목록을 함께 보냄 tools=[FAQ_TOOL]
② AI → 코드 “faq_search를 이 검색어로 불러 줘” tool_use
③ 코드 → 도구 handle_tool_use가 FAQ를 검색
④ 코드 → AI 검색 결과를 대화에 붙여 다시 보냄 tool_result
AI → 코드 결과를 읽고 최종 답을 씀 end_turn 
sequenceDiagram
    participant C as 내 코드 ask() · faq_tool_chat.py
    participant M as Claude API · 모델이 판단
    participant T as 도구 실행 · handle_tool_use
    C->>M: ① 질문 + 도구 목록 tools=[FAQ_TOOL]
    M-->>C: ② tool_use (faq_search, 검색어)
    C->>T: ③ 실행
    T-->>C: 검색 결과
    C->>M: ④ tool_result 재주입
    M-->>C: 최종 답 (end_turn)

핵심. 도구가 필요 없다고 판단하면 ②에서 tool_use 대신 end_turn으로 바로 답이 오고, ③④는 건너뜁니다. 용어. stop_reason은 응답이 끝난 이유입니다. 재주입은 실행 결과를 대화에 덧붙여 모델에게 다시 보내는 것입니다.

모델의 응답에 담겨 오는 것은 실행 결과가 아니라 요청서뿐입니다. 모델이 아무리 이상한 요청을 만들어도 코드가 거르면 실행되지 않습니다. 지금까지 써 온 Claude Code가 파일을 읽고, 셸 명령을 실행하고, 결과를 보고 다음 행동을 정하던 동작이 정확히 이 사이클입니다.

2-2. 도구는 이름 · 설명 · 입력 스키마 세 칸으로 알린다

  1. name은 부를 때 쓰는 이름. 영문 · 숫자 · 밑줄(_) · 하이픈(-)으로 64자 이내로 짓습니다. 모델은 tool_use에 이 이름을 적어 보냅니다.
  2. description은 언제 쓰는 도구인지. 모델은 코드를 읽지 않고 이 문장만 보고 부를지 정합니다.
  3. input_schema는 인자의 모양. properties에 인자 이름과 형식, required에 꼭 필요한 인자를 적습니다. 모델은 인자를 이 모양의 JSON으로 만듭니다.

faq_tool_chat.py · FAQ_TOOL (줄인 모양)

   FAQ_TOOL = {
     "name": "faq_search",       # 1. 부를 이름
     "description": "",          # 2. 언제 쓰나 (채울 곳)
     "input_schema": {           # 3. 인자의 모양
       "type": "object",
       "properties": {
         "query": {"type": "string"}},
       "required": ["query"],
     },
   }

스키마 읽는 법. properties → 인자 이름: 형식 ("string" 문자열 · "number" 숫자). required → 빠지면 안 되는 인자. 키트의 실제 코드에는 query에 "description": "검색할 질문 문장"이 한 줄 더 있습니다.

주의. input_schema는 형식만 알려 줄 뿐 값을 검사하지 않습니다. 음수나 엉뚱한 문자도 그대로 올 수 있어, 검사는 도구를 실행하는 코드가 합니다. 연결. ask()가 이 dict를 messages.create(tools=[FAQ_TOOL], …)로 질문과 함께 보냅니다. 실습 1에서 직접 채우는 곳은 description입니다.

2-3. 도구 요청과 결과는 messages에 짝으로 쌓인다

  1. 모델의 요청은 tool_use 블록. stop_reason이 tool_use인 응답에 id · name · input이 담겨 옵니다. 실행 결과가 아니라 요청서입니다.
  2. 결과는 tool_result 블록으로. 코드가 실행한 결과를 role이 user인 칸에 넣어 다시 보냅니다. tool_use_id로 어느 요청의 결과인지 짝을 맞춥니다.
  3. 짝이 빠지면 오류. tool_use마다 tool_result가 하나씩 있어야 합니다. 한 응답에 tool_use가 둘이면, tool_result 둘을 다음 user 칸 하나에 함께 넣습니다.

두 번째 호출의 messages: ① 질문 ② AI의 요청서 ③ 코드의 결과

   messages = [
     {"role": "user",                                        # ①
      "content": "API 키를 잃어버렸어요"},
     {"role": "assistant", "content": [{                     # ②
        "type": "tool_use", "id": "toolu_01",
        "name": "faq_search", "input": {"query": "API 키 분실"}}]},
     {"role": "user", "content": [{                          # ③
        "type": "tool_result", "tool_use_id": "toolu_01",
        "content": "유사도 0.82: ## API 키 …"}]},
   ]

ask()에서 tool_use를 꺼내 실행하는 곳 (줄인 모양)

   for block in response.content:          # 응답 조각을 하나씩
       if block.type == "tool_use":        # 요청서만 고른다
           result = handle_tool_use(       # 코드가 실행
               block.name, block.input)    # 도구 이름, 인자
           tool_use_id = block.id          # ③에 붙일 짝 번호

연결. ask()가 이 목록을 만들어 다시 create를 부릅니다. API는 이전 호출을 기억하지 않아(무상태) 요청서와 결과를 통째로 보내야 합니다. 핵심. tool_result가 user 칸에 들어가는 것은 대화가 user와 assistant를 번갈아야 하고, 도구를 실행한 쪽이 사용자 쪽 코드이기 때문입니다.

4. 검색기의 도구화: 질문이 한 종류면 고정 파이프라인, 섞이면 도구화가 낫다

시연에서 AI는 계산이 필요한 질문에만 도구를 불렀습니다. 지난주 RAG 검색기에도 같은 방식을 쓸 수 있습니다. 바뀌는 것은 검색기가 아니라 검색을 부를지 정하는 주체입니다. 선택 기준은 질문의 균일성입니다.

고정 파이프라인 · 워크플로(workflow) 도구화 · 에이전트(agent)
동작 매 질문마다 코드가 검색을 실행. 예측 가능하고 단순하며 검색 누락이 없습니다 AI가 필요할 때만 검색. 유연하지만 아래의 두 오류가 생길 수 있습니다
나은 때 질문이 한 종류뿐일 때. 예: 사내 인사규정 Q&A 봇, 보험사 약관 안내 봇 질문 종류가 섞일 때. 예: 쇼핑몰 고객센터 챗봇(인사 · 배송 조회 · 환불 규정 문의), 사내 업무 비서

도구화의 두 오류.

  • 호출 누락(under-calling). 검색이 필요한 규정 질문인데 AI가 검색 없이 기억으로 답합니다. 근거 없는 답이 나옵니다.
  • 과잉 호출(over-calling). 인사나 잡담에도 검색을 부릅니다. 응답이 느려지고 엉뚱한 문서가 답에 섞입니다.
  • 균형은 description이 정한다. 실습 1에서 description을 채워 이 균형을 맞춥니다.

판정 질문: 「호출 여부를 매번 판단해야 하는가」. 그렇다면 도구화, 아니라면 고정 파이프라인을 고릅니다.

6-4. 참고 · 코드 용어: stop_reason이 반복을 계속할지 정한다

코드에 나오는 말 사이클 무슨 뜻인가
create(…) ① Claude API를 한 번 부르는 함수입니다. 대화 기록(messages)과 도구 목록(tools)을 보내고 응답 r을 받습니다
tools=[FAQ_TOOL] ① 쓸 수 있는 도구의 설명서입니다. 이름 · description · 인자 모양이 들어 있고, 모델은 코드가 아니라 이 설명을 읽고 부를지 정합니다
r.stop_reason ② 응답이 왜 멈췄는지 알려 주는 값입니다. "tool_use"는 도구를 실행해 달라며 멈춘 것, "end_turn"은 답을 다 쓴 것입니다
tool_use 블록 ③ 응답 안의 도구 요청서입니다. 도구 이름(faq_search)과 인자({"query": …})가 들어 있어 handle_tool_use에 그대로 넘깁니다
tool_result · messages ④ tool_result는 실행 결과를 돌려보내는 형식입니다. API는 앞 대화를 기억하지 못하므로 요청서와 결과를 messages에 쌓아 통째로 다시 보냅니다
while · MAX_ROUNDS ② while은 조건이 참인 동안 반복하는 파이썬 문법입니다. MAX_ROUNDS(5회)는 도구 요청이 끝없이 이어지지 않게 막는 상한입니다

4/5에서. 출력 첫 줄이 (도구 호출: …)이면 stop_reason이 tool_use였던 것, (도구 호출 없음)이면 처음부터 end_turn이었던 것입니다. 기억할 것. 모델은 도구를 직접 실행하지 않습니다. tool_use로 요청만 하고, 실행은 우리 코드의 handle_tool_use가 합니다.

6-13. 참고 · 검색 품질: 검색기를 고쳐 올리고, 재현율로 잰다

방식 장점 단점 실무에서는
임베딩 모델 교체 (다국어 모델) 한국어를 학습한 모델은 표현이 달라도 뜻이 같은 문장을 찾습니다 모델이 크면 색인과 검색이 느립니다. 바꾸면 문서 전체를 다시 색인해야 합니다 대상 언어로 평가된 모델(예: bge-m3)을 고르고, 바꿀 때마다 다시 색인합니다
결과 개수 늘리기 (top-k) 놓친 조항이 결과 안에 들어올 확률이 오릅니다 모델이 읽을 글이 늘어 비용이 늘고, 관련 없는 청크가 답을 흐립니다 3~5개로 시작해 재현율을 보며 조정합니다
하이브리드 검색 (키워드 + 의미) 「재택근무」처럼 단어가 그대로 겹치는 조항을 확실히 찾습니다 두 점수를 합치는 규칙을 정해야 하고 구현이 늘어납니다 사내 문서 검색의 흔한 기본 구성입니다(BM25 키워드 검색 + 벡터 검색)
재순위화 (reranking) 넓게 뽑은 후보를 질문과 다시 비교해 순서를 바로잡습니다 단계가 하나 늘어 응답이 느려집니다 후보 20~50개를 뽑은 뒤 상위 3~5개로 줄일 때 씁니다

재는 법. 재현율(Recall@k)은 「질문 → 찾아야 할 조항」 짝 가운데 정답 조항이 상위 k개에 든 비율입니다. 고칠 때마다 같은 짝으로 다시 잽니다. 답의 안전장치. 검색이 놓쳐도 시스템 프롬프트에 「결과에 없으면 지어내지 말고 찾지 못했다고 말하라」를 둡니다. 키트의 embed_search.py는 상위 3개(TOP_K = 3)를 돌려줍니다.

지금 · calc_tool_bare.py의 run_tool

검증을 붙인 코드 · try / except

9-2. 루프 엔지니어링 · ③ 판정자 · 평가: AI가 AI를 평가한다

규칙 채점: 빠르고 저렴하지만 의미를 판단하지 못한다.

  • 정답셋 + 채점기. 수백 건 규모는 눈으로 못 읽으므로 평가를 체계로 만듭니다. 키워드 포함 같은 규칙은 빠르고 공짜지만, 표현만 다른 옳은 답을 탈락시키고 키워드만 넣은 오답을 통과시킵니다.
  • 재현율도 규칙 채점이다. 실습 1에서 본 검색 품질의 재현율도 규칙 채점입니다. 정답 키워드가 상위 3개에 있는지만 세므로, 키워드가 다른 항목에 있어도 맞다고 셉니다.

LLM as Judge (LLM이 심판인 채점): 기준이 품질을 정한다.

  • 채점 기준을 프롬프트로 주고 판정과 이유를 받는다. 융통성이 생기는 대신 비용 · 비결정성이 생깁니다. 규칙 채점을 기본으로 깔고 어려운 축(사실성 · 어조 · 근거 유무)에만 씁니다.
  • 원칙과 한계. 기준을 명시할 것. 기준이 없으면 심판은 인상만으로 점수를 매기고, 기준 한 줄을 지우면 그 축은 판정에서 빠집니다. 심판의 품질이 곧 기준 프롬프트의 품질이라, 실무에서는 채점 기준 문서가 코드처럼 리뷰되고 버전 관리됩니다. 산출물을 만든 대화와 격리할 것(자기 평가는 점수가 후하게 나오는 경향이 있음). 그리고 Judge의 판정도 검증 대상이지 최종 결론이 아닙니다.

면접 질문 “AI 산출물의 품질을 어떻게 관리하는가”에 대한 일반적인 답이 규칙 채점과 LLM as Judge의 조합입니다. 이것이 판정자 루프입니다. 다음. 만든 도구와 절차를 어디에 두고 어떻게 다시 부를지. 부품 지도(Claude Code의 부품 배치)와 스킬(필요할 때 읽히는 절차 문서).

11. 부품 지도

11-1. 확장 기능 지도

공식 문서의 확장 기능 가운데 이 과목에서 다루는 것입니다. 스킬과 MCP는 실습에서 만들어 봅니다.

부품 하는 일 공식 문서
CLAUDE.md · rules 매 세션 읽히는 상주 규칙. paths를 단 rules는 그 경로를 만질 때만 읽힙니다. 매 요청에 실리므로 200줄을 넘기면 분리합니다 docs/en/memory
Skill 호출될 때만 본문이 실리는 절차 문서. /이름으로 부르거나, 모델이 description을 보고 부릅니다 docs/en/skills
Hook · permissions 정해진 시점에 반드시 실행되는 스크립트와 허용 · 차단 목록. CLAUDE.md는 권고, 강제는 이 장치로. 필요할 때 덧붙입니다 docs/en/hooks-guide
MCP 외부 서비스 · 도구 연결의 표준 규약. DB 조회, 사내 시스템, 브라우저 제어처럼 외부 데이터 · 동작이 필요할 때 docs/en/mcp

이 밖에 서브에이전트(분리된 컨텍스트에서 일하고 요약만 돌려주는 보조 AI) · 플러그인(부품 묶음 배포) · 코드 인텔리전스 · 출력 스타일 등이 있습니다. 전체 목록은 공식 문서 https://code.claude.com/docs/en/features-overview 에 있습니다.

11-2. 가장 중요한 축: 로딩 시점

  1. 부품마다 실리는 시점과 양이 다르다. 컨텍스트 윈도우를 아껴 쓰는 문제와 이어집니다.
  2. 많이 실릴수록 비싸다. CLAUDE.md는 매 요청에 전체가 실려 200줄 이내로 둡니다. 다른 부품도 언제 · 얼마나 실리는지로 비용이 정해집니다.
  3. 컨텍스트 밖의 부품도 있다. 훅은 이벤트 발생 시 컨텍스트 밖에서 실행되고(비용 0), 서브에이전트는 별도 컨텍스트에서 돌고 요약만 돌아옵니다.

11-3. 선택 기준 · 부품 고르기: 반복되는 신호와 로딩 시점

  1. 신호가 나타나면 그 부품을 더한다. 아래 표는 공식 문서의 트리거 표를 줄인 것입니다. 같은 문제가 반복되는 신호가 보이면, 그 지식이 언제 · 얼마나 실려야 하는지(로딩 시점)에 맞는 부품을 고릅니다.
  2. 헷갈리기 쉬운 부품 쌍. CLAUDE.md 대 스킬: 늘 필요한 규칙은 CLAUDE.md, 가끔 쓰는 절차는 스킬. 스킬 대 훅: 스킬은 지시라 흔들릴 수 있고, 훅은 강제라 반드시 실행. MCP와 스킬: 경쟁이 아니라 조합(연결은 MCP, 잘 쓰는 법은 스킬).
  3. 처음부터 모두 갖추지 않는다. 부품마다 컨텍스트 비용이 있으므로, 신호가 나타난 부품만 하나씩 더합니다.
신호 도입할 부품 이유(로딩 시점)
프로젝트 규칙(예: 테스트는 pytest로)을 두 번 어겼다 CLAUDE.md 매 요청에 전체가 실림 · 늘 지킬 규칙
같은 절차 문서를 세 번째 붙여넣고 있다 스킬 평소엔 설명만, 쓸 때 본문 · 가끔 쓰는 절차
외부 서비스(예: 노션 · 사내 DB)의 내용을 대화창에 복사해 붙여넣는다 MCP 연결 도구 이름만 상주, 스키마는 쓸 때 · 외부 연결
본 작업과 별개인 조사(예: 로그 분석, 저장소 전체 검색)의 긴 출력이 대화를 채우고 있다 서브에이전트 별도 컨텍스트, 요약만 반환 · 대화 보호
시키지 않아도 매번 실행되어야 한다 훅 컨텍스트 밖에서 이벤트마다 실행 · 강제
두 번째 저장소에 같은 구성이 필요하다 플러그인 위 부품을 묶어 설치 · 저장소 간 재사용

연결. 신호는 무엇이 반복되는지, 로딩 시점은 언제 얼마나 실려야 하는지를 봅니다. 둘이 가리키는 부품이 같을 때 도입합니다.

12. Skill: 절차와 참고 자료

  1. 스킬은 이름 붙인 프롬프트다. 자주 쓰는 지시를 문서로 저장해 두고 /이름으로 부릅니다. 코드가 실행하는 함수가 아니라, AI가 읽고 따르는 문서입니다.
  2. 파일 하나로 만든다. .claude/skills/이름/SKILL.md 파일 하나면 됩니다. 이름은 영문 소문자 · 숫자 · 하이픈으로 짓습니다.
  3. 위는 언제 쓸지, 아래는 어떻게 할지. --- 사이의 머리말(frontmatter)에 적은 description을 보고 AI가 이 스킬을 언제 쓸지 정합니다. 그 아래 본문에는 따를 절차를 적고, 규칙마다 이유를 붙입니다.

규칙과 절차를 두는 위치

위치 읽히는 시점 적합한 내용
CLAUDE.md 매 세션 항상 어떤 작업에든 적용할 규칙
.claude/rules/ paths 지정 시 그 경로를 다룰 때만 특정 폴더의 규칙
.claude/skills/ /이름 호출 · 필요 판단 시 반복 절차 · 참고 자료

예시 · .claude/skills/tip-verify/SKILL.md (줄인 모양)

   ---
   name: tip-verify
   description: 팁 문서를 쓰거나 고칠 때 출처와
     사실을 점검한다. tips/ 폴더 작업 시 사용.
   ---
   # 팁 검증 절차
   1. 각 주장에 출처(파일 경로나 URL)를 붙인다.
      이유: 출처가 없으면 독자가 확인할 수 없다.
   2. 확실하지 않은 내용은 "확인 필요"로 표시한다.
      이유: 추측으로 채우면 틀린 내용이 사실처럼 남는다.

   # 상단 = frontmatter(시작 시 설명만 실림), 아래 = 본문(호출 시 실림)

핵심. 사람이 매번 하던 검증 지시를 스킬 본문에 적어 두는 것입니다. 따를지는 AI가 정하므로 결과는 고정 테스트로 확인합니다. 하네스 A/B 시연의 tip-verify가 실제 예입니다(시연 폴더에서는 하네스/skills/tip-verify/SKILL.md). 출처를 붙이게 하고 모르는 것은 「확인 필요」로 남기게 하는 이 두 규칙이 스킬에 넣는 환각 방지 지침입니다.

   ## 절차  ◀ ③

   ## 환각 방지  ◀ ⑤
   - 근거 칸에는 파일 경로와 찾은 id나 함수 이름을 적는다.
   - 파일을 열 수 없거나 대응이 확실하지 않으면 추측하지 말고 "확인 필요"로 적는다.

14. MCP 서버화

14-1. 스킬은 절차를 글로, MCP는 실행되는 도구를 내놓는다

  1. 실습 1~3에서 만든 것을 밖으로. 도구 정의(실습 1) · 검증(실습 2) · 스킬(실습 3)을 만들었습니다. 그런데 부가세 도구 VAT_TOOL은 calc_tool_bare.py 안에서만 동작합니다. MCP는 이 도구를 표준 규약으로 감싸 Claude Code 같은 MCP 지원 프로그램이 연결해 쓰게 합니다. 내놓는 쪽이 서버, 쓰는 쪽이 클라이언트입니다.
  2. 왜 스킬이 아니라 MCP인가. 스킬은 모델이 읽고 따르는 글이라, 계산을 맡기면 모델이 직접 셈합니다. MCP 도구는 코드가 실행하므로 음수 검사 같은 검증을 함수 안에 둘 수 있습니다.
  3. FastMCP: 함수가 곧 도구 정의. 파이썬 함수를 MCP 서버로 만드는 라이브러리입니다(gofastmcp.com). 함수 이름 · 인자 형 · 독스트링에서 도구 정의가 만들어지므로 description 원칙이 그대로 적용됩니다. 키트는 @mcp.tool 데코레이터 대신 mcp.add_tool(vat_calc) 한 줄로 등록합니다(결과는 같음). 데코레이터는 함수 정의 위에 @이름 한 줄을 붙여 그 함수에 기능을 더하는 파이썬 문법입니다.

이번 예 portfolio-check vat_calc(amount)

vat_calc는 계산이고 음수를 막아야 하므로 MCP 도구로 내놓습니다. 연결. 도구 정의는 FastMCP가 만들고, 검증은 함수 안에 남고, 절차는 스킬이 맡습니다. 둘은 함께 씁니다.

14-2. 왜 MCP인가: 포장하면 한 번 만든 도구를 여러 앱이 쓴다

  1. 한 번 만들어 여러 앱이 쓴다. 같은 calc_mcp.py를 Claude Code · Claude Desktop · Cursor에 연결합니다.
  2. 도구 쪽 코드가 줄어든다. 호출 반복 · API 키 · tool_use 처리는 앱(클라이언트)이 맡습니다.
  3. 모델이 바뀌어도 도구는 그대로. 특정 모델의 API 형식에 묶이지 않습니다.
  4. 컨텍스트를 아낀다. 평소엔 도구 이름만, 상세 스키마는 쓸 때 실립니다.
  5. 사용자가 통제한다. /mcp로 상태를 보고, 도구 실행 전에 허락 창이 뜹니다.

앱마다 따로 연결 대 MCP 하나로. 도구 셋(vat_calc · 사내 DB 조회 · GitHub)과 앱 셋(Claude Code · Claude Desktop · Cursor)을 앱마다 따로 연결하면 도구 3 × 앱 3 = 연결 9개입니다. MCP 규약 하나로 묶으면 도구 3 + 앱 3 = 연결 6개입니다. MCP에서는 도구를 하나 더해도 앱 쪽 코드는 고치지 않습니다.

14-3. 주고받는 것: MCP 서버는 함수를 켜 두고 호출을 기다리는 프로그램이다

서버는 calc_mcp.py를 실행해 둔 파이썬 프로그램입니다. 화면 없이 Claude Code와 메시지만 주고받습니다.

  1. 서버 실행과 초기화 (initialize). Claude Code가 시작할 때 등록된 명령(claude mcp add)으로 calc_mcp.py를 실행하고, initialize 메시지로 서로 버전과 기능을 맞춥니다.
  2. 도구 목록 요청 (tools/list). tools/list 요청에 서버가 함수에서 만든 이름 · 설명 · 입력을 돌려줍니다. 실습 1의 도구 정의 세 칸과 같습니다.
  3. 도구 호출 (tools/call). 계산이 필요하면 Claude Code가 tools/call로 「vat_calc, amount 1200000」을 보내고, 서버가 함수를 실행해 결과 문장을 돌려줍니다.

서버 쪽 · mcp/calc_mcp.py (줄인 모양)

   from fastmcp import FastMCP

   mcp = FastMCP("vat-calc")  # 서버 이름

   def vat_calc(amount: float) -> str:  # 이름 · 입력
       """공급가액(원)을 받아 부가세 10%와 합계 금액을 …"""
       if amount < 0:  # 검증은 함수 안
           return "오류: 금액은 0 이상이어야 합니다"
       vat = round(amount * 0.1)  # 계산해 문장으로 반환

   mcp.add_tool(vat_calc)  # 함수를 도구로 등록
   mcp.run()  # 켜 두고 부탁을 기다림

주고받는 메시지 · 「120만 원 모니터」 질문

   → tools/list
   ← vat_calc · amount(숫자) · "공급가액(원)을…"
   → tools/call vat_calc {"amount": 1200000}
   ← "…부가세 120,000원, 합계 1,320,000원"
   → Claude Code가 보냄   ← 서버가 돌려줌

연결. def 줄의 함수 이름은 name, 인자는 입력 스키마, 독스트링은 description이 됩니다. 실습 1에서 손으로 쓰던 dict를 FastMCP가 만듭니다. 스킬과 차이. 스킬은 Claude가 SKILL.md를 읽고 직접 일하고, MCP는 호출만 하며 계산 · 검증은 서버 함수가 합니다. 언제 부를지는 둘 다 설명 문장(description · 독스트링)이 정합니다. 키트의 실제 파일은 float(amount) 변환과 try/except, fastmcp가 없을 때도 직접 호출이 되게 하는 import 보호, if __name__ == "__main__": 아래의 mcp.run()까지 들어 있습니다(그래서 직접 import해도 서버가 켜지지 않습니다).

18-3. 정리 3/3 · 이번 주: 이번 주에 배운 것 · 다음

배운 것

  • 도구를 실행하는 것은 코드다. AI는 요청서만 만들고, 실행은 handle_tool_use가. 설명은 코드가 아니라 프롬프트.
  • 모델이 만든 인자는 믿지 않는다. 검증하고, 실패는 오류 문자열로 돌려보내고, 사과 · 대안은 모델이. 이것이 루프.
  • 부품마다 실리는 시점이 다르다. CLAUDE.md는 항상, rules는 경로, 스킬은 호출 때, MCP 스키마는 쓸 때.
  • 절차는 스킬, 실행은 MCP. 스킬은 이유를 붙인 절차를, MCP는 검증을 품은 함수를 내놓는다.
  • 판정은 결과로. 고정 테스트 11개가 통과해야 끝. AI의 보고가 아니라 결과로 확인한다.

다음. 기말시험 · 객관식 4지 선다 · 오픈북. 범위는 프롬프트와 컨텍스트 엔지니어링부터 이 수업까지. 확인 포인트를 다시 읽는 것이 준비입니다.

남은 것 · 이 수업의 다음 단계.

  • 루프 반복 자동화. AI가 테스트로 결과를 확인하고, 실패하면 고쳐 다시 도는 과정을 사람 없이 끝까지 돌립니다. 반복 상한과 사람에게 넘기는 조건이 핵심입니다.
  • 멀티 에이전트 상호작용. 조사 · 작성 · 검토를 맡은 에이전트 여럿이 결과를 주고받습니다. 검토 에이전트가 판정자 루프(LLM as Judge)를 맡습니다.

재료(도구 · 검증 · 스킬 · MCP)는 이미 손안에 있습니다. 자기 PC · 자기 키에서 시작합니다.

18-4. 한 학기 정리 · 실무 적용: 회사에서는 안전장치를 먼저 두고 AI에 맡기는 범위를 넓힌다

처음부터 에이전트를 만들지 않습니다. 7주에 배운 것을 이 순서로 씁니다.

  1. 첫 주: 읽고 지킨다. 기존 코드를 AI와 읽어 명세로 정리하고(2주), 테스트부터 돌립니다(3주). 팀 규칙은 CLAUDE.md에 적습니다(5주).
  2. 첫 달: 반복 일을 넘긴다. 지시는 필요한 자료만 골라 주고(4주), 사내 문서 질문은 근거와 함께 답하게 합니다(6주). 자주 하는 점검은 스킬로 만듭니다.
  3. 그다음: 도구를 연결한다. 사내 기능은 검증을 넣은 MCP 도구로 내놓습니다. 운영 배포처럼 되돌릴 수 없는 일은 도구로 만들지 않습니다(7주).
