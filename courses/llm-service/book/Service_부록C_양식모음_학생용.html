[부록 C] 양식 모음

2027학년도 「LLM 서비스 개발」의 준비 중인 교재입니다. 편집 상태를 검토하기 위해 미리 공개한 것으로, 수업 전에 내용과 순서가 바뀔 수 있습니다.

「LLM 서비스 개발」 1~13장의 공통 부록 · 2026-11-18 기준(키트는 각 장의 Service_NN장, 2026-11-18 판)

이 부록은 각 장의 실습 키트에 흩어져 있는 양식(*_양식.md)과 템플릿(이슈·풀 리퀘스트 템플릿, 지시문, 견본)을 장 순서대로 한곳에 모은 것이다. 이 과목은 4장부터 서비스 여섯 개를 차례로 만든다. 서비스마다 분석하는 대상이 다르므로(화면, 코드, 사람의 경험, 네트워크 호출, 애플리케이션, 자기 결과물) 장마다 쓰는 양식도 다르다. 그러나 근거를 표시하는 방법, 요구 문장의 형식, ID로 문서를 서로 가리키는 방법은 모든 장이 같다. 이 부록의 목적은 두 가지이다. 하나는 장을 건너 양식을 견주어 그 공통의 규칙을 한눈에 보이는 것이고, 다른 하나는 같은 학기의 프로젝트실습Ⅰ에서 팀원 모두가 같은 형식으로 쓰고 같은 ID로 문서를 가리키며 키트의 검사 도구를 그대로 돌릴 수 있게 하는 것이다.

절 번호는 장 번호와 같다. C-4는 4장의 양식, C-13은 13장의 양식이다. 각 양식은 다음 네 가지를 차례로 적는다.

  1. 쓰는 곳. 어느 장의 어느 절에서 무엇을 만드는 데 쓰는가, 복사해 둘 자리는 어디인가.
  2. 키트 경로. 받은 키트(~/kits/, 부록 A-12-3) 안의 경로와 줄 수. 키트 저장소의 클론 ~/kits-repo 아래에도 같은 경로로 있다.
  3. 양식 본문. 키트의 파일을 줄이지 않고 그대로 옮겼다. 칸 이름, 안내 문장, 「 」 자리가 모두 원문과 같다. 키트에 양식 파일이 없는 8장은 본문이 정한 칸을 빈 꼴로 옮겼고, 그 사실을 그 절에 밝혔다.
  4. 프로젝트실습Ⅰ에서 바꿀 곳. 팀의 주제로 쓸 때 고칠 자리와 그대로 둘 자리.

양식을 쓰는 방법은 모든 장에서 같다. 양식을 개인 실습 저장소(~/llm-service-lab/)의 그 장 폴더로 복사한 뒤 「 」 자리를 채우고, 안내 문장(>로 시작하는 줄)은 다 채운 뒤 지운다. 키트 안의 양식 파일 자체는 고치지 않는다. 키트의 교수/ 폴더(교수 전용의 예시와 견본 답)는 학생용 키트 저장소에 들어 있지 않으며, 이 부록에도 싣지 않는다. 이 부록과 키트의 원문이 다르면 키트의 원문이 우선한다.

양식에 쓰는 ID와 판

양식들은 ID로 서로를 가리킨다. 7장에서 문제 정의의 P-01이 페르소나 PS-1을 가리키고, 8장의 API 명세가 다시 P-01을 가리킨다. 4장 명세의 REQ-04를 수용 기준 AC-04-1, 5장의 인수 조건, 13장의 문제 목록과 이슈, 커밋 메시지가 가리킨다. 형식이 하나라도 어긋나면 사람은 문서를 따라가지 못하고 키트의 검사 도구(4장 ears_check.py, 7장 check_trace.py, 12장 spec_checklist.py, 13장 priority.py)는 연결을 찾지 못한다. 아래 표는 1~13장이 함께 지키는 ID의 형식이다.

요구와 설계의 ID

대상 형식 처음 정하는 장 가리키는 양식

  • 요구 문장의 형식은 4장 5절의 EARS 문형을 따른다: - **REQ-01** [문형] 문장. (근거). 문형은 상시, 사건, 상태, 선택, 원치 않는 동작, 복합 가운데 하나이고, 근거는 (관찰: …), (자료: …), (조사: …), (정함: …), (추측: …) 가운데 하나이다. 6장은 근거를 (근거: 줄 번호)로, 11장은 표의 「근거」 칸에 확인·추측·정함으로 적는다. 10장 키트의 명세 양식은 문형을 괄호로 적는 다른 꼴(- REQ-01 (사건): …)을 쓴다.
  • 명세에 요구를 더하거나 고친 줄 끝에는 ← 추가, ← 고침을 붙인다(5장 8-6, 6장 5-5, 12장 8-6, 13장 9-6).
  • 13장의 연습 견본(「잡프렙」, 지어낸 서비스)의 명세는 세 자리 요구 번호(REQ-007)를 쓴다. 연습 견본에만 있는 형식이며 자기 서비스의 명세에는 쓰지 않는다.
  • ID는 한 번 붙이면 바꾸지 않는다. 요구를 지울 때도 번호를 다시 매기지 않고, 그 번호를 비워 둔 채 변경 이력에 지운 까닭을 적는다. 다른 문서와 커밋이 그 번호를 가리키고 있기 때문이다.

명세의 판과 태그

프로젝트실습Ⅰ에서의 ID와 판 (권장안)

  • ID의 형식은 위 표를 그대로 쓴다. 키트의 검사 도구가 이 형식을 찾는다. 예를 들어 ears_check.py는 --id "REQ-\d{2}"로 두 자리 번호를 찾는다.
  • 요구 번호는 팀 명세의 REQ-01부터 차례로 매긴다. 여러 팀원이 같은 날 요구를 더할 때는 각자 번호를 정하지 말고, 명세의 변경을 풀 리퀘스트 하나로 모아 병합 직전에 번호를 확정한다. 병합 충돌이 번호에서 나기 때문이다(3장 6절).
  • 판은 팀 명세의 첫 판을 v1, 태그를 spec-v1로 하고(10장 8-10과 같은 꼴), 리뷰를 거쳐 내용이 바뀔 때마다 하나씩 올린다. 주차나 장 번호와 맞추지 않는다.
  • 위 세 항목은 이 부록의 권장안이다. 프로젝트실습Ⅰ에서 다른 규칙을 정하면 그 규칙을 따른다.

# 풀 리퀘스트 리뷰 점검표

리뷰어가 「Files changed」 탭을 열기 전에 이 점검표를 옆에 둔다. 모든 항목에 답한 뒤 결정(Comment, Approve, Request changes)을 고른다. 근거: Google Engineering Practices 「What to look for in a code review」, GitHub Docs 「Reviewing proposed changes in a pull request」(2026-11-14 확인).

## 1. 리뷰를 시작하기 전

- [ ] 풀 리퀘스트 설명을 읽고, 무엇을 왜 바꾸었는지 한 문장으로 말할 수 있다
- [ ] 연결된 이슈(`Closes #n`)를 열어 완료 조건을 확인하였다
- [ ] 바뀐 파일의 수와 줄 수가 이슈 하나의 크기에 맞다(관계없는 변경이 섞이지 않았다)

## 2. 내용

- [ ] 이슈의 완료 조건을 충족한다
- [ ] 바뀐 줄을 한 줄도 빠짐없이 읽었다. 이해하지 못한 줄은 질문으로 남겼다
- [ ] 파일 전체의 맥락에서 보아도 어색하지 않다(바뀐 줄 위아래를 펼쳐 보았다)
- [ ] 이름(파일, 브랜치, 제목)이 저장소 규칙을 따른다
- [ ] 충돌 표시(`<<<<<<<`, `=======`, `>>>>>>>`)가 남아 있지 않다
- [ ] 비밀번호, API 키, 토큰, 개인 정보가 들어 있지 않다

## 3. 코멘트의 문장

- [ ] 코멘트는 사람이 아니라 변경을 가리킨다(「당신은 ~」 대신 「이 줄은 ~」)
- [ ] 고칠 것을 요청할 때는 까닭을 함께 적었다
- [ ] 꼭 고치지 않아도 되는 의견에는 앞에 `사소함:`을 붙였다
- [ ] 바로 고칠 수 있는 한두 줄은 「제안(suggestion)」으로 고친 문장을 직접 보였다
- [ ] 잘된 점이 있으면 한 가지 이상 적었다

## 4. 결정

| 상황 | 결정 |
|---|---|
| 완료 조건을 충족하고, 남긴 코멘트가 모두 사소함이다 | Approve |
| 질문만 있고 아직 판단하지 못하였다 | Comment |
| 완료 조건을 충족하지 못하거나, 충돌 표시·비밀 정보가 있다 | Request changes |

- [ ] AI 도구가 만든 리뷰 초안을 썼다면, 초안의 모든 지적을 diff에서 직접 확인하였고 확인하지 못한 지적은 지웠다

# 논의 기록의 동의 문구 (견본)

> 논의를 시작하기 전에 묻는 사람이 아래 문구를 소리 내어 읽어 준다. 「 」 자리만 바꾸고 항목을 빼지 않는다. 같은 조의 조원끼리라도 읽는다. 조 밖의 사람에게 물을 때도 같은 문구를 쓴다.

---

이 논의는 「프로덕트 이름」을 고치기 위한 것이다. 지난 「기간」 동안 실제로 겪은 일을 듣고자 한다.

1. **목적.** 다음에 고칠 것을 정하기 위한 조사이다. 기록은 페르소나와 문제 정의를 쓰는 데에만 쓴다.
2. **적는 것.** 겪은 일을 적는 사람이 요약해 적고, 일부 말은 들은 그대로 적는다. 이름, 연락처, 학번은 적지 않고 「참여자 1」처럼 번호로 적는다.
3. **녹음.** 녹음과 촬영을 하지 않는다.
4. **보관과 기간.** 기록은 조의 비공개 저장소에 두고, 「프로젝트가 끝나면」 지운다. 조원과 지도 교수가 볼 수 있다.
5. **AI 도구.** 번호로 바꾼 기록을 AI 코딩 도구(Claude Code)에 넣어 정리의 초안을 만든다. 이 도구는 외부 회사(Anthropic)의 서비스이다.
6. **거부와 중단.** 답하기 싫은 질문은 넘겨도 되고, 중간에 그만두어도 된다.
7. **철회.** 논의가 끝난 뒤에도 기록을 지워 달라고 할 수 있다. 요청을 받으면 기록과 그 기록을 인용한 줄을 지운다.
8. **확인.** 끝나면 기록을 보여 준다. 사실과 다르거나 빼고 싶은 내용을 말해 달라.

위 내용을 듣고 논의에 참여하는 데 동의하는가?

---

- 기록 머리의 「동의」 칸에 `기록을 저장소에 남기고 AI 도구에 읽힌다는 것을 알리고 동의를 받았다`를 적는다.
- 동의를 받지 못했으면 기록하지 않는다.
- 근거: GOV.UK Service Manual 「Getting informed consent for user research」(녹음 여부, 자료를 다루는 다른 조직, 철회와 삭제), 개인정보 보호법 제15조 제2항의 고지 항목(목적, 항목, 기간, 거부할 권리)을 조원 논의에 맞게 옮겼다.
  • 프로젝트실습Ⅰ에서 바꿀 곳. 「 」 자리(프로덕트 이름, 기간, 지우는 때)만 바꾸고 항목을 빼지 않는다. 기록을 다른 AI 도구에 넣는다면 5항의 도구 이름과 회사를 그것으로 바꾼다.

# 요구사항 명세서: 문서 질의응답 (서비스 4)

이 양식을 `docs/요구사항명세서.md`로 복사한 뒤 낫표로 비워 둔 다섯 자리를 채운다: `cp -n docs/요구사항명세서_양식.md docs/요구사항명세서.md`. 요구 번호와 문형(EARS)은 바꾸지 않는다. 요구의 형식은 4장의 명세서와 같다: `- **REQ-01** [문형] 문장. (관련: 구현하는 자리)`. 문형의 이름도 4장과 같다(상시, 사건, 상태, 선택, 원치 않는 동작). 끝의 `(관련: …)`은 그 요구를 구현하는 파일과 함수이고, 「완성되어 있음」이 붙은 요구는 키트가 이미 구현하였다. 요구 아래의 들여 쓴 줄은 요구를 풀어 쓴 설명이다.

- 서비스: 서비스 4 「문서 요약과 질의응답」의 질의응답 기능(10장). 요약 기능은 9장의 `ch09/`에 있다.
- 자료: `자료/`의 가상 문서 다섯 개(학과 취업지원실의 안내, 규정, 공고 발췌)
- 판: v1

## 검색

- **REQ-01** [사건] 사용자가 질문을 보내면, 시스템은 자료 색인에서 질문과 코사인 유사도가 높은 순으로 청크 「  」개를 근거로 골라야 한다. (관련: `rag/search.py`의 `vector_search`)
- **REQ-02** [선택] 환경 변수 `EMBED_BACKEND`가 `ollama`인 경우, 시스템은 Ollama의 임베딩 모델로 임베딩해야 한다. (관련: `rag/embedder.py`, `rag/store.py`, 완성되어 있음)
  - 그렇지 않으면 글자 n-gram 대체 임베딩을 쓴다. 어느 쪽이든 쓴 임베딩 경로와 모델을 색인에 함께 기록한다.
- **REQ-03** [상시] 시스템은 색인을 만들기 전에 문서의 HTML 주석(`<!-- -->`)을 걷어 내야 한다. (관련: `rag/chunker.py`의 `clean_text`, 완성되어 있음)

## 답변

- **REQ-04** [상시] 시스템은 근거 블록, 질문, 지시의 순서로 증강 프롬프트를 만들고, 근거 블록마다 1부터 시작하는 번호와 출처(문서 제목 > 절 제목)를 붙여야 한다. (관련: `rag/answer.py`의 `build_prompt`)
- **REQ-05** [상시] 시스템은 답의 문장마다 사용한 근거의 번호를 [1] 형식으로 붙이도록 지시해야 한다. (관련: `build_prompt`)
- **REQ-06** [원치 않는 동작] 만약 1위 근거의 유사도가 기준값 「  」보다 낮으면, 시스템은 LLM을 부르지 않고 「자료에 없다」 문장(`rag/config.py`의 `NO_ANSWER`)으로 답해야 한다. (관련: `answer`, 완성되어 있음. 기준값은 환경 변수 `RAG_MIN_SCORE`)
- **REQ-07** [원치 않는 동작] 만약 근거에 질문의 답이 없으면, 시스템은 같은 「자료에 없다」 문장으로만 답하도록 지시해야 한다. (관련: `build_prompt`)

# 심각도 기준표

Nielsen(1994)의 0~4 척도를 이 과목의 프로덕트에 맞추어 예를 붙였다. 등급의 이름과 뜻은 원문을 따르고, 예는 이 과목에서 정한 것이다.

## 1. 등급

| 등급 | 이름 | 뜻 | 연습 견본(잡프렙)에서의 예 |
|---|---|---|---|
| 0 | 문제 아님 | 사용성 문제라고 보지 않는다 | 카드 모서리가 둥글지 않다(평가자의 취향) |
| 1 | 겉모양 문제 | 시간이 남으면 고친다 | 버튼 사이 간격이 화면마다 조금 다르다 |
| 2 | 작은 문제 | 고치되 우선순위는 낮다 | 영어 약어(JD)가 낯설지만 눌러 보면 무엇인지 안다 |
| 3 | 큰 문제 | 고치는 것이 중요하며 우선순위가 높다 | 요약이 나오는 동안 아무 표시가 없어 버튼을 거듭 누르고 결과가 겹친다 |
| 4 | 사용성 재앙 | 출시 전에 반드시 고친다 | 저장한 지원 일정이 새로 고침하면 사라진다 |

## 2. 등급을 정할 때 보는 것

| 요소 | 묻는 것 | 높이는 쪽 |
|---|---|---|
| 빈도 | 이 문제를 겪는 사용자가 많은가, 자주 겪는가 | 대부분의 사용자가 핵심 과업에서 겪는다 |
| 영향 | 겪었을 때 넘어가기 어려운가 | 과업을 끝내지 못하거나, 자료를 잃거나, 틀린 결과를 믿게 된다 |
| 지속성 | 한 번 알면 피해 갈 수 있는가, 매번 겪는가 | 알아도 매번 같은 손해를 본다 |
| 시장 영향 | 넘어가기 쉬워도 제품의 평판을 해치는가 | 첫 화면에서 보이거나, 신뢰를 잃게 한다 |

- AI 기능의 문제는 「틀린 결과를 믿게 되는가」를 영향에 넣는다. 근거 없는 요약을 사용자가 그대로 믿고 지원서를 쓰면, 화면에서는 오류가 보이지 않아도 영향이 크다.
- 자료를 잃는 문제(지운 것을 되살릴 수 없음, 저장한 것이 사라짐)는 드물게 일어나도 3 이상으로 본다.

## 3. 매기는 방법

1. 문제를 찾는 동안에는 찾는 데 집중하고, 다 찾은 뒤에 매긴다.
2. AI의 보고에 붙은 등급은 참고만 한다. 내 화면에서 재현한 뒤 위 네 요소로 내가 다시 매긴다.
3. 등급을 정하기 어려우면 두 등급 가운데 높은 쪽을 적고, 까닭을 문제 목록의 비고나 이슈에 적는다.

## 4. 우선순위 (이 과목의 규칙)

- 우선순위 점수 = 심각도(0~4) x 빈도(1 드묾, 2 가끔, 3 자주)
- 빈도는 과업을 하며 그 문제를 만난 정도로 정한다. 1은 특정한 조작(빈 값, 두 번 누르기, 창 좁히기)을 해야 나타나는 것, 2는 과업 하나에서 나타나는 것, 3은 과업 둘 이상이나 첫 화면에서 나타나는 것이다.
- 심각도 0은 목록에서 뺀다. 심각도 4는 점수와 관계없이 맨 앞에 둔다. 점수가 같으면 심각도가 높은 쪽이 앞선다.
- 계산은 `도구/priority.py`가 한다(`python 도구/priority.py 문제목록.md`).
