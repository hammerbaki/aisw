[부록 C] 양식 모음

2027학년도 「LLM 서비스 개발」의 준비 중인 교재입니다. 편집 상태를 검토하기 위해 미리 공개한 것으로, 수업 전에 내용과 순서가 바뀔 수 있습니다.

「LLM 서비스 개발」 1~13장의 공통 부록 · 2026-11 기준(키트는 2026-11-14 판)

이 부록은 각 장의 실습 키트에 흩어져 있는 양식(*_양식.md)과 템플릿(이슈·풀 리퀘스트 템플릿, 배포 워크플로, 설계 문서의 견본)을 장 순서대로 한곳에 모은 것이다. 이 과목의 1~13장은 공통 사례 「취업 준비 지원 서비스」(jobprep) 위에서 조사, 정의, 설계, 구현, 평가를 한 번씩 거친다. 같은 학기의 프로젝트실습Ⅰ에서는 팀이 자기 주제로 같은 절차를 되풀이한다. 그때 팀원 모두가 같은 형식으로 쓰고, 같은 ID로 문서를 서로 가리키고, 키트의 검사 도구를 그대로 돌릴 수 있도록 하는 것이 이 부록의 목적이다.

절 번호는 장 번호와 같다. C-4는 4장의 양식, C-13은 13장의 양식이다. 각 양식은 다음 네 가지를 차례로 적는다.

  1. 쓰는 곳. 어느 장의 어느 절에서 무엇을 만드는 데 쓰는가.
  2. 키트 경로. 받은 키트(~/kits/, 부록 A-8) 안의 경로. 배포 폴더 $KIT_HOME 아래에도 같은 경로로 있다.
  3. 양식 본문. 키트의 파일을 그대로 옮겼다. 긴 양식이나 공통 사례에만 쓰이는 부분은 핵심 칸만 싣고, 뺀 자리에 「(… 키트 원문 N~M줄 생략 …)」을 남겼다. 생략한 부분은 키트 경로의 원문을 본다. 본문 안의 칸 이름과 안내 문장은 원문 그대로이다.
  4. 프로젝트실습Ⅰ에서 바꿀 곳. 팀의 주제로 쓸 때 고칠 자리와 그대로 둘 자리.

양식을 쓰는 방법은 모든 장에서 같다. 양식을 저장소의 정해진 자리로 복사한 뒤 「 」 자리를 채우고, 안내 문장(>로 시작하는 줄이나 <!-- --> 주석)은 다 채운 뒤 지운다. 키트 안의 양식 파일 자체는 고치지 않는다. 이 부록과 키트의 원문이 다르면 키트의 원문이 우선한다.

양식에 쓰는 ID와 판

양식들은 ID로 서로를 가리킨다. 페르소나의 PS-1을 문제 정의가 가리키고, 문제 정의의 P-01을 명세의 추적표가 가리키고, 명세의 REQ-003을 화면 명세, 인수 조건, 이슈, 커밋 메시지가 가리킨다. 형식이 하나라도 어긋나면 사람은 문서를 따라가지 못하고 키트의 검사 도구는 연결을 찾지 못한다. 아래 표는 1~13장이 함께 지키는 ID의 형식이다. 부록 A의 「장 사이 약속」과 같은 성격의 약속이다.

명세의 판과 태그

요구사항 명세서의 판이 바뀌는 장만 태그를 단다. 판을 올릴 때는 명세서 「문서 정보」 표의 판, 「변경 이력」 표의 새 행, 커밋 뒤의 주석 태그(git tag -a) 세 곳을 함께 고친다. 태그는 git push origin <태그>로 따로 올린다(부록 B-2).

# 풀 리퀘스트 리뷰 점검표

리뷰어가 「Files changed」 탭을 열기 전에 이 점검표를 옆에 둔다. 모든 항목에 답한 뒤 결정(Comment, Approve, Request changes)을 고른다. 근거: Google Engineering Practices 「What to look for in a code review」, GitHub Docs 「Reviewing proposed changes in a pull request」(2026-11-14 확인).

## 1. 리뷰를 시작하기 전

- [ ] 풀 리퀘스트 설명을 읽고, 무엇을 왜 바꾸었는지 한 문장으로 말할 수 있다
- [ ] 연결된 이슈(`Closes #n`)를 열어 완료 조건을 확인하였다
- [ ] 바뀐 파일의 수와 줄 수가 이슈 하나의 크기에 맞다(관계없는 변경이 섞이지 않았다)

## 2. 내용

- [ ] 이슈의 완료 조건을 충족한다
- [ ] 바뀐 줄을 한 줄도 빠짐없이 읽었다. 이해하지 못한 줄은 질문으로 남겼다
- [ ] 파일 전체의 맥락에서 보아도 어색하지 않다(바뀐 줄 위아래를 펼쳐 보았다)
- [ ] 이름(파일, 브랜치, 제목)이 저장소 규칙을 따른다
- [ ] 충돌 표시(`<<<<<<<`, `=======`, `>>>>>>>`)가 남아 있지 않다
- [ ] 비밀번호, API 키, 토큰, 개인 정보가 들어 있지 않다

## 3. 코멘트의 문장

- [ ] 코멘트는 사람이 아니라 변경을 가리킨다(「당신은 ~」 대신 「이 줄은 ~」)
- [ ] 고칠 것을 요청할 때는 까닭을 함께 적었다
- [ ] 꼭 고치지 않아도 되는 의견에는 앞에 `사소함:`을 붙였다
- [ ] 바로 고칠 수 있는 한두 줄은 「제안(suggestion)」으로 고친 문장을 직접 보였다
- [ ] 잘된 점이 있으면 한 가지 이상 적었다

## 4. 결정

| 상황 | 결정 |
|---|---|
| 완료 조건을 충족하고, 남긴 코멘트가 모두 사소함이다 | Approve |
| 질문만 있고 아직 판단하지 못하였다 | Comment |
| 완료 조건을 충족하지 못하거나, 충돌 표시·비밀 정보가 있다 | Request changes |

- [ ] AI 도구가 만든 리뷰 초안을 썼다면, 초안의 모든 지적을 diff에서 직접 확인하였고 확인하지 못한 지적은 지웠다
  • 프로젝트실습Ⅰ에서 바꿀 곳. 바꾸지 않는다. 문서(조사 보고, 명세, 설계)의 리뷰에는 7장의 설계 리뷰 점검표(C-7-6)를 함께 쓴다. 4절의 결정 기준은 팀 README의 작업 규칙 3(승인 1개 이상)과 함께 읽는다.

# 인터뷰 동의 문구 (견본)

> 인터뷰를 시작하기 전에 진행자가 아래 문구를 소리 내어 읽어 준다. 참여자가 직접 읽어도 된다. 「 」 자리만 바꾸고, 항목을 빼지 않는다. 이 문구는 수업 안의 동료 인터뷰용이다. 수업 밖의 사람을 인터뷰할 때는 교수와 먼저 상의한다.

---

이 인터뷰는 「LLM 서비스 개발」 수업의 실습이다. 취업 준비 지원 서비스를 설계하기 위해, 취업 준비를 하는 학생이 실제로 어떻게 준비하고 있는지 듣고자 한다.

1. **목적.** 수업 실습의 사용자 조사이다. 기록은 수업 산출물(친화도 분석, 페르소나, 문제 정의)을 만드는 데에만 쓴다.
2. **적는 것.** 취업 준비 경험에 대한 이야기를 진행자가 요약해 적고, 일부 발언은 들은 그대로 적는다. 이름, 연락처, 학번, 학교 이름, 사는 곳은 적지 않는다. 참여자는 「P01」 같은 번호로만 적는다.
3. **녹음.** 녹음과 촬영을 하지 않는다.
4. **보관과 기간.** 기록은 진행자의 비공개 실습 저장소에 보관하고, 학기가 끝나면 진행자가 지운다. 기록은 교수가 산출물을 확인할 때 볼 수 있다. 같은 조의 수강생(4명 이내)이 이름 등을 지운 기록을 함께 분석할 수 있으며, 원하지 않으면 진행자만 쓴다.
5. **AI 도구.** 이름 등을 지운 기록을 AI 코딩 도구(Claude Code)에 넣어 분류와 요약의 초안을 만든다. 이 도구는 외부 회사(Anthropic)의 서비스이다.
6. **거부와 중단.** 참여는 자유이다. 참여하지 않거나, 답하기 싫은 질문을 넘기거나, 중간에 그만두어도 불이익이 없다. 이 실습의 평가와도 관계가 없다.
7. **철회.** 인터뷰가 끝난 뒤에도 기록을 지워 달라고 요청할 수 있다. 진행자는 요청을 받으면 기록과 그 기록을 인용한 부분을 지운다.
8. **확인.** 인터뷰가 끝나면 기록을 보여 준다. 사실과 다르거나 빼고 싶은 내용이 있으면 말해 달라.

# jobprep 프로젝트 규칙

> 이 양식을 `jobprep/CLAUDE.md`로 복사해 채운다. 200줄을 넘기지 않는다. 명세의 내용을 옮겨 적지 말고, 명세를 어떻게 쓰는지만 적는다.

## 이 프로젝트

- 취업 준비 지원 서비스. 대상 사용자는 「 」이다.

## 명세 규칙

- 명세에 없는 기능을 만들지 않는다. 명세가 정하지 않은 것은 구현하지 말고 질문 목록으로 보고한다.

- 「추가 규칙」

## 작업 방식

- 여러 파일을 바꾸는 작업은 계획 모드에서 계획을 먼저 보이고 승인을 받는다.
- 커밋 메시지 끝에 관련 REQ ID를 적는다. 예: `공고 상태 거르기 (REQ-005)`
- 「추가 규칙」

## 하지 않는 것

- API 키, 비밀번호, 실제 개인 정보를 파일에 쓰거나 커밋하지 않는다.
- 「추가 규칙」

# 심각도 기준표

Nielsen(1994)의 0~4 척도를 이 과목의 프로덕트에 맞추어 예를 붙였다. 등급의 이름과 뜻은 원문을 따르고, 예는 이 과목에서 정한 것이다.

## 1. 등급

| 등급 | 이름 | 뜻 | 잡프렙에서의 예 |
|---|---|---|---|
| 0 | 문제 아님 | 사용성 문제라고 보지 않는다 | 카드 모서리가 둥글지 않다(평가자의 취향) |
| 1 | 겉모양 문제 | 시간이 남으면 고친다 | 버튼 사이 간격이 화면마다 조금 다르다 |
| 2 | 작은 문제 | 고치되 우선순위는 낮다 | 영어 약어(JD)가 낯설지만 눌러 보면 무엇인지 안다 |
| 3 | 큰 문제 | 고치는 것이 중요하며 우선순위가 높다 | 요약이 나오는 동안 아무 표시가 없어 버튼을 거듭 누르고 결과가 겹친다 |
| 4 | 사용성 재앙 | 출시 전에 반드시 고친다 | 저장한 지원 일정이 새로 고침하면 사라진다 |

(… 키트 원문 15~33줄 생략 …)
## 4. 우선순위 (이 과목의 규칙)

- 우선순위 점수 = 심각도(0~4) x 빈도(1 드묾, 2 가끔, 3 자주)
- 빈도는 사용성 테스트에서 그 문제를 겪은 참가자의 비율로 정한다. 비율이 1/3 이하이면 1, 2/3 이하이면 2, 그보다 크면 3이다(참가자 3명이면 1명 = 1, 2명 = 2, 3명 = 3. 참가자 2명이면 1명 = 2, 2명 = 3). 테스트에서 관찰되지 않은 휴리스틱 문제는 평가자가 추정한 값을 쓰고 문제 목록의 출처 칸에 「휴리스틱」이라 적어 구별한다.
- 심각도 4는 점수와 관계없이 맨 앞에 둔다. 점수가 같으면 심각도가 높은 쪽이 앞선다.
- 계산은 `도구/aggregate.py problems`가 한다.

출처: Nielsen, J. (1994). Severity Ratings for Usability Problems. Nielsen Norman Group. https://www.nngroup.com/articles/how-to-rate-the-severity-of-usability-problems/ (2026-11-14 확인)
  • 프로젝트실습Ⅰ에서 바꿀 곳. 1절의 「잡프렙에서의 예」 열은 팀 서비스의 예로 바꾸어 두면 평가자 사이의 등급이 덜 갈린다. 등급의 이름과 뜻(원문)은 바꾸지 않는다. 4절의 빈도 환산 규칙은 참가자 수에 따라 다르므로, 참가자를 다섯 명으로 늘리면 「1/3 이하 → 1, 2/3 이하 → 2, 그보다 크면 3」의 규칙을 그대로 적용해 1명은 1, 2~3명은 2, 4~5명은 3이 된다.
