화면의 리버스 엔지니어링과 요구사항 명세

2027학년도 「LLM 서비스 개발」의 준비 중인 교재입니다. 편집 상태를 검토하기 위해 미리 공개한 것으로, 수업 전에 내용과 순서가 바뀔 수 있습니다.

학사 5주차 · 교재 04 · 서비스 1: 공고 모아보기 웹 (1/2)

개편 초안 7판(2026-11-18). 참고 서비스(잡코리아)의 화면 구성과 형식을 읽고, 공개 API(고용24)의 자료를 그 형식에 채워 내 서비스를 만드는 실습이다. 키트를 새 번호(Service_04장)로 만들었다. 0절, 3-4, 5-4, 5-6의 명령과 출력은 집필용 Windows PC(Git Bash, Python 3.13.7, pytest 9.2.0)에서 키트로 실행해 얻은 것이다. 3-4의 견본 응답은 항목 이름만 개발명세서를 따른 지어낸 자료이다. 고용24 인증키의 신청과 실제 응답, 잡코리아 화면의 관찰, 웹 검색 AI의 조사, Claude Code의 응답은 「실행 결과 자리」로 남겼다. 잡코리아의 첫 화면은 2026-11-18에 글자로만 읽었고 그림과 배치는 보지 못하였다.

이 장부터 한두 주에 서비스 하나를 만든다. 첫 서비스는 공고 모아보기 웹이다. 채용 공고를 한곳에서 보고 거르는 웹이다. 이 장에서 명세를 쓰고 5장에서 구현해 배포한다.

만드는 방법은 다음과 같다. 먼저 이미 운영 중인 채용 서비스인 잡코리아의 화면을 관찰한다. 화면이 어떤 영역으로 나뉘고, 공고 한 건에 어떤 항목을 보이고, 사용자가 무엇을 할 수 있는지를 적는다. 다음으로 고용24의 공개 API가 주는 채용 공고 자료를 읽는다. 그리고 잡코리아에서 읽은 화면의 구성에 고용24의 자료를 채운 내 서비스의 명세를 쓴다. 화면의 구성은 참고 서비스에서 배우고, 화면에 들어갈 실제 자료는 API에서 받는 것이다.

학습 목표

  • 참고 서비스의 화면을 관찰해 정보 항목, 조작, 화면 뒤의 처리를 확인한 것과 추측한 것으로 나누어 적을 수 있다.
  • 공개 API의 문서와 응답을 읽어 자료 항목표를 만들고, 내 서비스가 쓸 항목을 고를 수 있다.
  • 시장 규모를 공공 통계로 어림하고 타겟 페르소나를 정할 수 있다.
  • 경쟁 서비스를 웹 검색이 되는 AI로 조사하고, 결과를 출처로 확인해 기획에 반영할 수 있다.
  • 요구를 EARS 다섯 문형으로 쓰고, 모호한 문장을 문형에 맞게 교정할 수 있다.
  • 요구마다 근거와 수용 기준을 붙이고, 정하지 못한 것을 열린 질문으로 남길 수 있다.

1. 리버스 엔지니어링

1-1. 정의

설계에서 구현으로 가는 일을 순공학이라 한다. 리버스 엔지니어링(reverse engineering)은 반대 방향이다. Chikofsky와 Cross(1990)는 이를 대상 시스템을 분석해 구성 요소와 그 관계를 알아내고, 시스템을 다른 형태나 더 높은 추상 수준으로 표현하는 과정으로 정의한다[R1]. 리버스 엔지니어링을 하는 동안 대상 시스템은 고치지 않는다. 대상을 관찰하고, 알아낸 것을 문서로 적을 뿐이다.

용어 뜻 이 과목에서의 자리
순공학 요구와 설계에서 구현으로 간다 5장, 8장의 구현
리버스 엔지니어링 완성물을 분석해 구성과 관계를 알아내고 더 높은 수준으로 표현한다 이 장의 화면 관찰과 자료 읽기
설계 복원 완성물 밖의 지식과 추론까지 써서 설계를 되살린다 「추측」으로 표시하는 부분
재공학 분석한 결과로 새 형태를 다시 구현한다 6장의 재구현

1-2. 이 과목에서의 쓰임

이 과목은 리버스 엔지니어링을 내 서비스의 명세를 쓰는 준비 단계로 쓴다. 참고 서비스의 화면에서는 화면을 어떻게 구성하는지를 알아내고, API의 문서와 응답에서는 어떤 자료를 받을 수 있는지를 알아낸다. 이 둘을 합쳐 내 서비스의 명세를 쓴다. 읽는 대상은 장마다 다르다.

대상 얻는 것 장
참고 서비스의 화면 화면의 영역, 정보 항목, 조작 4
API의 문서와 응답 자료의 항목, 형식, 빈 값 4, 5
코드 동작의 조건과 결과 6
네트워크 호출 서버가 판정하는 규칙 8
앱의 구조 기능 하나의 경로 11

어느 대상이든 절차는 같다.

  1. 사람이 먼저 대상을 관찰해 기록한다.
  2. AI에게 분석을 맡긴다.
  3. 사람이 AI의 분석을 자기 기록과 대조한다.
  4. 확인한 것과 추측한 것을 나누어 명세에 옮긴다.

1번과 3번은 사람이 직접 한다. AI는 자기가 읽은 내용이 실제 화면과 같은지 스스로 확인하지 못한다. 사람의 기록이 있어야 AI의 분석에서 틀린 곳과 지어낸 곳을 찾을 수 있다.

1-3. 대상의 경계

참고 서비스는 남이 운영하는 서비스이다. 무엇을 참고하고 무엇을 가져오지 않는지를 먼저 정한다.

  • 참고하는 것은 화면의 구성이다. 화면이 어떤 영역으로 나뉘는지, 공고 한 건에 어떤 항목을 보이는지, 사용자가 어떤 조작을 할 수 있는지를 본다.
  • 가져오지 않는 것은 그 서비스의 문구, 이미지, 로고, 코드, 공고 자료이다. 내 서비스의 공고 자료는 고용24의 API에서 받는다.
  • 로그인해야 보이는 화면과 개인 정보가 나오는 화면은 대상으로 삼지 않는다.
  • 자동으로 많은 요청을 보내지 않는다.
  • API는 제공 기관이 정한 이용 조건 안에서 쓴다(3-3).

[최신 자료 자리: 참고 서비스의 이용 약관] 잡코리아의 이용 약관에서 화면의 자동 수집과 저작물의 이용에 관한 조항을 수업 전에 확인한다. 2026-11-18에는 약관을 열어 보지 않았다.

이 절은 법률 자문이 아니다.

1-4. 참고 프로덕트 고르기

참고 프로덕트는 내가 만들려는 서비스와 같은 일을 하는, 이미 운영 중인 서비스이다. 다음 기준으로 고른다.

기준 까닭
내 서비스와 사용자의 목적이 같다 목적이 다르면 화면의 구성을 참고할 수 없다
로그인하지 않고 핵심 화면을 볼 수 있다 계정을 만들거나 결제하지 않고 관찰한다
많은 사람이 쓴다 사용자가 이미 익숙한 구성이므로 내 서비스에서도 배우기 쉽다
화면에 채울 자료를 공개 API로 구할 수 있다 구성만 참고하고 자료는 직접 구해야 한다

서비스 1의 참고 프로덕트는 잡코리아이다. 사용자의 목적(채용 공고 찾기)이 같고, 첫 화면과 공고 목록을 로그인 없이 볼 수 있으며, 공고 자료는 고용24의 API로 구할 수 있다.

2. 화면의 관찰

2-1. 무엇을 적는가

화면 하나에서 네 가지를 적는다.

적는 것 뜻 예
정보 항목 화면에 보이는 자료의 칸 제목, 기관, 마감일
조작 사용자가 할 수 있는 일 상태 고르기, 검색, 쪽 이동
화면 뒤의 처리 조작의 결과를 만드는 규칙 마감일이 지나면 「마감」으로 표시
모르는 것 보아도 알 수 없는 것 결과가 없을 때의 화면

화면 뒤의 처리는 화면에 직접 보이지 않는다. 직접 조작해 결과를 본 것은 「확인」으로, 그럴 것이라고 짐작한 것은 「추측」으로 적는다. 예를 들어 상태에서 「접수중」을 골라 접수중인 공고만 남는 것을 보았다면 확인이다. 「마감일이 지나면 자동으로 마감으로 바뀔 것이다」는 본 적이 없으므로 추측이다. 추측을 확인으로 적으면, 사실인지 모르는 내용이 명세에 사실처럼 들어간다.

2-2. 관찰 기록

AI에게 맡기기 전에 사람이 먼저 2분 동안 본다. 이 기록이 AI의 분석을 대조하는 기준이다. 대상을 화면 하나로 정한다. 「이 서비스의 구조를 분석하라」고만 하면 AI가 서비스 전체를 추측으로 채운다. 2026년 2학기판 수업에서 실제로 일어난 일이다[R2].

위 예는 2026-11-18에 첫 화면의 글자를 읽어 옮긴 것이다[J1]. 그림, 배치, 탭을 넘겼을 때의 내용은 읽지 못하였다. 학습자는 자기 화면에서 본 것으로 채운다.

[그림 자리: 잡코리아 첫 화면의 공고 카드] 공고 묶음에서 카드 두세 장이 보이는 부분. 회사명, 제목, 조건 꼬리표, 마감 표시에 번호를 붙인다. 내 PC의 브라우저에서 로그인하지 않은 상태로 찍는다.

3. 공개 API 읽기

3-1. API가 주는 것

공개 API는 기관이 자료를 프로그램이 읽을 수 있는 형식으로 내주는 창구이다. 요청은 주소와 요청 변수이고, 응답은 정해진 형식의 자료이다. 같은 공고라도 화면과 API의 응답은 모양이 다르다. 화면에는 「D-3」처럼 사람이 읽기 좋게 바꾼 글이 보인다. API의 응답에는 <closeDt>(마감일자) 같은 항목 이름과 함께 바꾸기 전의 값이 들어 있다. 그래서 응답을 읽으면 자료에 어떤 항목이 있고 값이 어떤 형식인지를 추측하지 않고 알 수 있다.

API를 고를 때는 한국의 공개 API를 분야별로 모은 목록을 쓴다[A2]. 이 목록은 36개 분류로 나뉘고, 표의 열은 API, 설명, 인증이다. 인증의 값(apiKey, OAuth 등)이 그 API를 쓰는 데 필요한 절차를 알린다. 이 목록은 쓸 만한 API의 후보를 찾는 데 쓴다. 후보를 찾은 뒤에는 그 API를 제공하는 기관의 문서를 열어 이용 조건과 응답의 항목을 직접 확인한다.

3-2. 고용24 OPEN-API와 인증키의 신청

서비스 1의 자료는 고용24의 채용정보 API에서 받는다. 고용24의 안내에 따르면 이 API는 HTTP 기반이며 결과는 XML(UTF-8)로 온다[A1]. API를 부르려면 인증키가 필요하다. 인증키는 이용 허가를 받은 회원을 구분하는 값이다[A1]. 학습자가 각자 신청해 받는다(사용자 결정, 2026-11-18).

신청의 순서는 다음과 같다[A1].

  1. 고용24에 회원으로 가입한다.
  2. 로그인한 뒤 「OPEN-API 서비스 소개 및 신청」에서 채용정보를 골라 신청한다[A3].
  3. 담당자가 심사한다. 승인되면 인증키가 발급된다.
  4. 「신청현황」에서 인증키를 확인한다.

심사에 시간이 걸리므로 이 장의 수업보다 앞서 신청한다. 인증키에는 조건이 붙는다. 다른 기관에 넘길 수 없고, 개발명세서에 적힌 형식과 목적에 맞게 써야 한다[A1]. 교육과 비영리 목적의 이용은 가능하다(사용자 확인, 2026-11-18).

[최신 자료 자리: 인증키의 신청 자격과 심사 기간] 소개 쪽에는 「OPEN-API는 고용24 기업회원 전용 서비스」라고 적혀 있다[A1]. 학생이 개인회원으로 신청할 수 있는지, 신청서에 무엇을 적는지, 심사에 며칠이 걸리는지를 교수가 먼저 신청해 보고 확인한다. 2026-11-18에는 신청해 보지 않았다. 학생이 받을 수 없으면 교수가 받은 응답 파일을 Google 클래스룸으로 나누어 준다. 키트 저장소는 공개 저장소이므로 실제 응답을 넣지 않는다.

  • 확인 2 고용24의 「신청현황」에 채용정보 API의 신청이 보인다(승인 전이면 신청 상태를 적는다).

채용정보 목록의 요청은 다음과 같다[A3].

https://www.work24.go.kr/cm/openApi/call/wk/callOpenApiSvcInfo210L01.do?authKey=[인증키]&callTp=L&returnType=XML&startPage=1&display=10
요청 변수 필수 뜻
authKey 예 인증키
callTp 예 L은 목록, D는 상세
returnType 예 XML
startPage 예 시작 쪽. 기본 1, 최대 1000
display 예 한 번에 받는 건수. 기본 10, 최대 100
region 근무 지역의 코드
career 경력. N 신입, E 경력, Z 관계없음
keyword 검색어

요청 변수는 모두 37개이다[A3]. 위 표는 서비스 1에서 쓸 것만 옮겼다. 대괄호는 값을 넣을 자리를 뜻하며 실제 요청에는 쓰지 않는다.

3-3. 인증키의 자리

인증키는 내 이름으로 발급된 값이다. 남이 내 인증키로 요청을 보내면 그 사용량이 내 것으로 기록된다. 그래서 인증키를 다음 두 곳에 두지 않는다.

  • 저장소. 커밋한 파일은 원격 저장소에 올라가고 기록에 남는다.
  • 브라우저로 가는 코드. 웹 페이지의 HTML과 JavaScript는 누구나 열어 볼 수 있다.

이 장에서는 인증키를 저장소 밖의 파일(~/work24.env)에 export WORK24_KEY=… 꼴로 적어 두고, 명령을 실행할 때만 source로 읽어 쓴다. export가 있어야 그 터미널에서 실행한 프로그램(5장의 배포 전 점검 도구 등)도 값을 읽는다. 정적 웹은 모든 코드가 브라우저로 가므로 화면에서 API를 직접 부르지 않는다. 5장에서는 내 PC에서 자료를 미리 받아 파일로 저장하고, 화면은 그 파일을 읽는다. 인증키를 서버에 두고 서버가 API를 부르는 구조는 8장에서 다룬다.

3-4. 자료 항목표

응답을 읽어 항목마다 다음을 적는다. 이 표가 화면의 정보 항목과 요구 문장의 근거가 된다.

[파일: ch04/자료항목표.md] (예)

| 항목 | 뜻(개발명세서) | 값의 꼴 | 빈 값 | 내 서비스에서 |
|---|---|---|---|---|
| wantedAuthNo | 구인인증번호 | (응답에서 확인) | (확인) | 공고를 구분하는 값으로 쓴다 |
| company | 회사명 | 문자열 | (확인) | 카드에 보이고 검색한다 |
| title | 채용 제목 | 문자열 | (확인) | 카드에 보인다 |
| sal | 급여 | (응답에서 확인) | (확인) | 카드의 조건 꼬리표로 보인다 |
| region | 근무지역 | (응답에서 확인) | (확인) | 카드에 보이고 거른다 |
| career | 경력 | (응답에서 확인) | (확인) | 거른다 |
| closeDt | 마감일자 | (응답에서 확인) | (확인) | 남은 날을 계산해 「D-3」 꼴로 보이고 정렬한다 |
| wantedInfoUrl | 채용정보 URL | 주소 | (확인) | 카드를 누르면 이 주소로 간다 |
| busino | 사업자등록번호 | 문자열 | (확인) | 쓰지 않는다 |

항목의 이름과 뜻은 개발명세서에서 옮긴 것이다[A3]. 목록 응답의 항목은 모두 29개이다. 바깥의 <wantedRoot>에 3개(total, startPage, display)가 있고 공고 한 건(<wanted>)에 26개가 있다. 명세서는 대부분의 항목을 「String」으로만 적고 날짜의 꼴(예: 연도를 두 자리로 쓰는가)은 적지 않았다. 그래서 「값의 꼴」과 「빈 값」 칸은 실제 응답을 받아 채운다(7-3).

따라 하기 1: 값의 꼴 세기. 응답이 길면 눈으로 훑어서는 드문 값을 놓친다. 명령으로 센다. 키트의 견본/응답_지어낸것.xml은 항목 이름만 개발명세서를 따르고 회사, 공고, 값을 모두 지어낸 연습용 응답이다(공고 10건). 이것으로 명령을 익히고, 7-3에서 실제 응답에 같은 명령을 쓴다.

터미널 
X=~/kits/Service_04장/견본/응답_지어낸것.xml
grep -c "<wanted>" $X
grep -o "<closeDt>[^<]*</closeDt>" $X | sed 's/[0-9]/9/g' | sort | uniq -c
grep -o "<sal>[^<]*</sal>" $X | sed 's/[0-9]/9/g' | sort | uniq -c
10
      8 <closeDt>99-99-99</closeDt>
      2 <closeDt>채용시까지</closeDt>
      1 <sal>99999원</sal>
      1 <sal>9999만원 ~ 9999만원</sal>
      3 <sal>9999만원</sal>
      4 <sal>999만원</sal>
      1 <sal></sal>

grep -o는 항목 하나씩을 뽑고, sed 's/[0-9]/9/g'는 숫자를 모두 9로 바꾸어 값이 아니라 꼴만 남긴다. sort | uniq -c가 꼴마다 건수를 센다. 이 견본에서는 마감일에 날짜 꼴(8건)과 글자(「채용시까지」 2건)가 섞여 있고, 급여에 빈 값이 1건 있다. 실제 응답의 꼴은 다를 수 있다. 견본의 값을 자료 항목표에 옮겨 적지 않는다.

  • 확인 3 위 세 명령의 출력에서 「날짜가 아닌 마감일」의 건수와 「빈 급여」의 건수를 읽어 말할 수 있다(견본에서는 2건과 1건).

화면의 항목과 자료의 항목을 나란히 놓으면 화면 뒤의 처리가 보인다.

잡코리아의 카드에 보이는 것 고용24의 자료 사이에 필요한 처리
회사명 company 없음
공고 제목 title 없음
「D-1」, 「오늘마감」 closeDt 오늘 날짜와 마감일의 차이를 계산한다
「상시채용」 closeDt의 값(확인 필요) 날짜가 아닌 값을 어떻게 보일지 정한다
조건 꼬리표 sal, career 등 어느 항목을 꼬리표로 보일지 정한다

「D-1」은 자료에 들어 있지 않다. 화면이 마감일에서 계산한 것이다. 이런 계산의 규칙이 명세의 요구가 된다. 예를 들어 마감일이 오늘이면 「D-0」으로 보일지 「오늘마감」으로 보일지를 정해야 한다.

볼 것은 셋이다.

  1. 형식이 하나가 아닌 항목. 마감일이 날짜이기도 하고 글자이기도 하면 정렬과 계산의 규칙을 명세가 정해야 한다.
  2. 빈 값이 있는 항목. 빈 값을 화면에 어떻게 보일지 정하지 않으면 구현하는 쪽이 정한다.
  3. 쓰지 않는 항목. API가 주는 항목을 모두 화면에 보일 필요는 없다. 쓰지 않기로 한 항목도 표에 적어 둔다. 적어 두지 않으면 나중에 빠뜨린 것인지 일부러 뺀 것인지 알 수 없다.

4. 시장과 경쟁 서비스의 조사

명세를 쓰기 전에 두 가지를 조사한다. 이 서비스를 쓸 사람이 얼마나 되고 그 가운데 누구를 위해 만드는가, 그리고 같은 일을 하는 서비스들이 무엇을 제공하는가이다. 조사의 결과는 명세에서 기능을 넣고 빼는 근거로 쓴다.

4-1. 시장 규모와 타겟 페르소나

시장 규모는 이 서비스를 쓸 수 있는 사람의 수를 어림한 값이다. 정확한 값을 구하려는 것이 아니다. 「수천 명인가, 수십만 명인가」를 알아 서비스의 범위를 정하려는 것이다. 공공 통계 하나에서 출발해 조건을 하나씩 좁힌다.

전체: 청년(15~29세) 구직자의 수            ← 공공 통계에서 찾는다 (출처와 기준 시점을 적는다)
좁힘 1: 그 가운데 신입 채용 공고를 찾는 사람   ← 가정. 비율과 까닭을 적는다
좁힘 2: 그 가운데 이 서비스가 다루는 지역     ← 가정. 비율과 까닭을 적는다

통계에서 가져온 수와 내가 가정한 비율을 구분해 적는다. 가정을 통계처럼 적으면 읽는 사람이 근거가 있는 수로 오해한다.

[최신 자료 자리: 청년 구직자의 수] 출발점으로 쓸 통계표의 이름, 수치, 기준 시점. 확인할 곳: 국가통계포털(KOSIS)의 경제활동인구조사. 2026-11-18에는 수치를 확인하지 않았다. 수업 전에 통계표를 정해 예에 넣는다.

타겟 페르소나는 이 서비스를 쓸 사람들을 대표하는 가상의 한 사람이다. 모든 사람을 위한 서비스는 기능을 고르는 기준이 없다. 한 사람을 정해 두면 「이 사람에게 필요한 기능인가」로 넣고 뺄 수 있다. 이 장에서는 다음 네 줄만 적는다.

누구인가: 졸업을 앞두고 첫 직장을 찾는 전문대 2학년
무엇을 하려 하는가: 지원할 수 있는 신입 공고를 마감 전에 찾는다
지금 어떻게 하는가: 채용 사이트 두세 곳을 번갈아 본다
무엇이 불편한가: 마감이 가까운 공고를 놓친다

이 네 줄은 내가 세운 가정이다. 실제 사람에게 확인하는 방법(인터뷰)은 7장에서 다룬다.

4-2. 화면에서 기능 목록 뽑기

같은 일을 하는 서비스들이 무엇을 제공하는지 알아야 내 서비스에 넣을 기능을 고를 수 있다. 참고 프로덕트 하나만 보면 그 서비스에만 있는 기능과 어느 서비스에나 있는 기능을 구분할 수 없다. 소개 글은 오래되었거나 과장되었을 수 있으므로 화면에서 확인한 것을 기준으로 삼는다. 절차는 네 단계이다.

  1. 화면을 고정한다. 어느 주소를, 어떤 상태(로그인 여부, 기기)로, 언제 보았는지 적는다.
  2. 메뉴를 그대로 옮긴다. 이름을 바꾸지 않는다. 「채용달력」과 「공고달력」은 서비스마다 다른 이름이다.
  3. 기능을 사용자 업무로 묶는다. 비교표의 행은 메뉴 이름이 아니라 업무(공고 찾기, 일정 챙기기)의 이름이다.
  4. 관찰과 추정을 나눈다. 메뉴 이름으로 짐작한 것은 비고에 「메뉴 이름으로 판단」이라고 적는다.

  • △(일부·조건부): 일부만 있거나 조건이 붙는다. 조건을 비고에 쓴다.
  • -(확인되지 않음): 관찰한 범위에서 보지 못하였다.

「-」는 없다는 뜻이 아니다. 첫 화면에서 보지 못한 기능이 로그인 뒤에 있을 수 있다. 없다고 쓰려면 없음을 확인해야 하는데 공개 화면만으로는 어렵다.

다음은 2026-11-14에 다섯 서비스의 첫 화면과 전체 메뉴를 관찰한 비교표의 일부이다[K1]~[K5].

채용 공고 검색 ○ ○ ○ ○ ○

모든 서비스가 ○인 행은 갖추어야 하지만 차별점이 되지 못하는 기능이다. 한두 서비스만 ○인 행은 차별점의 후보이거나 수요가 작은 기능이다. 어느 쪽인지는 비교표만으로 알 수 없다.

4-4. AI의 조사와 확인

deep research는 AI가 여러 웹 문서를 스스로 찾아 읽고 보고서로 정리하는 기능이다. 사람이 서비스 다섯 곳을 하나씩 열어 보는 일을 대신 한다. ChatGPT와 Gemini에는 이 이름의 기능이 따로 있다. 그 기능이 없어도 된다. 웹 검색을 할 수 있는 AI이면 어느 것이든 같은 프롬프트로 조사할 수 있다. 도구는 학습자가 고른다.

[최신 자료 자리: deep research 기능의 이름과 무료 한도] 2026-11-18에 웹 검색 결과로 ChatGPT와 Gemini에 Deep Research라는 기능이 있음을 확인하였다. 공식 안내 쪽은 열지 않았다. 무료 요금제에서 쓸 수 있는 횟수는 확인하지 않았다. 수업 전에 각 서비스의 공식 안내에서 확인한다.

어느 도구를 쓰든 보고서에는 다음이 섞일 수 있다.

  • 오래된 정보. 지금은 없어진 기능이나 바뀐 요금.
  • 출처에 없는 내용. AI가 그럴듯하게 채운 문장.
  • 홍보 글의 표현. 서비스가 자기를 소개한 말을 사실처럼 옮긴 문장.

그래서 보고서를 그대로 믿지 않는다. 보고서의 주장 가운데 내 기획에 쓸 것만 골라, 출처를 직접 열어 확인한다.

확인의 결과 뜻 처리
확인됨 출처를 열어 보니 그 내용이 있고, 지금 화면에서도 보인다 기획에 쓴다
다름 출처는 있으나 내용이 다르거나 지금은 바뀌었다 본 대로 고쳐 쓴다
확인 못함 출처가 없거나 열리지 않는다 쓰지 않는다

모든 주장을 확인하지 않는다. 기획에 쓸 주장만 확인한다. 쓰지 않을 내용을 확인하는 데 시간을 들이지 않는다.

4-5. 조사의 예절

  • 로그인하지 않은 상태에서 누구나 볼 수 있는 화면만 본다. 관찰을 위해 계정을 만들거나 결제하지 않는다.
  • 관찰한 사실만 적는다. 「불편하다」, 「부실하다」 같은 평가는 평가 방법과 결과가 없으면 쓰지 않는다.

5. 요구사항과 EARS 문형

5-1. 용어

용어 뜻 예
요구 시스템이 가져야 할 능력이나 지켜야 할 조건 하나 공고를 마감일 순서로 보여야 한다
요구사항 명세서 요구를 ID, 문형, 근거, 수용 기준과 함께 적은 문서 ch04/요구사항명세서.md
수용 기준 요구가 충족되었는지 판정하는 관찰 가능한 조건 「접수중」을 고르면 보이는 모든 행의 상태가 접수중이다

요구는 시스템이 해야 할 일을 적은 문장이다. 수용 기준은 그 일이 되었는지를 확인하는 방법을 적은 문장이다. 요구가 「공고를 마감일 순서로 보여야 한다」라면, 수용 기준은 「마감일이 11-20인 공고와 11-15인 공고가 있을 때 목록을 열면 11-15인 공고가 위에 보인다」이다.

요구만 있고 수용 기준이 없으면 같은 요구를 사람마다 다르게 읽는다. 「마감일 순서」를 구현한 사람은 마감이 빠른 순으로, 검사하는 사람은 마감이 늦은 순으로 생각할 수 있다. 수용 기준이 있으면 둘이 같은 결과를 기대한다.

5-2. 좋은 요구 문장

성질 뜻 어긋난 예
검증 가능성 충족 여부를 관찰로 판정할 수 있다 「공고를 보기 좋게 보인다」
단일성 한 문장에 요구 하나 「저장해야 하고 알림도 보내야 한다」
조건의 명시 언제 그 동작을 하는지 드러난다 「검색 결과를 보인다」
주체의 명시 누가 하는지 드러난다 「공고가 정렬되어야 한다」
식별 고유한 ID가 있다 ID 없는 문장
구현 중립 무엇을 할지 말하고 어떻게 할지는 말하지 않는다 「sort() 함수로 정렬해야 한다」

마지막 행의 뜻은 다음과 같다. 명세에는 시스템이 해야 할 일(「마감일 순으로 정렬해 보인다」)을 적고, 그 일을 어떤 함수나 라이브러리로 구현할지는 적지 않는다. 구현 방법까지 적으면 구현 기술을 바꿀 때마다 명세도 고쳐야 한다. 구현 방법은 구현하는 단계에서 정한다.

5-3. EARS의 원리

EARS(Easy Approach to Requirements Syntax)는 요구 문장을 정해진 틀에 맞추어 쓰게 하는 작성법이다. 롤스로이스의 Alistair Mavin과 동료들이 항공기 엔진 제어 시스템의 요구를 분석하며 만들어 2009년 IEEE 국제 요구공학 학술대회에서 발표하였다[S3, S3a]. 원리는 둘이다.

  1. 절의 순서를 고정한다. 「전제 조건 → 트리거 → 시스템 이름 → 시스템의 응답」의 순서로 쓴다[S3].
  2. 키워드로 문형을 드러낸다. 키워드(While, When, Where, If … then)가 그 문장이 언제 적용되는지 알린다.

AWS의 명세 주도 개발 도구 Kiro는 요구 문서를 EARS 꼴로 쓴다[S6].

5-4. 다섯 문형

영어 원형은 Mavin의 공개 자료를 따르고[S3], 한국어 문형은 이 과목의 약속이다.

문형 키워드 한국어 문형 언제 쓰나
상시 없음 시스템은 <응답>해야 한다. 늘 성립해야 하는 성질
사건 When <트리거>하면, 시스템은 <응답>해야 한다. 사용자의 동작이나 외부 사건에 대한 반응
상태 While <상태>인 동안, 시스템은 <응답>해야 한다. 어떤 상태가 이어지는 동안
선택 Where <기능>이 포함된 경우, 시스템은 <응답>해야 한다. 있을 수도 없을 수도 있는 기능
원치 않는 동작 If … then 만약 <트리거>하면, 시스템은 <응답>해야 한다. 잘못된 입력, 실패, 자료 없음
복합 둘 이상 <상태>인 동안 <트리거>하면, 시스템은 <응답>해야 한다. 상태와 사건이 함께 걸릴 때

공고 목록에 적용하면 다음과 같다.

[상시] 시스템은 공고 목록을 마감일이 빠른 순으로 한 쪽에 10행씩 표시해야 한다.
[사건] 사용자가 지역을 고르고 검색을 실행하면, 시스템은 그 지역의 공고만 표시해야 한다.
[상태] 공고가 마감 상태인 동안, 시스템은 그 행을 흐리게 표시해야 한다.
[선택] 관심 공고 기능이 포함된 경우, 시스템은 각 행에 관심 표시 단추를 두어야 한다.
[원치 않는 동작] 만약 조건에 맞는 공고가 없으면, 시스템은 「검색 결과가 없다」는 안내를 표시해야 한다.

5-5. 한국어로 쓸 때의 규칙

검사기 ears_check.py가 다음 규칙으로 판정한다.

  1. 응답 절의 주체는 「시스템은」 하나이다.
  2. 응답은 「~야 한다」로 끝난다. 「표시한다」는 서술이지 요구가 아니다.
  3. 한 문장에 응답 하나이다. 「저장해야 하고 알림을 보내야 한다」는 두 요구이다.
  4. 조건절은 키워드로 끝난다. 사건은 「~하면」, 상태는 「~인 동안」, 선택은 「~이 포함된 경우」, 원치 않는 동작은 「만약 ~하면」이다.
  5. 확인할 수 없는 말(「잘, 적절히, 빠르게, 쉽게」)을 쓰지 않는다. 수치나 관찰 가능한 결과로 바꾼다.

명세를 다 쓴 뒤 문형별로 요구의 수를 세어 본다. 수가 0인 문형이 있으면 그 종류의 상황을 명세가 다루지 않은 것이다. 「사건」 문형이 하나도 없으면 사용자가 조작했을 때 시스템이 어떻게 반응하는지를 적지 않은 것이다. 「원치 않는 동작」 문형이 하나도 없으면 입력이 잘못되었거나 자료가 없을 때 어떻게 하는지를 적지 않은 것이다. 검사기는 문형별 수를 출력의 끝에 보인다.

메시지 원인 고치는 법
응답이 「~야 한다」(shall)로 끝나지 않는다 서술로 끝났다 「표시해야 한다」로 고친다
문형을 알 수 없다: 주체가 없다(…) 「시스템은」이 없다 「시스템은 목록을 정렬해 표시해야 한다」
라벨은 [사건]인데 문장 구조는 [상시]이다 「시스템은」이 조건보다 앞에 왔다 「조건절, 시스템은 …」의 순서로 바꾼다
한 문장에 요구가 둘 이상이다… 「~해야 하고 ~해야 한다」 문장을 나누고 새 ID를 붙인다
ID가 없는 요구 문장이다 목록 줄에 「~야 한다」가 있는데 ID가 없다 ID를 붙인다

ch04/연습/교정연습.md를 열어 세 문장을 손으로 고친다. 문형을 고르는 판단을 직접 해 보는 것이 목적이므로 Claude Code를 쓰지 않는다.

  • REQ-01 「공고를 잘 보여 준다」: 무엇을 보이는지 항목으로 적어 상시 문형으로.
  • REQ-04 「저장해야 하고 알림도 보내야 한다」: 두 요구로 나누고 뒤의 것에 새 ID(REQ-10)를 붙인다.
  • REQ-05 「오류가 나면 사용자에게 알린다」: 어떤 오류에 무엇을 보이는지 정해 원치 않는 동작 문형으로.

문장 앞에 라벨을 붙인다(예: - **REQ-01** [상시] 시스템은 ...해야 한다.). 원문이 정하지 않은 값을 정했으면 문장 뒤 괄호에 적는다. 검사기는 문장 끝의 근거 표시(6-2의 (관찰: …), (자료: …), (정함: …), (조사: …), (추측: …))와 ← 고침, ← 추가를 검사하지 않는다.

터미널 
python ~/kits/Service_04장/도구/ears_check.py ch04/연습/교정연습.md --id "REQ-\d{2}" | grep -E "^REQ-(01|04|05|10) |문형 분포|빈 문형|요약"
REQ-01   [상시] 통과
REQ-04   [사건] 통과
REQ-10   [선택] 통과
REQ-05   [원치 않는 동작] 통과
문형 분포: 상시 1, 사건 1, 상태 0, 선택 1, 원치 않는 동작 1, 복합 0
요약: 요구 10개, 수용 기준 0개, 오류 7건, 경고 5건

위는 세 문장을 고친 한 예로 실제로 낸 출력이다(2026-11-18). 남은 오류 7건은 손대지 않은 문장의 것이다. REQ-04의 알림을 선택으로 본 사람과 사건으로 본 사람은 둘 다 통과하지만, 앞의 것만 알림이 없는 판을 인정한다. 검사기를 통과한 뒤에도 사람이 판단할 자리가 남는다.

  • 확인 5 원문에서 오류 10건과 「빈 문형: 사건, 원치 않는 동작」을 보았고, 손으로 고친 뒤의 출력에서 REQ-01, REQ-04, REQ-05와 새로 나눈 요구가 통과이며 「빈 문형」 줄이 없다.

5-7. 검사기가 보지 못하는 것

검사기는 문장의 형식만 검사한다. 주체가 「시스템은」인지, 문장이 「~야 한다」로 끝나는지, ID가 있는지를 본다. 문장의 내용이 쓸 만한지는 보지 못한다. 「시스템은 공고를 올바르게 처리해야 한다」는 형식이 맞아 통과할 수 있다. 그러나 「올바르게」가 무엇인지 정해져 있지 않아, 구현한 결과가 이 요구를 충족하는지 판정할 수 없다. 이런 문장은 사람이 읽어서 찾고, 수용 기준을 붙여 보면 드러난다. 수용 기준을 쓸 수 없으면 요구가 모호한 것이다.

6. 수용 기준과 열린 질문

6-1. 수용 기준

형식은 - **AC-<요구 번호>-<순번>** (전제) ~일 때 (행동) ~하면 (결과) ~이다.이다. Spec Kit의 수용 시나리오(Given, When, Then)를 옮긴 것이다[S2d]. 좋은 수용 기준은 구체적인 자료와 관찰할 결과를 가진다.

요구 나쁜 수용 기준 좋은 수용 기준
마감일 순 정렬 목록이 마감일 순서로 보인다 마감일이 11-20, 11-15, 11-30인 공고 셋이 있을 때 목록을 열면 11-15, 11-20, 11-30의 순서로 보인다
마감 임박 표시 마감이 가까운 공고가 강조된다 오늘이 11-14이고 마감일이 11-17인 공고에는 「마감 임박」이 보이고, 11-18인 공고에는 보이지 않는다

둘째 행은 표시가 보여야 하는 경우(3일 남음)와 보이지 않아야 하는 경우(4일 남음)를 함께 확인한다. 보여야 하는 경우만 확인하면, 모든 공고에 「마감 임박」을 붙이는 잘못된 구현도 통과한다. 수용 기준을 쓸 수 없는 요구는 무엇을 해야 하는지가 아직 분명하지 않은 것이다. 요구를 먼저 고친다.

6-2. 근거의 표시

요구마다 어디서 왔는지를 문장 끝에 적는다.

표시 뜻
(관찰: …) 참고 서비스의 화면에서 본 것. 관찰 기록의 어느 칸인지 적는다
(자료: 항목 이름) 자료 항목표의 항목에서 나온 것
(정함: 까닭) 내가 정한 것. 까닭을 적는다
(조사: 출처) AI의 조사 보고 가운데 출처를 열어 확인한 것
(추측: 까닭) 확인하지 못한 것

내 서비스를 만드는 것이므로 「정함」이 많아도 된다. 화면의 구성은 참고 서비스에서 왔더라도, 어떤 기능을 넣고 뺄지는 내가 정하기 때문이다. 살펴야 할 것은 근거 표시가 없는 요구이다. AI에게 명세 초안을 맡기면 AI는 요청하지 않은 기능(예: 회원 가입, 추천)을 넣는 일이 있다. 그런 요구를 그대로 두면 내가 고르지 않은 기능이 내 서비스에 들어간다. 그래서 요구마다 근거를 적게 하고, 근거를 적을 수 없는 요구는 뺀다.

6-3. 열린 질문

지금 정할 수 없는 것은 「열린 질문」 표에 남긴다. 정하지 못한 것을 정한 것처럼 쓰지 않는다. Spec Kit은 이런 곳을 명세 안에 [NEEDS CLARIFICATION: ...]으로 표시한다[S2d]. 남기는 기준은 「틀리면 무엇을 다시 만들어야 하는가」이다. 값에 따라 화면이나 구현이 달라지는데 근거가 없는 것만 남긴다.

7-3. 응답 받기와 자료 항목표

인증키를 저장소 밖의 파일에 적고, 그 파일을 읽어 API를 한 번 부른다. 인증키를 echo로 적으면 셸의 명령 기록(~/.bash_history)에 남으므로 편집기로 적는다(부록 A-14-5). 받은 응답을 파일로 저장한다.

터미널 
code ~/work24.env     # 편집기가 열리면 export WORK24_KEY=발급받은_인증키 한 줄을 적고 저장한다
source ~/work24.env
cd ~/llm-service-lab/ch04
echo "ch04/응답_견본.xml" >> ~/llm-service-lab/.gitignore
curl -s "https://www.work24.go.kr/cm/openApi/call/wk/callOpenApiSvcInfo210L01.do?authKey=$WORK24_KEY&callTp=L&returnType=XML&startPage=1&display=10" > 응답_견본.xml
head -c 600 응답_견본.xml

첫 줄의 여기에_발급받은_인증키를 자기 인증키로 바꾼다. .gitignore에 응답 파일을 먼저 적고 받는다. head -c 600은 파일의 앞 600바이트를 보인다. 공고의 항목 이름(company, title 등)이 보이면 받은 것이다. 오류 안내가 보이면 인증키와 요청 변수를 확인한다. 인증키가 아직 발급되지 않았으면 교수가 Google 클래스룸에 올린 응답 파일을 응답_견본.xml로 저장해 진행한다. 그것도 없으면 키트의 지어낸 견본을 복사해(cp ~/kits/Service_04장/견본/응답_지어낸것.xml 응답_견본.xml) 절차만 익히고, 자료 항목표에 「지어낸 견본으로 채움」이라고 적는다.

[실행 결과 자리: 고용24 채용정보 목록의 실제 응답] 위 명령의 head -c 600 출력(인증키는 가린다). 바깥 요소의 이름, total의 값, 첫 공고의 항목 순서와 날짜의 꼴을 싣는다. 실행할 곳: 인증키를 받은 교수 PC. 2026-11-18에는 인증키가 없어 받지 못하였다. 응답이 키트의 견본과 구조가 다르면 견본과 5장의 변환 프로그램을 고친다.

받은 응답에 3-4의 세 명령을 쓴다. 파일 이름만 바꾼다(X=응답_견본.xml). display=100으로 한 번 더 받아 같은 명령을 다시 쓰면 10건에 없던 드문 꼴이 보일 수 있다. 출력을 자료 항목표의 「값의 꼴」과 「빈 값」 칸의 근거로 붙인다.

  • 확인 7 git -c core.quotepath=false check-ignore -v ch04/응답_견본.xml(저장소 맨 위에서)이 .gitignore의 규칙 한 줄을 출력하고, git ls-files | grep -c work24가 0이며, 응답 파일에 3-4의 명령을 써 마감일의 꼴별 건수를 얻었다.

[Claude Code] (계획 모드)

이 폴더의 응답_견본.xml을 읽고 자료 항목표를 만들어라.
- 항목마다 이름, 값의 꼴, 빈 값이 있는지를 적는다.

4. 확인과 반영. 보고서에서 내 기획에 쓸 주장을 다섯 개 고른다. 주장마다 출처를 열고, 그 서비스의 화면에서 직접 찾아본 뒤 확인표를 채운다(4-4).

[파일: ch04/조사.md] (확인표의 예)

| 주장 (보고서) | 출처 | 내가 본 것 | 결과 |
|---|---|---|---|
| 다섯 서비스 모두 채용 일정 달력이 있다 | (주소) | 잡코리아 「공채정보」, 사람인 「채용달력」에서 달력을 보았다. 나머지 셋은 메뉴에서 이름만 보았다 | 확인됨(둘), 이름만(셋) |
| AI 서류 코칭은 한 곳에만 있다 | (주소) | 그 메뉴를 찾았다. 다른 네 곳의 첫 화면 메뉴에는 없었다 | 확인됨 |
| (서비스)는 마감 임박 공고를 따로 모아 보인다 | 없음 | 출처가 없고 화면에서 찾지 못했다 | 확인 못함 |

확인한 것을 바탕으로 「기획에 반영할 것」을 셋 적는다. 넣을 기능, 넣지 않을 기능, 다르게 할 것을 하나씩 쓰고 까닭을 붙인다.

넣는다: 마감일 순 정렬. 다섯 서비스에 모두 있는 일정 기능의 가장 작은 꼴이다. 타겟이 마감을 놓친다
넣지 않는다: 이력서 작성. 여러 서비스에 이미 있고 이 서비스의 범위를 넘는다
다르게 한다: 마감 임박 표시를 목록의 맨 위에 둔다. 타겟의 불편에 바로 닿는다
  • 확인 10 조사.md에 시장 규모(출처와 가정의 구분), 타겟 페르소나 네 줄, 확인표 다섯 행 이상, 「기획에 반영할 것」 셋이 있다. 확인표의 「내가 본 것」 칸에 직접 본 내용이 적혀 있다.

7-5. 명세 초안

세 재료를 주고 명세의 초안을 받는다. 만들 기능은 내가 먼저 정해 프롬프트에 적는다. AI에게 기능을 정하게 하지 않는다. 받은 초안은 7-2에서 복사한 양식(요구사항명세서.md)의 4~7절에 옮긴다.

[Claude Code] (계획 모드)

공고 모아보기 웹의 요구사항 명세 초안을 써라. 근거는 관찰기록.md, 자료항목표.md, 조사.md 셋뿐이다.
화면의 구성(영역, 공고 한 건의 항목, 조작)은 관찰기록.md를 따르고, 화면에 채울 자료는 자료항목표.md의 항목만 쓴다.
만들 기능(내가 정함. 조사.md의 「기획에 반영할 것」을 따른다): 목록 보기, 마감일 순 정렬, 지역과 경력으로 거르기, 제목과 회사명으로 검색, 마감 임박 표시.
타겟: 조사.md의 타겟 페르소나.
- 형식: `- **REQ-01** [문형] 문장. (근거)` 한 줄에 하나. 주체는 「시스템은」, 응답은 「~야 한다」.
- 근거는 (관찰: …), (자료: 항목 이름), (조사: 출처), (정함: 까닭), (추측: 까닭) 가운데 하나. (조사: …)는 조사.md의 확인표에서 「확인됨」인 것만 쓴다.
- 위 기능 목록에 없는 기능을 더하지 마라. 더할 만한 것은 「제안」 절에 따로 적어라.
- 자료 항목표에서 형식이 둘 이상이거나 빈 값이 있는 항목마다 원치 않는 동작 요구를 하나씩 써라.
- 정할 수 없는 것은 요구로 쓰지 말고 「열린 질문」 절에 적어라.
파일은 만들지 마라.

[실행 결과 자리: 명세 초안에 대한 Claude Code의 응답] 위 프롬프트를 교수의 관찰 기록, 자료 항목표, 조사 기록이 있는 ch04에서 계획 모드로 보낸 응답. 요구의 수와 문형 분포, 「제안」 절에 들어간 기능, 근거 표시가 없거나 자료 항목표에 없는 항목을 근거로 든 요구가 있었는지를 싣는다. 실행할 곳: 교수 PC의 Claude Code. 집필 환경에서는 모델을 부르지 않았다.

초안을 읽고 「제안」에서 받아들일 것을 고른다. 받아들인 것은 근거를 (정함: 까닭)으로 직접 적는다. 계획 모드를 나와(Shift+Tab) 요구사항명세서.md에 저장하게 한다.

  • 확인 11 요구사항명세서.md에 요구, 「열린 질문」 절이 있고, 내가 정한 기능 목록에 없는 기능이 요구에 없다.

7-6. 근거의 대조와 수용 기준

검사기를 돌린다.

터미널 
cd ~/llm-service-lab/ch04
python ~/kits/Service_04장/도구/ears_check.py 요구사항명세서.md --id "REQ-\d{2}"

출력의 꼴은 5-6과 같다. 끝의 「요약」 줄에서 요구, 수용 기준, 오류의 수를 읽는다. 수용 기준이 없는 요구는 경고(수용 기준(AC)이 없다)로 나온다. 경고는 종료 코드를 바꾸지 않으므로, 수용 기준을 붙일 요구를 고르는 목록으로 쓴다.

오류를 고친 뒤 사람이 명세를 끝까지 읽고 세 가지를 한다.

  1. 근거의 대조. (자료: …)의 항목 이름이 자료 항목표에 실제로 있는지 본다. (관찰: …)이 관찰 기록에 있는지 본다. 없으면 (추측: …)으로 바꾸거나 요구를 뺀다.
  2. 빈칸의 보강. 문형 분포에서 0인 문형을 본다. 관찰 기록의 「보고도 알 수 없는 것」에서 상황을 골라 요구를 더해 12개 이상으로 만든다.
  3. 수용 기준. 요구 다섯 개 이상에 수용 기준을 붙인다(6-1). 견본 자료의 실제 값으로 쓴다. 경계가 있는 요구는 경계의 양쪽을 쓴다.
  • 확인 12 검사기의 요약에서 요구가 12개 이상, 수용 기준이 5개 이상, 오류가 0건이고, 「원치 않는 동작」이 2 이상이며, 근거를 대조해 고친 요구가 하나 이상 있다(없으면 대조한 요구 셋을 적는다).

판정 기준은 7-1의 완료 기준 여섯 개이다.

정리

  • 리버스 엔지니어링은 이미 있는 시스템을 고치지 않고 분석해, 알아낸 구조와 기능을 문서로 적는 일이다. 이 과목은 참고 서비스의 화면 구성과 API의 자료를 읽어 내 서비스의 명세를 쓰는 데 쓴다.
  • 화면을 관찰할 때는 정보 항목, 조작, 화면 뒤의 처리, 모르는 것을 적는다. 직접 조작해 본 것은 확인으로, 짐작한 것은 추측으로 나누어 적는다.
  • API의 응답에는 화면에 보이기 전의 값이 항목 이름과 함께 들어 있다. 형식이 둘 이상인 항목과 빈 값이 있는 항목은 화면에 어떻게 보일지를 명세에 요구로 적는다.
  • 인증키는 저장소와 브라우저의 코드에 두지 않는다.
  • EARS는 요구 문장을 다섯 문형으로 쓰게 한다. 요구의 수가 0인 문형이 있으면 그 종류의 상황(사용자의 조작, 잘못된 입력 등)을 명세가 다루지 않은 것이다.
  • 시장 규모는 통계에서 온 수와 가정을 나누어 적고, 타겟 페르소나 한 사람을 정해 기능을 고르는 기준으로 삼는다.
  • AI의 조사 보고는 기획에 쓸 주장만 골라 출처와 화면을 직접 확인한 뒤에 쓴다.
  • 요구마다 근거(관찰, 자료, 조사, 정함, 추측)를 적는다. 근거를 적을 수 없는 요구는 AI가 요청 없이 넣은 것일 수 있으므로 뺀다.
  • 요구마다 그 요구가 충족되었는지 확인하는 방법을 수용 기준으로 적는다. 수용 기준을 쓸 수 없으면 요구가 모호한 것이므로 요구를 고친다. 지금 정할 수 없는 것은 열린 질문으로 남긴다.
