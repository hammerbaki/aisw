화면의 리버스 엔지니어링과 요구사항 명세

2027학년도 「LLM 서비스 개발」의 준비 중인 교재입니다. 편집 상태를 검토하기 위해 미리 공개한 것으로, 수업 전에 내용과 순서가 바뀔 수 있습니다.

학사 5주차 · 교재 04 · 서비스 1: 공고 모아보기 웹 (1/2)

개편 초안(2026-11-18). 이 장은 plan/개편안.md의 단원형 구성에 따라 다시 엮은 초안이다. 옛 4장과 6장의 본문에서 옮긴 절의 실행 출력은 옛 키트(Service_04장, Service_06장)에서 확인한 것이다. 「실행 전」이라고 적은 절은 공식 문서를 근거로 새로 쓴 것이며 명령과 출력을 실행으로 확인하지 않았다. 키트와 작업 폴더의 이름은 아직 옛 장 번호를 쓴다.

1~3장에서 도구와 협업의 흐름을 익혔다. 이 장부터 한두 주에 서비스 하나를 만든다. 첫 서비스는 공고 모아보기 웹이며, 이 장에서 명세를 쓰고 5장에서 구현해 배포한다.

이 장의 방법은 리버스 엔지니어링이다. 이미 있는 서비스의 화면을 관찰해 그 서비스의 명세를 되살린다. 대상은 공공 기관이 로그인 없이 공개한 채용 게시판의 목록 화면 하나이다. 관찰한 것을 기능 목록으로 정리하고, 요구 문장을 EARS 문형으로 쓰고, 요구마다 수용 기준을 붙인다. 같은 일을 하는 서비스 다섯 개의 기능을 비교표로 정리해 명세의 범위를 정한다.

이 장에서 만드는 것은 공고 목록 화면의 요구사항 명세서와 경쟁 서비스 기능 비교표이다. 명세에는 관찰한 것만 들어간다. 관찰하지 않은 기능이 명세에 있으면 그 자리는 AI가 정한 것이다.

학습 목표

  • 이미 있는 서비스의 화면을 관찰해 정보 항목, 조작, 화면 뒤의 처리를 기능 목록으로 정리할 수 있다.
  • 주소와 질의 문자열을 읽어 화면의 근거를 만들고, 읽히지 않는 화면을 다른 근거로 처리할 수 있다.
  • 요구를 EARS 다섯 문형으로 쓰고, 모호한 문장을 문형에 맞게 교정할 수 있다.
  • 요구마다 수용 기준을 붙이고, 확인한 것과 추측한 것, 정하지 못한 것을 구분해 명세서에 적을 수 있다.
  • 같은 일을 하는 서비스의 기능을 관찰한 사실만으로 비교표에 정리할 수 있다.

0. 시작하기

설치, 로그인, 키트 저장소의 클론, 가상 환경은 부록 A, 매 수업의 시작 순서는 A-21을 따른다. 작업은 VS Code의 통합 터미널 두 개에서 한다. 하나는 명령을 직접 실행하는 [터미널]이고 다른 하나는 Claude Code용이다.

  • 이 장의 실행 상한. 실제 모델은 Claude Code 대화형으로만 부른다. 핵심 실습의 프롬프트는 단계마다 한 번, 고쳐 보내기는 단계마다 한 번까지이다.
  • 「읽기」 표시. 꼬리표에 「(읽기)」를 붙인 코드 블록은 따라 치지 않고 읽는다.
  • 키트. 옛 6장의 키트(Service_06장: 검사기, 채용 목록 자료, 양식)와 옛 4장의 키트(Service_04장: 비교표의 양식과 점검기)를 쓴다. 옛 4장의 키트는 0-1의 명령에서 Service_06장을 Service_04장으로 바꾸어 같은 방법으로 복사한다.

0-1. 키트 받기

키트 저장소에서 새 키트를 받고(git pull), 옛 6장 키트를 홈의 kits/로 복사한다(부록 A-12-3). 키트는 저장소 밖의 ~/kits/에 두고 필요한 파일만 저장소로 복사한다. 키트 전체를 저장소에 넣으면 교재의 재료와 학습자의 산출물이 섞인다.

터미널 
git -C ~/kits-repo pull
mkdir -p ~/kits
cp -rn ~/kits-repo/Service_06장 ~/kits/
ls ~/kits/Service_06장
README.md  requirements.txt  tests  기준산출물  도구  복원  양식  연습

mkdir -p ~/kits를 먼저 하지 않으면 cp가 ~/kits라는 이름으로 키트 폴더를 복사해 ~/kits/도구, ~/kits/복원이 생기고 이 장의 모든 경로가 어긋난다. -n은 이미 있는 파일을 덮어쓰지 않으므로 다시 실행해도 받아 둔 파일은 남는다.

키트의 구성은 다음과 같다. 학습자가 고쳐 쓰는 파일은 모두 이름이 _양식.md 또는 _원문.md로 끝나며, 원본은 그대로 두고 복사본을 고친다.

  • 도구/: EARS 문형 검사기 ears_check.py(4-9, 5절)
  • tests/: 검사기의 테스트(0-2)
  • 연습/: EARS 교정 연습의 원문(4-9)
  • 복원/: 채용 게시판 목록 자료 채용.csv, 관찰 기록과 비교표의 양식(5절)
  • 양식/, 기준산출물/: 이 장에서는 쓰지 않는다.

0-2. 검사기 확인

이 장의 실습은 작은 파이썬 프로그램 ears_check.py를 여러 번 쓴다. 명세서의 요구 문장이 EARS 문형의 구조를 따르는지, 요구마다 ID가 있는지, 추적표의 ID가 명세에 실제로 있는지를 점검하는 도구다. 표준 라이브러리만 쓰므로 검사기 자체는 설치할 것이 없다. 키트에 든 테스트로 도구가 내 PC에서 도는지 먼저 확인한다. 테스트에 쓰는 pytest는 과목 공통의 가상 환경(부록 A-13)에 설치한다.

터미널 
source ~/llm-service-lab/.venv/Scripts/activate
cd ~/kits/Service_06장
python -m pip install -q -r requirements.txt
python -m pytest -q
...............................s..                                       [100%]
33 passed, 1 skipped in 0.68s

첫 줄은 Windows의 경로이며, macOS는 source ~/llm-service-lab/.venv/bin/activate이다. 건너뛴 한 개(s)는 교수용 견본이 있어야 도는 테스트이므로 학생용 키트에서는 건너뛰는 것이 정상이다. No such file or directory가 나오면 가상 환경이 아직 없는 것이다. 부록 A-13-2의 절차로 만든 뒤 위 명령을 다시 실행한다.

0-3. 웹 도구의 허용

이 장은 Claude Code의 웹 검색(WebSearch)과 웹 페이지 읽기(WebFetch) 도구를 쓴다. 두 도구는 기본 설정에서 쓰기 전에 허용을 묻는다 [C2]. Claude Code 터미널에서 저장소 루트로 이동해 claude를 실행하고, /permissions로 지금 허용된 규칙을 확인해 둔다.

Claude Code 
/permissions

목록에 WebFetch나 WebSearch 규칙이 없으면 정상이다. 처음 웹 도구를 쓸 때 허용 질문이 나오고, 이때 어느 도메인을 읽으려는지 확인하고 허용한다. 「Yes, and don’t ask again for 도메인」을 고르면 그 도메인의 허용 규칙이 저장소의 .claude/settings.local.json에 저장된다 [C2]. 이 파일은 개인 설정이므로 커밋하지 않는다. 화면의 이름과 선택지는 2026-11 기준이며 바뀔 수 있다.

[그림 자리: /permissions 화면] Claude Code에서 /permissions를 연 화면. 허용과 거부 규칙의 목록, 각 규칙이 온 설정 파일이 보이게. 찍을 곳: 내 PC(Windows, VS Code의 Git Bash 터미널)의 Claude Code, 저장소 루트에서 실행.

1. 리버스 엔지니어링

1-1. 정의

설계에서 출발해 구현으로 가는 일을 순공학(forward engineering)이라 한다. 리버스 엔지니어링(reverse engineering, 역공학)은 그 반대 방향이다. 소프트웨어공학에서 널리 쓰이는 Chikofsky와 Cross(1990)의 분류는 리버스 엔지니어링을 대상 시스템을 분석해 두 가지를 얻는 과정으로 정의한다. 하나는 시스템의 구성 요소와 그 사이의 관계를 알아내는 것이고, 다른 하나는 시스템을 다른 형태나 더 높은 추상 수준으로 표현하는 것이다[R1]. 이 정의에서 눈여겨볼 점은 리버스 엔지니어링이 대상 시스템을 바꾸지 않는다는 것이다. 관찰하고 표현할 뿐이다.

같은 분류에는 이웃한 용어가 있다. 이 장의 실습이 어느 일에 해당하는지 구분해 둔다.

용어 뜻 (Chikofsky와 Cross의 분류를 이 과목에 맞게 풀어 씀) 이 과목에서의 자리
순공학 요구와 설계에서 구현으로 간다 5장과 8장의 구현
리버스 엔지니어링 완성물을 분석해 구성과 관계를 알아내고 더 높은 수준으로 표현한다 5-3의 구조 분석과 명세 복원
재문서화(redocumentation) 같은 수준에서 다른 보기를 만든다(코드에서 주석이나 도표를 만드는 일) 6장의 코드에서 명세 뽑기 일부
설계 복원(design recovery) 코드 밖의 지식(도메인 지식, 외부 정보, 추론)까지 써서 설계를 되살린다 5-3에서 「추측」으로 표시하는 부분
재공학(reengineering) 분석한 결과로 새 형태를 만들고 다시 구현한다 5장의 재구현

이 장의 핵심 실습 앞부분은 엄밀히 말하면 리버스 엔지니어링(구조 분석, 명세 복원)과 재공학(재구현)을 잇는 것이다. 이 교재에서는 둘을 묶어 「리버스 엔지니어링 실습」이라 부른다.

1-2. 쓰임

리버스 엔지니어링은 「문서가 없거나 믿을 수 없는 상태에서 출발하는 일」에 쓰인다. 현업에서 자주 만나는 세 경우를 정리한다.

경우 출발점 얻으려는 것 이 장의 절차가 하는 일
레거시 시스템 오래 운영되었지만 명세가 없거나 코드와 어긋난 시스템 현재 동작의 정확한 기술, 새 시스템으로 옮길 범위 동작을 관찰해 명세로 고정하고, 새 구현이 그 명세를 지키는지 검사한다
경쟁 서비스 분석 다른 회사의 공개 화면 기능 목록, 정보 구조, 우리 서비스와의 차이 3절의 기능 비교표를 한 화면 수준의 명세로 깊게 한다
인수인계 전임자가 남긴 코드와 짧은 메모 무엇이 의도된 동작이고 무엇이 우연인지 코드에서 명세를 뽑아 전임자나 사용자에게 확인받는다(6장)

GitHub의 Spec Kit 소개 글도 명세 주도 개발이 잘 맞는 자리로 새 프로젝트, 기존 시스템의 기능 추가와 함께 레거시 현대화를 든다. 레거시 시스템의 업무 규칙을 현대적인 명세에 담고, 물려받은 기술 부채 없이 다시 만드는 방식이다[S1]. 리버스 엔지니어링으로 명세를 되살리면 그 뒤는 명세 주도 개발의 순서를 그대로 따른다. 두 방법론이 한 장에 함께 있는 까닭이 여기에 있다.

1-3. 절차

이 장의 리버스 엔지니어링은 여섯 단계로 진행한다. 2026년 2학기판의 「명세를 뽑는 여섯 단계」를 이 과목의 용어로 다시 정리한 것이다[R2].

①과 ⑥이 사람의 일이라는 점이 중요하다. AI가 구조를 분석하고 명세를 쓰고 재구현까지 할 수 있지만, 「AI가 본 것이 실제 화면과 같은가」와 「차이가 결함인가 의도인가」는 사람이 판단한다. ⑤에서 원본의 정보를 막는 것도 같은 까닭이다. 재구현하는 AI가 원본을 볼 수 있으면 명세의 빈틈을 원본으로 메워 버리고, 빈틈이 드러나지 않는다.

1-4. 가져오는 것과 가져오지 않는 것

리버스 엔지니어링의 대상이 남의 서비스일 때는 경계를 먼저 정한다. 이 과목의 규칙은 다음과 같다.

  • 가져오는 것은 구조와 항목이다. 어떤 정보가 어떤 순서로 있고, 사용자가 무엇을 할 수 있는지를 명세 문장으로 옮긴다.
  • 가져오지 않는 것은 문장, 이미지, 코드다. 공고 원문을 통째로 옮기지 않고, 화면의 그림과 스크립트를 복사해 재구현에 넣지 않는다.
  • 로그인해야 보이는 화면, 개인 정보가 나오는 화면은 대상으로 삼지 않는다.
  • 자동으로 많은 요청을 보내지 않는다. 이 장의 실습은 한 사람이 목록 한 쪽을 몇 번 받아 보는 수준이다.
  • 사이트가 자동 수집 프로그램에 대해 밝혀 둔 규칙(robots.txt)과 이용 약관을 확인한다.

robots.txt는 사이트의 맨 위 경로에 두는 글 파일로, 자동 수집 프로그램(봇)에게 어느 경로를 가져가도 되는지 알린다. 사람이 브라우저로 보는 데는 적용되지 않지만, Claude Code의 웹 읽기 도구처럼 프로그램이 페이지를 가져올 때는 이 규칙을 따르는 경우가 있다. 2026년 2학기판 수업에서는 한 공공기관 사이트가 모든 봇을 막아 두어 AI의 웹 읽기가 거부될 수 있었고, curl로 받은 파일을 대신 읽혔다[R2]. 이 장의 대상 사이트의 규칙은 다음과 같다.

[터미널] (읽기)

curl -sL https://www.gjcity.go.kr/robots.txt
User-agent: Googlebot
Disallow:/sys/
Disallow:/saeol/
Disallow:/portal/bbs/list.do?ptIdx=64&mId=0502030000
Disallow:/portal/bbs/list.do?ptIdx=63&mId=0502010000
Disallow:/search/

2026-11-14에 받은 내용이며, 2026-11-16과 11-17에 다시 받아도 같았다. 이 규칙은 구글의 수집 프로그램에게 관리 경로와 일부 게시판, 검색 경로를 가져가지 말라고 한다. 이 장에서 읽을 채용시험정보 목록(/portal/examInfo/list.do)은 막힌 경로에 없다. 규칙은 사이트가 언제든 바꿀 수 있으므로 교수가 수업 당일에 다시 확인한다. 다른 후보 화면처럼 다른 사이트를 대상으로 삼을 때는 학습자가 같은 명령으로 직접 확인한다.

[최신 자료 자리: 대상 사이트의 규칙과 목록의 상태] robots.txt, 목록의 주소(mId=0202050000), 전체 쪽 수, 상태 값(stateCode 0~3), 표의 열 구성. 확인할 곳: https://www.gjcity.go.kr/robots.txt, D1의 주소. 2026-11-17의 값: robots.txt는 위와 같음, 76쪽, 접수중 8건, 접수예정 1건, 없는 검색어 0건. 누리집이 개편되면 HTML의 이름(td class="num", boardView)이 바뀌어 2절과 5절의 명령이 돌지 않으므로 수업 전에 다시 실행한다.

2. 화면과 URL을 읽는 방법

명세를 복원하려면 먼저 화면을 읽어야 한다. 웹 화면은 사람에게는 같은 화면으로 보여도, 프로그램에게는 「주소 한 번으로 내용이 다 오는 화면」과 「브라우저가 스크립트를 돌려야 내용이 생기는 화면」으로 나뉜다. 어느 쪽인지에 따라 AI에게 근거를 주는 방법이 달라진다. 이 절은 핵심 실습(5절)의 대상인 경기도 광주시청 누리집의 「채용시험정보」 목록으로 그 차이를 확인한다[D1]. 이 절의 명령은 「읽기」이다. 학습자는 명령과 출력을 읽고, 실제로 받는 것은 5-2에서 한다.

2-1. URL의 구조

브라우저 
https://www.gjcity.go.kr/portal/examInfo/list.do?mId=0202050000

브라우저로 이 주소를 열면 표가 하나 보인다. 열은 번호, 제목, 모집기관, 상태, 접수기간, 조회수, 등록일이고, 표 위에 상태를 고르는 상자와 검색이 있으며, 표 아래에 쪽 번호가 있다.

[그림 자리: 채용시험정보 목록 화면] 목록 첫 쪽 전체 캡처에 세 곳을 번호로 표시한다. ① 표 위의 상태 상자와 검색 영역, ② 표의 일곱 열, ③ 표 아래의 쪽 번호. 주소 표시줄의 list.do?mId=0202050000이 보이게 찍는다. 찍을 곳: 브라우저, 위 주소, 수업 직전. 이 주소를 부분으로 나누면 다음과 같다.

부분 값 뜻
스킴 https 암호화된 HTTP로 주고받는다
호스트 www.gjcity.go.kr 요청을 받는 서버의 이름
경로 /portal/examInfo/list.do 서버 안에서 어떤 화면(프로그램)을 부르는지. list.do는 목록 화면이다
질의 문자열 ?mId=0202050000 화면에 넘기는 값. 이름=값을 &로 잇는다. 여기서는 메뉴 번호

질의 문자열은 화면의 상태를 주소에 담는다. 같은 경로에 다른 값을 넘기면 다른 화면이 온다. 2-3에서 상태를 고르는 값을 직접 붙여 본다. 주소가 화면의 상태를 얼마나 담는지가 「URL로 읽히는 서비스인가」를 가르는 첫 번째 기준이다.

먼저 서버가 무엇을 돌려주는지 본다. -o /dev/null은 본문을 버리고, -w는 응답의 상태 코드와 형식을 출력하게 한다.

[터미널] (읽기)

curl -s -o /dev/null -w "%{http_code} %{content_type}\n" "https://www.gjcity.go.kr/portal/examInfo/list.do?mId=0202050000"
200 text/html;charset=UTF-8

200은 요청이 성공했다는 상태 코드이고, text/html;charset=UTF-8은 본문이 UTF-8로 인코딩된 HTML이라는 뜻이다. 오래된 공공 사이트 가운데는 EUC-KR로 된 곳도 있으며, 그때 받은 파일은 한국어가 깨져 보인다. 그런 경우 iconv -f euc-kr -t utf-8 페이지.html > 페이지_utf8.html로 바꾼 뒤 읽힌다.

출력 뜻 할 일
200 text/html;charset=UTF-8 정상이다 다음 단계로 간다
000 응답을 받지 못했다. 내 PC가 바깥 인터넷으로 나가지 못하거나(학교 망의 차단) 주소가 틀렸다 curl -sI https://www.google.com으로 바깥 연결을 먼저 본다. 바깥 연결이 안 되면 교수에게 알리고 키트의 채용.csv만으로 5절을 한다
200인데 2-2의 grep -c가 0이다 이 누리집은 없는 경로에도 200과 안내 화면을 돌려준다(2026-11-16, /portal/examInfo/nolist.do로 시험함). 상태 코드만으로는 경로가 맞는지 알 수 없다 브라우저로 같은 메뉴를 찾아 주소를 다시 확인한다. 누리집이 개편되었을 수 있다

2-2. 서버가 그린 표와 브라우저가 그린 화면

웹 화면이 만들어지는 방식은 크게 둘이다. 서버 렌더링은 서버가 표의 행까지 채운 HTML을 보내는 방식이고, 클라이언트 렌더링은 서버가 빈 틀과 스크립트를 보내면 브라우저가 스크립트를 돌려 자료를 받아 화면을 채우는 방식이다. 앞의 방식이면 curl로 받은 HTML 안에 표의 내용이 그대로 들어 있고, 뒤의 방식이면 빈 틀만 있다. 2026년 2학기판의 지도 앱 예제는 뒤의 경우였다. 주소를 읽으면 빈 껍데기만 오고, 가게 목록과 거리는 사람이 눌러야 나타났다[R2].

채용시험정보 목록이 어느 쪽인지 확인한다. 5-2에서 같은 명령으로 실습 폴더에 받는다.

[터미널] (읽기)

curl -sL "https://www.gjcity.go.kr/portal/examInfo/list.do?mId=0202050000" > 페이지.html
grep -c '<td class="num">' 페이지.html
grep -o '전체 페이지 [0-9]*' 페이지.html
10
전체 페이지 76

번호 칸(<td class="num">)이 10개 있으므로 표의 10행이 HTML에 이미 들어 있다. 서버 렌더링이다. 이런 화면은 Claude Code의 웹 읽기로도, curl로 받은 파일로도 근거를 만들 수 있다. 전체 쪽 수는 받은 날에 따라 다르다(2026-11-14와 11-17에 76쪽).

2-3. 질의 문자열로 화면 상태를 바꾸기

표 위의 상태 상자가 어떤 값을 보내는지 HTML에서 찾는다.

[터미널] (읽기)

grep -o '<option value="[0-9]">[^<]*' 페이지.html
<option value="0">접수예정
<option value="1">접수중
<option value="2">마감
<option value="3">결과공고

상자의 이름(name="stateCode")과 값을 알았으니 주소에 직접 붙여 본다. 「접수중」은 stateCode=1이다.

[터미널] (읽기)

curl -s "https://www.gjcity.go.kr/portal/examInfo/list.do?mId=0202050000&stateCode=1" | grep -c '<td class="num">'
curl -s "https://www.gjcity.go.kr/portal/examInfo/list.do?mId=0202050000&stateCode=1" | grep -o 'test_ing">[^<]*' | sort | uniq -c
8
      8 test_ing">접수중

행의 수가 바뀌고, 모든 행의 상태가 접수중이다(2026-11-17. 숫자는 받은 날에 따라 다르다). 상태 거르기는 서버가 하는 처리이며, 주소로 그 상태를 재현할 수 있다는 뜻이다. 이렇게 확인한 사실은 구조 분석에서 「추측」이 아니라 「확인」으로 적는다. 같은 방법으로 화면에서는 쉽게 볼 수 없는 경우도 확인할 수 있다. 5장의 비교에서 이 방법을 다시 쓴다.

2-4. 양식 제출과 자바스크립트 링크

주소로 모든 화면이 열리는 것은 아니다. 표의 제목을 누르면 상세 화면이 열리는데, 그 링크를 HTML에서 보면 다음과 같다.

[터미널] (읽기)

grep -o 'onclick="boardView([^)]*)' 페이지.html | head -3
grep -o 'form id="listForm"[^>]*' 페이지.html
onclick="boardView('1','1497')
onclick="boardView('1','1496')
onclick="boardView('1','1495')
form id="listForm" name="listForm" action="/portal/examInfo/list.do?mId=0202050000" method="post"

제목의 링크 주소는 #이고, 누르면 boardView라는 스크립트 함수가 돌아 숨은 양식에 글 번호를 넣고 POST 방식으로 제출한다. POST는 값을 주소가 아니라 요청 본문에 실어 보내므로, 상세 화면은 주소 하나로 열리지 않는다. 주소만 받아 읽는 AI는 목록까지는 읽지만 상세 화면의 내용은 읽지 못한다. 이 장의 복원 범위를 목록 화면 하나로 못 박는 까닭이다. 상세 화면의 내용을 명세에 넣으면 근거 없이 지어낸 문장이 된다.

조작 방식 주소로 재현되는가 구조 분석에서의 처리
목록 보기 GET, 서버 렌더링 된다 확인
상태 고르기 양식은 POST이나 주소의 질의 문자열도 받는다 된다(stateCode) 확인
쪽 이동 스크립트가 양식의 page 값을 바꾸어 제출 질의 문자열로 시험할 수 있다 확인 또는 추측
상세 보기 스크립트 함수 boardView가 POST로 제출 안 된다 범위 밖, 「알 수 없는 것」에 적는다

2-5. 읽히지 않는 화면의 처리

주소로 읽히지 않는 화면을 만나면 근거를 만드는 다른 방법을 쓴다. 근거가 바뀌어도 그 뒤의 단계(구조 분석 → 기능 목록 → 명세 → 재구현 → 비교)는 같다.

방법 언제 쓰나 장점 한계
① Claude Code의 웹 읽기(WebFetch) 서버 렌더링이고 봇을 막지 않을 때 프롬프트에 주소만 붙이면 된다 페이지를 마크다운으로 바꾼 뒤 별도의 모델 호출로 필요한 부분만 뽑아 넘긴다. 세부가 빠질 수 있다. 스크립트가 그리는 내용은 오지 않는다
② curl로 받은 HTML 웹 읽기가 거부되거나 원문 HTML이 필요할 때 표의 구조, 양식의 이름과 값까지 그대로 있다 스크립트가 그리는 내용은 역시 없다. 파일이 크다
③ 화면 캡처 스크립트가 그리는 화면, 배치와 색을 보아야 할 때 Claude Code에 이미지로 넣어 읽힐 수 있다 그 순간 보인 것까지만 근거가 된다. 값과 규칙은 없다
④ 사람의 관찰 기록 눌러야 바뀌는 흐름, 쓰면서 느끼는 불편 사용 맥락이 담긴다 사람마다 다르고, 빠뜨리고, 해석이 섞인다
⑤ 화면을 조작하는 AI 여러 화면을 눌러 가며 관찰해야 할 때 조작 기록과 캡처를 함께 남긴다 도구와 계정이 필요하다. 이 과목의 실습 환경에는 없다(2026년판 예제 C는 교수 시연이었다)

①에 대해 Claude Code 공식 문서는 웹 읽기 도구가 설계상 손실이 있는(lossy) 방식이라고 밝히고, 가공하지 않은 페이지가 필요하면 셸에서 curl을 쓰라고 안내한다[S7]. 기본 권한 모드에서 웹 읽기는 가져오기 전에 허락을 묻는다. 「Yes」는 이번 한 번만 허락하므로 같은 도메인이라도 다음에 다시 묻고, 「Yes, and don’t ask again for 도메인」은 그 도메인을 저장소의 .claude/settings.local.json에 허용 규칙으로 저장한다(2026-11 기준)[S7]. 수업에서는 이번 한 번만 허락하는 쪽을 고른다.

③의 경우 Claude Code는 이미지를 대화에 넣는 방법으로 끌어다 놓기, 붙여넣기, 이미지 파일 경로를 주는 방법을 공식 문서에 적고 있다[S4]. 캡처를 실습 폴더(예: ch06/복원/캡처/)에 저장한 뒤, 프롬프트에 「캡처/목록.png의 화면을 분석하라」처럼 경로를 적는 방법이 가장 간단하다. 어떤 캡처를 근거로 썼는지가 파일로 남기 때문이다.

어느 방법을 쓰든 공통으로 지킬 것이 있다. 근거의 종류와 날짜를 구조 분석의 맨 위에 적고, 근거에서 직접 본 것과 추론한 것을 구분해 「확인」과 「추측」으로 표시한다. 같은 주소라도 날이 바뀌면 공고가 바뀌므로, 관찰한 날짜가 없는 명세는 나중에 비교할 수 없다.

3. 경쟁 서비스의 기능 비교

명세의 범위를 정하려면 같은 일을 하는 서비스가 무엇을 제공하는지 알아야 한다. 이 절은 화면에서 확인한 사실만으로 기능 비교표를 만드는 방법을 다룬다.

3-1. 직접 경쟁, 간접 경쟁, 대체재

경쟁 서비스는 “같은 사용자의 같은 업무를 무엇이 대신 해결하는가”로 찾는다. 이름이 비슷한 서비스만 찾으면 실제 경쟁자를 놓친다. 취업 준비생이 마감일을 챙기는 데 쓰는 가장 흔한 도구는 취업 사이트가 아니라 휴대전화의 메모나 표 계산 프로그램일 수 있다.

분류 정의 공통 사례의 예
직접 경쟁 같은 사용자의 같은 업무를 같은 방식(온라인 서비스)으로 지원한다 취업 준비생 대상 채용 정보·자기소개서 서비스 (사람인, 잡코리아, 링커리어, 자소설닷컴)
간접 경쟁 같은 업무를 지원하지만 중심 사용자나 중심 업무가 다르다 공공 고용 서비스 전반을 다루는 고용24, 이직 콘텐츠가 첫 화면에 많은 원티드
대체재 다른 방식으로 같은 업무를 해결한다 학교 취업지원실의 상담, 표 계산 프로그램과 메모, 범용 AI 대화 서비스, 스터디 모임

분류는 판단이다. 판단에는 근거를 붙인다. 예를 들어 원티드를 간접 경쟁으로 둔 근거는 2026-11-14의 첫 화면에 “이직 로드맵” 같은 콘텐츠와 이직·연봉 질문을 멘토에게 묻는 안내가 보였다는 관찰이다 [K6]. 이 관찰이 “원티드는 신입 공고가 없다”는 뜻은 아니다. 관찰한 것과 추정한 것을 구분해 적는다.

대체재는 비교표에 넣지 않더라도 보고에는 적는다. 대체재가 강하면 새 서비스가 들어갈 자리가 좁다. 공고 모아보기 웹의 경우 “범용 AI 대화 서비스로 자기소개서를 고친다”는 대체재가 있으므로, 공통 사례의 자기소개서 피드백은 범용 대화 서비스와 무엇이 다른지(공고와의 대조, 일정과의 연결)를 가치 제안에서 밝혀야 한다.

3-2. 비교할 서비스 고르기

NN/g의 경쟁 사용성 평가 안내는 비교 대상을 2~4개로 두고, 후보가 많으면 비슷한 기능, 좋은 사용자 경험, 혁신적인 설계, 시장에서의 비중, 사용자가 실제로 함께 비교할 가능성으로 먼저 거르라고 권한다 [M3]. 또 내 서비스보다 못한 서비스만이 아니라 나은 서비스도 넣으라고 한다 [M3]. 못한 서비스만 보면 배울 것이 적다.

이 장은 사용성 평가가 아니라 기능 비교를 하므로 다섯 개를 고른다. 기능 비교는 사용자 과업을 직접 시켜 보는 평가보다 서비스당 시간이 적게 들기 때문이다. 공통 사례의 다섯 서비스와 고른 까닭은 다음과 같다.

  • 사람인 [K1]: 첫 화면에 신입·인턴 메뉴와 AI 기능 메뉴가 함께 있다.
  • 잡코리아 [K2]: 공채 정보와 신입·인턴 메뉴가 첫 화면에 있다.
  • 링커리어 [K3]: 대외활동·공모전·자기소개서 메뉴가 중심이다.
  • 자소설닷컴 [K4]: 채용달력과 자기소개서 메뉴가 첫 화면에 있다.
  • 고용24 [K5]: 고용노동부의 공공 고용 서비스이며, 취업지원 메뉴 아래 「우리학교 취업지원실」이 있다.

이 다섯 개는 공통 사례의 기준 선택이다. 수업 시점에 서비스가 바뀌었으면 같은 기준으로 바꾸어 고르고, 고른 까닭을 비교표 4절의 「분류의 근거」에 적는다.

3-3. 화면에서 기능 목록 뽑기

경쟁 서비스의 기능을 아는 가장 확실한 방법은 그 서비스의 화면을 직접 보는 것이다. 보도 기사나 블로그의 소개는 오래되었거나 과장되었을 수 있다. 화면을 관찰해 구조와 기능을 문서로 되살리는 일이 리버스 엔지니어링(reverse engineering)이고, 기능 목록은 그 첫 단계다. 이 장의 핵심 실습은 여기서 한 걸음 더 나아가 한 화면의 정보 항목과 조작과 규칙을 명세로 복원하고, 5장은 그 명세만으로 다시 만들어 원본과 비교한다.

화면에서 기능을 뽑는 절차는 네 단계다.

  1. 화면을 고정한다. 어느 주소를, 어떤 상태(로그인 여부, PC 또는 모바일)로, 언제 보았는지 적는다. 같은 서비스라도 로그인 전후와 기기에 따라 화면이 다르다.
  2. 메뉴를 그대로 옮긴다. 메뉴의 이름을 바꾸지 않고 화면의 표기 그대로 적는다. “채용달력”, “공고달력”, “채용 캘린더”는 서비스마다 다른 이름이다. 옮기는 단계에서 이름을 통일하면 무엇을 보았는지 되짚을 수 없다.
  3. 기능을 사용자 업무로 묶는다. 옮긴 메뉴를 사용자가 하려는 일(공고 찾기, 일정 챙기기, 서류 쓰기, 회사 알아보기, 물어보기)로 묶는다. 비교표의 행은 메뉴 이름이 아니라 이 업무의 이름이다.
  4. 관찰과 추정을 나눈다. 화면에 글자로 보인 것만 「확인됨」으로 적는다. 메뉴 이름으로 기능을 짐작한 것(예: 「취업톡톡」은 커뮤니티일 것이다)은 비고에 “메뉴 이름으로 판단”이라고 적는다.

3-4. 기능 비교표 만드는 법

비교표의 칸에 무엇을 쓰는지가 비교표의 품질을 정한다. 이 장의 비교표는 세 기호만 쓴다.

  • ○(확인됨): 메뉴나 화면에서 그 기능을 글자로 확인하였다.
  • △(일부·조건부): 기능의 일부만 있거나(작성 가이드는 있으나 작성 도구는 없다), 앱에서만 된다는 안내가 있다. 조건을 비고에 쓴다.
  • -(확인되지 않음): 관찰한 범위에서 보지 못하였다.

「-」를 “없음”으로 읽으면 안 된다. 첫 화면에서 보지 못한 기능이 로그인 뒤나 앱에 있을 수 있다. 「×(없음)」를 쓰려면 없다는 것을 확인해야 하는데, 공개 화면만으로는 그것을 확인하기 어렵다. 경쟁 서비스를 비방하지 않고 사실만 적는 방법이기도 하다.

표를 읽는 법도 정해 둔다. 모든 서비스가 ○인 행(공고 검색, 일정 달력, 기업 정보)은 이 서비스가 갖추어야 하지만 차별점은 되지 못하는 기능이다. 한두 서비스만 ○인 행(AI 코칭, 공공 지원 제도)은 차별점의 후보이거나, 수요가 작아 다른 서비스가 넣지 않은 기능이다. 어느 쪽인지는 비교표만으로 알 수 없고, 7장의 사용자 조사로 확인한다.

잡코리아의 이력서 칸이 「-」인 것은 관찰 범위의 한계를 보여 준다. 대형 채용 서비스에 이력서 기능이 없다고 보기는 어렵다. 그러나 이 장의 규칙은 “첫 화면과 전체 메뉴에서 글자로 확인한 것”이므로 「-」로 둔다. 이런 칸은 비고에 “첫 화면 메뉴에서 관찰되지 않았다”고 적어, 읽는 사람이 없다는 뜻으로 오해하지 않게 한다. 관찰 범위를 넓히면(예: 한 서비스의 하위 화면까지 관찰) 칸의 값이 바뀔 수 있다.

이기는 서비스를 정하는 표 비교표를 점수 경쟁으로 쓰면 ○가 많은 서비스를 따라 만들게 된다 NN/g는 경쟁 평가의 목적이 내 설계를 개선하는 것이며, 경쟁자를 베끼지 말고 차별화할 기회를 찾으라고 한다 [M3]
오래된 관찰 서비스는 메뉴를 자주 바꾼다 관찰 날짜를 적고, 수업 시점에 다시 관찰한다
상표의 과용 서비스 이름과 화면을 보고서 밖에서 쓰거나 평가를 덧붙인다 상표는 사실을 서술하는 범위에서만 쓰고, 확인되지 않은 주장을 쓰지 않는다

3-6. 경쟁 서비스 조사의 예절

경쟁 서비스는 남의 서비스다. 관찰하는 방법에도 지킬 선이 있다.

  1. 공개된 화면만 본다. 이 장의 관찰은 로그인하지 않은 상태에서 누구나 볼 수 있는 화면으로 한정한다. 관찰을 위해 계정을 만들거나 유료 기능을 결제하지 않는다. 로그인 뒤의 기능이 꼭 필요하면 학습자가 평소 쓰는 자기 계정으로 보되, 화면에 나온 다른 사람의 정보(지원자 수, 댓글 작성자 등)를 기록에 옮기지 않는다.
  2. 한 번에 한 페이지씩 읽는다. Claude Code의 웹 페이지 읽기 도구는 한 번에 주소 하나를 읽는다. 이 장의 관찰에는 서비스마다 첫 화면 하나면 충분하다. 공고 목록을 대량으로 긁어 모으는 프로그램을 만들거나 AI에게 그런 수집을 시키지 않는다. 서비스마다 이용약관이 자동 수집을 제한할 수 있고, 수집한 공고와 게시글에는 다른 사람의 저작권과 개인 정보가 섞여 있다.
  3. 사실만 쓴다. 비교표와 보고에는 관찰한 사실(메뉴의 이름, 기능의 유무)만 쓴다. “불편하다”, “광고가 많아 쓰기 싫다” 같은 평가는 평가 방법(13장의 휴리스틱 평가나 사용성 테스트)과 결과가 없으면 쓰지 않는다. 서비스를 깎아내리는 문장은 사실이어도 조사 보고의 목적(내 서비스의 방향을 정하는 것)에 보탬이 되지 않는다.
  4. 상표는 서술에만 쓴다. 서비스 이름은 무엇을 관찰했는지 밝히기 위해 쓴다. 공통 사례의 이름, 화면, 홍보 문구에 다른 서비스의 이름이나 로고를 쓰지 않는다.
  5. 화면을 그대로 옮기지 않는다. 화면 캡처는 수업 안에서 관찰 근거로만 쓰고, 공개 저장소에 올리지 않는다. 비교표의 근거는 메뉴 이름(짧은 사실)으로 충분하다.

4. 요구사항과 EARS 문형

4-1. 용어

이 과목에서 쓰는 용어를 정리한다. 같은 학기의 「소프트웨어공학」에서 더 엄밀한 정의를 다룰 수 있으며, 이 장은 실습에 필요한 범위로 한정한다.

기능 요구 시스템이 무엇을 하는가에 관한 요구 상태를 고르면 그 상태의 공고만 보인다

요구와 수용 기준은 짝이다. 요구는 「무엇을 해야 하는가」를 말하고, 수용 기준은 「무엇을 보면 했다고 인정하는가」를 말한다. 요구만 있고 수용 기준이 없으면, 구현한 사람과 검사하는 사람이 서로 다른 장면을 떠올린다. 5장의 인수 조건 표와 간단한 자동 검사는 이 장에서 쓴 수용 기준을 그대로 옮긴 것이 된다.

4-2. 좋은 요구 문장의 성질

요구 문장이 갖추어야 할 성질을 이 과목의 점검 기준으로 정리한다. 오른쪽 열은 이 장의 검사기 ears_check.py가 그 성질을 기계적으로 보는지, 사람이 보아야 하는지를 적은 것이다.

성질 뜻 어긋난 예 점검
검증 가능성 충족 여부를 관찰로 판정할 수 있다 「공고를 보기 좋게 보인다」 모호한 말은 검사기가 경고, 판정 가능성은 사람

마지막 성질이 중요하다. 명세가 「어떻게」까지 정하면 구현의 선택지가 줄고, 기술이 바뀔 때마다 명세를 고쳐야 한다. 명세는 「무엇을, 왜」를 말하고, 「어떻게」는 계획(plan)과 코드가 맡는다. 5장에서 보는 Spec Kit도 명세 단계에서 기술 스택을 쓰지 말고 계획 단계로 미루라고 한다[S2].

4-3. 자연어 요구의 문제

요구를 자유로운 문장으로 쓰면 세 가지 문제가 되풀이된다.

  • 모호성. 「잘」, 「적절히」, 「빠르게」, 「필요 시」처럼 확인할 수 없는 말이 들어간다. 「빠르게」가 0.5초인지 5초인지는 쓴 사람만 안다.
  • 불완전성. 정상적인 흐름만 적고 잘못된 입력, 자료가 없을 때, 기다리는 동안의 일을 빠뜨린다. 2026년 2학기판 수업에서 학생들이 AI로 뽑은 명세는 대부분 「원치 않는 동작」이 비어 있었다[R2].
  • 해석의 갈림. 같은 문장을 기획자, 개발자, 검사자, AI가 서로 다르게 읽는다. 「공고를 상태별로 보여야 한다」는 상태별 탭으로도, 상태 열로도, 상태 순 정렬로도 읽힌다.

이 세 문제는 AI가 구현을 맡을 때 더 커진다. 사람 개발자는 모호한 문장 앞에서 묻지만, AI는 대개 묻지 않고 하나를 골라 구현한다. 어느 쪽을 골랐는지는 결과를 보기 전까지 모른다.

4-4. EARS의 기원과 원리

EARS(Easy Approach to Requirements Syntax)는 요구 문장을 몇 가지 정해진 틀에만 맞추어 쓰게 하는 작성법이다. 롤스로이스의 Alistair Mavin과 동료들이 항공기 엔진 제어 시스템의 감항 규정을 분석하면서 만들었고, 2009년 미국 애틀랜타에서 열린 제17회 IEEE 국제 요구공학 학술대회(RE’09)에서 발표하였다[S3, S3a]. 논문은 자연어 요구에서 흔히 나타나는 여덟 가지 문제(모호성, 막연함 등)를 겨냥한 소수의 구조 규칙을 제안하고, 그 규칙을 따르면 모든 자연어 요구가 다섯 가지 단순한 틀 가운데 하나에 들어간다고 보였다. 감항 규정에서 뽑은 엔진 제어 요구에 적용한 사례 연구에서 일반적인 서술식 명세보다 질과 양 모두에서 나아졌다고 보고하였다[S3a].

EARS의 원리는 두 가지로 요약된다.

  1. 절의 순서를 고정한다. 요구 문장은 「전제 조건 → 트리거 → 시스템 이름 → 시스템의 응답」의 순서로 쓴다. 전제 조건은 없거나 여럿일 수 있고, 트리거는 없거나 하나이며, 시스템 이름은 정확히 하나, 응답은 하나 이상이다[S3].
  2. 키워드로 문형을 드러낸다. 조건이 상태인지 사건인지 선택 기능인지 원치 않는 상황인지를 키워드(While, When, Where, If … then)가 알린다. 키워드만 보아도 그 문장이 언제 적용되는지 알 수 있다.

EARS는 특별한 도구나 긴 교육 없이 쓸 수 있고, 영어가 모국어가 아닌 작성자에게도 도움이 된다고 저자는 밝힌다[S3]. 2025년부터는 AWS의 명세 주도 개발 도구 Kiro가 요구 문서(requirements.md)를 EARS 꼴로 쓰고 있다[S6].

4-5. 다섯 문형과 복합 문형

영어 원형은 Mavin의 공개 자료를 따르고[S3], 한국어 문형은 이 과목의 약속이다. 한국어는 동사가 문장 끝에 오므로 영어의 「the system shall」을 「시스템은 ~해야 한다」로 문장 끝에 둔다.

문형 키워드 영어 원형 한국어 문형 (이 과목의 약속) 언제 쓰나
상시(유비쿼터스) 없음 The <system> shall <response> 시스템은 <응답>해야 한다. 늘 성립해야 하는 성질
사건(이벤트) When When <trigger>, the <system> shall <response> <트리거>하면(할 때), 시스템은 <응답>해야 한다. 사용자의 동작이나 외부 사건에 대한 반응
상태 While While <precondition>, the <system> shall <response> <상태>인 동안, 시스템은 <응답>해야 한다. 어떤 상태가 이어지는 동안 계속 성립
선택 기능 Where Where <feature is included>, the <system> shall <response> <기능>이 포함된 경우, 시스템은 <응답>해야 한다. 판이나 설정에 따라 있을 수도 없을 수도 있는 기능
원치 않는 동작 If … then If <trigger>, then the <system> shall <response> 만약 <트리거>하면, 시스템은 <응답>해야 한다. 잘못된 입력, 실패, 자료 없음 같은 바라지 않는 상황
복합 둘 이상 While <precondition>, when <trigger>, the <system> shall <response> <상태>인 동안 <트리거>하면, 시스템은 <응답>해야 한다. 상태와 사건이 함께 걸릴 때

Mavin의 자료에 실린 예를 하나씩 우리말로 옮겨 보면 문형의 차이가 드러난다. 「휴대전화는 무게가 XX그램 미만이어야 한다」는 상시, 「『음소거』가 선택되면 노트북은 모든 소리 출력을 막아야 한다」는 사건, 「ATM에 카드가 없는 동안 ATM은 『카드를 넣어 시작한다』를 표시해야 한다」는 상태, 「차에 선루프가 있는 경우 차는 운전석 문에 선루프 조작판을 두어야 한다」는 선택, 「잘못된 카드 번호가 입력되면 웹사이트는 『카드 정보를 다시 입력한다』를 표시해야 한다」는 원치 않는 동작이다[S3].

같은 화면에 다섯 문형을 적용하면 다음과 같다. 대상은 2절에서 읽은 채용 공고 목록이다.

[상시] 시스템은 공고 목록을 번호의 내림차순으로 한 쪽에 10행씩 표시해야 한다.
[사건] 사용자가 상태를 고르고 검색을 실행하면, 시스템은 그 상태의 공고만 표시해야 한다.
[상태] 공고가 결과공고 상태인 동안, 시스템은 접수기간 칸에 「-」를 표시해야 한다.
[선택] 관심 공고 기능이 포함된 경우, 시스템은 각 행에 관심 표시 단추를 두어야 한다.
[원치 않는 동작] 만약 조건에 맞는 공고가 없으면, 시스템은 「검색 결과가 없다」는 안내를 표시해야 한다.
[복합] 공고가 접수중 상태인 동안 사용자가 그 공고를 고르면, 시스템은 접수 마감일까지 남은 날을 표시해야 한다.

4-6. 한국어로 쓸 때의 규칙

한국어 EARS는 표준이 따로 없다. 이 과목은 다음 규칙을 약속으로 정하고, 검사기 ears_check.py도 이 규칙으로 판정한다.

  1. 주체는 하나다. 응답 절의 주체를 「시스템은」으로 쓴다. 서비스 이름을 주체로 쓰려면 명세서의 문서 정보에 그 이름을 밝히고, 검사기에 --system 이름을 준다.
  2. 응답은 「~야 한다」로 끝난다. 「표시해야 한다」, 「보여야 한다」, 「두지 않아야 한다」처럼 의무를 나타내는 꼴이다. 「표시한다」, 「보여 준다」는 서술이지 요구가 아니다.
  3. 한 문장에 응답 하나. 「저장해야 하고 알림을 보내야 한다」는 두 요구다. 문장을 나누고 ID를 따로 붙인다. 응답 하나가 여러 동작을 묶는 「진행 표시를 보이고 단추를 비활성 상태로 두어야 한다」는 허용하되, 따로 검사할 필요가 있으면 나눈다.
  4. 조건절은 키워드로 끝난다. 사건은 「~하면」이나 「~할 때」, 상태는 「~인 동안」, 선택은 「~이 포함된 경우」, 원치 않는 동작은 「만약 ~하면」이다. 조건절 끝에 쉼표를 찍고 응답 절을 잇는다.
  5. 선택과 사건을 섞지 않는다. 「~하는 경우」는 이 과목에서 선택 기능에만 쓴다. 사용자의 동작에는 「~하면」을 쓴다.
  6. 원치 않는 동작은 「만약」으로 시작한다. 정상 흐름의 사건과 구분하기 위해서다. 「그러면 시스템은」처럼 영어의 then을 살려도 된다.
  7. 확인할 수 없는 말을 쓰지 않는다. 「잘, 적절히, 빠르게, 충분히, 가능하면, 필요 시, 편리하게, 쉽게, 직관적, 효율적, 등」은 수치나 관찰 가능한 결과로 바꾼다.

4-8. 흔한 잘못

잘못된 문장 무엇이 문제인가 고친 문장
공고를 잘 보여 준다. 주체 없음, 응답이 의무가 아님, 「잘」 시스템은 공고 목록의 각 행에 제목, 모집기관, 상태, 접수 마감일을 표시해야 한다.
상태 필터가 있어야 한다. 장치의 존재만 있고 동작이 없음 사용자가 상태를 고르면, 시스템은 그 상태의 공고만 표시해야 한다.
사용자는 관심 공고를 저장할 수 있어야 한다. 주체가 사용자. 시스템이 할 일이 아님 사용자가 관심 표시를 누르면, 시스템은 그 공고를 관심 공고 목록에 추가해야 한다.
오류가 나면 알린다. 어떤 오류인지, 무엇을 알리는지 없음 만약 공고 자료 파일을 읽지 못하면, 시스템은 「공고 자료를 불러오지 못했다」는 안내를 표시해야 한다.
검색 결과가 많으면 쪽을 나눈다. 「많으면」의 기준 없음 시스템은 검색 결과를 한 쪽에 10행씩 나누어 표시해야 한다.
마감 임박 공고는 강조해야 한다. 「임박」과 「강조」의 기준 없음 접수 마감일까지 남은 날이 3일 이하인 동안, 시스템은 그 공고 행에 「마감 임박」 표시를 붙여야 한다.
시스템은 localStorage에 JSON으로 저장해야 한다. 구현 방법을 정함 시스템은 관심 공고를 브라우저 저장소에 저장해 페이지를 다시 열어도 유지해야 한다.

마지막 행은 경계가 애매한 경우다. 「브라우저 저장소」도 넓은 의미에서 구현에 가까운 말이다. 이 과목은 「서버 없이 브라우저에서만 도는 서비스」라는 제약이 5장의 범위에서 정해져 있으므로 명세에 남겨 두고, 저장 형식(JSON)과 저장소의 종류(localStorage)는 계획 단계로 미룬다.

  • REQ-01 「공고를 잘 보여 준다」: 무엇을 보이는지 항목으로 적어 상시 문형으로.
  • REQ-04 「저장해야 하고 알림도 보내야 한다」: 두 요구로 나누고 뒤의 것에 새 ID(REQ-10)를 붙인다. 알림이 없는 판도 있을 수 있는지 생각해 문형을 고른다.
  • REQ-05 「오류가 나면 사용자에게 알린다」: 어떤 오류에 무엇을 보이는지 정해 원치 않는 동작 문형으로.

고칠 때는 문장 앞에 라벨을 붙인다(예: - **REQ-01** [상시] 시스템은 ...해야 한다.). 원문이 정하지 않은 값(시간, 개수, 날짜)을 정했으면 그 값을 문장 뒤의 괄호에 적는다. 예: (근거: 하루 전은 내가 정한 값). 검사기는 문장 끝의 (근거: ...), (관찰: ...), (추측: ...)과 ← 고침, ← 추가 표시를 무시한다. 다 고쳤으면 검사기를 다시 돌려 고친 문장의 줄과 요약만 본다.

나머지 일곱 문장(REQ-02, 03, 06~09, ID 없는 문장)을 모두 고쳐 오류 0건, 종료 코드 0을 만드는 것은 [선택]이다. REQ-06~09는 Claude Code에 맡겨 자기 판단과 비교해도 된다. 맡길 때는 고칠 문장과 규칙을 함께 준다.

[Claude Code] [선택]

ch06/연습/교정연습.md의 REQ-06~REQ-09를 EARS 문형으로 고쳐라. 규칙: 주체는 「시스템은」, 응답은 「~야 한다」로 끝낸다, 한 문장에 응답 하나, 문장 앞에 [상시|사건|상태|선택|원치 않는 동작] 라벨. 원문이 정하지 않은 값을 정했으면 문장 끝 괄호에 (근거: AI가 정한 값)이라고 적어라. 다른 줄은 고치지 마라.

AI가 고친 문장에서 「(근거: AI가 정한 값)」이 붙은 자리를 찾는다. 그 값이 1장에서 본 「AI가 스스로 정한 것」이다.

  • 확인 1 원문에 검사기를 돌려 오류 10건과 「빈 문형: 사건, 원치 않는 동작」을 보았고, 손으로 고친 뒤 다시 돌린 출력에서 REQ-01, REQ-04, REQ-05와 새로 나눈 요구가 통과이며 「빈 문형」 줄이 없다.

4-10. 검사기가 보는 것과 보지 못하는 것

검사기는 문장의 꼴을 본다. 문장의 뜻은 보지 못한다. 다음은 모두 검사기를 통과하지만 좋은 요구가 아니다.

- **REQ-01** [상시] 시스템은 사용자를 만족시켜야 한다.
- **REQ-02** [사건] 사용자가 무엇이든 하면, 시스템은 올바르게 반응해야 한다.
- **REQ-03** [상태] 시스템이 동작하는 동안, 시스템은 오류가 없어야 한다.

REQ-01은 관찰할 수 있는 결과가 없고, REQ-02의 「올바르게」와 「무엇이든」은 확인할 수 없으며, REQ-03은 검사할 방법이 없다. 검사기의 모호한 말 목록은 예시일 뿐이므로 이런 말을 다 잡지 못한다. 그래서 핵심 실습에서는 요구마다 수용 기준을 붙인다(4-11). 수용 기준을 쓸 수 없는 요구는 아직 요구가 아니다.

검사기는 사람의 검토를 대신하지 않는다. 검사기의 몫은 기계적인 실수(ID 빠짐, 문형과 라벨의 불일치, 추적표의 끊긴 고리)를 사람이 보기 전에 걸러 내는 것이다. 이 역할 분담은 5장의 자동 검사와 「AI에이전트 기획 및 개발」의 테스트로 이어진다.

4-11. 수용 기준

요구마다 수용 기준을 붙인다. 수용 기준은 「무엇을 보면 그 요구를 충족했다고 인정하는가」이며, 5장에서 인수 조건 표와 자동 검사로, 13장에서 사용성 시험의 과업으로 이어진다. 이 과목의 형식은 Spec Kit의 수용 시나리오(Given, When, Then)를 우리말로 옮긴 - **AC-<요구 번호>-<순번>** (전제) ~일 때 (행동) ~하면 (결과) ~이다.이다[S2d].

좋은 수용 기준은 구체적인 자료와 관찰할 결과를 가진다.

요구 나쁜 수용 기준 좋은 수용 기준
REQ-002 마감일 순 정렬 목록이 마감일 순서로 보인다 마감일이 11-20, 11-15, 11-30인 공고 셋이 있을 때 목록을 열면, 11-15, 11-20, 11-30의 순서로 보인다
REQ-003 마감 임박 표시 마감이 가까운 공고가 강조된다 시스템 날짜가 11-14이고 마감일이 11-17인 공고가 있을 때 목록을 열면 그 행에 「마감 임박」이 보인다. 마감일이 11-18인 공고에는 보이지 않는다
REQ-014 요약의 근거 요약에 근거가 있다 요약의 각 항목 아래 근거 문장이 공고 원문에 그대로 들어 있다(문자열 대조)

REQ-003의 좋은 수용 기준은 경계값을 둘 다 본다. 3일 남은 공고에는 보이고 4일 남은 공고에는 보이지 않아야 「3일 이하」라는 요구를 확인한 것이다. 한쪽만 보면 「모든 공고에 표시」하는 잘못된 구현도 통과한다.

검사기는 수용 기준이 하나라도 있으면, 수용 기준이 없는 요구를 경고로 알리고, 없는 요구를 가리키는 수용 기준(예: 명세에 없는 REQ-030을 가리키는 AC-030-1)을 오류로 알린다.

4-12. 열린 질문

명세를 쓰다 보면 지금 정할 수 없는 것이 남는다. 정하지 못한 것을 정한 것처럼 쓰면 그 자리가 다시 「AI가 정한 것」이 된다. Spec Kit은 이런 곳을 명세 안에 [NEEDS CLARIFICATION: ...]으로 표시하고, 명확화 단계(/speckit-clarify)에서 최대 다섯 개의 질문으로 좁힌다[S2c, S2d]. 이 과목은 같은 일을 계획 모드의 질문과 명세서의 「열린 질문」 표로 한다.

질문마다 관련 요구와 정할 장을 적는다. 근거로 지금 정할 수 있는 것은 정해 명세에 반영하고, 값에 따라 화면이나 구현이 달라지는데 근거가 없는 것만 남긴다(기준: 「틀리면 무엇을 다시 만들어야 하는가」). 열린 질문은 실패가 아니라 이후 장의 할 일 목록이며, 이후 장의 설계와 구현 계획이 이 표에서 출발한다.

위는 교수용 견본 명세로 낸 출력이다(2026-11-17). 요구의 수와 문형 분포는 사람마다 다르다. 오류가 있으면 오류 메시지를 Claude Code에 그대로 붙여 고치게 하거나 직접 고친다(4-9의 갈래표). 「원치 않는 동작」이 0이면 그 자체가 5장의 비교에서 확인할 빈틈 후보다.

검사기를 통과했으면 AI가 쓴 명세를 사람이 끝까지 읽고 세 질문에 답한다. ① 「추측」이 붙은 요구를 원본에서 확인할 방법(2-3)이 있는가. ② 관찰 기록과 다른 곳이 있는가(틀렸으면 고치고 줄 끝에 ← 고침). ③ 문형 분포에서 0인 문형으로 쓸 상황이 원본에 있는가. 원치 않는 동작이 0이면 「잘못된 경우」를 정하지 않은 것이다.

5-4. 요구의 보강과 수용 기준 (실행 전)

5-3의 복원 명세는 요구가 8개 안팎이다. 다음 세 가지를 차례로 한다.

  1. 근거의 대조. 요구마다 줄 끝에 근거를 적는다. 근거는 관찰 기록의 칸 이름이거나 구조 분석의 「확인」 항목이다. 근거를 적을 수 없는 요구는 (추측: 까닭)을 붙이거나 「복원하지 않은 것」 절로 옮긴다.
  2. 빈칸의 보강. 문형 분포에서 0인 문형을 본다. 관찰 기록의 「보고도 알 수 없는 것」과 「쓰면서 불편했던 것」에서 상황을 골라 요구를 더해 12개 이상으로 만든다. 원본에서 확인하지 못한 동작은 5장에서 내 구현이 따를 규칙으로 정하고 (정함: 까닭)을 붙인다.
  3. 수용 기준. 요구 다섯 개 이상에 4-11의 형식으로 수용 기준을 붙인다. 구체적인 자료(채용.csv의 행)와 관찰할 결과를 쓴다.

5-5. 경쟁 서비스의 기능 비교표

먼저 양식을 복사한다(mkdir -p ch04 && cp -n ~/kits/Service_04장/경쟁서비스_비교표_양식.md ch04/경쟁서비스_비교표.md). 키트의 P3로 다섯 서비스의 첫 화면과 메뉴를 관찰하게 한다. P3는 다섯 서비스의 공식 주소를 직접 준다. AI가 검색으로 주소를 찾게 하면 비공식 페이지나 광고 페이지를 읽을 수 있기 때문이다.

Claude Code 
다음 다섯 서비스의 공식 누리집 첫 화면과 전체 메뉴를 웹 페이지 읽기 도구로 읽어라: 「사람인 https://www.saramin.co.kr/zf_user/, 잡코리아 https://www.jobkorea.co.kr/, 링커리어 https://linkareer.com/, 자소설닷컴 https://jasoseol.com/, 고용24 https://www.work24.go.kr/」
규칙:
1. 페이지에 글자로 나타난 메뉴와 기능만 쓴다. 페이지에 없는 기능을 상식이나 기억으로 채우지 않는다.
2. 서비스마다 관찰한 메뉴 이름을 페이지의 표기 그대로 옮긴다.
3. 기능을 사용자의 업무 단위(공고 찾기, 일정 챙기기, 서류 쓰기 등)로 묶어 10행 이상의 비교표를 만든다.
4. 칸에는 ○(확인됨), △(일부·조건부), -(확인되지 않음)만 쓴다. "없음"이라고 쓰지 않는다. 첫 화면에서 보이지 않았다는 것은 없다는 뜻이 아니다.
5. 결과는 ch04/경쟁서비스_비교표.md의 양식(1절 비교표, 2절 근거 표)에 써 넣고, 관찰 날짜는 이 작업을 한 날짜(YYYY-MM-DD)로 적는다.
읽지 못한 페이지가 있으면 그 사실을 보고하라.

일부 서비스는 자동으로 페이지를 읽는 요청을 막거나, 화면의 메뉴를 스크립트로 그려 웹 페이지 읽기 도구가 메뉴를 보지 못할 수 있다. AI가 “읽지 못했다”고 보고하면 그 서비스는 학습자가 브라우저로 직접 열어 메뉴를 옮긴다.

AI의 비교표를 받은 뒤 학습자가 할 일은 넷이다.

  1. 직접 확인. 서비스마다 브라우저로 첫 화면을 열어, AI가 ○로 적은 기능 가운데 두 개 이상을 골라 화면에서 직접 찾는다. AI가 「-」로 적은 기능 가운데 하나를 골라 정말 첫 화면에 없는지 본다. 찾은 것은 비고나 2절 근거 표에 “직접 확인”으로 표시한다.
  2. 표기 확인. 2절 근거 표의 메뉴가 화면의 표기 그대로인지 본다(3-3). 비고에 화면의 표기가 남아 있는지 본다.
  3. 분류. 4절 분류 표에 직접 경쟁, 간접 경쟁, 대체재 세 행과 「분류의 근거」를 쓴다(3-1).
  4. 평가 문장 지우기. 비교표에 관찰한 사실이 아닌 좋고 나쁨의 판단(“불편하다”, “부실하다”)이 있으면 관찰한 사실로 바꾸거나 지운다(3-6).

정리

  • 리버스 엔지니어링은 완성물을 바꾸지 않고 분석해 구성과 관계를 알아내고 더 높은 수준(명세)으로 표현하는 일이다. 절차는 관찰 → 구조 분석 → 기능 목록 → 명세이며, 관찰과 대조는 사람이 한다.
  • 주소와 질의 문자열로 재현되는 화면은 curl과 웹 읽기로 근거를 만들고, 그렇지 않은 화면은 캡처와 관찰 기록으로 근거를 만든다. 근거에는 종류와 날짜를 적는다.
  • EARS는 요구 문장을 상시, 사건, 상태, 선택, 원치 않는 동작의 다섯 문형과 그 조합으로 쓰게 한다. 문형 분포의 0은 정하지 않은 상황을 가리킨다.
  • 수용 기준을 쓸 수 없는 요구는 아직 요구가 아니다. 정하지 못한 것은 「열린 질문」으로 남긴다.
  • 기능 비교표에는 화면에서 글자로 확인한 것만 쓴다. 「-」는 확인되지 않았다는 뜻이며 없다는 뜻이 아니다.
