[부록 B] 명령어 카드

2027학년도 「LLM 서비스 개발」의 준비 중인 교재입니다. 편집 상태를 검토하기 위해 미리 공개한 것으로, 수업 전에 내용과 순서가 바뀔 수 있습니다.

「LLM 서비스 개발」 1~13장의 공통 부록 · 2026-11 기준(Claude Code 2.1.296, git 2.55, GitHub CLI 2.88에서 확인)

자주 쓰는 명령을 도구별로 모은 참조표이다. 각 장은 명령을 처음 쓸 때 그 뜻을 설명하고, 이후에는 이 카드를 가리킨다. 명령을 어디에 입력하는가가 첫 번째 구분이다. 셸 명령은 [서버 터미널]에, 슬래시 명령과 프롬프트는 [Claude Code] 입력 창에 넣는다(부록 A의 꼬리표).

카드 도구 입력하는 곳
B-1 Claude Code 셸(시작 명령), Claude Code 입력 창(슬래시 명령, 단축키)
B-2 Git 셸
B-3 GitHub CLI(gh) 셸
B-4 셸 기본 명령 셸

도구는 판이 바뀌면 명령과 화면이 달라진다. 이 카드와 실제 동작이 다르면 각 도구의 도움말(claude --help, Claude Code 안의 /help, git help 명령, gh 명령 --help)과 공식 문서가 우선한다.

[최신 자료 자리: 이 카드가 확인한 도구의 판] 확인할 곳: 서버의 claude --version, git --version, gh --version. 2026-11-15 확인 값(집필용 PC): Claude Code 2.1.296, git 2.55.0, GitHub CLI 2.88.1(2026-03-12 배포). 서버의 판은 1주차 전에 확인하고, 다르면 아래 자리 표시의 문서에서 명령과 화면을 다시 확인한다.

B-1. Claude Code 명령 카드

B-1-1. 셸에서 시작하는 명령

서버 터미널 
claude
claude "이 폴더의 구조를 설명하라"
claude -c
claude -r
명령 뜻
claude 지금 폴더를 작업 폴더로 대화형 세션을 시작한다
claude "요청" 첫 요청을 넣은 채 대화형 세션을 시작한다
claude -c (--continue) 지금 폴더에서 가장 최근의 대화를 이어 간다
claude -r (--resume) 지난 대화 목록을 열어 골라 이어 간다. 뒤에 세션 ID나 검색어를 줄 수 있다
claude -n 이름 (--name) 세션에 이름을 붙여 시작한다. 이름은 입력 창, /resume 목록, 터미널 제목에 보인다
claude --permission-mode plan 계획 모드로 시작한다(B-1-6)
claude --model 모델 이 세션에서 쓸 모델을 정해 시작한다
claude --version (-v) 버전을 출력한다
claude doctor 설치와 설정 파일을 진단한다(읽기 전용)
claude update 지금 바로 최신판으로 업데이트한다
claude auth login / logout / status 셸에서 로그인, 로그아웃, 인증 상태 확인(부록 A-7)
claude --help 모든 옵션을 보여 준다
  • claude -p "요청"(--print)은 대화 화면 없이 한 번 답하고 끝내는 헤드리스 모드이다. 스크립트와 자동화에 쓰며, 이 과목의 실습에서는 쓰지 않는다(「AI에이전트 기획 및 개발」에서 다룬다).
  • --dangerously-skip-permissions는 모든 권한 확인을 건너뛴다. 도움말이 인터넷이 막힌 격리 환경에서만 쓰라고 경고하는 옵션이므로 실습 서버에서 쓰지 않는다(claude --help, 2026-11-14 확인).

[최신 자료 자리: claude 시작 옵션] -c, -r, -n, --permission-mode의 값, --model, auth·doctor·update. 확인할 곳: 서버의 claude --help, https://code.claude.com/docs/en/cli-reference. 마지막으로 확인한 날짜와 값: 2026-11-14, Claude Code 2.1.296의 도움말이 본문과 같다. 수업 전에 다시 확인한다.

B-1-2. 슬래시 명령

Claude Code 입력 창의 맨 앞에 /를 치면 명령 목록이 뜨고, 글자를 더 치면 목록이 좁혀진다[C1]. 명령은 메시지의 맨 앞에 있을 때만 명령으로 인식되며, 뒤에 붙인 글은 그 명령의 인자가 된다[C1]. 아래 표는 2026-11-14의 공식 문서에서 확인한 것이다.

시작과 상태

명령 뜻
/help 도움말과 쓸 수 있는 명령 목록. 막히면 여기서 시작한다
/status 설정 화면의 Status 탭. 버전, 모델, 계정, 연결 상태, 읽은 설정 파일을 보여 준다
/login / /logout Anthropic 계정에 로그인 / 로그아웃
/model [모델] 모델을 바꾸고 다음 세션의 기본값으로 저장한다. 목록에서 s를 누르면 이 세션에만 적용한다
/config 설정 화면(테마, 모델, 출력 형식 등)
/doctor 설치, 설정, CLAUDE.md의 문제를 진단하고 고칠 방법을 제안한다
/exit (/quit) Claude Code를 끝낸다

대화와 컨텍스트

명령 뜻
/clear (/reset, /new) 대화를 비우고 새로 시작한다. 이전 대화는 /resume으로 다시 열 수 있다
/compact [지시] 지금까지의 대화를 요약해 컨텍스트를 비운다. 요약에 남길 내용을 지시로 줄 수 있다
/context 컨텍스트 창이 얼마나 차 있는지 색 격자로 보여 준다
/usage (/cost) 세션의 비용, 요금제의 사용 한도, 활동 통계
/resume [세션] 지난 대화를 ID나 이름으로, 또는 목록에서 골라 이어 간다
/rename [이름] 지금 세션의 이름을 바꾼다. 이름을 주지 않으면 대화 내용으로 지어 준다
/branch [이름] 지금 시점에서 대화의 갈래를 만들어 다른 방향을 시도한다. 원래 대화는 /resume으로 돌아갈 수 있다
/btw [질문] 대화 기록에 남기지 않는 곁가지 질문을 한다
/export [파일이름] 대화를 일반 텍스트로 내보낸다. 실습 기록의 증빙으로 쓴다
/copy [N] 마지막(또는 N번째 전) 응답을 클립보드에 복사한다. 목록에서 w를 누르면 파일로 쓴다(SSH에서 유용)

작업의 통제

명령 뜻
/plan [설명] 계획 모드로 들어간다. 설명을 주면 그 일로 바로 계획을 시작한다(B-1-6)
/permissions 도구 사용의 허용, 확인, 거부 규칙을 보고 고친다
/rewind (/checkpoint, /undo) 대화와 코드를 앞 시점으로 되감거나, 한 시점부터 요약한다(B-1-7)
/diff 작업 트리의 변경(Claude가 지금까지 고친 것 포함)을 검토한다
/init 프로젝트를 분석해 CLAUDE.md 초안을 만든다(2장)
/memory CLAUDE.md 파일들을 편집하고 자동 메모리를 켜고 끈다
/add-dir 경로 이 세션에서 파일을 다룰 폴더를 더한다
/cd 경로 대화를 유지한 채 작업 폴더를 옮긴다

검토

명령 뜻
/review 지금의 변경(또는 지정한 풀 리퀘스트, 브랜치, 경로)을 코드 검토한다. /code-review의 별칭이다
/security-review 지금 브랜치의 변경을 보안 관점(주입, 인증, 정보 노출)에서 검토한다. 원격 origin이 있어야 한다

이 밖에 /theme(색 테마), /terminal-setup(VS Code 등에서 Shift+Enter 줄바꿈 설정), /tasks(백그라운드 작업 목록), /hooks, /mcp, /agents가 있다. 뒤의 세 가지는 「AI에이전트 기획 및 개발」에서 다룬다.

[최신 자료 자리: 슬래시 명령의 목록과 별칭] 확인할 곳: Claude Code 안의 /help, https://code.claude.com/docs/en/commands. 마지막으로 확인한 날짜와 값: 2026-11-14, 위 네 표의 명령과 별칭(/clear의 /reset·/new, /rewind의 /checkpoint·/undo, /usage의 /cost, /review는 /code-review의 별칭). 명령은 판마다 더해지거나 이름이 바뀌므로 수업 전에 다시 확인한다.

B-1-3. 단축키

키 뜻
Esc 진행 중인 응답이나 도구 실행을 멈춘다. 그때까지 한 일은 남고, 다음 지시를 기다린다. 열린 대화 상자는 닫는다
Esc Esc 입력 창이 비어 있으면 되감기 메뉴를 연다. 입력 중이면 쓰던 글을 지운다(↑로 되살린다)
Shift+Tab 권한 모드를 돌아가며 바꾼다(B-1-5)
Ctrl+C 실행 중이면 중단한다. 실행 중이 아니면 첫 번째는 입력을 지우고, 두 번째는 Claude Code를 끝낸다
Ctrl+D 두 번 누르면 Claude Code를 끝낸다. 입력 창에 글이 있으면 커서 뒤 글자를 지운다
↑ / ↓ 이전 입력을 불러온다
Ctrl+R 이전 입력을 검색한다
Ctrl+O 도구 사용의 상세 기록(트랜스크립트)을 켜고 끈다
Ctrl+T Claude의 할 일 목록을 보이거나 숨긴다
Ctrl+B 실행 중인 셸 명령을 백그라운드로 보낸다
Ctrl+G 입력 중인 프롬프트를 외부 편집기에서 연다. 긴 프롬프트를 쓸 때 쓴다
Ctrl+L 화면을 다시 그린다(화면이 깨졌을 때)
Ctrl+S 입력 중인 글을 잠시 치워 두고, 빈 입력 창에서 다시 누르면 되살린다
Alt+P 입력을 지우지 않고 모델을 바꾼다(Windows·리눅스)
? 입력 창이 비어 있을 때 단축키 도움말을 연다

여러 줄을 입력하는 방법은 다음과 같다. \를 친 뒤 Enter는 모든 터미널에서 되고, Ctrl+J도 설정 없이 된다. Shift+Enter는 Windows Terminal 등 일부 터미널에서 바로 되고, VS Code 통합 터미널에서는 /terminal-setup을 한 번 실행하면 된다[C2].

[최신 자료 자리: 단축키와 여러 줄 입력] 확인할 곳: Claude Code의 빈 입력 창에서 ?, https://code.claude.com/docs/en/interactive-mode. 마지막으로 확인한 날짜와 값: 2026-11-14, 위 표의 키(문서 기준. 서버의 터미널과 VS Code 통합 터미널에서 실제로 눌러 보지는 않았다). 수업 전에 다시 확인한다.

B-1-4. 입력 창의 특수 문법

문법 뜻 예
/명령 슬래시 명령 또는 스킬을 부른다 /status
@경로 파일이나 폴더를 대화에 참조로 넣는다. @를 치면 경로 자동 완성이 뜬다 @ch02/메모.md 이 파일을 요약하라
!명령 셸 모드. Claude를 거치지 않고 셸 명령을 바로 실행하고, 명령과 출력을 대화에 넣는다 !git status
\ + Enter 줄을 바꾼다
Claude Code 
@jobprep/docs/요구사항명세서.md 이 명세의 요구 가운데 인수 조건이 없는 것을 표로 정리하라
Claude Code 
!~/llm-service-lab/.venv/bin/python -m pytest -q
  • !로 실행한 명령은 Claude의 승인을 거치지 않는다. 출력이 대화에 들어가면 Claude가 그 출력에 바로 응답하며, 그 응답은 보통의 프롬프트와 같은 비용이 든다[C2].
  • 셸 모드에서 나오려면 빈 입력 창에서 Esc나 Backspace를 누른다.
  • 결과만 확인하고 Claude의 응답이 필요 없으면 ! 대신 옆의 서버 터미널에서 실행한다. 부록 A-5의 두 터미널 배치가 그 용도이다.

B-1-5. 권한 모드

권한 모드는 Claude가 묻지 않고 할 수 있는 일의 범위를 정한다[C3]. 화면 아래쪽의 모드 표시로 지금 모드를 본다.

모드(설정 값) 묻지 않고 하는 일 쓰는 때
Manual (default) 읽기만 모든 행동을 사람이 하나씩 검토할 때. 이 과목의 기본
acceptEdits 읽기, 작업 폴더 안의 파일 수정, 흔한 파일 명령(mkdir, touch, mv, cp 등) 검토 중인 코드를 반복해 고칠 때
plan 읽기(계획만 세우고 고치지 않는다) 고치기 전에 조사하고 계획할 때
auto 모든 일, 다만 분류기가 뒤에서 행동을 검토한다 긴 작업. 계정과 모델에 따라 쓸 수 없을 수 있다
dontAsk 미리 허용한 도구만. 물어야 할 것은 거부 자동화 스크립트
bypassPermissions 모든 일 격리된 컨테이너에서만. 실습 서버에서 쓰지 않는다

Shift+Tab을 누를 때마다 모드가 다음 순서로 돈다. auto는 쓸 수 있는 계정과 모델일 때만 순환에 들어가고, dontAsk는 순환에 나타나지 않는다[C3].

flowchart LR
    M["Manual<br/>(default)"] --> AE["acceptEdits"] --> P["plan"] --> AU["auto<br/>(쓸 수 있을 때)"] --> M

[그림 자리: 입력 창 아래의 권한 모드 표시] Shift+Tab을 누를 때마다 바뀌는 모드 표시(Manual, accept edits, plan, auto)를 네 장으로 나란히 보인다. 찍을 곳: 실습 서버의 Claude Code 입력 창.

  • 2026-11 기준으로 Claude Code는 auto를 쓸 수 있는 세션이면 auto로 시작하고, 쓸 수 없으면 Manual로 시작한다[C3]. 시작할 때 화면의 모드 표시를 확인하고, 수업에서 안내한 모드가 아니면 Shift+Tab으로 맞춘다.
  • 시작할 때부터 모드를 정하려면 claude --permission-mode manual처럼 옵션을 준다. 옵션의 값은 acceptEdits, auto, bypassPermissions, manual, dontAsk, plan이다(claude --help, 2026-11-14 확인).
  • 거부(deny) 규칙은 어느 모드에서나 지켜진다[C3]. 부록 A-13의 .env 읽기 거부가 이 규칙이다.
  • 권한을 묻는 화면에서 「Yes, and don’t ask again」을 고르면 그 명령의 허용 규칙이 .claude/settings.local.json에 저장된다[C4]. 무엇을 영구히 허용했는지는 /permissions에서 보고 지운다.

[최신 자료 자리: 권한 모드의 이름, 순환 순서, 시작 모드] 확인할 곳: https://code.claude.com/docs/en/permission-modes, claude --help. 2026-11-15 확인 값: 표시 이름과 설정 값은 Manual(default. CLI는 manual도 받는다), accept edits(acceptEdits), Plan(plan), Auto(auto), don’t ask(dontAsk), Bypass permissions(bypassPermissions)이다. Shift+Tab 순환은 default → acceptEdits → plan 뒤에, 켜 둔 경우 bypassPermissions, 그다음 auto가 온다. dontAsk는 순환에 없다. 터미널 세션은 v2.1.283부터 auto로 시작하고, claude -p와 Agent SDK는 v2.1.302부터 Manual로 시작한다. 수업 전에 다시 확인한다.

B-1-6. 계획 모드

계획 모드에서 Claude는 파일을 읽고 조사해 바꿀 계획을 제안하지만, 계획을 승인하기 전에는 소스를 고치지 않는다[C3]. 명세에서 구현으로 넘어가기 전에 Claude가 무엇을 어떤 순서로 할지 먼저 읽고 고치기 위해 쓴다(6장).

들어가는 법
Shift+Tab을 눌러 모드 표시가 plan이 되게 한다 대화 중에
/plan 설명 그 일로 바로 계획을 시작한다
claude --permission-mode plan 시작할 때부터
Claude Code 
/plan @jobprep/docs/요구사항명세서.md 의 R1~R3을 구현할 작업 목록을 세워라. 파일은 고치지 마라.

계획이 나오면 승인 화면에서 다음 가운데 하나를 고른다[C3]. 선택지 이름은 버전에 따라 다를 수 있다.

선택 뜻
Yes, and use auto mode 승인하고 auto 모드로 실행한다
Yes, manually approve edits 승인하되 파일 수정은 하나씩 확인받는다
No, keep planning 승인하지 않고 계획을 계속 다듬는다
  • 승인 화면에서 Ctrl+G를 누르면 계획을 편집기에서 열어 고친 뒤 진행할 수 있다[C3].
  • 승인 화면에서 Shift+Tab을 누르면 계획이 승인된다. 모드만 바꾸려면 먼저 Esc를 누른다[C3].

[그림 자리: 계획 모드의 승인 화면] Claude가 제안한 계획 아래에 세 선택지(Yes, and use auto mode / Yes, manually approve edits / No, keep planning)가 보이는 화면. 찍을 곳: 실습 서버의 Claude Code에서 /plan으로 계획을 받은 직후.

[최신 자료 자리: 계획 승인 선택지의 이름] 확인할 곳: https://code.claude.com/docs/en/permission-modes. 2026-11-15 확인 값: 본문의 세 선택지와 같다. auto 모드를 쓸 수 없는 세션에서는 첫 선택지가 「Yes, auto-accept edits」로, 시작할 때 우회 모드를 켰으면 「Yes, and switch to BYPASS PERMISSIONS (no further prompts) for this session」으로 보인다. 수업 전에 다시 확인한다.

B-1-7. 되감기(체크포인트)

Claude Code는 프롬프트를 보낼 때마다 그 직전의 코드 상태를 체크포인트로 남긴다[C5]. /rewind를 실행하거나 빈 입력 창에서 Esc를 두 번 누르면 되감기 메뉴가 열리고, 되돌아갈 프롬프트를 고른 뒤 다음 가운데 하나를 고른다.

선택 뜻
Restore code and conversation 코드와 대화를 모두 그 시점으로 되돌린다
Restore conversation 대화만 되돌리고 코드는 지금 그대로 둔다
Restore code 코드만 되돌리고 대화는 그대로 둔다
Summarize from here 그 시점 뒤의 대화를 요약해 컨텍스트를 비운다
Summarize up to here 그 시점 앞의 대화를 요약한다
Never mind 아무것도 하지 않고 돌아간다

되감기는 Git을 대신하지 않는다. 공식 문서가 밝히는 한계는 다음과 같다[C5].

한계 뜻 대신 쓰는 것
셸 명령의 변경 Claude의 편집 도구가 한 번도 고치지 않은 파일을 셸 명령(rm, mv, 스크립트)이 바꾼 것은 되돌리지 않는다 git restore
바깥의 변경 사람이 편집기로 고친 것, 다른 세션이 고친 것은 보통 추적하지 않는다 git diff로 확인, git restore
보관 기간 세션의 파일 스냅숏은 기본적으로 약 30일 뒤 정리된다 커밋
기록과 협업 세션 단위의 빠른 복구용이다 커밋, 브랜치, 원격 저장소

이 과목의 규칙: Claude Code에게 일을 맡기기 전에 git status가 깨끗한지 보고, 결과를 확인한 뒤 커밋한다. 되감기는 커밋 사이의 시행착오를 되돌리는 데 쓴다.

[그림 자리: 되감기 메뉴] 빈 입력 창에서 Esc를 두 번 눌러 연 프롬프트 목록과, 하나를 고른 뒤 나오는 여섯 선택지(Restore code and conversation 등). 찍을 곳: 실습 서버의 Claude Code에서 파일을 한 번 고치게 한 뒤.

[최신 자료 자리: 되감기의 선택지와 보관 기간] 확인할 곳: https://code.claude.com/docs/en/checkpointing. 마지막으로 확인한 날짜와 값: 2026-11-14, 선택지 여섯 개와 세션 스냅숏의 보관 기간 약 30일. 수업 전에 다시 확인한다.

B-1-8. 대화의 재개와 정리

하려는 일 명령
같은 폴더의 가장 최근 대화를 이어 간다 셸에서 claude -c
지난 대화를 골라 이어 간다 셸에서 claude -r, 또는 Claude Code 안에서 /resume
나중에 찾기 쉽게 이름을 붙인다 /rename 이름 또는 셸에서 claude -n 이름
지금 대화를 그대로 두고 다른 방향을 시도한다 /branch
다른 일로 넘어간다(이전 대화는 버린다) /clear
같은 일을 이어 가되 컨텍스트를 줄인다 /compact 남길 내용
/clear 직후 이전 대화로 돌아간다 /rewind 목록 맨 위의 이전 세션 항목, 또는 /resume

대화는 작업 폴더별로 저장되므로 claude -c는 같은 폴더에서 실행해야 그 폴더의 대화를 찾는다. 장마다 새 일을 시작할 때는 새 세션으로 시작하고, 그 장의 일을 이어 할 때만 재개한다. 앞 장의 긴 대화를 끌고 오면 컨텍스트가 차서 응답이 흐려진다.

B-2. Git 명령 카드

Git의 기본 개념은 2장에서, 팀 작업은 3장에서 배운다. 이 카드는 상황별로 명령을 찾는 표이다. 처음 한 번 하는 설정(user.name, user.email, core.quotepath)은 부록 A-9에 있다. 각 명령의 옵션은 git help 명령 또는 Git 참조 문서[G1]에서 확인한다.

Git이 다루는 세 자리를 먼저 구별한다.

flowchart LR
    W["작업 트리<br/>(내가 고친 파일)"] -- "git add" --> S["스테이징 영역<br/>(다음 커밋에 넣을 것)"]
    S -- "git commit" --> R["저장소 기록<br/>(커밋)"]
    R -- "git push" --> O["원격 저장소<br/>(GitHub)"]
    O -- "git pull" --> W
    S -- "git restore --staged" --> W
    R -- "git restore" --> W

B-2-1. 시작

상황 명령
지금 폴더를 새 저장소로 만든다 git init
원격 저장소를 내려받는다 git clone 주소 또는 gh repo clone 소유자/저장소
설정을 확인한다 git config --global --list
저장소에 넣지 않을 파일을 정한다 .gitignore 파일에 한 줄씩 적는다(.env, .venv/, __pycache__/)
어떤 규칙이 그 파일을 무시하게 하는지 본다 git check-ignore -v 파일

B-2-2. 기록

서버 터미널 
git status --short
git add README.md ch02/메모.md
git commit -m "첫 커밋: README와 메모"
?? README.md
?? ch02/
[main (root-commit) 20a4508] 첫 커밋: README와 메모

상황 명령
무엇이 바뀌었는지 짧게 본다 git status --short (?? 추적 안 됨, M 고침, A 스테이징됨, UU 충돌)
파일을 다음 커밋에 넣는다 git add 파일
폴더 안의 변경을 모두 넣는다 git add 폴더/ (넣기 전에 git status로 .env 같은 파일이 없는지 본다)
커밋한다 git commit -m "메시지"
이미 추적 중인 파일의 변경을 한 번에 커밋한다 git commit -am "메시지" (새 파일은 들어가지 않는다)
기준점에 이름(태그)을 붙인다 git tag spec-v1 (6장의 명세서 v1)

커밋 메시지는 무엇을 왜 바꾸었는지를 한 줄로 쓴다. Claude Code가 고친 것을 커밋할 때도 사람이 git diff로 읽은 뒤 메시지를 쓴다(2장).

B-2-3. 확인

상황 명령
커밋 기록을 한 줄씩 본다 git log --oneline
브랜치의 갈래까지 그림으로 본다 git log --oneline --graph
커밋마다 바뀐 파일을 본다 git log --stat -n 3
아직 스테이징하지 않은 변경을 본다 git diff
스테이징한 변경을 본다 git diff --staged
바뀐 파일 목록과 줄 수만 본다 git diff --stat
커밋 하나의 내용을 본다 git show 커밋 (git show --stat HEAD)
줄마다 누가 언제 고쳤는지 본다 git blame 파일 
$ git diff
diff --git a/ch02/메모.md b/ch02/메모.md
index fc7a21a..8bf3eae 100644
--- a/ch02/메모.md
+++ b/ch02/메모.md
@@ -1 +1,2 @@
 메모
+둘째 줄

+로 시작하는 줄이 더해진 줄, -로 시작하는 줄이 지워진 줄이다. HEAD는 지금 브랜치의 마지막 커밋이고, HEAD~1은 그 하나 앞이다.

B-2-4. 되돌리기

상황 명령 기록이 바뀌는가
고친 파일을 마지막 커밋 상태로 되돌린다(고친 내용은 사라진다) git restore 파일 아니오
스테이징만 취소한다(파일 내용은 그대로) git restore --staged 파일 아니오
파일을 특정 커밋의 상태로 가져온다 git restore --source=커밋 파일 아니오
실수로 추적하게 된 파일을 추적에서만 뺀다(.env) git rm --cached 파일 다음 커밋에서
이미 커밋한 것을 취소하는 새 커밋을 만든다 git revert 커밋 새 커밋이 더해진다
마지막 커밋의 메시지를 고친다(푸시하기 전만) git commit --amend -m "메시지" 마지막 커밋이 바뀐다
마지막 커밋을 풀어 변경을 스테이징 상태로 돌린다(푸시하기 전만) git reset --soft HEAD~1 마지막 커밋이 사라진다 
$ git revert --no-edit HEAD
[main 2d6f6f2] Revert "README 추가"
 1 file changed, 1 deletion(-)
$ git log --oneline
2d6f6f2 Revert "README 추가"
d6fa2e9 README 추가
20a4508 첫 커밋: README와 메모
  • 푸시한 커밋은 revert로 되돌린다. --amend와 reset은 기록을 고쳐 쓰므로, 이미 남과 나눈 커밋에 쓰면 다른 사람의 기록과 어긋난다.
  • git restore 파일로 사라진 변경은 Git으로 되살릴 수 없다. 확실하지 않으면 먼저 git diff로 무엇이 사라지는지 본다.
  • Claude Code의 되감기(B-1-7)와 Git의 되돌리기는 대상이 다르다. 셸 명령이 바꾼 파일과 커밋한 뒤의 상태는 Git으로 되돌린다.

B-2-5. 브랜치

상황 명령
브랜치 목록을 본다(*가 지금 브랜치) git branch (원격 포함: git branch -a)
새 브랜치를 만들고 옮겨 간다 git switch -c 브랜치
다른 브랜치로 옮겨 간다 git switch 브랜치
다른 브랜치를 지금 브랜치에 합친다 git merge 브랜치
병합이 끝난 브랜치를 지운다 git branch -d 브랜치
병합하지 않은 브랜치를 버린다 git branch -D 브랜치

브랜치 이름은 하는 일을 드러내게 짓는다(3장: feature/공고-필터, fix/마감일-계산. 12장: variant-chat, variant-form). 브랜치를 옮기기 전에 git status가 깨끗한지 본다. 커밋하지 않은 변경은 옮겨 간 브랜치로 따라온다.

B-2-6. 원격

상황 명령
원격 저장소를 등록한다 git remote add origin 주소
등록된 원격을 본다 git remote -v
처음 푸시하며 추적 관계를 맺는다 git push -u origin main
그 뒤의 푸시 git push
원격의 변경을 받아 오기만 한다(합치지 않는다) git fetch
받아 와서 지금 브랜치에 합친다 git pull
내 브랜치가 원격보다 앞섰는지 뒤졌는지 본다 git status -sb ([ahead 1], [behind 1])
원격의 브랜치를 지운다 git push origin --delete 브랜치

다른 곳(팀원, 또는 내 PC)에서 먼저 푸시한 뒤 내가 푸시하면 거절된다. 이때는 git pull로 받아 합친 뒤 다시 푸시한다. 강제 푸시(--force)로 덮어쓰지 않는다.

$ git push

B-2-7. 충돌

두 브랜치가 같은 파일의 같은 줄을 다르게 고쳤으면 Git은 자동으로 합치지 못하고 충돌을 알린다. 충돌은 오류가 아니라 사람이 골라야 하는 자리이다(3장).

$ git merge feature/a
Auto-merging README.md
CONFLICT (content): Merge conflict in README.md
Automatic merge failed; fix conflicts and then commit the result.
$ git status --short
UU README.md

파일 안에는 두 판이 표시와 함께 들어 있다.

파일: README.md 
<<<<<<< HEAD
# 실습
B안
=======
# 실습
A안
>>>>>>> feature/a
표시 뜻
<<<<<<< HEAD ~ ======= 지금 브랜치(합치는 쪽)의 내용
======= ~ >>>>>>> 브랜치 합쳐 오는 브랜치의 내용

해결 순서는 다음과 같다.

  1. git diff --name-only --diff-filter=U로 충돌한 파일을 찾는다.
  2. 파일을 편집기에서 열어 남길 내용으로 고치고, 세 가지 표시 줄을 모두 지운다.
  3. git add 파일로 해결했음을 알린다.
  4. git commit -m "충돌 해결: ..."으로 병합을 마친다.
  5. 해결을 포기하고 병합 전으로 돌아가려면 git merge --abort를 실행한다.
$ git add README.md
$ git commit -m "충돌 해결: A안과 B안 합침"
$ git log --oneline --graph
*   308eb52 충돌 해결: A안과 B안 합침
|\
| * 37401b3 A안
* | c7b9186 B안
|/
* 2d6f6f2 Revert "README 추가"

Claude Code에게 충돌 해결을 맡길 때도, 어느 쪽 내용을 남길지는 사람이 정해 지시하고, 결과를 git diff로 확인한 뒤 커밋한다.

B-2-8. 상황에서 명령 찾기

이런 때 이렇게 한다
Claude Code가 무엇을 고쳤는지 모르겠다 git status --short, git diff
Claude Code가 고친 것 가운데 한 파일만 버리고 싶다 git restore 파일
커밋 메시지에 오타가 있다(푸시 전) git commit --amend -m "..."
어제 푸시한 커밋이 잘못되었다 git revert 커밋 뒤 git push
.env를 git add해 버렸다(커밋 전) git rm --cached .env, .gitignore에 .env 추가
.env를 커밋하고 푸시해 버렸다 키 폐기가 먼저이다(부록 A-13)
푸시가 rejected로 거절된다 git pull 뒤 다시 git push
병합하다 충돌이 났는데 지금은 풀 시간이 없다 git merge --abort

B-4-2. 만들기, 복사, 이동, 삭제

하는 일 bash PowerShell

  • 이름에 공백이나 특수 문자가 있으면 큰따옴표로 감싼다(cp "내 파일.md" 백업/).

B-4-4. 권한

리눅스에서 파일마다 소유자, 그룹, 다른 사람의 읽기(r), 쓰기(w), 실행(x) 권한이 있다. ls -l의 맨 앞 열이 그것이다.

-rw------- 1 아이디 그룹  120 11월 14 10:00 .env
-rw-r--r-- 1 아이디 그룹  845 11월 14 10:00 README.md
drwxr-xr-x 2 아이디 그룹 4096 11월 14 10:00 ch02

(서버에서 보이는 형태의 예시이다. 날짜와 크기는 다르다.)

자리 뜻
첫 글자 - 파일, d 폴더
다음 세 글자 소유자의 권한(rw-: 읽기와 쓰기)
다음 세 글자 그룹의 권한
마지막 세 글자 다른 사람의 권한(---: 아무것도 못 한다)
하는 일 명령
나만 읽고 쓰게 한다(비밀 파일) chmod 600 .env
실행 권한을 더한다(스크립트) chmod +x 스크립트.sh
권한을 본다 ls -l 파일

숫자 권한의 각 자리는 소유자, 그룹, 다른 사람의 순서이고, 읽기 4, 쓰기 2, 실행 1을 더한 값이다. 600은 소유자 읽기와 쓰기(6), 그룹과 다른 사람은 없음(0, 0)이다. Windows의 파일에는 chmod가 거의 효과가 없다(부록 A-16).
