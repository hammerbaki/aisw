[부록 B] 명령어 카드

2027학년도 「LLM 서비스 개발」의 준비 중인 교재입니다. 편집 상태를 검토하기 위해 미리 공개한 것으로, 수업 전에 내용과 순서가 바뀔 수 있습니다.

「LLM 서비스 개발」 1~13장의 공통 부록 · 2026-11 기준(Windows 11의 Git Bash, Claude Code 2.1.296, git 2.55, GitHub CLI 2.88, 파이썬 3.13에서 확인)

자주 쓰는 명령을 도구별로 모은 참조표이다. 각 장은 명령을 처음 쓸 때 그 뜻을 설명하고, 이후에는 이 카드를 가리킨다. 장에서 「읽기」로 줄인 명령(학습자가 치지 않고 출력만 읽는 명령)도 이 카드에 실행 예와 함께 모았다. 연습용 저장소에서 직접 쳐 보고 싶으면 이 카드를 따라 한다.

명령을 어디에 입력하는가가 첫 번째 구분이다. 셸 명령은 [터미널](내 PC의 VS Code 통합 터미널. Windows는 Git Bash, macOS는 기본 셸)에, 슬래시 명령과 프롬프트는 [Claude Code] 입력 창에 넣는다(부록 A의 꼬리표). 출력 예시는 따로 밝히지 않으면 집필용 Windows 11 PC의 Git Bash에서 시험용 저장소로 실행한 결과이다(2026-11-17, 2026-11-18). 커밋 번호, 사용자 이름, 경로는 사람마다 다르다. 카드에 적은 「4장 7-3」 같은 번호는 그 명령을 쓰는 장과 소절이다.

카드 도구 입력하는 곳
B-1 Claude Code 셸(시작 명령), Claude Code 입력 창(슬래시 명령, 단축키)
B-2 Git 셸
B-3 GitHub CLI(gh) 셸
B-4 셸 기본 명령 셸
B-5 파이썬, 테스트, 로컬 서버, 장의 도구(json.tool, rag, REA) 셸
B-6 2장과 3장에서 옮긴 설명 (명령 카드가 아니다. 읽는 자료이다)

도구는 판이 바뀌면 명령과 화면이 달라진다. 이 카드와 실제 동작이 다르면 각 도구의 도움말(claude --help, Claude Code 안의 /help, git help 명령, gh 명령 --help)과 공식 문서가 우선한다.

[최신 자료 자리: 이 카드가 확인한 도구의 판] 확인할 곳: 내 PC의 claude --version, git --version, gh --version, python --version. 2026-11-17 확인 값(집필용 PC): Claude Code 2.1.296, git 2.55.0.windows.5, GitHub CLI 2.88.1(2026-03-12 배포), 파이썬 3.13.7, curl 8.21.0. 2026-11-18에 B-2-8·B-2-9·B-4-4·B-5의 새 출력을 같은 판으로 얻었다(Node.js 24.14.0은 REA의 조건에 맞지 않아 REA는 실행하지 않았다). 내 PC의 판이 다르면 아래 자리 표시의 문서에서 명령과 화면을 다시 확인한다.

B-1. Claude Code 명령 카드

B-1-1. 셸에서 시작하는 명령

터미널 
claude
claude "이 폴더의 구조를 설명하라"
claude -c
claude -r
명령 뜻
claude 지금 폴더를 작업 폴더로 대화형 세션을 시작한다
claude "요청" 첫 요청을 넣은 채 대화형 세션을 시작한다
claude -c (--continue) 지금 폴더에서 가장 최근의 대화를 이어 간다
claude -r (--resume) 지난 대화 목록을 열어 골라 이어 간다. 뒤에 세션 ID나 검색어를 줄 수 있다
claude -n 이름 (--name) 세션에 이름을 붙여 시작한다. 이름은 입력 창, /resume 목록, 터미널 제목에 보인다
claude --permission-mode plan 계획 모드로 시작한다(B-1-6)
claude --model 모델 이 세션에서 쓸 모델을 정해 시작한다
claude --version (-v) 버전을 출력한다
claude doctor 설치와 설정 파일을 진단한다(읽기 전용)
claude update 지금 바로 최신판으로 업데이트한다
claude auth login / logout / status 셸에서 로그인, 로그아웃, 인증 상태 확인(부록 A-8)
claude --help 모든 옵션을 보여 준다
  • claude -p "요청"(--print)은 대화 화면 없이 한 번 답하고 끝내는 헤드리스 모드이다. 스크립트와 자동화에 쓰며, 이 과목의 실습에서는 쓰지 않는다(「AI에이전트 기획 및 개발」에서 다룬다).
  • --dangerously-skip-permissions는 모든 권한 확인을 건너뛴다. 도움말이 인터넷이 막힌 격리 환경에서만 쓰라고 경고하는 옵션이므로 이 과목에서는 쓰지 않는다(claude --help, 2026-11-14 확인).

[최신 자료 자리: claude 시작 옵션] -c, -r, -n, --permission-mode의 값, --model, auth·doctor·update. 확인할 곳: 내 PC의 claude --help, https://code.claude.com/docs/en/cli-reference. 마지막으로 확인한 날짜와 값: 2026-11-17, Claude Code 2.1.296의 도움말이 본문과 같다. 수업 전에 다시 확인한다.

B-1-2. 슬래시 명령

Claude Code 입력 창의 맨 앞에 /를 치면 명령 목록이 뜨고, 글자를 더 치면 목록이 좁혀진다[C1]. 명령은 메시지의 맨 앞에 있을 때만 명령으로 인식되며, 뒤에 붙인 글은 그 명령의 인자가 된다[C1]. 아래 표는 2026-11-14의 공식 문서에서 확인한 것이다.

시작과 상태

명령 뜻
/help 도움말과 쓸 수 있는 명령 목록. 막히면 여기서 시작한다
/status 설정 화면의 Status 탭. 버전, 모델, 계정, 연결 상태, 읽은 설정 파일을 보여 준다
/login / /logout Anthropic 계정에 로그인 / 로그아웃
/model [모델] 모델을 바꾸고 다음 세션의 기본값으로 저장한다. 목록에서 s를 누르면 이 세션에만 적용한다
/config 설정 화면(테마, 모델, 출력 형식 등)
/doctor 설치, 설정, CLAUDE.md의 문제를 진단하고 고칠 방법을 제안한다
/exit (/quit) Claude Code를 끝낸다

대화와 컨텍스트

명령 뜻
/clear (/reset, /new) 대화를 비우고 새로 시작한다. 이전 대화는 /resume으로 다시 열 수 있다
/compact [지시] 지금까지의 대화를 요약해 컨텍스트를 비운다. 요약에 남길 내용을 지시로 줄 수 있다
/context 컨텍스트 창이 얼마나 차 있는지 색 격자로 보여 준다
/usage (/cost) 세션의 비용, 요금제의 사용 한도, 활동 통계
/resume [세션] 지난 대화를 ID나 이름으로, 또는 목록에서 골라 이어 간다
/rename [이름] 지금 세션의 이름을 바꾼다. 이름을 주지 않으면 대화 내용으로 지어 준다
/branch [이름] 지금 시점에서 대화의 갈래를 만들어 다른 방향을 시도한다. 원래 대화는 /resume으로 돌아갈 수 있다
/btw [질문] 대화 기록에 남기지 않는 곁가지 질문을 한다
/export [파일이름] 대화를 일반 텍스트로 내보낸다. 실습 기록의 증빙으로 쓴다
/copy [N] 마지막(또는 N번째 전) 응답을 클립보드에 복사한다. 목록에서 w를 누르면 파일로 쓴다

작업의 통제

명령 뜻
/plan [설명] 계획 모드로 들어간다. 설명을 주면 그 일로 바로 계획을 시작한다(B-1-6)
/permissions 도구 사용의 허용, 확인, 거부 규칙을 보고 고친다
/rewind (/checkpoint, /undo) 대화와 코드를 앞 시점으로 되감거나, 한 시점부터 요약한다(B-1-7)
/diff 작업 트리의 변경(Claude가 지금까지 고친 것 포함)을 검토한다
/init 프로젝트를 분석해 CLAUDE.md 초안을 만든다(2장)
/memory CLAUDE.md 파일들을 편집하고 자동 메모리를 켜고 끈다
/add-dir 경로 이 세션에서 파일을 다룰 폴더를 더한다
/cd 경로 대화를 유지한 채 작업 폴더를 옮긴다

검토

명령 뜻
/review 지금의 변경(또는 지정한 풀 리퀘스트, 브랜치, 경로)을 코드 검토한다. /code-review의 별칭이다
/security-review 지금 브랜치의 변경을 보안 관점(주입, 인증, 정보 노출)에서 검토한다. 원격 origin이 있어야 한다

이 밖에 /theme(색 테마), /terminal-setup(VS Code 등에서 Shift+Enter 줄바꿈 설정), /tasks(백그라운드 작업 목록), /hooks, /mcp, /agents가 있다. 뒤의 세 가지는 「AI에이전트 기획 및 개발」에서 다룬다.

[최신 자료 자리: 슬래시 명령의 목록과 별칭] 확인할 곳: Claude Code 안의 /help, https://code.claude.com/docs/en/commands. 마지막으로 확인한 날짜와 값: 2026-11-14, 위 네 표의 명령과 별칭(/clear의 /reset·/new, /rewind의 /checkpoint·/undo, /usage의 /cost, /review는 /code-review의 별칭). 명령은 판마다 더해지거나 이름이 바뀌므로 수업 전에 다시 확인한다.

B-1-3. 단축키

키 뜻
Esc 진행 중인 응답이나 도구 실행을 멈춘다. 그때까지 한 일은 남고, 다음 지시를 기다린다. 열린 대화 상자는 닫는다
Esc Esc 입력 창이 비어 있으면 되감기 메뉴를 연다. 입력 중이면 쓰던 글을 지운다(↑로 되살린다)

B-1-5. 권한 모드

권한 모드는 Claude가 묻지 않고 할 수 있는 일의 범위를 정한다[C3]. 화면 아래쪽의 모드 표시로 지금 모드를 본다.

모드(설정 값) 묻지 않고 하는 일 쓰는 때
Manual (default) 읽기만 모든 행동을 사람이 하나씩 검토할 때. 이 과목의 기본
acceptEdits 읽기, 작업 폴더 안의 파일 수정, 흔한 파일 명령(mkdir, touch, mv, cp 등) 검토 중인 코드를 반복해 고칠 때
plan 읽기(계획만 세우고 고치지 않는다) 고치기 전에 조사하고 계획할 때
auto 모든 일, 다만 분류기가 뒤에서 행동을 검토한다 긴 작업. 계정과 모델에 따라 쓸 수 없을 수 있다
dontAsk 미리 허용한 도구만. 물어야 할 것은 거부 자동화 스크립트
bypassPermissions 모든 일 격리된 컨테이너에서만. 이 과목에서는 쓰지 않는다

Shift+Tab을 누를 때마다 모드가 다음 순서로 돈다. auto는 쓸 수 있는 계정과 모델일 때만 순환에 들어가고, dontAsk는 순환에 나타나지 않는다[C3].

flowchart LR
    M["Manual<br/>(default)"] --> AE["acceptEdits"] --> P["plan"] --> AU["auto<br/>(쓸 수 있을 때)"] --> M

[그림 자리: 입력 창 아래의 권한 모드 표시] Shift+Tab을 누를 때마다 바뀌는 모드 표시(Manual, accept edits, plan, auto)를 네 장으로 나란히 보인다. 찍을 곳: 내 PC의 VS Code 통합 터미널에서 실행한 Claude Code 입력 창.

  • 2026-11 기준으로 Claude Code는 auto를 쓸 수 있는 세션이면 auto로 시작하고, 쓸 수 없으면 Manual로 시작한다[C3]. 시작할 때 화면의 모드 표시를 확인하고, 수업에서 안내한 모드가 아니면 Shift+Tab으로 맞춘다.
  • 시작할 때부터 모드를 정하려면 claude --permission-mode manual처럼 옵션을 준다. 옵션의 값은 acceptEdits, auto, bypassPermissions, manual, dontAsk, plan이다(claude --help, 2026-11-14 확인).
  • 거부(deny) 규칙은 어느 모드에서나 지켜진다[C3]. 부록 A-14-4의 .env 읽기 거부가 이 규칙이다.
  • 권한을 묻는 화면에서 「Yes, and don’t ask again」을 고르면 그 명령의 허용 규칙이 .claude/settings.local.json에 저장된다[C4]. 무엇을 영구히 허용했는지는 /permissions에서 보고 지운다.

[최신 자료 자리: 권한 모드의 이름, 순환 순서, 시작 모드] 확인할 곳: https://code.claude.com/docs/en/permission-modes, claude --help. 2026-11-15 확인 값: 표시 이름과 설정 값은 Manual(default. CLI는 manual도 받는다), accept edits(acceptEdits), Plan(plan), Auto(auto), don’t ask(dontAsk), Bypass permissions(bypassPermissions)이다. Shift+Tab 순환은 default → acceptEdits → plan 뒤에, 켜 둔 경우 bypassPermissions, 그다음 auto가 온다. dontAsk는 순환에 없다. 터미널 세션은 v2.1.283부터 auto로 시작하고, claude -p와 Agent SDK는 v2.1.302부터 Manual로 시작한다. 수업 전에 다시 확인한다.

B-1-6. 계획 모드

계획 모드에서 Claude는 파일을 읽고 조사해 바꿀 계획을 제안하지만, 계획을 승인하기 전에는 소스를 고치지 않는다[C3]. 명세에서 구현으로 넘어가기 전에 Claude가 무엇을 어떤 순서로 할지 먼저 읽고 고치기 위해 쓴다(2장 5-2에서 소개, 5장 1-3에서 자세히). 파일이 바뀌면 안 되는 분석 단계(4장 7-3의 응답 읽기)도 계획 모드에서 한다.

계획이 나오면 승인 화면에서 다음 가운데 하나를 고른다[C3]. 선택지 이름은 버전에 따라 다를 수 있다.

  • 승인 화면에서 Shift+Tab을 누르면 계획이 승인된다. 모드만 바꾸려면 먼저 Esc를 누른다[C3].

B-1-7. 되감기(체크포인트)

Claude Code는 프롬프트를 보낼 때마다 그 직전의 코드 상태를 체크포인트로 남긴다[C5]. /rewind를 실행하거나 빈 입력 창에서 Esc를 두 번 누르면 되감기 메뉴가 열리고, 되돌아갈 프롬프트를 고른 뒤 다음 가운데 하나를 고른다.

선택 뜻
Restore code and conversation 코드와 대화를 모두 그 시점으로 되돌린다
Restore conversation 대화만 되돌리고 코드는 지금 그대로 둔다
Restore code 코드만 되돌리고 대화는 그대로 둔다
Summarize from here 그 시점 뒤의 대화를 요약해 컨텍스트를 비운다
Summarize up to here 그 시점 앞의 대화를 요약한다
Never mind 아무것도 하지 않고 돌아간다

되감기는 Git을 대신하지 않는다. 공식 문서가 밝히는 한계는 다음과 같다[C5].

한계 뜻 대신 쓰는 것
셸 명령의 변경 Claude의 편집 도구가 한 번도 고치지 않은 파일을 셸 명령(rm, mv, 스크립트)이 바꾼 것은 되돌리지 않는다 git restore
바깥의 변경 사람이 편집기로 고친 것, 다른 세션이 고친 것은 보통 추적하지 않는다 git diff로 확인, git restore
보관 기간 세션의 파일 스냅숏은 기본적으로 약 30일 뒤 정리된다 커밋
기록과 협업 세션 단위의 빠른 복구용이다 커밋, 브랜치, 원격 저장소

이 과목의 규칙: Claude Code에게 일을 맡기기 전에 git status가 깨끗한지 보고, 결과를 확인한 뒤 커밋한다. 되감기는 커밋 사이의 시행착오를 되돌리는 데 쓴다.

[그림 자리: 되감기 메뉴] 빈 입력 창에서 Esc를 두 번 눌러 연 프롬프트 목록과, 하나를 고른 뒤 나오는 여섯 선택지(Restore code and conversation 등). 찍을 곳: 내 PC의 Claude Code에서 파일을 한 번 고치게 한 뒤.

[최신 자료 자리: 되감기의 선택지와 보관 기간] 확인할 곳: https://code.claude.com/docs/en/checkpointing. 마지막으로 확인한 날짜와 값: 2026-11-14, 선택지 여섯 개와 세션 스냅숏의 보관 기간 약 30일. 수업 전에 다시 확인한다.

태그의 두 번호. 주석 태그(git tag -a)는 태그 자체가 하나의 객체이므로 번호가 둘이다. 태그가 가리키는 커밋의 번호는 git log -1 --format=%h 태그로 보고, git rev-parse --short 태그는 태그 객체의 번호를 보인다. 12장 8-3은 앞의 명령으로 출발점 태그 spec-ch12의 커밋 번호를 보고 git worktree list의 번호와 견준다.

$ git log -1 --format=%h spec-v1
2ba6d6e
$ git rev-parse --short spec-v1
4288231

파일의 지문. git hash-object 파일은 파일 내용으로 계산한 번호를 보인다. 내용이 한 글자라도 다르면 번호가 다르다. 두 파일이 같은지, 복사한 뒤 바뀌지 않았는지를 볼 때 쓴다. Windows에도 있으므로 md5sum 대신 쓴다.

$ git hash-object notes.md

$ cp notes.md n2.md && git hash-object n2.md

$ echo "x" >> n2.md && git hash-object n2.md
2a338621e2cf8ba70c8859733ed473c4d85f8ed7

상황 명령 기록이 바뀌는가

파일을 특정 커밋의 상태로 가져온다 git restore --source=커밋 파일 아니오
실수로 추적하게 된 파일을 추적에서만 뺀다(.env) git rm --cached 파일 다음 커밋에서
이미 커밋한 것을 취소하는 새 커밋을 만든다 git revert 커밋 새 커밋이 더해진다
마지막 커밋의 메시지를 고친다(푸시하기 전만) git commit --amend -m "메시지" 마지막 커밋이 바뀐다
마지막 커밋을 풀어 변경을 스테이징 상태로 돌린다(푸시하기 전만) git reset --soft HEAD~1 마지막 커밋이 사라진다

  • --amend 뒤에 커밋 번호가 ee8d5f5에서 a9aef5d로 바뀌었다. 커밋을 고치는 것이 아니라 새 커밋으로 바꿔 끼운다.
  • --soft는 변경을 스테이징된 채(M), 모드를 생략한 reset(--mixed)은 작업 트리에만(M) 남긴다.

주의할 점은 다음과 같다.

  • 푸시한 커밋은 revert로 되돌린다. --amend와 reset은 기록을 고쳐 쓰므로, 이미 남과 나눈 커밋에 쓰면 다른 사람의 기록과 어긋난다.
  • git restore 파일로 사라진 변경은 Git으로 되살릴 수 없다. 확실하지 않으면 먼저 git diff로 무엇이 사라지는지 본다.
  • git reset --hard는 커밋하지 않은 변경까지 지운다. 이 과목의 개인 실습 저장소에서는 쓰지 않는다(2장 0-3, 8-1).
  • Claude Code의 되감기(B-1-7)와 Git의 되돌리기는 대상이 다르다. 셸 명령이 바꾼 파일과 커밋한 뒤의 상태는 Git으로 되돌린다.

$ git check-ref-format --branch "feature..x"

한 커밋으로 합치기와 버리기. --squash는 브랜치의 변경을 스테이징만 하고 커밋은 하지 않는다. 이어서 커밋하면 브랜치의 여러 커밋이 main에 커밋 하나로 들어간다. GitHub의 「Squash and merge」와 같은 결과이다(B-6-20). 이렇게 합친 브랜치는 Git이 병합된 것으로 보지 않으므로 -d가 거절하고, 버릴 때는 -D를 쓴다.

$ git merge --squash 3-try
Updating c769c04..45b9f55
Fast-forward
Squash commit -- not updating HEAD
 a.md | 2 ++
$ git status --short
A  a.md
$ git commit -qm "3-try를 한 커밋으로"
$ git branch -d 3-try
error: the branch '3-try' is not fully merged
$ git branch -D 3-try
Deleted branch 3-try (was 45b9f55).

(branch -d의 거절 뒤에 붙는 hint: 두 줄은 뺐다.) 브랜치를 옮기기 전에 git status가 깨끗한지 본다. 커밋하지 않은 변경은 옮겨 간 브랜치로 따라오거나, 덮어써질 때는 Git이 옮기기를 거부한다.

B-2-7. 충돌

두 브랜치가 같은 파일의 같은 줄을 다르게 고쳤으면 Git은 자동으로 합치지 못하고 충돌을 알린다. 충돌은 오류가 아니라 사람이 골라야 하는 자리이다(3장 6절).

$ git merge feature/a
Auto-merging README.md
CONFLICT (content): Merge conflict in README.md
Automatic merge failed; fix conflicts and then commit the result.
$ git status --short
UU README.md

파일 안에는 두 판이 표시와 함께 들어 있다.

파일: README.md 
<<<<<<< HEAD
# 실습
B안
=======
# 실습
A안
>>>>>>> feature/a
표시 뜻
<<<<<<< HEAD ~ ======= 지금 브랜치(합치는 쪽)의 내용
======= ~ >>>>>>> 브랜치 합쳐 오는 브랜치의 내용

해결 순서는 다음과 같다.

  1. git diff --name-only --diff-filter=U로 충돌한 파일을 찾는다.

  3. git add 파일로 해결했음을 알린다.
  4. git commit -m "충돌 해결: ..."으로 병합을 마친다.
  5. 해결을 포기하고 병합 전으로 돌아가려면 git merge --abort를 실행한다.

B-2-8. 작업 트리(worktree)

작업 트리는 한 저장소의 브랜치 여러 개를 서로 다른 폴더에 동시에 꺼내 두는 기능이다. 12장은 Orca가 이 기능으로 구현마다 작업 공간을 만든다(부록 A-21). Orca 없이 명령으로 할 때와, Orca가 만든 것을 확인할 때 쓴다(12장 3-2, 3-4, 8-3, 8-7).

상황 명령

B-6-3. 2장: 설정의 범위와 확인

Git 설정에는 범위가 셋 있다. --system은 그 PC의 모든 사용자(Git for Windows는 설치 폴더의 etc/gitconfig), --global은 내 계정의 모든 저장소(~/.gitconfig), --local(옵션을 생략하면 이것)은 저장소 하나(.git/config)에 적용된다. 좁은 범위의 값이 넓은 범위의 값을 이긴다. 값이 어느 파일에서 왔는지는 git config --list --show-origin으로 본다.

Windows에서 이 명령을 치면 --system 범위에 Git for Windows가 설치할 때 넣은 core.autocrlf=true와 credential.helper=manager가 보인다(집필용 PC, 2026-11-16). 앞의 것 때문에 git add가 「LF will be replaced by CRLF the next time Git touches it」 경고를 내는 일이 있다. 저장소에는 LF로 기록되므로 실습을 멈출 일이 아니다(부록 A-9). 뒤의 것은 2장 9절의 인증 정보를 Windows 자격 증명 관리자에 보관하는 장치이다.

[확인] git config --global --list에 user.name, @users.noreply.github.com으로 끝나는 user.email, init.defaultbranch=main, core.quotepath=false, pull.rebase=false, core.editor=nano가 모두 보인다.

B-6-4. 2장: 파일 참조 @와 셸 모드 !

@경로는 그 파일의 내용을 메시지에 함께 넣는다(예: @ch02/deadline/dday.py 를 설명하라). 폴더를 가리키면 내용이 아니라 파일 목록을 넣는다. @를 치면 경로 자동 완성 목록이 뜬다. Tab이나 Enter로 고른다. 파일 내용이 기본 25,000토큰을 넘거나 256KB보다 큰 텍스트 파일은 통째로 들어가지 않는다. @로 참조한 파일이 있는 폴더와 그 위 폴더의 CLAUDE.md도 함께 읽힌다[2장 C2].

!명령처럼 !로 시작하는 입력은 셸 모드이다(예: !git status --short). Claude Code가 명령을 해석하거나 허락을 묻지 않고 바로 실행하며, 명령과 출력이 대화에 더해져 Claude가 그것을 보고 답한다[2장 C7]. Claude Code를 나가지 않고 git status나 pytest의 결과를 보며, 그 결과를 대화의 재료로 삼을 때 쓴다. 빈 입력 창에서 Esc나 Backspace를 누르면 셸 모드에서 나온다.

!로 실행한 명령은 사람이 직접 실행한 것이다. 그러므로 !rm 같은 명령도 묻지 않고 실행된다. 위험한 명령은 !가 아니라 [터미널]에서 치고, 친 뒤 결과를 확인한다.

B-6-5. 2장: 작업 중 개입

Claude Code가 일하는 동안에도 사람은 끼어들 수 있다[2장 C1][2장 C10].

엉뚱한 방향으로 가기 시작하면 Esc를 누른다. 진행 중인 도구 실행이 멈추고 그때까지의 작업은 남는다. 멈추지 않고 방향만 고치려면 고칠 문장을 입력하고 Enter를 누른다. 메시지는 대기열에 들어가, 진행 중인 도구 실행이 끝나는 대로 읽힌다. 방금 시킨 일 자체를 무르려면 Esc 두 번이나 /rewind로 되감기 메뉴(2장 7절)를 연다. 공식 모범 사례는 “첫 1분을 지켜보고, 엇나가는 순간 Esc를 누르고, 두 번 고쳐도 안 되면 /clear로 새로 시작하라”고 권한다[2장 C10]. 같은 것을 세 번째 고치는 말은 실패한 시도 둘이 든 대화 위에 쌓일 뿐이기 때문이다.

B-6-8. 2장: 대화 재개

Claude Code는 대화를 세션 단위로 저장한다. 세션은 시작한 폴더에 묶인다. 나갔다가 같은 대화로 돌아오는 방법은 다음과 같다[2장 C2].

claude --continue(-c)는 지금 폴더의 가장 최근 대화를 이어서 열고, 없으면 「No conversation found to continue」를 출력하고 끝난다. claude --resume(-r)은 지난 대화 목록을 열어 고르게 하고, claude --resume 「이름」은 이름을 붙인 대화를 바로 연다. 세션 안에서는 /resume으로 다른 대화로 옮겨 간다. 이름은 세션 안에서 /rename 「이름」으로 붙이거나, claude -n 「이름」으로 처음부터 붙여 시작한다. 2장 10절은 -n ch02-main으로 이름을 붙여 시작하므로, 수업 중에 나가야 하면 claude --resume ch02-main --permission-mode manual로 다시 연다.

재개한 대화는 대화 이력과 체크포인트를 함께 돌려받는다. --continue나 이름으로 재개하면 끝날 때의 권한 모드도 되살린다. 다만 시작 모드를 정하는 옵션(--permission-mode)을 함께 주면 그 값이 이긴다. 목록에서 골라 재개하면 새 세션과 같은 모드로 시작한다(계획 모드로 끝난 대화는 계획 모드로 돌아온다)[2장 C2]. 이어 연 대화는 앞의 긴 대화를 그대로 컨텍스트에 싣는다. 이어서 할 일이 앞 대화와 관계가 없으면 새로 시작하는 편이 낫다. 계속 지킬 것은 이미 CLAUDE.md에 있다.

B-6-10. 2장: 체크포인트와 커밋의 분담

두 장치의 분담은 시점으로 정리된다. Claude Code에게 일을 시키기 직전에는 git status가 깨끗한지 보고, 아니면 커밋한다. 이번 지시로 바뀐 것만 git diff에 나오게 하기 위해서이다. 지시가 엇나갔다는 것을 바로 알았으면 Esc와 되감기로 대화와 파일을 함께 무른다. 결과를 확인했고 남기고 싶으면 git diff로 읽고 의미 단위로 커밋한다. 이미 커밋한 변경 하나를 무를 때는 git revert를 쓴다(2장 8절). 세션을 닫았거나, 체크포인트가 정리되었거나, 셸 명령이 바꾼 파일이면 Git만 남는다.

되감기에는 또 하나의 한계가 있다. 되감기는 프롬프트 단위로 돌아간다. 한 프롬프트로 변경 셋을 시켰다면, 되감기는 셋을 함께 무를 뿐 그중 하나만 고르지 못한다. 하나만 고르는 일은 변경을 커밋 셋으로 나누어 둔 뒤 git revert가 맡는다. Claude Code 공식 문서도 체크포인트는 세션 수준의 빠른 복구용이고, 영구 기록과 협업에는 Git을 계속 쓰라고 적는다[2장 C6][2장 C10].

B-6-11. 2장: 마지막 커밋 고치기와 브랜치 옮기기: amend와 reset

읽기. 아래는 연습용 저장소에서 실행한 명령과 출력이다. 학습자는 치지 않는다.

$ echo "- 임시 항목" >> notes.md
$ git commit -am "임시"
[main afa4940] 임시
$ git commit --amend -m "임시 항목 추가"
[main 9261965] 임시 항목 추가
$ git reset --soft HEAD~1
$ git status --short
M  notes.md
$ git commit -m "임시 항목 추가"
[main a62bebf] 임시 항목 추가
$ git reset HEAD~1
Unstaged changes after reset:
M   notes.md
$ git status --short
 M notes.md

(출력의 일부 줄은 줄였다.) git commit -a(-am의 a)는 이미 추적하는 파일의 변경을 스테이징까지 한 번에 한다. 새 파일은 넣지 않는다. --amend 뒤에 해시가 afa4940에서 9261965로 바뀐 것에 주목한다. --amend는 커밋을 고치는 것이 아니라 새 커밋으로 바꿔 끼운다. 그래서 푸시한 커밋에 쓰면 원격의 기록과 어긋난다.

git reset의 세 모드는 스테이징 영역과 작업 트리를 어디까지 함께 옮기는지가 다르다[2장 G7]. --soft는 커밋만 없애고 변경을 스테이징된 채(M) 남긴다. 메시지를 다시 쓰거나 커밋 둘을 하나로 합칠 때 쓴다. --mixed(모드를 생략한 것)는 커밋과 스테이징을 없애고 변경을 작업 트리에만(M) 남긴다. 커밋을 다른 묶음으로 다시 나눌 때 쓴다. 2장 10절에서 Claude Code가 지시를 어기고 커밋까지 했을 때 이 두 모드로 커밋을 푼다.

--hard는 작업 트리까지 덮어쓴다. 커밋하지 않은 변경이 있으면 그것도 사라진다. 커밋했던 내용은 git reflog(HEAD가 지나온 자리를 시간 순으로 적은 기록)로 찾아 git reset --hard 「해시」로 되찾을 수 있지만, 커밋한 적이 없는 내용은 Git으로 되찾을 수 없다. reflog는 내 컴퓨터에만 있고 일정 기간이 지나면 정리된다. Claude Code의 Auto 모드도 git reset --hard, git checkout -- ., git restore ., git clean -fd를 커밋하지 않은 변경을 버리는 명령으로 보고 기본으로 막는다[2장 C4]. 사람도 같은 기준으로 다룬다. 이 과목의 개인 실습 저장소에서는 reset --hard를 쓰지 않는다.

B-6-13. 3장: 읽기: 푸시 거부

두 사람이 한 원격 저장소를 쓸 때의 일을 출력으로 읽는다. 키트의 make_sandbox.sh는 원격 역할을 하는 bare 저장소 origin.git(작업 폴더 없이 .git의 내용만 가진 저장소. GitHub의 저장소가 이런 형태이다)과 그것을 클론한 두 폴더 a(개발자A), b(개발자B)를 내 PC에 만든다. 학습자는 이 도구를 3장 6-2에서 처음 실행한다. 아래는 집필용 PC의 Git Bash에서 얻은 출력이며, 경로는 /c/Users/「아이디」/로 바꾸었다.

두 사람이 같은 시점의 main에서 각자 커밋한다. A가 먼저 커밋하고 푸시한다. 이어서 B가 A의 푸시를 받지 않은 채 자기 커밋을 푸시한다.

$ cd ~/ch03-sandbox/a
$ echo "A의 메모" > a.txt && git add a.txt && git commit -m "A: 메모 추가" && git push
[main d04fa3a] A: 메모 추가
(…)
   1b43bc4..d04fa3a  main -> main
$ cd ~/ch03-sandbox/b
$ echo "B의 메모" > b.txt && git add b.txt && git commit -m "B: 메모 추가" && git push
[main 3819435] B: 메모 추가
(…)
To C:/Users/「아이디」/ch03-sandbox/origin.git
 ! [rejected]        main -> main (fetch first)
error: failed to push some refs to 'C:/Users/「아이디」/ch03-sandbox/origin.git'
hint: Updates were rejected because the remote contains work that you do not
hint: have locally. This is usually caused by another repository pushing to
hint: the same ref. If you want to integrate the remote changes, use
hint: 'git pull' before pushing again.
hint: See the 'Note about fast-forwards' in 'git push --help' for details.

&&는 앞 명령이 성공했을 때만 뒤 명령을 실행한다. B의 [rejected] ... (fetch first)는 “원격에 내가 모르는 커밋이 있으니 먼저 받아 오라”는 뜻이다. 파일 주고받기였다면 B의 파일이 A의 수정을 덮었을 자리에서, Git은 B를 멈춘다.

결과 읽기: 푸시 거부의 네 갈래. 이 장의 푸시 거부는 거부 줄의 괄호와 remote: 줄로 네 갈래를 가린다. 갈래마다 할 일이 다르므로 갈래를 먼저 정한다. ①과 ②는 연습 저장소에서 실제로 얻은 출력이다.

① ! [rejected]        main -> main (fetch first)
   원격에 내가 받지 않은 커밋이 있다 → 받아서 합친 뒤 푸시(바로 아래)
② ! [rejected]        main -> main (non-fast-forward)
   받기(fetch)는 했으나 합치지 않았다. git status -sb가 [ahead 1, behind 1]
   → 합친 뒤 푸시. 리베이스한 내 작업 브랜치라면 B-6-20의 rebase
③ remote: error: GH006: Protected branch update failed for refs/heads/main.
   ! [remote rejected] main -> main (protected branch hook declined)  (예시)
   저장소 규칙이 막았다 → 받아 와도 풀리지 않는다. 브랜치와 PR로(B-6-24)
④ remote: Permission to 「교수 계정」/ict-aisw-2027-team01-lab.git denied to 「아이디」.
   fatal: unable to access '…': The requested URL returned error: 403   (예시)
   쓰기 권한이 없다 → 3장 0-3의 권한 확인. 팀 배정은 교수에게
# 어느 갈래도 강제 푸시(--force)로 풀지 않는다

B는 원격의 커밋을 받아 자기 커밋과 합친 뒤 다시 푸시해야 한다. 받는 방법은 3장 4-2에서 자세히 다룬다. git pull --rebase는 원격의 커밋을 받은 뒤 내 커밋을 그 위로 옮겨 붙인다.

$ git pull --rebase
(…)
Successfully rebased and updated refs/heads/main.
$ git log --oneline --graph
* 5138304 B: 메모 추가
* d04fa3a A: 메모 추가
* 1b43bc4 팀 실습 저장소의 시작 파일
$ git push
   d04fa3a..5138304  main -> main

A의 커밋 위에 B의 커밋이 올라가 한 줄의 기록이 되었고 푸시가 받아들여졌다. B의 커밋 해시가 3819435에서 5138304로 바뀐 것에 주의한다. 커밋을 옮겨 붙이면 새 커밋이 만들어진다. 두 사람이 서로 다른 파일을 고쳤으므로 충돌은 없었다. 같은 줄을 고친 경우는 3장 6절에서 다룬다.

B-6-14. 3장: 개인 계정의 저장소와 조직의 저장소

GitHub의 저장소는 소유자가 개인 계정이거나 조직(Organization)이다. 2장의 llm-service-lab은 학습자 개인 계정의 저장소이다. 개인 계정의 저장소에서 다른 사람과 함께 일하려면 그 사람을 협업자(collaborator)로 한 명씩 초대한다. 협업자는 저장소를 읽고 푸시할 수 있으며, 비공개 저장소의 협업자에게 읽기 전용 권한만 주는 방법은 없다. 설정을 바꾸고 협업자를 더하는 것은 소유자뿐이다[3장 G13].

조직은 여러 사람이 저장소를 함께 소유하는 계정이다. 조직 안에 팀(team)을 만들고, 저장소 권한을 사람 단위가 아니라 팀 단위로 준다[3장 G11]. 팀원이 바뀌면 팀 명단만 고치면 되고, 사람이 떠나도 저장소는 조직에 남는다.

이 과목은 조직을 쓰지 않는다. 교수 계정에 팀마다 비공개 저장소 <팀>-lab을 만들고 팀원을 협업자로 초대한다. 팀원은 모두 write에 해당하는 권한을 받고, admin에 해당하는 일은 소유자인 교수만 한다. 프로젝트실습Ⅰ 저장소 <팀>-project도 교수 계정에 둔다.

요금제에 따라 쓸 수 있는 기능이 다르다. GitHub의 요금제 안내는 비공개 저장소의 보호 브랜치와 필수 리뷰어를 개인 계정에서는 GitHub Pro, 조직에서는 GitHub Team의 기능으로 적는다[3장 G12]. 보호 규칙은 저장소 소유자의 요금제를 따르므로, 부록 B-6의 「보호 브랜치 규칙의 항목」(B-6-23)과 「읽기: 팀 실습 저장소의 규칙과 거부되는 푸시」(B-6-24)의 보호 규칙은 교수 계정이 GitHub Pro이기에 동작한다.

[최신 자료 자리: GitHub 요금제별 보호 기능과 개인 계정 저장소의 권한] 비공개 저장소의 보호 브랜치·규칙 집합을 쓸 수 있는 요금제, 개인 계정 저장소의 협업자 권한. 확인할 곳 docs.github.com의 「GitHub’s plans」, 「About rulesets」, 「Permission levels for a personal account repository」. 2026-11-17 값: 보호 브랜치는 Pro·Team 이상, 규칙 집합은 Team·Enterprise 대상(Pro는 적지 않음), 개인 계정 저장소의 협업자는 쓰기 권한만 받는다.

B-6-15. 3장: 저장소의 기본 권한

조직의 저장소에는 다섯 가지 기본 권한이 있다. 개인 계정 저장소의 협업자와 소유자는 이 가운데 write와 admin에 해당한다. GitHub Docs는 권한마다 권장하는 대상을 다음과 같이 적는다[3장 G11]. 2026-11 기준 문서에는 이슈와 토론의 관리만 맡는 moderate 권한도 함께 실려 있으나, 이 과목에서는 쓰지 않는다.

권한 권장 대상 (GitHub Docs의 설명을 옮김) 조직을 쓴다면 줄 사람
read 코드에 기여하지 않고 프로젝트를 보거나 토론하는 사람 다른 팀의 학습자
triage 쓰기 권한 없이 이슈와 풀 리퀘스트를 적극적으로 관리하는 사람 조교
write 프로젝트에 적극적으로 푸시하는 사람 팀원 전원(이 과목의 협업자)
maintain 민감하거나 파괴적인 작업 없이 저장소를 관리하는 프로젝트 관리자 프로젝트실습Ⅰ 팀장(선택)
admin 민감하고 파괴적인 작업을 포함해 프로젝트 전체에 접근하는 사람 교수(이 과목의 소유자)

권한이 하는 일의 차이는 아래와 같다. ○는 할 수 있음이다.

할 수 있는 일 read triage write maintain admin
저장소 보기, 클론, 이슈와 풀 리퀘스트에 코멘트 ○ ○ ○ ○ ○
라벨 붙이기, 이슈와 풀 리퀘스트 닫기·다시 열기·담당자 지정 ○ ○ ○ ○
라벨 만들기와 고치기, 브랜치에 푸시, 풀 리퀘스트 병합 ○ ○ ○
필수 승인 수에 들어가는 리뷰 ○ ○ ○
보호된 브랜치에 푸시 ○ ○
보호 규칙과 규칙 집합 관리, 저장소 설정 변경, 저장소 삭제 ○

표에서 두 가지를 눈여겨본다. 첫째, 리뷰는 read 권한만 있어도 남길 수 있지만, 병합에 필요한 “필수 승인”으로 세어지는 것은 write 이상 권한을 가진 사람의 승인뿐이다[3장 G11]. write가 없는 사람이 승인을 눌러도 필수 승인 수는 채워지지 않는다. 둘째, 보호 규칙을 바꿀 수 있는 것은 admin(개인 계정에서는 소유자)뿐이다. 팀원 모두에게 admin을 주면 누구든 규칙을 끄고 main에 직접 푸시할 수 있으므로, admin은 꼭 필요한 사람에게만 준다. 필요한 만큼만 권한을 주는 이 원칙을 최소 권한의 원칙이라 한다. 3장 0-3에서 본 권한 출력의 "push":true, "admin":false가 협업자인 팀원의 권한이다.

B-6-16. 3장: 이슈 템플릿과 이슈 폼

같은 형식의 이슈를 여러 사람이 쓰면 템플릿이 필요하다. GitHub는 저장소의 .github/ISSUE_TEMPLATE/ 폴더에 든 파일을 이슈 템플릿으로 쓴다[3장 G15]. 템플릿은 기본 브랜치에 병합되어야 동작한다. 팀 실습 저장소에는 키트가 넣어 둔 템플릿 task.md가 있다.

파일: team-lab/.github/ISSUE_TEMPLATE/task.md 
---
name: 작업 이슈
about: 한 사람이 한 브랜치에서 끝낼 수 있는 작업 하나를 적는다
title: "[작업] "
labels: ["작업"]
assignees: []
---

## 무엇을 하는가

(한두 문장. 예: `members/_양식.md`를 복사해 내 소개 파일을 추가한다)

## 왜 하는가

(이 작업이 필요한 까닭. 관련 이슈가 있으면 `#번호`로 적는다)

## 완료 조건

- [ ] (관찰할 수 있는 결과. 예: `members/<아이디>.md`가 main에 있다)
- [ ] 풀 리퀘스트가 승인을 받아 병합되었다

--- 사이의 부분은 YAML 머리말(front matter)이다. name과 about은 이슈를 만들 때 고르는 화면에 보이는 이름과 설명이고, title, labels, assignees는 새 이슈에 미리 채워지는 값이다. GitHub Docs는 템플릿 이름이 세 글자보다 길어야 목록에 나타난다고 적는다[3장 G15]. 「작업」(두 글자) 대신 「작업 이슈」로 지은 까닭이다. 본문의 - [ ]는 체크박스이며, 이슈 화면에서 눌러 표시할 수 있다.

같은 폴더의 config.yml은 템플릿 고르는 화면을 설정한다.

파일: team-lab/.github/ISSUE_TEMPLATE/config.yml 
blank_issues_enabled: false
contact_links:
  - name: 수업 질문
    url: https://docs.github.com/en/issues
    about: 저장소 작업이 아닌 질문은 수업 시간에 하거나 교수에게 직접 묻는다. 이 링크는 GitHub 이슈 문서다.

blank_issues_enabled: false는 템플릿 없이 빈 이슈를 만드는 선택지를 숨긴다. 다만 write 이상 권한자에게는 「Blank issue」가 “Maintainers only” 표시와 함께 계속 보이고, read와 triage 권한자에게만 숨겨진다[3장 G15]. contact_links는 이슈 대신 갈 곳(질문 게시판, 보안 신고 창구 등)을 고르는 화면에 링크로 보인다.

마크다운 템플릿 말고 이슈 폼(issue form)도 있다. .yml 파일에 입력 칸을 정의해 웹 화면에 양식으로 보이게 하고, required: true로 필수 입력(예: 재현 방법)을 강제한다. 마크다운 템플릿은 빈칸을 막지 못하지만 만들기 쉽다. GitHub Docs는 2026-11 기준으로 이슈 폼을 공개 미리 보기(public preview)로 표시한다[3장 G15]. 이 과목은 마크다운 템플릿만 쓴다.

[최신 자료 자리: 이슈 폼의 상태와 기본 라벨] 이슈 폼이 아직 공개 미리 보기인지, 기본 라벨 열 개(부록 B-6의 「라벨과 마일스톤」)가 그대로인지. 확인할 곳 docs.github.com의 「Configuring issue templates for your repository」, 「Managing labels」. 2026-11-14 값은 본문과 같다.

B-6-17. 3장: 라벨과 마일스톤

라벨은 이슈와 풀 리퀘스트에 붙이는 꼬리표이다. 새 저장소에는 기본 라벨이 들어 있다. 2026-11 기준 GitHub Docs가 적는 기본 라벨은 accessibility, bug, documentation, duplicate, enhancement, good first issue, help wanted, invalid, question, wontfix이다[3장 G16]. 조직 소유자는 조직의 새 저장소에 들어갈 기본 라벨을 바꿀 수 있다.

라벨은 많을수록 좋지 않다. 라벨은 목록을 걸러 보기 위한 것이므로, 팀이 실제로 걸러 볼 기준만 둔다. 팀 실습 저장소에는 교수가 키트의 도구/labels_lab.tsv에 적힌 일곱 개의 라벨(작업, 문서, 버그, 충돌 실습, 리뷰 필요, 질문, usability)을 미리 만들어 두었다. usability는 13장 9-5에서 사용성 문제를 이 저장소의 이슈로 등록할 때 쓰는 이슈 템플릿(Service_13장/이슈템플릿/usability-problem.md)의 라벨이다. 이 파일은 한 줄에 「이름, 색, 설명」을 탭으로 나누어 적은 것이고, 키트의 labels.sh가 한 줄씩 읽어 gh label create --force(같은 이름이 있으면 고침)를 실행한다. DRY_RUN=1을 붙이면 명령만 보인다. 이 도구는 교수가 저장소를 준비할 때 쓴다. 학습자는 3장 4-4의 따라 하기에서 개인 저장소에 gh label create --force를 한 번 직접 실행한다.

$ DRY_RUN=1 bash labels.sh labels_lab.tsv "$OWNER/$REPO" | head -2
gh label create "작업" --color 1d76db --description "한 브랜치에서 끝낼 수 있는 작업" --force -R 「교수 계정」/ict-aisw-2027-team01-lab
gh label create "문서" --color 0075ca --description "문서의 추가와 수정" --force -R 「교수 계정」/ict-aisw-2027-team01-lab

마일스톤은 마감일이 있는 이슈와 풀 리퀘스트의 묶음이다. 마일스톤 화면에는 설명, 마감일, 완료율, 열린 항목과 닫힌 항목의 수가 보인다[3장 G17]. 프로젝트실습Ⅰ이라면 “중간 발표” 같은 마일스톤을 만들고 그때까지 끝낼 이슈를 묶는다. 완료율은 닫힌 항목의 비율로 계산되므로, 이슈를 닫는 습관이 없으면 마일스톤의 숫자는 의미가 없다.

B-6-19. 3장: AI 도구를 이용한 설명과 리뷰 초안

Claude Code는 터미널에서 git과 gh를 실행할 수 있으므로 풀 리퀘스트를 직접 만들 수도 있다. Claude Code 공식 문서의 일반 작업 흐름에는 “변경을 요약해 달라”, “PR을 만들어 달라”, “보안 개선에 대한 맥락을 더해 PR 설명을 보강해 달라”는 단계가 실려 있고, 만들어진 PR을 제출하기 전에 검토하라는 팁이 함께 있다[3장 C1]. 같은 문서는 Claude가 gh pr create로 PR을 만들면 그 세션이 PR에 연결되어, 나중에 claude --from-pr <번호>로 그 세션을 다시 찾을 수 있다고 적는다. 2026-11 기준 Claude Code(2.1.296)의 명령 목록에는 현재 변경이나 지정한 PR을 검토하는 /code-review(별칭 /review)가 있고, --comment를 붙이면 결과를 GitHub의 PR에 바로 게시한다[3장 C2]. 이 장에서 /code-review는 교수 시연으로만 본다.

[최신 자료 자리: Claude Code의 판과 PR 관련 명령] claude --version, /code-review(별칭 /review)의 옵션, claude --from-pr. 확인할 곳 code.claude.com/docs/en/commands, 같은 곳의 common-workflows. 2026-11-15 값: 2.1.296, 세 가지 모두 문서에 있음.

이 과목에서는 AI 도구에게 초안을 파일로 쓰게 하고, 게시는 사람이 한다. 까닭은 셋이다.

  1. 책임. 리뷰의 승인은 “내가 읽고 확인했다”는 서명이다. AI가 쓴 지적을 확인 없이 게시하면, 틀린 지적에도 내 이름이 붙는다.
  2. 사실과 다른 내용. AI 도구는 diff에 없는 내용(“테스트를 모두 통과했다”, “성능이 개선되었다”)을 그럴듯하게 덧붙이거나, 존재하지 않는 줄을 지적할 수 있다. 1장에서 본 확률적 생성의 성질이다.
  3. 범위. AI 도구는 변경과 관계없는 개선(다른 파일의 문체, 구조 변경)까지 제안하는 경향이 있다. 리뷰는 이 PR의 범위 안에서 한다.

절차는 다음과 같다. 3장 7-3(PR 설명)과 7-4(리뷰)에서 이 절차를 그대로 따른다.

  1. 사람이 git diff main...HEAD 또는 gh pr diff로 변경을 먼저 직접 읽는다.
  2. Claude Code에게 범위(이 diff, 이 템플릿)와 금지 사항(게시하지 말 것, diff에 없는 내용을 쓰지 말 것)을 준 프롬프트로 초안을 ~/ch03-drafts/의 파일에 쓰게 한다.
  3. 사람이 초안의 문장마다 diff의 해당 줄을 찾아 대조하고, 찾지 못한 문장은 지운다.
  4. 사람이 범위 밖의 제안을 지우고, 빠진 것(Closes #n 등)을 더한다.
  5. 사람이 고친 초안을 gh pr create --body-file, gh pr review --body-file로 게시한다. PR 설명의 「AI 도구의 사용」 절에 사용 사실과 사람이 고친 곳을 적는다.

Claude Code가 gh pr create나 git push처럼 원격을 바꾸는 명령을 실행하려 하면, 권한 설정에 따라 실행 전에 확인을 묻는다(2장). 이 장에서는 그 질문에 허용하지 않는다. 프롬프트에서 미리 금지해 두면 질문이 나오는 일 자체가 줄어든다. 초안 폴더 ~/ch03-drafts/는 Claude Code를 시작한 폴더 밖에 있으므로 파일을 쓸 때 확인을 물을 수 있다. 그때는 그 파일 하나에 대해서만 허용한다.

방식마다 잃는 것이 있다. GitHub Docs가 적는 주의 사항을 정리하면 다음과 같다[3장 G8].

B-6-21. 3장: GitHub 웹 편집기를 이용한 해결

간단한 충돌은 GitHub 화면에서도 해결할 수 있다. GitHub Docs가 적는 절차는 다음과 같다[3장 G10].

  1. 충돌이 있는 PR의 아래쪽에서 「Resolve conflicts」를 누른다.
  2. 편집기에 충돌 표시가 든 파일이 열린다. 충돌마다 내 쪽, 상대 쪽, 새 내용 중 하나로 고치고 충돌 표시를 지운다.
  3. 파일의 충돌을 다 고쳤으면 「Mark as resolved」를 누른다. 충돌한 파일이 여럿이면 왼쪽 목록에서 다음 파일을 골라 반복한다.
  4. 「Commit merge」를 누른다. 이 커밋은 PR의 브랜치(head)에 올라간다.
  5. 병합 상자로 돌아와 리뷰를 받고 「Merge pull request」를 누른다.

[그림 자리: GitHub 웹의 충돌 해결 편집기] 「Resolve conflicts」 편집기에서 충돌 표시가 강조된 화면과 「Mark as resolved」 단추. 찍을 곳: GitHub 웹, 시연용 저장소의 충돌한 PR.

웹 편집기로 해결할 수 있는 것은 같은 줄을 서로 다르게 고친 단순한 줄 충돌뿐이다. 수정/삭제 충돌, 이름 바꾸기 충돌 같은 그 밖의 충돌은 로컬에서 해결해야 하며, 그때는 「Resolve conflicts」 단추가 비활성화된다[3장 G10]. 또한 웹에서 해결하면 기준 브랜치 전체가 PR의 브랜치에 병합되고, PR의 브랜치가 보호된 브랜치이면 새 브랜치를 만들어야 한다. 2026-11 기준 문서는 저장소에서 Copilot의 클라우드 에이전트를 켜 둔 경우 병합 상자에 「Fix with Copilot」 단추가 나타난다고 적는다. 이 과목에서는 쓰지 않는다. AI 도구가 충돌을 해결해도 최종 문장을 정하는 판단은 사람이 해야 하기 때문이다.

수정/삭제 충돌은 로컬에서 다음처럼 보인다. 연습용 저장소에서 얻은 출력이다.

$ git merge x
CONFLICT (modify/delete): f.txt deleted in x and modified in HEAD.  Version HEAD of f.txt left in tree.
Automatic merge failed; fix conflicts and then commit the result.
$ git status --short
UD f.txt

UD는 “내 쪽은 고침(U, updated), 상대 쪽은 지움(D, deleted)”이다. 파일을 남길 것이면 git add f.txt, 지울 것이면 git rm f.txt를 한 뒤 커밋한다. 이 판단은 파일의 내용이 아니라 “이 파일이 아직 필요한가”라는 팀의 결정이므로, 지운 사람과 먼저 이야기한다.

B-6-22. 3장: 기본 브랜치 보호의 필요성

지금까지의 규칙(“main에 직접 커밋하지 않는다”, “강제 푸시를 하지 않는다”, “승인을 받은 뒤 병합한다”)은 사람이 지키는 약속이다. 약속은 바쁠 때, 실수할 때, 규칙을 모르는 새 팀원이 왔을 때 깨진다. AI 코딩 도구에게 넓은 권한을 준 경우에도 깨질 수 있다. GitHub는 이 약속의 일부를 저장소가 강제하게 하는 두 가지 장치를 준다. 보호 브랜치 규칙(branch protection rule)과 규칙 집합(ruleset)이다.

보호 규칙이 없는 main에서 일어날 수 있는 사고는 다음과 같다.

사고 결과 막는 규칙
리뷰 없이 main에 직접 푸시 아무도 읽지 않은 변경이 모든 팀원의 기준이 된다 병합 전 풀 리퀘스트 필수
승인 없이 자기 PR을 병합 리뷰 절차가 형식만 남는다 승인 수 필수(1개 이상)
승인 뒤에 몰래 커밋을 더 하고 병합 승인받은 것과 병합된 것이 다르다 새 커밋이 오면 승인 무효, 마지막 푸시에 대한 승인 필수
main에 강제 푸시 남들이 받아 간 커밋이 원격에서 사라진다 강제 푸시 차단
main 삭제 저장소의 기준이 사라진다 삭제 차단
미해결 리뷰 코멘트를 남긴 채 병합 지적이 반영되지 않은 채 들어간다 대화 해결 필수

B-6-23. 3장: 보호 브랜치 규칙의 항목

보호 브랜치 규칙은 브랜치 이름 패턴 하나에 규칙 하나를 건다. GitHub Docs가 적는 주요 항목은 다음과 같다[3장 G9].

항목 하는 일
병합 전 풀 리퀘스트 리뷰 필수 정한 수의 승인이 있어야 병합할 수 있다. 승인은 write 권한자 또는 지정된 코드 소유자의 것이어야 한다
오래된 승인 무효(dismiss stale approvals) 승인 뒤에 diff를 바꾸는 커밋이 오면 승인을 없앤다
코드 소유자 리뷰 필수 바뀐 파일의 코드 소유자(CODEOWNERS 파일에 적힌 사람)가 승인해야 한다
마지막 푸시에 대한 승인 마지막으로 푸시한 사람이 아닌 다른 사람이 승인해야 한다
상태 검사 통과 필수 자동 검사(테스트, 빌드)가 통과해야 한다
대화 해결 필수 모든 리뷰 코멘트의 대화가 해결되어야 한다
선형 기록 필수 병합 커밋을 막는다. squash나 rebase로만 병합할 수 있다
강제 푸시 허용 / 삭제 허용 기본값은 둘 다 막힘이다
우회 금지(do not allow bypassing) 관리자에게도 규칙을 적용한다. 기본값은 관리자 면제이다

두 가지 기본값을 기억한다. 강제 푸시와 브랜치 삭제는 보호 규칙을 거는 순간 기본으로 막힌다. 반면 관리자(admin)는 기본으로 규칙에서 면제된다[3장 G9]. 관리자도 실수하므로, 팀의 저장소에서는 “우회 금지”를 켜는 편이 안전하다.

CODEOWNERS는 .github/CODEOWNERS 파일에 “이 경로의 파일은 이 사람이나 팀이 책임진다”를 적은 것이다. PR이 그 경로를 바꾸면 GitHub가 코드 소유자에게 리뷰를 자동으로 요청한다[3장 G7]. 상태 검사는 GitHub Actions 같은 자동 검사의 결과를 병합 조건으로 삼는 것이며, 「AI에이전트 기획 및 개발」 13장(CI와 배포)에서 다룬다.

B-6-24. 3장: 읽기: 팀 실습 저장소의 규칙과 거부되는 푸시

교수는 팀 실습 저장소의 main에 보호 브랜치 규칙을 걸어 두었다. 「Require a pull request before merging」(승인 1개)과 「Do not allow bypassing the above settings」(우회 금지)를 켜고, 강제 푸시와 삭제는 기본값대로 막았다. 병합 방식은 저장소 설정에서 merge commit 하나만 허용한다. 규칙을 설정하는 화면(Settings → Branches)은 소유자에게만 보이므로 교수가 시연으로 보인다.

규칙의 세부는 협업자에게 보이지 않지만, main이 보호되어 있는지는 팀 실습 저장소 폴더에서 볼 수 있다. 아래는 실제 GitHub에서 실행하지 않은 예시이다.

(예시)
$ gh api "repos/$OWNER/$REPO/branches/main" --jq .protected
true

보호된 main에 직접 푸시하면 GitHub가 푸시를 거부한다. 거부 메시지는 대략 다음과 같은 모양이라고 알려져 있다. 수업에서는 교수가 시연용 저장소에서 보이며, 학습자가 팀 저장소의 main에 직접 푸시해 보지는 않는다.

(예시)
remote: error: GH006: Protected branch update failed for refs/heads/main.
remote: error: Changes must be made through a pull request.
 ! [remote rejected] main -> main (protected branch hook declined)

부록 B-6의 「읽기: 푸시 거부」의 [rejected] (fetch first)는 “먼저 받아 오라”는 Git의 거부였고, 이것은 “이 브랜치에는 풀 리퀘스트로만 들어올 수 있다”는 저장소 규칙의 거부이다. 받아 와도 해결되지 않는다. 브랜치를 만들어 PR을 연다. 3장 7절의 핵심 실습에서 승인 없는 병합이 거부되는 것도 이 보호 규칙 때문이다.

B-6-25. 3장: 대안 절차: 단독 수행

결석이나 팀 구성 문제로 혼자 남으면, 개인 계정의 비공개 저장소 ch03-solo를 키트의 team-lab/으로 만들고 내 PC의 두 클론 ~/solo/a, ~/solo/b로 두 사람을 흉내 낸다(user.name만 다르다). 다른 점은 승인뿐이다. 자기 PR은 승인할 수 없으므로(3장 5-1) 교수와 정한 한 사람을 협업자로 초대해 리뷰를 받는다.

터미널 
mkdir -p ~/solo && cd ~/solo
cp -r ~/kits/Service_03장/team-lab a
cd a
git init -b main
git add .
git commit -m "팀 실습 저장소의 시작 파일"
gh repo create ch03-solo --private --source . --remote origin --push
cd ~/solo
git clone "https://github.com/$(gh api user --jq .login)/ch03-solo.git" b
git -C a config user.name "개발자A"
git -C b config user.name "개발자B"

a에서 A 역할을, b에서 B 역할을 하고, A의 PR을 먼저 병합한 뒤 B의 PR에서 충돌을 해결한다. 점검은 --lab ~/solo/a로 한다. GitHub에 접속할 수 없으면 3장 6절의 연습 저장소로 충돌 해결까지만 하고, PR 부분은 다음 수업(4장)의 시작 전에 교수와 정한 시간에 보충한다.
