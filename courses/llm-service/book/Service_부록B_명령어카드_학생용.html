[부록 B] 명령어 카드

2027학년도 「LLM 서비스 개발」의 준비 중인 교재입니다. 편집 상태를 검토하기 위해 미리 공개한 것으로, 수업 전에 내용과 순서가 바뀔 수 있습니다.

「LLM 서비스 개발」 1~13장의 공통 부록 · 2026-11 기준(Windows 11의 Git Bash, Claude Code 2.1.296, git 2.55, GitHub CLI 2.88, 파이썬 3.13에서 확인)

자주 쓰는 명령을 도구별로 모은 참조표이다. 각 장은 명령을 처음 쓸 때 그 뜻을 설명하고, 이후에는 이 카드를 가리킨다. 장에서 「읽기」로 줄인 명령(학습자가 치지 않고 출력만 읽는 명령)도 이 카드에 실행 예와 함께 모았다. 연습용 저장소에서 직접 쳐 보고 싶으면 이 카드를 따라 한다.

명령을 어디에 입력하는가가 첫 번째 구분이다. 셸 명령은 [터미널](내 PC의 VS Code 통합 터미널. Windows는 Git Bash, macOS는 기본 셸)에, 슬래시 명령과 프롬프트는 [Claude Code] 입력 창에 넣는다(부록 A의 꼬리표). 출력 예시는 따로 밝히지 않으면 집필용 Windows 11 PC의 Git Bash에서 시험용 저장소로 실행한 결과이다(2026-11-17). 커밋 번호, 사용자 이름, 경로는 사람마다 다르다.

카드 도구 입력하는 곳
B-1 Claude Code 셸(시작 명령), Claude Code 입력 창(슬래시 명령, 단축키)
B-2 Git 셸
B-3 GitHub CLI(gh) 셸
B-4 셸 기본 명령 셸
B-5 파이썬, 테스트, 로컬 서버 셸

도구는 판이 바뀌면 명령과 화면이 달라진다. 이 카드와 실제 동작이 다르면 각 도구의 도움말(claude --help, Claude Code 안의 /help, git help 명령, gh 명령 --help)과 공식 문서가 우선한다.

[최신 자료 자리: 이 카드가 확인한 도구의 판] 확인할 곳: 내 PC의 claude --version, git --version, gh --version, python --version. 2026-11-17 확인 값(집필용 PC): Claude Code 2.1.296, git 2.55.0.windows.5, GitHub CLI 2.88.1(2026-03-12 배포), 파이썬 3.13.7, curl 8.21.0. 내 PC의 판이 다르면 아래 자리 표시의 문서에서 명령과 화면을 다시 확인한다.

B-1. Claude Code 명령 카드

B-1-1. 셸에서 시작하는 명령

터미널 
claude
claude "이 폴더의 구조를 설명하라"
claude -c
claude -r
명령 뜻
claude 지금 폴더를 작업 폴더로 대화형 세션을 시작한다
claude "요청" 첫 요청을 넣은 채 대화형 세션을 시작한다
claude -c (--continue) 지금 폴더에서 가장 최근의 대화를 이어 간다
claude -r (--resume) 지난 대화 목록을 열어 골라 이어 간다. 뒤에 세션 ID나 검색어를 줄 수 있다
claude -n 이름 (--name) 세션에 이름을 붙여 시작한다. 이름은 입력 창, /resume 목록, 터미널 제목에 보인다
claude --permission-mode plan 계획 모드로 시작한다(B-1-6)
claude --model 모델 이 세션에서 쓸 모델을 정해 시작한다
claude --version (-v) 버전을 출력한다
claude doctor 설치와 설정 파일을 진단한다(읽기 전용)
claude update 지금 바로 최신판으로 업데이트한다
claude auth login / logout / status 셸에서 로그인, 로그아웃, 인증 상태 확인(부록 A-8)
claude --help 모든 옵션을 보여 준다
  • claude -p "요청"(--print)은 대화 화면 없이 한 번 답하고 끝내는 헤드리스 모드이다. 스크립트와 자동화에 쓰며, 이 과목의 실습에서는 쓰지 않는다(「AI에이전트 기획 및 개발」에서 다룬다).
  • --dangerously-skip-permissions는 모든 권한 확인을 건너뛴다. 도움말이 인터넷이 막힌 격리 환경에서만 쓰라고 경고하는 옵션이므로 이 과목에서는 쓰지 않는다(claude --help, 2026-11-14 확인).

[최신 자료 자리: claude 시작 옵션] -c, -r, -n, --permission-mode의 값, --model, auth·doctor·update. 확인할 곳: 내 PC의 claude --help, https://code.claude.com/docs/en/cli-reference. 마지막으로 확인한 날짜와 값: 2026-11-17, Claude Code 2.1.296의 도움말이 본문과 같다. 수업 전에 다시 확인한다.

B-1-2. 슬래시 명령

Claude Code 입력 창의 맨 앞에 /를 치면 명령 목록이 뜨고, 글자를 더 치면 목록이 좁혀진다[C1]. 명령은 메시지의 맨 앞에 있을 때만 명령으로 인식되며, 뒤에 붙인 글은 그 명령의 인자가 된다[C1]. 아래 표는 2026-11-14의 공식 문서에서 확인한 것이다.

시작과 상태

명령 뜻
/help 도움말과 쓸 수 있는 명령 목록. 막히면 여기서 시작한다
/status 설정 화면의 Status 탭. 버전, 모델, 계정, 연결 상태, 읽은 설정 파일을 보여 준다
/login / /logout Anthropic 계정에 로그인 / 로그아웃
/model [모델] 모델을 바꾸고 다음 세션의 기본값으로 저장한다. 목록에서 s를 누르면 이 세션에만 적용한다
/config 설정 화면(테마, 모델, 출력 형식 등)
/doctor 설치, 설정, CLAUDE.md의 문제를 진단하고 고칠 방법을 제안한다
/exit (/quit) Claude Code를 끝낸다

대화와 컨텍스트

명령 뜻
/clear (/reset, /new) 대화를 비우고 새로 시작한다. 이전 대화는 /resume으로 다시 열 수 있다
/compact [지시] 지금까지의 대화를 요약해 컨텍스트를 비운다. 요약에 남길 내용을 지시로 줄 수 있다
/context 컨텍스트 창이 얼마나 차 있는지 색 격자로 보여 준다
/usage (/cost) 세션의 비용, 요금제의 사용 한도, 활동 통계
/resume [세션] 지난 대화를 ID나 이름으로, 또는 목록에서 골라 이어 간다
/rename [이름] 지금 세션의 이름을 바꾼다. 이름을 주지 않으면 대화 내용으로 지어 준다
/branch [이름] 지금 시점에서 대화의 갈래를 만들어 다른 방향을 시도한다. 원래 대화는 /resume으로 돌아갈 수 있다
/btw [질문] 대화 기록에 남기지 않는 곁가지 질문을 한다
/export [파일이름] 대화를 일반 텍스트로 내보낸다. 실습 기록의 증빙으로 쓴다
/copy [N] 마지막(또는 N번째 전) 응답을 클립보드에 복사한다. 목록에서 w를 누르면 파일로 쓴다

작업의 통제

명령 뜻
/plan [설명] 계획 모드로 들어간다. 설명을 주면 그 일로 바로 계획을 시작한다(B-1-6)
/permissions 도구 사용의 허용, 확인, 거부 규칙을 보고 고친다
/rewind (/checkpoint, /undo) 대화와 코드를 앞 시점으로 되감거나, 한 시점부터 요약한다(B-1-7)
/diff 작업 트리의 변경(Claude가 지금까지 고친 것 포함)을 검토한다
/init 프로젝트를 분석해 CLAUDE.md 초안을 만든다(2장)
/memory CLAUDE.md 파일들을 편집하고 자동 메모리를 켜고 끈다
/add-dir 경로 이 세션에서 파일을 다룰 폴더를 더한다
/cd 경로 대화를 유지한 채 작업 폴더를 옮긴다

검토

명령 뜻
/review 지금의 변경(또는 지정한 풀 리퀘스트, 브랜치, 경로)을 코드 검토한다. /code-review의 별칭이다
/security-review 지금 브랜치의 변경을 보안 관점(주입, 인증, 정보 노출)에서 검토한다. 원격 origin이 있어야 한다

이 밖에 /theme(색 테마), /terminal-setup(VS Code 등에서 Shift+Enter 줄바꿈 설정), /tasks(백그라운드 작업 목록), /hooks, /mcp, /agents가 있다. 뒤의 세 가지는 「AI에이전트 기획 및 개발」에서 다룬다.

[최신 자료 자리: 슬래시 명령의 목록과 별칭] 확인할 곳: Claude Code 안의 /help, https://code.claude.com/docs/en/commands. 마지막으로 확인한 날짜와 값: 2026-11-14, 위 네 표의 명령과 별칭(/clear의 /reset·/new, /rewind의 /checkpoint·/undo, /usage의 /cost, /review는 /code-review의 별칭). 명령은 판마다 더해지거나 이름이 바뀌므로 수업 전에 다시 확인한다.

B-1-3. 단축키

키 뜻
Esc 진행 중인 응답이나 도구 실행을 멈춘다. 그때까지 한 일은 남고, 다음 지시를 기다린다. 열린 대화 상자는 닫는다
Esc Esc 입력 창이 비어 있으면 되감기 메뉴를 연다. 입력 중이면 쓰던 글을 지운다(↑로 되살린다)
Shift+Tab 권한 모드를 돌아가며 바꾼다(B-1-5)
Ctrl+C 실행 중이면 중단한다. 실행 중이 아니면 첫 번째는 입력을 지우고, 두 번째는 Claude Code를 끝낸다
Ctrl+D 두 번 누르면 Claude Code를 끝낸다. 입력 창에 글이 있으면 커서 뒤 글자를 지운다
↑ / ↓ 이전 입력을 불러온다
Ctrl+R 이전 입력을 검색한다
Ctrl+O 도구 사용의 상세 기록(트랜스크립트)을 켜고 끈다
Ctrl+T Claude의 할 일 목록을 보이거나 숨긴다
Ctrl+B 실행 중인 셸 명령을 백그라운드로 보낸다
Ctrl+G 입력 중인 프롬프트를 외부 편집기에서 연다. 긴 프롬프트를 쓸 때 쓴다
Ctrl+L 화면을 다시 그린다(화면이 깨졌을 때)
Ctrl+S 입력 중인 글을 잠시 치워 두고, 빈 입력 창에서 다시 누르면 되살린다
Alt+P 입력을 지우지 않고 모델을 바꾼다(Windows·리눅스)
? 입력 창이 비어 있을 때 단축키 도움말을 연다

여러 줄을 입력하는 방법은 다음과 같다. \를 친 뒤 Enter는 모든 터미널에서 되고, Ctrl+J도 설정 없이 된다. Shift+Enter는 Windows Terminal 등 일부 터미널에서 바로 되고, VS Code 통합 터미널에서는 /terminal-setup을 한 번 실행하면 된다[C2].

[최신 자료 자리: 단축키와 여러 줄 입력] 확인할 곳: Claude Code의 빈 입력 창에서 ?, https://code.claude.com/docs/en/interactive-mode. 마지막으로 확인한 날짜와 값: 2026-11-14, 위 표의 키(문서 기준. Git Bash와 VS Code 통합 터미널에서 실제로 눌러 보지는 않았다). 수업 전에 다시 확인한다.

B-1-5. 권한 모드

권한 모드는 Claude가 묻지 않고 할 수 있는 일의 범위를 정한다[C3]. 화면 아래쪽의 모드 표시로 지금 모드를 본다.

모드(설정 값) 묻지 않고 하는 일 쓰는 때
Manual (default) 읽기만 모든 행동을 사람이 하나씩 검토할 때. 이 과목의 기본
acceptEdits 읽기, 작업 폴더 안의 파일 수정, 흔한 파일 명령(mkdir, touch, mv, cp 등) 검토 중인 코드를 반복해 고칠 때
plan 읽기(계획만 세우고 고치지 않는다) 고치기 전에 조사하고 계획할 때
auto 모든 일, 다만 분류기가 뒤에서 행동을 검토한다 긴 작업. 계정과 모델에 따라 쓸 수 없을 수 있다
dontAsk 미리 허용한 도구만. 물어야 할 것은 거부 자동화 스크립트
bypassPermissions 모든 일 격리된 컨테이너에서만. 이 과목에서는 쓰지 않는다

Shift+Tab을 누를 때마다 모드가 다음 순서로 돈다. auto는 쓸 수 있는 계정과 모델일 때만 순환에 들어가고, dontAsk는 순환에 나타나지 않는다[C3].

B-1-7. 되감기(체크포인트)

Claude Code는 프롬프트를 보낼 때마다 그 직전의 코드 상태를 체크포인트로 남긴다[C5]. /rewind를 실행하거나 빈 입력 창에서 Esc를 두 번 누르면 되감기 메뉴가 열리고, 되돌아갈 프롬프트를 고른 뒤 다음 가운데 하나를 고른다.

선택 뜻
Restore code and conversation 코드와 대화를 모두 그 시점으로 되돌린다
Restore conversation 대화만 되돌리고 코드는 지금 그대로 둔다
Restore code 코드만 되돌리고 대화는 그대로 둔다
Summarize from here 그 시점 뒤의 대화를 요약해 컨텍스트를 비운다
Summarize up to here 그 시점 앞의 대화를 요약한다
Never mind 아무것도 하지 않고 돌아간다

되감기는 Git을 대신하지 않는다. 공식 문서가 밝히는 한계는 다음과 같다[C5].

한계 뜻 대신 쓰는 것
셸 명령의 변경 Claude의 편집 도구가 한 번도 고치지 않은 파일을 셸 명령(rm, mv, 스크립트)이 바꾼 것은 되돌리지 않는다 git restore
바깥의 변경 사람이 편집기로 고친 것, 다른 세션이 고친 것은 보통 추적하지 않는다 git diff로 확인, git restore
보관 기간 세션의 파일 스냅숏은 기본적으로 약 30일 뒤 정리된다 커밋
기록과 협업 세션 단위의 빠른 복구용이다 커밋, 브랜치, 원격 저장소

이 과목의 규칙: Claude Code에게 일을 맡기기 전에 git status가 깨끗한지 보고, 결과를 확인한 뒤 커밋한다. 되감기는 커밋 사이의 시행착오를 되돌리는 데 쓴다.

[그림 자리: 되감기 메뉴] 빈 입력 창에서 Esc를 두 번 눌러 연 프롬프트 목록과, 하나를 고른 뒤 나오는 여섯 선택지(Restore code and conversation 등). 찍을 곳: 내 PC의 Claude Code에서 파일을 한 번 고치게 한 뒤.

[최신 자료 자리: 되감기의 선택지와 보관 기간] 확인할 곳: https://code.claude.com/docs/en/checkpointing. 마지막으로 확인한 날짜와 값: 2026-11-14, 선택지 여섯 개와 세션 스냅숏의 보관 기간 약 30일. 수업 전에 다시 확인한다.

+로 시작하는 줄이 더해진 줄, -로 시작하는 줄이 지워진 줄이다. HEAD는 지금 브랜치의 마지막 커밋이고, HEAD~1은 그 하나 앞이다.

바뀐 낱말만 보기. 표의 한 칸이나 문장의 숫자 하나를 고쳤을 때 git diff는 줄 전체를 지우고 더한 것으로 보인다. --word-diff는 바뀐 낱말만 [-지운 것-]{+더한 것+}으로 보인다. --no-index를 붙이면 저장소에 없는 두 파일도 같은 방식으로 견준다(4장 10-6, 8장 10-2).

git diff --no-index --word-diff r1.md r2.md
| 주색 | [-#1d4ed8-]{+#1e40af+} |
diff --git a/r1.md b/r2.md
index 9546226..7fb8e8e 100644
--- a/r1.md
+++ b/r2.md
@@ -1,2 +1,2 @@
공고 3건
마감 [-2건-]{+1건+}

git diff --no-index는 두 파일이 다르면 종료 코드 1로 끝난다. 오류가 아니다.

태그의 두 번호. 주석 태그(git tag -a)는 태그 자체가 하나의 객체이므로 번호가 둘이다. 태그가 가리키는 커밋의 번호는 git log -1 --format=%h 태그로 보고, git rev-parse --short 태그는 태그 객체의 번호를 보인다(12장 9-3).

$ git log -1 --format=%h spec-v1
2ba6d6e
$ git rev-parse --short spec-v1
4288231

파일의 지문. git hash-object 파일은 파일 내용으로 계산한 번호를 보인다. 내용이 한 글자라도 다르면 번호가 다르다. 두 파일이 같은지, 복사한 뒤 바뀌지 않았는지를 볼 때 쓴다(5장 3-7). Windows에도 있으므로 md5sum 대신 쓴다.

$ cp notes.md n2.md && git hash-object n2.md

B-2-4. 되돌리기

상황 명령 기록이 바뀌는가
고친 파일을 마지막 커밋 상태로 되돌린다(고친 내용은 사라진다) git restore 파일 아니오
스테이징만 취소한다(파일 내용은 그대로) git restore --staged 파일 아니오
파일을 특정 커밋의 상태로 가져온다 git restore --source=커밋 파일 아니오
실수로 추적하게 된 파일을 추적에서만 뺀다(.env) git rm --cached 파일 다음 커밋에서
이미 커밋한 것을 취소하는 새 커밋을 만든다 git revert 커밋 새 커밋이 더해진다
마지막 커밋의 메시지를 고친다(푸시하기 전만) git commit --amend -m "메시지" 마지막 커밋이 바뀐다
마지막 커밋을 풀어 변경을 스테이징 상태로 돌린다(푸시하기 전만) git reset --soft HEAD~1 마지막 커밋이 사라진다
마지막 커밋을 풀어 변경을 작업 트리에만 남긴다(푸시하기 전만) git reset HEAD~1 (--mixed) 마지막 커밋이 사라진다
HEAD가 지나온 자리를 본다 git reflog 아니오

  • --soft는 변경을 스테이징된 채(M), 모드를 생략한 reset(--mixed)은 작업 트리에만(M) 남긴다.
  • git reflog는 HEAD가 지나온 자리를 최근 것부터 보인다. 풀어 버린 커밋(416e22e)도 여기서 번호를 찾아 되찾을 수 있다. reflog는 내 컴퓨터에만 있고 일정 기간 뒤 정리된다.

주의할 점은 다음과 같다.

  • 푸시한 커밋은 revert로 되돌린다. --amend와 reset은 기록을 고쳐 쓰므로, 이미 남과 나눈 커밋에 쓰면 다른 사람의 기록과 어긋난다.
  • git restore 파일로 사라진 변경은 Git으로 되살릴 수 없다. 확실하지 않으면 먼저 git diff로 무엇이 사라지는지 본다.
  • git reset --hard는 커밋하지 않은 변경까지 지운다. 이 과목의 개인 실습 저장소에서는 쓰지 않는다(2장 9-3).
  • Claude Code의 되감기(B-1-7)와 Git의 되돌리기는 대상이 다르다. 셸 명령이 바꾼 파일과 커밋한 뒤의 상태는 Git으로 되돌린다.

브랜치 목록을 본다 git branch (원격 포함: git branch -a)
새 브랜치를 만들고 옮겨 간다 git switch -c 브랜치

git branch의 표시: *는 지금 브랜치, +는 다른 작업 트리(B-2-8)에 꺼내져 있는 브랜치이다.

$ git check-ref-format --branch "3 add member"
fatal: '3 add member' is not a valid branch name
$ git check-ref-format --branch "feature..x"
fatal: 'feature..x' is not a valid branch name

한 커밋으로 합치기와 버리기. --squash는 브랜치의 변경을 스테이징만 하고 커밋은 하지 않는다. 이어서 커밋하면 브랜치의 여러 커밋이 main에 커밋 하나로 들어간다. GitHub의 「Squash and merge」와 같은 결과이다(3장 6절). 이렇게 합친 브랜치는 Git이 병합된 것으로 보지 않으므로 -d가 거절하고, 버릴 때는 -D를 쓴다.

Deleted branch 3-try (was 45b9f55).

B-2-7. 충돌

두 브랜치가 같은 파일의 같은 줄을 다르게 고쳤으면 Git은 자동으로 합치지 못하고 충돌을 알린다. 충돌은 오류가 아니라 사람이 골라야 하는 자리이다(3장).

$ git merge feature/a
Auto-merging README.md
CONFLICT (content): Merge conflict in README.md
Automatic merge failed; fix conflicts and then commit the result.
$ git status --short
UU README.md

파일 안에는 두 판이 표시와 함께 들어 있다.

파일: README.md 
<<<<<<< HEAD
# 실습
B안
=======
# 실습
A안
>>>>>>> feature/a
표시 뜻
<<<<<<< HEAD ~ ======= 지금 브랜치(합치는 쪽)의 내용
======= ~ >>>>>>> 브랜치 합쳐 오는 브랜치의 내용

해결 순서는 다음과 같다.

  1. git diff --name-only --diff-filter=U로 충돌한 파일을 찾는다.
  2. 파일을 편집기에서 열어 남길 내용으로 고치고, 세 가지 표시 줄을 모두 지운다.
  3. git add 파일로 해결했음을 알린다.
  4. git commit -m "충돌 해결: ..."으로 병합을 마친다.
  5. 해결을 포기하고 병합 전으로 돌아가려면 git merge --abort를 실행한다.
$ git add README.md
$ git commit -m "충돌 해결: A안과 B안 합침"
$ git log --oneline --graph
*   308eb52 충돌 해결: A안과 B안 합침
|\
| * 37401b3 A안
* | c7b9186 B안
|/
* 2d6f6f2 Revert "README 추가"

(이 절의 출력은 2026-11-14에 git 2.55의 시험용 저장소에서 얻은 것이다.) Claude Code에게 충돌 해결을 맡길 때도, 어느 쪽 내용을 남길지는 사람이 정해 지시하고, 결과를 git diff로 확인한 뒤 커밋한다.

B-2-8. 작업 트리(worktree)

작업 트리는 한 저장소의 브랜치 여러 개를 서로 다른 폴더에 동시에 꺼내 두는 기능이다. 12장은 Orca가 이 기능으로 변형마다 작업 공간을 만든다(부록 A-20). Orca 없이 명령으로 할 때와, Orca가 만든 것을 확인할 때 쓴다(12장 3-2, 3-5).

echo
