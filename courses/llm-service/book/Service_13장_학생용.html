사용성 평가와 서비스 개선

2027학년도 「LLM 서비스 개발」의 준비 중인 교재입니다. 편집 상태를 검토하기 위해 미리 공개한 것으로, 수업 전에 내용과 순서가 바뀔 수 있습니다.

학사 15주차 · 교재 13 · 5부 평가

앞 장에서는 하나의 명세로 대화형과 양식형 두 구현을 만들고, 기준표로 견주어 하나를 병합하였다. 그 과정에서 명세가 정하지 않은 빈틈을 찾아 보강하였다. 그러나 기준표의 항목(명세 충족, 자동 검사, 응답 시간, 호출 비용)은 모두 만든 사람이 매긴 것이다. 사용자가 그 화면에서 실제로 목표를 이루는지는 아직 아무도 확인하지 않았다.

이 장은 과목의 마지막 단계인 평가를 다룬다. 동료가 만든 jobprep을 두 가지 방법으로 평가한다. 하나는 평가자가 원칙(휴리스틱)에 비추어 화면을 검토하는 휴리스틱 평가이고, 다른 하나는 다른 팀의 수강생이 과업 세 개를 직접 수행하는 것을 관찰하는 사용성 테스트이다. 테스트 뒤에는 SUS 설문으로 주관적 만족을 잰다. 찾은 문제는 심각도와 빈도로 줄을 세우고, 상위 세 개를 팀 실습 저장소의 이슈로 등록한다. 그중 하나 이상은 명세를 먼저 고치고 구현을 바꾸어 풀 리퀘스트로 올리고, 리뷰를 받아 병합한다.

이 장에서 만드는 것은 하나이다. 동료 평가에서 시작해 병합된 개선 풀 리퀘스트로 끝나는 한 바퀴이다. 이것을 하는 11절이 핵심 실습이고, 해결할 문제는 평가에서 찾은 상위 문제 하나를 명세와 구현에서 고쳐, 리뷰어가 재현 절차로 다시 확인했을 때 그 문제가 사라지게 하는 것이다. 그 흔적으로 jobprep/docs/평가/의 문서 세 개(휴리스틱.md, 사용성테스트.md, SUS.md), 이슈 세 개, 병합된 풀 리퀘스트 하나가 남는다. 1~10절의 이론과 두 따라 하기(4-4, 8-4)가 그 실습의 기준과 도구를 준비한다. 프로젝트실습Ⅰ에서 팀의 프로덕트를 출시 전에 점검할 때 같은 절차와 양식을 그대로 쓴다.

마지막 장이므로 끝에 과목 전체를 정리한다. 4장의 조사에서 13장의 평가까지 각 장이 남긴 산출물이 어떻게 이어지는지를 한 장의 지도로 보이고, 다음 학기 「AI에이전트 기획 및 개발」이 이 산출물을 어떻게 이어받는지를 짧게 적는다.

학습 목표

  • 사용성을 정의하고 측정 지표로 바꾼다. ISO 9241-11의 효과성, 효율성, 만족을 과업 성공 수준, 소요 시간과 오류 수, SUS 점수로 옮긴다.
    • 예시: “요약 기능이 쓰기 쉽다”를 “참가자 3명 중 몇 명이 요약의 근거를 제한 시간 안에 확인했는가”로 바꾼다.
    • 활용: 프로젝트실습Ⅰ의 출시 기준을 “편리하다”가 아니라 측정할 수 있는 문장으로 쓴다.
  • 휴리스틱 평가를 수행하고 결과를 통합한다. 평가자 두 명 이상이 독립적으로 평가한 뒤 기록을 합치고, 문제마다 심각도를 매긴다.
    • 예시: 두 평가자의 기록 14줄을 중복을 합쳐 문제 10개로 정리하고, 의견이 갈린 등급을 근거와 함께 남긴다.
    • 활용: 사용자를 모으기 어려운 단계에서 화면 설계의 결함을 먼저 걸러 낸다.
  • 과업 기반 사용성 테스트를 설계하고 진행한다. 과업 시나리오, 성공 기준, 진행자 대본, 관찰 기록을 갖추고 사고 발화법으로 진행한다.
    • 예시: “일주일 안에 마감하는 서울 지역 백엔드 공고를 골라 지원할 목록에 넣는다”처럼 메뉴 이름을 쓰지 않은 과업 카드를 만든다.
    • 활용: 팀 프로젝트의 중간 발표 전에 다른 팀원에게 15분짜리 테스트를 돌린다.
  • 평가 결과를 이슈와 명세 변경과 풀 리퀘스트로 잇는다. 문제를 재현 절차, 근거, 관련 요구 ID가 있는 이슈로 쓰고, 명세를 먼저 고친 뒤 구현을 바꾼다.
    • 예시: 이슈 #1에 대해 REQ-100을 명세에 넣고, 같은 풀 리퀘스트에서 app.js를 고쳐 Closes #1로 닫는다.
    • 활용: 평가가 보고서로 끝나지 않고 저장소의 변경 이력으로 남는다.

0. 시작하기

설치, 로그인, 키트 저장소의 클론, 가상 환경은 부록 A(A-7, A-8, A-12, A-13), 매 수업의 시작 순서는 A-21을 따른다. 작업은 VS Code의 통합 터미널 두 개(A-4-3)에서 한다. 하나는 명령을 치는 [터미널](Windows는 Git Bash, macOS는 기본 터미널), 하나는 웹이나 API 서버를 띄워 두는 서버용 터미널이다. 둘 다 가상 환경을 켠다.

  • 평가하는 곳. 평가 대상은 모두 각자의 PC에서 띄운다. 동료의 프로덕트도 팀 실습 저장소에서 동료의 브랜치를 받아 내 PC에서 띄운다(0-3, 11-2). 웹은 8100, API는 8000이다(부록 A-16).
  • 이 장의 실행 상한. 실제 모델은 Claude Code 대화형으로만 부른다. 개선 구현 1회와 고치기 1회까지이고, 관찰 기록의 AI 정리(9-3)는 [선택] 1회까지이다. 평가 대상의 AI 기능은 모의 모드(LLM_FAKE=1)로 쓰며 API 키를 쓰지 않는다.
  • 「읽기」 표시. 꼬리표에 「(읽기)」를 붙인 코드 블록은 따라 치지 않고 읽는다. 따라 치는 명령은 0절, 두 개의 따라 하기(4-4, 8-4), 핵심 실습(11절)에 있다.

0-1. 키트 받기와 도구 테스트

키트 저장소에서 새 키트를 받아(git pull) 홈의 kits/로 복사한다(부록 A-12-3). 키트는 저장소 밖에 두고 커밋하지 않는다. cp -rn의 -n은 이미 있는 파일을 덮어쓰지 않는다.

터미널 
git -C ~/kits-repo pull
mkdir -p ~/kits && cp -rn ~/kits-repo/Service_13장 ~/kits/
ls ~/kits/Service_13장
README.md            SUS_양식.md       기준산출물       심각도기준표.md      참가동의_양식.md
SUS설문_양식.md      과업시나리오_양식.md  도구     이슈템플릿         풀리퀘스트_양식.md
관찰기록_양식.md      사용성테스트_양식.md  진행자대본_양식.md  휴리스틱통합_양식.md  휴리스틱평가_양식.md

이 장에서 쓸 이름 두 개를 환경 변수로 정해 둔다. 팀 이름은 3장에서 만든 팀 실습 저장소 「팀」-lab의 앞부분이다. 터미널을 새로 열면 두 변수가 사라지므로, 터미널을 열 때마다 두 줄을 다시 실행한다.

터미널 
export TEAM=「팀 이름」          # 예: team3  →  저장소 이름 team3-lab
export ME=「내 GitHub 아이디」
echo "$TEAM-lab / $ME"

키트의 계산 도구 두 개(sus.py, aggregate.py)와 그 테스트를 돌려 본다. 이 장의 수치는 모두 이 도구로 낸다. 도구는 표준 라이브러리만 쓰고, 테스트에만 pytest가 필요하다. 가상 환경은 저장소 맨 위의 ~/llm-service-lab/.venv 하나이다(부록 A-13).

터미널 
source ~/llm-service-lab/.venv/Scripts/activate     # macOS: source ~/llm-service-lab/.venv/bin/activate
cd ~/kits/Service_13장/도구
python -m pip install -q -r requirements.txt
python -m pytest -q tests
.....................                                                    [100%]
21 passed in 0.61s

위 출력은 집필용 Windows PC의 Git Bash에서 얻은 것이다(2026-11-17, 파이썬 3.13.7, pytest 9.2.0). No module named 'pytest'가 나오면 가상 환경이 켜지지 않은 것이다.

0-2. 평가 대상의 확인

평가 대상은 12장에서 병합한 jobprep/이다. 6장부터 쌓은 명세서와 화면 명세, 9~11장의 웹과 API가 들어 있어야 한다.

터미널 
cd ~/llm-service-lab
git status --short
git log --oneline -3
ls jobprep jobprep/docs jobprep/docs/설계
a41c9e2 (HEAD -> main) 12장: variant-form 병합, 명세 빈틈 2건 보강
...
README.md  api  docs  prompts  rag  web
요구사항명세서.md  인수조건.md  프롬프트비교.md  검색평가.md  비교구현.md  설계  추적표.md

1. 사용성의 정의와 측정

1-1. ISO 9241-11의 정의

사용성(usability)은 국제 표준 ISO 9241-11:2018의 3.1.1에 정의되어 있다[U1]. 뜻을 옮기면 “특정한 사용자가 특정한 사용 맥락에서 특정한 목표를 이루기 위해 시스템, 제품, 서비스를 효과적이고 효율적이며 만족스럽게 사용할 수 있는 정도”이다. 이 정의에서 눈여겨볼 것은 「특정한」이라는 말이 세 번 나온다는 점이다. 사용성은 제품 혼자 가진 성질이 아니다. 누가, 무엇을 하려고, 어떤 환경에서 쓰는가가 정해져야 비로소 잴 수 있다. 같은 jobprep도 밤에 휴대폰으로 공고를 훑는 서지후(페르소나 PS-1)와 공고문의 자격 요건을 하나씩 해석해야 하는 임하람(PS-2)에게 사용성이 다르다.

표준은 세 요소를 따로 정의한다[U1].

요소 표준의 정의 (뜻을 옮김) 풀어 쓰면 잡프렙에서 재는 것
효과성 (effectiveness, 3.1.12) 사용자가 정해진 목표를 이루는 정확성과 완전성 목표를 얼마나 정확하고 빠짐없이 이루었는가 과업 성공 수준(완전성공, 사소한 문제, 큰 문제, 실패)
효율성 (efficiency, 3.1.13) 얻은 결과에 견준, 쓴 자원 결과를 얻는 데 든 자원. 표준은 시간, 사람의 노력, 비용, 재료를 예로 든다 과업 소요 시간, 오류 수, (LLM 기능이면) 호출 횟수
만족 (satisfaction, 3.1.14) 사용에서 비롯된 신체적, 인지적, 정서적 반응이 사용자의 필요와 기대를 충족하는 정도 쓰고 난 뒤의 느낌이 기대에 맞는가 SUS 점수, 과업 직후의 쉬움 평가, 발언

만족의 정의에는 「기대」가 들어 있다. 표준은 사용 전의 기대가 실제 사용의 만족에 영향을 줄 수 있다고 덧붙인다[U1]. AI 기능에서 이 점이 특히 중요하다. “무엇이든 정확히 답한다”고 약속한 화면은 같은 답을 내도 약속하지 않은 화면보다 만족이 낮아질 수 있다(5절).

표준은 사용 맥락(context of use)을 사용자, 목표와 과업, 자원, 환경의 조합으로 정의한다. 환경에는 기술적, 물리적, 사회적, 문화적, 조직적 환경이 들어간다[U1]. 수업의 평가는 이 맥락을 실제와 비슷하게 맞추려 하지만 다 맞추지는 못한다. 실제 사용자는 지하철에서 휴대폰으로 공고를 보지만, 수업의 참가자는 실습실의 큰 화면 앞에 앉아 있다. 평가 기록의 「환경」 칸은 이 차이를 남기기 위해 있다.

1-2. 사용성, 사용자 경험, 접근성

ISO 9241-11:2018은 사용성과 함께 접근성(accessibility), 사용자 경험(user experience), 사용으로 인한 해의 회피를 묶어 「인간 중심 품질(human-centred quality)」이라는 상위 개념을 둔다[U1]. 세 개념의 차이를 이 과목의 장과 대응시키면 다음과 같다.

  • 사용성은 정해진 사용자가 정해진 목표를 효과적, 효율적, 만족스럽게 이루는가를 묻는다. 이 장에서 다룬다.
  • 사용자 경험은 사용 전, 사용 중, 사용 후에 걸친 사용자의 인식과 반응 전체를 묻는다. 7장의 여정 지도가 이것을 그렸다.
  • 접근성은 가장 넓은 범위의 특성과 능력을 가진 사람이 쓸 수 있는가를 묻는다. 8장에서 WCAG 2.2로 점검하였다.

8장의 접근성 점검표를 통과했다고 사용성이 좋은 것은 아니다. 거꾸로 사용성 테스트의 참가자가 모두 과업에 성공했다고 접근성이 확보된 것도 아니다. 참가자 중에 화면 낭독기를 쓰는 사람이 없었을 수 있기 때문이다. 이 장의 휴리스틱 평가에서 접근성 문제(예: 낮은 명암비)를 발견하면 기록하되, 접근성의 체계적인 점검은 8장의 점검표로 다시 한다.

1-3. 기능 검사와 사용성 평가의 차이

9장의 인수 조건과 자동 검사, 12장의 비교 기준표는 “명세대로 동작하는가”를 물었다. 사용성 평가는 “사용자가 그것으로 목표를 이루는가”를 묻는다. 둘은 서로를 대신하지 못한다.

기능 검사 (9장 인수 조건) 사용성 평가 (이 장)
판정 기준 명세의 요구 문장 사용자의 목표와 과업
판정하는 사람 개발자, 자동 검사 평가자, 참가자의 행동
찾는 것 요구와 다르게 동작하는 곳(결함) 요구대로 동작해도 사용자가 막히는 곳
명세의 빈틈 찾지 못한다(명세에 없는 것은 검사 항목이 없다) 찾는다(사용자가 빈틈에 부딪힌다)
예 REQ-007 “10초 안에 요약을 보여야 한다” → 2.5초 만에 보였으므로 통과 2.5초 동안 아무 표시가 없어 참가자가 버튼을 다시 누르고 요약이 두 번 붙음

마지막 줄의 예가 이 장의 출발점이다. 요약 기능은 명세(REQ-007)를 지켰다. 그러나 명세가 「요약을 만드는 동안 무엇을 보일지」를 정하지 않았으므로, 구현은 아무것도 보이지 않았고 자동 검사는 그것을 잡지 못했다. 사용성 평가에서 찾은 문제는 그래서 구현만이 아니라 명세의 변경으로 이어진다(10절).

자기 명세서의 AI 기능 요구(요약, 피드백, 질의응답)가 「결과」만 정하고 「결과를 기다리는 동안」이나 「결과가 틀렸을 때」를 정하지 않았다면, 그 화면을 휴리스틱 평가에서 먼저 본다. 그런 요구는 통합 표에서 「(빈틈)」으로 나타난다(11-3).

2. 평가 방법의 지도

2-1. 전문가 평가와 사용자 테스트

사용성 평가 방법은 크게 두 갈래이다. 사용자 없이 전문가가 원칙에 비추어 검토하는 방법과, 실제 사용자(또는 대표 사용자)가 쓰는 것을 관찰하는 방법이다.

전문가 평가 (휴리스틱 평가 등) 사용자 테스트 (과업 기반 사용성 테스트 등)
근거 휴리스틱, 지침, 평가자의 경험 참가자의 실제 행동과 발화
비용 낮다. 참가자 모집이 필요 없다 높다. 모집, 일정, 진행, 기록이 필요하다
잘 찾는 것 일관성, 용어, 오류 메시지처럼 원칙에 비추어 보이는 문제 사용자의 정신 모형과 화면이 어긋나는 곳, 평가자가 예상하지 못한 행동
약점 실제로 문제가 아닌 것을 문제로 적고, 사용자만 겪는 문제를 놓친다 소수의 참가자가 보여 주는 문제만 보고, 과업이 지나가지 않는 화면은 보지 않는다

NN/g는 휴리스틱 평가가 사용자 조사를 보완할 뿐 대신하지 못한다고 적는다. 휴리스틱을 어긴 설계가 곧 문제인 것도 아니다. 맥락과 다른 선택지를 함께 보아야 한다[N2]. 그래서 이 장은 두 방법을 모두 쓰고, 두 방법이 같은 문제를 가리키면 그 문제의 근거가 강해진 것으로 본다(9절).

2-2. 형성 평가와 총괄 평가

평가는 목적에 따라서도 나뉜다[N10]. 형성 평가(formative)는 만드는 동안 무엇이 되고 무엇이 안 되는지, 왜 그런지를 적은 참가자의 정성적 관찰로 찾아 고친다. 결과물은 문제 목록과 개선 방향이다. 총괄 평가(summative)는 큰 개편의 직전·직후나 출시 결정 때 완성된 설계를 정량 지표(과업 시간, 성공률)로 기준이나 이전 판과 견주어 판정한다.

이 장의 평가는 형성 평가이다. 참가자 두 명으로 문제를 찾아 고치는 것이 목적이다. 과업 성공률과 SUS 점수도 재지만, 그 수치로 “잡프렙의 사용성은 58점이다”라고 판정하지 않는다. 같은 절차를 개선 뒤에 다시 해서 방향이 나아졌는지를 보는 데 쓴다(10-6). 총괄 평가로 수치를 주장하려면 참가자가 훨씬 많아야 한다(7절).

이 장은 휴리스틱 평가를 사용성 테스트보다 먼저 한다(흐름은 11-1의 그림). 평가자가 찾은 문제 가운데 심각도에 대해 의견이 갈린 것을 테스트에서 실제로 확인할 수 있기 때문이다. NN/g도 휴리스틱 평가의 우선순위 높은 항목을 다음 사용성 테스트의 길잡이로 쓰라고 권한다[N2]. 시간이 모자라 두 평가를 거의 동시에 진행하더라도, 휴리스틱 평가자는 사용성 테스트의 참가자가 될 수 없다는 원칙(0-5)은 지킨다.

3. 휴리스틱 평가

3-1. 닐슨의 10가지 휴리스틱

휴리스틱(heuristic)은 정답을 보장하지는 않지만 판단을 빠르게 해 주는 경험 법칙이다. 사용자 인터페이스의 휴리스틱으로 가장 널리 쓰이는 것은 제이콥 닐슨(Jakob Nielsen)이 1994년에 정리한 10가지이다. NN/g는 2024-01-30에 설명과 예를 고쳤으나 열 개의 항목은 그대로 두었다[N1]. 아래 표의 「뜻」은 원문을 옮긴 것이 아니라 요지를 풀어 쓴 것이다.

번호 휴리스틱 뜻 잡프렙에서 어긋나는 예
H1 시스템 상태의 가시성 (Visibility of system status) 시스템이 지금 무엇을 하고 있는지 적절한 때에 알려 준다 요약을 만드는 동안 아무 표시가 없다
H2 시스템과 현실 세계의 일치 (Match between the system and the real world) 사용자에게 익숙한 말과 개념을 쓰고, 정보를 자연스러운 순서로 보인다 “JD 파싱”, “Apply Tracker”
H3 사용자 통제와 자유 (User control and freedom) 잘못 누른 동작에서 빠져나올 길(취소, 되돌리기)이 분명하다 지원 일정의 삭제가 확인 없이 즉시 일어나고 되돌릴 수 없다
H4 일관성과 표준 (Consistency and standards) 같은 것은 같은 말과 같은 동작으로, 플랫폼과 업계의 관례를 따른다 같은 동작의 버튼이 화면마다 “저장”, “등록”으로 다르다
H5 오류 예방 (Error prevention) 오류가 일어나기 쉬운 조건을 없애거나, 실행 전에 확인을 받는다 마감일 칸에 “다음주”가 저장된다
H6 기억보다 인식 (Recognition rather than recall) 선택지와 정보를 화면에 보여, 사용자가 기억에 기대지 않게 한다 지역 필터를 적용한 뒤 무엇으로 걸렀는지 화면에 남지 않는다
H7 사용의 유연성과 효율성 (Flexibility and efficiency of use) 숙련자를 위한 지름길을 두되 초보자를 헷갈리게 하지 않는다 검색어를 입력하고 Enter를 눌러도 검색되지 않는다
H8 미적이고 최소한의 디자인 (Aesthetic and minimalist design) 필요한 정보만 두어 중요한 정보가 묻히지 않게 한다 공고 카드의 맨 위에 공고번호, 조회수, 담당 코드가 있고 마감일은 흐리게 작다
H9 오류의 인식, 진단, 회복 지원 (Help users recognize, diagnose, and recover from errors) 오류를 쉬운 말로, 무엇이 문제인지 정확히, 해결책과 함께 알린다 “Error: 422 Unprocessable Entity”
H10 도움말과 문서 (Help and documentation) 설명 없이 쓸 수 있는 것이 가장 좋지만, 필요하면 찾기 쉽고 과업 중심인 도움말을 둔다 무엇을 물을 수 있는지 알려 주는 곳이 없다

열 개를 외울 필요는 없다. 평가할 때는 키트 휴리스틱평가_양식.md의 번호표를 옆에 두고 본다. 중요한 것은 각 항목이 「사용자에게 무엇이 일어나는가」를 묻는다는 점이다. H4(일관성)를 어긴 화면은 보기에 거슬려서가 아니라, 사용자가 “저장”과 “등록”이 다른 동작이라고 생각하고 둘 다 눌러 보게 만들기 때문에 문제이다.

3-2. 평가자의 수

닐슨은 1994년에 자신의 여섯 개 프로젝트를 평균하여, 평가자 한 명이 사용성 문제의 약 35%만 찾았다고 보고하였다[N3]. 평가자마다 찾는 문제가 다르므로, 여러 평가자의 결과를 합치면 훨씬 많이 찾는다. 같은 글은 보통 세 명에서 다섯 명을 권하고, 그보다 많으면 늘어나는 정보가 적다고 하였다. NN/g의 2023년 안내도 같은 인터페이스를 세 명에서 다섯 명이 독립적으로 평가하는 것을 이상적이라고 적는다[N2].

수업에서는 시간 때문에 평가자를 두 명으로 한다. 두 명으로는 권장 범위에 못 미친다. 그래서 휴리스틱 평가만으로 문제 목록을 확정하지 않고, 사용성 테스트의 관찰로 보완한다. 프로젝트실습Ⅰ에서는 팀원 전원(세 명 이상)이 평가자가 되게 한다.

평가자를 늘릴수록 찾는 문제가 늘어나는 모습은 간단한 모형으로 볼 수 있다. 평가자 한 명이 문제 하나를 찾을 확률을 λ라 하고 평가자들이 서로 독립적이라고 가정하면, i명이 찾는 비율은 1 − (1 − λ)^i이다. 닐슨의 1994년 글은 평균 탐지율 34%를 바탕으로 한 곡선을 보인다[N3]. 그 값으로 계산하면 다음과 같다.

[터미널] (읽기)

python -c "
for i in range(1, 7):
    print(i, '명:', round(100 * (1 - (1 - 0.34) ** i)), '%')
"
1 명: 34 %
2 명: 56 %
3 명: 71 %
4 명: 81 %
5 명: 87 %
6 명: 92 %

두 명이면 절반을 조금 넘게 찾고, 다섯 명이면 열에 아홉 가까이 찾는다. 이 수치는 평가자가 서로 독립적이고 모든 문제가 똑같이 찾기 쉽다는 가정에 기댄 모형이다. 실제로는 쉬운 문제는 거의 모든 평가자가 찾고, 어려운 문제는 아무도 찾지 못하는 일이 흔하다. 모형의 값은 「평가자 한 명으로는 부족하다」는 방향을 보여 주는 데 쓴다.

λ를 0.20으로 낮추면(평가자가 휴리스틱에 익숙하지 않은 경우) 두 명이 찾는 비율은 36%로 떨어진다. 평가자가 원칙에 서툴수록 더 많은 평가자가 필요하다.

3-3. 평가 절차

NN/g의 안내[N2]를 수업의 시간에 맞추어 줄이면 다음과 같다.

  1. 준비(3분). 평가 범위(과업, 화면, 기기)를 정하고, 평가자가 휴리스틱 목록을 읽는다.
  2. 첫 번째 훑기(5분). 판단하지 않고 과업을 한 번 해 보며 제품을 익힌다.
  3. 두 번째 훑기(15분). 같은 과업을 다시 하며 휴리스틱에 어긋나는 곳을 적는다. 고칠 방향도 함께 적는다.
  4. 개별 심각도(5분). 자기가 적은 문제마다 등급(0~4)을 매긴다.
  5. 통합(10분). 평가자들이 모여 비슷한 기록을 묶고, 의견이 같은 곳과 다른 곳을 정리한다.

이 절차에서 지켜야 할 것은 「독립」이다. 평가자는 자기 기록을 끝낼 때까지 다른 평가자의 기록을 보지 않는다[N2]. 먼저 본 기록이 자기 판단을 끌고 가기 때문이다. 수업에서는 개별 기록을 각자 커밋한 뒤에 통합을 시작하는 것으로 독립을 지킨다(11-2절).

범위를 정할 때는 과업을 기준으로 한다. “잡프렙 전체”는 범위가 아니다. “과업 T1~T3이 지나가는 세 화면(SCR-01, SCR-03, SCR-06), 노트북 브라우저, 모의 모드”처럼 적는다. 범위를 좁혀야 25분 안에 깊이 볼 수 있고, 사용성 테스트의 과업과 같은 화면을 보게 되어 두 평가의 결과를 맞대기 쉽다.

  1. 위치가 특정된다. 화면 ID(SCR-06)와 요소(질문 칸)를 적어, 다른 사람이 같은 곳을 찾아갈 수 있다.
  2. 관찰한 사실과 재현 방법이 있다. “별로임”은 인상이다. 무엇을 넣었더니 무엇이 나왔는지를 적어야 다른 평가자와 개발자가 확인할 수 있다.
  3. 사용자에게 일어날 일이 있다. 이것이 심각도의 근거가 된다. “불편함”은 무엇이 일어나는지 말하지 않는다.
  4. 개선 제안이 결과로 적혀 있다. “개선 필요”는 제안이 아니다. 다만 제안은 구현 방법(“모달 창을 띄운다”)보다 사용자가 보게 될 결과(“다른 말로 물으면 된다는 것을 알린다”)로 쓰는 편이 좋다. 구현은 개발자가 정한다.

“디자인이 촌스러움”처럼 취향에 가까운 기록은 적어도 되지만, 그것이 과업에 어떤 영향을 주는지 말할 수 없다면 통합할 때 심각도 0(문제 아님)으로 정리될 가능성이 높다.

3-5. 휴리스틱 평가의 한계

휴리스틱 평가에서 나온 문제 목록은 「가설」이다. 다음 세 가지를 기억한다.

  • 오탐이 있다. 평가자가 문제라고 적었으나 실제 사용자는 전혀 막히지 않는 경우가 있다. 영어 약어 “JD”는 휴리스틱으로는 H2 위반이지만, 공고를 자주 보는 사용자에게는 익숙한 말일 수 있다. 사용성 테스트의 관찰로 확인한다.
  • 놓치는 문제가 있다. 사용자가 기능의 존재 자체를 모르는 경우(예: 요약 버튼이 있는 줄 모르고 공고를 끝까지 읽는다)는 휴리스틱으로 잘 드러나지 않는다.
  • 휴리스틱을 일부러 어길 때도 있다. NN/g는 휴리스틱을 의도적으로 어기는 설계라면 먼저 사용자 조사로 확인하라고 한다[N2]. 예를 들어 삭제 확인 창(H5)을 매번 띄우면 오히려 확인 창을 읽지 않고 누르는 습관이 생긴다. 이럴 때는 확인 창 대신 되돌리기(H3)를 두는 선택이 있다.

4. 심각도 등급

4-1. 0~4 척도

찾은 문제를 모두 한 번에 고칠 수는 없다. 무엇을 먼저 고칠지 정하려면 문제마다 심각도를 매겨야 한다. 닐슨이 1994년에 제안한 척도가 지금도 널리 쓰인다[N4].

등급 이름 뜻
0 문제 아님 사용성 문제라고 보지 않는다
1 겉모양 문제 (cosmetic) 시간이 남으면 고친다
2 작은 문제 (minor) 고치되 우선순위는 낮다
3 큰 문제 (major) 고치는 것이 중요하고 우선순위가 높다
4 사용성 재앙 (catastrophe) 출시 전에 반드시 고친다

키트의 심각도기준표.md는 각 등급에 잡프렙의 예를 붙여 두었다. 등급을 매길 때 이 예와 견준다.

4-2. 등급을 정하는 요소

닐슨은 심각도가 세 요소의 조합이라고 설명한다[N4].

  • 빈도: 흔히 일어나는가, 드물게 일어나는가. 요약 버튼은 거의 모든 사용자가 누르므로 그 버튼의 문제는 빈도가 높다.
  • 영향: 일어났을 때 사용자가 넘어가기 어려운가. 지운 지원 일정은 되살릴 수 없으므로 영향이 크다.
  • 지속성: 한 번 알고 나면 피해 갈 수 있는가, 매번 겪는가. “JD 파싱”이 요약이라는 것은 한 번 눌러 보면 알게 되므로 지속성이 낮다.

같은 글은 여기에 시장 영향(market impact)을 더한다. 넘어가기 쉬운 문제라도 제품의 평판을 크게 해칠 수 있다면 심각도를 높인다[N4]. AI 기능에서는 이 요소가 자주 등장한다. 요약이 틀린 내용을 그럴듯하게 보였는데 사용자가 그것을 믿고 지원서를 썼다면, 화면에는 오류가 하나도 보이지 않았어도 서비스는 신뢰를 잃는다.

이 과목에서는 한 가지를 더 정한다. 자료를 잃는 문제는 드물게 일어나도 3 이상으로 본다. 지운 일정을 되살릴 수 없는 문제(H3)는 빈도로 보면 낮지만, 일어났을 때 사용자가 마감일을 놓칠 수 있다.

4-3. 독립 등급과 평균

닐슨은 등급을 매기는 방법에 대해 다음을 권한다[N4].

  • 평가가 끝난 뒤에 매긴다. 평가하는 동안에는 새 문제를 찾는 데 집중한다.
  • 평가자마다 따로 매긴다. 다른 사람의 등급을 보지 않는다.
  • 한 사람의 등급은 믿을 만하지 않다. 세 명 정도의 평균을 쓴다.
  • 다른 평가자가 찾은 문제에도 등급을 매길 수 있도록, 문제를 충분히 자세하게(필요하면 화면 캡처와 함께) 적는다.

수업에서는 평가자 두 명이 자기가 찾은 문제에 먼저 등급을 매기고, 통합할 때 상대가 찾은 문제에도 등급을 매겨 두 값을 적는다. 두 값이 2 이상 차이 나면 「의견이 갈린 것」에 적고, 사용성 테스트에서 그 문제를 겪는 참가자가 있는지로 다시 정한다.

파일: 휴리스틱.md (통합 표의 한 줄) 
| H-04 | 지원 일정의 X는 확인 없이 즉시 지우고 되돌릴 수 없다 | SCR-03 | H3 | student3 #6 | 2, 3 → 3 | REQ-010 |

열의 순서는 ID, 문제, 화면, 휴리스틱, 발견, 심각도(평가자별 → 등급), 관련 요구 ID이다. 이 줄에서 평가자 한 명은 2(드물게 일어남), 다른 한 명은 3(자료를 잃음)을 주었다. 평균은 2.5이지만, 4-2절의 「자료를 잃는 문제는 3 이상」 규칙에 따라 3으로 정하였다. 이렇게 규칙으로 정한 경우에는 「의견이 갈린 것」 표에 그 까닭을 남긴다.

4-4. 따라 하기 1: 견본으로 휴리스틱 기록 연습

핵심 실습 전에 키트의 견본으로 휴리스틱 평가를 한 번 짧게 연습한다. 모든 학습자가 같은 견본을 보므로, 끝나고 교수 화면에서 결과를 맞대어 볼 수 있다. 견본을 띄우는 것은 11-2에서 동료의 프로덕트를 띄우는 것과 같은 동작이다.

5. LLM 기능의 사용성

5-1. 왜 따로 보는가

닐슨의 휴리스틱은 1990년대의 인터페이스를 바탕으로 정리되었다. 그 원칙은 AI 기능에도 그대로 적용되지만, LLM 기능에는 기존 인터페이스(예: 검색 필터)에 없던 성질이 셋 있다.

  1. 결과가 정해져 있지 않다. 검색 필터는 같은 입력에 같은 결과를 낸다. 공고 요약은 같은 입력에도 결과가 달라질 수 있다(10장의 temperature).
  2. 틀린 결과가 그럴듯하다. 검색 필터가 틀리면 빈 목록이나 오류 메시지처럼 대개 눈에 띈다. LLM은 틀린 내용을 자연스러운 문장으로 낸다(환각).
  3. 처리 시간이 길고 들쭉날쭉하다. 필터는 대개 즉시 끝난다. LLM 호출은 몇 초에서 수십 초가 걸리고 호출마다 다르다.

이 차이 때문에 LLM 기능의 사용성에서는 다음이 특히 중요해진다. 사용자가 기능에 무엇을 기대해야 하는지(기대 설정), 기다리는 동안 무엇을 보는지(진행 표시), 결과가 맞는지 어떻게 확인하는지(근거 확인), 마음에 들지 않을 때 무엇을 할 수 있는지(다시 생성과 수정), 실패했을 때 어디로 가는지(오류 회복)이다. 이 항목들을 다룬 공개 지침이 둘 있다.

5-2. Microsoft의 인간-AI 상호작용 지침

Microsoft 연구진은 2019년 CHI 학회에서 「Guidelines for Human-AI Interaction」을 발표하였다[H1]. 지침은 18개이고, 사용자와 AI의 상호작용 단계에 따라 넷으로 묶인다. 연구진은 디자인 실무자 49명이 인기 있는 AI 제품 20개에 지침을 적용해 보는 연구 등 여러 차례의 평가로 지침을 검증하였다고 밝힌다[H1]. 아래 표의 제목은 원문의 지침 제목을 옮긴 것이다.

잡프렙의 AI 기능에 직접 걸리는 것은 처음 두 개와 「틀렸을 때」의 다섯 개이다. G1과 G2는 기대 설정이다. 견본의 질문 화면은 “무엇이든 물어보세요. AI가 정확히 답해 드립니다.”라고 적었는데, 이는 G1(할 수 있는 일의 범위를 알리지 않음)과 G2(틀릴 수 있음을 알리지 않고 정확성을 약속함)를 함께 어긴다. G9는 다시 생성하거나 일부를 고칠 수단이고, G11은 근거 표시이다.

5-3. Google PAIR의 People + AI Guidebook

Google의 PAIR(People + AI Research) 팀이 낸 「People + AI Guidebook」은 AI 제품을 설계할 때의 고려 사항을 장별로 정리한다. 장에는 사용자 요구와 성공의 정의, 자료 수집과 평가, 정신 모형, 설명 가능성과 신뢰, 피드백과 통제, 오류와 우아한 실패가 있다[H2]. 이 장의 평가와 맞닿는 것은 두 장이다.

  • 정신 모형(Mental Models). 사용자가 제품이 어떻게 동작한다고 믿는가이다. 사용자의 정신 모형이 제품의 실제 능력과 어긋나면 기대가 채워지지 않고, 좌절과 오용과 이탈로 이어진다. 가이드북은 처음 소개할 때 제품이 무엇을 할 수 있고 무엇을 할 수 없는지, 어떻게 바뀔 수 있는지를 단계적으로 알리라고 권한다. 사람처럼 대화하는 제품일수록 사용자가 사람 수준의 능력을 기대하기 쉬우므로, 알고리즘이라는 성질과 한계를 알리라고 한다[H2].
  • 오류와 우아한 실패(Errors + Graceful Failure). AI는 확률적으로 동작하므로 언젠가 실패한다. 가이드북은 실패한 뒤의 길을 설계하라고 한다. 다른 선택지를 제시하고, 그 자리에서 피드백을 받고, 필요하면 사용자에게 통제권을 돌려준다[H2]. 견본의 “Error: 422”는 이 셋 가운데 아무것도 하지 않는다.

5-4. 생성형 AI 사용자에 대한 관찰 연구

NN/g는 생성형 AI 챗봇의 사용자를 관찰한 연구를 여러 편 냈다. 이 장의 평가 항목과 맞닿는 결과를 셋 고른다.

  • 세 챗봇의 정보 탐색 일지 연구(2023-09)[N11]. 참가자 18명이 2주 동안 대화 425건을 기록하였다. 대화 뒤에 답을 검증한 경우는 약 22%였다. 검증의 상호작용 비용이 높으면 챗봇으로 아낀 시간이 사라진다. 출처를 보인 도구는 검증을 쉽게 했지만, 링크를 열고 돌아오는 과정이 번거로웠다.
  • 아코디언 편집과 사과 따기(2023-09)[N12]. 참가자 8명의 사용성 연구이다. 사용자는 결과를 늘였다 줄였다를 되풀이하거나(아코디언 편집), 앞선 답의 일부를 골라 다시 쓰게 하였다(사과 따기). 연구진은 응답의 일부만 바꾸거나 직접 고칠 수 있게 하라고 권한다.
  • 새 사용자의 온보딩(2024-03)[N13]. 참가자 6명의 사용성 연구이다. AI 경험이 적은 사용자는 도구가 무엇을 할 수 있는지 몰라 헤맸다. 연구진은 짧은 소개, 맥락에 맞는 도움말, 범위가 넓은 예시 질문을 권한다.

첫 연구의 결과는 이 장의 과업 T2(“요약이 공고의 어디에서 나왔는지 확인한다”)를 둔 까닭이다. 근거 확인이 어렵게 설계된 화면에서는 사용자가 검증을 하지 않는다. 검증하지 않은 요약을 믿고 지원서를 쓰는 것이 이 서비스에서 가장 큰 위험이다.

5-5. AI 기능 점검 항목

위 지침과 연구를 휴리스틱 평가에 쓸 수 있도록 여섯 개의 점검 항목으로 줄였다. 키트의 휴리스틱 평가 양식 5절에 같은 표가 있다. 이 항목은 이 과목에서 정한 것이며, 표준이나 공인된 목록이 아니다.

번호 점검 항목 근거 잡프렙 견본의 상태
A1 기능이 무엇을 할 수 있고 무엇을 못 하는지 화면이 알려 주는가 HAX G1, PAIR 정신 모형 질문 화면이 자료의 범위를 알리지 않음

A4와 A6은 11장의 요구와 이어진다. 11장에서 RAG 질의응답에 근거 표시와 「자료에 없다」 응답을 넣었다면, 이 장에서는 그 표시가 사용자에게 보이고 이해되는지를 확인한다. 근거를 응답의 맨 끝에 작은 글씨로 붙였다면, 기능 검사는 통과해도 사용자는 근거를 보지 못할 수 있다.

핵심 실습에서는 자기 jobprep의 AI 기능 하나(요약, 자기소개서 피드백, 질의응답 중)를 골라 A1~A6을 「예/아니오/해당 없음」으로 표시하고, 「아니오」가 둘 이상이면 그 기능이 지나가는 과업을 사용성 테스트의 과업 셋 중 하나로 넣는다(11-3).

5-6. 다시 생성의 설계 선택

A5의 「다시 생성」은 버튼 하나로 끝나는 문제가 아니다. 다시 생성을 둘 때 정해야 할 것이 있다.

  • 이전 결과를 지우는가, 남겨 두고 넘겨 보게 하는가. 지우면 앞의 결과가 더 나았을 때 돌아갈 수 없다(H3).
  • 전체를 다시 만드는가, 고른 부분만 다시 만드는가. 전체만 되면 사용자는 마음에 든 부분까지 잃는다(아코디언 편집).
  • 횟수를 제한하는가. 호출마다 비용이 든다(10장). 제한한다면 남은 횟수를 보인다(H1).
  • 같은 입력으로 다시 만드는가, 지시(“더 짧게”)를 더하게 하는가. 같은 입력으로 다시 생성하면 temperature가 낮을 때 거의 같은 결과가 나와, 사용자가 버튼이 고장 났다고 생각할 수 있다.

이런 선택은 명세에 적어야 한다. 명세가 정하지 않으면 구현자(또는 Claude Code)가 임의로 정한다. 12장에서 두 구현이 같은 명세로 서로 다른 사용자 경험을 만든 것과 같은 현상이다.

자기 명세서에 「다시 생성」이나 「수정」에 관한 요구가 없는데 평가에서 그 문제가 관찰되면, 위 네 가지 중 하나를 골라 EARS 문형의 요구로 써서 명세에 넣는다(10-4). 예를 들면 “사용자가 다시 생성을 요청하면, 시스템은 이전 요약을 지우지 않고 새 요약과 나란히 보여야 한다.”이다.

6. 과업 기반 사용성 테스트의 설계

6-1. 테스트 계획

사용성 테스트는 대표 사용자에게 대표 과업을 주고, 그들이 과업을 하는 동안의 행동과 말을 관찰하는 방법이다. 닐슨은 사고 발화법을 쓴 사용성 테스트의 기본을 세 가지로 요약한다. 대표 사용자를 모으고, 대표 과업을 주고, 사용자가 말하게 하고 진행자는 말을 아낀다[N7].

테스트를 시작하기 전에 정할 것은 다섯 가지이다. 키트의 과업시나리오_양식.md 1절이 이 순서를 따른다.

  1. 목적: 이 테스트로 무엇을 결정하려 하는가. 예: 12장 병합본의 핵심 흐름 셋에서 막히는 곳을 찾아 이번 주에 고칠 것을 정한다(형성 평가).
  2. 알고 싶은 것: 관찰로 답할 질문은 무엇인가. 예: 사용자는 AI 요약의 근거를 확인할 수 있는가.
  3. 참가자: 누가 참가하고 누가 참가하면 안 되는가. 예: 다른 팀 수강생. 이 프로덕트를 만들거나 휴리스틱 평가를 한 사람은 제외한다.
  4. 과업: 참가자가 무엇을 하는가. T1~T3(6-2절).
  5. 지표: 무엇을 세고 재는가. 성공 수준, 시간, 오류 수, SUS(7~8절).

「알고 싶은 것」이 과업보다 먼저이다. 질문 없이 과업부터 만들면 제품의 모든 기능을 한 번씩 눌러 보게 하는 과업 목록이 나온다. 그런 테스트는 길기만 하고 결정에 쓸 답을 주지 않는다. 휴리스틱 평가에서 심각도 의견이 갈린 문제, 5-5절에서 「아니오」가 많았던 AI 기능이 좋은 질문의 출발점이다.

참가자의 대표성에는 한계가 있다. 잡프렙의 대상 사용자는 전문대학 2학년 취업 준비생이고, 수강생은 바로 그 집단이다(5장에서 동료를 인터뷰한 까닭과 같다). 그러나 수강생은 모두 개발을 배우는 학생이므로, 공고문과 화면의 낯선 용어에 막히는 취업 준비생(예: 페르소나 PS-2)을 대표하지 못한다. 이 한계를 사용성테스트.md의 개요에 적는다.

6-2. 과업 시나리오

과업 시나리오는 참가자에게 주는 짧은 상황 설명과 할 일이다. NN/g는 좋은 과업의 조건으로 세 가지를 든다[N8].

  1. 현실적이다. 실제 사용자가 할 법한 일이다. 참가자가 자기 기준으로 판단할 여지를 준다.
  2. 행동하게 한다. “어떻게 하실 건가요?”라고 묻지 않고 화면에서 직접 하게 한다. 말로 하는 설명은 실제 행동과 다르다.
  3. 단서를 주지 않는다. 어디를 누를지, 어느 메뉴를 쓸지 말하지 않는다. 특히 화면에 쓰인 이름을 과업에 쓰지 않는다. 다만 막연하게 쓰지도 않는다. 날짜, 지역 같은 필요한 세부는 넣는다.

나쁜 과업과 고친 과업을 견주어 본다.

[나쁜 예 1] 'JD 리스트' 탭에서 지역을 '서울'로 바꾸고 '적용'을 누른 뒤,
            '가온소프트'의 'Apply Tracker에 저장'을 누르세요.
  → 클릭할 곳을 모두 알려 준다. 참가자는 읽은 대로 누르기만 하므로 아무것도 관찰되지 않는다.
    화면의 낯선 이름(JD, Apply Tracker)이 사용자에게 통하는지도 알 수 없게 된다.

[나쁜 예 2] 잡프렙의 기능을 자유롭게 써 보세요.
  → 목표가 없어 성공과 실패를 판정할 수 없다. 참가자마다 다른 화면을 본다.

[나쁜 예 3] 공고를 찾아 저장하고, 요약을 보고, 상담 신청 방법도 알아보세요.
  → 목표가 셋이다. 어디에서 막혔는지 나누어 재기 어렵다.

[고친 예 T1] 일주일 안에 마감하는 서울 지역의 백엔드 신입 공고 하나를 골라,
            나중에 잊지 않도록 지원할 목록에 넣어 두세요.
  → 상황과 목표가 있고, 화면의 이름을 쓰지 않았다. 조건(7일, 서울, 백엔드 신입)이 있어
    성공을 판정할 수 있다.

과업마다 시작 상태와 제한 시간도 정한다. 시작 상태가 다르면 참가자를 견줄 수 없다. T1을 시작할 때 지원 일정이 비어 있어야 한다면, 참가자가 바뀔 때마다 브라우저 저장소를 비운다(진행자 대본의 「시작 전 점검」).

이 장의 과업 세 개는 잡프렙의 공통 흐름과 AI 기능을 고르게 지나가도록 정한다. 아래는 권장안이며, 자기 프로덕트의 화면에 맞게 조건을 바꾼다.

과업 과업 카드 (참가자에게 읽어 줌) 알고 싶은 것 지나가는 화면
T1 일주일 안에 마감하는 서울 지역의 백엔드 신입 공고 하나를 골라, 나중에 잊지 않도록 지원할 목록에 넣어 두세요. 검색·필터와 저장의 흐름 공고 목록, 지원 일정

과업 카드는 핵심 실습 단계 2(11-3)에서 키트의 과업시나리오_양식.md에 쓴다. 카드의 낱말을 자기 화면의 버튼과 탭 이름과 하나씩 대조해 겹치는 말이 없게 한다.

6-3. 성공 기준

과업마다 「성공」을 미리 정의한다. 진행 중에 정하면 진행자가 자기 제품에 너그러워진다. NN/g는 성공률을 가장 단순한 사용성 지표로 소개하면서, 성공을 여러 수준으로 나누어 부분 성공을 구별하는 방법을 보인다[N9]. 이 과목은 다음 네 수준을 쓴다.

수준 뜻 T1의 기준 예
완전성공 과업을 오류 없이 끝냈다 조건에 맞는 공고가 지원 일정에 한 번 들어갔다
사소한문제 끝냈으나 결과에 작은 흠이 있다 맞는 공고가 들어갔으나 두 번 들어갔다
큰문제 끝냈으나 결과가 목표와 크게 다르다 대전 지역의 공고가 들어갔다
실패 끝내지 못했다(포기, 시간 초과) 4분 안에 넣지 못했다

같은 글은 이 수준을 1, 0.66, 0.33, 0 같은 숫자로 바꾸어 평균 내지 말라고 경고한다. 수준은 순서만 있는 범주이므로 평균은 수학적으로 뜻이 없다[N9]. 그래서 키트의 aggregate.py는 수준마다 몇 명인지를 세어 보이고, 숫자 평균을 내지 않는다. 대신 「완료율」(실패가 아닌 비율)과 「완전성공률」을 함께 보인다.

AI 기능이 들어간 과업의 성공 기준에는 주의할 점이 있다. T2에서 참가자가 요약을 보았다고 성공은 아니다. 과업의 목표는 「자격을 확인하고 근거를 짚는 것」이다. 요약만 보고 근거를 짚지 못했다면 「큰문제」이다. 참가자가 근거를 짚었지만 요약이 실제로 틀렸고 참가자가 그것을 알아채지 못했다면, 그것도 「큰문제」로 기록하고 관찰 기록에 따로 표시한다. 사용자가 틀린 AI 결과를 믿은 사례는 이 서비스에서 가장 중요한 관찰이다.

6-4. 진행자 대본

진행자 대본은 진행자가 참가자에게 하는 말을 미리 적은 문서이다. 대본이 있으면 참가자마다 같은 안내를 받으므로 결과를 견줄 수 있고, 진행자가 긴장해서 힌트를 흘리는 일이 줄어든다. 키트의 진행자대본_양식.md는 다음 순서를 따른다.

  1. 시작 전 점검(참가자가 오기 전): 첫 화면, 저장소 비우기, LLM 모드, 과업 카드, 기록 양식, 시계
  2. 인사와 안내(2분): 목적, 「시험하는 것은 제품이다」, 기록 방식, 그만둘 권리, 동의
  3. 사고 발화 안내와 연습(1분)
  4. 과업 진행(과업당 3~4분): 허용하는 말과 하지 않는 말
  5. 과업 직후 질문(과업당 30초): 얼마나 쉬웠는가, 어디가 헷갈렸는가
  6. SUS 설문(2분)
  7. 마무리(1분): 가장 좋았던 점과 바꾸고 싶은 점

대본에서 가장 중요한 부분은 「진행 중에 하지 않는 말」이다. 만든 사람이 진행자를 맡으면 다음 말이 저절로 나온다.

참가자가 도움을 청하면 “저라면 어떻게 하실 것 같으세요?”라고 되묻는다. 두 번 청하거나 제한 시간이 지나면 그 과업을 실패로 기록하고 다음 과업으로 간다. 진행자가 힌트를 주었다면 그 시각과 말을 관찰 기록의 「진행자 개입」 표에 적는다. 닐슨도 진행자의 개입이 행동을 바꿀 수 있으므로, 영향을 주었을 수 있는 순간을 표시해 두었다가 분석에서 빼라고 권한다[N7].

대본은 참가자에게 그대로 읽어 주는 말이므로 존댓말로 쓴다. 교재의 문체 규칙은 대본 안의 말에 적용하지 않는다.

6-5. 사고 발화법

사고 발화법(thinking aloud)은 참가자가 과업을 하는 동안 머릿속 생각을 계속 소리 내어 말하게 하는 방법이다. 닐슨은 이를 가장 가치 있는 사용성 공학 방법이라고 부르며 장점과 한계를 함께 정리한다[N7].

장점 한계
사용자가 무엇을 오해했는지, 왜 그렇게 했는지가 드러난다 혼잣말을 계속하는 것은 부자연스럽다. 많은 사람이 어려워한다
특별한 장비가 필요 없고 싸다 참가자가 똑똑해 보이려고 생각을 걸러 말할 수 있다
진행이 조금 서툴러도 대개 쓸 만한 결과가 나온다 진행자의 질문이 행동을 바꿀 수 있다
종이 시제품부터 완성품까지 어느 단계에서나 쓴다 말하느라 과업 시간이 늘어난다. 정밀한 통계에 맞지 않는다

마지막 한계 때문에 이 장에서 잰 과업 시간은 실제 사용 시간보다 길다. 그 시간을 “잡프렙에서 공고 하나를 저장하는 데 2분이 걸린다”는 주장에 쓰지 않는다. 개선 전후를 같은 조건(사고 발화를 하는 조건)에서 견주는 데만 쓴다.

참가자가 말을 멈추면 진행자는 “지금 무슨 생각을 하고 계세요?”라고 짧게 묻는다. 닐슨도 참가자가 말을 이어 가도록 자주 일깨워야 한다고 적는다[N7]. 그러나 “왜 그 버튼을 누르셨어요?”처럼 행동의 이유를 캐묻는 질문은 참가자가 자기 행동을 돌아보고 고치게 만든다. 이유는 과업이 끝난 뒤 「과업 직후 질문」에서 묻는다.

6-6. 관찰 기록

기록자는 진행자와 다른 사람이 맡는 것이 원칙이다. 진행자는 참가자와 대본에 집중해야 하기 때문이다. 수업에서 진행자가 기록을 겸하는 경우는 6-7절에서 다룬다. 기록의 원칙은 하나이다. 본 것, 들은 것, 해석한 것을 나누어 적는다. 키트의 관찰기록_양식.md 3절은 이를 위해 칸을 셋으로 나누었다.

| 00:12 | T1 | 지역 선택에서 '서울'을 고르고 '적용'을 누름. 목록이 줄었으나 선택 칸은 ALL로 돌아감 | "어, 적용이 된 건가?" | 필터 상태가 보이지 않음 (H1, H6) |

  • 관찰 칸에는 화면에서 일어난 일과 참가자의 동작을 적는다. “헤맸다”가 아니라 “탭을 세 번 오갔다”처럼 쓴다.
  • 발화 칸에는 참가자의 말을 고치지 않고 따옴표 안에 적는다. 다른 사람의 이름이 나오면 「동기 A」처럼 바꾼다(9-4절).
  • 해석 칸에만 기록자의 판단을 적는다. 해석은 틀릴 수 있다. 나중에 원기록을 다시 볼 때 관찰과 해석이 섞여 있으면, 무엇이 사실이고 무엇이 기록자의 생각이었는지 가릴 수 없다.

시각은 과업 시작부터 잰다. 시각이 있어야 「과업 시간」을 계산할 수 있고, 이슈의 근거로 “관찰/P1.md 01:05”처럼 원기록의 위치를 가리킬 수 있다.

6-7. 세션의 진행과 역할

6-4의 대본은 과업마다 3~4분을 두는 시간이다. 수업의 한 세션(참가자 한 명)은 8분으로 줄인다. 인사·안내와 사고 발화 안내를 합쳐 1분, 과업 셋에 각 2분(제한 시간), SUS와 마무리에 1분이다. 과업이 짧고 화면이 셋뿐이어서 가능한 시간이며, 제한 시간에 걸리는 참가자가 나오면 그것도 관찰 결과이다. 세션에는 세 가지 역할이 있다.

  • 진행자(프로덕트 주인): 대본을 읽고, 과업 카드를 주고, 시간을 재고, 말을 아낀다.
  • 기록자(같은 팀의 동료 한 명): 관찰 기록을 쓰고, 과업 결과(수준, 시간, 오류 수)를 판정 근거와 함께 적는다.
  • 참가자(짝을 이룬 다른 팀의 수강생): 과업을 하며 생각을 말하고, SUS에 답한다.

프로덕트를 만든 사람이 진행자를 맡는 것은 수업의 사정 때문이다. 실무에서는 만든 사람이 진행하면 무의식중에 제품을 감싸기 쉬우므로 다른 사람이 진행하는 경우가 많다. 대본의 「하지 않는 말」을 지키는 것이 그만큼 중요하다.

수업에서는 두 팀이 짝을 이루어 라운드로 돌아가며 진행한다. 1팀과 2팀이 짝이면 첫 라운드(8분)는 1팀원 모두가 각자 자기 프로덕트의 진행자가 되고 2팀원이 한 명씩 참가자가 된다. 다음 라운드는 역할을 바꾼다. 상대를 바꾸어 이를 한 번 더 되풀이하면(네 라운드, 32분) 각 프로덕트가 참가자 두 명을 얻는다. 시간이 남아 두 라운드를 더 돌면 참가자가 세 명이 된다.

모든 팀원이 동시에 진행하는 라운드에서는 기록자를 따로 둘 수 없다. 이때는 진행자가 기록을 겸한다. 과업 결과(수준, 시간, 오류 수)와 핵심 발화만 그 자리에서 적고, 시간순 관찰은 과업이 끝날 때마다 바로 보충한다. 진행과 기록을 함께 하면 놓치는 것이 많다. 팀원 수가 맞지 않아 쉬는 사람이 생기면 그 사람이 기록자를 맡는다.

7. 표본 크기와 정량 지표

7-1. 다섯 명 규칙의 근거

사용성 테스트의 참가자 수에 대해 가장 널리 알려진 주장은 “다섯 명이면 된다”이다. 이 주장은 닐슨의 2000년 글에서 왔다[N5]. 그 근거는 다음 식이다.

n명의 참가자로 찾는 문제의 수 = N × (1 − (1 − L)^n)

  N : 설계에 있는 사용성 문제의 전체 수
  L : 참가자 한 명이 찾는 문제의 비율 (닐슨이 쓴 전형적인 값은 31%)

L = 0.31을 넣어 계산해 본다.

[터미널] (읽기)

python -c "
for n in [1, 2, 3, 5, 10, 15]:
    print(f'{n:>2}명: {100 * (1 - (1 - 0.31) ** n):5.1f}%')
"
 1명:  31.0%
 2명:  52.4%
 3명:  67.1%
 5명:  84.4%
10명:  97.6%
15명:  99.6%

다섯 명이면 약 85%를 찾고, 그 뒤로는 새로 찾는 문제가 빠르게 줄어든다. 닐슨이 말하려던 것은 “다섯 명이면 충분하다”보다 다음에 가깝다. 문제를 거의 다 찾으려면 15명쯤 필요하지만, 15명을 한 번에 테스트하기보다 다섯 명씩 세 번 테스트하고 그사이에 고치는 편이 낫다. 고친 것이 효과가 있었는지 확인하고, 고치면서 생긴 새 문제를 찾고, 처음에는 겉의 문제에 가려 보이지 않던 깊은 문제를 찾을 수 있기 때문이다[N5].

이 장의 참가자 두 명이면 기대되는 비율은 약 52%이다. 식의 가정이 맞더라도 찾지 못한 문제가 절반 가까이 남아 있을 수 있다는 뜻이다.

7-2. 다섯 명 규칙에 대한 반론

다섯 명 규칙은 여러 반론을 받았다. 반론의 요지는 대부분 식의 가정에 대한 것이다.

  • L은 일정하지 않다. 31%는 여러 프로젝트의 평균이다. 제품이 복잡하거나 과업이 많으면 한 명이 찾는 비율이 훨씬 낮을 수 있고, 그러면 다섯 명으로 찾는 비율도 낮아진다.
  • 문제마다 찾기 쉬운 정도가 다르다. 식은 모든 문제가 같은 확률로 발견된다고 가정한다. 실제로는 대부분이 겪는 문제와 일부만 겪는 문제가 섞여 있다. 드문 문제는 다섯 명으로 잘 드러나지 않는다.
  • 다섯 명을 누구로 뽑느냐에 따라 다르다. Faulkner(2003)는 참가자 60명의 자료에서 다섯 명을 무작위로 뽑는 모의실험을 하였다. 평균은 약 85%였으나, 어떤 다섯 명은 약 55%밖에 찾지 못하였다. 열 명이면 평균 약 95%, 가장 낮은 경우도 약 82%였다고 보고된다[S5][S6].

닐슨 자신도 같은 글에서 단서를 단다. 식은 사용자들이 서로 비슷하다고 가정하므로, 성격이 뚜렷이 다른 사용자 집단이 둘이면 집단마다 세 명에서 네 명을, 셋 이상이면 집단마다 적어도 세 명을 테스트하라고 한다[N5]. 2012년의 글에서는 연구의 종류에 따라 필요한 수를 나누어 적었다. 문제를 찾는 정성적 연구는 다섯 명, 수치를 주장하는 정량적 연구는 적어도 20명, 카드 소팅은 사용자 집단마다 적어도 15명이다[N6].

이 장의 테스트는 정성적 연구이고 참가자는 권장(5명)보다 적은 2~3명이다. 정량적 연구는 하지 않는다.

7-3. 이 수업의 2~3명이 말해 주는 것

참가자 두세 명은 어느 기준으로 보아도 적다. 그래도 테스트를 하는 까닭은 다음과 같다.

  • 말해 주는 것. 두세 명 가운데 두 명 이상이 같은 곳에서 막혔다면, 그 문제는 대부분의 사용자가 겪을 가능성이 높은 문제이다. 7-1절의 식으로 보아도, 많은 사람이 겪는 문제는 적은 참가자로도 잘 드러난다. 형성 평가의 목적(이번 주에 고칠 문제를 찾는 것)에는 이것으로 충분한 경우가 많다.
  • 말해 주지 못하는 것. 한 명도 겪지 않은 문제가 없다는 뜻은 아니다. “3명 중 0명이 실패했으므로 실패율 0%”라고 쓰지 않는다. 마찬가지로 “3명 중 2명이 성공(67%)”을 “사용자의 67%가 성공한다”로 일반화하지 않는다. aggregate.py가 참가자가 다섯 명 미만이면 경고 줄을 출력하는 까닭이다.

그래서 이 장의 문서에서는 비율을 쓸 때 반드시 「몇 명 중 몇 명」을 함께 쓴다. “완료율 67%”가 아니라 “3명 중 2명 완료(67%)”이다.

이 장에서 재는 지표는 ISO 9241-11의 세 요소와 대응한다(1-1절).

8. SUS 설문

8-1. SUS의 구성

SUS(System Usability Scale, 시스템 사용성 척도)는 존 브룩(John Brooke)이 만든 10문항 설문이다. 1996년 「Usability Evaluation in Industry」라는 책의 한 장으로 공개되었다[S1]. 문항이 짧고 제품의 종류를 가리지 않아, 사용성 테스트 직후의 주관적 만족을 재는 데 널리 쓰인다.

구성의 특징은 두 가지이다.

  • 응답은 1(전혀 그렇지 않다)부터 5(매우 그렇다)까지의 5점 척도이다.
  • 홀수 문항(1, 3, 5, 7, 9)은 긍정적인 문장이고, 짝수 문항(2, 4, 6, 8, 10)은 부정적인 문장이다[S2]. 긍정과 부정을 번갈아 두어, 응답자가 문항을 읽지 않고 한쪽 끝에만 표시하는 것을 어느 정도 막는다.

키트의 SUS설문_양식.md에 열 문항의 한국어 번역이 있다. 이 번역은 교재 집필자가 직접 한 것이다. 2026-11-14에 검색한 범위에서 타당도를 검증한 공개 한국어판 SUS를 찾지 못하였기 때문이다. 영어 원문은 [S2]에서 볼 수 있다.

번호 방향 문항 (집필자 번역)
1 긍정 이 시스템을 자주 사용하고 싶다.
2 부정 이 시스템은 쓸데없이 복잡하다.
3 긍정 이 시스템은 사용하기 쉬웠다.
4 부정 이 시스템을 사용하려면 기술을 잘 아는 사람의 도움이 필요할 것 같다.
5 긍정 이 시스템의 여러 기능이 잘 연결되어 있다.
6 부정 이 시스템에는 일관되지 않은 부분이 너무 많다.
7 긍정 대부분의 사람들이 이 시스템의 사용법을 매우 빨리 익힐 것 같다.
8 부정 이 시스템은 사용하기 매우 번거로웠다.
9 긍정 이 시스템을 사용하면서 자신 있었다.
10 부정 이 시스템을 사용하기 전에 배워야 할 것이 많았다.

번역이 검증되지 않았다는 것은 두 가지를 뜻한다. 첫째, 이 번역으로 얻은 점수를 영어판으로 쌓인 다른 연구의 점수와 엄밀하게 견줄 수 없다. 둘째, 같은 번역을 계속 쓰는 한 개선 전과 후를 견주는 데는 쓸 수 있다. 문항의 낱말을 수업마다 바꾸면 그것도 할 수 없으므로, 번역을 고치지 않고 그대로 쓴다.

8-2. 점수 계산

SUS 점수는 다음 순서로 계산한다[S3].

  1. 홀수 문항: 응답에서 1을 뺀다. (응답 1~5 → 0~4)
  2. 짝수 문항: 5에서 응답을 뺀다. (응답 1~5 → 4~0)
  3. 열 값을 더한다. (0~40)
  4. 2.5를 곱한다. (0~100)

부정 문항을 뒤집는 까닭은 모든 문항에서 「높을수록 좋음」이 되게 하기 위해서이다. 짝수 문항 2번(“쓸데없이 복잡하다”)에 1(전혀 그렇지 않다)을 고른 것은 좋은 평가이므로 4점이 된다.

공개된 계산 예로 검산해 본다. Adobe XD Ideas의 SUS 해설은 홀수 문항의 응답이 4, 5, 3, 4, 3이고 짝수 문항의 응답이 2, 1, 3, 1, 1인 예를 들어 77.5점을 계산한다[S4].

홀수 문항  4, 5, 3, 4, 3  → 각각 1을 뺌 → 3, 4, 2, 3, 2  → 합 14
짝수 문항  2, 1, 3, 1, 1  → 5에서 뺌   → 3, 4, 2, 4, 4  → 합 17
(14 + 17) × 2.5 = 77.5

키트의 sus.py는 이 계산을 한다. 테스트 test_published_example_77_5가 위 예를 그대로 검산한다.

파일: 도구/sus.py (계산 부분) 
def sus_score(responses):
    """응답 열 개(1~5의 정수)를 받아 SUS 점수(0~100)를 돌려준다."""
    if len(responses) != 10:
        raise SusError(f"응답은 10개여야 한다 (받은 개수: {len(responses)})")
    total = 0
    for number, value in enumerate(responses, start=1):
        if not isinstance(value, int) or isinstance(value, bool) or not 1 <= value <= 5:
            raise SusError(f"Q{number}의 응답은 1~5의 정수여야 한다 (받은 값: {value!r})")
        total += (value - 1) if number % 2 == 1 else (5 - value)
    return total * 2.5

enumerate(responses, start=1)이 문항 번호를 1부터 매기므로 number % 2 == 1이 홀수 문항이다. isinstance(value, bool)을 따로 막는 까닭은 파이썬에서 True가 정수 1로도 취급되기 때문이다. 응답 칸이 비었거나 6을 적었으면 계산하지 않고 어느 문항이 틀렸는지 알린다.

8-3. 점수의 해석

SUS 점수는 0~100 범위이지만 백분율이 아니다. 70점은 「70%가 만족했다」도 「상위 30%」도 아니다. Sauro는 여러 연구를 모아 SUS의 평균이 68점이라고 보고하였다. 연구 약 500건, 사용자 5천여 명의 자료이다[S3]. 같은 글은 점수를 백분위로 바꾸어 읽으면 이해하기 쉽다고 하며, 68점이 대략 50번째 백분위에 해당한다고 설명한다. 그래서 70점은 「평균을 조금 넘는다」로 읽는다.

해석할 때 다음을 지킨다.

[옳음] "평균 58.3점으로 68점보다 낮다. 참가자 3명이므로 방향만 본다"
       → 기준선과 표본 크기를 함께 적었다.
[틀림] "SUS 58.3%"
       → 백분율이 아니다.
[틀림] "모두 3을 고르면 50점이므로 50점이 보통이다"
       → 문항별 중간값의 합일 뿐이다. 여러 제품과 견준 평균은 68점이다.
[조심] "개선 뒤 58.3점에서 62.5점으로 올라 사용성이 나아졌다"
       → 참가자가 2~3명이면 한 사람의 응답 차이로도 이 정도 바뀐다. 과업 결과와 함께 읽는다.
[틀림] "우리 서비스는 경쟁 서비스(SUS 72점)보다 쓰기 어렵다"
       → 번역이 다르고 표본이 작아 다른 연구의 점수와 견줄 수 없다.

Sauro는 SUS가 적은 수의 참가자로도 신뢰도 있게 측정된다고 하면서도, 표본이 작으면 모집단의 실제 점수를 정밀하게 추정할 수 없으므로 신뢰 구간을 함께 계산하라고 한다[S3]. 참가자 세 명의 신뢰 구간은 매우 넓다. 이 장에서는 신뢰 구간을 계산하지 않는 대신, 「5명 미만이므로 방향만 본다」는 문장을 결과에 반드시 붙인다.

SUS 점수가 낮은 참가자가 어느 과업에서 막혔는지를 함께 보면 해석이 풍부해진다. 예시 자료에서 가장 낮은 35점을 준 P2는 T2에서 실패한 참가자이다. 만족의 수치가 효과성의 관찰과 같은 방향을 가리킨다.

9-2. 심각도와 빈도에 따른 우선순위

이 과목은 문제의 우선순위를 다음 규칙으로 정한다. 키트의 심각도기준표.md 4절에 같은 규칙이 있다.

우선순위 점수 = 심각도(0~4) × 빈도(1~3)

빈도: 사용성 테스트에서 그 문제를 겪은 참가자의 비율
       1/3 이하 → 1 (드묾),  2/3 이하 → 2 (가끔),  그보다 크면 → 3 (자주)
       테스트에서 관찰되지 않은 문제는 평가자가 추정한다

규칙: 심각도 0(문제 아님)은 목록에서 뺀다
      심각도 4는 점수와 관계없이 맨 앞에 둔다
      점수가 같으면 심각도가 높은 쪽이 앞선다

심각도에 이미 빈도가 들어 있는데(4-2절) 빈도를 또 곱하는 까닭이 있다. 휴리스틱 평가의 심각도는 평가자가 사용자를 상상해서 매긴 값이다. 사용성 테스트의 빈도는 실제로 관찰한 값이다. 둘을 곱하면, 평가자는 심각하다고 보았지만 아무도 겪지 않은 문제가 뒤로 밀리고, 평가자가 가볍게 보았지만 모두가 겪은 문제가 앞으로 온다.

곱셈 규칙에는 약점도 있다. 드물게 일어나지만 피해가 큰 문제가 뒤로 밀린다. 예시 자료의 U-04(지운 일정을 되살릴 수 없음)는 심각도 3, 빈도 1로 점수 3이 되어 8위로 밀린다. 이 문제가 자료를 잃게 한다는 점을 생각하면 너무 뒤이다. 그래서 「심각도 4는 맨 앞」이라는 예외를 두었다. 팀이 U-04를 자료 손실로 보아 심각도를 4로 올리면 맨 앞으로 온다. 규칙은 판단을 돕는 도구이고, 규칙의 결과를 뒤집을 때는 그 까닭을 이슈에 적는다.

9-3. AI로 관찰 기록을 정리할 때

관찰 기록이 참가자 세 명분, 시간순 표로 수십 줄이 되면 정리에 Claude Code를 쓰고 싶어진다. 쓸 수 있다. 다만 5장에서 인터뷰 기록으로 페르소나를 만들 때와 같은 위험이 있다. AI는 원기록에 없는 말을 그럴듯하게 만들어 넣을 수 있다. 사용성 평가에서 그 위험은 더 크다. 원기록에 없는 인용이 이슈의 근거로 올라가면, 존재하지 않는 사용자 문제를 고치느라 시간을 쓰게 된다.

AI에 정리를 맡길 때는 출처를 달게 한다.

Claude Code 
@reviews/ch13/「아이디」/jobprep/docs/평가/관찰/ 의 P1.md, P2.md(있으면 P3.md)는 사용성 테스트의 원기록이다.
이 기록에서 사용자가 겪은 문제를 뽑아 표로 정리하라.

규칙:
- 표의 열: 문제 | 겪은 참가자 | 근거(파일:시각) | 참가자의 말(있으면)
- 모든 줄의 「근거」 칸에 원기록의 파일 이름과 시각을 적는다. 근거를 적을 수 없는 문제는 쓰지 않는다.
- 「참가자의 말」에는 원기록의 「발화」 칸에 있는 문장만 큰따옴표 안에 그대로 옮긴다. 줄이거나 고치지 않는다.
- 「해석」 칸의 내용은 문제의 근거로 쓰지 않는다.
- 개선안은 쓰지 않는다.
- 결과를 docs/평가/관찰/AI정리.md 로 저장하라. 원기록 파일은 고치지 않는다.

AI가 정리를 끝내면 사람이 대조한다. 인용부터 기계적으로 확인할 수 있다. 정리본의 큰따옴표 안 문장이 원기록에 글자 그대로 있는지 찾는다.

[터미널] (읽기) (핵심 실습에서 AI 정리를 쓴 경우에만 실행)

grep -o '"[^"]*"' 관찰/AI정리.md | while IFS= read -r q; do
  if grep -qF -- "$q" 관찰/P*.md; then echo "있음  $q"; else echo "없음  $q"; fi
done
있음  "JD가 뭐지… 일단 눌러 볼게요"
있음  "안 눌렸나?"
없음  "요약이 너무 길다"

위 출력은 키트 교수/의 대조 예시(원기록 P2의 T2 부분)와 인용 세 개를 담은 정리본으로 2026-11-15에 실행한 결과이다. 출력은 세 갈래로 읽는다.

출력 뜻 할 일
있음 "…" 인용이 원기록에 글자 그대로 있다 「겪은 참가자」와 「근거」 칸만 사람이 확인한다
없음 "…" 원기록에 없거나 AI가 낱말을 바꾸었다 아래 문단대로 지우거나 실제 발화로 바꾼다
아무것도 출력되지 않는다 정리본에 곧은 큰따옴표(")가 하나도 없다. AI가 둥근 따옴표(“ ”)를 쓴 경우가 많다 sed -i 's/“/"/g; s/”/"/g' 관찰/AI정리.md로 바꾼 뒤 다시 돌린다. 출력이 없다고 「모두 맞다」로 읽지 않는다

「없음」이 나온 인용은 원기록에 없는 말이다. 지우거나, 원기록에서 해당 시각을 찾아 실제 발화로 바꾼다. 이 명령은 인용만 확인한다. 「겪은 참가자」와 「근거」 칸이 맞는지는 사람이 원기록의 해당 시각을 열어 하나씩 확인한다. 확인한 결과는 사용성테스트.md의 6절(AI로 정리한 부분과 대조 결과)에 남긴다.

AI 정리본에서 자주 나타나는 어긋남은 다음과 같다.

  • 없는 인용: 원기록에 없는 “요약이 너무 길다”. 위의 grep으로 찾는다.
  • 행동을 동기로 바꿈: “시간 종료”를 “포기했다”로 적는다. 원기록의 관찰 칸과 진행자 개입 표를 본다.
  • 해석을 사실로 올림: 기록자의 해석 “신뢰하지 않음”을 참가자의 말처럼 적는다. 문장의 출처가 발화 칸인지 해석 칸인지 본다.
  • 참가자 수를 부풀림: 한 명이 겪은 문제를 “참가자들이”로 적는다. 「겪은 참가자」 칸을 원기록의 파일별로 센다.
  • 관찰에 개선안을 섞음: “근거 링크를 달아야 한다”. 관찰 문서에서 빼고 이슈의 「개선 방향」으로 옮긴다.

9-4. 동의와 기록의 비식별화

사용성 테스트는 사람을 관찰하는 일이다. 참가자가 같은 반 수강생이어도, 참가자의 행동과 말이 저장소에 남는다는 점에서 동의와 비식별화가 필요하다. 영국 정부의 서비스 매뉴얼은 사용자 조사의 동의에 대해 다음을 요구한다[G4]. 누가 무엇을 위해 조사하는지, 어떤 자료를 모으고 어떻게 쓰고 얼마나 보관하는지를 알린다. 관찰자가 있는지, 녹화하는지를 알린다. 참여는 자발적이고 언제든 그만둘 수 있으며, 그만두면 그 사람의 자료를 지운다. 동의서는 쉬운 말로 쓰고, 동의 기록을 자료와 짝지어 보관한다.

키트의 참가동의_양식.md가 이 항목을 수업의 상황에 맞추어 적었다. 이 장에서 지키는 것은 다음과 같다.

항목 이 장의 처리
동의 진행자가 양식의 내용을 읽어 주고 구두 동의를 받는다. 동의하지 않으면 진행하지 않는다
성적과의 관계 참여 여부는 성적과 관계없다고 알린다. 참가를 거부한 수강생 대신 다른 참가자를 찾는다
식별자 이름, 학번, 연락처, 얼굴을 기록하지 않는다. 참가자는 P1, P2로 적는다
녹화 화면만 녹화한다(하는 경우). 녹화 파일은 저장소에 올리지 않고 수업이 끝나면 지운다
발화 속의 이름 참가자가 다른 사람의 이름이나 자기 개인 사정을 말하면 「동기 A」, 「(개인 사정)」으로 바꾸어 적는다
동의 기록 참가동의_양식.md는 저장소에 올리지 않는다. 관찰 기록의 「동의」 칸에 동의 여부와 시각만 적는다
철회 참가자가 그만두면 그 참가자의 관찰 기록과 SUS 응답을 지우고, 집계를 다시 돌린다

팀 실습 저장소는 교수 계정의 비공개 저장소이다. 그래도 팀원과 교수는 모두 볼 수 있고, 저장소의 이력은 지워도 남는다. 처음부터 식별할 수 있는 정보를 넣지 않는 것이 유일하게 확실한 방법이다.

참가자의 이름이나 학번이 기록에 들어가지 않았는지는 핵심 실습에서 grep으로 찾는다(11-4의 6).

10. 문제의 이슈 등록과 개선 풀 리퀘스트

이 절은 평가에서 찾은 문제를 이슈로 쓰고, 명세를 고친 뒤 구현을 바꾸어 풀 리퀘스트로 닫는 원리와 그 결과물의 모양을 다룬다. 명령은 핵심 실습의 단계 6~7(11-7, 11-8)에서 친다.

10-1. 좋은 이슈의 요소

우선순위 상위의 문제를 팀 실습 저장소의 이슈로 등록한다. 평가 문서는 한 시점의 기록이고, 이슈는 해결될 때까지 추적되는 일감이다. 3장에서 이슈의 기본(제목, 본문, 라벨, 담당자)을 다루었다. 사용성 문제의 이슈에는 다음이 더 필요하다.

  • 재현 절차. 개발자가 같은 문제를 직접 겪어 보아야 고칠 수 있다. 없으면 “제 화면에서는 안 그런데요”라는 답이 돌아온다.
  • 기대한 것과 실제로 일어난 것. 무엇이 문제인지에 대한 합의이다. 없으면 고친 뒤에도 해결되었는지 판단할 수 없다.
  • 근거. 평가 문서의 ID와 원기록의 위치이다. 이슈가 한 사람의 의견이 아님을 보인다. 없으면 리뷰어가 “정말 사용자가 그랬나?”를 묻는다.
  • 분류. 휴리스틱, 심각도, 빈도, 점수이다. 없으면 우선순위를 다시 정할 때 근거가 없다.
  • 관련 요구 ID와 화면 ID. 명세의 어느 곳을 고쳐야 하는지 가리킨다. 없으면 구현만 고치고 명세는 그대로 남는다.
  • 개선 방향. 사용자가 보게 될 결과로 쓴다. 구현 방법으로 쓰면 더 나은 해법을 미리 막는다.

키트의 이슈템플릿/usability-problem.md가 이 요소를 칸으로 갖추었다.

10-2. 이슈 템플릿

GitHub는 저장소의 .github/ISSUE_TEMPLATE/ 폴더에 있는 마크다운 파일을 이슈 템플릿으로 쓴다. 파일 머리의 YAML 머리말(front matter)에 템플릿 이름(name), 설명(about), 미리 채울 제목(title), 라벨(labels)을 적는다[G1]. 템플릿은 기본 브랜치(main)에 병합된 뒤에 이슈 작성 화면에 나타난다[G1].

파일: .github/ISSUE_TEMPLATE/usability-problem.md (머리말) 
---
name: 사용성 문제
about: 휴리스틱 평가나 사용성 테스트에서 찾은 문제를 등록한다
title: "[사용성] 「대상 아이디」: 「문제를 한 문장으로」"
labels: usability
---

템플릿과 usability 라벨은 팀에서 한 번만 등록한다(11-1). 템플릿을 평가 기록 브랜치에 함께 넣어 두면, 그 브랜치가 병합될 때 main에 들어간다(11-6).

10-3. 이슈의 본문

이슈는 웹 화면의 「New issue」에서 템플릿을 골라 쓰거나, 터미널에서 gh issue create --body-file로 본문 파일을 넘겨 만든다. 파일로 넘길 때는 템플릿의 YAML 머리말을 지운다. 머리말은 웹 화면이 템플릿을 고를 때 쓰는 정보이고, 본문에 남으면 이슈에 그대로 찍힌다(11-7).

10-5. 개선의 범위와 구현

개선은 이슈 번호를 넣은 브랜치(fix/7-summary-loading)에서 한다. 개선 풀 리퀘스트와 이슈가 평가 문서를 근거로 가리키므로, 평가 기록 풀 리퀘스트가 먼저 병합되어 있어야 한다.

구현을 Claude Code에게 맡길 때는 세 가지를 지시에 넣는다. 만족해야 할 요구 ID와 화면 상태, 고친 뒤에 다시 따라 할 이슈의 재현 절차, 범위의 한계(이 요구와 관계없는 동작은 바꾸지 않는다)이다. 범위를 묶지 않으면 Claude Code가 눈에 띈 다른 문제까지 고쳐, 리뷰어가 무엇을 보아야 하는지 흐려진다.

10-6. 리뷰와 재평가

개선 풀 리퀘스트의 리뷰어는 그 문제를 찾은 휴리스틱 평가자 한 명이다. GitHub는 작성자가 자기 풀 리퀘스트를 승인하지 못하게 하므로 승인은 반드시 다른 사람의 것이다. 사용성 개선의 리뷰에는 세 가지 관점이 있다.

  • 명세: 새 요구 문장이 EARS 문형을 지키는가, 구현이 그 문장을 만족하는가, 변경 이력이 있는가.
  • 코드: 범위 밖의 변경이 없는가, 실패했을 때도 상태가 원래대로 돌아오는가.
  • 재평가: 풀 리퀘스트의 브랜치를 자기 PC로 받아(gh pr checkout) 그 프로덕트를 띄우고, 이슈의 재현 절차를 직접 따라 해 본다.

재평가의 가장 좋은 방법은 그 과업을 처음 하는 참가자 한 명에게 같은 과업을 다시 시키는 것이다. 닐슨이 다섯 명씩 여러 번 테스트하라고 한 까닭도 고친 것이 실제로 효과가 있었는지 확인하기 위해서였다(7-1). 재현 절차는 「고쳐졌는가」를, 참가자 재테스트는 「고친 것이 사용자에게 통하는가」를 확인한다. 수업에서는 시간이 허락하면 다른 팀의 수강생 한 명에게 같은 과업을 다시 시키고, 그렇지 못하면 리뷰어가 재현 절차로 확인한다. 어느 쪽으로 했는지 리뷰 본문에 적는다. 문제가 남아 있으면 승인하지 않고 변경을 요청하며, 승인을 받으면 프로덕트 주인이 3장에서 정한 팀의 병합 방식으로 병합한다.

동료 두 명의 프로덕트를 각자의 PC에서 띄워 휴리스틱 평가를 하고, 내 프로덕트는 다른 팀의 참가자 두 명에게 과업 세 개로 테스트를 받는다. SUS와 집계로 문제의 우선순위를 정해 이슈 세 개를 등록하고, 그중 하나를 명세부터 고쳐 개선 풀 리퀘스트로 병합한다. 수업 70분의 실습이다.

11-2. 단계 1: 휴리스틱 개별 평가

동료의 브랜치를 내 PC로 받아 그 프로덕트를 띄우고, 개별 기록을 그 브랜치에 커밋한다. 평가할 프로덕트가 둘이므로 아래를 두 번 한다.

  1. 내 작업을 정리하고 동료의 브랜치로 옮긴다. 커밋하지 않은 변경이 있으면 옮길 때 막힌다. 동료가 올린 브랜치를 내 PC가 아직 모르므로 먼저 fetch한다.

  2. 상대가 찾은 문제에도 등급을 매겨 평가자별 등급 두 개를 적는다. 2 이상 차이 나면 「의견이 갈린 것」에 옮긴다(4-3).

  4. 문제가 아니라고 정한 기록은 지우지 않고 「문제가 아닌 것으로 정리한 기록」으로 옮긴다. 「평가자별 발견 수」도 채운다. 한 평가자만 찾은 문제의 수가 평가자를 두 명 둔 효과이다(3-2).

  6. 진행자대본.md의 「」 자리(이름, 프로덕트 설명, 녹화 여부)를 채운다.

확인 6 휴리스틱.md의 통합 표에 문제가 다섯 개 이상 있고, 모든 줄에 「발견」, 평가자별 등급, 관련 요구 ID(또는 「(빈틈)」)가 채워져 있다. 과업시나리오.md에 T1~T3의 카드와 성공 기준이 있고 점검표의 「단서 없음」이 모두 「예」이며, 진행자대본.md에 「」 자리가 남아 있지 않다.

12-2. 다음 학기로 이어지는 것

이 과목이 「무엇을 누구에게 만들 것인가」를 다루었다면, 다음 학기 「AI에이전트 기획 및 개발」은 「만든 것을 어떻게 안정적으로 유지할 것인가」를 다룬다. 이 과목의 결과를 정리한 기준 저장소 jobprep이 그 과목의 운영 대상이 된다. 다음 표의 괄호는 2026-11 현재 그 과목 편성표의 장 번호이다.

정리

  • 사용성은 특정한 사용자가 특정한 맥락에서 특정한 목표를 효과적, 효율적, 만족스럽게 이루는 정도이다(ISO 9241-11). 이 장은 효과성을 과업 성공 수준으로, 효율성을 시간과 오류 수로, 만족을 SUS로 쟀다.
  • 휴리스틱 평가는 평가자가 원칙에 비추어 화면을 검토하는 방법이다. 평가자 한 명은 문제의 일부만 찾으므로 여러 명이 독립적으로 평가한 뒤 합친다. 결과는 사용자 관찰로 확인할 가설이다.
  • 사용성 테스트는 대표 사용자에게 대표 과업을 주고 관찰하는 방법이다. 과업 카드에 화면의 이름을 쓰지 않고, 성공 기준을 미리 정하고, 진행자는 대본대로 말을 아낀다. 관찰, 발화, 해석을 나누어 기록한다.
  • 다섯 명 규칙은 문제를 찾는 반복적 정성 평가에 대한 것이다. 수치를 주장하려면 훨씬 많은 참가자가 필요하다. 2~3명의 결과는 「몇 명 중 몇 명」으로 쓰고 일반화하지 않는다.
  • SUS 점수는 백분율이 아니다. 여러 연구의 평균은 68점이며, 표본이 작으면 방향만 본다.
  • LLM 기능은 기대 설정, 진행 표시, 근거 확인, 다시 생성과 수정, 실패 뒤의 길을 따로 점검한다.
  • 평가에서 찾은 문제는 재현 절차와 근거와 요구 ID가 있는 이슈가 되고, 명세를 먼저 고친 뒤 구현을 바꾸는 풀 리퀘스트로 닫힌다. AI로 정리한 기록은 원기록과 대조한 뒤에 근거로 쓴다.

개념 점검

  1. ISO 9241-11의 사용성 정의에서 「특정한」이 붙는 세 가지는 무엇인가. 같은 제품의 사용성이 사용자마다 다를 수 있는 까닭을 이 정의로 설명하라.
  2. 휴리스틱 평가자가 독립적으로 평가해야 하는 까닭은 무엇인가. 평가자 두 명이 처음부터 함께 화면을 보며 평가하면 결과가 어떻게 달라질 것으로 예상되는가.
  3. 과업 카드 “‘JD 리스트’ 탭에서 ’Apply Tracker에 저장’을 눌러 공고를 저장하세요”의 문제를 두 가지 지적하고 고쳐 쓰라.
  4. 참가자 3명 중 3명이 과업에 성공했다. “이 기능의 성공률은 100%이다”라는 보고의 문제는 무엇인가. 어떻게 고쳐 써야 하는가.
  5. 사용성 평가에서 찾은 문제를 고칠 때 구현보다 명세를 먼저 고치는 까닭을 이 장의 예(요약 중 상태)로 설명하라.
