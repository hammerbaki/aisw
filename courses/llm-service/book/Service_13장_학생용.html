사용성 평가와 서비스 개선

2027학년도 「LLM 서비스 개발」의 준비 중인 교재입니다. 편집 상태를 검토하기 위해 미리 공개한 것으로, 수업 전에 내용과 순서가 바뀔 수 있습니다.

학사 15주차 · 교재 13 · 서비스 6: 앞 서비스 하나의 개선판

개편 초안 3판(2026-11-18). 평가의 방법을 동료 평가에서 「AI의 점검 → 내 눈과 손으로 확인 → 개선 문서」로 바꾸었다(plan/개편안.md 9절). 참가자 테스트, 다섯 명 규칙, SUS 설문은 뺐다. 새 키트(Service_13장)의 명령, priority.py와 테스트, 기준산출물(서비스 1의 견본)의 서버와 인수 조건 점검, 명세와 구현의 커밋 순서, git diff --stat은 집필용 PC(Windows 11, Git Bash, Python 3.13.7)에서 실행해 출력을 실었다. Aside의 점검과 Claude Code의 응답은 실행하지 않았으므로 「실행 결과 자리」로 남겼다.

지금까지 서비스 다섯 개를 만들었다. 인수 조건, 테스트, 대조, 기준표는 모두 만든 사람이 정한 검사이다. 사용자가 그 화면에서 목표를 쉽게 이루는지는 아직 확인하지 않았다.

이 장은 5장에서 만든 서비스 1(공고 모아보기 웹)의 사용성을 평가하고 고친다. 순서는 다음과 같다. 먼저 사용자가 할 과업 셋을 정하고 내가 직접 해 본다. 다음으로 브라우저 에이전트(Aside)에게 같은 과업을 시키고, 막힌 곳과 고칠 곳을 보고하게 한다. AI의 보고는 그대로 쓰지 않는다. 항목마다 내가 화면에서 직접 조작해 보고, 다시 나타난 문제만 남긴다. 남긴 문제 가운데 하나를 골라 명세를 먼저 고치고 구현을 고친다. 이것이 서비스 6이다.

고친 뒤에는 회귀를 확인한다. 회귀는 한 곳을 고치다가 앞에서 되던 다른 곳이 깨지는 일이다. 5장의 인수 조건 표를 처음부터 다시 점검해 확인한다.

이 장에서 지킬 규칙은 1장에서 정한 것이다. AI가 알려 준 것은 내 눈과 손으로 확인한 뒤에 쓴다. AI는 화면을 사람처럼 보지 않고, 하지 않은 조작을 했다고 적을 수 있으며, 어느 서비스에나 맞는 일반론을 이 화면의 문제처럼 적을 수 있다(6-4).

학습 목표

  • 사용성을 정의하고 측정 지표로 바꾼다. ISO 9241-11의 효과성, 효율성, 만족을 과업의 성공 수준, 소요 시간, 오류 수로 옮긴다.
  • 사용성 문제를 휴리스틱과 심각도로 분류해 기록한다. 문제마다 위치, 관찰한 사실, 재현 절차, 어긴 휴리스틱, 심각도를 적는다.
  • AI에게 서비스를 써 보게 하고, 그 보고를 직접 조작해 검증한다. 항목마다 「재현됨, 재현 안 됨, 판단 보류」로 판정하고 내가 본 것을 적는다.
  • 검증한 문제로 개선 문서를 쓰고, 명세를 먼저 고친 뒤 구현을 고치며, 회귀를 확인한다.

1. 사용성의 정의와 측정

1-1. ISO 9241-11의 정의

사용성(usability)은 국제 표준 ISO 9241-11:2018의 3.1.1에 정의되어 있다[U1]. 뜻을 옮기면 “특정한 사용자가 특정한 사용 맥락에서 특정한 목표를 이루기 위해 시스템, 제품, 서비스를 효과적이고 효율적이며 만족스럽게 사용할 수 있는 정도”이다. 이 정의에서 눈여겨볼 것은 「특정한」이라는 말이 세 번 나온다는 점이다. 사용성은 제품 혼자 가진 성질이 아니다. 누가, 무엇을 하려고, 어떤 환경에서 쓰는가가 정해져야 비로소 잴 수 있다. 같은 공고 모아보기 웹도 밤에 휴대폰으로 마감이 가까운 공고만 훑는 졸업 예정자와, 실습실의 큰 화면에서 지역과 경력 조건을 하나씩 걸어 보는 학습자에게 사용성이 다르다.

표준은 세 요소를 따로 정의한다[U1].

요소 표준의 정의 (뜻을 옮김) 풀어 쓰면 이 장에서 보는 것
효과성 (effectiveness, 3.1.12) 사용자가 정해진 목표를 이루는 정확성과 완전성 목표를 얼마나 정확하고 빠짐없이 이루었는가 과업 성공 수준(성공, 부분 성공, 실패, 판정 못함. 6-2)
효율성 (efficiency, 3.1.13) 얻은 결과에 견준, 쓴 자원 결과를 얻는 데 든 자원. 표준은 시간, 사람의 노력, 비용, 재료를 예로 든다 돌아가거나 잘못 누른 횟수, (LLM 기능이면) 호출 횟수
만족 (satisfaction, 3.1.14) 사용에서 비롯된 신체적, 인지적, 정서적 반응이 사용자의 필요와 기대를 충족하는 정도 쓰고 난 뒤의 느낌이 기대에 맞는가 이 장은 재지 않는다. 사용자에게 물어야 알 수 있기 때문이다(2-2)

만족의 정의에는 「기대」가 들어 있다. 표준은 사용 전의 기대가 실제 사용의 만족에 영향을 줄 수 있다고 덧붙인다[U1]. AI 기능에서 이 점이 특히 중요하다. “무엇이든 정확히 답한다”고 약속한 화면은 같은 답을 내도 약속하지 않은 화면보다 만족이 낮아질 수 있다(5절).

표준은 사용 맥락(context of use)을 사용자, 목표와 과업, 자원, 환경의 조합으로 정의한다. 환경에는 기술적, 물리적, 사회적, 문화적, 조직적 환경이 들어간다[U1]. 수업의 평가는 이 맥락을 실제와 비슷하게 맞추려 하지만 다 맞추지는 못한다. 실제 사용자는 지하철에서 휴대폰으로 공고를 보지만, 수업의 평가자는 실습실의 큰 화면 앞에 앉아 있다. 평가 기록의 「환경」 칸은 이 차이를 남기기 위해 있다.

1-2. 기능 검사와 사용성 평가의 차이

5장의 인수 조건과 자동 검사, 12장의 비교 기준표는 “명세대로 동작하는가”를 물었다. 사용성 평가는 “사용자가 그것으로 목표를 이루는가”를 묻는다. 둘은 서로를 대신하지 못한다.

마지막 줄의 예가 이 장의 출발점이다. 요약 기능은 명세(REQ-007)를 지켰다. 그러나 명세가 「요약을 만드는 동안 무엇을 보일지」를 정하지 않았으므로, 구현은 아무것도 보이지 않았고 자동 검사는 그것을 잡지 못했다. 사용성 평가에서 찾은 문제는 그래서 구현만이 아니라 명세의 변경으로 이어진다(9절).

서비스 1에도 같은 일이 있다. 기준산출물의 REQ-08은 「결과가 없으면 안내를 보인다」만 정하였다. 안내 뒤에 사용자가 무엇을 할 수 있는지는 정하지 않았으므로, 인수 조건은 통과해도 사용자는 그 화면에서 막힌다. 명세가 「결과」만 정하고 「기다리는 동안」, 「결과가 없거나 틀렸을 때」를 정하지 않은 요구는 문제 목록에서 「(빈틈)」이나 그 요구의 고침으로 나타난다(7-1).

2. 평가 방법의 지도

2-1. 전문가 평가와 사용자 테스트

사용성 평가 방법은 크게 두 갈래이다. 사용자 없이 전문가가 원칙에 비추어 검토하는 방법과, 실제 사용자(또는 대표 사용자)가 쓰는 것을 관찰하는 방법이다.

전문가 평가 (휴리스틱 평가 등) 사용자 테스트 (과업 기반 사용성 테스트 등)
근거 휴리스틱, 지침, 평가자의 경험 참가자의 실제 행동과 발화
비용 낮다. 참가자 모집이 필요 없다 높다. 모집, 일정, 진행, 기록이 필요하다
잘 찾는 것 일관성, 용어, 오류 메시지처럼 원칙에 비추어 보이는 문제 사용자의 정신 모형과 화면이 어긋나는 곳, 평가자가 예상하지 못한 행동
약점 실제로 문제가 아닌 것을 문제로 적고, 사용자만 겪는 문제를 놓친다 소수의 참가자가 보여 주는 문제만 보고, 과업이 지나가지 않는 화면은 보지 않는다

NN/g는 휴리스틱 평가가 사용자 조사를 보완할 뿐 대신하지 못한다고 적는다[N2]. 두 방법은 찾는 문제가 다르기 때문이다.

2-2. 이 장의 방법

이 장은 사용자 테스트를 하지 않는다. 참가자를 모으고 진행하는 데 드는 시간이 한 주의 수업을 넘는다. 그 대신 다음 세 가지를 순서대로 한다.

  1. 내가 과업을 직접 한다. 과업 셋을 처음 쓰는 사람처럼 해 보며 막힌 곳을 적는다. 전문가 평가의 가장 작은 꼴이다.
  2. AI가 같은 과업을 한다. 브라우저 에이전트가 화면을 조작하며 과업을 하고, 막힌 곳과 고칠 곳을 보고한다. 사람이 놓친 조작(빈 값 넣기, 빠르게 두 번 누르기)을 대신 해 보는 두 번째 평가자의 구실이다.
  3. AI의 보고를 내가 확인한다. 보고의 항목마다 재현 절차를 내 손으로 따라 해, 다시 나타난 것만 문제로 남긴다.

이 방법에는 한계가 있다. 나와 AI는 실제 사용자가 아니다. 나는 서비스를 만든 사람이어서 어디를 눌러야 하는지 안다. AI는 화면의 구조를 읽어 단추를 찾으므로, 사람이 단추를 찾지 못하는 문제를 겪지 않는다. 그래서 이 장의 결과는 「사용자가 겪을 가능성이 높은 문제의 목록」이며 「사용자가 겪은 문제의 목록」이 아니다. 개선 문서에 이 한계를 적는다.

2-3. 실제 사용자의 행동을 보는 방법: 태깅

서비스를 출시한 뒤에는 실제 사용자의 행동을 기록해 볼 수 있다. 태깅은 화면의 단추와 쪽에 기록 코드를 심어, 사용자가 무엇을 눌렀고 어디에서 떠났는지를 모으는 일이다. 예를 들어 「검색 단추를 눌렀다」, 「공고를 열었다」를 기록해 두면, 검색한 사람 가운데 몇 퍼센트가 공고를 열었는지를 셀 수 있다.

태깅은 사용자가 있어야 쓸 수 있다. 이 과목의 서비스는 출시 전이므로 태깅을 실습하지 않는다. 이 장의 방법은 출시 전에 문제를 줄이는 방법이고, 태깅은 출시 뒤에 실제 행동으로 그것을 확인하는 방법이다.

3. 휴리스틱 평가

3-1. 닐슨의 10가지 휴리스틱

휴리스틱(heuristic)은 정답을 보장하지는 않지만 판단을 빠르게 해 주는 경험 법칙이다. 사용자 인터페이스의 휴리스틱으로 가장 널리 쓰이는 것은 제이콥 닐슨(Jakob Nielsen)이 1994년에 정리한 10가지이다. NN/g는 2024-01-30에 설명과 예를 고쳤으나 열 개의 항목은 그대로 두었다[N1]. 아래 표의 「뜻」은 원문을 옮긴 것이 아니라 요지를 풀어 쓴 것이다.

번호 휴리스틱 뜻 연습 견본(잡프렙)에서 어긋나는 예
H1 시스템 상태의 가시성 (Visibility of system status) 시스템이 지금 무엇을 하고 있는지 적절한 때에 알려 준다 요약을 만드는 동안 아무 표시가 없다
H2 시스템과 현실 세계의 일치 (Match between the system and the real world) 사용자에게 익숙한 말과 개념을 쓰고, 정보를 자연스러운 순서로 보인다 “JD 파싱”, “Apply Tracker”
H3 사용자 통제와 자유 (User control and freedom) 잘못 누른 동작에서 빠져나올 길(취소, 되돌리기)이 분명하다 지원 일정의 삭제가 확인 없이 즉시 일어나고 되돌릴 수 없다
H4 일관성과 표준 (Consistency and standards) 같은 것은 같은 말과 같은 동작으로, 플랫폼과 업계의 관례를 따른다 같은 동작의 버튼이 화면마다 “저장”, “등록”으로 다르다
H5 오류 예방 (Error prevention) 오류가 일어나기 쉬운 조건을 없애거나, 실행 전에 확인을 받는다 마감일 칸에 “다음주”가 저장된다
H6 기억보다 인식 (Recognition rather than recall) 선택지와 정보를 화면에 보여, 사용자가 기억에 기대지 않게 한다 지역 필터를 적용한 뒤 무엇으로 걸렀는지 화면에 남지 않는다
H7 사용의 유연성과 효율성 (Flexibility and efficiency of use) 숙련자를 위한 지름길을 두되 초보자를 헷갈리게 하지 않는다 검색어를 입력하고 Enter를 눌러도 검색되지 않는다
H8 미적이고 최소한의 디자인 (Aesthetic and minimalist design) 필요한 정보만 두어 중요한 정보가 묻히지 않게 한다 공고 카드의 맨 위에 공고번호, 조회수, 담당 코드가 있고 마감일은 흐리게 작다
H9 오류의 인식, 진단, 회복 지원 (Help users recognize, diagnose, and recover from errors) 오류를 쉬운 말로, 무엇이 문제인지 정확히, 해결책과 함께 알린다 “Error: 422 Unprocessable Entity”
H10 도움말과 문서 (Help and documentation) 설명 없이 쓸 수 있는 것이 가장 좋지만, 필요하면 찾기 쉽고 과업 중심인 도움말을 둔다 무엇을 물을 수 있는지 알려 주는 곳이 없다

열 개를 외울 필요는 없다. 평가할 때는 키트 휴리스틱평가_양식.md의 번호표를 옆에 두고 본다. 중요한 것은 각 항목이 「사용자에게 무엇이 일어나는가」를 묻는다는 점이다. H4(일관성)를 어긴 화면은 보기에 거슬려서가 아니라, 사용자가 “저장”과 “등록”이 다른 동작이라고 생각하고 둘 다 눌러 보게 만들기 때문에 문제이다.

좋은 기록은 네 가지를 갖춘다.

  1. 위치가 특정된다. 화면 ID(SCR-06)와 요소(질문 칸)를 적어, 다른 사람이 같은 곳을 찾아갈 수 있다.
  2. 관찰한 사실과 재현 방법이 있다. “별로임”은 인상이다. 무엇을 넣었더니 무엇이 나왔는지를 적어야 다른 사람과 개발자가 확인할 수 있다.
  3. 사용자에게 일어날 일이 있다. 이것이 심각도의 근거가 된다. “불편함”은 무엇이 일어나는지 말하지 않는다.
  4. 개선 제안이 결과로 적혀 있다. “개선 필요”는 제안이 아니다. 다만 제안은 구현 방법(“모달 창을 띄운다”)보다 사용자가 보게 될 결과(“다른 말로 물으면 된다는 것을 알린다”)로 쓰는 편이 좋다. 구현은 개발자가 정한다.

3-3. 휴리스틱 평가의 한계

휴리스틱 평가에서 나온 문제 목록은 「가설」이다. 다음 세 가지를 기억한다.

  • 오탐이 있다. 평가자가 문제라고 적었으나 실제 사용자는 전혀 막히지 않는 경우가 있다. 영어 약어 “JD”는 휴리스틱으로는 H2 위반이지만, 공고를 자주 보는 사용자에게는 익숙한 말일 수 있다. 출시 뒤에 실제 사용자의 행동으로 확인할 일이다(2-3).
  • 놓치는 문제가 있다. 사용자가 기능의 존재 자체를 모르는 경우(예: 요약 버튼이 있는 줄 모르고 공고를 끝까지 읽는다)는 휴리스틱으로 잘 드러나지 않는다.
  • 휴리스틱을 일부러 어길 때도 있다. NN/g는 휴리스틱을 의도적으로 어기는 설계라면 먼저 사용자 조사로 확인하라고 한다[N2]. 예를 들어 삭제 확인 창(H5)을 매번 띄우면 오히려 확인 창을 읽지 않고 누르는 습관이 생긴다. 이럴 때는 확인 창 대신 되돌리기(H3)를 두는 선택이 있다.

4. 심각도 등급

4-1. 0~4 척도

찾은 문제를 모두 한 번에 고칠 수는 없다. 무엇을 먼저 고칠지 정하려면 문제마다 심각도를 매겨야 한다. 닐슨이 1994년에 제안한 척도가 지금도 널리 쓰인다[N4].

등급 이름 뜻
0 문제 아님 사용성 문제라고 보지 않는다
1 겉모양 문제 (cosmetic) 시간이 남으면 고친다
2 작은 문제 (minor) 고치되 우선순위는 낮다
3 큰 문제 (major) 고치는 것이 중요하고 우선순위가 높다
4 사용성 재앙 (catastrophe) 출시 전에 반드시 고친다

키트의 심각도기준표.md는 각 등급에 연습 견본의 예를 붙여 두었다. 등급을 매길 때 이 예와 견준다.

4-2. 등급을 정하는 요소

닐슨은 심각도가 세 요소의 조합이라고 설명한다[N4].

  • 빈도: 흔히 일어나는가, 드물게 일어나는가. 요약 버튼은 거의 모든 사용자가 누르므로 그 버튼의 문제는 빈도가 높다.
  • 영향: 일어났을 때 사용자가 넘어가기 어려운가. 지운 지원 일정은 되살릴 수 없으므로 영향이 크다.
  • 지속성: 한 번 알고 나면 피해 갈 수 있는가, 매번 겪는가. “JD 파싱”이 요약이라는 것은 한 번 눌러 보면 알게 되므로 지속성이 낮다.

같은 글은 여기에 시장 영향(market impact)을 더한다. 넘어가기 쉬운 문제라도 제품의 평판을 크게 해칠 수 있다면 심각도를 높인다[N4]. AI 기능에서는 이 요소가 자주 등장한다. 요약이 틀린 내용을 그럴듯하게 보였는데 사용자가 그것을 믿고 지원서를 썼다면, 화면에는 오류가 하나도 보이지 않았어도 서비스는 신뢰를 잃는다.

이 과목에서는 한 가지를 더 정한다. 자료를 잃는 문제는 드물게 일어나도 3 이상으로 본다. 지운 일정을 되살릴 수 없는 문제(H3)는 빈도로 보면 낮지만, 일어났을 때 사용자가 마감일을 놓칠 수 있다.

교수 화면에서 몇 개를 맞대어 본다. 휴리스틱 번호가 서로 달라도 관찰한 현상과 사용자에게 일어날 일이 같으면 같은 문제를 찾은 것이다. 같은 견본을 보고도 학습자마다 찾은 문제가 다르다. 한 사람은 문제의 일부만 찾는다는 뜻이며, 이 장에서 AI를 두 번째 평가자로 쓰는 까닭이다. 연습 견본의 AI 기능(요약, 자료 묻기)은 5절의 점검 항목을 익히는 데에도 쓴다. 내가 놓친 문제가 늘 보이는 것이었는지, 특정한 조작을 해야 드러나는 것이었는지를 기록 맨 아래에 적어 둔다.

5. LLM 기능의 사용성

5-1. 왜 따로 보는가

닐슨의 휴리스틱은 1990년대의 인터페이스를 바탕으로 정리되었다. 그 원칙은 AI 기능에도 그대로 적용되지만, LLM 기능에는 기존 인터페이스(예: 검색 필터)에 없던 성질이 셋 있다.

  1. 결과가 정해져 있지 않다. 검색 필터는 같은 입력에 같은 결과를 낸다. 공고 요약은 같은 입력에도 결과가 달라질 수 있다(9장의 temperature).
  2. 틀린 결과가 그럴듯하다. 검색 필터가 틀리면 빈 목록이나 오류 메시지처럼 대개 눈에 띈다. LLM은 틀린 내용을 자연스러운 문장으로 낸다(환각).
  3. 처리 시간이 길고 들쭉날쭉하다. 필터는 대개 즉시 끝난다. LLM 호출은 몇 초에서 수십 초가 걸리고 호출마다 다르다.

이 차이 때문에 LLM 기능의 사용성에서는 다음이 특히 중요해진다. 사용자가 기능에 무엇을 기대해야 하는지(기대 설정), 기다리는 동안 무엇을 보는지(진행 표시), 결과가 맞는지 어떻게 확인하는지(근거 확인), 마음에 들지 않을 때 무엇을 할 수 있는지(다시 생성과 수정), 실패했을 때 어디로 가는지(오류 회복)이다. 이 항목들을 다룬 공개 지침이 둘 있다.

5-2. AI 기능 점검 항목

위 지침과 연구를 휴리스틱 평가에 쓸 수 있도록 여섯 개의 점검 항목으로 줄였다. 키트의 휴리스틱 평가 양식 5절에 같은 표가 있다. 이 항목은 이 과목에서 정한 것이며, 표준이나 공인된 목록이 아니다.

번호 점검 항목 근거 연습 견본의 상태
A1 기능이 무엇을 할 수 있고 무엇을 못 하는지 화면이 알려 주는가 HAX G1, PAIR 정신 모형 질문 화면이 자료의 범위를 알리지 않음
A2 결과가 틀릴 수 있음을 알리는가, 과장된 약속은 없는가 HAX G2 “정확히 답해 드립니다”
A3 만드는 동안 진행 상태가 보이는가, 중복 요청이 막히는가 H1, H5 요약 중 표시 없음, 두 번 누르면 두 번 붙음
A4 결과의 근거를 확인할 수 있는가 HAX G11, NN/g 일지 연구 요약의 출처 문장이 보이지 않음
A5 결과가 마음에 들지 않을 때 다시 생성, 수정, 부분 수정의 길이 있는가 HAX G9, NN/g 아코디언 편집 다시 생성 버튼이 없음
A6 실패하거나 근거가 없을 때 이유와 다음에 할 일을 알리는가 H9, HAX G10, PAIR 오류 “Error: 422”

A4와 A6은 10장의 요구와 이어진다. 10장에서 RAG 질의응답에 근거 표시와 「자료에 없다」 응답을 넣었다면, 이 장에서는 그 표시가 사용자에게 보이고 이해되는지를 확인한다. 근거를 응답의 맨 끝에 작은 글씨로 붙였다면, 기능 검사는 통과해도 사용자는 근거를 보지 못할 수 있다.

이 장의 평가 대상인 서비스 1에는 AI 기능이 없으므로 핵심 실습에서는 이 항목을 쓰지 않는다. 9~10장의 서비스처럼 AI 기능이 있는 서비스를 평가할 때 A1~A6을 「예/아니오/해당 없음」으로 표시하고, 「아니오」가 둘 이상인 기능이 지나가는 과업을 과업 셋 가운데 하나로 넣는다.

6. AI와 함께 하는 사용성 점검

6-1. 과업 시나리오

과업 시나리오는 평가할 때 수행할 일을 사용자의 상황과 목표로 적은 것이다. 나와 AI가 같은 과업을 하므로, 과업이 분명해야 두 결과를 견줄 수 있다. NN/g는 좋은 과업의 조건으로 세 가지를 든다[N8].

  1. 현실적이다. 실제 사용자가 할 법한 일이다.
  2. 행동하게 한다. 「어떻게 하시겠습니까」라고 묻지 않고 화면에서 직접 하게 한다.
  3. 단서를 주지 않는다. 어디를 누를지 말하지 않는다. 화면에 쓰인 단추와 메뉴의 이름을 과업에 쓰지 않는다. 날짜와 지역 같은 조건은 넣는다.
[나쁜 예 1] 「지역」에서 「광주」를 고르고 「검색」을 누르세요.
  → 누를 곳을 모두 알려 준다. 읽은 대로 누르면 끝나므로 막히는 곳이 드러나지 않는다.

[나쁜 예 2] 서비스를 자유롭게 써 보세요.
  → 목표가 없어 성공과 실패를 판정할 수 없다.

[나쁜 예 3] 공고를 찾고, 마감일을 확인하고, 다른 지역도 찾아보세요.
  → 목표가 셋이다. 어디에서 막혔는지 나누어 볼 수 없다.

[고친 예 T1] 광주에서 일하는 신입 공고 가운데 마감이 가장 가까운 것을 찾아, 회사 이름을 말하세요.
  → 상황과 목표가 있고 화면의 이름을 쓰지 않았다. 답이 하나여서 성공을 판정할 수 있다.

과업마다 시작 상태를 정한다. 시작 상태가 다르면 나의 결과와 AI의 결과를 견줄 수 없다. 이 장에서는 과업마다 쪽을 새로 고친 첫 화면에서 시작한다.

6-2. 성공 기준

과업마다 「성공」을 과업을 하기 전에 정한다. 하고 난 뒤에 정하면 자기 서비스에 너그러워진다. NN/g는 성공을 여러 수준으로 나누어 부분 성공을 구별하는 방법을 보인다[N9]. 이 장은 다음 네 수준을 쓴다.

수준 뜻 T1의 기준 예
성공 과업을 오류 없이 끝냈다 맞는 회사 이름을 말했다
부분 성공 끝냈으나 돌아가거나 잘못 누른 곳이 있다 맞게 말했으나 정렬을 찾지 못해 목록을 끝까지 읽었다
실패 끝내지 못했거나 틀린 답을 냈다 마감이 지난 공고의 회사를 말했다
판정 못함 화면에서 결과를 확인할 수 없었다 목록이 뜨지 않았다

같은 글은 이 수준을 숫자로 바꾸어 평균을 내지 말라고 한다. 수준은 순서만 있는 범주이기 때문이다[N9]. 결과는 「과업 셋 가운데 성공 둘, 부분 성공 하나」처럼 센 그대로 적는다.

6-3. 브라우저 에이전트에게 과업을 맡기기

브라우저 에이전트는 글로 받은 일을 브라우저를 직접 조작해 수행하는 AI이다(5장). 에이전트에게 과업을 시키고 보고를 받을 때는 지시에 다섯 가지를 넣는다.

지시에 넣는 것 넣지 않으면 일어나는 일
과업과 시작 상태 과업 대신 화면 전체를 훑고 일반적인 평을 쓴다
한 조작을 순서대로 적으라는 요구 무엇을 눌러 보고 한 말인지 알 수 없다
문제마다 재현 절차를 적으라는 요구 내가 확인할 방법이 없다
직접 조작해 본 것과 짐작한 것을 나누라는 요구 짐작이 관찰처럼 적힌다
화면을 고치지 말고, 이 화면에서 본 것만 쓰라는 제한 어느 서비스에나 맞는 조언이 섞인다

[Aside] (읽기. 핵심 실습에서 보낸다)

http://localhost:8100/ 의 웹 서비스를 처음 쓰는 사람처럼 써 보라. 아래 과업 셋을 차례로 하되, 과업마다 쪽을 새로 고친 첫 화면에서 시작하라.

T1. (과업 카드의 문장)
T2. (과업 카드의 문장)
T3. (과업 카드의 문장)

보고의 규칙
1. 과업마다 실제로 한 조작을 순서대로 적어라. 누른 것, 입력한 것, 그 뒤 화면에 나타난 것을 적는다.
2. 과업마다 결과를 「성공, 부분 성공, 실패, 판정 못함」 가운데 하나로 적어라.
3. 막히거나 돌아간 곳을 문제로 적어라. 문제마다 다음을 붙인다.
   (1) 어느 화면의 무엇인가  (2) 무엇을 했더니 무엇이 나왔는가
   (3) 사람이 그대로 따라 할 수 있는 재현 절차  (4) 닐슨 휴리스틱의 번호(H1~H10)  (5) 심각도(0~4)
4. 문제마다 「조작해서 봄」과 「화면의 글자나 구조만 읽고 짐작함」 가운데 하나를 표시하라.
5. 이 화면에서 본 것만 써라. 「접근성을 높여라」 같은 일반적인 조언은 쓰지 마라.
6. 화면과 파일을 고치지 마라. 다른 사이트로 이동하지 마라.

6-4. AI의 보고가 틀리는 방식

AI의 보고는 문제의 후보 목록이다. 다음과 같은 방식으로 틀릴 수 있으므로 그대로 문제 목록에 옮기지 않는다.

틀리는 방식 예 내가 확인하는 방법
사람처럼 보지 않는다 에이전트는 화면의 구조를 읽어 단추를 찾는다. 글자가 작거나 단추가 화면 아래로 밀려 사람이 찾지 못하는 것은 보고되지 않는다 과업을 내가 직접 해 본다(보고에 없는 문제를 찾는다)
기다림을 느끼지 않는다 응답이 3초 걸려도 문제로 적지 않는다 직접 눌러 기다리는 시간을 본다
하지 않은 조작을 했다고 적는다 「창을 좁혔더니 표가 잘린다」고 적었으나 조작 기록에 창을 좁힌 일이 없다 조작 기록과 문제를 맞대어 본다
일반론을 이 화면의 문제로 적는다 「오류 안내가 부족하다」. 어느 오류인지 적지 않았다 재현 절차가 없는 항목은 「판단 보류」로 둔다
내 환경에서는 나타나지 않는다 에이전트의 창 크기나 저장된 상태가 내 것과 다르다 재현 절차를 그대로 따라 한다
사람과 다른 길로 과업을 끝낸다 주소의 값을 직접 고쳐 조건을 건다 조작 기록에서 사람이 하지 않을 조작을 찾는다

위 표는 일반적인 주의 사항이며, 어느 것이 얼마나 자주 일어나는지는 서비스와 도구에 따라 다르다. 실습의 검증표에서 직접 센다.

6-5. 눈과 손으로 확인하기

AI가 보고한 항목마다 재현 절차를 내 손으로 따라 하고, 다음 셋 가운데 하나로 판정한다.

판정 뜻 처리
재현됨 재현 절차대로 했더니 보고와 같은 일이 내 화면에서 일어났다 문제 목록에 넣는다
재현 안 됨 재현 절차대로 했으나 보고와 다른 일이 일어났다 넣지 않는다. 내가 본 것을 적어 둔다
판단 보류 재현 절차가 없거나, 따라 할 수 없거나, 일어난 일이 문제인지 판단할 수 없다 넣지 않는다. 까닭을 적는다

7-2. 심각도와 빈도에 따른 우선순위

이 과목은 문제의 우선순위를 다음 규칙으로 정한다. 키트의 심각도기준표.md 4절에 같은 규칙이 있다.

우선순위 점수 = 심각도(0~4) × 빈도(1~3)

빈도: 사용자가 그 문제를 만나는 정도
       1 (드묾)  특정한 조작을 해야 나타난다
       2 (가끔)  과업 하나에서 나타난다
       3 (자주)  과업 둘 이상에서 나타나거나 첫 화면에서 나타난다

규칙: 심각도 0(문제 아님)은 목록에서 뺀다
      심각도 4는 점수와 관계없이 맨 앞에 둔다
      점수가 같으면 심각도가 높은 쪽이 앞선다

심각도는 문제가 한 번 일어났을 때의 피해를 중심으로 매기고, 빈도는 과업을 하며 그 문제를 몇 번 만났는지로 매긴다. 둘을 곱하면 피해는 크지만 거의 만나지 않는 문제가 뒤로 가고, 피해는 작지만 늘 만나는 문제가 앞으로 온다.

곱셈 규칙에는 약점도 있다. 드물게 일어나지만 피해가 큰 문제가 뒤로 밀린다. 아래 예시 자료의 U-04(지운 일정을 되살릴 수 없음)는 심각도 3, 빈도 1로 점수 3이 되어 8위로 밀린다. 이 문제가 자료를 잃게 한다는 점을 생각하면 너무 뒤이다. 그래서 「심각도 4는 맨 앞」이라는 예외를 두었다. 규칙은 판단을 돕는 도구이고, 규칙의 결과를 뒤집을 때는 그 까닭을 이슈에 적는다.

7-4. 개선 문서

개선 문서는 무엇을 왜 고치는지를 근거와 함께 적은 문서이다. 고친 뒤에 읽는 사람이 「AI가 그렇게 말해서 고쳤다」가 아니라 「이 조작에서 이 일이 일어나서 고쳤다」를 알 수 있어야 한다.

1. 대상과 과업      평가한 서비스와 주소, 과업 셋과 성공 기준
2. 점검의 결과      과업마다 나의 결과와 AI의 결과 (성공 수준)
3. 검증의 결과      AI가 보고한 항목 수, 재현됨 / 재현 안 됨 / 판단 보류의 수, 내가 더 찾은 문제 수
4. 고칠 문제        문제 목록에서 고른 문제 하나와 고른 까닭 (우선순위 점수, 관련 요구)
5. 개선안          견준 안들, 고른 안과 까닭, 버린 안과 까닭
6. 명세의 변경      고치거나 더한 요구 ID와 인수 조건
7. 고친 뒤의 확인    재현 절차를 다시 한 결과, 회귀 확인의 결과
8. 한계            나와 AI는 실제 사용자가 아니다 (2-2)

3번의 수는 AI의 보고를 얼마나 믿을 수 있었는지를 보여 준다. 「열 개 가운데 여섯 개가 재현되었다」는 기록은 다음에 같은 도구를 쓸 때의 기준이 된다.

8. 문제의 이슈 등록과 명세 갱신

이 절은 고칠 문제를 이슈로 쓰고, 명세를 고친 뒤 구현을 바꾸는 원리를 다룬다. 명령은 핵심 실습에서 친다.

8-1. 좋은 이슈의 요소

고칠 문제를 팀 실습 저장소의 이슈로 등록한다. 평가 문서는 한 시점의 기록이고, 이슈는 해결될 때까지 추적되는 일감이다. 3장에서 이슈의 기본(제목, 본문, 라벨, 담당자)을 다루었다. 사용성 문제의 이슈에는 다음이 더 필요하다.

  • 재현 절차. 개발자가 같은 문제를 직접 겪어 보아야 고칠 수 있다. 없으면 “제 화면에서는 안 그런데요”라는 답이 돌아온다.
  • 기대한 것과 실제로 일어난 것. 무엇이 문제인지에 대한 합의이다. 없으면 고친 뒤에도 해결되었는지 판단할 수 없다.
  • 근거. 검증표의 번호와 내가 직접 본 것이다. 이슈가 AI의 짐작이 아니라 확인한 사실임을 보인다.
  • 분류. 휴리스틱, 심각도, 빈도, 점수이다. 없으면 우선순위를 다시 정할 때 근거가 없다.
  • 관련 요구 ID와 화면 ID. 명세의 어느 곳을 고쳐야 하는지 가리킨다. 없으면 구현만 고치고 명세는 그대로 남는다.
  • 개선 방향. 사용자가 보게 될 결과로 쓴다. 구현 방법으로 쓰면 더 나은 해법을 미리 막는다.

이슈를 하나 골라 고친다. 4장부터 지켜 온 명세 주도 개발의 순서에 따라, 구현보다 명세를 먼저 고친다.

flowchart LR
    I["이슈 #7<br/>요약 중 표시 없음"] --> S["명세 변경<br/>REQ-100 추가<br/>SCR-01 상태 정함"]
    S --> C["구현 변경<br/>app.js"]
    C --> V["확인<br/>재현 절차 다시 실행"]
    V --> P["풀 리퀘스트<br/>Closes #7"]

명세를 먼저 고치는 까닭은 세 가지이다.

  1. 명세가 문제의 원인일 때가 많다. 1-2에서 본 것처럼, 요약 중 상태는 명세가 정하지 않았기 때문에 구현되지 않았다. 구현만 고치면 다음에 누군가(또는 Claude Code가) 명세에서 다시 구현할 때 같은 문제가 돌아온다.
  2. 구현의 지시가 명확해진다. “요약 중 표시를 넣어 줘”보다 “REQ-100을 만족하도록 고쳐라”가 Claude Code에게 더 정확한 지시이다. 무엇이 완료인지가 명세 문장에 있다.
  3. 다 고쳤는지 판정할 수 있다. 명세의 새 문장과 고친 화면을 맞대어 보면 된다.

명세 변경은 4장의 EARS 문형을 따른다. 요약 중 상태는 「~하는 동안」의 상태 문형이다. 이벤트 문형(“요약을 요청하면 표시한다”)으로 쓰면 「요청한 순간」의 반응만 정하고 「기다리는 동안」을 정하지 않으므로 같은 빈틈이 남는다.

변경 이력에도 한 줄을 더한다. 명세서에 「명세가 정하지 않은 것」 목록(연습 견본 명세의 3절, 비교 구현에서 찾은 빈틈)이 있다면 해결된 항목을 지운다.

8-4. 개선의 범위와 구현

개선은 이슈 번호를 넣은 브랜치(fix/7-summary-loading)에서 한다. 아래의 예는 팀 실습 저장소에서 풀 리퀘스트로 고치는 경우이다. 이 장의 핵심 실습은 개인 실습 저장소에서 하므로 브랜치와 풀 리퀘스트 없이 커밋 둘(명세, 구현)로 한다.

구현을 Claude Code에게 맡길 때는 세 가지를 지시에 넣는다. 만족해야 할 요구 ID와 화면 상태, 고친 뒤에 다시 따라 할 이슈의 재현 절차, 범위의 한계(이 요구와 관계없는 동작은 바꾸지 않는다)이다. 범위를 묶지 않으면 Claude Code가 눈에 띈 다른 문제까지 고쳐, 무엇이 바뀌었는지 확인하기 어려워진다.

Claude Code가 고친 뒤에는 사람이 차이를 읽는다(2장). 먼저 git diff --stat으로 범위를 읽는다.

[터미널] (읽기)

 docs/요구사항명세서.md |  3 ++-
 web/app.js             | 15 ++++++++++++++-
 3 files changed, 18 insertions(+), 3 deletions(-)

9-4. 직접 확인

AI가 보고한 항목을 모두 검증표에 옮기고, 하나씩 재현 절차를 따라 한다(6-5). 시크릿 창을 새로 열어 시작 상태를 맞춘다.

| 번호 | AI의 보고 | AI의 표시 | 내가 한 조작 | 내가 본 것 | 판정 |
|---|---|---|---|---|---|
| A-01 | | | | | |

과업의 결과도 견준다. 과업마다 나의 결과와 AI의 결과를 나란히 적고, 다르면 AI의 조작 기록에서 까닭을 찾는다(6-4의 「사람과 다른 길」).

| 과업 | 나의 결과 | AI의 결과 | 다른 까닭 |
|---|---|---|---|
| T1 | 부분 성공 | 성공 | AI는 주소의 값을 고쳐 정렬하였다. 화면에서는 정렬하는 곳을 찾기 어렵다 |

표 아래에 판정의 수를 적는다. 「보고 N개: 재현됨 a, 재현 안 됨 b, 판단 보류 c」.

자주 하는 실수와 해결

증상 원인 해결
문제 기록이 「불편하다」, 「보기 좋지 않다」로 되어 있다 관찰이 아니라 평가를 적었다 위치, 한 조작, 나온 것을 적고 휴리스틱 번호를 붙인다
검증표의 「내가 본 것」이 AI의 보고와 같은 문장이다 직접 해 보지 않고 옮겨 적었다 재현 절차를 따라 하고 내 화면에서 일어난 일을 내 말로 적는다
검증표가 모두 「재현됨」이다 재현 절차 없이 그럴듯한 것을 인정하였다 재현 절차가 없는 항목은 「판단 보류」로 고친다
AI의 보고에 일반적인 조언만 있다 지시에 과업과 보고의 규칙을 넣지 않았다 6-3의 지시문으로 한 번 다시 요청한다
AI는 과업을 모두 성공했는데 나는 막혔다 AI는 화면의 구조를 읽어 단추를 찾는다 내가 막힌 곳을 출처 「직접」으로 문제 목록에 넣는다
priority.py가 「자료가 한 줄도 없다」나 「정수가 아니다」를 낸다 양식의 빈 줄만 있거나 심각도·빈도 칸에 글자가 들어갔다 줄마다 번호와 문제를 채우고 심각도는 0~4, 빈도는 1~3의 숫자로 적는다
Aside가 로컬 주소를 열지 못한다 서버가 꺼졌거나 포트가 다르다 서버용 터미널을 확인하고 부록 A-19-3을 따른다
개선 커밋에 다른 문제의 수정까지 섞였다 Claude Code에게 범위를 묶지 않고 지시하였다 「그 요구만」을 넣는다. 섞인 변경은 git restore -p로 되돌린다
고친 화면이 공개 주소에 반영되지 않는다 다시 올리지 않았거나 브라우저가 앞의 파일을 기억한다 공개 저장소에 푸시하고 Ctrl+Shift+R로 새로 고친다

정리

  • 사용성은 특정한 사용자가 특정한 맥락에서 특정한 목표를 효과적, 효율적, 만족스럽게 이루는 정도이다(ISO 9241-11).
  • 사용성 문제는 위치, 한 조작, 나온 것, 어긴 휴리스틱, 심각도로 기록한다. 「불편하다」는 기록이 아니다.
  • LLM 기능은 기대 설정, 진행 표시, 근거 확인, 다시 생성과 수정, 실패 뒤의 길을 따로 점검한다.
  • AI에게 서비스를 써 보게 하면 내가 하지 않은 조작에서 문제를 찾을 수 있다. 그러나 AI는 사람처럼 보지 않고, 하지 않은 조작을 적거나 일반론을 적을 수 있다.
  • AI의 보고는 항목마다 재현 절차를 내 손으로 따라 해 「재현됨, 재현 안 됨, 판단 보류」로 판정한다. 재현된 것과 내가 직접 찾은 것만 문제 목록에 넣는다.
  • 고칠 때는 명세를 먼저 고치고 구현을 바꾼다. 고친 뒤에는 재현 절차를 다시 하고, 처음의 인수 조건 전체로 회귀를 확인한다.
  • 이 방법의 결과는 사용자가 겪을 가능성이 높은 문제이다. 실제 사용자의 행동은 출시 뒤에 태깅으로 확인한다.
