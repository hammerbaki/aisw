개인 개발 환경: Claude Code와 Git

2027학년도 「LLM 서비스 개발」의 준비 중인 교재입니다. 편집 상태를 검토하기 위해 미리 공개한 것으로, 수업 전에 내용과 순서가 바뀔 수 있습니다.

학사 3주차 · 교재 02 · 1부 개발 환경

2026-11-18에 참조 성격의 소절 열두 개(Git 용어, 설정의 범위, 컨텍스트 관리와 대화 재개, 체크포인트의 한계, amend와 reset 등)를 부록 B-6으로 옮겼다. 본문에는 수업에서 직접 하는 것을 남겼고, 옮긴 내용을 가리키는 곳은 「부록 B-6의 …」으로 바꾸었다.

앞 장에서는 같은 프로그램을 “한 줄 요청”과 “요구 목록을 준 요청”으로 각각 만들게 하고 결과를 견주었다. 요구를 말하지 않은 자리는 AI가 임의로 채웠고, 그 차이가 결과의 차이가 되었다. 이 장은 그 실험의 뒷면을 다룬다. AI가 무엇을 바꾸었는지 사람이 정확히 알아야 하고, 바뀐 것 가운데 원하지 않는 것은 되돌릴 수 있어야 한다.

Claude Code는 한 번의 지시로 여러 파일을 고친다. 고친 내용은 화면을 스쳐 지나가고, “완료하였다”는 보고만 남는다. 사람이 확인할 수 있는 근거는 디스크에 남은 변경뿐이다. 그 변경을 줄 단위로 보여 주고, 의미 단위로 묶어 기록하고, 필요하면 하나만 골라 되돌리게 하는 도구가 버전 관리 시스템 Git이다. 이 장은 학과 교육과정에서 Git을 처음 다루는 자리이다.

이 장의 핵심 실습은 하나이다. 개인 실습 저장소 llm-service-lab에서 Claude Code에게 작은 프로그램의 변경 세 가지를 한꺼번에 시키고, 그 결과를 git diff로 읽어 커밋 셋으로 나누어 기록한다. 그 과정에서 “테스트는 모두 통과하였다”는 보고 뒤에 숨은 문제, 곧 사용자의 요구를 지키던 테스트가 함께 고쳐져 요구가 사라진 변경을 찾아낸다. 그 변경 하나만 git revert로 되돌려 요구를 되살리고, 기록 전체를 GitHub의 개인 저장소에 올린다. 완료 여부는 커밋 기록의 모양, 되살아난 테스트, 점검기의 결과로 판정한다.

이 저장소는 학기 끝까지 쓰인다. 4장부터 만드는 서비스의 명세와 구현이 모두 이 저장소에 커밋으로 쌓인다. 같은 학기의 프로젝트실습Ⅰ에서 팀 저장소를 다룰 때도 이 장의 명령이 그대로 쓰인다. 팀 작업의 절차(브랜치, 이슈, 풀 리퀘스트, 리뷰, 충돌 해결)는 다음 장에서 다룬다.

학습 목표

  • Claude Code의 작업 사이클을 통제한다. 읽기 → 계획 → 실행 → 확인의 순서로 일을 시키고, 계획 모드와 권한 확인으로 실행 전에 개입한다.
  • 변경을 Git으로 기록한다. 작업 트리, 스테이징 영역, 저장소의 세 영역을 구분하고, status, add, commit, log, diff로 변경을 읽고 의미 단위로 커밋한다.
  • 상황에 맞는 되돌리기를 고른다. 체크포인트와 되감기, restore, revert, reset의 차이를 알고 기록을 지우지 않는 방법을 먼저 쓴다.
  • 원격 저장소에 기록을 올린다. GitHub에 비공개 저장소를 만들어 푸시하고, 작업을 시작할 때 당겨 오고 끝낼 때 올리는 습관을 들인다.

0. 시작하기

실습은 내 PC(개인 노트북 또는 실습실 PC)에서 한다. VS Code의 통합 터미널을 두 개 나란히 연다(부록 A-4-3). 한쪽은 [터미널](직접 실행과 확인), 다른 쪽은 Claude Code로 쓴다. Windows에서는 두 터미널 모두 Git Bash여야 한다(부록 A-3-3). 두 터미널의 현재 폴더는 따로 움직이므로, 절마다 두 터미널이 어느 폴더에 있는지 먼저 확인한다.

이 장의 실행 상한. 실제 모델은 Claude Code의 대화형 세션으로만 쓴다(10절의 지시 A). 같은 지시를 여러 번 보내 결과를 견주는 반복 실행과 헤드리스 실행(claude -p)은 하지 않으며, 그 결과는 교수 시연의 실행 기록으로 본다.

0-1. 키트 받기

키트는 1주차에 클론한 키트 저장소(~/kits-repo)에서 저장소 밖의 ~/kits/로 받는다(부록 A-12-3). 개인 실습 저장소에는 키트에서 필요한 파일만 골라 복사한다. 키트 전체를 저장소에 넣으면 교수 배포물과 학습자의 작업이 한 기록에 섞이기 때문이다.

터미널 
git -C ~/kits-repo pull
mkdir -p ~/kits
cp -rn ~/kits-repo/Service_02장 ~/kits/
ls ~/kits/Service_02장
README.md  견본  골격  과제지시문.md  기준산출물  도구  작업기록_양식.md  카드

cp -rn은 폴더를 통째로 복사하되 이미 있는 파일은 덮어쓰지 않는다. ~/kits-repo가 없다는 오류가 나면 부록 A-12-2의 클론을 먼저 한다.

0-2. 앞 장 산출물 확인

1장의 결과는 ~/llm-service-lab/ch01/에 있다. 1장 시점에는 이 폴더가 아직 Git 저장소가 아니었다. 이 장의 3-4에서 ~/llm-service-lab 전체를 저장소로 만들고 ch01/을 첫 커밋에 넣는다.

터미널 
ls ~/llm-service-lab/ch01
README.md  가_한줄  나_요구목록  다_보강  비교.md  연습  요청문.md  요청문_양식.md  점검_모아보기.sh  점검자료  점검표_양식.md

출력은 키트의 기준 산출물을 복사한 경우이다. 1장을 마친 학습자의 ch01/에는 첫사용/이 더 있다. 핵심은 세 결과 폴더(가_한줄/, 나_요구목록/, 다_보강/)와 요청문.md, 비교.md이다. ch01/이 없거나 비어 있으면 mkdir -p ~/llm-service-lab 뒤 cp -rn ~/kits/Service_02장/기준산출물/ch01 ~/llm-service-lab/로 기준 산출물을 복사한다. 1장에서 각자 만든 것이 있으면 이 명령을 실행하지 않는다.

~/llm-service-lab 바로 아래에 .git 폴더가 이미 있으면 저장소가 먼저 만들어진 것이다. ls -a ~/llm-service-lab로 확인하고, .git이 보이면 3-4의 git init을 건너뛰고 git log --oneline으로 기록부터 본다.

확인 1 ls ~/kits/Service_02장에 골격, 견본, 도구, 카드, 과제지시문.md가 보이고, ~/llm-service-lab/ch01/에 가_한줄/, 나_요구목록/, 다_보강/, 요청문.md, 비교.md가 있다.

0-3. 이 장의 작업 공간

이 장에서 쓰는 폴더는 셋이며, 성격이 다르므로 섞지 않는다. 셋 모두 홈 폴더 바로 아래에 둔다. OneDrive로 동기화되는 「문서」나 「바탕 화면」 안에 두지 않는다(부록 A-12-1).

  • ~/kits/Service_02장/: 교수가 배포한 재료. 읽고 복사만 한다. 저장소가 아니다.
  • ~/llm-service-lab/: 개인 실습 저장소. 학기 내내 산출물이 쌓인다. 이 장에서 저장소로 만든다.

위험한 명령(reset --hard 등)은 개인 실습 저장소에서 쓰지 않는다. 개인 실습 저장소의 기록은 평가의 근거이므로 지우지 않는다.

1. 버전 관리의 필요

1-1. AI 코딩 도구와 버전 관리

Claude Code는 파일을 읽고, 고치고, 명령을 실행하는 도구를 가진 에이전트이다[C1]. 사람이 한 문장으로 지시하면 여러 파일을 차례로 고치고 테스트까지 돌린다. 이것이 생산성의 근원이면서 확인의 어려움이다. 사람은 Claude Code가 보고하는 문장을 읽지만, 실제로 바뀐 것은 디스크의 파일이다. 둘이 다를 수 있다.

Git은 그 차이를 드러낸다. Claude Code가 일을 시작하기 전에 커밋해 두면, 일이 끝난 뒤의 git diff가 “이번 지시로 바뀐 모든 것”이 된다. 보고에 없던 파일이 바뀌었거나, 지시하지 않은 테스트가 고쳐졌다면 diff에 그대로 나온다.

Claude Code에도 스스로 되돌리는 장치가 있다. 프롬프트마다 파일 상태를 저장하는 체크포인트(checkpoint)이다[C6]. 체크포인트와 Git 커밋은 쓰임이 다르다.

구분 Claude Code 체크포인트 Git 커밋
만들어지는 때 사람이 프롬프트를 보낼 때마다 자동으로 사람이 git commit을 실행할 때
담는 것 Claude Code가 파일 편집 도구로 고친 파일 사람이 스테이징한 모든 파일
담지 못하는 것 셸 명령으로만 바뀐 파일, 사람이 직접 고친 파일, 원격 작업 스테이징하지 않은 변경
보관 세션과 함께, 기본 약 30일 저장소가 있는 한
공유 내 컴퓨터의 그 세션에서만 원격 저장소로 공유
쓰임 방금 시킨 일을 대화째 무를 때 영구 기록, 협업, 특정 변경의 취소

Claude Code 공식 문서도 체크포인트가 “버전 관리를 대신하지 않는다”고 적는다[C6]. 이 장의 원칙은 다음과 같다. 체크포인트는 방금 시킨 일을 무르는 데 쓰고, 남길 결과는 사람이 diff를 읽은 뒤 커밋한다.

2. Git의 설정

2-1. 커밋 작성자 정보

커밋에는 작성자의 이름과 이메일이 들어간다. 설정하지 않고 커밋하면 Git이 「Author identity unknown」과 「fatal: unable to auto-detect email address」를 출력하고 멈춘다.

이메일은 GitHub 계정의 noreply 주소를 쓰기를 권한다. 개인 실습 저장소는 비공개로 만들지만, 같은 설정으로 만든 커밋은 팀 저장소나 나중에 공개하는 저장소에도 올라가고, 공개 저장소의 커밋은 누구나 읽을 수 있다. 개인 이메일 대신 GitHub가 주는 대체 주소를 넣으면 이 노출을 막는다. 주소의 모양은 숫자ID+사용자이름@users.noreply.github.com이다[H6]. GitHub 웹의 Settings → Emails에서 「Keep my email addresses private」를 켜면 그 화면에 자기 주소가 나온다[H5]. 부록 A-9에서 다른 주소를 넣었으면 같은 명령으로 바꾼다.

터미널 
git config --global user.email "「숫자ID+사용자이름」@users.noreply.github.com"

이름은 영문으로 쓰기를 권한다. 한글 이름도 동작하지만, 다른 도구가 작성자를 표시할 때 깨지는 경우가 있다. 커밋에 적히는 작성자 이름과 이메일은 본인임을 증명하지 않는다. Git은 이 값을 확인하지 않고 커밋에 적을 뿐이며, 푸시할 때의 인증은 9절의 GitHub 인증이 맡는다.

부록 A-9에서 설정한 셋과 이 장에서 더하는 편집기 설정의 뜻은 다음과 같다.

출력의 이름과 주소는 예시이다(실재하지 않는 계정). 줄의 순서는 설정한 순서를 따른다.

설정 뜻 하지 않으면
init.defaultBranch main 새 저장소의 첫 브랜치 이름을 main으로 첫 브랜치가 master가 되고, git init마다 안내문이 길게 나온다. GitHub의 기본 이름(main)과 달라 푸시할 때 혼동한다

nano는 Git for Windows에 함께 들어 있다(집필용 PC의 /usr/bin/nano, 2026-11-16 확인). 저장은 Ctrl+O 뒤 Enter, 나가기는 Ctrl+X이다. VS Code의 편집기를 쓰려면 core.editor "code --wait"로 설정한다.

3. 저장소와 세 영역

3-1. 저장소란 무엇인가

git init은 지금 폴더를 저장소로 만든다. 실제로 하는 일은 그 폴더 안에 .git 폴더를 만드는 것이다. 기록은 모두 .git 안에 쌓이고, 나머지 파일은 작업 트리가 된다.

.git 폴더는 직접 고치지 않는다. 이 폴더를 지우면 기록 전체가 사라지고 작업 트리의 파일만 남는다. Claude Code도 .git 폴더를 보호 경로로 다루어, 기본 모드에서는 이 폴더에 쓰기 전에 반드시 허락을 묻는다[C4].

저장소를 만들 위치를 잘못 고르는 실수가 흔하다. 홈 폴더(~)에서 git init을 하면 홈 전체가 저장소가 되어 git status에 모든 개인 파일이 나온다. 그 경우 rm -rf ~/.git으로 잘못 만든 .git 하나만 지운다. 이 명령은 기록만 지우고 파일은 지우지 않는다. 다른 폴더의 .git을 지우지 않도록 경로를 두 번 확인한다.

Git은 파일이 세 영역을 오간다고 본다[G1]. 커밋은 작업 트리를 그대로 찍는 것이 아니라, 스테이징 영역에 모아 둔 것만 찍는다.

스테이징 영역이 따로 있는 까닭은 “고친 것”과 “기록할 것”을 나누기 위해서이다. Claude Code가 파일 다섯 개를 한꺼번에 고쳐도, 사람은 그중 두 개만 골라 첫 커밋을 만들고 나머지를 다음 커밋에 넣을 수 있다. 이 장의 핵심 실습이 이 원리를 쓴다.

3-2. git status 읽기

git status는 세 영역의 상태를 한 번에 보여 준다. 무엇을 하기 전과 후에 습관처럼 친다. 막 만든 저장소에서 치면 다음이 나온다.

On branch main

No commits yet

Untracked files:
  (use "git add <file>..." to include in what will be committed)
    ch01/

nothing added to commit but untracked files present (use "git add" to track)

세 줄을 차례로 읽는다. 첫 줄은 지금 브랜치(main), 둘째 줄은 커밋이 아직 없다는 것, 그 아래는 Git이 아직 추적하지 않는 파일(ch01/)이다. 괄호 안의 (use "git add <file>..." ...)는 다음에 칠 수 있는 명령의 안내이다. Git의 안내문은 대개 정확하므로 지나치지 않고 읽는다.

짧은 형식(git status --short)은 파일 하나에 한 줄을 쓴다. 왼쪽 두 글자가 상태이다. 첫 글자는 스테이징 영역, 둘째 글자는 작업 트리의 상태이다.

D, D 지운 파일(스테이징 전, 후)
UU 병합 충돌 3장에서 다룬다

3-3. .gitignore: 기록하지 않을 것

저장소에 넣으면 안 되는 파일이 있다. 다른 컴퓨터에서 다시 만들 수 있는 것, 너무 큰 것, 그리고 비밀 정보이다. .gitignore 파일에 그 이름을 적으면 Git이 그 파일을 git status에서 보이지 않게 하고, git add로도 들어가지 않게 막는다[G9].

넣지 않는 것 예 까닭
가상 환경 .venv/ 수천 개의 파일. requirements.txt로 언제든 다시 만든다
실행 부산물 __pycache__/, .pytest_cache/ 실행할 때마다 다시 생긴다
비밀 정보 .env, 키 파일 한 번 커밋되면 기록에 남는다. 공개 저장소면 누구나 읽는다
개인 설정 CLAUDE.local.md, .claude/settings.local.json 나만 쓰는 지시와 권한 설정
편집기·운영체제 파일 .vscode/, .DS_Store, Thumbs.db 사람마다 다르다

키트의 견본(견본/gitignore_견본.txt)은 이 표의 규칙을 담고 있다. 규칙은 이렇게 읽는다. .venv/처럼 끝에 /가 붙으면 폴더에만 걸린다. .env는 어느 폴더에 있든 이름이 정확히 .env인 파일에 걸리고, .env.*는 .env.local처럼 .env.로 시작하는 파일에 걸린다. !.env.example처럼 앞에 !를 붙이면 예외가 되어, 키 이름만 적은 견본 파일은 커밋된다. 줄 맨 앞의 #은 주석이며, 규칙 뒤에 #을 붙여도 주석이 되지 않는다[G9].

두 가지를 알아 둔다. 첫째, .gitignore는 아직 추적하지 않는 파일에만 작용한다. 이미 커밋된 파일은 .gitignore에 적어도 계속 기록된다[G9]. 그 경우 git rm --cached <파일>로 추적에서 빼야 한다(9-6). 둘째, 파이썬 3.13부터 python -m venv가 가상 환경 폴더 안에 모든 것을 무시하는 .gitignore를 스스로 만든다[P1]. 파이썬이 3.12이면 이 파일이 생기지 않으므로 .venv/ 규칙이 없을 때 가상 환경 전체가 git status에 나온다. 어느 판이든 견본의 규칙을 둔다.

.gitignore가 막은 파일을 git add .env로 억지로 넣으려 하면 Git이 「The following paths are ignored by one of your .gitignore files」와 「hint: Use -f if you really want to add them.」을 출력하고 거부한다. -f는 이 경고를 무시하고 넣는 옵션이다. 비밀 정보 파일에는 쓰지 않는다.

4-3. 기록 보기: git log와 git show

명령 보이는 것
git log 커밋마다 해시 전체, 작성자, 시각, 메시지
git log --oneline 커밋마다 한 줄(해시 7자리와 제목)

4-4. 차이 보기: git diff

git diff는 이 장에서 가장 많이 쓰는 명령이다. 무엇과 무엇을 견주는지는 인자로 정한다.

명령 견주는 둘 쓰는 때
git diff 스테이징 영역 ↔︎ 작업 트리 고친 것 가운데 아직 스테이징하지 않은 것
git diff --staged 마지막 커밋 ↔︎ 스테이징 영역 커밋하기 직전, 무엇이 들어가는지
git diff HEAD 마지막 커밋 ↔︎ 작업 트리 스테이징 여부와 상관없이 마지막 커밋 이후 바뀐 모든 것
git diff <커밋> <커밋> 두 커밋 두 시점 사이
git diff --stat (위의 어느 것이든) 파일별 줄 수만 변경의 크기를 먼저 볼 때

읽기. 아래는 CSV 한 줄을 고친 뒤 git diff를 친 결과이다. 명령은 sed -i 's/데이터 분석 인턴/데이터 분석 인턴(체험형)/' ch02/deadline/applications.csv였다. 시간이 남으면 같은 명령을 쳐 보고, 끝나면 git restore ch02/deadline/applications.csv로 되돌린다.

diff --git a/ch02/deadline/applications.csv b/ch02/deadline/applications.csv
index 0e12864..f4bdb36 100644
--- a/ch02/deadline/applications.csv
+++ b/ch02/deadline/applications.csv
@@ -1,5 +1,5 @@
 회사,직무,마감일
-한빛데이터,데이터 분석 인턴,2027-03-20
+한빛데이터,데이터 분석 인턴(체험형),2027-03-20
 가람소프트,백엔드 개발,2027-03-12
 누리시스템,AI 서비스 기획,2027-03-15
 다온랩,프런트엔드 개발,2027-03-31

diff는 다음 순서로 읽는다. 10절의 핵심 실습은 이 표대로 읽는 일이다.

줄 뜻
diff --git a/… b/… 견주는 파일. a가 이전, b가 이후
--- a/…, +++ b/… 이전 쪽을 -로, 이후 쪽을 +로 표시하겠다는 선언
@@ -1,5 +1,5 @@ 변경 덩어리(hunk)의 위치. 이전 파일 1행부터 5줄이 이후 파일 1행부터 5줄이 되었다
공백으로 시작하는 줄 바뀌지 않은 앞뒤 문맥(기본 3줄)
-로 시작하는 줄 지워진 줄
+로 시작하는 줄 더해진 줄. 한 줄을 고치면 - 한 줄과 + 한 줄로 나온다

같은 변경을 git add하기 전에는 git diff에만 나오고 git diff --staged는 아무것도 출력하지 않는다. git add 뒤에는 반대가 되어 git diff가 비고 git diff --staged에 나온다(2026-11-16, 집필용 PC에서 확인). 변경이 작업 트리에서 스테이징 영역으로 옮겨 간 것이다. “git add를 했더니 diff가 사라졌다”는 놀람은 이 차이를 모를 때 생긴다. 한 문장만 고친 경우 git diff --word-diff를 쓰면 줄 전체가 아니라 바뀐 낱말만 [-지운 말-]{+더한 말+}로 보인다.

5. Claude Code의 작업 사이클

이 절과 다음 세 절(6~8절)의 단축키, 명령, 화면 문구는 2026-11 기준 Claude Code 2.1.29x의 공식 문서와 claude --help로 확인한 것이다. Claude Code는 자주 바뀐다. 화면이 이 절과 다르면 /help와 공식 문서가 우선한다. 5~8절은 읽고 이해하는 절이며, 실제 조작은 10절의 핵심 실습에서 한다.

5-1. 세션 시작과 권한 모드

Claude Code는 시작한 폴더를 작업 폴더로 삼는다. 저장소의 맨 위에서, 가상 환경을 켠 터미널에서 시작한다. 그래야 Claude Code가 실행하는 python도 가상 환경의 것이 된다(부록 A-13-1).

[터미널] · Claude Code를 띄울 터미널

cd ~/llm-service-lab
source .venv/Scripts/activate
claude --permission-mode manual

macOS는 둘째 줄이 source .venv/bin/activate이다. --permission-mode는 세션의 권한 모드를 정한다. 집필용 PC의 claude --help(2.1.296)는 acceptEdits, auto, bypassPermissions, manual, dontAsk, plan 여섯 값을 받는다고 적는다. manual은 공식 문서에서 「Manual」로 부르는 기본 확인 모드이며, 설정 파일에서는 default라는 값으로 쓴다[C4].

모드 (--permission-mode 값) 화면의 이름 묻지 않고 하는 일 이 과목에서
manual (default) Manual 파일 읽기만 이 장의 기본. 무엇을 묻는지 보기 위해
acceptEdits Edit automatically 읽기, 작업 폴더 안의 파일 편집과 mkdir·mv 같은 파일 명령 계획을 승인한 뒤 편집이 많을 때
plan Plan 읽기(탐색용 명령 포함). 파일은 고치지 않는다 계획을 먼저 받을 때
auto Auto 대부분. 분류기가 위험한 동작을 따로 검사해 막는다 이 장에서는 쓰지 않는다
dontAsk don’t ask 미리 허락한 도구만. 나머지는 묻지 않고 거부한다 쓰지 않는다
bypassPermissions Bypass permissions 모든 것 쓰지 않는다. 격리된 컨테이너용이다

2026-11 기준으로 터미널에서 새로 시작한 세션은 Auto 모드로 시작하는 것이 기본이다(2.1.283 이상). 다만 계정, 조직 설정, 모델이 Auto 모드의 조건을 충족하지 않으면 Manual로 시작한다[C4]. 학습자마다 구독과 모델이 달라 시작 모드도 달라지므로, 이 장에서는 --permission-mode manual로 시작 모드를 고정한다. 매번 묻는 화면을 직접 보아야 Claude Code가 무엇을 하려는지 알 수 있기 때문이다.

세션 안에서는 Shift+Tab으로 모드를 바꾼다. 누를 때마다 Manual → Edit automatically → Plan 순으로 돌고, Auto가 쓸 수 있는 세션이면 Plan 뒤에 Auto가 붙는다[C7]. 지금 모드는 입력 창 아래의 표시줄에 나온다(예: ⏸ plan mode on). Windows의 일부 터미널에서는 Shift+Tab 대신 Alt+M을 쓴다[C7].

[최신 자료 자리: 권한 모드와 시작 모드] 위 표의 모드 이름, 표시줄 문구, 기본 시작 모드를 확인한다. 확인할 곳: https://code.claude.com/docs/en/permission-modes, claude --help. 2026-11-15의 값: 2.1.283 이상은 Auto로 시작하고, default의 별칭이 manual이며, 표시는 ⏸ manual mode on, ⏵⏵ accept edits on, ⏸ plan mode on이다.

5-2. 계획 모드

계획 모드(plan mode)에서 Claude Code는 파일을 읽고 탐색하지만 소스 파일을 고치지 않는다. 대신 무엇을 어떻게 바꿀지 계획을 써서 승인을 기다린다[C4].

계획 모드로 들어가는 길은 셋이다. Shift+Tab을 눌러 plan mode on이 보일 때까지 돌리거나, 프롬프트 앞에 /plan을 붙이거나, claude --permission-mode plan으로 시작한다. 계획이 끝나면 승인 화면이 나온다. 「Yes, manually approve edits」는 승인하되 편집마다 묻고, 「Yes, and use auto mode」는 승인하고 Auto 모드로 실행하며, 「No, keep planning」은 고칠 점을 적어 계획을 더 다듬게 한다. 승인 화면에서 Ctrl+G를 누르면 계획을 편집기로 열어 직접 고칠 수 있다(선택지 이름은 2026-11 기준)[C4].

계획 모드에서 나올 때는 승인 화면이 없는 상태에서 Shift+Tab을 누른다. 승인 화면에서 Shift+Tab을 누르면 계획이 바로 승인된다. 모드를 바꾸려다 승인해 버리는 실수가 잦으므로, 승인 화면에서는 Esc로 먼저 닫는다[C4].

이 장에서 계획 모드를 쓰는 까닭은 하나이다. 계획에는 “어느 파일을 고칠 것인가”가 들어 있다. 계획에 없던 파일을 실행 단계에서 고치려 하면, 사람은 권한 확인 화면에서 그것을 알아챌 수 있다. 계획은 실행을 검사하는 기준이 된다.

6. CLAUDE.md 첫 작성

6-1. CLAUDE.md의 역할과 위치

Claude Code의 세션은 매번 빈 컨텍스트로 시작한다. 앞 세션에서 말한 규칙은 새 세션에 남지 않는다. 세션마다 알아야 할 것을 적어 두는 파일이 CLAUDE.md이며, Claude Code는 세션을 시작할 때 이 파일을 읽어 컨텍스트에 싣는다[C3].

놓는 곳에 따라 범위가 다르다. 저장소 맨 위의 CLAUDE.md는 커밋되어 저장소를 받는 모든 사람의 Claude Code가 읽는다. 10절에서 만드는 것이 이것이다. CLAUDE.local.md는 그 저장소에서 나만 쓰는 지시이며 .gitignore에 넣는다. ~/.claude/CLAUDE.md는 이 계정의 모든 저장소에 적용되는 개인 지시이다. 시작한 폴더와 그 위 폴더의 CLAUDE.md는 세션을 열 때 모두 읽히고, 서로 덮어쓰지 않고 이어 붙는다. 하위 폴더의 CLAUDE.md는 그 폴더의 파일을 읽거나 고칠 때 읽히며, 4장부터 서비스의 폴더에서 쓴다[C3].

공식 문서가 권하는 작성법은 다음과 같다[C3][C10].

  • 파일 하나를 200줄 안쪽으로 둔다. 길수록 컨텍스트를 많이 쓰고, 지시를 지키는 정도가 떨어진다.
  • 코드를 읽으면 알 수 있는 것은 쓰지 않는다. Claude가 스스로 알아낼 수 없는 것(실행 명령의 정확한 모양, 팀의 규칙, 금지 사항)을 쓴다.
  • 구체적으로 쓴다. “깔끔하게”가 아니라 “커밋 하나에 변경 하나”처럼 지켰는지 확인할 수 있게 쓴다.
  • CLAUDE.md에 적은 규칙은 Claude가 읽고 따르려 하는 지시이다. Claude가 그 규칙을 어겨도 자동으로 막히지는 않는다. 반드시 막아야 하는 동작은 권한 규칙이나 훅으로 막는다. 이 장은 Manual 모드의 권한 확인을 둘째 겹으로 쓰고, 훅은 「AI에이전트 기획 및 개발」에서 다룬다.

6-2. /init으로 초안 만들기

/init은 저장소를 분석해 CLAUDE.md 초안을 만든다. 빌드 명령, 테스트 방법, 발견한 관례를 적는다. 이미 CLAUDE.md가 있으면 덮어쓰지 않고 고칠 점을 제안한다[C3][C8].

/init의 초안은 사람마다 다르다. 대개 저장소 구조와 실행 명령은 잘 찾지만, “커밋은 사람이 지시할 때만 한다” 같은 작업 규칙은 코드에서 알아낼 수 없으므로 들어 있지 않다. 그런 규칙은 사람이 직접 써 넣어야 한다. 키트의 견본/CLAUDE_견본.md는 네 절(실행 명령, 작업 규칙, 커밋 메시지 규칙, 금지 사항)로 되어 있으며, 10-2에서 초안과 견주어 빠진 절을 더한다. 견본의 일부는 다음과 같다.

6-3. 읽혔는지 확인하기

파일을 저장했다고 이번 세션이 그것을 이미 읽은 것은 아니다. 세션을 시작할 때 읽히기 때문이다. 고친 뒤에는 /exit로 나왔다가 같은 폴더에서 다시 시작한다. /memory는 이 세션이 쓰는 메모리 파일의 목록을 열고, /context는 컨텍스트에 실린 메모리 파일을 항목별로 보인다(부록 B-6의 「/context로 보기」)[C8][C9]. 규칙이 실제로 쓰이는지는 “이 저장소에서 커밋은 언제 해도 되는가? 근거가 된 CLAUDE.md의 절을 함께 답하라”처럼 물어 본다. 답에 “사람이 지시할 때만”과 「금지 사항」 절이 나오면 규칙이 읽힌 것이다.

7. 체크포인트와 되감기

7-1. 체크포인트와 되감기 메뉴

Claude Code는 사람이 프롬프트를 보낼 때마다 그 직전의 파일 상태를 체크포인트로 저장한다. Claude가 파일 편집 도구로 고친 파일이 대상이다. 체크포인트는 대화와 함께 저장되므로 재개한 대화에서도 쓸 수 있다. 세션 하나에서 최근 100개를 유지하고, 기본 설정에서는 마지막 저장 뒤 약 30일이 지나면 정리된다[C6].

되감기 메뉴는 입력 창이 비어 있을 때 Esc를 두 번 누르거나 /rewind를 실행해 연다(/undo도 같은 명령이다). 입력 창에 글이 있으면 Esc 두 번은 그 글을 지운다. 지운 글은 입력 기록에 남으므로 ↑로 되찾는다[C6][C8].

메뉴는 이 세션에서 보낸 프롬프트를 나열한다. 하나를 고르면 다음 선택지가 나온다(2026-11 기준)[C6].

선택지 코드(파일) 대화
Restore code and conversation 그 프롬프트 직전으로 그 프롬프트 직전으로
Restore conversation 지금 그대로 그 프롬프트 직전으로
Restore code 그 프롬프트 직전으로 지금 그대로
Summarize from here 그대로 그 지점 이후의 대화를 요약
Summarize up to here 그대로 그 지점 이전의 대화를 요약
Never mind 아무것도 하지 않는다

그 지점 뒤에 되돌릴 파일 변경이 없으면 코드를 되돌리는 두 선택지는 나오지 않는다. 대화를 되돌리면 고른 프롬프트가 입력 창에 다시 채워지므로, 고쳐서 다시 보낼 수 있다[C6].

[최신 자료 자리: 체크포인트의 보관과 되감기 선택지] 보관 개수와 기간, 되감기 선택지의 이름, 별칭 명령을 확인한다. 확인할 곳: https://code.claude.com/docs/en/checkpointing. 2026-11-15의 값: 세션마다 최근 100개, 기본 약 30일(cleanupPeriodDays로 바꿈), 선택지는 위 표의 여섯, 별칭은 /undo이다.

8. Git 되돌리기

8-1. 상황에 따라 명령이 다르다

“되돌린다”는 말은 여러 일을 가리킨다. 고친 파일을 무르는 일, 스테이징을 취소하는 일, 커밋 하나의 효과를 없애는 일, 브랜치를 예전 커밋으로 옮기는 일은 서로 다른 명령이 맡는다. Git 공식 문서도 세 명령을 따로 구분해 설명한다[G5][G6][G7].

명령 바꾸는 것 기록(커밋) 위험
git restore <파일> 작업 트리의 파일을 스테이징 영역(없으면 마지막 커밋)의 내용으로 바꾸지 않는다 고친 내용을 되찾을 수 없다
git restore --staged <파일> 스테이징 영역을 마지막 커밋의 내용으로. 파일은 그대로 바꾸지 않는다 안전하다
git commit --amend 마지막 커밋을 새 커밋으로 바꿔 끼운다 마지막 하나를 고쳐 쓴다 푸시한 커밋에는 쓰지 않는다
git revert <커밋> 그 커밋의 변경을 거꾸로 적용한 새 커밋을 만든다 더한다(지우지 않는다) 안전하다. 충돌이 날 수 있다
git reset --soft <커밋> 브랜치를 그 커밋으로 옮긴다. 스테이징·작업 트리는 그대로 뒤의 커밋이 브랜치에서 빠진다 푸시한 커밋에는 쓰지 않는다
git reset <커밋> (--mixed) 브랜치를 옮기고 스테이징 영역을 그 커밋에 맞춘다. 작업 트리는 그대로 같음 같음
git reset --hard <커밋> 브랜치, 스테이징, 작업 트리를 모두 그 커밋으로 덮어쓴다 같음 커밋하지 않은 변경이 사라진다

원칙은 두 가지이다. 첫째, 기록을 지우는 명령(reset, --amend)보다 기록을 더하는 명령(revert)을 먼저 고른다. 둘째, 이미 푸시한 커밋은 기록을 지우는 명령으로 다루지 않는다. 원격과 내 기록이 어긋나 다음 푸시가 거부되고, 팀 저장소에서는 동료의 기록과 충돌한다. git reset 문서도 이미 다른 사람에게 준 커밋에는 하지 말라고 적는다[G7]. 키트의 카드/되돌리기_상황표.md에 이 절의 내용을 상황별로 정리해 두었다.

8-2. 비밀 정보를 커밋했을 때

API 키가 든 .env를 실수로 커밋했다면 순서가 중요하다.

  1. 키를 먼저 폐기하고 새로 발급한다. GitHub Docs는 비밀 정보가 커밋되었을 때 첫 단계로 그 비밀을 폐기하거나 교체하라고 하며, 교체만으로 충분한 경우가 많다고 적는다[H7]. 기록에서 지우는 일보다 먼저다. 이 과목의 API 키는 각자 Claude Console에서 발급하는 선택 사항이므로, 폐기도 각자 Console에서 한다(부록 A-14).
  2. 추적에서 뺀다. git rm --cached .env는 파일을 디스크에 남긴 채 다음 커밋부터 기록에서 뺀다. .gitignore에 .env를 넣어 함께 커밋한다.
  3. 앞선 커밋에는 여전히 남아 있다는 것을 안다. 이 절차를 따른 뒤 git log --oneline --all -- .env를 치면 「.env를 추적에서 뺌」 커밋 아래에 「실수로 .env 커밋」이 그대로 보이고, 그 커밋을 꺼내 보면 키가 그대로 있다. 기록에서 완전히 지우려면 기록을 고쳐 쓰는 별도 도구가 필요하고, 이미 푸시했다면 복제한 모든 사람에게 영향을 준다. 그래서 1번이 먼저다. 고용24 인증키를 받는 4장 전에 3-3의 .gitignore가 .env를 막고 있는지 다시 확인한다.

제출물

따로 올리는 파일은 없다. 개인 실습 저장소의 커밋과 GitHub의 원격 저장소가 제출물이다. 교수는 다음을 확인한다.

  • GitHub의 「사용자이름」/llm-service-lab이 비공개(Private)로 있고 로컬과 커밋 수가 같다.
  • 첫 커밋에 ch01/과 .gitignore가 있고, .venv와 .env는 기록 어디에도 없다.
  • 저장소 맨 위의 CLAUDE.md에 실행 명령, 작업 규칙, 커밋 메시지 규칙, 금지 사항의 네 절이 있다.
  • git log --oneline에 변경 셋의 커밋과 변경 2의 Revert 커밋이 있고, main의 tests/test_deadline.py에 test_render_keeps_csv_order가 있다.
  • ch02/작업기록.md의 체크포인트 시험, 권한 확인, 계획, 직접 확인, diff 읽기, 커밋, 되돌린 까닭, 원격 저장소의 칸이 채워져 있다.
  • check_ch02.py가 20/20 통과를 출력한다.

교수의 열람 방법(협업자 초대 등)은 수업에서 안내한다.

정리

  • Git은 작업 트리, 스테이징 영역, 저장소의 세 영역으로 변경을 다룬다. git add가 고른 것만 git commit이 기록한다. 그래서 한꺼번에 생긴 변경도 의미 단위로 나누어 기록할 수 있다.
  • git diff는 스테이징 전의 변경을, git diff --staged는 커밋될 변경을 보인다. Claude Code의 보고가 아니라 이 출력이 “무엇이 바뀌었는가”의 근거이다. 테스트 파일의 diff는 따로 읽는다. 통과한 테스트가 바뀐 테스트일 수 있다.
  • Claude Code는 읽기 → 계획 → 실행 → 확인으로 일한다. 계획 모드는 실행 전에 고칠 파일을 보이게 하고, Manual 모드의 권한 확인은 계획에 없던 동작을 그 자리에서 막게 한다.
  • CLAUDE.md는 세션마다 읽히는 지시 파일이다. 대화로 준 지시는 압축과 /clear에서 사라질 수 있으므로, 계속 지킬 규칙은 이 파일에 둔다. 다만 이 파일의 규칙을 Claude가 어겨도 자동으로 막히지는 않는다.
  • 체크포인트는 파일 편집 도구의 변경만, 프롬프트 단위로 되돌린다. 셸 명령의 변경, 원격 작업, Git 기록은 되돌리지 않는다. 남길 결과는 커밋으로 남긴다.
  • 되돌리기는 상황마다 명령이 다르다. 커밋 전에는 restore, 기록을 남기며 커밋 하나를 되돌릴 때는 revert이다. reset --hard와 강제 푸시는 개인 실습 저장소에서 쓰지 않는다.
  • 원격은 기록의 사본이자 공유의 자리이다. 작업을 시작할 때 git pull, 끝낼 때 git push.

개념 점검

  1. Claude Code가 dday.py와 deadline.py를 고쳤다. dday.py만 커밋하려면 어떤 명령을 어떤 순서로 쓰는가. 커밋 직전에 들어갈 파일을 확인하는 명령은 무엇인가.
  2. git add를 한 뒤 같은 파일을 또 고쳤다. git status --short에 그 파일은 어떻게 표시되며, 이때 git diff와 git diff --staged는 각각 무엇을 보이는가.
  3. Claude Code가 셸 명령 sed -i로 applications.csv를 고쳤고, 그 대화에서 이 파일을 편집 도구로 고친 적은 없다. 되감기의 「Restore code」로 이 변경이 돌아오는가. 돌아오지 않는다면 무엇으로 되돌리는가.
  4. 이미 푸시한 커밋 하나의 변경을 취소해야 한다. git revert와 git reset --hard 가운데 무엇을 쓰고, 다른 하나를 쓰지 않는 까닭은 무엇인가.
  5. Claude Code가 “모든 테스트가 통과하였다”고 보고하였다. 이 보고만으로 기존 요구가 지켜졌다고 판정할 수 없는 경우는 어떤 경우이며, 그것을 알아내려면 무엇을 보아야 하는가.
