2027학년도 「LLM 서비스 개발」의 준비 중인 교재입니다. 편집 상태를 검토하기 위해 미리 공개한 것으로, 수업 전에 내용과 순서가 바뀔 수 있습니다.

학사 7주차 · 교재 06 · 서비스 2: 명령줄 도구

개편 초안 2판(2026-11-18). 명령의 출력은 2026-11-18에 Windows 11의 Git Bash와 파이썬 3.13.7(PYTHONUTF8=1)에서 실행해 얻은 것이다. 견본 재구현의 대조도 같은 PC에서 실행하였다. Claude Code에 보내는 프롬프트(3-6, 4-1, 5-5)의 응답은 확인하지 않았으며, 그 자리에 「실행 결과 자리」를 두었다. 키트는 Service_06장이다. 8절의 API 이름은 2026-11-18에 공개 목록에서 확인하였고, 각 API의 이용 조건은 확인하지 않았다.

4~5장에서는 화면을 관찰해 명세를 되살렸다. 화면은 보이는 것만 말하므로 화면 뒤의 규칙은 추측으로 남았다. 이 장은 대상을 코드로 바꾼다. 코드는 동작의 조건과 결과를 줄 번호와 함께 말해 주므로, 명세의 문장마다 근거를 댈 수 있다. 대신 코드는 왜 그렇게 만들었는지를 말하지 않는다.

대상은 파이썬 표준 라이브러리의 명령줄 도구 python -m json.tool이다. JSON을 검사하고 보기 좋게 다시 찍는 90줄 안팎의 프로그램이다. 이 프로그램에서 명세를 뽑고, 명세만으로 다시 구현해 원본과 출력을 대조한다. 화면의 비교는 사람의 눈으로 하였으나 명령줄 프로그램의 비교는 명령으로 한다. 마지막에 요구, 코드의 위치, 확인 방법을 한 표로 잇는다.

학습 목표

  • 근거의 종류(화면, 코드, 실행 관찰)에 따라 명세에 담기는 것과 담기지 않는 것을 구분할 수 있다.
    • 예시: 「없는 파일을 주면 오류 추적이 나온다」는 실행으로 알고, 「그 동작이 의도인가」는 코드로도 알 수 없다고 적는다.
    • 활용: 졸업 프로젝트에서 남의 코드를 이어받을 때 확인할 것과 물어볼 것을 나눈다.
  • 진입점, 인자 정의, 오류 경로의 순서로 명령줄 프로그램을 읽고, 명세를 EARS 문장과 줄 번호 근거로 뽑을 수 있다.
    • 예시: --no-ensure-ascii의 store_false에서 「기본은 한글을 바꾸어 적는다」를 읽어 낸다.
    • 활용: 처음 보는 오픈소스 도구의 옵션을 문서보다 정확하게 정리한다.
  • 명세만으로 재구현한 프로그램을 원본과 같은 입력으로 실행해 표준 출력, 표준 오류, 종료 코드를 대조하고, 대조가 본 것과 보지 못한 것을 구분할 수 있다.
    • 예시: compare.sh가 「같다」고 한 없는 파일의 경우를 손으로 실행해 표준 오류의 차이를 찾는다.
    • 활용: 리팩터링이나 판 올림 뒤에 동작이 바뀌지 않았는지 확인하는 회귀 검사를 짠다.
  • 요구, 코드의 위치, 확인 방법을 추적표로 잇고, 찾은 빈틈을 명세에 되돌릴 수 있다.
    • 예시: 확인 방법이 없던 요구를 위해 cases.txt에 경우 하나를 더한다.
    • 활용: 팀 프로젝트에서 요구가 바뀔 때 고칠 코드와 다시 돌릴 시험을 찾는다.

1. 코드에서 명세를 뽑는다는 것

1-1. 근거의 종류와 명세

같은 대상이라도 무엇을 근거로 삼는가에 따라 명세에 담기는 것이 다르다.

근거 명세에 잘 담기는 것 담기지 않거나 추측이 되는 것 이 과목의 예
화면(URL, HTML) 보이는 정보 항목, 조작의 종류 화면 뒤의 규칙, 눌러야 나오는 화면 4장의 참고 프로덕트
코드 동작의 조건과 결과, 기본값, 오류 처리(줄 번호를 근거로 댈 수 있다) 왜 그렇게 만들었는지, 누구를 위한 것인지 이 장의 json.tool
실행 관찰 실제 입력에 대한 실제 출력과 종료 코드 시험하지 않은 입력에 대한 동작 이 장의 대조
사람의 관찰과 조사 쓰는 순서, 불편, 맥락 정확한 값과 규칙 7장의 인터뷰

코드는 무엇을 하는지는 말하지만 왜 하는지는 말하지 않는다. 그래서 코드에서 뽑은 명세는 그 코드를 만든 사람이나 쓰는 사람에게 확인받아야 한다. 회사에서 전임자의 프로그램을 이어받을 때, 코드를 읽어 정리한 문서를 들고 전임자에게 「이 동작은 일부러 그렇게 한 것인가」를 묻는 것으로 인수인계가 끝나는 까닭이다.

1-2. 의도와 사실

문서가 말하는 것은 의도이고 코드가 하는 것은 사실이다. 둘은 다를 수 있다. 문서에 없는 동작이 코드에 있고(문서화되지 않은 결정), 문서에 있는 동작이 코드에 없을 수 있다(빠진 구현). 코드에서 명세를 뽑을 때는 문서를 먼저 읽지 않는다. 문서를 보면서 코드를 읽으면 문서에 맞는 부분만 눈에 들어온다.

구현한 쪽이 의식하지 않은 결정도 코드에 남는다. 예외를 처리하지 않아 생긴 동작이 그것이다. 구현한 쪽에서 보면 아무것도 하지 않은 것이므로 결정으로 느껴지지 않는다. 그러나 사용자에게는 정해진 동작이다. 2-2와 3-4에서 그 예를 본다.

1-3. 분석해도 되는 대상과 사용권

코드의 리버스 엔지니어링은 대상의 사용권이 허용하는 범위에서 한다. 이 과목은 대상을 오픈소스 소프트웨어, 키트의 예제, 자기 결과물로 한정한다.

파이썬은 PSF 사용권(Python Software Foundation License Version 2)으로 배포된다. 이 사용권의 2항은 사용자에게 파이썬을 복제하고, 분석하고, 시험하고, 파생 저작물을 만들고, 배포하는 것을 허락한다. 조건은 PSF의 사용권 계약과 저작권 표시를 남기는 것이다. 3항은 파이썬을 바탕으로 만든 파생 저작물을 남에게 내놓을 때 바꾼 내용의 요약을 함께 넣게 한다. 4항은 파이썬을 「있는 그대로(AS IS)」 제공하며 보증하지 않는다고 적는다 [X1].

이 장의 실습에 비추면 다음과 같다.

이 장에서 하는 일 사용권에 비춘 판단
json/tool.py를 읽고 실행해 명세를 뽑는다 분석과 시험은 2항이 허락한다
명세만 보고 jsonfmt.py를 새로 쓴다 원본의 코드를 옮기지 않았으므로 원본의 복제가 아니다. 명세에 원본의 문장(도움말, 오류 안내)을 그대로 옮겨 적었다면 그 부분은 원본에서 온 것으로 적어 둔다
원본의 코드 일부를 내 프로그램에 복사한다 파생 저작물이다. PSF의 저작권 표시를 남기고 바꾼 내용을 요약한다(2항, 3항)

다른 저장소를 대상으로 삼을 때는 저장소의 LICENSE 파일을 먼저 읽는다. 사용권이 없는 저장소는 공개되어 있어도 분석과 재구현을 허락한 것이 아니다. 이 절은 법률 자문이 아니다.

2. 실행으로 관찰하기

2-1. 도움말과 기본 동작

코드를 읽기 전에 프로그램을 써 본다. 먼저 도움말을 본다.

터미널 
python -m json.tool --help

                           --no-indent | --compact]

사용법 줄의 [--indent INDENT | --tab | --no-indent | --compact]에서 세로 막대는 「이 가운데 하나만」이라는 뜻이다. 대괄호는 생략할 수 있다는 뜻이다. 그러므로 infile과 outfile도 생략할 수 있다. 생략하면 무엇을 읽고 어디에 쓰는지는 도움말에 없다.

키트에서 복사한 시험 자료를 넣어 본다. a.json은 한글이 든 자료이고 bad.json은 끝에 쉼표가 남은 잘못된 자료이다.

터미널 
cat a.json
python -m json.tool a.json
{"name": "홍길동", "skills": ["python", "git"], "age": 23}
{
    "name": "\ud64d\uae38\ub3d9",
    "skills": [
        "python",
        "git"
    ],
    "age": 23
}

한글이 \ud64d 꼴로 바뀌어 나온다. 도움말의 --no-ensure-ascii가 이 동작을 끈다. 옵션의 이름이 「끄는」 쪽이므로 기본값은 「ASCII가 아닌 글자를 \u 꼴로 바꾸어 적는다」이다. 도움말에는 기본값이 적혀 있지 않다. 써 보아야 아는 동작이다.

터미널 
python -m json.tool --sort-keys --no-ensure-ascii a.json
python -m json.tool --compact a.json
{
    "age": 23,
    "name": "홍길동",
    "skills": [
        "python",
        "git"

3-1. 읽는 순서

명령줄 프로그램의 코드는 다음 순서로 읽는다.

  1. 진입점. 프로그램이 시작하는 곳. 파이썬에서는 if __name__ == '__main__': 아래이다.
  2. 인자 정의. 인자와 옵션을 정의하는 곳. 옵션의 이름, 기본값, 함께 쓸 수 없는 옵션의 묶음이 여기에 있다.
  3. 입력. 어디서 읽는가(파일, 표준 입력), 어떤 인코딩으로 읽는가.
  4. 처리와 출력. 옵션이 처리에 어떻게 전달되는가, 어디에 쓰는가, 끝에 무엇을 붙이는가.

4-2. 견본 재구현 읽기

다음은 요구 여섯 개짜리 얇은 명세로 만든 견본이다. 명세에는 「파일 또는 표준 입력에서 JSON을 읽어 4칸 들여쓰기로 다시 찍는다」, 「--sort-keys, --indent, --compact」, 「잘못된 JSON과 열 수 없는 파일에는 안내를 내고 종료 코드 1로 끝난다」만 있었다.

[파일: 재구현/jsonfmt.py] (읽기. 교수용 견본 v1)

"""얇은 명세 v1(교수/얇은명세_v1.md)만 보고 만든 재구현의 견본. 명세가 정하지 않은 곳은 구현자가 정하였다."""
import argparse
import json
import sys

def main():
    p = argparse.ArgumentParser(prog="jsonfmt")
    p.add_argument("infile", nargs="?", default="-")
    p.add_argument("--sort-keys", action="store_true")
    p.add_argument("--indent", type=int, default=4)
    p.add_argument("--compact", action="store_true")
    a = p.parse_args()
    try:
        text = sys.stdin.read() if a.infile == "-" else open(a.infile, encoding="utf-8").read()
    except OSError:
        print(f"파일을 열 수 없다: {a.infile}", file=sys.stderr)
        return 1
    try:
        obj = json.loads(text)
    except ValueError as e:
        print(f"JSON이 아니다: {e}", file=sys.stderr)
        return 1
    if a.compact:
        out = json.dumps(obj, sort_keys=a.sort_keys, ensure_ascii=False, separators=(",", ":"))
    else:
        out = json.dumps(obj, sort_keys=a.sort_keys, ensure_ascii=False, indent=a.indent)
    print(out)
    return 0

if __name__ == "__main__":
    sys.exit(main())

명세는 한글을 어떻게 찍을지 정하지 않았다. 구현자는 한글을 그대로 찍기로 정하였다(ensure_ascii=False). 사용자에게는 이쪽이 더 낫다. 그러나 원본과는 다르다. 또 이 견본은 원본과 달리 OSError를 잡아 한 줄 안내를 낸다. 명세의 「열 수 없는 파일에는 안내」를 따른 것이다.

5. 출력의 대조

5-1. 대조의 설계

화면의 비교는 사람이 눈으로 하였다. 명령줄 프로그램은 같은 인자를 두 프로그램에 주고 결과를 명령으로 견줄 수 있다. 이처럼 기준이 되는 프로그램의 출력을 정답으로 삼아 새 프로그램을 시험하는 방법을 차등 시험(differential testing)이라 한다. 원본이 정답을 알려 주는 셈이므로, 기대 출력을 사람이 미리 쓰지 않아도 된다. 대신 원본의 결함도 정답처럼 보인다(3-5).

대조를 짜기 전에 세 가지를 정한다.

정할 것 고를 수 있는 것 이 장의 선택
무엇을 견주는가 표준 출력, 표준 오류, 종료 코드, 출력 파일 표준 출력과 종료 코드. 표준 오류는 5-3에서 따로 본다
얼마나 엄격히 견주는가 바이트까지 같음, 줄 끝과 공백을 무시함, 내용의 갈래만 같음 표준 출력은 바이트까지(cmp). 두 프로그램을 같은 PC에서 실행하므로 줄 끝과 인코딩이 같다
어떤 입력으로 견주는가 정상 입력, 경계값, 잘못된 입력, 옵션의 조합 관찰 기록의 행에서 고른다. 옵션마다 하나, 오류마다 하나

입력을 고를 때는 동작이 달라지는 지점마다 하나씩 고른다. --indent라면 2(보통 값), 0(줄은 바꾸되 들여쓰지 않는 경계), 음수와 숫자가 아닌 값(잘못된 입력)이 서로 다른 경우이다. 같은 갈래의 입력을 여럿 넣는 것보다 갈래마다 하나를 넣는 것이 적은 수로 많은 차이를 찾는다. 시험 자료에 한글이 없으면 한글을 찍는 방식의 차이는 드러나지 않는다. 자료가 차이를 숨기는 경우이다.

같다 | 종료 코드 1, 1 | none.json

위는 4-2의 견본(v1)으로 얻은 출력이다. 정상 입력 넷이 모두 다르다. 무엇이 다른지는 diff로 본다.

터미널 
python -m json.tool a.json > o.out; python jsonfmt.py a.json > r.out
diff o.out r.out
2c2
<     "name": "\ud64d\uae38\ub3d9",
---
>     "name": "홍길동",

2c2는 왼쪽 파일의 2행을 오른쪽 파일의 2행으로 바꾸면(change) 같아진다는 뜻이다. 한 줄이 다르다. 한글을 찍는 방법이다. 네 경우가 모두 같은 원인이다.

  • 확인 10 내 재구현으로 bash compare.sh가 인자마다 한 줄씩 「같다」 또는 「다르다」와 마지막의 합계 줄을 출력하고, 다른 경우 하나를 diff로 열어 다른 줄을 비교.md에 적었다.

5-3. 대조가 보지 못한 것

잘못된 입력 둘은 「같다」로 나왔다. 실제로 같은지 본다.

터미널 
python jsonfmt.py none.json; echo "종료 코드 $?"
python jsonfmt.py bad.json; echo "종료 코드 $?"
파일을 열 수 없다: none.json
종료 코드 1
JSON이 아니다: Illegal trailing comma before end of object: line 1 column 8 (char 7)
종료 코드 1

원본은 없는 파일에 오류 추적을 냈고(2-2), 견본은 한 줄의 안내를 낸다. 동작이 다르다. 그런데 compare.sh는 「같다」고 하였다. 이 도구가 표준 출력과 종료 코드만 보기 때문이다. 오류 안내는 표준 오류로 나가므로 비교되지 않았다(2-3).

검사가 「같다」고 말하는 것은 검사가 본 것이 같다는 뜻이다. 검사가 보지 않은 것은 말하지 않는다. 1장의 점검표, 5장의 인수 조건과 같은 한계이다. 그래서 대조의 결과를 적을 때는 무엇을 견주었는지를 함께 적는다. compare.sh가 합계 줄에 「견준 것」을 찍는 까닭이다.

표준 오류를 견주는 쪽으로 바꾸려 해도 판단이 남는다. 글자까지 견주면 안내 문구가 한 글자만 달라도 「다르다」가 된다. 견본처럼 안내를 한국어로 쓰기로 한 재구현은 모든 오류의 경우가 「다르다」가 된다. 「오류 추적이 나왔는가, 한 줄 안내가 나왔는가」처럼 갈래만 견주는 방법도 있다. 어느 쪽이 맞는가는 명세가 표준 오류에 대해 무엇을 정했는가에 달려 있다.

  • 확인 11 없는 파일에 대한 두 프로그램의 표준 오류가 다르다는 것을 직접 실행해 보았고, compare.sh가 그 차이를 잡지 못한 까닭을 비교.md의 「대조가 보지 못한 것」에 한 줄로 적었다.

5-4. 차이의 원인 분류

차이를 찾으면 원인을 다섯 가지 가운데 하나로 나눈다. 명세 빈틈만 명세로 되돌린다.

원인 뜻 이 장의 예 할 일
① 명세 빈틈 명세가 정하지 않아 구현자가 다르게 정하였다 한글을 찍는 방식 요구를 더한다
② 환경 차이 판, 운영체제, 인코딩, 줄 끝이 달라 생긴 차이 리눅스에서 만든 기대 출력과 Windows의 CRLF 같은 환경에서 다시 대조한다. 명세는 고치지 않는다
③ 시험 자료의 한계 자료가 차이를 드러내지 못하였다 한글이 없는 자료로는 ①이 보이지 않는다 cases.txt와 시험 자료를 늘린다
④ 의도한 차이 원본과 다르게 하기로 명세에서 정하였다 없는 파일에 한 줄 안내 명세에 결정과 까닭을 적어 둔다
⑤ 범위 밖 복원하지 않기로 한 기능 --json-lines, --tab, 출력 파일 명세의 「복원하지 않은 것」에 적는다

ch06/cli에서 cp -n ~/kits/Service_06장/양식/비교_양식.md 비교.md로 양식을 복사해 표를 채운다.

[파일: ch06/cli/비교.md] (표의 예)

| 경우 | 원본 | 재구현 | 견준 것 | 원인 | 명세 조치 |
|---|---|---|---|---|---|
| 한글이 든 입력 | \u 꼴로 바꾼다 | 그대로 찍는다 | 표준 출력 | ① 명세 빈틈 | REQ 추가: 기본은 바꾸어 적고 --no-ensure-ascii로 끈다 |

6. 명세와 코드의 추적

요구가 어느 코드로 구현되었고 무엇으로 확인되는지를 한 표로 잇는다. 이 표를 추적표(traceability matrix)라 한다. 요구가 바뀌면 고칠 코드와 다시 돌릴 확인을 이 표에서 찾는다. 이 장의 추적표는 원본의 근거(줄 번호)와 재구현의 위치를 함께 잇는다. 원본의 줄은 「이 요구가 어디서 왔는가」를, 재구현의 위치는 「이 요구가 어디에 구현되었는가」를 말한다. 양식은 ch06/cli에서 cp -n ~/kits/Service_06장/양식/추적표_양식.md 추적표.md로 복사한다.

[파일: ch06/cli/추적표.md] (예)

| 요구 | 원본의 근거(줄) | 재구현의 위치 | 확인 방법 | 결과 |
|---|---|---|---|---|
| REQ-01 파일 또는 표준 입력에서 읽는다 | 23-25, 60-63 | main()의 첫 try | cases.txt 1행, 표준 입력은 「< a.json」 행 | 같다 |
| REQ-05 --compact | 46-47, 55-57 | json.dumps의 separators | cases.txt 3행 | 같다 |
| REQ-06 열 수 없는 파일 | 처리하는 줄 없음 | 첫 try의 OSError | 손으로 실행(의도한 차이) | 한 줄 안내 |
| REQ-07 ASCII가 아닌 글자 | 31-32, 53 | json.dumps의 ensure_ascii | cases.txt 1~4행 | 같다 |

표를 두 방향으로 읽는다. 요구에서 확인으로 읽으면 확인 방법이 없는 요구가 보인다. 확인되지 않은 요구는 구현되었는지 알 수 없다. 확인에서 요구로 읽으면 어느 요구에도 닿지 않는 시험이 보인다. 그 시험은 명세에 없는 동작을 지키고 있다. 같은 키가 두 번 나오는 경우가 그 예이다. 명세에는 없지만 json 모듈이 정한 동작이다. 그런 시험은 지우지 말고 까닭을 적는다.

추적은 코드 안에서도 한다. 요구를 구현한 줄 위의 주석에 # REQ-07처럼 요구 번호를 적어 두면, 코드에서 명세로 돌아가는 가장 짧은 길이 된다. 요구 문장을 주석에 옮기지는 않는다. 명세가 바뀌면 옮긴 문장이 거짓이 된다.

  • 확인 13 추적표.md의 모든 요구에 원본의 근거와 확인 방법이 있고, 확인 방법이 없던 요구를 위해 cases.txt에 경우를 하나 이상 더하였다.

8. 읽을거리: 공개 API로 만드는 졸업 프로젝트의 아이디어

서비스 1은 「참고 프로덕트의 화면 구성 + 공개 API의 자료」로 만들었다. 졸업 프로젝트도 같은 방법으로 시작할 수 있다. 이 절은 주제를 정할 때 쓸 재료를 모은 것이다. 읽기만 하며 실습은 없다.

API의 이름은 공개 목록 public-apis-4Kr에 적힌 것이다 [Y1]. 이 목록은 한국의 공개 API를 35개 분류의 표로 모은 것으로, API마다 설명과 인증 방식(대부분 apiKey)이 적혀 있다. 2026-11-18에 읽은 목록은 「2026년 11월 8일 기준」이라고 적혀 있었고, 마지막 커밋은 2026-11-17이었다. 아래 API의 이름이 목록에 있는지, 이름에 든 기관이 목록에 적힌 주소의 기관과 맞는지는 같은 날 확인하였다(8-2 아래의 표). 그러나 각 API가 어떤 항목을 주는지, 받은 자료를 공개 서비스에 써도 되는지는 확인하지 않았다. 난이도는 집필자의 어림이다. 주제로 정하기 전에 제공 기관의 개발 문서와 이용 조건에서 직접 확인한다(4장 3절).

[최신 자료 자리: 8절 API들의 이용 조건] 각 API의 인증키 발급 조건(개인, 기업, 심사), 하루 호출 한도, 받은 자료를 공개 웹에 다시 보여도 되는지(출처 표시, 상업적 이용, 변경 금지 같은 조건). 확인할 곳: 8-2 아래 표의 각 주소와 공공데이터포털(https://www.data.go.kr/)의 이용 허락 범위. 이용 조건은 바뀔 수 있으므로 주제를 정하는 학기에 다시 확인한다. 2026-11-18에는 목록의 인증 열(apiKey)만 보았다.

8-1. 졸업 프로젝트에 알맞은 주제의 조건

AI소프트웨어학과의 졸업 프로젝트는 한 학기 안에 조원 서너 명이 만들어 남에게 보일 수 있어야 한다. 다음 네 조건을 갖춘 주제가 알맞다.

조건 뜻 갖추지 못하면
실제 자료가 있다 공개 API에서 받은 자료로 화면을 채운다 지어낸 자료로 만든 화면은 시연에서 쓸모를 보이기 어렵다
한 사람의 불편을 푼다 타겟 한 사람과 그 사람의 불편 하나가 있다 「누구나 쓰는 서비스」는 기능을 고를 기준이 없다
AI가 맡는 일이 분명하다 AI 없이는 하기 어려운 일 하나를 AI가 맡는다 AI가 장식이 된다. 규칙으로 되는 일은 규칙으로 한다
작게 시작할 수 있다 4주 안에 돌아가는 가장 작은 판이 있다 학기 말까지 돌아가는 것이 없다

8-3. AI가 맡는 일의 다섯 가지 꼴

공개 API의 자료에 AI를 붙이는 방법은 대체로 다음 다섯 가지이다. 9장과 10장에서 구현 방법을 다룬다.

꼴 하는 일 예 주의
문장을 조건으로 바꾸기 사용자의 문장을 지역, 날짜, 종류 같은 검색 조건으로 바꾼다 「학교 근처에서 저녁 먹을 곳」 → 위치와 업종 바꾼 조건을 화면에 보여 사용자가 고칠 수 있게 한다
글에서 항목 뽑기 긴 글에서 정해진 항목을 뽑는다 공고의 글 → 요구하는 기술의 목록 글에 없는 것을 지어내지 않는지 견본으로 확인한다
분류하기 문장을 정해 둔 갈래 가운데 하나로 나눈다 고장 신고 → 고장, 주차 방해, 요금 문제 갈래를 미리 정하고 「모르겠음」을 둔다
요약하기 여러 건의 자료를 한 문단으로 줄인다 실거래 목록 → 이 동네 시세의 한 문단 수는 프로그램이 계산해 넘긴다. AI에게 셈을 시키지 않는다
근거를 대며 답하기 자료에서 관련된 부분을 찾아 그것만을 근거로 답한다 「내일 체험 학습을 가도 될까」 → 예보를 근거로 답 근거가 된 자료를 함께 보이고, 자료에 없으면 「자료에 없다」고 답한다(10장)

어느 꼴이든 AI의 결과를 사용자가 확인할 수 있게 화면을 만든다. 이 과목의 규칙(1장)을 사용자에게도 적용하는 것이다.

8-4. 서비스 아이디어 열두 가지

난이도는 쓰는 API의 수, 지도의 사용, AI가 맡는 일의 어려움으로 어림하였다. 「먼저 만들 것」은 4주 안에 돌아가게 할 가장 작은 판이다.

① 등하교 공기 알림판 (난이도 하)

  • 쓰는 API: 에어코리아 실시간 대기오염정보, 기상청 동네예보
  • 참고할 화면: 날씨 앱의 첫 화면(오늘의 상태를 한 문장과 색으로 보이는 구성)
  • 타겟: 초등학생 자녀를 둔 보호자
  • 해결하는 불편: 아침마다 날씨 앱과 미세먼지 앱을 따로 열어 수치를 읽고 판단해야 한다.
  • 기능: 학교의 위치를 고르면 등교와 하교 시각의 미세먼지와 비 예보를 한 줄로 보이고 「마스크 필요」, 「우산 필요」를 표시한다.
  • AI가 맡는 일: 「내일 체험 학습을 가도 될까」 같은 물음에 예보 자료를 근거로 답한다. 수치를 등급으로 바꾸는 일은 규칙으로 하고 AI를 쓰지 않는다.
  • 먼저 만들 것: 지역 하나의 오늘 수치와 표시
  • 넓힐 방향: 여러 학교의 저장, 주간 예보, 알림
  • 기대효과: 판단에 필요한 정보가 한 화면에 모이고 수치를 해석하지 않아도 된다.

② 지금 여는 응급실과 약국 (난이도 중)

  • 쓰는 API: 중앙응급의료센터, 카카오맵
  • 참고할 화면: 지도 앱의 장소 목록(지도와 거리 순 목록을 나란히 보이는 구성)
  • 타겟: 밤이나 휴일에 아이가 아픈 보호자, 혼자 사는 대학생
  • 해결하는 불편: 급할 때 검색 결과에서 「지금 여는 곳」을 골라내기 어렵다.
  • 기능: 현재 위치에서 가까운 응급실과 지금 영업하는 약국을 거리 순으로 보이고 전화 걸기 단추를 둔다.
  • AI가 맡는 일: 「지금 여는 소아과 근처 약국」 같은 문장을 지역, 시각, 종류의 조건으로 바꾼다. 증상을 듣고 병을 짐작하는 기능은 만들지 않는다.
  • 먼저 만들 것: 지역 하나의 목록과 「지금 여는 곳」 거르기
  • 넓힐 방향: 지도 표시, 길 찾기 연결
  • 기대효과: 찾는 시간이 줄고 닫은 곳으로 가는 헛걸음이 준다. 화면에 119 안내를 먼저 보인다.

③ 빈 충전기 찾기 (난이도 중)

  • 쓰는 API: 전기차충전기정보, 네이버 지도 또는 카카오맵
  • 참고할 화면: 주차장 찾기 앱(지도 위에 빈자리의 수를 표시하는 구성)
  • 타겟: 집에 충전기가 없는 전기차 운전자
  • 해결하는 불편: 충전소에 도착해서야 모두 사용 중이거나 고장인 것을 안다.
  • 기능: 주변 충전소를 충전기의 종류(급속, 완속)와 사용 가능 여부로 걸러 보인다.
  • AI가 맡는 일: 사용자가 남긴 고장 신고의 문장을 「고장, 주차 방해, 요금 문제」로 분류해 충전소마다 모아 보인다.
  • 먼저 만들 것: 지역 하나의 충전소 목록과 상태 거르기
  • 넓힐 방향: 지도, 자주 가는 곳 저장, 신고 기능
  • 기대효과: 출발 전에 갈 곳을 정할 수 있다.

④ 자취생 장바구니 물가 (난이도 중)

  • 쓰는 API: 한국소비자원 참가격, KAMIS 농수축산물 유통 Open API
  • 참고할 화면: 가격 비교 사이트의 상품 목록(품목마다 최저가와 가격의 변화를 보이는 구성)
  • 타겟: 식비를 줄이려는 자취 대학생
  • 해결하는 불편: 어느 가게가 싼지, 지금이 비싼 때인지 알 방법이 없다.
  • 기능: 자주 사는 품목 열 개를 고르면 지역의 판매점별 가격과 지난주 대비 변화를 보인다.
  • AI가 맡는 일: 「김치찌개 2인분」 같은 문장에서 재료를 뽑아 품목과 맞추고, 재료의 가격을 더해 보인다.
  • 먼저 만들 것: 품목 열 개의 가격표
  • 넓힐 방향: 요리별 재료비, 가격 변화 그래프
  • 기대효과: 장보는 곳과 때를 근거를 가지고 정한다.

⑤ 이번 주말 공연과 전시 (난이도 하)

  • 쓰는 API: KOPIS 공연예술통합전산망, 한국문화정보원
  • 참고할 화면: 예매 사이트의 목록(포스터 카드, 날짜와 지역 거르기)
  • 타겟: 주말에 할 일을 찾는 대학생과 직장인
  • 해결하는 불편: 예매 사이트마다 따로 찾아야 하고 지역의 작은 공연은 찾기 어렵다.
  • 기능: 이번 주말에 우리 지역에서 하는 공연과 전시를 날짜, 장르, 가격대로 걸러 보인다. 예매는 원래의 쪽으로 보낸다.
  • AI가 맡는 일: 「조용하고 2만 원 아래인 것」 같은 취향의 문장으로 고르고, 고른 까닭을 공연의 소개 글에서 찾아 한 줄로 붙인다.
  • 먼저 만들 것: 지역 하나의 이번 주 목록과 거르기
  • 넓힐 방향: 취향 문장 검색, 찜 목록
  • 기대효과: 한곳에서 견주어 고르고 지역 공연이 눈에 띈다.

⑥ 대중교통 당일 여행 (난이도 상)

  • 쓰는 API: 한국관광공사 TourAPI 4.0, 기상청 동네예보, ODsay 대중교통 API
  • 참고할 화면: 여행 일정 앱(하루의 장소를 시간 순으로 늘어놓은 구성)
  • 타겟: 차가 없는 대학생
  • 해결하는 불편: 관광 정보, 교통편, 날씨를 따로 찾아 맞추어 보아야 한다.
  • 기능: 출발지를 넣으면 대중교통으로 갈 수 있는 관광지를 이동 시간 순으로 보이고 그날의 날씨를 함께 보인다.
  • AI가 맡는 일: 고른 관광지 셋으로 하루 일정의 초안을 쓴다. 장소의 설명과 이동 시간은 API의 자료만 쓰게 하고, 자료에 없는 것은 쓰지 않게 한다.
  • 먼저 만들 것: 출발지 하나에서 갈 수 있는 관광지 목록
  • 넓힐 방향: 일정 초안, 날씨에 따른 바꾸기
  • 기대효과: 갈 수 있는 곳의 범위를 한 번에 안다.

  • 기능: 동네를 고르면 최근 전월세 실거래의 보증금과 월세의 범위를 보인다.
  • AI가 맡는 일: 실거래 목록을 「최근 여섯 달 이 동네의 전세는 얼마에서 얼마 사이」처럼 한 문단으로 요약한다. 수는 프로그램이 계산해 넘기고 AI는 문장만 쓴다.
  • 먼저 만들 것: 동네 하나의 실거래 목록과 범위
  • 넓힐 방향: 지도, 동네 견주기
  • 기대효과: 제시된 가격이 높은지 낮은지를 견줄 기준이 생긴다. 아파트의 자료이므로 원룸과 오피스텔은 다른 자료가 필요하다.

  • 참고할 화면: 식단 기록 앱(끼니마다 음식을 더하고 하루의 합계를 보이는 구성)
  • 타겟: 운동을 시작한 대학생

  • 기능: 먹은 음식을 검색해 더하면 하루의 열량과 단백질의 합계를 보인다.
  • AI가 맡는 일: 「점심에 김치찌개와 밥 한 공기」 같은 문장에서 음식과 양을 뽑아 자료의 항목과 맞춘다. 맞춘 결과를 사용자가 확인하고 고칠 수 있게 한다.
  • 먼저 만들 것: 음식 검색과 하루 합계
  • 넓힐 방향: 문장 입력, 주간 기록

정리

  • 코드는 동작의 조건과 결과를 줄 번호와 함께 말하지만 왜 그렇게 만들었는지는 말하지 않는다. 코드에서 뽑은 명세는 사람에게 확인받는다.
  • 코드를 읽기 전에 실행해 관찰한다. 정상 입력과 잘못된 입력, 표준 출력과 표준 오류와 종료 코드를 함께 본다.
  • 명령줄 프로그램은 진입점, 인자 정의, 입력, 처리와 출력, 오류 경로의 순서로 읽는다. 인자 표가 도움말에 없는 기본값을 드러낸다.
  • 처리하지 않아 생긴 동작과 결함도 코드에 남는다. 그것을 요구로 옮길지 더 나은 동작을 정할지는 명세를 쓰는 사람이 정하고, 정한 것을 적는다.
  • 재구현하는 쪽에는 근거(줄 번호)와 대상의 이름을 주지 않는다.
  • 명령줄 프로그램의 대조는 명령으로 한다. 대조가 「같다」고 한 것은 대조가 본 것이 같다는 뜻이다.
  • 추적표는 요구, 원본의 근거, 재구현의 위치, 확인 방법을 잇는다. 확인 방법이 없는 요구는 구현되었는지 알 수 없다.

개념 점검

  1. 코드에서 뽑은 명세가 화면에서 뽑은 명세보다 나은 점 하나와, 코드로도 알 수 없는 것 하나를 이 장의 예로 들어라.
  2. --no-ensure-ascii라는 옵션 이름에서 기본 동작을 어떻게 추론하는가. 그 추론을 코드의 어느 낱말이 뒷받침하는가.
  3. 없는 파일을 주었을 때 3.12와 3.13의 종료 코드가 다른 까닭을 코드의 변화로 설명하라.
  4. compare.sh가 「같다 6, 다르다 0」을 낸 뒤에도 두 프로그램이 같다고 말할 수 없는 까닭 두 가지를 들어라.
  5. 원본의 결함(--json-lines와 파일)을 명세에 어떻게 적어야 하는가. 요구로 옮기면 무엇이 잘못되는가.
