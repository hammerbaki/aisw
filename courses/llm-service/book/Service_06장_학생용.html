6장

코드의 리버스 엔지니어링

2027학년도 「LLM 서비스 개발」의 준비 중인 교재입니다. 편집 상태를 검토하기 위해 미리 공개한 것으로, 수업 전에 내용과 순서가 바뀔 수 있습니다.

학사 7주차 · 교재 06 · 서비스 2: 명령줄 도구

개편 초안(2026-11-18). 이 장은 plan/개편안.md의 단원형 구성에 따라 새로 쓴 초안이다. 명령의 출력은 집필 환경(Linux, Python 3.13.18)에서 2026-11-18에 실제로 실행해 얻은 것이며, 실습실 PC(Windows 11, Git Bash)에서는 아직 확인하지 않았다. 「실행 전」이라고 적은 곳의 Claude Code 프롬프트는 응답을 확인하지 않았다. 키트는 아직 없다. 8절(공개 API로 만들 수 있는 서비스의 예)은 2026-11-18에 더한 읽을거리이며, API의 항목과 이용 조건은 확인하지 않았다.

4~5장에서는 화면을 관찰해 명세를 되살렸다. 화면은 보이는 것만 말한다. 화면 뒤의 규칙은 추측으로 남았다. 이 장은 대상을 코드로 바꾼다. 코드는 동작의 조건과 결과를 줄 번호와 함께 말해 주므로, 명세의 문장마다 근거를 댈 수 있다. 대신 코드는 왜 그렇게 만들었는지를 말하지 않는다.

대상은 파이썬 표준 라이브러리의 명령줄 도구 python -m json.tool이다. JSON을 검사하고 보기 좋게 다시 찍는 90줄짜리 프로그램이다. 이 프로그램에서 명세를 뽑고, 명세만으로 다시 구현해 원본과 출력을 대조한다. 화면의 비교는 사람의 눈으로 하였으나 명령줄 프로그램의 비교는 명령으로 한다. 마지막에 요구, 코드의 위치, 확인 명령을 한 표로 잇는다.

학습 목표

  • 근거의 종류(화면, 코드, 관찰)에 따라 명세에 담기는 것과 담기지 않는 것을 구분할 수 있다.
  • 실행 관찰과 코드 읽기로 명령줄 프로그램의 명세를 EARS 문장으로 뽑고, 문장마다 근거(줄 번호 또는 실행 결과)를 붙일 수 있다.
  • 명세만으로 재구현한 프로그램을 원본과 같은 입력으로 실행해 출력과 종료 코드를 대조할 수 있다.
  • 대조가 본 것과 보지 못한 것을 구분하고, 찾은 빈틈을 명세에 되돌릴 수 있다.
  • 요구, 코드의 위치, 확인 명령을 추적표로 이을 수 있다.

1. 코드에서 명세를 뽑는다는 것

1-1. 근거의 종류와 명세

같은 대상이라도 무엇을 근거로 삼는가에 따라 명세에 담기는 것이 다르다.

근거 명세에 잘 담기는 것 담기지 않거나 추측이 되는 것 이 과목의 예
화면(URL, HTML) 보이는 정보 항목, 조작의 종류 화면 뒤의 규칙, 눌러야 나오는 화면 4장의 채용 게시판
코드 동작의 조건과 결과, 기본값, 오류 처리(줄 번호를 근거로 댈 수 있다) 왜 그렇게 만들었는지, 누구를 위한 것인지 이 장의 json.tool
실행 관찰 실제 입력에 대한 실제 출력과 종료 코드 시험하지 않은 입력에 대한 동작 이 장의 대조
사람의 관찰과 조사 쓰는 순서, 불편, 맥락 정확한 값과 규칙 7장의 인터뷰

코드는 무엇을 하는지는 말하지만 왜 하는지는 말하지 않는다. 그래서 코드에서 뽑은 명세는 그 코드를 만든 사람이나 쓰는 사람에게 확인받아야 한다. 인수인계의 리버스 엔지니어링이 전임자와의 대화로 끝나는 까닭이다.

1-2. 의도와 사실

문서가 말하는 것은 의도이고 코드가 하는 것은 사실이다. 둘은 다를 수 있다. 문서에 없는 동작이 코드에 있고(문서화되지 않은 결정), 문서에 있는 동작이 코드에 없을 수 있다(빠진 구현). 코드에서 명세를 뽑을 때는 문서를 먼저 읽지 않는다. 문서를 보면서 코드를 읽으면 문서에 맞는 부분만 눈에 들어온다.

구현한 쪽이 의식하지 않은 결정도 코드에 남는다. 기본값을 그대로 두어 생긴 동작이 그것이다. 구현한 쪽에서 보면 아무것도 하지 않은 것이므로 결정으로 느껴지지 않는다. 2에서 그 예를 본다.

1-3. 분석해도 되는 대상

코드의 리버스 엔지니어링은 대상의 사용권이 허용하는 범위에서 한다. 이 과목은 대상을 오픈소스 소프트웨어, 키트의 예제, 자기 결과물로 한정한다. 파이썬은 Python Software Foundation License Version 2로 배포되며, 이 사용권은 복제, 분석, 시험, 파생 저작물의 작성을 허용한다 [X1]. 다른 저장소를 대상으로 삼을 때는 저장소의 LICENSE 파일을 먼저 읽는다. 사용권이 없는 저장소는 공개되어 있어도 분석과 재구현을 허락한 것이 아니다. 이 절은 법률 자문이 아니다.

2. 실행으로 관찰하기

2-1. 도움말과 기본 동작

코드를 읽기 전에 프로그램을 써 본다. 먼저 도움말을 본다.

터미널 
python -m json.tool --help
usage: python -m json.tool [-h] [--sort-keys] [--no-ensure-ascii]
                           [--json-lines] [--indent INDENT | --tab |
                           --no-indent | --compact]
                           [infile] [outfile]

A simple command line interface for json module to validate and pretty-print
JSON objects.

positional arguments:
  infile             a JSON file to be validated or pretty-printed
  outfile            write the output of infile to outfile

options:
  -h, --help         show this help message and exit
  --sort-keys        sort the output of dictionaries alphabetically by key
  --no-ensure-ascii  disable escaping of non-ASCII characters
  --json-lines       parse input using the JSON Lines format. Use with --no-
                     indent or --compact to produce valid JSON Lines output.
  --indent INDENT    separate items with newlines and use this number of
                     spaces for indentation
  --tab              separate items with newlines and use tabs for indentation
  --no-indent        separate items with spaces rather than newlines
  --compact          suppress all whitespace separation (most compact)

시험할 입력을 만든다. 한글이 든 자료 하나와 잘못된 자료 하나이다.

터미널 
printf '{"name": "홍길동", "skills": ["python", "git"], "age": 23}\n' > a.json
printf '{"a": 1,}\n' > bad.json
python -m json.tool a.json
{
    "name": "홍길동",
    "skills": [
        "python",
        "git"
    ],
    "age": 23
}

한글이 홍 꼴로 바뀌어 나온다. 도움말의 --no-ensure-ascii가 이 동작을 끈다. 기본값이 「ASCII가 아닌 글자를 바꾸어 적는다」라는 뜻이다. 도움말에는 기본값이 적혀 있지 않다. 써 보아야 아는 동작이다.

터미널 
python -m json.tool --sort-keys --no-ensure-ascii a.json
python -m json.tool --compact a.json
{
    "age": 23,
    "name": "홍길동",
    "skills": [
        "python",
        "git"
    ]
}
{"name":"홍길동","skills":["python","git"],"age":23}
  • 확인 2 a.json의 기본 출력에서 한글이 \u로 시작하는 글자로 나오고, --no-ensure-ascii를 주면 한글 그대로 나온다.

2-2. 잘못된 입력

정상 입력만 보면 명세의 절반만 본 것이다. 잘못된 입력에 대한 동작과 종료 코드를 본다. 종료 코드는 echo $?로 본다. 0은 성공이고 그 밖의 값은 실패이다.

python -m json.tool none.json; echo "종료 코드 $?"
python -m json.tool --indent 2 --compact a.json; echo "종료 코드 $?"

2-3. 관찰 기록

관찰한 것을 표로 적는다. 코드를 읽은 뒤의 명세와 대조할 기준이다. AI의 분석을 보기 전에 저장한다.

3. 코드를 읽어 명세 뽑기

3-1. 읽는 순서

명령줄 프로그램의 코드는 다음 순서로 읽는다.

  1. 입구. 인자와 옵션을 정의하는 곳. 옵션의 이름, 기본값, 함께 쓸 수 없는 옵션의 묶음이 여기에 있다.
  2. 입력. 어디서 읽는가(파일, 표준 입력), 어떤 인코딩으로 읽는가.
  3. 처리. 옵션이 처리에 어떻게 전달되는가.
  4. 출력. 어디에 쓰는가, 끝에 무엇을 붙이는가.
  5. 오류. 어떤 예외를 잡고 어떤 예외를 잡지 않는가. 잡지 않는 예외가 2-2의 오류 추적이 된다.

줄 수를 먼저 본다. 90줄이면 사람이 끝까지 읽을 수 있다. AI에게 맡기더라도 사람이 읽을 수 있는 크기의 대상을 고르는 것이 첫 결정이다.

터미널 
wc -l "$(python -c "import json.tool, inspect; print(inspect.getsourcefile(json.tool))")"
90 /usr/local/lib/python3.13/json/tool.py

- 코드가 실제로 하는 동작을 EARS 문장으로 쓴다. 형식: `- **REQ-01** [문형] 문장. (근거: 줄 번호)`

파일은 만들지 마라.

4-2. 견본 재구현 읽기 (읽기)

다음은 요구 여섯 개짜리 얇은 명세로 만든 견본이다. 명세에는 「파일 또는 표준 입력에서 JSON을 읽어 들여쓰기 4칸으로 다시 찍는다」, 「--sort-keys, --indent, --compact」, 「잘못된 JSON과 열 수 없는 파일에는 안내를 내고 종료 코드 1로 끝난다」만 있었다.

[파일: 재구현/jsonfmt.py] (읽기. 교수용 견본)

"""복원 명세 v1만 보고 만든 재구현의 견본. 명세가 정하지 않은 곳은 구현자가 정하였다."""
import argparse
import json
import sys

def main():
    p = argparse.ArgumentParser(prog="jsonfmt")
    p.add_argument("infile", nargs="?", default="-")
    p.add_argument("--sort-keys", action="store_true")
    p.add_argument("--indent", type=int, default=4)
    p.add_argument("--compact", action="store_true")
    a = p.parse_args()
    try:
        text = sys.stdin.read() if a.infile == "-" else open(a.infile, encoding="utf-8").read()
    except OSError:
        print(f"파일을 열 수 없다: {a.infile}", file=sys.stderr)
        return 1
    try:
        obj = json.loads(text)
    except ValueError as e:
        print(f"JSON이 아니다: {e}", file=sys.stderr)
        return 1
    if a.compact:
        out = json.dumps(obj, sort_keys=a.sort_keys, ensure_ascii=False, separators=(",", ":"))
    else:
        out = json.dumps(obj, sort_keys=a.sort_keys, ensure_ascii=False, indent=a.indent)
    print(out)
    return 0

if __name__ == "__main__":
    sys.exit(main())

명세는 한글을 어떻게 찍을지 정하지 않았다. 구현자는 한글을 그대로 찍기로 정하였다(ensure_ascii=False). 사용자에게는 이쪽이 더 낫다. 그러나 원본과는 다르다.

5. 출력의 대조

5-1. 같은 입력, 두 프로그램

화면의 비교는 사람이 눈으로 하였다. 명령줄 프로그램은 같은 인자를 두 프로그램에 주고 표준 출력과 종료 코드를 명령으로 견줄 수 있다. 시험할 인자를 한 줄에 하나씩 적는다.

파일: 재구현/cases.txt 
a.json
--sort-keys a.json
--compact a.json
--indent 2 a.json
bad.json
none.json
파일: 재구현/compare.sh 
#!/bin/bash
# 원본과 재구현에 같은 인자를 주고 표준 출력과 종료 코드를 견준다.
while read -r args; do
  python -m json.tool $args > o.out 2> o.err; oc=$?
  python jsonfmt.py $args > r.out 2> r.err; rc=$?
  if cmp -s o.out r.out && [ $oc -eq $rc ]; then res="같다"; else res="다르다"; fi
  echo "$res | 종료 코드 $oc, $rc | $args"
done < cases.txt
터미널 
cd ~/llm-service-lab/ch06/cli/재구현

다르다 | 종료 코드 0, 0 | --sort-keys a.json
다르다 | 종료 코드 0, 0 | --compact a.json
다르다 | 종료 코드 0, 0 | --indent 2 a.json
같다 | 종료 코드 1, 1 | bad.json
같다 | 종료 코드 1, 1 | none.json

위는 4-2의 견본으로 얻은 출력이다. 정상 입력 넷이 모두 다르다. 무엇이 다른지는 diff로 본다.

터미널

diff o.out r.out
2c2
<     "name": "홍길동",
---
>     "name": "홍길동",

한 줄이 다르다. 한글을 찍는 방법이다. 네 경우가 모두 같은 원인이다.

  • 확인 7 bash compare.sh가 인자마다 한 줄씩 「같다」 또는 「다르다」를 출력하고, 다른 경우 하나를 diff로 열어 다른 줄을 찾았다.

5-2. 대조가 보지 못한 것

잘못된 입력 둘은 「같다」로 나왔다. 실제로 같은지 본다.

터미널 
python jsonfmt.py none.json; echo "종료 코드 $?"
python jsonfmt.py bad.json; echo "종료 코드 $?"
파일을 열 수 없다: none.json
종료 코드 1
JSON이 아니다: Illegal trailing comma before end of object: line 1 column 8 (char 7)
종료 코드 1

원본은 없는 파일에 오류 추적을 냈고(2-2), 견본은 한 줄의 안내를 낸다. 동작이 다르다. 그런데 compare.sh는 「같다」고 하였다. 이 도구가 표준 출력과 종료 코드만 보기 때문이다. 오류 안내는 표준 오류로 나가므로 비교되지 않았다.

검사가 「같다」고 말하는 것은 검사가 본 것이 같다는 뜻이다. 검사가 보지 않은 것은 말하지 않는다. 1장의 점검표, 5장의 인수 조건과 같은 한계이다. 그래서 대조의 결과를 적을 때는 무엇을 견주었는지를 함께 적는다.

  • 확인 8 없는 파일에 대한 두 프로그램의 동작이 다르다는 것을 직접 실행해 보았고, compare.sh가 그 차이를 잡지 못한 까닭을 비교.md에 한 줄로 적었다.

5-3. 차이의 분류와 명세 조치

차이의 원인은 5장의 다섯 가지로 나눈다. 명세 빈틈만 명세로 되돌린다.

[파일: ch06/cli/비교.md] (표의 예)

| 경우 | 원본 | 재구현 | 견준 것 | 원인 | 명세 조치 |
|---|---|---|---|---|---|
| 한글이 든 입력 | \u 꼴로 바꾼다 | 그대로 찍는다 | 표준 출력 | ① 명세 빈틈 | REQ 추가: 기본은 바꾸어 적고 --no-ensure-ascii로 끈다 |
| 없는 파일 | 오류 추적, 종료 코드 1 | 한 줄 안내, 종료 코드 1 | 손으로 실행 | ④ 의도한 차이 | 명세의 요구를 그대로 둔다 |
| 잘못된 JSON의 안내 문구 | 영문 한 줄 | 「JSON이 아니다: 」를 앞에 붙인다 | 손으로 실행 | ① 명세 빈틈 | 열린 질문: 안내 문구를 원본과 같게 할 것인가 |

없는 파일의 동작은 원본을 따르지 않기로 하였다. 복원은 복제가 아니다. 원본의 동작이 처리하지 않아 생긴 것으로 보이면, 명세는 더 나은 동작을 정할 수 있다. 다만 그 결정을 「의도한 차이」로 적어 둔다. 적어 두지 않으면 다음에 대조하는 사람이 같은 차이를 다시 조사한다.

5-4. 명세를 고쳐 다시 맞추기

6. 명세와 코드의 추적

요구가 어느 코드로 구현되었고 무엇으로 확인되는지를 한 표로 잇는다. 요구가 바뀌면 고칠 코드와 다시 돌릴 확인을 이 표에서 찾는다.

[파일: ch06/cli/추적표.md] (예)

| 요구 | 재구현의 위치 | 확인 방법 | 결과 |
|---|---|---|---|
| REQ-01 파일 또는 표준 입력에서 읽는다 | jsonfmt.py main()의 입력 부분 | cases.txt 1행, 표준 입력은 손으로 | 같다 |
| REQ-04 --compact | jsonfmt.py의 출력 부분 | cases.txt 3행 | 같다 |
| REQ-08 열 수 없는 파일 | jsonfmt.py의 OSError 처리 | 손으로 실행(의도한 차이) | 한 줄 안내 |
| REQ-11 ASCII가 아닌 글자 | jsonfmt.py의 ensure_ascii | cases.txt 1~4행 | 같다 |

표를 두 방향으로 읽는다. 요구에서 확인으로 읽으면 확인 방법이 없는 요구가 보인다. 확인되지 않은 요구는 구현되었는지 알 수 없다. 확인에서 요구로 읽으면 어느 요구에도 닿지 않는 시험이 보인다. 그 시험은 명세에 없는 동작을 지키고 있다.

  • 확인 10 추적표.md의 모든 요구에 확인 방법이 있고, cases.txt에 확인 방법이 없던 요구를 위한 경우를 하나 이상 더하였다.

7. 핵심 실습: json.tool의 명세 추출과 재구현 대조

1~6절의 따라 하기가 이 실습의 앞부분이다. 여기서는 각자의 재구현으로 같은 일을 끝까지 한다.

번호 완료 기준 확인하는 방법
1 명세.md에 EARS 요구가 10개 이상이고 요구마다 근거가 있다 파일을 읽는다
2 재구현/명세.md에 근거와 대상의 이름이 없다 grep -c
3 내 재구현으로 bash compare.sh가 실행되고 cases.txt가 10행 이상이다 실행
4 비교.md에 차이 네 행 이상이 원인, 견준 것과 함께 있다 파일을 읽는다
5 compare.sh가 표준 오류도 견주도록 고쳤거나, 견주지 않는 까닭을 적었다 비교.md
6 명세.md에 ← 추가가 하나 이상 있고 추적표.md가 있다 파일을 읽는다

진행 순서는 다음과 같다.

  1. 각자의 Claude Code로 3-2의 추출과 4-1의 재구현을 한다. 견본(jsonfmt.py)을 복사하지 않는다.
  2. cases.txt에 경우를 더해 10행 이상으로 만든다. 표준 입력, 같은 키, 빈 입력, --indent 0처럼 관찰 기록의 「보고도 알 수 없는 것」에서 고른다.
  3. bash compare.sh를 실행하고 다른 경우를 diff로 연다.
  4. 「같다」로 나온 경우 가운데 잘못된 입력을 손으로 실행해 표준 오류를 본다. compare.sh에 cmp -s o.err r.err를 더할지 정한다. 더하면 안내 문구가 한 글자만 달라도 「다르다」가 된다. 그것이 원하는 엄격함인지 판단해 비교.md에 적는다.
  5. 명세 빈틈 하나를 명세에 되돌리고 재구현 세션을 이어 반영한 뒤 다시 대조한다.
  6. 추적표를 쓰고 커밋한다.

8. 읽을거리: 공개 API로 만들 수 있는 서비스의 예

서비스 1은 「참고 프로덕트의 화면 구성 + 공개 API의 자료」로 만들었다. 같은 방법으로 만들 수 있는 서비스의 예를 모았다. 졸업 프로젝트와 프로젝트실습의 주제를 정할 때 출발점으로 쓴다. 이 절은 읽기만 하며 실습은 없다.

API의 이름은 공개 목록 public-apis-4Kr에 적힌 것이다[Y1]. 이 목록은 한국의 공개 API를 36개 분류로 모은 것으로, API마다 설명과 인증 방식이 표로 정리되어 있다(마지막 갱신 2026-09-07). 아래의 예는 아이디어이다. 각 API가 어떤 항목을 주는지, 인증키가 필요한지, 받은 자료를 공개 서비스에 써도 되는지는 확인하지 않았다. 주제로 정하기 전에 제공 기관의 개발 문서와 이용 조건에서 직접 확인한다(4장 3절).

8-1. 서비스 아이디어 열 가지

① 등하교 공기 알림판

  • 쓰는 API: 에어코리아 실시간 대기오염정보, 기상청 동네예보
  • 참고할 화면: 날씨 앱의 첫 화면(오늘의 상태를 한 문장과 색으로 보이는 구성)
  • 기능: 학교나 집의 위치를 고르면 등교와 하교 시각의 미세먼지와 비 예보를 한 줄로 보인다. 「마스크 필요」, 「우산 필요」를 표시한다.
  • 타겟: 초등학생 자녀를 둔 보호자
  • 해결하는 불편: 아침마다 날씨 앱과 미세먼지 앱을 따로 열어 수치를 읽고 판단해야 한다.
  • 기대효과: 판단에 필요한 정보가 한 화면에 모이고, 수치를 해석하지 않아도 된다.

② 지금 여는 응급실과 약국

  • 쓰는 API: 중앙응급의료센터, 카카오맵
  • 참고할 화면: 지도 앱의 장소 목록(지도와 거리 순 목록을 나란히 보이는 구성)
  • 기능: 현재 위치에서 가까운 응급실과 지금 영업하는 약국을 거리 순으로 보인다. 전화 걸기 단추를 둔다.
  • 타겟: 밤이나 휴일에 아이가 아픈 보호자, 혼자 사는 대학생
  • 해결하는 불편: 급할 때 검색 결과에서 「지금 여는 곳」을 골라내기 어렵다.
  • 기대효과: 찾는 시간이 줄고, 닫은 곳으로 가는 헛걸음이 준다.
  • 주의: 의료 정보는 안내일 뿐이다. 화면에 119와 응급 상황의 안내를 먼저 보인다.

③ 빈 충전기 찾기

  • 쓰는 API: 전기차충전기정보, 네이버 지도 또는 카카오맵
  • 참고할 화면: 주차장 찾기 앱(지도 위에 빈자리의 수를 표시하는 구성)
  • 기능: 주변 충전소를 충전기의 종류(급속, 완속)와 사용 가능 여부로 걸러 보인다.
  • 타겟: 집에 충전기가 없는 전기차 운전자
  • 해결하는 불편: 충전소에 도착해서야 모두 사용 중이거나 고장인 것을 안다.
  • 기대효과: 출발 전에 갈 곳을 정할 수 있다.

④ 자취생 장바구니 물가

  • 쓰는 API: 한국소비자원 참가격, KAMIS(농산물 유통 정보)
  • 참고할 화면: 가격 비교 사이트의 상품 목록(품목마다 최저가와 가격의 변화를 보이는 구성)
  • 기능: 자주 사는 품목 열 개를 고르면 지역의 판매점별 가격과 지난주 대비 변화를 보인다.
  • 타겟: 식비를 줄이려는 자취 대학생
  • 해결하는 불편: 어느 가게가 싼지, 지금이 비싼 때인지 알 방법이 없다.
  • 기대효과: 장보는 곳과 때를 근거를 가지고 정한다.

⑤ 이번 주말 공연과 전시

  • 쓰는 API: KOPIS 공연예술통합전산망, 한국문화정보원
  • 참고할 화면: 예매 사이트의 목록(포스터 카드, 날짜와 지역 거르기)
  • 기능: 이번 주말에 우리 지역에서 하는 공연과 전시를 날짜, 장르, 가격대로 걸러 보인다. 예매는 원래의 쪽으로 보낸다.
  • 타겟: 주말에 할 일을 찾는 대학생과 직장인
  • 해결하는 불편: 예매 사이트마다 따로 찾아야 하고, 지역의 작은 공연은 찾기 어렵다.
  • 기대효과: 한곳에서 견주어 고른다. 지역 공연이 눈에 띈다.

⑥ 대중교통 당일 여행

  • 쓰는 API: 한국관광공사 TourAPI 4.0, 기상청 동네예보, ODsay 대중교통 API
  • 참고할 화면: 여행 일정 앱(하루의 장소를 시간 순으로 늘어놓은 구성)
  • 기능: 출발지를 넣으면 대중교통으로 갈 수 있는 관광지를 이동 시간 순으로 보이고, 그날의 날씨를 함께 보인다.
  • 타겟: 차가 없는 대학생
  • 해결하는 불편: 관광 정보, 교통편, 날씨를 따로 찾아 맞추어 보아야 한다.
  • 기대효과: 갈 수 있는 곳의 범위를 한 번에 안다.

⑦ 첫 자취방 시세 보기

  • 쓰는 API: 아파트 전월세 실거래가, 브이월드

  • 기능: 동네를 고르면 최근 전월세 실거래의 보증금과 월세의 범위를 보인다.
  • 타겟: 처음 방을 구하는 사회 초년생
  • 해결하는 불편: 매물의 호가만 보여서 실제로 얼마에 계약되는지 모른다.
  • 기대효과: 제시된 가격이 높은지 낮은지를 견줄 기준이 생긴다.
  • 주의: 아파트의 자료이다. 원룸과 오피스텔은 다른 자료가 필요하다.

⑨ 학과에서 직업까지

판정 기준은 7절의 완료 기준 여섯 개이다.

정리

  • 코드는 동작의 조건과 결과를 줄 번호와 함께 말하지만 왜 그렇게 만들었는지는 말하지 않는다. 코드에서 뽑은 명세는 사람에게 확인받는다.
  • 코드를 읽기 전에 실행해 관찰한다. 정상 입력과 잘못된 입력, 표준 출력과 종료 코드를 함께 본다.
  • 처리하지 않아 생긴 동작도 코드에 남는다. 그것을 요구로 옮길지 더 나은 동작을 정할지는 명세를 쓰는 사람이 정하고, 정한 것을 적는다.
  • 재구현하는 쪽에는 근거(줄 번호)와 대상의 이름을 주지 않는다.
  • 명령줄 프로그램의 대조는 명령으로 한다. 대조가 「같다」고 한 것은 대조가 본 것이 같다는 뜻이다.
  • 추적표는 요구, 코드의 위치, 확인 방법을 잇는다. 확인 방법이 없는 요구는 구현되었는지 알 수 없다.
