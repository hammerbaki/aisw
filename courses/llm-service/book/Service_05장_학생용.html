5장

명세 기반 구현과 배포

2027학년도 「LLM 서비스 개발」의 준비 중인 교재입니다. 편집 상태를 검토하기 위해 미리 공개한 것으로, 수업 전에 내용과 순서가 바뀔 수 있습니다.

학사 6주차 · 교재 05 · 서비스 1: 공고 모아보기 웹 (2/2)

개편 초안 3판(2026-11-18). 서비스 1의 방향을 「참고 프로덕트의 구성 + 공개 API의 자료」로 바꾸어 다시 썼다(plan/개편안.md 9절). 키트를 새 번호(Service_05장)로 만들었다. 0절, 4-3, 8-2, 8-4의 세기, 8-6의 검사기, 8-7의 배포 전 점검은 집필용 Windows PC(Git Bash, Python 3.13.7, pytest 9.2.0, curl 8.21.0)에서 키트로 실행해 얻은 출력이다. 변환에 쓴 견본 응답은 항목 이름만 개발명세서를 따른 지어낸 자료(공고 10건)이며, 실제 고용24 응답으로는 실행하지 않았다. Claude Code의 계획과 구현, Aside의 판정, GitHub Pages 배포는 「실행 결과 자리」로 남겼다.

4장에서 요구사항 명세서를 썼다. 화면의 구성은 참고 프로덕트(잡코리아)를 관찰해 정했고, 화면에 채울 자료는 고용24 OPEN-API의 채용정보로 정했다. 이 장은 그 명세로 서비스를 만든다. 고용24에서 받은 응답을 화면이 읽을 수 있는 파일로 바꾸고, 명세를 Claude Code에 주어 정적 웹으로 구현하고, 인수 조건으로 검사한 뒤 GitHub Pages에 배포한다.

구현은 Claude Code가 한다. 사람이 하는 일은 세 가지이다. 구현 전에 계획을 읽고 명세에 없는 것을 빼는 일, 구현 뒤에 인수 조건을 화면에서 직접 확인하는 일, 명세가 정하지 않아 생긴 빈틈을 명세에 되돌리는 일이다. 이것이 명세 주도 개발(SDD, Spec-Driven Development)의 가장 작은 한 바퀴이다.

인수 조건의 점검은 브라우저 에이전트(Aside)에게도 맡겨 본다. 에이전트의 판정은 그대로 쓰지 않는다. 내가 화면에서 직접 확인한 결과와 맞대어 본다. AI가 알려 준 것은 내 눈과 손으로 확인한 뒤에 쓴다(1장).

학습 목표

  • 명세 주도 개발의 단계를 Claude Code의 계획 모드로 수행할 수 있다.
  • 공개 API의 응답을 화면용 자료 파일로 바꾸고, 인증키와 받은 자료가 공개되는 범위를 설명할 수 있다.
  • 요구에서 인수 조건(Given-When-Then)을 쓰고 화면에서 점검할 수 있다.
  • 브라우저 에이전트의 판정을 내가 직접 확인한 결과와 대조할 수 있다.
  • 정적 웹을 로컬 서버로 확인하고 GitHub Pages에 배포할 수 있다.

0. 시작하기

부록 A의 시작 순서(A-22)를 따른다. 이 장의 키트를 받고, 4장의 산출물이 개인 실습 저장소에 있는지 확인한다.

터미널

cp -rn ~/kits-repo/Service_05장 ~/kits/
cd ~/kits/Service_05장 && python -m pytest -q
cd ~/llm-service-lab
ls ch04
git status --short
git check-ignore -v ch04/응답_견본.xml
.......                                                                  [100%]
7 passed in 2.96s

위 출력은 키트의 테스트이다(변환 프로그램과 배포 전 점검 도구). 그 아래의 ls ch04에 관찰기록.md, 자료항목표.md, 조사.md, 요구사항명세서.md, 응답_견본.xml이 보여야 한다. 마지막 명령은 .gitignore의 규칙 한 줄을 출력해야 한다. 아무것도 출력하지 않으면 응답 파일이 저장소에 올라갈 수 있는 상태이므로 4장 7-3으로 돌아간다.

  • 이 장의 실행 상한. Claude Code는 대화형으로만 쓴다. 프롬프트는 단계마다 한 번, 고쳐 보내기는 한 번까지이다. Aside의 점검은 한 번이다.

  • API 호출. 이 장에서는 API를 새로 부르지 않는다. 4장에서 받은 응답_견본.xml을 쓴다. 인증키가 늦게 발급되어 4장에서 받지 못했으면 이 장을 시작할 때 4장 7-3의 명령으로 한 번 받는다. 그때도 발급되지 않았으면 교수가 Google 클래스룸에 올린 응답 파일을 응답_견본.xml로 저장해 쓴다.

  • 키트. 이 장의 Service_05장(변환 프로그램, 로컬 서버 확인 쪽, 양식, 배포 전 점검 도구)과 4장의 Service_04장(EARS 검사기)을 쓴다.

  • 확인 1 키트의 테스트가 7 passed이고, ch04/에 요구사항명세서.md와 응답_견본.xml이 있으며, git check-ignore가 규칙 한 줄을 출력하고, git status --short에 4장의 커밋하지 않은 변경이 없다.

1. 명세 주도 개발

1-1. 정의

명세 주도 개발(SDD)은 구현보다 명세를 먼저 쓰고, 명세를 AI 구현의 입력이자 결과를 검사하는 기준으로 삼는 개발 방식이다. GitHub는 2025년 9월 오픈소스 도구 Spec Kit을 공개하면서, 이 방식을 「코드가 진실의 원천」인 상태에서 「의도가 진실의 원천」인 상태로 옮겨 가는 일로 설명하였다[S1]. 같은 글은 AI 코딩 에이전트가 모호한 지시를 받으면 그럴듯하지만 의도에서 벗어난 코드를 낸다고 진단하고, 명세를 한 번 쓰고 버리는 문서가 아니라 생성, 검사, 검증을 이끄는 「살아 있는 산출물」로 다루자고 한다[S1].

1장에서 본 「바이브 코딩」과 견주면 차이가 분명하다.

관점 바이브 코딩 명세 주도 개발
출발점 한 줄 요청 명세(요구, 수용 기준)
정하지 않은 자리 AI가 그때그때 채운다. 요청할 때마다 결과가 달라진다 명세가 정한다. 정하지 않은 자리는 질문 목록으로 돌아온다
결과의 판정 「돌아가는가」 「명세의 수용 기준을 충족하는가」
변경 코드를 고친다 명세를 고치고 다시 구현한다. 변경 이력이 명세에 남는다
사람의 일 결과를 보고 다시 요청한다 명세를 쓰고, 단계마다 AI의 산출물을 검토한다
다시 만들기 같은 결과가 나오지 않는다 명세가 같으면 같은 기능이 나온다(모양은 다를 수 있다)

사람의 일이 사라지는 것이 아니다. GitHub의 글은 단계마다 사람이 「명세가 의도를 담았는가, 계획이 현실의 제약을 지키는가, AI가 빠뜨린 경계 사례가 없는가」를 확인해야 한다고 강조한다. 산출물은 AI가 만들고 그것이 맞는지는 사람이 확인한다는 것이다[S1]. 이 과목에서 학습자가 맡는 일이 바로 그 확인이다.

1-2. GitHub Spec Kit의 단계

Spec Kit은 명세 주도 개발의 단계를 코딩 에이전트 안에서 실행하는 명령(에이전트 스킬)으로 제공한다. 2026-11-14에 확인한 최신판은 v1.4.0(2026-11-10 공개)이다. 처음 공개될 때는 명세, 계획, 작업, 구현의 네 단계였고[S1], 지금은 구현 뒤에 「수렴(converge)」 단계와 선택적인 품질 관문 세 개가 더해졌다[S2, S2a].

단계 명령(Claude Code에서) 하는 일 주요 산출물
원칙 /speckit-constitution 프로젝트의 원칙을 정한다. 이후 모든 단계가 이 원칙에 비추어 평가된다. 프로젝트마다 한 번 .specify/memory/constitution.md
명세 /speckit-specify 무엇을 왜 만드는지 쓴다. 기술 스택은 쓰지 않는다 specs/001-기능이름/spec.md, checklists/requirements.md
명확화(선택) /speckit-clarify 명세의 모호한 곳에 대해 최대 다섯 개의 질문을 하고 답을 명세에 반영한다 spec.md 갱신
계획 /speckit-plan 기술 스택과 구조를 받아 설계 산출물을 만든다. 명세의 모호한 곳을 먼저 조사로 푼다 plan.md, research.md, data-model.md 등
점검표(선택) /speckit-checklist 명세가 완전하고 일관된지 보는 점검표를 만든다. 「요구사항의 단위 테스트」 점검표 파일
작업 /speckit-tasks 계획을 의존 순서대로 작업 목록으로 나눈다 tasks.md
분석(선택) /speckit-analyze 명세, 계획, 작업 사이의 충돌과 빈틈을 읽기 전용으로 보고한다 보고(파일을 고치지 않는다)
구현 /speckit-implement 작업 목록을 순서대로 실행한다 코드
수렴 /speckit-converge 코드를 명세, 계획, 작업과 대조해 빈틈이 있으면 작업을 덧붙인다. 「수렴됨」이 나올 때까지 구현과 수렴을 되풀이한다 tasks.md 갱신

[최신 자료 자리: Spec Kit의 판과 명령 이름] 최신판 번호, 단계의 수와 이름, Claude Code에서 부르는 명령의 꼴(/speckit-specify와 /speckit.specify), 설치 명령(uv tool install specify-cli, specify init … --integration claude). 확인할 곳: https://github.com/github/spec-kit/releases, https://github.github.com/spec-kit/. 2026-11-14에 확인한 값: v1.4.0(2026-11-10), 위 표의 아홉 단계, 하이픈 꼴. 판이 자주 오르므로 수업 전에 다시 확인한다.

문서는 짧은 경로(명세 → 계획 → 작업 → 구현 → 수렴)와 품질 관문을 넣은 긴 경로를 구분하고, 원칙은 어느 경로든 처음에 한 번 정하라고 한다[S2a]. Claude Code에 설치하면 각 명령이 .claude/skills/speckit-<명령>/SKILL.md 꼴의 스킬로 들어가고, 대화창에서 /speckit-specify처럼 부른다[S2b]. 명령의 이름은 판에 따라 바뀌어 왔다. 초기 문서와 일부 에이전트용 문서는 /speckit.specify처럼 점을 쓴다[S2c]. 도구의 이름은 바뀌어도 단계의 순서는 같다는 점이 이 과목에서 Spec Kit을 다루는 까닭이다.

Spec Kit의 명세 양식(spec-template.md)을 보면 명세가 무엇을 담아야 하는지에 대한 한 가지 답이 보인다[S2d].

  • 사용자 시나리오와 검사: 우선순위가 붙은 사용자 이야기와 「Given … When … Then …」 꼴의 수용 시나리오. 이 과목에서는 수용 기준(4장).
  • 경계 사례: 경계 조건과 오류 상황. 이 장에서는 원치 않는 동작 문형.
  • 기능 요구: FR-001 꼴의 ID와 「System MUST …」 문장, 모호한 곳의 [NEEDS CLARIFICATION: ...]. 이 과목에서는 EARS 요구 문장과 열린 질문(4장).
  • 핵심 개체: 다루는 자료와 그 관계. 이 장에서는 명세서의 「용어」.
  • 성공 기준: 기술에 중립적이고 측정할 수 있는 결과. 이 과목에서는 13장의 사용성 평가에서 잰다.

Spec Kit의 기능 요구는 「System MUST」라는 한 가지 꼴만 쓰고, EARS처럼 조건의 종류를 문형으로 나누지 않는다. 대신 「NEEDS CLARIFICATION」 표시로 모호한 곳을 드러내게 한다. 이 장은 둘을 합쳐, 요구 문장은 EARS로 쓰고 모호한 곳은 「열린 질문」 표로 모은다.

1-3. Claude Code의 계획 모드

계획 모드(plan mode)는 Claude Code가 조사하고 계획을 제안하되 소스 파일을 고치지 않는 권한 모드다. Claude는 파일을 읽고, 탐색용 셸 명령을 돌리고, 계획을 쓰지만, 사람이 계획을 승인하기 전에는 편집하지 않는다[S5]. 2장에서 처음 써 보았으며, 이 장에서는 명세 주도 개발의 「계획」 단계를 맡긴다.

들어가고 나오는 방법은 다음과 같다(2026-11 기준, Claude Code 2.1.296에서 확인)[S4, S5].

2. API의 자료를 화면에 넣는 길

2-1. 브라우저에서 API를 바로 부르지 않는 까닭

화면(브라우저)에서 고용24의 API를 직접 부르면 구조가 가장 단순하다. 그러나 이 서비스는 그렇게 하지 않는다. 까닭은 두 가지이다.

  1. 인증키가 드러난다. 브라우저가 API를 부르려면 자바스크립트 코드에 인증키가 들어 있어야 한다. 브라우저로 받은 코드는 누구나 읽을 수 있다. 개발자 도구의 Network 탭에 요청 주소가 인증키와 함께 그대로 보인다. 인증키는 양도할 수 없다[A1].
  2. 브라우저가 막을 수 있다. 브라우저는 다른 출처(주소의 앞부분이 다른 곳)로 보낸 요청의 응답을, 그쪽 서버가 허용한 경우에만 코드에 넘긴다(CORS). 고용24의 API가 이것을 허용하는지는 확인하지 않았다.

그래서 이 장은 다음 길을 쓴다.

flowchart LR
    A["고용24 OPEN-API"] -- "내 PC에서 한 번 호출<br/>(인증키 사용)" --> B["응답_견본.xml<br/>저장소에 올리지 않음"]
    B -- "변환 프로그램" --> C["web/data/jobs.json<br/>화면에 쓸 항목만"]
    C -- "fetch (같은 출처)" --> D["정적 웹<br/>index.html, app.js"]

인증키는 내 PC에서 API를 부를 때만 쓰이고 화면에는 가지 않는다. 화면은 미리 받아 둔 자료 파일만 읽는다.

이 길의 약점은 자료가 받은 시점에 멈춘다는 것이다. 오늘 받은 공고는 내일이면 일부가 마감된다. 그래서 화면에 「자료를 받은 날짜와 시각」을 보이게 한다. 사용자가 호출할 때마다 새 자료를 받는 구조는 서버가 필요하며 8장에서 다룬다.

2-2. 화면에 쓸 항목만 남기기

API의 응답에는 화면에 쓰지 않는 항목이 있다. 4장의 자료 항목표에서 「쓰지 않는다」고 정한 항목은 자료 파일에 넣지 않는다. 까닭은 다음과 같다.

  • 자료 파일은 배포하면 누구나 내려받을 수 있다. 화면에 보이지 않는 항목도 파일에 있으면 공개된 것이다.
  • 응답에는 사업자등록번호(busino) 같은 항목이 있다. 서비스에 필요하지 않은 항목을 다시 공개할 까닭이 없다.
  • 항목이 적으면 명세와 구현을 맞대어 보기 쉽다.

2-3. 출처와 받은 시각의 표시

공개 API의 자료를 쓰는 서비스는 자료의 출처를 화면에 보인다. 이 서비스는 화면 아래에 「자료: 고용24 OPEN-API 채용정보, 받은 시각」을 적고, 공고마다 고용24의 원문 주소(wantedInfoUrl)로 가는 연결을 둔다. 지원은 원문에서 하게 한다.

고용24의 자료는 교육과 비영리 목적으로 쓸 수 있다(담당 교수의 확인). 이 과목의 서비스는 수업의 결과물로 공개하며 돈을 받지 않는다. 인증키는 양도할 수 없으므로[A1] 공개하는 것은 받은 자료이고 인증키가 아니다.

작업 하나를 Claude Code에 맡길 때 쓰는 지시문을 이 과목에서는 구현 지시문이라 부른다. 구현 지시문은 다섯 칸으로 구성한다.

다섯 칸은 2026년판 3주차의 두 사고에 대한 대응이기도 하다. “완료했습니다”를 믿었다가 빠진 요구가 드러난 일은 완료 조건이, AI가 테스트를 고친 일은 금지 사항이 없을 때 생긴다 [R1].

4. 정적 웹과 로컬 서버

4-1. 정적 웹

정적 웹(static web)은 미리 만들어 둔 파일(HTML, CSS, 자바스크립트, 이미지, JSON)을 서버가 그대로 보내 주기만 하는 웹이다. 요청이 올 때마다 서버에서 프로그램이 돌아 답을 만드는 웹을 동적 웹이라 한다. 2026년판 3주차는 이 구분을 “정적 파일”과 “서버 코드”로 설명하였다 [R1].

정적 웹에서도 화면은 움직인다. 검색어를 넣으면 목록이 줄고, 버튼을 누르면 글자가 바뀐다. 그 일은 서버가 아니라 사용자의 브라우저가 자바스크립트로 한다. 이 장의 웹이 정적 웹으로 충분한 까닭과 한계를 표로 정리한다.

할 일 이 장의 웹에서 하는 곳 정적 웹으로 되는가
공고 10~100건 보여 주기 브라우저가 data/jobs.json을 받아 화면을 만든다 된다. 자료가 모든 사용자에게 같기 때문이다

고른 조건의 기억 브라우저 저장소(localStorage) 이 브라우저 안에서는 된다. 다른 기기와는 공유되지 않는다
공고 자료 새로 고치기 사람이 내 PC에서 다시 받아 바꾸고 다시 배포 된다. 다만 자동으로 새 공고를 모으지는 못한다
고용24 API를 사용자가 열 때마다 부르기 서버가 인증키로 부른다 안 된다. 인증키를 브라우저에 두면 누구나 볼 수 있다. 8장에서 서버를 붙인다
로그인, 여러 기기 동기화 서버와 데이터베이스 안 된다. 명세의 범위 밖이다

정적 웹의 장점은 운영할 것이 없다는 데 있다. 서버 프로그램이 없으므로 서버가 멈출 일, 데이터베이스가 깨질 일, 서버 쪽 보안 구멍이 없다. GitHub Pages 같은 정적 호스팅에 파일만 올리면 된다. 단점은 사용자마다 다른 것을 서버에 보관할 수 없다는 점이다. 이 장은 그 단점을 브라우저 저장소로 메운다.

2026년판 3주차의 실습 1은 HTML 파일을 더블클릭해 file:// 주소로 열어 보았다 [R1]. 그때는 파일 하나짜리 화면이라 잘 열렸다. 이 장의 웹처럼 자료 파일을 따로 읽는 화면을 같은 방법으로 열면 화면의 틀은 보이지만 공고가 하나도 나오지 않는다. 키트의 서버확인/index.html은 같은 폴더의 data/jobs.json을 읽어 건수만 보이는 쪽이다. 탐색기에서 이 파일을 더블클릭해 열면 Chromium 계열 브라우저의 Console에 다음과 같은 오류가 보인다.

위 문구는 2026-11-14에 Chromium 156에서 옛 키트의 화면으로 확인한 것이며 브라우저와 판에 따라 다르다. MDN에 따르면 여러 브라우저는 로컬 파일을 출처가 불투명한(opaque) 것으로 다루고, 다른 자원을 요청하는 일(CORS 요청)은 http와 https에서만 허용하며, 로컬에서 시험하려면 로컬 서버를 띄우라고 안내한다 [W4]. 로컬 파일이 다른 로컬 파일을 마음대로 읽을 수 있으면, 내려받은 HTML 파일 하나가 내 컴퓨터의 다른 파일을 읽어 밖으로 보낼 수 있기 때문이다.

서버확인/index.html은 이때 화면에 「공고 자료를 불러오지 못했습니다. 로컬 서버로 열었는지 확인하십시오.」를 보인다. 오류를 Console에만 남기지 않고 화면에 보이는 것은 4장에서 쓴 「자료를 읽지 못하면 안내한다」는 원치 않는 동작 요구를 구현한 모습이다.

4-3. 로컬 서버: python -m http.server

파이썬 표준 라이브러리의 http.server는 지정한 폴더의 파일을 http로 보내 주는 간단한 서버다. 설치할 것이 없다 [P1].

  • [port]: 기다릴 포트 번호. 기본값은 8000이다 [P1].
  • -b, --bind 주소: 연결을 받을 주소. 기본값은 모든 네트워크 주소이고, 127.0.0.1이면 이 컴퓨터 안에서만 받는다 [P1].
  • -d, --directory 폴더: 보낼 폴더. 기본값은 지금 폴더다 [P1].

공식 문서는 이 서버를 운영용으로 쓰지 말라고 경고한다. 기본적인 보안 점검만 하고, 심볼릭 링크를 따라가 지정한 폴더 밖의 파일을 보낼 수 있기 때문이다 [P1]. 개발 중의 확인에만 쓰고, 공개는 GitHub Pages로 한다.

이 과목은 웹 서버를 포트 8100으로 띄운다(부록 A-16). 기본값 8000은 8장부터 API 서버가 쓴다. 각자의 PC에서 실습하므로 다른 학습자와 번호가 겹칠 일은 없다. 주소를 127.0.0.1로 묶어 같은 무선망의 다른 컴퓨터가 접속하지 못하게 한다.

따라 하기 2: 로컬 서버로 열기. 키트의 서버확인/을 작업 폴더로 복사해 서버를 띄운다. data/jobs.json은 키트의 지어낸 견본 응답을 8-2의 변환 프로그램으로 바꾸어 둔 것이다.

터미널 
cd ~/llm-service-lab
mkdir -p ch05
cp -rn ~/kits/Service_05장/서버확인 ch05/
python -m http.server 8100 --bind 127.0.0.1 --directory ch05/서버확인
Serving HTTP on 127.0.0.1 port 8100 (http://127.0.0.1:8100/) ...

이 터미널은 서버가 돌고 있으므로 다른 명령을 받지 않는다. 멈출 때는 Ctrl+C를 누른다. 다른 터미널을 열어 curl로 요청 세 개를 보낸다. -w는 응답의 상태 코드와 내용 형식을 출력하게 한다.

[터미널] (둘째 터미널)

curl -s -o /dev/null -w "%{http_code} %{content_type}\n" http://127.0.0.1:8100/
curl -s -o /dev/null -w "%{http_code} %{content_type}\n" http://127.0.0.1:8100/data/jobs.json
curl -s -o /dev/null -w "%{http_code}\n" http://127.0.0.1:8100/nothing.html
200 text/html
200 application/json
404

서버를 띄운 터미널에는 요청마다 한 줄씩 기록이 찍힌다. 이 기록이 「브라우저(여기서는 curl)가 무엇을 요청했고 서버가 무엇을 답했는가」의 증거이다. 다음은 집필용 Windows PC에서 위 세 요청을 보낸 기록이다(2026-11-18).

127.0.0.1 - - [18/Nov/2026 20:17:07] "GET / HTTP/1.1" 200 -
127.0.0.1 - - [18/Nov/2026 20:17:08] "GET /data/jobs.json HTTP/1.1" 200 -
127.0.0.1 - - [18/Nov/2026 20:17:08] code 404, message File not found
127.0.0.1 - - [18/Nov/2026 20:17:08] "GET /nothing.html HTTP/1.1" 404 -

끝의 숫자는 HTTP 상태 코드다. 200은 성공, 404는 그런 파일이 없음이다. 화면이 깨졌을 때 이 기록에서 404가 난 파일을 찾으면, 경로의 오타나 대소문자 차이를 바로 알 수 있다. 이어서 브라우저에서 http://localhost:8100/을 연다. 「공고 10건을 읽었다」와 자료의 출처, 받은 시각이 보인다. 화면 파일이 없는 폴더에서 띄우면 브라우저에 파일 목록 화면(「Directory listing for /」)이 보인다. GitHub Pages는 이런 목록을 보이지 않는다.

  • 확인 3 curl의 세 출력이 200 text/html, 200 application/json, 404이고, 서버를 띄운 터미널에 같은 세 요청의 기록이 있다.
  • 확인 4 같은 index.html을 탐색기에서 더블클릭해 열면 「불러오지 못했습니다」가, http://localhost:8100/으로 열면 「공고 10건을 읽었다」가 보인다. 확인한 뒤 서버를 Ctrl+C로 멈춘다.

Windows에서는 같은 포트에 http.server를 두 번 띄워도 오류 없이 둘 다 떠서, 고친 파일이 반영되지 않은 것처럼 보일 수 있다(부록 A-16-1).

[그림 자리: 로컬 웹 서버와 브라우저] VS Code 통합 터미널에 Serving HTTP on 127.0.0.1 port 8100과 요청 기록이 보이고, 옆의 브라우저 주소창에 localhost:8100과 공고 목록이 보이는 화면. 웹 서버를 띄운 Windows 11 PC에서 찍는다.

5. 인수 조건

5-1. 요구와 인수 조건

요구사항 명세서의 문장은 “시스템이 무엇을 해야 하는가”를 말하지만, 그것만으로는 구현이 요구를 충족했는지 판정하기 어렵다. 「사용자가 검색어를 입력하면, 시스템은 채용제목이나 회사명에 검색어가 든 공고만 표시해야 한다」는 요구는 어떤 자료에서, 어떤 검색어를 넣고, 무엇을 보면 충족인가. 이 물음에 답한 것이 인수 조건(acceptance criteria)이다. 인수 조건은 요구 하나를 「이 상황에서 이렇게 하면 이것이 보여야 한다」는 구체적인 예로 바꾼 것이고, 예를 통과하면 그 요구를 받아들인다(인수한다). 출발점은 4장 명세서의 수용 기준이다. 수용 기준이 견본이나 가상의 값으로 쓰였으면, 이 장에서 화면에 실제로 올린 자료(jobs.json)의 값으로 바꾼다.

구분 요구 (명세) 인수 조건
말하는 것 일반 규칙 구체적인 예 하나
예 검색어가 든 공고만 보인다 공고 10건이 있을 때 「개발」을 넣으면, 제목이나 회사명에 「개발」이 든 공고 2건만 마감일 순으로 보인다
판정 사람의 해석이 필요하다 화면을 보면 참과 거짓이 갈린다
수 요구 하나 요구 하나에 하나 이상
누가 읽는가 기획자, 개발자, AI 개발자, 검사하는 사람, 자동 검사

인수 조건은 테스트와 다르다. 테스트는 인수 조건을 확인하는 수단의 하나다. 같은 인수 조건을 사람이 화면에서 손으로 확인할 수도 있고, 코드로 쓴 검사가 확인할 수도 있다. 이 장은 사람이 화면에서 확인하고, 브라우저 에이전트의 판정을 그 결과에 맞대어 본다. 코드로 쓴 검사는 8장에서 다룬다. 테스트를 먼저 쓰고 구현을 그에 맞추어 키우는 테스트 주도 개발(TDD)은 「AI에이전트 기획 및 개발」 2장이 다룬다.

5-2. Given-When-Then

인수 조건은 흔히 Given-When-Then의 세 부분으로 쓴다. Daniel Terhorst-North와 Chris Matts가 행위 주도 개발(BDD)의 일부로 만든 형식이고, 시나리오 하나를 세 부분으로 나누어 쓰는 방식이다 [S2].

부분 뜻 [S2] 이 장의 예 (마감 임박 표시)
Given 행동 전의 상태. 시나리오의 전제 조건 기준일이 2027-04-14이고, 마감일이 04-17인 공고와 04-18인 공고가 있다
When 명세하려는 행동 목록 화면을 연다
Then 그 행동의 결과로 기대하는 변화 04-17의 공고에 「마감 임박 D-3」이 보이고, 04-18의 공고에는 보이지 않는다

Given을 빼먹기 쉽다. 「검색어를 넣으면 결과가 나온다」는 Given이 없다. 공고가 0건이면 무엇을 넣어도 결과가 없다. 위 예에서 기준일을 적지 않으면, 수업하는 날에 따라 같은 공고가 임박이기도 하고 아니기도 하다. Given이 다르면 같은 When이 다른 Then을 낳는다. 이 사실은 7절의 브라우저 에이전트 판정을 읽을 때 다시 쓴다.

Then은 관찰할 수 있어야 한다. “빠르게 보인다”, “잘 동작한다”, “사용하기 편하다”는 Then이 될 수 없다. 무엇을 보면 참인지 정할 수 없기 때문이다. 화면의 글자, 요소의 수, 요소가 보이는가, 주소가 무엇인가처럼 보면 참과 거짓이 갈리는 것으로 쓴다.

5-3. 좋은 인수 조건과 나쁜 인수 조건

나쁜 예 문제 고친 예
검색이 잘 된다 Then을 관찰할 수 없다. Given과 When이 없다 Given 10건, When 「개발」 입력, Then 제목이나 회사명에 「개발」이 든 공고 2건만 보인다
filter 함수가 배열을 거른다 구현 방법을 적었다. 사용자는 함수를 보지 않는다 Then을 화면에 보이는 카드로 쓴다
지역으로 걸러진다 「걸러진다」를 어떻게 보는지 없다 Given 10건, When 지역 「광주」, Then 지역이 「광주」로 시작하는 카드 4장만 보인다
마감 임박 공고가 눈에 띈다 「임박」, 「눈에 띈다」가 수와 모양으로 정해지지 않았다 Given 기준일 2027-04-14, When 목록을 연다, Then 0~3일 남은 공고에 「마감 임박 D-N」
오류 없이 동작한다 무엇을 했을 때의 오류인지 없다 Given data/jobs.json이 없다, When 화면을 연다, Then 「공고 자료를 불러오지 못했습니다」가 보인다

인수 조건을 쓰다 보면 명세의 빈틈이 드러난다. 「검색어가 든」은 영문의 대소문자를 가리는가. 공백만 넣으면 어떻게 되는가. 명세가 말하지 않는 것은 인수 조건이 정하지 않는다. 인수 조건이 명세에 없는 규칙을 만들면, 명세와 인수 조건이 서로 다른 말을 하는 두 기준이 된다. 빈틈을 찾으면 명세에 결정을 더하고 인수 조건은 그 결정을 따른다.

6. 배포의 개념과 GitHub Pages

6-1. 로컬과 배포

배포(deployment)는 내 파일을 서버에 올려 누구든 요청할 수 있게 하는 일이고, 그 결과가 공개 주소다 [R1]. 구현과 검사를 하는 동안의 웹은 로컬에 있다. 내 PC의 폴더에 파일이 있고, 그 파일을 보는 사람은 나 하나다. 배포하면 파일이 GitHub의 서버로 가고, 주소를 아는 누구나 연다.

구분 로컬 (핵심 실습 8-2~8-6) 배포 (8-7)
파일의 위치 내 PC의 ch05/web/ GitHub Pages 서버
주소 http://localhost:8100/ https://아이디.github.io/jobs-board/
보는 사람 나 주소를 아는 누구나(검색 엔진 포함)
고친 것의 반영 저장하고 새로고침 커밋하고 푸시하면 워크플로가 다시 배포
잘못되었을 때 나만 본다 모든 방문자가 본다
브라우저 저장소의 출처 http://localhost:8100 https://아이디.github.io (다른 출처이므로 기록이 이어지지 않는다)

이 장은 2026년판 3주차가 소개한 “만드는 동안은 로컬, 완성본만 배포”의 동선대로, 인수 조건을 로컬에서 통과한 뒤에 배포한다 [R1].

6-2. GitHub Pages

GitHub Pages는 저장소의 HTML, CSS, 자바스크립트 파일을 그대로 받아 웹사이트로 내보내는 정적 사이트 호스팅이다 [G3]. 사이트에는 두 종류가 있다 [G3]. 사용자·조직 사이트는 이름이 아이디.github.io인 저장소에서 나오고 주소가 https://아이디.github.io이며 계정마다 하나다. 프로젝트 사이트는 아무 저장소에서나 나오고 주소가 https://아이디.github.io/저장소이름이며 저장소마다 하나다. 이 장의 사이트는 jobs-board 저장소의 프로젝트 사이트이므로 주소가 https://아이디.github.io/jobs-board/이다. 주소에 저장소 이름이 하위 경로로 들어가므로 파일의 경로는 상대 경로로 쓴다.

사용 한도(게시 사이트 1GB, 월 대역폭 100GB, 배포 시간 10분 등)가 있으나 이 장의 사이트는 50KB 안팎이다 [G5].

[최신 자료 자리: Pages와 Actions의 사용 한도] Pages 한도 [G5]와 비공개 저장소의 Actions 포함 사용량 [G7]. 2026-11-16에 다시 확인한 값은 1GB, 월 100GB, 시간당 10회, 10분, Free 월 12달러·Pro 월 18달러 상당이다.

7. 브라우저 에이전트와 판정의 근거

7-1. 브라우저 에이전트

브라우저 에이전트는 자연어로 받은 작업을 브라우저를 직접 조작해 수행하는 AI이다. 이 장은 Aside(2025년 가을 Y Combinator 선정)를 쓴다. Aside는 웹사이트에서 여러 단계의 일을 하되 결제·메시지 같은 민감한 동작 앞에서는 사람의 승인을 기다리는 브라우저로 소개되고 [B1][B2], 개발자 문서는 첫 사용 예로 로컬 웹앱의 스모크 테스트를 든다 [B3].

인수 조건은 코드로 쓴 검사나 사람이 화면에서 한 손 점검으로 확인한다. 브라우저 에이전트는 자연어로 쓴 인수 조건 표를 받아 판정을 돌려주는 또 하나의 방법이다. 이 절의 물음은 에이전트가 「통과」라고 보고한 것을 근거로 삼을 수 있는가이다. “구현했습니다”라는 말 대신 바뀐 파일을 읽듯이, 에이전트의 판정도 손 점검에 대어 본다.

학습자는 각자 설치한 Aside를 자기 계정으로 쓴다(계정 부록 A-2-3, 설치·로그인과 로컬 웹 열기 A-19, 이 장 전에 끝낸다). 맡기는 일은 인수 조건 표의 점검 한 번이다(핵심 실습). 같은 일을 하는 다른 도구로 Ego Lite가 있다(무료, macOS·Windows) [B4].

[최신 자료 자리: Aside의 요금, 크레딧, 지원 운영체제] 확인할 곳 [B2], https://aside.com/pricing, 부록 A-2-3과 A-19-1. 2026-11-16에 확인한 값은 무료 요금제 월 500 크레딧(루틴 3개, 자기 구독 연결 가능), Pro 월 20달러, Max 월 200달러, macOS 15 이상과 Windows 10 22H2 이상·Windows 11(리눅스 없음)이다. 수업 전에 다시 확인한다.

7-2. 지켜야 할 세 가지

  1. 내 PC의 로컬 주소로만 한다. 대상은 핵심 실습에서 내 PC에 띄운 웹 서버 http://localhost:8100/이며, 공개 배포 주소로 하지 않는다. Aside도 같은 PC에서 돌므로 이 주소를 바로 연다(부록 A-19-3). 인수 조건은 배포 전의 판정이다. 에이전트가 갈 수 있는 곳도 이 주소 하나로 좁힌다.
  2. 자격 증명을 주지 않는다. 이 웹은 로그인이 없다. 작업 지시에 GitHub 계정, Claude 계정, API 키를 적지 않고, 에이전트의 브라우저에 다른 사이트의 로그인 탭을 열어 두지 않는다. Aside는 자격 증명을 AI에 드러내지 않고 자동 입력한다고 밝히지만 [B2], 쓸 일이 없는 자격 증명은 처음부터 닿지 않게 한다.
  3. 개인 정보를 입력하게 하지 않는다. 에이전트의 AI 모델은 화면의 내용과 지시를 읽는다. 입력값은 인수 조건 표에 적힌 값만 쓰게 한다. 에이전트가 다른 사이트로 가거나 승인을 요청하면 지시를 벗어난 것이므로 거절한다.

8-2. 자료 파일 만들기

응답 파일(XML)을 화면용 자료 파일(JSON)로 바꾼다. 아래 프로그램을 키트에서 ch05/xml2json.py로 복사한다(cp -n ~/kits/Service_05장/xml2json.py ch05/). KEEP의 목록은 자기 자료 항목표의 「내 서비스에서」 칸에 맞추어 고친다. 인증키가 아직 없으면 키트의 견본/응답_지어낸것.xml로 먼저 실행해 본다.

[파일: ch05/xml2json.py] (머리의 설명 몇 줄은 줄여 실었다)

"""고용24 채용정보 목록 응답(XML)을 화면용 JSON으로 바꾼다.

쓰는 법: python xml2json.py 응답.xml jobs.json
"""
import json
import os
import sys
import xml.etree.ElementTree as ET
from datetime import datetime

# 화면에 쓰는 항목만 남긴다. 자료 항목표의 「내 서비스에서」 칸을 따른다.
KEEP = ["wantedAuthNo", "company", "title", "salTpNm", "sal", "region",
        "career", "minEdubg", "regDt", "closeDt", "wantedInfoUrl"]


def main(src, dst):
    root = ET.parse(src).getroot()
    jobs = []
    for el in root.iter():
        # 공고 한 건: wantedAuthNo를 자식으로 가진 요소
        if el.find("wantedAuthNo") is None:
            continue
        job = {k: (el.findtext(k) or "").strip() for k in KEEP}
        jobs.append(job)
    out = {
        "source": "고용24 OPEN-API 채용정보",
        "fetched": datetime.fromtimestamp(os.path.getmtime(src)).strftime("%Y-%m-%d %H:%M"),
        "count": len(jobs),
        "jobs": jobs,
    }
    with open(dst, "w", encoding="utf-8") as f:
        json.dump(out, f, ensure_ascii=False, indent=2)
    empty = {k: sum(1 for j in jobs if not j[k]) for k in KEEP}
    print(f"공고 {len(jobs)}건 → {dst}")
    print("빈 값:", {k: v for k, v in empty.items() if v} or "없음")
    print("날짜가 아닌 closeDt:", sorted({j["closeDt"] for j in jobs if not j["closeDt"][:2].isdigit()}) or "없음")


if __name__ == "__main__":
    if len(sys.argv) != 3:
        sys.exit(__doc__)
    main(sys.argv[1], sys.argv[2])

프로그램은 응답의 바깥 구조를 가정하지 않는다. wantedAuthNo(구인인증번호)를 자식으로 가진 요소를 공고 한 건으로 본다. 목록 응답의 공고마다 이 항목이 있기 때문이다[A3].

  • 구현 전에 계획을 읽어 명세에 없는 기능을 빼고, 「명세가 정하지 않아 정한 것」을 받아 적는다. 그 목록이 명세의 빈틈이다.
  • 인수 조건은 요구를 구체적인 전제, 행동, 기대 결과로 옮긴 것이다. 기대 결과에는 자료에서 직접 센 수를 적는다.
  • 브라우저 에이전트의 판정은 내가 화면에서 직접 확인한 결과와 맞대어 본다. 「판정 못함」을 고를 수 있게 지시하고, 근거가 없는 「통과」는 믿지 않는다.
  • 배포는 남의 기기에서 열리는 것이 기준이다. 공개 저장소에 올린 것은 모두 공개된다.
