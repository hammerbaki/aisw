학사 6주차 · 교재 05 · 서비스 1: 공고 모아보기 웹 (2/2)

개편 초안(2026-11-18). 이 장은 plan/개편안.md의 단원형 구성에 따라 다시 엮은 초안이다. 옛 6장과 9장의 본문에서 옮긴 절의 실행 출력은 옛 키트(Service_06장)에서 확인한 것이다. 「실행 전」이라고 적은 절은 공식 문서를 근거로 새로 쓴 것이며 명령과 출력을 실행으로 확인하지 않았다. 키트와 작업 폴더의 이름은 아직 옛 장 번호를 쓴다.

4장에서 공공 채용 게시판의 목록 화면을 관찰해 요구사항 명세서를 썼다. 이 장은 그 명세만으로 구현한다. 원본을 보지 못한 구현자(새 세션의 Claude Code)가 명세만 읽고 만든 결과를 원본과 견주면, 둘이 갈라지는 자리에서 명세의 빈틈이 드러난다. 빈틈은 코드가 아니라 명세를 고쳐 메운다.

구현은 두 번 한다. 먼저 명령줄 프로그램으로 빠르게 한 바퀴를 돌아 빈틈을 찾고, 이어서 같은 명세를 정적 웹으로 구현해 인수 조건으로 검사하고 GitHub Pages에 배포한다. 이것이 명세 주도 개발(SDD, Spec-Driven Development)의 최소 단위이다. 명세가 구현의 입력이고 검사의 기준이다.

학습 목표

  • 명세만으로 재구현한 결과를 원본과 비교해 차이의 원인을 분류하고, 명세 빈틈을 명세에 되돌릴 수 있다.
  • 명세 주도 개발의 단계를 Claude Code의 계획 모드로 수행할 수 있다.
  • 요구에서 인수 조건(Given-When-Then)을 쓰고, 자동 확인과 손 점검을 구분할 수 있다.
  • 정적 웹을 로컬 서버로 확인하고 GitHub Pages에 배포하며, 공개되는 것의 범위를 설명할 수 있다.
  • 브라우저 에이전트의 판정을 근거와 대조할 수 있다.

1. 명세 주도 개발

1-1. 정의

명세 주도 개발(SDD)은 구현보다 명세를 먼저 쓰고, 명세를 AI 구현의 입력이자 결과를 검사하는 기준으로 삼는 개발 방식이다. GitHub는 2025년 9월 오픈소스 도구 Spec Kit을 공개하면서, 이 방식을 「코드가 진실의 원천」인 상태에서 「의도가 진실의 원천」인 상태로 옮겨 가는 일로 설명하였다[S1]. 같은 글은 AI 코딩 에이전트가 모호한 지시를 받으면 그럴듯하지만 의도에서 벗어난 코드를 낸다고 진단하고, 명세를 한 번 쓰고 버리는 문서가 아니라 생성, 검사, 검증을 이끄는 「살아 있는 산출물」로 다루자고 한다[S1].

1장에서 본 「바이브 코딩」과 견주면 차이가 분명하다.

관점 바이브 코딩 명세 주도 개발
출발점 한 줄 요청 명세(요구, 수용 기준)
정하지 않은 자리 AI가 그때그때 채운다. 요청할 때마다 결과가 달라진다 명세가 정한다. 정하지 않은 자리는 질문 목록으로 돌아온다
결과의 판정 「돌아가는가」 「명세의 수용 기준을 충족하는가」
변경 코드를 고친다 명세를 고치고 다시 구현한다. 변경 이력이 명세에 남는다
사람의 일 결과를 보고 다시 요청한다 명세를 쓰고, 단계마다 AI의 산출물을 검토한다
다시 만들기 같은 결과가 나오지 않는다 명세가 같으면 같은 기능이 나온다(모양은 다를 수 있다)

사람의 일이 사라지는 것이 아니다. GitHub의 글은 단계마다 사람이 「명세가 의도를 담았는가, 계획이 현실의 제약을 지키는가, AI가 빠뜨린 경계 사례가 없는가」를 확인해야 한다고 강조한다. 산출물은 AI가 만들고 그것이 맞는지는 사람이 확인한다는 것이다[S1]. 이 과목에서 학습자가 맡는 일이 바로 그 확인이다.

1-2. GitHub Spec Kit의 단계

Spec Kit은 명세 주도 개발의 단계를 코딩 에이전트 안에서 실행하는 명령(에이전트 스킬)으로 제공한다. 2026-11-14에 확인한 최신판은 v1.4.0(2026-11-10 공개)이다. 처음 공개될 때는 명세, 계획, 작업, 구현의 네 단계였고[S1], 지금은 구현 뒤에 「수렴(converge)」 단계와 선택적인 품질 관문 세 개가 더해졌다[S2, S2a].

단계 명령(Claude Code에서) 하는 일 주요 산출물
원칙 /speckit-constitution 프로젝트의 원칙을 정한다. 이후 모든 단계가 이 원칙에 비추어 평가된다. 프로젝트마다 한 번 .specify/memory/constitution.md
명세 /speckit-specify 무엇을 왜 만드는지 쓴다. 기술 스택은 쓰지 않는다 specs/001-기능이름/spec.md, checklists/requirements.md
명확화(선택) /speckit-clarify 명세의 모호한 곳에 대해 최대 다섯 개의 질문을 하고 답을 명세에 반영한다 spec.md 갱신
계획 /speckit-plan 기술 스택과 구조를 받아 설계 산출물을 만든다. 명세의 모호한 곳을 먼저 조사로 푼다 plan.md, research.md, data-model.md 등
점검표(선택) /speckit-checklist 명세가 완전하고 일관된지 보는 점검표를 만든다. 「요구사항의 단위 테스트」 점검표 파일
작업 /speckit-tasks 계획을 의존 순서대로 작업 목록으로 나눈다 tasks.md
분석(선택) /speckit-analyze 명세, 계획, 작업 사이의 충돌과 빈틈을 읽기 전용으로 보고한다 보고(파일을 고치지 않는다)
구현 /speckit-implement 작업 목록을 순서대로 실행한다 코드
수렴 /speckit-converge 코드를 명세, 계획, 작업과 대조해 빈틈이 있으면 작업을 덧붙인다. 「수렴됨」이 나올 때까지 구현과 수렴을 되풀이한다 tasks.md 갱신

[최신 자료 자리: Spec Kit의 판과 명령 이름] 최신판 번호, 단계의 수와 이름, Claude Code에서 부르는 명령의 꼴(/speckit-specify와 /speckit.specify), 설치 명령(uv tool install specify-cli, specify init … --integration claude). 확인할 곳: https://github.com/github/spec-kit/releases, https://github.github.com/spec-kit/. 2026-11-14에 확인한 값: v1.4.0(2026-11-10), 위 표의 아홉 단계, 하이픈 꼴. 판이 자주 오르므로 수업 전에 다시 확인한다.

문서는 짧은 경로(명세 → 계획 → 작업 → 구현 → 수렴)와 품질 관문을 넣은 긴 경로를 구분하고, 원칙은 어느 경로든 처음에 한 번 정하라고 한다[S2a]. Claude Code에 설치하면 각 명령이 .claude/skills/speckit-<명령>/SKILL.md 꼴의 스킬로 들어가고, 대화창에서 /speckit-specify처럼 부른다[S2b]. 명령의 이름은 판에 따라 바뀌어 왔다. 초기 문서와 일부 에이전트용 문서는 /speckit.specify처럼 점을 쓴다[S2c]. 도구의 이름은 바뀌어도 단계의 순서는 같다는 점이 이 과목에서 Spec Kit을 다루는 까닭이다.

Spec Kit의 명세 양식(spec-template.md)을 보면 명세가 무엇을 담아야 하는지에 대한 한 가지 답이 보인다[S2d].

  • 사용자 시나리오와 검사: 우선순위가 붙은 사용자 이야기와 「Given … When … Then …」 꼴의 수용 시나리오. 이 과목에서는 수용 기준(4장).
  • 경계 사례: 경계 조건과 오류 상황. 이 장에서는 원치 않는 동작 문형.
  • 기능 요구: FR-001 꼴의 ID와 「System MUST …」 문장, 모호한 곳의 [NEEDS CLARIFICATION: ...]. 이 과목에서는 EARS 요구 문장과 열린 질문(4장).
  • 핵심 개체: 다루는 자료와 그 관계. 이 장에서는 명세서의 「용어」.
  • 성공 기준: 기술에 중립적이고 측정할 수 있는 결과. 이 과목에서는 13장의 사용성 평가에서 잰다.

Spec Kit의 기능 요구는 「System MUST」라는 한 가지 꼴만 쓰고, EARS처럼 조건의 종류를 문형으로 나누지 않는다. 대신 「NEEDS CLARIFICATION」 표시로 모호한 곳을 드러내게 한다. 이 장은 둘을 합쳐, 요구 문장은 EARS로 쓰고 모호한 곳은 「열린 질문」 표로 모은다.

1-3. Claude Code의 계획 모드

계획 모드(plan mode)는 Claude Code가 조사하고 계획을 제안하되 소스 파일을 고치지 않는 권한 모드다. Claude는 파일을 읽고, 탐색용 셸 명령을 돌리고, 계획을 쓰지만, 사람이 계획을 승인하기 전에는 편집하지 않는다[S5]. 2장에서 처음 써 보았으며, 이 장에서는 명세 주도 개발의 「계획」 단계를 맡긴다.

들어가고 나오는 방법은 다음과 같다(2026-11 기준, Claude Code 2.1.296에서 확인)[S4, S5].

[최신 자료 자리: Claude Code의 계획 모드 조작] 권한 모드의 순환 순서와 단축키(Shift+Tab, Ctrl+G), 상태 표시줄 문구(⏸ plan mode on), 계획 승인 질문의 선택지 이름, claude --permission-mode plan, /plan. 확인할 곳: https://code.claude.com/docs/en/permission-modes, claude --help. 2026-11-14에 Claude Code 2.1.296으로 확인한 값이 아래 표이다. 수업 전에 학습자 PC에 설치된 판으로 다시 확인한다.

하려는 일 방법
세션 중에 계획 모드로 Shift+Tab을 눌러 상태 표시줄에 ⏸ plan mode on이 보일 때까지 돈다. 순서는 default → acceptEdits → plan
프롬프트 하나만 계획 모드로 프롬프트 앞에 /plan을 붙인다
처음부터 계획 모드로 시작 claude --permission-mode plan
계획 모드에서 나오기 승인 질문이 떠 있지 않을 때 Shift+Tab. 승인 질문이 떠 있을 때는 먼저 Esc (그 상태의 Shift+Tab은 계획을 승인한다)

  • Yes, and use auto mode(자동 모드를 쓸 수 없으면 Yes, auto-accept edits): 계획을 승인하고 편집을 자동으로 받아들이는 모드로 넘어간다. 이 장에서는 쓰지 않는다.

  • No, keep planning: 계획 모드에 머물며 무엇을 바꿀지 말한다. 계획을 검토만 할 때 쓴다.

계획 모드의 쓰임은 「파일이 바뀌면 안 되는 분석 단계」를 보호하는 것이다. 4장의 구조 분석은 남의 서비스를 읽기만 하는 단계이므로 계획 모드에서 한다. 저장은 계획 모드를 나온 뒤에 따로 시킨다. 이렇게 단계를 나누면, 분석 결과를 읽고 고칠 기회가 저장 전에 한 번 생긴다. 한 번만 계획을 받고 싶으면 「/plan 복원명세.md를 읽고 명세가 정하지 않은 상황을 세 개 제안하라」처럼 프롬프트 앞에 /plan을 붙인다.

승인 질문에서 무심코 Enter를 누르면 첫 선택지가 골라질 수 있으므로 상태 표시줄을 보는 습관을 들인다. 받은 계획은 세션 동안 ~/.claude/plans/ 아래에 파일로 남는다[S5].

2. 재구현과 비교

4장에서 본 절차의 여섯 단계 가운데 ⑤ 재구현과 ⑥ 비교는 리버스 엔지니어링을 명세의 검사로 바꾸는 단계다. 명세만 받은 구현자가 무엇을 만드는지 보면, 명세가 무엇을 정했고 무엇을 정하지 않았는지가 결과의 차이로 드러난다. 이 절은 핵심 실습의 8-2~8-4에서 쓰는 규칙과 분류를 정리한다.

2-1. 원본을 보지 못한 구현자

재구현 폴더에는 명세와 자료만 넣는다. 원본의 주소, 받은 HTML(페이지.html), 구조 분석 파일은 넣지 않는다. 재구현하는 AI가 원본을 볼 수 있으면 명세의 빈틈을 원본으로 메워 버리고, 빈틈이 드러나지 않는다. 같은 까닭으로 구조를 분석한 세션을 쓰지 않고 새 세션을 연다. Claude Code의 세션은 대화 기록을 맥락으로 가지므로, 원본을 읽은 세션은 원본을 읽은 기억을 갖고 있다. 원본을 분석한 쪽과 명세만 받아 구현하는 쪽 사이에 오가는 것이 명세뿐이어야 한다.

재구현을 맡길 때는 「명세가 정하지 않아 네가 정한 것을 목록으로 보고하라」를 함께 요구한다. AI는 정보가 비어 있으면 그럴듯한 값으로 채우므로, 그 목록이 곧 명세의 빈틈 후보다. 명세가 「범위를 넘는 쪽 번호」를 정하지 않았다면 AI는 빈 목록, 마지막 쪽, 오류 가운데 하나를 스스로 고르고, 그 결정이 목록에 한 줄로 나온다. 그러므로 재구현이 원본과 똑같으면 잘한 것이 아니라 분리가 무너졌는지 먼저 의심한다.

2-2. 차이의 원인 다섯 가지

비교는 기능마다 원본과 재구현이 어떻게 하는지 적고, 다르면 그 원인을 다섯 가지로 분류한다. 원인에 따라 명세에 할 일이 다르다.

원인 뜻 명세 조치
① 명세 빈틈 명세가 정하지 않아 재구현이 임의로 정했다 명세에 요구를 더하거나 열린 질문으로 남긴다
② 매체 차이 웹 화면과 명령줄의 차이(단추와 옵션, 색과 글자) 명세는 그대로. 배치와 모양은 11장의 화면 명세가 맡는다
③ 데이터 한계 채용.csv에 없는 정보(상세 원문, 전체 76쪽) 명세는 그대로. 자료 범위를 명세의 맨 위에 밝힌다
④ 의도한 차이 원본보다 낫게 정한 것 명세에 그대로 두고, 비교표에 「의도」로 적는다
⑤ 범위 밖 처음부터 복원하지 않기로 한 것 「복원하지 않은 것」 절에 있는지 확인한다

명세 빈틈만 명세로 되돌린다. 매체 차이와 데이터 한계는 명세를 고칠 일이 아니다. 예를 들어 원본은 쪽 번호 단추를 보이고 재구현은 --page 옵션을 받는다면 ②이다. 이것을 명세 빈틈으로 보고 「쪽 번호 단추를 1~10까지 보여야 한다」를 명세에 넣으면, 문장 명세가 화면의 모양까지 정하게 된다. 그것은 11장 화면 명세의 몫이다.

복원은 복제가 아니다. 원본이 결과가 없을 때 빈 표만 보인다면, 복원 명세는 그것을 결함으로 보고 안내를 일부러 정할 수 있다(④). 원본의 구조를 이해한 위에서 더 나은 명세를 쓰는 것이 리버스 엔지니어링이 경쟁 분석에 쓰일 때의 본래 목적이다.

2-3. 실행 결과의 갈래

재구현 프로그램을 실행한 직후에는 정답 화면을 맞히지 않는다. 자기 화면이 다음 가운데 어느 갈래인지 찾는다. 오른쪽 열이 비교와 되돌리기(8-3, 8-4)에서 할 일이다.

프로그램의 상태 명세에서 본 원인 10-6·8-4에서 할 일
상태나 검색어를 줄 방법이 없고 전체 목록만 나온다 사건 문형의 요구가 없거나 「고르면」이 빠졌다 ① 명세 빈틈. 사건 요구를 더한다
없는 상태 이름을 주면 error: argument --state: invalid choice 같은 사용법 오류로 끝난다 잘못된 입력에 대한 원치 않는 동작 요구가 없어, 쓴 도구(argparse 등)의 기본 동작이 그대로 나왔다 ① 명세 빈틈. 원치 않는 동작 요구를 더할지 정한다
결과가 없을 때 아무것도 보이지 않는다 「결과가 없으면」의 원치 않는 동작 요구가 없다 ① 명세 빈틈
표가 아니라 세로 막대로 나눈 글자로 나온다 매체를 명세가 정하지 않았다. 명령줄은 4장에서 정한 매체이다 ② 매체 차이. 명세는 그대로 둔다
명세에 있는 열(예: 상세 내용)이 나오지 않는다 채용.csv에 그 정보가 없다 ③ 데이터 한계. 명세 맨 위의 자료 범위를 확인한다
명세의 요구가 모두 동작한다 문형이 고르게 있었다 「명세가 정하지 않아 정한 것」 목록에서 빈틈을 찾는다

둘째 행의 문구는 견본 프로그램에 없는 상태 이름(--state 모집중)을 주어 실제로 얻은 것이다(종료 코드 2). 오류로 끝나는 것 자체가 결함이 아니라, 명세가 그 상황을 정하지 않았다는 것이 요점이다.

2-4. 원본에 직접 묻기

「결과가 없을 때」와 「범위를 넘는 쪽 번호」는 화면에서 만들기 번거롭다. 3-3처럼 질의 문자열로 상태를 주소에 담을 수 있으면 원본에 직접 물어볼 수 있다. 빈 결과는 접수예정 공고가 없는 날의 stateCode=0이나 없는 검색어(searchType=E_TITLE&searchTxt=없는검색어123, 한글은 퍼센트 부호로 바뀐다)로, 범위를 넘는 쪽은 page=999로 만든다. 2026-11-14에는 stateCode=0이 0행, 11-16과 11-17에는 1행이었고 없는 검색어는 늘 0행이었다. 그래서 8-3은 두 방법을 모두 시험해 0행이 나오는 쪽을 쓴다.

이렇게 확인한 원본의 동작은 비교표의 「원본」 칸에 「관찰」로 적는다. 원본의 동작이 사용자에게 좋지 않아 보여도, 비교표에는 있는 그대로 적고 판단은 「원인」 칸(④)과 「명세 조치」 칸에서 한다.

3. 구현 지시문의 구성

3-1. 지시문의 다섯 칸

작업 하나를 Claude Code에 맡길 때 쓰는 지시문을 이 과목에서는 구현 지시문이라 부른다. 구현 지시문은 다섯 칸으로 구성한다.

칸 담는 것 빠지면 생기는 일
참조 이 작업이 따르는 명세의 요구 번호, 화면 명세의 화면 번호, 디자인 토큰, 이미 있는 공통 코드 Claude Code가 명세 대신 일반적인 관례로 만든다. 문구, 상태, 색이 명세와 달라진다
범위 만들 파일, 고쳐도 되는 파일, 고치지 않을 파일 다른 화면의 파일까지 “개선”한다. 커밋의 차이가 커져 검토할 수 없다
금지 사항 쓰지 않을 기술과 방식(외부 주소, 절대 경로, innerHTML, 명세에 없는 기능, 검사 파일 수정) 검사를 통과시키려고 검사를 고치거나, 배포 뒤에 깨지는 방식으로 만든다
완료 조건 끝났다고 말할 수 있는 관찰 가능한 결과(실행할 명령과 기대하는 출력) “구현했습니다”라는 말로 끝난다. 무엇이 확인되었는지 알 수 없다
모호할 때 명세가 정하지 않은 것을 만났을 때 할 일 빈틈을 Claude Code가 조용히 메운다. 그 결정은 어디에도 남지 않는다

다섯 칸은 2026년판 3주차의 두 사고에 대한 대응이기도 하다. “완료했습니다”를 믿었다가 빠진 요구가 드러난 일은 완료 조건이, AI가 테스트를 고친 일은 금지 사항이 없을 때 생긴다 [R1].

4. 정적 웹과 로컬 서버

4-1. 정적 웹

정적 웹(static web)은 미리 만들어 둔 파일(HTML, CSS, 자바스크립트, 이미지, JSON)을 서버가 그대로 보내 주기만 하는 웹이다. 요청이 올 때마다 서버에서 프로그램이 돌아 답을 만드는 웹을 동적 웹이라 한다. 2026년판 3주차는 이 구분을 “정적 파일”과 “서버 코드”로 설명하였다 [R1].

정적 웹에서도 화면은 움직인다. 검색어를 넣으면 목록이 줄고, 버튼을 누르면 글자가 바뀐다. 그 일은 서버가 아니라 사용자의 브라우저가 자바스크립트로 한다. 이 장의 웹이 정적 웹으로 충분한 까닭과 한계를 표로 정리한다.

할 일 이 장의 웹에서 하는 곳 정적 웹으로 되는가
공고 30건 보여 주기 브라우저가 data/jobs.json을 받아 화면을 만든다 된다. 자료가 모든 사용자에게 같기 때문이다
검색과 고르기 브라우저의 자바스크립트 된다. 30건은 브라우저가 다루기에 작다
관심 공고와 일정 기록 브라우저 저장소(localStorage) 이 브라우저 안에서는 된다. 다른 기기와는 공유되지 않는다
공고 자료 새로 고치기 사람이 jobs.json을 고쳐 다시 배포 된다. 다만 자동으로 새 공고를 모으지는 못한다
공고 요약(LLM) 서버가 API 키로 LLM을 부른다 안 된다. 키를 브라우저에 두면 누구나 볼 수 있다. 8장에서 서버를 붙인다
로그인, 여러 기기 동기화 서버와 데이터베이스 안 된다. 명세의 범위 밖이다

정적 웹의 장점은 운영할 것이 없다는 데 있다. 서버 프로그램이 없으므로 서버가 멈출 일, 데이터베이스가 깨질 일, 서버 쪽 보안 구멍이 없다. GitHub Pages 같은 정적 호스팅에 파일만 올리면 된다. 단점은 사용자마다 다른 것을 서버에 보관할 수 없다는 점이다. 이 장은 그 단점을 브라우저 저장소로 메운다.

4-2. file://로 열면 생기는 일

2026년판 3주차의 실습 1은 HTML 파일을 더블클릭해 file:// 주소로 열어 보았다 [R1]. 그때는 파일 하나짜리 화면이라 잘 열렸다. 이 장의 웹을 같은 방법으로 열면 화면의 틀은 보이지만 공고가 하나도 나오지 않는다.

[브라우저] (개발자 도구 F12 → Console 탭)

Fetch API cannot load file:///C:/.../jobprep/web/data/jobs.json.
URL scheme "file" is not supported.

위 문구는 2026-11-14에 Chromium 156에서 확인한 것이며 브라우저와 판에 따라 다르다. MDN에 따르면 여러 브라우저는 로컬 파일을 출처가 불투명한(opaque) 것으로 다루고, 다른 자원을 요청하는 일(CORS 요청)은 http와 https에서만 허용하며, 로컬에서 시험하려면 로컬 서버를 띄우라고 안내한다 [W4]. 로컬 파일이 다른 로컬 파일을 마음대로 읽을 수 있으면, 내려받은 HTML 파일 하나가 내 컴퓨터의 다른 파일을 읽어 밖으로 보낼 수 있기 때문이다.

견본 구현은 이때 화면에 “공고 자료를 불러오지 못했습니다. 로컬 서버로 열었는지 확인하십시오.”를 보인다. 오류를 콘솔에만 남기지 않고 화면에 보이는 것은 REQ-004(공고 자료를 읽지 못하면 안내)와 화면 명세 SCR-01의 「오류」 상태를 구현한 것이다.

4-3. 로컬 서버: python -m http.server

파이썬 표준 라이브러리의 http.server는 지정한 폴더의 파일을 http로 보내 주는 간단한 서버다. 설치할 것이 없다 [P1].

  • [port]: 기다릴 포트 번호. 기본값은 8000이다 [P1].
  • -b, --bind 주소: 연결을 받을 주소. 기본값은 모든 네트워크 주소이고, 127.0.0.1이면 이 컴퓨터 안에서만 받는다 [P1].
  • -d, --directory 폴더: 보낼 폴더. 기본값은 지금 폴더다 [P1].

공식 문서는 이 서버를 운영용으로 쓰지 말라고 경고한다. 기본적인 보안 점검만 하고, 심볼릭 링크를 따라가 지정한 폴더 밖의 파일을 보낼 수 있기 때문이다 [P1]. 개발 중의 확인에만 쓰고, 공개는 GitHub Pages로 한다.

이 과목은 웹 서버를 포트 8100으로 띄운다(부록 A-16). 기본값 8000은 8장부터 API 서버가 쓴다. 각자의 PC에서 실습하므로 다른 학습자와 번호가 겹칠 일은 없다. 주소를 127.0.0.1로 묶어 같은 무선망의 다른 컴퓨터가 접속하지 못하게 한다. 핵심 실습에서 다음 명령으로 실제로 띄운다. 여기서는 명령과 출력을 읽는다.

터미널 
cd ~/llm-service-lab/jobprep/web
python -m http.server 8100 --bind 127.0.0.1
Serving HTTP on 127.0.0.1 port 8100 (http://127.0.0.1:8100/) ...

이 터미널은 서버가 돌고 있으므로 다른 명령을 받지 않는다. 멈출 때는 Ctrl+C를 누른다. 브라우저에서 http://localhost:8100/을 바로 연다. 서버를 띄운 터미널에는 브라우저가 요청한 파일마다 한 줄씩 기록이 찍힌다. 이 기록이 “브라우저가 무엇을 요청했고 서버가 무엇을 답했는가”의 증거다. 다음은 집필용 Windows PC에서 요청 세 개를 보낸 기록이다(2026-11-17).

127.0.0.1 - - [17/Nov/2026 01:04:10] "GET / HTTP/1.1" 200 -
127.0.0.1 - - [17/Nov/2026 01:04:10] "GET /data/jobs.json HTTP/1.1" 200 -
127.0.0.1 - - [17/Nov/2026 01:04:11] code 404, message File not found
127.0.0.1 - - [17/Nov/2026 01:04:11] "GET /nothing.html HTTP/1.1" 404 -

끝의 숫자는 HTTP 상태 코드다. 200은 성공, 404는 그런 파일이 없음이다. 화면이 깨졌을 때 이 기록에서 404가 난 파일을 찾으면, 경로의 오타나 대소문자 차이를 바로 알 수 있다. 화면 파일이 아직 없는 폴더에서 띄우면 브라우저에 파일 목록 화면(“Directory listing for /”)이 보인다. GitHub Pages는 이런 목록을 보이지 않는다.

Windows에서는 같은 포트에 http.server를 두 번 띄워도 오류 없이 둘 다 떠서, 고친 파일이 반영되지 않은 것처럼 보일 수 있다(부록 A-16-1).

[그림 자리: 로컬 웹 서버와 브라우저] VS Code 통합 터미널에 Serving HTTP on 127.0.0.1 port 8100과 요청 기록이 보이고, 옆의 브라우저 주소창에 localhost:8100과 공고 목록이 보이는 화면. 웹 서버를 띄운 Windows 11 PC에서 찍는다.

5. 인수 조건

5-1. 요구와 인수 조건

요구사항 명세서의 문장은 “시스템이 무엇을 해야 하는가”를 말하지만, 그것만으로는 구현이 요구를 충족했는지 판정하기 어렵다. REQ-006 “제목이나 모집기관에 검색어가 든 공고만 표시해야 한다”는 어떤 자료에서, 어떤 검색어를 넣고, 무엇을 보면 충족인가. 이 물음에 답한 것이 인수 조건(acceptance criteria)이다. 인수 조건은 요구 하나를 “이 상황에서 이렇게 하면 이것이 보여야 한다”는 구체적인 예로 바꾼 것이고, 예를 통과하면 그 요구를 받아들인다(인수한다). 출발점은 명세서 6절의 수용 기준이다. 수용 기준 AC-006-1의 예(「공무직」)는 이 장의 자료에 없으므로 같은 번호로 예를 바꾼다. 자료의 「기업」(company)이 명세의 「모집기관」이다.

구분 요구 (명세) 인수 조건
말하는 것 일반 규칙 구체적인 예 하나
예 검색어가 든 공고만 보인다 30건이 있을 때 “데이터”를 넣으면, 제목이나 기업에 “데이터”가 든 공고만 마감일 순으로 보인다
판정 사람의 해석이 필요하다 화면을 보면 참과 거짓이 갈린다
수 요구 하나 요구 하나에 하나 이상
누가 읽는가 기획자, 개발자, AI 개발자, 검사하는 사람, 자동 검사

인수 조건은 테스트와 다르다. 테스트는 인수 조건을 확인하는 수단의 하나다. 같은 인수 조건을 사람이 화면에서 손으로 확인할 수도 있고, 이 장의 자동 검사처럼 기계가 확인할 수도 있다. 이 과목은 인수 조건을 쓰고 기계로 확인하는 데까지 다룬다. 테스트를 먼저 쓰고 구현을 그에 맞추어 키우는 테스트 주도 개발(TDD)은 「AI에이전트 기획 및 개발」 2장이 다룬다.

5-2. Given-When-Then

인수 조건은 흔히 Given-When-Then의 세 부분으로 쓴다. Daniel Terhorst-North와 Chris Matts가 행위 주도 개발(BDD)의 일부로 만든 형식이고, 시나리오 하나를 세 부분으로 나누어 쓰는 방식이다 [S2].

부분 뜻 [S2] 이 장의 예 (AC-009-1)
Given 행동 전의 상태. 시나리오의 전제 조건 JOB-005가 관심 공고가 아니다
When 명세하려는 행동 상세 화면에서 저장을 누르고, 새로고침하고, 새 탭에서 관심 공고 화면을 연다
Then 그 행동의 결과로 기대하는 변화 버튼이 “관심 해제”로 남고, 새 탭의 관심 공고 화면에 JOB-005가 보인다

Given을 빼먹기 쉽다. “검색어를 넣으면 결과가 나온다”는 Given이 없다. 공고가 0건이면 무엇을 넣어도 결과가 없다. 관심 공고가 이미 저장된 상태에서 저장 버튼을 누르면 해제가 된다. Given이 다르면 같은 When이 다른 Then을 낳는다. 이 사실은 7절의 브라우저 에이전트 판정을 읽을 때 다시 쓴다.

Then은 관찰할 수 있어야 한다. “빠르게 보인다”, “잘 동작한다”, “사용하기 편하다”는 Then이 될 수 없다. 무엇을 보면 참인지 정할 수 없기 때문이다. 화면의 글자, 요소의 수, 요소가 보이는가, 주소가 무엇인가처럼 보면 참과 거짓이 갈리는 것으로 쓴다.

5-3. 좋은 인수 조건과 나쁜 인수 조건

나쁜 예 문제 고친 예
검색이 잘 된다 Then을 관찰할 수 없다. Given과 When이 없다 Given 30건, When “데이터” 입력, Then 제목이나 기업에 “데이터”가 든 공고만 보인다
filter 함수가 배열을 거른다 구현 방법을 적었다. 사용자는 함수를 보지 않는다 Then을 화면에 보이는 카드로 쓴다
관심 공고가 저장된다 “저장된다”를 어떻게 보는지 없다 Then 버튼이 “관심 해제”로 바뀌고, 새 탭의 관심 공고 화면에 보인다
마감 임박 공고가 눈에 띈다 “임박”, “눈에 띈다”가 수와 모양으로 정해지지 않았다 Given 기준일 2027-05-17, When 목록을 연다, Then 0~3일 남은 공고에 「마감 임박 D-N」(REQ-003의 3일 이하, 검사용 약속의 문구)
오류 없이 동작한다 무엇을 했을 때의 오류인지 없다 Given 일정 0건, When 날짜 없이 추가, Then 오류 문구가 보이고 일정이 0건이다

인수 조건을 쓰다 보면 명세의 빈틈이 드러난다. “검색어가 포함된”은 대소문자를 가리는가. 공백만 넣으면 어떻게 되는가. 명세가 말하지 않는 것은 인수 조건이 정하지 않는다. 인수 조건이 명세에 없는 규칙을 만들면, 명세와 인수 조건이 서로 다른 말을 하는 두 기준이 된다. 빈틈을 찾으면 명세에 결정을 더하고 인수 조건은 그 결정을 따른다.

6. 배포의 개념과 GitHub Pages

6-1. 로컬과 배포

배포(deployment)는 내 파일을 서버에 올려 누구든 요청할 수 있게 하는 일이고, 그 결과가 공개 주소다 [R1]. 구현과 검사를 하는 동안의 웹은 로컬에 있다. 내 PC의 폴더에 파일이 있고, 그 파일을 보는 사람은 나 하나다. 배포하면 파일이 GitHub의 서버로 가고, 주소를 아는 누구나 연다.

구분 로컬 (핵심 실습 1~5단계) 배포 (6단계부터)
파일의 위치 내 PC의 jobprep/web/ GitHub Pages 서버
주소 http://localhost:8100/ https://아이디.github.io/llm-service-lab/
보는 사람 나 주소를 아는 누구나(검색 엔진 포함)
고친 것의 반영 저장하고 새로고침 커밋하고 푸시하면 워크플로가 다시 배포
잘못되었을 때 나만 본다 모든 방문자가 본다
브라우저 저장소의 출처 http://localhost:8100 https://아이디.github.io (다른 출처이므로 기록이 이어지지 않는다)

이 장은 2026년판 3주차가 소개한 “만드는 동안은 로컬, 완성본만 배포”의 동선대로, 인수 조건을 로컬에서 통과한 뒤에 배포한다 [R1].

6-2. GitHub Pages

GitHub Pages는 저장소의 HTML, CSS, 자바스크립트 파일을 그대로 받아 웹사이트로 내보내는 정적 사이트 호스팅이다 [G3]. 사이트에는 두 종류가 있다 [G3]. 사용자·조직 사이트는 이름이 아이디.github.io인 저장소에서 나오고 주소가 https://아이디.github.io이며 계정마다 하나다. 프로젝트 사이트는 아무 저장소에서나 나오고 주소가 https://아이디.github.io/저장소이름이며 저장소마다 하나다. 이 장의 사이트는 jobs-board 저장소의 프로젝트 사이트이므로 주소가 https://아이디.github.io/jobs-board/이다. 주소에 저장소 이름이 하위 경로로 들어가므로 파일의 경로는 상대 경로로 쓴다.

사용 한도(게시 사이트 1GB, 월 대역폭 100GB, 배포 시간 10분 등)가 있으나 이 장의 사이트는 50KB 안팎이다 [G5].

[최신 자료 자리: Pages와 Actions의 사용 한도] Pages 한도 [G5]와 비공개 저장소의 Actions 포함 사용량 [G7]. 2026-11-16에 다시 확인한 값은 1GB, 월 100GB, 시간당 10회, 10분, Free 월 12달러·Pro 월 18달러 상당이다.

7. 브라우저 에이전트와 판정의 근거

7-1. 브라우저 에이전트

브라우저 에이전트는 자연어로 받은 작업을 브라우저를 직접 조작해 수행하는 AI이다. 이 장은 Aside(2025년 가을 Y Combinator 선정)를 쓴다. Aside는 웹사이트에서 여러 단계의 일을 하되 결제·메시지 같은 민감한 동작 앞에서는 사람의 승인을 기다리는 브라우저로 소개되고 [B1][B2], 개발자 문서는 첫 사용 예로 로컬 웹앱의 스모크 테스트를 든다 [B3].

인수 조건은 코드로 쓴 검사나 사람이 화면에서 한 손 점검으로 확인한다. 브라우저 에이전트는 자연어로 쓴 인수 조건 표를 받아 판정을 돌려주는 또 하나의 방법이다. 이 절의 물음은 에이전트가 「통과」라고 보고한 것을 근거로 삼을 수 있는가이다. “구현했습니다”라는 말 대신 바뀐 파일을 읽듯이, 에이전트의 판정도 손 점검에 대어 본다.

학습자는 각자 설치한 Aside를 자기 계정으로 쓴다(계정 부록 A-2-3, 설치·로그인과 로컬 웹 열기 A-19, 이 장 전에 끝낸다). 맡기는 일은 인수 조건 표의 점검 한 번이다(핵심 실습). 같은 일을 하는 다른 도구로 Ego Lite가 있다(무료, macOS·Windows) [B4].

[최신 자료 자리: Aside의 요금, 크레딧, 지원 운영체제] 확인할 곳 [B2], https://aside.com/pricing, 부록 A-2-3과 A-19-1. 2026-11-16에 확인한 값은 무료 요금제 월 500 크레딧(루틴 3개, 자기 구독 연결 가능), Pro 월 20달러, Max 월 200달러, macOS 15 이상과 Windows 10 22H2 이상·Windows 11(리눅스 없음)이다. 수업 전에 다시 확인한다.

7-2. 지켜야 할 세 가지

  1. 내 PC의 로컬 주소로만 한다. 대상은 핵심 실습에서 내 PC에 띄운 웹 서버 http://localhost:8100/이며, 공개 배포 주소로 하지 않는다. Aside도 같은 PC에서 돌므로 이 주소를 바로 연다(부록 A-19-3). 인수 조건은 배포 전의 판정이다. 에이전트가 갈 수 있는 곳도 이 주소 하나로 좁힌다.
  2. 자격 증명을 주지 않는다. 이 웹은 로그인이 없다. 작업 지시에 GitHub 계정, Claude 계정, API 키를 적지 않고, 에이전트의 브라우저에 다른 사이트의 로그인 탭을 열어 두지 않는다. Aside는 자격 증명을 AI에 드러내지 않고 자동 입력한다고 밝히지만 [B2], 쓸 일이 없는 자격 증명은 처음부터 닿지 않게 한다.
  3. 개인 정보를 입력하게 하지 않는다. 에이전트의 AI 모델은 화면의 내용과 지시를 읽는다. 입력값은 인수 조건 표에 적힌 값만 쓰게 한다. 에이전트가 다른 사이트로 가거나 승인을 요청하면 지시를 벗어난 것이므로 거절한다.

Aside 
http://localhost:8100/ 에 열린 정적 웹을 아래 인수 조건 표로 점검해 줘.
- 이 주소와 그 아래 경로만 연다. 다른 사이트로 가지 않는다.
- 로그인, 결제, 메시지 보내기, 파일 내려받기, 브라우저 설정 바꾸기를 하지 않는다.

- 확인할 방법이 없으면 추측하지 말고 「판정 못함」과 그 까닭을 적는다.

(여기에 ch05/인수조건.md 의 「에이전트」 행을 붙인다)

에이전트의 판정을 내 손 점검과 서버의 요청 기록(로컬 서버를 띄운 터미널)에 대조한다. 판정이 다르면 화면을 다시 보고 어느 쪽이 맞는지 적는다.

자주 하는 실수와 해결

증상 원인 해결
재구현 세션이 원본의 내용을 안다 재구현을 분석한 세션에서 했거나, 재구현 폴더에 구조분석.md가 있다 새 터미널, 새 세션에서 다시 한다(2-1)
claude --continue가 엉뚱한 세션을 연다 그 명령을 다른 폴더에서 실행했다 이어 열리는 세션은 그 폴더의 마지막 세션이다. 구현한 폴더로 옮겨 다시 실행한다
프로그램 실행이 can't open file을 낸다 파일 이름은 AI가 지으므로 사람마다 다르다 ls로 본 이름으로 실행한다
재구현 프로그램의 한글 오류 메시지가 알아볼 수 없는 글자로 깨진다 Windows에서 파이썬이 오류 출력을 시스템 기본 인코딩(cp949)으로 내보내는데, 터미널은 UTF-8로 읽었다. 파이프(|)로 넘길 때도 생긴다 터미널마다 export PYTHONUTF8=1을 한 번 하거나 명령 앞에 PYTHONUTF8=1을 붙인다(0절). 키트의 검사기는 스스로 UTF-8로 출력하므로 해당하지 않는다
화면에 목록이 없고 Console에 CORS 오류가 보인다 index.html을 file://로 열었다 로컬 서버로 연다(4-2)
공개 주소에서만 목록이 없다 경로가 /로 시작하거나 파일 이름의 대소문자가 다르다 Network 탭에서 404가 난 주소를 보고 상대 경로로 고친다

정리

  • 명세 주도 개발은 명세를 구현의 입력이자 검사의 기준으로 삼는다. Spec Kit의 단계는 Claude Code의 계획 모드와 마크다운 파일로 같은 순서를 밟을 수 있다.
  • 재구현한 결과가 원본과 다른 자리는 명세 빈틈, 매체 차이, 데이터 한계, 의도한 차이, 범위 밖으로 나뉜다. 명세 빈틈만 명세로 되돌린다.
  • 구현자가 원본을 볼 수 있으면 빈틈이 드러나지 않는다. 분석한 쪽과 구현하는 쪽 사이에 오가는 것은 명세뿐이어야 한다.
  • 인수 조건은 요구를 구체적인 전제, 행동, 기대 결과로 옮긴 것이다. 기계가 확인할 것과 사람이 볼 것을 나눈다.
  • 배포는 남의 기기에서 열리는 것이 기준이다. 공개 저장소에 올린 것은 모두 공개된다.
  • 브라우저 에이전트의 판정은 근거와 대조한다. 「판정 못함」을 고를 수 있게 지시한다.
