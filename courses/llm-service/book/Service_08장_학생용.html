API 명세와 웹앱의 구현

2027학년도 「LLM 서비스 개발」의 준비 중인 교재입니다. 편집 상태를 검토하기 위해 미리 공개한 것으로, 수업 전에 내용과 순서가 바뀔 수 있습니다.

학사 10주차 · 교재 08 · 서비스 3: 예약·일정 웹앱 (2/2)

개편 초안(2026-11-18). 이 장은 plan/개편안.md의 단원형 구성에 따라 새로 쓴 초안이다. 서버의 코드와 출력은 집필 환경(Linux, Python 3.13.18, FastAPI 0.163.2, Pydantic 2.14.3, Uvicorn 0.54.0, pytest 9.2.0)에서 2026-11-18에 실제로 실행해 얻은 것이며, 실습실 PC(Windows 11, Git Bash)에서는 아직 확인하지 않았다. 「실행 전」이라고 적은 곳은 실행으로 확인하지 않았다. 키트와 예제 웹앱은 아직 없다.

7장에서 예제 웹앱의 호출을 기록해 끝점 목록을 만들었다. 이 장은 그 목록을 API 명세로 고쳐 쓰고, 명세만으로 서버를 구현한다. 5장의 정적 웹에는 서버가 없었다. 예약 서비스에는 서버가 있어야 한다. 겹치는 예약을 막는 판정은 여러 사용자의 예약을 모두 아는 쪽만 할 수 있기 때문이다.

구현한 서버가 명세대로인지는 두 가지로 확인한다. 하나는 테스트이다. 다른 하나는 대조이다. 7장에서 기록한 요청을 내 서버에 같은 순서로 보내 응답의 상태 코드를 견준다. 6장에서 명령줄 프로그램의 출력을 대조한 방법을 서버에 적용한 것이다.

학습 목표

  • 끝점 목록에서 API 명세(요청, 응답, 오류)를 쓰고, 기록에 없던 경우를 열린 질문으로 남기거나 정할 수 있다.
  • 판정을 서버 쪽에 두어야 하는 까닭을 설명하고, 입력의 검증과 업무 규칙의 판정을 구분해 구현할 수 있다.
  • 상태 코드를 실패의 원인에 따라 고를 수 있다.
  • API 명세의 경우마다 테스트를 쓰고, 경계의 경우를 포함할 수 있다.
  • 기록한 요청을 내 서버에 다시 보내 응답을 대조하고, 대조가 본 것과 보지 못한 것을 구분할 수 있다.

1. API 명세

1-1. 끝점 목록에서 명세로

끝점 목록은 관찰한 것의 기록이다. 명세는 구현이 지켜야 할 약속이다. 둘의 차이는 기록에 없던 경우에 있다. 목록의 「모른다」를 명세는 정하거나 열린 질문으로 남겨야 한다. 정하지 않으면 구현하는 쪽이 정한다.

API 명세는 끝점마다 다음을 적는다.

항목 적는 것
요청 메서드, 경로, 질의 문자열, 본문의 항목과 형식(필수인가, 범위)
성공 응답 상태 코드와 본문의 항목
오류 응답 경우마다 상태 코드와 안내 문구
규칙 서버가 판정하는 업무 규칙(EARS 문장)
근거 7장의 끝점 목록의 행, 또는 「정함」과 그 까닭

1-2. 명세의 예

[파일: ch08/API명세.md] (일부)


## POST /api/reservations  예약을 만든다

요청 본문(JSON)
| 항목 | 형식 | 필수 | 범위 |
|---|---|---|---|
| room_id | 정수 | 예 | 있는 방의 id |
| date | 날짜(YYYY-MM-DD) | 예 | |
| start, end | 시각(HH:MM) | 예 | end는 start보다 뒤 |
| name | 문자열 | 예 | 1~20자 |

응답
| 경우 | 상태 코드 | 본문 | 근거 |
|---|---|---|---|
| 만들었다 | 201 | 만든 예약(id 포함) | 끝점 목록 3행 |
| 같은 방, 같은 날에 겹치는 예약이 있다 | 409 | detail: 안내 문구 | 끝점 목록 4행 |
| 없는 방이다 | 404 | detail: 안내 문구 | 정함: 기록에 없다 |
| 형식이 틀렸거나 end가 start보다 뒤가 아니다 | 422 | detail: 틀린 항목 | 정함: 기록에 없다 |

규칙
- **REQ-03** [원치 않는 동작] 만약 같은 방, 같은 날에 시간이 겹치는 예약이 있으면, 시스템은 예약을 만들지 않고 409로 응답해야 한다.
- **REQ-04** [상시] 시스템은 한 예약의 끝 시각과 다른 예약의 시작 시각이 같은 경우를 겹치지 않는 것으로 판정해야 한다. (정함: 10:00~11:00 뒤에 11:00~12:00을 잡을 수 있어야 한다)

REQ-04는 기록에 없던 경우이다. 「겹친다」는 말은 끝과 시작이 맞닿은 경우를 정하지 않는다. 정하지 않으면 <와 <= 가운데 하나를 구현하는 쪽이 고른다. 명세가 정해야 할 경계이다.

1-3. 상태 코드의 선택

브라우저 쪽의 코드는 상태 코드를 보고 무엇을 할지 정한다. 실패의 원인에 따라 코드를 나눈다.

코드 뜻 예약 API에서 생기는 때 화면이 할 일
200 성공 목록을 돌려준다 그린다
201 만들었다 예약을 만들었다 목록을 다시 읽는다
204 성공, 본문 없음 예약을 지웠다 목록을 다시 읽는다
404 대상이 없다 없는 방, 없는 예약 목록을 다시 읽고 알린다
409 지금의 상태와 충돌한다 겹치는 예약 다른 시간을 고르게 한다
422 요청의 내용이 틀렸다 형식, 범위, 앞뒤가 바뀐 시각 틀린 칸을 알린다. 다시 눌러도 같다

409와 422를 나누는 까닭이 있다. 422는 요청 자체가 틀린 것이어서 언제 보내도 실패한다. 409는 요청은 옳으나 지금의 자료와 충돌하는 것이어서, 앞의 예약이 취소되면 같은 요청이 성공한다. 화면의 안내가 달라야 한다.

2. 서버 쪽 판정

2-1. 브라우저의 검사는 편의이다

화면에서 끝 시각을 시작 시각보다 앞으로 고르지 못하게 막을 수 있다. 그것은 사용자의 편의를 위한 것이며 보호가 아니다. 서버의 주소를 아는 사람은 화면을 거치지 않고 요청을 직접 보낼 수 있다. 7장에서 본 대로 요청은 메서드, 경로, 본문일 뿐이고, curl 한 줄로 만들 수 있다. 그러므로 지켜야 하는 규칙은 서버가 판정한다.

판정 브라우저 서버
빈 칸, 형식 한다(빨리 알리기 위해) 한다
끝 시각이 시작 시각보다 뒤인가 한다 한다
다른 예약과 겹치는가 할 수 없다(다른 사용자의 예약을 모른다) 한다
내 예약만 지울 수 있는가 할 수 없다 한다(이 장의 범위 밖. 6-1)

2-2. 입력의 검증과 업무 규칙의 판정

서버의 판정은 두 층으로 나뉜다.

  • 입력의 검증. 요청 하나만 보고 판정할 수 있다. 형식, 필수, 범위. 틀리면 422이다.
  • 업무 규칙의 판정. 저장된 자료와 견주어야 판정할 수 있다. 겹침, 있는 방인가. 틀리면 409 또는 404이다.

FastAPI는 요청 본문의 모양을 Pydantic 모델로 적으면 입력의 검증을 대신 해 준다 [X3]. 업무 규칙은 함수 안에 직접 쓴다.

2-3. 겹침의 판정

두 구간 [s1, e1)과 [s2, e2)가 겹치는 조건은 s1 < e2이고 s2 < e1인 것이다. 끝과 시작이 같은 경우(e1 == s2)는 둘째 조건이 거짓이므로 겹치지 않는다. 1-2의 REQ-04가 정한 대로이다. 조건을 <=로 쓰면 맞닿은 예약이 거절된다. 글자 하나가 명세의 경계를 정한다.

3. 따라 하기: 예약 API

3-1. 서버의 코드 (읽기)

다음은 1-2의 명세로 만든 서버의 견본이다. 각자의 서버는 핵심 실습에서 Claude Code로 만든다. 자료는 메모리에 두므로 서버를 끄면 사라진다.

[파일: ch08/app.py] (읽기. 교수용 견본)

"""스터디룸 예약 API. 자료는 메모리에 둔다(서버를 끄면 사라진다)."""
from datetime import date, time

from fastapi import FastAPI, HTTPException
from pydantic import BaseModel, Field

app = FastAPI(title="예약 API")

ROOMS = [
    {"id": 1, "name": "스터디룸 A", "capacity": 4},
    {"id": 2, "name": "스터디룸 B", "capacity": 8},
]
RESERVATIONS: list[dict] = []
NEXT_ID = {"value": 1}

class ReservationIn(BaseModel):
    room_id: int
    date: date
    start: time
    end: time
    name: str = Field(min_length=1, max_length=20)

@app.get("/api/rooms")
def list_rooms():
    return ROOMS

@app.get("/api/reservations")
def list_reservations(date: date):
    return [r for r in RESERVATIONS if r["date"] == date]

@app.post("/api/reservations", status_code=201)
def create_reservation(body: ReservationIn):
    if not any(room["id"] == body.room_id for room in ROOMS):
        raise HTTPException(status_code=404, detail="없는 방이다")
    if body.end <= body.start:
        raise HTTPException(status_code=422, detail="끝 시각은 시작 시각보다 뒤여야 한다")
    for r in RESERVATIONS:
        same = r["room_id"] == body.room_id and r["date"] == body.date
        if same and body.start < r["end"] and r["start"] < body.end:
            raise HTTPException(status_code=409, detail="겹치는 예약이 있다")
    new = {"id": NEXT_ID["value"], **body.model_dump()}
    NEXT_ID["value"] += 1
    RESERVATIONS.append(new)
    return new

@app.delete("/api/reservations/{reservation_id}", status_code=204)
def delete_reservation(reservation_id: int):
    for r in RESERVATIONS:
        if r["id"] == reservation_id:
            RESERVATIONS.remove(r)
            return
    raise HTTPException(status_code=404, detail="없는 예약이다")

ReservationIn이 입력의 검증이고, create_reservation 안의 세 판정이 업무 규칙이다. 겹침의 조건은 2-3의 식 그대로이다.

3-2. 서버 띄우기와 요청 보내기

[터미널] 하나에서 서버를 띄운다. 끌 때는 Ctrl+C를 누른다.

[터미널] (서버용)

cd ~/llm-service-lab/ch08
python -m uvicorn app:app --port 8300

다른 [터미널]에서 요청을 보낸다. -w는 응답 뒤에 상태 코드를 붙여 보인다.

터미널 
B='{"room_id": 1, "date": "2027-05-17", "start": "10:00", "end": "11:00", "name": "연습"}'
curl -s http://localhost:8300/api/rooms; echo
curl -s -w "\n상태 코드 %{http_code}\n" -X POST http://localhost:8300/api/reservations -H "Content-Type: application/json" -d "$B"
[{"id":1,"name":"스터디룸 A","capacity":4},{"id":2,"name":"스터디룸 B","capacity":8}]
{"id":1,"room_id":1,"date":"2027-05-17","start":"10:00:00","end":"11:00:00","name":"연습"}
상태 코드 201

보낸 시각은 10:00인데 응답은 10:00:00이다. 명세는 시각의 형식을 HH:MM이라고만 적었고 응답의 형식은 정하지 않았다. 구현이 정한 것이다. 화면이 이 값을 그대로 보이면 초가 붙어 보인다. 명세의 빈틈 하나이다.

  • 확인 2 서버가 떠 있는 동안 GET /api/rooms가 방의 목록을 돌려주고, POST /api/reservations가 상태 코드 201과 id가 든 본문을 돌려준다.

3-3. 거절되는 요청

겹치는 시간과 틀린 형식을 보낸다.

터미널

3-4. 자동 문서

FastAPI는 코드에서 대화형 문서를 만든다. 서버가 떠 있는 동안 브라우저에서 http://localhost:8300/docs를 열면 끝점 넷과 요청 본문의 모양이 보인다. 이 문서는 구현에서 나온 것이다. 1-2의 명세와 나란히 놓으면 구현이 명세와 다른 곳(항목의 이름, 필수 여부)을 찾을 수 있다. 6장에서 말한 의도(명세)와 사실(구현)의 대조이다.

[그림 자리: FastAPI의 자동 문서] http://localhost:8300/docs에서 POST /api/reservations를 펼쳐 요청 본문의 모양이 보이는 화면. 내 PC의 브라우저에서 찍는다.

4. 테스트와 대조

4-1. 경우 하나에 테스트 하나

명세의 「응답」 표의 행마다 테스트를 하나 쓴다. 테스트는 서버를 띄우지 않고 요청을 보내는 TestClient로 쓴다 [X1]. 경계(맞닿은 예약)의 테스트를 반드시 넣는다.

파일: ch08/test_app.py 
from fastapi.testclient import TestClient

import app as m

client = TestClient(m.app)
BODY = {"room_id": 1, "date": "2027-05-17", "start": "10:00", "end": "11:00", "name": "연습"}

def setup_function():
    m.RESERVATIONS.clear()
    m.NEXT_ID["value"] = 1

def test_create_and_list():
    assert client.post("/api/reservations", json=BODY).status_code == 201
    got = client.get("/api/reservations", params={"date": "2027-05-17"}).json()
    assert len(got) == 1 and got[0]["name"] == "연습"

def test_overlap_is_rejected():
    client.post("/api/reservations", json=BODY)
    r = client.post("/api/reservations", json={**BODY, "start": "10:30", "end": "11:30"})
    assert r.status_code == 409

def test_touching_is_allowed():
    client.post("/api/reservations", json=BODY)
    r = client.post("/api/reservations", json={**BODY, "start": "11:00", "end": "12:00"})
    assert r.status_code == 201

def test_end_before_start():
    r = client.post("/api/reservations", json={**BODY, "start": "11:00", "end": "10:00"})
    assert r.status_code == 422

def test_delete_twice():
    client.post("/api/reservations", json=BODY)
    assert client.delete("/api/reservations/1").status_code == 204
    assert client.delete("/api/reservations/1").status_code == 404
터미널 
python -m pytest -q 2>&1 | tail -1
5 passed, 1 warning in 0.28s

시간은 실행마다 다르다. 경고 한 건은 테스트 도구가 쓰는 패키지(httpx)의 교체를 알리는 것이며 결과와 무관하다. setup_function이 테스트마다 자료를 비운다. 비우지 않으면 앞 테스트가 만든 예약이 남아 뒤 테스트의 결과를 바꾼다.

test_touching_is_allowed가 REQ-04를 지킨다. 누군가 겹침의 조건을 <=로 바꾸면 이 테스트가 실패한다.

4-2. 기록의 재생

7장의 HAR에는 예제 웹앱이 받은 요청과 낸 응답이 순서대로 들어 있다. 같은 요청을 내 서버에 같은 순서로 보내면, 내 서버가 예제와 같은 응답을 내는지 견줄 수 있다.

파일: ch08/replay.py 
"""HAR에 기록된 /api/ 요청을 내 서버에 같은 순서로 보내고 상태 코드를 견준다."""
import json
import sys
import urllib.error
import urllib.request
from urllib.parse import urlsplit

har, base = sys.argv[1], sys.argv[2].rstrip("/")
same = diff = 0
for i, e in enumerate(json.load(open(har, encoding="utf-8"))["log"]["entries"]):
    req = e["request"]
    u = urlsplit(req["url"])
    if not u.path.startswith("/api/"):
        continue
    data = req.get("postData", {}).get("text")
    r = urllib.request.Request(
        base + u.path + ("?" + u.query if u.query else ""),
        data=data.encode("utf-8") if data else None,
        method=req["method"],
        headers={"Content-Type": "application/json"} if data else {},
    )
    try:
        got = urllib.request.urlopen(r).status
    except urllib.error.HTTPError as err:
        got = err.code
    want = e["response"]["status"]
    mark = "같다" if got == want else "다르다"
    same, diff = same + (got == want), diff + (got != want)
    print(f'{i:>3} {mark} | 기록 {want}, 내 서버 {got} | {req["method"]} {u.path}')
print(f"같다 {same}건, 다르다 {diff}건")

서버를 껐다가 다시 띄워 자료를 비운 뒤 실행한다.

터미널

  3 같다 | 기록 200, 내 서버 200 | GET /api/reservations
  4 같다 | 기록 201, 내 서버 201 | POST /api/reservations
  5 같다 | 기록 200, 내 서버 200 | GET /api/reservations
  6 같다 | 기록 409, 내 서버 409 | POST /api/reservations
  7 같다 | 기록 204, 내 서버 204 | DELETE /api/reservations/1
  8 같다 | 기록 404, 내 서버 404 | DELETE /api/reservations/1
같다 7건, 다르다 0건

위 출력은 7장의 견본 HAR(손으로 만든 요청 9건)와 3-1의 견본 서버로 2026-11-18에 실제로 얻은 것이다. 예제 웹앱의 기록으로 얻은 것이 아니다.

이 대조에는 세 가지 한계가 있다.

  1. 상태 코드만 본다. 본문의 항목과 형식은 견주지 않았다. 3-2에서 본 10:00:00은 이 대조로 드러나지 않는다.
  2. 기록에 있는 요청만 본다. 7장에서 하지 않은 조작은 견줄 수 없다. 맞닿은 예약은 기록에 없었다.
  3. 순서와 상태에 기댄다. 서버에 앞선 자료가 남아 있으면 id가 달라져 삭제의 요청이 다른 예약을 가리킨다. 그래서 서버를 다시 띄운 뒤에 실행한다.
  • 확인 5 서버를 다시 띄운 뒤 replay.py의 마지막 줄이 「다르다 0건」이거나, 다른 행마다 까닭을 ch08/대조.md에 적었다.

5. 명세 주도 도구의 시연: MoAI-ADK (교수 시연, 실행 전)

4~5장과 이 장에서 명세 → 계획 → 구현 → 검사의 순서를 Claude Code와 마크다운 파일로 밟았다. 같은 순서를 단계로 고정해 주는 도구가 있다. MoAI-ADK는 Claude Code를 감싸는 에이전트 하네스이다. 저장소의 안내에 따르면 작업을 /moai plan(명세) → /moai run(구현) → /moai sync(문서와 정리)의 세 단계로 진행하고, 완료의 주장을 실제로 실행한 명령과 출력에 묶는다 [X2].

이 절은 교수 화면의 시연으로 10분 동안 보고, 학습자는 설치하지 않는다. 시연에서 볼 것은 둘이다.

볼 것 이 과목에서 손으로 한 일 도구가 하는 일
단계의 고정 계획 모드에서 받고, 나와서 저장하고, 새 세션에서 구현한다 명령 하나가 단계 하나를 맡고 산출물의 자리가 정해져 있다
완료의 근거 인수 조건 표, 테스트, 대조를 사람이 돌린다 「끝났다」는 주장에 실행한 명령과 출력을 붙이게 한다

도구가 단계를 고정해 주어도 명세의 빈틈은 사람이 찾는다. 이 장의 REQ-04(맞닿은 예약)는 도구가 대신 정해 주지 않는다.

[최신 자료 자리: MoAI-ADK의 명령과 지원 환경] 수업 전에 저장소의 안내를 다시 읽는다. 확인할 곳: https://github.com/modu-ai/moai-adk. 2026-11-18에 읽은 값: 세 단계의 명령 이름은 위와 같고, Windows는 WSL을 권장하며 cmd.exe는 지원하지 않는다고 안내한다. 사용권은 Apache-2.0이다. 설치와 실행은 해 보지 않았다. 실습실 PC에서 되지 않으면 시연을 저장소의 안내를 읽는 것으로 바꾼다.

정리

  • 끝점 목록은 관찰의 기록이고 API 명세는 약속이다. 기록에 없던 경우를 명세가 정하지 않으면 구현하는 쪽이 정한다.
  • 지켜야 하는 규칙은 서버가 판정한다. 브라우저의 검사는 편의이다.
  • 입력의 검증은 요청 하나만 보고, 업무 규칙의 판정은 저장된 자료와 견주어 한다. 상태 코드가 그 차이를 알린다.
  • 경계의 경우는 글자 하나로 갈린다. 명세가 정하고 테스트가 지킨다.
  • 기록의 재생은 상태 코드, 기록에 있는 요청, 같은 순서만 본다. 대조가 본 것을 함께 적는다.
  • 명세 주도 도구는 단계를 고정해 주지만 명세의 빈틈은 사람이 찾는다.
