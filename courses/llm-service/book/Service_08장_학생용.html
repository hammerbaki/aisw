네트워크 동작의 분석과 API 구현

2027학년도 「LLM 서비스 개발」의 준비 중인 교재입니다. 편집 상태를 검토하기 위해 미리 공개한 것으로, 수업 전에 내용과 순서가 바뀔 수 있습니다.

학사 10주차 · 교재 08 · 서비스 3: 예약·일정 웹앱 (2/2)

개편 초안 2판(2026-11-18). 키트(Service_08장)와 예제 웹앱(스터디룸 예약)을 만들고, 명령과 출력을 집필용 PC(Windows 11, Git Bash, Python 3.13.7, FastAPI 0.163.2, Pydantic 2.14.3, Uvicorn 0.54.0, httpx 0.28.1, pytest 9.2.0, curl 8.21.0)에서 실행해 얻은 것으로 바꾸었다. 견본 HAR은 브라우저의 내보내기가 아니라 예제 웹앱에 실제로 보낸 요청과 응답을 키트의 스크립트로 기록한 것이다(1-5). REA, MoAI-ADK, Chrome의 HAR 내보내기 화면, 고용24의 실제 응답, Claude Code 프롬프트의 응답은 확인하지 못하였으며 「실행 결과 자리」로 남겼다.

7장에서 사람을 조사해 문제를 정의하였다. 이 장은 이미 있는 웹앱에서 명세의 재료를 모은다. 키트의 예제 웹앱(스터디룸 예약)을 내 PC에서 실행해 브라우저와 서버가 주고받는 호출을 기록하고, 그 기록에서 끝점(endpoint)의 목록을 뽑는다. 4장은 화면을, 6장은 코드를 읽었고 이 장은 호출을 읽는다. 이어서 그 목록을 API 명세로 고쳐 쓰고, 명세만으로 서버를 구현한다. 5장의 정적 웹에는 서버가 없었다. 예약 서비스에는 서버가 있어야 한다. 겹치는 예약을 막는 판정은 여러 사용자의 예약을 모두 아는 쪽만 할 수 있기 때문이다.

구현한 서버가 명세대로인지는 두 가지로 확인한다. 하나는 테스트이다. 다른 하나는 대조이다. 앞에서 기록한 요청을 내 서버에 같은 순서로 보내 응답의 상태 코드를 견준다. 6장에서 명령줄 프로그램의 출력을 대조한 방법을 서버에 적용한 것이다.

학습 목표

  • 브라우저의 개발자 도구로 네트워크 호출을 HAR 파일로 기록하고, 민감한 정보가 들어가지 않게 다룰 수 있다.
  • HAR 기록에서 끝점 목록을 뽑고, 확인한 것과 추측한 것을 구분할 수 있다.
  • 끝점 목록에서 API 명세(요청, 응답, 오류)를 쓰고, 기록에 없던 경우를 열린 질문으로 남기거나 정할 수 있다.
  • 판정을 서버 쪽에 두어야 하는 까닭을 설명하고, 입력의 검증과 업무 규칙의 판정을 구분해 구현할 수 있다.
  • HTTP 메서드의 성질과 상태 코드의 뜻에 따라 끝점과 응답을 설계할 수 있다.
  • API 명세의 경우마다 테스트를 쓰고, 경계의 경우를 포함할 수 있다.
  • 기록한 요청을 내 서버에 다시 보내 응답을 대조하고, 대조가 본 것과 보지 못한 것을 구분할 수 있다.

1. 네트워크 호출의 기록과 분석

1-1. 무엇을 분석해도 되는가

네트워크 호출의 분석은 화면의 관찰보다 깊이 들어간다. 로그인한 상태의 호출에는 쿠키와 토큰이 들어 있고, 응답에는 다른 사용자의 정보가 들어 있을 수 있다. 서비스의 이용 약관이 자동화된 접근이나 분석을 금지하는 경우도 있다. 이 과목은 대상을 다음으로 한정한다.

  1. 키트가 제공하는 예제 웹앱(내 PC에서 실행한다).
  2. 자기가 만든 서비스.

REA의 저장소도 쓰임을 합법적인 연구와 교육, 상호 운용성, 자기 소유이거나 살펴볼 권한이 있는 소프트웨어의 분석으로 적고 있다[H1]. 이 절은 법률 자문이 아니다.

1-2. 요청과 응답

웹앱의 화면은 브라우저가 서버에 요청을 보내고 응답을 받아 그린다. HTTP의 규격(RFC 9110)은 요청이 대상(주소)과 메서드로 무엇을 할지를 밝히고, 응답이 상태 코드로 그 결과를 알린다고 정한다[R1]. 요청 하나는 다음으로 이루어진다.

요소 뜻 예
메서드 무엇을 하려는가 GET(읽기), POST(만들기), DELETE(지우기)
경로 무엇에 대해 /api/reservations
질의 문자열 읽을 조건 ?date=2027-05-17
머리글(header) 요청에 관한 정보 Content-Type: application/json
본문 보낼 자료(JSON) {"room_id": 1, "start": "10:00"}

응답은 상태 코드, 머리글, 본문이다. 상태 코드는 세 자리 수이고 첫 자리가 결과의 갈래를 말한다. RFC 9110은 다섯 갈래를 둔다. 1xx는 정보, 2xx는 성공, 3xx는 다른 곳으로 가라는 안내, 4xx는 요청한 쪽의 잘못, 5xx는 서버의 잘못이다[R1]. 메서드와 경로의 한 쌍을 끝점이라 부른다. 웹앱의 서버가 하는 일은 끝점의 목록으로 정리된다.

화면에는 「예약할 수 없다」는 한 줄만 보여도, 호출에는 서버가 무엇을 거절하였는지가 상태 코드와 본문으로 남는다. 겹치는 예약의 거절처럼 서버가 판정하는 규칙은 화면의 관찰로는 추측이지만 호출의 기록으로는 확인이다.

1-3. 메서드의 성질: 안전과 멱등

메서드는 이름만 다른 것이 아니라 약속된 성질이 다르다. RFC 9110은 두 성질을 정의한다[R1].

  • 안전(safe). 그 메서드의 뜻이 사실상 읽기뿐이다. 요청을 보내도 서버의 상태를 바꾸려 하지 않는다. GET, HEAD, OPTIONS, TRACE가 안전하다.
  • 멱등(idempotent). 같은 요청을 여러 번 보낸 결과가 서버에 미치는 효과가 한 번 보낸 것과 같다. 안전한 메서드와 PUT, DELETE가 멱등이다. POST는 멱등이 아니다.

이 성질은 설계와 분석에 바로 쓰인다. 첫째, 목록을 읽는 끝점을 GET으로 두었다면 그 요청은 예약을 바꾸지 않아야 한다. 브라우저와 중간의 장치는 안전한 요청을 미리 보내거나 다시 보내도 된다고 여기기 때문이다. 둘째, 같은 예약을 지우는 DELETE를 두 번 보내면 둘째 응답은 404일 수 있다. 응답은 달라도 서버의 상태(그 예약이 없음)는 한 번 보낸 것과 같으므로 멱등이라는 약속은 지켜진다. 셋째, POST는 두 번 보내면 예약이 두 건 생길 수 있다. 예약 단추를 빠르게 두 번 누르는 사용자를 생각하면, 겹침의 판정이 서버에 있어야 하는 까닭이 하나 더 생긴다.

메서드 안전 멱등 이 장의 쓰임
GET 예 예 방과 예약의 목록 읽기
POST 아니오 아니오 예약 만들기
PUT 아니오 예 (쓰지 않음) 예약을 통째로 바꾸기
PATCH 아니오 아니오 (쓰지 않음) 예약의 일부 바꾸기
DELETE 아니오 예 예약 지우기

PATCH는 RFC 9110이 아니라 RFC 5789가 정의하며 멱등을 약속하지 않는다[R2].

1-4. 따라 하기: 예제 웹앱 실행

키트의 예제 웹앱을 띄운다. 터미널 하나를 이 서버에 쓰고, 끌 때는 그 터미널에서 Ctrl+C를 누른다.

[터미널] (예제 웹앱용)

스터디룸 예약 예제 웹앱: http://localhost:8200/  (끝내려면 Ctrl+C)

브라우저에서 http://localhost:8200/을 열면 날짜, 방, 시작과 끝 시각, 이름 칸과 그날의 예약 목록이 보인다. 화면은 서버의 /api/ 끝점만 부른다. 다른 터미널에서 끝점 둘을 직접 불러 본다.

터미널 
curl -s http://localhost:8200/api/rooms; echo
curl -s "http://localhost:8200/api/reservations?date=2027-05-17"; echo
[{"id":1,"name":"스터디룸 A","capacity":4},{"id":2,"name":"스터디룸 B","capacity":8}]

1-5. HAR 파일

HAR(HTTP Archive)는 브라우저가 주고받은 요청과 응답을 JSON 한 파일로 저장하는 형식이다. Chrome의 개발자 도구에서 만든다.

  1. 예제 웹앱을 연 탭에서 F12로 개발자 도구를 열고 Network 탭을 고른다.
  2. Preserve log를 켠다. 화면이 바뀌어도 기록이 지워지지 않는다.
  3. 기록할 조작을 한다(7-2).
  4. Network 탭의 내보내기 단추(아래 화살표)에서 Export HAR (sanitized)를 골라 저장한다.

Chrome은 130판부터 HAR를 내보낼 때 Cookie, Set-Cookie, Authorization 헤더를 기본으로 뺀다[H2][H3]. 민감한 정보를 넣어 내보내는 선택지는 개발자 도구의 설정에서 「Allow to generate HAR with sensitive data」를 켜야 나타난다[H2]. 이 과목에서는 그 설정을 켜지 않는다.

[실행 결과 자리: Chrome의 HAR 내보내기 화면] Chrome 개발자 도구의 Network 탭에서 Preserve log를 켜고 내보내기 단추를 눌러 「Export HAR (sanitized)」가 보이는 화면과, 그렇게 내보낸 session.har의 har_list.py 출력. 실행할 곳: 내 PC의 Chrome에서 예제 웹앱(8200)을 연 상태. 집필 환경에서는 브라우저의 개발자 도구를 조작할 수 없어 확인하지 못하였다. 메뉴와 설정의 이름은 [H2]와 [H3]으로만 확인하였다.

HAR의 구조. HAR 1.2는 표준 기구가 확정한 규격이 아니다. W3C의 웹 성능 작업반이 2012년에 초안을 만들었다가 발행하지 않고 그만두었으며, 지금 그 문서에는 쓰지 말라는 표시가 붙어 있다[H4]. 그래도 브라우저와 분석 도구는 이 1.2판의 구조를 사실상의 공통 형식으로 쓴다. 초안이 정한 뼈대는 다음과 같다[H4][H5].

위치 필수 항목 뜻
log version, creator, entries 판(1.2), 만든 프로그램, 요청과 응답의 목록
entries[i] startedDateTime, time, request, response, cache, timings 요청 하나. 시간 순서로 늘어선다
request method, url, httpVersion, cookies, headers, queryString, headersSize, bodySize 본문이 있으면 postData(mimeType, text)
response status, statusText, httpVersion, cookies, headers, content, redirectURL, headersSize, bodySize content.text가 응답 본문이다
timings send, wait, receive 밀리초. 해당하지 않는 단계는 -1이다

크기를 모르면 headersSize와 bodySize에 -1을 적는다. 규격에 없는 항목을 더할 때는 이름을 밑줄(_)로 시작한다. Chrome이 더하는 _initiator 같은 항목이 그것이다[H5]. 초안은 HAR 파일에 민감한 정보가 들어 있을 수 있으니 다른 사람에게 보내기 전에 사용자에게 알리라고 적는다[H4].

1-6. HAR에서 요청 목록 뽑기

HAR는 JSON이므로 프로그램으로 읽을 수 있다. 요청은 log.entries 배열에 시간 순서로 들어 있다. 키트의 har_list.py는 /api/로 시작하는 요청만 골라 순서대로 보이고, 끝에 (메서드, 경로, 상태 코드)로 묶어 센다.

파일: ~/kits/Service_08장/har_list.py 
"""HAR 파일의 /api/ 요청을 (메서드, 경로, 상태 코드)로 묶어 센다. 표준 라이브러리만 쓴다."""
import collections
import json
import sys
from urllib.parse import urlsplit

sys.stdout.reconfigure(encoding="utf-8")  # Windows의 Git Bash에서도 한글이 깨지지 않게
with open(sys.argv[1], encoding="utf-8") as f:
    har = json.load(f)
count = collections.Counter()
for i, e in enumerate(har["log"]["entries"]):
    u = urlsplit(e["request"]["url"])
    if not u.path.startswith("/api/"):
        continue
    count[(e["request"]["method"], u.path, e["response"]["status"])] += 1
    print(f'{i:>3} {e["request"]["method"]:<6} {u.path}{"?" + u.query if u.query else ""} -> {e["response"]["status"]}')
print("--- 묶음")
for (m, p, s), n in sorted(count.items(), key=lambda x: (x[0][1], x[0][0], x[0][2])):
    print(f"{m:<6} {p:<28} {s}  {n}회")

2. API 명세

2-1. 끝점 목록에서 명세로

끝점 목록은 관찰한 것의 기록이다. 명세는 구현이 지켜야 할 약속이다. 둘의 차이는 기록에 없던 경우에 있다. 목록의 「모른다」를 명세는 정하거나 열린 질문으로 남겨야 한다. 정하지 않으면 구현하는 쪽이 정한다.

API 명세는 끝점마다 다음을 적는다.

항목 적는 것
요청 메서드, 경로, 질의 문자열, 본문의 항목과 형식(필수인가, 범위)
성공 응답 상태 코드와 본문의 항목, 시각 같은 값의 꼴
오류 응답 경우마다 상태 코드와 본문의 모양
규칙 서버가 판정하는 업무 규칙(EARS 문장)
근거 끝점 목록(1-8)의 행, 또는 「정함」과 그 까닭

2-2. 끝점의 설계: 자원과 메서드

예제 웹앱의 끝점은 일정한 꼴을 따른다. 경로는 자원(방, 예약)을 가리키는 명사이고, 그 자원에 무엇을 할지는 메서드가 말한다. 이 꼴은 Fielding이 2000년에 정리한 REST 구조 양식에서 온다. REST에서 자원은 이름으로 가리킬 수 있는 정보의 단위이고, 모든 구성 요소가 같은 꼴의 인터페이스로 자원을 다루며, 요청 하나가 그 요청을 이해하는 데 필요한 정보를 모두 담는다(무상태)[F1].

하려는 일 이 장의 끝점 피하는 꼴 피하는 까닭
그날의 예약 읽기 GET /api/reservations?date=… GET /api/getReservations 동사가 경로와 메서드에 두 번 들어간다
예약 만들기 POST /api/reservations GET /api/reserve?room=1&start=10:00 상태를 바꾸는 일을 안전한 메서드에 실었다(1-3)
예약 하나 지우기 DELETE /api/reservations/1 POST /api/deleteReservation 멱등이라는 성질을 잃는다. 다시 보내도 되는지 알 수 없다

자원의 모음(/api/reservations)과 그 가운데 하나(/api/reservations/1)를 경로로 나누면, 같은 경로에 메서드만 바꾸어 읽기, 만들기, 지우기를 붙일 수 있다. 예약의 시간을 바꾸는 기능을 더한다면 PATCH /api/reservations/1이 이 꼴에 맞는다. 7장의 문제 정의 P-01(취소와 바꾸기)이 그 기능의 근거가 된다. 이 장의 범위에서는 만들지 않고 명세의 열린 질문으로 남긴다.

무상태의 뜻도 이 장에 걸린다. 서버는 「직전에 이 사용자가 고른 날짜」를 기억하지 않는다. 그래서 목록을 읽는 요청마다 date를 실어 보낸다. 5-2의 재생이 기록의 요청을 하나씩 다시 보내기만 해도 같은 응답을 기대할 수 있는 것은 요청이 필요한 정보를 모두 담기 때문이다. 다만 서버에 저장된 예약은 상태이므로, 재생 전에 서버를 비워야 한다.

2-4. 상태 코드의 선택

브라우저 쪽의 코드는 상태 코드를 보고 무엇을 할지 정한다. 실패의 원인에 따라 코드를 나눈다. 뜻은 RFC 9110의 정의를 따른다[R1].

코드 RFC 9110의 뜻 예약 API에서 생기는 때 화면이 할 일
200 OK 요청이 성공하였다 목록을 돌려준다 그린다
201 Created 새 자원을 만들었다. 만든 자원은 Location 머리글로 가리킬 수 있다 예약을 만들었다 목록을 다시 읽는다
204 No Content 성공하였고 보낼 본문이 없다 예약을 지웠다 목록을 다시 읽는다
400 Bad Request 요청의 문법이나 틀이 잘못되어 처리하지 않는다 본문이 JSON으로 읽히지 않는다 다시 보내도 같다
404 Not Found 대상이 없다(또는 있음을 밝히지 않는다) 없는 방, 없는 예약 목록을 다시 읽고 알린다
409 Conflict 대상의 지금 상태와 충돌한다. 충돌을 풀면 다시 보낼 수 있다 겹치는 예약 다른 시간을 고르게 한다
422 Unprocessable Content 형식은 읽었으나 담긴 내용을 처리할 수 없다 날짜의 꼴, 빈 이름, 앞뒤가 바뀐 시각 틀린 칸을 알린다. 다시 눌러도 같다
502 Bad Gateway 위쪽 서버에서 잘못된 응답을 받았다 공개 API의 실패(3-4) 잠시 뒤 다시 하게 한다
503 Service Unavailable 지금 처리할 수 없다 인증키가 설정되지 않았다(3-4) 운영자에게 알린다

409와 422를 나누는 까닭이 있다. 422는 요청 자체가 틀린 것이어서 언제 보내도 실패한다. 409는 요청은 옳으나 지금의 자료와 충돌하는 것이어서, 앞의 예약이 취소되면 같은 요청이 성공한다. 화면의 안내가 달라야 한다. 400과 422의 경계는 「읽을 수 있는가」이다. 본문이 JSON이 아니면 400, JSON이지만 항목이 틀렸으면 422이다. 4-2와 4-3에서 FastAPI가 실제로 이렇게 나누는 것을 본다.

201의 정의는 만든 자원을 Location 머리글로 가리킬 수 있다고 적는다[R1]. 예제 웹앱과 견본 서버는 Location을 보내지 않고 본문에 id를 담는다. 이것도 명세가 정할 수 있는 선택이다. 204에는 본문이 없으므로, RFC 9110은 204 응답에 Content-Length 머리글을 보내지 말라고 정한다[R1]. 예제 웹앱은 이 규칙을 따른다.

2-5. OpenAPI

API 명세를 사람만 읽는 표로 두지 않고 기계가 읽는 문서로 쓰는 표준이 있다. OpenAPI 명세(OAS)는 HTTP API를 프로그래밍 언어와 무관한 꼴로 기술하는 표준이며, 사람과 기계가 소스 코드를 읽지 않고도 서비스가 무엇을 하는지 알게 하는 것을 목적으로 한다[O2]. 2026-11-18에 확인한 최신판은 3.2.1(2026-09-10)이다[O2].

OpenAPI의 부분 담는 것 2-3의 표에서
paths 경로마다 메서드(operation)와 그 요청, 응답 끝점 하나하나
responses 상태 코드마다 응답의 설명과 본문의 모양 「응답」 표의 행
components/schemas 여러 곳에서 다시 쓰는 자료의 모양. JSON Schema(2020-12)를 따른다 「요청 본문」 표

FastAPI는 코드에서 OpenAPI 문서를 만들어 /openapi.json으로 내준다. 4-4에서 견본 서버의 문서를 열어 보면 POST /api/reservations의 응답에 201과 422만 있고 404와 409가 없다. FastAPI는 함수의 선언(status_code=201, Pydantic 모델)에서 문서를 만들고, 함수 안에서 HTTPException으로 낸 응답은 알지 못하기 때문이다. 문서에 넣으려면 경로 데코레이터에 responses={409: {...}}처럼 따로 적어야 한다[X4]. 구현에서 나온 문서는 구현이 선언한 것만 담는다. 명세가 정한 응답이 문서에 빠져 있다면, 문서와 구현 가운데 어느 쪽을 고칠지 사람이 정한다.

3. 서버 쪽 판정

3-1. 브라우저의 검사는 편의이다

예제 웹앱의 화면은 끝 시각을 시작 시각보다 앞으로 고르면 요청을 보내지 않고 「끝 시각은 시작 시각보다 뒤여야 한다」고 알린다. 그것은 사용자의 편의를 위한 것이며 보호가 아니다. 서버의 주소를 아는 사람은 화면을 거치지 않고 요청을 직접 보낼 수 있다. 1-2에서 본 대로 요청은 메서드, 경로, 머리글, 본문일 뿐이고, curl 한 줄로 만들 수 있다. 그러므로 지켜야 하는 규칙은 서버가 판정한다.

판정 브라우저 서버
빈 칸, 형식 한다(빨리 알리기 위해) 한다
끝 시각이 시작 시각보다 뒤인가 한다 한다
다른 예약과 겹치는가 할 수 없다(다른 사용자의 예약을 모른다) 한다
내 예약만 지울 수 있는가 할 수 없다 한다(이 장의 범위 밖. 7-1)

마지막 행은 API 보안에서 가장 흔한 약점과 이어진다. OWASP의 API Security Top 10(2023년판)은 첫 항목(API1:2023)으로 「객체 수준 권한 부여의 결함」을 든다. 객체의 식별자를 받는 끝점이 요청한 사람이 그 객체에 접근해도 되는지를 확인하지 않는 문제이다[O3]. DELETE /api/reservations/1에서 1을 2로 바꾸면 남의 예약이 지워지는 서버가 그 예이다. 이 장의 서버는 로그인이 없어 이 판정을 하지 않는다. 졸업 프로젝트에서 로그인을 붙이면 끝점마다 이 판정을 서버에 넣는다.

3-2. 입력의 검증과 업무 규칙의 판정

서버의 판정은 두 층으로 나뉜다.

  • 입력의 검증. 요청 하나만 보고 판정할 수 있다. 형식, 필수, 범위. 틀리면 422이다.
  • 업무 규칙의 판정. 저장된 자료와 견주어야 판정할 수 있다. 겹침, 있는 방인가. 틀리면 409 또는 404이다.

검증은 허용할 것을 적는 쪽으로 한다. 「날짜에 한글이 있으면 거절」처럼 막을 것을 늘어놓으면 빠뜨린 경우가 통과한다. 「YYYY-MM-DD로 읽히는 날짜만 받는다」처럼 받을 꼴을 적으면 나머지는 모두 거절된다. 검증은 받은 값을 서버가 쓰는 꼴로 바꾸는 일도 한다. 견본 서버는 "10:00"을 시각 객체로 바꾼 뒤 견주므로, 글자열의 비교에서 생기는 실수("9:00"이 "10:00"보다 큰 것으로 비교됨)를 피한다.

FastAPI는 요청 본문의 모양을 Pydantic 모델로 적으면 입력의 검증을 대신 해 준다. 검증에 실패하면 422와 함께 틀린 항목마다 위치(loc)와 까닭(msg)을 담은 목록을 돌려준다[X3]. 업무 규칙은 함수 안에 직접 쓰고, HTTPException으로 상태 코드와 detail을 정한다[X3].

3-3. 겹침의 판정

두 구간 [s1, e1)과 [s2, e2)가 겹치는 조건은 s1 < e2이고 s2 < e1인 것이다. 끝과 시작이 같은 경우(e1 == s2)는 둘째 조건이 거짓이므로 겹치지 않는다. 2-3의 REQ-04가 정한 대로이다. 조건을 <=로 쓰면 맞닿은 예약이 거절된다. 글자 하나가 명세의 경계를 정한다.

3-4. 공개 API는 서버가 부른다

5장의 서비스 1은 고용24의 자료를 미리 받아 파일로 두었다. 화면에서 API를 바로 부르면 인증키가 드러나기 때문이었다. 서버가 있으면 다른 길이 생긴다. 화면은 내 서버에 묻고, 내 서버가 인증키를 가지고 공개 API를 부른다.

"""고용24 채용정보를 서버에서 불러 화면에 넘기는 끝점.

인증키는 환경 변수 WORK24_KEY에서 읽는다. 브라우저에는 가지 않는다.
"""
import os
import time
import xml.etree.ElementTree as ET

import httpx
from fastapi import FastAPI, HTTPException

URL = "https://www.work24.go.kr/cm/openApi/call/wk/callOpenApiSvcInfo210L01.do"
KEEP = ["wantedAuthNo", "company", "title", "region", "career", "closeDt", "wantedInfoUrl"]
TTL = 600  # 초. 같은 자료를 10분 동안 다시 부르지 않는다

app = FastAPI()
client = httpx.Client(timeout=5.0)
_cache = {"at": 0.0, "jobs": None}


def parse(xml_text):
    root = ET.fromstring(xml_text)
    return [{k: (el.findtext(k) or "").strip() for k in KEEP}
            for el in root.iter() if el.find("wantedAuthNo") is not None]


@app.get("/api/jobs")
def jobs():
    key = os.environ.get("WORK24_KEY")
    if not key:
        raise HTTPException(503, "서버에 인증키가 설정되지 않았다")
    now = time.time()
    if _cache["jobs"] is not None and now - _cache["at"] < TTL:
        return {"cached": True, "count": len(_cache["jobs"]), "jobs": _cache["jobs"]}
    try:
        r = client.get(URL, params={"authKey": key, "callTp": "L", "returnType": "XML",
                                    "startPage": 1, "display": 10})
        r.raise_for_status()
        found = parse(r.text)
    except (httpx.HTTPError, ET.ParseError):
        raise HTTPException(502, "공고 자료를 받지 못했다")
    _cache.update(at=now, jobs=found)
    return {"cached": False, "count": len(found), "jobs": found}

3-5. 인증키의 자리와 새는 경로

인증키와 API 키는 서비스에서 가장 조심해야 하는 자격 증명이다. OWASP는 「민감 정보 노출」에 보안 자격 증명을 포함하고, 꼭 필요한 곳에서만 접근하게 하라고 권한다[O1]. 이 소절의 내용은 고용24의 인증키와 9장의 Claude API 키에 똑같이 적용된다.

키가 있어야 하는 자리는 하나이다. 저장소에 들어가지 않는 파일(.env 또는 저장소 밖의 ~/work24.env)에 두고 서버 프로그램만 읽는다. .env.example에는 변수의 이름만 적고 값은 비운다. 이 파일은 커밋되어 어떤 변수가 필요한지를 다른 사람에게 알린다.

나머지 자리에는 키가 없어야 한다. 파이썬 코드에는 쓸 까닭이 없다. 환경 변수에서 읽기 때문이다. 브라우저로 가는 자바스크립트는 누구나 열어 본다. 문서와 커밋 메시지는 저장소에 남는다. 키가 저장소에 한 번 커밋되면 다음 커밋에서 지워도 이력에 남는다. 푸시까지 했다면 그 키는 샌 것으로 보고 바로 폐기하고 새로 발급받는다.

새는 경로 막는 장치 확인 방법
키가 든 파일을 커밋한다 .gitignore에 그 파일을 적는다 git check-ignore -v .env
코드에 키를 붙여 넣는다 환경 변수에서 읽는다 grep -rc "$WORK24_KEY" .(5장 8-2)
브라우저의 코드가 공개 API를 직접 부른다 브라우저는 내 서버만 부른다(3-4) 개발자 도구의 Network 탭에 공개 API의 주소가 없다
공개 API의 오류가 그대로 화면에 나간다 오류를 내 문구로 바꾼다 3-4의 다섯째 테스트

Claude Code가 키 파일을 읽어 대화에 남긴다 설정에서 그 파일의 읽기를 막는다 부록 A-14-4

"""스터디룸 예약 API. 자료는 메모리에 둔다(서버를 끄면 사라진다)."""
from datetime import date, time

from fastapi import FastAPI, HTTPException
from pydantic import BaseModel, Field

app = FastAPI(title="예약 API")

ROOMS = [
    {"id": 1, "name": "스터디룸 A", "capacity": 4},
    {"id": 2, "name": "스터디룸 B", "capacity": 8},
]
RESERVATIONS: list[dict] = []
NEXT_ID = {"value": 1}

class ReservationIn(BaseModel):
    room_id: int
    date: date
    start: time
    end: time
    name: str = Field(min_length=1, max_length=20)

@app.get("/api/rooms")
def list_rooms():
    return ROOMS

@app.get("/api/reservations")
def list_reservations(date: date):
    return [r for r in RESERVATIONS if r["date"] == date]

@app.post("/api/reservations", status_code=201)
def create_reservation(body: ReservationIn):
    if not any(room["id"] == body.room_id for room in ROOMS):
        raise HTTPException(status_code=404, detail="없는 방이다")
    if body.end <= body.start:
        raise HTTPException(status_code=422, detail="끝 시각은 시작 시각보다 뒤여야 한다")
    for r in RESERVATIONS:
        same = r["room_id"] == body.room_id and r["date"] == body.date
        if same and body.start < r["end"] and r["start"] < body.end:
            raise HTTPException(status_code=409, detail="겹치는 예약이 있다")
    new = {"id": NEXT_ID["value"], **body.model_dump()}
    NEXT_ID["value"] += 1
    RESERVATIONS.append(new)
    return new

@app.delete("/api/reservations/{reservation_id}", status_code=204)
def delete_reservation(reservation_id: int):
    for r in RESERVATIONS:
        if r["id"] == reservation_id:
            RESERVATIONS.remove(r)
            return
    raise HTTPException(status_code=404, detail="없는 예약이다")

ReservationIn이 입력의 검증이고, create_reservation 안의 세 판정이 업무 규칙이다. 겹침의 조건은 3-3의 식 그대로이다.

5-2. 기록의 재생

HAR에는 예제 웹앱이 받은 요청과 낸 응답이 순서대로 들어 있다. 같은 요청을 내 서버에 같은 순서로 보내면, 내 서버가 예제와 같은 응답을 내는지 견줄 수 있다.

"""HAR에 기록된 /api/ 요청을 내 서버에 같은 순서로 보내고 상태 코드를 견준다."""
import json
import sys
import urllib.error
import urllib.request
from urllib.parse import urlsplit

sys.stdout.reconfigure(encoding="utf-8")  # Windows의 Git Bash에서도 한글이 깨지지 않게
har, base = sys.argv[1], sys.argv[2].rstrip("/")
with open(har, encoding="utf-8") as f:
    entries = json.load(f)["log"]["entries"]
same = diff = 0
for i, e in enumerate(entries):
    req = e["request"]
    u = urlsplit(req["url"])
    if not u.path.startswith("/api/"):
        continue
    data = req.get("postData", {}).get("text")
    r = urllib.request.Request(
        base + u.path + ("?" + u.query if u.query else ""),
        data=data.encode("utf-8") if data else None,
        method=req["method"],
        headers={"Content-Type": "application/json"} if data else {},
    )
    try:
        got = urllib.request.urlopen(r).status
    except urllib.error.HTTPError as err:
        got = err.code
    want = e["response"]["status"]
    mark = "같다" if got == want else "다르다"
    same, diff = same + (got == want), diff + (got != want)
    print(f'{i:>3} {mark} | 기록 {want}, 내 서버 {got} | {req["method"]} {u.path}')
print(f"같다 {same}건, 다르다 {diff}건")

Windows에서 localhost는 IPv6 주소(::1)를 먼저 시도하는데, uvicorn은 127.0.0.1(IPv4)에서만 받으므로 요청마다 실패한 시도를 기다린 뒤 IPv4로 다시 잇기 때문이다. 서버를 다시 띄우지 않고 한 번 더 실행하자 「다르다 2건」이 나왔다. 5번의 예약이 앞 실행의 예약과 겹쳐 409가 되었고, 9번이 지우려는 1번 예약이 이미 없어 404가 되었다.

이 대조에는 세 가지 한계가 있다.

  1. 상태 코드만 본다. 본문의 항목과 형식은 견주지 않았다. 4-2에서 본 10:00:00은 이 대조로 드러나지 않는다.
  2. 기록에 있는 요청만 본다. 기록에 없는 조작은 견줄 수 없다. 맞닿은 예약과 앞뒤가 바뀐 시각은 기록에 없었다.
  3. 순서와 상태에 기댄다. 서버에 앞선 자료가 남아 있으면 id가 달라져 삭제의 요청이 다른 예약을 가리킨다. 그래서 서버를 다시 띄운 뒤에 실행한다.
  • 확인 6 견본 서버를 다시 띄운 뒤 replay.py의 마지막 줄이 「같다 10건, 다르다 0건」이다.

6. 명세 주도 도구의 시연: MoAI-ADK (교수 시연)

4~5장과 이 장에서 명세 → 계획 → 구현 → 검사의 순서를 Claude Code와 마크다운 파일로 밟았다. 같은 순서를 단계로 고정해 주는 도구가 있다. MoAI-ADK는 Claude Code를 감싸는 에이전트 하네스이다. 저장소의 안내에 따르면 작업을 /moai plan(명세) → /moai run(구현) → /moai sync(문서와 정리)의 세 단계로 진행하고, 완료의 주장을 실제로 실행한 명령과 출력에 묶는다[X2].

이 절은 교수 화면의 시연으로 10분 동안 보고, 학습자는 설치하지 않는다. 시연에서 볼 것은 둘이다.

볼 것 이 과목에서 손으로 한 일 도구가 하는 일
단계의 고정 계획 모드에서 받고, 나와서 저장하고, 새 세션에서 구현한다 명령 하나가 단계 하나를 맡고 산출물의 자리가 정해져 있다
완료의 근거 인수 조건 표, 테스트, 대조를 사람이 돌린다 「끝났다」는 주장에 실행한 명령과 출력을 붙이게 한다

도구가 단계를 고정해 주어도 명세의 빈틈은 사람이 찾는다. 이 장의 REQ-04(맞닿은 예약)는 도구가 대신 정해 주지 않는다.

[실행 결과 자리: MoAI-ADK 시연] 교수 PC에서 2-3의 명세 일부를 입력으로 /moai plan → /moai run → /moai sync를 차례로 실행한 화면과, /moai run이 완료를 주장하며 붙인 명령과 출력. 실행할 곳: 교수 PC(Windows는 WSL을 권장한다는 안내에 따라 WSL), 교수 계정. 설치와 실행은 아직 해 보지 않았다.

[최신 자료 자리: MoAI-ADK의 명령과 지원 환경] 수업 전에 저장소의 안내를 다시 읽는다. 확인할 곳: https://github.com/modu-ai/moai-adk. 2026-11-18에 읽은 값: 세 단계의 명령 이름은 위와 같고, Windows는 WSL을 권장하며 cmd.exe는 지원하지 않는다고 안내한다. 사용권은 Apache-2.0이다. 실습실 PC에서 되지 않으면 시연을 저장소의 안내를 읽는 것으로 바꾼다.

7-4. API 명세

Claude Code를 ch08에서 계획 모드로 열고 초안을 받는다.

[Claude Code] (계획 모드)

정리

  • 화면에 보이지 않는 서버의 규칙은 네트워크 호출의 응답에 드러난다. 끝점은 메서드와 경로의 한 쌍이다.
  • 메서드에는 약속된 성질이 있다. 안전한 메서드는 상태를 바꾸지 않고, 멱등인 메서드는 여러 번 보내도 효과가 같다.
  • HAR는 걸러서 내보내도 주소와 본문이 그대로 들어 있다. 지어낸 값만 입력하고 저장소에 올리지 않는다.
  • 끝점 목록은 관찰의 기록이고 API 명세는 약속이다. 기록에 없던 경우를 명세가 정하지 않으면 구현하는 쪽이 정한다.
  • 지켜야 하는 규칙은 서버가 판정한다. 브라우저의 검사는 편의이다.
  • 입력의 검증은 요청 하나만 보고, 업무 규칙의 판정은 저장된 자료와 견주어 한다. 상태 코드가 그 차이를 알린다.
  • 구현에서 나온 OpenAPI 문서는 구현이 선언한 것만 담는다. 명세와 견주어 빠진 응답을 찾는다.
  • 경계의 경우는 글자 하나로 갈린다. 명세가 정하고 테스트가 지킨다.
  • 기록의 재생은 상태 코드, 기록에 있는 요청, 같은 순서만 본다. 대조가 보지 못한 것을 손으로 견준다.
  • 인증키가 필요한 공개 API는 서버가 부른다. 인증키는 환경 변수에 두고, 쓸 항목만 넘기고, 잠시 기억해 두고, 공개 API의 실패를 내 오류로 바꾼다.
