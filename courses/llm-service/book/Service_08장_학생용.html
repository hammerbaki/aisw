UI 설계와 프로토타이핑

2027학년도 「LLM 서비스 개발」의 준비 중인 교재입니다. 편집 상태를 검토하기 위해 미리 공개한 것으로, 수업 전에 내용과 순서가 바뀔 수 있습니다.

학사 10주차 · 교재 08 · 3부 설계

앞 장은 페르소나의 여정에서 사이트맵과 사용자 흐름을 끌어내고, 명세서 v2에 화면 목록을 더하였다. 그 결과로 「어떤 화면이 몇 개 있고, 사용자가 어떤 순서로 지나가는가」는 정해졌다. 그러나 화면 하나하나에 무엇이 어떤 순서와 크기로 놓이는지, 공고가 하나도 없을 때나 요약 생성이 실패했을 때 화면이 어떻게 보이는지는 아직 정해지지 않았다. 이 빈칸을 그대로 둔 채 구현을 맡기면 Claude Code가 그 빈칸을 자기 판단으로 채운다. 6장에서 명세 없이 재생성한 화면의 배치와 색이 실행할 때마다 달라졌던 것과 같은 일이다.

이 장은 그 빈칸을 화면 명세로 닫는다. 화면 명세는 화면마다 목적, 관련 요구, 구성 요소, 상태, 상호작용, 접근성 메모를 문장과 표로 적고, 배치는 그림으로 정한 문서이다. 색과 글꼴과 간격은 디자인 토큰이라는 이름 붙은 값으로 한곳에 모은다. 그다음 화면 명세와 토큰을 입력으로 삼아 Claude Code에게 클릭 가능한 HTML 프로토타입을 만들게 하고, 그 결과를 다시 화면 명세에 대어 대조한다. 명세가 구현의 입력이자 검사의 기준이라는 명세 주도 개발의 원리를 화면 단위에서 한 번 더 적용하는 셈이다.

이 장에서 만드는 것은 공통 사례 「취업 준비 지원 서비스(jobprep)」의 핵심 화면 4개(공고 목록, 공고 상세, 지원 일정, 지원 일정 등록)의 화면 명세와 HTML 프로토타입이다. 이것을 만드는 10절이 핵심 실습이고, 해결할 문제는 대비 점검과 키보드 점검에서 실패한 항목을 찾아 고치는 것이다. 키트의 토큰 견본에는 대비 미달 쌍이 일부러 하나 들어 있고, Claude Code가 만든 화면에는 키보드로 쓸 때 드러나는 결함이 섞이기 쉽다. 1~9절의 이론과 두 따라 하기(6-4, 9-3)가 그 실습의 기준과 도구를 준비한다. 9장은 이 결과로 동작하는 웹을 구현하고, 프로젝트실습Ⅰ도 이 양식과 도구를 쓴다.

화면을 설계하는 일은 그림을 잘 그리는 일과 다르다. 이 장에서 다루는 시각적 위계, 그리드, 토큰, 상태, 접근성은 모두 「누가 다시 만들어도 같은 화면이 나오게 하는 규칙」이다. 규칙이 문서에 있으면 사람과 AI가 같은 화면을 만들고, 규칙이 없으면 만들 때마다 다른 화면이 나온다.

학습 목표

  • 화면 명세의 구성 요소(화면 ID, 목적, 요구 ID, 구성 요소, 상태, 상호작용, 접근성 메모)를 갖춘 명세를 쓰고, 기능은 문장으로, 배치는 그림으로 정하는 까닭을 설명한다.
    • 예시: 공고 목록 화면(SCR-01)의 명세에 빈 상태의 문구와 「조건 모두 지우기」 버튼을 넣고, ASCII 와이어프레임으로 모바일 배치를 그린다.
    • 활용: 프로젝트실습Ⅰ에서 팀의 화면을 나누어 맡을 때, 화면 명세가 팀원 사이와 팀원과 AI 사이의 합의 문서가 된다.
  • 디자인 토큰을 기본 토큰과 의미 토큰의 두 층으로 정의하고, CSS 사용자 지정 속성으로 바꾸어 화면에 적용한다.
    • 예시: color-text-muted의 값을 {gray-50}에서 {gray-60}으로 한 줄 바꾸면 모든 화면의 보조 글자색이 함께 바뀐다.
    • 활용: 디자인 시스템(예: 한국 정부의 KRDS)의 토큰 문서를 읽고 자기 프로덕트에 옮긴다.
  • WCAG 2.2의 대비, 키보드, 레이블, 대체 텍스트, 상태 메시지 기준을 공식으로 계산하거나 도구와 손으로 점검하고, 자동 점검이 판정하지 못하는 범위를 구별한다.
    • 예시: 같은 회색 #6b7280이 흰 바탕에서는 4.83:1로 통과하고 옅은 회색 카드 위에서는 4.47:1로 미달하는 것을 계산으로 확인한다.
    • 활용: 9장 이후의 구현물과 프로젝트실습Ⅰ의 결과물을 같은 도구로 점검한다.
  • 화면 명세에서 Claude Code로 HTML 프로토타입을 만들고, 그 결과를 명세의 항목별로 대조해 일치, 다름, 없음을 기록한다.
    • 예시: 공고 상세 화면(SCR-02)의 「생성 중 재요청 금지」를 프로토타입에서 두 번 눌러 보고 대조표에 「일치」로 적는다.
    • 활용: AI의 「완료했다」는 보고를 받는 대신, 명세 항목별 대조 기록으로 결과를 검수한다.

0. 시작하기

설치, 로그인, 키트 저장소의 클론, 가상 환경은 부록 A(A-7, A-8, A-12, A-13), 매 수업의 시작 순서는 A-21을 따른다. 작업은 VS Code의 통합 터미널 두 개(A-4-3)에서 한다. 하나는 명령을 치는 [터미널](Windows는 Git Bash, macOS는 기본 터미널), 하나는 Claude Code이다. 둘 다 가상 환경을 켠다(source ~/llm-service-lab/.venv/Scripts/activate, macOS는 .venv/bin/activate).

  • 작업 폴더. 이 장의 명령과 Claude Code는 모두 ~/llm-service-lab/jobprep에서 실행한다(cd ~/llm-service-lab/jobprep 뒤 claude). 이 폴더에서 시작하면 저장소 맨 위의 CLAUDE.md(2장)와 jobprep/CLAUDE.md(6장)가 처음부터 함께 적용된다[C2]. 프롬프트의 @docs/…, @prototype/…은 이 폴더에서 본 경로이다. 9장도 같은 폴더에서 시작한다. 7장은 ch05/, ch07/을 함께 읽느라 저장소 맨 위에서 시작했지만, 이 장의 입력과 산출물은 모두 jobprep/ 안에 있다.
  • 이 장의 실행 상한. 실제 모델은 Claude Code 대화형으로만 부른다. 따라 하기 2에서 1회, 핵심 실습에서 화면 명세 초안 5회(0절과 화면 넷), 프로토타입 4회, 키보드 점검 뒤의 고치기 화면마다 1회까지, 명세서 v3 1회이다. 스크린샷 대조(9-5)는 [선택] 1회까지. 프로토타입의 요약은 가짜 응답이므로 API 키를 쓰지 않는다.
  • 「읽기」 표시. 꼬리표에 「(읽기)」를 붙인 코드 블록은 따라 치지 않고 읽는다. 따라 치는 명령은 0절, 두 개의 따라 하기(6-4, 9-3), 핵심 실습(10절)에 있다.

0-1. 키트 받기

키트 저장소에서 새 키트를 받아(git pull) 홈의 kits/로 복사한다(부록 A-12-3). 키트는 산출물이 아니므로 저장소 밖에 두고 커밋하지 않는다.

터미널 
git -C ~/kits-repo pull
mkdir -p ~/kits && cp -rn ~/kits-repo/Service_08장 ~/kits/
KIT=~/kits/Service_08장
ls "$KIT"
README.md  prototype_시작  requirements.txt  tests  tools  기준산출물  디자인토큰_견본.md  예제  접근성점검_양식.md  화면명세_양식.md

KIT 변수는 터미널을 새로 열면 사라지므로 다시 입력하거나 ~/.bashrc 끝에 넣어 둔다.

키트의 도구가 이 PC에서 도는지 테스트로 확인한다. 세 도구는 표준 라이브러리만 쓰고, 테스트와 선택 도구 keyboard_walk.py에 필요한 requirements.txt(pytest, playwright)는 가상 환경을 켠 뒤 설치한다.

터미널 
source ~/llm-service-lab/.venv/Scripts/activate     # macOS: source ~/llm-service-lab/.venv/bin/activate
cd "$KIT"
python -m pip install -q -r requirements.txt
python -m pytest -q
.............s..........s........                                        [100%]
31 passed, 2 skipped in 1.49s

학생 배포본에는 교수 폴더가 없으므로 그 폴더를 쓰는 테스트 2개는 건너뛴다(skipped). 실패(failed)가 하나라도 있으면 키트를 다시 복사한다.

[최신 자료 자리: 키트가 고정한 패키지의 판] requirements.txt의 pytest 9.2.0, playwright 1.64.0. 확인할 곳 https://pypi.org/project/playwright/. 2026-11-16 값: 최신은 pytest 9.2.0, playwright 1.65.2.

1. 와이어프레임, 목업, 프로토타입

1-1. 세 산출물의 구별

화면을 설계하는 과정에서는 여러 종류의 중간 산출물이 만들어진다. 실무에서 가장 자주 쓰는 이름은 와이어프레임(wireframe), 목업(mockup), 프로토타입(prototype)이다. 세 이름은 회사와 도구마다 조금씩 다르게 쓰이지만, 무엇을 정하고 무엇을 비워 두는가로 구별하면 혼동이 줄어든다.

산출물 정하는 것 비워 두는 것 대표적인 형태 주로 묻는 질문
와이어프레임 화면에 무엇이 있고 어디에 놓이는가(구조와 배치) 색, 글꼴, 실제 문구, 동작 회색 상자와 선, 손그림, ASCII 그림 필요한 요소가 다 있는가. 순서가 맞는가
목업 최종 화면이 어떻게 보이는가(시각 표현) 동작. 눌러도 아무 일이 없다 디자인 도구의 정지 화면 위계가 읽히는가. 브랜드와 맞는가
프로토타입 사용자가 무엇을 하면 화면이 어떻게 바뀌는가(상호작용) 실제 데이터와 서버 클릭 가능한 디자인 파일, HTML 과업을 끝까지 할 수 있는가. 상태 전환이 이해되는가

세 산출물은 차례대로만 만드는 것이 아니다. 와이어프레임 단계에서 이미 버튼을 눌러 다음 화면으로 넘어가는 종이 프로토타입을 만들 수 있고, 목업 없이 와이어프레임에서 바로 HTML 프로토타입으로 갈 수도 있다. 이 장은 와이어프레임(ASCII 그림)에서 바로 HTML 프로토타입으로 간다. 목업 단계를 따로 두지 않는 대신, 시각 표현은 디자인 토큰과 시각적 위계의 규칙으로 정한다.

1-2. 충실도의 세 차원

프로토타입이 최종 시스템과 얼마나 닮았는가를 충실도(fidelity)라고 한다. 닐슨 노먼 그룹(NN/g)은 충실도를 하나의 눈금이 아니라 세 차원으로 나누어 본다[N1].

차원 낮은 충실도 높은 충실도
상호작용 사람이 「컴퓨터」 역할을 맡아 종이를 바꿔 끼운다 링크와 메뉴가 실제로 동작하고 자동으로 반응한다
시각 배치만 대략 같다. 크기, 간격, 위계는 다르다 배치, 위계, 간격, 화면 크기가 실제 시스템과 같다
내용 요약이나 자리 표시 글자만 있다 실제 문구와 실제에 가까운 데이터가 들어 있다

세 차원은 따로 움직인다. 이 장의 HTML 프로토타입은 상호작용이 높고(화면 간 이동, 상태 전환이 실제로 동작한다), 시각은 중간이며(토큰을 적용했으나 다듬지 않았다), 내용도 중간이다(가상의 공고 여섯 건과 고정된 「오늘」 날짜를 쓴다). 어느 차원을 높일지는 프로토타입으로 무엇을 확인하려는가에 달려 있다.

1-3. 저충실도와 고충실도의 선택

NN/g는 두 쪽의 장단점을 다음과 같이 정리한다[N1].

  • 저충실도의 장점: 준비 시간이 짧아 설계에 시간을 더 쓴다. 시험 도중에도 고쳐 그릴 수 있다. 미완성으로 보여 사용자와 이해관계자가 부정적인 의견을 편하게 낸다. 만든 사람이 결과물에 덜 집착한다.
  • 저충실도의 단점: 사람이 화면을 바꾸는 동안 흐름이 끊긴다. 「컴퓨터」 역할의 사람이 실수하면 사용자가 혼란에 빠진다.
  • 고충실도의 장점: 반응이 빠르고 실제와 같아 사용자가 실제처럼 행동한다. 작업 흐름, 특정 컴포넌트, 글자의 가독성 같은 세부를 시험할 수 있다. 진행자가 관찰에 집중한다.
  • 고충실도의 단점: 클릭할 자리와 반응을 모두 미리 만들어야 하므로 시간이 든다.

생성형 AI 코딩 도구는 고충실도의 단점인 「만드는 시간」을 크게 줄였다. 화면 명세가 있으면 클릭 가능한 HTML 프로토타입을 몇 분 안에 얻을 수 있다. 그러면 고충실도의 장점을 얻으면서 저충실도의 장점(쉽게 고치고 버린다)도 어느 정도 누릴 수 있다. 다만 새로운 위험이 생긴다. 잘 다듬어진 화면은 「거의 다 된 것」처럼 보여서 리뷰어가 구조의 문제보다 색과 문구에 의견을 낸다. 그래서 이 장은 프로토타입을 만들기 전에 화면 명세를 먼저 쓰고, 리뷰도 명세를 기준으로 받는다.

NN/g는 AI 기능이 들어간 시스템을 AI를 만들기 전에 시험하는 방법으로 「오즈의 마법사(Wizard of Oz)」 시험을 든다[N1]. 사람이 뒤에서 AI의 응답을 대신 만들어 보여 주는 방식이다. 이 장의 프로토타입에서 공고 요약은 실제 LLM을 부르지 않고, 미리 써 둔 가짜 응답을 1.2초 뒤에 보여 준다. 10장에서 실제 API를 붙이기 전에 「요약을 기다리고, 읽고, 원문과 대조하는」 경험을 먼저 설계하고 시험하기 위해서이다.

1-4. 그림이 필요한 까닭

2026년판 교재의 화면 명세 실습은 「말로는 배치가 맞춰지지 않는다」에서 출발하였다[R1]. 「카드를 나란히」라고 쓰면 그것이 2열인지 3열인지, 간격이 얼마인지는 읽는 사람마다 다르게 이해한다. 그림 한 장이면 이 해석의 차이가 한 번에 사라진다.

그래서 화면 명세는 기능과 배치의 기준을 함께 가지고, 이 장은 여기에 시각의 기준을 더한다.

  • 기능의 기준: 어떤 요소가 있고, 무엇을 하면 어떻게 되며, 어떤 상태가 있는가. 문장과 표로 적는다(화면명세.md).
  • 배치의 기준: 요소가 어디에 어떤 크기와 순서로 놓이는가. 그림으로 정한다(ASCII 와이어프레임, HTML 프로토타입. 선택 도구로 Pencil).
  • 시각의 기준: 색, 글꼴, 간격의 값. 토큰 표로 정한다(디자인토큰.md).

구현자(사람 또는 AI)는 세 기준을 함께 받는다. 셋이 서로 어긋나면 임의로 정하지 않고 묻는다. 이 원칙을 화면 명세의 첫머리에 적어 두고, Claude Code에 보내는 프롬프트에도 넣는다(9절).

2. 시각적 위계와 레이아웃 그리드

2-1. 시각적 위계

시각적 위계(visual hierarchy)는 화면의 요소들을 배열해 사용자의 눈이 의도한 중요도의 순서대로 요소를 읽게 하는 일이다[N2]. 공고 목록 카드라면 사용자는 공고 제목을 먼저 읽고, 그다음 마감일, 그다음 모집기관과 지역을 읽어야 한다. 이 순서는 페르소나 PS-1 서지후(아르바이트와 병행하며 밤에 휴대폰으로 공고를 훑다가 마감 시각을 놓친다)의 과업에서 나온다. 위계는 디자이너의 취향이 아니라 사용자 조사의 결과를 화면으로 옮긴 것이다.

NN/g는 위계를 만드는 수단으로 색과 대비, 크기, 묶기를 든다[N2]. 여기에 실무에서 함께 쓰는 정렬을 더해 네 수단으로 정리한다.

수단 원리 공고 카드에 적용한 예 지나칠 때의 문제
크기 큰 요소가 먼저 눈에 들어온다 제목 20px 굵게, 본문 16px, 보조 14px 크기 단계가 많으면 무엇이 중요한지 다시 흐려진다
대비 주변과 명도·채도 차이가 큰 요소가 눈에 띈다. 굵기 차이도 대비이다 제목은 가장 진한 회색, 모집기관·지역은 진한 중간 회색 빨간색처럼 강한 색을 여러 곳에 쓰면 경고가 경고로 보이지 않는다
간격(묶기) 가까이 있는 것은 한 묶음으로, 떨어진 것은 다른 묶음으로 읽힌다. 배경이나 테두리로 묶을 수도 있다 카드 안 간격 8px, 카드 사이 24px. 카드는 옅은 회색 면 테두리와 상자를 남발하면 화면이 칸막이로 가득 찬다
정렬 같은 선에 맞춘 요소는 관계가 있어 보이고, 눈이 선을 따라 움직인다 카드 안의 모든 줄을 왼쪽 선에 맞춘다 가운데 정렬과 왼쪽 정렬을 섞으면 눈이 매 줄 시작점을 찾아야 한다

NN/g는 구체적인 지침도 준다[N2]. 글자 크기는 작게, 중간, 크게의 세 단계 정도로 제한하고, 웹 본문은 14~16px, 소제목은 18~22px, 제목은 32px 안팎을 출발점으로 삼는다. 가장 큰 크기의 요소는 한 화면에 둘을 넘기지 않는다. 빨간색 같은 따뜻하고 밝은 색은 경고와 오류에 아껴 쓴다. 색만으로 중요도를 나타내지 않는다. 색을 구별하지 못하는 사용자가 있기 때문이다.

2-2. 흐림 검사

위계가 의도대로 읽히는지는 흐림 검사(squint test)로 빠르게 확인한다[N2]. 화면을 흐리게 만들어 글자를 읽을 수 없게 한 뒤, 무엇이 먼저 눈에 들어오는지 본다. 글자를 읽지 못해도 제목의 덩어리, 카드의 경계, 주 버튼이 보이면 위계가 서 있는 것이다.

키트의 예제/위계_비교.html(교수 시연. 혼자 보려면 0-4의 웹 서버를 예제 폴더에서 띄운다)의 가와 나는 같은 공고 세 건을 보여 준다. 「흐리게 보기」를 눌러 가와 나에서 가장 먼저 눈에 들어오는 것을 견준다.

가에서는 빨간 마감일 줄이 공고 제목보다 먼저 눈에 띄고, 카드의 경계가 보이지 않아 세 공고가 한 덩어리로 읽힌다. 나에서는 회색 면 세 개가 먼저 보이고, 각 면의 맨 위 굵은 줄(제목)이 그다음에 보인다. 가는 크기와 굵기가 모두 같고, 가운데 정렬이며, 간격이 3px, 9px, 19px로 제각각이다. 나는 제목 20px 굵게, 보조 14px, 간격은 8px의 배수, 왼쪽 정렬이다. 핵심 실습에서는 자기 프로토타입에 같은 검사를 한다(10-5). 개발자 도구에서 body에 filter: blur(3px)를 잠시 주면 어느 화면이든 흐리게 볼 수 있다.

2-3. 간격 체계

간격을 매번 눈대중으로 정하면 3px, 9px, 19px처럼 제각각인 값이 쌓인다. 간격 체계는 쓸 수 있는 간격의 값을 미리 몇 개로 정해 두는 규칙이다. NN/g는 8px 단위를 권한다. 화면 크기의 다수가 8의 배수이므로 값을 8의 배수로 두면 크기를 바꿀 때 계산이 쉬워진다[N3].

jobprep의 간격 토큰은 다음 여섯 단계이다.

space-1  0.25rem   4px  아이콘과 글자 사이처럼 아주 촘촘한 자리
space-2  0.5rem    8px  레이블과 입력 칸 사이, 카드 안 줄 사이
space-3  1rem     16px  카드 안쪽 여백, 모바일 화면의 좌우 여백
space-4  1.5rem   24px  카드 사이, 입력 항목 사이
space-5  2rem     32px  절 사이
space-6  3rem     48px  화면 머리와 본문 사이

값을 rem으로 적으면 사용자가 브라우저의 기본 글자 크기를 키울 때 간격도 함께 커진다(7절).

간격 체계의 핵심은 「묶음 안의 간격은 묶음 사이의 간격보다 작다」는 한 가지 규칙이다. 카드 안의 줄 간격(8px)이 카드 사이의 간격(24px)보다 크면, 사용자는 카드의 마지막 줄을 다음 카드의 첫 줄로 읽는다. 양식에서도 레이블과 그 입력 칸 사이(8px)는 입력 항목과 다음 항목 사이(24px)보다 좁아야 레이블이 어느 칸의 것인지 헷갈리지 않는다.

2-4. 레이아웃 그리드

레이아웃 그리드는 화면을 세로 열로 나누고 요소를 그 열에 맞추어 놓는 틀이다. NN/g는 그리드를 이루는 요소로 열(column), 거터(gutter), 여백(margin)을 든다[N3].

  • 열: 내용이 놓이는 세로 칸이다. 폭을 백분율로 두어 화면 폭에 맞게 늘고 줄게 한다. 열의 수는 기기마다 다르다.
  • 거터: 열과 열 사이의 빈 공간이다. 고정 값으로 두고, 중단점에서 바꿀 수 있다. 넓은 화면일수록 넓게 둔다.
  • 여백: 화면 왼쪽과 오른쪽 끝의 빈 공간이다. 고정 값 또는 화면 폭의 비율로 두며, 내용은 여백에 들어가지 않는다.

데스크톱에서는 12열 그리드가 흔하고, 모바일에서는 4열처럼 열을 줄인다[N3]. 12열이 널리 쓰이는 까닭은 12가 1, 2, 3, 4, 6으로 나누어떨어져 한 줄에 카드 2개, 3개, 4개를 모두 놓을 수 있기 때문이다. 그리드의 종류는 열 그리드(세로 열만), 모듈 그리드(열과 행이 만든 칸. 상품 목록에 알맞다), 위계 그리드(중요한 내용에 더 넓은 칸)로 나뉜다[N3].

jobprep의 공고 목록은 카드가 같은 크기로 반복되므로 열 그리드로 충분하다. 열의 수를 화면 폭에 따라 1, 2, 3으로 바꾼다. 공고 상세는 원문과 요약의 중요도가 다르므로 넓은 화면에서 3:2로 나누는 위계 그리드를 쓴다.

2-5. CSS 그리드로 옮기기

그리드를 CSS로 옮길 때 실제로 12열을 선언할 필요는 없다. CSS 그리드 레이아웃의 grid-template-columns와 fr 단위(남은 공간의 몫)로 필요한 열만 선언한다[W4].

[파일: prototype/css/style.css] (일부)

/* 카드 목록: 기본(모바일) 1열 */
.card-list {
  display: grid;
  gap: var(--space-4);              /* 거터 24px */
  grid-template-columns: 1fr;
}
main {
  max-width: var(--content-max-width);   /* 1152px */
  margin: 0 auto;
  padding: 0 var(--space-3);             /* 여백 16px */
}

gap이 거터이고, main의 좌우 padding이 여백이다. 열의 수를 바꾸는 규칙은 7절의 중단점에서 더한다. 공고 상세를 넓은 화면에서 원문 3, 요약 2로 나누는 위계 그리드는 grid-template-columns: 3fr 2fr이다(7-2).

3. 디자인 토큰

3-1. 디자인 토큰의 정의

디자인 토큰(design token)은 색, 글꼴, 간격, 그림자처럼 화면에서 되풀이되는 디자인 속성의 값에 이름을 붙여 한곳에 모아 둔 것이다. 한국 정부의 디자인 시스템 KRDS는 디자인 토큰을 「반복되는 디자인 속성을 변수로 정의해 코드화한 것」으로 설명하고, 그 목적을 디자인 시스템 전반의 일관성 유지와 관리로 든다[K2].

토큰이 없는 CSS에서는 진한 파랑 #1d4ed8이 주 버튼, 링크, 초점 표시에 흩어져 수십 번 적힌다. 색을 바꾸려면 그 자리를 모두 찾아 고쳐야 하고, 비슷하지만 다른 값(#1e40af, #2563eb)이 섞이면 어느 값이 의도된 것인지 아무도 모른다.

토큰을 쓰면 값은 토큰 파일 한 곳에만 있고, 화면의 CSS는 이름(var(--color-primary))만 가리킨다. 값을 바꾸려면 토큰 한 줄을 고치면 된다. AI에게 화면을 만들게 할 때도 「색은 토큰의 의미 색만 쓰고 16진 값을 직접 쓰지 않는다」고 지시하면, AI가 비슷한 색을 새로 지어내는 일을 막을 수 있다.

3-2. 토큰의 계층

KRDS는 토큰을 세 계층으로 나눈다[K2].

계층 뜻 KRDS의 이름 예 직접 쓰는가
프리미티브(기본) 토큰 색 팔레트, 서체, 굵기, 기본 간격 수치 같은 값 자체 primary-50, gray-5, number-4 쓰지 않는다. 다른 토큰이 참조한다
시멘틱(의미) 토큰 배경, 아이콘, 테두리처럼 용도나 맥락에 의미를 부여한 토큰. 기본 토큰을 참조한다 color-icon-primary, color-border-gray-light 화면의 CSS가 쓴다
컴포넌트 토큰 버튼, 입력 칸, 카드처럼 특정 UI에 직접 적용하는 토큰. 의미 토큰을 참조한다 --namespace-component--type-padding-x 형식 해당 컴포넌트의 CSS만 쓴다

계층을 나누는 까닭은 「무엇」과 「어디에」를 떼어 놓기 위해서이다. 기본 토큰 gray-50은 「중간 회색」이라는 값일 뿐 어디에 쓰는지 말하지 않는다. 의미 토큰 color-text-muted는 「보조 글자색」이라는 용도를 말한다. 보조 글자가 너무 흐리다는 리뷰를 받으면 color-text-muted가 가리키는 기본 토큰만 바꾸면 되고, 같은 회색을 쓰는 다른 용도(입력 칸 테두리)는 영향을 받지 않는다.

이 장의 jobprep은 화면이 네 개뿐이므로 기본 토큰과 의미 토큰의 두 층으로 둔다. 컴포넌트 토큰은 컴포넌트가 많아지고 여러 팀이 같은 컴포넌트를 쓸 때 더한다.

3-3. 토큰의 이름

토큰의 이름은 사람과 AI가 모두 읽고 추측할 수 있어야 한다. KRDS는 기본 색에 「색상명-단계」 형식을 쓰고, 단계는 명도를 뜻하는 숫자로 둔다(primary-50, danger-60)[K1]. 의미 토큰은 「분류-용도-변형」의 순서로 이름을 짓는다(color-border-gray-light)[K2]. jobprep의 토큰도 같은 방식을 따른다.

기본 색       색이름-명도단계(숫자가 클수록 어둡다)   gray-5, gray-90, blue-60
의미 색       color-용도(-변형)                     color-text, color-text-muted, color-danger-soft
글꼴          font-속성-용도                        font-size-body, font-weight-bold
간격          space-단계                            space-1 ~ space-6
모양과 크기   속성-용도                             radius-card, size-target-min

이름에는 소문자, 숫자, 하이픈만 쓴다. CSS 사용자 지정 속성은 대소문자를 구별하므로[W5] --Color-Text와 --color-text는 다른 속성이 된다. 처음부터 소문자로만 쓰면 이 실수가 생기지 않는다.

이름에 값을 넣지 않는 것도 규칙이다. color-blue-text라고 지으면 브랜드 색이 초록으로 바뀌는 날 이름이 거짓말이 된다.

3-4. W3C 디자인 토큰 형식

디자인 도구(Figma, Penpot 등)와 코드가 토큰을 주고받으려면 공통 형식이 필요하다. W3C의 디자인 토큰 커뮤니티 그룹(Design Tokens Community Group)은 이 형식을 만드는 모임이며, 2025년 10월 28일에 첫 안정판인 디자인 토큰 형식 모듈 2025.10을 발표하였다[W8][W9]. 이 형식의 요점은 다음과 같다[W8].

  • 파일은 JSON이고, 권장 확장자는 .tokens 또는 .tokens.json이다.
  • $value 속성을 가진 객체가 토큰이고, 그 객체의 키가 토큰의 이름이다. $value가 없는 객체는 토큰을 묶는 그룹이다.
  • $type은 토큰의 종류(color, dimension, fontFamily, fontWeight, duration, number 등)를 밝힌다. 그룹에 적으면 안의 토큰이 물려받는다. 도구는 값을 보고 종류를 짐작하면 안 된다.
  • 다른 토큰을 가리키는 별칭(alias)은 중괄호로 쓴다. "{color.gray.90}"은 그 토큰의 $value로 풀린다. 서로를 가리키는 순환 참조는 오류이다.
  • 길이(dimension)는 {"value": 8, "unit": "px"}처럼 숫자와 단위를 나누어 적는다. 단위는 px 또는 rem이다.

[파일: 예시.tokens.json] (형식을 보이기 위한 예)

{
  "color": {
    "$type": "color",
    "gray": {
      "90": { "$value": { "colorSpace": "srgb", "components": [0.067, 0.094, 0.153], "hex": "#111827" } }
    },
    "text": { "$value": "{color.gray.90}", "$description": "본문 글자" }
  },
  "space": {
    "$type": "dimension",
    "2": { "$value": { "value": 0.5, "unit": "rem" } }
  }
}

이 장은 이 JSON을 직접 쓰지 않는다. 대신 사람이 읽고 리뷰하기 쉬운 마크다운 표(디자인토큰.md)에 토큰을 적고, 별칭은 W3C 형식과 같은 중괄호 문법({gray-90})을 빌려 쓴다. 표 한 줄이 토큰 하나이므로 풀 리퀘스트의 차이(diff)에서 어느 토큰이 바뀌었는지 한눈에 보인다. 팀이 디자인 도구를 쓰기 시작하면 이 표를 W3C 형식의 JSON으로 바꾸는 일은 Claude Code에게 맡길 수 있다.

위 JSON에서 color.text의 실제 값은 별칭 {color.gray.90}을 따라가 얻는 #111827이다.

견본의 표는 다음 약속을 따른다. 키트의 도구가 이 약속에 맞추어 표를 읽는다.

  1. 표의 첫 칸은 토큰 이름, 둘째 칸은 값이며 둘 다 백틱으로 감싼다. 백틱이 없는 줄은 토큰으로 읽지 않는다.
  2. 이름은 소문자, 숫자, 하이픈만 쓴다. 어기면 도구가 줄 번호와 함께 오류를 낸다.
  3. 같은 이름은 한 번만 쓴다. 두 번 쓰면 「N줄에도 있다」 오류가 난다.
  4. 값에서 다른 토큰은 {gray-90}처럼 중괄호로 가리킨다. 없는 토큰을 가리키면 오류이다.
  5. 제목에 「대비 쌍」이 든 절의 표는 토큰이 아니라 대비를 잴 색의 쌍이다(전경, 배경, 기준, 용도). 6절에서 쓴다.

의미 색 표의 한 줄을 본다.

[파일: docs/설계/디자인토큰.md] (1-2절의 일부)

| `color-text` | `{gray-90}` | 본문 글자 |
| `color-text-muted` | `{gray-50}` | 보조 글자(마감일, 모집기관과 지역, 도움말) |
| `color-border-input` | `{gray-50}` | 입력 칸의 테두리 |

color-text-muted와 color-border-input은 지금 같은 기본 토큰 gray-50을 가리킨다. 그래도 두 의미 토큰을 따로 두는 까닭은 용도가 다르기 때문이다. 6절에서 보조 글자의 대비가 부족한 것이 드러나면 color-text-muted만 바꾼다.

3-6. CSS 사용자 지정 속성

CSS 사용자 지정 속성(custom property)은 --로 시작하는 이름에 값을 담아 두고 var() 함수로 꺼내 쓰는 CSS의 기능이다. 흔히 「CSS 변수」라고 부른다. MDN이 설명하는 요점은 다음과 같다[W5].

  • 선언: --로 시작하는 이름을 쓰고, 선택자가 범위를 정한다. 전역으로 쓰려면 :root에 선언한다.
  • 사용: 속성 값이 들어갈 자리에 var(--color-text)처럼 쓴다. 속성 이름, 선택자, 미디어 쿼리 조건에는 쓸 수 없다.
  • 대체 값: var(--color-text, black)의 둘째 인수는 속성이 정의되지 않았거나 잘못되었을 때 쓰인다. 첫 쉼표 뒤가 모두 대체 값이다.
  • 상속: 일반 속성처럼 부모에서 자식으로 상속된다. 하위 요소에서 다시 선언하면 그 아래만 바뀐다.
  • 대소문자: 이름의 대소문자를 구별한다. --a와 --A는 다른 속성이다.
  • 자바스크립트: getComputedStyle(el).getPropertyValue("--color-text")로 계산된 값을 읽는다.

미디어 쿼리 조건에 var()를 쓸 수 없다는 점은 실제로 자주 부딪힌다. @media (min-width: var(--bp-wide))는 동작하지 않는다. 그래서 중단점의 값은 화면명세.md의 0절에 기록하고, CSS에는 숫자로 적는다(7절).

3-7. 토큰 변환기

디자인토큰.md를 tokens.css로 바꾸는 일은 사람이 손으로 하지 않는다. 손으로 옮기면 토큰 문서와 CSS가 금세 어긋난다. 키트의 tokens_to_css.py가 표를 읽어 :root 블록을 만든다. 별칭 {gray-90}은 var(--gray-90)으로 바뀐다.

[터미널] (읽기)

cd ~/llm-service-lab/jobprep
python "$KIT/tools/tokens_to_css.py" docs/설계/디자인토큰.md | head -12
/* 이 파일은 tools/tokens_to_css.py가 디자인토큰.md에서 만든다. 직접 고치지 않는다.
   값을 바꾸려면 디자인토큰.md를 고치고 도구를 다시 실행한다. */

:root {
  /* 1-1. 기본 색 */
  --gray-0: #ffffff;
  --gray-5: #f5f6f8;
  --gray-20: #d1d5db;
  --gray-50: #6b7280;
  --gray-60: #4b5563;
  --gray-90: #111827;
  --blue-5: #eff6ff;

의미 색은 기본 색을 var()로 가리킨다.

[터미널] (읽기)

  --color-text: var(--gray-90);
  --color-primary: var(--blue-60);

별칭을 값으로 풀어 적지 않고 var()로 남기는 까닭은 3-2의 계층을 CSS에서도 유지하기 위해서이다. 브라우저 개발자 도구에서 --color-text를 보면 그것이 --gray-90을 가리킨다는 관계가 그대로 보인다.

변환기는 토큰 문서의 실수도 잡는다. 없는 토큰을 가리키는 별칭을 일부러 넣어 본다.

[터미널] (읽기)

mkdir -p ~/tmp
cp docs/설계/디자인토큰.md ~/tmp/토큰시험.md

python "$KIT/tools/tokens_to_css.py" ~/tmp/토큰시험.md; echo "종료 코드 $?"
오류: 없는 토큰 'grey-90'를 가리킨다
종료 코드 2

gray를 grey로 잘못 쓴 별칭 하나 때문에 변환이 멈춘다. 손으로 옮겼다면 브라우저는 정의되지 않은 var(--grey-90)을 만나 글자색을 상속값으로 처리했을 것이고, 화면은 오류 없이 조용히 다른 색으로 그려졌을 것이다[W5].

시험 파일은 rm ~/tmp/토큰시험.md로 지운다. 이 실험은 수업에서 교수가 시연한다.

3-8. 화면에서 토큰 쓰기

화면의 CSS에는 의미 토큰만 쓴다. 기본 토큰과 16진 색을 직접 쓰지 않는다.

.card .meta { color: var(--color-text-muted); font-size: var(--font-size-small); }

이 규칙이 지켜졌는지는 검색 한 줄로 확인한다. tokens.css 밖의 CSS에 #으로 시작하는 6자리 색이 있으면 규칙을 어긴 것이다. 키트의 시작 파일에 대한 결과는 다음과 같다.

이 검사는 따라 하기 2(9-4)와 핵심 실습(10-5)에서 Claude Code가 만든 CSS에 쓴다.

4. 컴포넌트와 상태

4-1. 컴포넌트

컴포넌트(component)는 화면 여러 곳에서 같은 모양과 같은 동작으로 되풀이되는 UI의 단위이다. 버튼, 입력 칸, 카드, 알림 상자가 대표적이다. 화면을 컴포넌트의 조합으로 설계하면 같은 일을 하는 요소가 화면마다 다르게 생기는 일을 막을 수 있다. 사용자는 한 화면에서 배운 「파란 면 버튼은 주 행동」이라는 규칙을 다른 화면에서도 그대로 쓴다.

jobprep의 핵심 화면 4개에서 되풀이되는 컴포넌트를 뽑으면 다음과 같다.

  • 전역 내비게이션(모든 화면): 현재 화면과 비활성(아직 없는 화면)의 변형이 있다. 정보구조.md의 순서와 레이블을 그대로 쓴다.
  • 버튼(모든 화면): 주 버튼과 보조 버튼. 한 화면의 한 영역에 주 버튼은 하나만 둔다.
  • 입력 칸(SCR-01, SCR-04): 한 줄, 여러 줄, 선택, 날짜, 검색. 보이는 레이블, 도움말, 오류 문장이 한 묶음이다.
  • 공고 카드(SCR-01, SCR-03): 공고용과 일정용(삭제 버튼 있음). 제목은 링크이고 h2이다.
  • 마감 임박 표시(SCR-01, SCR-02): 「마감 임박 D-N」, 「마감 임박 D-day」. 접수 마감일까지 3일 이내에만 붙는다(REQ-003).
  • 알림 상자(모든 화면): 빈 상태, 오류, 완료. 색과 함께 제목이나 「오류:」 같은 글자로 종류를 밝힌다.
  • 상태 문장(SCR-01~03): 결과 수, 생성 중, 완료. 화면 낭독기가 읽도록 상태 영역으로 둔다(6절).

화면 명세에는 컴포넌트를 처음 정의하는 자리를 하나만 둔다. jobprep은 화면명세.md의 0절(모든 화면에 공통)이 그 자리이다. 각 화면의 명세는 「주 버튼」, 「알림 상자(빈 상태)」처럼 컴포넌트의 이름만 쓴다.

4-2. 컴포넌트의 상태

하나의 컴포넌트는 여러 상태(state)를 가진다. 버튼은 평소의 모습 말고도 마우스를 올렸을 때, 키보드로 초점을 받았을 때, 누를 수 없을 때의 모습이 각각 있어야 한다. 화면 전체도 상태를 가진다. 공고 목록은 공고가 있을 때, 불러오는 중일 때, 하나도 없을 때, 불러오지 못했을 때가 모두 다른 화면이다.

상태 뜻 버튼에서 화면(목록)에서 빠뜨리면
기본(default) 아무 일도 없는 평소 파란 면에 흰 글자 카드 목록
호버(hover) 마우스 포인터가 위에 있다 밑줄 마우스 사용자가 누를 수 있는지 망설인다
초점(focus) 키보드 초점이 있다 3px 파란 테두리 키보드 사용자가 자기 위치를 잃는다(WCAG 2.4.7)
누름(active) 누르는 순간 눌렸는지 확신하지 못해 거듭 누른다
비활성(disabled) 지금은 누를 수 없다 흐리게, 포인터 모양 바꿈 왜 안 눌리는지 모른다
로딩(loading) 시스템이 일하는 중 돌아가는 표시와 「…하는 중」 회색 자리 상자 멈춘 줄 알고 다시 누르거나 떠난다
빈 상태(empty) 보여 줄 내용이 아직 없다 안내와 다음 행동 고장 난 줄 안다
오류(error) 실패하였다 무엇이 실패했고 어떻게 하는지 무엇을 해야 하는지 모른다
성공(success) 끝났다 완료 알림 저장되었는지 다시 확인하러 간다

AI에게 화면을 만들게 하면 기본 상태는 대개 잘 만들어지고, 그 밖의 상태가 빠지기 쉽다. 「공고 목록 화면을 만들어 줘」라고만 하면 0건일 때의 화면은 빈 공간이 되기 쉽다. 그래서 화면 명세의 상태 표는 「기본」 줄보다 그 아래 줄이 더 중요하다.

4-3. 시스템 상태의 표시와 응답 시간

닐슨의 사용성 휴리스틱 첫째 항목은 「시스템 상태의 가시성」이다. 사용자는 시스템이 지금 어떤 상태인지 알아야 다음 행동을 정할 수 있다. 행동의 결과를 바로 알려 주는 피드백은 실수를 빨리 알아차리고 고치게 하고, 오래 걸리는 처리의 진행 표시는 사용자가 같은 버튼을 거듭 누르는 일을 줄인다[N4].

얼마나 기다리면 무엇을 보여야 하는가에 대해서는 닐슨이 정리한 응답 시간의 세 한계가 기준으로 쓰인다[N5].

한계 사용자가 느끼는 것 화면이 할 일 jobprep의 예
0.1초 시스템이 즉시 반응한다 결과만 보이면 된다. 따로 표시하지 않는다 필터를 바꾸면 목록이 바로 바뀐다
1초 지연을 느끼지만 생각의 흐름은 끊기지 않는다 특별한 표시가 없어도 되지만, 이보다 길면 흐름이 끊긴다 화면 이동
10초 주의를 붙잡아 둘 수 있는 한계 이보다 길면 언제 끝나는지 알려야 한다. 진행률 막대가 가장 좋다. 오래 걸리는 처리는 중단할 수단도 둔다 공고 요약 생성

LLM 기능은 이 표의 셋째 줄에 걸치는 경우가 많다. 공고 요약은 보통 몇 초, 길면 10초를 넘는다. 그래서 SCR-02의 명세는 생성 중 상태에 「요약을 만드는 중이에요. 보통 10초 안에 끝나요.」라는 문장을 넣어 예상 시간을 알린다. 생성 중에 버튼을 다시 누르면 같은 요청이 한 번 더 가고 비용이 두 배가 되므로, 생성 중에는 버튼을 잠근다(REQ-016).

4-4. 빈 상태

빈 상태(empty state)는 내용이 아직 없거나 보여 줄 수 없는 컨테이너, 화면, 패널이다[N6]. NN/g는 빈 상태의 설계 지침으로 세 가지를 든다[N6].

  1. 시스템 상태를 알린다. 빈 칸으로 두지 않고, 불러오는 중인지, 실패했는지, 정말 없는지를 구별해 알린다. 불러오는 중에 「없음」을 보이면 신뢰를 잃는다. SCR-03(지원 일정 0건)은 제목 「아직 지원 일정이 없어요」를 두고, 불러오기 실패와는 다른 상자를 쓴다.
  2. 배우게 한다. 이 기능이 무엇이고 어떻게 시작하는지 알려 준다. SCR-03은 「관심 있는 공고에서 「지원 일정에 추가」를 누르면 날짜순으로 여기에 모여요.」라고 쓴다.
  3. 다음 행동으로 가는 길을 준다. 설명에 그치지 않고 그 일을 하는 곳으로 바로 가게 한다. SCR-03은 「공고 찾아보기」(SCR-01)와 「직접 등록하기」(SCR-04) 두 버튼을 둔다.

검색 결과가 0건인 빈 상태(SCR-01)는 처음 쓰는 사람의 빈 상태(SCR-03)와 성격이 다르다. 사용자가 조건을 너무 좁게 걸었기 때문이다. 이때 다음 행동은 「조건을 넓히는 것」이므로, 안내 문장과 함께 「조건 모두 지우기」 버튼을 둔다(REQ-007).

4-5. 상태를 CSS와 HTML로 나타내기

상태마다 따로 클래스를 지어 붙이는 대신, 가능하면 HTML의 속성과 CSS의 의사 클래스를 쓴다. 그러면 화면에 보이는 모습과 보조 기술(화면 낭독기)이 읽는 상태가 한 곳에서 정해진다.

[파일: prototype/css/style.css] (버튼의 상태)

.btn--primary { background: var(--color-primary); color: var(--color-on-primary); }
.btn:hover { text-decoration: underline; }                 /* 호버 */
:focus-visible {                                            /* 초점(키보드) */
  outline: var(--focus-ring-width) solid var(--color-focus);
  outline-offset: 2px;
}
.btn[aria-disabled="true"], .btn:disabled {                 /* 비활성 */
  opacity: 0.6; cursor: not-allowed; text-decoration: none;
}
.btn[aria-busy="true"]::before {                            /* 로딩: 돌아가는 원 */
  content: ""; width: 1em; height: 1em; border-radius: 50%;
  border: 2px solid currentColor; border-right-color: transparent;
  animation: spin 0.8s linear infinite;
}
@media (prefers-reduced-motion: reduce) {
  .btn[aria-busy="true"]::before { animation: none; }
}

몇 가지를 짚어 둔다.

  • :focus-visible은 브라우저가 초점을 사용자에게 보여 주어야 한다고 판단할 때만 맞는다. 키보드로 초점을 옮기면 보이고, 마우스로 버튼을 누를 때는 보통 보이지 않는다. 그래서 초점 표시를 없애지 않고도 마우스 사용자의 화면을 깔끔하게 둘 수 있다[W6]. outline: none으로 초점 표시를 지우기만 하는 것은 WCAG 2.4.7의 실패 사례이다[W2].
  • 비활성 버튼에는 HTML의 disabled 속성과 aria-disabled="true" 두 방법이 있다. disabled는 버튼을 초점 순서에서 빼 버린다. 사용자가 「요약 만들기」를 눌렀는데 그 버튼이 생성 중에 disabled가 되면, 키보드 초점이 갈 곳을 잃고 문서 처음으로 튄다. 그래서 SCR-02는 aria-disabled="true"로 잠그고, 스크립트가 생성 중의 누름을 무시하게 한다.
  • aria-busy="true"는 그 요소가 갱신되는 중임을 보조 기술에 알린다. 같은 속성을 CSS 선택자로도 써서 돌아가는 표시를 그린다.
  • 움직임을 줄이도록 설정한 사용자(prefers-reduced-motion)에게는 회전 애니메이션을 멈춘다.

4-6. 상태 표의 작성

화면 명세의 상태 표는 「언제」, 「화면에 보이는 것」, 「문구」의 세 칸을 반드시 채운다. 「문구」 칸을 비워 두면 AI가 문구를 지어내고, 같은 상황에 화면마다 다른 말투의 문구가 생긴다.

[파일: docs/설계/화면명세.md] (SCR-01의 상태 표. 머리 줄은 줄였다)

| 기본 | 공고가 1건 이상 | 결과 수와 카드 목록 | 「공고 N건」 |
| 로딩 | 공고를 불러오는 동안 | 카드 자리에 회색 상자 3개, 영역에 aria-busy | 「공고를 불러오는 중이에요」 |
| 빈 상태 | 조건에 맞는 공고가 0건 | 안내 상자: 제목, 바꾸는 방법, 「조건 모두 지우기」 버튼 | 「조건에 맞는 공고가 없어요」 |
| 오류 | 공고 자료를 읽지 못함 | 오류 상자(role="alert")와 「다시 불러오기」 | 「공고 자료를 불러오지 못했어요. …」 |

문구 칸의 말투는 해요체이다. 화면의 문구는 교재의 문체와 다른 「서비스의 말투」를 따른다. 어떤 말투를 쓸지는 화면명세.md 0절에 한 번 정해 두고, 모든 화면이 따른다. 이 장의 본문에 인용하는 화면 문구는 서비스의 말투 그대로 옮긴다.

프로토타입에서는 상태를 일부러 만들기 어렵다. 공고가 0건인 상태를 보려면 데이터를 지워야 하고, 불러오기 실패를 보려면 네트워크를 끊어야 한다. 그래서 jobprep의 프로토타입은 주소 뒤에 ?state=empty, ?state=loading, ?state=error를 붙이면 해당 상태를 바로 보이게 만든다. 리뷰어는 주소만 바꾸어 명세의 상태 표를 한 줄씩 대조한다.

키트의 시작 파일에는 아직 상태가 구현되어 있지 않으므로, index.html 주소 뒤에 ?state=empty를 붙여도 화면이 달라지지 않는다. 「명세에는 있으나 구현에는 없는 상태」가 이렇게 보인다. 따라 하기 2(9-3)에서 이 빈칸 가운데 세 줄을 채운다.

5. 양식 설계와 오류 메시지

5-1. 양식 설계의 권고

양식(form)은 사용자가 시스템에 정보를 넣는 화면이다. jobprep에서는 SCR-04 지원 일정 등록이 양식이고, SCR-01의 검색과 필터도 작은 양식이다. NN/g는 웹 양식의 설계 권고로 다음 열 가지를 든다[N7].

번호 권고 SCR-04에 적용한 결정
1 양식을 짧게 한다. 다른 데서 얻을 수 있거나 나중에 받아도 되는 항목은 뺀다 모집기관의 주소, 채용 담당자는 받지 않는다
2 레이블을 입력 칸 가까이 두고, 관련 항목을 시각적으로 묶는다 레이블은 칸 바로 위, 레이블과 칸 사이 8px
3 한 열로 배치해 위에서 아래로 내려가게 한다 넓은 화면에서도 한 열
4 항목과 선택지를 논리적 순서로 둔다. 키보드 탭 순서를 시험한다 모집기관 → 공고 제목 → 일정 종류 → 날짜 → 메모
5 자리 표시 글자(placeholder)를 쓰지 않는다 형식 안내는 칸 위 도움말로
6 칸의 종류와 폭을 예상 입력에 맞춘다 날짜는 type="date"
7 선택 항목을 분명히 표시하고 수를 줄인다 「(필수)」, 「(선택)」을 글자로 표시. 선택 항목은 메모 하나
8 형식과 입력 조건을 오류 메시지가 아니라 미리 알린다 「100자까지 적을 수 있어요」를 칸 위에
9 초기화(Reset) 버튼을 두지 않는다. 필요하면 덜 눈에 띄는 취소를 둔다 「취소」는 보조 버튼
10 오류 메시지를 눈에 잘 띄고 구체적으로 쓰며, 색만 쓰지 않고, 입력한 값을 남긴다 5-3, 5-4

자리 표시 글자를 레이블 대신 쓰면 입력을 시작하는 순간 글자가 사라져 무엇을 넣는 칸이었는지 잊고, 옅은 회색이라 대비도 부족하다. 키트의 일정등록_나쁜예.html이 이 방식을 쓴다.

5-2. 레이블과 안내

WCAG 2.2의 성공 기준 3.3.2(레이블 또는 지시, 수준 A)는 사용자가 입력해야 하는 곳에 레이블이나 지시를 제공하도록 요구한다[W1]. 레이블은 눈에 보이고, 입력 칸과 프로그램적으로 연결되어야 한다. 연결 방법은 <label for="아이디">와 입력 칸의 id를 맞추는 것이 가장 단순하다. 레이블을 누르면 입력 칸에 초점이 가므로 누를 수 있는 면적도 넓어진다[W3].

[파일: prototype/schedule-new.html] (날짜 칸)

<div class="field">
  <label for="date">날짜 <span class="req">(필수)</span></label>
  <span class="hint" id="date-hint">공고에서 왔으면 접수 마감일이 채워져 있어요</span>
  <input id="date" name="date" type="date"
         aria-describedby="date-hint" required>
</div>

aria-describedby는 레이블 말고 덧붙여 읽을 설명을 연결한다. 화면 낭독기는 이 칸에 초점이 오면 「날짜 (필수), 날짜 입력, 공고에서 왔으면 접수 마감일이 채워져 있어요」처럼 레이블과 설명을 함께 읽는다. 필수 표시를 별표(*) 하나로만 하면 별표의 뜻을 따로 알려야 하므로, jobprep은 「(필수)」를 글자로 쓴다.

모집기관 칸에는 autocomplete="organization"을 단다. WCAG 1.3.5(입력 목적 식별, AA)는 사용자에 관한 정보를 받는 칸의 목적을 프로그램이 알 수 있게 하라고 요구하며[W1], autocomplete 값이 그 수단이다. 브라우저가 전에 넣은 값을 제안할 수 있다.

5-3. 오류 메시지의 지침

WCAG 2.2는 오류에 대해 두 기준을 둔다[W1]. 3.3.1(오류 식별, A)은 입력 오류가 자동으로 감지되면 오류가 난 항목을 밝히고 오류를 글자로 설명하라고 요구한다. 3.3.3(오류 제안, AA)은 오류를 고치는 방법을 알고 있으면 그것을 사용자에게 제안하라고 요구한다. 여기에 1.4.1(색의 사용, A)이 더해진다. 색만으로 정보를 전하면 안 되므로 빨간 테두리만으로 오류를 알릴 수 없다.

NN/g는 오류 메시지의 지침을 보이기, 전달, 효율의 세 묶음으로 정리한다[N8].

묶음 지침 뜻
보이기 오류가 난 자리 가까이 둔다 메시지를 원인이 된 칸 옆에 두어 둘의 관계가 보이게 한다
눈에 띄고 중복된 표시를 쓴다 빨간색, 굵은 글씨에 아이콘이나 테두리를 더한다. 색만으로는 색각 이상 사용자가 알아보지 못한다
심각도에 맞게 보인다 가벼운 문제는 조용히, 진행을 막는 문제만 대화 상자로
검사 시점을 조심한다 사용자가 입력을 마치기 전에 오류를 띄우지 않는다
전달 사람이 읽을 수 있는 말을 쓴다 전문 용어와 오류 코드를 피한다
문제를 정확히 설명한다 「오류가 발생했습니다」 대신 무엇이 잘못되었는지
고치는 방법을 알려 준다 무엇을 하면 되는지
사용자를 탓하지 않는다 시스템의 규칙을 중심으로, 농담 없이
효율 입력한 값을 지킨다 오류가 나도 지우지 않고 고칠 수 있게 남긴다
고치는 수고를 줄인다 고칠 값을 고를 수 있게 제안한다

이 지침을 SCR-04의 오류 문구에 적용한다.

칸과 조건 나쁜 문구 좋은 문구 고친 점
모집기관이 비었다 「필수 항목입니다」 「모집기관을 입력해 주세요.」 어느 칸인지 밝힌다
날짜가 비었다 「잘못된 입력」 「날짜를 골라 주세요. 예: 2027-04-30」 고치는 방법과 형식 예
날짜가 지났다 「날짜 오류(E102)」 「날짜가 지났어요. 오늘(2027-04-09) 이후 날짜를 골라 주세요.」 코드를 빼고, 무엇이 문제인지와 기준 날짜를 알린다
저장 실패 「저장 실패」 「지원 일정을 저장하지 못했어요. 브라우저가 이 사이트의 데이터 저장을 막고 있어요. … 입력한 내용은 그대로 있어요.」 까닭과 고치는 방법을 알리고(REQ-026), 입력이 남아 있음을 알려 안심시킨다

5-4. 오류의 표시 구조

오류가 둘 이상일 수 있는 양식은 두 곳에 오류를 보인다. 양식 위의 오류 요약과 각 칸 아래의 오류 문장이다. 저장을 눌렀을 때 오류가 있으면 초점을 오류 요약으로 옮긴다. 키보드와 화면 낭독기 사용자는 그 자리에서 오류가 몇 건이고 무엇인지 듣고, 요약의 항목을 눌러 해당 칸으로 바로 간다.

flowchart TD
    A["「일정 저장」 누름"] --> B{"규칙에 맞는가"}
    B -- 예 --> C["저장 → SCR-03<br/>완료 알림"]
    B -- 아니오 --> D["오류 요약을 보이고<br/>초점을 요약으로"]
    D --> E["칸마다 오류 문장<br/>aria-invalid, aria-describedby"]
    E --> F["요약의 항목을 누르면<br/>해당 칸으로 초점"]
    F --> A

<div id="error-summary" class="notice notice--error" role="alert" tabindex="-1">
  <h2>입력을 확인해 주세요 (2건)</h2>
  <ul>
    <li><a href="#company">모집기관을 입력해 주세요.</a></li>
    <li><a href="#date">날짜가 지났어요. 오늘(2027-04-09) 이후 날짜를 골라 주세요.</a></li>
  </ul>
</div>
...
<label for="company">모집기관 <span class="req">(필수)</span></label>
<input id="company" name="company" aria-invalid="true" aria-describedby="company-error">
<p id="company-error" class="error">오류: 모집기관을 입력해 주세요.</p>
  • role="alert"는 내용이 나타나면 화면 낭독기가 하던 말을 끊고 바로 읽게 한다[W7]. 진행을 막는 오류이므로 이 역할이 맞다.
  • tabindex="-1"은 탭 순서에는 넣지 않되 스크립트로 초점을 줄 수 있게 한다[W3].
  • aria-invalid="true"는 칸이 잘못된 값을 가졌음을 보조 기술에 알린다.
  • 오류 문장 앞의 「오류:」는 색을 보지 못하는 사용자에게도 이 문장이 오류임을 알린다. CSS의 ::before로 붙인 글자는 보조 기술에 따라 읽히지 않을 수 있으므로 HTML의 글자로 넣는다.

5-5. 검사 시점

언제 검사할 것인가는 사용성과 접근성이 함께 걸린 결정이다. NN/g는 사용자가 행동하기 전에 오류를 띄우지 말되, 자주 틀리는 칸에는 입력하는 대로 검사하는 방식도 쓸 수 있다고 한다[N8]. 선택지는 셋이다.

  • 입력하는 동안(글자마다): 즉시 알지만 다 쓰기도 전에 오류가 뜬다. 비밀번호 규칙처럼 조건을 하나씩 맞추어 가는 칸에 알맞다.
  • 칸을 떠날 때: 칸 하나를 마칠 때마다 알지만, 오류 문장이 나타나고 사라지며 화면이 위아래로 움직인다. 형식이 정해진 긴 양식에 알맞다.
  • 저장을 누를 때: 화면이 흔들리지 않고 오류를 한 번에 모아 보이지만, 끝까지 쓴 뒤에야 안다. 짧은 양식에 알맞다.

jobprep의 SCR-04는 칸이 다섯 개뿐인 짧은 양식이므로 「저장을 누를 때」를 택한다. 이 결정에는 이 교재의 견본 프로토타입을 만들면서 겪은 사례가 있다. 견본의 첫 판은 칸을 떠날 때 다시 검사하게 하였다. 날짜를 고친 뒤 바로 「일정 저장」을 누르면, 날짜 칸을 떠나는 순간 그 아래의 오류 문장이 사라지고 저장 버튼이 한 줄 위로 올라갔다. 그 결과 저장 버튼을 겨냥한 클릭이 빈 곳에 떨어져 아무 일도 일어나지 않았다. 이 결함은 9절의 자동 점검(Playwright)이 저장 뒤의 화면 이동을 기다리다 시간 초과를 낸 것으로 드러났다. 화면 명세 SCR-04의 상호작용 표에 「칸을 고치는 중에는 오류를 즉시 다시 띄우지 않는다. 검사는 저장을 누를 때 한다」를 더하고 프로토타입을 고쳤다.

5-6. 나쁜 예의 점검

키트의 예제/일정등록_나쁜예.html은 5-1~5-4의 권고를 일부러 어긴 양식이다. 수업에서는 교수가 화면에 띄우고, 학습자가 먼저 사람의 눈으로 문제를 찾아 「무엇이 문제이고 어느 기준에 어긋나는지」를 한 줄씩 말한다. 예: 「회사명 칸에 레이블이 없고 자리 표시 글자만 있다 — NN/g 5, WCAG 3.3.2」. 소스 보기(Ctrl+U)로 HTML을 읽으면 레이블, alt, tabindex의 문제가 보인다. 6-8에서 같은 파일을 점검 도구에 넣어, 사람이 찾은 문제와 도구가 찾은 문제를 비교한다.

6. 접근성

6-1. 접근성과 WCAG 2.2

웹 접근성은 장애가 있는 사람을 포함해 누구나 웹 서비스를 인식하고, 조작하고, 이해할 수 있게 하는 일이다. 화면 낭독기로 듣는 사용자, 키보드만 쓰는 사용자, 색을 구별하기 어려운 사용자, 화면을 크게 확대해 보는 사용자가 모두 jobprep의 사용자가 될 수 있다. 햇빛 아래에서 휴대전화를 보는 사람에게도 대비가 필요하다.

국제 기준은 W3C의 웹 콘텐츠 접근성 지침(Web Content Accessibility Guidelines, WCAG)이다. WCAG 2.2는 2023년 10월 5일에 W3C 권고안(Recommendation)으로 처음 발표되었고, 현재 판은 2024년 12월 12일에 다시 발행된 권고안이다[W1][W10]. WCAG는 인식의 용이성, 운용의 용이성, 이해의 용이성, 견고성의 네 원칙 아래 지침을 두고, 지침마다 시험할 수 있는 성공 기준(success criterion)을 둔다. 성공 기준은 A, AA, AAA의 세 수준으로 나뉘며, 법령과 조달 기준은 대개 AA까지를 요구한다. 한국에서는 WCAG를 바탕으로 한 「한국형 웹 콘텐츠 접근성 지침 2.2」를 방송통신표준심의회가 2022년 12월 28일에 발표하였고, 공공 누리집이 이를 적용한다[K3].

성공 기준은 「1.4.3」처럼 번호로 부른다. 첫 숫자가 원칙, 둘째가 지침, 셋째가 기준이다. 이 장에서 다루는 성공 기준을 모으면 다음과 같다[W1].

번호 이름 수준 요지 이 장의 절
1.1.1 텍스트 아닌 콘텐츠 A 텍스트 아닌 콘텐츠에 같은 목적의 텍스트 대체를 둔다 6-6

6-2. 대비 기준

WCAG 1.4.3은 글자와 글자 이미지의 대비율을 4.5:1 이상으로 요구한다. 큰 글자(18포인트 이상, 또는 굵은 14포인트 이상)는 3:1이면 된다[W1]. 1.4.11은 글자가 아닌 요소에 3:1을 요구한다. 입력 칸의 테두리, 초점 표시, 체크 상자의 선처럼 「그것이 없으면 UI를 알아볼 수 없는 부분」이 대상이다[W1]. 장식용 구분선처럼 정보를 전하지 않는 선은 대상이 아니다.

  • 본문 글자, 보조 글자, 링크, 버튼 글자는 4.5:1(1.4.3)이다. jobprep에서는 color-text/color-bg, color-text-muted/color-surface, color-on-primary/color-primary 같은 쌍이다.
  • 큰 글자는 3:1(1.4.3)이지만, 이 장은 이 완화를 쓰지 않고 화면 제목도 4.5:1로 맞춘다.
  • 입력 칸 테두리와 초점 표시는 3:1(1.4.11)이다. color-border-input/color-bg, color-focus/color-surface가 해당한다.
  • 장식 구분선(color-divider)은 기준이 없으므로 대비 쌍 표에 넣지 않는다.

KRDS는 명도 단계의 숫자에 대비 기준을 묶어 둔다. 단계 40은 3:1, 50은 4.5:1, 70은 7:1, 90은 15:1을 맞추도록 색을 조정하였고, 이를 「매직넘버」라고 부른다[K1]. KRDS는 주 색 primary-50이 처음에 3.9:1이어서 명도를 조정했다고 밝힌다[K1]. 색을 고를 때 대비를 나중에 재지 않고 처음부터 단계에 넣어 둔 설계이다.

6-3. 대비의 계산

대비율은 두 색의 상대 휘도(relative luminance)로 계산한다. 상대 휘도는 색의 밝기를 가장 어두운 검정 0부터 가장 밝은 흰색 1까지로 나타낸 값이다. WCAG 2.2는 sRGB 색의 상대 휘도를 다음과 같이 정의한다[W1].

1. 채널마다(R, G, B):  c = 8비트 값 / 255
2. c ≤ 0.04045 이면  c' = c / 12.92
   아니면            c' = ((c + 0.055) / 1.055) ^ 2.4
3. L = 0.2126 × R' + 0.7152 × G' + 0.0722 × B'

대비율 = (L1 + 0.05) / (L2 + 0.05)     L1은 밝은 색, L2는 어두운 색. 범위 1:1 ~ 21:1

2단계는 화면의 밝기 값을 사람의 눈이 느끼는 선형 밝기로 되돌리는 계산이다. 3단계의 가중치는 사람의 눈이 초록에 가장 민감하고 파랑에 가장 둔감하다는 사실을 반영한다. 같은 255라도 초록은 휘도에 0.7152만큼, 파랑은 0.0722만큼 기여한다. 문턱값 0.04045는 2021년 5월 전까지 0.03928이었으나, 계산 결과에 실제 차이가 없어 고쳐졌다[W1].

보조 글자색 #6b7280을 손으로 계산해 본다.

채널 16진 8비트 c = 값/255 c’ (2단계) 가중치 기여
R 6b 107 0.4196 0.1470 0.2126 0.0313
G 72 114 0.4471 0.1683 0.7152 0.1204
B 80 128 0.5020 0.2159 0.0722 0.0156
L = 0.1672

흰 바탕(L = 1)과의 대비율은 (1 + 0.05) / (0.1672 + 0.05) = 4.83이다. 옅은 회색 카드 면 #f5f6f8(L = 0.9210)과의 대비율은 (0.9210 + 0.05) / (0.1672 + 0.05) = 4.47이다. 같은 글자색이 바탕에 따라 통과와 미달로 갈린다.

판정할 때는 계산 결과를 반올림하지 않는다. 4.47을 반올림해 4.5로 적으면 통과처럼 보이지만 기준에 못 미친다. 키트의 계산기는 소수 둘째 자리 아래를 버린다.

많이 쓰이는 색 몇 가지를 계산기로 재면 다음과 같다. 밝은 파랑 #3b82f6 위에 흰 글자를 올리면 3.67:1로 4.5에 못 미친다. 자리 표시 글자에 흔히 쓰는 #9ca3af는 흰 바탕에서 2.53:1이다.

6-5. 키보드 접근

키보드만 쓰는 사용자는 Tab으로 다음 요소, Shift+Tab으로 이전 요소로 초점을 옮기고, Enter로 링크와 버튼을 누르고, Space로 버튼과 체크 상자를 누르고, 방향키로 선택 목록 안을 움직인다[W3]. 이 조작이 화면의 모든 기능에 통하도록 하는 것이 2.1.1(키보드)이다.

키보드 접근의 대부분은 올바른 HTML 요소를 쓰는 것으로 해결된다. <button>, <a href>, <input>, <select>는 기본으로 초점을 받고 키보드로 동작한다. <div>에 onclick을 달아 버튼처럼 쓰면 초점도 받지 않고 Enter도 듣지 않는다. 이것을 고치려면 role="button", tabindex="0", 키 처리 코드를 모두 직접 넣어야 한다. 처음부터 <button>을 쓰는 것이 훨씬 쉽다[W3].

점검 항목 기준 jobprep에서의 구현
모든 기능을 키보드로 2.1.1 버튼과 링크는 모두 <button>, <a href>
갇히지 않는다 2.1.2 대화 상자를 직접 만들지 않고 브라우저 기본 확인 창을 쓴다
되풀이 블록 건너뛰기 2.4.1 첫 초점에 「본문 바로가기」 링크
순서가 읽는 순서와 같다 2.4.3 tabindex에 양수를 쓰지 않는다. 0과 -1만 쓴다
초점이 보인다 2.4.7 :focus-visible에 3px 테두리
초점이 가려지지 않는다 2.4.11 화면 위에 고정되는 머리글을 두지 않는다
누름 영역 2.5.8 24×24 이상. jobprep은 버튼과 홀로 놓인 링크를 44px 높이로

tabindex에 1 이상의 값을 주면 그 요소가 문서 순서와 상관없이 먼저 초점을 받는다. 화면의 위에서 아래로 읽는 순서와 초점 순서가 어긋나므로 쓰지 않는다. tabindex="0"은 원래 초점을 받지 않는 요소를 문서 순서대로 초점 순서에 넣고, tabindex="-1"은 탭 순서에는 넣지 않되 스크립트로 초점을 줄 수 있게 한다[W3].

2.5.8(목표 크기, 최소)은 누르는 대상이 24×24 CSS 픽셀 이상이기를 요구한다. 다만 몇 가지 예외가 있다. 작은 대상이라도 그 중심에 지름 24px의 원을 그렸을 때 다른 대상과 겹치지 않으면 된다(간격 예외). 같은 기능을 하는 다른 큰 대상이 있어도 되고, 문장 안의 링크처럼 줄 높이에 묶인 대상도 예외이다[W1]. jobprep은 이 최소 기준보다 넉넉하게, 버튼과 홀로 놓인 링크의 높이를 size-target-min(44px)으로 둔다.

손으로 하는 키보드 점검은 다음 순서로 한다. 마우스는 책상 한쪽으로 치운다.

  1. 주소창을 누른 뒤 Tab을 한 번 누른다. 「본문 바로가기」가 나타나야 한다.
  2. Tab을 계속 누르며 초점이 가는 순서를 종이에 적는다. 초점이 보이지 않는 순간이 있으면 표시한다.
  3. 과업 하나(예: 공고를 골라 지원 일정에 추가)를 키보드만으로 끝까지 해 본다.
  4. Shift+Tab으로 거꾸로도 가 본다. 어딘가에서 빠져나오지 못하면 함정이다.

이 순서는 핵심 실습의 키보드 점검(10-6)에서 그대로 쓴다. 미리 연습하려면 예제/위계_비교.html에서 「흐리게 보기」 버튼까지 Tab으로 가서 Enter나 Space로 눌러 본다. 이 예제는 초점 표시를 따로 꾸미지 않았으므로 브라우저의 기본 테두리가 보인다.

6-6. 이름, 레이블, 대체 텍스트

화면 낭독기는 각 요소의 역할(버튼, 링크, 입력 칸)과 이름(무엇을 하는 버튼인가)을 읽는다. WCAG 4.1.2(이름, 역할, 값)는 모든 UI 구성 요소의 이름과 역할을 프로그램이 알 수 있게 하라고 요구한다[W1]. 이름이 없는 버튼은 화면 낭독기에서 「버튼」이라고만 읽혀 무엇을 하는지 알 수 없다.

대체 텍스트를 쓸 때는 이미지의 모습이 아니라 그 자리에서의 목적을 쓴다. 모집기관의 로고가 공고 카드의 모집기관 이름 옆에 있다면 그 이름이 이미 글자로 있으므로 로고는 장식이고 alt=""가 맞다. 로고가 홈으로 가는 링크 안에 혼자 있다면 그 링크의 이름이 되어야 하므로 alt="jobprep 홈"이 맞다. 주변 글에 이미 있는 내용을 대체 텍스트에 되풀이하지 않는다[W3].

2.5.3(이름 안의 레이블)은 보이는 레이블의 글자가 접근 가능한 이름 안에 들어 있기를 요구한다[W1]. 음성으로 화면을 조작하는 사용자는 화면에 보이는 글자를 말해 버튼을 누르기 때문이다. SCR-03의 삭제 버튼은 화면에 「삭제」만 보이지만, 여러 카드의 삭제 버튼을 구별하려고 aria-label을 단다. 이때 이름을 「삭제: 한빛데이터(가상) 웹 프론트엔드 개발 신입」처럼 보이는 글자로 시작하게 한다.

6-7. 상태 메시지

목록을 거르면 결과 수가 바뀌고, 요약을 만들면 「만드는 중」이 「만들었어요」로 바뀐다. 눈으로 보는 사용자는 이 변화를 바로 알지만, 화면 낭독기 사용자는 초점이 그 문장으로 가지 않는 한 모른다. 그렇다고 초점을 매번 그 문장으로 옮기면 사용자가 하던 일(필터 고르기)이 끊긴다. WCAG 4.1.3(상태 메시지)은 이런 메시지를 초점 이동 없이 보조 기술이 알 수 있게 하라고 요구한다[W1].

수단은 라이브 영역(live region)이다. aria-live 속성을 가진 요소의 내용이 바뀌면 화면 낭독기가 그 변화를 읽는다[W7].

  • aria-live="polite": 사용자가 하던 말이 끝나기를 기다렸다 읽는다. 가장 많이 쓴다. aria-live="assertive"는 하던 말을 끊고 바로 읽으므로 아껴 쓴다.
  • role="status": 암묵적으로 polite인 역할이다. 호환성을 위해 aria-live="polite"를 함께 다는 것이 권장된다. jobprep은 결과 수, 생성 중, 저장 완료에 쓴다.
  • role="alert": 오류와 경고에 쓰며 즉시 읽힌다. aria-live="assertive"를 함께 달면 일부 환경(iOS의 VoiceOver)에서 두 번 읽힌다. jobprep은 오류 요약과 불러오기 실패에 쓴다.

MDN은 라이브 영역에 대해 중요한 주의를 준다. 보조 기술은 「이미 있던 영역의 내용이 바뀌는 것」을 읽으므로, 영역을 스크립트로 새로 만들면서 같은 순간에 내용을 넣으면 읽히지 않을 수 있다. 라이브 영역은 처음 HTML에 빈 채로 넣어 두고, 나중에 내용만 바꾸는 것이 가장 확실하다[W7].

[파일: prototype/index.html] (결과 수 영역)

<p id="result-status" class="result-count" role="status" aria-live="polite"></p>

[파일: prototype/js/app.js] (필터가 바뀔 때)

status.textContent = `공고 ${hits.length}건`;

라이브 영역이 처음 HTML에 빈 채로 있고, 스크립트는 그 내용만 바꾼다. 보조 기술이 「이미 있던 영역의 내용 변화」를 읽기 때문이다.

6-9. 자동 점검의 한계

점검기의 오류가 0건이라는 것은 「이 아홉 규칙을 어기지 않았다」는 뜻일 뿐이다. 접근성을 통과했다는 뜻이 아니다. 점검기는 alt가 있는지는 알지만 그 내용이 이미지의 목적을 전하는지는 모른다. <label>이 연결되었는지는 알지만 「입력 1」 같은 레이블이 무엇을 넣으라는 말인지 모른다. 초점 표시의 대비, 실제 키보드 이동 순서, 화면 낭독기가 읽는 결과도 판정하지 못한다.

그래서 접근성 점검은 세 겹으로 한다. 첫째, 자동 도구로 기계가 판정할 수 있는 것을 모두 걸러 낸다. 둘째, 사람이 키보드로 과업을 끝까지 해 보고 점검표를 채운다. 셋째, 가능하면 화면 낭독기로 들어 본다. 이 장의 핵심 실습은 첫째와 둘째를 하고, 셋째는 「점검하지 못한 것」에 적는다. 접근성점검.md의 마지막 절이 그 자리이다.

7. 반응형 화면

7-1. 반응형 웹 디자인

반응형 웹 디자인(responsive web design)은 페이지가 모든 화면 크기와 해상도에서 잘 그려지고 쓸 수 있게 하는 접근 방식이다. 이 말은 이선 마콧(Ethan Marcotte)이 2010년에 만들었고, 유동 그리드, 유동 이미지, 미디어 쿼리의 세 가지로 설명하였다[W4]. 특정 기술 하나가 아니라 접근 방식이라는 점이 중요하다.

반응형 화면의 첫 줄은 뷰포트 메타 태그이다. 모바일 브라우저는 이 태그가 없으면 화면을 약 980px 폭의 가상 화면으로 그린 뒤 축소해 보여 준다. 그러면 중단점이 의도대로 동작하지 않는다. MDN은 이 태그를 언제나 <head>에 넣으라고 권한다[W4].

[파일: prototype/index.html] (<head> 안)

<meta name="viewport" content="width=device-width, initial-scale=1">

7-2. 모바일 우선과 중단점

모바일 우선(mobile first)은 좁은 화면의 한 열 배치를 기본 CSS로 쓰고, 화면이 넓어질 때 달라지는 규칙만 미디어 쿼리로 더하는 방식이다[W4]. 넓은 화면을 기본으로 쓰고 좁은 화면에서 지우는 방식은 지울 규칙이 많아 CSS가 복잡해진다. 한 열에 무엇을 먼저 놓을지 정하면 넓은 화면에서도 그 순서가 유지된다.

레이아웃이 바뀌는 화면 폭을 중단점(breakpoint)이라고 한다. MDN은 중단점을 특정 기기의 크기가 아니라 상대 단위(em, rem)로 정하라고 권한다[W4]. 기기는 해마다 바뀌지만, 「카드 두 장이 나란히 들어갈 만큼 넓어졌는가」라는 내용의 기준은 바뀌지 않는다.

이름 조건 공고 목록 필터 공고 상세
기본 0 이상 카드 1열 세로로 쌓는다 원문 아래 요약
중간 40rem(640px) 이상 카드 2열 한 줄(2:1:1) 원문 아래 요약
넓음 64rem(1024px) 이상 카드 3열 한 줄 원문 3, 요약 2로 나란히

[파일: prototype/css/style.css] (중단점)

/* 중단점 1: 40rem(640px) 이상. 필터를 한 줄로, 카드를 2열로 */
@media (min-width: 40rem) {
  .filters { grid-template-columns: 2fr 1fr 1fr; align-items: end; }
  .card-list { grid-template-columns: repeat(2, 1fr); }
}
/* 중단점 2: 64rem(1024px) 이상. 카드 3열, 상세는 본문과 요약을 나란히 */
@media (min-width: 64rem) {
  .card-list { grid-template-columns: repeat(3, 1fr); }
  .detail-grid { grid-template-columns: 3fr 2fr; align-items: start; }
}

MDN의 예제는 @media screen and (width >= 600px)처럼 범위 문법을 쓴다[W4]. (min-width: 40rem)과 (width >= 40rem)은 같은 조건이다. 이 교재는 오래된 브라우저에서도 동작하는 min-width 표기를 쓴다. 미디어 쿼리 안에서 rem은 사용자가 정한 브라우저의 기본 글자 크기를 기준으로 계산되므로, 글자를 크게 설정한 사용자에게는 중단점도 함께 커진다. 3-6에서 보았듯이 미디어 쿼리 조건에는 var()를 쓸 수 없으므로 중단점 값은 CSS에 숫자로 적고, 화면명세.md 0절에 기록한다.

7-3. 리플로와 확대

WCAG 1.4.10(리플로)은 폭 320 CSS 픽셀에서 가로와 세로 두 방향으로 스크롤하지 않고 내용을 쓸 수 있기를 요구한다[W1]. 320 CSS 픽셀은 폭 1280px 화면에서 브라우저를 400% 확대한 것과 같다. 저시력 사용자가 화면을 크게 확대했을 때 글줄마다 좌우로 스크롤해야 한다면 글을 읽을 수 없다. 1.4.4(글자 크기 조정)는 200%까지 키워도 내용과 기능을 잃지 않기를 요구한다[W1].

리플로를 깨는 흔한 원인은 다음과 같다.

  • 고정 폭: width: 400px인 카드는 max-width와 백분율, fr로 바꾼다.
  • 줄이 바뀌지 않는 긴 글자: 긴 URL이나 영문 단어에는 overflow-wrap: anywhere를 준다.
  • 열이 많은 표: 표만 가로 스크롤 영역에 넣는다. 표는 두 방향 배치가 필요한 예외에 든다.
  • 원본 크기 그대로의 이미지: img { max-width: 100%; height: auto; }[W4].
  • px로 고정한 글자: font-size: 14px 대신 rem을 쓴다.

브라우저 개발자 도구의 기기 모드에서 폭을 320으로 두고 가로 스크롤 막대가 생기는지 본다. 다음 명령으로 개발자 도구의 콘솔에서 수치로 확인할 수도 있다. 값이 320 이하면 가로 넘침이 없다.

8. 화면 명세

8-1. 화면 명세의 구성

화면 명세는 화면 하나에 대해 「무엇을 위해 있고(목적), 어느 요구를 충족하며(요구 ID), 무엇이 어디에 있고(구성 요소와 그림), 어떤 상태가 있으며(상태), 무엇을 하면 어떻게 되고(상호작용), 접근성을 위해 무엇을 지키는가(접근성 메모)」를 적은 문서이다. 키트의 화면명세_양식.md는 화면마다 일곱 칸을 둔다.

칸 내용 빠뜨리면 생기는 일
1) 개요 화면 ID, 목적 한 문장, 관련 요구 ID, 들어오고 나가는 길, 사용자 흐름의 위치 화면이 무엇을 위해 있는지 몰라, 리뷰가 취향 싸움이 된다
2) 와이어프레임 모바일 배치의 그림과 넓은 화면에서 달라지는 점 배치를 AI가 정한다
3) 구성 요소 위에서 아래 순서(= 초점 순서)의 요소 표. 종류, 규칙, 관련 요구 요소가 빠지거나 순서가 바뀐다
4) 상태 기본, 로딩, 빈 상태, 오류 등. 언제, 보이는 것, 문구 기본 상태만 만들어진다
5) 상호작용 사용자 동작과 시스템 반응의 표 버튼을 눌렀을 때의 동작을 AI가 지어낸다
6) 접근성 메모 초점 순서, 상태 알림, 그 화면에 특유한 접근성 결정 화면마다 접근성 처리가 달라진다
7) 열린 질문 명세서에 답이 없어 정하지 못한 것과 누가 언제 정하는가 모르는 것을 아는 것처럼 구현한다

화면 ID는 명세서 v2의 화면 목록(SCR-01~08)을 그대로 쓴다. 이 ID는 9장의 구현 파일, 10장의 API 연결, 13장의 사용성 평가 기록까지 같은 화면을 가리키는 이름이 된다. 그래서 이 장에서는 화면 ID를 바꾸지 않는다.

화면명세.md의 첫머리에는 모든 화면에 공통인 0절을 둔다. 머리와 내비게이션, 본문 바로가기, 문구의 말투, 중단점, 초점 표시, 누름 영역처럼 화면마다 되풀이하면 어긋나기 쉬운 결정을 한곳에 적는다. 각 화면의 명세에는 그 화면에만 있는 것을 쓴다.

8-2. 목적과 요구 ID

목적 칸은 「사용자가 이 화면에서 끝내는 일」을 한 문장으로 쓴다. 「공고 목록을 보여 준다」는 시스템이 하는 일이고, 「사용자가 조건에 맞는 공고를 마감일이 가까운 순으로 훑어보고 하나를 고른다」는 사용자가 끝내는 일이다. 목적을 사용자 쪽에서 쓰면 그 화면에 필요 없는 요소를 걸러 낼 기준이 생긴다. 공고 목록에 「인기 공고 배너」를 넣자는 의견이 나오면, 그것이 「조건에 맞는 공고를 고르는 일」을 돕는지 묻는다.

관련 요구 칸은 명세서의 요구 ID를 적는다. 모든 요구가 적어도 한 화면에 나타나야 하고, 화면의 모든 구성 요소는 적어도 하나의 요구에서 와야 한다. 앞쪽은 「빠진 기능」을, 뒤쪽은 「요구에 없는 기능」을 찾는 검사이다. 앞쪽은 다음 명령으로 거칠게 확인한다. 핵심 실습(10-3)에서는 0이 나온 줄만 남겨 본다.

0이 나온 요구는 화면 명세에 없는 요구이다. 이 장의 화면 밖에 있는 요구는 0이 정상이다. 자기소개서 피드백과 취업 자료 질의응답(REQ-017~021)은 10~11장의 화면 SCR-05, SCR-06에서, 지난 공고 묶음(REQ-011)은 9장의 SCR-07에서, 외부 전송 동의(REQ-027)는 SCR-05와 SCR-08에서 다룬다. 키 보호와 모의 모드(REQ-022, REQ-023)는 특정 화면이 아니라 서비스 전체에 적용한다. 그 밖의 요구가 0이면 빠진 것이다. 숫자 뒤에 쉼표로 이어 쓴 ID(REQ-001, 002, 003)는 이 검색에 잡히지 않으므로, 화면명세.md에서는 요구 ID를 REQ-002처럼 하나씩 완전한 형태로 적는다.

뒤쪽 검사를 하다 보면 화면에 꼭 필요하지만 명세서에 없는 요소(지역 필터, 입력 오류, 삭제 확인, 접근성 기준 등)가 나온다. 7장의 사용자 흐름도 날짜 형식 오류의 처리를 「8장 화면 명세에서 정함」으로 넘겼다. 이런 요소를 화면 명세에만 두면 9장의 인수 조건이 근거로 삼을 요구가 없어진다. 그래서 화면 명세에는 「7) 열린 질문」에 「요구 추가 제안」으로 적어 두고, 10-7에서 REQ-028부터 새 요구로 더해 명세서를 v3로 올린다. 본문이 인용하는 정답 예시의 REQ-028~039가 그 번호이다.

8-3. 와이어프레임 그리기

이 장은 와이어프레임을 ASCII 그림으로 그린다. 글자로 그린 그림은 화면명세.md 안에 바로 들어가고, git의 차이에서 무엇이 바뀌었는지 보이며, Claude Code가 그대로 읽는다. 다듬은 그림이 아니어도 된다. 정해야 하는 것은 요소의 순서, 묶음, 대략의 크기와 위치이다.

ASCII 와이어프레임에서 쓰는 약속은 다음과 같다.

「선택을 바꿔도 다른 화면으로 가지 않는다」는 WCAG 3.2.2(입력 시)에서 온다. 선택 목록에서 지역을 고르는 순간 다른 페이지로 넘어가면, 키보드 사용자는 방향키로 선택지를 훑어보는 것만으로 페이지가 바뀌어 버린다. 같은 화면 안에서 목록만 갱신하는 것은 맥락의 변화가 아니므로 괜찮다.

상호작용 표의 「초점을 검색어 칸으로 옮긴다」 같은 문장은 AI가 스스로 넣지 않는 대표적인 결정이다. 「조건 모두 지우기」 버튼은 누르는 순간 빈 상태 상자와 함께 사라지므로, 초점을 어디로 보낼지 정하지 않으면 초점이 문서 처음으로 튄다. 명세에 적어 두어야 구현된다.

8-5. LLM 기능이 들어간 화면

SCR-02 공고 상세에는 10장에서 구현할 공고 요약 영역이 있다. LLM 기능은 화면을 미리 설계해 두지 않으면 「버튼을 누르면 AI의 답이 나온다」 수준으로 구현되기 쉽다. 그러나 LLM의 출력은 일반 기능의 출력과 성격이 다르다. 느리고, 같은 요청에도 매번 다르며, 틀릴 수 있고, 비용이 든다. 화면은 이 네 성질을 모두 다루어야 한다.

성질 화면이 다룰 일 SCR-02의 결정 근거
느리다(몇 초~10초 이상) 생성 중임을 알리고 예상 시간을 말한다. 재요청을 막는다 버튼에 돌아가는 표시와 「요약을 만드는 중」, 상태 문장 「보통 10초 안에 끝나요」, aria-busy, aria-disabled [N4][N5], REQ-016
매번 다르다 마음에 들지 않으면 다시 만들게 한다 완료 뒤 버튼 이름이 「다시 만들기」로 바뀐다 [N10]
틀릴 수 있다 AI가 만든 것임을 밝히고, 근거를 문장 옆에 두어 대조하게 한다 고지 문장 「AI가 만든 요약이에요. 마감일과 자격 요건은 근거 문장과 원문 문단을 눌러 확인해 주세요.」, 항목마다 근거 문장과 「원문 N문단」 링크, 원문에 없는 항목은 「공고에 없음」 [N9], REQ-014, REQ-015
실패하고 비용이 든다 실패를 알리고 다시 시도할 길을 준다. 원문은 언제나 볼 수 있다 오류 상자와 「다시 시도」, 원문 영역은 요약과 따로 있어 실패해도 남는다. 사용 한도에 닿으면 요청을 보내지 않고 다시 쓸 수 있는 시각을 알린다 REQ-024, REQ-025

근거 표시는 특히 신중하게 설계한다. NN/g의 조사에 따르면 사용자는 생성형 AI의 인용 링크를 거의 누르지 않고, 인용이 붙어 있다는 것만으로 답을 더 믿는다. 인용이 지어낸 것이거나 주장을 뒷받침하지 않아도 그렇다[N9]. NN/g는 그래서 인용을 본문과 구별되게 표시하고, 인용을 해당 문장 바로 옆에 두며, 「출처」 같은 막연한 이름 대신 무엇을 가리키는지 알 수 있는 이름을 쓰고, 사용자에게 확인하라고 권하라고 한다[N9]. SCR-02의 근거 표시는 이 권고를 따른다. 요약은 네 항목(자격 요건, 근무 조건, 제출 서류, 접수 마감일, REQ-013)이고, 항목 바로 아래에 근거가 된 원문 문장을 인용하며(REQ-014) 그 끝에 링크를 붙인다. 링크의 이름은 「원문 3문단」이며, 누르면 그 문단으로 초점이 가고 문단이 강조된다. 원문이 바로 옆에 있으므로 대조하는 데 한 번의 누름이면 된다.

같은 글에서 NN/g는 단계별 추론 과정을 보여 주는 표시가 실제 모델의 작동을 충실히 드러내지 않는 사후 설명인 경우가 많다고 지적하고, 확신을 주는 그런 표시보다 출처와 한계의 분명한 진술에 기대라고 권한다[N9]. 그래서 SCR-02는 「AI가 이렇게 생각했어요」 같은 설명 영역을 두지 않는다.

「다시 만들기」 같은 후속 동작은 NN/g가 생성형 AI 챗봇의 응답 아래에 흔히 놓이는 컨트롤로 든 것이다. NN/g는 이런 컨트롤에 표준 아이콘을 쓰되 레이블이나 툴팁을 붙이고, 기능의 이름을 분명히 하라고 권한다[N10]. SCR-02는 아이콘 없이 「다시 만들기」라는 글자 버튼을 쓴다.

8-6. 선택 도구: Pencil

2026년판 교재는 화면 명세의 그림을 Pencil(pen.dev)로 그렸다[R1]. Pencil은 VS Code와 Cursor의 확장으로 쓰는 디자인 캔버스이고, 화면은 객체의 트리를 적은 JSON 텍스트 파일 .pen으로 저장되며 그 스키마는 공개되어 있다[P1]. Claude Code 같은 에이전트는 MCP로 Pencil에 연결해 캔버스에 그리거나 .pen을 읽어 코드에 적용한다[P1].

ASCII 그림은 순서, 묶음, 대략의 위치까지 정하고, git 차이가 줄 단위로 읽히며, 설치가 필요 없다. Pencil은 크기, 간격, 정렬까지 정하지만 .pen의 차이를 사람이 읽기 어렵고, 확장, 계정, MCP 연결이 필요하다. 그래서 이 장은 ASCII 그림과 HTML 프로토타입을 기본으로 한다. Pencil을 쓰는 팀도 기능은 화면명세.md가, 배치는 .pen이 기준이다. 설치와 연결 절차는 2026년판 교재(LLM_02주차 9-3~9-6절)에 있다.

8-7. Claude Code로 화면 명세 초안 쓰기

화면 명세의 초안은 Claude Code에게 쓰게 할 수 있다. 이 절의 프롬프트는 핵심 실습(10-3)에서 SCR-01에 보낸다. 명세서 v2, 정보 구조, 사용자 흐름이 이미 있으므로, Claude Code는 이 셋을 읽고 양식의 칸을 채운다. 사람이 할 일은 초안을 읽고, 명세서에 없는 내용이 들어가지 않았는지, 상태와 문구가 빠지지 않았는지 검토하는 것이다.

계획 모드로 시작한다. 계획 모드에서 Claude Code는 파일을 읽고 계획을 제안하지만, 사람이 승인하기 전에는 파일을 고치지 않는다[C1]. Shift+Tab을 상태 표시줄에 plan mode on이 보일 때까지 누르거나, claude --permission-mode plan으로 시작한다(2026-11 기준. 화면의 표시는 판에 따라 바뀔 수 있다).

Claude Code 
@docs/요구사항명세서.md @docs/설계/정보구조.md @docs/설계/사용자흐름.md @docs/설계/화면명세.md 를 읽어라.
화면명세.md는 양식이다. 이 양식에 따라 SCR-01 공고 목록 하나의 화면 명세 초안을 쓸 계획을 세워라.

규칙:
- 요구 ID와 화면 ID는 명세서의 것만 쓴다. 명세서에 없는 기능을 넣지 않는다.
- 화면에 필요해 보이지만 명세서에 없는 요소는 구성 요소 표에 넣지 말고 「7) 열린 질문」에 「요구 추가 제안」으로 적는다.
- 상태 표에는 기본, 로딩, 빈 상태, 오류를 모두 쓰고, 문구 칸을 비우지 않는다. 문구는 해요체.
- 와이어프레임은 폭 36칸 안팎의 ASCII 그림으로 모바일 배치를 그리고, 넓은 화면의 차이는 그림 아래 문장으로 쓴다.
- 명세서만으로 정할 수 없는 것은 지어내지 말고 「7) 열린 질문」에 적어라.
계획만 보여 주고, 내가 승인하면 그때 파일을 고쳐라.

Claude Code가 보여 주는 계획은 학습자마다 다르다. 다음은 예시이며, 실제 화면과 다를 수 있다.

(예시) 계획
1. 요구사항명세서.md 7절 화면 목록에서 SCR-01의 관련 요구 REQ-001~008을 확인
2. 정보구조.md 「내비게이션」 표의 순서와 레이블(공고, 지원 관리, 자기소개서, 자료 묻기)을 0절에 반영
3. 사용자흐름.md FLOW-01의 1~2단계를 개요의 「사용자 흐름」에 연결
4. 구성 요소 6개, 상태 4개, 상호작용 4개, 접근성 메모 5개 작성
5. 열린 질문: 공고가 많을 때 쪽 나누기 방식(명세서에 없음)
6. 요구 추가 제안: 지역·직무 분야 필터, 결과 수(명세서에 없음)

계획을 읽고, 명세서에 없는 것(예: 「인기 공고」 영역, 「로그인」 버튼)이 계획에 들어 있으면 승인하기 전에 빼라고 답한다. 승인한 뒤 Claude Code가 화면명세.md를 고치면, git diff로 바뀐 줄을 읽는다. 바뀐 파일이 화면명세.md 하나여야 한다.

[터미널] (핵심 실습 10-3에서)

cd ~/llm-service-lab/jobprep
git diff --stat
git diff docs/설계/화면명세.md | head -40

초안에서 볼 것은 상태 표의 네 줄과 문구, 관련 요구 칸의 ID가 명세서에 있는가, 명세서에 없는 요소가 「요구 추가 제안」에 있는가이다.

9. Claude Code로 만드는 HTML 프로토타입

9-1. 프로토타입의 범위

이 장의 프로토타입은 빌드 도구 없는 HTML, CSS, 자바스크립트로 만든다. npm install도, 번들러도, 프레임워크도 쓰지 않으며, 파일을 브라우저로 열면 바로 동작해야 한다. 9장은 이 구조를 그대로 이어 쓴다.

  • 프로토타입이 하는 것: 네 화면 사이의 이동, 가짜 데이터 6건의 검색과 필터, 관심 공고 저장과 해제, 양식 검사와 오류 표시, 공고 요약의 생성 중·완료·오류·한도 상태(가짜 응답), ?state= 주소로 상태 바로 보기.
  • 하지 않는 것(9~10장의 일): 실제 공고 데이터 받기, 브라우저 저장소에 영구 저장, 서버에 저장, 실제 LLM 호출, 로그인과 사용자 구분.

가짜 데이터의 날짜가 실제 날짜를 따르면 「마감 임박 D-2」 표시와 공고의 상태(접수예정, 접수중, 마감)가 날마다 달라져 리뷰어마다 다른 화면을 보게 된다. 그래서 프로토타입은 「오늘」을 2027-04-09로 고정한다(js/data.js의 TODAY). 공고마다 접수 시작일(opens)과 접수 마감일(deadline)을 두어 상태를 정한다. 모집기관과 공고는 모두 가상이고 이름 끝에 「(가상)」을 붙인다.

9-3. 프롬프트의 설계와 따라 하기 2

화면 명세에서 프로토타입을 만드는 프롬프트에는 네 가지가 들어가야 한다. 입력 파일, 기준의 우선순위, 금지 사항, 완료 조건이다.

  2. 기준의 우선순위: 기능은 화면 명세, 배치는 와이어프레임, 시각은 토큰이고, 어긋나면 묻는다. 빠뜨리면 AI가 셋 중 하나를 골라 임의로 맞춘다.
  3. 금지 사항: 빌드 도구와 외부 라이브러리, 16진 색(토큰만 쓴다), 명세에 없는 요소, tokens.css 수정을 금한다. 빠뜨리면 프레임워크가 들어오고, 비슷한 새 색이 생긴다.
  4. 완료 조건: 점검 명령의 결과(오류 0건)와 명세 항목별 보고. 빠뜨리면 「완료했습니다」 한 줄로 끝난다.

9-5. 명세와의 대조

점검 도구를 통과했다는 것은 「기계가 알아볼 수 있는 규칙을 어기지 않았다」는 뜻이다. 명세대로 만들어졌는지는 사람이 명세의 표를 한 줄씩 대조해 확인한다. 화면명세.md의 끝에 「프로토타입 대조 기록」 표를 두고, 명세의 구성 요소·상태·상호작용 표의 줄마다 결과를 적는다.

  • 일치: 명세대로 구현되었다. 할 일이 없다.
  • 다름: 구현되었으나 명세와 다르다. 명세가 맞으면 구현을 고치고, 구현이 더 나으면 명세를 고친다. 어느 쪽인지 적는다.
  • 없음: 명세에 있으나 구현되지 않았다. 구현을 요청한다.
  • 명세 밖: 구현에 있으나 명세에 없다. 빼거나, 필요하면 명세에 더한다.

「다름」에서 구현이 더 나은 경우도 있다(5-5의 검사 시점 사례). 이때는 명세에 결정을 더하고, 대조 기록에 「다름 → 고침」과 고친 내용을 남긴다. 명세 주도 개발에서 명세는 처음 쓴 그대로 굳어 있는 문서가 아니라, 구현과 대조하며 빈틈을 메워 가는 문서이다.

둘째 해결 과제이다. 자동 점검은 초점의 행방을 보지 못한다(6-9). 6-5의 순서로 끝낸 화면을 키보드만으로 점검해 접근성점검.md 2절에 14개 항목을 판정하고, 1절에는 단계 1과 4의 자동 점검 결과를 옮긴다.

과업은 화면마다 하나이다. SCR-01은 0건을 만든 뒤 「조건 모두 지우기」, SCR-02는 「요약 만들기」에서 근거 링크까지, SCR-03은 일정 삭제, SCR-04는 빈 칸으로 저장한 뒤 오류 요약에서 칸으로 가서 고쳐 저장하기이다. 과업마다 초점이 어디 있는지 눈으로 따라간다.

Claude Code가 만든 화면에서 자주 나오는 실패와 고치는 법이다(견본의 첫 판에도 이 가운데 넷이 있었다).

  • 「요약 만들기」 뒤 초점이 문서 처음으로 간다: 생성 중에 disabled를 썼다. aria-disabled="true"로 바꾼다(4-5).
  • 「조건 모두 지우기」나 일정 삭제 뒤 초점이 사라진다: 지워지는 요소에 초점이 있었다. 명세대로 검색어 칸이나 화면 제목(tabindex="-1")에 focus()를 준다(8-4).
  • 오류 요약에 초점이 가지 않거나 읽히지 않는다: tabindex="-1"이 없거나, 요약을 스크립트로 새로 만들었다. HTML에 hidden으로 미리 두고 내용만 바꾼다(5-4, 6-7).
  • 홀로 놓인 링크가 24px보다 작다: 높이를 size-target-min으로 키운다(6-5, 9-6).

실패를 찾으면 3절에 화면과 요소, WCAG 번호, 조치를 적는다. 고치는 일은 Claude Code에게 맡겨도 되며, 실행 상한에 따라 화면마다 한 번의 요청으로 한다. 요청에는 본 것과 기대를 사실로 적는다.

정리

  • 화면 명세는 화면마다 목적, 요구 ID, 와이어프레임, 구성 요소, 상태, 상호작용, 접근성 메모, 열린 질문을 적는다. 기능은 문장으로, 배치는 그림으로, 시각은 토큰으로 정하고, 셋이 어긋나면 구현자는 묻는다. 화면을 설계하며 정한 요구는 명세서에 새 번호로 더해 판을 v3로 올린다.
  • 충실도는 상호작용, 시각, 내용의 세 차원이다. AI가 만드는 시간을 줄였으므로 고충실도 프로토타입을 빨리 얻을 수 있지만, 그만큼 명세를 먼저 쓰고 명세로 리뷰해야 한다.
  • 시각적 위계는 크기, 대비, 간격, 정렬로 만들고, 흐림 검사로 확인한다. 간격은 8px 단위의 체계로, 배치는 열·거터·여백의 그리드로 정한다.
  • 디자인 토큰은 기본 토큰과 의미 토큰으로 나누고, 화면은 의미 토큰만 쓴다. 토큰의 원본은 디자인토큰.md 하나이고 tokens.css는 도구가 만든다.
  • 상태(기본, 호버, 초점, 비활성, 로딩, 빈 상태, 오류, 성공)는 기본 상태보다 그 밖의 상태가 빠지기 쉽다. LLM 기능은 느리고, 매번 다르고, 틀릴 수 있고, 비용이 든다는 네 성질을 화면이 다룬다.
  • 대비는 WCAG의 상대 휘도 공식으로 계산하고 반올림하지 않는다. 같은 색도 바탕에 따라 통과와 미달이 갈리고, 미달은 표의 줄이 아니라 색을 고쳐 없앤다.
  • 자동 점검 오류 0건은 접근성 통과가 아니다. 키보드 점검과 명세 대조는 사람이 하고, 찾은 실패는 고친 뒤 다시 점검한다.

개념 점검

  1. 와이어프레임, 목업, 프로토타입이 각각 정하는 것과 비워 두는 것을 쓰라.
  2. 의미 토큰 color-text-muted와 color-border-input이 같은 기본 토큰을 가리키는데도 따로 두는 까닭을 이 장의 대비 사례로 설명하라.
  3. 글자색 #767676과 흰 바탕의 대비율이 4.54:1일 때, 이 색을 옅은 회색 면 위의 본문 글자에 그대로 써도 되는지 판단하는 절차를 쓰라.
  4. 생성 중인 「요약 만들기」 버튼을 disabled가 아니라 aria-disabled="true"로 잠그는 까닭을 키보드 사용자의 관점에서 설명하라.
  5. HTML 점검기의 오류가 0건인 프로토타입에 남아 있을 수 있는 접근성 문제를 세 가지 들고, 각각 무엇으로 찾는지 쓰라.
