[6주차] 리버스 엔지니어링과 명세 주도 개발

LLM 서비스 개발

6주차

리버스 엔지니어링과 명세 주도 개발

2027학년도 「LLM 서비스 개발」의 준비 중인 교재입니다. 편집 상태를 검토하기 위해 미리 공개한 것으로, 수업 전에 내용과 순서가 바뀔 수 있습니다.

학사 7주차 · 교재 06 · 2부 조사와 정의

4장에서 시장과 경쟁 서비스를 조사해 가치 제안을 썼고, 5장에서 동료 인터뷰로 페르소나 두 명과 문제 정의 세 개를 얻었다. 조사는 「누구의 어떤 문제를 풀 것인가」를 정하는 일이었다. 이 장은 그 결정을 명세로 고정한다. 명세가 고정되어야 7장 이후의 설계와 구현이 같은 기준을 보고 움직이며, 구현을 맡는 Claude Code도 추측 대신 문장을 읽고 일한다.

이 장에서는 두 방법론을 함께 다룬다. 첫째는 리버스 엔지니어링이다. 이미 있는 서비스의 화면을 관찰해 그 서비스의 명세를 되살리고, 되살린 명세만으로 다시 만들어 원본과 비교한다. 원본과 다시 만든 것이 갈라지는 자리가 명세의 빈틈이다. 둘째는 명세 주도 개발(SDD, Spec-Driven Development)이다. 구현보다 명세를 먼저 쓰고, 그 명세를 AI 구현의 입력이자 결과를 검사하는 기준으로 삼는다. 앞의 일은 「빈틈이 어디에 생기는가」를 몸으로 확인하게 하고, 뒤의 일은 그 경험을 공통 사례의 명세서에 적용하게 한다.

이 장에서 만드는 것은 하나다. 공통 사례 「취업 준비 지원 서비스(jobprep)」의 요구사항 명세서 v1이다. 명세서에는 EARS 문형으로 쓴 요구 문장 15개 이상, 요구마다의 수용 기준, 문제 정의와 요구를 잇는 추적표가 들어가고, 명세에서 끌어낸 프로젝트 규칙 jobprep/CLAUDE.md가 붙는다. 완성한 판에는 Git 태그 spec-v1을 단다. 그 앞에서 공공 채용 게시판 한 화면의 명세를 복원하고 재구현하는 축약 실습으로 빈틈을 찾는 눈을 기른다.

이 명세서는 6장에서 끝나는 문서가 아니다. 7장에서 사용자 흐름과 화면 목록이 더해져 v2가 되고, 8장에서 화면 명세가 붙고, 9~12장의 구현은 이 문서의 요구와 수용 기준을 기준으로 검사되며, 13장의 사용성 평가 결과가 다시 이 문서를 고친다. 같은 학기의 프로젝트실습Ⅰ은 같은 절차를 팀의 주제에 적용한다. 중간시험(8주차) 직전의 장이므로 1~5장에서 다룬 Git, Claude Code, 조사 결과가 모두 이 장의 실습에 쓰인다.

학습 목표

  • 이미 있는 서비스의 화면을 관찰해 명세를 복원하고, 그 명세로 재구현해 빈틈을 찾을 수 있다.
    • 예시: 공공 채용 게시판의 목록 화면에서 정보 항목, 조작, 화면 뒤의 처리를 구조 분석으로 정리하고, 명세만으로 만든 프로그램과 원본의 차이를 「명세 빈틈, 매체 차이, 데이터 한계, 의도한 차이, 범위 밖」으로 분류한다.
    • 활용: 문서가 없는 레거시 시스템의 인수인계, 경쟁 서비스 분석, 외주 결과물의 검수처럼 「완성물에서 출발하는 일」에 같은 절차를 쓴다.
  • 요구를 EARS 다섯 문형으로 쓰고, 모호한 문장을 문형에 맞게 교정할 수 있다.
    • 예시: 「검색이 빠르게 되어야 한다」를 「사용자가 검색어를 입력하고 검색을 누르면, 시스템은 1초 안에 결과 목록을 표시해야 한다」로 고친다.
    • 활용: 기획, 개발, 검사, AI가 같은 문장을 같은 뜻으로 읽게 하는 공통 계약을 쓴다. 시험의 「명세 문장의 작성과 교정」 문항이 이 목표를 본다.
  • 조사 결과(가치 제안, 페르소나, 문제 정의)에서 요구사항 명세서, 수용 기준, 추적표를 만들 수 있다.
    • 예시: 문제 정의 P-01 「흩어진 공고와 마감 시각」에서 기능 F-01~F-03과 요구 REQ-001~REQ-012를 끌어내고, 요구마다 수용 기준 AC를 붙인 뒤 추적표로 잇는다.
    • 활용: 「이 기능은 왜 있는가」라는 질문에 문제 정의의 ID로 답한다. 기능을 뺄 때 어떤 문제가 다시 열리는지 추적표로 본다.
  • 명세 주도 개발의 단계를 Claude Code의 계획 모드로 수행하고, 명세의 판을 Git 태그와 변경 이력으로 관리할 수 있다.
    • 예시: 명세에서 jobprep/CLAUDE.md를 끌어내고, 계획 모드에서 구현 계획을 받아 검토만 한 뒤, 명세서 v1에 태그 spec-v1을 달고 이후의 변경을 git diff spec-v1로 본다.
    • 활용: GitHub Spec Kit, Kiro 같은 명세 주도 도구가 바뀌어도 「명세 → 계획 → 작업 → 구현 → 검사」의 순서와 사람이 검토하는 자리는 그대로 쓴다.

0. 시작하기

실습 서버 접속, 터미널 두 개의 배치, Claude Code 로그인은 부록 A의 절차를 따른다. 이 절은 이 장의 키트를 받고, 앞 장의 산출물과 저장소 상태를 확인한다.

0-1. 키트 받기

키트는 배포 폴더 $KIT_HOME에 있다. 저장소 밖의 ~/kits/에 받아 두고, 필요한 파일만 저장소로 복사한다. 키트 전체를 저장소에 넣으면 교재의 재료와 학습자의 산출물이 섞인다.

서버 터미널 
mkdir -p ~/kits
cp -rn "$KIT_HOME/Service_06주차" ~/kits/
ls ~/kits/Service_06주차
README.md  requirements.txt  tests  기준산출물  도구  복원  양식  연습

mkdir -p ~/kits를 먼저 하는 데는 까닭이 있다. ~/kits가 없는 상태에서 cp -rn "$KIT_HOME/Service_06주차" ~/kits/를 실행하면, cp는 ~/kits라는 이름으로 키트 폴더를 복사해 버린다. 그러면 ~/kits/Service_06주차가 아니라 ~/kits/도구, ~/kits/복원이 생기고, 이 장의 모든 경로가 어긋난다. 집필할 때 실제로 이 일이 일어났다. -n은 이미 있는 파일을 덮어쓰지 않는다는 뜻이므로, 같은 명령을 다시 실행해도 받아 둔 파일은 그대로 남는다.

키트의 구성은 다음과 같다. 학습자가 고쳐 쓰는 파일은 모두 이름이 _양식.md 또는 _원문.md로 끝나며, 원본은 그대로 두고 복사본을 고친다.

  • 도구/: EARS 문형 검사기 ears_check.py (4, 6, 7, 8절)

  • tests/: 검사기의 테스트 (0절)

  • 연습/: EARS 교정 연습의 원문 (4절)

  • 복원/: 채용 게시판 목록 자료 채용.csv, 관찰 기록과 비교표의 양식 (6절)

  • 양식/: 요구사항 명세서, 추적표, CLAUDE.md의 양식 (7~8절)

  • 기준산출물/: 4~5장 산출물이 없는 학습자를 위한 견본 (0절)

  • 확인 1 ls ~/kits/Service_06주차에 도구, 복원, 양식, 연습, 기준산출물, tests가 보인다.

0-2. 검사기 확인

이 장의 실습은 작은 파이썬 프로그램 ears_check.py를 여러 번 쓴다. 명세서의 요구 문장이 EARS 문형의 구조를 따르는지, 요구마다 ID가 있는지, 추적표의 ID가 명세에 실제로 있는지를 점검하는 도구다. 표준 라이브러리만 쓰므로 설치할 것은 없다. 키트에 든 테스트로 도구가 이 서버에서 도는지 먼저 확인한다. 테스트에 쓰는 pytest는 과목 공통의 가상 환경 ~/llm-service-lab/.venv(부록 A)에 설치하고, 그 환경의 파이썬을 경로로 불러 실행한다.

서버 터미널 
cd ~/kits/Service_06주차
~/llm-service-lab/.venv/bin/python -m pip install -q -r requirements.txt
~/llm-service-lab/.venv/bin/python -m pytest -q
...............................s..                                       [100%]
33 passed, 1 skipped in 1.06s

건너뛴 한 개(s)는 교수용 견본이 있어야 도는 테스트이므로 학생용 키트에서는 건너뛰는 것이 정상이다. No such file or directory가 나오면 가상 환경이 아직 없는 것이다. 부록 A의 절차대로 python3 -m venv ~/llm-service-lab/.venv로 만든 뒤 위 명령을 다시 실행한다.

  • 확인 2 ~/llm-service-lab/.venv/bin/python -m pytest -q의 마지막 줄이 33 passed, 1 skipped이다(시간은 달라도 된다).

1. 요구사항과 명세

1-1. 1장의 실험이 남긴 질문

1장에서 같은 앱을 두 번 만들었다. 한 번은 「공고 마감일을 알려 주는 프로그램을 만들어라」 같은 한 줄 요청으로, 한 번은 요구 목록을 붙인 요청으로 만들었다. 한 줄 요청의 결과는 그럴듯하게 돌아갔지만, 날짜 형식이 틀린 행을 만났을 때 멈추거나, 마감이 지난 공고를 그대로 보이거나, 학습자가 생각하지 않은 기능을 덧붙였다. 요청이 정하지 않은 자리를 AI가 스스로 채웠기 때문이다. 요구 목록을 준 쪽은 목록에 적힌 만큼은 맞게 동작했고, 목록에 없는 자리에서만 같은 일이 일어났다.

이 실험에서 끌어낼 수 있는 원리는 둘이다. 첫째, AI는 정보가 비어 있을 때 멈추지 않고 그럴듯한 값으로 채운다. 그러므로 「정하지 않은 것」은 곧 「AI가 정한 것」이 된다. 둘째, 요구 목록이 있으면 결과를 그 목록에 대어 검사할 수 있다. 목록이 없으면 결과가 맞는지 판단할 기준 자체가 없다. 이 장은 이 두 원리를 체계화한다. 정하지 않은 자리를 찾아내는 기술이 리버스 엔지니어링과 EARS이고, 목록을 기준으로 삼아 구현과 검사를 이끄는 방식이 명세 주도 개발이다.

2. 리버스 엔지니어링

2-1. 정의

설계에서 출발해 구현으로 가는 일을 순공학(forward engineering)이라 한다. 리버스 엔지니어링(reverse engineering, 역공학)은 그 반대 방향이다. 소프트웨어공학에서 널리 쓰이는 Chikofsky와 Cross(1990)의 분류는 리버스 엔지니어링을 대상 시스템을 분석해 두 가지를 얻는 과정으로 정의한다. 하나는 시스템의 구성 요소와 그 사이의 관계를 알아내는 것이고, 다른 하나는 시스템을 다른 형태나 더 높은 추상 수준으로 표현하는 것이다[R1]. 이 정의에서 눈여겨볼 점은 리버스 엔지니어링이 대상 시스템을 바꾸지 않는다는 것이다. 관찰하고 표현할 뿐이다.

같은 분류에는 이웃한 용어가 있다. 이 장의 실습이 어느 일에 해당하는지 구분해 둔다.

용어 뜻 (Chikofsky와 Cross의 분류를 이 과목에 맞게 풀어 씀) 이 과목에서의 자리
순공학 요구와 설계에서 구현으로 간다 7~11장의 설계와 구현

①과 ⑥이 사람의 일이라는 점이 중요하다. AI가 구조를 분석하고 명세를 쓰고 재구현까지 할 수 있지만, 「AI가 본 것이 실제 화면과 같은가」와 「차이가 결함인가 의도인가」는 사람이 판단한다. ⑤에서 원본의 정보를 막는 것도 같은 까닭이다. 재구현하는 AI가 원본을 볼 수 있으면 명세의 빈틈을 원본으로 메워 버리고, 빈틈이 드러나지 않는다.

2-4. 가져오는 것과 가져오지 않는 것

리버스 엔지니어링의 대상이 남의 서비스일 때는 경계를 먼저 정한다. 이 과목의 규칙은 다음과 같다.

  • 가져오는 것은 구조와 항목이다. 어떤 정보가 어떤 순서로 있고, 사용자가 무엇을 할 수 있는지를 명세 문장으로 옮긴다.
  • 가져오지 않는 것은 문장, 이미지, 코드다. 공고 원문을 통째로 옮기지 않고, 화면의 그림과 스크립트를 복사해 재구현에 넣지 않는다.
  • 로그인해야 보이는 화면, 개인 정보가 나오는 화면은 대상으로 삼지 않는다.
  • 자동으로 많은 요청을 보내지 않는다. 이 장의 실습은 한 사람이 목록 한 쪽을 몇 번 받아 보는 수준이다.
  • 사이트가 자동 수집 프로그램에 대해 밝혀 둔 규칙(robots.txt)과 이용 약관을 확인한다.

robots.txt는 사이트의 맨 위 경로에 두는 글 파일로, 자동 수집 프로그램(봇)에게 어느 경로를 가져가도 되는지 알린다. 사람이 브라우저로 보는 데는 적용되지 않지만, Claude Code의 웹 읽기 도구처럼 프로그램이 페이지를 가져올 때는 이 규칙을 따르는 경우가 있다. 2026년 2학기판 수업에서는 한 공공기관 사이트가 모든 봇을 막아 두어 AI의 웹 읽기가 거부될 수 있었고, curl로 받은 파일을 대신 읽혔다[R2]. 이 장의 대상 사이트의 규칙을 본다.

서버 터미널 
curl -sL https://www.gjcity.go.kr/robots.txt
User-agent: Googlebot
Disallow:/sys/
Disallow:/saeol/
Disallow:/portal/bbs/list.do?ptIdx=64&mId=0502030000
Disallow:/portal/bbs/list.do?ptIdx=63&mId=0502010000
Disallow:/search/

2026-11-14에 받은 내용이며, 2026-11-16에 다시 받아도 같았다. 이 규칙은 구글의 수집 프로그램에게 관리 경로와 일부 게시판, 검색 경로를 가져가지 말라고 한다. 이 장에서 읽을 채용시험정보 목록(/portal/examInfo/list.do)은 막힌 경로에 없다. 규칙은 사이트가 언제든 바꿀 수 있으므로 수업 당일에 다시 확인한다.

[최신 자료 자리: 대상 사이트의 규칙과 목록의 상태] 경기도 광주시청 누리집의 robots.txt, 채용시험정보 목록의 주소(mId=0202050000), 전체 쪽 수, 상태 값(stateCode 0~3), 표의 열 구성. 확인할 곳: https://www.gjcity.go.kr/robots.txt, https://www.gjcity.go.kr/portal/examInfo/list.do?mId=0202050000. 2026-11-16에 확인한 값: robots.txt는 위와 같음, 전체 76쪽, 접수중 8건, 접수예정 1건. 누리집이 개편되면 주소와 HTML의 이름(td class="num", boardView)이 바뀌어 3절의 명령이 그대로 돌지 않으므로 수업 전에 3절의 명령을 모두 다시 실행한다.

  • 확인 5 robots.txt를 받아 보고, /portal/examInfo/가 Disallow 줄에 없음을 확인하였다.

3. URL을 읽는 방법

명세를 복원하려면 먼저 화면을 읽어야 한다. 웹 화면은 사람에게는 같은 화면으로 보여도, 프로그램에게는 「주소 한 번으로 내용이 다 오는 화면」과 「브라우저가 스크립트를 돌려야 내용이 생기는 화면」으로 나뉜다. 어느 쪽인지에 따라 AI에게 근거를 주는 방법이 달라진다. 이 절은 6절의 대상인 경기도 광주시청 누리집의 「채용시험정보」 목록으로 그 차이를 확인한다[D1].

3-1. URL의 구조

브라우저 
https://www.gjcity.go.kr/portal/examInfo/list.do?mId=0202050000

브라우저로 이 주소를 열면 표가 하나 보인다. 열은 번호, 제목, 모집기관, 상태, 접수기간, 조회수, 등록일이고, 표 위에 상태를 고르는 상자와 검색이 있으며, 표 아래에 쪽 번호가 있다.

[그림 자리: 채용시험정보 목록 화면] 목록 첫 쪽 전체 캡처에 세 곳을 번호로 표시한다. ① 표 위의 상태 상자와 검색 영역, ② 표의 일곱 열, ③ 표 아래의 쪽 번호. 주소 표시줄의 list.do?mId=0202050000이 보이게 찍는다. 찍을 곳: 브라우저, 위 주소, 수업 직전. 이 주소를 부분으로 나누면 다음과 같다.

부분 값 뜻
스킴 https 암호화된 HTTP로 주고받는다
호스트 www.gjcity.go.kr 요청을 받는 서버의 이름
경로 /portal/examInfo/list.do 서버 안에서 어떤 화면(프로그램)을 부르는지. list.do는 목록 화면이다
질의 문자열 ?mId=0202050000 화면에 넘기는 값. 이름=값을 &로 잇는다. 여기서는 메뉴 번호

질의 문자열은 화면의 상태를 주소에 담는다. 같은 경로에 다른 값을 넘기면 다른 화면이 온다. 3-3에서 상태를 고르는 값을 직접 붙여 본다. 주소가 화면의 상태를 얼마나 담는지가 「URL로 읽히는 서비스인가」를 가르는 첫 번째 기준이다.

먼저 서버가 무엇을 돌려주는지 본다. -o /dev/null은 본문을 버리고, -w는 응답의 상태 코드와 형식을 출력하게 한다.

서버 터미널 
curl -s -o /dev/null -w "%{http_code} %{content_type}\n" "https://www.gjcity.go.kr/portal/examInfo/list.do?mId=0202050000"
200 text/html;charset=UTF-8

200은 요청이 성공했다는 상태 코드이고, text/html;charset=UTF-8은 본문이 UTF-8로 인코딩된 HTML이라는 뜻이다. 오래된 공공 사이트 가운데는 EUC-KR로 된 곳도 있으며, 그때 받은 파일은 한국어가 깨져 보인다. 그런 경우 iconv -f euc-kr -t utf-8 페이지.html > 페이지_utf8.html로 바꾼 뒤 읽힌다.

출력 뜻 할 일
200 text/html;charset=UTF-8 정상이다 다음 단계로 간다
000 응답을 받지 못했다. 서버에서 바깥 인터넷으로 나가지 못하거나 주소가 틀렸다 curl -sI https://www.google.com으로 바깥 연결을 먼저 본다. 바깥 연결이 안 되면 교수에게 알리고 키트의 채용.csv만으로 6절을 한다
200인데 3-2의 grep -c가 0이다 이 누리집은 없는 경로에도 200과 안내 화면을 돌려준다(2026-11-16, /portal/examInfo/nolist.do로 시험함). 상태 코드만으로는 경로가 맞는지 알 수 없다 브라우저로 같은 메뉴를 찾아 주소를 다시 확인한다. 누리집이 개편되었을 수 있다
301, 302 다른 주소로 옮기라는 응답이다 -L을 붙여 따라가게 하고, 마지막 주소를 기록한다
  • 확인 6 상태 코드 200과 text/html이 출력된다.

3-2. 서버가 그린 표와 브라우저가 그린 화면

웹 화면이 만들어지는 방식은 크게 둘이다. 서버 렌더링은 서버가 표의 행까지 채운 HTML을 보내는 방식이고, 클라이언트 렌더링은 서버가 빈 틀과 스크립트를 보내면 브라우저가 스크립트를 돌려 자료를 받아 화면을 채우는 방식이다. 앞의 방식이면 curl로 받은 HTML 안에 표의 내용이 그대로 들어 있고, 뒤의 방식이면 빈 틀만 있다. 2026년 2학기판의 지도 앱 예제는 뒤의 경우였다. 주소를 읽으면 빈 껍데기만 오고, 가게 목록과 거리는 사람이 눌러야 나타났다[R2].

채용시험정보 목록이 어느 쪽인지 확인한다. 받은 파일은 6절에서 다시 쓰므로 실습 폴더에 저장한다.

서버 터미널 
mkdir -p ~/llm-service-lab/ch06/복원
cd ~/llm-service-lab/ch06/복원
curl -sL "https://www.gjcity.go.kr/portal/examInfo/list.do?mId=0202050000" > 페이지.html
grep -c '<td class="num">' 페이지.html
grep -o '전체 페이지 [0-9]*' 페이지.html
10
전체 페이지 76

번호 칸(<td class="num">)이 10개 있으므로 표의 10행이 HTML에 이미 들어 있다. 서버 렌더링이다. 이런 화면은 Claude Code의 웹 읽기로도, curl로 받은 파일로도 근거를 만들 수 있다. 전체 쪽 수는 받은 날에 따라 다르다(2026-11-14에 76쪽).

  • 확인 7 grep -c가 10을 출력하고, 전체 페이지 뒤에 쪽 수가 보인다.

3-3. 질의 문자열로 화면 상태를 바꾸기

표 위의 상태 상자가 어떤 값을 보내는지 HTML에서 찾는다.

서버 터미널 
grep -o '<option value="[0-9]">[^<]*' 페이지.html
<option value="0">접수예정
<option value="1">접수중
<option value="2">마감
<option value="3">결과공고

상자의 이름(name="stateCode")과 값을 알았으니 주소에 직접 붙여 본다. 「접수중」은 stateCode=1이다.

서버 터미널 
curl -s "https://www.gjcity.go.kr/portal/examInfo/list.do?mId=0202050000&stateCode=1" | grep -c '<td class="num">'
curl -s "https://www.gjcity.go.kr/portal/examInfo/list.do?mId=0202050000&stateCode=1" | grep -o 'test_ing">[^<]*' | sort | uniq -c
8
      8 test_ing">접수중

행의 수가 바뀌고, 모든 행의 상태가 접수중이다(숫자는 받은 날에 따라 다르다). 상태 거르기는 서버가 하는 처리이며, 주소로 그 상태를 재현할 수 있다는 뜻이다. 이렇게 확인한 사실은 구조 분석에서 「추측」이 아니라 「확인」으로 적는다. 같은 방법으로 화면에서는 쉽게 볼 수 없는 경우도 확인할 수 있다. 6절의 비교에서 이 방법을 다시 쓴다.

  • 확인 8 stateCode=1을 붙인 요청의 행 수가 3-2의 10과 다르고, 모든 행이 「접수중」이다.

3-4. 양식 제출과 자바스크립트 링크

주소로 모든 화면이 열리는 것은 아니다. 표의 제목을 누르면 상세 화면이 열리는데, 그 링크를 HTML에서 보면 다음과 같다.

서버 터미널 
grep -o 'onclick="boardView([^)]*)' 페이지.html | head -3
grep -o 'form id="listForm"[^>]*' 페이지.html
onclick="boardView('1','1496')
onclick="boardView('1','1495')
onclick="boardView('1','1494')
form id="listForm" name="listForm" action="/portal/examInfo/list.do?mId=0202050000" method="post"

제목의 링크 주소는 #이고, 누르면 boardView라는 스크립트 함수가 돌아 숨은 양식에 글 번호를 넣고 POST 방식으로 제출한다. POST는 값을 주소가 아니라 요청 본문에 실어 보내므로, 상세 화면은 주소 하나로 열리지 않는다. 주소만 받아 읽는 AI는 목록까지는 읽지만 상세 화면의 내용은 읽지 못한다. 이 장의 복원 범위를 목록 화면 하나로 못 박는 까닭이다. 상세 화면의 내용을 명세에 넣으면 근거 없이 지어낸 문장이 된다.

조작 방식 주소로 재현되는가 구조 분석에서의 처리
목록 보기 GET, 서버 렌더링 된다 확인
상태 고르기 양식은 POST이나 주소의 질의 문자열도 받는다 된다(stateCode) 확인
쪽 이동 스크립트가 양식의 page 값을 바꾸어 제출 질의 문자열로 시험할 수 있다 확인 또는 추측
상세 보기 스크립트 함수 boardView가 POST로 제출 안 된다 범위 밖, 「알 수 없는 것」에 적는다
  • 확인 9 boardView가 든 링크와 method="post"인 양식을 찾았고, 상세 화면이 주소 하나로 열리지 않는 까닭을 말할 수 있다.

3-5. 읽히지 않는 화면의 처리

주소로 읽히지 않는 화면을 만나면 근거를 만드는 다른 방법을 쓴다. 근거가 바뀌어도 그 뒤의 단계(구조 분석 → 기능 목록 → 명세 → 재구현 → 비교)는 같다.

방법 언제 쓰나 장점 한계
① Claude Code의 웹 읽기(WebFetch) 서버 렌더링이고 봇을 막지 않을 때 프롬프트에 주소만 붙이면 된다 페이지를 마크다운으로 바꾼 뒤 별도의 모델 호출로 필요한 부분만 뽑아 넘긴다. 세부가 빠질 수 있다. 스크립트가 그리는 내용은 오지 않는다
② curl로 받은 HTML 웹 읽기가 거부되거나 원문 HTML이 필요할 때 표의 구조, 양식의 이름과 값까지 그대로 있다 스크립트가 그리는 내용은 역시 없다. 파일이 크다
③ 화면 캡처 스크립트가 그리는 화면, 배치와 색을 보아야 할 때 Claude Code에 이미지로 넣어 읽힐 수 있다 그 순간 보인 것까지만 근거가 된다. 값과 규칙은 없다
④ 사람의 관찰 기록 눌러야 바뀌는 흐름, 쓰면서 느끼는 불편 사용 맥락이 담긴다 사람마다 다르고, 빠뜨리고, 해석이 섞인다
⑤ 화면을 조작하는 AI 여러 화면을 눌러 가며 관찰해야 할 때 조작 기록과 캡처를 함께 남긴다 도구와 계정이 필요하다. 이 과목의 실습 환경에는 없다(2026년판 예제 C는 교수 시연이었다)

①에 대해 Claude Code 공식 문서는 웹 읽기 도구가 설계상 손실이 있는(lossy) 방식이라고 밝히고, 가공하지 않은 페이지가 필요하면 셸에서 curl을 쓰라고 안내한다[S7]. 기본 권한 모드에서 웹 읽기는 가져오기 전에 허락을 묻는다. 「Yes」는 이번 한 번만 허락하므로 같은 도메인이라도 다음에 다시 묻고, 「Yes, and don’t ask again for 도메인」은 그 도메인을 저장소의 .claude/settings.local.json에 허용 규칙으로 저장한다(2026-11 기준)[S7]. 수업에서는 이번 한 번만 허락하는 쪽을 고른다.

③의 경우 Claude Code는 이미지를 대화에 넣는 방법으로 끌어다 놓기, 붙여넣기, 이미지 파일 경로를 주는 방법을 공식 문서에 적고 있다[S4]. 실습 서버에서는 경로를 주는 방법이 가장 간단하다. 내 PC에서 찍은 캡처를 VS Code의 탐색기로 서버의 실습 폴더에 끌어다 놓은 뒤, 프롬프트에 「캡처/목록.png의 화면을 분석하라」처럼 경로를 적는다.

어느 방법을 쓰든 공통으로 지킬 것이 있다. 근거의 종류와 날짜를 구조 분석의 맨 위에 적고, 근거에서 직접 본 것과 추론한 것을 구분해 「확인」과 「추측」으로 표시한다. 같은 주소라도 날이 바뀌면 공고가 바뀌므로, 관찰한 날짜가 없는 명세는 나중에 비교할 수 없다.

4. EARS 문형

4-1. 자연어 요구의 문제

요구를 자유로운 문장으로 쓰면 세 가지 문제가 되풀이된다.

  • 모호성. 「잘」, 「적절히」, 「빠르게」, 「필요 시」처럼 확인할 수 없는 말이 들어간다. 「빠르게」가 0.5초인지 5초인지는 쓴 사람만 안다.
  • 불완전성. 정상적인 흐름만 적고 잘못된 입력, 자료가 없을 때, 기다리는 동안의 일을 빠뜨린다. 2026년 2학기판 수업에서 학생들이 AI로 뽑은 명세는 대부분 「원치 않는 동작」이 비어 있었다[R2].
  • 해석의 갈림. 같은 문장을 기획자, 개발자, 검사자, AI가 서로 다르게 읽는다. 「공고를 상태별로 보여야 한다」는 상태별 탭으로도, 상태 열로도, 상태 순 정렬로도 읽힌다.

이 세 문제는 AI가 구현을 맡을 때 더 커진다. 사람 개발자는 모호한 문장 앞에서 묻지만, AI는 대개 묻지 않고 하나를 골라 구현한다. 어느 쪽을 골랐는지는 결과를 보기 전까지 모른다.

4-2. EARS의 기원과 원리

EARS(Easy Approach to Requirements Syntax)는 요구 문장을 몇 가지 정해진 틀에만 맞추어 쓰게 하는 작성법이다. 롤스로이스의 Alistair Mavin과 동료들이 항공기 엔진 제어 시스템의 감항 규정을 분석하면서 만들었고, 2009년 미국 애틀랜타에서 열린 제17회 IEEE 국제 요구공학 학술대회(RE’09)에서 발표하였다[S3, S3a]. 논문은 자연어 요구에서 흔히 나타나는 여덟 가지 문제(모호성, 막연함 등)를 겨냥한 소수의 구조 규칙을 제안하고, 그 규칙을 따르면 모든 자연어 요구가 다섯 가지 단순한 틀 가운데 하나에 들어간다고 보였다. 감항 규정에서 뽑은 엔진 제어 요구에 적용한 사례 연구에서 일반적인 서술식 명세보다 질과 양 모두에서 나아졌다고 보고하였다[S3a].

EARS의 원리는 두 가지로 요약된다.

  1. 절의 순서를 고정한다. 요구 문장은 「전제 조건 → 트리거 → 시스템 이름 → 시스템의 응답」의 순서로 쓴다. 전제 조건은 없거나 여럿일 수 있고, 트리거는 없거나 하나이며, 시스템 이름은 정확히 하나, 응답은 하나 이상이다[S3].
  2. 키워드로 문형을 드러낸다. 조건이 상태인지 사건인지 선택 기능인지 원치 않는 상황인지를 키워드(While, When, Where, If … then)가 알린다. 키워드만 보아도 그 문장이 언제 적용되는지 알 수 있다.

EARS는 특별한 도구나 긴 교육 없이 쓸 수 있고, 영어가 모국어가 아닌 작성자에게도 도움이 된다고 저자는 밝힌다[S3]. 2025년부터는 AWS의 명세 주도 개발 도구 Kiro가 요구 문서(requirements.md)를 EARS 꼴로 쓰고 있다[S6].

4-3. 다섯 문형과 복합 문형

영어 원형은 Mavin의 공개 자료를 따르고[S3], 한국어 문형은 이 과목의 약속이다. 한국어는 동사가 문장 끝에 오므로 영어의 「the system shall」을 「시스템은 ~해야 한다」로 문장 끝에 둔다.

Mavin의 자료에 실린 예를 하나씩 우리말로 옮겨 보면 문형의 차이가 드러난다. 「휴대전화는 무게가 XX그램 미만이어야 한다」는 상시, 「『음소거』가 선택되면 노트북은 모든 소리 출력을 막아야 한다」는 사건, 「ATM에 카드가 없는 동안 ATM은 『카드를 넣어 시작한다』를 표시해야 한다」는 상태, 「차에 선루프가 있는 경우 차는 운전석 문에 선루프 조작판을 두어야 한다」는 선택, 「잘못된 카드 번호가 입력되면 웹사이트는 『카드 정보를 다시 입력한다』를 표시해야 한다」는 원치 않는 동작이다[S3].

같은 화면에 다섯 문형을 적용하면 다음과 같다. 대상은 3절에서 읽은 채용 공고 목록이다.

[상시] 시스템은 공고 목록을 번호의 내림차순으로 한 쪽에 10행씩 표시해야 한다.
[사건] 사용자가 상태를 고르고 검색을 실행하면, 시스템은 그 상태의 공고만 표시해야 한다.
[상태] 공고가 결과공고 상태인 동안, 시스템은 접수기간 칸에 「-」를 표시해야 한다.
[선택] 관심 공고 기능이 포함된 경우, 시스템은 각 행에 관심 표시 단추를 두어야 한다.
[원치 않는 동작] 만약 조건에 맞는 공고가 없으면, 시스템은 「검색 결과가 없다」는 안내를 표시해야 한다.
[복합] 공고가 접수중 상태인 동안 사용자가 그 공고를 고르면, 시스템은 접수 마감일까지 남은 날을 표시해야 한다.

4-4. 한국어로 쓸 때의 규칙

한국어 EARS는 표준이 따로 없다. 이 과목은 다음 규칙을 약속으로 정하고, 검사기 ears_check.py도 이 규칙으로 판정한다.

  1. 주체는 하나다. 응답 절의 주체를 「시스템은」으로 쓴다. 서비스 이름을 주체로 쓰려면 명세서의 문서 정보에 그 이름을 밝히고, 검사기에 --system 이름을 준다.
  2. 응답은 「~야 한다」로 끝난다. 「표시해야 한다」, 「보여야 한다」, 「두지 않아야 한다」처럼 의무를 나타내는 꼴이다. 「표시한다」, 「보여 준다」는 서술이지 요구가 아니다.
  3. 한 문장에 응답 하나. 「저장해야 하고 알림을 보내야 한다」는 두 요구다. 문장을 나누고 ID를 따로 붙인다. 응답 하나가 여러 동작을 묶는 「진행 표시를 보이고 단추를 비활성 상태로 두어야 한다」는 허용하되, 따로 검사할 필요가 있으면 나눈다.
  4. 조건절은 키워드로 끝난다. 사건은 「~하면」이나 「~할 때」, 상태는 「~인 동안」, 선택은 「~이 포함된 경우」, 원치 않는 동작은 「만약 ~하면」이다. 조건절 끝에 쉼표를 찍고 응답 절을 잇는다.
  5. 선택과 사건을 섞지 않는다. 「~하는 경우」는 이 과목에서 선택 기능에만 쓴다. 사용자의 동작에는 「~하면」을 쓴다.
  6. 원치 않는 동작은 「만약」으로 시작한다. 정상 흐름의 사건과 구분하기 위해서다. 「그러면 시스템은」처럼 영어의 then을 살려도 된다.
  7. 확인할 수 없는 말을 쓰지 않는다. 「잘, 적절히, 빠르게, 충분히, 가능하면, 필요 시, 편리하게, 쉽게, 직관적, 효율적, 등」은 수치나 관찰 가능한 결과로 바꾼다.

4-6. 흔한 잘못

잘못된 문장 무엇이 문제인가 고친 문장
공고를 잘 보여 준다. 주체 없음, 응답이 의무가 아님, 「잘」 시스템은 공고 목록의 각 행에 제목, 모집기관, 상태, 접수 마감일을 표시해야 한다.
상태 필터가 있어야 한다. 장치의 존재만 있고 동작이 없음 사용자가 상태를 고르면, 시스템은 그 상태의 공고만 표시해야 한다.
사용자는 관심 공고를 저장할 수 있어야 한다. 주체가 사용자. 시스템이 할 일이 아님 사용자가 관심 표시를 누르면, 시스템은 그 공고를 관심 공고 목록에 추가해야 한다.
오류가 나면 알린다. 어떤 오류인지, 무엇을 알리는지 없음 만약 공고 자료 파일을 읽지 못하면, 시스템은 「공고 자료를 불러오지 못했다」는 안내를 표시해야 한다.
검색 결과가 많으면 쪽을 나눈다. 「많으면」의 기준 없음 시스템은 검색 결과를 한 쪽에 10행씩 나누어 표시해야 한다.
마감 임박 공고는 강조해야 한다. 「임박」과 「강조」의 기준 없음 접수 마감일까지 남은 날이 3일 이하인 동안, 시스템은 그 공고 행에 「마감 임박」 표시를 붙여야 한다.
시스템은 localStorage에 JSON으로 저장해야 한다. 구현 방법을 정함 시스템은 관심 공고를 브라우저 저장소에 저장해 페이지를 다시 열어도 유지해야 한다.

마지막 행은 경계가 애매한 경우다. 「브라우저 저장소」도 넓은 의미에서 구현에 가까운 말이다. 이 과목은 「서버 없이 브라우저에서만 도는 서비스」라는 제약이 9장의 범위에서 정해져 있으므로 명세에 남겨 두고, 저장 형식(JSON)과 저장소의 종류(localStorage)는 계획 단계로 미룬다.

메시지 원인 고치는 법
응답이 「~야 한다」(shall)로 끝나지 않는다 「표시한다」, 「보여 준다」처럼 서술로 끝났다 「표시해야 한다」로 고친다
문형을 알 수 없다: 주체가 없다(…) 「목록이 정렬되어야 한다」처럼 「시스템은」이 없다 「시스템은 목록을 정렬해 표시해야 한다」
문형을 알 수 없다: 조건절 「사용자가 검색을 누르고」이 문형의 키워드(…)로 끝나지 않는다 조건절이 「~하고」, 「~해서」로 끝났다 「사용자가 검색을 누르면,」처럼 키워드로 끝내고 쉼표를 찍는다
라벨은 [사건]인데 문장 구조는 [상시]이다 「시스템은」이 조건보다 앞에 왔다(「시스템은 사용자가 상태를 고르면 …」) 「조건절, 시스템은 …」의 순서로 바꾼다
모르는 라벨 [이벤트] 라벨에 이 과목의 문형 이름이 아닌 말을 썼다 상시, 사건, 상태, 선택, 원치 않는 동작, 복합 가운데 하나로 쓴다
한 문장에 요구가 둘 이상이다… 「~해야 하고 ~해야 한다」 문장을 나누고 새 ID를 붙인다
ID가 겹친다(7행과 8행) 같은 ID를 두 번 썼다 뒤의 것에 새 ID를 붙인다. 앞의 ID는 바꾸지 않는다
ID가 없는 요구 문장이다 목록 줄에 「~야 한다」가 있는데 ID가 없다 ID를 붙이거나, 설명이면 목록 기호를 뺀다
문형 라벨이 없다(문장 구조는 상시) 경고. 라벨을 붙이지 않았다 괄호 안의 문형이 의도와 같으면 그 라벨을 붙인다
확인할 수 없는 말이 있다: 「잘」 경고. 모호한 말이 있다 수치나 관찰할 수 있는 결과로 바꾼다
파일이 없다: … 경로가 틀렸다(종료 코드 2) ls로 경로를 확인한다

VS Code에서 ch06/연습/교정연습.md를 열어 손으로 고친다. 처음 다섯 문장(REQ-01~05)은 Claude Code를 쓰지 않는다. 문형을 고르는 판단을 직접 해 보는 것이 이 연습의 목적이다. 고칠 때는 다음을 지킨다.

  • 문장 앞에 라벨을 붙인다. 예: - **REQ-01** [상시] 시스템은 ...해야 한다.
  • 원문이 정하지 않은 값(시간, 개수, 날짜)을 정했으면 그 값을 문장 뒤의 괄호에 적는다. 예: (근거: 1초는 내가 정한 값). 검사기는 문장 끝의 (근거: ...), (관찰: ...), (추측: ...)과 ← 고침, ← 추가 표시를 무시한다.
  • 한 문장에 요구가 둘이면 새 ID(REQ-10)를 만들어 나눈다.
  • ID가 없는 마지막 문장에는 ID를 붙인다.

REQ-06~09는 Claude Code에 맡겨 비교해도 된다. 맡길 때는 고칠 문장과 규칙을 함께 준다.

  • 확인 11 고친 교정연습.md에서 검사기가 오류 0건을 출력하고 종료 코드가 0이다.

4-8. 검사기가 보는 것과 보지 못하는 것

검사기는 문장의 꼴을 본다. 문장의 뜻은 보지 못한다. 다음은 모두 검사기를 통과하지만 좋은 요구가 아니다.

- **REQ-01** [상시] 시스템은 사용자를 만족시켜야 한다.
- **REQ-02** [사건] 사용자가 무엇이든 하면, 시스템은 올바르게 반응해야 한다.
- **REQ-03** [상태] 시스템이 동작하는 동안, 시스템은 오류가 없어야 한다.

REQ-01은 관찰할 수 있는 결과가 없고, REQ-02의 「올바르게」와 「무엇이든」은 확인할 수 없으며, REQ-03은 검사할 방법이 없다. 검사기의 모호한 말 목록은 예시일 뿐이므로 이런 말을 다 잡지 못한다. 그래서 7절에서는 요구마다 수용 기준을 붙인다. 수용 기준을 쓸 수 없는 요구는 아직 요구가 아니다.

검사기는 사람의 검토를 대신하지 않는다. 검사기의 몫은 기계적인 실수(ID 빠짐, 문형과 라벨의 불일치, 추적표의 끊긴 고리)를 사람이 보기 전에 걸러 내는 것이다. 이 역할 분담은 9장의 자동 검사와 「AI에이전트 기획 및 개발」의 테스트로 이어진다.

5. 명세 주도 개발

5-1. 정의

명세 주도 개발(SDD)은 구현보다 명세를 먼저 쓰고, 명세를 AI 구현의 입력이자 결과를 검사하는 기준으로 삼는 개발 방식이다. GitHub는 2025년 9월 오픈소스 도구 Spec Kit을 공개하면서, 이 방식을 「코드가 진실의 원천」인 상태에서 「의도가 진실의 원천」인 상태로 옮겨 가는 일로 설명하였다[S1]. 같은 글은 AI 코딩 에이전트가 모호한 지시를 받으면 그럴듯하지만 의도에서 벗어난 코드를 낸다고 진단하고, 명세를 한 번 쓰고 버리는 문서가 아니라 생성, 검사, 검증을 이끄는 「살아 있는 산출물」로 다루자고 한다[S1].

1장에서 본 「바이브 코딩」과 견주면 차이가 분명하다.

관점 바이브 코딩 명세 주도 개발
출발점 한 줄 요청 명세(요구, 수용 기준)
정하지 않은 자리 AI가 그때그때 채운다. 요청할 때마다 결과가 달라진다 명세가 정한다. 정하지 않은 자리는 질문 목록으로 돌아온다
결과의 판정 「돌아가는가」 「명세의 수용 기준을 충족하는가」
변경 코드를 고친다 명세를 고치고 다시 구현한다. 변경 이력이 명세에 남는다
사람의 일 결과를 보고 다시 요청한다 명세를 쓰고, 단계마다 AI의 산출물을 검토한다
다시 만들기 같은 결과가 나오지 않는다 명세가 같으면 같은 기능이 나온다(모양은 다를 수 있다)

사람의 일이 사라지는 것이 아니다. GitHub의 글은 단계마다 사람이 「명세가 의도를 담았는가, 계획이 현실의 제약을 지키는가, AI가 빠뜨린 경계 사례가 없는가」를 확인해야 한다고 강조한다. 산출물은 AI가 만들고 그것이 맞는지는 사람이 확인한다는 것이다[S1]. 이 과목에서 학습자가 맡는 일이 바로 그 확인이다.

5-2. GitHub Spec Kit의 단계

Spec Kit은 명세 주도 개발의 단계를 코딩 에이전트 안에서 실행하는 명령(에이전트 스킬)으로 제공한다. 2026-11-14에 확인한 최신판은 v1.4.0(2026-11-10 공개)이다. 처음 공개될 때는 명세, 계획, 작업, 구현의 네 단계였고[S1], 지금은 구현 뒤에 「수렴(converge)」 단계와 선택적인 품질 관문 세 개가 더해졌다[S2, S2a].

단계 명령(Claude Code에서) 하는 일 주요 산출물
원칙 /speckit-constitution 프로젝트의 원칙을 정한다. 이후 모든 단계가 이 원칙에 비추어 평가된다. 프로젝트마다 한 번 .specify/memory/constitution.md
명세 /speckit-specify 무엇을 왜 만드는지 쓴다. 기술 스택은 쓰지 않는다 specs/001-기능이름/spec.md, checklists/requirements.md
명확화(선택) /speckit-clarify 명세의 모호한 곳에 대해 최대 다섯 개의 질문을 하고 답을 명세에 반영한다 spec.md 갱신
계획 /speckit-plan 기술 스택과 구조를 받아 설계 산출물을 만든다. 명세의 모호한 곳을 먼저 조사로 푼다 plan.md, research.md, data-model.md 등
점검표(선택) /speckit-checklist 명세가 완전하고 일관된지 보는 점검표를 만든다. 「요구사항의 단위 테스트」 점검표 파일
작업 /speckit-tasks 계획을 의존 순서대로 작업 목록으로 나눈다 tasks.md
분석(선택) /speckit-analyze 명세, 계획, 작업 사이의 충돌과 빈틈을 읽기 전용으로 보고한다 보고(파일을 고치지 않는다)
구현 /speckit-implement 작업 목록을 순서대로 실행한다 코드
수렴 /speckit-converge 코드를 명세, 계획, 작업과 대조해 빈틈이 있으면 작업을 덧붙인다. 「수렴됨」이 나올 때까지 구현과 수렴을 되풀이한다 tasks.md 갱신

[최신 자료 자리: Spec Kit의 판과 명령 이름] 최신판 번호, 단계의 수와 이름, Claude Code에서 부르는 명령의 꼴(/speckit-specify와 /speckit.specify), 설치 명령(uv tool install specify-cli, specify init … --integration claude). 확인할 곳: https://github.com/github/spec-kit/releases, https://github.github.com/spec-kit/. 2026-11-14에 확인한 값: v1.4.0(2026-11-10), 위 표의 아홉 단계, 하이픈 꼴. 판이 자주 오르므로 수업 전에 다시 확인한다.

문서는 짧은 경로(명세 → 계획 → 작업 → 구현 → 수렴)와 품질 관문을 넣은 긴 경로를 구분하고, 원칙은 어느 경로든 처음에 한 번 정하라고 한다[S2a]. Claude Code에 설치하면 각 명령이 .claude/skills/speckit-<명령>/SKILL.md 꼴의 스킬로 들어가고, 대화창에서 /speckit-specify처럼 부른다[S2b]. 명령의 이름은 판에 따라 바뀌어 왔다. 초기 문서와 일부 에이전트용 문서는 /speckit.specify처럼 점을 쓴다[S2c]. 도구의 이름은 바뀌어도 단계의 순서는 같다는 점이 이 과목에서 Spec Kit을 다루는 까닭이다.

Spec Kit의 명세 양식(spec-template.md)을 보면 명세가 무엇을 담아야 하는지에 대한 한 가지 답이 보인다[S2d].

  • 사용자 시나리오와 검사: 우선순위(P1, P2…)를 붙인 사용자 이야기, 각 이야기를 따로 검사하는 방법, 「Given … When … Then …」 꼴의 수용 시나리오. 이 장에서는 문제 정의(5장)와 수용 기준(7-5)이 맡는다.
  • 경계 사례: 경계 조건과 오류 상황에서 무슨 일이 일어나는가. 이 장에서는 원치 않는 동작 문형이 맡는다.
  • 기능 요구: FR-001 꼴의 ID와 「System MUST …」 문장. 모호한 곳은 [NEEDS CLARIFICATION: ...]으로 표시한다. 이 장에서는 EARS 요구 문장과 열린 질문(7-8)이 맡는다.
  • 핵심 개체: 다루는 자료와 그 관계(구현 없이). 이 장에서는 명세서의 「용어」(공고, 상태, 관심 공고)가 맡는다.
  • 성공 기준: 기술에 중립적이고 측정할 수 있는 결과. 이 장에서는 가치 제안의 기대 이익이 맡고, 13장의 평가에서 잰다.

Spec Kit의 기능 요구는 「System MUST」라는 한 가지 꼴만 쓰고, EARS처럼 조건의 종류를 문형으로 나누지 않는다. 대신 「NEEDS CLARIFICATION」 표시로 모호한 곳을 드러내게 한다. 이 장은 둘을 합쳐, 요구 문장은 EARS로 쓰고 모호한 곳은 「열린 질문」 표로 모은다.

5-3. Kiro의 명세

AWS의 Kiro도 명세 주도 개발을 도구로 제공한다. 기능 명세 하나는 세 파일로 이루어진다. requirements.md(사용자 이야기와 요구), design.md(기술 구조, 순서도, 오류 처리와 검사 전략), tasks.md(추적할 수 있는 구현 작업)이다. 요구는 「WHEN [조건/사건] THE SYSTEM SHALL [기대 동작]」 꼴의 EARS로 쓰고, 이렇게 쓰면 요구가 명확하고 검사할 수 있고 추적할 수 있다고 설명한다[S6]. 요구에서 출발하는 경로(요구 → 설계 → 작업)와 설계에서 출발하는 경로(설계 → 요구 → 작업)를 고를 수 있다는 점도 눈여겨볼 만하다. 앞의 것은 새로 만드는 제품에, 뒤의 것은 성능 같은 비기능 제약이 강한 일에 맞는다고 한다[S6].

Spec Kit과 Kiro는 이름과 파일이 다르지만 공통 구조가 있다. 무엇(명세) → 어떻게(계획, 설계) → 작업 → 구현 → 대조의 순서이고, 각 단계의 산출물이 마크다운 파일이며, 단계 사이에 사람이 검토한다. 이 과목은 특정 도구를 설치하지 않고, Claude Code의 기본 기능인 계획 모드와 마크다운 파일로 같은 순서를 밟는다.

5-4. Claude Code의 계획 모드

계획 모드(plan mode)는 Claude Code가 조사하고 계획을 제안하되 소스 파일을 고치지 않는 권한 모드다. Claude는 파일을 읽고, 탐색용 셸 명령을 돌리고, 계획을 쓰지만, 사람이 계획을 승인하기 전에는 편집하지 않는다[S5]. 2장에서 처음 써 보았으며, 이 장에서는 명세 주도 개발의 「계획」 단계를 맡긴다.

들어가고 나오는 방법은 다음과 같다(2026-11 기준, Claude Code 2.1.296에서 확인)[S4, S5].

[최신 자료 자리: Claude Code의 계획 모드 조작] 권한 모드의 순환 순서와 단축키(Shift+Tab, Ctrl+G), 상태 표시줄 문구(⏸ plan mode on), 계획 승인 질문의 선택지 이름, claude --permission-mode plan, /plan. 확인할 곳: https://code.claude.com/docs/en/permission-modes, claude --help. 2026-11-14에 Claude Code 2.1.296으로 확인한 값이 아래 표이다. 수업용 서버의 판으로 다시 확인한다.

  • Yes, and use auto mode(자동 모드를 쓸 수 없으면 Yes, auto-accept edits): 계획을 승인하고 편집을 자동으로 받아들이는 모드로 넘어간다. 이 장에서는 쓰지 않는다.
  • Yes, manually approve edits: 계획을 승인하고 편집을 하나씩 확인한다. 파일을 저장하게 할 때 쓴다.
  • No, keep planning: 계획 모드에 머물며 무엇을 바꿀지 말한다. 계획을 검토만 할 때 쓴다.

계획 모드의 쓰임은 「파일이 바뀌면 안 되는 분석 단계」를 보호하는 것이다. 6절의 구조 분석과 7절의 기능 도출은 남의 서비스와 자기 조사 결과를 읽기만 하는 단계이므로 계획 모드에서 한다. 저장은 계획 모드를 나온 뒤에 따로 시킨다. 이렇게 단계를 나누면, 분석 결과를 읽고 고칠 기회가 저장 전에 한 번 생긴다. 한 번만 계획을 받고 싶으면 「/plan ch05/문제정의.md를 읽고 문제마다 필요한 기능을 두세 개씩 제안하라」처럼 프롬프트 앞에 /plan을 붙인다.

상태 표시줄을 보고 계획 모드인지 확인하는 습관을 들인다. 승인 질문에서 무심코 Enter를 누르면 첫 선택지가 골라질 수 있다. 계획 모드에서 받은 계획은 세션 동안 ~/.claude/plans/ 아래에 파일로 남는다(설정 plansDirectory로 바꿀 수 있다)[S5].

[그림 자리: 계획 모드의 상태 표시줄과 승인 질문] 두 장을 나란히 둔다. 왼쪽은 입력 창 아래 상태 표시줄의 ⏸ plan mode on, 오른쪽은 계획이 준비된 뒤의 승인 질문(Yes, manually approve edits / No, keep planning 등). 찍을 곳: 실습 서버의 Claude Code, 6-3의 프롬프트를 보낸 화면. 선택지 이름은 판에 따라 다르므로 수업 직전의 판으로 찍는다.

6-5. 명세 읽기

AI가 쓴 명세를 한 번은 사람이 끝까지 읽는다. VS Code에서 복원명세.md를 열고 다음 세 질문에 답한다. 답은 비교.md를 만들 때 「찾은 빈틈과 처리」 절에 옮기므로, 지금은 명세 파일 안에서 해당 줄 끝에 표시만 한다.

  1. 「추측」이 붙은 요구는 무엇인가. 그 요구는 원본에서 확인할 방법이 있는가(3-3의 질의 문자열처럼). 확인할 방법이 있으면 6-7에서 확인한다.
  2. 관찰 기록과 다른 곳이 있는가. 내가 본 것과 명세가 다르면 어느 쪽이 맞는지 화면을 다시 본다. 명세가 틀렸으면 고치고 줄 끝에 ← 고침을 붙인다.
  3. 비어 있는 문형은 무엇인가. 검사기의 문형 분포에서 0인 문형을 보고, 그 문형으로 쓸 만한 상황이 원본에 있는지 생각한다. 예: 선택이 0이면 「판에 따라 있을 수도 없을 수도 있는 기능」이 원본에 없다는 뜻이므로 정상일 수 있다. 원치 않는 동작이 0이면 「잘못된 경우」를 정하지 않은 것이다.
파일: ch06/복원/복원명세.md 
- **REQ-04** [사건] 사용자가 상태(접수예정, 접수중, 마감, 결과공고)를 고르고 검색을 실행하면, 시스템은 그 상태의 공고만 표시해야 한다. ← 고침 (상태전체를 고르면 모두 보인다는 것은 REQ-01이 맡는다)

고칠 곳이 없으면 고치지 않아도 된다. 읽고 판단한 것이 이 단계의 목적이다.

  • 확인 17 세 질문의 답을 정했고, 고친 곳이 있으면 그 줄 끝에 ← 고침이 있다.

- 기술 이름(localStorage, FastAPI, 함수 이름)을 요구에 쓰지 않는다
- 근거 파일에 없는 값(일수, 개수, 시간)을 정했으면 7절 열린 질문에 「AI가 정한 값」으로 적어라

- 동작을 바꾸는 요청은 명세에서 시작한다. 해당 REQ를 고치고 「변경 이력」에 한 줄을 적은 뒤 구현한다.
- 명세나 추적표를 고친 뒤 `python tools/ears_check.py docs/요구사항명세서.md --trace docs/추적표.md --problems ../ch05/문제정의.md`를 실행해 오류 0건을 확인한다.

태그에는 두 종류가 있다. 이름만 커밋에 붙이는 가벼운 태그(git tag 이름)와, 만든 사람, 날짜, 메시지를 Git 데이터베이스에 함께 저장하는 주석 태그(git tag -a 이름 -m 메시지)다. 판을 표시하는 데는 주석 태그를 쓴다[G1, G2]. 위 출력의 마지막 부분처럼 git show spec-v1은 태그의 정보(만든 사람, 날짜, 메시지)와 그 태그가 가리키는 커밋을 함께 보여 준다.

git push는 태그를 원격으로 보내지 않는다. 태그는 따로 보낸다[G1].

서버 터미널 
git push origin main
git push origin spec-v1
git ls-remote --tags origin
To github.com:「아이디」/llm-service-lab.git
 * [new tag]         spec-v1 -> spec-v1

e3ac470bb4ddabb92f5e218575a70a2544c8f87e    refs/tags/spec-v1^{}

^{}가 붙은 줄은 주석 태그가 가리키는 커밋이다. GitHub 저장소의 「Tags」 화면에서도 spec-v1이 보인다. 해시는 학습자마다 다르며, 원격 조작이므로 위 출력은 예시이다.

[그림 자리: GitHub 저장소의 태그 목록] 저장소의 Code 화면에서 가지 선택 상자를 열고 「Tags」 탭을 고른 상태, 또는 /tags 화면에 spec-v1과 태그 메시지가 보이는 캡처. 찍을 곳: 브라우저, github.com/「아이디」/llm-service-lab/tags. 메뉴 이름은 GitHub 화면 개편에 따라 바뀔 수 있으므로 수업 직전에 찍는다.

이미 보낸 태그는 옮기지 않는다. 같은 이름으로 다시 만들려 하면(git tag -a spec-v1 -m "고친 판") Git이 fatal: tag 'spec-v1' already exists로 막는다. -f로 강제로 옮길 수는 있지만, 이미 그 태그를 받아 간 사람의 저장소에서는 옛 태그가 그대로 남아 서로 다른 커밋을 같은 이름으로 부르게 된다. Git 문서는 이런 경우 새 이름을 쓰는 것이 온당하다고 하고, Git이 사용자 몰래 태그를 바꾸지 않는다고 강조한다[G2]. 명세를 고치면 v1.1, v2처럼 새 판을 만들고, 판의 이름을 태그로 단다(spec-v2는 7장).

8-4. 변경 이력과 판의 비교

v1을 확정한 뒤에도 명세는 바뀐다. 변경은 세 곳에 남긴다. 명세서의 요구(무엇이 바뀌었나), 명세서의 「변경 이력」 표(왜 바뀌었나), Git 커밋(언제 누가 바꾸었나)이다. 다음은 7-7의 동료 검토에서 「공백만 든 검색어를 어떻게 하는지 정하지 않았다」는 지적을 받아 고친 예다.

8-6. (나) 실습 복기

조사 결과에서 명세서 v1을 쓰고, 규칙을 끌어내고, 판을 고정하였다.

  1. 요구마다 근거와 판정을 붙였다. 모든 요구가 추적표로 문제 정의에 닿고, 수용 기준으로 판정된다. 「이 요구는 왜 있는가」와 「무엇을 보면 했다고 하는가」에 ID로 답할 수 있다.
  2. 기계와 사람의 몫을 나누었다. 검사기는 꼴과 끊긴 고리를 잡았고, 동료 검토와 열린 질문은 뜻과 빈자리를 다루었다. 검사기를 통과한 명세도 동료가 읽으면 고칠 곳이 나온다.
  3. 판을 고정하고 변경을 따로 남겼다. 태그 spec-v1은 옮기지 않는다. 바뀐 것은 변경 이력과 커밋으로 남기고, 판과 판의 차이를 git diff spec-v1로 본다.

코드에서 뽑은 명세에도 「코드만으로 알 수 없는 것」이 남는다. 코드는 무엇을 하는지는 말하지만 왜 하는지는 말하지 않는다. 그래서 코드에서 뽑은 명세는 그 코드를 만든 사람이나 쓰는 사람에게 확인받아야 한다. 인수인계에서 리버스 엔지니어링이 「전임자와의 대화」로 끝나는 까닭이다.

정리

  • 리버스 엔지니어링은 완성물을 바꾸지 않고 분석해 구성과 관계를 알아내고 더 높은 수준(명세)으로 표현하는 일이다. 이 장의 절차는 관찰 → 구조 분석 → 기능 목록 → 명세 → 재구현 → 비교이며, 관찰과 비교는 사람이 한다.
  • 웹 화면은 서버가 내용을 채워 보내는 경우와 브라우저의 스크립트가 채우는 경우가 있다. 주소와 질의 문자열로 재현되는 화면은 curl과 웹 읽기로 근거를 만들고, 그렇지 않은 화면은 캡처, 관찰 기록, 화면을 조작하는 도구로 근거를 만든다. 근거에는 종류와 날짜를 적는다.
  • 명세로 재구현한 결과가 원본과 다른 자리는 명세 빈틈, 매체 차이, 데이터 한계, 의도한 차이, 범위 밖으로 나뉜다. 명세 빈틈만 명세로 되돌린다.
  • EARS는 요구 문장을 상시, 사건(When), 상태(While), 선택(Where), 원치 않는 동작(If … then)의 다섯 문형과 그 조합으로 쓰게 한다. 문형을 고르는 일은 빈칸을 찾는 일이며, 문형 분포의 0은 정하지 않은 상황을 가리킨다.
  • 명세 주도 개발은 명세를 구현의 입력이자 검사의 기준으로 삼는다. Spec Kit의 단계(원칙, 명세, 명확화, 계획, 작업, 분석, 구현, 수렴)는 Claude Code의 계획 모드와 마크다운 파일로 같은 순서를 밟을 수 있다.
  • 요구사항 명세서는 요구, 수용 기준, 추적표가 한 묶음이다. 수용 기준을 쓸 수 없는 요구는 아직 요구가 아니고, 문제에 닿지 않는 요구는 근거를 다시 묻는다.
  • 명세에서 끌어낸 CLAUDE.md는 명세의 내용이 아니라 명세를 쓰는 규칙을 담는다. 명세의 판은 주석 태그와 변경 이력으로 관리하고, 한 번 쓴 ID와 보낸 태그는 바꾸지 않는다.

  1. 6절의 재구현에서 원본의 주소와 페이지.html을 재구현 폴더에 넣지 않고 새 세션에서 재구현하는 까닭은 무엇인가?
