비교 구현

2027학년도 「LLM 서비스 개발」의 준비 중인 교재입니다. 편집 상태를 검토하기 위해 미리 공개한 것으로, 수업 전에 내용과 순서가 바뀔 수 있습니다.

학사 14주차 · 교재 12 · 서비스 5: 데스크톱 앱의 기능 하나 (2/2)

개편 초안 2판(2026-11-18). 예시를 11장의 FromScratch 자동 저장으로 바꾸었다. 키트(Service_12장)의 테스트와 도구, 핵심 실습의 git 명령(태그, 작업 트리 둘, 커밋, 규모, 명세 보강, 병합, 보존, 정리)은 Windows 11의 Git Bash(git 2.55.0, Python 3.13.7)에서 교수용 견본 구현으로 끝까지 실행해 출력을 실었다. 두 구현을 실제로 만드는 Orca의 작업 공간과 Claude Code 두 세션은 「실행 결과 자리」로 남겼다. 교수가 실습실 PC에서 리허설한 뒤 채운다. 2026-11-19에 7-6(연습 저장소의 작업 트리와 보존 태그, 따라 하기)을 더하였다.

지금까지는 명세 하나에서 구현 하나를 얻었다. 명세가 정하지 않은 곳은 Claude Code가 정했고, 그 결정이 좋은지 나쁜지는 견줄 대상이 없어 판단하기 어려웠다. 이 장은 같은 명세에서 구현을 둘 만든다. 11장의 기능 명세와 화면 명세를 두 에이전트에게 주고, 한 가지만 다르게 지시한다. 두 구현은 에이전트 개발 환경 Orca에서 내 PC의 작업 공간 두 개로 나란히 만든다. 작업 공간마다 git 작업 트리와 브랜치가 하나씩이고, 그 안에서 Claude Code 세션이 하나씩 돈다.

두 구현을 같은 기준으로 재어 기준표를 채운다. 두 구현이 서로 다르게 정한 곳이 명세의 빈틈이며, 그 빈틈을 명세에 보강한다. 끝으로 어느 구현을 택했는지와 그 까닭을 결정 기록(ADR)으로 남기고, 택한 구현을 main에 병합하며, 택하지 않은 구현은 태그로 보존한다.

학습 목표

  • 같은 명세의 구현을 둘 만드는 목적을 설명하고, 변형의 축을 하나로 정할 수 있다.
    • 예시: 자동 저장의 「저장 상태를 늘 보인다」와 「바뀔 때만 알린다」를 축으로 정한다.
  • git 작업 트리로 두 구현을 나란히 두고, Orca에서 두 에이전트를 같은 조건으로 실행할 수 있다.
  • 비교 기준을 구현 전에 정하고, 두 구현을 같은 방법으로 재어 기준표를 채울 수 있다.
  • 두 구현이 서로 다르게 정한 곳에서 명세의 빈틈을 찾아 보강할 수 있다.
    • 예시: 한 구현은 빈 글을 저장하고 다른 구현은 안내 글을 다시 보인다. 사용자가 볼 수 있는 차이이므로 요구로 올린다.
  • 선택의 근거를 결정 기록으로 남기고, 택하지 않은 구현을 태그로 보존할 수 있다.
    • 활용: 졸업 프로젝트에서 팀의 의견이 갈릴 때 둘 다 만들어 재고 ADR로 결정한다.

  • 이 장의 실행 상한. Claude Code 세션은 변형마다 하나, 구현 지시 한 번과 고침 한 번까지이다. 프로덕트 코드의 LLM 호출은 없다.

  • 확인 1 python -m pytest -q가 4 passed이고, git status --short가 빈 출력이며, ch11/에 기능명세.md와 화면명세.md가 있다.

1. 비교 구현의 목적

1-1. 같은 명세, 다른 결과

2026년판 「리버스 엔지니어링과 SDD」 수업의 예제 D에서는 포트폴리오 코드에서 명세를 뽑고, 그 명세만으로 다시 만든 재생성본을 원본과 나란히 놓았다[R1]. 두 화면은 같은 명세에서 나왔는데도 달랐고, 그 차이를 세 갈래로 나누었다.

  1. 문장. 눌렀을 때의 동작, 보여 주는 정보, 문구의 차이다. 요구사항 명세에 요구 한 줄(EARS)로 채운다.
  2. 그림. 배치, 간격, 색, 순서의 차이다. 문장으로 써도 해석이 갈리므로 화면 명세로 채운다.
  3. 사람이 준비하는 것. 실제 문구, 이미지, 색 값처럼 문장으로도 그림으로도 정해지지 않는 것이다. 사람이 넣는다.

그때의 비교는 원본과 재생성본 사이였다. 원본은 사람이 만든 것이므로, 차이의 상당 부분은 원본 제작자가 명세로 옮기지 않은 결정이었다. 이 장의 비교는 다르다. 두 구현이 모두 같은 명세에서 나온다. 그런데도 두 구현이 다르다면, 그 차이는 명세가 정하지 않아 구현이 각자 정한 곳에서만 생긴다. 차이가 곧 명세의 빈틈을 가리키는 지표가 된다.

차이가 생기는 자리는 둘이다. 첫째는 이 장에서 일부러 다르게 지시한 축이다. 저장 상태를 늘 보이라고 한 쪽과 바뀔 때만 알리라고 한 쪽의 화면이 다른 것은 당연하다. 둘째는 지시하지 않았는데 달라진 곳이다. 예를 들어 사용자가 글을 모두 지웠을 때 한 구현은 빈 글을 저장하고 다른 구현은 저장을 지워 안내 글을 다시 보인다면, 그것은 지시의 차이가 아니라 명세의 빈틈 때문이다. 핵심 실습의 빈틈 찾기가 둘째 종류의 차이를 찾는 절차이다.

1-2. 탐색과 선택

GitHub이 명세 주도 개발 도구 Spec Kit을 공개하며 쓴 글은, 명세가 구현과 분리되어 있으면 계획의 여러 변형을 요청해 견주거나 여러 판을 만들어 빠르게 실험할 수 있다고 설명한다[S1]. 사람이 손으로 구현하던 시절에는 같은 기능을 두 번 만드는 비용이 커서 하나를 정해 만들고 고쳐 나갔다. 구현을 AI가 맡으면 두 번째 구현의 비용은 지시문 하나와 검토 시간으로 줄어든다. 줄어든 비용만큼 「만들어 보고 고른다」는 선택지가 현실이 된다.

비교 구현은 두 단계로 이루어진다.

  1. 탐색(exploration). 명세가 열어 둔 공간에서 서로 다른 해법을 둘 이상 만든다. 이 단계의 목표는 좋은 구현이 아니라 서로 다른 구현이다. 비슷한 두 구현은 비교해도 배울 것이 적다.
  2. 선택(selection). 정해 둔 기준으로 견주어 하나를 고르고, 고른 까닭과 버린 것의 장점을 기록한다. 선택한 구현만 다음 단계(13장의 평가)로 간다.

변형이 셋을 넘으면 측정과 대조에 드는 시간이 구현 시간보다 커진다. 이 장은 변형을 둘로 정한다.

1-3. A/B 테스트와의 차이

같은 기능의 두 판을 견주는 방법으로 가장 널리 알려진 것은 A/B 테스트이다. A/B 테스트는 실제 사용자를 두 무리로 나누어 서로 다른 판을 보여 주고, 전환율 같은 지표로 어느 판이 나은지 통계적으로 가린다. 닐슨은 A/B 테스트가 실제 사용자의 실제 행동을 재고 작은 차이도 가려낼 수 있지만, 분명한 목표 하나가 있을 때만 쓸 수 있고, 완성된 구현과 실제 트래픽이 필요하며, 왜 그런 결과가 나왔는지는 말해 주지 않는다고 정리하였다[U17].

구분 A/B 테스트 이 장의 비교 구현
언제 출시 뒤, 실제 트래픽이 있을 때 출시 전, 개발 중
누가 판단하나 실제 사용자의 행동(전환율, 클릭) 개발자의 측정과 점검(명세 충족, 휴리스틱, 접근성)
무엇을 비교하나 대개 한 요소의 작은 차이(단추 문구, 배치) 상호작용 방식처럼 구조가 다른 두 구현
얻는 것 어느 쪽이 지표를 올리는가 어느 쪽이 명세를 더 잘 지키는가, 명세의 빈틈은 어디인가
못 하는 것 왜 그런지 설명하지 못한다 실제 사용자의 선호를 알지 못한다

두 방법은 경쟁 관계가 아니라 순서 관계이다. 비교 구현으로 하나를 골라 출시하고, 출시 뒤에 그 안의 작은 요소를 A/B 테스트로 다듬는다. 이 과목에는 실제 트래픽이 없으므로, 사용자의 판단은 13장의 사용성 평가가 대신한다.

1-4. 비교 구현의 비용과 한계

비교 구현은 공짜가 아니다. Claude Code 세션이 둘이므로 구현에 드는 사용량이 두 배가 되고, 사람이 읽어야 할 계획, 보고, 변경도 두 배가 된다. 측정과 대조에 드는 시간까지 더하면, 기능 하나를 하나만 만들 때보다 두세 배의 시간이 든다. 그러므로 모든 기능을 둘씩 만들지 않는다. 비교 구현이 값을 하는 경우는 다음과 같다.

  • 선택이 뒤에서 바꾸기 어려운 구조를 정할 때. 상호작용 방식, 데이터의 저장 위치, 외부 API의 선택처럼 한번 정하면 다른 기능이 그 위에 쌓이는 결정이다.
  • 팀 안에서 의견이 갈리고, 어느 쪽도 근거를 내놓지 못할 때. 회의를 한 번 더 하는 것보다 둘 다 만들어 재는 편이 빠르다.
  • 명세가 새로 쓰였고 아직 검증되지 않았을 때. 11장의 명세가 그렇다. 두 구현의 차이로 명세의 빈틈을 찾는 효과가 크다.

반대로 단추 문구나 색처럼 되돌리기 쉬운 결정에는 쓰지 않는다.

비교에는 사람의 치우침도 끼어든다. 먼저 만든 변형을 오래 들여다보면 그쪽에 정이 들고(매몰 비용), 처음 본 숫자가 판단의 기준점이 된다(기준점 효과). 이 장이 기준을 구현 전에 정하고, 두 변형을 동시에 만들고, 같은 순서로 재는 것은 이 치우침을 줄이기 위해서이다. 그래도 남는 치우침은 결정 기록의 「결과」에 버린 쪽의 장점을 적는 것으로 드러낸다.

2. 변형의 축

2-1. 변형의 세 축

같은 명세의 구현을 다르게 만드는 방향을 변형의 축이라 부른다. 자주 쓰는 축은 세 가지이다.

축 무엇을 바꾸나 자동 저장의 예 LLM 서비스의 예
상호작용 방식 사용자가 입력하고 결과를 받는 방식 저장 상태를 늘 보이기와 바뀔 때만 알리기 대화형 화면과 양식형 화면
처리 전략 같은 결과를 내는 시스템 쪽의 방식 입력이 멈춘 뒤 저장하기와 바뀔 때마다 저장하기(원본 FromScratch) 한 번에 다 쓰게 하기와 나누어 부르기
구현 기술 같은 동작을 만드는 기술 localStorage와 IndexedDB 서버에서 화면 만들기와 브라우저에서 만들기

세 축은 서로 독립이 아니다. 바뀔 때마다 저장하면 「저장 안 됨」인 순간이 거의 없으므로 상태를 보이는 방식도 따라 바뀐다. 그래도 한 번의 비교에서 의도적으로 바꾸는 축은 하나로 한다. 두 축을 함께 바꾸면 결과의 차이가 어느 축에서 왔는지 가릴 수 없기 때문이다. 실험에서 한 번에 한 변수만 바꾸는 것과 같은 원리이다.

축은 기능 명세가 정하지 않은 것에서 고른다. 11장의 명세는 저장의 시점(입력이 멈추고 1초)과 상태의 문구를 정했지만, 상태를 화면의 어디에 언제 보일지는 정하지 않았다. 이 빈칸이 이 장의 축이 된다.

2-2. 상태 표시: 늘 보이는 표시와 알림

닐슨의 첫째 휴리스틱은 시스템 상태의 가시성이다. 시스템은 적절한 피드백으로 지금 무슨 일이 일어나는지 사용자에게 늘 알려야 한다[U11]. 자동 저장은 이 휴리스틱이 특히 문제가 되는 기능이다. 사용자가 아무것도 누르지 않는데 저장이 일어나므로, 화면이 말해 주지 않으면 앱을 닫아도 되는 순간을 알 수 없다. 원본 FromScratch는 저장 상태를 하나도 보이지 않는다(11장 1-3).

상태를 알리는 방식은 크게 둘이다. NN/g는 화면의 요소를 눈에 띄게 하는 시각 단서를 표시(indicator), 사용자의 지금 입력과 상관없이 시스템의 사건을 알리는 것을 알림(notification)으로 나눈다[U20].

구분 늘 보이는 표시(variant-a) 바뀔 때만 알림(variant-b)
모양 글 아래의 상태 영역 「저장 안 됨」, 「저장됨」 오른쪽 아래에 잠깐 뜨는 알림(토스트)
강점 언제 보아도 상태를 안다 쓰는 동안 화면이 조용하다
약점 쓰는 동안 문구가 계속 바뀐다 놓치기 쉽다. 사라진 뒤에는 상태를 알 수 없다
실패를 알릴 때 같은 자리에서 문구와 단추가 바뀐다 알림이 사라지지 않게 따로 만들어야 한다

NN/g는 사용자의 동작이 필요 없는 수동 알림은 놓치기 쉬우므로, 시스템을 이해하는 데 꼭 필요한 정보라면 늘 보이는 표시가 안전하다고 적는다. 또 잠깐 떴다 사라지는 토스트는 오류를 알리는 데 맞지 않다고 하며, 오류 토스트가 5초 만에 사라져 사용자가 내용을 5분이나 기다린 사례를 든다[U20]. 접근성에서도 차이가 있다. 상태를 보조 기술에 알리는 영역(role="status")은 처음부터 화면에 있어야 안정적으로 읽힌다(11장 4-3). 숨겼다가 보이는 알림은 이 점을 따로 확인해야 한다.

어느 쪽이 나은지는 미리 정할 수 없다. 그래서 둘 다 만들어 같은 기준으로 잰다. 같은 갈림길은 LLM 서비스에도 있다. 대화형 화면은 이어서 묻기에 강하지만 무엇을 물을지 사용자가 떠올려야 한다. NN/g는 이것을 「표현의 장벽(articulation barrier)」이라 부르고[U19], 입력란 주변의 단추와 제안 같은 「프롬프트 컨트롤」이 그 부담을 줄인다고 정리하였다[U18]. 또 Claude의 Messages API는 상태를 기억하지 않으므로 대화를 이어 가려면 매번 대화 전체를 다시 보내야 하고, 대화가 길어질수록 입력 토큰이 늘어난다[A1]. 졸업 프로젝트에서 이 축을 비교한다면 호출 수와 토큰이 기준표에 들어간다.

3. 변형별 브랜치와 작업 트리

2장에서 브랜치를 만들고 오가는 법을 배웠고, 3장에서 기능마다 브랜치를 두어 풀 리퀘스트로 합쳤다. 이 장의 브랜치는 성격이 다르다. 기능 브랜치는 결국 모두 main에 합쳐지지만, 변형 브랜치는 둘 중 하나만 합쳐진다. 다른 하나는 비교의 근거로 남는다.

3-1. 브랜치 전환 방식

가장 단순한 방법은 저장소 폴더 하나에서 브랜치를 바꾸어 가며 작업하는 것이다.

[터미널] (읽기)

git switch -c variant-a      # a 구현, 커밋
git switch main
git switch -c variant-b      # b 구현, 커밋
git switch variant-a         # a를 다시 보려면 전환

git switch는 작업 폴더의 파일을 그 브랜치의 내용으로 바꾼다[G4]. 폴더가 하나뿐이므로 한 번에 한 변형만 디스크에 있다. 이 방식에는 세 가지 불편이 있다.

  1. 두 변형의 화면을 동시에 띄워 나란히 볼 수 없다.
  2. Claude Code가 한 변형을 구현하는 동안 다른 변형을 진행할 수 없다.
  3. 커밋하지 않은 변경이 있으면 전환이 거부된다. 다른 브랜치의 같은 파일을 덮어쓰게 되기 때문이다.

셋째 경우의 화면은 다음과 같다. 집필 때 버려도 되는 연습 저장소에서 일부러 만든 상황이다.

error: Your local changes to the following files would be overwritten by checkout:
    greet.txt
Please commit your changes or stash them before you switch branches.
Aborting

3-2. git worktree

git worktree는 저장소 하나에 작업 폴더를 여러 개 붙인다[G2]. 처음부터 있던 폴더를 주 작업 트리(main worktree), 새로 붙인 폴더를 연결 작업 트리(linked worktree)라 부른다. 작업 트리마다 다른 브랜치를 꺼내 둘 수 있으므로, 두 변형이 동시에 디스크에 있게 된다.

명령 하는 일
git worktree add <경로> -b <새 브랜치> <출발점> 출발점(태그, 커밋)에서 새 브랜치를 만들고 <경로>에 꺼낸다
git worktree add <경로> <브랜치나 태그> 이미 있는 브랜치(또는 태그)를 <경로>에 꺼낸다
git worktree list 주 작업 트리를 먼저, 연결 작업 트리를 이어서 보인다
git worktree remove <경로> 연결 작업 트리를 지운다. 추적하지 않는 파일이나 바뀐 파일이 있으면 거부한다
git worktree prune 폴더를 손으로 지워 버린 작업 트리의 관리 정보를 정리한다

작업 트리끼리 무엇을 함께 쓰고 무엇을 따로 쓰는지 알아 두어야 한다. 커밋, 브랜치, 태그 같은 저장소의 기록은 모두 함께 쓴다. 한 작업 트리에서 만든 커밋이 다른 작업 트리의 git log --all에 바로 보인다. 반면 HEAD(지금 꺼낸 브랜치)와 인덱스(스테이징 영역)는 작업 트리마다 따로이다[G2]. 그래서 같은 브랜치를 두 작업 트리에 동시에 꺼낼 수 없다. 한쪽에서 커밋하면 다른 쪽의 작업 폴더가 그 브랜치와 어긋나기 때문이다. 집필 PC에서 이미 꺼낸 브랜치를 한 번 더 꺼내려 하면 다음과 같이 거부되었다(경로의 앞부분은 줄였다).

Preparing worktree (checking out 'variant-x')
fatal: 'variant-x' is already used by worktree at 'C:/Users/아이디/demo/lab-x'

이 메시지는 실수가 아니라 보호 장치이다. 주 작업 트리에서 그 브랜치를 보려면 전환하지 말고 그 작업 트리 폴더로 간다. 작업 트리는 추적하는 파일만 새로 꺼낸다. .gitignore가 거르는 파일(.env, 가상 환경, 기록 파일)은 새 작업 트리에 없다. 변형마다 설정과 기록이 섞이지 않는다는 뜻이기도 하다.

git worktree list에서 git branch를 함께 보면 *는 지금 작업 트리의 브랜치, +는 그 브랜치가 다른 작업 트리에 꺼내져 있다는 뜻이다[G4]. git worktree remove로 폴더를 지워도 브랜치와 커밋은 남는다. 작업 트리는 브랜치를 꺼내 두는 폴더일 뿐이기 때문이다.

3-3. Claude Code의 작업 트리 기능

Claude Code도 작업 트리를 직접 만든다. claude --worktree <이름>(줄여서 -w)으로 시작하면 저장소 루트의 .claude/worktrees/<이름>/에 작업 트리를 만들고 worktree-<이름> 브랜치를 꺼낸 뒤 그 안에서 세션을 연다. 출발점의 기본값은 원격의 기본 브랜치(대개 origin/main)이다[C8].

이 장의 핵심 실습은 --worktree를 쓰지 않고 Orca(3-4)로 작업 공간을 만든다. 브랜치 이름을 variant-a처럼 뜻이 드러나게 정할 수 있고, 출발점을 명세를 커밋한 태그 spec-ch12로 분명히 정할 수 있기 때문이다. 기본 설정의 --worktree는 원격에서 출발하므로, 명세 커밋을 아직 푸시하지 않았으면 명세가 없는 상태에서 출발한다. Claude Code 문서도 특정 브랜치를 꺼낼 때는 git으로 직접 만들라고 안내한다[C8].

[최신 자료 자리: Claude Code의 작업 트리 기능과 이 장이 쓰는 옵션] --worktree(-w)의 위치, 브랜치 이름, 출발점, .worktreeinclude의 동작, 그리고 핵심 실습이 쓰는 --permission-mode plan, /model, /effort의 이름. 확인할 곳은 https://code.claude.com/docs/en/worktrees, https://code.claude.com/docs/en/cli-reference와 내 PC의 claude --help이다. 2026-11-16에 집필 PC의 Claude Code 2.1.296에서 claude --help로 -n, --name, -w, --worktree [name], --permission-mode가 있음을 확인하였다. 위의 동작은 2026-11-14에 문서로 확인한 것이다.

3-4. Orca: 작업 트리 위의 에이전트 개발 환경

Orca는 MIT 사용권의 무료 공개 소프트웨어로 macOS, Windows, 리눅스에서 돈다[O1]. 작업마다 git 작업 트리를 만들고 그 안에서 Claude Code 같은 CLI 에이전트를 나란히 실행한다[O2]. 이런 도구를 에이전트 개발 환경(ADE, Agentic Development Environment)이라 부른다. 이 과목은 내 PC의 저장소를 Orca에서 로컬로 연다. 에이전트와 git 명령이 모두 내 PC에서 돌고[O3], Orca 자체에는 계정이 필요 없으며, Orca의 터미널에서 실행한 Claude Code가 각자의 구독 계정을 그대로 쓴다(부록 A-21).

[최신 자료 자리: Orca의 판과 이 장이 쓰는 메뉴 이름] 판, 저장소를 더하는 메뉴, 작업 트리 만들기 창의 Run on·Branch from·Advanced의 Branch name, 에이전트 권한(Manual, Auto, Yolo), 오케스트레이션이 실험 기능(Settings → Experimental)인지. 확인할 곳은 https://github.com/stablyai/orca/releases와 https://orca.dev/docs/이다. 2026-11-16 확인 값: v1.4.261, 메뉴 이름은 본문과 같다. Branch from 칸이 태그를 받는지, 로컬 실행에서 작업 트리를 만드는 폴더가 어디인지는 문서에서 확인하지 못하였다. 수업 전에 다시 확인한다.

Orca를 쓸 때 알아 둘 성질은 넷이다. 모두 Orca 문서의 작업 트리 절에 있다[O2].

  1. 실제 git 작업 트리. Orca의 작업 공간은 모두 실제 git 작업 트리이다. 그래서 3-2의 설명이 그대로 맞고, 무엇을 만들었는지는 늘 git worktree list로 확인할 수 있다. 반대로 git worktree add로 만든 작업 트리는 Orca 목록에 저절로 나타나지 않는다.
  2. 출발점의 기본값. 브랜치 이름은 작업 이름에서 정해지고, 출발점(Branch from)의 기본은 대개 origin/main이다. 푸시하지 않은 커밋에서 출발하려면 반드시 바꾼다. 3-3의 --worktree와 같은 함정이다.
  3. 삭제. Orca에서 작업 공간을 삭제하면 확인을 받은 뒤 작업 트리 폴더와 브랜치를 함께 지운다. 남길 변형은 7-2처럼 태그를 먼저 붙인다.
  4. 자동 정리. 작업 트리의 자동 정리 규칙은 기본으로 꺼져 있으므로 정리는 사람이 한다.

여러 에이전트를 조정자와 작업자로 나누어 돌리는 Orca의 오케스트레이션은 실험 기능이므로[O4] 교수 시연으로만 본다. 조정자와 작업자가 각자 모델을 불러 사용량을 사람이 예측하기 어렵기 때문이다.

3-5. 세 방식의 비교

브랜치 이름과 출발점 사람이 정한다 사람이 명령에 적는다 작업 이름에서 정하고, 출발점의 기본은 대개 origin/main이다
커밋하지 않은 변경 전환을 막는다 작업 트리마다 따로 있어 막지 않는다 같다. diff 화면에서 줄마다 본다
정리 브랜치만 지운다 작업 트리를 지우고 브랜치를 지운다 삭제 하나가 작업 트리와 브랜치를 함께 지운다

컴퓨터 자원이 부족하거나 변형이 한 파일만 다르면 브랜치 전환으로 충분하다. 이 장처럼 두 변형을 나란히 실행해 재야 하면 작업 트리가 맞다. 명령과 Orca는 결과가 같다. Orca는 작업 트리 방식 위에 화면을 얹은 것이므로, 출발점과 정리는 어느 쪽으로 했든 git 명령으로 확인한다[O2]. Orca를 쓸 수 없는 PC에서는 같은 절차를 3-2의 명령으로 한다(8-3).

4. 변형 지시문

4-1. 같은 명세를 두 번 주는 원칙

두 구현의 차이가 의도한 축에서만 생기게 하려면, 지시의 나머지를 똑같이 맞추어야 한다.

어긋나는 곳 생기는 일 맞추는 방법
지시문의 문장 한쪽에만 「꼼꼼히 확인하라」를 쓰면 그쪽만 점검이 많다 공통 지시를 파일로 쓰고 두 세션에 같은 파일을 준다
대화의 앞 내용 두 번째 변형을 같은 세션에서 시키면 첫 구현을 보고 따라 한다 변형마다 새 세션을 연다
출발 커밋 한쪽이 명세 수정 전 커밋에서 출발한다 두 브랜치를 같은 태그(spec-ch12)에서 만든다
모델과 노력 수준 한쪽만 높은 수준으로 돌린다 /model, /effort를 두 세션에서 같게 둔다
사람의 개입 한쪽에만 중간에 추가 요구를 한다 개입은 질문에 답하는 것으로 한정하고, 답을 두 세션에 똑같이 준다

새 세션을 여는 까닭은 Claude Code 모범 사례 문서에도 있다. 명세 파일을 만든 뒤에는 새 세션에서 그 파일로 구현을 시작하라고 권한다. 깨끗한 맥락과 글로 적힌 완료 기준에서 출발하기 위해서이다[C6]. 이 장에서는 그 이유가 하나 더 있다. 앞 변형의 대화가 남아 있으면 두 번째 구현은 독립된 구현이 아니게 된다.

4-2. 지시문의 구조: 공통과 차이

지시문은 세 파일로 나눈다. 공통 지시 하나와 변형별 지시 둘이다. 변형별 파일에는 공통 지시와 다른 것만 적는다. 그러면 두 변형의 차이가 무엇인지 파일 두 개의 diff로 바로 보인다.

  • ch12/변형지시/공통.md: 기준 문서, 할 일, 계약, 하지 말 것, 보고 형식. 두 세션에 똑같이 준다.
  • ch12/변형지시/a.md, b.md: 변형의 축 하나에 관한 지시만. 그 세션에만 준다.
파일: ~/kits/Service_12장/변형지시_공통_양식.md 
기준 문서: ch12/기능명세.md, ch12/화면명세.md. 두 문서를 고치지 마라.
할 일: ch12/app/ 에 index.html, style.css, app.js 로 기능을 구현하라. 저장은 브라우저 저장소(localStorage)를 쓴다.
계약: 저장 키는 「memo」, 값은 글 전체의 문자열이다. 주소에 ?state=「상태 이름」을 붙이면 화면 명세의 그 상태를 바로 보인다.
하지 말 것: 빌드 도구, npm, 외부 CDN과 라이브러리, 명세에 없는 기능, ch12/app/ 밖의 파일 수정.
보고: ① 만든 파일 ② 요구 ID마다 구현한 곳(파일과 함수) ③ 명세에 없어 스스로 정한 것의 목록 ④ 직접 확인한 방법

「계약」 줄은 두 구현을 같은 방법으로 점검하기 위한 약속이다. 저장 키와 값의 모양이 같으면 개발자 도구에서 같은 키를 보고 판정할 수 있고, ?state=가 같으면 같은 주소로 같은 상태를 열어 본다. 계약은 명세가 정하지 않은 결정 일부를 사람이 먼저 정한 것이다. 이것은 의도한 것이다. 이 장이 보려는 빈틈은 계약 밖, 즉 동작의 세부에서 생긴다.

보고의 ③(명세에 없어 스스로 정한 것)에 주목한다. Claude Code가 스스로 정한 것을 밝히게 하면, 명세 대조 전에 빈틈 후보의 첫 목록을 얻는다. 다만 이 목록은 구현한 쪽의 자기 보고이므로 빠지는 것이 있다(5-6).

5. 비교 기준과 측정

5-1. 비교 기준표

비교를 시작하기 전에 기준을 정해 둔다. 구현을 보고 나서 기준을 정하면, 마음에 드는 쪽이 이기는 기준을 고르게 된다. 이 장은 다음 다섯 기준을 쓴다.

기준 정의 재는 법 해석할 때 주의
명세 충족률 (충족 + 0.5 × 부분) ÷ (전체 − 해당없음) 점검표를 손으로 채우고 spec_checklist.py로 센다 판정에 관찰한 근거를 함께 적어야 의미가 있다
휴리스틱 위반 수 닐슨의 10가지 가운데 1, 5, 9에 어긋나는 문제의 수 화면을 써 보며 표에 적는다 평가자 한 명의 빠른 점검이다. 정식 평가는 13장
키보드 점검 마우스 없이 주요 조작을 끝낼 수 있는가 11장 3-3의 손 점검, 선택으로 keyboard_walk.py 막힌 곳을 적는다. 「됨」만 적지 않는다
HTML 점검 오류 html_check.py의 오류 수 11장 키트의 점검기 0건이 접근성을 보증하지 않는다
코드 규모 변형이 더한 줄 수 git diff --shortstat spec-ch12...<브랜치> -- ch12/app 작은 것이 좋다는 뜻이 아니다. 같은 충족률이면 작은 쪽이 고치기 쉽다

기준끼리 결론이 엇갈리는 것이 보통이다. 이때 기준표에서 바로 결론을 내지 말고, 먼저 「넘으면 안 되는 선」을 확인한다. 명세의 필수 요구를 충족하지 못하거나 HTML 점검에 오류가 있는 변형은 다른 기준이 아무리 좋아도 고르지 않는다. 선을 넘지 않은 변형끼리는 사용자의 과업에 가장 가까운 기준을 앞에 둔다. 그 순서를 결정 기록에 적는다.

다섯 기준에 가중치를 주어 점수 하나로 합치지 않는다. 합친 점수는 보기 편하지만, 가중치를 어떻게 주느냐에 따라 결론이 바뀐다. 기준표는 기준별로 나란히 보이고, 어느 기준을 더 무겁게 볼지는 결정 기록에서 맥락과 함께 밝힌다.

5-2. 명세 충족 점검표

명세 충족률은 요구 하나하나를 실제로 써 보고 판정해서 얻는다. 판정은 네 가지 가운데 하나이다.

  • 충족: 요구의 모든 부분을 관찰했다. 예: 「회의 메모」를 치고 1.5초 뒤 새로고침하자 글이 그대로 있었다.
  • 부분: 요구의 일부만 관찰했다. 예: 실패 문구는 뜨지만 「다시 시도」 단추가 없다.
  • 미충족: 관찰하지 못했다. 판정할 방법이 없어 관찰하지 못한 것도 여기에 넣고, 근거 칸에 「판정 못함: 까닭」을 적는다. 판정하지 못한 것을 충족으로 적지 않는다.
  • 해당없음: 그 변형에 해당하는 경우가 없다. 드물며, 쓰면 까닭을 근거 칸에 적는다.

근거 칸에는 무엇을 보고 판정했는지 적는다. 「됨」만 적으면 나중에 다른 사람이 같은 판정에 이를 수 없다. 키트의 연습 점검표로 집계 도구를 써 본다.

파일: ~/kits/Service_12장/연습/점검표_A.md 
| ID | 요구 요약 | 판정 | 근거(관찰한 것) |
|---|---|---|---|
| REQ-02 | 다시 열면 마지막 글 | 충족 | 새로고침 뒤 친 글이 그대로 있음 |
| REQ-03 | 처음에는 안내 글 | 충족 | 저장소를 비우고 열자 안내 글이 보임 |
| REQ-05 | 바뀐 동안 「저장 안 됨」 | 충족 | 치는 동안 글 아래에 「저장 안 됨」 |
| REQ-07 | 저장 실패를 알림 | 미충족 | 판정 못함: 실패를 만들 방법(?state=error)이 없음 |

판정 칸에 정해진 말이 아닌 것(예: 「거의」, 「됨」)을 쓰면 도구가 그 줄을 「판정을 읽지 못함」으로 알리고 끝 상태 코드 1로 끝난다.

5-3. 휴리스틱 위반 수

닐슨의 사용성 휴리스틱 10가지는 화면의 사용성 문제를 찾는 점검 목록이다[U11]. 13장에서 정식으로 다루며, 이 장에서는 자동 저장에 가장 가까운 셋으로 두 변형을 빠르게 훑는다.

번호 휴리스틱 자동 저장에서 볼 곳
1 시스템 상태의 가시성 지금 저장되었는지, 쓰는 중인지 화면에서 알 수 있는가
5 오류 예방 저장되지 않은 글을 남긴 채 화면을 닫게 되는가
9 오류의 인식, 진단, 회복 저장에 실패했을 때 무엇이 잘못되었고 무엇을 하면 되는지 알려 주는가

위반 하나는 「어느 휴리스틱에, 어느 화면 위치에서, 무엇이 문제인가」를 한 줄로 적는다. 닐슨 노먼 그룹은 휴리스틱 평가에 평가자 3~5명을 권한다. 한 사람은 아무리 숙련되어도 문제 일부를 놓치기 때문이다[U16]. 이 장의 수는 구현한 본인 한 명의 점검이므로 두 변형을 같은 조건에서 견주는 데만 쓰고, 절대적인 품질로 읽지 않는다.

5-4. 코드 규모

코드 규모는 변형이 출발점에 비해 더한 줄 수로 잰다. git diff의 점 세 개 표기 spec-ch12...variant-a는 두 쪽이 갈라진 지점에서 variant-a까지의 변경만 보인다[G5]. 그 사이 main에 명세 보강이 커밋되어도 변형의 규모에 섞이지 않는다. 점 두 개 A..B는 git diff에서 두 끝의 차이 전체를 보이므로 main이 앞서 나가면 main의 변경이 거꾸로 섞인다. 비교에는 점 세 개를 쓴다. 명령의 끝에 -- ch12/app을 붙이면 그 폴더의 변경만 센다.

5-6. 자기 보고와 써 보는 대조

4-2에서 공통 지시의 보고 항목에 「명세에 없어 스스로 정한 것」을 넣었다. 구현한 세션이 스스로 밝힌 이 목록과, 사람이 두 구현을 써 보며 찾은 차이를 견주면 두 방법의 성격이 드러난다.

자기 보고는 구현한 쪽이 의식하고 내린 결정을 잘 잡는다. 「알림은 2초 뒤에 사라진다」처럼 구현하면서 고민한 결정은 대개 보고에 나온다. 반면 의식하지 않은 결정, 즉 기본값을 그대로 두어 생긴 동작은 빠지기 쉽다. 「저장 대기 중에 화면을 닫으면 마지막 입력을 잃는다」는 구현한 쪽에서 보면 아무것도 하지 않은 것이므로 결정으로 느껴지지 않는다. 써 보는 대조는 사용자의 눈으로 보므로 이런 것을 잡는다.

두 목록을 합칠 때는 다음처럼 표시해 둔다.

  • 보고와 써 봄 모두에 있다: 구현한 쪽이 알고 정한 결정이다. 명세로 올릴지 판단만 하면 된다.
  • 써 봄에만 있다: 의식하지 않은 결정이다. 사용자에게 문제가 되는지 먼저 본다. 13장의 사용성 평가에서 문제로 나올 가능성이 크다.
  • 보고에만 있다: 화면에 드러나지 않는 결정(함수 이름, 코드 구조)이거나 써 보며 놓친 것이다.

6. 결정 기록

6-1. ADR

두 변형 가운데 하나를 고른 결정은 명세에 다 담기지 않는다. 명세는 「무엇을」을 적고, 「왜 이것을 골랐고 무엇을 버렸는가」는 적지 않기 때문이다. 이것을 남기는 문서가 아키텍처 결정 기록(Architecture Decision Record, ADR)이다.

ADR은 마이클 나이가드(Michael Nygard)가 2011년 글에서 제안한 형식이다[D1]. 그는 큰 설계 문서는 아무도 읽지 않고 고치지도 않으므로, 결정 하나를 작은 문서 하나에 적자고 하였다. 그가 제안한 항목은 다섯이다.

결정 그 힘들에 대한 응답. 「~한다」로 시작하는 능동문 variant-a를 병합하고 variant-b는 태그로 보존한다
결과 결정 뒤의 상태. 좋은 것, 나쁜 것, 중립인 것을 모두 상태를 늘 안다, 쓰는 동안 문구가 바뀐다, 13장에서 확인할 것

나이가드의 글에서 지켜야 할 규칙이 몇 가지 더 있다[D1]. ADR은 저장소 안에 마크다운으로 두고 번호를 차례로 붙이며, 번호를 다시 쓰지 않는다. 결정이 뒤집히면 옛 ADR을 지우지 않고 상태를 「대체됨」으로 바꾸고 새 ADR을 쓴다. 한 문서는 한두 쪽이며, 미래의 개발자와 대화하듯 완전한 문장으로 쓴다. 이 결정 기록 모음을 ADR 커뮤니티는 결정 로그(decision log)라 부른다[D2].

결과 항목에 나쁜 것을 쓰는 것이 ADR의 핵심이다. 「a가 모든 면에서 낫다」고 쓰면, 몇 달 뒤 알림 방식이 다시 제안되었을 때 그때 무엇을 잃었는지 알 수 없다. 「쓰는 동안 화면이 조용한 장점을 잃었다」를 적어 두면, 그것이 문제가 되는 순간 이 결정을 다시 볼 이유가 기록에 있다.

6-2. 좋은 기록과 나쁜 기록

항목 나쁜 예 좋은 예
맥락 두 방식을 비교했다 명세 충족률은 a 92.9%, b 71.4%이다. b는 입력하는 동안 「저장 안 됨」을 보이지 않는다(REQ-05 미충족). 코드 규모는 79줄과 80줄로 차이가 없다
결정 a가 더 좋아서 a로 한다 variant-a를 main에 병합한다. variant-b는 태그 kept-variant-b로 보존하고 브랜치는 지운다
결과 좋아졌다 사용자가 언제든 저장 여부를 본다. 글을 쓰는 동안 상태 문구가 계속 바뀐다. 13장에서 그 문구가 거슬리는지 확인한다

좋은 예의 숫자는 교수용 견본 구현 둘을 이 장의 방법으로 잰 값이다. 학습자의 값은 자기 구현에서 나온다.

6-3. 결정 기록을 쓰는 때와 추적

모든 결정에 ADR을 쓰지는 않는다. 나이가드는 ADR의 대상을 「아키텍처에 중요한」 결정, 곧 구조, 비기능 특성(성능, 비용, 보안), 의존성, 인터페이스, 구현 기법에 영향을 주는 결정으로 한정하였다[D1]. 다음 질문 가운데 하나에 「그렇다」면 ADR을 쓴다.

  • 이 결정을 되돌리려면 여러 파일이나 다른 기능을 함께 고쳐야 하는가
  • 이 결정이 비용, 응답 시간, 개인 정보의 처리를 바꾸는가
  • 같은 질문이 몇 달 뒤 다시 나올 가능성이 있는가

ADR, 명세, 커밋, 태그는 서로를 가리켜야 나중에 따라갈 수 있다. 보강한 요구의 근거 칸은 비교를, ADR의 맥락은 기준표의 수치를, ADR의 결정은 보존 태그를, 병합 커밋의 메시지는 결정 기록을 가리킨다. 이 연결이 있으면 「왜 이 화면은 상태를 늘 보이는가」라는 질문에서 출발해 ADR, 기준표, 점검표, 보존된 구현까지 차례로 따라갈 수 있다.

7. 병합과 보존

7-1. 병합 커밋을 남기는 병합

선택한 변형을 main에 합칠 때 git merge --no-ff를 쓴다. --no-ff는 빨리 감기(fast-forward)가 가능해도 병합 커밋을 만들라는 옵션이다[G3]. 빨리 감기 병합은 main의 끝을 변형의 끝으로 옮기기만 하므로, 나중에 기록을 보면 변형의 커밋이 처음부터 main에서 만든 것처럼 보인다. 병합 커밋을 남기면 「여기서 variant-a를 합쳤다」는 사실과 그 커밋 메시지가 기록에 남는다. 이 장에서는 변형을 만든 뒤 main에 명세 보강을 커밋하므로 대개 빨리 감기가 불가능하고 병합 커밋이 저절로 생긴다. 그래도 --no-ff를 습관으로 붙인다.

7-2. 태그로 보존

택하지 않은 변형은 지우지 않고 태그로 보존한다. 태그는 커밋 하나를 가리키는 이름이고, 브랜치와 달리 움직이지 않는다. 주석 태그(git tag -a)는 만든 사람, 날짜, 메시지를 담은 태그 객체를 만든다[G6]. 기록으로 남길 태그는 주석 태그로 만든다.

태그를 먼저 만들고 브랜치를 지운다. 순서가 바뀌면 병합하지 않은 변형의 커밋을 가리키는 이름이 하나도 없게 된다. 그런 커밋은 한동안 남아 있지만 찾기 어렵고, 결국 git의 정리 작업으로 사라진다.

7-3. 작업 트리와 브랜치의 정리

정리는 작업 트리 → 브랜치 순서로 한다. 작업 트리에 꺼내 둔 브랜치는 지울 수 없기 때문이다.

명령 결과
git worktree remove <작업 트리의 경로> 작업 트리 폴더를 지운다. 커밋하지 않은 변경이나 추적하지 않는 파일이 있으면 거부한다
git branch -d variant-a 병합한 브랜치를 지운다
git branch -d variant-b 거부된다. 병합하지 않은 브랜치이기 때문이다
git branch -D variant-b 강제로 지운다. 태그가 커밋을 가리키고 있으므로 커밋은 남는다

-d의 거부는 실수로 작업을 잃지 않게 하는 장치이므로, -D를 치기 전에 git tag로 태그가 있는지 반드시 확인한다.

7-4. 태그의 푸시

git push는 태그를 보내지 않는다. 태그는 따로 보내야 한다.

  • git push origin <태그>: 그 태그 하나를 보낸다.
  • git push origin --tags: 모든 태그를 보낸다.
  • git push origin main --follow-tags: main과 함께, 보내는 커밋에서 닿을 수 있는 주석 태그를 보낸다.

--follow-tags는 편하지만 이 장에서는 함정이 있다. 보존 태그는 main에서 닿을 수 없는 커밋을 가리키므로 보내지지 않는다. 집필 PC의 연습 저장소(원격은 같은 PC의 빈 저장소)에서 spec-ch12와 kept-variant-b를 만든 뒤 --follow-tags로 보낸 결과는 다음과 같다(경로의 앞부분은 줄였다).

[터미널] (읽기)

git push origin main --follow-tags
git ls-remote --tags origin

7-5. 보존한 변형을 다시 보기

태그로 보존한 변형은 언제든 다시 볼 수 있다.

git show kept-variant-b:ch12/app/app.js | head -2
git worktree add ../b-다시보기 kept-variant-b
git switch -c variant-b-2 kept-variant-b

첫 명령은 파일 하나를 꺼내지 않고 출력한다. 둘째는 태그를 작업 트리로 꺼낸다(브랜치가 아니므로 「detached HEAD」 상태가 된다). 셋째는 태그에서 새 브랜치를 만들어 이어서 개발한다. 13장의 사용성 평가에서 버린 변형의 장점이 다시 필요해지면 셋째 방법으로 되살린다.

태그: spec-ch12, kept-variant-(택하지 않은 쪽)

판정 기준은 8-1의 완료 기준 여섯 개이다.

정리

  • 같은 명세에서 구현을 둘 만들면, 두 구현이 다르게 정한 곳에서 명세의 빈틈이 드러난다.
  • 변형의 축은 하나만 둔다. 지시문을 공통과 차이로 나누면 두 변형의 차이가 파일의 차이로 보인다.
  • 작업 트리는 브랜치마다 폴더를 따로 두게 한다. 두 구현은 같은 태그에서 출발해야 한다.
  • 비교 기준은 구현을 보기 전에 정한다. 판정에는 관찰한 근거를 적고, 판정하지 못한 것을 충족으로 적지 않는다.
  • 자기 보고는 의식한 결정을 잡고, 써 보는 대조는 의식하지 않은 결정을 잡는다.
  • 선택의 근거는 결정 기록에 남긴다. 택하지 않은 구현은 태그로 보존하고 태그를 따로 푸시한다.

개념 점검.

  1. 같은 명세의 두 구현이 달라지는 자리 둘을 말하고, 그 가운데 명세의 빈틈을 가리키는 것은 어느 것인가.
  2. 두 작업 트리에 같은 브랜치를 꺼낼 수 없는 까닭은 무엇인가.
  3. Orca나 claude --worktree의 출발점을 기본값으로 두면 생기는 문제는 무엇인가.
  4. 명세 충족률이 높은 변형을 무조건 고르지 않는 까닭과, 먼저 보는 것은 무엇인가.
  5. git push origin main --follow-tags로 보존 태그가 올라가지 않는 까닭은 무엇인가.
