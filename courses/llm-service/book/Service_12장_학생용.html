[12장] 다중 프로덕트의 비교 구현

LLM 서비스 개발

12장

다중 프로덕트의 비교 구현

2027학년도 「LLM 서비스 개발」의 준비 중인 교재입니다. 편집 상태를 검토하기 위해 미리 공개한 것으로, 수업 전에 내용과 순서가 바뀔 수 있습니다.

학사 14주차 · 교재 12 · 4부 구현

9장부터 11장까지 하나의 명세에서 세 가지 프로덕트를 만들었다. 9장의 공고 모아보기는 브라우저 안에서만 도는 정적 웹이었고, 10장의 공고 요약은 LLM API를 서버 쪽에서 부르는 기능이었으며, 11장의 질의응답은 학과 취업 자료를 근거로 답하는 RAG 기능이었다. 세 장 모두 명세 한 판에서 구현 하나를 얻었다. 명세가 정하지 않은 곳은 Claude Code가 정했고, 그 결정이 좋은지 나쁜지는 견줄 대상이 없어 판단하기 어려웠다.

이 장은 같은 명세에서 구현을 둘 만든다. 공통 사례에 새 기능 「자기소개서 피드백」을 더하고, 이 기능을 대화형 화면(variant-chat)과 양식형 화면(variant-form)으로 각각 구현한다. 두 구현은 에이전트 개발 환경 Orca에서 내 PC의 작업 공간 두 개로 나란히 만든다. 작업 공간마다 git 작업 트리와 브랜치가 하나씩이고, 그 안에서 Claude Code 세션이 하나씩 돈다. 두 구현을 명세 충족률, 자동 검사, 휴리스틱 위반, 응답 시간, 호출 수와 토큰, 코드 규모로 같은 방법으로 재어 비교 기준표 jobprep/docs/비교구현.md를 채운다. 두 구현이 서로 다르게 정한 곳이 명세의 빈틈이며, 그 빈틈을 EARS 문장으로 명세에 보강한다. 6장에서 경쟁 서비스의 화면에서 명세를 되살린 리버스 엔지니어링을 자기 구현에 적용하는 방법도 이론과 [선택] 단계로 다룬다. 끝으로 어느 구현을 택했는지와 그 까닭을 결정 기록(ADR)으로 남기고, 택한 구현을 main에 병합하며, 택하지 않은 구현은 태그로 보존한 뒤 작업 공간을 정리한다.

프로젝트실습Ⅰ에서도 팀은 같은 갈림길을 여러 번 만난다. 화면을 대화형으로 할지 양식형으로 할지, 프롬프트를 한 번에 길게 줄지 단계로 나눌지를 회의에서 말로 정하면 결정의 근거가 남지 않는다. 이 장의 절차는 그 결정을 측정과 문서로 내리는 방법이다. 병합한 결과는 13장에서 동료가 사용성 평가로 다시 검증한다.

학습 목표

  • 같은 명세로 서로 다른 구현을 작업 공간 두 개에서 나란히 만든다. 변형의 축을 하나 정하고, 공통 지시와 변형별 차이로 나눈 지시문을 두 Claude Code 세션에 준다.
    • 예시: Orca에서 spec-v7을 출발점으로 작업 공간 variant-form과 variant-chat을 만들고, 같은 REQ-080~089를 각자의 새 세션으로 구현한다.
    • 활용: 프로젝트실습Ⅰ에서 화면 방식이나 프롬프트 전략을 놓고 팀의 의견이 갈릴 때, 둘 다 만들어 보고 정한다.
  • 비교 기준을 정하고 측정값으로 기준표를 채운다. 명세 충족률, 자동 검사, 휴리스틱 위반, 과업 시간, 호출 수와 토큰, 코드 규모를 같은 과업과 같은 도구로 잰다.
    • 예시: 모의 모드에서 양식형의 과업당 호출은 2회, 대화형은 3회이고, 대화형은 대화 이력을 매번 다시 보내 입력 토큰이 늘어난다.
    • 활용: “이쪽이 더 낫다”를 “과업당 토큰이 절반이고 충족률이 20%p 높다”로 바꾸어 보고한다.
  • 두 구현이 다르게 정한 곳에서 명세의 빈틈을 찾아 EARS로 보강한다. 두 세션의 보고, 화면 점검, 같은 요청의 응답 비교로 빈틈을 찾고, 구현에서 명세를 다시 뽑아 대조하는 방법을 안다.
    • 예시: 같은 답변을 두 구현이 378자와 281자로 다르게 세었다. 명세 REQ-082가 세는 방식을 정하지 않았기 때문이다.
    • 활용: 남이 만든 코드를 인수할 때 코드에서 명세를 뽑아 문서와 대조한다.
  • 결정을 기록하고 하나를 병합하며 다른 하나를 보존한다. ADR의 다섯 항목으로 결정을 쓰고, git merge --no-ff, 주석 태그, 작업 공간과 브랜치의 정리로 저장소에 남긴다.
    • 예시: ADR-001에 양식형 채택의 맥락과 결과를 쓰고, 대화형은 variant-chat-v1 태그로 남긴다.
    • 활용: 몇 달 뒤 “왜 대화형이 아니냐”는 질문에 기록과 태그로 답한다.

0. 시작하기

설치, 로그인, 키트 저장소의 클론, 가상 환경은 부록 A(A-7, A-8, A-12, A-13), Orca의 설치는 A-20, 매 수업의 시작 순서는 A-21을 따른다. 작업은 VS Code의 통합 터미널(A-4-3)과 Orca에서 한다. 명령을 치는 [터미널]은 Windows에서 Git Bash, macOS에서 기본 터미널이며, 터미널마다 가상 환경을 켠다(source ~/llm-service-lab/.venv/Scripts/activate, macOS는 .venv/bin/activate). 이 장은 터미널을 평소보다 많이 쓴다. 처음에는 확인용 [터미널] 하나와 Claude Code 하나로 시작하고, 핵심 실습에서 Orca의 작업 공간마다 터미널이 하나씩 더 생긴다.

  • 작업 폴더. 명령과 Claude Code는 ~/llm-service-lab/jobprep에서 실행한다. 프롬프트의 @docs/…는 이 폴더에서 본 경로이다. 핵심 실습의 두 Claude Code 세션은 각 작업 공간의 jobprep에서 시작한다.
  • 이 장의 실행 상한. 실제 모델은 Claude Code 대화형으로만 부른다. 0-3의 호출 모듈 확장 1회(필요한 학생만), 핵심 실습의 구현 2세션(변형마다 1)과 ADR 초안 1회이다. [선택] 단계는 추출 2세션과 대응 1회, REQ-090~093 반영 1회까지. 프로덕트의 LLM 호출은 모두 모의 모드(LLM_FAKE=1)이며, 실제 모델로 같은 과업을 되풀이해 재는 것(5-10)과 Orca의 오케스트레이션은 교수 시연이다.
  • 「읽기」 표시. 꼬리표에 「(읽기)」를 붙인 코드 블록은 따라 치지 않고 읽는다. 따라 치는 명령은 0절, 세 개의 따라 하기(2-5, 4-3, 5-9), 핵심 실습(9절)에 있다.

0-1. 키트 받기

키트 저장소에서 새 키트를 받아(git pull) 홈의 kits/로 복사한다(부록 A-12-3). 키트에는 기준 산출물(기준산출물/jobprep/)이 들어 있다. 키트가 저장소 밖에 있으므로 Claude Code가 진짜 jobprep/과 키트의 견본을 혼동해 견본을 고칠 일이 없다.

터미널

mkdir -p ~/kits && cp -rn ~/kits-repo/Service_12장 ~/kits/
ls ~/kits/Service_12장

시연기록/에는 교수가 수업 전에 실제 모델로 두 변형을 잰 기록(호출 기록, 시간 CSV, 요약)이 들어간다. 5-10에서 쓴다. 수업 전에 기록이 올라오지 않았으면 안내 파일만 있다.

10장부터 써 온 가상 환경 ~/llm-service-lab/.venv(부록 A-13)를 켜고 키트의 검사를 돌린다.

키트의 검사는 기준 산출물의 앱을 불러 쓰므로 requirements.txt가 11장 기준 산출물과 같은 패키지를 고정한다.

  • 확인 1 키트의 python -m pytest -q 마지막 줄이 9 passed이다(걸린 시간은 환경마다 다르다). 실패가 있으면 python --version이 3.12 이상인지, 가상 환경이 켜져 있는지(프롬프트 앞에 (.venv)) 본다.

0-2. 앞 장 산출물의 확인

이 장이 받는 것은 9~11장의 프로덕트다. 공고 모아보기 화면(jobprep/web/), 요약과 질의응답 API(jobprep/api/), 요구사항 명세서와 추적표, 인수 조건, 화면 명세(jobprep/docs/)가 있어야 한다.

1. 비교 구현의 목적

1-1. 같은 명세, 다른 경험

2026년판 「리버스 엔지니어링과 SDD」 수업의 예제 D에서는 포트폴리오 코드에서 명세를 뽑고, 그 명세만으로 다시 만든 재생성본을 원본과 나란히 놓았다[R1]. 두 화면은 같은 명세에서 나왔는데도 달랐고, 그 차이를 세 갈래로 나누었다.

  1. 문장. 눌렀을 때의 동작, 보여 주는 정보, 문구의 차이다. 요구사항 명세에 요구 한 줄(EARS)로 채운다.
  2. 그림. 배치, 간격, 색, 순서의 차이다. 문장으로 써도 해석이 갈리므로 화면 명세(8장의 화면 명세와 디자인 토큰)로 채운다.
  3. 사람이 준비하는 것. 실제 문구, 이미지, 색 값, 키처럼 문장으로도 그림으로도 정해지지 않는 것이다. 사람이 넣는다.

그때의 비교는 원본과 재생성본 사이였다. 원본은 사람이 만든 것이고 재생성본은 명세에서 나온 것이므로, 차이의 상당 부분은 원본 제작자가 명세로 옮기지 않은 결정이었다. 이 장의 비교는 다르다. 두 구현이 모두 같은 명세에서 나온다. 그런데도 두 구현이 다르다면, 그 차이는 명세가 정하지 않아 구현이 각자 정한 곳에서만 생긴다. 차이가 곧 명세의 빈틈을 가리키는 지표가 된다.

차이가 생기는 자리는 둘이다. 첫째는 이 장에서 일부러 다르게 지시한 축이다. 대화형과 양식형은 상호작용 방식을 다르게 하라고 시켰으므로 화면이 다른 것이 당연하다. 둘째는 지시하지 않았는데 달라진 곳이다. 예를 들어 두 구현이 글자 수를 서로 다르게 센다면, 그것은 지시의 차이가 아니라 명세의 빈틈 때문이다. 이 장의 6절과 핵심 실습의 9-8은 둘째 종류의 차이를 찾는 절차다.

같은 명세가 다른 경험을 낳는다는 것은 사용자에게도 중요하다. 명세의 모든 요구를 충족한 두 구현이 있어도, 한 사용자는 대화형에서 원하는 것을 바로 얻고 다른 사용자는 양식형에서 더 빨리 끝낸다. 명세 충족은 출발선일 뿐이며, 어느 경험이 대상 사용자에게 맞는지는 측정과 평가로 정한다.

1-2. 탐색과 선택

GitHub이 명세 주도 개발 도구 Spec Kit을 공개하며 쓴 글은, 명세가 구현과 분리되어 있으면 계획의 여러 변형을 요청해 견주거나 여러 판을 만들어 빠르게 실험할 수 있다고 설명한다[S1]. 사람이 손으로 구현하던 시절에는 같은 기능을 두 번 만드는 비용이 커서 하나를 정해 만들고 고쳐 나갔다. 구현을 AI가 맡으면 두 번째 구현의 비용은 지시문 하나와 검토 시간으로 줄어든다. 줄어든 비용만큼 “만들어 보고 고른다”는 선택지가 현실이 된다.

비교 구현은 두 단계로 이루어진다.

  1. 탐색(exploration). 명세가 열어 둔 공간에서 서로 다른 해법을 둘 이상 만든다. 이 단계의 목표는 좋은 구현이 아니라 서로 다른 구현이다. 비슷한 두 구현은 비교해도 배울 것이 적다.
  2. 선택(selection). 정해 둔 기준으로 견주어 하나를 고르고, 고른 까닭과 버린 것의 장점을 기록한다. 선택한 구현만 다음 단계(13장의 평가)로 간다.

탐색을 무한히 넓히지 않는 것도 중요하다. 변형이 셋을 넘으면 측정과 대조에 드는 시간이 구현 시간보다 커진다. 이 장은 변형을 둘로 정한다.

1-3. A/B 테스트와의 차이

같은 기능의 두 판을 견주는 방법으로 가장 널리 알려진 것은 A/B 테스트다. A/B 테스트는 실제 사용자를 두 무리로 나누어 서로 다른 판을 보여 주고, 전환율 같은 지표로 어느 판이 나은지 통계적으로 가린다. 닐슨은 A/B 테스트가 실제 사용자의 실제 행동을 재고 작은 차이도 가려낼 수 있지만, 분명한 목표 하나가 있을 때만 쓸 수 있고, 완성된 구현과 실제 트래픽이 필요하며, 왜 그런 결과가 나왔는지는 말해 주지 않는다고 정리하였다[U17].

1-4. 비교 구현의 비용과 한계

비교 구현은 공짜가 아니다. Claude Code 세션이 둘이므로 구현에 드는 사용량이 두 배가 되고, 사람이 읽어야 할 계획, 보고, 변경도 두 배가 된다. 측정과 대조에 드는 시간까지 더하면, 기능 하나를 하나만 만들 때보다 두세 배의 시간이 든다. 그러므로 모든 기능을 둘씩 만들지 않는다. 비교 구현이 값을 하는 경우는 다음과 같다.

  • 선택이 뒤에서 바꾸기 어려운 구조를 정할 때. 상호작용 방식, 데이터의 저장 위치, 외부 API의 선택처럼 한번 정하면 다른 기능이 그 위에 쌓이는 결정이다.
  • 팀 안에서 의견이 갈리고, 어느 쪽도 근거를 내놓지 못할 때. 회의를 한 번 더 하는 것보다 둘 다 만들어 재는 편이 빠르다.
  • 명세가 새로 쓰였고 아직 검증되지 않았을 때. 두 구현의 차이로 명세의 빈틈을 찾는 효과가 크다.

반대로 단추 문구나 색처럼 되돌리기 쉬운 결정, 이미 검증된 명세의 작은 확장에는 쓰지 않는다.

비교에는 사람의 치우침도 끼어든다. 먼저 만든 변형을 오래 들여다보면 그쪽에 정이 들고(매몰 비용), 처음 본 숫자가 판단의 기준점이 된다(기준점 효과). 이 장이 기준을 구현 전에 정하고, 두 변형을 동시에 만들고, 같은 시나리오로 재는 것은 이 치우침을 줄이기 위해서다. 그래도 남는 치우침은 결정 기록의 「결과」에 버린 쪽의 장점을 적는 것으로 드러낸다.

2. 변형의 축과 변형 설계

2-1. 변형의 세 축

같은 명세의 구현을 다르게 만드는 방향을 변형의 축이라 부른다. LLM 기능이 들어간 서비스에서 자주 쓰는 축은 세 가지다.

축 무엇을 바꾸나 공통 사례의 예 주로 갈리는 기준
상호작용 방식 사용자가 입력하고 결과를 받는 방식 대화형 화면과 양식형 화면 휴리스틱 위반, 과업 시간, 호출 수
프롬프트 전략 LLM에 일을 시키는 방식 한 번에 세 부분을 다 쓰게 하기와, 강점·보완점·예시를 세 번에 나누어 부르기 호출 수, 토큰, 출력 품질
구현 기술 같은 동작을 만드는 기술 서버에서 화면을 만들기(FastAPI 템플릿)와 브라우저에서 만들기(자바스크립트) 코드 규모, 응답 시간, 유지 보수

세 축은 서로 독립이 아니다. 대화형을 고르면 대화 이력을 보내야 하므로 프롬프트 전략이 따라 바뀐다. 그래도 한 번의 비교에서 의도적으로 바꾸는 축은 하나로 한다. 두 축을 함께 바꾸면 결과의 차이가 어느 축에서 왔는지 가릴 수 없기 때문이다. 실험에서 한 번에 한 변수만 바꾸는 것과 같은 원리다.

2-2. 상호작용 방식: 대화형과 양식형

이 장은 상호작용 방식을 축으로 고른다. LLM 서비스에서 가장 먼저 부딪히는 갈림길이기 때문이다. 채팅 화면은 LLM 서비스의 기본 모양처럼 여겨지지만, 모든 과업에 맞지는 않는다.

구분 대화형(chat) 양식형(form)
입력 자유로운 문장. 한 번에 하나씩 정해진 칸(문항, 제한, 답변). 한 번에 모두
출력 문장. 구조는 모델이 정한다 정해진 칸(강점, 보완점, 예시)
강점 이어서 묻기, 좁혀 가기, 예상하지 못한 요청 빠짐없는 입력, 결과의 비교와 검사, 적은 호출
약점 무엇을 물어야 할지 사용자가 떠올려야 한다. 이력이 길어진다 정해진 칸 밖의 요청을 받지 못한다
LLM 호출 메시지마다 한 번, 이력 전체를 함께 보낸다 제출마다 한 번

대화형의 첫째 약점은 닐슨 노먼 그룹이 「표현의 장벽(articulation barrier)」이라 부른 문제와 닿아 있다. 원하는 것을 글로 정확히 쓰기 어렵다는 것이다. 이 그룹의 글은 생성형 AI 화면에서 글 입력만 주지 말고, 선택지나 제안 같은 그래픽 요소를 섞어 기억해서 쓰는 부담을 줄이자고 제안한다[U19]. 또 다른 글은 입력란 주변에 두는 단추, 메뉴, 제안 문장 같은 「프롬프트 컨트롤」이 사용자가 무엇을 할 수 있는지 알려 주고 입력을 줄인다고 정리하였다[U18]. 양식형은 이 생각을 끝까지 밀어붙인 모양이다.

두 방식 사이에는 섞은 모양도 있다. 대화창을 두되 첫 입력은 양식으로 받거나, 대화의 응답 아래에 「보완점 첫째를 예시로」 같은 단추를 두는 방식이다. 실제 서비스는 대개 이런 혼합형으로 간다. 이 장에서 혼합형을 셋째 변형으로 만들지 않는 까닭은 1-2의 원칙(변형은 서로 달라야 하고, 수는 둘로 한다) 때문이다. 양 끝의 두 변형을 재어 보면, 혼합형에서 어느 쪽의 무엇을 가져올지 근거를 가지고 정할 수 있다.

대화형의 둘째 약점은 비용과 맞닿아 있다. Claude의 Messages API는 상태를 기억하지 않는다(stateless). 대화를 이어 가려면 매번 대화 전체를 다시 보내야 한다[A1]. 대화가 세 번 오가면 셋째 요청에는 앞의 두 번이 모두 실려 가고, 입력 토큰이 그만큼 늘어난다. 이 장의 측정에서 이 차이가 숫자로 드러난다.

2-3. 프롬프트 전략과 구현 기술을 축으로 할 때 [선택]

같은 절차는 다른 두 축에도 쓰인다. 프롬프트 전략을 축으로 하면 화면과 API 계약은 같게 두고 api/feedback.py의 호출 방식(한 번에 세 부분을 받기, 세 번에 나누어 부르기)만 다르게 지시한다. 휴리스틱 위반은 비슷하게 나오므로 비교의 무게는 호출 수, 토큰, 과업 시간, 출력의 질(10장의 평가 문항과 채점 기준)로 옮겨 간다. 구현 기술을 축으로 하면 같은 화면을 브라우저의 자바스크립트가 그리거나 서버가 HTML로 만들어 보내며, 차이는 코드 규모, 검사의 쉬움, 응답 시간의 구성에서 난다. 어느 축이든 바뀌지 않는 것(화면, 계약)은 공통 지시에, 그 축의 내용만 차이 파일에 적는다.

2-4. 공통 사례의 변형 기능: 자기소개서 피드백

변형을 비교할 기능으로 「자기소개서 피드백」을 고른다. 설계안이 10장의 LLM 기능 후보로 「공고 요약」과 함께 들었던 기능이다. 후보였던 「면접 준비 도우미」 대신 이 기능을 고른 까닭은 다음과 같다.

기준 자기소개서 피드백 면접 준비 도우미
두 방식이 모두 자연스러운가 그렇다. 양식(문항, 제한, 답변)도, 대화(붙여 넣고 더 묻기)도 쓰인다 대화 쪽으로 기운다. 질문과 답이 오가는 과업이다
입력과 출력의 구조 입력이 길고 구조가 있다(문항, 글자 수 제한). 출력도 나눌 수 있다(강점, 보완점, 예시) 질문 하나, 답 하나로 구조가 약하다
앞 장과의 연결 9장의 공고(자격 요건), 11장의 취업 자료(작성 안내)를 쓴다 11장의 자료를 쓴다
검사 가능성 세 부분의 존재, 글자 수, 짧은 답변 거부를 자동으로 검사할 수 있다 답의 좋고 나쁨을 자동으로 가리기 어렵다

한쪽 방식에 유리한 기능을 고르면 비교의 결론이 처음부터 정해진다. 자기소개서 피드백은 두 방식이 모두 실제 서비스에 있는 과업이라 비교할 가치가 있다.

명세는 키트의 명세추가_자기소개서피드백.md가 준다. 이 장의 주제는 명세를 쓰는 일이 아니라 같은 명세의 구현을 견주는 일이므로, 6장의 방법으로 쓴 명세 한 절을 받아서 쓴다. 다만 그대로 붙이지 말고 먼저 읽는다.

3. 변형별 브랜치와 작업 트리

2장에서 브랜치를 만들고 오가는 법을 배웠고, 3장에서 기능마다 브랜치를 두어 풀 리퀘스트로 합쳤다. 이 장의 브랜치는 성격이 다르다. 기능 브랜치는 결국 모두 main에 합쳐지지만, 변형 브랜치는 둘 중 하나만 합쳐진다. 다른 하나는 비교의 근거로 남는다.

3-1. 브랜치 전환 방식

가장 단순한 방법은 저장소 폴더 하나에서 브랜치를 바꾸어 가며 작업하는 것이다.

[터미널] (읽기)

git switch -c variant-form      # 양식형 구현, 커밋
git switch main
git switch -c variant-chat      # 대화형 구현, 커밋
git switch variant-form         # 양식형을 다시 보려면 전환

git switch는 작업 폴더의 파일을 그 브랜치의 내용으로 바꾼다[G4]. 폴더가 하나뿐이므로 한 번에 한 변형만 디스크에 있다. 이 방식에는 세 가지 불편이 있다.

  1. 두 변형의 서버를 동시에 띄울 수 없다. 응답 시간을 번갈아 재야 하고, 화면을 나란히 놓고 볼 수 없다.
  2. Claude Code가 한 변형을 구현하는 동안 다른 변형을 진행할 수 없다.
  3. 커밋하지 않은 변경이 있으면 전환이 거부된다. 다른 브랜치의 같은 파일을 덮어쓰게 되기 때문이다.

셋째 경우의 화면은 다음과 같다. 집필 때 버려도 되는 연습 저장소에서 일부러 만든 상황이다.

error: Your local changes to the following files would be overwritten by checkout:
    greet.txt
Please commit your changes or stash them before you switch branches.
Aborting

3-2. git worktree

git worktree는 저장소 하나에 작업 폴더를 여러 개 붙인다[G2]. 처음부터 있던 폴더를 주 작업 트리(main worktree), 새로 붙인 폴더를 연결 작업 트리(linked worktree)라 부른다. 작업 트리마다 다른 브랜치를 꺼내 둘 수 있으므로, 두 변형이 동시에 디스크에 있게 된다.

명령 하는 일
git worktree add <경로> -b <새 브랜치> 지금 커밋에서 새 브랜치를 만들고 <경로>에 꺼낸다
git worktree add <경로> <브랜치나 태그> 이미 있는 브랜치(또는 태그, 커밋)를 <경로>에 꺼낸다
git worktree list 주 작업 트리를 먼저, 연결 작업 트리를 이어서 보인다
git worktree remove <경로> 연결 작업 트리를 지운다. 추적하지 않는 파일이나 바뀐 파일이 있으면 거부한다
git worktree prune 폴더를 손으로 지워 버린 작업 트리의 관리 정보를 정리한다

작업 트리끼리 무엇을 함께 쓰고 무엇을 따로 쓰는지 알아 두어야 한다. 커밋, 브랜치, 태그 같은 저장소의 기록은 모두 함께 쓴다. 한 작업 트리에서 만든 커밋이 다른 작업 트리의 git log --all에 바로 보인다. 반면 HEAD(지금 꺼낸 브랜치)와 인덱스(스테이징 영역)는 작업 트리마다 따로다[G2]. 그래서 같은 브랜치를 두 작업 트리에 동시에 꺼낼 수 없다. 한쪽에서 커밋하면 다른 쪽의 작업 폴더가 그 브랜치와 어긋나기 때문이다.

fatal: 'variant-form' is already used by worktree at 'C:/Users/아이디/orca/workspaces/llm-service-lab/variant-form'

이 메시지는 실수가 아니라 보호 장치다. 주 작업 트리에서 variant-form을 보려면 전환하지 말고 그 작업 트리 폴더로 간다.

작업 트리는 추적하는 파일만 새로 꺼낸다. .gitignore가 거르는 파일, 즉 .env, 가상 환경, api/logs/, __pycache__/는 새 작업 트리에 없다. 이 장에서 이 성질은 오히려 쓸모가 있다. 변형마다 호출 기록 api/logs/llm_calls.jsonl이 따로 생겨 섞이지 않는다.

git worktree list와 git branch는 작업 트리를 다음처럼 보인다. 집필 때 연습 저장소에서 variant-b 브랜치를 옆 폴더에 꺼낸 화면이다(읽기).

C:/Users/아이디/ch12-연습/git-연습    38fbf4f [main]
C:/Users/아이디/ch12-연습/git-연습-b  9b3d962 [variant-b]
* main
  variant-a
+ variant-b

*는 지금 작업 트리의 브랜치, +는 그 브랜치가 다른 작업 트리에 꺼내져 있다는 뜻이다[G4]. 연결 작업 트리에서 만든 커밋은 주 작업 트리의 git log variant-b에 바로 보이고, git worktree remove로 폴더를 지워도 브랜치와 커밋은 남는다. 작업 트리는 브랜치를 꺼내 두는 폴더일 뿐이기 때문이다.

3-3. Claude Code의 작업 트리 기능

Claude Code도 작업 트리를 직접 만든다. claude --worktree <이름>(줄여서 -w)으로 시작하면 저장소 루트의 .claude/worktrees/<이름>/에 작업 트리를 만들고 worktree-<이름> 브랜치를 꺼낸 뒤 그 안에서 세션을 연다[C8]. 2026-11 기준으로 확인한 동작은 다음과 같다.

  • 출발점. 기본값은 원격의 기본 브랜치(대개 origin/main)다. 설정 worktree.baseRef를 "head"로 하면 지금의 HEAD에서 출발한다.
  • 끝낼 때. 이름을 주지 않은 세션은 바뀐 것이 없으면 작업 트리를 지운다. 바뀐 것이 있으면 남길지 지울지 묻는다.
  • 무시 파일. .env 같은 무시 파일은 저장소 루트의 .worktreeinclude(형식은 .gitignore와 같다)에 적은 것만 복사한다.
  • 권장 설정. 문서가 권하는 대로 기준 산출물의 .gitignore에 .claude/worktrees/가 들어 있다.

이 장의 핵심 실습은 Orca(3-4)로 작업 공간을 만들고, --worktree는 쓰지 않는다. 까닭은 세 가지다. 첫째, 브랜치 이름을 variant-form처럼 뜻이 드러나게 정할 수 있다. 둘째, 출발점을 명세를 커밋한 spec-v7로 분명히 정할 수 있다. 기본 설정의 --worktree는 원격의 기본 브랜치에서 출발하므로, 명세 커밋을 아직 푸시하지 않았으면 명세가 없는 상태에서 출발한다. 셋째, 두 세션을 한 화면에 나란히 두고 작업 공간마다 터미널과 diff 화면을 붙이는 일은 Orca가 맡는다. Claude Code 문서도 특정 브랜치를 꺼내거나 저장소 밖에 둘 때는 git으로 직접 만들라고 안내한다[C8].

[최신 자료 자리: Claude Code의 작업 트리 기능과 이 장이 쓰는 옵션] --worktree(-w)의 위치·브랜치 이름·출발점·.worktreeinclude의 동작, 그리고 9절이 쓰는 -n(--name), --permission-mode plan, /model, /effort, /resume의 이름. 확인할 곳은 https://code.claude.com/docs/en/worktrees, https://code.claude.com/docs/en/cli-reference와 내 PC의 claude --help다. 2026-11-16에 집필 PC의 Claude Code 2.1.296에서 claude --help로 -n, --name, -w, --worktree [name], --permission-mode가 있음을 확인하였다. 위 다섯 줄의 동작은 2026-11-14에 문서로 확인한 것이다.

3-4. Orca: 작업 트리 위의 에이전트 개발 환경

Orca는 MIT 사용권의 무료 공개 소프트웨어로 macOS, Windows, 리눅스에서 돈다[O1]. 작업마다 git 작업 트리를 만들고 그 안에서 Claude Code 같은 CLI 에이전트를 나란히 실행한다[O2]. 이런 도구를 에이전트 개발 환경(ADE, Agentic Development Environment)이라 부른다. 이 과목은 내 PC의 저장소를 Orca에서 로컬로 연다. 에이전트와 git 명령이 모두 내 PC에서 돌고[O3], Orca 자체에는 계정이 필요 없으며, Orca의 터미널에서 실행한 Claude Code가 각자의 구독 계정을 그대로 쓴다(부록 A-20).

[최신 자료 자리: Orca의 판과 이 장이 쓰는 메뉴 이름] 판, 저장소를 더하는 메뉴, 작업 트리 만들기 창의 Run on·Branch from·Advanced의 Branch name, 에이전트 권한(Manual, Auto, Yolo), 오케스트레이션이 실험 기능(Settings → Experimental)인지. 확인할 곳은 https://github.com/stablyai/orca/releases와 https://orca.dev/docs/이다. 2026-11-16 확인 값: v1.4.261, 메뉴 이름은 본문과 같다. 로컬 실행에서 Run on 칸이 어떤 이름으로 보이는지와 작업 트리를 만드는 폴더는 문서에서 확인하지 못하였다. 수업 전에 다시 확인한다.

Orca를 쓸 때 알아 둘 성질은 넷이다. 모두 Orca 문서의 작업 트리 절에 있다[O2].

  1. 실제 git 작업 트리. Orca의 작업 공간은 모두 실제 git 작업 트리다. 그래서 3-2의 설명이 그대로 맞고, 무엇을 만들었는지는 늘 확인 터미널의 git worktree list로 확인할 수 있다. 반대로 git worktree add로 만든 작업 트리는 Orca 목록에 저절로 나타나지 않는다.
  2. 출발점의 기본값. 브랜치 이름은 작업 이름에서 정해지고, 출발점(Branch from)의 기본은 대개 origin/main이다. 푸시하지 않은 커밋에서 출발하려면 반드시 바꾼다. 3-3의 --worktree와 같은 함정이다.
  3. 삭제. Orca에서 작업 공간을 삭제하면 확인을 받은 뒤 작업 트리 폴더와 브랜치를 함께 지운다. 남길 변형은 8-2처럼 태그를 먼저 붙인다.
  4. 자동 정리. 작업 트리의 자동 정리 규칙은 기본으로 꺼져 있으므로 정리는 사람이 한다.

여러 에이전트를 조정자와 작업자로 나누어 돌리는 Orca의 오케스트레이션은 실험 기능이므로[O4] 교수 시연으로만 본다. 조정자와 작업자가 각자 모델을 불러 사용량을 사람이 예측하기 어렵기 때문이다.

3-5. 세 방식의 비교

기준 브랜치 전환(폴더 하나) git worktree 명령(폴더 여럿) Orca(ADE)
두 변형을 동시에 실행 불가 가능(포트를 나눈다) 가능(작업 공간마다 터미널)
Claude Code 두 세션을 동시에 불가 가능(터미널을 나누어 연다) 가능(작업 공간마다 에이전트를 한 화면에)
브랜치 이름과 출발점 사람이 정한다 사람이 명령에 적는다 작업 이름에서 정하고, 출발점의 기본은 대개 origin/main이다
디스크 사용 작다 작업 트리마다 파일 사본 같다(실제 git 작업 트리)
커밋하지 않은 변경 전환을 막는다 작업 트리마다 따로 있어 막지 않는다 같다. diff 화면에서 줄마다 본다
무시 파일(.env, 기록) 공유 작업 트리마다 따로 따로. 설정한 경로만 복사하거나 잇는다
정리 브랜치만 지운다 작업 트리를 지우고 브랜치를 지운다 삭제 하나가 작업 트리와 브랜치를 함께 지운다

컴퓨터 자원이 부족하거나 변형이 한 파일만 다르면 브랜치 전환으로 충분하다. 이 장처럼 두 변형을 나란히 실행해 재야 하면 작업 트리가 맞다. 명령과 Orca는 결과가 같다. Orca는 작업 트리 방식 위에 화면을 얹은 것이므로, 출발점과 정리는 어느 쪽으로 했든 git 명령으로 확인한다[O2]. Orca를 쓸 수 없는 PC에서는 같은 절차를 3-2의 명령으로 하며, 그때의 순서는 교수가 안내한다.

3-6. 작업 트리와 실행 환경

공통 사례에 작업 공간을 쓸 때 실행 환경에서 챙길 것이 셋 있다.

  1. 가상 환경. .venv/는 무시 목록에 있어 작업 공간으로 따라가지 않는다. 어느 작업 공간의 터미널에서든 source ~/llm-service-lab/.venv/Scripts/activate(macOS는 .venv/bin/activate)로 주 작업 트리의 가상 환경을 켜서 같은 환경을 쓴다. Claude Code도 가상 환경을 켠 터미널에서 실행한다.
  2. .env와 키. 이 장의 측정은 모두 키가 필요 없는 모의 모드로 하므로, 작업 공간에 .env를 복사하지 않고 명령마다 LLM_FAKE=1을 붙인다. 교수 시연(5-10)에서 복사한 .env는 무시 파일이라 커밋되지 않고, 작업 공간을 지울 때 함께 지워진다.
  3. 포트. 두 변형의 서버를 같은 PC에서 동시에 띄우므로 포트를 나눈다. API의 고정 포트 8000(부록 A-16)을 variant-form에, 둘째 서버인 variant-chat에 8001을 쓴다. 각 서버가 자기 변형의 웹을 같은 출처에서 보내므로 8100의 정적 서버는 쓰지 않는다(10장). 서버마다 JOBPREP_VARIANT를 주어 호출 기록에 변형 이름이 남게 한다.

서버를 띄우는 명령은 9-6에 있다.

4. 변형 지시문

4-1. 같은 명세를 두 번 주는 원칙

두 구현의 차이가 의도한 축에서만 생기게 하려면, 지시의 나머지를 똑같이 맞추어야 한다. 어긋나기 쉬운 곳과 맞추는 방법은 다음과 같다.

어긋나는 곳 생기는 일 맞추는 방법
지시문의 문장 한쪽에만 “테스트를 꼼꼼히”를 쓰면 그쪽만 테스트가 많다 공통 지시를 파일로 쓰고 두 세션에 같은 파일을 준다
대화의 앞 내용 두 번째 변형을 같은 세션에서 시키면 첫 구현을 보고 따라 한다 변형마다 새 세션을 연다
출발 커밋 한쪽이 명세 수정 전 커밋에서 출발한다 두 브랜치를 같은 커밋(spec-v7)에서 만든다
모델과 노력 수준 한쪽만 높은 수준으로 돌린다 /model, /effort를 두 세션에서 같게 둔다
사람의 개입 한쪽에만 중간에 추가 요구를 한다 개입은 질문에 답하는 것으로 한정하고, 답을 두 세션에 똑같이 준다

새 세션을 여는 까닭은 Claude Code 모범 사례 문서에도 있다. 명세 파일을 만든 뒤에는 새 세션에서 그 파일로 구현을 시작하라고 권한다. 깨끗한 맥락과 글로 적힌 완료 기준에서 출발하기 위해서다[C6]. 이 장에서는 그 이유가 하나 더 있다. 앞 변형의 대화가 남아 있으면 두 번째 구현은 독립된 구현이 아니게 된다.

4-2. 지시문의 구조: 공통과 차이

지시문은 세 파일로 나눈다. 공통 지시 하나와 변형별 지시 둘이다. 변형별 파일에는 공통 지시와 다른 것만 적는다. 그러면 두 변형의 차이가 무엇인지 파일 두 개의 diff로 바로 보인다.

  • docs/변형지시/공통.md: 기준 문서, 할 일, 하지 말 것, 보고 형식. 두 세션에 똑같이 준다.
  • docs/변형지시/form.md: 상호작용 방식, API 계약, 파일 이름. form 세션에만 준다.
  • docs/변형지시/chat.md: 같은 항목의 대화형 판. chat 세션에만 준다.

5. 비교 기준과 측정

5-1. 비교 기준표

비교를 시작하기 전에 기준을 정해 둔다. 구현을 보고 나서 기준을 정하면, 마음에 드는 쪽이 이기는 기준을 고르게 된다. 이 장은 다음 여덟 기준을 쓴다.

기준 정의 재는 법 해석할 때 주의
명세 충족률 (충족 + 0.5 × 부분) ÷ (전체 − 해당없음) 점검표를 손으로 채우고 spec_checklist.py로 센다 판정은 관찰한 근거를 함께 적어야 의미가 있다
자동 검사 통과 같은 검사 5개 가운데 통과 수, 변형 자신의 테스트 통과 수 check_common.py, pytest -q 변형 자신의 테스트는 수가 아니라 실패 여부만 본다. 테스트를 많이 쓴 쪽이 이기면 안 된다
휴리스틱 위반 수 닐슨의 10가지에 어긋나는 문제의 수 화면을 써 보며 표에 적는다 평가자 한 명의 빠른 점검이다. 정식 평가는 13장
과업 시간 과업 하나(시나리오)를 끝내는 데 걸린 시간의 중앙값 measure_latency.py 모의 모드의 시간은 흉내 낸 값이다
과업당 호출 수 과업 하나에 든 LLM 호출 수 token_report.py 사용자가 실제로 하는 행동을 시나리오가 잘 옮겼는가
과업당 토큰 입력 토큰 + 출력 토큰 token_report.py 모의 모드는 글자 수로 어림한 값이다
과업당 비용 토큰 × 단가 token_report.py --price-in --price-out 단가는 수업 직전에 공식 가격표에서 확인한다
코드 규모 변형이 더한 줄 수 git diff --shortstat main...<브랜치> 작은 것이 좋다는 뜻이 아니다. 같은 충족률이면 작은 쪽이 고치기 쉽다

기준마다 「더 나은 쪽」의 방향이 정해져 있다. 충족률과 통과 수는 클수록, 위반 수, 시간, 호출 수, 토큰, 비용은 작을수록 낫다. 코드 규모는 방향보다 충족률과 함께 읽는다.

기준끼리 결론이 엇갈리는 것이 보통이다. 한 변형은 충족률이 높고 다른 변형은 비용이 낮을 수 있다. 이때 기준표에서 바로 결론을 내지 말고, 먼저 「넘으면 안 되는 선」을 확인한다. 명세의 필수 요구를 충족하지 못하거나(미충족), 공통 검사에 실패하거나, 비용이 교수가 정한 한도를 넘는 변형은 다른 기준이 아무리 좋아도 고르지 않는다. 선을 넘지 않은 변형끼리는 대상 사용자의 문제(5장의 문제 정의)에 가장 가까운 기준을 앞에 둔다. 그 순서를 7절의 결정 기록에 적는다.

여덟 기준에 가중치를 주어 점수 하나로 합치지 않는다. 합친 점수는 보기 편하지만, 가중치를 어떻게 주느냐에 따라 결론이 바뀐다. 기준표는 기준별로 나란히 보이고, 어느 기준을 더 무겁게 볼지는 7절의 결정 기록에서 맥락과 함께 밝힌다.

5-2. 명세 충족 점검표

명세 충족률은 요구 하나하나를 실제로 써 보고 판정해서 얻는다. 판정은 네 가지 중 하나다.

  • 충족: 요구의 모든 부분을 관찰했다. 예: 50자 미만이면 안내가 나오고 호출 기록이 늘지 않는다.
  • 부분: 요구의 일부만 관찰했다. 예: 첫 답변의 글자 수는 세지만 고친 답변은 세지 않는다.
  • 미충족: 관찰하지 못했다. 예: 공고를 고르는 수단이 없다.
  • 해당없음: 그 변형에 해당하는 경우가 없다. 드물며, 쓰면 까닭을 근거 칸에 적는다.

근거 칸에는 무엇을 보고 판정했는지 적는다. “됨”만 적으면 나중에 다른 사람이 같은 판정에 이를 수 없다. 키트의 연습 점검표는 다음과 같으며, 5-9에서 집계 도구로 센다.

|---|---|---|---|
| DL-01 | 남은 날 수 | 충족 | 카드에 「D-5」 표시 |

판정 칸에 정해진 말이 아닌 것(예: “거의”, “됨”)을 쓰면 도구가 그 줄을 「판정을 읽지 못함」으로 알려 주고 끝 상태 코드 1로 끝난다.

두 변형에 같은 시험지를 내는 것이 공통 자동 검사다. 키트의 check_common.py는 피드백 요구 가운데 자동으로 판정할 수 있는 다섯 개를 검사한다.

검사 보내는 것 통과 조건

REQ-082 같은 답변, 제한 100 초과를 알린다

REQ-087의 검사 방법은 따로 짚어 둔다. 「남기지 않는다」는 부정형 요구는 응답만 보아서는 판정할 수 없다. 그래서 검사용 답변에 다른 곳에 나올 리 없는 표지 문장을 넣어 보내고, 검사를 시작한 뒤 바뀐 모든 파일(호출 기록 포함)에서 그 문장을 찾는다. 하나라도 나오면 실패이고, 어느 파일인지 출력한다. 이 방법은 데이터베이스나 외부 서비스에 남기는 경우는 잡지 못하므로, 그런 저장소를 쓰는 구현이라면 검사를 늘려야 한다.

두 변형의 API 모양이 다르므로, 요청을 어떻게 만들고 응답의 어디를 볼지는 검사 어댑터가 정한다. 어댑터는 4절의 API 계약을 기계가 읽는 모양으로 옮긴 것이다.

파일: ~/kits/Service_12장/검사어댑터/chat.json 
{
  "variant": "chat",
  "path": "/api/feedback/chat",
  "body": {"question": "{question}", "limit": "{limit}", "job_id": null,
           "messages": [{"role": "user", "content": "{answer}"}]},
  "parts": {"mode": "text", "field": "reply", "markers": ["강점", "보완", "예시"]},
  "over_limit": {"mode": "text", "field": "reply", "contains": "초과"}
}

양식형 어댑터는 parts를 "mode": "fields"로 두고 strengths, improvements, rewrite 칸을 본다. 검사는 서버를 띄우지 않고 같은 프로세스 안에서 앱을 불러 모의 모드로 돈다. 아직 변형이 없는 main에 돌리면 경로 /api/feedback가 없다(HTTP 405)와 통과 0/5로 끝난다(5-9에서 직접 본다). 405가 나오는 까닭은 기준 산출물이 /에 정적 화면을 연결해 두어, 없는 경로에 대한 POST가 “허용되지 않는 메서드”로 처리되기 때문이다. 핵심 실습에서 변형을 구현한 뒤 같은 명령이 통과 5/5가 되어야 한다.

자동 검사가 두 변형에서 모두 통과하는 일은 흔하다. 그렇다고 비교가 무의미한 것은 아니다. 자동 검사는 최소 조건을 지키는지 확인할 뿐이고, 두 구현의 차이는 대개 자동으로 판정하기 어려운 곳(경험, 비용, 명세 밖의 결정)에 있다.

5-4. 응답 시간의 측정

응답 시간은 사용자가 과업을 끝내기까지 기다린 시간으로 잰다. 요청 하나의 시간이 아니라 과업 하나의 시간을 재는 까닭은, 대화형은 같은 과업에 요청이 더 많기 때문이다. 요청 하나가 빨라도 과업 전체는 느릴 수 있다.

과업은 시나리오 파일로 정한다. 키트의 두 시나리오는 같은 과업 「초안으로 피드백을 받고, 고친 답변으로 한 번 더 확인한다」를 두 방식으로 옮긴 것이다.

[파일: ~/kits/Service_12장/시나리오/chat.json] 단계 부분

"steps": [
  {"path": "/api/feedback/chat", "say": "{answer}"},
  {"path": "/api/feedback/chat", "say": "보완점 첫째를 고친 예시 문장으로 보여 줘."},
  {"path": "/api/feedback/chat", "say": "{answer_revised}\n\n위처럼 고쳤다. 다시 봐 줘."}
]

say 단계는 앞 단계의 응답을 대화 이력에 붙여 다음 요청에 함께 보낸다. 양식형 시나리오는 같은 과업을 요청 두 번(초안, 고친 답변)으로 옮긴다. 대화형에 요청이 하나 더 있는 것은 대화형에서 사용자가 실제로 하는 행동(예시를 더 묻기)을 넣었기 때문이다. 시나리오가 실제 행동을 잘 옮겼는지는 비교의 공정성을 좌우하므로 비교구현.md에 시나리오 파일 이름을 적는다.

측정 도구 measure_latency.py의 동작은 다음과 같다.

  1. 시계. 파이썬의 time.perf_counter()로 잰다. 이 시계는 짧은 시간을 재는 데 쓰는, 해상도가 가장 높은 단조 시계다. 시스템 시각이 바뀌어도 거꾸로 가지 않는다[P1]. time.time()은 시각을 알려 주는 시계이므로 시간 간격을 재는 데 쓰지 않는다.
  2. 준비 실행. 첫 실행은 모듈을 불러오고 연결을 여느라 느리다. --warmup 1(기본값)로 한 번 돌리고 재지 않는다.
  3. 반복과 중앙값. --repeat 5로 다섯 번 재고 중앙값을 보고한다. 평균은 한 번 튄 값에 크게 끌려가지만 중앙값은 덜 끌려간다.
  4. 두 가지 대상. --base http://127.0.0.1:8000은 실행 중인 서버에 HTTP로 보낸다. --app-dir <jobprep>은 같은 프로세스 안의 앱에 보내므로 네트워크 시간이 빠진다. 비교 기준표에는 --base로 잰 값을 쓴다.

5-5. 호출 수, 토큰, 비용

LLM 호출의 비용은 토큰으로 정해진다. Messages API의 응답에는 usage 객체가 있고, 그 안의 input_tokens와 output_tokens가 그 호출에서 쓴 입력과 출력 토큰 수다[A1]. 기준 산출물의 llm.py는 실제 호출에서는 이 두 값을, 모의 모드에서는 글자 수로 어림한 값(10장과 같이 글자 수에 0.8을 곱한 값)을 호출 기록에 남긴다.

비용은 다음 식으로 어림한다.

과업당 비용 = (입력 토큰 × 입력 단가 + 출력 토큰 × 출력 단가) ÷ 1,000,000 ÷ 과업 수

단가는 백만 토큰당 달러로 공시된다. 2026-11-14에 공식 모델 개요 표에서 확인한 값 가운데 하나를 예로 들면, Claude Haiku 4.5는 입력 1달러, 출력 5달러다[A4]. 같은 표의 다른 모델은 단가가 다르고, 단가는 바뀔 수 있다. 수업에서 쓰는 단가는 그날 공식 가격표에서 확인해 비교구현.md에 날짜와 함께 적는다. 출력 단가가 입력 단가의 몇 배이므로, 출력을 짧게 하는 설계(예: 정해진 칸만 출력)가 비용에 크게 듣는다.

[최신 자료 자리: 수업에서 쓰는 모델의 토큰 단가] token_report.py의 --price-in, --price-out에 넣을 값. 확인할 곳은 https://platform.claude.com/docs/en/about-claude/models/overview와 https://platform.claude.com/docs/en/about-claude/pricing이다. 이 절의 예(입력 1달러, 출력 5달러)는 2026-11-14에 확인한 Claude Haiku 4.5의 단가다. 2026-11-16에 다시 확인한 현행 저가 모델 Claude Haiku 5.5의 단가는 백만 토큰당 입력 0.10달러부터, 출력 0.50달러부터이며, 10만 토큰을 넘는 프롬프트는 값이 더 높다. 수업에서 쓰는 모델(LLM_MODEL)의 단가를 수업 직전에 다시 확인한다.

키트의 연습 기록 연습/호출기록_예시.jsonl에는 변형 A의 호출 2회와 변형 B의 호출 4회가 있고, B의 하나는 실패했다. 이 기록을 집계 도구 token_report.py에 주면 변형별 호출 수, 토큰, 과업당 비용이 마크다운 표로 나온다(5-9). 표이므로 비교구현.md에 그대로 붙일 수 있다. --tasks는 기록에 담긴 과업 수다. 측정 도구로 준비 1회와 반복 5회를 돌렸다면 6이다.

연습 기록의 B를 보면 입력 토큰이 호출마다 220, 300, 380으로 늘어난다. 대화 이력을 매번 다시 보내는 구현에서 나타나는 모양이다. 대화형은 대화가 길어질수록 호출 하나의 입력 토큰이 커지므로, 과업당 토큰은 호출 수보다 빠르게 늘어난다.

5-10. 실제 호출의 기록으로 다시 보기 (교수 시연) [선택]

모의 모드의 값은 구조적 차이(호출 수, 이력의 재전송)를 보일 뿐 실제 시간과 토큰은 아니다. 실제 모델로 다시 재는 단계는 같은 과업을 되풀이해 부르므로 이 장의 실행 상한을 넘는다. 그래서 교수 시연으로 한다. 교수는 수업 전에 다음 순서로 잰다. 나중에 실제 호출을 할 때도 같은 순서를 따른다.

  1. 비용을 먼저 어림한다. 모의 모드의 과업당 토큰 × 반복 횟수 × 단가에 두 배의 여유를 두고 한도 안인지 본다.
  2. 반복을 줄인다. --warmup 0 --repeat 3으로 재고, 그 한계를 기준표에 적는다.
  3. 환경을 바꾼다. 키가 든 .env를 변형의 작업 공간에 복사하고(3-6), LLM_FAKE=0과 수업 직전에 확인한 같은 LLM_MODEL로 두 변형을 띄운다.

원 명세가 있는데 굳이 구현에서 명세를 다시 뽑는 까닭은, 원 명세가 말하는 것과 구현이 실제로 하는 것은 다르기 때문이다. 원 명세는 의도이고, 추출 명세는 사실이다. 구현이 의도보다 많은 일을 하면(명세에 없는 결정), 그 부분은 원 명세만 읽어서는 보이지 않는다. 구현이 의도보다 적은 일을 하면(빠진 요구), 원 명세의 체크리스트로는 보이지만 “왜 빠졌는가”는 보이지 않는다. 두 변형에서 각각 뽑아 견주면, 두 구현이 같은 자리에서 서로 다르게 정한 곳이 드러난다. 그 자리가 명세가 말하지 않은 곳이다.

6-2. 1단계: 원 명세를 가린 추출

추출은 원 명세를 보지 않고 한다. 원 명세를 보면서 구현을 읽으면, 구현에서 명세에 맞는 부분만 눈에 들어오고 명세에 없는 결정은 지나친다. 확인 편향이다. 그래서 1단계는 다음 조건에서 한다.

  1. 변형의 작업 트리에서 새 세션을 연다. 구현한 세션은 원 명세를 이미 읽었다.
  2. 계획 모드로 연다(claude --permission-mode plan). 추출은 읽기만 하는 일이며, 계획 모드에서는 파일을 고치지 않고 읽고 제안만 한다[C2].
  3. 지시문에 「요구사항명세서와 변형 지시문을 읽지 말라」고 쓰고, 읽을 파일을 구현 파일로 한정한다.
  4. 출력 형식을 정한다. 추출 명세의 ID(form은 F-, chat은 C-), EARS 문장, 근거 파일. 대응 칸은 비워 둔다.

프롬프트의 「읽지 마라」는 요청일 뿐 강제가 아니며, 확실히 막으려면 권한 설정의 Read 거부 규칙을 쓴다[C2]. 이 장에서는 프롬프트로 지시하고, 추출이 끝난 뒤 Claude Code가 읽은 파일 목록에 docs/나 tests/가 없는지 화면에서 확인한다. 있으면 그 추출 명세는 버리고 새 세션에서 다시 뽑는다.

6-3. 2단계: 대응 칸 채우기

2단계에서 원 명세를 연다. 추출 요구마다 원 명세의 어느 요구에 대응하는지 「대응」 칸에 적는다. 하나의 추출 요구가 원 요구 둘에 걸치면 쉼표로 적고, 대응하는 원 요구가 없으면 -를 적는다.

이 단계는 Claude Code에 맡겨도 되지만 결과는 사람이 한 줄씩 확인한다. 대응을 넓게 잡으면 빈틈이 사라지기 때문이다. 예를 들어 「둘째 메시지부터는 글자 수를 세지 않는다」를 REQ-082(초과 표시)에 대응시키면 빈틈 목록에서 빠진다. 이 문장은 REQ-082가 정하지 않은 것을 구현이 정한 것이므로 -가 맞다. 판단 기준은 한 문장이다. 원 요구의 문장만 읽고 그 추출 요구를 예측할 수 있었는가. 예측할 수 없었다면 -다.

[Claude Code] 주 작업 트리

@docs/요구사항명세서.md 의 「자기소개서 피드백」 절 REQ-080~REQ-089와 @docs/비교/추출명세_chat.md 를 대조해 추출 명세의 대응 칸을 채워라.
원 요구의 문장만으로 그 추출 요구를 예측할 수 있을 때만 그 ID를 적고, 예측할 수 없으면 - 를 적어라.
대응을 적은 줄마다 판단 근거를 한 문장으로 보고하라. 파일의 다른 칸은 고치지 마라.

코드 대신 화면에서 뽑는 방법도 있다. 6장에서 경쟁 서비스를 다룰 때처럼 사람이 화면을 써 보며 관찰한 동작을 문장으로 적는 것이다. 화면 관찰은 사용자가 실제로 겪는 동작만 잡으므로 사용자 관점의 빈틈(예: 새로 고치면 대화가 사라진다)을 잘 찾지만, 입력 길이의 상한이나 실패 처리처럼 겪기 어려운 동작은 놓친다. 코드 추출은 그 반대다. 이 장의 핵심 실습은 두 세션의 보고와 화면 점검(9-6)으로 빈틈을 찾고, 코드 추출은 [선택] 단계(9-8)로 둔다.

6-4. 요구 ID 집합의 대조

키트의 연습 재료는 「마감 임박 표시」 기능의 원 명세(DL-01~04)와, 이 명세로 만든 두 구현 A, B에서 뽑은 추출 명세다. 대응 칸까지 채운 두 추출 명세를 spec_diff.py로 대조하면 다음과 같다.

원 명세 요구 4개
추출 명세 A: 요구 4개, 대응 없음 1개
추출 명세 B: 요구 5개, 대응 없음 2개

6-5. 대조 결과 읽기

대조 결과의 세 부분은 서로 다른 것을 알려 준다.

[1] 어떤 추출에도 대응이 없는 원 요구. 두 구현 모두 그 요구를 구현하지 않았거나, 구현했지만 코드에서 뽑히지 않은 것이다. 뒤의 경우가 의외로 많다. 「~하지 않아야 한다」 같은 부정형 요구(예: REQ-087 답변을 남기지 않는다)는 코드에 그 동작이 없다는 것으로만 충족되므로, 코드를 읽어서는 문장이 나오지 않는다. 이런 요구는 추출이 아니라 검사(공통 검사의 REQ-087)로 확인한다.

[2] 같은 줄에서 다르게 정한 곳. 두 변형이 모두 대응하는 원 요구라도, 대응하는 추출 문장을 나란히 읽으면 내용이 다를 수 있다. 연습의 DL-02는 A가 「3일 이내」, B가 「72시간 이내」로 구현했다. 원 명세 「3일 이내」가 날짜 단위인지 시간 단위인지 정하지 않았기 때문이다. 도구는 ID만 견주므로 이 차이는 사람이 문장을 읽어 찾는다. 이 장의 빈틈 가운데 중요한 것은 대개 여기서 나온다.

[3] 원 명세 밖의 결정. 구현이 명세 없이 정한 동작이다. 연습의 A-04와 B-04는 같은 문제(남은 날 수의 기준 시각)를 서로 반대로 정했다. 사용자 컴퓨터의 자정 기준과 서버의 UTC 기준은 한국에서 아홉 시간 차이가 나므로, 밤 열 시에 본 「마감 1일 전」이 두 구현에서 다르게 보인다. 한쪽에만 있는 결정(B-05 빈 마감일)도 다른 구현이 그 경우를 어떻게 처리하는지 확인할 거리다.

찾은 빈틈은 2026년판의 세 갈래로 나누어 처리한다[R1].

6-6. 자기 보고와 추출의 비교

4-2에서 공통 지시의 보고 항목에 「명세에 없어 스스로 정한 것」을 넣었다. 구현한 세션이 스스로 밝힌 이 목록과, 새 세션이 코드에서 뽑은 추출 명세의 [3]을 견주면 두 방법의 성격이 드러난다.

자기 보고는 구현한 쪽이 의식하고 내린 결정을 잘 잡는다. 「글자 수를 공백을 빼고 센다」처럼 구현하면서 고민한 결정은 대개 보고에 나온다. 반면 의식하지 않은 결정, 즉 기본값을 그대로 두어 생긴 동작은 빠지기 쉽다. 「대화 횟수에 상한을 두지 않는다」나 「관계없는 질문에도 답한다」는 구현한 쪽에서 보면 아무것도 하지 않은 것이므로 결정으로 느껴지지 않는다. 추출은 코드에 남은 동작과 남지 않은 제약을 읽는 사람의 눈으로 보므로 이런 것을 잡는다.

두 목록을 합칠 때는 다음처럼 표시해 두면 다음 장에서 쓸모가 있다.

  • 보고와 추출 모두에 있다: 구현한 쪽이 알고 정한 결정. 명세로 올릴지 판단만 하면 된다.
  • 추출에만 있다: 의식하지 않은 결정. 사용자에게 문제가 될 수 있는지 먼저 본다. 13장의 사용성 평가에서 문제로 나올 가능성이 크다.
  • 보고에만 있다: 추출이 놓쳤거나 코드에 드러나지 않는 결정. 추출 프롬프트에서 읽을 파일이 빠지지 않았는지 확인한다.

7. 명세 보강과 결정 기록

7-1. 빈틈을 EARS로

빈틈 하나를 명세 문장 하나로 바꾼다. 연습의 「남은 날 수의 기준 시각」을 예로 든다.

DL-05 (상시) 시스템은 마감까지 남은 날 수를 한국 표준시(KST) 날짜 기준으로 계산해야 한다.
DL-06 (원치 않는 동작) 만약 마감일이 비어 있으면, 시스템은 남은 날 수 대신 「상시 채용」을 보여야 한다.

보강할 때 지키는 규칙이 셋 있다.

  1. 새 ID를 붙인다. 기존 요구(DL-02)의 문장을 고치고 싶어도 고쳐 쓰지 않는다. 6장의 ID 규칙대로, 바꿀 때는 새 ID를 붙이고 옛 요구에 「대체됨(DL-07)」을 적는다. 이미 그 ID로 쓴 테스트, 추출 명세의 대응, 커밋 메시지가 그대로 뜻을 유지하기 때문이다.
  2. 두 구현 중 하나를 그대로 받아 적지 않는다. 빈틈을 메우는 결정은 사용자에게 맞는 쪽으로 한다. 두 구현의 결정은 후보일 뿐이다. 연습의 기준 시각은 A(사용자 컴퓨터)도 B(UTC)도 아닌 KST로 정했다. 사용자가 모두 한국에 있고, 사용자 컴퓨터의 시계는 틀릴 수 있기 때문이다.
  3. 보강의 출처를 적는다. 요구 끝에 괄호로 「12장 대조: A-04, B-04」를 적거나, 변경 이력에 적는다. 나중에 그 요구가 왜 생겼는지 추적할 수 있다.

EARS 문장의 품질은 6장의 기준으로 점검한다. 「적절히」, 「빠르게」, 「잘」 같은 말이 들어가면 검사할 수 없다. 「빠르게 응답해야 한다」 대신 「5초 안에 응답의 첫 부분을 보여야 한다」처럼 관찰할 수 있는 값으로 쓴다.

7-2. 결정 기록: ADR

빈틈을 메운 결정과, 두 변형 중 하나를 고른 결정은 명세에 다 담기지 않는다. 명세는 「무엇을」을 적고, 「왜 이것을 골랐고 무엇을 버렸는가」는 적지 않기 때문이다. 이것을 남기는 문서가 아키텍처 결정 기록(Architecture Decision Record, ADR)이다.

ADR은 마이클 나이가드(Michael Nygard)가 2011년 글에서 제안한 형식이다[D1]. 그는 큰 설계 문서는 아무도 읽지 않고 고치지도 않으므로, 결정 하나를 작은 문서 하나에 적자고 하였다. 그가 제안한 항목은 다섯이다.

결정 그 힘들에 대한 응답. 「~한다」로 시작하는 능동문 양식형을 병합하고 대화형은 태그로 보존한다
결과 결정 뒤의 상태. 좋은 것, 나쁜 것, 중립인 것을 모두 비용이 절반, 이어서 묻기는 잃음, 뒤따라 할 일

나이가드의 글에서 지켜야 할 규칙 몇 가지가 더 있다[D1]. ADR은 저장소 안에 마크다운으로 두고 번호를 차례로 붙이며, 번호를 다시 쓰지 않는다. 결정이 뒤집히면 옛 ADR을 지우지 않고 상태를 「대체됨」으로 바꾸고 새 ADR을 쓴다. 한 문서는 한두 쪽이며, 미래의 개발자와 대화하듯 완전한 문장으로 쓴다. 이 결정 기록 모음을 ADR 커뮤니티는 결정 로그(decision log)라 부른다[D2].

결과 항목에 나쁜 것을 쓰는 것이 ADR의 핵심이다. 「양식형이 모든 면에서 낫다」고 쓰면, 몇 달 뒤 대화형이 다시 제안되었을 때 그때 무엇을 잃었는지 알 수 없다. 「이어서 묻기를 잃었다」를 적어 두면, 그것이 문제가 되는 순간 이 결정을 다시 볼 이유가 기록에 있다.

7-3. 좋은 기록과 나쁜 기록

항목 나쁜 예 좋은 예
맥락 대화형과 양식형을 비교했다 양식형은 충족률 100%, 과업당 토큰 829(모의)였고, 대화형은 80%, 1615였다. 대화형은 이어서 묻기가 자연스러웠다
결정 양식형이 더 좋아서 양식형으로 한다 양식형(variant-form)을 main에 병합한다. 대화형은 태그 variant-chat-v1로 보존하고 브랜치는 지운다
결과 좋아졌다 과업당 호출이 3회에서 2회로 준다. 보완점을 하나씩 좁혀 묻는 경험이 없어진다. REQ-091을 병합본에 구현해야 한다

7-4. 결정 기록을 쓰는 때와 추적

모든 결정에 ADR을 쓰지는 않는다. 나이가드는 ADR의 대상을 「아키텍처에 중요한」 결정, 곧 구조, 비기능 특성(성능, 비용, 보안), 의존성, 인터페이스, 구현 기법에 영향을 주는 결정으로 한정하였다[D1]. 이 과목의 공통 사례에 옮기면 다음 질문 가운데 하나에 「그렇다」면 ADR을 쓴다.

  • 이 결정을 되돌리려면 여러 파일이나 다른 기능을 함께 고쳐야 하는가
  • 이 결정이 비용, 응답 시간, 개인 정보의 처리를 바꾸는가
  • 같은 질문이 몇 달 뒤 다시 나올 가능성이 있는가

자기소개서 피드백의 상호작용 방식은 세 질문 모두에 해당한다. 반면 「보완점을 두 개 보일지 세 개 보일지」는 명세의 요구 한 줄로 충분하다.

ADR, 명세, 커밋, 태그는 서로를 가리켜야 나중에 따라갈 수 있다. 이 장의 산출물 사이의 연결은 다음과 같다.

출발 가리키는 것 어디에 적나
명세의 보강 요구(REQ-090) 대조에서 나온 근거(F-03, C-03) 요구 문장 끝의 괄호
비교구현.md 측정 명령, 시나리오 파일, 태그 spec-v7 1절 비교 조건, 2절 「재는 법」

병합 커밋 ADR 번호 커밋 메시지 「(ADR-001)」
태그 variant-chat-v1 비교 당시의 대화형 구현 태그 메시지

이 연결이 있으면 「왜 이 화면은 양식형인가」라는 질문에서 출발해 ADR, 기준표, 측정 명령, 보존된 구현까지 차례로 따라갈 수 있다. 「AI에이전트 기획 및 개발」에서 이 저장소를 운영 대상으로 삼을 때, 에이전트가 읽는 것도 이 문서들이다.

8. 병합과 보존

8-1. 병합 커밋을 남기는 병합

선택한 변형을 main에 합칠 때 git merge --no-ff를 쓴다. --no-ff는 빨리 감기(fast-forward)가 가능해도 병합 커밋을 만들라는 옵션이다[G3]. 빨리 감기 병합은 main의 끝을 변형의 끝으로 옮기기만 하므로, 나중에 기록을 보면 변형의 커밋이 처음부터 main에서 만든 것처럼 보인다. 병합 커밋을 남기면 「여기서 variant-form을 합쳤다」는 사실과 그 커밋 메시지(ADR 번호)가 기록에 남는다.

이 장에서는 변형을 만든 뒤 main에 명세 보강을 커밋하므로 대개 빨리 감기가 불가능하고 병합 커밋이 저절로 생긴다. 그래도 --no-ff를 습관으로 붙인다. 3장의 풀 리퀘스트 병합에서 GitHub의 기본 방식(Create a merge commit)도 같은 일을 한다.

8-2. 태그로 보존

택하지 않은 변형은 지우지 않고 태그로 보존한다. 태그는 커밋 하나를 가리키는 이름이고, 브랜치와 달리 움직이지 않는다. 주석 태그(git tag -a)는 만든 사람, 날짜, 메시지를 담은 태그 객체를 만든다[G6]. 릴리스나 이 장의 보존처럼 기록으로 남길 태그는 주석 태그로 만든다.

git tag -a variant-chat-v1 variant-chat -m "12장 대화형 변형(보존, 병합하지 않음)"
git tag -a variant-form-v1 variant-form -m "12장 양식형 변형(병합)"
git tag -n1

태그를 먼저 만들고 브랜치를 지운다. 순서가 바뀌면 병합하지 않은 변형의 커밋을 가리키는 이름이 하나도 없게 된다. 그런 커밋은 한동안 남아 있지만 찾기 어렵고, 결국 git의 정리 작업으로 사라진다.

8-3. 작업 트리와 브랜치의 정리

정리는 작업 트리 → 브랜치 순서로 한다. 작업 트리에 꺼내 둔 브랜치는 지울 수 없기 때문이다.

명령 결과
git worktree remove <form 작업 공간의 경로> 작업 트리 폴더를 지운다. 커밋하지 않은 변경이나 추적하지 않는 파일이 있으면 거부한다(무시 파일은 함께 지운다)
git branch -d variant-form 병합한 브랜치를 지운다
git branch -d variant-chat 거부된다. 병합하지 않은 브랜치이기 때문이다
git branch -D variant-chat 강제로 지운다. 태그가 커밋을 가리키고 있으므로 커밋은 남는다

-d가 거부하는 화면은 다음과 같다. 이 거부는 실수로 작업을 잃지 않게 하는 장치이므로, -D를 치기 전에 태그가 있는지 반드시 확인한다.

error: the branch 'variant-chat' is not fully merged
hint: If you are sure you want to delete it, run 'git branch -D variant-chat'

8-4. 태그의 푸시

git push는 태그를 보내지 않는다. 태그는 따로 보내야 한다.

  • git push origin <태그>: 그 태그 하나를 보낸다.
  • git push origin --tags: 모든 태그를 보낸다.
  • git push origin main --follow-tags: main과 함께, 보내는 커밋에서 닿을 수 있는 주석 태그를 보낸다.

--follow-tags는 편하지만 이 장에서는 함정이 있다. variant-chat-v1은 main에서 닿을 수 없는 커밋을 가리키므로 보내지지 않는다. 집필 때 로컬의 원격 흉내 저장소로 확인한 결과, --follow-tags로는 spec-v7, spec-v7.1, variant-form-v1만 올라갔고 variant-chat-v1은 따로 보내야 했다.

8-5. 보존한 변형을 다시 보기

태그로 보존한 변형은 언제든 다시 볼 수 있다.

git show variant-chat-v1:jobprep/api/feedback_chat.py | head -3
git worktree add ../chat-다시보기 variant-chat-v1
git switch -c variant-chat-2 variant-chat-v1

첫 명령은 파일 하나를 꺼내 보지 않고 출력한다. 둘째는 태그를 작업 트리로 꺼낸다(브랜치가 아니므로 「detached HEAD」 상태가 된다). 셋째는 태그에서 새 브랜치를 만들어 이어서 개발한다. 13장의 사용성 평가에서 대화형의 장점이 다시 필요해지면 셋째 방법으로 되살린다.

프로젝트실습Ⅰ의 팀 저장소에서는 3장의 풀 리퀘스트 흐름을 쓴다. 두 변형 브랜치를 각각 초안(draft) 풀 리퀘스트로 올려 나란히 리뷰하고, 고른 쪽을 병합하며, 다른 쪽은 병합하지 않고 닫는다[G7]. 닫은 풀 리퀘스트에는 「ADR-001에 따라 병합하지 않음」과 보존 태그 이름을 댓글로 남긴다.

정리

  • 같은 명세로 만든 두 구현의 차이는 의도한 축(상호작용 방식)과 명세가 정하지 않은 곳에서만 생긴다. 뒤의 차이가 명세의 빈틈이다.

  • 결정은 ADR(제목, 상태, 맥락, 결정, 결과)로 남기고, 택하지 않은 변형은 주석 태그로 보존한 뒤 작업 공간과 브랜치를 정리한다.

  1. 같은 명세로 만든 두 구현이 글자 수를 서로 다르게 센다. 이것은 지시의 차이인가, 명세의 빈틈인가? 근거를 들어 답하라.
  2. 비교 구현과 A/B 테스트를 「언제」와 「누가 판단하는가」의 두 기준으로 구별하라.
  3. 브랜치 전환 대신 작업 트리(Orca의 작업 공간)를 쓰면 이 장의 측정에서 무엇이 가능해지는가? 두 가지를 들라.
  4. 대화형 변형의 과업당 토큰이 호출 수의 비율보다 크게 느는 까닭을 Messages API의 성질로 설명하라.
  5. 구현에서 명세를 다시 뽑을 때 원 명세와 테스트 폴더를 읽지 못하게 하는 까닭은 무엇인가?
