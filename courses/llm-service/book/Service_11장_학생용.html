애플리케이션의 분석과 UI 설계

2027학년도 「LLM 서비스 개발」의 준비 중인 교재입니다. 편집 상태를 검토하기 위해 미리 공개한 것으로, 수업 전에 내용과 순서가 바뀔 수 있습니다.

학사 13주차 · 교재 11 · 서비스 5: 데스크톱 앱의 기능 하나 (1/2)

개편 초안 2판(2026-11-18). 대상 앱을 FromScratch로 정하고, 저장소의 사실(사용권, 판, 마지막 커밋, 코드)을 2026-11-18에 확인해 본문의 예를 실제 코드에 맞추었다. 키트(Service_11장)의 테스트와 도구, 대상 앱의 내려받기와 코드 검색, 대비와 HTML 점검, 키보드 기록기는 Windows 11의 Git Bash(Python 3.13.7)에서 실행해 출력을 실었다. 대상 앱의 설치와 실행, REA, Claude Code의 응답은 「실행 결과 자리」로 남겼다. 교수가 실습실 PC에서 리허설한 뒤 채운다.

지금까지 화면(4장), 코드 한 파일(6장), 네트워크 호출(8장)을 읽었다. 이 장의 대상은 설치해 쓰는 데스크톱 앱이다. 파일이 여럿이고, 화면을 그리는 부분과 파일을 다루는 부분이 나뉘어 있으며, 둘이 메시지를 주고받는다. 사람이 처음부터 끝까지 읽기에는 크다. 그래서 구조를 먼저 보고 기능 하나의 경로만 따라간다.

서비스 5는 오픈소스 데스크톱 앱의 기능 하나를 골라 웹으로 다시 만드는 것이다. 이 장에서 그 기능을 분석해 기능 명세를 쓰고, 화면 명세와 클릭할 수 있는 HTML 프로토타입을 만든다. 12장에서 같은 명세로 구현 둘을 만들어 견준다.

서비스 1과 3은 참고 프로덕트의 구성에 공개 API의 자료를 채웠다. 서비스 5에서 참고 프로덕트는 오픈소스 앱 자신이다. 화면만이 아니라 코드까지 읽을 수 있다는 점이 다르다. 이 단원의 기능(메모의 자동 저장)은 사용자가 입력한 것을 다루므로 공개 API의 자료를 쓰지 않는다. 졸업 프로젝트에서는 이 장의 방법으로 참고 프로덕트의 기능 하나를 분석하고, 6장 8절에서 고른 공개 API의 자료를 그 화면에 채운다.

학습 목표

  • Electron 앱의 구조(주 프로세스, 렌더러, 프리로드, 프로세스 사이의 통신)를 설명하고, 기능 하나가 그 구조를 어떻게 지나가는지 코드에서 따라갈 수 있다.
    • 예시: FromScratch의 자동 저장이 렌더러의 ipc.send('writeContent')에서 주 프로세스의 fs.writeFileSync로 가는 경로를 줄 번호로 적는다.
    • 활용: 졸업 프로젝트에서 참고할 앱의 기능 하나를 같은 방법으로 분석한다.
  • 관찰, 코드 읽기, 분석 도구의 결과에서 확인한 것과 추측한 것과 새로 정한 것을 구분해 기능 명세를 쓸 수 있다.
    • 예시: 「멈추면 잠시 뒤에 저장되는 것 같다」는 관찰을 코드로 확인해 「바뀔 때마다 저장한다」로 고친다.
  • 와이어프레임, 화면의 상태, 상호작용, 접근성 메모를 화면 명세로 쓸 수 있다.
  • WCAG 2.2의 대비와 키보드 기준을 화면 명세와 프로토타입에 반영하고, 도구와 손으로 점검할 수 있다.
    • 예시: 원본 앱의 저장 안내 문구가 대비 3.18:1로 기준(4.5:1)에 못 미침을 계산하고 재구현에서 고친다.
  • 화면 명세만으로 Claude Code에게 HTML 프로토타입을 만들게 하고, 결과를 명세와 대조할 수 있다.

1. 데스크톱 앱의 분석

1-1. Electron의 프로세스 모델

Electron은 웹 기술(HTML, CSS, JavaScript)로 데스크톱 앱을 만드는 틀이다. 구조는 웹 브라우저와 닮았다. 앱 하나는 여러 프로세스로 돌며, 개발자가 주로 다루는 것은 셋이다[X1].

부분 하는 일 할 수 있는 것
주 프로세스(main) 앱의 시작점이다. 앱의 수명과 창(BrowserWindow), 메뉴, 대화 상자를 맡는다 Node.js 환경에서 돈다. 파일과 운영체제의 기능에 접근한다
렌더러(renderer) 창 하나마다 하나씩 생겨 웹 페이지를 그린다 기본으로 require와 Node.js API를 쓰지 못한다
프리로드(preload) 렌더러에서 웹 내용이 읽히기 전에 실행되는 스크립트이다 Node.js API에 접근할 수 있고, 렌더러에 허용할 기능만 골라 내놓는다

렌더러가 파일에 직접 접근하지 못하게 한 것은 보안 때문이다. 창에 남의 웹 내용이 하나라도 섞이면, 그 내용이 사용자의 파일을 읽고 지울 수 있게 되기 때문이다. Electron은 판을 올리며 기본값을 바꾸어 왔다[X4][X5].

설정 뜻 기본값의 변화 FromScratch(Electron 4)
nodeIntegration 렌더러에서 Node.js API를 쓰는가 5.0부터 false true로 켰다(main.dev.js 128줄)
contextIsolation 프리로드와 웹 내용의 전역 공간을 나누는가 12.0부터 true 설정 없음(그때 기본은 false)
프로세스 샌드박스 렌더러의 운영체제 접근을 막는가 20.0부터 켜짐 해당 없음
remote 모듈 렌더러가 주 프로세스의 객체를 직접 부르는가 12.0에서 사용 중단 예고, 14.0에서 제거 remote.getGlobal()을 쓴다(FromScratch.jsx 21~22줄)

지금의 권장 구조에서는 렌더러가 파일을 쓰려면 프리로드가 내놓은 함수를 거쳐 주 프로세스에 부탁해야 한다. 프리로드는 contextBridge.exposeInMainWorld로 필요한 함수만 웹 쪽에 건넨다[X1]. FromScratch는 이 구조가 기본이 되기 전에 만들어졌으므로 프리로드가 없고, 렌더러가 Node.js의 require('electron')을 바로 쓴다. 분석할 때 「프리로드 파일이 무엇인가」라는 물음에 「없다」가 답이 될 수 있다는 뜻이다.

1-2. 프로세스 사이의 통신(IPC)

렌더러가 주 프로세스에 일을 부탁하는 메시지를 프로세스 사이의 통신(IPC, Inter-Process Communication)이라 한다. 메시지는 이름이 붙은 통로(channel)로 오간다. 통로의 이름은 개발자가 마음대로 정한다[X2]. Electron 문서는 통신을 세 방식으로 나눈다.

방향 보내는 쪽 받는 쪽 쓰는 곳
렌더러 → 주, 한 방향 ipcRenderer.send ipcMain.on 답이 필요 없는 알림(저장해 달라)
렌더러 → 주, 양방향 ipcRenderer.invoke ipcMain.handle 답을 기다리는 부탁(파일을 골라 경로를 달라). 렌더러는 Promise로 답을 받는다
주 → 렌더러 webContents.send ipcRenderer.on 메뉴나 단축키를 화면에 알릴 때

다음은 지금의 권장 구조로 「메모 저장」을 만든다면 어떤 모양이 되는지 보인 설명용 코드이다. 실행하지 않는다.

파일: 예 · preload.js와 main.js의 일부 
// preload.js: 렌더러에 save 함수 하나만 내놓는다
const { contextBridge, ipcRenderer } = require('electron')

2. 와이어프레임과 화면의 상태

2-1. 세 산출물의 구별

화면을 설계하는 과정에서 가장 자주 쓰는 중간 산출물의 이름은 와이어프레임(wireframe), 목업(mockup), 프로토타입(prototype)이다. 세 이름은 회사와 도구마다 조금씩 다르게 쓰이므로, 무엇을 정하고 무엇을 비워 두는가로 구별한다.

산출물 정하는 것 비워 두는 것 대표적인 형태 주로 묻는 질문
와이어프레임 무엇이 어디에 있는가(구조와 배치) 색, 글꼴, 실제 문구, 동작 회색 상자와 선, 손그림, ASCII 그림 필요한 요소가 다 있는가. 순서가 맞는가
목업 최종 화면이 어떻게 보이는가(시각 표현) 동작. 눌러도 아무 일이 없다 디자인 도구의 정지 화면 위계가 읽히는가
프로토타입 무엇을 하면 화면이 어떻게 바뀌는가(상호작용) 실제 데이터와 저장 클릭 가능한 디자인 파일, HTML 과업을 끝까지 할 수 있는가. 상태 전환이 이해되는가

이 장은 와이어프레임(ASCII 그림)에서 바로 HTML 프로토타입으로 간다. 목업 단계를 따로 두지 않는 대신, 시각 표현은 디자인 토큰 파일 하나와 대비 점검으로 정한다.

2-2. 저충실도와 고충실도

NN/g는 두 쪽의 장단점을 다음과 같이 정리한다[N1]. 저충실도(종이, 회색 상자)는 준비가 빠르고 시험 도중에도 고쳐 그릴 수 있으며, 미완성으로 보여 의견을 편하게 받는다. 대신 사람이 화면을 바꾸는 동안 흐름이 끊긴다. 고충실도(클릭 가능한 화면)는 실제와 같아 사용자가 실제처럼 행동하고, 작업 흐름과 글자의 가독성 같은 세부를 시험할 수 있다. 대신 클릭할 자리와 반응을 모두 미리 만들어야 하므로 시간이 든다.

생성형 AI 코딩 도구는 고충실도의 단점인 「만드는 시간」을 크게 줄였다. 화면 명세가 있으면 클릭 가능한 HTML 프로토타입을 몇 분 안에 얻는다. 다만 새로운 위험이 생긴다. 잘 다듬어진 화면은 「거의 다 된 것」처럼 보여서 리뷰어가 구조의 문제보다 색과 문구에 의견을 낸다. 그래서 이 장은 프로토타입을 만들기 전에 화면 명세를 먼저 쓰고, 리뷰도 명세를 기준으로 받는다.

프로토타입은 실제 저장을 하지 않는다. 대신 주소에 ?state=error처럼 상태 이름을 붙이면 그 상태를 바로 보이게 한다. 저장 실패처럼 일부러 만들기 어려운 상태를 리뷰어가 눈으로 확인할 수 있게 하려는 것이다. NN/g가 AI 기능을 만들기 전에 사람이 뒤에서 응답을 대신 만들어 보이는 「오즈의 마법사(Wizard of Oz)」 시험을 권하는 것도 같은 생각이다[N1]. 실제 동작을 붙이기 전에 경험을 먼저 설계하고 시험한다.

2-3. 시각적 위계

시각적 위계(visual hierarchy)는 화면의 요소를 배열해 사용자의 눈이 의도한 중요도의 순서대로 읽게 하는 일이다[N2]. 위계의 순서는 사용자의 과업에서 나온다. 메모장의 사용자가 하는 일은 「떠오른 것을 바로 적는다」이므로 가장 먼저 눈에 들어와야 하는 것은 입력 칸이다. 저장 상태는 필요할 때 확인하는 보조 정보이므로 작고 조용해야 한다. FromScratch가 화면에 글만 두고 나머지를 숨긴 것도 이 위계를 극단까지 밀어붙인 결정이다.

NN/g는 위계를 만드는 수단으로 색과 대비, 크기, 묶기를 든다[N2]. 여기에 실무에서 함께 쓰는 정렬을 더한다.

수단 원리 메모 화면에 적용한 예 지나칠 때의 문제
크기 큰 요소가 먼저 눈에 들어온다 입력 칸이 화면 높이의 대부분을 쓴다. 상태 문구는 14px 모든 것을 크게 하면 무엇이 중요한지 흐려진다
대비 주변과 명도 차이가 큰 요소가 눈에 띈다 본문 글자는 바탕과 4.82:1, 저장 실패 문구는 밝은 빨강 강한 색을 여러 곳에 쓰면 경고가 경고로 보이지 않는다
간격(묶기) 가까이 있는 것은 한 묶음으로 읽힌다 상태 문구와 「다시 시도」 단추를 한 상자에 묶는다 상자를 남발하면 화면이 칸막이로 가득 찬다
정렬 같은 선에 맞춘 요소는 관계가 있어 보인다 제목, 입력 칸, 상태를 왼쪽 선에 맞춘다 정렬을 섞으면 눈이 매 줄 시작점을 찾아야 한다

NN/g는 글자 크기를 세 단계 정도로 제한하고, 빨간색 같은 강한 색은 경고와 오류에 아껴 쓰며, 색만으로 중요도를 나타내지 말라고 권한다[N2]. 색을 구별하지 못하는 사용자가 있기 때문이다.

2-4. 컴포넌트와 화면의 상태

하나의 컴포넌트는 여러 상태(state)를 가진다. 단추는 평소의 모습 말고도 마우스를 올렸을 때, 키보드로 초점을 받았을 때, 누를 수 없을 때의 모습이 있어야 한다. 화면 전체도 상태를 가진다. 메모 화면은 처음 열었을 때, 쓰는 중일 때, 저장했을 때, 저장하지 못했을 때가 모두 다른 화면이다.

상태 뜻 단추에서 메모 화면에서 빠뜨리면
기본(default) 아무 일도 없는 평소 테두리와 밝은 글자 저장된 글
호버(hover) 마우스 포인터가 위에 있다 밑줄이나 면 색 누를 수 있는지 망설인다
초점(focus) 키보드 초점이 있다 3px 테두리 입력 칸의 테두리 키보드 사용자가 자기 위치를 잃는다(WCAG 2.4.7)
비활성(disabled) 지금은 누를 수 없다 흐리게 왜 안 눌리는지 모른다
진행 중(loading, saving) 시스템이 일하는 중 「…하는 중」 「저장 안 됨」 끝난 줄 알고 앱을 닫는다
빈 상태(empty) 보여 줄 내용이 아직 없다 처음 연 화면의 안내 고장 난 줄 안다
오류(error) 실패하였다 저장 실패와 다시 시도 글을 잃은 줄 모른다
성공(success) 끝났다 「저장됨」 저장되었는지 다시 확인하러 간다

AI에게 화면을 만들게 하면 기본 상태는 대개 잘 만들어지고 그 밖의 상태가 빠지기 쉽다. 「메모 화면을 만들어 줘」라고만 하면 저장 실패의 화면은 없기 쉽다. 그래서 화면 명세의 상태 표는 「기본」 줄보다 그 아래 줄이 더 중요하다. 자동 저장은 상태가 눈에 보이지 않는 기능이라 이 점이 특히 두드러진다. 원본 FromScratch는 저장 상태를 하나도 보이지 않는다. 그러면 사용자는 앱을 닫아도 되는 순간을 화면에서 알 수 없다.

2-5. 빈 상태

빈 상태(empty state)는 내용이 아직 없거나 보여 줄 수 없는 컨테이너, 화면, 패널이다[N6]. NN/g는 빈 상태의 설계 지침으로 세 가지를 든다[N6].

  1. 시스템 상태를 알린다. 빈 칸으로 두지 않고, 불러오는 중인지, 실패했는지, 정말 없는지를 구별해 알린다.
  2. 배우게 한다. 이 기능이 무엇이고 어떻게 시작하는지 알려 준다.
  3. 다음 행동으로 가는 길을 준다. 설명에 그치지 않고 그 일을 하는 곳으로 바로 가게 한다.

FromScratch의 빈 상태는 따로 만든 화면이 아니라 본문에 미리 넣어 둔 안내 글이다. 저장 파일이 없으면 「이 앱은 입력한 것을 자동으로 저장하므로 저장할 필요가 없다」는 뜻의 영어 글을 본문에 보인다(FromScratch.jsx 101~109줄, 117줄). 이 방식은 둘째 지침(배우게 한다)을 충족하고, 안내 글을 지우는 것이 곧 시작이므로 셋째 지침도 충족한다. 웹 재구현에서도 이 방식을 그대로 옮길 수 있다. 다만 한국어 사용자에게 맞게 문구를 바꾸고, 안내 글을 지운 뒤 빈 글을 저장하는지 다시 안내 글을 보일지는 정해야 한다. 이 물음은 12장에서 두 구현이 서로 다르게 답하는 자리가 된다.

2-6. 오류 메시지

WCAG 2.2는 오류에 대해 두 기준을 둔다[W1]. 3.3.1(오류 식별, A)은 오류가 자동으로 감지되면 오류가 난 곳을 밝히고 글자로 설명하라고 요구한다. 3.3.3(오류 제안, AA)은 고치는 방법을 알고 있으면 제안하라고 요구한다. 여기에 1.4.1(색의 사용, A)이 더해진다. 색만으로 정보를 전하면 안 되므로 빨간 글자만으로 실패를 알릴 수 없다.

NN/g는 오류 메시지의 지침을 보이기, 전달, 효율의 세 묶음으로 정리한다[N8]. 보이기는 오류가 난 자리 가까이, 눈에 띄게, 심각도에 맞게 두는 것이다. 전달은 사람이 읽을 수 있는 말로 문제를 정확히 설명하고 고치는 방법을 알리되 사용자를 탓하지 않는 것이다. 효율은 입력한 값을 지키고 고치는 수고를 줄이는 것이다. 이 지침을 메모의 저장 실패에 적용한다.

상황 나쁜 문구 좋은 문구 고친 점
브라우저 저장소에 쓰지 못했다 「저장 실패」 「저장하지 못했다. 입력한 글은 화면에 그대로 있다.」와 「다시 시도」 단추 입력이 남아 있음을 알려 안심시키고, 다음 행동을 준다
저장소가 가득 찼다 「QuotaExceededError」 「이 브라우저의 저장 공간이 가득 찼다. 글을 복사해 다른 곳에 옮긴 뒤 다시 시도한다.」 오류 코드를 빼고 까닭과 고치는 방법을 알린다
실패를 알리는 곳 화면 위쪽의 대화 상자 입력 칸 바로 아래의 상태 영역 원인과 가까이 두고, 쓰기를 막지 않는다

3. 접근성

3-1. 접근성과 WCAG 2.2

웹 접근성은 장애가 있는 사람을 포함해 누구나 웹 서비스를 인식하고, 조작하고, 이해할 수 있게 하는 일이다. 화면 낭독기로 듣는 사용자, 키보드만 쓰는 사용자, 색을 구별하기 어려운 사용자, 화면을 크게 확대해 보는 사용자가 모두 서비스의 사용자이다. 햇빛 아래에서 휴대전화를 보는 사람에게도 대비가 필요하다.

국제 기준은 W3C의 웹 콘텐츠 접근성 지침(WCAG)이다. WCAG 2.2는 2023년 10월 5일에 W3C 권고안으로 처음 발표되었고, 현재 판은 2024년 12월 12일에 다시 발행된 권고안이다[W1][W10]. WCAG는 인식의 용이성, 운용의 용이성, 이해의 용이성, 견고성의 네 원칙 아래 지침을 두고, 지침마다 시험할 수 있는 성공 기준을 둔다. 성공 기준은 A, AA, AAA의 세 수준이며, 법령과 조달 기준은 대개 AA까지를 요구한다. 한국에서는 WCAG를 바탕으로 한 「한국형 웹 콘텐츠 접근성 지침 2.2」를 방송통신표준심의회가 2022년 12월 28일에 발표하였다[K3]. 이 장에서 다루는 성공 기준은 다음과 같다[W1].

번호 이름 수준 요지

3-2. 대비의 계산

1.4.3은 글자와 그 바탕의 대비율(contrast ratio)이 4.5:1 이상이기를 요구한다. 큰 글자(18pt 이상, 굵으면 14pt 이상)는 3:1이다. 1.4.11은 입력 칸의 테두리와 초점 표시처럼 글자가 아닌 UI 요소에 3:1을 요구한다[W1]. 대비율은 두 색의 상대 휘도(relative luminance)로 계산한다.

채널 c = 8비트 값 / 255
c <= 0.04045 이면 c / 12.92, 아니면 ((c + 0.055) / 1.055) ^ 2.4
L = 0.2126 R + 0.7152 G + 0.0722 B
대비율 = (밝은 쪽 L + 0.05) / (어두운 쪽 L + 0.05)          범위 1 ~ 21

초록 채널의 가중치가 가장 큰 것은 사람의 눈이 초록에 가장 민감하기 때문이다. 대비율은 반올림하지 않는다. 4.47:1은 4.5:1이 아니다.

3-3. 키보드 접근

키보드만 쓰는 사용자는 Tab으로 다음 요소, Shift+Tab으로 이전 요소로 초점을 옮기고, Enter로 링크와 단추를 누르고, Space로 단추와 체크 상자를 누른다[W3]. 이 조작이 화면의 모든 기능에 통하도록 하는 것이 2.1.1(키보드)이다. 키보드 접근의 대부분은 올바른 HTML 요소를 쓰는 것으로 해결된다. <button>, <a href>, <textarea>는 기본으로 초점을 받고 키보드로 동작한다. <div>에 onclick을 달면 초점도 받지 않고 Enter도 듣지 않는다[W3].

글을 쓰는 앱에서는 2.1.2(키보드 함정 없음)가 특히 문제가 된다. 2.1.2는 키보드로 들어간 요소에서 키보드만으로 나올 수 있어야 하며, 화살표나 Tab 같은 표준 방법이 아니면 나오는 방법을 사용자에게 알려야 한다고 요구한다[W1]. 코드 편집기는 대개 Tab을 들여쓰기에 쓴다. FromScratch도 편집기 설정에 indentWithTabs: true와 'Shift-Tab': 'indentLess'를 두었다(FromScratch.jsx 27줄, 272줄). 그렇다면 본문에 들어간 초점이 Tab으로는 빠져나오지 못할 수 있다. 다만 화면에 본문 말고는 초점을 받을 요소가 거의 없으므로 실제로 갇히는지는 실행해 보아야 안다(추측). 웹 재구현에서는 둘 가운데 하나를 정해 명세에 적는다.

  1. <textarea>의 기본 동작을 따른다. Tab은 초점을 다음 요소로 옮기고 들여쓰기는 하지 않는다.
  2. Tab을 들여쓰기에 쓰고, 빠져나오는 방법(예: Esc 뒤 Tab)을 화면에 적는다.

손으로 하는 키보드 점검은 다음 순서로 한다. 마우스는 책상 한쪽으로 치운다.

  1. 주소창을 누른 뒤 Tab을 한 번 누른다. 「본문 바로가기」가 나타나야 한다.
  2. Tab을 계속 누르며 초점이 가는 순서를 적는다. 초점이 보이지 않는 순간이 있으면 표시한다.
  3. 과업 하나(글을 쓰고 저장 상태를 확인한다)를 키보드만으로 끝까지 해 본다.
  4. Shift+Tab으로 거꾸로도 가 본다. 어딘가에서 빠져나오지 못하면 함정이다.

4. 화면 명세와 프로토타입

4-1. 화면 명세의 구성

화면 명세는 화면 하나에 대해 「무엇을 위해 있고(목적), 어느 요구를 충족하며(요구 ID), 무엇이 어디에 있고(구성 요소와 그림), 어떤 상태가 있으며(상태), 무엇을 하면 어떻게 되고(상호작용), 접근성을 위해 무엇을 지키는가(접근성 메모)」를 적은 문서이다. 키트의 화면명세_양식.md는 화면마다 일곱 칸을 둔다.

칸 내용 빠뜨리면 생기는 일
1) 개요 화면 ID, 목적 한 문장, 관련 요구 ID, 들어오고 나가는 길 화면이 무엇을 위해 있는지 몰라 리뷰가 취향 싸움이 된다
2) 와이어프레임 좁은 화면 배치의 그림과 넓은 화면에서 달라지는 점 배치를 AI가 정한다
3) 구성 요소 위에서 아래 순서(= 초점 순서)의 요소 표 요소가 빠지거나 순서가 바뀐다
4) 상태 기본, 진행 중, 빈 상태, 오류 등. 언제, 보이는 것, 문구, 관련 요구 기본 상태만 만들어진다
5) 상호작용 사용자 동작과 시스템 반응의 표 단추를 눌렀을 때의 동작을 AI가 지어낸다
6) 접근성 메모 초점 순서, 상태 알림, 키보드 함정, 대비 화면마다 접근성 처리가 달라진다
7) 열린 질문 명세에 답이 없어 정하지 못한 것과 누가 언제 정하는가 모르는 것을 아는 것처럼 구현한다

화면 ID는 SCR-01 꼴로 붙인다. 이 ID는 구현 파일과 12장의 점검표까지 같은 화면을 가리키는 이름이 된다. 명세의 첫머리에는 모든 화면에 공통인 0절(본문 바로가기, 문구의 말투, 초점 표시, 누름 영역)을 둔다.

와이어프레임은 ASCII 그림으로 그린다. 글자로 그린 그림은 화면명세.md 안에 바로 들어가고, git의 차이에서 무엇이 바뀌었는지 보이며, Claude Code가 그대로 읽는다. 정해야 하는 것은 요소의 순서, 묶음, 대략의 크기와 위치이다.

구성 요소 표의 순서는 화면의 위에서 아래 순서이고, 그것이 곧 키보드 초점의 순서이다.

| 1 | 본문 바로가기 | 링크 | 입력 칸으로 간다 | |
| 2 | 화면 제목 | 제목(h1) | 「메모」 | |
| 3 | 메모 본문 | 입력(textarea) | 숨긴 레이블 「메모 본문」, 도움말 연결 | REQ-02, REQ-03, REQ-06 |

상호작용 표의 「초점을 입력 칸으로 돌린다」 같은 문장은 AI가 스스로 넣지 않는 대표적인 결정이다. 「다시 시도」 단추는 저장에 성공하는 순간 사라지므로, 초점을 어디로 보낼지 정하지 않으면 초점이 문서 처음으로 튄다. 명세에 적어 두어야 구현된다.

상태 영역에 role="status"를 두는 것은 4.1.3(상태 메시지)에서 온다. 화면 낭독기 사용자는 「저장됨」이라는 글자가 바뀌어도 초점이 그곳에 없으면 알지 못한다. 상태 역할을 가진 영역은 내용이 바뀔 때 초점을 옮기지 않고 읽힌다. 이 영역은 처음부터 HTML에 있어야 한다. 숨겨 두었다가 나타나는 영역은 바뀐 내용을 놓치는 보조 기술이 있다.

4-4. 프로토타입의 범위

이 장의 프로토타입은 빌드 도구 없는 HTML, CSS, JavaScript로 만든다. npm install도, 번들러도, 프레임워크도 쓰지 않으며, 파일을 브라우저로 열면 바로 동작해야 한다. 12장의 구현도 이 구조를 따른다.

  • 프로토타입이 하는 것: 화면 명세의 구성 요소, 상태마다의 화면과 문구, ?state= 주소로 상태 바로 보기, 키보드로 하는 조작, 상태 전환의 흉내(입력하면 「저장 안 됨」, 1초 뒤 「저장됨」).
  • 하지 않는 것(12장의 구현이 할 일): 실제로 브라우저 저장소에 쓰기, 다시 열었을 때 글 되살리기, 실제 저장 실패의 처리.

색은 키트의 토큰 파일에서 만든 tokens.css의 의미 토큰만 쓴다. 화면의 CSS에 16진 색을 직접 적으면 대비 점검의 대상에서 빠지기 때문이다.

판정 기준은 5-1의 완료 기준 일곱 개이다.

정리

  • Electron 앱은 주 프로세스, 렌더러, 프리로드로 나뉘고 IPC의 통로로 이어진다. 통로의 목록이 주 프로세스가 하는 일을 말해 준다. 옛 앱에는 프리로드가 없고 remote로 통로를 거치지 않는 경로가 있을 수 있다.
  • 큰 대상은 구조를 먼저 보고 기능 하나의 경로만 따라간다. 관찰의 짐작과 도구의 결과는 근거의 줄을 열어 확인한다.
  • 매체가 바뀌면 옮길 수 없는 것이 생긴다. 명세에 그 대응을 적고, 원본과 다르게 정한 것은 「정함」으로 밝힌다.
  • 화면 명세는 목적, 요구 ID, 구성 요소, 상태, 상호작용, 접근성 메모, 열린 질문을 적는다. 기본 상태만 있는 명세는 원치 않는 동작을 빠뜨린 것이다.
  • 대비는 공식으로 계산하고 반올림하지 않는다. 점검기의 통과는 접근성을 보증하지 않으며 키보드 점검은 사람이 한다.

개념 점검.

  1. FromScratch에 프리로드 파일이 없는 까닭과, 지금의 Electron에서 같은 기능을 만들 때 달라지는 설정 둘을 말하라.
  2. grep의 통로 목록만으로는 놓치는 경로는 무엇이고, 어떻게 찾았는가.
  3. 관찰 기록의 「멈춘 뒤에 저장되는 것 같다」가 코드와 다른 까닭을 줄 번호로 설명하라.
  4. 흰색 40%의 글자를 대비 점검기에 그대로 넣을 수 없는 까닭은 무엇인가.
  5. 상태 영역을 처음부터 HTML에 두어야 하는 까닭은 무엇인가.
