11장

검색 증강 생성(RAG) 기능의 구현

2027학년도 「LLM 서비스 개발」의 준비 중인 교재입니다. 편집 상태를 검토하기 위해 미리 공개한 것으로, 수업 전에 내용과 순서가 바뀔 수 있습니다.

학사 13주차 · 교재 11 · 4부 구현

앞 장에서는 공고 요약 기능을 FastAPI 백엔드(jobprep/api/)로 만들고, LLM 호출을 서버 쪽 함수 하나로 모았다. 그 기능은 사용자가 붙여 넣은 공고 본문만 다루었다. 모델이 이미 알고 있는 일반 지식과 사용자가 건넨 글만으로 답이 나오는 기능이었다. 취업 준비생이 실제로 묻는 질문은 다르다. “현장실습 나가려면 몇 학점이 필요한가”, “취업지원실은 몇 시까지 여는가”처럼 답이 학과의 내부 자료에만 있는 질문이 많다. 모델은 그 자료를 학습한 적이 없으므로, 그대로 물으면 그럴듯한 숫자를 지어낸다.

이 장은 그 문제를 검색 증강 생성(Retrieval-Augmented Generation, RAG)으로 푼다. 질문과 관련된 자료 조각을 코드가 먼저 찾고, 그 조각을 근거로 붙여 모델에게 보내며, 모델에게는 근거 안에서만 답하고 근거 번호를 밝히게 한다. 근거가 없으면 “자료에 없다”고 답하게 한다. 이 장에서 만드는 것은 하나다. 학과 취업 지원 자료(가상 문서 다섯 개)를 근거로 답하는 취업 자료 질의응답이다. 색인과 검색과 답변을 맡는 jobprep/rag/, 그것을 서비스로 내놓는 POST /api/ask, 근거를 함께 보여 주는 화면 web/ask.html, 그리고 검색 품질을 숫자로 남긴 docs/검색평가.md가 산출물이다.

절차는 앞 장들과 같다. 먼저 명세서에 RAG 요구를 EARS 문형으로 더하고, 그 명세와 함수의 독스트링을 Claude Code에 주어 구현하게 하고, 고정 테스트로 판정한다. 구현 뒤에는 평가 문항 10개로 재현율@3을 재어 기록하고, 청킹 설정을 바꾸었을 때 생긴 회귀(전에 찾던 문항을 놓치게 된 것) 하나를 원인부터 찾아 설정 하나로 고친다. 느낌이 아니라 숫자로 검색을 고르는 습관이 이 장의 핵심이다.

프로젝트실습Ⅰ에서 팀 프로덕트가 “우리 자료로 답하는 기능”을 가지게 되면 이 장의 구조(색인 단계와 질의 단계, 근거 블록, 기준값, 평가 문항)를 그대로 옮겨 쓴다. 다음 장(12장)은 이 장까지 만든 기능을 두 가지 화면(대화형과 양식형)으로 구현해 비교한다.

학습 목표

  • RAG의 두 단계를 설명하고 각 부품을 코드에서 찾는다. 색인 단계(청킹, 임베딩, 저장)와 질의 단계(검색, 증강, 생성)를 구분한다.
    • 예시: “기준값 판정은 질의 단계의 어디에 있는가”라는 물음에 rag/answer.py의 answer 함수 안, 검색 직후라고 답한다.
    • 활용: 팀 프로덕트의 RAG에서 답이 틀렸을 때 어느 단계부터 볼지 정한다.
  • 검색 품질을 재현율@k로 재고, 설정을 바꾼 결과를 숫자로 비교한다.
    • 예시: 고정 길이 200자로 바꾸자 재현율@3이 0.90에서 0.80으로 떨어지면, 새로 놓친 문항의 원인을 청크의 경계에서 찾고 겹침 하나를 바꾸어 고친 뒤 기준값을 다시 정한다.
    • 활용: “검색이 좋아졌다”는 보고를 평가 문항과 수치로 뒷받침한다.
  • 근거를 밝히고 모르면 모른다고 답하는 증강 프롬프트와 기준값을 설계한다.
    • 예시: 근거 블록마다 번호와 출처를 달고, 1위 유사도가 기준값보다 낮으면 LLM을 부르지 않고 “자료에 없다”고 답한다.
    • 활용: 사내 규정, 학칙, 제품 설명서처럼 틀린 답의 비용이 큰 질의응답 기능을 만든다.
  • RAG에 고유한 위험(문서에 숨은 지시, 근거 없는 확신)을 명세와 화면에서 다룬다.
    • 예시: 자료의 HTML 주석을 색인 전에 걷어 내고, 화면은 답을 textContent로만 넣는다.
    • 활용: 외부 문서를 받아 색인하는 기능을 만들 때 검토 절차와 방어를 명세에 적는다.

0. 시작하기

설치, 로그인, 키트 저장소의 클론, 가상 환경은 부록 A(A-7, A-8, A-12, A-13), 매 수업의 시작 순서는 A-21을 따른다. 작업은 VS Code의 통합 터미널 두 개(A-4-3)에서 한다. 하나는 명령을 직접 실행하는 [터미널](Windows는 Git Bash, macOS는 기본 터미널)이고, 다른 하나는 Claude Code용이다. 핵심 실습에서 API 서버를 띄울 때는 10장처럼 셋째 터미널(API 터미널)을 하나 더 연다. 모든 터미널에서 가상 환경을 켜 둔다(source ~/llm-service-lab/.venv/Scripts/activate, macOS는 .venv/bin/activate). Windows에서는 한글 출력이 깨지지 않게 부록 A-3-4대로 PYTHONUTF8=1을 등록해 두었는지 본다.

  • 이 장의 실행 상한. Claude Code 대화형은 구현 지시 1회와 고침 지시 1~2회이다(12-3). 프로덕트의 실제 호출(LLM_FAKE=0)은 Console 키를 발급한 학생만 python -m rag ask 1회이다(12-13 [선택]). 여러 질문의 실제 답과 Ollama 경로의 측정은 교수가 만든 실행 기록으로 읽는다. Ollama는 자기 PC에 설치한 학생의 선택이다(3-5, 부록 A-17).
  • 「읽기」 표시. 꼬리표에 「(읽기)」를 붙인 코드 블록은 따라 치지 않고 읽는다. 따라 치는 명령은 0절, 따라 하기 둘(4-4, 5-2), 핵심 실습(12절)에 있다.

0-1. 키트 받기와 합치기

키트 저장소에서 새 키트를 받아 ~/kits/로 복사한 뒤, 그 안의 jobprep/를 개인 실습 저장소의 jobprep/에 합친다(부록 A-12-3). 먼저 저장소가 깨끗한지 본다. git status --short가 아무것도 출력하지 않아야 한다. 10장의 작업이 커밋되지 않은 채 남아 있으면 먼저 커밋한다. 이 장의 변경과 섞이면 어느 변경이 어느 장의 것인지 가를 수 없다.

git status --short
git -C ~/kits-repo pull

cp -rn ~/kits-repo/Service_11장 ~/kits/

1. LLM이 모르는 것

1-1. 모델의 지식에는 날짜와 경계가 있다

LLM의 지식은 학습에 쓴 데이터에서 온다. 그러므로 지식에는 두 가지 경계가 있다. 첫째는 시간의 경계다. Anthropic은 모델마다 “신뢰할 수 있는 지식의 기준 시점(reliable knowledge cutoff)”과 “학습 데이터의 기준 시점(training data cutoff)”을 모델 개요 문서에 밝힌다[A1]. 앞의 것은 모델의 지식이 가장 넓고 믿을 만한 시점까지를, 뒤의 것은 학습에 쓴 데이터의 더 넓은 범위를 가리킨다[A1]. 그 시점 이후에 바뀐 학칙, 새로 올라온 공고, 개정된 규정은 모델이 알 수 없다.

[최신 자료 자리: 현재 모델의 지식 기준 시점] 수업에서 쓰는 저가 모델(LLM_MODEL)의 신뢰할 수 있는 지식의 기준 시점과 학습 데이터의 기준 시점. 확인할 곳은 https://platform.claude.com/docs/en/about-claude/models/overview의 「Latest models」 표다. 2026-11-16에 확인한 값은 현행 네 모델(Claude Fable 5.2, Opus 5.5, Sonnet 5.5, Haiku 5.5) 모두 2026년 6월이다. 수업 직전에 다시 확인한다.

둘째는 접근의 경계다. 학과 취업지원실의 안내문, 회사의 복무 규정, 팀의 회의록처럼 공개 웹에 없는 문서는 학습 데이터에 들어간 적이 없다. 모델은 그런 문서의 존재조차 모른다.

경계 밖의 질문을 받으면 모델은 “모른다”고 답하기보다, 비슷한 문서에서 흔히 보이는 내용으로 그럴듯한 답을 만드는 경우가 많다. 1장에서 본 환각(hallucination)이다. 취업 상담에서는 이것이 곧 사고가 된다. “현장실습은 30학점 이상이면 된다”는 틀린 답을 믿은 학생은 신청 시기를 놓친다.

취업 준비생의 질문 네 개를 이 두 경계에 비추어 본다.

  • “자기소개서에서 STAR 구성이 무엇인가”는 공개된 일반 지식이므로 모델이 대체로 답한다.
  • “우리 학과 취업지원실은 몇 시까지 여는가”는 내부 문서에만 있으므로 답할 수 없다(접근의 경계).
  • “누리소프트 신입 공고의 마감일은 언제인가”는 학습 시점 뒤에 나온 공고이므로 답할 수 없다(시간의 경계).
  • “지금 이 공고에 지원자가 몇 명인가”는 시시각각 바뀌는 값이다. 문서를 찾아 붙이는 방식으로도 답할 수 없고, 원본 시스템에 그 순간 물어야 한다.

이 장이 다루는 것은 둘째와 셋째 질문이다. 넷째 질문은 모델에게 도구를 주어 원본 시스템을 조회하게 하는 방식이 맞으며, 「AI에이전트 기획 및 개발」에서 다룬다.

1-2. 모르는 것을 알게 하는 네 가지 방법

모델에게 자료를 알게 하는 방법은 크게 넷이다. 이 장이 RAG를 고른 까닭을 비교로 정리한다.

방법 하는 일 강점 약점 맞는 경우
프롬프트에 통째로 넣기 자료 전체를 매 요청에 붙인다 가장 단순하다. 검색 실패가 없다 자료가 크면 비용과 지연이 커진다 자료가 작을 때
검색 증강 생성(RAG) 질문마다 관련 조각만 찾아 붙인다 자료가 커도 된다. 자료를 바꾸면 색인만 다시 만든다. 출처를 밝힐 수 있다 검색이 틀리면 답도 틀린다 자료가 크고 자주 바뀔 때
미세 조정(파인튜닝) 자료로 모델을 추가 학습시킨다 말투와 형식을 몸에 익힌다 비싸고 느리다. 자료가 바뀌면 다시 학습한다. 출처를 밝히기 어렵다 형식과 문체를 바꿀 때
실시간 조회(도구 사용) 질문이 오면 원본 시스템에 바로 묻는다 항상 지금 값이다 시스템마다 연결을 만들어야 한다 재고, 배송 상태처럼 수시로 바뀌는 값

Anthropic은 Contextual Retrieval을 소개한 글에서, 지식 기반이 20만 토큰(약 500쪽)보다 작으면 RAG 없이 자료 전체를 프롬프트에 넣는 것도 방법이라고 하였다[A2]. 같은 글은 프롬프트 캐싱을 쓰면 이 방식의 지연과 비용을 크게 줄일 수 있다고 덧붙였다[A2]. 이 장의 가상 자료 다섯 개는 그 기준보다 훨씬 작다. 그런데도 RAG를 만드는 까닭은 두 가지다. 하나는 실제 학과의 자료(학칙 전문, 수년 치 공고, 상담 기록)가 금세 그 기준을 넘는다는 것이다. 다른 하나는 RAG의 절차(청킹, 임베딩, 검색, 평가)를 작은 자료에서 끝까지 손으로 돌려 보아야 큰 자료에서 무엇이 틀렸는지 찾을 수 있다는 것이다.

1-3. RAG가 실패하는 두 지점

RAG는 환각을 줄이지만 없애지 않는다. 실패는 주로 두 곳에서 일어난다.

검색 실패. 엉뚱한 조각을 찾아도 생성 단계는 그 조각으로 성실하게 답한다. “현장실습 중에 아파서 못 가면 어떻게 하나”의 정답은 출석과 결석 조항인데, 검색이 보험 조항을 가져오면 모델은 “상해보험에 가입되어 있다”고 답하고 조항 번호까지 붙인다. 출처가 붙어 있으므로 사용자는 지어낸 답보다 이쪽을 더 쉽게 믿는다. 이 장의 측정(재현율@3)은 이 실패를 숫자로 잡기 위한 것이다.

갱신 실패. 색인은 문서를 미리 잘라 숫자로 바꾸어 둔 것이므로 저절로 새로워지지 않는다. 규정이 개정되어도 색인을 다시 만들지 않으면 옛 규정으로 답한다. 문서가 바뀌는 주기에 맞추어 색인을 다시 만드는 일은 운영의 문제다. 현장실습 운영 규정처럼 거의 바뀌지 않는 자료는 개정 공지가 날 때 다시 만들면 된다. 취업 지원 안내와 특강 일정은 학기마다 바뀌므로 학기 시작 전에 다시 만든다. 채용 공고는 수시로 올라오므로 공고가 올라올 때마다, 적어도 하루 한 번 다시 만든다. 지원자 수나 남은 자리처럼 시시각각 바뀌는 값은 색인에 넣지 않고 실시간 조회로 다룬다.

갱신과 함께 생각할 것이 문서 안의 시점 표현이다. “올해”, “이번 학기” 같은 말은 청크만 떼어 보면 언제를 가리키는지 알 수 없다. 2026년 2학기판 6주차에서도 같은 문제를 다루었다(재무 보고서의 “올해”). 키트의 문서들은 머리말에 기준 시점(“2027년 3월 1일 시행본”, “2027년 4월에 소개한 공고”)을 적어 두었지만, 그 머리말은 별도 청크가 되므로 다른 절의 청크에는 시점이 붙어 있지 않다. 실무에서는 문서의 시행일이나 작성일을 메타데이터로 청크마다 붙이고, 답할 때 함께 보여 준다.

이 장은 검색 실패를 다룬다. 갱신 실패는 색인을 언제 다시 만드는지의 운영 규칙이므로, docs/검색평가.md의 결론에 “자료가 바뀌면 python -m rag index를 다시 실행한다”는 한 줄로 남긴다.

2. RAG의 구조: 색인 단계와 질의 단계

2-1. 두 단계

RAG는 시점이 다른 두 단계로 움직인다. 색인 단계는 자료가 바뀔 때 한 번 돈다. 문서를 조각(청크, chunk)으로 자르고, 조각마다 의미를 숫자 목록(벡터)으로 바꾸어(임베딩) 저장한다. 이 저장물이 색인(index)이다. 질의 단계는 질문이 올 때마다 돈다. 질문도 같은 방식으로 벡터로 바꾸고, 색인에서 가까운 조각을 찾고(검색, Retrieval), 그 조각을 질문과 함께 프롬프트에 묶고(증강, Augmentation), 모델이 답을 만든다(생성, Generation).

2-2. 단계와 키트의 파일

키트의 rag/ 패키지는 그림의 상자 하나를 파일 하나가 맡도록 나누었다. 학생이 완성할 함수 네 개는 굵게 표시하였다.

단계 하는 일 파일 주요 함수
색인 문서 읽기, 주석 걷어 내기, 청킹 chunker.py load_documents, clean_text, chunk_document
색인·질의 임베딩(Ollama 또는 대체 구현) embedder.py embed_texts, embed_text
색인 저장과 읽기, 임베딩 경로 검사 store.py build_index, load_index
질의 벡터 검색, 키워드 검색, 혼합 검색 search.py vector_search, keyword_search, hybrid_search
질의 증강 프롬프트, 이력 자르기, 기준값, 인용 answer.py build_prompt, trim_history, answer
질의 LLM 호출(모의 모드) llm.py call_llm
측정 재현율, 정밀도, 기준값 비교 evaluate.py recall_at_k, run_eval, calibrate
설정 환경 변수 config.py chunk_mode, min_score 등
명령 명령 줄 입구 __main__.py index, search, prompt, ask, eval, calibrate
서비스 API와 화면 api/ask_route.py, web/ask.* POST /api/ask

설정은 모두 환경 변수로 바꾼다. 코드의 숫자를 고치지 않고 CHUNK_MAX_CHARS=200 python -m rag index처럼 명령 앞에 값을 붙이면, 같은 코드로 여러 설정을 비교할 수 있다. 실험의 조건이 명령 한 줄에 남으므로 보고서에 옮기기도 쉽다.

2-4. RAG 기능에서 정할 것

RAG 기능을 서비스에 넣는다는 것은 코드 몇 줄을 더하는 일이 아니라 여러 가지를 결정하는 일이다. 이 장의 나머지 절은 아래 결정을 하나씩 다룬다. 결정마다 근거(측정값이나 문서)를 남기고, 결정한 값은 11절에서 명세서의 요구로 옮긴다.

  1. 자료의 범위. 무엇을 근거로 삼는가. 이 장은 취업지원실의 자료 다섯 개로 정하였다. 범위 밖의 질문은 「자료에 없다」로 답한다(8절).
  2. 갱신 주기. 자료가 바뀌면 언제 색인을 다시 만드는가(1-3절).
  3. 청킹. 어디서, 얼마나 길게, 얼마나 겹쳐 자르는가. 청크에 무엇을 붙이는가(4절).
  4. 임베딩 모델. 어느 모델로 벡터를 만드는가. 바꾸면 색인 전체와 기준값을 다시 만든다(3절).
  5. 검색 방법과 k. 벡터, 키워드, 혼합 가운데 무엇을, 몇 개를 근거로 쓰는가(5절, 6절).
  6. 증강 프롬프트. 근거를 어떤 형식으로 붙이고 무엇을 지시하는가(7절).
  7. 모를 때의 응답. 기준값과 거절 문장(8절).
  8. 대화 이력. 몇 왕복을, 무엇을 남기는가(9절).
  9. 화면. 근거를 어떻게 보이고, 모델의 글을 어떻게 안전하게 넣는가(10절).
  10. 위험. 자료에 숨은 지시를 어떻게 막는가(13절).

이 목록은 프로젝트실습Ⅰ에서 팀의 RAG 기능을 설계할 때 그대로 점검표로 쓸 수 있다. 결정하지 않고 넘어간 항목은 구현하는 사람(또는 Claude Code)이 임의로 정하게 된다. 6장에서 본 대로, 명세가 정하지 않은 것은 구현이 추측으로 채운다.

3. 임베딩과 코사인 유사도

3-1. 임베딩

임베딩(embedding)은 글 하나를 고정된 길이의 숫자 목록, 곧 벡터(vector)로 바꾸는 변환이다. 임베딩 모델은 뜻이 비슷한 글이 가까운 벡터가 되도록 학습되어 있다. 그래서 “화상 면접 준비”와 “비대면 면접 환경”처럼 낱말이 일부만 겹치는 글도, 좋은 임베딩 모델에서는 가까운 벡터가 된다. 검색은 “질문의 벡터와 가까운 청크의 벡터를 찾는 일”이 된다.

임베딩 모델은 답을 만드는 생성 모델과 다른 부품이다. Anthropic은 자체 임베딩 모델을 제공하지 않으며, 문서에서는 임베딩 제공자의 한 예로 Voyage AI를 소개한다[A3]. 같은 문서는 임베딩 모델을 고를 때 볼 것으로 학습 데이터의 규모와 분야 적합성, 추론 속도, 사내 데이터로 추가 학습할 수 있는지를 든다[A3]. 이 과목은 외부 임베딩 서비스의 계정과 비용을 피하기 위해 키트의 대체 구현을 기본으로 한다. 자기 PC에 Ollama를 설치한 학생은 Ollama가 제공하는 로컬 임베딩 모델을 선택으로 쓸 수 있다(부록 A-17, 사용자 결정 11). 이 장의 측정과 확인은 모두 대체 구현으로 하므로, 누가 실행해도 숫자가 같다.

두 모델은 입력과 출력부터 다르다. 생성 모델(10장)은 시스템 지시와 대화로 된 프롬프트를 받아 글을 내고, 임베딩 모델은 글 하나 또는 여러 개를 받아 모델마다 길이가 정해진 숫자 목록을 낸다. 이 과목에서 생성 모델은 Claude API(LLM_MODEL, 모의 모드 LLM_FAKE=1)로, 임베딩 모델은 대체 구현(기본)이나 Ollama(EMBED_BACKEND=ollama와 EMBED_MODEL, 선택)로 부른다. 비용도 따로 잡힌다. 생성 모델은 입력과 출력 토큰으로, 외부 임베딩 서비스는 입력 토큰으로 값을 매기고, 로컬 모델은 내 PC의 계산 자원을 쓴다. 가장 큰 차이는 바꿀 때의 비용이다. 생성 모델을 바꾸면 프롬프트를 다시 점검하면 되지만, 임베딩 모델을 바꾸면 색인 전체를 다시 만들어야 한다.

이 차이가 중요한 까닭은 임베딩 모델마다 벡터의 길이와 눈금이 다르다. 모델 A로 만든 색인에 모델 B로 만든 질문 벡터를 견주면 숫자는 나오지만 뜻이 없다. Ollama 문서도 색인과 질의에 같은 임베딩 모델을 쓰라고 권한다[A4]. 키트의 store.py는 색인을 만들 때 임베딩 경로와 모델 이름을 meta.json에 적어 두고, 색인을 읽을 때 지금의 경로와 다르면 오류를 낸다.

3-2. 코사인 유사도

두 벡터가 얼마나 가까운지는 대개 코사인 유사도(cosine similarity)로 잰다. 두 벡터가 이루는 각의 코사인 값이다. 같은 방향이면 1, 직각이면 0, 반대 방향이면 -1이다.

코사인 유사도(a, b) = (a · b) / (|a| × |b|)
  a · b : 같은 자리의 성분끼리 곱해 모두 더한 값(내적)
  |a|   : 성분 제곱의 합의 제곱근(벡터의 길이)

벡터의 길이를 미리 1로 맞추어 두면(L2 정규화) 분모가 1이 되므로, 코사인 유사도는 내적과 같아진다. Ollama 문서는 /api/embed가 L2 정규화된 벡터를 돌려준다고 밝히고[A4], Voyage AI 임베딩도 길이 1로 정규화되어 있어 내적과 코사인이 같다고 Claude 문서가 설명한다[A3]. 키트의 embedder.py는 어느 경로든 한 번 더 정규화해 두고, 검색에서는 행렬 곱 하나(index.vectors @ q)로 모든 청크의 유사도를 한꺼번에 구한다.

유사도가 1에 가까우면 같은 문장이거나 표현이 거의 같은 글이고, 음수는 실무 임베딩에서 드물다. 실무에서 자주 오해되는 것은 “관계없으면 0 안팎”이라는 기대다. 유사도의 절대값은 모델마다 눈금이 다르다. 2026년 2학기 수업에서 쓴 nomic-embed-text 모델은 관계없는 문장 쌍에도 0.5를 넘는 값을 내었다(2026년판 6주차 기록). 그러므로 “0.7 이상이면 관련 있다” 같은 기준은 모델을 바꾸면 그대로 쓸 수 없고, 평가 문항으로 다시 정해야 한다(8절).

Ollama는 내 컴퓨터에서 공개 모델을 돌리는 도구다. 임베딩은 POST /api/embed로 요청한다[A4][A5].

3-4. 키트의 대체 구현

대체 구현은 의미를 이해하지 못한다. 글을 두 글자 묶음과 세 글자 묶음(문자 n-gram)으로 쪼개고, 묶음마다 해시 값으로 2,048칸 가운데 한 칸을 골라 1씩 더한 뒤 길이를 1로 맞춘다. 두 글이 같은 글자 묶음을 많이 공유할수록 유사도가 커진다. 표면의 글자가 겹치는 정도를 재는 셈이다.

파일: jobprep/rag/embedder.py (일부) 
def _fallback_one(text):
    text = " ".join(text.lower().split())
    vec = np.zeros(FALLBACK_DIM, dtype=np.float32)
    for n in (2, 3):
        for i in range(len(text) - n + 1):
            gram = text[i:i + n]
            if gram.strip() == "":
                continue
            vec[zlib.crc32(gram.encode("utf-8")) % FALLBACK_DIM] += 1.0
    return vec

zlib.crc32는 파이썬을 다시 실행해도 같은 값을 내는 해시다. 파이썬 내장 hash()는 실행마다 값이 바뀔 수 있어 색인과 질문의 벡터가 어긋나므로 쓰지 않는다.

이 성질이 키트가 대체 구현을 기본값으로 둔 까닭이다. 환경 변수 EMBED_BACKEND의 기본값은 fallback이고, ollama(Ollama만 쓴다, 연결할 수 없으면 오류)와 auto(Ollama를 먼저 시도하고 안 되면 대체 구현)는 고를 때만 쓰인다. 대체 구현은 설치가 필요 없고 같은 글에 언제나 같은 벡터를 내므로, Ollama를 설치한 학생과 설치하지 않은 학생의 재현율과 기준값이 같아진다. auto를 기본으로 두면 Ollama가 켜진 PC에서만 다른 숫자가 나와, 같은 문항 파일로 잰 결과를 서로 견줄 수 없게 된다.

첫 줄의 describe()가 지금 쓰는 임베딩 경로를 알려 준다. 첫 쌍은 「면접」이라는 두 글자를 공유해 0.43이 나왔다. 둘째 쌍은 겹치는 글자가 없어 0이다. 셋째 쌍은 뜻이 거의 같은데도 겹치는 글자가 없어 0이다. 셋째 쌍이 대체 구현의 한계를 보여 준다. 의미 임베딩 모델이라면 셋째 쌍에 0보다 분명히 큰 값을 줄 것으로 기대하지만, 이 장의 집필 환경에서는 확인하지 못하였다. 실행 기록 1절에서 같은 세 쌍의 값을 찾아 대체 구현의 값과 견준다.

이 한계는 뒤의 재현율 측정에서 실제로 나타난다. 평가 문항 6번 “현장실습 중에 아파서 못 가면 어떻게 해?”의 정답 조항은 “질병”, “결석”으로 적혀 있다. 대체 구현은 이 문항을 놓친다(12-5).

4. 청킹 전략

4-1. 왜 자르는가

문서를 통째로 하나의 벡터로 만들면 여러 주제가 한 벡터에 섞인다. “현장실습 운영 규정” 전체의 벡터는 자격, 학점, 보험, 평가의 뜻이 평균된 것이어서 어느 질문에도 어중간하게 가깝다. 또 검색된 문서를 통째로 프롬프트에 붙이면 비용이 들고, 모델이 긴 근거 속에서 정답 문장을 놓칠 수 있다. 반대로 너무 잘게 자르면 조각 하나만으로는 뜻이 통하지 않는다. “단기 실습은 3학점”이라는 조각은 무엇의 3학점인지를 앞 문장에 두고 왔을 수 있다.

Anthropic의 Contextual Retrieval 글은 기본 RAG가 문서를 대개 수백 토큰 이하의 조각으로 자르며, 조각의 크기와 경계와 겹침이 모두 검색 성능에 영향을 준다고 정리하였다[A2]. 청킹은 이 세 가지를 정하는 일이다.

4-3. 제목 붙이기

청크를 잘라 내면 그 청크가 어느 문서의 어느 절이었는지가 사라진다. “결석이 실습 기간의 5분의 1을 넘으면 학점을 인정하지 않는다”라는 조각만 보아서는 현장실습 이야기인지 일반 수업 이야기인지 알 수 없다.

Contextual Retrieval은 이 문제를 풀기 위해 청크마다 그 청크가 문서 전체에서 어떤 자리인지를 설명하는 짧은 맥락(대개 50~100토큰)을 Claude로 만들어 청크 앞에 붙인 뒤 임베딩하고 키워드 색인을 만든다[A2]. 이 글이 보고한 실험에서, 상위 20개 청크 안에 정답을 찾지 못하는 비율(1 - 재현율@20)은 맥락을 붙인 임베딩만으로 5.7%에서 3.7%로 35% 줄었고, 맥락을 붙인 BM25를 더하면 2.9%로 49%, 여기에 재순위화(reranking)를 더하면 1.9%로 67% 줄었다[A2].

이 장의 키트는 LLM을 부르지 않는 값싼 판을 쓴다. 청크 앞에 「문서 제목 > 절 제목」 한 줄을 붙여 임베딩한다(CHUNK_ADD_TITLE=1). 화면과 프롬프트에 나가는 본문(text)에는 붙이지 않고, 임베딩에 넣는 글(embed_text)에만 붙인다. LLM으로 맥락을 만드는 방식과 비교하면 정보가 적지만, 비용이 들지 않고 결과가 매번 같다.

세 방식을 견주면 다음과 같다. 아무것도 붙이지 않는 방식(CHUNK_ADD_TITLE=0)은 비용이 없지만 청크가 제 위치를 잃는다. 제목 붙이기(기본)는 비용 없이 문서와 절의 이름을 남긴다. Contextual Retrieval은 청크마다 LLM 호출이 한 번씩 들지만 가장 풍부한 맥락을 남긴다. 같은 글은 프롬프트 캐싱을 쓰면 문서 토큰 100만 개당 약 1.02달러로 맥락을 만들 수 있다고 계산하였다(800토큰 청크, 8천 토큰 문서를 가정)[A2]. 이 키트는 Contextual Retrieval을 구현하지 않고 소개만 한다.

집필 때 대체 구현으로 잰 결과, 이 장의 자료에서는 제목 붙이기를 꺼도(CHUNK_ADD_TITLE=0) 재현율@3이 0.90으로 같았다. 절 제목(## 제3조 (참여 자격))이 이미 청크 본문의 첫 줄에 들어 있고, 문서 제목이 덧붙이는 글자가 대체 구현의 유사도를 크게 바꾸지 못했기 때문으로 보인다. 제목 붙이기의 효과는 절 제목이 본문에 없는 청크(긴 절을 나눈 둘째 조각 이후)나 의미 임베딩에서 더 클 것으로 예상하지만, 이 장에서는 확인하지 못하였다.

5. 벡터 검색, 키워드 검색, 혼합 검색

5-1. 벡터 검색과 저장 방식

벡터 검색은 질문 벡터와 모든 청크 벡터의 유사도를 구해 큰 순서로 k개를 고른다. 청크가 수천 개 이하이면 모든 청크와 하나씩 견주는 전수 비교로 충분하다. 넘파이에서는 정규화된 행렬과 벡터의 곱 한 번이 곧 모든 청크의 코사인 유사도다.

scores = index.vectors @ q           # (청크 수,) 모든 청크의 유사도
order = np.argsort(scores)[::-1][:k] # 큰 순서로 k개의 번호

np.argsort는 작은 값부터의 번호를 돌려주므로 [::-1]로 뒤집는다. 이 두 줄이 핵심 실습(12-3)에서 완성할 vector_search의 핵심이다.

청크가 수십만 개를 넘으면 질문마다 모든 청크와 견주는 비용이 커진다. 그때 벡터 데이터베이스(pgvector, Chroma 등)를 쓴다. 벡터 데이터베이스는 저장할 때 비슷한 벡터끼리 미리 묶어 두고, 질문이 오면 가까운 묶음만 열어 본다(근사 최근접 이웃 검색). 속도를 얻는 대신 정답이 옆 묶음에 있으면 놓칠 수 있다. 원리는 전수 비교와 같다.

규모에 따라 고르는 저장 방식을 정리하면 이렇다. 청크가 수천 개 이하이면 이 장처럼 파일(JSON과 .npy)에 두고 넘파이로 전수 비교한다. 수만에서 수십만 개이면 관계형 데이터베이스의 벡터 확장(pgvector 등)과 근사 검색 색인을 쓴다. 그보다 크거나 여러 서비스가 한 색인을 함께 쓰면 전용 벡터 데이터베이스가 근사 검색, 메타데이터 필터, 접근 권한을 함께 맡는다.

저장 공간도 어림해 둔다. 벡터 하나는 차원 수 × 4바이트(32비트 실수)다. 이 장의 대체 구현은 2,048차원이므로 청크 36개가 약 290KB다(4-4절의 v.nbytes). 1,024차원 모델로 청크 10만 개를 저장하면 1,024 × 4 × 100,000 = 약 410MB가 되어, 메모리에 통째로 올려 두고 매 질문마다 전수 비교하기에는 부담이 커지기 시작한다. Claude 문서가 소개하는 임베딩 양자화(32비트 실수를 8비트 정수나 1비트로 줄이는 것)는 저장 공간을 4배에서 32배까지 줄이는 대신 정확도를 조금 내준다[A3].

전용 데이터베이스로 옮길 때 새로 생기는 일이 접근 권한이다. 여러 부서의 문서를 한 색인에 넣으면 한 부서의 질문에 다른 부서의 비공개 문서가 근거로 나올 수 있다. OWASP의 LLM 응용 10대 위험은 이를 벡터와 임베딩의 약점(2025년판 LLM08, 2026년판 LLM09)의 하나로 들고, 권한을 인식하는 벡터 저장소와 출처 검증을 대책으로 제시한다[O2][O3]. 이 목록은 2025년판과 2026년판(2026-08-03)의 항목 번호가 일부 다르므로, 이 강의안은 두 판의 번호를 함께 적는다[O3].

[최신 자료 자리: OWASP LLM 응용 10대 위험의 판과 항목 번호] 이 장이 쓰는 번호(프롬프트 주입 LLM01, 벡터와 임베딩의 약점 2025년판 LLM08·2026년판 LLM09, 부적절한 출력 처리 2025년판 LLM05·2026년판 LLM10)가 최신 판과 같은지. 확인할 곳은 https://genai.owasp.org/llm-top-10/와 https://genai.owasp.org/resource/owasp-genai-llm-top-10-2026/다. 2026-11-15에 2026년판(2026-08-03 게시)의 자료 쪽을 확인하였고, 두 판의 번호 대응은 「AI에이전트 기획 및 개발」 11장 2-1절의 표를 따랐다.

5-2. 키워드 검색: BM25

키워드 검색은 질문의 낱말이 청크에 몇 번, 얼마나 드물게 나오는지로 점수를 매긴다. 가장 널리 쓰이는 공식이 BM25다. Anthropic의 Contextual Retrieval 글은 BM25를 TF-IDF를 바탕으로 문서 길이를 보정하고 낱말 빈도의 효과가 일정 수준에서 포화되게 한 순위 함수로 설명하며, 오류 코드 같은 고유한 식별자를 찾는 데 강하다고 하였다[A2].

BM25 점수는 세 요소로 이루어진다.

  • 낱말 빈도(tf). 청크 안에 질문의 낱말이 나온 횟수다. 여러 번 나올수록 점수가 오르지만 그 효과는 점점 줄어든다(포화). 키트는 포화의 정도를 정하는 상수를 k1 = 1.2로 두었다.
  • 역문서 빈도(idf). 그 낱말이 드문 청크에만 나올수록 크다. “현장실습”처럼 여러 청크에 나오는 낱말은 점수에 적게, “누리소프트”처럼 한 청크에만 나오는 낱말은 크게 기여한다. 키트는 청크 36개를 기준으로 센다.
  • 길이 보정. 긴 청크가 낱말을 많이 가져 유리해지지 않도록 청크 길이를 평균 길이와 견주어 점수를 깎는다. 보정의 세기는 b = 0.75다.

한국어에서는 낱말 나누기가 문제다. 키트의 tokenize는 띄어쓰기로만 자르므로 “자기소개서는”과 “자기소개서를”이 다른 낱말이 된다. 실무의 한국어 키워드 검색은 형태소 분석기로 조사와 어미를 떼어 낸다. 키트는 이 약점을 그대로 보이기 위해 단순하게 두었다.

5-3. 혼합 검색: RRF

벡터 검색과 키워드 검색은 서로 다른 질문에 강하다. 둘을 합치면 한쪽이 놓친 것을 다른 쪽이 잡을 수 있다. 문제는 두 점수의 눈금이 다르다는 것이다(코사인은 0~1, BM25는 0~수십). 그래서 점수 대신 순위를 합친다. 역순위 융합(Reciprocal Rank Fusion, RRF)은 각 방법에서의 순위 r마다 1/(k + r)을 더한 값으로 다시 순위를 매긴다. Elasticsearch 문서는 이 상수 k의 기본값을 60으로 두며, 값이 클수록 낮은 순위의 결과도 영향을 더 남긴다고 설명한다[R2]. 이 방식은 Cormack 등이 2009년 SIGIR에서 발표하였다[R3].

RRF 점수(청크) = Σ 1 / (60 + 그 방법에서의 순위)
예) 벡터 1위, 키워드 3위인 청크: 1/61 + 1/63 = 0.0164 + 0.0159 = 0.0323
    벡터 2위, 키워드에는 없는 청크: 1/62 = 0.0161

키트의 hybrid_search는 두 방법에서 각각 상위 20개를 받아 RRF로 합친다. 벡터 검색이 완성되어야 돌아가므로 핵심 실습(12-5)에서 세 방법을 함께 비교한다.

방법 강한 질문 약한 질문 키트
벡터 검색 표현이 달라도 뜻이 같은 질문(의미 임베딩일 때) 고유 명사, 숫자, 코드 vector_search(완성할 함수)
키워드 검색(BM25) 고유 명사, 정확한 용어 일상어, 동의어, 조사가 붙은 낱말 keyword_search
혼합 검색(RRF) 두 쪽의 장점을 함께 두 쪽이 모두 놓친 질문 hybrid_search

혼합이 항상 낫지는 않다. 한쪽이 틀린 청크를 높은 순위로 내면 그것이 섞여 들어와 맞던 것을 밀어낼 수도 있다. 그래서 “섞으면 좋아진다”고 가정하지 않고, 같은 평가 문항으로 세 방법을 재어 고른다.

5-4. 재순위화

검색을 두 번에 나누어 하는 방법도 있다. 먼저 빠른 검색으로 후보를 넉넉히(수십~수백 개) 뽑고, 그 후보만 더 정밀한 모델로 다시 순위를 매긴다. 이 둘째 단계를 재순위화(reranking)라 하고, 그 모델을 재순위화 모델(reranker)이라 한다. 재순위화 모델은 질문과 청크를 한 쌍으로 함께 읽어 관련도를 매기므로, 질문과 청크를 따로 벡터로 만든 뒤 견주는 임베딩보다 정확하지만 느리다. 그래서 전체 청크가 아니라 후보에만 쓴다.

Contextual Retrieval 실험은 상위 150개를 먼저 뽑아 재순위화한 뒤 상위 20개를 남기는 방식으로, 검색 실패율을 맥락 붙이기만 했을 때보다 더 낮추었다(4-3절의 67%)[A2]. Claude 문서도 임베딩 제공자의 재순위화 모델을 함께 소개한다[A3]. 이 장의 키트는 재순위화를 구현하지 않았다. 질문마다 호출이 하나 늘고 외부 서비스 계정이 필요하기 때문이다. 재현율@3을 더 올려야 할 때 검토할 다음 단계로 기억해 둔다. 검색 품질을 올리는 방법을 비용이 낮은 것부터 늘어놓으면 대략 청킹 조정, 제목이나 맥락 붙이기, 키워드 검색과의 혼합, 임베딩 모델 교체, 재순위화의 순서다. 어느 단계든 같은 평가 문항으로 전후를 재어 판단한다.

6. 검색 품질의 측정: 재현율@k

6-1. 정밀도와 재현율

정보 검색에서 검색 결과의 품질을 재는 가장 기본적인 두 척도는 정밀도(precision)와 재현율(recall)이다[R1]. 질문 하나에 대해, 자료 전체 가운데 실제로 관련 있는 것(정답)과 검색기가 돌려준 것을 견준다.

정답(관련 있음) 정답 아님
검색됨 맞게 찾음(tp) 잘못 찾음(fp)
검색 안 됨 놓침(fn) 맞게 뺌(tn) 
정밀도 = tp / (tp + fp)   돌려준 것 가운데 정답의 비율
재현율 = tp / (tp + fn)   정답 가운데 돌려준 것의 비율

두 척도는 서로 당긴다. 자료 전부를 돌려주면 재현율은 1이 되지만 정밀도는 바닥이 된다. 하나만 돌려주면 정밀도는 높을 수 있지만 재현율은 떨어진다.

6-2. 상위 k개로 자른 척도

RAG의 검색기는 순위가 매겨진 목록을 돌려주고, 그 가운데 상위 k개만 프롬프트에 들어간다. 그래서 상위 k개로 자른 척도를 쓴다.

척도 정의 이 장의 쓰임
재현율@k 정답 가운데 상위 k개 안에 든 것의 비율 주 척도. 모델이 받은 근거 안에 정답이 있었는가
정밀도@k 상위 k개 가운데 정답의 비율 보조 척도. 근거 블록에 쓸데없는 청크가 얼마나 섞였는가
적중@k(Hit@k) 상위 k개 안에 정답이 하나라도 있으면 1 문항마다 정답이 하나뿐이면 재현율@k와 같다

RAG에서 재현율@k를 주 척도로 삼는 까닭은 단순하다. 정답이 근거 블록 안에 없으면 모델은 맞힐 수 없다. 정답이 들어 있기만 하면 함께 들어간 다른 청크는 지시(“근거에 없는 내용은 덧붙이지 않는다”)와 모델이 걸러 낼 기회가 있다. Contextual Retrieval 글이 상위 20개 청크의 재현율(정확히는 1 - 재현율@20)을 척도로 쓴 것도 같은 까닭이다[A2]. 이 장은 k = 3을 쓴다. 근거 블록이 짧아 모의 응답과 화면이 읽기 쉽기 때문이다.

6-3. 정답을 무엇으로 표시하는가

재현율을 재려면 문항마다 정답을 미리 표시해 두어야 한다. 키트의 평가문항.csv는 정답을 청크가 아니라 절(「문서이름#절 제목」)로 적었다.

평가 문항을 만드는 원칙은 세 가지다.

  1. 실제 사용자의 말투로 쓴다. 문서의 용어(“질병으로 결석”)가 아니라 학생의 말(“아파서 못 가면”)로 쓴다. 문서의 문장을 그대로 질문으로 바꾸면 재현율이 실제보다 높게 나온다.
  2. 정답을 질문을 쓰기 전에 정하지 않는다. 질문을 먼저 모으고, 그 답이 자료의 어디에 있는지를 사람이 찾아 표시한다.
  3. 자료에 없는 질문을 따로 둔다. 기준값을 정하려면 자료에 없는 질문(범위밖문항.csv)의 점수도 알아야 한다(8절).

6-4. 손으로 재 보기

다음은 가상의 측정 결과다. 각 문항의 재현율@3을 직접 계산한다.

문항 정답 절 상위 3개 청크가 걸친 절
가 A B, A, C
나 D E, F, G
다 H, I H, J, K
라 L L, L, M

가는 1.0, 나는 0.0, 다는 0.5, 라는 1.0이다. 평균 재현율@3은 (1.0 + 0.0 + 0.5 + 1.0) / 4 = 0.625이고, 적중은 4문항 가운데 3문항이다. 라에서 상위 청크 둘이 같은 절 L에 걸쳐 있어도 정답 절이 하나이므로 재현율은 1.0을 넘지 않는다. 정밀도@3은 라가 2/3, 가가 1/3이다.

이 계산이 핵심 실습(12-3)에서 완성할 recall_at_k가 하는 일이다. 문항 10개로 잰 값은 한 문항이 0.1이다. 두 설정의 차이가 0.1이면 한 문항이 바뀐 것이므로 “경향”으로 읽고, 결론을 낼 때는 놓친 문항을 하나하나 들여다본다.

6-5. 평가 문항의 관리

평가 문항은 한 번 만들고 끝나는 파일이 아니다. 10장의 프롬프트 비교에서 평가 문항을 고정해 두고 판본을 바꾸었듯이, 검색에서도 문항 파일을 고정해 두어야 설정 사이의 비교가 공정하다. 그래서 평가문항.csv는 테스트처럼 다룬다. 측정할 때마다 문항을 바꾸지 않고, 바꿀 때는 커밋 메시지에 까닭을 적는다.

문항은 다음 때 더한다. 자료에 새 문서가 들어오면 그 문서에 답이 있는 질문을 한두 개 더한다. 실제 사용자가 보낸 질문 가운데 틀린 답이 나온 것은 정답 절을 표시해 더한다. 문항이 늘면 측정의 해상도도 높아진다. 문항 50개이면 한 문항이 0.02이므로, 0.1의 차이는 다섯 문항의 차이가 되어 우연으로 보기 어려워진다.

키트의 테스트 test_기본_설정의_재현율은_기록한_값_이상이다는 기본 설정의 재현율@3이 0.8 아래로 떨어지면 실패한다. 측정을 테스트로 만들어 두면, 나중에 누군가 청킹이나 검색 코드를 고쳐 재현율을 떨어뜨렸을 때 바로 드러난다. 이것을 회귀 시험이라 한다. 다만 이 테스트의 기준(0.8)은 대체 구현으로 잰 값이다. 테스트는 언제나 대체 구현으로 돌도록 conftest.py가 EMBED_BACKEND=fallback을 설정해 두었다.

7-2. 배치의 근거

Claude 문서의 긴 문맥 프롬프트 지침은 두 가지를 권한다[P1]. 첫째, 긴 문서는 프롬프트의 위쪽에 두고 질문과 지시는 그 아래에 둔다. 같은 지침은 질문을 끝에 두었을 때 복잡한 다중 문서 입력에서 응답 품질이 최대 30%까지 나아졌다는 시험 결과를 소개한다[P1]. 둘째, 여러 문서를 쓸 때는 문서마다 태그로 감싸고 출처 같은 메타데이터를 하위 태그로 붙인다[P1]. 이 장의 형식(자료 → 질문 → 지시, 근거마다 번호와 출처)은 이 지침을 따랐다. 태그 이름을 한국어로 쓴 것은 학생이 읽기 쉽게 하기 위해서이며, 태그 이름 자체에 정해진 규칙은 없다.

7-3. 인용을 받는 두 방식

이 장은 지시 3으로 모델에게 “[1]처럼 번호를 붙이라”고 시키고, 코드가 답에서 [숫자]를 찾아 화면에 연결한다(cited_numbers). 이를 프롬프트 기반 인용이라 한다. 모델이 번호를 빠뜨리거나 없는 번호를 쓸 수 있다는 약점이 있다.

Claude API에는 인용(Citations) 기능이 따로 있다[P2]. 문서를 document 블록으로 보내고 인용을 켜면, API가 답의 각 주장에 대해 근거 문서의 정확한 위치와 인용한 글(cited_text)을 구조화된 형식으로 돌려준다. 문서에 따르면 이 방식은 인용이 반드시 제공된 문서의 올바른 위치를 가리키도록 보장하며, cited_text는 출력 토큰으로 계산하지 않는다[P2]. RAG의 청크마다 문장 단위로 인용하게 하려면 청크를 일반 텍스트 문서로, 청크를 더 쪼개지 않으려면 사용자 정의 내용(custom content) 문서로 넣으라고 안내한다[P2].

7-4. 근거의 양: 컨텍스트 예산

k를 키우면 재현율은 오르거나 그대로이지만, 근거 블록이 길어지고 관계없는 청크도 함께 들어간다. Contextual Retrieval 실험에서는 상위 20개를 넘긴 것이 10개나 5개보다 나았으나, 같은 글은 청크를 많이 넣으면 모델이 산만해질 수 있으니 실험으로 정하라고 하였다[A2]. 키트는 두 가지로 양을 조절한다. 근거 수는 TOP_K(기본 3)로, 근거 본문의 전체 글자 수는 MAX_CONTEXT_CHARS(기본 3,000자)로 제한한다. fit_evidence는 상한을 넘으면 순위가 낮은 근거부터 빼고, 1위는 항상 남긴다.

파일: jobprep/rag/answer.py (일부, 완성되어 있음) 
def fit_evidence(hits, max_chars=None):
    max_chars = max_chars or config.max_context_chars()
    kept, total = [], 0
    for hit in hits:
        size = len(hit["chunk"]["text"])
        if kept and total + size > max_chars:
            break
        kept.append(hit)
        total += size
    return kept

8. 「자료에 없다」 응답과 유사도 기준값

8-1. 검색기는 “없다”고 말하지 않는다

5절에서 본 대로 검색기는 질문과 관계가 없어도 항상 k개를 돌려준다. “학생식당 이번 주 메뉴 알려줘”라는 질문에도 가장 덜 먼 청크 세 개가 근거로 붙는다. 그 근거로 모델이 무언가를 답하기 시작하면 사고가 된다. 그래서 「자료에 없다」를 두 층으로 만든다.

층 어디서 무엇을 막는가 키트
1층: 유사도 기준값 코드. 검색 직후, LLM을 부르기 전 자료와 아예 관계없는 질문 answer()의 top < threshold 판정, RAG_MIN_SCORE
2층: 프롬프트 지시 모델. 근거를 읽은 뒤 관련 문서는 있지만 답이 들어 있지 않은 질문 지시 2

1층은 LLM을 부르지 않으므로 비용이 들지 않고 결과가 매번 같다. 2층은 1층을 통과한 질문 가운데 근거에 답이 없는 것을 막는다. 예를 들어 “취업 장려금은 인턴도 받을 수 있어?”는 취업 장려금 절과 가깝지만, 만약 그 절에 인턴에 관한 문장이 없었다면 모델이 지시 2로 거절해야 한다.

8-2. 기준값은 맞바꾸기다

기준값을 높이면 자료에 있는 질문까지 거절하고(과잉 거절), 낮추면 자료에 없는 질문에 엉뚱한 근거로 답한다(오답). 어느 쪽이 더 나쁜지는 서비스가 정한다.

취업 자료 질의응답에서 기준값이 너무 높으면 자료에 있는 질문도 “자료에 없다”가 되고, 학생은 취업지원실에 직접 문의한다. 불편하지만 해는 적다. 기준값이 너무 낮으면 자료에 없는 질문에 관계없는 근거로 답하고, 학생은 틀린 마감일이나 틀린 학점 기준을 믿게 된다. 해가 크다. 이 서비스에서는 오답의 비용이 더 크므로, 두 무리 사이에서 안전한 쪽으로 정한다. 기준값을 정하는 절차는 다음과 같다.

  1. 자료에 있는 질문(평가 문항 10개)과 자료에 없는 질문(범위 밖 문항 3개)의 1위 유사도를 각각 잰다.
  2. 두 무리가 갈리면 그 사이의 값을 기준값으로 정한다. 키트의 calibrate는 두 값의 가운데를 후보로 낸다.
  3. 두 무리가 겹치면 기준값만으로는 가를 수 없다. 2층(프롬프트 지시)이 막아야 하고, 임베딩 모델이나 청킹을 바꾸어 다시 잰다.
  4. 임베딩 모델, 청킹 설정, 자료를 바꾸면 1번부터 다시 한다.

키트의 기본 기준값은 대체 구현에서 0.18, Ollama 경로에서 0.50이다. 0.18은 집필 때 이 절차로 잰 값이고, 0.50은 자리만 잡아 둔 값이다. Ollama 경로의 기준값은 그 모델로 calibrate를 돌려 다시 정한다(교수 시연의 실행 기록 5절, 또는 3-5의 [선택]). 임베딩이 같아도 청킹 설정을 바꾸면 기준값이 움직인다는 것은 핵심 실습에서 직접 본다(12-10).

거절 문장은 config.py의 상수 NO_ANSWER 하나로 고정한다.

파일: jobprep/rag/config.py (일부) 
NO_ANSWER = "제공된 취업 자료에는 이 질문에 대한 내용이 없습니다. 취업지원실(공학관 205호)에 문의하십시오."

문장을 고정해 두면 세 가지가 쉬워진다. 첫째, 프롬프트의 지시 2가 이 문장을 그대로 쓰라고 할 수 있다. 둘째, 코드가 모델의 답에 이 문장이 들어 있는지로 grounded(근거로 답했는가)를 판정할 수 있다. 셋째, 화면이 거절을 다른 모양으로 보일 수 있다. 문장 끝에 다음 행동(취업지원실 문의)을 넣은 것은 거절만 하고 끝나면 사용자가 막다른 길에 서기 때문이다. 이 문장은 서비스가 사용자에게 내보내는 문구이므로 존댓말로 썼다.

8-4. 거절은 자료 보강의 신호다

서비스를 내놓은 뒤에는 “자료에 없다”로 답한 질문이 쌓인다. 이 기록은 두 가지로 쓰인다. 첫째, 자주 거절된 질문은 자료가 비어 있는 곳을 가리킨다. “기숙사 입사 신청”을 묻는 학생이 많다면 취업 자료의 범위를 넓힐지, 학교 생활 안내 서비스로 안내할지를 정해야 한다. 둘째, 거절된 질문 가운데 자료에 답이 있었던 것은 과잉 거절이므로 기준값이나 검색을 고칠 단서가 된다. 이런 질문은 정답 절을 표시해 평가 문항에 더한다.

기록할 때는 개인 정보에 주의한다. 학생의 질문에는 이름, 학번, 지원한 회사 같은 정보가 섞일 수 있다. 기록은 질문 원문 대신 범주와 1위 유사도만 남기거나, 원문을 남기더라도 보관 기간과 열람 권한을 정한다. 5장에서 다룬 비식별화가 여기서도 쓰인다. 이 장의 키트는 거절 기록을 남기지 않는다. 기록 기능을 더한다면 그것도 명세의 요구(「만약 “자료에 없다”로 답하면, 시스템은 질문의 범주와 1위 유사도를 기록해야 한다」)로 먼저 적는다.

9. 대화 이력과 컨텍스트 크기

9-1. 이력은 프로그램이 들고 다닌다

Claude API는 이전 호출을 기억하지 않는다. 대화가 이어지는 것처럼 보이는 것은 프로그램이 지금까지의 대화를 messages에 담아 매번 다시 보내기 때문이다(10장). Claude 문서의 컨텍스트 창 설명도 대화가 진행될수록 사용자 메시지와 모델의 답이 컨텍스트 창 안에 쌓이며, 시스템 프롬프트와 모든 메시지가 컨텍스트 창을 차지한다고 설명한다[P3].

RAG에서는 무엇을 이력에 쌓을지가 문제다. 매 질문의 증강 프롬프트(근거 블록 포함)를 그대로 쌓으면 세 가지가 나빠진다.

  1. 누적. 질문마다 근거 세 개(약 600자)가 이력에 쌓인다. 열 번째 질문에는 지난 근거 27개가 함께 간다.
  2. 비용. 매 호출의 입력 토큰이 늘어 요금이 커진다. 대화 한 건의 비용은 대략 「평균 입력 길이 × 호출 수 × 토큰 단가」이므로, 이력에 무엇을 남기는지가 곧 비용 결정이다.
  3. 오염. 지난 질문의 근거가 새 질문의 답을 끌어간다. 지난 프롬프트의 [1]과 이번 프롬프트의 [1]이 서로 다른 근거를 가리키므로 근거 번호도 엉킨다.

그래서 이력에는 원래 질문과 답만 남기고, 근거 블록은 이번 질문의 것만 마지막 메시지에 붙인다. answer()가 만드는 messages는 다음 모양이다.

[ {user: 앞 질문}, {assistant: 앞 답}, …(최근 4왕복까지)…, {user: <자료>…</자료><질문>이번 질문</질문>지시…} ]

9-2. 자르기와 요약하기

대화가 길어지면 결국 컨텍스트 창의 한계에 닿는다. 현재 Claude 모델들의 컨텍스트 창은 모델에 따라 100만 토큰 또는 20만 토큰이다[P3]. 한계에 닿기 전에도 문제가 있다. Claude 문서는 토큰 수가 늘수록 정확도와 회상이 떨어지는 현상을 컨텍스트 부패(context rot)라 부르며, 얼마나 넣을 수 있는지보다 무엇을 넣는지를 고르는 일이 중요하다고 설명한다[P3]. 이력을 다루는 방법은 크게 둘이다.

[최신 자료 자리: 컨텍스트 창의 크기와 압축 기능의 상태] 수업에서 쓰는 모델의 컨텍스트 창과 서버 쪽 압축(compaction)의 제공 상태. 확인할 곳은 https://platform.claude.com/docs/en/build-with-claude/context-windows다. 2026-11-16에 확인한 값은 현행 네 모델을 포함한 최근 모델이 100만 토큰, 그 밖의 모델(Claude Sonnet 4.5 등)이 20만 토큰이고, 압축은 Claude 4.6 이후 모델에서 베타로 제공된다. 수업 직전에 다시 확인한다.

자르기 요약하기
하는 일 최근 몇 왕복만 남기고 앞을 버린다 앞 대화를 짧은 요약으로 바꾸어 남긴다
비용 없음 요약할 때 LLM 호출이 한 번 더 든다
잃는 것 버린 내용은 완전히 잊는다 요약 과정에서 내용이 빠지거나 바뀔 수 있다
맞는 서비스 질문이 한 건씩 끝나는 안내형(이 장) 처음 조건이 끝까지 필요한 상담형

취업 자료 질의응답은 질문이 대개 한 건씩 끝나므로 자르기를 쓴다. trim_history는 최근 MAX_TURNS(기본 4) 왕복, 곧 메시지 8건만 남긴다. 이 함수도 핵심 실습(12-3)에서 완성한다. Claude API에는 서버 쪽에서 앞 대화를 자동으로 요약하는 압축(compaction) 기능도 있다[P3]. 긴 대화를 다루는 상담형 서비스라면 비교해 볼 만하다.

9-3. 이력은 생성에만 들어가고 검색에는 들어가지 않는다

이 장의 구조에는 알아 둘 빈틈이 하나 있다. 이력은 생성 단계의 messages에는 들어가지만, 검색은 이번 질문 한 문장으로만 한다. 그래서 “현장실습 중에 아파서 못 가면 어떻게 해?” 다음에 “그럼 진단서는 언제까지 내?”라고 이어 물으면, 검색기는 「그럼 진단서는 언제까지 내?」만 보고 청크를 찾는다. 집필 때 화면에서 두 질문을 차례로 보낸 결과, 이 이어진 질문의 1위 유사도는 0.098로 기준값 0.18보다 낮아 “자료에 없다”로 답하였다. 정답(제11조의 “증빙은 실습이 끝난 뒤 7일 안에”)이 자료에 있는데도 그렇다.

실무에서는 이 빈틈을 질문 다시 쓰기(query rewriting)로 메운다. 검색하기 전에 LLM에게 이력과 이번 질문을 주고 “앞 대화 없이도 뜻이 통하는 검색용 질문 한 문장”을 만들게 한 뒤, 그 문장으로 검색한다. 호출이 한 번 늘어나는 대신 이어진 질문의 검색이 나아진다. 이 장의 키트는 이를 구현하지 않았다. 명세서에 “알려진 한계”로 적어 두고, 12장의 대화형 구현에서 다시 다룬다.

10. 근거 표시 화면

10-1. 근거를 보여 주는 까닭

RAG의 답은 근거와 함께 보여야 쓸모가 있다. 사용자는 답 옆의 번호를 눌러 원문을 확인할 수 있어야 하고, 개발자는 틀린 답을 보고 검색이 틀렸는지 생성이 틀렸는지를 가를 수 있어야 한다. 키트의 화면 web/ask.html은 세 가지를 보인다.

영역 보이는 것 사용자가 하는 일
답 모델의 답. [1], [2]는 근거 목록으로 가는 링크 번호를 눌러 해당 근거로 이동한다
근거 상태 “근거 3개를 찾아 답하였다(1위 유사도 0.203)” 또는 “근거를 찾지 못하였다” 답을 얼마나 믿을지 정한다
근거 목록 번호, 문서 제목 › 절 제목, 유사도, 답에 사용했는지, 펼치면 본문 원문을 읽어 답과 대조한다

유사도 숫자를 사용자에게 보일지는 서비스마다 판단이 다르다. 학생에게는 숫자가 어렵고, 개발 단계에서는 숫자가 디버깅에 쓸모 있다. 이 장은 학습을 위해 보이고, 13장의 사용성 평가에서 다시 판단한다.

10-2. 답을 글자 그대로 넣는다

화면 코드에서 가장 중요한 규칙은 서버가 준 글을 HTML로 해석하지 않는 것이다. 답과 근거 본문에는 자료를 쓴 사람과 모델이 만든 글이 섞여 있다. 그 안에 <img src=x onerror=…> 같은 글이 들어 있을 때 innerHTML로 넣으면 브라우저가 그것을 HTML로 해석해 스크립트를 실행할 수 있다. 크로스 사이트 스크립팅(XSS)이다. MDN은 innerHTML이 일반 텍스트가 아니라 HTML을 다루므로 XSS 공격에 취약할 수 있어, 글을 넣을 때는 쓰지 말라고 권한다[W1]. 10장에서 다룬 OWASP의 부적절한 출력 처리(2025년판 LLM05, 2026년판 LLM10)와 같은 문제다.

ask.js는 모든 글을 textContent로 넣고, 답 속의 [숫자]만 골라 링크 요소를 만들어 붙인다.

파일: jobprep/web/ask.js (일부) 
function renderAnswer(text, citationCount) {
  const box = $("answer");
  box.replaceChildren();
  const parts = text.split(/(\[\d+\])/);
  for (const part of parts) {
    const m = part.match(/^\[(\d+)\]$/);
    const n = m ? Number(m[1]) : 0;
    if (m && n >= 1 && n <= citationCount) {
      const a = document.createElement("a");
      a.href = `#cite-${n}`;
      a.textContent = part;
      a.className = "cite";
      box.append(a);
    } else {
      box.append(document.createTextNode(part));
    }
  }
}

split에 괄호가 있는 정규식을 주면 구분자([1] 등)도 결과 배열에 남는다. 번호가 근거 수를 넘으면(모델이 없는 번호를 쓴 경우) 링크로 만들지 않고 글자로 둔다.

이 규칙이 키트의 화면에서 지켜지는지는 핵심 실습에서 grep으로 센다(12-8).

10-3. 대화 이력은 화면이 들고 있다

API는 이력을 저장하지 않는다. 화면이 원래 질문과 답을 배열 history에 모아 두었다가 요청마다 최근 4왕복을 함께 보낸다. 서버는 받은 이력을 다시 trim_history로 자른다. 화면과 서버가 같은 상한을 두는 까닭은, 화면 코드는 사용자가 바꿀 수 있으므로 서버가 믿고 쓸 수 없기 때문이다. 요청 모델(AskRequest)도 질문은 500자, 이력은 40건으로 길이를 제한한다.

파일: jobprep/api/ask_route.py (일부) 
class Turn(BaseModel):
    role: Literal["user", "assistant"]
    content: str = Field(max_length=4000)


class AskRequest(BaseModel):
    question: str = Field(min_length=1, max_length=500)
    history: list[Turn] = Field(default_factory=list, max_length=40)

Literal["user", "assistant"]은 그 두 값만 받는다는 뜻이다. 화면이 "system" 같은 역할을 보내 시스템 지시를 바꾸려 하면 FastAPI가 422 오류로 거절한다.

11. 명세에 RAG 요구 추가

11-1. 명세에서 시작한다

6장부터 이 과목은 구현을 바꾸기 전에 명세서를 먼저 고친다. 이 장도 같다. RAG 기능의 요구를 docs/요구사항명세서.md에 EARS 문형으로 더한 뒤, 그 명세를 Claude Code에 주어 구현하게 한다. 명세의 요구 하나하나가 테스트 하나 이상과 이어지고, 측정(재현율@3)도 요구로 적는다.

EARS의 다섯 문형을 다시 정리한다[E1]. 영어 원형의 키워드(While, When, Where, If … then)를 이 과목은 한국어 문형으로 옮겨 쓴다(6장).

문형 영어 원형 이 장의 한국어 문형 이 장의 예
항상(Ubiquitous) The system shall … 시스템은 …해야 한다 근거 블록, 질문, 지시의 순서로 프롬프트를 만든다
사건(Event-driven) When …, the system shall … …하면, 시스템은 …해야 한다 질문을 보내면 상위 3개 청크를 근거로 고른다
상태(State-driven) While …, the system shall … …하는 동안, 시스템은 …해야 한다 대화가 이어지는 동안 최근 4왕복만 보낸다
선택 기능(Optional feature) Where …, the system shall … …가 있는 곳에서는, 시스템은 …해야 한다 Ollama가 있는 곳에서는 그 모델로 임베딩한다
원치 않는 상황(Unwanted behaviour) If …, then the system shall … 만약 …이면, 시스템은 …해야 한다 만약 1위 유사도가 기준값보다 낮으면 LLM을 부르지 않는다

12. 핵심 실습: 취업 자료 질의응답의 구현과 검색 회귀의 해결

Claude Code는 먼저 명세와 네 파일을 읽고, 계획을 보인 뒤 파일을 고치겠다고 권한을 묻는다. 권한 창에서 고치려는 파일이 세 개(search.py, evaluate.py, answer.py)를 벗어나는지 본다. tests/나 자료/를 고치겠다고 하면 거절하고 지시를 다시 보낸다(2장의 권한 확인). 고침 지시는 1~2회까지로 한다(0절의 실행 상한).

[최신 자료 자리: Claude Code의 권한 창 문구와 판] 권한 창의 선택지 문구와 단축키, 권한 모드의 이름. 확인할 곳은 https://code.claude.com/docs/en/permissions와 내 PC의 claude --version이다. 2026-11-16에 집필 PC에서 확인한 판은 Claude Code 2.1.296이며, 권한 창의 실제 문구는 이 장에서 확인하지 못하였다.

12-4. 테스트 판정

테스트를 직접 실행하고, 테스트 파일이 그대로인지 키트의 원본과 견준다. 테스트를 고쳐 통과시키는 일을 막기 위해서다.

터미널 
python -m pytest tests/rag
diff -r -x __pycache__ tests/rag ~/kits/Service_11장/jobprep/tests/rag && echo "테스트 파일 그대로"
.............................                                            [100%]
29 passed in 4.93s
테스트 파일 그대로

diff -r은 두 폴더를 하위 폴더까지 견주고, -x __pycache__는 그 이름의 폴더를 비교에서 뺀다[U1]. 테스트를 실행하면 파이썬이 tests/rag/__pycache__/에 컴파일한 파일을 남기는데[U2], 키트의 원본 폴더에는 그것이 없다. -x를 빼면 테스트 파일이 그대로여도 Only in tests/rag: __pycache__ 한 줄이 나오고 && 뒤의 echo가 실행되지 않는다. diff가 아무것도 출력하지 않고 테스트 파일 그대로가 나오면 두 폴더가 같다.

결과 읽기: 내 화면은 어느 갈래인가. 숫자가 아니라 마지막 줄과 오류의 종류로 찾는다. ①만 다음 단계로 간다.

갈래 화면 상태 할 일
① 29 passed와 테스트 파일 그대로 완료 12-5로
② N failed이고 실패 줄 끝이 NotImplementedError 네 함수 가운데 아직 비어 있는 것이 있다 실패한 테스트의 파일 이름(test_rag_search 등)으로 빈 함수를 찾아 그 함수만 다시 지시한다
③ N failed이고 AssertionError: assert … 함수는 있으나 독스트링과 다르게 동작한다 기대값과 실제 값을 읽고, 그 테스트의 요구(11-2의 표)를 Claude Code에 알려 고치게 한다
④ 통과했는데 diff가 37c37처럼 바뀐 줄을 출력한다 테스트가 고쳐졌다. 통과는 근거가 되지 못한다 키트의 원본 테스트를 다시 복사하고, 구현만 고치라고 다시 지시한다
⑤ Only in tests/rag: __pycache__만 나온다 테스트는 그대로다. 명령에서 -x __pycache__를 빠뜨렸다 명령을 고쳐 다시 실행한다

③의 화면에서 E 줄의 == 왼쪽이 실제 값, 오른쪽이 기대값이다. 그 차이를 한 문장으로 말할 수 있으면(예: “유사도가 낮은 것부터 나온다”) Claude Code에 보낼 고침 지시도 짧아진다.

통과한 뒤에는 구현을 한 번 읽는다. trim_history가 max_turns가 0일 때를 어떻게 다루었는지 본다. history[-0:]은 빈 목록이 아니라 전체를 돌려준다. 독스트링이 정하지 않은 경계를 구현이 어떻게 다루었는지 읽는 것이 리뷰의 일이다.

  • 확인 6 tests/rag가 29 passed이고 diff -r -x __pycache__가 아무것도 출력하지 않아 테스트 파일 그대로가 나온다(갈래 ①). 처음에 다른 갈래였으면 그 번호와 고친 방법을 말할 수 있다.

12-7. API 연결

10장의 FastAPI 앱(api/app.py)에 질의응답 라우터를 붙인다. 두 줄을 더한다. 10장의 앱은 파일 맨 끝에서 9장의 웹 폴더를 뿌리 경로(/)에 붙인다(app.mount("/", StaticFiles(...))). 라우터는 반드시 이 줄보다 위에서 등록한다. 뿌리 경로에 붙인 정적 파일 앱이 먼저 등록되면 /api/ask 요청까지 가로채기 때문이다. FastAPI 문서는 큰 앱을 여러 파일로 나눌 때 APIRouter를 만들고 app.include_router()로 붙이는 방식을 안내하고[F2], 정적 파일은 app.mount로 붙인다고 설명한다[F3].

### 알려진 한계 (11장)

- 검색은 이번 질문 한 문장으로만 한다. 앞 대화에 기대는 이어진 질문(예: "그럼 진단서는 언제까지 내?")은 근거를 찾지 못할 수 있다. 질문 다시 쓰기(query rewriting)는 12장에서 검토한다.

12-13. 실제 모델의 답 읽기 [선택]

모의 응답은 1위 근거의 첫 문장을 옮길 뿐이므로 답의 질을 보여 주지 못한다. 실제 모델의 답은 두 길 가운데 하나로 본다. Console 키를 발급해 .env에 키와 LLM_MODEL을 넣은 학생은 아래 명령을 한 번만 실행한다(0절의 실행 상한). 명령 앞의 LLM_FAKE=0은 그 명령 한 번에만 모의 모드를 끈다(부록 A-15-3). 키가 없는 학생은 실행 기록 6절에서 같은 질문의 증강 프롬프트와 실제 모델의 답을 읽는다.

[터미널] (Console 키를 발급한 학생만, 1회)

LLM_FAKE=0 python -m rag ask "취업 장려금은 인턴도 받을 수 있어?"

모의 응답은 1위 근거의 첫 문장(“학과는 … 취업 장려금 20만 원을 지급한다. [1]”)만 옮겨 질문(인턴도 받는가)에 답하지 못한다. 실제 모델은 셋째 문장(“인턴과 계약 기간이 6개월 미만인 일자리는 장려금 대상이 아니다”)으로 답할 것으로 기대하나, 집필 때 실제 호출을 하지 않아 결과를 싣지 않는다.

재현율은 “정답 근거가 들어갔는가”만 센다. 근거가 들어갔어도 모델이 그것을 잘못 읽거나 근거 밖의 말을 덧붙일 수 있으므로, OWASP는 응답이 근거에 바탕을 두었는지(groundedness)를 평가하라고 권한다[O1]. 답 하나를 다음 네 물음으로 판정한다.

  1. 답의 문장마다 근거 번호가 있는가.
  2. 번호가 가리키는 근거를 펼쳤을 때 그 문장의 내용이 실제로 들어 있는가.
  3. 근거에 없는 숫자, 날짜, 이름이 답에 들어 있지 않은가.
  4. 근거에 답이 없었다면 정해진 「자료에 없다」 문장으로 답했는가.

답이 틀렸으면 prompt의 출력으로 원인의 단계를 가른다. 정답 절이 상위 3개에 없었으면 검색(청킹, 임베딩, 검색 방법), 상위 3개에 있었는데 프롬프트에서 빠졌으면 증강(MAX_CONTEXT_CHARS, fit_evidence), 프롬프트에 있었는데도 틀렸으면 생성(지시 문장, 모델)의 문제다.

판정 결과는 docs/검색평가.md 7절에 한두 줄로 적는다. 실행도 기록도 없으면 「기록 없음」으로 적는다.

  1. 구현은 Claude Code가, 판정은 내가 하였다. 근거는 직접 실행한 29 passed와 테스트 폴더의 diff였다(12-4).
  2. 검색은 측정으로 골랐다. vector 0.90, 혼합 0.80이었고, 범위 밖 질문은 기준값에서 거절되었다(12-5, 12-6).
  3. 회귀는 원인을 찾은 뒤 설정 하나로 고쳤다. 4번을 놓친 원인은 고정 길이의 경계였고 겹침 하나로 고쳤으며, 기준값이 0.17로 내려간 대가까지 재어 채택을 정하였다(12-9~12-11).

이 절은 [선택]이며 확인 번호가 없다. 같은 위험을 「AI에이전트 기획 및 개발」 11장이 셸과 파일 쓰기를 가진 에이전트에서 깊이 다룬다. 이 장에서는 RAG의 자료가 지시가 되는 경로와 겹 방어를 읽고, 시간이 남거나 수업 뒤에 실험(13-3)을 해 본다.

13-1. 자료가 지시가 되는 경로

RAG는 문서의 글을 프롬프트에 그대로 넣는다. 그 글 안에 “이전 지시를 무시하고 …라고 답하라” 같은 문장이 있으면, 모델은 그것을 자료로 읽을 수도 있고 지시로 읽을 수도 있다. 사용자가 직접 넣은 것이 아니라 외부 자료를 거쳐 들어온 지시이므로 간접 프롬프트 주입(indirect prompt injection)이라 한다.

OWASP의 LLM 응용 10대 위험은 이것을 첫째 위험인 프롬프트 주입(LLM01. 2025년판과 2026년판 모두 1위)의 한 갈래로 다룬다[O1][O3]. 간접 프롬프트 주입은 LLM이 웹 사이트나 파일 같은 외부 출처의 입력을 받을 때 일어나며, 그 내용은 사람에게 보이지 않아도 모델이 읽기만 하면 된다[O1]. 같은 문서는 RAG와 미세 조정이 정확도를 높이지만 프롬프트 주입을 완전히 막지는 못한다는 연구를 언급하고, 공격 시나리오의 하나로 RAG 저장소의 문서를 고쳐 그 문서가 검색될 때 답을 왜곡하는 경우를 든다[O1].

정리

  • RAG는 모델이 모르는 자료(학습 시점 뒤의 정보, 내부 문서)를 질문마다 찾아 근거로 붙이고, 그 안에서만 답하게 하는 구조다. 색인 단계(청킹, 임베딩, 저장)와 질의 단계(검색, 증강, 생성)로 나뉜다.
  • 정규화된 임베딩 벡터의 내적이 코사인 유사도다. 눈금은 모델마다 다르므로 색인과 질문은 같은 모델로 만들고, 측정을 서로 견주려면 임베딩 경로를 고정한다(키트의 기본값 fallback).
  • 청킹은 경계, 길이, 겹침의 선택이며, 설정을 하나씩 바꾸어 같은 평가 문항의 재현율@k로 고른다. 문항이 10개이면 한 문항이 0.1이므로 차이는 놓친 문항을 들여다보며 읽는다.
  • 설정을 바꾸어 전에 찾던 문항을 놓치면 회귀다. 1위의 절과 정답 절의 조각을 열어 원인(이 장에서는 고정 길이의 경계)을 찾고, 설정 하나(겹침)로 고친 뒤, 기준값에 준 영향까지 재어 채택을 정한다.
  • 증강 프롬프트는 자료 → 질문 → 지시의 순서로 쓰고, 근거마다 번호와 출처를 붙인다.
  • 「자료에 없다」는 두 층이다. 코드의 유사도 기준값이 관계없는 질문을 LLM 앞에서 막고, 프롬프트의 지시가 근거에 답이 없는 질문을 막는다.

개념 점검

  1. 평가 문항 하나의 정답 절이 둘(A, B)이고 상위 3개 청크가 걸친 절이 A, C, D일 때, 이 문항의 재현율@3과 적중@3은 각각 얼마인가.
  2. 대체 임베딩으로 만든 색인을 그대로 두고 EMBED_BACKEND=ollama로 질문만 바꾸어 검색하면 무엇이 문제인가. 키트는 이것을 어떻게 막는가.
  3. 유사도 기준값을 0.30으로 올리면 이 장의 대체 구현(기본 설정)에서 무엇이 일어나는가. calibrate의 출력으로 설명하라.
  4. 대화 이력에 증강 프롬프트(근거 블록 포함)를 그대로 쌓으면 생기는 문제 두 가지를 쓰라.
  5. 고정 길이 200자에서 4번 문항을 놓친 원인은 무엇이며, 겹침 50이 그것을 고친 까닭은 무엇인가. 겹침 50을 채택할 때 기준값을 다시 정해야 하는 까닭도 쓰라.
