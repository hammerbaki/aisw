[부록 A] 실습 환경

2027학년도 「LLM 서비스 개발」의 준비 중인 교재입니다. 편집 상태를 검토하기 위해 미리 공개한 것으로, 수업 전에 내용과 순서가 바뀔 수 있습니다.

「LLM 서비스 개발」 1~13장의 공통 부록 · 2026-11 기준

이 부록은 실습 환경을 갖추는 절차를 한곳에 모은 것이다. 이 과목의 실습은 학생 각자의 계정으로, 개인 노트북(권장) 또는 실습실 PC에서 한다(사용자 결정 11, 2026-11-16). 학과 실습 서버는 쓰지 않는다. 계정 준비, 터미널과 편집기, 파이썬·GitHub CLI·Claude Code의 설치와 로그인, Git과 GitHub의 준비, 키트 받기, 가상 환경, 프로덕트용 API 키와 모의 모드, 포트, 로컬 임베딩, 브라우저 검사 도구, 브라우저 에이전트 Aside와 에이전트 개발 환경 Orca의 준비를 차례로 다룬다. 각 장의 0절은 이 절차를 되풀이하지 않고 이 부록의 절 번호를 가리킨다.

실습실 PC는 Windows 11로 가정한다. 본문의 명령과 출력은 Windows 11의 Git Bash를 기준으로 하고, macOS에서 달라지는 곳만 따로 적는다.

A-1. 실습 환경의 구성

이 과목의 실습은 학습자 각자의 PC에서 한다. 파일, 프로그램, 계정의 로그인이 모두 그 PC에 있다. 개인 노트북을 권장한다. 실습실 PC를 쓰면 매 수업 같은 자리에 앉는 것이 아니고, 복원 프로그램이 있으면 껐다 켤 때 설치와 로그인이 지워질 수 있기 때문이다. 어느 PC에서 하든 작업은 GitHub의 저장소로 이어진다. 한 PC에서 커밋해 푸시하고, 다른 PC에서 받아 이어 한다.

A-3. 터미널과 셸

이 교재의 명령은 bash 문법으로 쓴다. Windows에서는 Git for Windows에 딸린 Git Bash를 쓴다. Git Bash는 Windows에서 bash와 ls, cp, grep 같은 유닉스 명령을 쓰게 해 주는 셸이고, Windows의 Claude Code가 셸 명령을 실행할 때 쓰는 셸이기도 하다[C1]. 같은 셸에서 사람이 직접 명령을 실행하면 Claude Code가 보는 결과와 사람이 보는 결과가 같아진다.

터미널은 창이고, 셸은 그 창 안에서 명령을 받아 실행하는 프로그램이다. 같은 명령이라도 어느 셸에 입력하느냐에 따라 결과가 다르다.

A-3-1. Windows: Git for Windows 설치

A-3-4. Windows에서 한글이 깨질 때: 파이썬의 UTF-8 모드와 curl

Windows의 파이썬은 따로 정하지 않으면 한국어 Windows의 기본 문자 집합(cp949)으로 화면 출력을 내보내고, 표준 입력을 읽고, 파일을 연다. 그래서 Git Bash에서 파이썬의 출력을 파이프(|)로 다른 명령에 넘기면 한글이 깨진다. 파이프로 받는 쪽도 같다. curl … | python -c "…json.loads(sys.stdin.read())…"처럼 UTF-8 JSON을 파이썬이 표준 입력으로 받으면 한글 키를 cp949로 잘못 읽어, 있는 키를 찾지 못하고 KeyError를 낸다(집필용 PC에서 확인, 2026-11-17). 인코딩을 밝히지 않고 UTF-8 파일을 여는 프로그램은 UnicodeDecodeError: 'cp949' codec can't decode로 멈춘다. 환경 변수 PYTHONUTF8=1을 두면 파이썬이 UTF-8 모드로 돌아 화면 출력과 파일의 기본 인코딩이 UTF-8이 된다[P3]. Git Bash를 열 때마다 켜지도록 한 번 등록한다(macOS는 기본이 UTF-8이므로 하지 않아도 된다).

터미널 
echo 'export PYTHONUTF8=1' >> ~/.bashrc
source ~/.bashrc
python -c "import sys; print(sys.flags.utf8_mode, sys.stdout.encoding)" | cat
1 utf-8

등록하기 전에는 같은 명령이 0 cp949를 출력한다(집필용 PC, Windows 11, 파이썬 3.13.7, 2026-11-17). VS Code의 통합 터미널에서도 새 터미널을 연 뒤 위의 확인 명령이 1 utf-8을 출력하는지 본다. 등록한 뒤에는 넘기는 쪽과 받는 쪽이 모두 UTF-8이 된다.

curl의 한글 인자. Git Bash의 curl은 명령줄에 적은 한글을 cp949 바이트로 보낸다. 그래서 -d '{"q": "인턴"}'처럼 한글이 든 요청 본문을 인자로 주면 UTF-8을 기대하는 API 서버가 본문을 읽지 못해 400을 돌려준다. 이것은 파이썬의 설정이 아니므로 PYTHONUTF8=1로 풀리지 않는다. 한글이 든 본문은 heredoc으로 표준 입력에 넣고 --data-binary @-로 보내거나, 파일로 써 두고 --data-binary @파일로 보낸다. heredoc과 파일의 내용은 바이트가 그대로 가므로 UTF-8로 간다.

터미널 
curl -s -X POST http://127.0.0.1:8000/「API 경로」 \n  -H 'Content-Type: application/json' --data-binary @- <<'JSON'
{"q": "인턴도 받을 수 있어?"}
JSON

집필용 PC(curl 8.21.0, Git Bash, 2026-11-17)에서 본문을 UTF-8로 검사하는 시험용 서버에 보내 보았다. -d로 준 인턴은 c0 ce c5 cf(cp949)로 도착해 400을 받았고, 같은 내용을 heredoc과 파일로 보내면 ec 9d b8 ed 84 b4(UTF-8)로 도착해 200을 받았다. macOS의 터미널은 UTF-8이므로 이 문제가 없다.

[최신 자료 자리: 파이썬의 UTF-8 모드 기본값] 파이썬의 다음 판들에서 UTF-8 모드가 기본이 되는지. 확인할 곳 [P3]와 PEP 686. 2026-11-17에 집필용 PC의 파이썬 3.13.7에서 기본이 꺼져 있음(0 cp949)을 확인하였다.

A-4. VS Code와 통합 터미널

Claude Code가 만든 파일을 읽고 직접 고치는 일은 편집기로 하고, 실행과 확인은 터미널로 한다. 편집기는 VS Code를 쓰고, 터미널은 VS Code 안의 통합 터미널을 쓴다.

A-4-1. 설치

  1. code.visualstudio.com에서 자기 운영체제의 설치 파일을 내려받아 설치한다. 선택 항목은 기본값으로 둔다. Windows의 설치 화면에 「PATH에 추가」 항목이 있으면 켜 둔다. 실습실 PC에 이미 있으면 실행만 확인한다.
  2. VS Code를 실행한다.

A-4-2. 통합 터미널을 Git Bash로 (Windows)

VS Code의 Windows 판은 통합 터미널을 PowerShell로 연다. 이 교재의 명령은 bash 문법이므로 기본 터미널을 Git Bash로 바꾼다[V1].

  1. Ctrl+Shift+P로 명령 팔레트를 연다.
  2. Terminal: Select Default Profile을 입력해 고른 뒤, 목록에서 Git Bash를 고른다. 목록에 없으면 A-3-1의 설치가 끝났는지 보고 VS Code를 다시 시작한다.
  3. 메뉴의 Terminal > New Terminal로 터미널을 연다. 터미널 패널 오른쪽 위에 bash가 보이고, 입력 줄이 Git Bash의 모양이면 된다.

같은 설정을 설정 파일(settings.json)에 직접 적을 수도 있다. 설정 키는 terminal.integrated.defaultProfile.windows이고 값은 "Git Bash"이다[V1].

macOS는 통합 터미널이 기본 셸(zsh)로 열리므로 바꿀 것이 없다.

[최신 자료 자리: VS Code의 터미널 프로필 메뉴 이름] 명령 팔레트의 Terminal: Select Default Profile, 설정 키 terminal.integrated.defaultProfile.windows, 터미널 패널의 + 옆 화살표 메뉴. 확인할 곳: https://code.visualstudio.com/docs/terminal/profiles. 2026-11-16 확인 값: 본문의 이름과 같다. 집필용 PC의 VS Code는 1.144.0이다. 수업 전에 다시 확인한다.

A-4-3. 터미널 두 개의 배치

이 과목은 터미널 두 개를 나란히 두고 일한다. 한쪽에서 Claude Code에게 일을 시키고, 다른 쪽에서 그 결과를 사람이 직접 실행하고 확인한다. “AI가 만들고 사람이 검증한다”는 이 과목의 원칙을 화면 배치로 옮긴 것이다.

  1. 메뉴의 File > Open Folder로 작업 폴더를 연다. 1장에서는 홈 폴더 아래의 llm-service-lab(없으면 1장 0절에서 만든다), 2장부터는 ~/llm-service-lab이다. 폴더를 신뢰할지 물으면 내가 만든 폴더이므로 신뢰한다.
  2. Terminal > New Terminal로 터미널을 연다.
  3. 터미널 패널 오른쪽 위의 분할 아이콘(또는 Terminal > Split Terminal)을 눌러 하나 더 연다.
자리 이름 하는 일 꼬리표
왼쪽 Claude Code 터미널 claude를 실행해 일을 시킨다 [Claude Code]

  • 두 터미널의 현재 폴더는 따로 움직인다. 한쪽에서 cd를 해도 다른 쪽은 그대로이다. 실습 전에 두 터미널 모두 그 장의 작업 폴더로 옮긴다.
  • 가상 환경(A-13)도 터미널마다 따로 켠다.
  • 확인 터미널에서 pwd로 현재 폴더를, ls로 목록을 수시로 확인한다.

  • 마크다운 파일(.md)은 편집기에서 Ctrl+Shift+V를 누르면 서식이 적용된 미리보기로 볼 수 있다. 키트의 README와 양식을 읽을 때 쓴다.

A-7. Claude Code 설치

Claude Code는 각자의 PC에 설치한다. 관리자 권한은 필요 없다[C1].

  2. Claude Code는 Git for Windows가 있으면 셸 명령을 Git Bash로 실행하고, 없으면 PowerShell로 실행한다[C1]. 이 교재의 명령이 bash 기준이므로 A-3-1을 먼저 끝낸다. Git Bash를 찾지 못한다는 안내가 나오면 A-22의 표를 본다.

A-7-2. macOS

[터미널] (macOS)

curl -fsSL https://claude.ai/install.sh | bash

실행 파일은 ~/.local/bin/claude에 놓인다[C1]. 설치가 끝나면 터미널을 새로 연다.

A-8. Claude Code 로그인

이 과목에서 Claude Code는 각자의 구독 계정(A-2-1)으로 로그인해 쓴다. Claude Code에 API 키를 등록하지 않는다.

A-8-1. 첫 로그인

  1. Claude Code 터미널(왼쪽)에서 작업 폴더로 가서 claude를 실행한다.
터미널 
cd ~
claude
  1. 처음 실행하면 화면 테마를 고르고, 로그인 방식을 고르는 화면이 나온다. 구독 계정의 로그인(Claude 계정)을 고른다. 선택지의 이름은 Claude Code 판에 따라 조금씩 다르다.
  2. 내 PC의 브라우저가 열리고 로그인 화면이 나온다. 브라우저가 저절로 열리지 않으면 c를 눌러 로그인 주소를 복사하고 브라우저 주소창에 붙여 넣는다[C2].
  3. 브라우저에서 자기 구독 계정으로 로그인하고 접근을 승인한다.
  4. 브라우저가 터미널로 돌아가지 않고 로그인 코드를 보여 주면, 그 코드를 복사해 터미널의 Paste code here if prompted 자리에 붙여 넣고 Enter를 누른다[C2].
  5. 터미널에 Login successful이 나오면 Enter를 눌러 계속한다.
  6. 이어서 보안 안내와 폴더 신뢰 질문이 나온다. 폴더 신뢰는 Claude Code가 그 폴더의 파일을 읽고 그 폴더의 설정을 적용해도 되는지 묻는 것이다. 내가 만든 폴더이면 신뢰한다고 답한다. 키트나 남의 저장소처럼 내용을 모르는 폴더에서 처음 실행할 때는 이 질문을 그냥 넘기지 않는다.

[그림 자리: Claude Code 첫 실행의 로그인 화면] 로그인 방식을 고르는 목록, 브라우저의 승인 화면, 로그인 뒤의 Login successful을 차례로 보인다(두세 장). 찍을 곳: 실습실 PC(Windows 11)의 VS Code 터미널에서 처음 실행한 claude. 계정의 이메일은 가린다.

Claude Code를 실행하지 않고 셸에서 바로 로그인할 수도 있다. claude auth login은 로그인만 하고 끝나는 명령이다. 기본은 Claude 구독 계정 로그인이고, --console을 붙이면 Claude Console 계정으로, --sso를 붙이면 조직의 SSO로 로그인한다(claude auth login --help, 2026-11-14 확인).

터미널

claude auth status --text

로그인 전에 claude auth status --text를 실행하면 다음이 나온다(2026-11-14, Claude Code 2.1.296, 빈 설정 폴더로 실행).

Anthropic base URL: https://api.anthropic.com
Not logged in. Run claude auth login to authenticate.

로그인한 뒤에는 로그인 방식과 계정을 보여 준다. --text를 빼면 같은 내용을 JSON으로 출력한다.

[최신 자료 자리: 로그인 화면의 문구와 claude auth login의 선택지] 로그인 방식 목록의 이름, 주소 복사 키, 코드 입력 문구, --console·--sso 옵션. 확인할 곳: https://code.claude.com/docs/en/authentication 의 「Log in to Claude Code」, claude auth login --help. 2026-11-15 확인 값: 브라우저가 열리지 않으면 c로 주소를 복사하고, 코드는 Paste code here if prompted에 붙이며, 끝나면 Login successful이 나온다. 옵션은 2026-11-14에 Claude Code 2.1.296의 도움말로 확인하였다. 수업 전에 다시 확인한다.

A-8-3. 로그인의 유지와 다시 로그인

  • 로그인 정보는 Windows에서 홈 폴더의 .claude\.credentials.json에 저장된다(집필용 PC에서 파일의 자리를 확인함, 2026-11-16). macOS는 키체인에 저장된다[C2]. 이 파일을 복사하거나 남에게 보내지 않고, 저장소에 넣지 않는다.
  • 로그인은 PC를 껐다 켜도 유지된다. 로그인이 만료될 때가 가까우면 Claude Code가 시작할 때 경고를 보이고, 만료되면 요청마다 Login expired · Please run /login이 나온다. 그때 /login을 실행한다[C2].
  • 다른 계정으로 바꾸려면 Claude Code 안에서 /logout을 실행한 뒤 다시 /login을 한다. /logout은 첫 실행 설정도 함께 초기화한다[C2]. 공용 PC에서는 수업이 끝날 때 /logout을 한다(A-2-5).
  • ANTHROPIC_API_KEY 환경 변수를 셸이나 Windows에 등록하지 않는다. Claude Code는 이 변수가 있으면 그 키를 쓸지 묻고, 승인하면 구독 로그인보다 그 키를 먼저 쓴다[C2]. ~/.bashrc(Git Bash), ~/.zshrc(macOS), Windows의 사용자 환경 변수 어디에도 넣지 않는다. 프로덕트용 키를 발급했으면 A-14의 방식으로 .env 파일에만 둔다.

[최신 자료 자리: 자격 증명의 저장 위치, 만료 안내 문구, 인증 우선순위] 확인할 곳: https://code.claude.com/docs/en/authentication 의 「Credential management」, 「Renew an expiring login」, 「Authentication precedence」. 2026-11-15 확인 값: 리눅스는 ~/.claude/.credentials.json(파일 모드 0600), macOS는 키체인. 만료 사흘 전부터 시작할 때 Your login expires in 3 days · run /login to renew가 보이고, 만료 뒤에는 요청마다 Login expired · Please run /login이 나온다. 대화형 실행에서 ANTHROPIC_API_KEY는 한 번 승인하면 구독 로그인보다 먼저 쓰이고, -p 실행에서는 묻지 않고 쓰인다. Windows의 저장 위치는 문서가 아닌 집필용 PC의 파일로 확인하였다. 수업 전에 다시 확인한다.

다음은 가짜 키를 환경 변수로 주고 인증 상태를 본 결과이다(2026-11-14). 로그인 대신 환경 변수의 키가 인증 수단으로 잡힌다.

$ ANTHROPIC_API_KEY=가짜값 claude auth status --text
API key: ANTHROPIC_API_KEY
Anthropic base URL: https://api.anthropic.com

A-9. Git 설정

Git은 커밋마다 작성자의 이름과 이메일을 기록한다. 처음 한 번 설정해 두면 그 PC의 모든 저장소에 적용된다[G1].

터미널 
git config --global user.name "홍길동"
git config --global user.email "GitHub에_등록한_이메일"
git config --global core.quotepath false
git config --global init.defaultBranch main
git config --global pull.rebase false
git config --global --list
user.name=홍길동
user.email=GitHub에_등록한_이메일
core.quotepath=false
init.defaultbranch=main
pull.rebase=false
설정 뜻 이 과목에서 정하는 까닭
user.name 커밋에 남는 작성자 이름 팀 저장소에서 누가 고쳤는지 구별한다. 실명 또는 1주차에 정한 표기
user.email 커밋에 남는 작성자 이메일 GitHub 계정에 등록한 이메일을 써야 커밋이 내 계정의 기여로 표시된다[H1]
core.quotepath false 한글 파일 이름을 그대로 보여 준다 이 과목의 파일 이름(요구사항명세서.md 등)과 키트 폴더 이름(Service_NN주차)이 한글이다
init.defaultBranch main git init으로 만든 저장소의 첫 브랜치 이름 GitHub의 기본 브랜치 이름과 맞춘다
pull.rebase false git pull이 원격의 변경을 병합(merge)으로 합친다 두 갈래로 나뉜 기록을 합칠 때 Git 판에 따라 방식을 묻는 메시지가 나오는 것을 막는다

core.quotepath를 true(기본값)로 두면 한글 파일 이름이 8진수 기호로 바뀌어 보인다. 같은 저장소에서 두 설정을 견준 결과이다(2026-11-14, git 2.55).

$ git -c core.quotepath=true status --short
?? "ch02/\354\203\210\355\214\214\354\235\274.md"
$ git status --short
?? ch02/새파일.md

이메일을 공개하고 싶지 않으면 GitHub의 Settings > Emails에서 「Keep my email addresses private」를 켜고, GitHub가 제공하는 no-reply 주소를 user.email에 넣을 수 있다[H1]. 그 주소는 같은 설정 화면에 표시된다. 2장은 커밋이 공개 저장소에 올라갈 때를 생각해 이 no-reply 주소로 바꾸기를 권하고, 편집기를 nano로 정한다.

[최신 자료 자리: GitHub 이메일 설정 화면의 메뉴 이름] Settings > Emails, 「Keep my email addresses private」, no-reply 주소의 꼴. 확인할 곳: https://docs.github.com/en/account-and-profile/setting-up-and-managing-your-personal-account-on-github/managing-email-preferences/setting-your-commit-email-address. 마지막으로 확인한 날짜와 값: 2026-11-14, 본문의 이름과 같다. 수업 전에 다시 확인한다.

Git for Windows의 시스템 설정. Git for Windows는 설치할 때 모든 사용자에게 걸리는 시스템 설정 파일 C:/Program Files/Git/etc/gitconfig에 몇 가지 값을 넣는다. 집필용 PC에서 git config --system --list --show-origin으로 본 값은 core.autocrlf=true, pull.rebase=false, init.defaultbranch=master였다(2026-11-17). 위의 --global 설정은 사용자 설정이므로 시스템 설정보다 앞선다. 그래서 init.defaultBranch main을 꼭 넣는다. 넣지 않으면 Windows에서 git init으로 만든 저장소의 첫 브랜치가 master가 된다. pull.rebase는 시스템 설정에도 false가 있어 결과가 같지만, macOS와 같은 동작이 되도록 사용자 설정에도 적는다. 어느 파일의 값이 쓰이는지 모르겠으면 git config --show-origin --get 설정이름으로 본다.

Windows의 줄 끝 경고. 시스템 설정의 core.autocrlf=true 때문에 git add나 git pull 때 LF will be replaced by CRLF the next time Git touches it 같은 경고가 나온다. 저장소에는 LF로 기록되므로 실습을 멈출 일은 아니다. Git Bash의 bash는 줄 끝이 CRLF인 셸 스크립트도 실행한다(집필용 PC에서 확인, 2026-11-16).

확인 6 git config --global --list에 위 다섯 줄이 있고, user.email이 GitHub 계정의 이메일과 같다.

A-10. GitHub CLI 인증과 개인 저장소의 공개 범위

A-10-1. GitHub CLI 인증

gh auth login으로 한 번 인증하면 gh 명령과 git push가 모두 그 인증을 쓴다.

터미널 
gh auth login

질문이 차례로 나온다. 다음과 같이 답한다.

질문 답
Where do you use GitHub? GitHub.com
What is your preferred protocol for Git operations on this host? HTTPS
Authenticate Git with your GitHub credentials? Yes
How would you like to authenticate GitHub CLI? Login with a web browser

질문의 문구는 gh 2.88에서 확인한 것이다. 마지막 답을 고르면 First copy your one-time code: XXXX-XXXX 형식의 한 번만 쓰는 코드가 나오고, Enter를 누르면 내 PC의 브라우저가 https://github.com/login/device를 연다. GitHub에 로그인한 상태에서 그 코드를 입력하고 GitHub CLI의 접근을 승인한다. 터미널로 돌아오면 Logged in as 사용자이름이 나온다.

[그림 자리: 브라우저에서 GitHub CLI의 기기 인증을 승인하는 화면] https://github.com/login/device에서 한 번용 코드(XXXX-XXXX)를 넣는 칸과 GitHub CLI의 접근을 승인하는 단추. 찍을 곳: gh auth login을 진행하는 동안 저절로 열린 내 PC의 브라우저. 실제 코드와 계정 이름은 가린다.

터미널 
gh auth status
github.com
  ✓ Logged in to github.com account 사용자이름 (keyring)
  - Active account: true
  - Git operations protocol: https
  - Token: gho_************************************
  - Token scopes: 'gist', 'read:org', 'repo', 'workflow'

위 출력은 gh 2.88의 출력 형식에 맞춘 예시이다. 사용자 이름과 토큰 범위는 사람마다 다를 수 있다.

  • 인증 정보는 운영체제의 자격 증명 저장소(Windows는 자격 증명 관리자, macOS는 키체인)에 저장된다. 괄호 안의 keyring이 그 뜻이다(gh auth login --help, 2026-11-14 확인).
  • 토큰은 화면에 일부만 보인다. 화면을 캡처해 공유할 때도 토큰 줄은 가린다.
  • git push가 사용자 이름과 비밀번호를 물으면 GitHub 인증이 Git에 연결되지 않은 것이다. gh auth setup-git을 실행한 뒤 다시 한다. GitHub는 git push에서 계정 비밀번호를 받지 않는다.
  • 공용 PC에서는 수업이 끝날 때 gh auth logout을 한다(A-2-5).

로그인하지 않은 상태에서 gh auth status를 실행하면 다음이 나온다(2026-11-14, gh 2.88).

You are not logged into any GitHub hosts. To log in, run: gh auth login

A-10-2. 개인 저장소의 공개 범위와 Pages

비공개로 두면 9장의 GitHub Pages 배포에 요금제 조건이 붙는다.

요금제 GitHub Pages를 쓸 수 있는 저장소 근거
GitHub Free(개인 계정의 기본) 공개 저장소만 [H6][H7]

A-11. 수업용 조직의 초대 수락

팀 저장소(3장부터)와 키트 저장소(1장부터, A-12)는 수업용 GitHub 조직(Organization)에 있다. 교수가 1주차에 받은 사용자 이름으로 조직에 초대하면, 학생이 초대를 받아들여야 조직의 구성원이 된다[H3]. 키트 저장소를 클론하려면 구성원이어야 하므로 1주차에 받아들인다.

  1. GitHub에 등록한 이메일로 초대 링크가 든 메일이 온다[H3]. GitHub에 로그인한 브라우저에서 그 링크를 연다. 조직의 이름(조직이름)은 1주차에 안내한다.
  2. 초대 화면에서 초대를 받아들인다. 메일을 찾지 못하면 아래의 gh api 명령으로 상태를 확인하고 받아들인다.
  3. 초대는 7일이 지나면 만료된다[H3]. 만료되었으면 교수에게 다시 초대를 요청한다.
  4. 조직이 2단계 인증을 요구하면, 2단계 인증을 켠 뒤에 받아들일 수 있다[H3].
  5. 조직이 이메일 주소로 초대한 경우에는 그 주소가 내 GitHub 계정에 인증된 이메일이어야 받아들일 수 있다[H3].

[그림 자리: 수업용 조직의 초대를 받아들이는 화면] 초대 메일의 링크로 연 GitHub 화면의 조직 이름과 수락 단추, 수락 뒤 조직의 People 탭에 내 계정이 보이는 모습. 찍을 곳: 내 PC의 브라우저. 조직 이름과 다른 학생의 계정은 가린다.

[최신 자료 자리: 조직 초대의 만료 기간과 수락 조건] 확인할 곳: https://docs.github.com/en/organizations/managing-membership-in-your-organization/inviting-users-to-join-your-organization. 마지막으로 확인한 날짜와 값: 2026-11-14, 초대는 7일 뒤 만료되고, 조직이 2단계 인증을 요구하면 켠 뒤에 받아들일 수 있다. 수업 전에 다시 확인한다.

조직 구성원이 되었는지는 브라우저에서 조직 화면의 People 탭으로 확인하거나, 터미널에서 GitHub API로 확인한다. state가 active이면 구성원이고, pending이면 초대를 아직 받아들이지 않은 것이다[H5].

터미널 
gh api user/memberships/orgs/조직이름 --jq .state
active

위 출력은 REST API 문서에 따른 예시이다. 집필 때 실제 조직으로는 실행하지 않았다.

초대를 받아들이지 않은 상태(pending)에서는 같은 API에 state를 active로 보내 받아들일 수도 있다[H5]. 브라우저 화면이 열리지 않을 때만 쓴다.

터미널 
gh api -X PATCH user/memberships/orgs/조직이름 -f state=active --jq .state

확인 8 gh api user/memberships/orgs/조직이름 --jq .state가 active를 출력한다(1주차, 늦어도 3장 전).

조직에 들어오면 3장에서 팀 실습 저장소 <팀>-lab을 클론한다. 클론 위치는 ~/teams/<팀>-lab으로 정한다. 개인 실습 저장소 안에 클론하지 않는다. 저장소 안에 다른 저장소를 넣으면 바깥 저장소의 git status가 안쪽 저장소를 알 수 없는 변경으로 보이기 때문이다. 팀원이 서로 리뷰할 산출물(7·8·13장)은 팀 실습 저장소의 reviews/chNN/「아이디」/에 올린다. 장과 아이디로 폴더를 나누므로 여러 사람이 같은 파일을 고쳐 충돌하는 일이 없다. 프로젝트실습Ⅰ의 팀 저장소는 같은 조직의 <팀>-project이다(3장 9-5).

A-13. 파이썬 가상 환경과 패키지 설치

파이썬 키트(테스트가 있는 골격, 9장의 브라우저 검사, 10장의 FastAPI 백엔드, 11장의 RAG 코드)는 필요한 패키지와 판을 requirements.txt에 적어 둔다. 패키지는 PC 전체가 아니라 가상 환경(virtual environment)에 설치한다. 가상 환경은 정해진 프로젝트만 쓰는 파이썬 실행 파일과 패키지 폴더의 묶음이다. 관리자 권한 없이 설치할 수 있고, PC의 다른 파이썬 프로그램과 부딪치지 않는다[P1].

이 과목은 가상 환경을 개인 실습 저장소 맨 위에 하나(~/llm-service-lab/.venv) 만들어 학기 내내 쓴다. 장마다 그 장의 requirements.txt를 이 환경에 더 설치한다. 장마다 가상 환경을 따로 만들면 같은 패키지가 여러 벌 쌓여 디스크를 차지하고, 지금 어느 환경을 쓰는지 헷갈리기 쉽다. 각 장의 키트는 같은 패키지를 같은 판으로 고정한다(예: pytest==9.2.0, 10·11장의 python-dotenv==1.2.4).

A-13-1. 켜고 쓰는 것이 기본이다

가상 환경 안의 파이썬은 운영체제마다 자리가 다르다. Windows는 .venv/Scripts/python, macOS는 .venv/bin/python이다. 같은 명령을 두 운영체제에서 쓰기 위해, 이 교재는 터미널마다 가상 환경을 켜고 python으로 부르는 것을 기본으로 한다. 켜면 입력 줄 앞에 (.venv)가 붙고, 그 터미널의 python과 pip가 가상 환경의 것을 가리킨다.

하는 일 Windows(Git Bash) macOS
만들기(한 번) python -m venv .venv python3 -m venv .venv
켜기(터미널마다) source ~/llm-service-lab/.venv/Scripts/activate source ~/llm-service-lab/.venv/bin/activate
켠 뒤의 파이썬 python python
끄기 deactivate deactivate
켜지 않고 경로로 부르기 ~/llm-service-lab/.venv/Scripts/python ~/llm-service-lab/.venv/bin/python
  • 장의 본문에서 python -m pytest, python -m uvicorn처럼 python으로 시작하는 명령은 가상 환경을 켠 터미널을 전제로 한다.
  • 켜는 명령은 터미널을 새로 열 때마다 한다. 두 터미널(A-4-3)에서 각각 켠다. Claude Code는 가상 환경을 켠 터미널에서 실행한다. 그래야 Claude Code가 실행하는 명령도 그 터미널의 환경을 물려받는다.
  • Claude Code가 다른 파이썬을 부르거나 No module named … 오류를 내면, 프롬프트에 가상 환경의 경로(위 표의 마지막 줄)로 실행하라고 적는다.
  • PowerShell에서 켜는 명령은 .venv\Scripts\Activate.ps1이다. 이 교재는 PowerShell을 실습에 쓰지 않는다.

  • pip를 python -m pip로 부르는 까닭은 그 파이썬에 딸린 pip를 확실히 쓰기 위해서이다.
  • 설치가 끝난 뒤 [notice] A new release of pip is available 안내가 나올 수 있다. 수업에서는 무시해도 된다.
  • 설치 중에 이미 있던 패키지를 다른 판으로 바꾼다는 줄(Successfully uninstalled 패키지-판)이 나오면, 두 장의 키트가 같은 패키지를 다른 판으로 고정한 것이다. 그대로 진행하되 교수에게 알린다.

A-13-3. 가상 환경을 다루는 규칙

  • .venv는 저장소에 커밋하지 않는다. 파이썬 3.13부터 venv는 가상 환경 안에 그 폴더 전체를 무시하는 .gitignore를 스스로 만든다P1. 3.12에서는 이 파일이 생기지 않으므로, 저장소 맨 위의 .gitignore에 .venv/를 적어 둔다(2장에서 만든다).
  • 하위 폴더(chNN/, jobprep/)에 가상 환경을 또 만들지 않는다. 키트의 README가 「가상 환경을 만든다」고 하면 저장소 맨 위의 환경에 그 장의 패키지를 설치하는 것으로 읽는다.
  • 가상 환경은 언제든 지우고 다시 만들 수 있는 것으로 다룬다. 그 안에 내 코드를 두지 않는다. 다른 폴더로 옮기면 동작하지 않는다(안의 스크립트가 만든 자리의 절대 경로를 기억한다)[P1]. 저장소를 옮겼으면 .venv를 지우고 다시 만든다.
  • 패키지가 꼬였으면 다음 순서로 처음부터 다시 만든다. 마지막 줄은 저장소 안의 모든 requirements.txt를 찾아 차례로 설치한다. rm -rf .venv는 pwd로 저장소 맨 위인지 확인한 뒤에 실행한다.

[터미널] (Windows. macOS는 python3 -m venv, .venv/bin/activate)

cd ~/llm-service-lab
deactivate 2>/dev/null
rm -rf .venv
python -m venv .venv
source .venv/Scripts/activate
find . -name requirements.txt -not -path "./.venv/*" -exec python -m pip install -q -r {} \;
  • 키트에 없는 패키지가 필요하다고 Claude Code가 제안하면, 바로 설치하지 말고 무엇을 왜 설치하는지 읽는다. 설치하기로 했으면 그 장의 requirements.txt에도 판과 함께 적는다. 적지 않으면 다른 사람(또는 다시 만든 가상 환경)에서 같은 코드가 돌지 않는다.

확인 10 가상 환경을 켠 터미널에서 which python이 ~/llm-service-lab/.venv 안의 파일을 가리키고, python -m pip list가 그 장의 requirements.txt에 적힌 패키지를 같은 판으로 보여 준다.

A-14. 프로덕트의 API 키 (선택)

10장부터 학습자가 만드는 프로덕트(FastAPI 백엔드, RAG 질의응답)는 Anthropic의 Messages API를 부르도록 만든다. 실제로 부르려면 API 키가 필요하다. 이 과목에서 키는 선택이다(사용자 결정 11). 모든 장은 키 없이 모의 모드(A-15)로 끝까지 할 수 있고, 실제 모델의 응답은 교수 시연과 교수가 배포하는 실행 기록으로 본다. 직접 실제 호출을 해 보고 싶은 학생만 각자 Claude Console에서 키를 발급한다.

API 키는 요청한 사람을 식별하고 사용량을 청구하는 문자열이므로 비밀번호처럼 다룬다.

A-14-1. 구독 로그인을 프로덕트에 쓰지 않는 까닭

Claude Code에 로그인한 구독 계정을 프로덕트 코드의 LLM 호출에 쓸 수는 없다. Anthropic의 Claude Code 문서 「Legal and compliance」는 두 인증 방식의 용도를 나눈다[C4].

  • 구독 계정의 로그인(OAuth)은 구독자가 Claude Code와 Anthropic의 앱을 통상적으로 쓰기 위한 것이다.
  • Claude의 기능을 쓰는 제품이나 서비스를 만드는 개발자는, Agent SDK를 쓰는 경우를 포함해, Claude Console의 API 키(또는 지원되는 클라우드 제공자)로 인증해야 한다.
  • 제3자가 자기 앱에 Claude.ai 로그인을 넣거나, 사용자 대신 구독 자격 증명으로 요청을 보내는 것은 허용되지 않는다. 문서의 표현으로는 개발자가 Claude.ai의 자격 증명이나 세션 토큰을 “collect, store, or intermediate”(수집, 저장, 중개)해서는 안 된다.

[최신 자료 자리: 인증 수단의 용도에 관한 약관 문구] 구독 로그인과 API 키의 용도 구분, 자격 증명의 중개를 금지하는 문장. 확인할 곳: https://code.claude.com/docs/en/legal-and-compliance. 마지막으로 확인한 날짜: 2026-11-14(본문의 요약과 인용). 약관은 바뀔 수 있으므로 학기 전에 다시 읽는다.

학습자가 만드는 공고 요약 API는 그 자체가 하나의 서비스이므로 API 키를 쓰는 쪽에 속한다. 그래서 이 과목은 Claude Code(개발 도구)는 구독 로그인으로, 프로덕트는 API 키로 나눈다. 로그인 정보 파일(~/.claude/.credentials.json)을 코드에서 읽어 쓰는 일도 같은 이유로 하지 않는다.

  1. 키를 쓰기로 했으면 Claude Console(https://platform.claude.com/)에 가입하고, 선불로 사용 크레딧을 산 뒤 키를 만든다. 작업 공간(workspace)에 월 지출 한도를 낮게 정해 두면, 반복문의 실수로 크레딧이 한꺼번에 쓰이는 일을 막는다. 결제는 학생 본인이 하며, 이 교재와 수업은 결제 정보를 다루지 않는다.
  2. 키는 만들 때 한 번만 전체가 보인다. 키를 만들기 전에 아래 5단계로 .env를 만들어 두고, 키가 보이면 6단계처럼 바로 붙여 넣는다. 메모장, 메신저, 이메일에 옮겨 두지 않는다.

A-14-3. 커밋되지 않는지 확인

저장소의 .gitignore에 .env가 있어야 한다. 저장소 맨 위의 .gitignore는 2장의 견본으로 만들었고, 10장 키트의 jobprep/.gitignore에도 .env가 있다. jobprep/에서 다음 두 명령으로 확인한다.

터미널 
cd ~/llm-service-lab/jobprep
git check-ignore -v .env
git status --short
jobprep/.gitignore:2:.env   .env

git check-ignore -v가 어느 .gitignore의 몇째 줄이 .env를 무시하게 하는지 보여 주면 된다. 위 출력은 10장 키트의 jobprep/.gitignore가 있을 때이고, 그 파일이 없으면 저장소 맨 위의 견본이 잡혀 .gitignore:12:.env .env처럼 나온다(2026-11-14, git 2.55에서 두 경우를 확인). 아무것도 출력하지 않으면 무시되지 않는 것이므로 커밋하기 전에 .gitignore에 .env를 더한다. git status --short에 .env가 보이면 안 된다.

실수로 git add까지 했다면, 커밋하기 전에 스테이징에서만 빼낸다. 파일은 지워지지 않는다(2026-11-14, git 2.55에서 확인).

터미널 
git rm --cached .env
$ git status --short
A  .env
$ git rm --cached -q .env
$ git status --short
?? .env

키를 커밋하거나 푸시했으면 그 키는 이미 샌 것으로 본다. 다음 커밋에서 파일을 지워도 기록에 남아 있기 때문이다. 바로 Claude Console에서 그 키를 폐기하고 새 키를 만든다. 기록을 고쳐 쓰는 것으로 해결하려 하지 않는다. 팀 저장소에 올렸으면 교수에게도 알린다.

A-15. 모의 모드와 모델 변수

A-15-1. 모의 모드 LLM_FAKE

이 과목에서 LLM을 부르는 모든 키트 코드는 환경 변수 LLM_FAKE가 1이면 API를 부르지 않고 정해진 응답을 낸다. 이것을 모의 모드(fake mode)라 한다. 모의 모드를 두는 까닭은 세 가지이다.

  1. 키가 없거나, 지출 한도에 닿았거나, 네트워크가 막혀도 수업이 멈추지 않는다.
  2. 같은 입력에 늘 같은 출력이 나오므로 테스트가 매번 같은 결과를 낸다. 실제 모델의 응답은 호출마다 달라질 수 있다.
  3. 비용이 들지 않는다. 테스트를 수십 번 돌려도 사용량이 쌓이지 않는다.

모의 모드로 확인하는 것은 코드의 흐름(입력 검사, 응답 형식, 오류 처리, 화면 연결)이다. 요약이 잘 되었는지 같은 응답의 품질은 실제 호출로만 확인할 수 있으며, 키가 없는 학생은 교수가 배포하는 실행 기록으로 본다.

A-15-2. 모델 변수 LLM_MODEL

키트의 코드에는 모델 이름을 적지 않는다. 실제 호출에 쓸 모델은 환경 변수 LLM_MODEL로 받는다. 모델은 새로 나오고 오래된 것은 지원이 끝나므로, 코드에 이름을 박아 두면 학기 중에 코드를 고쳐야 할 수 있다. 값은 수업 직전에 Anthropic의 공식 모델 목록에서 확인한 모델 이름을 교수가 안내한다. 10장 키트의 .env.example에는 2026-11 기준의 저가 모델 claude-haiku-5-5가 들어 있고, LLM_MODEL이 비어 있으면 코드의 기본값(같은 모델)을 쓴다. 수업에서 다른 이름을 안내하면 .env의 그 줄만 바꾼다.

10~11장의 코드가 읽는 환경 변수는 다음과 같다. 값은 모두 jobprep/.env에 둔다.

A-15-3. 값을 주는 세 자리와 우선순위

변수는 .env에 적어 두거나, 명령 앞에 붙여 그 명령에만 줄 수 있다. 키트의 코드는 python-dotenv로 .env를 읽되 이미 설정된 환경 변수는 덮어쓰지 않는다. 그래서 명령 앞에 붙인 값이 .env의 값보다 앞선다. Git Bash와 macOS의 zsh 모두 같은 문법을 쓴다.

자리 쓰는 법 적용 범위
명령 앞 LLM_FAKE=0 python ... 그 명령 한 번
export export LLM_FAKE=1 그 터미널을 닫을 때까지
.env LLM_FAKE=1 한 줄 그 폴더에서 실행하는 키트 코드

다음은 .env에 LLM_FAKE=1을 두고, 같은 확인 코드를 그대로 실행한 결과와 명령 앞에 LLM_FAKE=0을 붙여 실행한 결과이다(2026-11-14, Git Bash, 10장 키트와 같은 python-dotenv 1.2.4).

$ python check_env.py
LLM_FAKE = 1
$ LLM_FAKE=0 python check_env.py
LLM_FAKE = 0

export로 바꾼 값은 잊기 쉽다. 터미널을 오래 쓴 뒤 결과가 이상하면 echo "$LLM_FAKE"로 지금 값을 확인한다. 값을 지우려면 unset LLM_FAKE를 실행한다. PowerShell은 명령 앞에 변수를 붙이는 문법이 없으므로 이 교재의 명령을 PowerShell에 입력하지 않는다.

A-15-4. 실제 호출의 순서 (키를 발급한 학생)

실제 모델을 부르는 확인은 장마다 정한 실행 상한 안에서만 하고, 순서는 다음과 같다.

  1. 모의 모드로 테스트가 모두 통과하는지 본다(가상 환경을 켠 터미널).
터미널 
cd ~/llm-service-lab/jobprep
LLM_FAKE=1 python -m pytest -q
  1. .env에 키(A-14)와 LLM_MODEL이 들어 있는지 본다.
  2. 그 장이 안내하는 명령 하나만 LLM_FAKE=0을 붙여 실행한다. 반복문이나 테스트 전체를 실제 호출로 돌리지 않는다.
  3. 응답을 확인했으면 모의 모드로 돌아온다. .env의 LLM_FAKE=1은 바꾸지 않는다.

실제 호출이 실패하면 API는 HTTP 상태 코드와 오류 종류(type)를 JSON으로 돌려준다[A1]. 대표적인 것은 다음과 같다. 오류 메시지 전체를 Claude Code에 붙여 넣을 때는 키가 섞여 있지 않은지 먼저 본다.

상태 코드와 종류 흔한 원인 조치
401 authentication_error 키가 비었거나, 잘못 붙여 넣었거나, 폐기되었다. 앞뒤에 공백이나 따옴표가 있다 .env의 줄을 다시 확인한다(A-14)
400 invalid_request_error 요청의 형식이 틀렸다. 크레딧이 모자라거나 작업 공간의 지출 한도에 닿았을 때도 이 코드가 온다 메시지를 읽고 요청을 고친다. 한도라면 모의 모드로 진행한다
403 permission_error 키가 그 자원(모델 등)을 쓸 권한이 없다 Console에서 키의 작업 공간과 권한을 본다
404 not_found_error 요청한 자원이 없다. LLM_MODEL의 이름이 틀린 경우가 흔하다 수업에서 안내한 이름을 그대로 넣는다
429 rate_limit_error 속도 제한이나 지출 상한에 닿았다 잠시 뒤 다시 한다. 계속되면 모의 모드로 진행한다
529 overloaded_error API가 일시적으로 과부하이다 잠시 뒤 다시 한다
연결 시간 초과 내 PC의 네트워크 문제(학내 무선망의 차단 포함) 모의 모드로 진행하고 교수에게 알린다

확인 12 jobprep/에서 LLM_FAKE=1 python -m pytest -q가 키 없이도 통과한다(10장).

A-16. 포트

8장부터는 내 PC에서 서버 프로그램을 띄우고 브라우저로 접속한다. 8~9장은 정적 웹 화면을 보내는 python -m http.server를, 10~12장은 API 서버를 띄우는 uvicorn을 쓴다. 이런 서버 프로그램은 포트(port)라는 번호 하나를 차지하고 그 번호로 오는 요청을 기다린다.

각자의 PC에서 실습하므로 다른 학생과 번호가 겹칠 일이 없다. 이 과목은 번호를 고정한다(사용자 결정 11).

포트 번호 쓰는 곳 브라우저 주소
API 서버 8000 10~12장의 uvicorn. 9장의 웹을 같은 서버에서 함께 보낸다 http://localhost:8000/
웹 서버 8100 8~9장의 http.server. 10장부터 웹 화면을 API와 따로 띄울 때 http://localhost:8100/
터미널 
cd ~/llm-service-lab
python -m http.server 8100 --bind 127.0.0.1
Serving HTTP on 127.0.0.1 port 8100 (http://127.0.0.1:8100/) ...

위 출력은 집필용 Windows PC의 Git Bash에서 얻은 것이다(2026-11-16, 파이썬 3.13.7). 브라우저에서 http://localhost:8100/을 바로 연다. 포트 전달 같은 단계는 필요 없다.

  • --bind 127.0.0.1은 내 PC 안에서만 접속을 받게 한다. 같은 무선망의 다른 컴퓨터가 내 화면에 들어오지 못한다. uvicorn은 --host를 주지 않으면 처음부터 127.0.0.1에서만 받으므로 --port 8000만 붙인다(10장).
  • 같은 PC에서 같은 종류의 서버를 둘 띄울 때만 둘째 서버에 다른 번호를 준다. 12장은 두 변형의 API 서버를 함께 띄우므로 variant-form은 8000, variant-chat은 8001을 쓴다(12장 3-6). 8100은 웹 서버의 번호이므로 둘째 API 서버에 쓰지 않는다.
  • 서버가 도는 동안 그 터미널은 다른 명령을 받지 않는다. 멈출 때는 Ctrl+C를 누른다. 멈추지 않고 터미널만 닫으면 프로그램이 남아 포트를 계속 차지할 수 있다.

A-16-1. 이미 쓰는 포트일 때

앞서 띄운 서버를 잊었거나 다른 프로그램이 같은 번호를 쓰면 문제가 생긴다. 집필용 Windows PC에서 같은 번호로 두 번 띄워 본 결과는 프로그램마다 달랐다(2026-11-16).

$ python -m uvicorn app:app --port 8000      ← 이미 8000에서 uvicorn이 도는 중
...
ERROR:    [Errno 10048] error while attempting to bind on address ('127.0.0.1', 8000): [winerror 10048] 각 소켓 주소(프로토콜/네트워크 주소/포트)는 하나만 사용할 수 있습니다
$ python -m http.server 8100 --bind 127.0.0.1   ← 이미 8100에서 http.server가 도는 중
Serving HTTP on 127.0.0.1 port 8100 (http://127.0.0.1:8100/) ...

uvicorn은 오류를 내고 멈추지만, Windows의 http.server는 오류 없이 둘 다 뜬다. 이때 브라우저가 어느 쪽의 화면을 받을지 알 수 없어, 고친 파일이 반영되지 않은 것처럼 보인다. macOS와 리눅스에서는 두 번째 http.server가 Address already in use 오류를 낸다(리눅스에서 확인, 2026-11-14). 그래서 서버를 띄우기 전과 화면이 이상할 때 그 번호를 누가 쓰는지 본다.

[터미널] (Windows의 Git Bash)

netstat -ano | findstr :8100
  TCP    127.0.0.1:8100         0.0.0.0:0              LISTENING       23284
  TCP    127.0.0.1:8100         0.0.0.0:0              LISTENING       39572

위 출력은 두 http.server를 함께 띄운 상태에서 얻은 것이다(2026-11-16). 줄이 없으면 아무도 쓰지 않는 것이고, LISTENING 줄의 마지막 숫자가 그 포트를 쓰는 프로그램의 번호(PID)이다. findstr 대신 grep ":8100 "을 써도 같다.

[터미널] (macOS)

lsof -nP -iTCP:8100 -sTCP:LISTEN

쓰는 프로그램을 찾았으면 다음 순서로 정리한다.

  1. 내가 띄운 서버이면 그 터미널을 찾아 Ctrl+C를 누른다.
  2. 터미널을 이미 닫았으면 번호로 끝낸다. Git Bash에서는 taskkill //PID 번호 //F(빗금 두 개)이고, macOS에서는 kill 번호이다. 내가 띄운 파이썬이 맞는지 모르겠으면 끝내지 않고 3을 한다.
  3. 다른 번호를 쓴다. 웹 서버는 python -m http.server 8101 --bind 127.0.0.1처럼 번호만 바꾼다. API 서버를 다른 번호로 띄우면(--port 8001) 그 API를 부르는 웹 화면의 주소와, 웹을 따로 띄웠을 때 API가 받아 줄 웹 주소(.env의 WEB_ORIGIN, A-15-2)도 같이 바꾼다. 바꾼 번호는 장의 명령을 입력할 때마다 같이 바꾼다.

확인 13 python -m http.server 8100 --bind 127.0.0.1을 띄웠을 때 Serving HTTP on 127.0.0.1 port 8100이 나오고, netstat -ano | findstr :8100(macOS는 lsof)에 LISTENING 줄이 하나만 있으며, 브라우저에서 http://localhost:8100/이 열린다.

A-17. 로컬 임베딩: 대체 구현과 Ollama(선택)

11장의 RAG 기능은 문서와 질문을 숫자 벡터로 바꾸는 임베딩(embedding)을 쓴다. 이 과목은 키트의 대체 구현을 기본으로 한다(사용자 결정 11). 대체 구현은 외부 모델 없이 문자 단위의 n-gram 같은 단순한 방법으로 벡터를 만든다. 설치할 것이 없고 키와 비용이 들지 않는다. 검색은 되지만 의미가 비슷한 다른 표현은 잘 찾지 못하므로, 유사도 값과 재현율은 이 방법의 값으로 읽는다.

자기 PC에 Ollama를 설치한 학생은 Ollama의 로컬 임베딩 모델을 쓸 수 있다(선택). Ollama는 내 PC의 11434 포트에서 HTTP API를 제공하고, 임베딩은 /api/embed 주소로 요청한다[O1].

11장 키트는 다음 환경 변수로 둘을 고른다. 값은 jobprep/.env에 두거나 명령 앞에 붙인다(A-15-3).

변수 뜻 값
EMBED_BACKEND 임베딩을 만드는 방법 fallback(대체 구현, 값을 주지 않았을 때의 기본), ollama, auto(Ollama를 먼저 시도하고 안 되면 대체 구현)
OLLAMA_URL Ollama 서버의 주소 기본 http://localhost:11434
EMBED_MODEL 임베딩 모델 이름 기본 nomic-embed-text
RAG_MIN_SCORE 근거로 쓸 검색 결과의 최소 유사도 11장에서 정한다

11장 키트는 EMBED_BACKEND를 주지 않으면 대체 구현을 쓴다. 수업의 측정값을 서로 견줄 수 있도록 11장의 재현율 측정은 대체 구현으로 하고, 아래처럼 값을 밝혀 두면 .env에 다른 값을 적어 둔 경우에도 같은 조건이 된다. Ollama를 쓴 결과는 그 옆에 따로 적는다.

터미널 
cd ~/llm-service-lab/jobprep
EMBED_BACKEND=fallback python -m pytest -q

Ollama를 쓰려면(선택). https://ollama.com/download에서 자기 운영체제의 설치 파일을 받아 설치한다. Windows의 설치 파일은 관리자 권한 없이 홈 폴더에 설치되며, Windows 10 22H2 이상과 프로그램용 4GB 이상의 디스크가 필요하다[O2]. 모델은 따로 내려받으며 크기가 크다. 설치한 뒤 모델을 받고 동작을 확인한다.

터미널 
ollama pull nomic-embed-text
curl -s http://localhost:11434/api/tags | head -c 300; echo
{"models":[{"name":"nomic-embed-text:latest", ...}]}

위 출력은 예시이다(집필용 PC에는 Ollama를 설치하지 않았다). 모델 목록(JSON)이 나오면 Ollama가 동작하는 것이다. 아무것도 나오지 않거나 curl이 연결하지 못하면 Ollama가 꺼진 것이므로 fallback으로 진행한다.

[최신 자료 자리: Ollama의 설치와 임베딩 모델] 설치 파일, 시스템 요구 사항, 임베딩 API 주소, 모델 받기 명령, 모델의 크기. 확인할 곳: https://ollama.com/download, https://docs.ollama.com/windows, https://docs.ollama.com/capabilities/embeddings. 2026-11-16 확인 값: Windows는 OllamaSetup.exe, 관리자 권한 불필요, Windows 10 22H2 이상, 프로그램 4GB 이상, API는 http://localhost:11434. 2026-11-14 확인 값: 임베딩 주소 /api/embed, 키트의 기본 모델 nomic-embed-text. ollama pull과 모델 크기는 확인하지 못하였다. 11장 전에 다시 확인한다.

확인 14 jobprep/에서 EMBED_BACKEND=fallback python -m pytest -q가 통과한다(11장).

A-18. 브라우저 검사 도구(Playwright)

9장은 Playwright로 브라우저를 프로그램이 조작하게 해서, 만든 화면이 인수 조건을 지키는지 검사한다. Playwright는 파이썬 꾸러미와 별도로 브라우저 파일을 내려받아 쓴다[PW1]. 내 PC(Windows, macOS)에 설치한다.

  1. 설치 자리. 꾸러미는 개인 실습 저장소의 가상 환경(A-13)에 9장 키트의 requirements.txt로 설치하고, 브라우저는 같은 가상 환경의 파이썬으로 받는다. 다른 파이썬으로 받으면 판이 맞지 않아 Executable doesn't exist 오류가 난다.

[터미널] (가상 환경을 켠 터미널)

cd ~/llm-service-lab
python -m pip install -r 「9장 키트가 안내하는 requirements.txt」
python -m playwright install --only-shell chromium
  1. 창 없이 실행한다. 9장의 검사는 브라우저를 창 없이(headless) 띄운다. Playwright의 파이썬 안내는 테스트가 기본적으로 headless로 돌아 브라우저 창이 열리지 않는다고 밝힌다[PW2]. --only-shell은 headless에서만 쓰는 Chromium을 받게 하여, 전체 Chromium을 받지 않아도 되게 한다[PW1]. 검사가 도는 모습을 창으로 보고 싶으면 --only-shell을 빼고 전체 Chromium을 받는다.
  2. 용량과 자리. 브라우저 파일은 Windows에서 홈 폴더의 AppData\Local\ms-playwright(Git Bash에서 ~/AppData/Local/ms-playwright), macOS에서 ~/Library/Caches/ms-playwright에 놓인다[PW1]. 집필할 때 잰 크기는 headless 전용 Chromium이 약 278MB, 전체 Chromium이 약 437MB였다(Windows, Playwright 1.64.0, 9장의 측정). 다른 Playwright 판을 설치했다가 지우면, 어느 설치도 쓰지 않는 판의 브라우저는 자동으로 지워진다[PW1].
  3. 운영체제의 라이브러리를 설치하는 playwright install-deps는 리눅스용이다[PW1]. Windows와 macOS에서는 실행하지 않는다.

[최신 자료 자리: Playwright의 판, 브라우저 크기, 설치 위치] 확인할 곳: https://playwright.dev/python/docs/intro, https://playwright.dev/python/docs/browsers, PyPI의 playwright. 2026-11-16 확인 값: 설치 위치는 Windows %USERPROFILE%\AppData\Local\ms-playwright, macOS ~/Library/Caches/ms-playwright, 리눅스 ~/.cache/ms-playwright. --only-shell은 headless 셸만 받는다. 2026-11-14 확인 값: Playwright 1.64.0, headless 전용 Chromium 약 278MB, 전체 Chromium 약 437MB(Windows에서 잼). 9장 전에 다시 확인한다.

확인 15 가상 환경을 켠 터미널에서 python -c "import playwright; print('ok')"가 ok를 출력하고, ls ~/AppData/Local/ms-playwright(macOS는 ls ~/Library/Caches/ms-playwright)에 chromium_headless_shell-로 시작하는 폴더가 있다(9장).

A-19. Aside 설치와 로컬 웹 점검

9장 9-5는 내 PC에서 띄운 자기 웹을 브라우저 에이전트 Aside에게 인수 조건 표로 점검하게 한다. Aside는 자연어로 받은 작업을 브라우저를 직접 조작해 수행하는 브라우저이다[AS1][AS2]. 이 절은 Aside를 설치하고 로그인하는 일과, 내 PC의 웹을 Aside에서 여는 일을 다룬다. 계정(A-2-3), 설치, 로그인은 9장 수업 전에 끝낸다. 수업 시간 안에 계정을 만들면 인증 메일과 로그인에 시간을 빼앗긴다.

A-19-1. 쓸 수 있는 컴퓨터

A-19-3. 내 PC의 웹을 Aside에서 열기

9장의 웹은 내 PC에서 웹 서버 포트 8100(A-16)으로 띄운다. Aside도 같은 PC에서 돌므로 그 주소를 바로 연다.

  1. 먼저 평소의 브라우저에서 http://localhost:8100/을 열어 공고 목록이 보이는지 본다. 여기서 안 보이면 Aside의 문제가 아니라 웹 서버의 문제다(A-16).
  2. Aside에서 같은 주소 http://localhost:8100/을 연다.

지킬 것은 세 가지다.

  • 로컬 주소만 연다. 9장의 점검은 GitHub Pages의 공개 주소가 아니라 localhost에서 한다.
  • 자격 증명을 주지 않는다. GitHub 계정, Claude 계정, API 키를 Aside의 작업 지시에 적지 않는다. 점검하는 동안 Aside에 다른 사이트의 로그인 탭을 열어 두지 않는다. Aside는 자격 증명을 AI에 드러내지 않고 자동 입력한다고 밝히지만[AS2], 9장의 웹은 로그인이 없으므로 쓸 일이 없다.
  • 민감한 동작은 승인하지 않는다. Aside는 결제·게시·메시지 같은 동작 앞에서 사람의 확인을 기다린다[AS2]. 9장 점검 중에 그런 확인 요청이 나오면 지시를 벗어난 것이므로 거절한다.

[그림 자리: Aside에서 연 로컬 웹] Aside의 주소창에 localhost:8100, 화면에 공고 목록이 보이는 상태. 찍을 곳: 웹 서버를 띄운 Windows 11 PC.

확인 16 평소의 브라우저와 Aside에서 http://localhost:8100/이 모두 열려 공고 목록이 보인다(9장).

A-20. Orca 설치와 로컬 저장소

Orca는 작업마다 git 작업 트리를 만들고, 그 안에서 Claude Code 같은 터미널 기반 에이전트를 나란히 실행하는 데스크톱 프로그램이다[OR1]. 이런 도구를 에이전트 개발 환경(ADE, Agentic Development Environment)이라 부른다. MIT 사용권의 무료 공개 소프트웨어이며 macOS, Windows, 리눅스용이 있다[OR1]. 이 과목은 내 PC의 저장소를 Orca에서 로컬로 연다. 에이전트와 git worktree 명령이 모두 내 PC에서 돈다[OR2]. 이 절은 설치와, 작업 트리를 만들고 정리할 때 정할 것을 다룬다. 작업 트리를 만들어 쓰는 절차는 12장 핵심 실습의 9-3~9-4에 있다. 이 절은 12장 전에 마친다.

[최신 자료 자리: Orca의 판과 설치 방법] 최신 판, 운영체제별 설치 파일, Homebrew·AUR 패키지 이름. 확인할 곳: https://github.com/stablyai/orca/releases, https://github.com/stablyai/orca의 README, https://orca.dev. 2026-11-16 확인 값: v1.4.261(2026-11-16, Latest). Windows는 .exe, macOS는 Apple Silicon·Intel용 DMG, 리눅스는 AppImage. Homebrew는 brew install --cask stablyai/orca/orca(이름만 쓴 orca는 다른 프로그램이다), Arch Linux는 AUR의 stably-orca-bin. 수업 전에 다시 확인한다.

A-20-1. 설치

Orca 자체에는 계정이 필요 없다(A-2-4). Orca의 터미널에서 실행하는 Claude Code가 A-8에서 로그인한 구독 계정을 그대로 쓴다.

  1. https://orca.dev에서 자기 운영체제의 설치 파일을 내려받는다. 같은 파일이 GitHub 릴리스 쪽에도 있다.
  2. Windows는 내려받은 .exe를 실행한다. macOS는 DMG를 열어 응용 프로그램 폴더로 옮긴다.
  3. Orca를 실행해 첫 화면이 뜨는지 본다. 처음 실행할 때 운영체제가 보안 경고를 보이면, 내려받은 곳이 위의 공식 주소인지 확인한 뒤 실행을 허용한다.

[터미널] (macOS에서 Homebrew를 쓰는 경우)

brew install --cask stablyai/orca/orca

[그림 자리: Orca의 첫 화면] 설치 직후 Orca를 처음 실행한 창. 왼쪽의 빈 프로젝트 목록과 저장소를 더하는 단추, 설정(Settings) 단추의 위치를 표시한다. 찍을 곳: Windows 11 PC의 Orca.

12장 전에 다음을 확인해 둔다.

  1. Orca의 터미널에서 claude --version이 판 번호를 출력하고, claude를 실행했을 때 로그인 상태가 유지되는지 본다(A-8-2). Windows에서 Orca의 터미널이 Git Bash가 아니면, 이 교재의 명령을 입력하기 전에 셸을 확인한다(uname -s, A-3-3).
  2. 이 실습에서 한 사람이 여는 에이전트 세션은 둘이고, 각 세션은 자기소개서 피드백 기능을 변형 하나로 구현한다(변형마다 5~15분). 사용 한도가 거의 찬 계정이면 수업 전에 한도가 회복되는 시점을 확인한다.

A-20-2. 저장소를 열고 작업 트리를 만들 때 정할 것

Orca에서 저장소를 더할 때 내 PC의 폴더(12장에서는 ~/llm-service-lab)를 고른다. 작업 트리를 만드는 창에서는 다음을 정한다[OR4].

칸 정할 값 까닭
이름 작업을 나타내는 짧은 이름 기본으로 브랜치 이름이 여기서 정해진다
Run on 이 PC(로컬) 에이전트와 git 명령이 내 PC에서 돈다
Branch from 실습이 정한 출발점(예: main, 태그) 기본값은 대개 origin/main이다. 푸시하지 않은 커밋에서 출발하려면 반드시 바꾼다
Advanced → Branch name 실습이 정한 브랜치 이름 이름을 분명히 정한다

에이전트를 처음 시작하면 그 폴더를 신뢰할지 묻는다. 에이전트 권한은 파일을 고칠 때마다 사람이 승인하는 Manual로 둔다. Orca가 만든 작업 트리는 실제 git 작업 트리이므로[OR4], 확인 터미널의 git worktree list로 언제든 확인할 수 있다. 작업 트리가 놓이는 폴더는 판과 설정에 따라 다르므로, 경로는 늘 git worktree list로 읽는다.

[최신 자료 자리: Orca의 작업 트리 창과 설정 메뉴 이름] 저장소를 더하는 메뉴, 작업 트리 창의 Run on(로컬을 가리키는 표기)·Branch from·Advanced → Branch name, 에이전트 권한(Manual 등), Settings → Workspace Cleanup. 확인할 곳: https://orca.dev/docs/model/worktrees, https://orca.dev/docs/settings, https://orca.dev/docs/ways-to-run. 2026-11-16 확인 값: 메뉴 이름은 본문과 같다. 로컬 실행에서 Run on 칸이 보이는지, 보이면 로컬이 어떤 이름으로 표시되는지는 확인하지 못하였다. 수업 전에 다시 확인한다.

확인 17 Orca의 목록에 내 PC의 저장소가 있고, Orca에서 만든 작업 트리가 확인 터미널의 git worktree list에 보인다(12장).

A-20-3. 끝난 뒤 정리

작업 트리는 내 PC에 파일 사본을 남긴다. 끝난 작업 트리는 그날 정리한다.

  • Orca에서 작업 트리를 삭제하면 확인을 받은 뒤 작업 트리 폴더와 브랜치를 함께 지운다[OR4]. 남겨야 할 브랜치가 있으면 먼저 태그를 붙인다.
  • 터미널에서 지울 때는 git worktree remove <경로>, git branch -D <브랜치> 순서로 한다. 폴더를 rm -rf로 지웠으면 git worktree prune -v로 관리 정보를 정리한다.
  • 명령으로 지운 작업 트리가 Orca 목록에 남아 있으면 목록에서 뺀다.
  • Orca의 작업 트리 자동 정리 규칙(Settings → Workspace Cleanup)은 기본으로 꺼져 있다[OR4]. 켜지 않는다. 규칙에 맞는 작업 트리가 몇 초 안에 지워질 수 있다.
  • 막힌 작업 트리는 지우지 않고 남긴다. 에이전트가 이상하게 고쳤거나 커밋이 기대와 다를 때 작업 트리를 바로 지우면, 무엇이 잘못되었는지 볼 근거가 사라진다. 태그를 붙이거나 그대로 둔 채 교수나 짝에게 보이고, 원인을 본 뒤에 지운다.
터미널 
cd ~/llm-service-lab
git worktree list
git worktree prune -v

증상 원인 할 일
Orca의 터미널에서 claude를 찾지 못한다 Orca가 Claude Code를 설치하기 전에 실행되었거나, 다른 셸로 열렸다 Orca를 다시 시작한다. 그래도 안 되면 ~/.local/bin/claude --version으로 확인한다(A-7)
작업 트리의 커밋이 기대와 다르다 Branch from을 기본값(origin/main)으로 두었다 작업 트리를 남겨 둔 채 원인을 확인하고, 출발점을 바꾸어 새로 만든다
git worktree list에 Orca의 작업 트리가 안 보인다 확인 터미널이 다른 저장소에 있거나, Orca가 다른 폴더를 열었다 pwd와 Orca가 연 저장소의 경로를 본다
두 에이전트를 띄우자 PC가 느려진다 자기 PC의 코어와 메모리가 모자란다 에이전트를 하나씩 차례로 돌린다. 다른 프로그램(브라우저 탭 등)을 닫는다
작업 트리를 지웠는데 폴더가 남았다 Orca가 지우지 못한 파일이 있다(다른 프로그램이 파일을 열고 있음 등) VS Code와 터미널에서 그 폴더를 닫고 git worktree remove, git worktree prune -v를 한다
