이 부록은 실습 환경을 갖추는 절차를 한곳에 모은 것이다. 실습 서버 접속, 편집기 연결, Claude Code의 설치와 로그인, 키트 받기, Git과 GitHub의 준비, 파이썬 가상 환경, 프로덕트용 API 키와 모의 모드, 로컬 임베딩, 서버 없이 내 PC에서 하는 길, 개인 포트, 서버에서의 브라우저 검사를 차례로 다룬다. 각 장의 0절은 이 절차를 되풀이하지 않고 이 부록의 절 번호를 가리킨다.

A-1. 실습 환경의 구성

이 과목의 실습은 학과 리눅스 실습 서버에서 한다. 내 컴퓨터는 서버에 접속하는 창구이고, 파일과 프로그램은 서버의 내 홈 폴더에 있다. 실습실 PC와 개인 노트북 어느 쪽으로 접속해도 같은 파일을 본다. 서버를 쓸 수 없는 경우를 위해 내 PC에서 같은 실습을 하는 길을 A-16에 둔다.

A-2. 실습 서버 접속

  1. 내 PC에서 Windows PowerShell을 연다. 시작 메뉴에서 PowerShell을 검색해 실행하거나, Win + X를 눌러 목록에서 터미널을 고른다. 창의 입력 줄이 PS C:\Users\...>로 시작하면 내 PC의 PowerShell이다. Windows Terminal 창이 열려도 그 안에서 PowerShell이 돌고 있으면 같은 자리이다.

    터미널은 창이고, 셸은 그 창 안에서 명령을 받아 실행하는 프로그램이다. PowerShell은 Windows의 셸이고, 서버에서는 bash가 셸이다. 같은 명령이라도 어느 셸에 입력하느냐에 따라 결과가 다르다.

  2. 다음 명령으로 서버에 접속한다. 아이디와 서버주소는 1주차에 안내하는 값으로 바꾼다.

내 PC · PowerShell 
ssh 아이디@서버주소
  1. 처음 접속하면 서버를 신뢰할지 묻는 질문이 나온다. yes를 입력한다. 이 질문은 서버의 신원(호스트 키)을 내 PC에 기록하는 단계이며, 같은 서버에 다시 접속하면 나오지 않는다.
The authenticity of host '서버주소 (...)' can't be established.
ED25519 key fingerprint is SHA256:....
Are you sure you want to continue connecting (yes/no/[fingerprint])? yes
아이디@서버주소's password:

  1. 비밀번호를 입력한다. 입력하는 동안 화면에 아무 글자도 나오지 않는 것이 정상이다. 다 입력하고 Enter를 누른다.

  2. 입력 줄이 [아이디@서버이름 ~]$ 모양으로 바뀌면 서버에 들어온 것이다. 이후의 명령은 이 서버에서 실행된다.

지금 이 창이 내 PC인지 서버인지는 입력 줄의 모양으로 구별한다. 막혔을 때 가장 먼저 확인할 것이 이 구별이다.

입력 줄 위치 이 자리에서 하는 일

A-3. 비밀번호 변경

초기 비밀번호가 여러 학생에게 같거나 화면으로 안내된 것이면, 다른 사람이 내 계정으로 접속할 수 있다. 첫 접속 직후 passwd로 본인만 아는 비밀번호로 바꾼다.

서버 터미널 
passwd
Changing password for user 아이디.
Current password:            ← 지금 비밀번호
New password:                ← 새 비밀번호
Retype new password:         ← 새 비밀번호를 한 번 더
passwd: all authentication tokens updated successfully.
  • 세 번의 입력 모두 화면에 글자가 나오지 않는다.
  • 새 비밀번호가 너무 짧거나 사전에 있는 단어이면 BAD PASSWORD 메시지와 함께 거부된다. 더 긴 비밀번호로 다시 한다.
  • 새 비밀번호는 다른 서비스(학교 포털, GitHub, Claude 계정)와 다르게 정한다. 한 곳에서 새면 다른 곳까지 열리기 때문이다.
  • 비밀번호를 여러 번 틀리면 일정 시간 접속이 막힐 수 있다. 잊었으면 교수에게 재설정을 요청한다.

확인 2 passwd가 updated successfully를 출력하였고, 새 비밀번호로 다시 접속된다.

A-4. VS Code와 Remote-SSH

터미널 명령만으로는 여러 파일을 오가며 읽고 고치기 어렵다. Claude Code가 만든 파일을 읽고 직접 고치는 일은 편집기로 하고, 실행과 확인은 터미널로 한다. 편집기는 VS Code를 쓴다. Remote - SSH 확장을 더하면 서버의 폴더를 내 PC의 폴더처럼 열어, 파일을 내려받고 올리는 과정 없이 서버의 파일을 그 자리에서 고칠 수 있다[V1].

  1. code.visualstudio.com에서 Windows용 설치 파일을 내려받아 설치한다. 선택 항목은 기본값으로 둔다. 실습실 PC에 이미 있으면 실행만 확인한다.
  2. VS Code 왼쪽 세로 막대의 확장(Extensions) 아이콘을 누르고 Remote - SSH를 검색해 Microsoft가 만든 확장(식별자 ms-vscode-remote.remote-ssh)을 설치한다.
  3. F1(또는 Ctrl+Shift+P)로 명령 팔레트를 열고 Remote-SSH: Connect to Host...를 고른 뒤 아이디@서버주소를 입력한다. 서버의 종류를 물으면 Linux를 고른다.
  4. 비밀번호를 묻는 칸이 위쪽에 나오면 A-3에서 바꾼 비밀번호를 입력한다. 처음 연결할 때는 VS Code가 서버 쪽 구성 요소를 설치하느라 1~2분이 걸린다.
  5. 새 창의 왼쪽 아래 상태 표시줄에 SSH: 서버주소가 보이면 연결된 것이다.
  6. 메뉴의 File > Open Folder를 누르고 /home/아이디를 입력한다. 비밀번호를 한 번 더 물을 수 있다. 폴더를 신뢰할지 물으면 신뢰한다(내 홈 폴더이다).
  7. 왼쪽 탐색기에 내 홈 폴더의 파일이 보인다. 파일을 열어 고치고 Ctrl+S로 저장하면 서버의 파일이 바뀐다.

마크다운 파일(.md)은 편집기에서 Ctrl+Shift+V를 누르면 서식이 적용된 미리보기로 볼 수 있다. 키트의 README와 양식을 읽을 때 쓴다.

확인 3 VS Code 왼쪽 아래에 SSH: 서버주소가 보이고, 탐색기에 /home/아이디의 파일이 보인다.

Remote-SSH는 비밀번호를 저장하지 않으므로 연결할 때마다 묻는다. SSH 키로 비밀번호 없이 접속하는 방법이 있으나[V1], 키 파일을 다루는 일이 늘어나므로 이 과목에서는 요구하지 않는다.

Remote-SSH 연결이 여러 번 실패하면 그 시간에는 PowerShell 창 두 개로 진행한다. 두 창 모두에서 ssh 아이디@서버주소로 접속하면, 그 둘이 A-5의 두 터미널을 대신한다. 파일 내용은 cat 파일이름으로 본다. 연결 문제는 수업 뒤에 해결하며, A-18의 표를 먼저 본다.

A-5. 터미널 두 개의 배치

이 과목은 터미널 두 개를 나란히 두고 일한다. 한쪽에서 Claude Code에게 일을 시키고, 다른 쪽에서 그 결과를 사람이 직접 실행하고 확인한다. “AI가 만들고 사람이 검증한다”는 이 과목의 원칙을 화면 배치로 옮긴 것이다.

  1. Remote-SSH로 연결된 VS Code 창에서 메뉴의 Terminal > New Terminal을 누른다. 이 터미널은 서버에서 열리므로 ssh를 다시 입력하지 않는다.
  2. 터미널 패널 오른쪽 위의 분할 아이콘(또는 Terminal > Split Terminal)을 눌러 터미널을 하나 더 연다.
  3. 두 터미널의 이름을 정해 둔다.
자리 이름 하는 일 꼬리표
왼쪽 Claude Code 터미널 claude를 실행해 일을 시킨다 [Claude Code]
오른쪽 서버 터미널 파일 확인, 테스트 실행, git 명령 [서버 터미널]
  • 두 터미널의 현재 폴더는 따로 움직인다. 한쪽에서 cd를 해도 다른 쪽은 그대로이다. 실습 전에 두 터미널 모두 그 장의 작업 폴더로 옮긴다.
  • 서버 터미널에서 pwd로 현재 폴더를, ls로 목록을 수시로 확인한다.
  • VS Code 통합 터미널의 붙여넣기는 Ctrl+V이다. 내 PC의 PowerShell 창에서는 마우스 오른쪽 클릭이 붙여넣기이다.
  • 터미널 패널이 좁으면 패널 경계를 끌어 넓히거나, 편집기 영역을 줄인다. Claude Code의 화면은 폭이 좁으면 줄이 많이 꺾인다.

확인 4 VS Code 안에 서버 프롬프트([아이디@서버이름 ~]$)가 뜬 터미널이 두 개 나란히 있다.

A-6. Claude Code 설치

Claude Code는 서버에 미리 설치되어 있지 않다. 각자 자기 계정 안에 설치한다. 관리자 권한은 필요 없고, 설치 파일은 내 홈 폴더(~/.local/bin/claude와 ~/.local/share/claude/)에 놓인다[C1].

  1. 서버 터미널에서 공식 설치 명령을 실행한다. 이 명령은 공식 문서(Advanced setup)의 「Native Install」에 있는 macOS·Linux·WSL용 명령이다(2026-11-14 확인)[C1].
서버 터미널 
curl -fsSL https://claude.ai/install.sh | bash

curl이 설치 스크립트를 내려받고, |(파이프)가 그 내용을 bash에 넘겨 실행한다. 내려받는 동안에는 진행 표시가 없을 수 있다. 설치 주소는 공식 문서의 것만 쓴다. 블로그나 메신저로 받은 설치 명령은 실행하지 않는다.

  1. 설치가 끝나면 터미널을 닫고 새로 연다. 새로 연 터미널이라야 설치된 명령의 경로를 읽는다. VS Code에서는 터미널 패널의 휴지통 아이콘으로 터미널을 닫고 Terminal > New Terminal로 다시 연 뒤, 분할해서 두 개로 만든다.

  2. 버전을 확인한다.

서버 터미널 
claude --version
2.1.xxx (Claude Code)

버전 번호는 설치한 날에 따라 다르다. claude: command not found가 나오면 터미널을 새로 열었는지 먼저 확인하고, 그래도 안 되면 A-18의 표를 본다.

  1. 설치 상태를 진단한다. claude doctor는 세션을 시작하지 않고 설치 상태, 설정 파일의 오류, 자동 업데이트 결과를 읽기 전용으로 보여 준다[C1].
서버 터미널 
claude doctor

Claude Code는 이 방식으로 설치하면 백그라운드에서 스스로 업데이트한다. 업데이트는 다음 실행부터 적용된다. 바로 최신판으로 올리려면 claude update를 실행한다[C1]. 이 교재의 화면 이름과 메뉴는 2026-11 기준이므로, 학기 중에 표시가 달라질 수 있다. 다르면 /help와 공식 문서가 우선한다.

확인 5 새로 연 터미널에서 claude --version이 버전 번호와 (Claude Code)를 출력한다.

A-7. Claude Code 계정 로그인

이 과목에서 Claude Code는 계정 로그인으로 쓴다. 학생 개인이 API 키를 Claude Code에 등록하지 않는다. Claude Code를 쓸 수 있는 계정은 Claude의 유료 구독(Pro, Max 등), 팀 단위 계정(Team, Enterprise), Claude Console 계정이며, 무료 Claude 계정에는 Claude Code가 포함되지 않는다[C1][C2]. 이 과목에서 어떤 종류의 계정으로 로그인하는지와 로그인 화면에서 무엇을 고르는지는 수업 첫 주에 안내한다. 계정 종류에 따라 로그인 화면의 선택지와 이후의 사용 한도가 다르므로, 안내 전에 개인 결제로 구독을 시작하지 않는다.

A-7-1. 첫 로그인

  1. Claude Code 터미널(왼쪽)에서 내 홈 폴더로 가서 claude를 실행한다.
서버 터미널 
cd ~
claude
  1. 처음 실행하면 화면 테마를 고르고, 로그인 방식을 고르는 화면이 나온다. 1주차에 안내받은 방식을 고른다. 선택지의 이름은 Claude Code 버전에 따라 조금씩 다르다.
  2. 로그인 주소가 화면에 나온다. 서버에는 브라우저가 없으므로 브라우저가 저절로 열리지 않을 수 있다. 그때는 c를 눌러 로그인 주소를 복사하고 내 PC의 브라우저 주소창에 붙여 넣는다[C2]. 주소가 길어 줄이 꺾여 보이면 마우스로 끌어 복사하지 말고 c를 쓴다.
  3. 브라우저에서 1주차에 안내받은 계정으로 로그인하고 접근을 승인한다.
  4. 브라우저가 터미널로 돌아가지 않고 로그인 코드를 보여 주면, 그 코드를 복사해 터미널의 Paste code here if prompted 자리에 붙여 넣고 Enter를 누른다[C2].
  5. 터미널에 Login successful이 나오면 Enter를 눌러 계속한다.
  6. 이어서 보안 안내와 폴더 신뢰 질문이 나온다. 보안 안내는 읽고 넘기고, 폴더 신뢰 질문에는 내 홈 폴더이므로 신뢰한다고 답한다. 폴더 신뢰는 Claude Code가 그 폴더의 파일을 읽고 그 폴더의 설정을 적용해도 되는지 묻는 것이다. 키트나 남의 저장소처럼 내용을 모르는 폴더에서 처음 실행할 때는 이 질문을 그냥 넘기지 않는다.

Claude Code를 실행하지 않고 셸에서 바로 로그인할 수도 있다. claude auth login은 로그인만 하고 끝나는 명령이다. 기본은 Claude 구독 계정 로그인이고, --console을 붙이면 Claude Console 계정으로, --sso를 붙이면 조직의 SSO로 로그인한다(claude auth login --help, 2026-11-14 확인).

서버 터미널 
claude auth login
claude auth status --text
(로그인 전)
Anthropic base URL: https://api.anthropic.com
Not logged in. Run claude auth login to authenticate.

로그인한 뒤에는 claude auth status --text가 로그인 방식과 계정을 보여 준다. --text를 빼면 같은 내용을 JSON으로 출력한다.

A-7-2. 로그인 상태의 확인

Claude Code 입력 창에서 /status를 입력하면 버전, 모델, 계정, 연결 상태를 보여 주는 설정 화면의 Status 탭이 열린다[C3]. 로그인 방식(Login method)과 계정이 1주차에 안내받은 것과 같은지 확인한다. 확인했으면 Esc로 닫고 /exit로 Claude Code를 끝낸다.

Claude Code 
/status
/exit

/status 화면에서 볼 것은 다음과 같다.

항목 확인할 것
버전 claude --version과 같은 번호
로그인 방식과 계정 1주차에 안내받은 계정 종류와 이메일
모델 수업에서 안내한 모델
작업 폴더 Claude Code를 실행한 폴더
설정 출처(Setting sources) 어떤 설정 파일을 읽었는가

모델은 Claude Code 안에서 /model로 바꾼다. /model로 고른 모델은 다음 세션의 기본값으로 저장된다[C3]. 수업에서 쓸 모델은 계정 종류와 비용에 따라 1주차에 안내한다.

A-7-3. 로그인의 유지와 다시 로그인

  • 로그인 정보는 서버의 ~/.claude/.credentials.json에 저장되고, 이 파일은 본인만 읽을 수 있는 권한으로 만들어진다[C2]. 이 파일을 복사하거나 남에게 보내지 않는다. 저장소에 넣지 않는다.
  • 다시 접속해도 로그인은 유지된다. 로그인이 만료될 때가 가까우면 Claude Code가 시작할 때 경고를 보이고, 만료되면 요청마다 Login expired · Please run /login이 나온다. 그때 /login을 실행한다[C2].
  • 다른 계정으로 바꾸려면 Claude Code 안에서 /logout을 실행한 뒤 다시 /login을 한다. /logout은 첫 실행 설정도 함께 초기화하므로, 다음 claude 실행에서 로그인과 설정을 다시 한다[C2].
  • 셸에 ANTHROPIC_API_KEY 환경 변수를 등록하지 않는다. Claude Code는 이 변수가 있으면 그 키를 쓸지 묻고, 승인하면 계정 로그인보다 그 키를 먼저 쓴다[C2]. 2026년 2학기에는 이 변수로 Claude Code를 인증했으나 이 과목은 그렇게 하지 않는다. 10장부터 받는 프로덕트용 키는 A-13의 방식으로 .env 파일에만 둔다.

다음은 같은 PC에서 가짜 키를 환경 변수로 주고 인증 상태를 본 결과이다(2026-11-14). 로그인 대신 환경 변수의 키가 인증 수단으로 잡힌다.

$ ANTHROPIC_API_KEY=가짜값 claude auth status --text
API key: ANTHROPIC_API_KEY
Anthropic base URL: https://api.anthropic.com

확인 6 /status의 로그인 방식과 계정이 1주차에 안내받은 것과 같고, 서버 터미널의 echo ${ANTHROPIC_API_KEY:-없음}이 없음을 출력한다.

A-8. 작업 폴더와 키트 받기

A-8-1. 서버의 폴더

서버에서 쓰는 폴더는 성격에 따라 다섯으로 나뉜다.

폴더 권한 쓰임
내 홈 ~ (/home/아이디) 읽기와 쓰기 내 작업 공간. 다른 학생은 볼 수 없다
개인 실습 저장소 ~/llm-service-lab/ 읽기와 쓰기 2장에서 만드는 Git 저장소. 1~5장의 결과는 chNN/, 6장부터의 공통 사례 결과는 jobprep/에 쌓인다
배포 폴더 $KIT_HOME 읽기 전용 장마다 키트 폴더 Service_NN주차/가 올라온다
받은 키트 ~/kits/ 읽기와 쓰기 배포 폴더에서 복사해 온 키트. 여기서 읽고, 필요한 파일을 저장소로 옮긴다
팀 실습 저장소 ~/teams/<팀>-lab/ 읽기와 쓰기 3장부터 수업용 조직의 팀 저장소를 클론하는 자리. 개인 실습 저장소 안에 두지 않는다

배포 폴더는 읽기만 되므로 그 안에서 파일을 고치거나 프로그램을 실행하지 않는다. 키트를 ~/kits/로 복사해 온 뒤 작업한다. 키트는 저장소 밖에 둔다. 키트 전체를 저장소에 넣으면 교수의 배포물과 학습자의 작업이 한 기록에 섞이기 때문이다. 키트의 파일 가운데 무엇을 저장소의 어느 자리로 옮기는지는 각 장의 0절이 정한다. 예를 들어 1장은 키트의 내용물을 ~/llm-service-lab/ch01/로 복사하고, 4장은 양식 다섯 개만 ch04/로 복사한다.

A-8-2. $KIT_HOME 등록

배포 폴더의 실제 경로는 1주차에 안내한다. 그 경로를 환경 변수 KIT_HOME에 넣어 두면, 각 장의 명령이 경로를 몰라도 $KIT_HOME으로 배포 폴더를 가리킬 수 있다. 아래의 배포폴더 자리에 안내받은 경로를 넣는다.

서버 터미널 
echo 'export KIT_HOME=배포폴더' >> ~/.bashrc
source ~/.bashrc
echo "$KIT_HOME"
ls "$KIT_HOME"
배포폴더
Service_01주차  Service_02주차  ...
  • 환경 변수는 프로그램들이 공통으로 읽는 이름과 값의 쌍이다. export로 만든 변수는 그 셸과 그 셸이 실행하는 프로그램에 전달된다.
  • ~/.bashrc는 서버 터미널을 열 때마다 자동으로 읽히는 설정 파일이다. >>는 파일 끝에 한 줄을 덧붙이고, >는 파일을 새로 만들어 덮어쓴다. 여기서 >를 쓰면 ~/.bashrc의 기존 내용이 지워지므로 반드시 >>를 쓴다.
  • source ~/.bashrc는 바뀐 설정을 지금 터미널에 바로 읽힌다. 이미 열려 있던 다른 터미널에는 적용되지 않으므로, 그 터미널에서도 source ~/.bashrc를 하거나 새로 연다.
  • 같은 줄을 두 번 덧붙였으면 ~/.bashrc를 VS Code로 열어 한 줄을 지운다. 마지막 줄의 값이 적용된다.

A-8-3. 장의 키트 받기

장마다 0절의 첫 명령이 그 장의 키트를 받는 명령이다. 형식은 다음과 같다(NN은 장 번호).

서버 터미널 
mkdir -p ~/kits
cp -rn "$KIT_HOME/Service_NN주차" ~/kits/
ls ~/kits/Service_NN주차
부분 뜻
mkdir -p ~/kits ~/kits 폴더를 만든다. 이미 있으면 아무 일도 하지 않는다
cp -r 폴더를 안의 내용까지 통째로 복사한다
cp -n 같은 이름의 파일이 이미 있으면 덮어쓰지 않는다
"$KIT_HOME/..." 큰따옴표는 경로에 공백이나 한글이 있어도 한 덩어리로 다루게 한다

-n을 쓰는 까닭은 받은 키트의 파일을 고친 뒤 같은 명령을 다시 실행해도 고친 내용이 지워지지 않게 하기 위해서이다. 다음은 그 동작을 확인한 기록이다(2026-11-14, Git Bash).

$ cp -rn "$KIT_HOME/Service_10주차" kits/
$ echo "내가 고침" > kits/Service_10주차/README.md
$ cp -rn "$KIT_HOME/Service_10주차" kits/
$ cat kits/Service_10주차/README.md
내가 고침

반대로, 교수가 키트를 고쳐 다시 배포했을 때 새 판을 받으려면 내 사본의 이름을 바꾸어 보관하고 다시 받는다. 지우고 받으면 내가 고친 내용이 사라진다.

서버 터미널 
mv ~/kits/Service_NN주차 ~/kits/Service_NN주차_내사본
cp -rn "$KIT_HOME/Service_NN주차" ~/kits/

키트의 README.md가 무엇이 들어 있고 어떤 순서로 쓰는지를 알려 준다. 키트에서 이름이 _양식.md로 끝나는 파일은 답을 적는 파일의 원본이다. 양식에는 직접 쓰지 않고, 장의 0절이 안내하는 이름으로 복사해 쓴다. 기준산출물/ 폴더는 앞 장의 산출물이 없는 학생을 위한 것이다. 앞 장을 마친 학생은 자기 산출물을 쓴다.

확인 7 echo "$KIT_HOME"이 1주차에 안내받은 경로를 출력하고, ls "$KIT_HOME"에 Service_ 폴더가 보인다.

A-9. Git 설정

Git은 커밋마다 작성자의 이름과 이메일을 기록한다. 처음 한 번 설정해 두면 서버의 모든 저장소에 적용된다[G1].

서버 터미널 
git config --global user.name "홍길동"
git config --global user.email "GitHub에_등록한_이메일"
git config --global core.quotepath false
git config --global init.defaultBranch main
git config --global pull.rebase false
git config --global --list
user.name=홍길동
user.email=GitHub에_등록한_이메일
core.quotepath=false
init.defaultbranch=main
pull.rebase=false
설정 뜻 이 과목에서 정하는 까닭
user.name 커밋에 남는 작성자 이름 팀 저장소에서 누가 고쳤는지 구별한다. 실명 또는 1주차에 정한 표기
user.email 커밋에 남는 작성자 이메일 GitHub 계정에 등록한 이메일을 써야 커밋이 내 계정의 기여로 표시된다[H1]
core.quotepath false 한글 파일 이름을 그대로 보여 준다 이 과목의 파일 이름(요구사항명세서.md 등)이 한글이다
init.defaultBranch main git init으로 만든 저장소의 첫 브랜치 이름 GitHub의 기본 브랜치 이름과 맞춘다
pull.rebase false git pull이 원격의 변경을 병합(merge)으로 합친다 두 갈래로 나뉜 기록을 합칠 때 Git 판에 따라 방식을 묻는 메시지가 나오는 것을 막는다

core.quotepath를 true(기본값)로 두면 한글 파일 이름이 8진수 기호로 바뀌어 보인다. 같은 저장소에서 두 설정을 견준 결과이다(2026-11-14, git 2.55).

$ git -c core.quotepath=true status --short
?? "ch02/\354\203\210\355\214\214\354\235\274.md"
$ git status --short
?? ch02/새파일.md

이메일을 공개하고 싶지 않으면 GitHub의 Settings > Emails에서 「Keep my email addresses private」를 켜고, GitHub가 제공하는 no-reply 주소를 user.email에 넣을 수 있다[H1]. 그 주소는 같은 설정 화면에 표시된다.

확인 8 git config --global --list에 위 다섯 줄이 있고, user.email이 GitHub 계정의 이메일과 같다.

A-10. GitHub 계정, GitHub CLI 인증, 학생 혜택

A-10-1. GitHub 계정 만들기

이 과목과 프로젝트실습에서 저장소를 GitHub에 둔다. 학생 개인의 계정을 쓴다. 이미 계정이 있으면 그것을 쓴다.

  1. 브라우저에서 github.com/signup에 들어가 이메일, 비밀번호, 사용자 이름을 정해 가입한다. 가입 과정에서 이메일 인증을 해야 계정을 쓸 수 있다[H2].
  2. 사용자 이름은 저장소 주소(github.com/사용자이름/저장소)와 커밋 기록에 공개된다. 취업 포트폴리오로도 쓰이므로 본인을 알아볼 수 있는 이름을 권한다.
  3. 2단계 인증(2FA)을 켠다. GitHub 문서는 2단계 인증을 강하게 권장하고[H2], 수업용 조직이 2단계 인증을 요구하도록 설정되어 있으면 켜지 않은 계정은 초대를 받아들일 수 없다[H3]. 인증 앱(OTP 앱)이나 패스키를 쓰고, 복구 코드는 저장소가 아닌 안전한 곳에 보관한다.
  4. 1주차에 GitHub 사용자 이름을 제출한다(수업용 조직에 초대하기 위해서이다).

A-10-2. GitHub CLI 인증

GitHub CLI(gh)는 터미널에서 GitHub의 저장소, 이슈, 풀 리퀘스트를 다루는 공식 명령 도구이다[H4]. gh auth login으로 한 번 인증하면 gh 명령과 git push가 모두 그 인증을 쓴다.

서버 터미널 
gh auth login

질문이 차례로 나온다. 다음과 같이 답한다.

질문 답
Where do you use GitHub? GitHub.com
What is your preferred protocol for Git operations on this host? HTTPS
Authenticate Git with your GitHub credentials? Yes
How would you like to authenticate GitHub CLI? Login with a web browser

질문의 문구는 gh 2.88에서 확인한 것이다. 마지막 답을 고르면 First copy your one-time code: XXXX-XXXX 형식의 한 번만 쓰는 코드와 함께, Enter를 누르면 브라우저로 https://github.com/login/device를 연다는 안내가 나온다. 서버에서는 브라우저가 열리지 않으므로 다음 순서로 한다.

  1. 화면의 코드를 적어 두거나 복사한다.
  2. 내 PC의 브라우저에서 https://github.com/login/device를 연다.
  3. GitHub에 로그인한 상태에서 코드를 입력하고 GitHub CLI의 접근을 승인한다.
  4. 터미널로 돌아오면 Logged in as 사용자이름이 나온다.
서버 터미널 
gh auth status
github.com
  ✓ Logged in to github.com account 사용자이름 (keyring)
  - Active account: true
  - Git operations protocol: https
  - Token: gho_************************************
  - Token scopes: 'gist', 'read:org', 'repo', 'workflow'
  • 인증 정보는 시스템의 자격 증명 저장소에 저장되고, 저장소가 없는 환경에서는 일반 파일로 저장된다. 어디에 저장되었는지는 gh auth status가 보여 준다(gh auth login --help, 2026-11-14 확인). 서버에서는 괄호 안이 (keyring)이 아닌 파일 경로로 나올 수 있다.
  • 토큰은 화면에 일부만 보인다. 화면을 캡처해 공유할 때도 토큰 줄은 가린다.
  • git push가 사용자 이름과 비밀번호를 물으면 GitHub 인증이 Git에 연결되지 않은 것이다. gh auth setup-git을 실행한 뒤 다시 한다. GitHub는 git push에서 계정 비밀번호를 받지 않는다.
  • 인증을 지우려면 gh auth logout을 실행한다. 서버를 다른 사람과 함께 쓰는 계정으로 접속한 적이 있다면 반드시 지운다.

로그인하지 않은 상태에서 gh auth status를 실행하면 다음이 나온다(2026-11-14, gh 2.88).

You are not logged into any GitHub hosts. To log in, run: gh auth login

확인 9 gh auth status에 ✓ Logged in to github.com account 사용자이름과 Git operations protocol: https가 보인다.

A-10-3. 개인 저장소의 공개 범위와 학생 혜택

2장에서 GitHub에 올리는 개인 실습 저장소 llm-service-lab은 비공개(Private)로 만든다. 이 저장소에는 학기 내내의 작업 기록과 평가의 근거가 쌓이고, 실수로 넣은 파일(설정, 기록)이 섞일 수도 있기 때문이다. 교수가 학생의 비공개 저장소를 읽는 방법(협업자 초대 등)은 수업에서 안내한다.

비공개로 두면 9장에서 문제가 하나 생긴다. 9장은 정적 웹 화면을 GitHub Pages로 배포하는데, Pages를 쓸 수 있는 저장소는 계정의 요금제에 따라 다르다.

요금제 GitHub Pages를 쓸 수 있는 저장소 근거
GitHub Free(개인 계정의 기본) 공개 저장소만 [H6][H7]
GitHub Pro 공개 저장소와 비공개 저장소 [H6]

그래서 이 과목은 GitHub의 학생 혜택으로 GitHub Pro를 받는 길을 권한다. GitHub Education의 학생 개발자 묶음(Student Developer Pack)은 혜택 목록에 「Free GitHub Pro while you are a student」(재학 중 GitHub Pro 무료)를 적는다[H8]. 신청 조건과 절차는 다음과 같다(GitHub Docs, 2026-11-14 확인)[H9].

  1. 학위나 학력을 주는 과정에 재학 중이고, 13세 이상이며, 개인 GitHub 계정이 있어야 한다.
  2. 현재의 재학 상태를 보이는 서류(재학 기간이 적힌 학생증, 시간표, 성적 증명서, 재학 증명서 등)를 낸다. 학교가 학교 이메일을 요구하면, 신청 전에 그 이메일을 GitHub 계정에 더하고 인증한다.
  3. 브라우저에서 https://github.com/settings/education/benefits를 열고 「GitHub Education」 아래의 「Start an application」을 눌러 양식을 채운 뒤 제출한다.

문서는 심사에 걸리는 기간을 밝히지 않는다. 9장 직전에 신청하면 늦을 수 있으므로 1주차에 신청한다. 승인 결과는 GitHub에 등록한 이메일로 온다. 학생 혜택을 받지 못한 학생은 9장에서 Pages용 공개 저장소를 따로 만드는 길을 쓴다(9장에서 안내한다).

비공개 저장소에서 연 Pages 사이트도 인터넷에 공개된다. GitHub Docs는 저장소가 비공개여도 Pages 사이트는 인터넷에서 누구나 볼 수 있다고 밝히고, 배포 전에 민감한 자료를 저장소에서 지우라고 권한다[H7]. 저장소를 비공개로 두는 것은 저장소의 파일과 기록을 가리는 것이지, 배포한 화면을 가리는 것이 아니다.

A-11. 수업용 조직의 초대 수락

3장부터 팀 저장소는 수업용 GitHub 조직(Organization)에 둔다. 교수가 1주차에 받은 사용자 이름으로 조직에 초대하면, 학생이 초대를 받아들여야 조직의 구성원이 된다[H3].

  1. GitHub에 등록한 이메일로 초대 링크가 든 메일이 온다[H3]. GitHub에 로그인한 브라우저에서 그 링크를 연다. 조직의 이름(조직이름)은 수업에서 안내한다.
  2. 초대 화면에서 초대를 받아들인다. 메일을 찾지 못하면 아래의 gh api 명령으로 상태를 확인하고 받아들인다.
  3. 초대는 7일이 지나면 만료된다[H3]. 만료되었으면 교수에게 다시 초대를 요청한다.
  4. 조직이 2단계 인증을 요구하면, 2단계 인증을 켠 뒤에 받아들일 수 있다[H3].
  5. 조직이 이메일 주소로 초대한 경우에는 그 주소가 내 GitHub 계정에 인증된 이메일이어야 받아들일 수 있다[H3].

조직 구성원이 되었는지는 브라우저에서 조직 화면의 People 탭으로 확인하거나, 서버 터미널에서 GitHub API로 확인한다. state가 active이면 구성원이고, pending이면 초대를 아직 받아들이지 않은 것이다[H5].

서버 터미널 
gh api user/memberships/orgs/조직이름 --jq .state
active

초대를 받아들이지 않은 상태(pending)에서는 같은 API에 state를 active로 보내 받아들일 수도 있다[H5]. 브라우저 화면이 열리지 않을 때만 쓴다.

서버 터미널 
gh api -X PATCH user/memberships/orgs/조직이름 -f state=active --jq .state

A-12. 파이썬 가상 환경과 패키지 설치

파이썬 키트(테스트가 있는 골격, 9장의 브라우저 검사, 10장의 FastAPI 백엔드, 11장의 RAG 코드)는 필요한 패키지와 버전을 requirements.txt에 적어 둔다. 패키지는 서버 전체가 아니라 가상 환경(virtual environment)에 설치한다. 가상 환경은 정해진 프로젝트만 쓰는 파이썬 실행 파일과 패키지 폴더의 묶음이다. 관리자 권한 없이 설치할 수 있고, 서버의 다른 사용자와 부딪치지 않는다[P1].

이 과목은 가상 환경을 개인 실습 저장소 맨 위에 하나(~/llm-service-lab/.venv) 만들어 학기 내내 쓴다. 장마다 그 장의 requirements.txt를 이 환경에 더 설치한다. 장마다 가상 환경을 따로 만들면 같은 패키지가 여러 벌 쌓여 홈 폴더의 용량을 차지하고, 지금 어느 환경을 쓰는지 헷갈리기 쉽다. 하나로 두면 저장소 맨 위 .gitignore의 .venv/ 한 줄로 커밋에서 뺄 수 있다. 각 장의 키트는 같은 패키지를 같은 판으로 고정한다(예: pytest==9.2.0, 10·11장의 python-dotenv==1.2.4).

A-12-1. 만들기와 설치

가상 환경은 2장에서 개인 실습 저장소를 만들 때 처음 만든다(2장 3-4). 그 뒤로는 만들지 않고 패키지만 더 설치한다.

서버 터미널 
cd ~/llm-service-lab
python3 -m venv .venv
.venv/bin/python --version
.venv/bin/python -m pip install -r ch02/deadline/requirements.txt
.venv/bin/python -m pip list
Python 3.12.x
...
Package    Version
---------- -------
pytest     9.2.0
...
명령 뜻
python3 -m venv .venv 지금 폴더(저장소 맨 위)에 .venv라는 가상 환경을 만든다. 이름 앞의 점은 숨김 폴더라는 뜻이다. 이미 있으면 다시 하지 않는다
.venv/bin/python -m pip install -r 파일 그 장의 requirements.txt에 적힌 패키지를 적힌 판 그대로 설치한다. 장마다 이 줄만 경로를 바꾸어 실행한다
.venv/bin/python -m pip list 설치된 패키지와 판을 보여 준다
source .venv/bin/activate 가상 환경을 켠다. 입력 줄 앞에 (.venv)가 붙고, 이후 python과 pip는 가상 환경의 것을 가리킨다
deactivate 가상 환경을 끈다
  • 이 과목은 가상 환경을 켜지 않고 그 안의 파이썬을 경로로 부르는 것을 기본으로 한다(.venv/bin/python …). 켰는지 껐는지를 신경 쓰지 않아도 되므로, Claude Code에게 실행을 맡길 때도 이 형식을 쓴다.
  • .venv/bin/python은 저장소 맨 위에서 부를 때의 경로이다. jobprep/처럼 한 단계 아래의 폴더에서는 ../.venv/bin/python으로 부르거나, 어느 폴더에서나 통하는 홈에서 시작하는 경로 ~/llm-service-lab/.venv/bin/python을 쓴다. 또는 source ~/llm-service-lab/.venv/bin/activate로 켠 뒤 python을 쓴다.
  • pip를 python -m pip로 부르는 까닭은 그 파이썬에 딸린 pip를 확실히 쓰기 위해서이다. 가상 환경을 켜지 않은 채 pip만 치면 다른 파이썬에 설치될 수 있다.
  • 설치가 끝난 뒤 [notice] A new release of pip is available 안내가 나올 수 있다. 수업에서는 무시해도 된다.
  • 설치 중에 이미 있던 패키지를 다른 판으로 바꾼다는 줄(Successfully uninstalled 패키지-판)이 나오면, 두 장의 키트가 같은 패키지를 다른 판으로 고정한 것이다. 그대로 진행하되 교수에게 알린다.
서버 터미널 
cd ~/llm-service-lab/jobprep
~/llm-service-lab/.venv/bin/python -m pytest -q

A-12-2. 가상 환경을 다루는 규칙

  • .venv는 저장소에 커밋하지 않는다. 파이썬 3.13부터 venv는 가상 환경 안에 그 폴더 전체를 무시하는 .gitignore를 스스로 만든다[P1]. 서버의 파이썬이 3.12이면 이 파일이 생기지 않으므로, 저장소 맨 위의 .gitignore에 .venv/를 적어 둔다(2장에서 만든다).
  • 하위 폴더(chNN/, jobprep/)에 가상 환경을 또 만들지 않는다. 키트의 README가 「가상 환경을 만든다」고 하면 저장소 맨 위의 환경에 그 장의 패키지를 설치하는 것으로 읽는다.
  • 가상 환경은 언제든 지우고 다시 만들 수 있는 것으로 다룬다. 그 안에 내 코드를 두지 않는다. 다른 폴더로 옮기면 동작하지 않는다(안의 스크립트가 만든 자리의 절대 경로를 기억한다)[P1]. 저장소를 옮겼으면 .venv를 지우고 다시 만든다.
  • 패키지가 꼬였으면 다음 순서로 처음부터 다시 만든다. 마지막 줄은 저장소 안의 모든 requirements.txt를 찾아 차례로 설치한다.
서버 터미널 
cd ~/llm-service-lab
deactivate 2>/dev/null
rm -rf .venv
python3 -m venv .venv
find . -name requirements.txt -not -path "./.venv/*" -exec .venv/bin/python -m pip install -q -r {} \;
  • 키트에 없는 패키지가 필요하다고 Claude Code가 제안하면, 바로 설치하지 말고 무엇을 왜 설치하는지 읽는다. 설치하기로 했으면 그 장의 requirements.txt에도 판과 함께 적는다. 적지 않으면 다른 사람(또는 다시 만든 가상 환경)에서 같은 코드가 돌지 않는다.

확인 11 ~/llm-service-lab/.venv/bin/python -m pip list가 그 장의 requirements.txt에 적힌 패키지를 같은 판으로 보여 주고, ls -a ~/llm-service-lab에 .venv가 하나만 있다.

A-13. 프로덕트의 API 키

10장부터 학습자가 만드는 프로덕트(FastAPI 백엔드, RAG 질의응답)는 Anthropic의 Messages API를 부른다. 이 호출에는 API 키가 필요하다. API 키는 요청한 사람을 식별하고 사용량을 청구하는 문자열이므로 비밀번호처럼 다룬다.

A-13-1. 계정 로그인을 프로덕트에 쓰지 않는 까닭

Claude Code에 로그인한 계정을 프로덕트 코드의 LLM 호출에 쓸 수는 없다. Anthropic의 Claude Code 문서 「Legal and compliance」는 두 인증 방식의 용도를 나눈다[C4].

  • 구독 계정의 로그인(OAuth)은 구독자가 Claude Code와 Anthropic의 앱을 통상적으로 쓰기 위한 것이다.
  • Claude의 기능을 쓰는 제품이나 서비스를 만드는 개발자는, Agent SDK를 쓰는 경우를 포함해, Claude Console의 API 키(또는 지원되는 클라우드 제공자)로 인증해야 한다.
  • 제3자가 자기 앱에 Claude.ai 로그인을 넣거나, 사용자 대신 구독 자격 증명으로 요청을 보내는 것은 허용되지 않는다. 문서의 표현으로는 개발자가 Claude.ai의 자격 증명이나 세션 토큰을 “collect, store, or intermediate”(수집, 저장, 중개)해서는 안 된다.

학습자가 만드는 공고 요약 API는 그 자체가 하나의 서비스이므로 API 키를 쓰는 쪽에 속한다. 그래서 이 과목은 Claude Code(개발 도구)는 계정 로그인으로, 프로덕트는 API 키로 나눈다. 로그인 정보 파일(~/.claude/.credentials.json)을 코드에서 읽어 쓰는 일도 같은 이유로 하지 않는다.

A-13-2. 키의 배부와 보관

  1. 실습용 키의 발급 여부는 정해지지 않았고, 수업 첫 주에 안내한다. 발급하는 경우에는 교수가 학과 조직의 Claude Console에서 실습용 작업 공간과 사용 한도를 정해 배부한다. 키가 없어도 모든 장의 실습은 모의 모드(LLM_FAKE=1)로 끝까지 할 수 있고, 실제 모델의 응답은 교수 시연과 교수가 배포하는 실행 기록으로 본다. 학생이 개인 결제로 키를 만들 필요는 없다.
  2. 키는 공통 사례 폴더의 jobprep/.env 파일에만 둔다. 10~12장의 백엔드와 RAG 코드가 모두 이 파일을 읽는다. .env는 저장소에 커밋하지 않는다.
  3. 10장 키트의 jobprep/.env.example은 변수의 이름과 키가 아닌 기본값만 적은 견본이다. ANTHROPIC_API_KEY의 값은 비어 있다. 이 파일은 커밋한다. 다른 사람이 어떤 변수가 필요한지 알 수 있게 하기 위해서이다. 다음은 10장 키트의 견본 그대로이다.
파일: jobprep/.env.example 
# 이 파일을 .env 로 복사해 쓴다: cp .env.example .env
# .env 는 .gitignore 에 들어 있어 커밋되지 않는다. 이 파일(.env.example)에는 값을 적지 않는다.

# 1이면 API를 부르지 않는 모의 모드. 실제 호출은 0으로 바꾸고 아래 키를 채운 뒤에만 한다
LLM_FAKE=1

# 실습용 키를 받은 경우에만 적는다(발급 여부는 수업 첫 주에 안내). .env 에만 적는다
ANTHROPIC_API_KEY=

# 모델 이름. 2026-11 기준 저가 모델. 수업 직전에 공식 모델 목록에서 다시 확인한다
LLM_MODEL=claude-haiku-5-5

# 생각(thinking)의 깊이. low는 싸고 빠르다. 비워 두면 보내지 않는다(모델 기본값 medium)
LLM_EFFORT=low

# API가 쓸 프롬프트 판본(판본 비교에서 채택한 것)
PROMPT_VERSION=v3

# 접속지 하나가 1분에 보낼 수 있는 요약 요청 수
RATE_LIMIT_PER_MIN=10
  1. jobprep/에서 견본을 복사해 .env를 만든다. -n은 .env가 이미 있으면 덮어쓰지 않는다.
서버 터미널 
cd ~/llm-service-lab/jobprep
cp -n .env.example .env
chmod 600 .env
  1. VS Code에서 .env를 열어 ANTHROPIC_API_KEY= 뒤에 배부받은 키를 붙여 넣고 저장한다. 따옴표와 공백 없이 한 줄로 넣는다. 터미널에서 echo "ANTHROPIC_API_KEY=..." >> .env로 넣지 않는다. 명령이 셸의 기록(~/.bash_history)에 키와 함께 남기 때문이다.

chmod 600 .env는 파일을 소유자만 읽고 쓸 수 있게 한다. 서버를 여러 사람이 쓰므로 하는 조치이다(B-4의 권한 절).

A-13-3. 커밋되지 않는지 확인

저장소의 .gitignore에 .env가 있어야 한다. 저장소 맨 위의 .gitignore는 2장의 견본으로 만들었고, 10장 키트의 jobprep/.gitignore에도 .env가 있다. jobprep/에서 다음 두 명령으로 확인한다.

서버 터미널 
cd ~/llm-service-lab/jobprep
git check-ignore -v .env
git status --short
jobprep/.gitignore:2:.env   .env

git check-ignore -v가 어느 .gitignore의 몇째 줄이 .env를 무시하게 하는지 보여 주면 된다. 위 출력은 10장 키트의 jobprep/.gitignore가 있을 때이고, 그 파일이 없으면 저장소 맨 위의 견본이 잡혀 .gitignore:12:.env .env처럼 나온다(2026-11-14, git 2.55에서 두 경우를 확인). 아무것도 출력하지 않으면 무시되지 않는 것이므로 커밋하기 전에 .gitignore에 .env를 더한다. git status --short에 .env가 보이면 안 된다.

실수로 git add까지 했다면, 커밋하기 전에 스테이징에서만 빼낸다. 파일은 지워지지 않는다(2026-11-14, git 2.55에서 확인).

서버 터미널 
git rm --cached .env
$ git status --short
A  .env
$ git rm --cached -q .env
$ git status --short
?? .env

키를 커밋하거나 푸시했으면 그 키는 이미 샌 것으로 본다. 다음 커밋에서 파일을 지워도 기록에 남아 있기 때문이다. 바로 교수에게 알려 그 키를 폐기하고 새 키를 받는다. 기록을 고쳐 쓰는 것으로 해결하려 하지 않는다.

A-13-4. 키를 다루는 규칙

하는 것 하지 않는 것
.env에만 둔다 코드, 프롬프트, 마크다운 문서, 커밋 메시지에 키를 적는다
키의 존재는 앞 몇 글자나 「있음/없음」으로만 확인한다 키 전체를 화면에 출력하거나 캡처한다
서버 쪽(백엔드)에서만 읽는다 브라우저에서 도는 자바스크립트에 키를 넣는다(10장)
프로젝트의 .claude/settings.json에 .env를 읽지 못하게 하는 거부 규칙을 둔다 Claude Code에게 .env를 열어 보게 하거나 키를 붙여 넣는다
~/.bashrc가 아닌 .env에 둔다 export ANTHROPIC_API_KEY=...를 ~/.bashrc에 넣는다(A-7-3)

Claude Code가 .env를 읽지 못하게 하는 설정은 공식 문서의 예와 같은 형식으로 쓴다[C5]. 저장소에 커밋하면 같은 저장소를 쓰는 모든 사람에게 적용된다.

파일: jobprep/.claude/settings.json 
{
  "permissions": {
    "deny": [
      "Read(./.env)",
      "Read(./.env.*)"
    ]
  }
}

키가 들어갔는지는 값을 출력하지 않고 확인한다. 다음은 키트의 방식처럼 .env를 읽은 뒤 「있음/없음」만 출력하는 확인이다.

서버 터미널 
cd ~/llm-service-lab/jobprep
~/llm-service-lab/.venv/bin/python -c "from dotenv import load_dotenv; import os; load_dotenv(); print('KEY_SET' if os.getenv('ANTHROPIC_API_KEY') else 'KEY_EMPTY')"
KEY_SET

확인 12 git check-ignore -v .env가 .gitignore의 줄을 출력하고, 위 확인 명령이 KEY_SET을 출력한다(10장 전까지).

A-14. 모의 모드와 모델 변수

A-14-1. 모의 모드 LLM_FAKE

이 과목에서 LLM을 부르는 모든 키트 코드는 환경 변수 LLM_FAKE가 1이면 API를 부르지 않고 정해진 응답을 낸다. 이것을 모의 모드(fake mode)라 한다. 모의 모드를 두는 까닭은 세 가지이다.

  1. 키가 없거나, 사용 한도에 닿았거나, 네트워크가 막혀도 수업이 멈추지 않는다.
  2. 같은 입력에 늘 같은 출력이 나오므로 테스트가 매번 같은 결과를 낸다. 실제 모델의 응답은 호출마다 달라질 수 있다.
  3. 비용이 들지 않는다. 테스트를 수십 번 돌려도 사용량이 쌓이지 않는다.

모의 모드로 확인하는 것은 코드의 흐름(입력 검사, 응답 형식, 오류 처리, 화면 연결)이다. 요약이 잘 되었는지 같은 응답의 품질은 실제 호출로만 확인할 수 있다.

A-14-2. 모델 변수 LLM_MODEL

키트의 코드에는 모델 이름을 적지 않는다. 실제 호출에 쓸 모델은 환경 변수 LLM_MODEL로 받는다. 모델은 새로 나오고 오래된 것은 지원이 끝나므로, 코드에 이름을 박아 두면 학기 중에 코드를 고쳐야 할 수 있다. 값은 수업 직전에 Anthropic의 공식 모델 목록에서 확인한 모델 이름을 교수가 안내한다. 10장 키트의 .env.example에는 2026-11 기준의 저가 모델 claude-haiku-5-5가 들어 있고, LLM_MODEL이 비어 있으면 코드의 기본값(같은 모델)을 쓴다. 수업에서 다른 이름을 안내하면 .env의 그 줄만 바꾼다.

10~11장의 코드가 읽는 환경 변수는 다음과 같다. 값은 모두 jobprep/.env에 둔다.

변수 뜻 장
LLM_FAKE 1이면 API를 부르지 않는 모의 모드 10~12장
LLM_MODEL 실제 호출에 쓸 모델 이름 10~12장
LLM_EFFORT 모델이 생각에 쓰는 노력의 정도(low 등). 비우면 보내지 않는다 10장
PROMPT_VERSION API가 쓸 프롬프트 판본 10장
RATE_LIMIT_PER_MIN 접속지 하나가 1분에 보낼 수 있는 요약 요청 수 10장
EMBED_BACKEND, OLLAMA_URL, EMBED_MODEL 임베딩을 만드는 방법과 Ollama 설정(A-15) 11장
RAG_MIN_SCORE 근거로 쓸 검색 결과의 최소 유사도 11장

A-14-3. 값을 주는 두 자리와 우선순위

두 변수는 .env에 적어 두거나, 명령 앞에 붙여 그 명령에만 줄 수 있다. 키트의 코드는 python-dotenv로 .env를 읽되 이미 설정된 환경 변수는 덮어쓰지 않는다. 그래서 명령 앞에 붙인 값이 .env의 값보다 앞선다.

자리 쓰는 법 적용 범위
명령 앞 LLM_FAKE=0 ~/llm-service-lab/.venv/bin/python ... 그 명령 한 번
export export LLM_FAKE=1 그 터미널을 닫을 때까지
.env LLM_FAKE=1 한 줄 그 폴더에서 실행하는 키트 코드

다음은 .env에 LLM_FAKE=1을 두고, 같은 확인 코드를 그대로 실행한 결과와 명령 앞에 LLM_FAKE=0을 붙여 실행한 결과이다(2026-11-14, 10장 키트와 같은 python-dotenv 1.2.4).

$ python check_env.py
LLM_FAKE = 1
$ LLM_FAKE=0 python check_env.py
LLM_FAKE = 0

export로 바꾼 값은 잊기 쉽다. 터미널을 오래 쓴 뒤 결과가 이상하면 echo "$LLM_FAKE"로 지금 값을 확인한다. 값을 지우려면 unset LLM_FAKE를 실행한다.

A-14-4. 실제 호출의 순서

실제 모델을 부르는 확인은 교수 시연이 기본이다. 학생은 교수가 배포한 실행 기록으로 같은 확인을 한다. 키를 받은 학생이 직접 실제 호출을 해 볼 때는 장의 확인 단계에서만 하고, 순서는 다음과 같다.

  1. 모의 모드로 테스트가 모두 통과하는지 본다.
서버 터미널 
cd ~/llm-service-lab/jobprep
LLM_FAKE=1 ~/llm-service-lab/.venv/bin/python -m pytest -q
  1. .env에 키(A-13)와 LLM_MODEL이 들어 있는지 본다.
  2. 그 장이 안내하는 명령 하나만 LLM_FAKE=0을 붙여 실행한다. 반복문이나 테스트 전체를 실제 호출로 돌리지 않는다.
  3. 응답을 확인했으면 모의 모드로 돌아온다. .env의 LLM_FAKE=1은 바꾸지 않는다.

실제 호출이 실패하면 API는 HTTP 상태 코드와 오류 종류(type)를 JSON으로 돌려준다[A1]. 대표적인 것은 다음과 같다. 오류 메시지 전체를 Claude Code에 붙여 넣을 때는 키가 섞여 있지 않은지 먼저 본다.

상태 코드와 종류 흔한 원인 조치
401 authentication_error 키가 비었거나, 잘못 붙여 넣었거나, 폐기되었다. 앞뒤에 공백이나 따옴표가 있다 .env의 줄을 다시 확인한다(A-13). 계속되면 교수에게 알린다

403 permission_error 키가 그 자원(모델 등)을 쓸 권한이 없다 교수에게 알린다
404 not_found_error 요청한 자원이 없다. LLM_MODEL의 이름이 틀린 경우가 흔하다 수업에서 안내한 이름을 그대로 넣는다
429 rate_limit_error 속도 제한이나 지출 상한에 닿았다 잠시 뒤 다시 한다. 계속되면 모의 모드로 진행한다
529 overloaded_error API가 일시적으로 과부하이다 잠시 뒤 다시 한다
연결 시간 초과 서버의 네트워크 문제 모의 모드로 진행하고 교수에게 알린다

A-15. 로컬 임베딩과 대체 구현

11장의 RAG 기능은 문서와 질문을 숫자 벡터로 바꾸는 임베딩(embedding)을 쓴다. 이 과목은 2026년 2학기처럼 실습 서버에서 돌아가는 Ollama의 로컬 임베딩 모델을 쓴다. 로컬 임베딩은 외부 API를 부르지 않으므로 키와 비용이 들지 않는다. Ollama는 서버의 11434 포트에서 HTTP API를 제공하고, 임베딩은 /api/embed 주소로 요청한다[O1].

서버에 Ollama가 있는지, 쓸 모델이 받아져 있는지는 다음으로 확인한다.

서버 터미널 
curl -s http://localhost:11434/api/tags | head -c 300; echo
{"models":[{"name":"모델이름:latest", ...}]}

모델 목록(JSON)이 나오면 Ollama가 동작하는 것이다. Connection refused가 나오거나 아무것도 나오지 않으면 Ollama가 없거나 꺼진 것이다.

Ollama를 쓸 수 없으면 키트의 대체 구현으로 진행한다. 대체 구현은 외부 모델 없이 문자 단위의 n-gram 같은 단순한 방법으로 벡터를 만든다. 검색은 되지만 의미가 비슷한 다른 표현은 잘 찾지 못하므로, 유사도 값과 재현율은 참고용으로만 본다. 11장 키트는 다음 환경 변수로 둘을 고른다. 값은 jobprep/.env에 두거나 명령 앞에 붙인다(A-14-3).

변수 뜻 값
EMBED_BACKEND 임베딩을 만드는 방법 auto(기본. Ollama를 먼저 시도하고 안 되면 대체 구현), ollama, fallback(대체 구현)
OLLAMA_URL Ollama 서버의 주소 기본 http://localhost:11434
EMBED_MODEL 임베딩 모델 이름 기본 nomic-embed-text. 수업에서 안내한 값으로 바꿀 수 있다
RAG_MIN_SCORE 근거로 쓸 검색 결과의 최소 유사도 11장에서 정한다
서버 터미널 
cd ~/llm-service-lab/jobprep
EMBED_BACKEND=fallback ~/llm-service-lab/.venv/bin/python -m pytest -q

확인 14 curl -s http://localhost:11434/api/tags가 모델 목록을 출력하거나, Ollama가 없으면 EMBED_BACKEND=fallback으로 11장 키트의 테스트가 통과한다(11장).

A-19. 개인 포트

8장부터는 서버에서 프로그램을 띄우고 브라우저로 접속한다. 8~9장은 정적 웹 화면을 보내는 python3 -m http.server를, 10~12장은 API 서버를 띄우는 uvicorn을 쓴다. 이런 서버 프로그램은 포트(port)라는 번호 하나를 차지하고 그 번호로 오는 요청을 기다린다. 한 컴퓨터에서 같은 번호를 두 프로그램이 함께 쓸 수는 없다.

실습 서버는 여러 학생이 함께 쓰므로, 모두가 기본값(8000)을 쓰면 두 번째 사람부터 실행이 실패한다. 다음은 같은 포트를 두 번 열었을 때 두 번째 명령이 내는 오류이다(2026-11-14, 리눅스의 파이썬에서 확인).

$ python3 -m http.server 8001 --bind 127.0.0.1
...
OSError: [Errno 98] Address already in use

그래서 이 과목은 학생마다 쓸 포트를 출석 번호로 정한다.

포트 번호 출석 번호 1번의 예 쓰는 곳
첫째 포트 8000 + 출석번호 (8001~8099) 8001 서버 프로그램을 하나만 띄울 때. 정적 웹 서버 또는 API 서버
둘째 포트 8100 + 출석번호 (8101~8199) 8101 서버 프로그램을 둘 함께 띄울 때의 두 번째(예: 화면을 보내는 정적 서버와 API 서버를 함께 띄운다)

본문의 명령은 출석 번호 1번의 8001과 8101로 적고 「부록 A의 자기 포트」라고 밝힌다. 명령을 입력할 때 이 두 숫자를 자기 번호로 바꾼다. 출석 번호 7번이면 8007과 8107이다.

서버 터미널 
cd ~/llm-service-lab
python3 -m http.server 8001 --bind 127.0.0.1
Serving HTTP on 127.0.0.1 port 8001 (http://127.0.0.1:8001/) ...
  • --bind 127.0.0.1은 서버 안에서만 접속을 받게 한다. 서버 밖의 네트워크에서 내 화면에 들어오지 못한다. uvicorn은 --host를 주지 않으면 처음부터 127.0.0.1에서만 받으므로 --port 8001만 붙인다(10장).
  • 서버가 도는 동안 그 터미널은 다른 명령을 받지 않는다. 멈출 때는 Ctrl+C를 누른다. 멈추지 않고 터미널만 닫으면 프로그램이 남아 포트를 계속 차지할 수 있다.
  • 내 PC의 브라우저로 보려면 VS Code의 포트 전달(port forwarding)을 쓴다. 명령 팔레트에서 Forward a Port를 고르거나 터미널 패널의 Ports 탭에서 「Add Port」를 눌러 자기 포트를 넣으면, VS Code가 내 PC에서 열 주소(localhost:번호)를 알려 준다[V1]. 서버 없이 내 PC에서 하는 경우(A-16)에는 이 단계 없이 http://127.0.0.1:번호/를 연다.
  • 내 포트를 다른 프로그램이 이미 쓰는지는 ss -ltn | grep ":8001 "로 본다. 한 줄이 나오면 쓰이는 중이다. 내가 띄운 것을 잊었으면 그 터미널을 찾아 Ctrl+C를 누르고, 남이 내 번호를 쓰고 있으면 교수에게 알린다.

확인 17 자기 첫째 포트로 python3 -m http.server를 띄웠을 때 Serving HTTP on 127.0.0.1 port 자기포트가 나오고, VS Code의 Ports 탭에 그 번호가 보인다.

A-20. 서버에서 쓰는 브라우저 검사 도구(Playwright)

9장은 Playwright로 브라우저를 프로그램이 조작하게 해서, 만든 화면이 인수 조건을 지키는지 검사한다. Playwright는 파이썬 꾸러미와 별도로 브라우저 파일을 내려받아 쓴다[PW1]. 실습 서버에서 쓸 때는 다음을 지킨다.

  1. 설치 자리. 꾸러미는 개인 실습 저장소의 가상 환경(A-12)에 9장 키트의 requirements.txt로 설치하고, 브라우저는 같은 가상 환경의 파이썬으로 받는다. 다른 파이썬으로 받으면 판이 맞지 않아 Executable doesn't exist 오류가 난다.
서버 터미널 
cd ~/llm-service-lab
.venv/bin/python -m pip install -r 「9장 키트가 안내하는 requirements.txt」
.venv/bin/python -m playwright install --only-shell chromium
  1. 화면 없이 실행한다. 서버에는 화면이 없으므로 브라우저를 창 없이(headless) 띄운다. Playwright의 파이썬 안내는 테스트가 기본적으로 headless로 돌아 브라우저 창이 열리지 않는다고 밝힌다[PW2]. 검사 코드에서 headless=False로 바꾸지 않는다. --only-shell은 headless에서만 쓰는 Chromium을 받게 하여, 전체 Chromium을 받지 않아도 되게 한다[PW1].
  2. 용량. 브라우저 파일은 리눅스에서 ~/.cache/ms-playwright에 놓인다[PW1]. 집필할 때 잰 크기는 headless 전용 Chromium이 약 278MB, 전체 Chromium이 약 437MB였다(Windows, Playwright 1.64.0, 9장의 측정). 홈 폴더에 용량 한도가 있으면 받기 전에 du -sh ~/.cache/ms-playwright와 df -h ~로 남은 자리를 본다. 다른 Playwright 판을 설치했다가 지우면, 어느 설치도 쓰지 않는 판의 브라우저는 자동으로 지워진다[PW1].
  3. 시스템 라이브러리는 학생이 설치하지 않는다. 리눅스에서 브라우저가 돌려면 운영체제의 라이브러리가 필요하다. Playwright는 이를 설치하는 playwright install-deps를 제공하지만[PW1], 이 명령은 운영체제의 꾸러미를 설치하므로 관리자 권한이 있어야 하고 학생 계정으로는 실행할 수 없다. 교수가 학기 전에 서버에 갖추어 둔다.
  4. 지원 운영체제. Playwright 공식 안내의 시스템 요구 사항은 리눅스로 Debian 12·13과 Ubuntu 22.04·24.04·26.04를 든다[PW2]. 2026년 2학기의 실습 서버(Rocky Linux 9)는 이 목록에 없으므로, 서버에서 브라우저가 뜨는지는 학기 전에 교수가 확인한다. 서버에서 브라우저 검사가 돌지 않으면 브라우저 검사만 내 PC(A-16)에서 실행하고, 나머지 실습은 서버에서 계속한다.

확인 18 ~/llm-service-lab/.venv/bin/python -c "import playwright; print('ok')"가 ok를 출력하고, ls ~/.cache/ms-playwright에 chromium_headless_shell-로 시작하는 폴더가 있다(9장).
