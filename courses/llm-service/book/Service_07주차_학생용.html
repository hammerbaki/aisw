[7주차] 사용자 경험 설계: 사용자 여정과 정보 구조

7주차

사용자 경험 설계: 사용자 여정과 정보 구조

2027학년도 「LLM 서비스 개발」의 준비 중인 교재입니다. 편집 상태를 검토하기 위해 미리 공개한 것으로, 수업 전에 내용과 순서가 바뀔 수 있습니다.

학사 9주차 · 교재 07 · 3부 설계

6장에서 공통 사례 「취업 준비 지원 서비스」(이하 jobprep)의 요구사항 명세서 v1을 EARS 문형으로 썼다. 명세서 v1은 시스템이 무엇을 해야 하는가를 요구 하나하나의 문장으로 고정한 문서이다. 그러나 요구 문장을 모두 모아도 사용자가 그 기능들을 어떤 순서로 만나고, 어디에서 찾고, 일이 잘못되었을 때 어디로 돌아가는지는 드러나지 않는다. 요구 23개가 빠짐없이 구현된 서비스라도 사용자가 원하는 기능을 찾지 못하거나, 오류가 난 뒤 갈 곳이 없으면 쓰이지 않는다.

이 장은 요구와 화면 사이의 이 빈자리를 설계한다. 5장의 페르소나 한 명이 서비스 밖에서 겪는 과정을 사용자 여정 지도로 그리고, 서비스 안의 기능과 콘텐츠를 사이트맵으로 조직하고, 핵심 과업 두 개를 예외 흐름까지 포함한 사용자 흐름도로 그린다. 그리고 그 결과를 명세서에 되돌려 넣는다. 명세서 v2에는 화면 목록이 생기고, 화면마다 그 화면이 충족하는 요구 ID가 붙는다. 흐름을 그리는 과정에서 v1이 정하지 않은 동작(예: 사용 한도를 넘었을 때)이 드러나면 요구를 추가한다.

이 장에서 만드는 것은 하나의 설계 문서 묶음이다. 여정 지도(여정지도.md), 정보 구조(정보구조.md), 사용자 흐름(사용자흐름.md), 그리고 화면 목록이 추가된 명세서 v2이다. 그림은 모두 mermaid로 그려 저장소에 텍스트로 남기고, 화면 ID와 요구 ID의 연결은 키트의 검사 스크립트로 확인한다. 마지막으로 설계 문서를 팀 실습 저장소에 풀 리퀘스트로 올려 동료 한 명 이상에게 리뷰를 받는다.

8장은 이 장의 화면 목록과 흐름으로 화면 명세와 HTML 프로토타입을 만든다. 프로젝트실습Ⅰ에서 팀의 주제로 설계할 때도 이 장의 양식과 검사 스크립트를 그대로 쓸 수 있다.

학습 목표

  • 사용자 여정 지도와 서비스 블루프린트를 구분하고 작성한다. 여정 지도는 사용자의 행동, 생각, 감정, 접점을 단계별로 적고, 블루프린트는 그 뒤에서 일어나는 서비스의 후면 과정을 적는다.
    • 예시: 페르소나 PS-1(서지후)이 공고를 찾아 지원하기까지 네 단계의 여정 지도를 그리고, 「공고 요약」 단계의 후면 과정(LLM 호출, 결과 검증, 실패 처리)을 블루프린트로 펼친다.
    • 활용: 프로젝트실습Ⅰ의 팀 주제에서 어느 단계에 기능을 넣을지 정할 때 근거가 된다.
  • 정보 구조의 네 요소로 서비스의 구조를 설계하고 카드 소팅과 트리 테스트로 점검한다. 조직 체계, 레이블, 내비게이션, 검색을 정하고 사이트맵으로 그린다.
    • 예시: 카드 26장을 짝과 개방형으로 분류한 결과로 전역 메뉴의 레이블을 고친다.
    • 활용: 메뉴 이름을 개발자의 말이 아니라 사용자의 말로 정하는 근거를 남긴다.
  • 핵심 과업의 사용자 흐름을 예외 흐름까지 포함해 mermaid로 그린다. 빈 결과, 오류, 권한의 세 가지 예외를 흐름 안에 둔다.
    • 예시: 「자기소개서 피드백 받기」 흐름에 외부 전송 동의가 없을 때와 사용 한도를 넘었을 때의 갈래를 그린다.
    • 활용: 9~11장에서 구현할 때 예외 화면을 빠뜨리지 않는 점검표가 된다.
  • 설계를 명세로 옮기고 그 연결을 검사한다. 명세서 v2에 화면 목록과 흐름을 추가하고, 화면 ID와 요구 ID가 서로 맞는지 스크립트로 확인한 뒤 풀 리퀘스트로 리뷰받는다.
    • 예시: check_design.py가 사이트맵에만 있고 화면 목록에는 없는 화면을 오류로 알린다.
    • 활용: 명세와 설계가 어긋나는 것을 구현 전에 찾는다.

0. 시작하기

접속, Claude Code 로그인, 개인 실습 저장소의 위치는 부록 A를 따른다. 이 절에서는 키트를 받고, 앞 장의 산출물을 확인하고, 이 장의 폴더를 만든다.

0-1. 키트 받기

키트는 배포 폴더 $KIT_HOME에 있다. 다른 장과 같이 저장소 밖의 ~/kits/에 받아 두고, 이 장에서 필요한 파일만 저장소로 복사한다(0-2, 0-3).

서버 터미널 
cd ~/llm-service-lab
git status --short
git pull
mkdir -p ~/kits
cp -rn "$KIT_HOME/Service_07주차" ~/kits/
ls ~/kits/Service_07주차
README.md  check_design.py  requirements.txt  tests  견본  기준산출물
리뷰점검표_양식.md  여정지도_양식.md  카드목록.md  카드소팅기록_양식.md
  • git status --short가 아무것도 출력하지 않으면 커밋하지 않은 변경이 없는 상태이다. 무언가 출력되면 6장의 작업을 먼저 커밋한다.
  • mkdir -p ~/kits를 먼저 하는 까닭은 6장 0-1과 같다. ~/kits가 없을 때 바로 복사하면 ~/kits 자체가 키트 폴더가 된다.
  • -n은 이미 있는 파일을 덮어쓰지 않는다. 작업 중에 키트를 다시 받아도 고친 파일이 지워지지 않는다.

확인 1 ls ~/kits/Service_07주차의 출력에 check_design.py와 여정지도_양식.md가 있다.

0-2. 앞 장 산출물의 확인

이 장은 두 가지를 받는다. 6장의 요구사항 명세서 v1과 5장의 페르소나이다. 명세서는 6장에서 spec-v1 태그를 붙여 두었다.

서버 터미널 
cd ~/llm-service-lab
ls jobprep/docs/요구사항명세서.md ch05/페르소나.md
git tag --list "spec-*"
grep -c "REQ-" jobprep/docs/요구사항명세서.md
ch05/페르소나.md  jobprep/docs/요구사항명세서.md
spec-v1
27

grep -c는 REQ-가 들어 있는 줄의 수를 센다. 숫자는 명세서마다 다르다. 0이면 요구 ID가 없는 것이므로 6장의 명세서를 다시 확인한다.

두 파일 가운데 하나라도 없으면 키트의 기준 산출물을 복사한다. 자기 산출물이 있으면 이 단계를 건너뛴다.

서버 터미널 
cd ~/llm-service-lab
mkdir -p ch05/기록 jobprep/docs
cp -n ~/kits/Service_07주차/기준산출물/ch05/*.md ch05/
cp -n ~/kits/Service_07주차/기준산출물/ch05/기록/*.md ch05/기록/
cp -n ~/kits/Service_07주차/기준산출물/jobprep/CLAUDE.md jobprep/
cp -n ~/kits/Service_07주차/기준산출물/jobprep/docs/*.md jobprep/docs/

기준 산출물은 5장과 6장의 견본이다. 페르소나는 5장의 수업용 예시 기록 네 편(가상의 기록)에서 만든 연습용이며, 모든 주장 끝에 [인터뷰_예시_01:L12]처럼 근거가 된 기록의 파일 이름과 줄 꼬리표가 붙어 있다. 이 장의 여정 지도도 같은 방식으로 근거를 단다.

이 장의 본문은 기준 산출물의 요구 ID(REQ-001~REQ-023)와 페르소나(PS-1 서지후, PS-2 임하람)로 설명한다. 자기 명세서를 쓰는 학습자는 요구 ID를 자기 명세서의 것으로 바꾸어 읽는다.

확인 2 ch05/페르소나.md와 jobprep/docs/요구사항명세서.md가 모두 있고, 명세서에 REQ-로 시작하는 요구 ID가 있다.

0-3. 이 장의 폴더

설계 문서는 jobprep의 문서 폴더 아래 설계/에 둔다. 카드 소팅 기록은 장 폴더에 둔다. 공통 사례의 산출물(jobprep)과 수업 활동의 기록(chNN)을 나누기 위해서이다.

서버 터미널 
cd ~/llm-service-lab
mkdir -p jobprep/docs/설계 ch07/카드소팅 ch07/기준자료
cp -rn ~/kits/Service_07주차/기준산출물/ch05/. ch07/기준자료/
tree -L 2 jobprep ch07 2>/dev/null || find jobprep ch07 -maxdepth 2
jobprep
├── CLAUDE.md
└── docs
    ├── 설계
    ├── 요구사항명세서.md
    └── 추적표.md
ch07
├── 기준자료
│   ├── 기록
│   ├── 문제정의.md
│   ├── 친화도.md
│   └── 페르소나.md

1. 사용자 경험과 인간 중심 설계

1-1. 사용자 경험의 정의

사용자 경험(user experience, UX)은 일상에서 “쓰기 편한 화면” 정도의 뜻으로 쓰이지만, 표준은 이보다 넓게 정의한다. ISO 9241-210:2019는 사용자 경험을 시스템, 제품, 서비스의 사용 또는 예상된 사용에서 비롯되는 사용자의 지각과 반응으로 정의하고, 그 감정, 믿음, 선호, 행동, 성취가 사용 전, 사용 중, 사용 후에 걸쳐 일어난다고 주석을 단다[X1]. 지인의 추천이나 첫 화면의 인상처럼 서비스를 쓰기 전의 일도 경험의 일부이다.

같은 표준은 사용자 경험이 시스템의 표현, 기능, 성능, 상호작용 방식, 보조 기능에서 비롯될 뿐 아니라, 사용자의 이전 경험, 태도, 기술, 습관, 성격에서도 비롯된다고 설명한다[X1]. 그러므로 같은 화면이라도 사용자에 따라 경험이 다르다. 5장에서 페르소나를 만든 까닭이 여기에 있다. 설계는 “사용자 일반”이 아니라 특정한 사용자, 특정한 목표, 특정한 상황을 대상으로 한다.

사용성(usability)은 사용자 경험과 자주 섞여 쓰이지만 범위가 다르다.

구분 사용성 사용자 경험
정의(ISO 9241-210이 인용하는 ISO 9241-11:2018) 특정 사용자가 특정 사용 맥락에서 특정 목표를 효과성, 효율성, 만족을 가지고 달성할 수 있는 정도 사용 또는 예상된 사용에서 비롯되는 지각과 반응
시점 주로 사용하는 동안 사용 전, 사용 중, 사용 후
재는 방법 과업 성공률, 걸린 시간, 오류 수, 만족 설문 위의 것에 더해 기대, 신뢰, 감정의 변화
이 과목에서 다루는 장 13장(사용성 평가) 7장(여정, 구조, 흐름), 8장(화면), 13장

표준은 “사용성은 쓰기 쉽게 만드는 것일 뿐”이라는 생각을 흔한 오해로 꼽는다[X1]. 이 장에서 다루는 여정과 구조는 화면 하나의 편리함보다 넓은 범위, 즉 사용자가 목표를 이루기까지 거치는 전체 과정을 대상으로 한다.

사용 맥락(context of use). ISO 9241-210은 사용 맥락을 사용자, 목표와 과업, 자원, 환경의 조합으로 정의하고, 환경에는 기술적, 물리적, 사회적, 문화적, 조직적 환경이 모두 들어간다고 적는다[X1]. jobprep의 페르소나 PS-1(서지후)은 아르바이트와 과제를 마친 밤늦게, 잠들기 전에 휴대폰으로 공고를 훑어본다[인터뷰_예시_01:L3]. 이 사실은 화면의 크기(기술적 환경), 하루 일과를 마친 피곤한 상태(물리적 환경), 짧게 끊기는 시간(과업의 조건)을 동시에 알려 준다. 사용 맥락을 적지 않은 설계는 넓은 모니터 앞에 앉은 개발자 자신을 사용자로 가정하게 된다.

1-2. 사용자 경험의 다섯 층위

제시 제임스 개릿(Jesse James Garrett)은 2000년에 사용자 경험을 이루는 요소를 한 장의 그림으로 정리하였고, 2002년에 같은 이름의 책 『The Elements of User Experience』로 펴냈다[X2]. 그는 사용자 경험의 결정을 추상적인 것에서 구체적인 것으로 쌓이는 다섯 층위(plane)로 나누었다.

층위 (아래에서 위로) 정하는 것 jobprep에서의 예 이 과목의 장
전략(strategy) 서비스의 목표와 사용자의 요구 흩어진 공고를 한곳에서 보고 마감을 놓치지 않게 한다(P-01) 4장, 5장
범위(scope) 기능 명세와 콘텐츠 요구 REQ-001~REQ-023 6장
구조(structure) 상호작용 설계와 정보 구조 사이트맵, 사용자 흐름 7장
골격(skeleton) 인터페이스 설계, 내비게이션 설계, 정보 설계 화면의 배치, 메뉴의 위치, 와이어프레임 8장
표면(surface) 시각 설계 색, 글꼴, 간격, 아이콘 8장

이 표에서 층위와 각 층위가 정하는 것은 개릿의 책의 장 구성에서 확인한 것이다[X2]. 「이 과목의 장」 열은 이 교재가 대응시킨 것이다.

다섯 층위에서 두 가지를 읽을 수 있다.

  1. 아래 층위가 위 층위의 선택지를 정한다. 범위에 없는 기능은 구조에 넣을 수 없고, 구조에 없는 화면은 골격을 가질 수 없다. 이것이 명세 주도 개발(SDD)에서 “명세에 없는 것은 만들지 않는다”는 원칙과 같은 방향이다.
  2. 위 층위에서 아래 층위의 빈틈이 드러난다. 흐름을 그리다가(구조) 명세에 없는 동작을 발견하면(범위) 명세를 고친다. 그러므로 층위는 한 번씩 차례로 끝내는 단계가 아니라, 아래에서 위로 쌓되 위에서 발견한 것을 아래로 되돌리는 관계로 보는 것이 실무에 맞다. 이 장에서 명세서를 v2로 올리는 일이 이 되먹임에 해당한다.

7장은 다섯 층위 가운데 구조 층위를 맡는다. 구조 층위의 두 작업, 상호작용 설계(사용자가 어떤 순서로 무엇을 하고 시스템이 어떻게 반응하는가)와 정보 구조(기능과 콘텐츠를 어떻게 나누고 이름 붙이는가)가 이 장의 5~7절에 대응한다.

1-3. 인간 중심 설계의 원칙과 활동

ISO 9241-210은 인간 중심 설계(human-centred design)를 시스템의 사용에 초점을 맞추고 인간 공학과 사용성의 지식과 기법을 적용해 상호작용 시스템을 더 쓸 만하게 만드는 설계와 개발의 접근 방식으로 정의한다[X1]. 표준은 “사용자 중심 설계”라는 말 대신 “인간 중심 설계”를 쓰는데, 사용자뿐 아니라 시스템의 영향을 받는 다른 이해관계자까지 고려한다는 뜻을 담기 위해서라고 밝힌다[X1].

표준은 어떤 설계 과정을 쓰든 인간 중심 접근이라면 지켜야 할 여섯 원칙을 든다[X1]. 괄호 안은 이 과목에서 그 원칙을 지키는 자리이다.

  1. 설계는 사용자, 과업, 환경에 대한 명시적 이해에 근거한다(5장의 페르소나, 이 장의 여정 지도).
  2. 사용자가 설계와 개발 전체에 참여한다(6절의 카드 소팅과 트리 테스트, 13장).
  3. 사용자 중심 평가가 설계를 이끌고 다듬는다(13장).
  4. 과정은 반복적이다(명세서 v1 → v2 → …).
  5. 설계는 사용자 경험 전체를 다룬다(여정 지도의 서비스 밖 단계).
  6. 설계 팀에 여러 분야의 기술과 관점이 있다(9절의 동료 리뷰).

표준은 반복의 원칙을 설명하면서, 상호작용의 모든 세부를 개발 초기에 완전하고 정확하게 명세하는 것은 불가능하다고 적는다[X1]. 사용자의 요구 가운데 상당수는 사용자가 실제 해결안을 보고 반응할 때에야 드러나기 때문이다. 이 장에서 흐름을 그리며 명세서를 고치는 일과 8장에서 프로토타입을 보며 명세를 다시 고치는 일이 모두 이 원칙의 적용이다.

표준은 원칙에 이어 인간 중심 설계의 활동을 넷으로 나눈다[X1].

flowchart LR
    P(["인간 중심 설계의 계획"]) --> A1["사용 맥락의 이해와 명시"]
    A1 --> A2["사용자 요구의 명시"]
    A2 --> A3["설계 해결안의 작성"]
    A3 --> A4["요구에 대한 설계의 평가"]
    A4 -- 요구를 충족함 --> F(["설계 해결안이 요구를 충족"])
    A4 -- 반복 --> A1
    A4 -- 반복 --> A2
    A4 -- 반복 --> A3

네 활동은 표준의 7.2~7.5절이며, 이 과목에서는 각각 4~5장(조사와 페르소나), 6~7장(명세서 v1, v2), 7~8장(여정 지도, 사이트맵, 흐름, 화면 명세, 프로토타입), 7장의 트리 테스트와 13장(사용성 평가)에 대응한다. 그림의 활동 이름과 절 번호는 표준의 목차에서 확인한 것이고[X1], 화살표 배치는 이 교재가 단순화한 것이며 표준의 그림을 옮긴 것이 아니다. 표준의 7.4절은 설계 해결안을 만들 때 사용자의 과업, 사용자와 시스템의 상호작용, 사용자 인터페이스를 사용자 경험 전체를 고려해 설계하라고 하고, 설계 해결안을 구현할 사람에게 전달하는 일까지 이 활동에 넣는다[X1]. 이 장의 마지막에 설계를 명세서로 옮기고 리뷰받는 일이 바로 그 전달에 해당한다.

2. 사용자 여정 지도

2-1. 여정 지도란 무엇인가

사용자 여정 지도(user journey map, customer journey map)는 한 사람이 목표를 이루기 위해 거치는 과정을 시각화한 것이다[N1]. 여정 지도는 시간 순서로 늘어선 단계 위에 사용자의 행동, 생각, 감정을 적어 하나의 이야기로 만든다. NN/g는 여정 지도의 구성 요소를 다섯 가지로 든다[N1].

구성 요소 뜻 jobprep의 예 (PS-1)
행위자(actor) 지도의 주인공. 한 지도에 한 관점을 둔다 서지후(PS-1)
시나리오와 기대 지도가 다루는 상황과 그 상황에서 행위자가 바라는 것 공고를 찾아 첫 지원서를 제출하기까지. 마감을 놓치지 않기를 바란다
여정 단계 지도를 나누는 큰 구간. 시나리오마다 다르다 공고 탐색, 지원 판단, 일정 관리, 지원서 제출
행동, 생각, 감정 단계마다 하는 일, 머릿속의 질문, 기분의 높낮이 관심 공고로 저장한다 / “본 건지 안 본 건지” / 감정 -2
기회 경험을 개선할 수 있는 지점과 그 책임 공고를 한 목록에 모은다 → REQ-002

이 다섯 가지에 더해, 이 교재는 두 행을 더 둔다. 접점(touchpoint) 은 사용자가 서비스나 조직과 만나는 지점(앱, 웹 사이트, 대화방, 사람, 문서)이다. 불편(pain point) 은 그 단계에서 사용자가 막히거나 화가 나는 지점이다. 접점은 3절의 서비스 블루프린트에서 「증거」가 되고, 불편은 「기회」의 출발점이 된다.

NN/g는 여정 지도가 사건의 연쇄, 시간에 걸쳐 펼쳐지는 과정, 여러 채널이 관여하는 시나리오에 가장 잘 맞는다고 본다[N1]. 두 주에 걸쳐 여러 앱과 사이트를 오가는 「공고를 찾아 지원하기」는 여정 지도가 맞고, 몇 분 안에 한 화면에서 끝나는 「검색 결과 보기」는 7절의 사용자 흐름도가 맞는다.

2-2. 여정 지도와 비슷한 지도들

UX 설계에서 쓰는 지도는 여럿이다. 이름이 비슷해 섞어 쓰기 쉬우므로 범위로 구분해 둔다[N3][N1].

지도 범위 초점 이 과목에서
공감 지도(empathy map) 한 사용자 유형의 마음가짐. 시간 순서가 없다 말하는 것, 생각하는 것, 느끼는 것, 하는 것 5장
사용자 여정 지도 특정 제품이나 서비스와 관련된 한 행위자의 과정 목표, 행동, 생각, 감정의 시간 순 변화 이 장 2절
서비스 블루프린트 특정 여정을 뒷받침하는 서비스 제공자 쪽 접점 뒤의 사람, 증거, 과정 이 장 3절
사용자 스토리 지도(user-story map) 구현할 기능의 묶음과 출시 계획 무엇을 어느 출시에 넣는가 다루지 않음
사용자 흐름도(user flow) 한 제품 안에서 한 과업의 단계 사용자의 행동과 시스템의 반응 이 장 7절

NN/g는 여정 지도가 발견과 이해를 돕고, 사용자 스토리 지도는 계획을 돕는다고 구분한다[N1]. 여정 지도에서 찾은 기회를 무엇부터 구현할지는 여정 지도가 아니라 명세서와 작업 계획이 정한다.

2-3. 지도의 범위 정하기

여정 지도를 그리기 전에 세 가지를 정한다. 이 셋이 흐리면 지도는 모든 것을 담으려다 아무것도 보여 주지 못한다.

  1. 행위자 한 명. 한 지도에는 한 관점만 둔다[N1]. PS-1과 PS-2를 한 지도에 섞으면, 같은 단계에서 한 사람은 기쁘고 한 사람은 화가 나는 칸이 생겨 감정 곡선이 의미를 잃는다.
  2. 시나리오 하나와 그 끝. 시나리오는 시작과 끝이 분명해야 한다. 「취업 준비」는 시나리오가 아니라 삶의 한 시기이다. 「개발 직무 공고를 찾아 첫 지원서를 제출하기까지」는 시작(공고 탐색을 시작함)과 끝(제출함)이 있다.
  3. 현재 여정인가, 미래 여정인가. 현재 여정(current-state)은 서비스가 없는 지금 사용자가 겪는 과정이고, 미래 여정(future-state)은 서비스가 생긴 뒤에 기대하는 과정이다. NN/g는 시나리오가 기존 경험일 수도 있고 아직 설계 중인 제품의 예상 경험일 수도 있다고 본다[N1]. 이 장에서는 현재 여정을 그리고 미래의 모습은 「기회」 행에 적는다. 현재 여정이 근거(인터뷰)를 가질 수 있는 반면, 미래 여정은 아직 아무도 겪지 않은 것이어서 가정으로 채워지기 쉽기 때문이다.

GOV.UK 서비스 매뉴얼은 범위를 너무 넓게 잡으면 목적이 흐려지고 너무 좁게 잡으면 문제를 풀지 못하므로, 사용자의 전체 목표로 시야를 넓힌 뒤 하위 과업으로 나누라고 하며 그 도구로 여정 지도를 권한다[V2]. 같은 매뉴얼의 서비스 표준 2항은 기술이나 미리 정한 해결책(생성형 AI 포함)이 아니라 사용자의 요구를 중심으로 설계하라고 요구한다[V1]. 「LLM으로 공고를 요약한다」는 해결책이고, 「지원 가능한지 빨리 판단하고 싶다」가 요구이다.

2-4. 가설 지도와 조사 기반 지도

여정 지도는 조사 자료에서 그려야 하지만, 실제로는 팀이 알고 있다고 믿는 것에서 먼저 그려지는 일이 많다. NN/g는 여정 지도를 만드는 과정을 다섯 단계로 정리하면서 이 차이를 분명히 한다[N2]. 괄호 안은 이 과목에서 그 단계에 해당하는 일이다.

  1. 목표와 협력자: 핵심 팀을 꾸리고 누구의 어떤 여정인지 범위를 정한다(2-3의 세 가지).
  2. 내부 조사: 조직 안에 이미 있는 자료와 직원 인터뷰를 모은다(4장의 조사 보고).
  3. 가정 세우기: 내부 자료로 현재 여정의 가설 지도를 그리고 조사 계획을 세운다(2-6의 Claude Code 초안).
  4. 외부 조사: 사용자에게서 새 자료를 모아 가설 지도를 확인하거나 반박한다(5장의 인터뷰 기록).
  5. 이야기로 시각화: 새 자료로 가설 지도를 고치고 핵심 순간을 시각적 이야기로 만든다(2-5의 작성).

NN/g는 가설 지도(hypothesis map)가 어디에 자료가 없는지를 보여 주는 초안일 뿐이며, 최종 지도는 내부의 가정이 아니라 사용자 조사에 근거해야 한다고 강조한다[N2]. 이 장의 여정 지도는 칸마다 근거 표시를 붙여 이 구분을 문서 안에 남긴다.

  • [근거: 인터뷰_예시_01:L13]: 그 칸의 내용이 기록 인터뷰_예시_01.md의 L13 줄에 있다. 5장의 인용 형식 앞에 「근거:」를 붙인 꼴이다.
  • [가정]: 근거가 없고 설계자가 추정하였다. 가정은 지도의 끝에 「가정과 확인할 것」으로 모아 다음 조사의 질문이 된다.

근거 표시를 강제하는 까닭은 두 가지이다. 하나는 사람이 쓴 지도에도 기억과 추측이 섞이기 때문이다. 다른 하나는 2-6에서 다루듯 Claude Code가 그럴듯한 내용을 채워 넣기 때문이다. 근거 표시가 있으면 리뷰어가 무작위로 몇 칸을 골라 원 기록과 대조할 수 있다.

2-6. Claude Code로 만드는 여정 지도 초안과 근거 대조

여정 지도의 초안은 Claude Code에 맡길 수 있다. 인터뷰 기록과 페르소나를 읽고 단계를 나누어 표를 채우는 일은 언어 모델이 잘하는 일이다. 문제는 잘한다는 것이 “그럴듯하게 채운다”는 뜻이라는 데 있다. 기록에 없는 행동이나 감정이 매끄러운 문장으로 들어가면, 표만 보아서는 어느 칸이 근거 있는 칸인지 알 수 없다. 그래서 초안을 요청할 때 근거 표시를 의무로 걸고, 받은 뒤에는 사람이 대조한다.

Claude Code에서 @로 파일을 가리키면 그 파일의 내용이 대화에 들어간다[C1]. 연습에서는 기준 산출물의 페르소나와 인터뷰 기록을 @로 넘기고, 양식과 규칙을 함께 준다. 10절에서는 같은 프롬프트의 경로를 자기 페르소나와 기록으로 바꾸어 쓴다.

  1. 근거 표시가 없는 칸. 키트의 검사 스크립트는 여정 지도 표에서 근거 표시가 없는 칸을 경고로 알린다. 8절에서 스크립트 전체를 다루므로 여기서는 결과만 본다.
  2. 근거 표시가 있지만 그 줄에 그 내용이 없는 칸. 스크립트는 표시의 유무만 보고 내용은 보지 않는다. 사람이 무작위로 두세 칸을 골라 sed -n '줄p'로 원 기록을 연다.
  3. [가정] 칸의 처리. 가정은 지우거나, 「가정과 확인할 것」 표로 옮겨 다음 조사의 질문으로 만든다. 위 예시의 「동기들이 먼저 지원하는 것을 보고」는 서지후의 기록 어디에도 없는 내용이다. 페르소나 파일의 PS-2 공감 지도에 있는 다른 참여자의 말(인터뷰_예시_04)이 섞여 들어온 것으로 보인다. 그럴듯한 사연이 붙었기 때문에 오히려 의심해야 하는 칸이다.

2-7. 여정 지도에서 자주 생기는 문제

  • 행위자가 섞임. 같은 칸에 “어떤 학생은 …, 다른 학생은 …”이 있으면 페르소나마다 지도를 따로 그린다.
  • 단계가 화면 이름. 단계가 「홈」, 「목록」, 「상세」이면 목표의 변화로 다시 나눈다. 화면 단위는 사용자 흐름도의 일이다.
  • 서비스가 이미 있는 것처럼 씀. 현재 여정의 행동에 “jobprep에서 검색한다”가 있으면, 지금 쓰는 도구로 고쳐 쓰고 jobprep은 기회 행에만 쓴다.
  • 감정이 모두 중립. 감정 행이 0, 0, 0, 0이면 인터뷰의 「가장 좋았던 때와 나빴던 때」 질문의 답을 찾는다.
  • 기회가 해결책만 있음. “AI 챗봇을 넣는다”처럼 쓰지 말고, 불편을 먼저 쓴 뒤 그 불편을 푸는 방향과 요구 ID로 쓴다.
  • 근거가 페르소나 문서뿐. 페르소나도 요약이다. 가능한 한 원 기록의 줄을 가리킨다.

3. 서비스 블루프린트

3-1. 블루프린트의 요소와 선

여정 지도는 사용자의 눈으로 본 과정이다. 그러나 사용자가 「요약」 버튼을 누른 뒤 요약이 나타나기까지 서비스 안에서 무슨 일이 일어나는지는 여정 지도에 나오지 않는다. 서비스 블루프린트(service blueprint)는 특정 고객 여정의 접점에 사람, 물리적·디지털 증거, 과정이 어떻게 연결되는지를 나타낸 그림이다[N4]. NN/g는 블루프린트를 여정 지도의 “2부”라고 부른다[N4]. 여정 지도가 고객의 앞면을 그린다면, 블루프린트는 그 뒤의 운영을 그린다.

블루프린트의 요소는 다섯이다[N4].

요소 뜻 jobprep 「공고 요약」의 예
고객 행동 고객이 목표를 위해 하는 단계와 선택. 대개 조사나 여정 지도에서 가져온다 공고 상세를 연다, 「요약」을 누른다, 요약을 읽는다
전면 행동(frontstage) 고객이 볼 수 있는 활동. 사람과 사람, 또는 사람과 컴퓨터 사이에 일어난다 처리 중 표시, 요약 표시, 실패 안내
후면 행동(backstage) 전면을 뒷받침하지만 고객에게 보이지 않는 활동 요약 API가 프롬프트를 만들고 LLM을 부르고 결과를 검사한다
지원 과정(processes) 서비스를 제공하기 위해 조직 안에서 필요한 과정 공고 수집, 프롬프트 판본 관리, 사용 한도 관리, 호출 기록
증거(evidence) 블루프린트의 사람들이 마주하는 물건과 장소 공고 상세 화면, 「AI 요약」 표시, 근거 문장

블루프린트는 이 요소들을 세 개의 선으로 나눈다[N4].

  • 상호작용선(line of interaction): 고객과 조직이 직접 주고받는 지점을 나눈다.
  • 가시선(line of visibility): 선 위는 고객에게 보이는 활동, 선 아래는 보이지 않는 활동이다.
  • 내부 상호작용선(line of internal interaction): 고객을 직접 대하는 쪽과 그들을 간접적으로 지원하는 쪽을 나눈다.

NN/g는 블루프린트가 접점이 많고 여러 부서의 협력이 필요한 서비스에 맞으며, 나쁜 경험의 근본 원인과 놓치기 쉬운 의존 관계를 드러낸다고 본다[N4]. 작은 서비스라도 LLM 기능이 들어가면 화면(전면), API 서버(후면), 모델 제공자와 사용 한도(지원 과정)가 서로 다른 곳에 있고, 실패가 어느 층에서 생겼는지에 따라 사용자에게 보여 줄 안내가 달라진다.

3-2. 「공고 요약」의 블루프린트

PS-1의 여정 2단계 「지원 판단」에서 공고 요약 기능(REQ-013~REQ-016)이 쓰이는 장면을 블루프린트로 펼친다. 표의 열은 시간 순서이고, 행은 위에서 아래로 고객에게서 멀어진다.

층 ① 상세를 연다 ② 요약을 누른다 ③ 기다린다 ④ 요약을 읽는다
증거 공고 상세 화면(SCR-02) 「요약」 버튼 처리 중 표시 「AI 요약」 표시가 붙은 네 항목과 근거 문장
고객 행동 목록에서 공고를 고른다 버튼을 누른다 원문을 읽으며 기다린다 자격 요건, 근무 조건, 제출 서류, 마감일을 읽고 지원 여부를 정한다
─ 상호작용선 ─
전면 행동 상세를 그린다 버튼을 누를 수 없게 바꾼다 처리 중 표시를 보인다 요약을 그린다. 실패하면 실패 안내와 다시 시도
─ 가시선 ─
후면 행동 브라우저 저장소에서 공고를 읽는다 요약 API에 공고 본문을 보낸다 API가 프롬프트를 만들고 LLM을 부른다. 시간 제한을 잰다 응답이 정해진 형식(네 항목과 근거 문장)인지 검사한다
─ 내부 상호작용선 ─
지원 과정 공고 수집과 정리 사용 한도 확인 모델 제공자의 API, 프롬프트 판본 호출 기록(시각, 토큰 수, 성공 여부)

이 표를 그리면 여정 지도와 명세서에서 보이지 않던 것이 보인다.

  • ③의 시간 제한. 몇 초를 기다리면 실패로 볼 것인가는 사용자 경험의 결정이지만 후면에서 정해진다. 명세서 v1에는 이 값이 없다. 10장에서 API를 구현할 때 정할 값으로 기록해 둔다.
  • ②의 사용 한도. 사용 한도를 넘었을 때 무엇을 보여 줄지가 v1에 없다. 7절의 흐름에서 다시 만나고, 8절에서 요구(REQ-025)로 추가한다.
  • ④의 형식 검사. LLM의 응답이 네 항목의 형식을 지키지 않을 수 있다. 형식이 깨진 응답을 화면에 그대로 그리지 않고 실패로 처리하는 것은 후면의 일이지만, 사용자에게는 실패 안내로 보인다. v1에는 요약이 실패했을 때의 동작도 없으므로, 이것도 8절에서 요구(REQ-024)로 추가한다.
  • 증거의 「AI 요약」 표시. 1-4에서 본 대로 LLM의 결과는 원문과 다를 수 있다. 요약이 AI의 생성물이라는 표시와 원문 링크를 증거 행에 두는 것은 사용자가 결과를 얼마나 믿을지 스스로 판단하게 하는 장치이다.

3-3. 블루프린트에서 요구가 나오는 자리

블루프린트의 아래쪽 층은 주로 비기능 요구와 운영의 결정으로 이어진다. 기준 명세서와 맞대어 보면, 후면에서 자기소개서 본문을 보내는 일은 REQ-019(서버에 보관하지 않음)와 v1에 없는 전송 전 동의(8절에서 REQ-027로 추가)로, 형식 검사는 구조화 출력으로, 시간 제한은 아직 정하지 않은 기준 값으로 이어지며 모두 10장에서 구현한다. 지원 과정의 사용 한도는 7장에서 추가할 요구 후보(REQ-025)가 되고, 질의응답의 근거 문서는 REQ-020과 REQ-021로 11장에서 다룬다. 호출 기록은 REQ-019와 부딪칠 수 있다.

이 「부딪침」처럼, 블루프린트는 요구들이 서로 부딪치는 곳도 드러낸다. 호출 기록에 디버깅을 위해 요청 본문을 남기면 REQ-019(자기소개서 본문을 보관하지 않음)를 어기게 된다. 이런 충돌은 구현 중에 발견되면 고치기 어렵다. 설계 단계에서 기록해 두고 10장의 구현 지시에 넣는다.

4. 작업 분석

4-1. 목표, 과업, 하위 과업

여정 지도는 두 주에 걸친 과정을 다루지만, 화면을 설계하려면 그보다 훨씬 작은 단위가 필요하다. 사용자가 「지원 일정을 등록한다」는 한 문장 안에는 회사를 고르고, 전형 단계를 고르고, 날짜를 넣고, 저장하는 여러 동작이 들어 있다. 작업 분석(task analysis)은 사용자가 목표를 이루기 위해 과업을 어떻게 수행하는지를 체계적으로 연구하는 방법이다[N5].

작업 분석에서는 목표와 과업을 구분한다[N5]. 목표(goal)는 사용자가 이루려는 결과(예: 마감 전에 지원한다)이고, 과업(task)은 목표를 이루는 특정한 수단으로서 관찰할 수 있고 시작과 끝이 있는 활동(예: 지원 일정을 등록한다)이며, 하위 과업(subtask)은 과업을 이루는 더 작은 단계(예: 날짜를 입력한다)이다.

ISO 9241-210도 같은 구분을 한다. 과업은 특정 목표를 이루기 위해 하는 활동의 집합이며, 목표는 그것을 이루는 수단과 무관하지만 과업은 목표를 이루는 특정한 수단을 기술한다고 정의한다[X1]. 이 구분이 중요한 까닭은 같은 목표에 여러 과업이 있을 수 있기 때문이다. 「마감 전에 지원한다」는 목표는 달력 앱에 적는 과업으로도, 휴대전화 알람을 맞추는 과업으로도, jobprep에 일정을 등록하는 과업으로도 이룰 수 있다. 설계자는 과업이 아니라 목표에서 출발해야 더 짧은 과업을 설계할 수 있다.

4-2. 자료의 수집

NN/g는 작업 분석의 자료를 모으는 방법으로 맥락 질문(현장에서 인터뷰하고 관찰하기), 중요 사건 인터뷰, 일지나 추적 기록, 활동 표본 추출, 분석자가 직접 단계를 밟아 보는 모의 수행을 들고, 자기 보고나 모의 수행에만 기대지 말고 사용자를 자기 맥락에서 관찰하라고 권한다[N5].

이 과목에서 쓸 수 있는 자료는 5장의 인터뷰 기록이다. 인터뷰는 자기 보고이므로, 기록에서 관찰:로 표시한 줄(진행자가 직접 본 것)과 A:로 표시한 줄(참여자의 답)을 구분해 읽는다. 기준 산출물의 인터뷰_예시_01에는 참여자가 휴대폰의 채용 관련 즐겨찾기 다섯 개를 보여 준 것을 진행자가 직접 본 기록이 있다(L7). 같은 내용이라도 관찰은 말보다 강한 근거이다. 자료가 부족한 과업은 분석자가 직접 모의 수행해 단계를 센다. 다만 분석자는 사용자보다 그 앱에 익숙할 수 있으므로, 모의 수행의 결과는 단계의 목록으로만 쓰고 걸린 시간이나 어려움의 근거로는 쓰지 않는다.

4-3. 계층적 작업 분석

계층적 작업 분석(hierarchical task analysis, HTA)은 작업 분석의 결과를 그리는 가장 흔한 방식이다. 목표와 시나리오에서 시작해 주요 과업으로 나누고, 필요한 만큼 하위 과업으로 다시 나눈다[N5]. HTA는 과업을 어떤 순서와 조건으로 수행하는지를 「계획(plan)」으로 적을 수 있다. 계획은 초보자와 숙련자의 차이나 일부 사용자에게만 해당하는 단계(예: 비밀번호를 잊은 사용자만 거치는 재설정 단계)를 나타낸다[N5].

PS-1의 「지원 일정 등록」을 jobprep이 있다고 가정하고(미래 과업) 분석하면 다음과 같다.

5. 정보 구조

5-1. 정보 구조란 무엇인가

정보 구조(information architecture, IA)는 정보를 찾을 수 있고 이해할 수 있게 만드는 분야이다[I1]. NN/g의 카델로(Jen Cardello)는 정보 구조를 사이트의 정보 뼈대라고 부르고, 내비게이션은 사용자가 그 정보에 닿게 하는 화면 요소의 집합이라고 구분한다[N6]. 정보 구조는 화면에 직접 보이지 않으며 표와 그림으로 문서화되고, 그 문서가 화면을 만든다[N6]. 정보 구조를 바꾸면 여러 화면의 메뉴와 링크가 함께 바뀌고, 내비게이션을 바꾸면 한 화면의 배치가 바뀐다. 이 과목에서는 정보 구조와 내비게이션의 종류와 위치를 7장에서, 화면 위의 모양을 8장에서 정한다.

정보 구조의 구성 요소는 흔히 넷으로 나눈다. Interaction Design Foundation은 정보 구조의 주요 구성 요소로 조직 체계, 레이블 체계, 내비게이션 체계, 검색 체계를 든다[I1]. 이 네 체계의 구분은 모빌(Peter Morville)과 로젠펠드(Louis Rosenfeld)의 책 『Information Architecture for the World Wide Web』에서 널리 퍼진 것이다[I2].

flowchart LR

    IA --> L["레이블 체계: 묶음을 무엇이라 부르는가"]
    IA --> N["내비게이션 체계: 어떻게 돌아다니는가"]
    IA --> S["검색 체계: 어떻게 찾는가"]

5-2. 조직 체계

조직 체계(organization system)는 콘텐츠와 기능을 무엇을 기준으로 묶는지 정한다. 모빌과 로젠펠드는 조직의 기준(scheme)을 정확한 기준과 모호한 기준으로 나눈다[I2].

구분 기준 뜻 jobprep의 예
정확한 기준 가나다(알파벳) 순 이름 순으로 늘어놓는다 기업 정보의 회사 이름 목록
정확한 기준 시간 순 날짜 순으로 늘어놓는다 공고 목록의 마감일 순(REQ-002), 지원 일정(REQ-010)
정확한 기준 지역 장소로 묶는다 근무 지역 필터(v1에는 없다. PS-1이 먼저 보는 조건이어서 요구 후보가 된다[인터뷰_예시_01:L29])
모호한 기준 주제 다루는 대상으로 묶는다 공고, 자기소개서, 취업 자료
모호한 기준 과업 사용자가 하려는 일로 묶는다 찾기, 관리하기, 준비하기, 묻기
모호한 기준 사용자 집단 누구를 위한 것인가로 묶는다 1학년용, 2학년용(jobprep에서는 쓰지 않음)
모호한 기준 은유 익숙한 현실의 개념을 빌린다 「서랍」, 「책상」(jobprep에서는 쓰지 않음)

정확한 기준은 항목이 서로 겹치지 않는 구역으로 나뉘므로 만들고 유지하기 쉽고, 사용자가 찾는 대상의 이름을 이미 알 때 잘 맞는다[I2]. 모호한 기준은 경계가 분명하지 않아 설계하기 어렵지만, 사용자가 무엇을 찾는지 정확히 모를 때 더 도움이 된다[I2]. 실제 서비스는 둘을 섞는다. jobprep은 전역 메뉴를 과업(모호한 기준)으로 나누고, 공고 목록 안에서는 마감일(정확한 기준)로 정렬하고 상태(접수예정, 접수중, 마감)로 거른다.

조직 구조. 묶음과 묶음 사이의 관계를 조직 구조라고 한다. 가장 흔한 것은 계층(hierarchy)이다. 상위 항목 아래에 하위 항목이 들어가는 나무 모양이며, 대개 사이트의 주 내비게이션이 된다[I2]. 계층을 설계할 때는 깊이와 폭을 함께 본다. 넓고 얕은 계층은 원하는 것까지 누르는 횟수가 적지만 한 화면의 선택지가 많아 고르기 어렵다. 좁고 깊은 계층은 한 번에 고를 것이 적지만, 원하는 것이 어느 갈래에 있는지 맞히지 못하면 되돌아와야 한다. jobprep은 전역 메뉴를 4개로 두고, 전역 메뉴에서 어느 화면이든 두 번 안에 닿게 한다.

5-3. 레이블 체계

레이블(label)은 묶음과 링크의 이름이다. 레이블이 하는 일은 그 아래에 무엇이 있는지를 누르기 전에 알려 주는 것이다. 좋은 레이블의 조건은 다음과 같다.

  • 사용자의 말을 쓴다. 개발자가 쓰는 말(「마이페이지」, 「챗봇」, 「RAG 검색」)이 아니라 사용자가 인터뷰에서 쓴 말(「저장한 공고」, 「자료 묻기」)을 쓴다. 6절의 카드 소팅은 사용자의 말을 모으는 방법이다.
  • 하는 일로 부른다. 「챗봇」은 기술의 이름이어서 무엇을 물을 수 있는지 알려 주지 않는다. 「자료 묻기」나 「취업 자료 질문」은 하는 일과 대상을 함께 알려 준다.
  • 서로 겹치지 않는다. 「공고」와 「채용 정보」가 나란히 있으면 사용자는 둘의 차이를 추측해야 한다.
  • 같은 대상에는 같은 말을 쓴다. 메뉴에서 「지원 일정」이라 부른 것을 화면 제목에서 「내 스케줄」이라 부르면 사용자는 다른 곳에 왔다고 생각한다.

레이블의 일관성은 명세서와도 관계가 있다. 명세서 v2의 화면 목록에 적은 화면 이름이 메뉴의 레이블, 화면의 제목, 흐름도의 칸 이름에서 모두 같아야 한다. 8절의 화면 목록이 이 이름의 기준이 된다.

5-4. 내비게이션 체계

내비게이션은 사용자가 정보 구조 안을 돌아다니는 수단이다. NN/g는 내비게이션의 종류로 전역, 지역, 유틸리티 내비게이션과 이동 경로(breadcrumb), 필터, 패싯, 관련 링크, 바닥글을 들고, 각각에 대해 사용 우선순위, 배치, 패턴(탭, 메가 메뉴, 아코디언 등)을 정하라고 한다[N6].

종류 뜻 jobprep에서
전역(global) 거의 모든 화면에 같은 자리에 있는 주 메뉴 공고, 지원 관리, 자기소개서, 자료 묻기
지역(local) 한 갈래 안에서 옮겨 다니는 메뉴 지원 관리 안의 「지원 일정」, 「관심 공고」 탭
유틸리티(utility) 내용과 직접 관계없는 도구 설정, 이용 안내
맥락(contextual) 내용 안에 박힌 링크 공고 상세의 「지원 일정에 추가」
이동 경로(breadcrumb) 지금 위치까지의 경로 깊이가 두 단계뿐이어서 두지 않는다
필터와 패싯 목록을 조건으로 좁히기 공고 목록의 상태 거르기(REQ-005)와 검색어(REQ-006)

내비게이션의 배치는 화면 크기에 따라 다르다. PS-1처럼 휴대폰으로 쓰는 사용자에게는 화면 아래쪽 탭이 엄지로 닿기 쉽고, 컴퓨터로 공고문을 보는 PS-2에게는[인터뷰_예시_02:L5] 위쪽 막대가 익숙하다. 이 장에서는 어떤 항목이 전역이고 어떤 항목이 지역인가까지만 정하고, 배치는 8장에서 정한다.

5-5. 검색 체계

검색 체계는 사용자가 구조를 따라가지 않고 원하는 것을 바로 찾게 한다. jobprep에는 성격이 다른 두 가지 찾기가 있다. 공고 검색(SCR-01)은 제목이나 모집기관의 낱말을 받아 조건에 맞는 공고의 목록을 보이고(REQ-006), 결과가 없으면 그 사실과 조건을 푸는 방법을 안내한다(REQ-007). 9장에서 목록 거르기로 구현한다. 취업 자료 질의응답(SCR-06)은 자연어 질문을 받아 근거 문서가 붙은 답 한 개를 보이고, 근거가 없으면 자료에 없다고 답한다(REQ-021). 11장에서 검색 증강 생성으로 구현한다.

질의응답을 검색 체계의 하나로 보면, 두 기능 모두 「결과가 없을 때」를 설계해야 한다는 공통점이 드러난다. 7절의 예외 흐름에서 이 두 경우를 「빈 결과」로 다룬다.

5-6. 사이트맵

사이트맵(sitemap)은 정보 구조를 나무 모양으로 그린 문서이다. 콘텐츠와 기능을 층으로 나누고 하위 항목을 상위 항목 아래에 둔다[N6]. 사이트맵은 정보 구조의 산출물이지 내비게이션 요소가 아니다[N6]. 화면 아래쪽에 「사이트맵」이라는 링크 목록을 두는 것과는 다른 이야기이다.

이 장의 사이트맵은 mermaid의 flowchart TD로 그리고, 화면 칸의 레이블은 반드시 「SCR-번호 화면 이름」으로 시작한다. 그래야 8절의 검사 스크립트가 사이트맵의 화면과 명세서의 화면 목록을 대조할 수 있다. 전역 메뉴의 이름처럼 화면이 아닌 칸은 화면 ID 없이 쓰고 다른 색으로 칠한다.

```mermaid
    classDef nav fill:#eef3ff,stroke:#4a6fd8
    class TOP,JOBS,G2 nav
```

sed -n '/시작/,/끝/p'는 시작 무늬가 있는 줄부터 끝 무늬가 있는 줄까지를 출력한다. 견본의 사이트맵은 두 갈래만 채운 골격이다. 나머지 갈래는 6절의 카드 소팅 결과로 채운다.

견본의 표기를 읽는 법은 다음과 같다. 맨 위의 TOP["jobprep"]은 서비스 이름이며 화면이 아니다. jobprep의 첫 화면은 공고 목록(SCR-01)이다. LIST["SCR-01 공고 목록"]에서 노드 ID는 LIST이고 화면에 보이는 글자는 「SCR-01 공고 목록」이다. 노드 ID에는 하이픈과 한글을 쓰지 않는다. -->는 상위에서 하위로 가는 구조 관계이고, 점선 -.->는 유틸리티 내비게이션처럼 어디서나 가는 관계이다. classDef nav ...는 nav라는 꾸밈 이름에 색과 테두리를 정하고, class TOP,JOBS,G2 nav는 세 노드에 그 꾸밈을 적용해 화면이 아닌 메뉴 칸을 구분한다.

확인 8 jobprep/docs/설계/정보구조.md를 미리 보기로 열었을 때 사이트맵이 위에서 아래로 그려지고 「공고」 칸이 다른 색으로 칠해져 있다. 이어서 견본의 G2 갈래를 「지원 관리」로 바꾸고 그 아래에 SCR-03 지원 일정을 넣어 다시 그렸을 때 바뀐 대로 보인다.

5-7. 정보 구조의 점검 질문

사이트맵을 그린 뒤 다음 질문으로 점검한다. 리뷰(9절)에서도 같은 질문을 쓴다.

  1. 모든 화면이 맨 위(서비스 이름)에서 이어지는가. 들어오는 화살표가 없는 화면은 도달할 수 없으므로 갈래에 넣거나 맥락 링크를 적는다.
  2. 전역 메뉴가 너무 많지 않은가. 많으면 묶음을 합치거나 일부를 지역 메뉴로 내린다.
  3. 한 화면이 두 갈래에 들어가 있지 않은가. 주된 위치를 하나 정하고 다른 곳은 맥락 링크로 적는다.
  4. 레이블이 사용자의 말인가. 카드 소팅 기록의 묶음 이름과 대조하고, 바꾸면 레이블 표에 까닭을 적는다.
  5. 레이블과 명세서 v2 화면 목록의 이름이 같은가. 다르면 한쪽으로 맞춘다.

6. 카드 소팅과 트리 테스트

6-1. 카드 소팅

카드 소팅(card sorting)은 연구 참가자가 이름이 적힌 카드들을 자기에게 말이 되는 묶음으로 나누는 방법이다[N7]. 참가자가 만든 묶음과 그 묶음에 붙인 이름은 사용자가 정보를 어떻게 조직되어 있으리라 기대하는지, 즉 사용자의 정신 모형(mental model)을 드러낸다[N7]. 설계자가 머릿속으로 정한 메뉴 구조가 사용자의 기대와 다를 때, 카드 소팅은 그 차이를 구현 전에 보여 준다.

카드 소팅은 묶음을 누가 정하느냐에 따라 세 가지로 나뉜다[N7].

방식 묶음 쓰는 때 주의
개방형(open) 참가자가 묶음을 만들고 이름도 짓는다 사용자가 자연스럽게 어떻게 분류하는지 알고 싶을 때. 가장 흔한 방식이다 묶음 이름이 제각각이어서 해석에 손이 많이 간다
폐쇄형(closed) 연구자가 묶음을 미리 정하고 참가자는 카드를 넣기만 한다 정해 둔 구조를 확인할 때 내비게이션의 확인에는 대개 트리 테스트가 더 낫다
혼합형(hybrid) 일부 묶음만 미리 정한다 한두 묶음에 확신이 있을 때 미리 정한 묶음이 참가자의 분류를 끌어당겨 편향을 만든다

진행 방식도 둘로 나뉜다. 진행자가 함께 있는 방식(moderated)은 참가자가 왜 그렇게 묶었는지 되물을 수 있어 정성적인 통찰을 얻는다. 진행자가 없는 방식(unmoderated)은 온라인 도구로 많은 사람에게 돌려 정량 자료를 모은다[N7].

인원과 카드 수. NN/g는 정성 연구에는 최소 15명, 정량 연구에는 최소 30~50명을 권하고, 카드는 참가자의 피로를 피하기 위해 30~50장을 권한다[N7]. 카드가 약 50장을 넘으면 참가자가 지쳐 큰 「기타」 묶음을 만들기 쉽다[N7].

이 장의 짝 활동은 참가자 2명, 카드 26장이다. 권장 인원에 한참 못 미치므로, 그 결과는 결론이 아니라 가설이다. 이 활동의 목적은 정보 구조를 확정하는 것이 아니라 그 절차를 익히는 것이다. 프로젝트실습Ⅰ에서 실제 대상 사용자에게 할 때는 권장 인원을 지킨다.

한계. 카드 소팅은 카드를 맥락 없이 보여 준다. 화면의 그림, 링크, 페이지 구조가 없고, 탐색 경로 전체를 보여 주지 못하며, 대개 한 층의 분류만 나온다[N7]. 또한 사용자마다 정신 모형이 달라 결과를 해석하기 어려울 수 있다[N7]. 그래서 카드 소팅으로 만든 구조는 6-4의 트리 테스트로 다시 확인한다.

6-2. 짝 활동: 개방형 카드 소팅

키트의 카드목록.md에는 jobprep의 기능과 콘텐츠 26장이 있다. 카드의 이름은 명세서의 용어가 아니라 사용자가 알아볼 말로 썼다. 짝과 역할을 나누어 진행자와 참가자를 한 번씩 맡는다.

서버 터미널

「종류」 열의 F는 기능, C는 콘텐츠이다. 이 열은 진행자만 본다. 참가자가 보면 「기능」과 「콘텐츠」로 나누는 쪽으로 끌려갈 수 있다.

진행 순서는 다음과 같다(한 사람당 15분 안팎).

  1. 준비(2분). 진행자는 교수가 나눠 준 인쇄 카드 26장을 섞어 책상에 펼친다. 인쇄본이 없으면 종이에 번호와 카드 이름을 옮겨 적는다.

  2. 지시(1분). 진행자는 다음 지시문을 그대로 읽는다. 지시문을 바꾸면 참가자의 분류가 달라진다.

    교수 화면

비슷하다고 생각하는 것끼리 묶어 주세요. 묶음의 수와 크기는 자유입니다.

묶으면서 생각나는 것을 소리 내어 말해 주세요.

  3. 분류(8분). 참가자는 카드를 묶고, 진행자는 참가자가 하는 말을 기록 양식의 「참가자의 말」 칸에 그대로 적는다. 진행자는 분류를 돕지 않는다. “이건 어디에 넣어야 해요?”라는 질문에는 “어디에 넣고 싶으세요?”로 되돌린다.

  4. 이름 붙이기와 되묻기(3분). 묶음마다 이름을 받고, 망설인 카드가 있었다면 왜 망설였는지 묻는다.

  5. 기록(1분). 묶음마다 카드 번호를 양식에 적는다.

빠진 카드와 중복된 카드는 눈으로 찾기 어렵다. 다음 명령으로 첫 번째 표에 나온 번호를 세어 본다.

서버 터미널 
cd ~/llm-service-lab
sed -n '/^## 참가자 1/,/^## 역할/p' ch07/카드소팅/기록_짝.md | grep -E '^\|[^|]*\| *[0-9]' \
  | grep -oE '\b[0-2][0-9]\b' | sort | uniq -d
sed -n '/^## 참가자 1/,/^## 역할/p' ch07/카드소팅/기록_짝.md | grep -E '^\|[^|]*\| *[0-9]' \
  | grep -oE '\b[0-2][0-9]\b' | sort -u | wc -l
26

sed는 「참가자 1의 묶음」 절만 잘라 내고, 첫 grep -E는 그 가운데 둘째 칸이 숫자로 시작하는 행, 즉 카드 번호가 적힌 표의 행만 남긴다(머리 행, 구분 행, 「망설인 카드」 줄은 빠진다). 둘째 grep -oE는 두 자리 숫자만 뽑는다. uniq -d는 두 번 이상 나온 번호만 출력하므로, 첫 명령이 아무것도 출력하지 않으면 중복이 없다. 둘째 명령은 서로 다른 번호의 수를 세며, 26이 아니면 빠진 카드가 있다. 참가자 2의 표는 '/^## 역할/,/^## 두 결과/p'로 바꾸어 센다.

6-3. 결과의 분석

카드 소팅의 결과는 두 가지 방향으로 읽는다. 어떤 카드들이 함께 묶였는가(구조)와, 묶음을 무엇이라고 불렀는가(레이블)이다.

함께 묶인 정도. 참가자가 많을 때는 두 카드가 같은 묶음에 들어간 참가자의 비율을 모든 카드 쌍에 대해 계산한 유사도 행렬(similarity matrix)이나, 그것을 나무 모양으로 그린 덴드로그램(dendrogram)을 쓴다[N7]. 참가자가 둘이면 행렬 대신 관심 있는 카드 쌍 몇 개만 골라 비교한다. 기록 양식의 「두 결과의 비교」 표가 이 일을 한다.

카드 쌍 참가자 1 참가자 2 함께 묶인 비율 해석
07 관심 공고 · 08 지원 일정 등록 같은 묶음 같은 묶음 2/2 「관리」의 한 갈래로 둔다
14 학과 추천 채용 · 16 취업 자료에 질문하기 다른 묶음 같은 묶음 1/2 갈린다. 트리 테스트의 과업으로 확인한다
21 자기소개서 전송 동의 · 12 자기소개서 피드백 같은 묶음 다른 묶음 1/2 갈린다. 동의는 설정에도, 피드백 화면에도 연결한다

위 표의 판정은 예시이다. 「함께 묶인 비율」이 1/2인 쌍은 사용자의 정신 모형이 갈리는 곳이다. 이런 카드는 한쪽 갈래에 두고 다른 쪽에서 맥락 링크로 연결하거나, 6-4의 트리 테스트로 어느 쪽이 더 잘 찾히는지 확인한다.

묶음의 이름. 참가자가 지은 묶음 이름은 레이블의 후보이다. 위의 기록 예시에서 참가자는 「마이페이지」가 아니라 「내 지원 관리」라고 불렀다. 같은 내용의 묶음에 두 참가자가 비슷한 이름을 붙였다면 그 이름을 레이블로 쓸 근거가 된다. 레이블을 바꾸면 정보구조.md의 레이블 표에 바꾼 까닭으로 참가자의 말을 적는다.

확인 10 기록 양식의 「두 결과의 비교」 표에서 세 쌍을 모두 판정하였고, 「정보 구조에 반영한 것」에 전역 메뉴 후보와, 카드 소팅에서 근거를 얻은 레이블을 하나 이상 적었다.

6-4. 트리 테스트

트리 테스트(tree testing)는 참가자가 사이트의 범주 계층에서 특정한 것을 찾게 하는 과업 기반 연구 방법이다[N8]. 시제품도 화면 디자인도 콘텐츠도 필요 없고, 내비게이션 나무와 과업만 있으면 된다. 참가자는 중첩된 범주를 눌러 내려가며 찾는 것이 있으리라 생각하는 곳을 고른다[N8].

카드 소팅과 트리 테스트는 짝을 이룬다. 카드 소팅은 사용자가 콘텐츠를 어떻게 묶고 무엇이라 부르는지를 드러내는 생성적 방법이고, 트리 테스트는 이름까지 붙은 완성된 계층을 시험하는 평가적 방법이다[N8]. 카드 소팅의 결과는 모호한 경우가 많으므로 거기서 나온 계층을 트리 테스트로 확인하라고 NN/g는 권한다[N8].

과업 쓰기. 트리 테스트의 과업은 찾을 대상의 범주 이름을 쓰지 않고 시나리오나 동기로 쓴다[N8]. “관심 공고를 찾으세요”라고 하면 참가자는 「관심 공고」라는 낱말을 찾아 누를 뿐이다.

  • 나쁜 과업 「관심 공고를 찾으세요」 → 좋은 과업 「지난주에 나중에 보려고 저장해 둔 공고를 다시 보고 싶다」(정답: 지원 관리 > 관심 공고)
  • 나쁜 과업 「지원 일정 등록 화면으로 가세요」 → 좋은 과업 「다음 주 화요일 면접 날짜를 적어 두고 싶다」(정답: 지원 관리 > 지원 일정)
  • 나쁜 과업 「자료 묻기를 누르세요」 → 좋은 과업 「우리 학과로 들어온 추천 채용이 있는지 알고 싶다」(정답: 자료 묻기)

과업마다 정답 위치를 미리 정해 둔다. NN/g는 과업 지시를 짧게 쓰고, 정답 위치를 정의해 성공률을 계산하라고 한다[N8].

지표. 트리 테스트는 정답 위치에 닿았는가(성공률), 되돌아가지 않고 곧바로 갔는가(직접성, directness), 얼마나 걸렸는가(과업 시간), 틀린 경로로 어느 범주를 골랐는가를 잰다[N8]. 종이로 할 때는 마지막으로 고른 곳이 정답이면 성공, 한 번이라도 위로 되돌아갔으면 간접으로 적고, 처음 누른 범주를 기록한다. 과업 시간은 이 활동에서 재지 않는다.

직접성은 레이블이 얼마나 분명한지를 보여 준다[N8]. 성공했더라도 여러 번 되돌아갔다면 그 길의 레이블이 참가자를 헷갈리게 한 것이다.

종이 트리 테스트. 짝 활동의 마지막 10분에 한다. 사이트맵을 들여쓴 목록으로 옮겨 종이에 적고, 맨 위 층만 보여 준다. 참가자가 하나를 고르면 그 아래 층을 보여 준다. 진행자는 고른 경로를 그대로 적는다.

7. 사용자 흐름도

7-1. 여정과 흐름의 차이

사용자 흐름(user flow)은 한 제품 안에서 흔한 과업 하나를 끝내는 데 필요한 전형적이거나 이상적인 단계를 나타낸 것이다[N9]. 여정과 흐름은 범위와 세밀함이 다르다.

구분 사용자 여정 사용자 흐름
범위 넓다. 여러 접점과 채널 좁다. 한 제품 안
시간 며칠, 몇 주, 몇 달 몇 분, 몇 시간
담는 것 행동, 생각, 감정 사용자의 주요 행동과 시스템의 반응. 감정은 담지 않는다
산출물 여정 지도 흐름도, 와이어플로(wireflow), 과업 다이어그램
쓰는 때 과정이 여러 채널에 걸치고 감정이 중요한 결정이 있을 때 목표가 한 제품 안에서 끝날 때

이 표는 NN/g의 비교를 정리한 것이다[N9]. NN/g는 흐름을 흔히 낮은 충실도의 와이어플로, 단순한 흐름도, 과업 다이어그램으로 나타낸다고 하며, 특정한 표기법을 정하지는 않는다[N9]. 이 장은 흐름도를 mermaid의 flowchart로 그리고, 7-2의 표기 규칙을 정해 쓴다. 8장에서 화면의 와이어프레임이 생기면, 흐름도의 화면 칸을 와이어프레임으로 바꾼 와이어플로를 만들 수 있다.

PS-1의 여정에서 「공고 탐색」, 「지원 판단」, 「일정 관리」의 세 단계는 jobprep 안에서 한 흐름(FLOW-01)이 된다. 두 주에 걸쳤던 일이 서비스 안에서는 몇 분짜리 흐름으로 바뀐다. 여정 지도의 「기회」가 흐름으로 구체화되는 모습이다.

7-2. 흐름도의 표기

흐름도는 모양으로 칸의 종류를 구분한다. 이 장의 규칙은 다음과 같다. 키트의 견본과 교재의 그림이 모두 이 규칙을 따른다.

칸의 종류 모양 mermaid 문법 예
시작과 끝 경기장 모양(둥근 양끝) S(["시작: …"]) 시작: 공고를 찾고 싶다
화면 네모 L["SCR-01 공고 목록"] SCR-01 공고 목록
사용자의 행동 평행사변형 Q[/"검색어 입력"/] 검색어 입력 또는 상태 선택
판단 마름모 R{"결과가 있는가"} 결과가 있는가
시스템의 처리 네모(화면 ID 없음) SAVE["저장"] 마감 하루 전 알림 예약
예외 처리 빗금 테두리 네모 E1["…"]:::exc 빈 결과 안내와 조건 풀기

판단에서 나가는 화살표에는 반드시 조건을 적는다(R -- 없음 --> E1). 조건이 없는 갈래는 읽는 사람이 어느 쪽이 어느 경우인지 추측하게 만든다. 화면 칸의 글자는 사이트맵과 마찬가지로 「SCR-번호 화면 이름」으로 시작한다.

7-3. mermaid flowchart의 문법

mermaid는 텍스트로 그림을 정의하는 도구이다. 마크다운의 코드 블록에 언어 이름 mermaid를 붙이면 GitHub, VS Code 등에서 그림으로 그려진다[M2][M4]. 흐름도의 기본 문법은 다음과 같다[M1].

선언과 방향. 첫 줄에 flowchart와 방향을 쓴다. TD(또는 TB)는 위에서 아래로, LR은 왼쪽에서 오른쪽으로, BT와 RL은 그 반대 방향이다[M1]. 이 장은 사이트맵과 사용자 흐름에 TD를, 단계가 적은 흐름과 블루프린트에 LR을 쓴다.

노드. 노드는 ID와 글자로 이루어진다. A["글자"]처럼 쓰면 ID는 A, 화면에 보이는 것은 「글자」이다. 모양은 괄호의 종류로 정한다[M1].

A["네모"]          B("둥근 모서리")       C(["경기장 모양"])
D{"마름모"}        E[/"평행사변형"/]      F[("원통: 데이터 저장소")]
G(("원"))          H{{"육각형"}}          I[["서브루틴"]]

연결. 화살표의 모양과 글자[M1].

A --> B              실선 화살표
A --- B              화살표 없는 선
A -.-> B             점선 화살표
A ==> B              굵은 화살표
A -- 조건 --> B      글자가 붙은 화살표
A -->|조건| B        같은 뜻의 다른 표기
A --> B --> C        이어 쓰기

묶음과 꾸밈. subgraph 이름 … end로 노드를 묶고, classDef로 꾸밈을 정의해 :::이름 또는 class 노드들 이름으로 적용한다[M1]. %%로 시작하는 줄은 주석이다[M1].

%% 예외 칸은 빗금 테두리로 그린다
classDef exc fill:#fff1f0,stroke:#d4380d,stroke-dasharray:4 3
E1["빈 결과 안내"]:::exc

한글과 특수 문자. 노드의 글자는 큰따옴표로 감싼다. 따옴표로 감싸면 괄호나 한글 같은 문자를 글자로 쓸 수 있다[M1]. 따옴표가 없으면 A[공고 (요약)]의 괄호가 모양 문법으로 해석되어 오류가 난다.

흔한 오류 두 가지. mermaid 문서가 경고하는 것이다[M1].

  • 노드의 글자나 ID를 소문자 end로 쓰면 그림 전체가 깨진다. end는 subgraph를 닫는 낱말이기 때문이다. End, END, 끝처럼 쓴다. 이 장의 견본은 끝 노드의 ID를 FIN이나 END로 쓴다.
  • 화살표 바로 뒤의 노드 ID가 o나 x로 시작하면 원이나 엑스 끝 모양의 연결(--o, --x)로 읽힌다. ID 앞에 공백을 두거나 첫 글자를 대문자로 쓴다.

이 장에서는 이 밖에 두 가지 규칙을 더 지킨다.

  • 노드 ID는 영문 대문자와 숫자로만 쓴다. SCR-01처럼 하이픈이 든 ID는 연결 기호와 헷갈릴 수 있다. 화면 ID는 ID가 아니라 글자에 쓴다(L["SCR-01 공고 목록"]).
  • 한 노드는 한 번만 글자를 정한다. 같은 ID에 다른 글자를 두 번 쓰면 마지막 것만 남아, 앞에서 쓴 글자가 사라진 이유를 찾기 어렵다.

7-4. 예외 흐름

흐름도의 첫 초안은 대개 모든 것이 잘되는 경로, 즉 정상 경로(happy path)만 그린다. 그러나 사용자가 서비스에서 가장 오래 머물고 가장 크게 실망하는 곳은 예외에서이다. 이 장은 예외를 세 종류로 나누어 흐름마다 하나 이상씩 넣는다.

종류 뜻 jobprep의 예 설계의 원칙
빈 결과 처리는 성공했지만 보여 줄 것이 없다 검색 결과 없음, 관심 공고가 아직 없음, 자료에 근거 없음 비어 있다는 사실, 그 까닭, 채우는 길을 보인다
오류 입력이나 처리가 실패했다 날짜 형식 오류, 요약 실패, 시간 초과, 저장 실패 무엇이 잘못되었는지, 사용자의 입력을 지키면서, 다음에 할 일을 알린다
권한 사용자나 브라우저의 허락이 없어 진행할 수 없다 알림 권한 거부, 외부 전송 동의 없음 허락이 왜 필요한지 알리고, 허락하지 않아도 갈 수 있는 길을 둔다

빈 결과. NN/g는 빈 상태(empty state)를 비워 두지 말라고 한다. 빈 화면은 사용자에게 아직 불러오는 중인지, 실패했는지, 결과가 없는지 알려 주지 못하고, 사용자는 새로 고침을 반복하거나 포기한다[N10]. 빈 상태는 시스템의 상태를 알리고, 그 자리에 무엇이 올 수 있는지 가르치고, 그것을 채우는 과업으로 가는 길을 주어야 한다[N10]. 불러오는 중에 「결과 없음」을 먼저 보이는 것처럼 상태를 잘못 알리는 것은 더 나쁘다[N10]. jobprep의 「관심 공고」 화면이 처음 비어 있을 때는 “아직 저장한 공고가 없다”는 안내와 함께 공고 목록으로 가는 버튼을 둔다.

오류. NN/g의 오류 메시지 지침은 세 갈래이다[N11].

  • 보임. 오류가 난 곳 가까이에 보이고, 색만으로 알리지 않으며, 대화 상자는 심각한 오류에만 쓴다. jobprep의 날짜 오류는 날짜 칸 바로 아래에 글자와 아이콘으로 보인다.
  • 전달. 쉬운 말로, 구체적인 문제를, 고치는 방법과 함께, 사용자를 탓하지 않는 어조로 쓴다. 예를 들어 “날짜 형식이 맞지 않습니다”보다 “날짜를 2027-03-15처럼 입력해 주세요”가 낫다(화면의 문구이므로 경어체 그대로 적었다).
  • 효율과 회복. 흔한 실수는 미리 막고, 사용자의 입력을 지우지 않고, 고칠 후보를 제시한다. 요약이 실패해도 공고 원문과 입력을 그대로 두는 것(8절에서 더하는 REQ-024)도 같은 원칙이다.

권한. 웹 서비스의 권한에는 두 종류가 있다. 하나는 브라우저가 묻는 권한(알림, 위치 등)이고, 다른 하나는 서비스가 묻는 동의(개인 정보의 외부 전송 등)이다. 두 경우 모두 사용자는 거절할 수 있어야 하고, 거절해도 서비스의 나머지는 쓸 수 있어야 한다. PS-1은 마감일을 적지 않고 앱 알림에 기댄다(인터뷰_예시_01:L13). 그러므로 알림 권한을 거절한 사용자에게도 마감을 알아차릴 다른 길(「마감 임박」 표시)이 있어야 한다. 외부 전송 동의에는 기록의 직접 근거가 없다. 그러나 피드백을 받으려면 자기소개서가 외부 모델 제공자에게 전송되므로(1-4) 설계자의 판단으로 넣고, 13장의 평가에서 확인할 것으로 남긴다.

LLM 기능의 예외. 1-4와 3-2에서 본 대로 LLM 기능에는 일반 기능에 없는 예외가 있다. 시간 초과에는 멈췄다는 안내와 다시 시도(입력은 그대로)를, 사용 한도 초과에는 다시 쓸 수 있는 시각을, 형식이 깨진 응답에는 요약을 만들지 못했다는 안내와 원문 읽기를, 근거 없음에는 자료에 없다는 답과 다른 경로(학과 사무실 등)를 보인다.

GOV.UK 서비스 매뉴얼은 양식을 질문 하나에 한 페이지로 나누는 것에서 시작하라고 하고(집중과 오류 회복이 쉽다), 해당하지 않는 사람을 걸러 내는 질문을 앞에 두라고 한다[V3]. FLOW-02에서 외부 전송 동의를 전송 직전에 묻는 것도 같은 원칙이다. 동의하지 않는 사용자는 처리 중 화면까지 가지 않는다.

8. 설계에서 명세로

8-1. 명세서 v2에 들어가는 것

6장의 명세서 v1은 「시스템은 무엇을 해야 하는가」를 요구 문장으로 고정하였다. 7장의 설계는 그 요구들이 어느 화면에서, 어떤 순서로 사용자에게 나타나는지를 정하였다. 명세 주도 개발에서 설계는 명세 밖에 따로 떠 있으면 안 된다. 9장에서 Claude Code에 구현을 지시할 때 넘기는 입력은 명세서이고, 명세서에 없는 화면과 흐름은 구현에서 추측으로 채워지기 때문이다. 그래서 설계의 결과 가운데 구현이 기대야 할 것을 명세서로 옮긴다.

  • 화면 목록: 화면 ID, 화면 이름, 목적, 관련 요구, 진입 흐름. 사이트맵에서 옮겨 온다.
  • 사용자 흐름: 흐름 ID, 이름, 행위자, 지나는 화면, 문서의 위치. 사용자흐름.md에서 옮겨 온다.
  • 추가 요구: 흐름의 예외에서 찾은 빈틈을 EARS 문형으로 쓴 요구.
  • 변경 이력: v2의 행.

여정 지도와 카드 소팅 기록은 명세서로 옮기지 않는다. 이 둘은 설계의 근거이지 구현의 입력이 아니다. 명세서에서는 「근거」 열이나 문서 머리의 근거 목록에서 이 문서들을 가리키기만 한다.

ISO 9241-210도 사용자 요구의 명세를 한 번에 끝내지 않는다. 표준은 시나리오, 초기 목업, 시제품으로 사용자의 피드백을 받아 요구 명세가 사용자 요구를 정확하고 완전하게 담았는지 확인하면서 반복적으로 다듬는다고 예시한다[X1]. 명세서의 판을 올리는 것은 이 반복을 기록으로 남기는 방법이다.

8-2. 화면 목록과 화면 ID

화면 ID는 SCR- 뒤에 두 자리 번호를 붙인다. 화면 ID가 필요한 까닭은 같은 화면을 여러 문서가 가리키기 때문이다. 사이트맵, 흐름도, 명세서, 8장의 화면 명세, 9장의 구현 지시, 13장의 평가 기록이 모두 같은 화면을 가리키는데, 이름만으로 가리키면 「공고 목록」, 「공고 리스트」, 「채용 목록」이 같은 화면인지 알 수 없다.

화면 목록의 열은 화면 ID, 화면 이름, 목적, 관련 요구, 진입 흐름이다. 화면 ID는 한 번 정하면 바꾸지 않고, 화면을 없애도 그 번호를 다시 쓰지 않는다. 화면 이름은 사이트맵 칸의 이름, 메뉴의 레이블, 화면의 제목과 같게 쓴다. 목적은 사용자가 그 화면에서 하는 일을 한 문장으로 쓴다(예: 공고를 찾고 거른다). 관련 요구에는 그 화면이 충족하는 요구 ID를 모두 적고(예: SCR-01에 REQ-001~008), 진입 흐름에는 그 화면을 지나는 흐름 ID를 적는다. 지나는 흐름이 없으면 -로 둔다.

「관련 요구」가 이 장의 핵심 연결이다. 연결은 두 방향으로 점검한다.

  • 화면에서 요구로: 모든 화면에는 관련 요구가 하나 이상 있어야 한다. 요구가 없는 화면은 명세에 근거가 없는 화면이다. 그 화면이 정말 필요하다면 요구를 추가하고, 필요 없다면 사이트맵에서 뺀다.
  • 요구에서 화면으로: 모든 기능 요구는 어느 화면 하나 이상에 연결되어야 한다. 연결되지 않은 기능 요구는 사용자가 만날 자리가 없는 기능이다. 화면 목록에서 빠뜨렸거나, 요구가 너무 추상적이어서 화면에 내려앉지 못한 것이다.

비기능 요구(예: 6장 명세의 「공통 품질 요구」인 REQ-022 키 보호와 REQ-023 모의 모드)는 특정 화면이 아니라 서비스 전체에 적용되므로 화면마다 적지 않고 표 아래에 한 줄로 적는다.

6장에서 만든 추적표(jobprep/docs/추적표.md)는 페르소나와 문제 정의에서 요구로 가는 연결이었다. 화면 목록은 그 연결을 요구에서 화면으로 한 단계 더 잇는다.

새 요구의 번호는 v1의 마지막 번호 다음부터 붙인다. 기준 명세서는 REQ-023에서 끝났으므로 REQ-024부터이다. 6장 8-4의 v1.1 연습은 연습용 번호(REQ-901)를 쓰고 병합하지 않았으므로 이 번호 매김에 영향을 주지 않는다. 기존 요구의 번호를 앞으로 당기거나 바꾸어 끼우지 않는다. 다른 문서가 이미 그 번호를 가리키고 있기 때문이다. 같은 까닭으로 요구를 없앨 때도 번호를 지우지 않고 「삭제(v2): 까닭」이라고 남긴다.

흐름의 예외 가운데 요구로 만들지 않는 것도 있다. 날짜 형식 오류의 안내 문구처럼 화면의 세부에 해당하는 것은 8장의 화면 명세에서 정한다. 요구로 올리는 기준은 「이 동작이 없으면 구현자가 추측해야 하는가」이다. 사용 한도를 넘었을 때 아무 안내 없이 버튼이 눌리지 않는 구현과, 한도와 다시 쓸 시각을 알려 주는 구현은 둘 다 그럴듯하므로, 명세가 정해야 한다.

확인 15 jobprep/docs/요구사항명세서.md의 「요구 문장」 절 끝에 흐름에서 찾은 요구가 한 개 이상 있고, 그 번호가 v1의 마지막 번호 다음부터 이어진다.

키트의 견본에 있는 두 절을 명세서의 「열린 질문」 절 앞에 붙인다. 6장의 견본이면 「## 7. 화면 목록」, 「## 8. 사용자 흐름」이 되고 뒤의 「열린 질문」과 「변경 이력」은 9, 10이 된다. 자기 명세서의 절 구성이 다르면 그 번호에 맞추어 고친다. 「## 화면 목록」이라는 제목의 낱말은 바꾸지 않는다. 검사 스크립트가 이 낱말이 든 절을 찾기 때문이다.

8-5. 연결 검사 스크립트

명세서, 사이트맵, 흐름도는 서로 다른 파일이다. 사이트맵에 화면을 하나 더 그리고 명세서의 화면 목록에 넣는 것을 잊거나, 흐름도에 오타로 SCR-60이라고 쓰거나, 명세서에서 요구 번호를 고치고 흐름도는 그대로 두는 일이 쉽게 일어난다. 이런 어긋남은 사람이 눈으로 찾기 어렵고, 9장에서 구현이 어긋난 문서를 입력으로 받으면 그대로 구현된다. 키트의 check_design.py는 이 연결을 기계적으로 검사한다.

검사 결과의 종류 까닭
명세서에 「화면 목록」 절이 있는가 오류 없으면 나머지 검사를 할 수 없다
화면 목록에 같은 화면 ID가 두 번 나오는가 오류 한 ID가 두 화면을 가리키면 연결이 모호하다
화면 목록의 모든 화면에 관련 요구가 있는가 오류 명세에 근거 없는 화면이다
화면 목록의 요구 ID가 명세의 요구 절에 있는가 오류 없는 요구를 가리킨다(오타, 삭제된 요구)
사이트맵과 흐름도의 화면 ID가 화면 목록에 있는가 오류 명세에 없는 화면을 설계하였다
흐름도의 요구 ID가 명세에 있는가 오류 없는 요구를 가리킨다
모든 기능 요구가 어느 화면에 연결되는가 경고 사용자가 만날 자리가 없는 요구이다
화면 목록의 모든 화면이 사이트맵에 있는가 경고 도달 경로가 문서에 없는 화면이다
여정 지도 표의 칸마다 근거 표시가 있는가 경고 근거 없는 칸은 가설이다

오류와 경고를 나눈 기준은 「구현을 막아야 하는가」이다. 오류는 문서끼리 서로 모순되는 상태이므로 고치기 전에는 9장으로 넘어가지 않는다. 경고는 판단이 필요한 상태이다. 예를 들어 여정 지도의 한 칸에 근거가 없더라도, 그것이 리뷰에서 받아들여진 가정이라면 [가정] 표시를 붙여 경고를 없앤다.

스크립트가 ID를 찾는 규칙은 다음과 같다.

  • 요구 ID: REQ- 뒤에 숫자 세 자리. 제목에 「요구」가 든 ## 절 안에서 찾고, 절 제목이나 ### 소제목에 「비기능」이나 「품질」이 든 곳(예: 6장 양식의 「공통 품질 요구」)의 요구는 비기능 요구로, 나머지는 기능 요구로 본다.
  • 화면 ID: SCR- 뒤에 숫자 두 자리. 명세서에서는 「화면 목록」 절의 표에서 각 행의 첫 칸만 화면 ID로 읽는다.
  • 사이트맵과 흐름도: 파일 전체에서 SCR-와 REQ-가 붙은 ID를 모두 찾는다.
  • 여정 지도: 「여정 지도」가 제목에 든 절의 표에서 「단계」와 「기회」 행을 뺀 모든 칸에 [근거: …] 또는 [가정]이 있는지 본다.

먼저 앞 장의 명세서 v1(화면 목록이 없는 판)으로 실행해 본다. 8-4에서 이미 화면 목록을 붙였더라도, 태그 spec-v1이 가리키는 판을 꺼내 따로 검사할 수 있다. 작업 파일은 저장소 밖의 ~/tmp/에 둔다. 여러 사람이 함께 쓰는 서버의 /tmp는 다른 사용자의 같은 이름 파일과 부딪칠 수 있기 때문이다.

8-6. Claude Code로 만드는 사이트맵과 화면 목록의 초안

사이트맵과 화면 목록의 초안도 Claude Code에 맡길 수 있다. 2-6의 여정 지도와 같은 원칙을 지킨다. 근거를 함께 달게 하고, 사람이 대조하고, 검사 스크립트를 돌린다. 여기에 한 가지 원칙을 더한다. Claude Code는 초안을 쓰고, 화면 목록의 ID와 요구 연결은 사람이 확정한다. 언어 모델은 그럴듯한 화면을 더 만들어 내는 경향이 있다. 명세에 없는 「추천 공고」, 「커뮤니티」 같은 화면이 초안에 끼어들면, 그것은 설계가 아니라 범위의 확장이다.

Claude Code 
@jobprep/docs/요구사항명세서.md @ch07/카드소팅/기록_짝.md @jobprep/docs/설계/정보구조.md
jobprep/docs/설계/정보구조.md(5-6에서 복사한 견본)의 사이트맵 초안을 견본의 표기대로 완성하라.
- 화면은 명세서 v2의 화면 목록(SCR-01~SCR-08)만 쓴다. 새 화면을 만들지 않는다

- 화면 칸의 글자는 "SCR-번호 화면 이름"으로 시작한다
- 노드 ID는 영문 대문자와 숫자만 쓴다. end라는 낱말은 쓰지 않는다
- 다 쓴 뒤 python3 ~/kits/Service_07주차/check_design.py jobprep/docs를 실행하고 출력을 그대로 보여라

초안에서 자주 보이는 문제는 다음과 같다. 명세에 없는 화면이 끼어들면 검사 스크립트가 「화면 목록에 없는 화면 ID」로 알리거나 화면 ID 없는 칸이 생긴다. 지우거나, 정말 필요하면 요구와 함께 정식으로 추가한다. 레이블이 「마이페이지」, 「대시보드」, 「챗봇」처럼 개발자의 말이면 카드 소팅 기록의 묶음 이름으로 바꾼다. 근거로 든 참가자의 말이 grep -n "그 말" ch07/카드소팅/기록_짝.md로 찾아지지 않으면 근거를 지우고 레이블을 다시 정한다. 검사 결과를 「통과」라고 보고했는데 자기 터미널에서는 실패하면, 실제 출력을 붙여 다시 고치게 한다.

9. 설계 문서의 리뷰

9-1. 설계 문서를 리뷰받는 까닭

코드에서 발견된 구조 문제는 여러 파일을 고쳐야 하지만, 설계 문서에서 발견된 문제는 문서 몇 줄을 고치면 된다. ISO 9241-210의 원칙 「설계 팀에 여러 분야의 기술과 관점이 있다」도 혼자 쓴 설계가 놓치는 것을 다른 관점이 찾는다는 뜻이다[X1].

이 장의 리뷰는 3장에서 만든 팀 실습 저장소(「팀」-lab)에서 한다. 개인 실습 저장소(llm-service-lab)는 개인의 기록이고, 팀 실습 저장소는 동료와 풀 리퀘스트를 주고받는 연습장이다. 설계 문서를 팀 실습 저장소의 reviews/ch07/「아이디」/ 폴더로 복사해 풀 리퀘스트를 올리고(3장에서 정한 리뷰용 폴더), 같은 팀의 동료 한 명 이상에게 리뷰를 요청한다. 3장에서 익힌 흐름(브랜치 → 커밋 → 푸시 → 풀 리퀘스트 → 리뷰 → 병합)을 그대로 쓴다.

flowchart LR
    A["개인 저장소에서 설계"] --> B["팀 저장소로 복사"]
    B --> C["브랜치, 커밋, 푸시"]
    C --> D["풀 리퀘스트와 리뷰 요청"]

9-3. 리뷰하기

리뷰를 요청받은 동료는 두 가지 방법으로 본다. 하나는 브라우저에서 풀 리퀘스트를 보는 것이고, 다른 하나는 자기 터미널에서 그 브랜치를 받아 검사 스크립트를 돌리는 것이다. 두 가지를 모두 한다.

브라우저에서 보기. GitHub는 풀 리퀘스트의 마크다운 파일에서 mermaid 그림을 그린다[M2]. 「Files changed」 탭의 파일 머리에서 「Display the rich diff」(파일 모양 아이콘)를 누르면 문서가 렌더링된 모습으로 바뀐 내용을 보여 준다. 추가된 글은 초록 바탕, 지운 글은 빨간 바탕에 취소선으로 표시된다[M3]. 다만 줄에 의견을 다는 일은 원본 보기(source diff)에서만 할 수 있다[M3].

리뷰 의견을 다는 순서는 다음과 같다[G1].

  1. 「Files changed」 탭을 연다.
  2. 의견을 달 줄에 마우스를 올리고 파란 더하기 아이콘을 누른다. 여러 줄이면 첫 줄 번호를 누르고 마지막 줄 번호를 Shift를 누른 채 누른다.
  3. 의견을 쓰고 「Start a review」를 누른다. 이미 리뷰를 시작했다면 「Add review comment」를 누른다. 제출 전의 의견은 리뷰어 자신에게만 보인다.
  4. 다 본 파일은 파일 머리의 「Viewed」를 표시한다.
  5. 「Review changes」를 누르고 요약 의견을 쓴 뒤 「Comment」, 「Approve」, 「Request changes」 가운데 하나를 고르고 「Submit review」를 누른다.

세 가지 결정의 뜻은 다르다[G2]. 「Comment」는 승인도 변경 요청도 아닌 의견이고, 「Approve」는 병합해도 좋다는 뜻이고, 「Request changes」는 병합 전에 고쳐야 할 것이 있다는 뜻이다.

터미널에서 보기. 리뷰어는 풀 리퀘스트의 브랜치를 받아 스크립트를 직접 실행한다. 작성자가 「통과」라고 적었더라도 리뷰어가 직접 확인한다.

9-4. 리뷰 의견 쓰기

리뷰 의견은 「무엇이 문제인지, 왜 문제인지, 어떻게 고치면 좋을지」를 함께 쓴다. 키트의 리뷰점검표_양식.md에 점검 항목 열 가지가 있다. 리뷰어는 점검표를 리뷰 요약에 붙여 판정하고, 줄 단위의 의견을 두 개 이상 단다.

「여정 지도가 좀 이상해요」, 「메뉴가 많아요」 같은 의견은 작성자가 무엇을 고쳐야 할지 알려 주지 않는다. 다음은 같은 지적을 좋은 의견으로 쓴 예이다.

여정지도.md 14행: 「생각」 3단계의 근거가 인터뷰_예시_01:L13인데, 그 줄은 마감일을
따로 적지 않는다는 내용이어서 따옴표 안의 혼잣말("주말에 써야지")과 맞지 않습니다.
그 말이 있는 L15로 바꾸거나 [가정]으로 표시하는 것이 좋겠습니다.

정보구조.md 사이트맵: 전역 메뉴가 7개입니다. 카드 소팅에서 「지원 관리」와 「관심 공고」를
한 묶음으로 만든 기록(기록_짝.md 12행)이 있으니 둘을 합쳐 5개로 줄이면 어떨까요.

좋은 의견에는 파일과 줄, 근거, 제안이 있다. 리뷰 의견은 리뷰 대상 문서의 문장이 아니므로 동료에게 쓰는 글의 예절을 따라 경어체로 써도 된다.

설계 리뷰에서 특히 볼 것. 코드 리뷰와 달리 설계 리뷰는 「동작하는가」를 실행해 볼 수 없다. 대신 문서와 근거를 대조한다.

  1. 근거 대조. 여정 지도에서 무작위로 두 칸을 골라 근거의 줄을 연다. 리뷰어가 작성자의 인터뷰 기록을 볼 수 없으면(개인 저장소에 있으므로), 작성자에게 그 줄의 내용을 리뷰 답글로 붙여 달라고 요청한다.
  2. 막다른 칸. 흐름도의 예외 칸에서 나가는 화살표가 없는 곳을 찾는다.
  3. 레이블의 일관성. 사이트맵의 화면 이름, 흐름도의 화면 이름, 명세서 화면 목록의 이름이 같은지 본다.
  4. 범위의 확장. 명세에 근거가 약한 화면이나 기능이 끼어들지 않았는지 본다.

확인 22 동료의 풀 리퀘스트에 리뷰 점검표가 든 요약 의견과, 파일과 줄을 가리키는 줄 단위 의견 두 개 이상을 달고 「Submit review」로 제출하였다.

여정지도.md를 채워라. 행위자는 「페르소나 이름」이다.

- 기회 행을 뺀 모든 칸 끝에 [근거: 인터뷰_번호:L줄번호]를 붙인다
- 기록에 없는 내용은 쓰지 말고, 꼭 필요하면 [가정]이라고 쓴다
- 기회 행에는 @jobprep/docs/요구사항명세서.md 의 요구 ID를 적는다
- 감정 곡선의 line 값을 감정 행의 숫자와 같게 고친다
- 다 쓴 뒤 [가정] 칸의 목록을 보여라

초안을 받으면 사람이 다음을 한다.

  1. 근거 표시 두 개 이상을 무작위로 골라 원 기록의 그 줄을 연다(grep "^L줄번호 " ch05/기록/인터뷰_번호.md). 맞지 않으면 고친다.
  2. [가정] 칸은 원 기록을 grep으로 찾아본 뒤, 근거가 있으면 근거로 바꾸고 없으면 「가정과 확인할 것」 표로 옮긴다.
  3. 2-7의 표로 흔한 문제를 점검한다. 특히 단계가 화면 이름이 아닌지, 현재 여정에 jobprep이 들어가지 않았는지 본다.
  4. 「기회에서 나온 명세 변경」에 기회 가운데 명세에 반영할 것과 하지 않을 것을 적는다.

확인 25 여정 지도의 근거 표시 두 개를 원 기록과 대조한 결과를 지도 끝에 「근거 대조: L13 맞음, L15 고침(…)」처럼 적었다.

10-8. 리뷰

9절의 순서로 팀 실습 저장소에 풀 리퀘스트를 올리고, 동료 한 명 이상에게 리뷰를 요청한다. 같은 팀의 동료가 올린 풀 리퀘스트 하나 이상을 리뷰한다. 리뷰는 수업 시간 안에 끝나지 않을 수 있다. 리뷰의 제출과 반영, 병합은 다음 수업(8장) 시작 전까지 끝낸다.

확인 32 팀 실습 저장소에 자기 풀 리퀘스트가 있고, 동료의 리뷰가 한 개 이상 달려 있다. gh pr view 「번호」 --json reviews --jq '.reviews | length'의 출력이 1 이상이다.

정리

  • 사용자 경험은 사용 전, 사용 중, 사용 후에 걸친 사용자의 지각과 반응이다(ISO 9241-210). 이 장은 개릿의 다섯 층위 가운데 구조 층위를 맡고, 그 결과로 범위 층위(명세서)를 고친다.
  • 인간 중심 설계는 사용 맥락의 이해, 요구의 명시, 설계 해결안의 작성, 평가의 네 활동을 반복한다. 명세서의 판을 올리는 것은 이 반복을 기록하는 방법이다.
  • 사용자 여정 지도는 행위자 한 명, 시나리오 하나의 행동, 생각, 감정, 접점, 불편, 기회를 단계별로 적는다. 칸마다 근거를 달아 가설과 조사 결과를 구분한다.
  • 서비스 블루프린트는 접점 뒤의 전면 행동, 후면 행동, 지원 과정을 가시선으로 나누어 그린다. LLM 기능의 시간 제한, 사용 한도, 형식 검사는 후면에서 정해지지만 사용자에게는 예외로 보인다.
  • 정보 구조는 조직, 레이블, 내비게이션, 검색의 네 체계로 이루어진다. 카드 소팅은 사용자의 분류와 말을 모으고(생성적), 트리 테스트는 이름 붙은 구조에서 찾을 수 있는지 확인한다(평가적).
  • 사용자 흐름도는 한 과업의 화면, 행동, 판단을 그리며, 빈 결과, 오류, 권한의 예외와 그 뒤에 갈 곳까지 그려야 완성된다. 예외를 그리면 명세의 빈틈이 드러난다.
  • 설계는 명세서 v2의 화면 목록으로 옮겨지고, 화면과 요구의 연결은 스크립트로 검사하고 동료의 리뷰로 확인한다.

개념 점검 문항

  1. ISO 9241-210이 정의하는 사용자 경험과 사용성의 차이를 시점과 재는 방법의 두 측면에서 설명하라.
  2. 두 페르소나(PS-1, PS-2)를 한 여정 지도에 함께 그리면 어떤 문제가 생기는가. 감정 행을 예로 들어 설명하라.
  3. 서비스 블루프린트의 가시선 아래에 있는 일 가운데, LLM 기능에서 사용자 경험에 직접 영향을 주는 것 두 가지를 들고, 각각이 사용자에게 어떻게 보이는지 설명하라.
  4. 개방형 카드 소팅과 트리 테스트는 각각 어떤 질문에 답하는가. 카드 소팅만으로 메뉴 구조를 확정하면 안 되는 까닭은 무엇인가.
  5. 명세서 v2의 화면 목록에서 「관련 요구」가 빈 화면과, 어느 화면에도 연결되지 않은 기능 요구는 각각 무엇을 뜻하며 어떻게 처리하는가.
