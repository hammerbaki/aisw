팀 공동 작업: GitHub 기반 협업 흐름

2027학년도 「LLM 서비스 개발」의 준비 중인 교재입니다. 편집 상태를 검토하기 위해 미리 공개한 것으로, 수업 전에 내용과 순서가 바뀔 수 있습니다.

학사 4주차 · 교재 03 · 1부 개발 환경

앞 장에서는 혼자 쓰는 저장소를 다루었다. 개인 실습 저장소 llm-service-lab을 만들고, Claude Code가 만든 변경을 git diff로 읽은 뒤 커밋으로 나누어 기록하고, 잘못된 변경을 되돌린 뒤 GitHub에 푸시하였다. 그 저장소에 커밋하는 사람은 학습자 한 사람뿐이었다. 한 사람이 쓰는 저장소에서는 “누가 무엇을 고치고 있는가”를 물을 일이 없고, 원격 저장소의 내용이 내 컴퓨터의 내용과 다를 일도 거의 없다.

팀이 되면 두 물음이 동시에 생긴다. 첫째, 같은 파일을 두 사람이 고치면 누구의 변경이 살아남는가. 둘째, 지금 누가 무엇을 하고 있으며 그 일이 끝났는지를 어디에서 확인하는가. Git은 첫째 물음에 대해 변경을 줄 단위로 합치고 겹치는 곳만 충돌로 알리는 방법을 준다. GitHub는 둘째 물음에 대해 이슈(issue)로 일을 나누고, 풀 리퀘스트(pull request)로 변경을 검토받고, 승인 뒤에 병합하는 흐름을 준다. 이 장은 두 도구를 한 흐름으로 묶어 쓰는 방법을 다룬다.

이 장의 핵심 실습은 하나이다(9절). 3~4명의 팀이 팀 실습 저장소 <팀>-lab에서 이슈 → 브랜치 → 풀 리퀘스트 → 리뷰 → 병합을 한 사람이 한 바퀴씩 돌고, 키트가 정해 둔 같은 파일의 같은 줄을 두 사람이 고쳐 병합 충돌을 일부러 만든 뒤 해결한다. 만든 것은 병합된 풀 리퀘스트이고, 해결하는 문제는 그 충돌이다. 따라 하기는 개인 저장소의 풀 리퀘스트(4-4)와 연습 저장소의 충돌 해결(7-2~7-4) 둘이다.

이 흐름은 같은 학기의 프로젝트실습Ⅰ에서 바로 쓰인다. 프로젝트실습Ⅰ의 팀 저장소는 같은 절차로 그 과목의 첫 시간에 만든다. 이 과목 안에서도 7장(사용자 조사), 11장(UI 설계), 13장(사용성 평가)에서 설계 문서와 개선안을 팀 실습 저장소의 풀 리퀘스트로 올려 동료 리뷰를 받는다.

학습 목표

  • 팀 작업의 흐름을 설명한다. GitHub flow의 여섯 단계(브랜치, 변경, 풀 리퀘스트, 리뷰 반영, 병합, 브랜치 삭제)가 각각 어떤 문제를 막는지 말할 수 있다.
  • 이슈와 풀 리퀘스트로 일을 나누고 검토한다. 완료 조건이 있는 이슈를 쓰고, 이슈 번호가 든 브랜치에서 작업하고, Closes #n으로 이슈를 연결한 풀 리퀘스트를 올리고, 점검표에 따라 리뷰한다.
  • 병합 충돌의 원인을 읽고 해결한다. 충돌 표시(<<<<<<<, =======, >>>>>>>)에서 양쪽의 변경을 구분하고, 로컬과 GitHub 웹 편집기에서 해결한 뒤 충돌 표시가 남지 않았음을 확인한다.
  • 저장소의 권한과 보호 규칙을 고른다. 다섯 권한(read, triage, write, maintain, admin)의 차이와 보호 브랜치·규칙 집합이 막는 일을 설명하고, AI 도구가 만든 풀 리퀘스트 설명과 리뷰 초안을 사람이 검토하는 절차를 따른다.

0. 시작하기

이 절은 키트를 받고, 앞 장의 개인 저장소와 GitHub 로그인 상태를 확인하고, 교수 계정에 있는 팀 실습 저장소를 내 PC에 클론한다. 실습은 내 PC의 터미널(Windows는 Git Bash, macOS는 기본 터미널)에서 한다. Claude Code의 설치와 로그인은 부록 A-7·A-8, GitHub 계정은 A-2-2, GitHub CLI 인증은 A-10-1, 협업자 초대의 수락은 A-11에 있다.

이 장의 실행 상한. 실제 모델은 대화형 Claude Code로 초안 두 건(풀 리퀘스트 설명, 리뷰 초안)을 쓸 때만 부른다. /code-review의 자동 검토는 교수 시연으로 본다.

0-1. 키트 받기

키트는 1주차에 클론한 키트 저장소 ~/kits-repo에서 받아 저장소 밖의 ~/kits/에 둔다. 명령의 뜻은 부록 A-12-3에 있다.

터미널 
git -C ~/kits-repo pull
mkdir -p ~/kits
cp -rn ~/kits-repo/Service_03장 ~/kits/
ls ~/kits/Service_03장
README.md
project-repo
team-lab
기준산출물
도구

team-lab/은 팀 실습 저장소의 시작 파일이다. 교수가 이 폴더로 팀마다 저장소를 미리 만들어 두었으므로, 학습자가 이 폴더를 직접 GitHub에 올리지 않는다. 학습자가 쓰는 것은 도구/, 협업기록_양식.md, 리뷰점검표.md, project-repo/README_양식.md이다.

0-2. 개인 저장소와 Git 설정의 확인

이 장은 2장의 개인 실습 저장소 ~/llm-service-lab을 받아 쓴다. 저장소가 원격(origin)과 연결되어 있고 푸시하지 않은 커밋이 없는지 보고, 2장에서 한 Git 전역 설정을 확인한다. 특히 core.quotePath가 켜져 있으면(Git의 기본값) Git이 한글 파일 이름을 "\354\204\234..."처럼 8진수로 바꾸어 보인다. 이 장의 충돌 실습 파일 이름이 서비스소개.md이므로, 2장의 설정이 빠져 있으면 다시 설정한다.

터미널 
cd ~/llm-service-lab
git status -sb
git remote get-url origin
git config --global --get-regexp 'user.email|core.quotepath|pull.rebase'
git --version
(예시)
## main...origin/main
https://github.com/「내 아이디」/llm-service-lab.git
user.email 「숫자ID+사용자이름」@users.noreply.github.com
core.quotepath false
pull.rebase false
git version 2.55.0.windows.5

첫 줄의 ## main...origin/main 뒤에 [ahead 2]처럼 괄호가 붙어 있으면 푸시하지 않은 커밋이 있다는 뜻이다. git push로 먼저 올린다. 저장소가 아예 없으면 키트의 기준산출물/README.md를 따라 make_lab.sh로 최소 저장소를 만들고 gh repo create로 GitHub에 올린다.

세 줄 중 빠진 것이 있으면 2장 2절의 git config --global 명령으로 다시 설정한다. user.email이 GitHub 계정의 noreply 주소여야 GitHub 화면에서 커밋이 내 계정에 연결되고, 9-5의 점검 도구가 내 커밋을 찾는다. 이 장의 점검 도구는 git 2.38 이상에서 가장 정확하게 동작하며, 그보다 낮은 판을 위한 대체 판정도 들어 있다.

[최신 자료 자리: 내 PC의 git과 gh 판] git --version(2.38 이상, zdiff3는 2.35 이상)과 gh --version. 확인할 곳 git-scm.com/downloads, github.com/cli/cli/releases. 2026-11-16 집필용 PC(Windows 11, Git Bash)의 값은 git 2.55.0.windows.5, gh 2.88.1이고, macOS와 실습실 PC는 확인하지 못하였다.

0-3. GitHub CLI와 팀 실습 저장소

이 장은 GitHub 웹 화면과 GitHub CLI(gh)를 함께 쓴다. 웹 화면은 처음 보는 기능의 모양을 익힐 때, gh는 같은 일을 빠르게 되풀이할 때 쓴다. 교수는 수업 전에 교수 계정에 팀마다 비공개 팀 실습 저장소 ict-aisw-2027-<팀>-lab(이 교재에서는 줄여 <팀>-lab)을 만들고 팀원을 협업자로 초대해 두었다. 교수 계정과 팀 이름을 여러 번 쓰므로 셸 변수 파일 ~/ch03.env에 적어 둔다. 「 」 안을 교수가 알려 준 값으로 바꾼다. 이 장에서 Claude Code와 사람이 함께 고치는 초안 파일은 홈 폴더의 ~/ch03-drafts/에 둔다.

터미널 
gh auth status
cat > ~/ch03.env <<'EOF'
export OWNER=「교수 계정」
export TEAM=「팀 이름. 예: team01」
export REPO="ict-aisw-2027-$TEAM-lab" PROJ="ict-aisw-2027-$TEAM-project"
EOF
source ~/ch03.env
mkdir -p ~/ch03-drafts
gh api user/repository_invitations --jq '.[].repository.full_name'
gh api "repos/$OWNER/$REPO/collaborators" --jq '.[].login'
(예시)
github.com
  ✓ Logged in to github.com account 「내 아이디」 (keyring)
  - Active account: true
  - Git operations protocol: https
  - Token: gho_************************************
  - Token scopes: 'gist', 'read:org', 'repo', 'workflow'
「교수 계정」
「팀원1 아이디」
「팀원2 아이디」
「팀원3 아이디」
  • Logged in이 보이지 않으면 gh auth login을 실행한다(부록 A-10-1).
  • 첫 목록(받지 않은 초대)에 저장소 이름이 나오면 초대를 아직 수락하지 않은 것이다. 부록 A-11로 수락한다. 협업자 목록에 내 아이디가 없거나 404가 나면 교수에게 알린다.
  • 터미널을 새로 열 때마다 source ~/ch03.env를 한 번 실행한다.

이제 팀 실습 저장소를 클론하고, 이 저장소에 대한 내 권한을 GitHub API로 확인한다. 팀 저장소는 개인 저장소 안에 두지 않는다. 저장소 안에 다른 저장소를 넣으면 바깥 저장소의 git status가 안쪽 저장소를 이상한 변경으로 보이기 때문이다. 클론 자리는 학기 내내 ~/teams/<팀>-lab이다. 팀원 소개는 members/「아이디」.md에, 7·11·13장에서 서로 리뷰할 산출물은 reviews/chNN/「아이디」/에 둔다.

터미널 
mkdir -p ~/teams && cd ~/teams
gh repo clone "$OWNER/$REPO" "$TEAM-lab"
cd "$TEAM-lab" && ls -a
gh api "repos/$OWNER/$REPO" --jq .permissions
(예시)
Cloning into 'team01-lab'...
./  ../  .git/  .github/  README.md  members/  서비스소개.md
{"admin":false,"maintain":false,"pull":true,"push":true,"triage":true}

--jq는 API 응답(JSON)에서 원하는 부분만 뽑는다. API에서는 read를 pull, write를 push라 부른다(권한의 뜻은 2-2). gh repo view --web을 실행하면 브라우저에서 저장소 첫 화면이 열린다.

출력 블록의 첫 줄이 (예시)인 것은 GitHub와 주고받는 명령의 출력으로, 실제 GitHub에서 실행하지 못하고 gh의 형식에 따라 쓴 것이다. 표시가 없는 git 출력은 집필용 PC의 Git Bash에서 연습 저장소로 실제로 얻었다.

확인 1 0-2의 git status -sb 첫 줄이 괄호 없는 ## main...origin/main이고, 0-3의 권한 출력에 "push":true와 "admin":false가 있다.

1. 팀 작업의 문제와 GitHub flow

1-1. 덮어쓰기와 갱신 분실

Git 없이 팀이 같은 문서를 고치는 가장 흔한 방법은 파일을 메신저나 공유 폴더로 주고받는 것이다. 이 방법에는 구조적인 결함이 있다. A와 B가 같은 판본 기획서_v3.docx를 받아 각자 고친 뒤 공유 폴더에 올리면, 나중에 올린 사람의 파일이 먼저 올린 사람의 수정을 통째로 덮는다. 덮인 쪽은 자기 수정이 사라진 것을 한참 뒤에야 알고, 무엇이 사라졌는지 확인할 기록도 없다. 이 현상을 갱신 분실(lost update)이라 한다.

Git은 이 문제를 두 단계로 막는다. 첫째, 원격 저장소에 내가 아직 받지 않은 커밋이 있으면 내 푸시를 거부한다(푸시 거부). 원격의 커밋을 내 커밋으로 덮어쓰는 일이 기본적으로 일어나지 않는다. 둘째, 원격의 커밋을 받아 내 커밋과 합칠 때 서로 다른 곳을 고친 변경은 자동으로 합치고, 같은 곳을 다르게 고친 경우에만 멈추고 사람에게 묻는다(줄 단위 병합). 멈춘 상태가 병합 충돌(merge conflict)이다.

방식 두 사람이 같은 파일을 고쳤을 때 사라진 수정을 찾을 수 있는가
파일 주고받기 나중에 올린 파일이 앞의 수정을 덮는다 없다. 기록이 남지 않는다
공유 문서 동시 편집 글자 단위로 섞인다. 의도가 다른 두 수정이 한 문장에 섞일 수 있다 판 기록이 있으면 찾을 수 있으나, 무엇을 왜 바꾸었는지는 남지 않는다
Git과 원격 저장소 받지 않은 커밋이 있으면 푸시가 거부된다. 다른 곳의 수정은 자동으로 합쳐지고, 같은 곳은 충돌로 알린다 커밋마다 누가, 언제, 무엇을, 왜(메시지) 바꾸었는지 남는다

1-2. GitHub flow

GitHub flow는 GitHub가 문서로 제시하는 가벼운 브랜치 기반 작업 흐름이다[G5]. 기본 브랜치(대개 main)는 언제나 쓸 수 있는 상태로 두고, 모든 변경은 짧게 사는 브랜치에서 만든 뒤 풀 리퀘스트로 검토받아 합친다. GitHub Docs는 이를 여섯 단계로 적는다.

flowchart LR
    I["이슈<br/>할 일과 담당자"] --> B["1 브랜치 만들기<br/>3-add-member-hong"]
    B --> C["2 변경과 커밋<br/>푸시로 백업·공유"]
    C --> P["3 풀 리퀘스트<br/>Closes #3"]
    P --> R["4 리뷰 반영<br/>코멘트 → 추가 커밋"]
    R -->|승인| M["5 병합<br/>main에 들어감"]
    M --> D["6 브랜치 삭제<br/>이슈 자동 종료"]
    R -->|변경 요청| C

그림 1. GitHub flow: 이슈에서 시작해 브랜치, 풀 리퀘스트, 리뷰, 병합을 거쳐 브랜치 삭제로 끝난다. 2026년 2학기판의 그림 「git 협업 흐름: 커밋은 내 기록, 푸시는 공유, 풀 리퀘스트는 검토 요청」을 단계로 나누어 다시 그렸다.

단계 하는 일 막는 문제
1 브랜치 만들기 짧고 설명적인 이름의 브랜치를 기본 브랜치에서 만든다 작업 중인 변경이 팀의 기준을 흔드는 일
2 변경과 커밋 한 커밋에 한 가지 완결된 변경을 담고, 자주 푸시한다 컴퓨터 고장으로 작업을 잃는 일, 되돌릴 단위가 커지는 일
3 풀 리퀘스트 변경의 요약과 해결하는 문제를 적고 관련 이슈를 연결한다. 끝나기 전이면 초안(draft)으로 연다 무엇을 왜 바꾸었는지 모른 채 합치는 일
4 리뷰 반영 리뷰어는 전체 또는 특정 줄에 코멘트를 남기고, 작성자는 커밋을 더 해 답한다 한 사람만 본 변경이 그대로 들어가는 일
5 병합 승인을 받은 뒤 기본 브랜치에 합친다. 충돌과 보호 규칙이 병합을 막을 수 있다 검토와 충돌 해결을 건너뛴 병합
6 브랜치 삭제 병합한 브랜치를 지운다. 풀 리퀘스트와 커밋 기록은 남는다 끝난 브랜치에 실수로 다시 커밋하는 일

GitHub Docs는 2단계에서 “서로 관련 없는 변경은 브랜치를 따로 만들라”고 권한다[G5]. 한 브랜치에 여러 변경이 섞이면 리뷰하기 어렵고, 그중 하나가 늦어지면 나머지도 함께 묶인다. 이 장의 브랜치 하나는 이슈 하나에 대응한다.

1-3. 읽기: 푸시 거부

두 사람이 한 원격 저장소를 쓸 때의 일을 출력으로 읽는다. 키트의 make_sandbox.sh는 원격 역할을 하는 bare 저장소 origin.git(작업 폴더 없이 .git의 내용만 가진 저장소. GitHub의 저장소가 이런 형태이다)과 그것을 클론한 두 폴더 a(개발자A), b(개발자B)를 내 PC에 만든다. 학습자는 이 도구를 7-2에서 처음 실행한다. 아래는 집필용 PC의 Git Bash에서 얻은 출력이며, 경로는 /c/Users/「아이디」/로 바꾸었다.

두 사람이 같은 시점의 main에서 각자 커밋한다. A가 먼저 커밋하고 푸시한다. 이어서 B가 A의 푸시를 받지 않은 채 자기 커밋을 푸시한다.

$ cd ~/ch03-sandbox/a
$ echo "A의 메모" > a.txt && git add a.txt && git commit -m "A: 메모 추가" && git push
[main d04fa3a] A: 메모 추가
(…)
   1b43bc4..d04fa3a  main -> main
$ cd ~/ch03-sandbox/b
$ echo "B의 메모" > b.txt && git add b.txt && git commit -m "B: 메모 추가" && git push
[main 3819435] B: 메모 추가
(…)
To C:/Users/「아이디」/ch03-sandbox/origin.git
 ! [rejected]        main -> main (fetch first)
error: failed to push some refs to 'C:/Users/「아이디」/ch03-sandbox/origin.git'
hint: Updates were rejected because the remote contains work that you do not
hint: have locally. This is usually caused by another repository pushing to
hint: the same ref. If you want to integrate the remote changes, use
hint: 'git pull' before pushing again.
hint: See the 'Note about fast-forwards' in 'git push --help' for details.

&&는 앞 명령이 성공했을 때만 뒤 명령을 실행한다. B의 [rejected] ... (fetch first)는 “원격에 내가 모르는 커밋이 있으니 먼저 받아 오라”는 뜻이다. 파일 주고받기였다면 B의 파일이 A의 수정을 덮었을 자리에서, Git은 B를 멈춘다.

결과 읽기: 푸시 거부의 네 갈래. 이 장의 푸시 거부는 거부 줄의 괄호와 remote: 줄로 네 갈래를 가린다. 갈래마다 할 일이 다르므로 갈래를 먼저 정한다. ①과 ②는 연습 저장소에서 실제로 얻은 출력이다.

① ! [rejected]        main -> main (fetch first)
   원격에 내가 받지 않은 커밋이 있다 → 받아서 합친 뒤 푸시(바로 아래)
② ! [rejected]        main -> main (non-fast-forward)
   받기(fetch)는 했으나 합치지 않았다. git status -sb가 [ahead 1, behind 1]
   → 합친 뒤 푸시. 리베이스한 내 작업 브랜치라면 7-5
③ remote: error: GH006: Protected branch update failed for refs/heads/main.
   ! [remote rejected] main -> main (protected branch hook declined)  (예시)
   저장소 규칙이 막았다 → 받아 와도 풀리지 않는다. 브랜치와 PR로(8-4)
④ remote: Permission to 「교수 계정」/ict-aisw-2027-team01-lab.git denied to 「아이디」.
   fatal: unable to access '…': The requested URL returned error: 403   (예시)
   쓰기 권한이 없다 → 0-3의 권한 확인. 팀 배정은 교수에게
# 어느 갈래도 강제 푸시(--force)로 풀지 않는다

B는 원격의 커밋을 받아 자기 커밋과 합친 뒤 다시 푸시해야 한다. 받는 방법은 4-2에서 자세히 다룬다. git pull --rebase는 원격의 커밋을 받은 뒤 내 커밋을 그 위로 옮겨 붙인다.

$ git pull --rebase
(…)
Successfully rebased and updated refs/heads/main.
$ git log --oneline --graph
* 5138304 B: 메모 추가
* d04fa3a A: 메모 추가
* 1b43bc4 팀 실습 저장소의 시작 파일
$ git push
   d04fa3a..5138304  main -> main

A의 커밋 위에 B의 커밋이 올라가 한 줄의 기록이 되었고 푸시가 받아들여졌다. B의 커밋 해시가 3819435에서 5138304로 바뀐 것에 주의한다. 커밋을 옮겨 붙이면 새 커밋이 만들어진다. 두 사람이 서로 다른 파일을 고쳤으므로 충돌은 없었다. 같은 줄을 고친 경우는 7절에서 다룬다.

1-4. 사례: 여러 작업자가 쓰는 저장소의 작업 규칙

이 교재의 원본도 Git 저장소이다. 교수 한 사람이 쓰지만, 연구실 컴퓨터와 집 컴퓨터, 그리고 여러 개의 AI 코딩 도구 세션이 같은 저장소에 커밋한다. 사람이 둘 이상인 팀과 같은 조건이다. 이 저장소의 작업 규칙은 다음과 같다.

  1. 파일을 고치기 전에 git fetch로 원격의 main과 새 브랜치를 확인한다.
  2. 관련 파일만 골라 git add 한다. git add -A를 쓰지 않는다.
  3. 커밋한 뒤 git pull --rebase origin main을 하고 푸시한다.
  4. 강제 푸시를 하지 않는다. 이미 푸시한 커밋을 고쳐 쓰지 않는다.
  5. 다른 브랜치가 고치고 있는 파일은 그 브랜치가 합쳐질 때까지 건드리지 않는다.

규칙마다 막는 사고가 있다. 1번은 낡은 판에서 작업을 시작하는 일을, 2번은 다른 세션이 만들다 만 파일이 내 커밋에 섞이는 일을, 3번은 1-3에서 본 푸시 거부를, 4번은 다른 컴퓨터가 이미 받아 간 커밋이 원격에서 사라지는 일을, 5번은 같은 파일을 두 세션이 고쳐 충돌하는 일을 막는다. AI 코딩 도구는 지시받은 범위를 넘어 여러 파일을 한 번에 고칠 수 있으므로, 2번 규칙처럼 “커밋할 파일을 사람이 고른다”는 원칙이 특히 중요하다. 이 장의 팀 실습 저장소 README도 같은 원칙을 담고 있다.

2. 저장소의 소유자와 권한

2-1. 개인 계정의 저장소와 조직의 저장소

GitHub의 저장소는 소유자가 개인 계정이거나 조직(Organization)이다. 2장의 llm-service-lab은 학습자 개인 계정의 저장소이다. 개인 계정의 저장소에서 다른 사람과 함께 일하려면 그 사람을 협업자(collaborator)로 한 명씩 초대한다. 협업자는 저장소를 읽고 푸시할 수 있으며, 비공개 저장소의 협업자에게 읽기 전용 권한만 주는 방법은 없다. 설정을 바꾸고 협업자를 더하는 것은 소유자뿐이다[G13].

조직은 여러 사람이 저장소를 함께 소유하는 계정이다. 조직 안에 팀(team)을 만들고, 저장소 권한을 사람 단위가 아니라 팀 단위로 준다[G11]. 팀원이 바뀌면 팀 명단만 고치면 되고, 사람이 떠나도 저장소는 조직에 남는다.

이 과목은 조직을 쓰지 않는다. 교수 계정에 팀마다 비공개 저장소 <팀>-lab을 만들고 팀원을 협업자로 초대한다. 팀원은 모두 write에 해당하는 권한을 받고, admin에 해당하는 일은 소유자인 교수만 한다. 프로젝트실습Ⅰ 저장소 <팀>-project도 교수 계정에 둔다.

요금제에 따라 쓸 수 있는 기능이 다르다. GitHub의 요금제 안내는 비공개 저장소의 보호 브랜치와 필수 리뷰어를 개인 계정에서는 GitHub Pro, 조직에서는 GitHub Team의 기능으로 적는다[G12]. 보호 규칙은 저장소 소유자의 요금제를 따르므로, 8절의 보호 규칙은 교수 계정이 GitHub Pro이기에 동작한다.

[최신 자료 자리: GitHub 요금제별 보호 기능과 개인 계정 저장소의 권한] 비공개 저장소의 보호 브랜치·규칙 집합을 쓸 수 있는 요금제, 개인 계정 저장소의 협업자 권한. 확인할 곳 docs.github.com의 「GitHub’s plans」, 「About rulesets」, 「Permission levels for a personal account repository」. 2026-11-17 값: 보호 브랜치는 Pro·Team 이상, 규칙 집합은 Team·Enterprise 대상(Pro는 적지 않음), 개인 계정 저장소의 협업자는 쓰기 권한만 받는다.

2-2. 저장소의 기본 권한

조직의 저장소에는 다섯 가지 기본 권한이 있다. 개인 계정 저장소의 협업자와 소유자는 이 가운데 write와 admin에 해당한다. GitHub Docs는 권한마다 권장하는 대상을 다음과 같이 적는다[G11]. 2026-11 기준 문서에는 이슈와 토론의 관리만 맡는 moderate 권한도 함께 실려 있으나, 이 과목에서는 쓰지 않는다.

권한 권장 대상 (GitHub Docs의 설명을 옮김) 조직을 쓴다면 줄 사람
read 코드에 기여하지 않고 프로젝트를 보거나 토론하는 사람 다른 팀의 학습자
triage 쓰기 권한 없이 이슈와 풀 리퀘스트를 적극적으로 관리하는 사람 조교
write 프로젝트에 적극적으로 푸시하는 사람 팀원 전원(이 과목의 협업자)
maintain 민감하거나 파괴적인 작업 없이 저장소를 관리하는 프로젝트 관리자 프로젝트실습Ⅰ 팀장(선택)
admin 민감하고 파괴적인 작업을 포함해 프로젝트 전체에 접근하는 사람 교수(이 과목의 소유자)

표에서 두 가지를 눈여겨본다. 첫째, 리뷰는 read 권한만 있어도 남길 수 있지만, 병합에 필요한 “필수 승인”으로 세어지는 것은 write 이상 권한을 가진 사람의 승인뿐이다[G11]. write가 없는 사람이 승인을 눌러도 필수 승인 수는 채워지지 않는다. 둘째, 보호 규칙을 바꿀 수 있는 것은 admin(개인 계정에서는 소유자)뿐이다. 팀원 모두에게 admin을 주면 누구든 규칙을 끄고 main에 직접 푸시할 수 있으므로, admin은 꼭 필요한 사람에게만 준다. 필요한 만큼만 권한을 주는 이 원칙을 최소 권한의 원칙이라 한다. 0-3에서 본 권한 출력의 "push":true, "admin":false가 협업자인 팀원의 권한이다.

3. 이슈

3-1. 이슈의 구성

이슈(issue)는 저장소에 딸린 할 일 카드이다. 버그 보고, 기능 제안, 문서 수정, 질문처럼 “해야 하거나 결정해야 하는 일” 하나를 적는다. 이슈에는 번호가 붙고(#1, #2…), 이 번호는 같은 저장소의 풀 리퀘스트와 같은 번호 체계를 쓴다. 이슈 #1 다음에 풀 리퀘스트를 열면 그 풀 리퀘스트가 #2가 된다.

구성 요소 뜻 정하는 사람
제목 할 일을 한 줄로. 동사로 끝나게 쓴다(예: “팀원 소개 파일을 추가한다”) 작성자
본문 무엇을, 왜, 완료 조건. 마크다운으로 쓴다 작성자
담당자(assignee) 이 일을 맡은 사람. 여러 명도 가능하다 triage 이상
라벨(label) 일의 종류와 상태를 나타내는 꼬리표(작업, 버그, 문서 등) 붙이기는 triage 이상, 만들기는 write 이상
마일스톤(milestone) 마감일이 있는 이슈 묶음. 진행률이 백분율로 보인다 붙이기는 triage 이상, 만들기는 write 이상
연결된 풀 리퀘스트 이 이슈를 처리하는 변경. 오른쪽 「Development」 칸에 보인다 자동 또는 write 이상

3-2. 이슈의 완료 조건

좋은 이슈는 읽은 사람이 “이 일이 끝났는지”를 판정할 수 있게 쓴 이슈이다. “README 정리”라는 이슈는 언제 닫아야 하는지 알 수 없다. “README의 작업 규칙 절에 브랜치 이름 규칙을 추가한다. 완료 조건: 규칙 절에 <이슈 번호>-<동사>-<대상> 형식과 예시 하나가 있다”는 이슈는 판정할 수 있다. 1장에서 한 줄 요청과 요구 목록 요청을 비교하였는데, 이슈도 같다. 완료 조건은 이슈의 요구 목록이다.

나쁜 이슈 빠진 것 고친 이슈
로그인 고치기 무엇이 문제인지, 언제 끝나는지 비밀번호가 틀렸을 때 안내 문구가 나오지 않는다. 완료 조건: 틀린 비밀번호로 로그인하면 “비밀번호가 맞지 않습니다”가 보인다
디자인 개선 범위 공고 목록 화면의 글자 대비를 WCAG 2.2 AA(4.5:1) 이상으로 맞춘다. 완료 조건: 본문 글자 색 대비 측정값이 4.5 이상
이거 왜 안 돼요? 재현 방법, 기대한 결과 python app.py 실행 시 ModuleNotFoundError: fastapi. 기대: 서버가 8000번에서 뜬다. 재현: 새 가상 환경에서 실행
회의록 할 일이 아니다 회의에서 정한 일을 각각 이슈로 나눈다

한 이슈는 한 사람이 한 브랜치에서 끝낼 수 있는 크기로 쓴다. 이슈 하나에 일이 여럿 들어 있으면 체크리스트로 나누거나 이슈를 쪼갠다.

3-3. 이슈 템플릿과 이슈 폼

같은 형식의 이슈를 여러 사람이 쓰면 템플릿이 필요하다. GitHub는 저장소의 .github/ISSUE_TEMPLATE/ 폴더에 든 파일을 이슈 템플릿으로 쓴다[G15]. 템플릿은 기본 브랜치에 병합되어야 동작한다. 팀 실습 저장소에는 키트가 넣어 둔 템플릿 task.md가 있다.

파일: team-lab/.github/ISSUE_TEMPLATE/task.md 
---
name: 작업 이슈
about: 한 사람이 한 브랜치에서 끝낼 수 있는 작업 하나를 적는다
title: "[작업] "
labels: ["작업"]
assignees: []
---

## 무엇을 하는가

(한두 문장. 예: `members/_양식.md`를 복사해 내 소개 파일을 추가한다)

## 왜 하는가

(이 작업이 필요한 까닭. 관련 이슈가 있으면 `#번호`로 적는다)

## 완료 조건

- [ ] (관찰할 수 있는 결과. 예: `members/<아이디>.md`가 main에 있다)
- [ ] 풀 리퀘스트가 승인을 받아 병합되었다

--- 사이의 부분은 YAML 머리말(front matter)이다. name과 about은 이슈를 만들 때 고르는 화면에 보이는 이름과 설명이고, title, labels, assignees는 새 이슈에 미리 채워지는 값이다. GitHub Docs는 템플릿 이름이 세 글자보다 길어야 목록에 나타난다고 적는다[G15]. 「작업」(두 글자) 대신 「작업 이슈」로 지은 까닭이다. 본문의 - [ ]는 체크박스이며, 이슈 화면에서 눌러 표시할 수 있다.

같은 폴더의 config.yml은 템플릿 고르는 화면을 설정한다.

파일: team-lab/.github/ISSUE_TEMPLATE/config.yml 
blank_issues_enabled: false
contact_links:
  - name: 수업 질문
    url: https://docs.github.com/en/issues
    about: 저장소 작업이 아닌 질문은 수업 시간에 하거나 교수에게 직접 묻는다. 이 링크는 GitHub 이슈 문서다.

blank_issues_enabled: false는 템플릿 없이 빈 이슈를 만드는 선택지를 숨긴다. 다만 write 이상 권한자에게는 「Blank issue」가 “Maintainers only” 표시와 함께 계속 보이고, read와 triage 권한자에게만 숨겨진다[G15]. contact_links는 이슈 대신 갈 곳(질문 게시판, 보안 신고 창구 등)을 고르는 화면에 링크로 보인다.

마크다운 템플릿 말고 이슈 폼(issue form)도 있다. .yml 파일에 입력 칸을 정의해 웹 화면에 양식으로 보이게 하고, required: true로 필수 입력(예: 재현 방법)을 강제한다. 마크다운 템플릿은 빈칸을 막지 못하지만 만들기 쉽다. GitHub Docs는 2026-11 기준으로 이슈 폼을 공개 미리 보기(public preview)로 표시한다[G15]. 이 과목은 마크다운 템플릿만 쓴다.

[최신 자료 자리: 이슈 폼의 상태와 기본 라벨] 이슈 폼이 아직 공개 미리 보기인지, 기본 라벨 열 개(3-4)가 그대로인지. 확인할 곳 docs.github.com의 「Configuring issue templates for your repository」, 「Managing labels」. 2026-11-14 값은 본문과 같다.

3-4. 라벨과 마일스톤

라벨은 이슈와 풀 리퀘스트에 붙이는 꼬리표이다. 새 저장소에는 기본 라벨이 들어 있다. 2026-11 기준 GitHub Docs가 적는 기본 라벨은 accessibility, bug, documentation, duplicate, enhancement, good first issue, help wanted, invalid, question, wontfix이다[G16]. 조직 소유자는 조직의 새 저장소에 들어갈 기본 라벨을 바꿀 수 있다.

라벨은 많을수록 좋지 않다. 라벨은 목록을 걸러 보기 위한 것이므로, 팀이 실제로 걸러 볼 기준만 둔다. 팀 실습 저장소에는 교수가 키트의 도구/labels_lab.tsv에 적힌 여섯 개의 라벨(작업, 문서, 버그, 충돌 실습, 리뷰 필요, 질문)을 미리 만들어 두었다. 이 파일은 한 줄에 「이름, 색, 설명」을 탭으로 나누어 적은 것이고, 키트의 labels.sh가 한 줄씩 읽어 gh label create --force(같은 이름이 있으면 고침)를 실행한다. DRY_RUN=1을 붙이면 명령만 보인다. 9-5에서 이 도구를 쓴다.

$ DRY_RUN=1 bash labels.sh labels_lab.tsv "$OWNER/$REPO" | head -2
gh label create "작업" --color 1d76db --description "한 브랜치에서 끝낼 수 있는 작업" --force -R 「교수 계정」/ict-aisw-2027-team01-lab
gh label create "문서" --color 0075ca --description "문서의 추가와 수정" --force -R 「교수 계정」/ict-aisw-2027-team01-lab

마일스톤은 마감일이 있는 이슈와 풀 리퀘스트의 묶음이다. 마일스톤 화면에는 설명, 마감일, 완료율, 열린 항목과 닫힌 항목의 수가 보인다[G17]. 프로젝트실습Ⅰ이라면 “중간 발표” 같은 마일스톤을 만들고 그때까지 끝낼 이슈를 묶는다. 완료율은 닫힌 항목의 비율로 계산되므로, 이슈를 닫는 습관이 없으면 마일스톤의 숫자는 의미가 없다.

4. 브랜치와 풀 리퀘스트

4-1. 브랜치와 병합의 기초, 이름 규칙

브랜치. 브랜치는 커밋 하나를 가리키는 이름표이다. 새 커밋을 만들면 지금 있는 브랜치의 이름표가 그 커밋으로 옮겨 가고, 다른 브랜치는 그대로 있다. git switch -c <이름>은 지금 커밋에서 새 브랜치를 만들고 그리로 옮겨 가며, git switch <이름>은 있는 브랜치로 옮겨 간다. git branch는 브랜치 목록을 보이고 지금 있는 곳에 *를 붙인다.

두 가지 병합. git merge <브랜치>는 그 브랜치의 커밋을 지금 브랜치에 합친다. 합치는 쪽(main)에 그사이 새 커밋이 없으면 Git은 이름표를 앞으로 옮기기만 한다. 이것이 빨리 감기(fast-forward)이며 새 커밋이 생기지 않는다. 양쪽에 서로 없는 커밋이 있으면 부모가 둘인 병합 커밋(merge commit)을 새로 만든다. --no-ff를 붙이면 빨리 감기가 가능해도 병합 커밋을 만들어 “여기서 한 갈래가 합쳐졌다”는 기록을 남긴다. GitHub의 「Create a merge commit」이 이 방식이다(6-1).

그래프 읽기. 다음은 연습 저장소(7-2)에서 브랜치 둘을 만들어 하나는 그냥, 하나는 --no-ff로 합친 출력이다.

$ git switch -c 1-add-memo
Switched to a new branch '1-add-memo'
(memo.txt를 만들어 커밋하고 git switch main)
$ git merge 1-add-memo
Updating 392ed47..e5eafcf
Fast-forward
(2-add-todo 브랜치에서 todo.txt를 커밋하고 git switch main)
$ git merge --no-ff 2-add-todo -m "Merge branch '2-add-todo'"
Merge made by the 'ort' strategy.
$ git log --oneline --graph
*   fb3b943 Merge branch '2-add-todo'
|\  
| * e10477e 할 일 추가
|/  
* e5eafcf 메모 추가
* 392ed47 팀 실습 저장소의 시작 파일

--graph에서 *는 커밋, |와 /, \는 갈래의 선이다. 빨리 감기로 합친 e5eafcf는 갈래 없이 한 줄에 놓이고, --no-ff로 합친 fb3b943에서는 갈래가 갈라졌다가(|\) 다시 만난다(|/). git log --merges --format="%h %p %s"로 보면 fb3b943 e5eafcf e10477e …처럼 부모가 둘 적힌다.

이름 규칙. GitHub Docs는 브랜치 이름을 increase-test-timeout처럼 짧고 설명적으로 지으라고 권한다[G5]. 팀은 여기에 규칙을 더해 이름만 보고도 무슨 일인지 알 수 있게 한다. 이 과목의 규칙은 <이슈 번호>-<동사>-<대상>이다. 3-add-member-hong은 이슈 #3, 무엇을 하는지(add), 무엇에(member-hong)가 다 보인다. 반면 hong처럼 사람 이름만 쓰면 무슨 일인지 모르고 한 사람이 브랜치를 둘 만들면 구분되지 않는다. fix처럼 짧은 낱말은 무엇을 고치는지 모르고, 같은 이름이 이미 있으면 만들 수도 없다.

영문 소문자와 숫자, 하이픈(-)만 쓰는 것이 안전하다. Git은 한글 브랜치 이름도 받아들이지만, 셸에서 입력하기 번거롭고 일부 도구가 주소를 깨뜨려 보인다. Git이 허용하지 않는 이름은 git check-ref-format으로 미리 확인할 수 있다. 다음은 그 출력이다.

$ git check-ref-format --branch "3-add-member-hong"
3-add-member-hong
$ git check-ref-format --branch "3 add member"
fatal: '3 add member' is not a valid branch name
$ git check-ref-format --branch "feature..x"
fatal: 'feature..x' is not a valid branch name

공백, 연속된 마침표(..), ~, ^, :, ?, *, [, 역슬래시가 금지 문자이고, 하이픈으로 시작하는 이름도 안 된다[G2]. gh issue develop 3 --name 3-add-member-hong --checkout처럼 이슈에서 바로 브랜치를 만들면 이슈 화면의 「Development」 칸에 나타난다. 이 장의 실습에서는 git switch -c를 쓴다.

4-2. fetch와 pull

팀 작업에서는 원격 저장소가 계속 바뀐다. 내 컴퓨터의 저장소는 원격의 변화를 저절로 알지 못한다. 원격의 상태를 받아 오는 명령이 둘 있다.

명령 하는 일 바뀌는 것 바뀌지 않는 것
git fetch 원격의 새 커밋과 브랜치를 내려받는다 원격 추적 브랜치(origin/main 등) 내 브랜치(main), 작업 폴더의 파일
git pull git fetch를 한 뒤, 받은 원격 브랜치를 내 현재 브랜치에 합친다 원격 추적 브랜치, 내 현재 브랜치, 작업 폴더의 파일 다른 로컬 브랜치

원격 추적 브랜치(remote-tracking branch)는 “마지막으로 받아 왔을 때 원격의 그 브랜치가 가리키던 커밋”을 내 저장소에 적어 둔 것이다. origin/main이 그 예이며, 이름 앞의 origin/이 원격의 이름이다. 이것은 마지막 fetch 시점의 기록일 뿐, 지금 이 순간 원격의 상태가 아니다. 이 차이가 팀 작업에서 가장 흔한 착각을 만든다. 1-3의 연습 저장소에서 읽어 본다. 1-3이 끝난 시점에 원격에는 B의 커밋이 올라가 있고, A는 아직 그것을 받지 않았다.

$ cd ~/ch03-sandbox/a
$ git status
On branch main
Your branch is up to date with 'origin/main'.

nothing to commit, working tree clean
$ git log --oneline -2 origin/main
d04fa3a A: 메모 추가
1b43bc4 팀 실습 저장소의 시작 파일

git status가 “up to date”라고 말하지만, 원격에는 B의 커밋이 이미 있다. git status는 원격에 묻지 않고, 내 저장소에 적힌 origin/main과 내 main을 비교할 뿐이기 때문이다. fetch로 그 기록을 새로 받고, 받은 것을 읽어 본 뒤, pull로 합친다.

$ git fetch
From C:/Users/「아이디」/ch03-sandbox/origin
   d04fa3a..5138304  main       -> origin/main
$ git status
On branch main
Your branch is behind 'origin/main' by 1 commit, and can be fast-forwarded.
  (use "git pull" to update your local branch)

nothing to commit, working tree clean
$ git log --oneline main..origin/main
5138304 B: 메모 추가
$ git diff --stat main origin/main
 b.txt | 1 +
 1 file changed, 1 insertion(+)
$ git pull --ff-only
Updating d04fa3a..5138304
Fast-forward
 b.txt | 1 +
 1 file changed, 1 insertion(+)
 create mode 100644 b.txt
$ git status -sb
## main...origin/main

fetch의 출력 d04fa3a..5138304 main -> origin/main은 원격 추적 브랜치 origin/main이 옮겨졌다는 뜻이다. 이제 git status는 “1 커밋 뒤처져 있다”고 정확히 말한다. main..origin/main은 “origin/main에는 있고 main에는 없는 커밋”이다. fetch만 한 상태에서는 작업 폴더의 파일이 바뀌지 않았으므로, 받은 변경을 먼저 읽고 합칠지 정할 수 있다. Fast-forward(빨리 감기)는 내 main에 원격에 없는 커밋이 하나도 없어서, 내 브랜치의 끝을 원격의 끝으로 옮기기만 하면 되는 경우이다. 새 커밋이 생기지 않는다.

git pull이 받은 커밋을 합치는 방법은 넷이다. 2026-11 기준 git 문서는 방법을 정하지 않으면 빨리 감기만 시도하고, 갈라진 경우에는 실패한다고 적는다[G2].

명령 합치는 방법 갈라진 경우(양쪽에 서로 없는 커밋이 있을 때)
git pull --ff-only 빨리 감기만 실패하고 멈춘다. 아무것도 바뀌지 않는다
git pull --rebase 내 커밋을 원격 커밋 위로 옮겨 붙인다 한 줄의 기록. 내 커밋의 해시가 바뀐다
git pull --no-rebase 병합 커밋을 만든다 두 갈래가 합쳐진 기록
git pull (설정 pull.rebase false) --no-rebase와 같다 병합 커밋을 만든다
git pull (설정 없음) 빨리 감기를 시도 아래의 힌트를 보이고 멈춘다

2장에서 pull.rebase false를 전역으로 설정한 계정에서는 git pull만 쳐도 병합 커밋으로 합친다. Windows의 Git for Windows는 설치할 때 이 값을 시스템 설정에 넣어 두므로(집필용 PC에서 git config --system --list로 확인), 전역 설정이 없어도 같다. 이 설정이 어디에도 없는 컴퓨터(대개 macOS)에서 1-3의 B가 git pull만 쳤다면 다음 힌트가 나온다. 설정을 모두 비운 상태에서 연습 저장소로 얻은 출력이다.

hint: You have divergent branches and need to specify how to reconcile them.
hint: You can do so by running one of the following commands sometime before
hint: your next pull:
hint:
hint:   git config pull.rebase false  # merge
hint:   git config pull.rebase true   # rebase
hint:   git config pull.ff only       # fast-forward only
hint: (…4줄 생략…)
fatal: Need to specify how to reconcile divergent branches.

이 장에서는 설정에 기대지 않고, 상황마다 명령에 방법을 적는다. 어느 컴퓨터에서 실행해도 같은 일이 일어나게 하기 위해서이다. GitHub flow에서는 main에 직접 커밋하지 않으므로, main을 받을 때는 언제나 git pull --ff-only로 충분하다. 이 명령이 실패한다면 main에 실수로 커밋했다는 신호이다. 내 작업 브랜치를 최신 main에 맞출 때는 7절의 git merge origin/main을 쓴다.

4-3. 풀 리퀘스트의 구성

풀 리퀘스트는 “내 브랜치의 변경을 기준 브랜치에 합쳐 달라”는 제안이다[G7]. 이름이 “끌어가 달라는 요청(pull request)”인 까닭은, 변경을 만든 사람이 직접 합치는 대신 저장소 쪽이 그 변경을 끌어가 합치게 하는 흐름에서 왔기 때문이다. GitLab은 같은 기능을 머지 리퀘스트(merge request)라 부른다.

구성 요소 뜻 이 과목의 규칙
base 브랜치 변경이 들어갈 브랜치 main
head(compare) 브랜치 변경이 들어 있는 브랜치 <이슈 번호>-<동사>-<대상>
제목 변경을 한 줄로 이슈 제목과 같게 쓴다
설명(본문) 무엇을, 왜, 리뷰어가 볼 곳, 확인한 것 저장소의 템플릿을 채운다. Closes #n 필수
리뷰어(reviewer) 검토를 요청받은 사람이나 팀 리뷰 순환의 다음 사람
담당자(assignee) 이 풀 리퀘스트를 끝까지 책임지는 사람 작성자 자신(@me)
초안(draft) 아직 리뷰받을 준비가 안 된 상태 작업 중에는 초안으로 연다

풀 리퀘스트 화면에는 탭이 넷 있다. 「Conversation」에는 설명, 코멘트, 리뷰, 커밋과 이벤트가 시간 순으로 쌓인다. 「Commits」는 브랜치의 커밋 목록, 「Checks」는 자동 검사의 결과, 「Files changed」는 리뷰어가 읽는 차이(diff)이다[G7]. 화면 아래쪽의 병합 상자(merge box)는 병합을 막는 것(충돌, 승인 부족, 실패한 검사)을 보이고, 막는 것이 없으면 「Merge pull request」 단추를 활성화한다.

[최신 자료 자리: GitHub 풀 리퀘스트 화면의 이름] 이 장이 인용하는 탭과 단추(「Files changed」, 「Ready for review」, 「Start a review」, 「Resolve conflicts」, 「Fix with Copilot」 등)의 이름. 확인할 곳 시연용 저장소의 PR 화면, docs.github.com의 「About pull requests」. 2026-11-14에 문서로만 확인하였다.

초안 풀 리퀘스트. 초안으로 연 풀 리퀘스트는 병합할 수 없고, 코드 소유자에게 리뷰가 자동으로 요청되지 않는다. 작업이 끝나면 「Ready for review」를 눌러 일반 풀 리퀘스트로 바꾸며, 언제든 다시 초안으로 돌릴 수 있다[G7]. 초안은 “아직 끝나지 않았지만 방향을 먼저 보여 주고 싶을 때” 쓴다. 다 만든 뒤에 처음 보여 주면, 방향이 틀렸을 때 고칠 양이 크다.

이슈 연결. 풀 리퀘스트의 설명에 연결 키워드와 이슈 번호를 적으면, 그 풀 리퀘스트가 기본 브랜치에 병합될 때 이슈가 자동으로 닫힌다[G6]. 연결 키워드는 close, closes, closed, fix, fixes, fixed, resolve, resolves, resolved의 아홉 개이다. 대소문자를 가리지 않고 뒤에 쌍점을 붙여도 된다(CLOSES: #3). 이슈가 여럿이면 Resolves #5, resolves #7처럼 이슈마다 키워드를 다시 쓰고, 다른 저장소의 이슈는 Fixes 조직/저장소#100처럼 쓴다. 자동으로 닫히는 것은 풀 리퀘스트가 기본 브랜치를 향할 때뿐이다. main이 아닌 다른 브랜치를 향한 풀 리퀘스트에서는 키워드가 무시된다[G6]. 키워드는 커밋 메시지에 써도 동작하지만, 그 경우 이슈 화면에 풀 리퀘스트가 연결 항목으로 나타나지 않는다. 이 과목에서는 풀 리퀘스트 설명에 적는다.

4-4. 따라 하기: 개인 저장소의 이슈에서 병합까지

팀 저장소에서 일을 시작하기 전에, 혼자 쓰는 개인 저장소에서 이슈 → 브랜치 → 초안 풀 리퀘스트 → 병합을 한 바퀴 돈다. 혼자서 실수해도 남에게 영향이 없는 곳에서 명령을 먼저 익히기 위해서이다. 만들 이슈는 “개인 저장소에 ch03/협업기록.md를 추가한다”이고, 이 파일의 빈칸은 9-5에서 채운다.

1) 이슈. 개인 저장소에 라벨 「작업」을 만들고 이슈를 만든다. gh issue create는 만든 이슈의 주소를 출력한다. 주소의 끝이 이슈 번호이므로 셸 변수에 담아 둔다. @me는 로그인한 나 자신을 가리킨다. ${URL##*/}는 셸의 문자열 자르기로, 마지막 /까지를 지우고 남은 부분(번호)을 얻는다.

터미널 
cd ~/llm-service-lab
gh label create "작업" --color 1d76db --description "한 브랜치에서 끝낼 수 있는 작업" --force
URL=$(gh issue create \
  --title "ch03 협업기록을 추가한다" \
  --body "3장 협업기록 양식을 ch03/협업기록.md로 복사한다. 완료 조건: main에 ch03/협업기록.md가 있다." \
  --label "작업" --assignee "@me")
ISSUE=${URL##*/}
echo "$URL / 이슈 번호: $ISSUE"

2) 브랜치와 커밋. 이슈 번호가 든 브랜치를 만들고, 양식을 복사해 커밋하고 푸시한다. 터미널을 새로 열어 $ISSUE가 비어 있으면, 둘째 줄이 이슈 목록에서 번호를 다시 찾는다.

3) 초안 풀 리퀘스트. 풀 리퀘스트의 설명은 파일로 먼저 쓴다. 명령줄의 --body "..."에 긴 글을 넣으면 따옴표와 줄바꿈이 꼬이기 쉬우므로 --body-file로 파일을 준다. 이 heredoc은 <<'EOF'가 아니라 <<EOF로 열었다. 따옴표가 없으면 셸이 $ISSUE를 실제 번호로 바꾸어 넣는다. 마지막 명령은 PR의 상태를 JSON으로 보이며, closingIssuesReferences는 이 PR이 병합되면 닫힐 이슈의 목록이다.

터미널

GitHub의 merge commit 병합은 --no-ff와 같아서, 원격의 main에는 부모가 둘인 c41f9a2가 생기고 그래프에 갈래가 남았다. 내 PC의 main은 그 커밋을 받기만 하므로 git pull --ff-only가 빨리 감기(Fast-forward)로 끝난다. gh가 병합 뒤에 이미 받아 왔으면 Already up to date.가 나온다. 7d0e5b1은 2장의 마지막 커밋이며 해시와 제목은 사람마다 다르다. git fetch --prune은 원격에서 지워진 브랜치의 원격 추적 브랜치를 지운다.

개인 저장소 한 바퀴의 복기. 혼자 쓰는 저장소에서 GitHub flow를 한 바퀴 돌았다.

  1. 일을 기록으로 시작하였다. 브랜치 이름과 PR 설명이 이슈 번호를 가리켰고, 병합으로 이슈가 닫혔다.
  2. 변경을 사람이 먼저 읽었다. 초안 PR과 gh pr diff는 “합치기 전에 읽는다”는 단계이다.
  3. 기록의 모양을 골랐다. merge commit으로 병합해 갈래와 합류가 main에 남았다.

5. 코드 리뷰

5-1. 리뷰의 세 가지 결정

GitHub에서 리뷰를 마칠 때는 세 가지 결정 중 하나를 고른다[G7].

결정 뜻 고르는 경우
Comment 승인도 변경 요청도 아닌 일반 의견 질문만 있거나 아직 판단하지 못하였을 때
Approve 병합해도 된다 완료 조건을 충족하고, 남은 의견이 모두 사소할 때
Request changes 병합 전에 반드시 고쳐야 할 것이 있다 완료 조건 미충족, 오류, 충돌 표시나 비밀 정보가 남았을 때

몇 가지 규칙이 이 결정에 붙어 있다.

  • 풀 리퀘스트의 작성자는 자기 풀 리퀘스트를 승인할 수 없다[G7]. 그래서 혼자 쓰는 저장소에서는 승인 단계가 생기지 않는다. 4-4의 개인 저장소 연습에서 승인을 건너뛴 까닭이다.
  • 리뷰는 read 권한만 있어도 남길 수 있지만, 보호 규칙의 “필수 승인 수”에 세어지는 것은 write 이상 권한을 가진 사람의 승인이다[G11].
  • 리뷰어를 지정해 리뷰를 요청하면 그 사람에게 알림이 간다. 리뷰를 요청하려면 저장소에 write 권한이 있어야 한다[G7].
  • 리뷰를 받은 뒤 작성자가 커밋을 더 하면, 리뷰어에게 다시 리뷰를 요청할 수 있다(「Conversation」 탭 오른쪽 칸에서 리뷰어 이름 옆의 동기화 아이콘)[G18]. 보호 규칙에 “새 커밋이 오면 기존 승인을 무효로 한다(dismiss stale approvals)”가 켜져 있으면 승인을 다시 받아야 한다[G9].

5-2. 줄 코멘트와 제안

리뷰는 「Files changed」 탭에서 한다. GitHub Docs가 적는 순서는 다음과 같다[G7].

  1. 「Files changed」를 연다. 파일을 하나씩 읽고, 오른쪽의 연결된 이슈로 맥락을 확인한다.
  2. 줄에 마우스를 올리면 나타나는 파란 + 아이콘을 눌러 그 줄에 코멘트를 쓴다. 여러 줄은 첫 줄 번호를 누르고 마지막 줄 번호까지 끌거나 Shift를 누른 채 누른다.
  3. 첫 코멘트에서 「Start a review」를 누르면 코멘트가 바로 게시되지 않고 대기(pending) 상태로 모인다. 대기 중인 코멘트는 나만 보이고, 게시 전까지 고칠 수 있다.
  4. 다 읽은 파일은 머리줄 오른쪽의 「Viewed」를 체크한다. 파일이 접히고, 진행 막대에 읽은 파일 수가 보인다. 그 파일이 나중에 바뀌면 체크가 풀린다.
  5. 「Review changes」를 눌러 요약 코멘트를 쓰고, 세 결정 중 하나를 골라 「Submit review」를 누른다.

[그림 자리: 「Files changed」 탭의 줄 코멘트 상자] 줄 코멘트 상자를 연 화면(파란 + 아이콘, 제안 아이콘, 「Start a review」 단추). 찍을 곳: GitHub 웹, 시연용 저장소 PR의 「Files changed」 탭.

제안(suggestion). 한두 줄을 고치는 의견은 말로 설명하는 것보다 고친 문장을 직접 보이는 편이 빠르다. 코멘트 상자의 제안 아이콘을 누르면 다음 블록이 들어가고, 블록 안의 줄을 고쳐 쓴다.

[브라우저] · 줄 코멘트 상자에 쓰는 내용

역할 칸이 양식 문구 그대로 남아 있다. 역할을 적어 주면 좋겠다.
```suggestion
- 역할: B
```

write 권한이 있는 사람은 제안 아래의 「Commit suggestion」을 눌러 그 자리에서 커밋할 수 있다. 제안이 여럿이면 「Add suggestion to batch」로 모은 뒤 「Commit suggestions」로 한 커밋에 반영한다. 제안을 적용한 사람이 커밋한 사람이 되고, 제안한 리뷰어는 공동 작성자(co-author)로 기록된다[G18].

대화의 해결. 줄 코멘트 하나하나는 대화(conversation)이다. 작성자가 의견을 반영하면 「Resolve conversation」을 눌러 닫는다. 보호 규칙에 “모든 대화가 해결되어야 병합할 수 있다”를 걸면, 닫히지 않은 대화가 병합을 막는다[G9].

5-4. AI 도구를 이용한 설명과 리뷰 초안

Claude Code는 터미널에서 git과 gh를 실행할 수 있으므로 풀 리퀘스트를 직접 만들 수도 있다. Claude Code 공식 문서의 일반 작업 흐름에는 “변경을 요약해 달라”, “PR을 만들어 달라”, “보안 개선에 대한 맥락을 더해 PR 설명을 보강해 달라”는 단계가 실려 있고, 만들어진 PR을 제출하기 전에 검토하라는 팁이 함께 있다[C1]. 같은 문서는 Claude가 gh pr create로 PR을 만들면 그 세션이 PR에 연결되어, 나중에 claude --from-pr <번호>로 그 세션을 다시 찾을 수 있다고 적는다. 2026-11 기준 Claude Code(2.1.296)의 명령 목록에는 현재 변경이나 지정한 PR을 검토하는 /code-review(별칭 /review)가 있고, --comment를 붙이면 결과를 GitHub의 PR에 바로 게시한다[C2]. 이 장에서 /code-review는 교수 시연으로만 본다.

[최신 자료 자리: Claude Code의 판과 PR 관련 명령] claude --version, /code-review(별칭 /review)의 옵션, claude --from-pr. 확인할 곳 code.claude.com/docs/en/commands, 같은 곳의 common-workflows. 2026-11-15 값: 2.1.296, 세 가지 모두 문서에 있음.

이 과목에서는 AI 도구에게 초안을 파일로 쓰게 하고, 게시는 사람이 한다. 까닭은 셋이다.

  1. 책임. 리뷰의 승인은 “내가 읽고 확인했다”는 서명이다. AI가 쓴 지적을 확인 없이 게시하면, 틀린 지적에도 내 이름이 붙는다.
  2. 사실과 다른 내용. AI 도구는 diff에 없는 내용(“테스트를 모두 통과했다”, “성능이 개선되었다”)을 그럴듯하게 덧붙이거나, 존재하지 않는 줄을 지적할 수 있다. 1장에서 본 확률적 생성의 성질이다.
  3. 범위. AI 도구는 변경과 관계없는 개선(다른 파일의 문체, 구조 변경)까지 제안하는 경향이 있다. 리뷰는 이 PR의 범위 안에서 한다.

절차는 다음과 같다. 9-3(PR 설명)과 9-4(리뷰)에서 이 절차를 그대로 따른다.

  1. 사람이 git diff main...HEAD 또는 gh pr diff로 변경을 먼저 직접 읽는다.
  2. Claude Code에게 범위(이 diff, 이 템플릿)와 금지 사항(게시하지 말 것, diff에 없는 내용을 쓰지 말 것)을 준 프롬프트로 초안을 ~/ch03-drafts/의 파일에 쓰게 한다.
  3. 사람이 초안의 문장마다 diff의 해당 줄을 찾아 대조하고, 찾지 못한 문장은 지운다.
  4. 사람이 범위 밖의 제안을 지우고, 빠진 것(Closes #n 등)을 더한다.
  5. 사람이 고친 초안을 gh pr create --body-file, gh pr review --body-file로 게시한다. PR 설명의 「AI 도구의 사용」 절에 사용 사실과 사람이 고친 곳을 적는다.

Claude Code가 gh pr create나 git push처럼 원격을 바꾸는 명령을 실행하려 하면, 권한 설정에 따라 실행 전에 확인을 묻는다(2장). 이 장에서는 그 질문에 허용하지 않는다. 프롬프트에서 미리 금지해 두면 질문이 나오는 일 자체가 줄어든다. 초안 폴더 ~/ch03-drafts/는 Claude Code를 시작한 폴더 밖에 있으므로 파일을 쓸 때 확인을 물을 수 있다. 그때는 그 파일 하나에 대해서만 허용한다.

6. 병합 방식

6-1. 세 가지 병합 방식

GitHub의 병합 상자에는 「Merge pull request」 단추 옆에 화살표가 있고, 저장소가 허용한 병합 방식 가운데 하나를 고를 수 있다. GitHub Docs가 설명하는 세 방식은 다음과 같다[G8].

방식 GitHub의 단추 하는 일 main의 기록
merge commit Create a merge commit 브랜치의 모든 커밋을 그대로 두고, 둘을 잇는 병합 커밋을 새로 만든다. git merge --no-ff에 해당한다 갈래와 합류가 보인다. 커밋이 모두 남는다
squash Squash and merge 브랜치의 커밋을 하나로 합친 새 커밋을 main 위에 올린다 한 줄. PR 하나가 커밋 하나
rebase Rebase and merge 브랜치의 커밋을 하나씩 main 위에 다시 만들어 올린다. 병합 커밋이 없다 한 줄. 커밋은 모두 남지만 해시가 새로 바뀐다

방식마다 잃는 것이 있다. GitHub Docs가 적는 주의 사항을 정리하면 다음과 같다[G8].

  • squash는 원래 커밋들의 해시와 시점, 중간 커밋의 작성자 정보를 잃는다. 스쿼시 병합 뒤에 같은 브랜치에서 계속 작업해 다시 PR을 열면, 이미 합친 커밋이 새 PR에 또 나타나고 같은 충돌을 되풀이해 풀게 된다. 스쿼시로 병합한 브랜치는 지우고 새로 만든다.
  • rebase는 GitHub가 커밋을 새로 만들므로 커미터 정보와 해시가 모두 바뀐다. 처음부터 비어 있던 커밋은 버린다. 충돌이 있으면 작성자가 로컬에서 리베이스하고 강제 푸시해야 이 방식을 쓸 수 있다.
  • merge commit은 기록이 복잡해 보이지만 아무것도 잃지 않는다. 특히 브랜치에서 충돌을 해결한 병합 커밋이 main의 기록에 그대로 남는다.
고르는 기준 merge commit squash rebase
작업 중 커밋(“오타 수정”, “다시 시도”)이 많다 그대로 남는다 하나로 정리된다 그대로 남는다
PR 단위로 되돌리기(git revert) 병합 커밋 하나를 되돌린다(-m 1 필요) 커밋 하나를 되돌린다 커밋 여러 개를 되돌려야 한다
브랜치에서 한 충돌 해결이 main에 남는가 남는다 사라진다(결과만 남는다) 사라진다

정답은 팀이 정한다. 저장소 관리자는 Settings의 「Pull Requests」에서 허용할 방식을 고르고, 「Automatically delete head branches」로 병합한 브랜치를 자동으로 지우게 할 수 있다. 이 장의 팀 실습 저장소는 merge commit만 허용하고 브랜치 자동 삭제를 켜 두었다. 9절에서 해결한 충돌이 main의 기록에 남아야 완료 기준을 점검할 수 있기 때문이다.

7. 병합 충돌

7-1. 충돌이 생기는 조건

병합은 세 판을 비교한다. 두 브랜치가 갈라진 지점의 판(공통 조상, merge base), 내 쪽의 판(ours), 상대 쪽의 판(theirs)이다. Git은 공통 조상과 비교해 한쪽만 바꾼 곳은 바뀐 쪽을 택하고, 양쪽이 같은 곳을 서로 다르게 바꾼 경우에만 멈춘다. 이것을 삼방향 병합(three-way merge)이라 한다[G1].

상황 Git의 처리 충돌 종류
서로 다른 파일을 고쳤다 자동으로 합친다 없음
같은 파일의 떨어진 줄을 고쳤다 자동으로 합친다 없음
같은 파일의 같은 줄을 다르게 고쳤다 멈춘다 내용 충돌(content)
같은 파일의 바로 붙은 줄을 각각 고쳤다 멈춘다 내용 충돌(content)
같은 파일의 끝에 서로 다른 줄을 덧붙였다 멈춘다 내용 충돌(content)
한쪽은 파일을 지우고 다른 쪽은 고쳤다 멈춘다 수정/삭제 충돌(modify/delete)

“바로 붙은 줄”과 “끝에 덧붙이기”는 직관과 다르므로 이 교재를 쓰며 git 2.55로 시험해 보았다. 여섯 줄 파일에서 한 브랜치는 3번 줄을 고치고, 다른 브랜치가 3번 줄을 고치면 충돌, 4번 줄을 고쳐도 충돌, 5번 줄을 고치면 자동 병합이었다. 두 브랜치가 각각 파일 끝에 다른 한 줄을 덧붙인 경우에도 충돌하였다. 바뀐 두 곳 사이에 바뀌지 않은 줄이 하나도 없으면 Git은 두 변경을 하나의 덩어리로 보고 어느 순서로 놓을지 묻는다.

팀 실습 저장소의 서비스소개.md에서 짝 1이 고치는 「한 줄 소개」 줄과 짝 2가 고치는 「핵심 기능」 줄 사이에 바뀌지 않는 줄을 여러 개 둔 까닭이 이것이다. 팀 실습 저장소 README가 “팀원 목록 표에 이름을 덧붙이지 말고 사람마다 파일을 만들라”고 정한 까닭도 같다. 여러 사람이 한 파일의 끝에 줄을 덧붙이면 거의 반드시 충돌한다.

7-3. 충돌 표시

충돌한 파일을 연다. Git은 충돌한 곳에 양쪽의 내용을 표시와 함께 넣어 두었다.

## 한 줄 소개

<<<<<<< HEAD
- 한 줄 소개: 자기소개서 초안을 AI가 검토해 고칠 곳을 알려 주는 서비스
=======
- 한 줄 소개: 채용 공고를 한곳에 모아 마감일 순으로 보여 주는 서비스

## 대상 사용자

<<<<<<< HEAD부터 =======까지가 내 쪽(지금 있는 브랜치 2-write-intro-b)의 내용이고, =======부터 >>>>>>> origin/main까지가 상대 쪽(합치려는 origin/main)의 내용이다. 표시 바깥의 줄(## 한 줄 소개, ## 대상 사용자)은 충돌하지 않은 부분이며 이미 합쳐진 상태이다. 충돌 해결은 표시 세 줄을 지우고 그 사이를 원하는 최종 내용으로 바꾸는 일이다. 어느 한쪽을 고를 수도 있고, 둘을 합친 새 문장을 쓸 수도 있다.

기본 표시는 공통 조상의 내용을 보이지 않으므로, “원래 무엇이었는데 양쪽이 각각 어떻게 바꾸었는가”를 알 수 없다. 표시 방식을 zdiff3로 바꾸면 공통 조상의 내용이 ||||||| 아래에 함께 보인다[G2]. 지금 충돌한 파일을 이 방식으로 다시 만들어 본다.

## 대상 사용자

base 아래의 (작성 전)이 공통 조상의 내용이다. 양쪽 모두 빈칸을 채운 것이므로, 어느 한쪽을 버리기보다 합치는 것이 맞다는 판단을 할 수 있다. 항상 이 방식으로 보려면 git config --global merge.conflictStyle zdiff3를 설정한다. zdiff3는 git 2.35에 들어왔으므로, 그보다 낮은 git에서는 diff3를 쓴다. 충돌 중에 Git은 공통 조상, 내 쪽, 상대 쪽을 단계(stage) 1, 2, 3으로 보관하므로, git show :1:서비스소개.md, :2:, :3:으로 세 판을 각각 볼 수도 있다[G2].

7-5. GitHub 웹 편집기를 이용한 해결

간단한 충돌은 GitHub 화면에서도 해결할 수 있다. GitHub Docs가 적는 절차는 다음과 같다[G10].

  1. 충돌이 있는 PR의 아래쪽에서 「Resolve conflicts」를 누른다.
  2. 편집기에 충돌 표시가 든 파일이 열린다. 충돌마다 내 쪽, 상대 쪽, 새 내용 중 하나로 고치고 충돌 표시를 지운다.
  3. 파일의 충돌을 다 고쳤으면 「Mark as resolved」를 누른다. 충돌한 파일이 여럿이면 왼쪽 목록에서 다음 파일을 골라 반복한다.
  4. 「Commit merge」를 누른다. 이 커밋은 PR의 브랜치(head)에 올라간다.
  5. 병합 상자로 돌아와 리뷰를 받고 「Merge pull request」를 누른다.

[그림 자리: GitHub 웹의 충돌 해결 편집기] 「Resolve conflicts」 편집기에서 충돌 표시가 강조된 화면과 「Mark as resolved」 단추. 찍을 곳: GitHub 웹, 시연용 저장소의 충돌한 PR.

웹 편집기로 해결할 수 있는 것은 같은 줄을 서로 다르게 고친 단순한 줄 충돌뿐이다. 수정/삭제 충돌, 이름 바꾸기 충돌 같은 그 밖의 충돌은 로컬에서 해결해야 하며, 그때는 「Resolve conflicts」 단추가 비활성화된다[G10]. 또한 웹에서 해결하면 기준 브랜치 전체가 PR의 브랜치에 병합되고, PR의 브랜치가 보호된 브랜치이면 새 브랜치를 만들어야 한다. 2026-11 기준 문서는 저장소에서 Copilot의 클라우드 에이전트를 켜 둔 경우 병합 상자에 「Fix with Copilot」 단추가 나타난다고 적는다. 이 과목에서는 쓰지 않는다. AI 도구가 충돌을 해결해도 최종 문장을 정하는 판단은 사람이 해야 하기 때문이다.

수정/삭제 충돌은 로컬에서 다음처럼 보인다. 연습용 저장소에서 얻은 출력이다.

$ git merge x
CONFLICT (modify/delete): f.txt deleted in x and modified in HEAD.  Version HEAD of f.txt left in tree.
Automatic merge failed; fix conflicts and then commit the result.
$ git status --short
UD f.txt

UD는 “내 쪽은 고침(U, updated), 상대 쪽은 지움(D, deleted)”이다. 파일을 남길 것이면 git add f.txt, 지울 것이면 git rm f.txt를 한 뒤 커밋한다. 이 판단은 파일의 내용이 아니라 “이 파일이 아직 필요한가”라는 팀의 결정이므로, 지운 사람과 먼저 이야기한다.

8. 보호 브랜치와 규칙 집합

8-1. 기본 브랜치 보호의 필요성

지금까지의 규칙(“main에 직접 커밋하지 않는다”, “강제 푸시를 하지 않는다”, “승인을 받은 뒤 병합한다”)은 사람이 지키는 약속이다. 약속은 바쁠 때, 실수할 때, 규칙을 모르는 새 팀원이 왔을 때 깨진다. AI 코딩 도구에게 넓은 권한을 준 경우에도 깨질 수 있다. GitHub는 이 약속의 일부를 저장소가 강제하게 하는 두 가지 장치를 준다. 보호 브랜치 규칙(branch protection rule)과 규칙 집합(ruleset)이다.

보호 규칙이 없는 main에서 일어날 수 있는 사고는 다음과 같다.

사고 결과 막는 규칙
리뷰 없이 main에 직접 푸시 아무도 읽지 않은 변경이 모든 팀원의 기준이 된다 병합 전 풀 리퀘스트 필수
승인 없이 자기 PR을 병합 리뷰 절차가 형식만 남는다 승인 수 필수(1개 이상)
승인 뒤에 몰래 커밋을 더 하고 병합 승인받은 것과 병합된 것이 다르다 새 커밋이 오면 승인 무효, 마지막 푸시에 대한 승인 필수
main에 강제 푸시 남들이 받아 간 커밋이 원격에서 사라진다 강제 푸시 차단
main 삭제 저장소의 기준이 사라진다 삭제 차단
미해결 리뷰 코멘트를 남긴 채 병합 지적이 반영되지 않은 채 들어간다 대화 해결 필수

8-2. 보호 브랜치 규칙의 항목

보호 브랜치 규칙은 브랜치 이름 패턴 하나에 규칙 하나를 건다. GitHub Docs가 적는 주요 항목은 다음과 같다[G9].

항목 하는 일
병합 전 풀 리퀘스트 리뷰 필수 정한 수의 승인이 있어야 병합할 수 있다. 승인은 write 권한자 또는 지정된 코드 소유자의 것이어야 한다
오래된 승인 무효(dismiss stale approvals) 승인 뒤에 diff를 바꾸는 커밋이 오면 승인을 없앤다
코드 소유자 리뷰 필수 바뀐 파일의 코드 소유자(CODEOWNERS 파일에 적힌 사람)가 승인해야 한다
마지막 푸시에 대한 승인 마지막으로 푸시한 사람이 아닌 다른 사람이 승인해야 한다
상태 검사 통과 필수 자동 검사(테스트, 빌드)가 통과해야 한다
대화 해결 필수 모든 리뷰 코멘트의 대화가 해결되어야 한다
선형 기록 필수 병합 커밋을 막는다. squash나 rebase로만 병합할 수 있다
강제 푸시 허용 / 삭제 허용 기본값은 둘 다 막힘이다
우회 금지(do not allow bypassing) 관리자에게도 규칙을 적용한다. 기본값은 관리자 면제이다

두 가지 기본값을 기억한다. 강제 푸시와 브랜치 삭제는 보호 규칙을 거는 순간 기본으로 막힌다. 반면 관리자(admin)는 기본으로 규칙에서 면제된다[G9]. 관리자도 실수하므로, 팀의 저장소에서는 “우회 금지”를 켜는 편이 안전하다.

CODEOWNERS는 .github/CODEOWNERS 파일에 “이 경로의 파일은 이 사람이나 팀이 책임진다”를 적은 것이다. PR이 그 경로를 바꾸면 GitHub가 코드 소유자에게 리뷰를 자동으로 요청한다[G7]. 상태 검사는 GitHub Actions 같은 자동 검사의 결과를 병합 조건으로 삼는 것이며, 「AI에이전트 기획 및 개발」 13장(CI와 배포)에서 다룬다.

8-3. 읽기: 팀 실습 저장소의 규칙과 거부되는 푸시

교수는 팀 실습 저장소의 main에 보호 브랜치 규칙을 걸어 두었다. 「Require a pull request before merging」(승인 1개)과 「Do not allow bypassing the above settings」(우회 금지)를 켜고, 강제 푸시와 삭제는 기본값대로 막았다. 병합 방식은 저장소 설정에서 merge commit 하나만 허용한다. 규칙을 설정하는 화면(Settings → Branches)은 소유자에게만 보이므로 교수가 시연으로 보인다.

규칙의 세부는 협업자에게 보이지 않지만, main이 보호되어 있는지는 팀 실습 저장소 폴더에서 볼 수 있다. 아래는 실제 GitHub에서 실행하지 않은 예시이다.

(예시)
$ gh api "repos/$OWNER/$REPO/branches/main" --jq .protected
true

보호된 main에 직접 푸시하면 GitHub가 푸시를 거부한다. 거부 메시지는 대략 다음과 같은 모양이라고 알려져 있다. 수업에서는 교수가 시연용 저장소에서 보이며, 학습자가 팀 저장소의 main에 직접 푸시해 보지는 않는다.

(예시)
remote: error: GH006: Protected branch update failed for refs/heads/main.
remote: error: Changes must be made through a pull request.
 ! [remote rejected] main -> main (protected branch hook declined)

1-3의 [rejected] (fetch first)는 “먼저 받아 오라”는 Git의 거부였고, 이것은 “이 브랜치에는 풀 리퀘스트로만 들어올 수 있다”는 저장소 규칙의 거부이다. 받아 와도 해결되지 않는다. 브랜치를 만들어 PR을 연다. 9절의 핵심 실습에서 승인 없는 병합이 거부되는 것도 이 보호 규칙 때문이다.

9. 핵심 실습: 팀 실습 저장소의 GitHub flow와 병합 충돌 해결

만드는 것은 팀 실습 저장소에 병합된 풀 리퀘스트(한 사람이 둘 이상)와 개인 저장소의 협업기록이다. 해결하는 문제는 짝끼리 같은 줄을 일부러 다르게 고쳐 만든 병합 충돌이다. 짝의 PR이 먼저 병합되면 나중 PR이 충돌 상태가 되고, 나중 사람이 두 사람이 동의한 문장으로 풀어야 병합할 수 있다. 4-4와 7-2~7-4의 따라 하기가 이 실습의 두 반쪽이다.

9-1. 준비와 역할

3~4명의 팀이 팀 실습 저장소 <팀>-lab에서 네 단계를 한다.

단계 하는 일 누가 절
1 팀원 소개 파일: 이슈 → 브랜치 → PR → 리뷰 → 병합 모두 각자 한 바퀴 9-2
2 같은 줄을 고쳐 충돌 만들기, AI 초안으로 PR 설명 쓰기 짝 1(A, B), 짝 2(C, D) 9-3
3 충돌 해결(짝 1은 로컬, 짝 2는 웹 편집기), AI 초안으로 리뷰하기, 병합 각 짝의 나중 사람과 리뷰어 9-4
4 협업기록 작성, 점검, 개인 저장소에 커밋 모두 9-5

역할은 GitHub 아이디의 알파벳 순서로 정한다. 첫째가 A이다. 정하는 데 시간을 쓰지 않기 위해서이며, 역할의 무게는 같다. 리뷰는 다음 사람이 한다. A의 PR은 B가, B의 PR은 C가, C의 PR은 D가(3인 팀은 A가), D의 PR은 A가 리뷰한다. 3인 팀은 짝 2를 C와 A로 한다. 결석 등으로 2인이 되면 짝 1만 하고 서로 리뷰한다. 혼자 남으면 9-6의 대안 절차를 따른다.

모두 팀 실습 저장소를 최신으로 맞추고, 팀원끼리 역할을 확인한 뒤, 내 역할과 내 PR을 리뷰할 사람을 셸 변수 파일에 더해 둔다.

터미널 
source ~/ch03.env
cd ~/teams/"$TEAM-lab"
git switch main && git pull --ff-only
gh api "repos/$OWNER/$REPO/collaborators" --jq '.[].login' | sort
cat >> ~/ch03.env <<'EOF'
export ROLE=「내 역할. A, B, C, D 중 하나」
export ME=「내 GitHub 아이디」
export REVIEWER=「내 PR을 리뷰할 사람의 아이디」
EOF
source ~/ch03.env
echo "$ROLE $ME → $REVIEWER"
(예시)
Already up to date.
「교수 계정」   ← 나오면 소유자. 역할 없음
「아이디 1」   ← A
「아이디 2」   ← B
「아이디 3」   ← C
「아이디 4」   ← D
B 「아이디 2」 → 「아이디 3」

막힐 때. 핵심 실습은 기다리는 단계가 많으므로, 막힌 것인지 기다리는 것인지부터 가린다. 기다리는 동안에는 남의 리뷰나 협업기록 1~2절을 한다. 표에 없는 증상은 장 끝의 「자주 하는 실수와 해결」을 본다.

증상 원인 해결
리뷰 요청이 오지 않는다(gh pr list --search "review-requested:@me"가 빈 출력) 작성자가 --reviewer를 빠뜨렸거나 아이디 철자가 틀렸다 작성자가 gh pr edit 「PR 번호」 --add-reviewer 「아이디」로 더한다
Approve를 누를 수 없다 내 PR이다 작성자는 자기 PR을 승인할 수 없다. 리뷰어에게 요청한다(5-1)
gh pr merge가 거부되거나 병합 단추가 비활성이다 승인이 없거나 승인 뒤의 커밋으로 무효가 되었다. 또는 충돌이 있다 gh pr view --json reviewDecision,mergeable로 가린 뒤 다시 리뷰를 요청하거나 충돌을 해결한다. --admin은 쓰지 않는다
충돌 실습에서 충돌이 나지 않았다 상대 PR이 병합된 뒤에 main을 받아 브랜치를 만들었거나, 짝과 다른 줄을 고쳤다 짝이 다른 줄 하나(예: 「대상 사용자」 아래 새 줄)를 정해 9-3을 다시 한다. 또는 7절의 연습 저장소로 갈음한다

9-2. 단계 1: 팀원 소개 파일

모두 동시에 진행한다. 각자 다른 파일(members/<아이디>.md)을 만들므로 충돌하지 않는다.

1) 이슈 만들기(웹). 브라우저에서 팀 실습 저장소의 「Issues」 → 「New issue」를 누른다. 템플릿 고르는 화면에 「작업 이슈」가 보인다(3-3의 config.yml 때문에 「Blank issue」는 “Maintainers only”로 표시된다). 「작업 이슈」를 고르면 제목에 [작업]이, 본문에 템플릿이, 라벨에 「작업」이 미리 채워져 있다. 제목을 [작업] 팀원 소개 파일 추가: 「내 아이디」로 하고, 본문의 괄호를 채우고, 오른쪽 「Assignees」에서 나를 지정한 뒤 「Create」를 누른다.

[그림 자리: 이슈 템플릿을 고르는 화면] 「New issue」를 누른 뒤의 템플릿 목록(「작업 이슈」, 「Blank issue」의 Maintainers only 표시, 「수업 질문」 링크). 찍을 곳: GitHub 웹, 시연용 저장소의 Issues 탭.

2) 브랜치와 소개 파일. 만든 이슈의 번호를 확인해 셸 변수에 담고, 브랜치를 만들어 양식을 복사한다. 파일 이름은 GitHub 아이디이다.

터미널 
gh issue list --assignee "@me" --label "작업"
ISSUE1=「위 목록에서 내 이슈 번호」
git switch -c "$ISSUE1-add-member-$ME"
cp members/_양식.md "members/$ME.md"

VS Code 탐색기에서 members/「내 아이디」.md를 열어 채우고 저장한다. 이어서 스테이징한 변경을 읽고 커밋한다. git diff --cached는 스테이징한 변경을 보인다. 커밋하기 전에 내가 무엇을 커밋하는지 읽는 습관이다(2장).

터미널 
git add "members/$ME.md"
git diff --cached
git commit -m "팀원 소개 파일 추가: $ME"
git push -u origin "$ISSUE1-add-member-$ME"

3) 풀 리퀘스트. 저장소의 PR 템플릿을 초안 폴더로 복사해 채우고, 리뷰어를 지정해 연다.

터미널 
cp .github/pull_request_template.md ~/ch03-drafts/pr1.md
code ~/ch03-drafts/pr1.md

편집기에서 Closes #(이슈 번호)의 괄호를 내 이슈 번호로 바꾸고, 나머지 칸을 채워 저장한다. 이어서 번호를 확인하고 PR을 연다.

터미널 
grep -n "Closes #" ~/ch03-drafts/pr1.md
gh pr create --base main --title "팀원 소개 파일 추가: $ME" --body-file ~/ch03-drafts/pr1.md \
  --reviewer "$REVIEWER" --assignee "@me" --label "작업"
(예시)
7:Closes #3

Creating pull request for 3-add-member-「내 아이디」 into main in 「교수 계정」/ict-aisw-2027-team01-lab

https://github.com/「교수 계정」/ict-aisw-2027-team01-lab/pull/7

grep의 출력에서 Closes # 뒤가 괄호가 아니라 내 이슈 번호인지 확인한다. 템플릿의 (이슈 번호)를 그대로 두는 실수가 흔하다.

4) 리뷰(리뷰어). 나에게 리뷰 요청이 온 PR을 gh pr list --search "review-requested:@me"로 찾는다. 브라우저에서 그 PR의 「Files changed」를 열고 리뷰점검표.md에 따라 읽는다. 줄 코멘트를 하나 이상 남긴다. 고칠 것이 있으면 제안(suggestion)으로 고친 문장을 보인다(5-2). 모든 항목을 확인했으면 「Review changes」 → 「Approve」 → 「Submit review」를 누른다. 고칠 것이 남았으면 「Request changes」를 고른다.

5) 반영과 병합(작성자). 리뷰어가 「Request changes」를 남겼으면, 같은 브랜치에서 고치고 커밋·푸시한다. PR이 저절로 갱신된다. 제안은 웹에서 「Commit suggestion」으로 반영해도 된다. 그 경우 원격 브랜치에 커밋이 생기므로 로컬에서 git pull로 받는다. 승인을 받았으면 작성자가 병합한다.

터미널 
gh pr view --json reviewDecision,mergeable --jq '{reviewDecision, mergeable}'
gh pr merge --merge --delete-branch
git switch main && git pull --ff-only
gh issue view "$ISSUE1" --json state --jq .state
(예시)
{"mergeable":"MERGEABLE","reviewDecision":"APPROVED"}
✓ Merged pull request 「교수 계정」/ict-aisw-2027-team01-lab#7 (팀원 소개 파일 추가: 「내 아이디」)
✓ Deleted local branch 3-add-member-「내 아이디」 and switched to branch main
✓ Deleted remote branch 3-add-member-「내 아이디」
Already up to date.
CLOSED

reviewDecision이 APPROVED가 아니면 규칙 집합 때문에 병합이 거부된다(8-3). 리뷰어를 기다리는 동안 다른 팀원의 리뷰를 한다.

확인 6 gh pr list --state merged --author "@me"에 내 소개 파일 PR이 보이고, 내 이슈가 CLOSED이다.

확인 7 gh pr list --state merged --search "reviewed-by:@me"에 내가 Approve 또는 Request changes로 리뷰한 팀원의 PR이 보인다.

9-3. 단계 2: 병합 충돌의 생성

짝마다 두 사람이 서비스소개.md의 같은 줄을 서로 다르게 고친다. 짝 1(A, B)은 「한 줄 소개」 줄, 짝 2(C, D)는 「핵심 기능」 줄이다. 가상의 「취업 준비 지원 서비스」(대상: 전문대학 2학년 취업 준비생)를 기준으로, 짝의 앞 사람(A, C)은 “누가 어떤 상황에서 쓰는가”의 관점으로, 뒤 사람(B, D)은 “서비스가 무엇을 해 주는가”의 관점으로 한 문장을 쓴다. 짝끼리 문장을 미리 맞추지 않는다. 다른 문장이어야 충돌이 난다.

중요한 순서. 두 사람 모두 상대의 PR이 병합되기 전에 브랜치를 만들고 커밋해야 한다. 한 사람의 PR이 먼저 병합된 뒤에 main을 받아 브랜치를 만들면, 이미 고쳐진 줄을 고치는 것이므로 충돌이 나지 않는다.

1) 이슈와 브랜치. 이슈는 gh로 만든다. 제목과 라벨만 다르고 절차는 9-2와 같다.

터미널 
cd ~/teams/"$TEAM-lab"
git switch main && git pull --ff-only
URL=$(gh issue create --title "[작업] 서비스 소개 문장 작성 ($ROLE)" \
  --body "서비스소개.md의 담당 줄을 내 관점의 한 문장으로 쓴다. 완료 조건: 줄의 (작성 전)이 문장으로 바뀌어 main에 있다." \
  --label "충돌 실습" --assignee "@me")
ISSUE2=${URL##*/}
git switch -c "$ISSUE2-write-intro-$ME"

VS Code에서 서비스소개.md를 열어 내 담당 줄의 (작성 전)을 내 문장으로 바꾸고 저장한다. 이어서 바뀐 줄을 확인하고 커밋한다.

터미널

2) PR 설명의 초안을 Claude Code로 쓰기. 다른 터미널에서 팀 실습 저장소 폴더로 가 Claude Code를 시작하고 다음 프롬프트를 보낸다. 「 」 안을 바꾼다.

- diff에 없는 내용(테스트 통과, 성능 개선 등)은 쓰지 않는다. 모르는 칸은 「(작성자 확인 필요)」로 남긴다.

3) 먼저 연 PR을 리뷰하고 병합하기. 짝 안에서 PR을 먼저 연 사람의 것을 먼저 리뷰하고 병합한다(9-2의 4)와 5)와 같다). 병합되는 순간 짝의 다른 PR은 충돌 상태가 된다. 짝의 나중 사람이 자기 PR의 상태를 확인한다.

9-4. 단계 3: 충돌 해결과 리뷰

짝 1은 로컬에서, 짝 2는 GitHub 웹 편집기에서 해결한다. 팀 안에서 두 방법을 모두 보게 하기 위해서이다. 해결하는 사람은 짝의 나중 사람이고, 해결한 최종 문장은 짝의 앞 사람에게 확인받는다.

짝 1: 로컬 해결. 7-2~7-4와 같은 절차이다. 먼저 최신 main을 내 브랜치에 합친다.

[터미널] · 짝 1의 나중 사람(B)

cd ~/teams/"$TEAM-lab"
git switch "$ISSUE2-write-intro-$ME"
git fetch
git merge origin/main

결과 읽기: git merge origin/main의 네 갈래. 출력의 갈래를 정한 뒤 다음으로 간다. ①만 해결 단계로 간다. 네 출력은 연습 저장소에서 실제로 얻었다.

① CONFLICT (content): Merge conflict in 서비스소개.md
   짝의 PR이 먼저 병합되었고 같은 줄을 고쳤다 → 정상. 아래의 해결로 간다
② Already up to date.
   origin/main에 내 브랜치가 모르는 커밋이 없다 → 짝의 PR이 병합되었는지
   (gh pr list --state merged) 보고, 병합된 뒤 git fetch부터 다시
③ Merge made by the 'ort' strategy.
   짝과 다른 줄을 고쳐 자동으로 합쳐졌다 → 충돌 실습으로는 성립하지 않는다.
   이 병합 커밋은 그대로 푸시해도 되며, 충돌은 9-1 「막힐 때」의 다시 하기로
④ error: Your local changes to the following files would be overwritten by merge:
    서비스소개.md
   커밋하지 않은 수정이 있어 병합이 시작되지 않았다 → git status, git diff로
   무엇인지 보고 커밋하거나 지운 뒤 다시
# ②③은 9-3에서 CONFLICTING을 보았다면 나오지 않는다

①이면 공통 조상이 보이게 표시를 다시 만들고(git checkout --conflict=zdiff3 서비스소개.md), 편집기에서 두 사람의 문장을 합친 한 문장으로 고쳐 저장한다. 이어서 표시가 남지 않았음을 확인하고 해결 커밋을 만든다.

[터미널] · 짝 1의 나중 사람(B)

grep -nE '^(<<<<<<<|=======|>>>>>>>|\|\|\|\|\|\|\|)( |$)' 서비스소개.md || echo '충돌 표시 없음'

git commit --no-edit

짝 2: 웹 편집기 해결. 짝 2의 나중 사람(D, 3인 팀은 A)은 브라우저에서 자기 PR을 열고 7-5의 절차를 따른다. 「Resolve conflicts」 → 충돌 표시를 지우고 최종 문장으로 고침 → 「Mark as resolved」 → 「Commit merge」. 웹에서 만든 해결 커밋은 원격 브랜치에만 있으므로, 로컬에서 그 브랜치를 계속 쓰려면 git pull로 받는다.

최종 문장의 확인. 해결한 사람은 gh pr comment --body "충돌을 해결하였다. 최종 문장: 「최종 문장」. @「짝의 앞 사람 아이디」 확인 부탁한다."로 PR에 코멘트를 남기고, gh pr view --json mergeable --jq .mergeable이 MERGEABLE인지 확인한다. 짝의 앞 사람이 동의하면 리뷰어가 리뷰를 시작한다.

리뷰어: AI 초안으로 리뷰하기. 충돌을 해결한 PR의 리뷰어는 5-4의 절차로 리뷰한다. 팀 실습 저장소 폴더에서 gh pr checkout 「PR 번호」로 그 PR의 브랜치를 받고 gh pr diff 「PR 번호」로 변경을 먼저 읽은 뒤, Claude Code에 다음 프롬프트를 보낸다.

[Claude Code] · 리뷰어

풀 리퀘스트 #「PR 번호」를 리뷰하려 한다. gh pr diff 「PR 번호」 의 출력과 서비스소개.md 전체를 읽고,
~/kits/Service_03장/리뷰점검표.md 의 항목에 따라 리뷰 초안을 홈 폴더의 ch03-drafts/review2.md 에 써 줘.

조건:
- 충돌 표시(<<<<<<<, =======, >>>>>>>, |||||||)가 남았는지 반드시 확인하고 결과를 적는다.
- 지적마다 파일 이름과 줄 번호를 적는다. diff에 없는 내용은 쓰지 않는다.
- 사소한 의견은 「사소함:」으로 시작한다.
- 결정(Approve, Comment, Request changes)은 쓰지 않는다. 사람이 정한다.
- gh 명령, git 명령으로 저장소를 바꾸지 않는다. 파일 하나만 쓴다.

git push가 [rejected] ... (fetch first)로 거부된다 원격에 내가 받지 않은 커밋이 있다 작업 브랜치면 git fetch 뒤 git merge origin/<브랜치>, main이면 git pull --ff-only. 강제 푸시로 덮지 않는다(1-3)

정리

  • 팀 작업의 두 문제는 덮어쓰기와 작업의 가시성이다. Git은 푸시 거부와 줄 단위 병합으로 덮어쓰기를 막고, GitHub는 이슈와 풀 리퀘스트로 누가 무엇을 왜 바꾸었는지를 남긴다.
  • GitHub flow는 브랜치 → 변경 → 풀 리퀘스트 → 리뷰 반영 → 병합 → 브랜치 삭제의 여섯 단계이다. 이 과목은 여기에 이슈를 앞에 두고, 브랜치 이름에 이슈 번호를 넣고, PR 설명에 Closes #n을 적는다.
  • 개인 계정 저장소의 협업자는 write를 받고 설정은 소유자만 바꾼다. 조직은 팀 단위로 권한을 준다. 필수 승인으로 세어지는 것은 write 이상의 승인이고, 작성자는 자기 PR을 승인할 수 없다.
  • git fetch는 원격 추적 브랜치만 바꾸고, git pull은 받은 것을 내 브랜치에 합친다. git status는 마지막 fetch 시점과 비교한다.
  • 병합 방식은 merge commit, squash, rebase이다. 각각 기록의 모양과 잃는 정보가 다르다. 공유한 브랜치는 리베이스하거나 강제 푸시하지 않는다.
  • 충돌은 같은 줄이나 붙은 줄을 양쪽이 고쳤을 때 난다. 표시를 읽고 최종 내용을 쓴 뒤, 표시가 남지 않았음을 확인하고 커밋한다. 단순한 줄 충돌은 웹 편집기로도 해결한다.
  • 보호 규칙과 규칙 집합은 팀의 약속을 저장소가 강제하게 한다. AI 도구가 쓴 PR 설명과 리뷰는 초안이며, diff에 대어 확인하고 게시하는 것은 사람이다.
