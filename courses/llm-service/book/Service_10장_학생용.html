2027학년도 「LLM 서비스 개발」의 준비 중인 교재입니다. 편집 상태를 검토하기 위해 미리 공개한 것으로, 수업 전에 내용과 순서가 바뀔 수 있습니다.

학사 12주차 · 교재 10 · 서비스 4: 문서 요약과 질의응답 (2/2)

개편 초안 2판(2026-11-18). 이 장은 옛 11장을 줄인 것이다. 키트는 새 장 번호의 Service_10장이고 작업 폴더는 ~/llm-service-lab/ch10/이다. 9장의 결과 없이 시작한다. 이 장의 명령과 출력은 모두 2026-11-18에 Windows 11의 Git Bash와 Python 3.13.7에서 대체 임베딩과 모의 모드(LLM_FAKE=1)로 실행해 얻은 것이다. Claude Code가 함수를 완성하는 단계는 키트의 완성판을 넣어 대신 실행하였다. Claude Code의 대화, 실제 모델의 답, Ollama 임베딩은 실행하지 않았고 「실행 결과 자리」로 남겼다. 자료는 옛 구성의 가상 문서 다섯 개(학과 취업지원실의 안내, 규정, 공고 발췌)를 그대로 쓴다. 질의응답은 API와 화면에 붙이지 않고 명령줄(python -m rag)로 확인한다.

[최신 자료 자리: 서비스 4의 자료] 이 단원의 자료를 공개 API로 받은 문서(후보: 고용24 직업정보의 직업정보 상세와 직업사전)로 바꿀지 정하지 않았다. 바꾸면 자료/의 문서, rag/평가문항.csv와 rag/범위밖문항.csv, 기준값, 이 장의 모든 출력이 바뀐다. 확인할 곳: 고용24 OPEN-API의 개발명세서(plan/개편안.md 9절의 26, U9). 2026-11-18에는 가상 문서를 쓴다.

9장의 요약 기능은 사용자가 건넨 글만 다루었다. 실제 질문은 다르다. “현장실습 나가려면 몇 학점이 필요한가”, “취업지원실은 몇 시까지 여는가”처럼 답이 내부 자료에만 있는 질문이 많다. 모델은 그 자료를 학습한 적이 없으므로, 그대로 물으면 그럴듯한 숫자를 지어낸다.

이 장은 그 문제를 검색 증강 생성(Retrieval-Augmented Generation, RAG)으로 푼다. 질문과 관련된 자료 조각을 코드가 먼저 찾고, 그 조각을 근거로 붙여 모델에게 보내며, 모델에게는 근거 안에서만 답하고 근거 번호를 밝히게 한다. 근거가 없으면 “자료에 없다”고 답하게 한다. 이 장에서 만드는 것은 문서 다섯 개를 근거로 답하는 질의응답이다. 색인과 검색과 답변을 맡는 ch10/rag/, 서비스 4의 명세서 docs/요구사항명세서.md, 검색 품질을 숫자로 남긴 docs/검색평가.md가 산출물이다.

절차는 앞 장들과 같다. 명세서에 요구를 EARS 문형으로 적고, 그 명세와 함수의 독스트링을 Claude Code에 주어 구현하게 하고, 고정 테스트로 판정한다. 구현 뒤에는 평가 문항 10개로 재현율@3을 재고, 청킹 설정을 바꾸었을 때 생긴 회귀(전에 찾던 문항을 놓치게 된 것) 하나를 원인부터 찾아 설정 하나로 고친다. 느낌이 아니라 숫자로 검색을 고르는 습관이 이 장의 핵심이다.

학습 목표

  • RAG의 두 단계를 설명하고 각 부품을 코드에서 찾는다.
    • 예시: 색인 단계(청킹, 임베딩, 저장)는 chunker.py, embedder.py, store.py가, 질의 단계(검색, 증강, 생성)는 search.py, answer.py, llm.py가 맡는다.
    • 활용: 프로젝트의 문서 검색 기능을 설계할 때 두 단계를 나누어 그린다.
  • 검색 품질을 재현율@k로 재고, 설정을 바꾼 결과를 숫자로 비교한다.
    • 예시: 고정 길이 200자로 자르면 재현율@3이 0.90에서 0.80으로 떨어진다.
    • 활용: 청킹이나 임베딩을 바꿀 때마다 같은 평가 문항으로 다시 잰다.
  • 근거를 밝히고 모르면 모른다고 답하는 증강 프롬프트와 기준값을 설계한다.
    • 예시: 1위 유사도가 0.18보다 낮은 “학생식당 메뉴” 질문은 LLM을 부르기 전에 거절된다.
    • 활용: 서비스의 거절 문장을 하나로 고정하고 다음 행동을 안내한다.

0. 시작하기

설치, 키트 저장소, 가상 환경은 부록 A(A-12, A-13), 매 수업의 시작 순서는 A-22를 따른다. 작업은 VS Code의 통합 터미널 두 개(A-4-3)에서 한다. 하나는 명령을 직접 실행하는 [터미널]이고, 다른 하나는 Claude Code용이다. 모든 터미널에서 가상 환경을 켜 두고, Windows에서는 부록 A-3-4대로 PYTHONUTF8=1을 등록해 두었는지 본다.

  • 이 장의 실행 상한. Claude Code 대화형은 구현 지시 1회와 고침 지시 1~2회이다(8-3). 프로덕트의 실제 호출(LLM_FAKE=0)은 Console 키를 발급한 학생만 python -m rag ask 1회이다. 여러 질문의 실제 답과 Ollama 경로의 측정은 교수가 만든 실행 기록으로 읽는다. Ollama는 자기 PC에 설치한 학생의 선택이다(부록 A-17).
  • 「읽기」 표시. 꼬리표에 「(읽기)」를 붙인 코드 블록은 따라 치지 않고 읽는다.

0-2. 패키지 설치와 처음 상태

이 장은 넘파이(NumPy)를 새로 쓴다. 저장소 맨 위의 가상 환경 ~/llm-service-lab/.venv를 켠 터미널에서 설치한다(부록 A-13). 견본 .env.example을 .env로 복사한다. LLM_FAKE=1이므로 어떤 코드도 API를 부르지 않는다.

터미널 
python -m pip install -q -r requirements.txt
python -c "import numpy, anthropic; print(numpy.__version__, anthropic.__version__)"
cp -n .env.example .env
grep LLM_FAKE .env
2.5.4 2.8.0
LLM_FAKE=1

임베딩 경로를 정하는 EMBED_BACKEND는 따로 정하지 않는다. 키트의 기본값이 대체 구현(fallback)이므로 누가 실행해도 이 강의안과 같은 숫자가 나온다(2-3).

[최신 자료 자리: 키트가 고정한 패키지의 판] requirements.txt의 판(numpy 2.5.4, anthropic 2.8.0, python-dotenv 1.2.4, pytest 9.2.0)이 학생 PC의 파이썬(3.12 이상)에 설치되는지 수업 전에 다시 확인한다. 확인할 곳은 PyPI(https://pypi.org/project/numpy/ 등)다. 2026-11-18에 Windows 11의 Python 3.13.7에서 설치와 테스트를 확인하였고, macOS에서는 확인하지 못하였다.

이어서 테스트를 처음 상태로 돌리고, 받은 키트를 그대로 한 번 커밋한다. 키트의 rag/에는 학생이 완성할 함수 네 개가 비어 있어 NotImplementedError를 낸다. 그러므로 처음 실행한 테스트는 실패하는 것이 정상이다. 실패의 개수를 먼저 보아 두면 구현 뒤에 무엇이 바뀌었는지 판정할 수 있다. 받은 상태를 커밋해 두는 까닭은, 뒤에서 Claude Code가 고친 파일을 git status와 git diff로 가려내기 위해서이다.

1. RAG의 구조

1-1. 모델이 모르는 것과 RAG가 실패하는 지점

모델은 학습한 시점 뒤의 정보와 공개되지 않은 내부 문서를 모른다. RAG는 그런 자료를 질문마다 찾아 근거로 붙이고, 그 안에서만 답하게 한다. RAG는 환각을 줄이지만 없애지 않는다. 실패는 주로 두 곳에서 일어난다.

검색 실패. 엉뚱한 조각을 찾아도 생성 단계는 그 조각으로 성실하게 답한다. “현장실습 중에 아파서 못 가면 어떻게 하나”의 정답은 출석과 결석 조항인데, 검색이 보험 조항을 가져오면 모델은 “상해보험에 가입되어 있다”고 답하고 조항 번호까지 붙인다. 출처가 붙어 있으므로 사용자는 지어낸 답보다 이쪽을 더 쉽게 믿는다. 이 장의 측정(재현율@3)은 이 실패를 숫자로 잡기 위한 것이다.

갱신 실패. 색인은 문서를 미리 잘라 숫자로 바꾸어 둔 것이므로 저절로 새로워지지 않는다. 규정이 개정되어도 색인을 다시 만들지 않으면 옛 규정으로 답한다. 그래서 자료가 바뀌는 주기(규정은 개정 때, 안내는 학기마다, 공고는 매일)에 맞추어 색인을 다시 만들고, 남은 자리처럼 시시각각 바뀌는 값은 색인에 넣지 않고 실시간 조회로 다룬다.

이 장은 검색 실패를 다룬다. 갱신 실패는 운영 규칙이므로 docs/검색평가.md의 결론에 “자료가 바뀌면 python -m rag index를 다시 실행한다”는 한 줄로 남긴다.

1-2. 두 단계

RAG는 시점이 다른 두 단계로 움직인다. 색인 단계는 자료가 바뀔 때 한 번 돈다. 문서를 조각(청크, chunk)으로 자르고, 조각마다 의미를 숫자 목록(벡터)으로 바꾸어(임베딩) 저장한다. 이 저장물이 색인(index)이다. 질의 단계는 질문이 올 때마다 돈다. 질문도 같은 방식으로 벡터로 바꾸고, 색인에서 가까운 조각을 찾고(검색, Retrieval), 그 조각을 질문과 함께 프롬프트에 묶고(증강, Augmentation), 모델이 답을 만든다(생성, Generation).

2. 임베딩과 코사인 유사도

2-1. 임베딩

임베딩(embedding)은 글 하나를 고정된 길이의 숫자 목록, 곧 벡터로 바꾸는 변환이다. 임베딩 모델은 뜻이 비슷한 글이 가까운 벡터가 되도록 학습되어 있다. 그래서 “화상 면접 준비”와 “비대면 면접 환경”처럼 낱말이 일부만 겹치는 글도, 좋은 임베딩 모델에서는 가까운 벡터가 된다.

임베딩 모델은 답을 만드는 생성 모델과 다른 부품이다. Anthropic은 자체 임베딩 모델을 제공하지 않으며, 문서에서는 임베딩 제공자의 한 예로 Voyage AI를 소개한다[A3]. 이 과목은 외부 임베딩 서비스의 계정과 비용을 피하기 위해 키트의 대체 구현을 기본으로 하고, 자기 PC에 Ollama를 설치한 학생은 로컬 임베딩 모델을 선택으로 쓸 수 있다(부록 A-17). 두 모델은 바꿀 때의 비용이 다르다. 생성 모델을 바꾸면 프롬프트를 다시 점검하면 되지만, 임베딩 모델을 바꾸면 색인 전체를 다시 만들어야 한다. 모델마다 벡터의 길이와 눈금이 달라, 모델 A로 만든 색인에 모델 B의 질문 벡터를 견주면 숫자는 나오지만 뜻이 없기 때문이다. Ollama 문서도 색인과 질의에 같은 모델을 쓰라고 권한다[A4]. 키트의 store.py는 색인의 임베딩 경로와 모델 이름을 meta.json에 적고, 질문의 경로와 다르면 오류를 낸다.

2-2. 코사인 유사도

두 벡터가 얼마나 가까운지는 대개 코사인 유사도(cosine similarity)로 잰다. 두 벡터가 이루는 각의 코사인 값이며, 같은 방향이면 1, 직각이면 0이다.

코사인 유사도(a, b) = (a · b) / (|a| × |b|)
  a · b : 같은 자리의 성분끼리 곱해 모두 더한 값(내적)
  |a|   : 성분 제곱의 합의 제곱근(벡터의 길이)

벡터의 길이를 미리 1로 맞추어 두면(L2 정규화) 코사인 유사도는 내적과 같아진다[A3][A4]. 키트의 embedder.py는 벡터를 정규화해 두고, 검색에서는 행렬 곱 하나(index.vectors @ q)로 모든 청크의 유사도를 한꺼번에 구한다. 유사도의 절대값은 모델마다 눈금이 다르다. 2026년 2학기 수업에서 쓴 nomic-embed-text는 관계없는 문장 쌍에도 0.5를 넘는 값을 내었다(2026년판 6주차 기록). 그러므로 “0.7 이상이면 관련 있다” 같은 기준은 모델을 바꾸면 그대로 쓸 수 없고, 평가 문항으로 다시 정해야 한다(6절).

2-3. 키트의 대체 구현

대체 구현은 의미를 이해하지 못한다. 글을 두 글자 묶음과 세 글자 묶음(문자 n-gram)으로 쪼개고, 묶음마다 해시 값으로 2,048칸 가운데 한 칸을 골라 1씩 더한 뒤 길이를 1로 맞춘다. 두 글이 같은 글자 묶음을 많이 공유할수록 유사도가 커진다.

파일: ch10/rag/embedder.py (일부) 
def _fallback_one(text):
    text = " ".join(text.lower().split())
    vec = np.zeros(FALLBACK_DIM, dtype=np.float32)
    for n in (2, 3):
        for i in range(len(text) - n + 1):
            gram = text[i:i + n]
            if gram.strip() == "":
                continue
            vec[zlib.crc32(gram.encode("utf-8")) % FALLBACK_DIM] += 1.0
    return vec

zlib.crc32는 파이썬을 다시 실행해도 같은 값을 내는 해시다. 파이썬 내장 hash()는 실행마다 값이 바뀔 수 있어 쓰지 않는다. 그래서 대체 구현은 설치가 필요 없고 같은 글에 언제나 같은 벡터를 내며, Ollama를 설치한 학생과 설치하지 않은 학생의 재현율과 기준값이 같아진다. 환경 변수 EMBED_BACKEND의 기본값이 fallback인 까닭이다. ollama는 Ollama만 쓰고, auto는 Ollama를 먼저 시도하므로 PC마다 숫자가 달라질 수 있다. 다음은 대체 구현으로 세 쌍의 유사도를 잰 결과다.

3. 청킹 전략

3-1. 왜 자르는가

문서를 통째로 하나의 벡터로 만들면 여러 주제가 한 벡터에 섞인다. 「현장실습 운영 규정」 전체의 벡터는 자격, 학점, 보험, 평가의 뜻이 평균된 것이어서 어느 질문에도 어중간하게 가깝다. 검색된 문서를 통째로 프롬프트에 붙이면 비용이 들고, 모델이 긴 근거 속에서 정답 문장을 놓칠 수 있다. 반대로 너무 잘게 자르면 “단기 실습은 3학점”이라는 조각만으로는 무엇의 3학점인지 알 수 없다. Anthropic의 Contextual Retrieval 글은 기본 RAG가 문서를 대개 수백 토큰 이하의 조각으로 자르며, 조각의 크기와 경계와 겹침이 모두 검색 성능에 영향을 준다고 정리하였다[A2].

축 선택지 길게 또는 크게 하면 짧게 또는 작게 하면
경계 제목(절) 단위, 문단 단위, 고정 글자 수 뜻이 끝나는 곳에서 끊긴다(제목 단위) 문장 중간에서 끊길 수 있다(고정 길이)
길이 최대 글자 수(CHUNK_MAX_CHARS) 주제가 섞인다. 근거 블록이 길어진다 뜻이 끊긴다. 청크 수가 늘어난다
겹침 앞 청크의 끝을 다음 청크 앞에 반복(CHUNK_OVERLAP) 경계에 걸친 문장을 지킨다. 중복이 는다 경계에 걸친 문장이 반씩 나뉜다

3-2. 제목 붙이기

청크를 잘라 내면 그 청크가 어느 문서의 어느 절이었는지가 사라진다. Contextual Retrieval은 청크마다 문서 전체에서의 자리를 설명하는 짧은 맥락(대개 50~100토큰)을 Claude로 만들어 청크 앞에 붙인 뒤 임베딩한다. 이 글이 보고한 실험에서 상위 20개 청크 안에 정답을 찾지 못하는 비율은 맥락을 붙인 임베딩만으로 5.7%에서 3.7%로 35% 줄었고, 맥락을 붙인 BM25를 더하면 49%, 재순위화(reranking)까지 더하면 67% 줄었다[A2].

이 장의 키트는 LLM을 부르지 않는 값싼 판을 쓴다. 청크 앞에 「문서 제목 > 절 제목」 한 줄을 붙여 임베딩한다(CHUNK_ADD_TITLE=1). 화면과 프롬프트에 나가는 본문(text)에는 붙이지 않고, 임베딩에 넣는 글(embed_text)에만 붙인다. LLM으로 맥락을 만드는 방식보다 정보가 적지만 비용이 들지 않고 결과가 매번 같다.

4. 벡터 검색, 키워드 검색, 혼합 검색

4-1. 벡터 검색과 저장 방식

벡터 검색은 질문 벡터와 모든 청크 벡터의 유사도를 구해 큰 순서로 k개를 고른다. 청크가 수천 개 이하이면 모든 청크와 하나씩 견주는 전수 비교로 충분하다.

scores = index.vectors @ q           # (청크 수,) 모든 청크의 유사도
order = np.argsort(scores)[::-1][:k] # 큰 순서로 k개의 번호

np.argsort는 작은 값부터의 번호를 돌려주므로 [::-1]로 뒤집는다. 이 두 줄이 핵심 실습에서 완성할 vector_search의 핵심이다. 청크가 수십만 개를 넘으면 비슷한 벡터끼리 미리 묶어 두고 가까운 묶음만 열어 보는 벡터 데이터베이스(pgvector, Chroma 등)를 쓴다. 여러 부서의 문서를 한 색인에 넣으면 한 부서의 질문에 다른 부서의 비공개 문서가 근거로 나올 수도 있다. OWASP는 이를 벡터와 임베딩의 약점(2025년판 LLM08, 2026년판 LLM09)으로 들고, 권한을 인식하는 벡터 저장소를 대책으로 제시한다[O2][O3].

4-2. 키워드 검색과 따라 하기 2

키워드 검색은 질문의 낱말이 청크에 몇 번, 얼마나 드물게 나오는지로 점수를 매긴다. 가장 널리 쓰이는 공식이 BM25다. Contextual Retrieval 글은 BM25를 TF-IDF를 바탕으로 문서 길이를 보정한 순위 함수로 설명하며, 고유한 식별자를 찾는 데 강하다고 하였다[A2]. BM25 점수는 세 요소로 이루어진다. 청크 안에 질문의 낱말이 나온 횟수(낱말 빈도)는 많을수록 점수를 올리지만 효과가 점점 준다(키트의 k1 = 1.2). 그 낱말이 드문 청크에만 나올수록(역문서 빈도) 크게 기여한다. 긴 청크가 낱말을 많이 가져 유리해지지 않도록 길이를 보정한다(b = 0.75). 키트의 tokenize는 띄어쓰기로만 자르므로 “자기소개서는”과 “자기소개서를”이 다른 낱말이 된다. 실무의 한국어 키워드 검색은 형태소 분석기로 조사와 어미를 떼어 낸다.

키워드 검색은 이미 완성되어 있으므로 지금 실행할 수 있다. 출력을 읽는 법(순위, 점수, 유사도, 문서 > 절, 본문 앞부분)은 핵심 실습에서 그대로 쓴다.

4-3. 혼합 검색: RRF

벡터 검색과 키워드 검색은 서로 다른 질문에 강하므로 둘을 합치면 한쪽이 놓친 것을 다른 쪽이 잡을 수 있다. 두 점수의 눈금이 다르므로(코사인은 0~1, BM25는 0~수십) 점수 대신 순위를 합친다. 역순위 융합(Reciprocal Rank Fusion, RRF)은 각 방법에서의 순위 r마다 1/(k + r)을 더한 값으로 다시 순위를 매긴다. Elasticsearch 문서는 상수 k의 기본값을 60으로 둔다[R2]. 이 방식은 Cormack 등이 2009년 SIGIR에서 발표하였다[R3].

RRF 점수(청크) = Σ 1 / (60 + 그 방법에서의 순위)
예) 벡터 1위, 키워드 3위인 청크: 1/61 + 1/63 = 0.0164 + 0.0159 = 0.0323
    벡터 2위, 키워드에는 없는 청크: 1/62 = 0.0161

키트의 hybrid_search는 두 방법에서 각각 상위 20개를 받아 RRF로 합친다. 혼합이 항상 낫지는 않다. 한쪽이 틀린 청크를 높은 순위로 내면 그것이 섞여 들어와 맞던 것을 밀어낼 수도 있다. 그래서 같은 평가 문항으로 세 방법을 재어 고른다(8-5).

5. 검색 품질의 측정: 재현율@k

5-1. 정밀도와 재현율

정보 검색에서 검색 결과의 품질을 재는 가장 기본적인 두 척도는 정밀도(precision)와 재현율(recall)이다[R1]. 정밀도는 돌려준 것 가운데 정답의 비율이고, 재현율은 정답 가운데 돌려준 것의 비율이다. 자료 전부를 돌려주면 재현율은 1이 되지만 정밀도는 바닥이 되므로 두 척도는 서로 당긴다.

RAG의 검색기는 순위가 매겨진 목록을 돌려주고, 그 가운데 상위 k개만 프롬프트에 들어간다. 그래서 상위 k개로 자른 척도를 쓴다. 재현율@k는 정답 가운데 상위 k개 안에 든 것의 비율이고, 정밀도@k는 상위 k개 가운데 정답의 비율이다. 이 장은 재현율@3을 주 척도로 삼는다. 정답이 근거 블록 안에 없으면 모델은 맞힐 수 없지만, 정답이 들어 있기만 하면 함께 들어간 다른 청크는 지시와 모델이 걸러 낼 기회가 있기 때문이다. Contextual Retrieval 글이 상위 20개의 재현율을 척도로 쓴 것도 같은 까닭이다[A2].

5-2. 손으로 재 보기

다음은 가상의 측정 결과다. 각 문항의 재현율@3을 직접 계산한다.

문항 정답 절 상위 3개 청크가 걸친 절
가 A B, A, C
나 D E, F, G
다 H, I H, J, K
라 L L, L, M

가는 1.0, 나는 0.0, 다는 0.5, 라는 1.0이다. 평균 재현율@3은 (1.0 + 0.0 + 0.5 + 1.0) / 4 = 0.625이다. 라에서 상위 청크 둘이 같은 절 L에 걸쳐 있어도 정답 절이 하나이므로 재현율은 1.0을 넘지 않는다. 정밀도@3은 라가 2/3, 가가 1/3이다. 이 계산이 핵심 실습에서 완성할 recall_at_k가 하는 일이다. 문항 10개로 잰 값은 한 문항이 0.1이므로, 두 설정의 차이가 0.1이면 “경향”으로 읽고 놓친 문항을 하나하나 들여다본다.

6-2. 두 층과 기준값

검색기는 질문과 관계가 없어도 항상 k개를 돌려준다. “학생식당 이번 주 메뉴 알려줘”라는 질문에도 가장 덜 먼 청크 세 개가 근거로 붙는다. 그 근거로 모델이 무언가를 답하기 시작하면 사고가 된다. 그래서 「자료에 없다」를 두 층으로 만든다. 1층은 코드의 유사도 기준값이다. 검색 직후 1위 유사도가 기준값(RAG_MIN_SCORE)보다 낮으면 LLM을 부르지 않으므로 비용이 들지 않고 결과가 매번 같다. 2층은 프롬프트의 지시 2이다. 관련 문서는 있지만 답이 들어 있지 않은 질문을 모델이 거절하게 한다.

기준값은 맞바꾸기다. 높이면 자료에 있는 질문까지 거절하고(과잉 거절), 낮추면 자료에 없는 질문에 엉뚱한 근거로 답한다(오답). 이 서비스에서 과잉 거절은 학생이 취업지원실에 직접 문의하게 만들 뿐이지만, 오답은 틀린 마감일이나 학점 기준을 믿게 만든다. 오답의 비용이 더 크므로 안전한 쪽으로 정한다. 절차는 다음과 같다.

  1. 자료에 있는 질문(평가 문항 10개)과 자료에 없는 질문(범위 밖 문항 3개)의 1위 유사도를 각각 잰다.
  2. 두 무리가 갈리면 그 사이의 값을 기준값으로 정한다. 키트의 calibrate는 두 값의 가운데를 후보로 낸다.
  3. 두 무리가 겹치면 기준값만으로는 가를 수 없으므로 2층에 맡기고, 임베딩이나 청킹을 바꾸어 다시 잰다.
  4. 임베딩 모델, 청킹 설정, 자료를 바꾸면 1번부터 다시 한다.

키트의 기본 기준값은 대체 구현에서 0.18(이 절차로 잰 값), Ollama 경로에서 0.50(자리만 잡은 값)이다. 거절 문장은 config.py의 상수 NO_ANSWER 하나로 고정해, 지시 2가 그대로 쓰게 하고 코드가 그 문장으로 거절을 알아보게 한다. 문장 끝의 다음 행동(취업지원실 문의)은 사용자가 막다른 길에 서지 않게 한다.

7. 대화 이력과 컨텍스트

Claude API는 이전 호출을 기억하지 않는다. 대화가 이어지는 것처럼 보이는 것은 프로그램이 지금까지의 대화를 messages에 담아 매번 다시 보내기 때문이다[P3]. RAG에서 매 질문의 증강 프롬프트(근거 블록 포함)를 그대로 쌓으면 열 번째 질문에는 지난 근거 27개가 함께 가서 비용이 늘고, 지난 프롬프트의 [1]과 이번 프롬프트의 [1]이 서로 다른 근거를 가리켜 번호가 엉킨다. 그래서 이력에는 원래 질문과 답만 남기고, 근거 블록은 이번 질문의 것만 마지막 메시지에 붙인다. trim_history는 최근 MAX_TURNS(기본 4) 왕복, 곧 메시지 8건만 남긴다. 앞 대화를 요약으로 바꾸어 남기는 방법도 있지만, 질문이 한 건씩 끝나는 안내형 서비스에는 자르기가 맞다. Claude 문서는 토큰이 늘수록 정확도와 회상이 떨어지는 현상을 컨텍스트 부패(context rot)라 부르며, 얼마나 넣을 수 있는지보다 무엇을 넣는지가 중요하다고 설명한다[P3].

[최신 자료 자리: 컨텍스트 창의 크기와 압축 기능의 상태] 수업에서 쓰는 모델의 컨텍스트 창과 서버 쪽 압축(compaction)의 제공 상태. 확인할 곳은 https://platform.claude.com/docs/en/build-with-claude/context-windows다. 2026-11-16에 확인한 값은 현행 모델이 100만 토큰, 그 밖의 모델(Claude Sonnet 4.5 등)이 20만 토큰이고, 압축은 Claude 4.6 이후 모델에서 베타로 제공된다.

이 구조에는 빈틈이 하나 있다. 이력은 생성 단계에는 들어가지만, 검색은 이번 질문 한 문장으로만 한다. 그래서 “현장실습 중에 아파서 못 가면 어떻게 해?” 다음에 “그럼 진단서는 언제까지 내?”라고 이어 물으면, 검색기는 뒤 문장만 보고 청크를 찾는다. 옛 키트로 잰 이 이어진 질문의 1위 유사도는 0.098로 기준값보다 낮아 “자료에 없다”가 되었다. 실무에서는 검색 전에 LLM에게 이력과 이번 질문을 주고 “앞 대화 없이도 뜻이 통하는 검색용 질문”을 만들게 하는 질문 다시 쓰기(query rewriting)로 메운다. 키트는 이를 구현하지 않았으므로 명세서에 「알려진 한계」로 적는다.

8-4. 테스트 판정

테스트를 직접 실행하고, 테스트 파일이 그대로인지 키트의 원본과 견준다. 테스트를 고쳐 통과시키는 일을 막기 위해서다.

diff -r은 두 폴더를 하위 폴더까지 견주고, -x __pycache__는 그 이름의 폴더를 비교에서 뺀다[U1]. 테스트를 실행하면 파이썬이 tests/rag/__pycache__/에 컴파일한 파일을 남기는데[U2] 키트의 원본에는 그것이 없기 때문이다. 24 passed가 아니면 실패 줄을 읽는다. 끝이 NotImplementedError이면 아직 비어 있는 함수가 있으므로 그 함수만 다시 지시하고, AssertionError이면 E 줄의 == 왼쪽(실제 값)과 오른쪽(기대값)의 차이를 한 문장으로 말해 고침 지시를 보낸다. 통과했는데 diff가 바뀐 줄을 출력하면 테스트가 고쳐진 것이므로 키트의 원본을 다시 복사하고 구현만 고치게 한다.

통과한 뒤에는 구현을 한 번 읽는다. trim_history가 max_turns가 0일 때를 어떻게 다루었는지 본다. history[-0:]은 빈 목록이 아니라 전체를 돌려준다. 독스트링이 정하지 않은 경계를 구현이 어떻게 다루었는지 읽는 것이 리뷰의 일이다.

calibrate의 전체 출력에서 자료에 있는 질문의 최저는 0.1752(10번), 자료에 없는 질문의 최고는 0.1582다. 기준값 0.18을 그대로 두면 10번이 거절되는 과잉 거절이 생긴다. 후보 0.17이면 10번은 답하고 범위 밖 질문은 여전히 거절되지만, 두 무리의 틈이 0.045에서 0.017로 좁아졌다. 모의 응답이 낱말 가운데(「은 일이 …」)서 시작하는 것은 고정 길이 조각이 문장 가운데서 시작하기 때문이다. calibrate의 전체 출력을 docs/검색평가.md 5절의 「고친 설정」 칸에 붙이고, 4절 표의 셋째 줄을 채운다.

  • 확인 10 겹침 50의 eval에서 4번이 [O]이고 재현율@3이 1.00이며, docs/검색평가.md 4·5절에 고친 설정 하나(CHUNK_OVERLAP=50), calibrate의 후보(0.17), 기준값 0.18에서 10번이 거절되는 것이 적혀 있다.

고친 설정은 4번의 회귀를 풀었다. 그렇다고 곧바로 기본 설정을 버리지 않고, 숫자를 나란히 놓고 고른다.

이 장에서 관찰한 한계를 명세서의 「알려진 한계」 절에 적는다.

- 검색은 이번 질문 한 문장으로만 한다. 앞 대화에 기대는 이어진 질문(예: "그럼 진단서는 언제까지 내?")은 근거를 찾지 못할 수 있다. 질문 다시 쓰기(query rewriting)는 구현하지 않았다.
- 대체 임베딩은 글자 겹침만 잰다. 뜻이 같고 표현이 다른 질문(평가 문항 6번)을 놓친다.

정리

  • RAG는 모델이 모르는 자료를 질문마다 찾아 근거로 붙이고, 그 안에서만 답하게 하는 구조다. 색인 단계(청킹, 임베딩, 저장)와 질의 단계(검색, 증강, 생성)로 나뉜다.
  • 정규화된 임베딩 벡터의 내적이 코사인 유사도다. 눈금은 모델마다 다르므로 색인과 질문은 같은 모델로 만들고, 측정을 견주려면 임베딩 경로를 고정한다.
  • 청킹은 경계, 길이, 겹침의 선택이며, 설정을 하나씩 바꾸어 같은 평가 문항의 재현율@k로 고른다.
  • 설정을 바꾸어 전에 찾던 문항을 놓치면 회귀다. 1위의 절과 정답 절의 조각을 열어 원인을 찾고, 설정 하나로 고친 뒤, 기준값에 준 영향까지 재어 채택을 정한다.
  • 증강 프롬프트는 자료 → 질문 → 지시의 순서로 쓰고, 근거마다 번호와 출처를 붙인다.
  • 「자료에 없다」는 두 층이다. 코드의 기준값이 관계없는 질문을 LLM 앞에서 막고, 프롬프트의 지시가 근거에 답이 없는 질문을 막는다.

개념 점검.

  1. 검색 실패와 갱신 실패를 예를 들어 구분하라.
  2. 임베딩 모델을 바꾸면 색인을 다시 만들어야 하는 까닭은 무엇인가.
  3. 정답 절이 둘인 문항에서 상위 3개가 그 가운데 하나만 담았다면 재현율@3은 얼마인가.
  4. 기준값을 낮추었을 때와 높였을 때 생기는 문제를 하나씩 들라.
  5. 고정 길이 200자에서 4번 문항을 놓친 원인과, 겹침이 그것을 푼 까닭을 설명하라.
