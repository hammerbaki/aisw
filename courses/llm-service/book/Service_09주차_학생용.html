웹 프로덕트의 구현과 배포

2027학년도 「LLM 서비스 개발」의 준비 중인 교재입니다. 편집 상태를 검토하기 위해 미리 공개한 것으로, 수업 전에 내용과 순서가 바뀔 수 있습니다.

학사 11주차 · 교재 09 · 4부 구현

6장에서 요구사항 명세서를 쓰고, 7장에서 사용자 흐름과 화면 목록을 더하고, 8장에서 화면 명세와 디자인 토큰과 프로토타입을 만들었다. 지금까지의 산출물은 모두 “무엇을 만들 것인가”에 대한 문서다. 이 장은 그 문서를 처음으로 동작하는 프로덕트로 바꾸는 장이다. 4부 「구현」이 여기서 시작한다.

이 장에서 만드는 것은 하나다. 공통 사례 「취업 준비 지원 서비스」의 첫 프로덕트인 공고 모아보기·관심 공고·지원 일정 관리 웹(jobprep/web/)이다. 가상의 채용 공고 30건을 검색하고, 관심 공고를 표시하고, 지원 일정을 적어 두는 정적 웹이다. 서버 프로그램은 없고, 사용자의 기록은 브라우저 저장소에 남는다.

구현은 Claude Code가 한다. 학습자가 하는 일은 세 가지다. 명세에서 계획과 작업 목록을 끌어내고 구현 지시문을 쓰는 일, 명세의 요구를 인수 조건으로 바꾸어 구현을 검사하는 일, 검사를 통과한 것만 GitHub Pages로 공개하는 일이다. 마지막으로 사용자 의견에서 나온 명세 변경 한 건을 반영해 다시 구현하고 다시 배포한다. 명세 → 구현 → 검사 → 배포 → 명세 변경 → 재구현 → 재배포의 한 바퀴가 이 장의 전체 모양이다.

이 장의 웹은 10장에서 공고 요약 기능(LLM API)이 붙는 화면이 되고, 11~13장에서 계속 고쳐 쓰인다. 프로젝트실습Ⅰ에서 팀의 프로덕트를 처음 공개할 때도 이 장의 절차(인수 조건 표, 배포 전 점검, 배포 워크플로)를 그대로 쓴다.

학습 목표

  • 명세서와 화면 명세에서 계획과 작업 목록을 끌어내고, 작업 하나를 구현 지시문 하나로 바꾸어 Claude Code에 맡길 수 있다.
    • 예시: SCR-01(공고 목록)의 요구 REQ-001~004, REQ-006, REQ-007, REQ-028, REQ-029를 묶어 작업 T-03을 만들고, 참조·범위·금지 사항·완료 조건이 든 지시문으로 구현을 맡긴다.
    • 활용: 프로젝트실습Ⅰ에서 팀원이 같은 명세로 작업을 나누어 맡을 때 작업 목록이 분담표가 된다.
  • 명세의 요구를 Given-When-Then 형식의 인수 조건으로 바꾸고, 자동 검사와 손 점검으로 통과 여부를 판정할 수 있다.
    • 예시: REQ-009(관심 공고 유지)를 “저장하고 새 탭에서 열어도 보인다”는 인수 조건 AC-009-1로 바꾸고, 검사 결과로 판정한다.
    • 활용: “완성했다”는 보고를 “인수 조건 26개 가운데 자동 22개 통과, 손 점검 4개 기록”으로 바꾼다.
  • 정적 웹과 브라우저 저장소의 동작과 한계(출처, 수명, 용량, 개인 정보)를 설명하고, 로컬 서버로 확인할 수 있다.
    • 예시: file://로 열면 공고 자료를 읽지 못하는 까닭과, python -m http.server로 열면 되는 까닭을 말한다.
    • 활용: 사용자의 기록을 어디에 둘지(브라우저, 서버) 정하는 설계 판단의 근거가 된다.
  • 공개할 파일을 점검하고 GitHub Actions 워크플로로 GitHub Pages에 배포하며, 명세 변경을 반영해 다시 배포할 수 있다.
    • 예시: 저장소 안 jobprep/web/에서 공개할 파일만 골라 https://아이디.github.io/llm-service-lab/로 내보낸다.
    • 활용: 포트폴리오에 문서가 아니라 동작하는 주소와 그 주소를 만든 명세·검사·변경 이력을 함께 제시한다.

0-2. 키트 받기

키트는 부록 A가 정하는 배포 폴더($KIT_HOME)에 있다. 다른 장과 같이 저장소 밖(~/kits/)에 받아 두고, 필요한 파일만 저장소로 옮긴다. 저장소의 상태부터 확인한다. 받기 전에 커밋하지 않은 변경이 있으면, 키트에서 온 파일과 섞여 나중에 무엇이 어디서 왔는지 가리기 어렵다.

서버 터미널

KIT=~/kits/Service_09주차
ls "$KIT"

커밋 해시와 메시지는 학습자마다 다르다. 교수 폴더는 학생용 배포 폴더에 없을 수 있다. KIT 변수는 새 터미널에서 다시 입력한다.

0-3. 앞 장 산출물의 확인

이 장이 받는 입력은 네 가지다. 8장에서 v3(태그 spec-v3)가 된 요구사항 명세서(REQ-001~039), 8장의 화면 명세(SCR-01~04), 디자인 토큰, 프로토타입이다.

서버 터미널 
cd ~/llm-service-lab/jobprep
ls docs/요구사항명세서.md docs/설계/화면명세.md docs/설계/디자인토큰.md prototype/
grep -c '^- \*\*REQ-' docs/요구사항명세서.md
grep -c '^## SCR-0[1-4]' docs/설계/화면명세.md
docs/요구사항명세서.md  docs/설계/디자인토큰.md  docs/설계/화면명세.md

prototype/:
css  index.html  job.html  js  schedule-new.html  schedule.html
39
4

파일이 없거나 요구가 비어 있으면 키트의 기준 산출물을 복사한다. cp -rn의 -n은 이미 있는 파일을 덮어쓰지 않는다는 뜻이다. 자기 산출물이 일부 있으면 그것은 그대로 남고 빠진 것만 채워진다.

[서버 터미널] (앞 장 산출물이 없을 때만)

cd ~/llm-service-lab
cp -rn "$KIT/기준산출물/jobprep" .
git add jobprep
git commit -m "docs: 9장 기준 산출물로 앞 장 산출물 채움"

기준 산출물은 8장의 정답(명세서 v3, 화면 명세 v3, 디자인 토큰, 접근성 점검, 프로토타입)과 7장의 설계 문서다. 자기 산출물을 쓰는 학습자는 화면 명세에 SCR-01~04가 있고 요구 번호가 세 자리(REQ-001)인지 본다. 화면 구성이 달라 자동 검사와 맞지 않으면 이 장은 기준 산출물의 명세로 구현하고, 차이는 12장의 비교 구현에서 다룬다.

1. 명세에서 구현으로

1-1. 명세 주도 개발의 네 단계

6장에서 명세 주도 개발(Spec-Driven Development, SDD)을 “구현보다 명세를 먼저 쓰고, 명세를 AI 구현의 입력이자 검사의 기준으로 삼는 방식”으로 정의하였다. GitHub의 Spec Kit은 이 방식을 명세(Specify) → 계획(Plan) → 작업(Tasks) → 구현(Implement)의 단계로 나누고, 단계마다 마크다운 문서 하나를 남겨 다음 단계의 입력으로 쓴다 [S1]. 6~8장은 앞의 한 단계(명세)를 세 장에 걸쳐 한 것이고, 이 장은 나머지 세 단계를 한다.

단계 질문 입력 산출물 (이 장) Spec Kit의 대응 명령 [S1]
명세 무엇을, 왜 조사, 페르소나, 문제 정의 요구사항명세서.md, 화면명세.md (6~8장) /speckit-specify, /speckit-clarify
계획 어떤 기술과 구조로 명세 + 기술 결정 Claude Code 계획 모드의 계획 /speckit-plan (plan.md)
작업 어떤 순서의 어떤 조각으로 계획 작업목록.md /speckit-tasks (tasks.md)
구현 조각을 하나씩 작업 하나 + 지시문 web/의 파일과 커밋 /speckit-implement

이 과목은 Spec Kit을 설치하지 않고 같은 단계를 Claude Code의 기본 기능(계획 모드, 파일 참조, 작업 목록)으로 한다. 도구의 명령 이름이 바뀌어도 단계의 뜻은 남는다.

[최신 자료 자리: Spec Kit의 명령 이름] 명령의 표기(/speckit-specify, /speckit.specify)와 단계 구성. 확인할 곳 https://github.github.com/spec-kit/quickstart.html. 2026-11-14 집필 때 두 표기가 함께 보였다. 수업 전에 다시 확인한다.

계획과 작업을 명세와 따로 두는 까닭은 질문이 다르기 때문이다. 명세는 사용자가 보는 결과를 말하고 기술을 말하지 않는다. REQ-009는 “페이지를 다시 열어도 유지해야 한다”고만 말하고, localStorage와 sessionStorage 가운데 무엇을 쓸지는 계획이 정한다. 계획이 명세에 섞이면 기술을 바꿀 때마다 명세를 고쳐야 하고, 명세가 사용자의 요구인지 개발자의 결정인지 가릴 수 없게 된다.

1-2. 계획 모드

Claude Code의 계획 모드(plan mode)는 파일을 읽고 탐색 명령을 실행해 계획을 쓰되, 사람이 계획을 승인하기 전에는 소스를 고치지 않는 권한 모드다 [C2]. 들어가는 방법은 세 가지다.

  • 실행 중 전환. Shift+Tab을 상태 표시줄에 ⏸ plan mode on이 보일 때까지 누른다 [C1].
  • 한 번만. 프롬프트 앞에 /plan을 붙인다 [C2].
  • 시작부터. claude --permission-mode plan으로 시작한다 [C1]. 이 장의 1절은 이 방법을 쓴다.

계획이 나오면 승인 화면이 뜬다. 2026-11 기준 선택지는 세 가지다 [C2].

  • Yes, and use auto mode(자동 모드를 쓸 수 없으면 Yes, auto-accept edits): 승인하고 편집을 묻지 않고 진행한다.
  • Yes, manually approve edits: 승인하되 편집마다 사람이 확인한다.
  • No, keep planning: 계획 모드에 머물며 무엇을 바꿀지 말한다.

[최신 자료 자리: 계획 모드의 들어가는 법과 승인 선택지] 위 세 방법과 세 선택지의 이름. 확인할 곳 https://code.claude.com/docs/en/permission-modes. 2026-11-16에 다시 확인한 값은 위와 같다(집필 때 Claude Code 2.1.296).

[그림 자리: 계획 모드의 승인 화면] 상태 표시줄의 ⏸ plan mode on과 세 선택지가 보이는 화면. 1-3의 요청을 보낸 Claude Code에서 찍는다.

승인 화면에서 Ctrl+G는 계획을 편집기로 열고, Shift+Tab은 계획을 승인하므로 빠져나가려면 먼저 Esc를 누른다 [C2]. 이 장에서는 계획을 승인하지 않는다. 계획은 작업 목록을 만드는 재료로만 쓰고 구현은 작업 하나씩 따로 지시한다. 계획 하나를 승인해 전체 구현을 맡기면, 결과가 틀렸을 때 어느 작업에서 틀렸는지 찾기 어렵고 커밋도 하나로 뭉친다.

1-4. 계획의 검토

계획은 그대로 쓰지 않고 명세에 대어 읽는다. 검토의 질문은 세 가지다.

  2. 명세에 있는데 계획에서 빠진 것이 있는가. 화면 명세의 「지원 일정에 추가」 링크, 빈 상태 안내, 없는 공고 안내처럼 화면의 “상태”는 계획에서 자주 빠진다.

작업 목록은 계획의 구현 순서를 “한 번의 지시로 끝나고, 끝났는지 확인할 수 있고, 커밋 하나가 되는 크기”의 조각으로 나눈 표다. 크기가 이보다 크면 결과를 검토하기 어렵고, 작으면 지시문을 쓰는 비용이 구현보다 커진다. 판단의 기준을 표로 정리한다.

2-1. 지시문의 다섯 칸

작업 하나를 Claude Code에 맡길 때 쓰는 지시문을 이 과목에서는 구현 지시문이라 부른다. 구현 지시문은 다섯 칸으로 구성한다.

칸 담는 것 빠지면 생기는 일
참조 이 작업이 따르는 명세의 요구 번호, 화면 명세의 화면 번호, 디자인 토큰, 이미 있는 공통 코드 Claude Code가 명세 대신 일반적인 관례로 만든다. 문구, 상태, 색이 명세와 달라진다

완료 조건 끝났다고 말할 수 있는 관찰 가능한 결과(실행할 명령과 기대하는 출력) “구현했습니다”라는 말로 끝난다. 무엇이 확인되었는지 알 수 없다

다섯 칸은 2026년판 3주차의 두 사고에 대한 대응이기도 하다. “완료했습니다”를 믿었다가 빠진 요구가 드러난 일은 완료 조건이, AI가 테스트를 고친 일은 금지 사항이 없을 때 생긴다 [R1].

2-4. 화면 명세에 「검사용 약속」 붙이기

자동 검사는 화면의 요소를 이름으로 찾는다. “검색어 입력란”을 기계가 찾으려면 그것이 #search-input이라는 약속이 있어야 한다. 이 약속이 없으면 Claude Code가 지은 이름(#searchBox, #q)과 검사가 찾는 이름이 어긋나, 기능은 맞는데 검사가 실패한다. 그래서 이 장은 화면 명세에 「검사용 약속」 절을 더한다. 화면 명세가 사람에게는 화면의 모양을, 기계에게는 화면의 이름표를 정하는 문서가 된다.

줄 번호는 자기 화면 명세의 길이에 따라 다르다. 약속은 다섯 부분이다. 화면과 구현 파일의 대응(0-5의 표), 파일과 경로(상대 경로, 외부 주소 금지), 정렬과 기준일, 브라우저 저장소의 키, 화면마다의 식별자(id와 class)다. 식별자를 바꿀 때는 이 표와 검사를 함께 고친다. 기준일 약속은 REQ-003(마감 임박 표시) 때문에 있다. 이 요구의 결과는 “오늘”에 따라 바뀌므로(5월 17일이면 5월 19일 마감 공고에 「마감 임박 D-2」, 5월 22일이면 「마감」), 검사가 실제 오늘 날짜를 쓰면 같은 구현의 결과가 날마다 달라진다. 수업 날에는 통과하고 다음 주에는 실패하는 검사는 아무것도 증명하지 못한다. 그래서 주소에 ?today=YYYY-MM-DD가 있으면 화면이 그 날을 오늘로 보고, 검사는 이 약속으로 날짜를 고정한다. 사용자는 이 매개변수를 쓰지 않는다. 시간처럼 밖에서 들어오는 값을 바꿔 끼울 수 있게 하는 것은 검사할 수 있는 소프트웨어의 일반적인 설계 방법이다(10장의 모의 모드 LLM_FAKE=1도 같은 생각이다).

이 약속은 구현 방법을 정하는 것처럼 보이지만, 명세의 원칙(기술을 말하지 않는다)을 어기지 않는다. 약속이 정하는 것은 “밖에서 관찰할 수 있는 이름”이지 내부 구조가 아니다. 함수 이름, 파일 안의 코드 배치, 자료 처리 방법은 여전히 구현이 정한다.

확인 8 docs/설계/화면명세.md에 「검사용 약속」 절이 있고, jobprep/CLAUDE.md에 「웹 구현 규칙」이 있다. 둘을 한 커밋으로 남겼다.

3. 정적 웹과 로컬 서버

3-1. 정적 웹

정적 웹(static web)은 미리 만들어 둔 파일(HTML, CSS, 자바스크립트, 이미지, JSON)을 서버가 그대로 보내 주기만 하는 웹이다. 요청이 올 때마다 서버에서 프로그램이 돌아 답을 만드는 웹을 동적 웹이라 한다. 2026년판 3주차는 이 구분을 “정적 파일”과 “서버 코드”로 설명하였다 [R1].

정적 웹에서도 화면은 움직인다. 검색어를 넣으면 목록이 줄고, 버튼을 누르면 글자가 바뀐다. 그 일은 서버가 아니라 사용자의 브라우저가 자바스크립트로 한다. 이 장의 웹이 정적 웹으로 충분한 까닭과 한계를 표로 정리한다.

3-2. 정적 자료를 JSON으로 두는 까닭

공고 30건은 HTML 안에 직접 적을 수도 있으나, 이 장은 공고를 data/jobs.json이라는 별도 파일로 두고 화면이 그 파일을 읽어 그린다. 자료가 바뀌면 jobs.json만 고치면 되고, 목록·상세·관심 공고·일정의 네 화면이 같은 파일을 읽어 함께 맞으며, 10장에서 자료를 서버가 내주게 바꾸어도 JSON의 모양이 같아 화면은 읽는 주소만 바꾸면 된다.

브라우저의 자바스크립트는 fetch()로 파일을 요청하고 .json()으로 자바스크립트의 객체로 바꾼다. 견본 구현의 공통 기능은 다음과 같다.

[파일: jobprep/web/js/common.js] (견본 구현의 일부)

/* 공고 자료(data/jobs.json)를 읽는다. 상대 경로로 부른다(프로젝트 사이트의 하위 경로에서도 동작). */
async function loadJobs() {
  const response = await fetch("data/jobs.json");
  if (!response.ok) {
    throw new Error("공고 자료를 읽지 못했습니다: " + response.status);
  }
  const data = await response.json();
  return data.jobs;
}

학습자의 구현은 Claude Code가 만들므로 모양이 다를 수 있다. 읽을 때 볼 곳은 두 군데다. 주소가 "data/jobs.json"처럼 / 없이 시작하는가(상대 경로), 읽지 못했을 때의 처리가 있는가(response.ok 확인과 화면의 오류 문구)이다.

3-3. file://로 열면 생기는 일

2026년판 3주차의 실습 1은 HTML 파일을 더블클릭해 file:// 주소로 열어 보았다 [R1]. 그때는 파일 하나짜리 화면이라 잘 열렸다. 이 장의 웹을 같은 방법으로 열면 화면의 틀은 보이지만 공고가 하나도 나오지 않는다.

[브라우저] (개발자 도구 F12 → Console 탭)

Fetch API cannot load file:///C:/.../jobprep/web/data/jobs.json.
URL scheme "file" is not supported.

위 문구는 2026-11-14에 Chromium 156에서 확인한 것이며 브라우저와 판에 따라 다르다. MDN에 따르면 여러 브라우저는 로컬 파일을 출처가 불투명한(opaque) 것으로 다루고, 다른 자원을 요청하는 일(CORS 요청)은 http와 https에서만 허용하며, 로컬에서 시험하려면 로컬 서버를 띄우라고 안내한다 [W4]. 로컬 파일이 다른 로컬 파일을 마음대로 읽을 수 있으면, 내려받은 HTML 파일 하나가 내 컴퓨터의 다른 파일을 읽어 밖으로 보낼 수 있기 때문이다.

견본 구현은 이때 화면에 “공고 자료를 불러오지 못했습니다. 로컬 서버로 열었는지 확인하십시오.”를 보인다. 오류를 콘솔에만 남기지 않고 화면에 보이는 것은 REQ-004(공고 자료를 읽지 못하면 안내)와 화면 명세 SCR-01의 「오류」 상태를 구현한 것이다.

3-4. 로컬 서버: python -m http.server

파이썬 표준 라이브러리의 http.server는 지정한 폴더의 파일을 http로 보내 주는 간단한 서버다. 설치할 것이 없다 [P1].

  • [port]: 기다릴 포트 번호. 기본값은 8000이다 [P1].
  • -b, --bind 주소: 연결을 받을 주소. 기본값은 모든 네트워크 주소이고, 127.0.0.1이면 이 컴퓨터 안에서만 받는다 [P1].
  • -d, --directory 폴더: 보낼 폴더. 기본값은 지금 폴더다 [P1].

공식 문서는 이 서버를 운영용으로 쓰지 말라고 경고한다. 기본적인 보안 점검만 하고, 심볼릭 링크를 따라가 지정한 폴더 밖의 파일을 보낼 수 있기 때문이다 [P1]. 개발 중의 확인에만 쓰고, 공개는 9절의 GitHub Pages로 한다.

실습 서버는 여러 학습자가 함께 쓰므로, 모두 기본값 8000번을 쓰면 두 번째 사람부터 “Address already in use” 오류가 난다. 그래서 학습자마다 개인 포트를 쓴다(부록 A-19). 이 장의 웹은 첫째 포트 8000+출석번호를 쓰며, 본문의 8001은 출석 번호 1번의 예시다. 주소는 127.0.0.1로 묶어 서버 밖의 네트워크에서는 접속할 수 없게 한다.

서버 터미널 
cd ~/llm-service-lab/jobprep/web
python3 -m http.server 8001 --bind 127.0.0.1
Serving HTTP on 127.0.0.1 port 8001 (http://127.0.0.1:8001/) ...

이 터미널은 서버가 돌고 있으므로 다른 명령을 받지 않는다. 멈출 때는 Ctrl+C를 누른다.

서버는 실습 서버 안에서 돌고, 브라우저는 내 PC에 있다. VS Code Remote-SSH의 포트 전달(Ports 보기의 Add Port에 자기 포트를 넣는다)로 내 PC의 localhost:번호에서 연다(부록 A-19) [W7]. 서버 없이 내 PC에서 하는 학습자는 http://127.0.0.1:번호/를 바로 연다.

[그림 자리: VS Code의 포트 전달] 아래쪽 패널 Ports 보기에 자기 포트(예: 8001)와 내 PC 쪽 주소 localhost:8001이 한 줄로 보이는 화면. VS Code Remote-SSH로 실습 서버에 접속한 창에서 찍는다.

브라우저에서 http://localhost:8001/(자기 번호)을 연다. 서버 터미널에는 브라우저가 요청한 파일마다 한 줄씩 기록이 찍힌다. 이 기록이 “브라우저가 무엇을 요청했고 서버가 무엇을 답했는가”의 증거다.

127.0.0.1 - - [14/Nov/2026 12:22:21] "GET / HTTP/1.1" 200 -
127.0.0.1 - - [14/Nov/2026 12:22:21] "GET /data/jobs.json HTTP/1.1" 200 -
127.0.0.1 - - [14/Nov/2026 12:22:21] code 404, message File not found
127.0.0.1 - - [14/Nov/2026 12:22:21] "GET /nothing.html HTTP/1.1" 404 -

끝의 숫자는 HTTP 상태 코드다. 200은 성공, 404는 그런 파일이 없음이다. 화면이 깨졌을 때 이 기록에서 404가 난 파일을 찾으면, 경로의 오타나 대소문자 차이를 바로 알 수 있다.

확인 9 구현을 시작하기 전(화면 파일이 없는 지금) 로컬 서버를 띄워 브라우저로 열면 파일 목록 화면(“Directory listing for /”)이 보이고, data/jobs.json을 누르면 공고 자료가 보인다.

3-5. 프로젝트 사이트의 하위 경로를 미리 흉내 내기 [선택]

9절에서 배포할 주소는 https://아이디.github.io/llm-service-lab/이다. 사이트가 도메인의 맨 위(/)가 아니라 저장소 이름 아래(/llm-service-lab/)에 열린다. 이것이 GitHub Pages의 프로젝트 사이트다 [G3].

이 차이 때문에 생기는 대표적인 실패가 /로 시작하는 경로다. 화면이 fetch("/data/jobs.json")으로 자료를 부르면, 로컬 서버(http://localhost:8001/)에서는 http://localhost:8001/data/jobs.json이 되어 잘 열린다. 배포한 뒤에는 https://아이디.github.io/data/jobs.json을 찾는다. 저장소 이름이 빠진 주소이므로 404가 난다. 로컬에서는 잘 되던 것이 배포하면 깨지는, “제 머신에선 되는데요”의 전형이다 [R1].

배포하기 전에 이 상황을 로컬에서 흉내 낼 수 있다. 3-4의 서버를 Ctrl+C로 멈추고, 같은 포트로 web의 한 단계 위인 jobprep에서 띄운 뒤 /web/으로 연다. 사이트가 하위 경로에 열리는 프로젝트 사이트와 같은 조건이 된다.

서버 터미널 
cd ~/llm-service-lab/jobprep
python3 -m http.server 8001 --bind 127.0.0.1

브라우저에서 http://localhost:8001/web/을 연다. 집필할 때 fetch("/data/jobs.json")으로 바꾼 견본은 맨 위에서 띄운 서버에서 30건, 하위 경로에서 0건과 오류 문구를 보였고, 상대 경로로 되돌리면 둘 다 30건이었다.

확인 10 [선택] 구현을 마친 뒤(7절) jobprep에서 띄운 서버의 /web/ 주소로 열어도 공고 30건이 보인다. 이 확인은 7절의 손 점검 목록에 다시 나온다.

3-6. 개발자 도구로 보는 세 곳

브라우저의 개발자 도구(F12)는 정적 웹을 확인하는 기본 도구다. 이 장에서 쓰는 곳은 세 군데다.

  • Console: 자바스크립트 오류와 경고. 화면이 비었을 때 맨 먼저 본다. 빨간 줄의 첫 문장이 원인인 경우가 많다.
  • Network: 브라우저가 요청한 파일, 주소, 상태 코드. 404가 난 파일, 사이트 밖으로 나간 요청이 있는지 본다(AC-039-1).
  • Application → Storage → Local storage: 이 출처의 localStorage 키와 값. 관심 공고와 일정이 어떻게 저장되었는지 본다(AC-039-3).

[그림 자리: 개발자 도구의 Network 탭과 Local storage] Network 탭에 jobs.json 행과 상태 200이 보이는 화면, Application → Local storage에 jobprep:saved 키와 값이 보이는 화면. Chrome에서 로컬 서버로 연 목록 화면을 찍는다.

확인 11 개발자 도구의 Network 탭을 연 채로 새로고침했을 때 요청 목록에 jobs.json이 보이고 상태가 200이다.

4. 브라우저 저장소

4-1. Web Storage와 출처

브라우저 저장소(Web Storage)는 웹 페이지가 사용자의 브라우저 안에 문자열 키와 값을 저장하는 기능이다. localStorage와 sessionStorage 두 가지가 있다 [W1][W2]. 이 장의 관심 공고(REQ-008, REQ-009, REQ-038)와 지원 일정(REQ-009, REQ-010, REQ-032)은 localStorage에 저장한다.

저장소는 출처(origin)마다 따로 있다. 출처는 프로토콜, 호스트, 포트의 묶음이다. http://example.com과 https://example.com은 프로토콜이 달라 서로 다른 저장소를 가진다 [W1]. 이 규칙에서 이 장에 중요한 사실 세 가지가 나온다.

  1. 로컬과 배포의 기록은 이어지지 않는다. http://localhost:8001에서 저장한 관심 공고는 https://아이디.github.io에서 보이지 않는다. 출처가 다르기 때문이다. 포트 번호가 바뀌어도 출처가 바뀌므로, 다른 번호로 서버를 띄우면 저장소가 비어 있는 것처럼 보인다. 자기 포트를 늘 같은 번호로 쓰는 까닭의 하나다.
  2. 같은 계정의 다른 저장소 사이트와는 출처가 같다. 출처에는 경로가 들어가지 않는다. https://아이디.github.io/llm-service-lab/과 https://아이디.github.io/다른저장소/는 같은 출처이므로 같은 localStorage를 쓴다. 두 사이트가 모두 saved라는 키를 쓰면 서로의 값을 덮어쓴다. 화면 명세의 약속이 키 앞에 jobprep:를 붙이게 한 까닭이 이것이다.
  3. file://의 저장소는 믿을 수 없다. 그 동작은 정해져 있지 않고 브라우저마다 다르다 [W1].

4-2. 기본 사용법 [선택]

localStorage의 키와 값은 문자열이다 [W1]. 배열이나 객체를 저장하려면 JSON.stringify로 문자열로 바꾸어 넣고, 꺼낼 때 JSON.parse로 되돌린다.

[브라우저] (개발자 도구 Console 탭에 한 줄씩 입력)

localStorage.setItem("jobprep:saved", JSON.stringify(["JOB-003", "JOB-017"]));
localStorage.getItem("jobprep:saved");
JSON.parse(localStorage.getItem("jobprep:saved")).length;
localStorage.setItem("숫자", 3);
typeof localStorage.getItem("숫자");
localStorage.removeItem("숫자");
undefined
'["JOB-003","JOB-017"]'
2
undefined
'string'
undefined

숫자 3을 넣어도 꺼내면 문자열 "3"이 된다. JSON.stringify 없이 배열을 넣으면 "JOB-003,JOB-017"처럼 쉼표로 이은 문자열이 되어, 꺼낸 뒤 배열로 되돌릴 수 없다. Claude Code가 만든 코드에서 setItem이 나오면 그 앞에 JSON.stringify가 있는지 본다.

저장된 값은 깨져 있을 수 있다. 사용자가 개발자 도구에서 값을 고쳤거나, 이전 판의 구현이 다른 모양으로 저장했을 수 있다. 견본 구현은 읽을 때 오류를 잡아 빈 배열로 다룬다.

[파일: jobprep/web/js/common.js] (견본 구현의 일부)

/* 저장소에서 배열을 읽는다. 값이 없거나 깨져 있으면 빈 배열을 돌려준다. */
function readList(key) {
  try {
    const raw = localStorage.getItem(key);
    const value = raw ? JSON.parse(raw) : [];
    return Array.isArray(value) ? value : [];
  } catch (error) {
    return [];
  }
}

/* 저장소에 배열을 쓴다. 용량 초과나 저장 차단이면 false 를 돌려준다. */
function writeList(key, list) {
  try {
    localStorage.setItem(key, JSON.stringify(list));
    return true;
  } catch (error) {
    return false;
  }
}

쓰기에도 try가 있는 까닭은 두 가지 실패 때문이다. 저장 용량을 넘으면 브라우저가 QuotaExceededError를 던진다 [W3]. 사용자가 사이트 데이터 저장을 막았거나 정책이 막으면 localStorage에 접근할 때 SecurityError가 난다 [W1]. 견본의 지원 일정 화면은 쓰기에 실패하면 “브라우저 저장소에 쓰지 못했습니다.”를 보인다.

확인 12 [선택] Console에서 위 여섯 줄을 실행해 같은 결과를 얻고, Application 탭의 Local storage에서 jobprep:saved 키를 확인한 뒤 지웠다.

4-3. 데이터의 수명

명세 REQ-009는 “페이지를 다시 열어도 유지”를 요구하고, 이 장의 인수 조건은 그것을 “새 탭에서 열어도”, “브라우저를 닫았다 다시 열어도”로 구체화한다. 브라우저 저장소의 종류마다 수명이 다르므로, 계획이 어느 것을 골랐는지가 이 요구의 충족을 가른다.

저장 방법 언제까지 남는가 다른 탭에서 보이는가 이 장에서
자바스크립트 변수 페이지를 떠나거나 새로고침하면 사라진다 아니다 화면이 그리는 동안의 임시 값
sessionStorage 탭이나 창을 닫으면 사라진다. 새로고침은 견딘다 [W2] 아니다. 새 탭은 새 세션이다 [W2] 쓰지 않는다
localStorage 만료가 없다. 브라우저를 다시 시작해도 남는다 [W1] 같은 출처의 모든 탭 관심 공고, 지원 일정
사생활 보호(시크릿) 창의 localStorage 마지막 시크릿 탭을 닫으면 지워진다 [W1] 같은 시크릿 세션 안 손 점검 때 주의
서버의 데이터베이스 서버가 지울 때까지 다른 기기에서도 범위 밖(로그인이 필요하다)

sessionStorage의 함정은 새로고침을 견딘다는 데 있다. 저장하고 새로고침해 보는 것만으로는 localStorage와 구별되지 않으므로, AC-009-1은 “새 탭에서 열어도 보이는가”를 함께 본다. 집필할 때 견본의 localStorage를 sessionStorage로 바꾸어 검사하자 AC-008-1, AC-038-1, AC-010-1은 통과하고 새 탭을 여는 AC-009-1만 실패하였다.

“만료가 없다”가 “영원히 남는다”는 뜻은 아니다. 브라우저 저장소는 최선 노력(best-effort) 저장이어서, 저장 공간이 모자라거나 브라우저의 정책이나 사용자가 사이트 데이터를 지우면 사라진다 [W3]. 그래서 견본 구현의 꼬리말은 “관심 공고와 지원 일정은 이 브라우저에만 저장된다”고 사용자에게 알린다.

4-4. 용량 [선택]

MDN에 따르면 브라우저는 출처마다 localStorage 5MiB까지 저장할 수 있다 [W3]. 이 장의 기록은 수 킬로바이트에 그친다. 공고 자료는 저장소에 넣지 않고 매번 data/jobs.json에서 읽으며, 저장소에는 사용자가 만든 것만 둔다.

4-5. 개인 정보와 브라우저 저장소

localStorage의 값은 암호화되지 않은 문자열이다. 같은 컴퓨터를 쓰는 다른 사람(공용 PC의 다음 사용자)이 개발자 도구로 열어 볼 수 있고, 화면에 악성 스크립트가 끼어들면(XSS) 저장소의 값이 밖으로 빠져나갈 수 있다.

명세 REQ-039는 이 위험을 두 가지로 다룬다. 기록을 외부로 보내지 않고, 메모에 개인 정보를 적지 않게 안내한다(견본은 메모 입력란 아래에 안내 문구를 둔다). 안내 문구는 입력을 기술적으로 막지 못하므로, 저장하는 것(공고 번호, 단계, 날짜, 짧은 메모)을 명세가 좁게 정하고 그 밖의 입력란(이름, 연락처)을 두지 않는 것이 더 강한 대책이다.

4-6. 사용자 입력을 화면에 넣는 법

지원 일정의 메모는 사용자가 친 글자이고, 그 글자가 목록 화면에 다시 나온다. 이때 innerHTML로 넣으면 글자가 HTML로 해석된다. MDN은 innerHTML을 교차 사이트 스크립팅(XSS) 공격의 가장 흔한 통로로 꼽고, 사용자가 준 내용이 평문이어야 하면 textContent를 쓰라고 권한다 [W5].

파일: 비교용 예시 (쓰지 않는다) 
// 위험: 메모가 HTML 로 해석된다
item.innerHTML = `<span class="memo">${entry.memo}</span>`;

// 안전: 메모는 글자로만 들어간다
const memo = document.createElement("span");
memo.className = "memo";
memo.textContent = entry.memo;
item.append(memo);

메모에 <img src=x onerror=alert(1)>를 넣으면, 위의 방식은 깨진 이미지를 만들고 onerror의 스크립트를 실행한다 [W5]. 아래의 방식은 그 글자를 그대로 보일 뿐이다. 스스로를 공격하는 사례라 해가 작아 보이지만, 10장에서 사용자 입력과 외부 문서에 영향을 받는 LLM의 출력을 화면에 넣을 때 같은 문제가 커진다. 그래서 innerHTML 금지를 이 장에서 CLAUDE.md의 규칙으로 세워 둔다.

확인 13 구현을 마친 뒤(7절) 지원 일정의 메모에 <b>굵게</b>를 넣어 추가했을 때, 목록에 굵은 글자가 아니라 <b>굵게</b>라는 글자가 그대로 보인다.

5. 인수 조건

5-1. 요구와 인수 조건

요구사항 명세서의 문장은 “시스템이 무엇을 해야 하는가”를 말하지만, 그것만으로는 구현이 요구를 충족했는지 판정하기 어렵다. REQ-006 “제목이나 모집기관에 검색어가 든 공고만 표시해야 한다”는 어떤 자료에서, 어떤 검색어를 넣고, 무엇을 보면 충족인가. 이 물음에 답한 것이 인수 조건(acceptance criteria)이다. 인수 조건은 요구 하나를 “이 상황에서 이렇게 하면 이것이 보여야 한다”는 구체적인 예로 바꾼 것이고, 예를 통과하면 그 요구를 받아들인다(인수한다). 출발점은 명세서 6절의 수용 기준이다. 수용 기준 AC-006-1의 예(「공무직」)는 이 장의 자료에 없으므로 같은 번호로 예를 바꾼다. 자료의 「기업」(company)이 명세의 「모집기관」이다.

구분 요구 (명세) 인수 조건
말하는 것 일반 규칙 구체적인 예 하나
예 검색어가 든 공고만 보인다 30건이 있을 때 “데이터”를 넣으면, 제목이나 기업에 “데이터”가 든 공고만 마감일 순으로 보인다
판정 사람의 해석이 필요하다 화면을 보면 참과 거짓이 갈린다
수 요구 하나 요구 하나에 하나 이상
누가 읽는가 기획자, 개발자, AI 개발자, 검사하는 사람, 자동 검사

인수 조건은 테스트와 다르다. 테스트는 인수 조건을 확인하는 수단의 하나다. 같은 인수 조건을 사람이 화면에서 손으로 확인할 수도 있고, 이 장의 자동 검사처럼 기계가 확인할 수도 있다. 이 과목은 인수 조건을 쓰고 기계로 확인하는 데까지 다룬다. 테스트를 먼저 쓰고 구현을 그에 맞추어 키우는 테스트 주도 개발(TDD)은 「AI에이전트 기획 및 개발」 2장이 다룬다.

5-2. Given-When-Then

인수 조건은 흔히 Given-When-Then의 세 부분으로 쓴다. Daniel Terhorst-North와 Chris Matts가 행위 주도 개발(BDD)의 일부로 만든 형식이고, 시나리오 하나를 세 부분으로 나누어 쓰는 방식이다 [S2].

부분 뜻 [S2] 이 장의 예 (AC-009-1)
Given 행동 전의 상태. 시나리오의 전제 조건 JOB-005가 관심 공고가 아니다
When 명세하려는 행동 상세 화면에서 저장을 누르고, 새로고침하고, 새 탭에서 관심 공고 화면을 연다
Then 그 행동의 결과로 기대하는 변화 버튼이 “관심 해제”로 남고, 새 탭의 관심 공고 화면에 JOB-005가 보인다

Given을 빼먹기 쉽다. “검색어를 넣으면 결과가 나온다”는 Given이 없다. 공고가 0건이면 무엇을 넣어도 결과가 없다. 관심 공고가 이미 저장된 상태에서 저장 버튼을 누르면 해제가 된다. Given이 다르면 같은 When이 다른 Then을 낳는다.

Then은 관찰할 수 있어야 한다. “빠르게 보인다”, “잘 동작한다”, “사용하기 편하다”는 Then이 될 수 없다. 무엇을 보면 참인지 정할 수 없기 때문이다. 화면의 글자, 요소의 수, 요소가 보이는가, 주소가 무엇인가처럼 보면 참과 거짓이 갈리는 것으로 쓴다.

5-3. 좋은 인수 조건과 나쁜 인수 조건

나쁜 예 문제 고친 예
검색이 잘 된다 Then을 관찰할 수 없다. Given과 When이 없다 Given 30건, When “데이터” 입력, Then 제목이나 기업에 “데이터”가 든 공고만 보인다
filter 함수가 배열을 거른다 구현 방법을 적었다. 사용자는 함수를 보지 않는다 Then을 화면에 보이는 카드로 쓴다
관심 공고가 저장된다 “저장된다”를 어떻게 보는지 없다 Then 버튼이 “관심 해제”로 바뀌고, 새 탭의 관심 공고 화면에 보인다
마감 임박 공고가 눈에 띈다 “임박”, “눈에 띈다”가 수와 모양으로 정해지지 않았다 Given 기준일 2027-05-17, When 목록을 연다, Then 0~3일 남은 공고에 「마감 임박 D-N」(REQ-003의 3일 이하, 검사용 약속의 문구)
오류 없이 동작한다 무엇을 했을 때의 오류인지 없다 Given 일정 0건, When 날짜 없이 추가, Then 오류 문구가 보이고 일정이 0건이다

인수 조건을 쓰다 보면 명세의 빈틈이 드러난다. “검색어가 포함된”은 대소문자를 가리는가. 공백만 넣으면 어떻게 되는가. 명세가 말하지 않는 것은 인수 조건이 정하지 않는다. 인수 조건이 명세에 없는 규칙을 만들면, 명세와 인수 조건이 서로 다른 말을 하는 두 기준이 된다. 빈틈을 찾으면 명세에 결정을 더하고(1-4의 메모 길이처럼) 인수 조건은 그 결정을 따른다.

5-4. 인수 조건 표

인수 조건은 표로 모은다. 번호는 AC-<요구 번호 세 자리>-<순번>이다. REQ-007의 두 번째 인수 조건이면 AC-007-2다. 명세서의 수용 기준을 구체화한 것은 그 번호(-1)를 그대로 쓰고, 이 장에서 더한 것은 다음 순번을 쓴다. 번호만 보고도 어느 요구의 것인지 알 수 있어, 요구가 바뀌었을 때 고칠 인수 조건을 바로 찾는다.

「확인 방법」 칸에는 셋 중 하나를 적는다.

5-5. 추적: 요구에서 인수 조건으로 [선택]

6장의 추적표는 페르소나와 문제 정의에서 요구로 이어지는 선을 그렸다. 인수 조건 표는 그 선을 요구에서 검사로 잇는다. 선이 끊긴 곳을 찾는 질문은 두 가지다.

  1. 이 장에서 구현하는 요구(작업 목록의 「요구」 칸) 가운데 인수 조건이 하나도 없는 것이 있는가. 그 요구는 충족했는지 아무도 확인하지 않는다.

6. 간단한 자동 검사

6-1. 무엇을 기계가 확인하는가

자동 검사는 인수 조건 가운데 기계가 판정할 수 있는 것을 사람 대신 판정하는 프로그램이다. 사람이 손으로 하면 인수 조건 20개를 한 번 확인하는 데 수십 분이 걸리고, 고칠 때마다 다시 해야 한다. 기계는 같은 확인을 1분 안팎에 매번 똑같이 한다. 집필할 때 견본 구현에 대해 브라우저 검사 22개를 실행하는 데 약 39초가 걸렸다(Windows 11, 2026-11-14).

층 파일 보는 것 필요한 것 속도

6-2. 정적 검사의 구성

정적 검사는 파이썬의 html.parser로 HTML을 읽는다. HTMLParser는 잘못된 마크업도 읽을 수 있는 파서이고, 여는 태그를 만날 때마다 태그 이름과 (속성 이름, 값) 쌍의 목록을 넘겨준다 [P2]. 검사의 PageParser는 이 목록에서 lang, id, href, src, label for를 모은다. 브라우저를 띄우지 않으므로 자바스크립트가 나중에 만드는 요소(공고 카드)는 보지 못한다. 그것은 브라우저 검사의 몫이다.

검사 항목은 S-01~S-08의 여덟 개다. 항목마다 관련 인수 조건이 있다(check/README.md의 표). 예를 들어 S-04는 화면 명세 「검사용 약속」의 식별자가 HTML에 모두 있는지 본다. 검사 안의 식별자 목록은 화면 명세의 표를 그대로 옮긴 것이다.

6-3. Playwright 준비

Playwright는 브라우저를 프로그램으로 조작하는 도구다 [P3]. 이 장은 동기 방식(playwright.sync_api)만 쓰고, 공식 안내가 먼저 보이는 pytest-playwright 대신 playwright 꾸러미만 쓴다. 검사 프로그램을 일반 파이썬 스크립트로 두어 인수 조건과 검사 함수가 하나씩 대응하는 것만 보이기 위해서다.

Playwright는 파이썬 꾸러미와 별도로 브라우저 파일을 내려받는다. 이 장은 화면 없이(headless) 검사만 하므로 --only-shell로 headless 전용 Chromium만 받는다 [P5]. 받는 위치와 크기, 서버에서 지킬 것은 부록 A-20에 있다.

6-4. 인수 조건 하나가 검사 함수 하나

브라우저 검사는 인수 조건마다 함수 하나를 둔다. 함수 위의 @ac(번호, 제목)가 그 함수를 인수 조건 번호에 묶는다. 함수의 본문은 Given, When, Then의 순서를 그대로 따른다.

[파일: jobprep/web/check/check_browser.py] (일부)

@ac("AC-009-1", "관심 공고로 저장한 뒤 새로고침해도, 새 탭에서 열어도 저장 상태가 남는다")
def ac_009_1(page, base):
    # Given: JOB-005 가 관심 공고가 아니다 (검사마다 새 브라우저 문맥이라 저장소가 비어 있다)
    page.goto(base + "detail.html?id=JOB-005")
    expect(page.locator("#save-toggle")).to_have_text("관심 공고 저장", timeout=TIMEOUT)
    # When: 저장하고 새로고침한다
    page.click("#save-toggle")
    page.reload()
    # Then: 버튼이 "관심 해제"로 남는다
    expect(page.locator("#save-toggle")).to_have_text("관심 해제", timeout=TIMEOUT)
    # 새 탭에서 연다. sessionStorage 로 잘못 구현하면 새로고침은 통과해도 여기서 실패한다.
    other = page.context.new_page()
    other.goto(base + "saved.html")
    expect(other.locator(".saved-item[data-job-id='JOB-005']")).to_be_visible(timeout=TIMEOUT)

읽는 데 필요한 Playwright의 말은 많지 않다.

표현 뜻
page.goto(주소) 그 주소를 연다
page.locator("#save-toggle") 화면에서 그 식별자의 요소를 가리킨다(아직 찾지는 않는다)
page.click(...), page.fill(..., "글자"), page.select_option(..., "값") 누른다, 입력한다, 고른다
expect(요소).to_have_text("…") 요소의 글자가 그것이어야 한다
expect(요소).to_have_count(n) 그 요소가 n개여야 한다
expect(요소).to_be_visible(), .to_be_hidden() 보여야 한다, 숨어야 한다
expect(요소).to_contain_text("…") 그 글자를 포함해야 한다

expect는 기대한 상태가 될 때까지 요소를 다시 찾아 확인하기를 되풀이하고, 기본 5초가 지나도 안 되면 실패로 본다 [P4]. 화면이 자료를 받아 그리는 데 걸리는 짧은 시간을 기다려 주므로, 검사 안에 “1초 쉬기” 같은 줄을 넣지 않아도 된다.

기대값은 구현에서 가져오지 않는다. AC-006-1은 “데이터”를 검색했을 때 보여야 할 공고 번호를 검사가 jobs.json에서 직접 계산한다. 명세 REQ-002, REQ-006, REQ-028을 파이썬으로 옮긴 함수다.

[파일: jobprep/web/check/check_browser.py] (일부)

def expected_ids(keyword="", category="", region=""):
    """명세 REQ-002, REQ-006, REQ-028 을 그대로 계산한 기대 결과(마감일 순 공고 번호)."""
    out = []
    for job in JOBS:
        text = f"{job['title']} {job['company']}".lower()   # REQ-006: 제목이나 모집기관
        if keyword and keyword.lower() not in text:
            continue
        if category and job["category"] != category:

구현의 자바스크립트를 베껴 기대값을 만들면, 구현이 틀렸을 때 기대값도 같이 틀려 검사가 통과한다. 기대값은 명세에서 나와야 한다.

검사 프로그램은 스스로 로컬 서버를 띄운다. 127.0.0.1의 빈 포트에 web 폴더를 보내는 서버를 만들고, 검사가 끝나면 닫는다. 그래서 3절처럼 서버를 따로 띄워 둘 필요가 없다. 인수 조건마다 새 브라우저 문맥(context)을 열므로, 앞 검사에서 저장한 관심 공고가 다음 검사의 Given을 흐리지 않는다.

6-5. 검사가 증명하지 않는 것

모든 검사가 통과해도 다음은 알 수 없다.

  • 검사가 고른 예 밖의 입력. “데이터”와 “개발자”를 검색해 보았다고 모든 검색어가 맞다는 보장은 없다.
  • 화면이 보기 좋은가, 글이 읽기 쉬운가, 사용자가 길을 잃지 않는가. 이것은 13장의 사용성 평가가 다룬다.
  • 손 점검으로 남긴 항목. 키보드 조작, 실제 폰, 브라우저 재시작.
  • 명세 자체가 맞는가. 검사는 구현이 명세를 따르는지를 볼 뿐, 명세가 사용자의 문제를 푸는지는 보지 않는다.

그래서 보고는 “검사를 통과했다”가 아니라 “인수 조건 몇 개 가운데 자동 몇 개 통과, 손 점검 몇 개 기록”으로 한다. 무엇을 확인했고 무엇을 확인하지 않았는지가 함께 드러나야 한다.

확인 18 check/README.md의 「검사가 보증하지 않는 것」을 읽고, 자기 인수 조건 표에서 손 점검으로 둔 행이 4개 이상인지 확인하였다.

8. 배포의 개념과 GitHub Pages

8-1. 로컬과 배포

배포(deployment)는 내 파일을 서버에 올려 누구든 요청할 수 있게 하는 일이고, 그 결과가 공개 주소다 [R1]. 7절까지의 웹은 로컬에 있다. 실습 서버의 내 폴더에 파일이 있고, 그 파일을 보는 사람은 나 하나다. 배포하면 파일이 GitHub의 서버로 가고, 주소를 아는 누구나 연다.

구분 로컬 (7절까지) 배포 (9절부터)
파일의 위치 실습 서버의 jobprep/web/ GitHub Pages 서버
주소 http://localhost:포트/ https://아이디.github.io/llm-service-lab/
보는 사람 나 주소를 아는 누구나(검색 엔진 포함)
고친 것의 반영 저장하고 새로고침 커밋하고 푸시하면 워크플로가 다시 배포
잘못되었을 때 나만 본다 모든 방문자가 본다
브라우저 저장소의 출처 http://localhost:포트 https://아이디.github.io (다른 출처이므로 기록이 이어지지 않는다)

이 장은 2026년판 3주차가 소개한 “만드는 동안은 로컬, 완성본만 배포”의 동선대로, 인수 조건을 로컬에서 통과한 뒤에 배포한다 [R1].

8-2. 공개되는 것

배포에서 가장 먼저 물을 것은 “무엇이 공개되는가”다. GitHub Pages에서는 공개되는 것이 두 겹이다.

  1. 사이트에 올린 파일. 브라우저가 받는 파일은 모두 누구나 내려받을 수 있다. 자바스크립트를 숨기거나 줄여도 내용은 읽힌다. 화면에 보이지 않는 주석, 쓰지 않는 파일, 실수로 들어간 키도 마찬가지다.
  2. 저장소 자체. GitHub Free 계정에서는 Pages를 쓰려면 저장소가 공개여야 한다 [G4][G6]. 저장소가 공개이면 사이트에 올리지 않은 파일(docs/, ch05/의 인터뷰 기록, 커밋 기록 전체)도 누구나 읽는다.

GitHub Pro 계정은 비공개 저장소에서도 Pages를 쓸 수 있지만, 그때도 사이트는 인터넷에 공개된다 [G4]. 사이트를 비공개로 게시하는 기능은 GitHub Enterprise Cloud의 조직에만 있다 [G6]. 재학생은 Student Developer Pack에서 학생인 동안 GitHub Pro를 무료로 받을 수 있다(부록 A-10-3) [G10].

[최신 자료 자리: 요금제별 Pages 조건과 학생 혜택] Free 계정이 비공개 저장소에서 Pages를 쓸 수 있는지, Student Developer Pack에 GitHub Pro가 드는지. 확인할 곳 [G4], [G6], [G10]. 2026-11-14 집필 때의 값은 아래 표와 같다. 학기 초에 다시 확인한다.

5장의 인터뷰 기록은 비식별화했더라도 동료의 경험이므로 개인 실습 저장소는 비공개로 둔다. 학생 혜택(Pro)이 있으면 그 저장소에서 Pages만 공개하고, 없으면 Pages용 공개 저장소를 따로 만든다(9-5). 어느 길이든 공개되는 것은 _site의 파일뿐이다.

GitHub Pages는 방문자의 IP 주소를 보안 목적으로 기록하고 [G3], 비밀번호나 카드 번호 같은 민감한 거래를 다루지 말라고 정한다 [G5]. 이 장의 웹은 로그인도 결제도 없다.

확인 23 자기 GitHub 계정의 요금제(Free 또는 Pro)와 llm-service-lab 저장소의 공개 범위를 확인하고, 위 표의 어느 행인지 docs/배포기록.md의 「배포 설정」에 적었다. 저장소가 공개이면 git ls-files | head -50으로 공개될 파일을 훑어보았다.

8-3. GitHub Pages

GitHub Pages는 저장소의 HTML, CSS, 자바스크립트 파일을 그대로 받아 웹사이트로 내보내는 정적 사이트 호스팅이다 [G3]. 사이트에는 두 종류가 있다 [G3]. 사용자·조직 사이트는 이름이 아이디.github.io인 저장소에서 나오고 주소가 https://아이디.github.io이며 계정마다 하나다. 프로젝트 사이트는 아무 저장소에서나 나오고 주소가 https://아이디.github.io/저장소이름이며 저장소마다 하나다. 이 장의 사이트는 llm-service-lab 저장소의 프로젝트 사이트이므로 주소가 https://아이디.github.io/llm-service-lab/이다. 3-5에서 본 하위 경로가 여기서 나온다.

사용 한도(게시 사이트 1GB, 월 대역폭 100GB, 배포 시간 10분 등)가 있으나 이 장의 사이트는 50KB 안팎이다 [G5].

[최신 자료 자리: Pages와 Actions의 사용 한도] Pages 한도 [G5]와 비공개 저장소의 Actions 포함 사용량(8-4) [G7]. 2026-11-16에 다시 확인한 값은 1GB, 월 100GB, 시간당 10회, 10분, Free 월 12달러·Pro 월 18달러 상당이다.

8-4. 게시 원천: 브랜치와 워크플로 [선택]

이 과목은 GitHub Actions 워크플로로 게시한다. 이 절은 그 까닭을 다른 방식과 견주어 설명한다.

GitHub Pages가 어디서 파일을 가져올지를 게시 원천(publishing source)이라 한다. 두 가지가 있다 [G1].

방식 하는 일 고를 수 있는 폴더 맞는 경우
브랜치에서 게시 정한 브랜치에 푸시하면 그 브랜치의 폴더를 게시한다 저장소 맨 위(/) 또는 /docs 둘 중 하나 [G1] 사이트만 담은 저장소, 빌드 과정이 필요 없는 경우
GitHub Actions 워크플로 워크플로가 공개 폴더를 만들어 올리고 배포한다 워크플로가 정한 아무 폴더 공개할 파일을 고르거나 검사를 거쳐야 하는 경우, 사이트가 저장소의 일부인 경우

이 장의 사이트는 저장소 맨 위도 /docs도 아닌 jobprep/web/에 있어, 브랜치에서 게시하는 방식으로는 이 폴더를 고를 수 없다. 맨 위를 게시하면 저장소의 모든 파일(명세, 인터뷰 기록, 검사)이 사이트로 공개되고, /docs로 옮기면 6장부터 쌓아 온 jobprep/ 구조와 10장 이후의 경로가 모두 바뀐다.

그래서 이 과목은 GitHub Actions 워크플로를 쓴다. 고른 까닭을 정리한다.

  1. 폴더 제약이 없다. 워크플로가 jobprep/web/에서 공개할 파일만 골라 공개 폴더(_site)를 만들고, 그 폴더를 올린다.
  2. 공개할 파일을 고른다. check/ 폴더, 설명 파일(README.md), 점(.)으로 시작하는 파일은 사이트에 들어가지 않는다. 명세와 기록은 저장소에만 남는다.
  3. 검사를 통과해야 배포된다. 워크플로가 정적 검사와 배포 전 점검을 먼저 실행하고, 실패하면 배포 단계로 가지 않는다. 2026년판 3주차가 “실무의 표준 흐름”으로 소개한 CI(자동 검증)와 CD(검증을 통과한 버전의 자동 배포)를 작은 규모로 한다 [R1].
  4. 배포가 커밋에 묶인다. 워크플로의 실행 기록마다 어느 커밋을 배포했는지 남는다. 사이트에 문제가 생기면 그 커밋으로 거슬러 간다.
  5. 비용이 들지 않는다. 공개 저장소의 표준 실행기(runner)는 무료이고, 비공개 저장소는 계정의 월 포함 사용량 안에서 돈다 [G6][G7]. 이 장의 워크플로는 한 번에 1분 안팎이다.

사이트만 담은 저장소(예: 포트폴리오용 아이디.github.io)라면 더 쉬운 브랜치 게시가 맞다. 이 과목의 저장소는 명세, 설계, 검사, 다음 장의 서버 코드를 함께 담으므로 공개할 것을 고르는 단계가 필요하다.

9. 중심 실습: GitHub Pages 배포

9-1. 3단계의 순서

순서는 .gitignore 확인과 배포 전 점검(서버 터미널), 워크플로 파일 읽기(VS Code), 저장소의 Pages 설정(내 PC 브라우저의 GitHub), 푸시와 워크플로 실행 확인(서버 터미널과 Actions 탭), 공개 주소 점검(PC와 폰), 배포 기록이다.

9-2. .gitignore 확인

0절에서 키트의 gitignore_추가.txt를 .gitignore에 더하였다. 더한 줄은 세 무리다.

[파일: ~/llm-service-lab/.gitignore] (9장에서 더한 부분)

# 배포 전 점검 도구가 만드는 공개 폴더. 만들어 쓰는 것이므로 커밋하지 않는다
_site/
# 파이썬 캐시와 가상 환경
__pycache__/
.venv/
# 비밀 정보 (10장에서 API 키를 쓴다. 지금 미리 막아 둔다)
.env

끝에 /가 붙은 패턴은 폴더에만 맞는다 [G11]. .gitignore는 아직 추적하지 않는 파일에만 효과가 있다. 이미 커밋한 파일은 .gitignore에 적어도 계속 추적된다. 그런 파일을 추적에서 빼려면 git rm --cached로 색인에서 지운 뒤 .gitignore에 적는다 [G11]. 다만 이미 푸시한 커밋에는 그 파일이 남아 있으므로, 비밀 정보였다면 그 값을 폐기하고 새로 발급받는 것이 먼저다.

서버 터미널 
cd ~/llm-service-lab
git check-ignore -v _site/index.html .env
.gitignore:4:_site/ _site/index.html
.gitignore:9:.env   .env

줄 번호는 자기 .gitignore의 길이에 따라 다르다. 두 줄이 모두 나오면 두 경로가 무시된다는 뜻이다.

9-3. 배포 전 점검

jobprep/tools/predeploy.py는 저장소 맨 위에서 실행한다. 하는 일은 네 가지다. 공개할 파일만 고르기, 비밀 정보와 개인 정보로 보이는 문자열 찾기, 파일 크기와 /로 시작하는 경로 확인하기, 문제가 없으면 공개 폴더(_site) 만들기다. 2026년판의 prepare_site.py(공개할 파일만 deploy/로 복사)를 이 과목의 폴더 구조에 맞추고 점검을 더한 것이다 [R1].

서버 터미널 
cd ~/llm-service-lab
python3 jobprep/tools/predeploy.py

자동 점검은 정해진 형태만 찾는다. 위 목록과 파일 내용을 직접 읽고 배포한다.

위 출력은 견본 구현으로 집필할 때 실행한 결과다. 파일의 수와 크기는 구현마다 다르다. 읽을 곳은 두 목록이다. 「공개할 파일」에 공개하면 안 되는 것이 없는가, 「뺀 파일」에 공개해야 하는 것(예: 이미지)이 빠지지 않았는가.

점검이 무엇을 잡는지 일부러 시험해 본다. 견본 구현에 가짜 키 한 줄과 전화번호 모양의 글자를 넣고 실행하면 다음처럼 멈춘다(집필할 때 확인한 출력이다).

멈춤: 아래를 고친 뒤 다시 실행한다
  x index.html: 개인 정보로 보인다 (휴대전화 번호 형태: 010-…)
  x js/common.js: 비밀 정보로 보인다 (Anthropic API 키 형태)
  x js/common.js: 비밀 정보로 보인다 (키·비밀번호 대입문)

찾는 형태는 API 키와 토큰의 알려진 모양, password = "…" 같은 대입문, 휴대전화 번호, 주민등록번호, 전자우편 주소다. 이 도구는 정해진 형태만 찾으므로 통과가 안전을 보증하지 않는다. 출력의 마지막 줄이 그것을 다시 말한다.

GitHub의 푸시 보호(push protection)도 공개 저장소로의 푸시에서 지원하는 형태의 비밀을 막지만, 그 밖의 비밀은 막지 못한다 [G8]. 도구 둘이 겹쳐도 사람이 목록을 읽는 단계는 빠지지 않는다.

확인 24 9-2의 git check-ignore -v가 두 줄을 보이고, predeploy.py가 PREDEPLOY_OK로 끝나고, 「공개할 파일」 목록에 check/, .md, 점으로 시작하는 파일이 없다. git status --short에 _site가 나타나지 않는다(무시되고 있다).

9-4. 워크플로 파일 읽기

0절에서 복사한 .github/workflows/pages.yml이 배포 워크플로다. GitHub Actions의 워크플로는 저장소 맨 위의 .github/workflows/ 폴더에 있는 YAML 파일이다. jobprep/ 안이 아니라 저장소 맨 위에 두어야 GitHub가 찾는다. 파일을 위에서부터 읽는다.

[파일: ~/llm-service-lab/.github/workflows/pages.yml] (앞부분)

name: Pages 배포

on:
  push:
    branches: [main]
    paths:
      - "jobprep/web/**"
      - "jobprep/tools/predeploy.py"
      - ".github/workflows/pages.yml"
  workflow_dispatch:        # Actions 탭에서 손으로 다시 돌릴 수 있게 한다

permissions:
  contents: read            # 저장소를 읽기만 한다
  pages: write              # Pages 에 배포한다
  id-token: write           # 배포 요청이 이 저장소의 워크플로에서 왔음을 증명한다

concurrency:
  group: pages
  cancel-in-progress: false # 진행 중인 배포는 끝까지 두고, 기다리는 것 중 가장 새것만 돈다
항목 뜻
on.push.branches main에 푸시할 때 돈다
on.push.paths 바뀐 파일이 이 경로에 있을 때만 돈다. 명세 문서만 고친 푸시로는 배포하지 않는다
workflow_dispatch Actions 탭의 버튼으로 손으로 돌릴 수 있다
permissions 이 워크플로가 받는 권한. Pages 배포에는 최소한 pages: write와 id-token: write가 필요하다 [G2]
concurrency 배포가 겹치지 않게 한다. GitHub의 견본 워크플로와 같은 설정이다

[파일: ~/llm-service-lab/.github/workflows/pages.yml] (build 작업)

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - name: 저장소 받기
        uses: actions/checkout@v7

      - name: 파이썬 준비
        uses: actions/setup-python@v7
        with:
          python-version: "3.12"

      - name: 정적 검사 (표준 라이브러리만 쓴다)
        run: python jobprep/web/check/check_static.py jobprep/web

      - name: 배포 전 점검과 공개 폴더 만들기
        run: python jobprep/tools/predeploy.py --src jobprep/web --out _site

      - name: Pages 설정 읽기
        uses: actions/configure-pages@v6

      - name: 공개 폴더 올리기
        uses: actions/upload-pages-artifact@v5
        with:
          path: _site

runs-on: ubuntu-latest는 GitHub가 빌려주는 리눅스 실행기에서 돈다는 뜻이다. 실행기는 매번 빈 상태에서 시작하므로 첫 단계에서 저장소를 받는다. run: 단계의 두 명령은 학습자가 6-2와 9-3에서 손으로 실행한 것과 같다. 어느 단계든 종료 코드가 0이 아니면 그 자리에서 멈추고 뒤의 단계는 돌지 않는다.

upload-pages-artifact는 공개 폴더를 Pages용 아티팩트(작업 사이에 넘기는 묶음 파일)로 올린다. 이 액션은 기본으로 점으로 시작하는 파일과 폴더를 넣지 않는다 [G9]. predeploy.py가 _site에 남기는 표시 파일(.made-by-predeploy)이 사이트에 올라가지 않는 까닭이다.

[파일: ~/llm-service-lab/.github/workflows/pages.yml] (deploy 작업)

  deploy:
    needs: build
    runs-on: ubuntu-latest
    environment:
      name: github-pages
      url: ${{ steps.deployment.outputs.page_url }}
    steps:
      - name: GitHub Pages 에 배포
        id: deployment
        uses: actions/deploy-pages@v5

needs: build는 build 작업이 성공해야 deploy 작업이 돈다는 뜻이다. environment의 이름 github-pages는 Pages 배포용 환경이며, 없으면 자동으로 만들어진다 [G1][G2]. url에는 배포한 사이트의 주소가 들어가 실행 기록 화면에 표시된다.

@v7, @v6, @v5는 각 액션의 주 버전이며 해마다 오르므로 수업 전에 다시 확인한다. 워크플로를 Claude Code에게 고치게 하더라도 권한(permissions)과 배포 대상이 바뀌지 않았는지는 사람이 읽는다.

[최신 자료 자리: 배포 워크플로 액션의 주 버전] checkout, setup-python, configure-pages, upload-pages-artifact, deploy-pages의 최신 릴리스. 확인할 곳 각 액션 저장소의 Releases 또는 gh api repos/actions/deploy-pages/releases/latest --jq .tag_name. 2026-11-14의 값은 v7, v7, v6, v5, v5이다.

확인 25 워크플로 파일에서 정적 검사 단계와 배포 전 점검 단계를 찾고, 두 단계 가운데 하나가 실패하면 deploy 작업이 돌지 않는 까닭을 needs와 종료 코드로 설명할 수 있다.

배포 전에 로컬의 마지막 확인을 한다. 커밋하지 않은 변경이 있으면 그것은 배포되지 않는다.

서버 터미널 
cd ~/llm-service-lab
git status --short
python3 jobprep/web/check/check_static.py jobprep/web | tail -1
git push origin main
(git status 의 출력은 비어 있다)
정적 검사 결과: 통과 8 / 실패 0
...
To github.com:아이디/llm-service-lab.git
   6993d6a..2bd724e  main -> main

푸시 출력은 예시다. 푸시가 끝나면 저장소의 Actions 탭을 연다. 「Pages 배포」 실행이 노란 점(진행 중)에서 초록 확인 표시(성공)나 빨간 X(실패)로 바뀌고, 실행을 누르면 build와 deploy 두 작업과 단계마다의 출력이 보인다.

[선택] GitHub CLI로도 같은 것을 본다(부록 B).

서버 터미널 
gh run list --workflow pages.yml --limit 3
gh run watch

gh run list는 최근 실행의 상태(성공, 실패, 진행 중), 커밋 메시지, 워크플로 이름, 브랜치를 한 줄씩 보인다. 출력의 모양은 GitHub CLI의 판에 따라 다르다. gh run watch는 진행 중인 실행을 골라 끝날 때까지 단계를 보인다.

실패하면 빨간 X가 붙은 단계를 열어 출력의 마지막 부분을 읽는다. 정적 검사나 배포 전 점검에서 실패했다면, 그 출력은 로컬에서 같은 명령을 실행했을 때와 같다. 로컬에서 고치고 다시 커밋·푸시한다. 로컬에서는 통과했는데 워크플로에서만 실패한다면, 커밋하지 않은 파일이 로컬에만 있는 경우가 가장 흔하다.

[그림 자리: Actions의 실행 화면] 「Pages 배포」 실행에서 build와 deploy 두 작업과 공개 주소가 보이는 모습. 성공한 실행과 build가 실패한 실행을 한 장씩 GitHub 웹에서 찍는다.

막혔을 때는 빨간 X가 붙은 단계의 이름으로 갈래를 고른다. 단계 이름은 워크플로 파일의 name이다.

실패한 단계 뜻 할 일
정적 검사 로컬에서 본 실패와 같다. 커밋하지 않은 파일이 흔한 원인이다 git status --short, 로컬에서 같은 명령
배포 전 점검과 공개 폴더 만들기 공개 폴더에 비밀 정보나 개인 정보 모양이 있다 출력의 x 줄을 고친다(9-3)
Pages 설정 읽기, GitHub Pages 에 배포 Pages가 꺼져 있거나 Source가 GitHub Actions가 아니다 9-5의 설정 뒤 Re-run
deploy 작업이 돌지 않음 build가 실패해 needs: build에 막혔다 build의 실패 단계부터 본다
모두 성공인데 옛 화면 브라우저가 이전 파일을 다시 쓴다 강력 새로고침(10-7)

확인 26 Actions 탭에서 이 커밋의 「Pages 배포」 실행이 성공으로 끝났고, deploy 작업의 화면에 공개 주소가 표시된다.

9-7. 공개 주소의 점검

공개 주소를 PC와 폰에서 각각 연다. 2026년판 3주차의 원칙은 그대로다. 내 브라우저에서 되는 것은 증거가 아니고, 남의 기기에서 열리고 기능이 동작하는 것이 배포의 기준이다 [R1].

점검 PC 브라우저 폰
네 화면이 열린다(메뉴로 이동) 본다 본다
공고 30건, 검색, 분야·지역 고르기 본다 검색 하나만
관심 공고 저장 → 관심 공고 화면 본다 본다
지원 일정 추가 → 새로고침해도 남음 본다 본다
가로 스크롤이 없다 (자동 AC-035-1) 본다(AC-035-2)
개발자 도구 Network에 404가 없다 본다 -
주소창의 자물쇠(https) 본다 본다

로컬에서 저장한 관심 공고는 공개 주소에서 보이지 않는다. 4-1에서 본 출처의 차이이며 오류가 아니다.

공개 주소에서 공고가 없으면 Network 탭에서 404가 난 요청의 주소를 본다. /llm-service-lab/이 빠졌으면 /로 시작하는 경로(3-5)이고, 주소가 맞으면 파일 이름의 대소문자다. Pages는 Index.html과 index.html을 다른 파일로 다룬다.

확인 27 자기 폰에서 공개 주소를 열어 관심 공고 저장과 지원 일정 추가가 되고 가로 스크롤이 없음을 확인하였다. 결과를 인수조건.md의 AC-035-2 행과 손 점검 기록에 적었다.

9-8. 배포 기록

키트의 양식을 cp -n "$KIT/배포기록_양식.md" docs/배포기록.md로 복사하고(jobprep에서), 「배포 설정」과 「배포 이력」의 D-01 행을 채운다. 커밋 칸에는 배포한 커밋의 해시를, 워크플로 칸에는 Actions의 실행 결과를 적는다. 공개 주소에는 GitHub 아이디가 들어간다. 아이디가 실명이나 학번이면 그것도 공개되는 정보라는 점을 알고 적는다.

서버 터미널 
git add docs/배포기록.md docs/인수조건.md
git commit -m "docs: 첫 배포 기록 D-01, AC-035-2 손 점검"
git push origin main

이 커밋은 jobprep/docs/만 바꾸므로 워크플로의 paths에 걸리지 않아 배포가 다시 돌지 않는다. Actions 탭에 새 실행이 생기지 않는 것을 확인한다.

3단계 복기

  1. 공개할 것을 골랐다. 저장소 전체가 아니라 predeploy.py가 고르고 사람이 목록을 읽은 _site만 사이트가 되었다. 명세, 인터뷰 기록, 검사는 저장소에 남았다.
  2. 검사가 배포의 문이 되었다. 로컬에서 손으로 돌린 명령을 워크플로가 다시 돌리고, 종료 코드가 0이 아니면 deploy가 돌지 않는다.
  3. 남의 기기에서 확인했다. 공개 주소가 폰에서 열리고 기능이 동작한 것이 배포의 기준이며, 그 결과가 D-01로 남았다.

10. 중심 실습: 명세 변경과 재배포

10-1. 변경 요청

첫 배포본을 동료 둘에게 써 보게 했더니 같은 의견이 나왔다고 하자. 키트의 변경요청_CR-01.md가 그 의견을 정리한 변경 요청이다. 관련 문제는 P-01(흩어진 공고와 마감 시각)이고, 의견을 낸 사람의 모습은 페르소나 PS-1 서지후와 같다.

[파일: 키트 변경요청_CR-01.md] (요청 내용)

"관심 공고 화면에 공고가 저장한 순서대로 쌓인다. 열 건쯤 저장하고 나면 급한 공고가 아래에 묻혀서,
어느 것부터 서류를 준비해야 할지 날짜를 하나씩 다시 봐야 한다. 상시 채용 공고는 급하지 않으니 뒤에 있으면 좋겠다."

먼저 이 요청이 명세에 이미 있는지 본다. 명세 v3의 REQ-002는 공고 목록(SCR-01)의 정렬이고, REQ-011은 마감된 관심 공고를 「지난 공고」로 묶는 요구다. 관심 공고 목록(SCR-07)의 순서를 정한 요구는 없다(있다면 변경이 아니라 구현 누락이다). 이 문장을 Claude Code에게 그대로 주고 “반영해 줘”라고 하면, “급한 공고”가 무엇인지, 상시 공고와 마감된 공고를 어디에 둘지를 Claude Code가 정하고 그 결정은 코드 안에만 남는다. 다음에 고칠 사람은 코드를 읽어 결정을 거꾸로 알아내야 한다. 6장의 리버스 엔지니어링을 내 프로덕트에 다시 하게 되는 셈이다.

명세 주도 개발에서 변경은 명세에서 시작한다. 순서는 요구 문장(요구사항명세서.md, 추적표.md), 인수 조건(인수조건.md), 검사(web/check/, 구현 전에 실패 확인), 재구현(web/js/, 전체 통과), 변경 이력과 한 커밋, 재배포와 배포 기록이다.

10-2. 요구 문장으로 바꾸기

변경 요청의 말 가운데 판정할 수 없는 것을 찾는다. “급한 공고”, “뒤에 있으면”이다. 요청이 말하지 않은 경우도 함께 찾는다.

요청의 말 정할 것 이 장의 기준 답 정한 근거
급한 공고 순서의 기준 접수 마감일이 가까운 순 공고 목록(REQ-002)과 같은 기준이면 사용자가 두 화면에서 같은 규칙을 쓴다
상시 채용은 뒤에 상시 공고의 자리 맨 뒤 요청 그대로. 공고 목록의 검사용 약속과 같다
(요청에 없음) 마감일이 같은 공고 공고 번호 순 검사용 약속의 「정렬」 줄. 순서가 실행마다 바뀌지 않게 한다
(요청에 없음) 이미 마감된 공고 마감일 순서 그대로(맨 앞에 「마감」 표시와 함께 온다) 마감된 공고를 따로 묶는 것은 REQ-011의 일이다. 이 판에서 구현하지 않으므로 열린 질문으로 남긴다
(요청에 없음) 정렬 기준을 사용자가 바꾸기 두지 않는다 요청하지 않은 기능이다(1-4의 검토와 같은 판단)

넷째 행처럼 요청이 말하지 않은 경우를 정하는 것도 명세의 일이다. 정하지 않으면 Claude Code가 마감된 공고를 숨기는 구현을 만들어도 틀렸다고 할 근거가 없다. 마감된 공고의 불편은 REQ-011을 구현하는 판에서 푼다. 변경 하나에 요구 하나를 대응시켜야 무엇이 왜 바뀌었는지 가릴 수 있다.

10-3. 검사할 수 있게 하는 예

마감일이 이른 공고부터 저장하면, 정렬하지 않고 저장한 순서대로 보이는 구현도 마감일 순으로 보인다. 그런 검사는 구현 전에도 통과하므로 아무것도 확인하지 않는다. 그래서 예를 고를 때 “틀린 구현이 실패하는가”를 먼저 묻는다. 가장 그럴듯한 틀린 구현이 “저장한 순서대로”이므로 검사는 마감일의 역순으로 저장하고, 상시 공고의 자리를 보는 검사는 상시 공고를 맨 먼저 저장한다.

화면 명세는 바꾸지 않는다. 관심 공고의 항목(.saved-item[data-job-id])이 이미 검사용 약속에 있고 순서는 화면에 놓인 순서로 본다. 같은 마감일의 순서와 상시 공고의 자리도 약속의 「정렬」 줄이 정하였다.

10-8. 되돌리기 [선택]

배포한 뒤 문제가 발견되면 어떻게 하는가. 이 장의 배포는 커밋에 묶여 있으므로, 되돌리는 것도 커밋으로 한다. 2장에서 본 git revert가 그 방법이다. git revert는 지정한 커밋의 변경을 거꾸로 적용하는 새 커밋을 만든다. 기록을 지우지 않으므로 푸시한 뒤에도 안전하게 쓸 수 있다.

[서버 터미널] (문제가 생겼을 때만. 이 장에서는 실행하지 않는다)

git revert --no-edit HEAD~1      # 「spec: 관심 공고의 마감순 정렬」 커밋을 되돌리는 새 커밋
git push origin main             # 워크플로가 v3 상태를 다시 배포한다

이때 명세, 추적표, 인수 조건, 검사도 함께 v3로 돌아간다. 한 커밋에 묶어 둔 덕분이다. 되돌린 뒤에는 변경 이력에 “v4 철회, 까닭”을 한 줄 더한다. 되돌리기도 명세의 변경이기 때문이다.

4단계 복기

  1. 변경은 명세에서 시작했다. 사용자의 말을 판정할 수 있는 요구 REQ-040으로 바꾸고, 요청이 말하지 않은 경우(같은 마감일, 이미 마감된 공고)까지 정하였다.
  2. 검사가 먼저 실패했다. 틀린 구현이 실패하도록 저장 순서를 골랐고, 구현 전의 통과 0 / 실패 2가 검사가 무언가를 가른다는 증거다.
  3. 한 커밋이 한 변경이다. 명세, 추적표, 인수 조건, 검사, 구현이 spec-v4 한 커밋에 묶여, 재배포(D-02)와 되돌리기가 모두 그 커밋 하나로 된다.

11. 브라우저 에이전트로 하는 인수 조건 점검

11-1. 브라우저 에이전트와 이 절의 물음

브라우저 에이전트는 자연어로 받은 작업을 브라우저를 직접 조작해 수행하는 AI이다. 이 절은 Aside(2025년 가을 Y Combinator 선정)를 쓴다. Aside는 웹사이트에서 여러 단계의 일을 하되 결제·메시지 같은 민감한 동작 앞에서는 사람의 승인을 기다리는 브라우저로 소개되고 [B1][B2], 개발자 문서는 첫 사용 예로 로컬 웹앱의 스모크 테스트를 든다 [B3].

이 장은 인수 조건을 이미 사람이 코드로 쓴 판정(Playwright 검사, 7-5)과 사람이 화면에서 한 판정(손 점검, 7-6)으로 확인하였다. 브라우저 에이전트는 자연어로 쓴 인수 조건 표를 받아 화면을 누르고 판정을 돌려주는 셋째 방법이다. 이 절의 물음은 에이전트가 「통과」라고 보고한 것을 근거로 삼을 수 있는가이다. 7-1에서 “구현했습니다”라는 말 대신 바뀐 파일을 읽었듯이, 에이전트의 판정도 다른 두 방법의 결과에 대어 본다.

학습자는 실습실 PC에 설치된 Aside를 자기 계정으로 직접 쓴다. 계정은 이 장 전에 각자 마련하고, 설치와 로그인은 부록 A-21(Aside 설치와 로컬 웹 연결)을 따른다. 맡기는 일은 인수 조건 여덟 행 한 번이다. 같은 일을 하는 다른 도구로 Ego Lite가 있다(무료, macOS·Windows) [B4].

[최신 자료 자리: Aside의 요금, 크레딧, 지원 운영체제] 확인할 곳 [B2], https://aside.com/pricing. 2026-11-16에 확인한 값은 무료 요금제 월 500 크레딧(루틴 3개, 자기 구독 연결 가능), Pro 월 20달러, Max 월 200달러, macOS 15 이상과 Windows 10 22H2 이상·Windows 11(리눅스 없음)이다. 수업 전에 다시 확인한다.

11-2. 지켜야 할 세 가지

  1. 로컬 주소로만 한다. 대상은 3-4의 로컬 서버를 포트 전달로 연 http://localhost:8001/(자기 포트)이며, 공개 배포 주소로 하지 않는다. 인수 조건은 배포 전의 판정이고, 로컬은 Playwright가 검사한 것과 같은 커밋을 본다. 에이전트가 갈 수 있는 곳도 이 주소 하나로 좁힌다.
  2. 자격 증명을 주지 않는다. 이 웹은 로그인이 없다. 작업 지시에 GitHub 계정, 실습 서버 비밀번호, API 키를 적지 않고, 에이전트의 브라우저에 다른 사이트의 로그인 탭을 열어 두지 않는다. Aside는 자격 증명을 AI에 드러내지 않고 자동 입력한다고 밝히지만 [B2], 쓸 일이 없는 자격 증명은 처음부터 닿지 않게 한다.
  3. 개인 정보를 입력하게 하지 않는다. 에이전트의 AI 모델은 화면의 내용과 지시를 읽는다. 입력값은 인수 조건 표에 적힌 값만 쓰게 한다(REQ-039의 안내와 같다).

  3. 판정 못함은 그대로 둔다. 그 행은 Playwright나 손 점검의 결과로 판정한다. 에이전트에게 다시 시켜 억지로 판정을 받지 않는다.

  • 명세 주도 개발에서 구현은 명세 → 계획 → 작업 → 구현의 순서로 한다. 계획은 계획 모드로 받아 명세에 대어 검토하고, 작업 목록은 “한 번의 지시, 확인할 수 있음, 커밋 하나”의 크기로 나누어 파일로 남긴다.
  • 구현 지시문은 참조, 범위, 금지 사항, 완료 조건, 모호할 때의 다섯 칸으로 쓴다. 모든 작업에 공통인 규칙은 CLAUDE.md에 두고, 지켰는지는 검사로 확인한다.
  • 정적 웹은 자료(JSON)와 화면을 나누고, file://가 아니라 로컬 서버로 확인한다. 프로젝트 사이트의 하위 경로 때문에 경로는 상대 경로로 쓴다.
  • localStorage는 출처마다 따로 있고, 만료가 없으나 최선 노력 저장이며, 암호화되지 않는다. 사용자 입력은 textContent로 화면에 넣는다.
  • 인수 조건은 요구를 Given-When-Then의 구체적인 예로 바꾼 것이다. 기계가 확인할 수 있는 것은 자동 검사로, 나머지는 손 점검으로 확인하고 기록한다. 검사의 기대값은 구현이 아니라 명세에서 계산한다.
  • GitHub Pages는 브랜치(맨 위 또는 /docs)나 워크플로로 게시한다. 저장소 안의 하위 폴더를 공개할 파일만 골라 검사를 거쳐 내보내려면 워크플로가 맞다. 저장소와 사이트에서 무엇이 공개되는지 먼저 확인한다.
  • 명세 변경은 명세에서 시작해 인수 조건, 검사(먼저 실패), 구현(통과), 변경 이력까지 한 커밋으로 묶고, 다시 배포해 공개 주소에서 확인한다.
  • 브라우저 에이전트의 판정은 또 하나의 보고다. 로컬 주소에서 자격 증명 없이 맡기고, 「판정 못함」을 허용하며, Playwright 검사와 손 점검에 대어 가린다.

개념 점검

  1. fetch("data/jobs.json")과 fetch("/data/jobs.json")은 로컬 서버에서는 둘 다 동작하는데, GitHub Pages의 프로젝트 사이트에서는 하나만 동작한다. 어느 쪽이 왜 깨지는가?
  2. 관심 공고를 sessionStorage에 저장한 구현이 “저장 후 새로고침해도 남는다”는 검사는 통과한다. REQ-009를 충족하지 못한다는 것을 드러내려면 인수 조건의 When을 어떻게 써야 하는가?
  3. “검색이 빠르고 정확하게 동작한다”는 인수 조건의 문제를 Given-When-Then의 관점에서 두 가지 들고, 고쳐 쓰라.
  4. 이 장의 웹을 GitHub Pages의 「브랜치에서 게시」 방식으로 내보내기 어려운 까닭과, 워크플로 방식이 그 문제를 푸는 방법을 설명하라.
  5. REQ-003(마감 임박 표시)의 검사가 실제 오늘 날짜를 쓰면 어떤 문제가 생기는가? 이 장은 그 문제를 명세의 어디에서 어떻게 풀었는가? 같은 관점에서, CR-01(REQ-040)의 검사는 왜 마감일의 역순으로 관심 공고를 저장하는가?

다음 장 안내

이 장의 웹은 공고를 보여 주기만 한다. 공고 원문이 길면 사용자는 여전히 끝까지 읽어야 무엇을 요구하는지 안다. 10장 「LLM 기능의 통합: API 연동과 프롬프트 설계」는 이 웹의 상세 화면에 공고 요약 기능을 붙인다. 요약은 LLM API를 불러야 하고, API 키는 브라우저에 둘 수 없으므로(3-1의 표), 처음으로 서버 프로그램(FastAPI, jobprep/api/)이 생긴다. 이 장에서 세운 것이 그대로 이어진다. 명세의 공고 요약 요구(REQ-013~016, REQ-024, REQ-025)를 구현하고, 인수 조건을 쓰고, .gitignore의 .env로 키를 저장소 밖에 두고, innerHTML 금지 규칙으로 LLM의 출력을 안전하게 화면에 넣는다. 정적 웹은 GitHub Pages에 그대로 두고, 요약 서버는 실습 서버에서 실행한다.
