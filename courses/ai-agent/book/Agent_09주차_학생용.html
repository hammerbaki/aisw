[9장] 에이전트 루프의 구조: API와 도구 호출

AI에이전트 기획 및 개발

9장

에이전트 루프의 구조: API와 도구 호출

2027학년도 「AI에이전트 기획 및 개발」의 준비 중인 교재입니다. 편집 상태를 검토하기 위해 미리 공개한 것으로, 수업 전에 내용과 순서가 바뀔 수 있습니다.

학사 11주차 · 교재 09 · 3부 하네스와 루프

7장에서는 1~6장의 부품(규칙, 설정과 권한, 스킬, MCP, 훅, 서브에이전트)을 하네스로 조립하였고, 8장에서는 그 하네스를 감싼 바깥 루프를 만들었다. 8장의 루프는 파이썬 스크립트 ops/loop/fix_until_green.py가 claude -p를 부르고, pytest로 판정하고, 실패하면 실패 출력을 붙여 다시 부르며, 시도 상한(세 번)이나 비용·시간 상한에 닿으면 멈추고 사람에게 넘기는 구조였다. 그 루프에서 Claude Code 한 번의 실행은 안을 들여다보지 않는 상자였다.

이 장은 그 상자를 연다. Claude Code가 요청 하나를 받아 파일을 읽고, 명령을 실행하고, 결과를 보고 다음 행동을 정하는 반복은 Claude API의 도구 사용(tool use) 위에서 돈다. 모델은 “이 도구를 이 인자로 실행해 달라”는 요청서만 쓰고, 실행은 모델을 감싼 프로그램이 한다. 이 장에서는 그 프로그램을 파이썬으로 직접 만든다. 핵심 실습(7절)의 산출물은 jobprep 저장소의 agent_loop/이다. 도구 두 개(search_jobs, read_doc)를 쓰는 최소 에이전트 루프이며, 최대 반복 상한, 인자 검증, 오류 결과, 사람 승인을 갖추고, 정해진 응답을 차례로 내는 모의 모델로 테스트를 통과한다. 만드는 도중에 문제 하나를 해결한다. 골격의 문서 읽기 도구는 ../../README.md 같은 이름을 받으면 자료 폴더 밖의 파일을 그대로 읽는다. 이 경로 탈출을 모의 모델과 테스트로 재현하고, 처리 함수 안의 두 겹 검사로 막은 뒤 같은 테스트로 막혔음을 확인한다.

직접 만든 루프는 두 가지에 쓰인다. 첫째, 앞 장들에서 만든 훅, 권한 규칙, 서브에이전트가 루프의 어느 자리에 끼어드는지 코드의 줄로 가리킬 수 있게 된다. 둘째, 10장의 역할 에이전트와 프로젝트실습Ⅱ의 졸업 프로젝트에서 LLM 기능이 외부 자료를 찾아야 할 때 이 구조를 그대로 쓴다. 같은 일을 Claude Agent SDK로 하면 무엇이 대신 처리되는지, Claude Code 안에서는 같은 루프가 어떻게 도는지는 9~11절에서 읽는다.

이 장의 실습은 처음부터 끝까지 모의 모델로 돈다. 실제 모델을 부르는 단계는 Console의 API 키를 각자 발급한 학습자만 한 번 하는 선택이다. Claude Code는 계정 로그인으로 쓰지만, 직접 만든 프로그램과 Agent SDK는 API 키로만 인증한다. Anthropic은 제3자 개발자가 자기 제품에서 Claude.ai 로그인이나 구독 자격 증명을 쓰는 것을 허용하지 않기 때문이다[D1][S5].

학습 목표

  • 에이전트 루프의 한 바퀴를 메시지 수준에서 설명할 수 있다.
    • 예시: tool_use 블록의 id와 tool_result 블록의 tool_use_id가 짝을 이루고, 결과가 user 역할의 메시지로 돌아간다는 것을 저장된 JSON에서 가리킨다.
    • 활용: Claude Code나 다른 에이전트가 이상하게 행동할 때 대화 기록(JSON)을 읽고 어느 왕복에서 어긋났는지 찾는다.
  • 도구 정의를 쓰고, 모델이 만든 인자를 검증할 수 있다.
    • 예시: search_jobs의 설명에 “언제 쓰지 않는가”를 넣고, limit: 50이나 ../../README.md 같은 인자를 코드가 거부하게 한다.
    • 활용: 졸업 프로젝트에서 LLM에게 데이터베이스 조회나 파일 읽기를 맡길 때, 모델을 믿지 않고도 안전하게 열어 준다.
  • 종료 조건, 최대 반복 상한, 오류 결과, 사람 승인을 갖춘 최소 루프를 구현하고 모의 모델로 테스트할 수 있다.
    • 예시: 끝없이 도구만 부르는 모의 모델을 넣어 루프가 6회에서 멈추는지 pytest로 확인한다.
    • 활용: 비용과 비결정성 없이 에이전트 코드를 회귀 테스트하는 방법으로 12장(평가)과 13장(CI)에 이어진다.
  • 직접 구현한 루프를 Agent SDK와 Claude Code의 구조에 대응시킬 수 있다.
    • 예시: loop.py의 pre_tool_hooks가 Claude Code의 PreToolUse 훅, approver가 권한 확인, max_turns가 SDK의 max_turns에 해당한다고 표로 정리한다.
    • 활용: 10장에서 역할 에이전트를 설계할 때 어떤 통제를 어느 자리(훅, 권한, 도구 안의 검사)에 둘지 고른다.

0. 시작하기

이 장은 내 PC에서 진행한다. 설치, 로그인, 키트 저장소의 클론(~/kits-repo)은 부록 A로 끝냈다고 전제한다. 확인 터미널([터미널], Windows는 Git Bash)과 Claude Code 터미널을 나란히 두고 둘 다 가상 환경을 켠다(부록 A-4-2, A-9-1). 파이썬의 한글 출력을 파이프(|)로 넘기는 명령이 많으므로 Windows에서는 부록 A-4-4의 PYTHONUTF8=1 등록을 먼저 확인한다.

이 장의 실행 상한. 모의 모델이 기본이며 핵심 실습과 모든 확인은 키 없이 끝난다. 실제 API는 Console의 키를 각자 발급한 학습자만 7-9절의 명령 하나를 1회 실행한다(부록 A-12-3). Agent SDK 판과 그 밖의 실제 API 왕복은 교수 시연이며 시연기록/으로 읽는다. Claude Code는 7-4절에서 맡길 때만 대화형으로 쓴다(선택).

키트의 구성은 README.md에 있다. 시작/은 저장소에 넣을 골격(agent_loop/의 TODO 네 곳)과 루프 테스트 39개이고, 참고/는 견본 기록(3절)과 9~11절에서 읽는 재료이며, 도구/loop_map.py와 기준산출물/.claude/(7장 조립본의 사본)는 11절에서, 루프대조_양식.md는 7절부터 쓴다. 시연기록/에는 교수가 수업 전에 실제 모델의 실행 기록을 올린다.

작업은 1장에서 만든 저장소 ~/agent-lab/jobprep/에서 한다. 앞 장의 작업이 모두 커밋되어 있고 테스트가 통과하는지 먼저 본다.

터미널 
cd ~/agent-lab/jobprep
source .venv/Scripts/activate        # macOS: source .venv/bin/activate
git status --short
grep -E '^(LLM_FAKE|LLM_MODEL)=' .env
python -m pytest -q | tail -1
LLM_FAKE=1
LLM_MODEL=claude-haiku-5-5
(앞 장까지의 테스트 수) passed in 3.12s

git status --short가 빈 출력이어야 한다. 줄이 나오면 앞 장의 작업을 먼저 커밋한다. .env의 LLM_FAKE가 1이 아니면 1로 고친다. 테스트 수는 앞 장을 어디까지 했는가에 따라 다르며, 기준 저장소를 막 받은 상태라면 43 passed이다.

[최신 자료 자리: 기본 모델의 이름과 가격] LLM_MODEL의 기본값과 그 모델의 단가. 확인할 곳: https://platform.claude.com/docs/en/about-claude/models/overview. 2026-11-15에 확인한 값: Claude Haiku 5.5, ID claude-haiku-5-5, 입력 백만 토큰당 0.10달러부터, 출력 0.50달러부터. 은퇴 예정일은 「2027-10-07 이후」(확인할 곳: https://platform.claude.com/docs/en/about-claude/model-deprecations, 2026-11-17)이므로 2027년 2학기 중 바뀔 수 있다. 수업 전에 다시 본다.

이 장의 핵심 실습은 앞 장의 산출물에 기대지 않는다. 앞 장의 결과는 0-2의 동결 기록에만 쓴다. 키트의 기준산출물/.claude/는 11절에서 읽기만 하고 저장소로 복사하지 않는다. 훅 설정만 옮기고 훅 스크립트가 없으면 Claude Code가 편집할 때마다 훅 오류를 내기 때문이다.

1. 에이전트 루프

1-1. 모델 호출 한 번과 에이전트

앞 과목에서 만든 api/llm.py의 complete(system, prompt, task)는 모델에게 한 번 묻고 답을 받는 함수이다. 요약 기능은 공고 본문을 프롬프트에 넣어 한 번 부르고, 질의응답 기능은 코드가 먼저 검색한 근거를 프롬프트에 넣어 한 번 부른다. 무엇을 검색할지, 몇 번 부를지, 언제 끝낼지는 모두 코드가 정한다. Anthropic은 이런 구조를 워크플로(workflow)라 부르고, 모델이 스스로 과정과 도구 사용을 정하는 구조를 에이전트(agent)라 부른다[E1].

1장에서 에이전트를 “모델 + 도구 + 루프”로 정의하였다. 같은 글은 에이전트를 환경의 피드백을 받아 가며 도구를 쓰는 LLM의 루프로 설명한다[E1]. 이 장에서 다루는 것은 그 정의의 세 번째 요소, 루프이다.

1-2. 루프의 다섯 단계

에이전트 루프의 한 바퀴는 다섯 단계이다[A2].

  1. 모델 호출. 프로그램이 질문, 도구 목록, 지금까지의 대화 기록을 Messages API로 보낸다.
  2. 도구 요청. 모델이 답 대신 tool_use 블록(도구 이름과 인자)을 돌려준다. 응답의 stop_reason은 tool_use이다.
  3. 프로그램이 실행. 프로그램이 인자를 검사하고 도구를 실행한다.
  4. 결과 돌려주기. 프로그램이 실행 결과를 tool_result 블록으로 만들어 대화 기록에 붙이고 1로 돌아간다.
  5. 끝. 모델이 도구 없이 답을 쓰면(stop_reason이 end_turn) 루프를 끝낸다. 정해 둔 횟수에 닿아도 끝낸다.
sequenceDiagram
    participant P as 프로그램 (agent_loop/loop.py)
    participant M as 모델 (Messages API)
    participant T as 도구 (tools.py)
    P->>M: ① 질문 + 도구 목록 + 대화 기록
    M-->>P: ② tool_use (search_jobs, {"field": "AI 서비스"})
    P->>T: ③ 인자 검사 후 실행
    T-->>P: 공고 목록(JSON 문자열)
    P->>M: ④ 대화 기록 + tool_result
    M-->>P: ② tool_use (read_doc, {"name": "05_…md"})
    P->>T: ③ 실행
    T-->>P: 문서 본문
    P->>M: ④ 대화 기록 + tool_result
    M-->>P: ⑤ 답 (end_turn)

코드에서의 자리는 이렇다. ①은 model.create(...), ②는 그 반환값의 content, ③은 execute()와 그 안의 run_tool(), ④는 messages.append(...), ⑤는 return AgentResult(...)이다. ①③④는 프로그램이, ②는 모델이 한다. ⑤는 모델이 end_turn으로 정하기도 하고 프로그램이 상한으로 정하기도 한다.

②와 ③은 같은 회차 안에서 여러 번 일어날 수 있다. 모델이 한 응답에 tool_use 블록을 둘 이상 넣을 수 있기 때문이다(3-4절).

1-3. 모델은 도구를 실행하지 않는다

도구 사용은 애플리케이션과 모델 사이의 약속이다. 애플리케이션은 어떤 일을 할 수 있는지와 그 입력의 모양을 알려 주고, 모델은 언제 어떻게 부를지 정한다. 공식 문서는 모델이 스스로는 아무것도 실행하지 않는다고 밝힌다[A2]. 모델은 구조화된 요청을 내고, 실행은 애플리케이션의 코드(또는 Anthropic의 서버에서 도는 서버 도구)가 한다. 모델은 도구의 구현 코드를 받지 않고, 정의(이름, 설명, 스키마)와 돌려받은 결과만 본다[A2].

이 사실에서 세 가지가 따라 나온다.

  • 실행 여부의 최종 결정권은 프로그램에 있다. 모델이 어떤 요청을 쓰든 프로그램이 거부하면 실행되지 않는다. 6장의 훅과 3장의 권한 규칙이 동작하는 근거가 이것이다.
  • 모델이 만든 인자는 사용자 입력과 같은 등급의 믿지 않는 입력이다. 모델은 없는 문서 이름, 범위 밖의 숫자, 폴더 밖의 경로를 만들 수 있다. 검사는 실행하는 코드가 한다(5절).
  • 모델은 도구의 결과만 보고 다음 행동을 정한다. 결과가 길면 대화 기록이 커지고, 결과가 모호하면 다음 판단이 흔들린다. 결과의 모양도 설계 대상이다(5-5절).

2026년 2학기판 LLM 7주차의 계산 도구 실습에서, 모델이 음수 금액을 이상하다고 보고 되물은 일이 있었다. 그것은 모델의 판단이었지 코드의 방어가 아니었다. 같은 질문을 다시 하면 모델이 도구를 불러 음수 합계가 그대로 나올 수 있었다. 방어는 매번 같은 결과를 내는 코드에 두어야 한다.

2. Messages API와 도구 정의

2-1. 요청의 구성

Messages API는 POST /v1/messages 하나로 모델을 부른다[A1]. 이 장의 루프가 매 회차 보내는 요청은 다섯 항목으로 이루어진다.

  • model: 모델 이름. loop.py는 LLM_MODEL 환경 변수에서 읽고 코드에 적지 않는다.
  • max_tokens: 이 응답에서 생성할 최대 토큰 수. api/llm.py의 MAX_TOKENS(2048)를 쓴다.
  • system: 시스템 프롬프트. loop.py의 SYSTEM이다.
  • messages: 지금까지의 대화 기록 전체. 회차마다 두 칸씩 늘어난다.
  • tools: 도구 정의의 목록. definitions(tools)가 만든다.

tool_choice(도구 선택 방식, 2-4절), thinking(생각 설정), stop_sequences 같은 항목도 있지만 이 장의 루프는 기본값을 쓴다.

Messages API는 상태를 기억하지 않는다(stateless). 문서는 이전 대화의 차례를 messages 매개변수로 넘기면 모델이 그 다음 차례를 만든다고 설명한다[A1]. 서버는 앞선 호출을 기억하지 않으므로, 프로그램이 대화 기록 전체를 매번 다시 보낸다. 8절에서 이것이 토큰 비용에 어떤 영향을 주는지 잰다.

기준 저장소의 api/llm.py는 temperature를 보내지 않는다. 파이썬 SDK anthropic은 2.0.0부터 API 버전 2026-10-21을 쓰는데[A18], 이 버전에서는 temperature, top_p, top_k를 보내면 기본값이어도 400 오류가 난다[A19]. 기준 저장소가 고정한 anthropic==2.8.0이 실제로 어느 API 버전을 보내는지 교수 화면에서 확인한다(읽기. 가상 환경을 켠 저장소에서 같은 명령을 쳐도 된다).

교수 화면

        "name에는 문서의 파일 이름만 쓴다. 폴더 경로, 절대 경로, '..'가 들어간 이름은 거부된다. "
        f"본문이 {MAX_DOC_CHARS}자를 넘으면 앞부분만 돌려주고 잘렸다고 표시한다. "
        "현장실습, 취업지원센터, 이력서와 자기소개서, ... 에 관한 질문에 쓴다. "
        "읽을 수 있는 문서: " + ", ".join(doc_names())
    ),
    "input_schema": {
        "type": "object",
        "properties": {
            "name": {"type": "string", "minLength": 1, "maxLength": 60,
                     "description": "문서 파일 이름. 예: 01_현장실습_안내.md"},
        },
        "required": ["name"],
        "additionalProperties": False,
    },
}

input_schema의 각 줄은 다음 뜻이다.

  • type: "object": 인자 전체는 JSON 객체이다. 도구의 입력은 언제나 객체이다.
  • properties: 인자의 이름과 각 인자의 규칙. 이 도구에는 name 하나가 있다.
  • required: 빠지면 안 되는 인자. 여기서는 name이다.
  • additionalProperties: false: properties에 없는 인자를 받지 않는다. 모델이 path 같은 인자를 지어내면 거부한다.
  • minLength, maxLength: 문자열 길이의 범위(1~60자).
  • 인자 안의 description: 인자 하나의 뜻. 모델이 값을 만들 때 읽는다.

설명 끝에 읽을 수 있는 문서 목록을 넣었다. 모델이 문서 이름을 지어내지 않고 목록에서 고르게 하기 위해서이다. 목록은 doc_names()가 폴더를 읽어 만들므로 문서가 늘면 설명도 따라 바뀐다.

2-3. 설명은 곧 프롬프트이다

모델은 도구의 코드를 읽지 않고 정의만 보고 부를지 정한다. API는 tools를 받으면 도구 정의, 도구 설정, 사용자의 시스템 프롬프트로 특별한 시스템 프롬프트를 만들어 모델에게 준다[A12]. 문서에 실린 그 틀의 첫머리는 “In this environment you have access to a set of tools you can use to answer the user’s question.”이고, 그 아래에 JSON Schema 형식의 도구 정의가 들어간다. 도구 정의는 프롬프트의 일부이다.

공식 문서는 도구 성능에 가장 큰 영향을 주는 요인으로 매우 자세한 설명을 꼽고, 설명에 담을 것을 다음과 같이 든다[A12].

  1. 도구가 무엇을 하는가
  2. 언제 써야 하는가(그리고 언제 쓰지 말아야 하는가)
  3. 각 인자가 무엇을 뜻하고 도구의 동작에 어떻게 영향을 주는가
  4. 도구가 돌려주지 않는 정보 같은 주의 사항과 한계

도구마다 적어도 3~4문장을 쓰고, 복잡한 도구는 더 길게 쓰라고 권한다[A12]. Anthropic의 「Writing tools for agents」는 도구 설명을 새로 온 동료에게 설명하듯 쓰라고 하고, 설명을 조금 고치는 것만으로도 결과가 크게 좋아질 수 있다고 보고한다[E6].

도구 정의는 토큰 비용이기도 하다. 요청의 입력 토큰에는 tools 매개변수(이름, 설명, 스키마)가 들어가고, 그와 별도로 도구 사용을 위한 시스템 프롬프트가 붙는다[A10]. 그 크기는 모델과 tool_choice에 따라 다르며, 2026-11-14 기준 문서의 표에서 Claude Haiku 5.5는 auto·none일 때 286토큰, any·tool일 때 406토큰이다[A10]. 도구 정의가 회차마다 다시 실리므로 쓰지 않는 도구를 등록해 두는 것도 비용이다.

2-4. 도구 선택 방식: tool_choice

tool_choice는 모델이 도구를 쓸지 정하는 방식을 바꾼다[A12].

  • {"type": "auto"}: 도구를 부를지 모델이 정한다. 도구 없이 답할 수도 있다. tools가 있을 때의 기본값이다.
  • {"type": "any"}: 도구 가운데 하나를 반드시 부른다.
  • {"type": "tool", "name": "..."}: 이름을 댄 도구를 반드시 부른다.
  • {"type": "none"}: 도구를 부르지 않는다. tools가 없을 때의 기본값이다.

any와 tool은 강제 호출이다. API가 assistant 메시지 앞부분을 미리 채워 도구 호출을 강제하므로, 모델은 도구 호출 앞에 설명 문장을 쓰지 않는다[A12]. 강제 호출이 되지 않는 경우도 있다. 2026-11-14 기준 문서에 따르면 수동 확장 사고(thinking: {type: "enabled"})에서는 any와 tool이 오류이고, Claude Opus 5.5와 Claude Sonnet 5.5 등은 생각 설정과 관계없이 any와 tool에 400을 돌려준다[A12]. 이 과목의 기본 모델인 Claude Haiku 5.5는 강제 호출을 받지만, 강제하면 생각 블록 없이 도구 호출부터 시작한다[A12][A20].

tool_choice 안에 "disable_parallel_tool_use": true를 넣으면 한 응답에 도구 호출이 하나 이하로 제한된다(auto일 때). 최상위 매개변수가 아니라 tool_choice 안에 넣는 값이다[A14].

이 장의 루프는 tool_choice를 보내지 않는다(기본값 auto). 에이전트는 도구가 필요 없을 때 바로 답할 수 있어야 하기 때문이다. 문서는 모델이 도구를 너무 적게 쓰면 시스템 프롬프트에 “Use the tools to investigate before responding.” 같은 지시를 넣어 조절하라고 한다[A10]. loop.py의 SYSTEM에 “공고와 자료의 내용은 반드시 도구로 확인하고”를 넣은 까닭이 이것이다.

3-2. tool_use 블록

모델이 도구를 부를 때 응답의 stop_reason은 tool_use이고, content에 tool_use 블록이 하나 이상 들어 있다. 블록의 필드는 셋이다[A13].

  • id: 이 도구 요청의 고유 식별자. 결과를 돌려줄 때 짝을 맞추는 데 쓴다.
  • name: 부르려는 도구의 이름.
  • input: 도구에 넘길 인자. 도구의 input_schema에 맞춘 JSON 객체이다.

견본 기록의 1번 메시지는 다음과 같다.

3-3. tool_result 블록

프로그램은 도구를 실행한 뒤 role이 user인 새 메시지에 tool_result 블록을 넣어 보낸다[A13].

  • type(필수): "tool_result".
  • tool_use_id(필수): 이 결과가 답하는 tool_use 블록의 id.
  • content(선택): 결과. 문자열이거나 text·image·document·search_result 블록의 목록이다.
  • is_error(선택): 도구 실행이 실패했으면 true.

견본 기록의 2번 메시지이다(결과 문자열은 줄였다).

{
  "role": "user",
  "content": [
    {
      "type": "tool_result",
      "tool_use_id": "toolu_fake_01",
      "content": "{\"total\": 4, \"returned\": 3, \"jobs\": [{\"id\": 12, \"title\": \"LLM 응용 개발 인턴\", ...}]}"
    }
  ]
}

content는 문자열이다. search_jobs가 돌려준 JSON을 문자열로 그대로 넣었으므로 따옴표 앞에 역슬래시가 붙어 보인다. 모델은 이 문자열을 읽고 다음 행동을 정한다.

tool_result에는 형식 규칙이 있다[A13].

  1. 결과는 요청 바로 뒤에 온다. 도구 요청이 든 assistant 메시지와 결과가 든 user 메시지 사이에 다른 메시지를 끼울 수 없다.
  2. 결과 블록이 먼저, 글은 뒤에. 결과를 담은 user 메시지에서 tool_result 블록이 content 배열의 앞에 와야 한다. 글(text)을 넣으려면 모든 결과 뒤에 넣는다. 글이 결과 앞에 오면 400 오류이다.
  3. 요청마다 결과 하나. tool_use 블록마다 짝이 되는 tool_result가 있어야 한다. 짝이 빠지면 “tool_use ids were found without tool_result blocks immediately after” 같은 오류가 난다.

규칙 2에서 글을 결과 뒤에 넣는 것은 허용되지만, 이 장의 루프는 글을 아예 넣지 않는다. 공식 문서는 도구 결과 바로 뒤에 글 블록을 붙이면 모델이 내용 없이 end_turn으로 끝나는 빈 응답이 생길 수 있다고 하고, 결과만 보내라고 권한다[A15].

3-4. 병렬 도구 호출

모델은 한 응답에 tool_use 블록을 여러 개 넣을 수 있다. 기본으로 켜져 있다[A14]. 공고 검색과 문서 읽기처럼 서로 기대지 않는 일은 한 번에 요청하는 편이 빠르다. 이때의 규칙은 다음과 같다[A14].

  • 실행 순서는 프로그램이 정한다. 동시에 돌려도 되고, 나온 순서대로 돌려도 된다. 읽기 전용 작업은 병렬로 돌리기에 안전하고, 부작용이나 순서 의존이 있는 도구는 차례로 돌리는 편이 낫다.
  • 모든 결과를 user 메시지 하나에 담는다. 결과마다 user 메시지를 따로 만드는 것이 가장 흔한 실수이며, 그렇게 하면 모델이 병렬 호출을 피하도록 “학습”된다고 문서는 경고한다.
[

    {"type": "tool_use", "id": "toolu_fake_01", "name": "search_jobs", "input": {"field": "AI 서비스", "limit": 3}},
    {"type": "tool_use", "id": "toolu_fake_02", "name": "read_doc", "input": {"name": "05_자격증_응시료_지원.md"}}
  ]},
  {"role": "user", "content": [
    {"type": "tool_result", "tool_use_id": "toolu_fake_01", "content": "{\"total\": 4, ...}"},

이 장의 루프는 결과를 나온 순서대로 차례로 실행하고, 결과를 하나의 목록에 모아 한 번에 붙인다. 두 도구 모두 읽기 전용이지만 동시 실행까지는 하지 않는다. 테스트 test_parallel_results_in_one_user_message가 이 규칙을 지키는지 본다.

3-5. 생각 블록과 응답 그대로 붙이기

Claude Haiku 5.5를 비롯한 최신 모델은 생각(thinking)이 기본으로 켜져 있다[A20]. 이때 응답의 content에는 text, tool_use 외에 thinking 블록이 섞여 온다. 도구 결과를 돌려줄 때는 그 생각 블록을 고치지 않고 완전한 상태로 assistant 메시지에 넣어 보내야 한다[A20]. 모델은 도구를 부르면서 응답 만들기를 잠시 멈추고, 결과를 받으면 같은 응답을 이어 쓰기 때문에 앞의 생각이 남아 있어야 한다.

그래서 loop.py는 응답의 블록을 고르거나 고치지 않고 response["content"]를 통째로 assistant 메시지에 넣는다.

[파일: agent_loop/loop.py] run_agent()에서 응답을 기록에 넣는 줄

        # 응답은 받은 그대로(생각 블록 포함) assistant 칸에 넣는다
        messages.append({"role": "assistant", "content": response["content"]})

text 블록만 남기고 나머지를 버리는 식으로 “정리”하면, 생각이 켜진 모델에서 다음 요청이 실패하거나 모델이 앞선 판단을 잃는다.

4. 종료 조건과 최대 반복 상한

4-1. stop_reason의 값

모든 성공 응답에는 모델이 왜 생성을 멈췄는지를 알리는 stop_reason이 있다. 2026-11-14 기준 문서는 일곱 값을 든다[A15]. 파이썬 SDK 2.8.0의 타입 정의도 같은 일곱 값이다(anthropic.types.StopReason).

값 뜻 권장 처리[A15] 이 장의 루프
end_turn 모델이 응답을 자연스럽게 마쳤다 응답을 쓴다. 빈 응답에 주의 답으로 끝낸다
tool_use 모델이 도구를 부른다 클라이언트 도구를 실행하고 결과를 돌려준다 실행하고 다음 회차
max_tokens max_tokens 한도에 닿았다 한도를 올리거나 이어 쓴다. 마지막 블록이 잘린 tool_use이면 한도를 올려 다시 요청 답으로 쓰지 않고 멈춘다
stop_sequence 지정한 멈춤 문자열이 나왔다 어느 것이 나왔는지 stop_sequence로 확인 쓰지 않음. 멈춘다
pause_turn 서버 도구의 내부 반복이 상한(요청당 기본 10회)에 닿았다 응답을 그대로 붙여 다시 보낸다 서버 도구를 쓰지 않으므로 생기지 않음
refusal 모델이 응답을 거절하였다 stop_details를 읽고 대체 모델로 다시 시도 멈춘다
model_context_window_exceeded 응답이 모델의 컨텍스트 창을 채웠다 잘린 응답으로 다룬다 멈춘다

이 가운데 루프를 이어 가는 값은 tool_use 하나이다. 공식 문서도 루프의 기본 모양을 “stop_reason이 tool_use인 동안 도구를 실행하고 대화를 이어 간다”로 설명한다[A2]. 나머지 값에서 루프를 빠져나오되, 정상 종료는 end_turn뿐이다. max_tokens에서 나온 글은 문장 중간에서 끊긴 것이므로 답으로 확정하지 않는다. 기준 저장소의 api/llm.py가 stop_reason이 refusal이나 max_tokens이면 LLMError를 내는 것과 같은 판단이다.

refusal은 오류 상태 코드가 아니라 정상 응답(HTTP 200)으로 온다[A15]. 예외 처리만으로는 거절을 잡을 수 없고, stop_reason을 반드시 읽어야 한다.

4-2. 루프의 종료 조건

루프가 끝나는 경우를 모두 적으면 다음과 같다. 이것이 AgentResult.stop에 들어가는 값이다.

종료 조건 답(answer) 프로그램의 종료 코드
end_turn 모델이 도구 없이 답했다 마지막 응답의 글 0
max_turns 회차가 상한에 닿았다 없음(None) 1
max_tokens 응답이 출력 한도에서 잘렸다 잘린 글(참고용) 1
refusal 등 그 밖의 stop_reason 있으면 글 1
tool_use_without_block stop_reason은 tool_use인데 블록이 없다 없음 1

마지막 줄은 실제 API에서 생기지 않아야 하는 경우이다. 그래도 루프가 빈 결과 목록을 보내 400 오류를 내게 두지 않고, 이상한 응답으로 기록하고 멈춘다. 끝나는 길을 모두 이름 붙여 두면 8장의 바깥 루프나 12장의 평가가 종료 사유별로 결과를 셀 수 있다.

명령행에서 실행하면 end_turn일 때만 종료 코드가 0이다. 8장의 루프 스크립트가 pytest의 종료 코드로 판정했듯이, 다른 스크립트가 이 루프를 부를 때 종료 코드로 성공을 가를 수 있다.

4-3. 최대 반복 상한

stop_reason만으로 끝을 정하면, 모델이 계속 도구를 부르는 경우 루프가 끝나지 않는다. 같은 검색을 되풀이하거나, 오류를 고치지 못하고 같은 인자로 다시 부르거나, 끝없이 더 많은 자료를 찾는 경우이다. 그래서 회차에 상한을 둔다. 「Building effective agents」는 통제를 유지하는 장치로 최대 반복 횟수 같은 멈춤 조건을 두라고 한다[E1].

loop.py는 회차를 for turn in range(1, max_turns + 1)로 세고, 상한을 넘으면 max_turns로 끝낸다. 상한의 기본값은 6이다.

[파일: agent_loop/loop.py] 상한과 루프의 뼈대

MAX_TURNS = 6  # 모델 호출의 최대 횟수. 이 횟수 안에 끝나지 않으면 멈추고 알린다

def run_agent(question, model, tools=None, max_turns=MAX_TURNS, approver=None,
              pre_tool_hooks=(), system=SYSTEM, verbose=False):
    ...

        ...
    say(f"[중단] 최대 반복 {max_turns}회에 닿았다")
    return AgentResult(None, "max_turns", max_turns, messages, log)

상한을 몇으로 정하는가는 정상적인 작업에 필요한 회차에서 출발한다. 이 장의 질문은 공고 검색 1회, 문서 읽기 1회, 답 1회로 3회차면 끝난다. 도구가 오류를 내 한 번 고쳐 부르면 4회차, 두 도구를 따로 한 번씩 더 부르면 5회차가 된다. 그 위에 한 번의 여유를 두어 6으로 정했다.

상한이 너무 낮으면 정상 작업이 중간에 끊기고(답 없이 max_turns), 오류에서 회복할 기회가 없다. 너무 높으면 폭주한 루프가 오래 돌며 비용과 시간을 쓰고, 대화 기록이 커져 회차마다 입력 토큰이 는다(8절).

Agent SDK는 같은 장치를 max_turns 옵션으로 제공하고, 이와 별도로 비용 추정치로 멈추는 max_budget_usd를 둔다[S1]. 상한에 닿으면 결과 메시지의 subtype이 error_max_turns나 error_max_budget_usd가 된다[S1]. 이 장의 루프에는 비용 상한이 없다. 모의 모델은 비용이 0이기 때문이다. 실제 모델로 운영할 때 더할 항목이며 12장에서 다룬다.

4-4. 상한에 닿았을 때 할 일

상한에 닿은 루프는 답을 지어내지 않는다. answer를 None으로 두고 stop을 max_turns로 남긴다. 상한에 닿았다는 사실 자체가 정보이기 때문이다. 원인은 셋 가운데 하나인 경우가 많다.

  1. 도구 설명이 모호해 모델이 같은 도구를 잘못된 인자로 되풀이해 부른다 → 설명과 오류 문장을 고친다.
  2. 질문이 도구로 답할 수 없는 것이다 → 시스템 프롬프트에 “답할 수 없으면 그렇게 말한다”를 둔다.
  3. 작업이 정말로 길다 → 상한을 올리거나 작업을 나눈다(10장의 역할 분담).

어느 경우인지는 회차 기록(AgentResult.log)을 읽어야 안다. 그래서 루프는 회차마다 stop_reason, 부른 도구와 인자, 오류 여부, 보낸 기록의 크기를 남긴다. 8장의 루프가 실패 보고서를 남기고 사람에게 넘긴 것과 같은 원칙이다.

생각해 볼 것. 4-2절의 표를 보고, 모의 시나리오 runaway(끝없이 도구만 부른다)와 truncated(출력 한도에서 잘린다)를 실행하면 각각 어떤 stop 값과 종료 코드가 나올지 루프대조.md의 여백이나 공책에 적어 둔다. 7-2절과 7-3절에서 실제로 실행해 맞춰 본다.

5. 도구 인자의 검증과 오류 결과

5-1. 모델이 만든 인자

모델이 만든 인자는 틀릴 수 있다. 공식 문서는 필수 인자를 채울 정보가 사용자 질문에 없을 때 모델이 되묻기도 하지만 그럴듯한 값을 추측해 넣기도 한다고 하고, 날씨 도구에 위치를 주지 않았는데 모델이 "New York, NY"를 넣은 예를 보인다[A10]. 형식이 틀리는 경우도 있다. 정수 인자에 "2"(문자열)나 "two"를 넣는 식이다[A16].

인자가 틀리는 길을 정리하면 다음과 같다. 각 줄의 오른쪽 열이 agent_loop/tools.py의 방어이다.

위 다섯 줄은 스키마로 표현할 수 있는 검사이고, 아래 세 줄은 스키마로 표현할 수 없는 검사이다. 「문서 이름이 자료 폴더 안의 파일이어야 한다」는 JSON Schema의 어휘로 적을 수 없다. 도메인의 규칙은 처리 함수 안에서 검사한다.

5-2. 스키마 검사와 strict 모드

tools.py의 validate(schema, args)는 JSON Schema의 일부 어휘만 다루는 작은 검사기이다. 어긋난 점을 문장의 목록으로 돌려주고, 맞으면 빈 목록을 돌려준다. 파이썬에서 True가 int이기도 하다는 점(isinstance(True, int)가 참)을 따로 막는다. 다루는 어휘와 각 어휘에서 내는 문장의 예는 다음과 같다.

  • type(형): 'limit'는 integer 형식이어야 한다. 받은 값: '3'.
  • required(빠진 인자): 필수 인자 'name'가 없다.
  • additionalProperties: false(모르는 인자): 알 수 없는 인자 'city'이다. 쓸 수 있는 인자: field, keyword, limit.
  • enum(허용값): 'field'는 다음 중 하나여야 한다: 웹 개발, ... 받은 값: 'AI'.
  • minLength, maxLength(문자열 길이): 'keyword'는 30자 이하여야 한다.
  • minimum, maximum(수의 범위): 'limit'는 10 이하여야 한다. 받은 값: 50.

이 검사기는 골격에서 이미 동작한다. 교수 화면에서 run_tool()을 모델 없이 직접 불러 확인한다(읽기).

API에는 스키마 준수를 보장하는 방법이 따로 있다. 도구 정의에 "strict": true를 두면, 모델의 토큰 생성을 스키마에 맞는 출력으로만 제한한다(문법 제약 생성, grammar-constrained sampling)[A16]. 이때 도구의 input은 input_schema를 엄격히 따르고 도구 이름도 언제나 유효하다고 문서는 보장한다[A16]. 이 기능은 additionalProperties: false를 요구하며, 지원하는 JSON Schema의 범위가 정해져 있다(구조화 출력 문서의 「JSON Schema limitations」)[A16].

strict 모드를 쓰더라도 코드의 검사는 남긴다. 까닭은 셋이다.

  1. strict가 보장하는 것은 스키마이다. 「자료 폴더 안의 파일」 같은 도메인 규칙은 스키마로 적을 수 없다.
  2. 같은 도구를 strict가 없는 경로(모의 모델, 다른 제공자의 모델, MCP 클라이언트)에서도 부른다. 처리 함수가 스스로를 지켜야 어느 경로로 불려도 안전하다.
  3. 스키마 어휘 가운데 strict 모드가 지원하지 않는 것이 있을 수 있다. 지원 범위는 수업 직전에 문서에서 다시 확인한다.

Agent SDK도 같은 판단을 한다. claude-agent-sdk 0.2.182의 소스를 보면, create_sdk_mcp_server()가 만든 서버는 처리 함수를 부르기 전에 jsonschema로 입력을 검사하고, 어긋나면 Input validation error: ...를 오류 결과로 돌려준다(2026-11-14, 설치한 패키지의 소스에서 확인).

5-3. 경로 제한

read_doc은 파일을 읽는 도구이다. 파일을 읽는 도구가 받는 경로를 그대로 쓰면 경로 탈출(path traversal)이 생긴다. ../../.env처럼 상위 폴더로 올라가는 이름으로 허용된 폴더 밖의 파일을 읽는 공격이다. 11장에서 다룰 간접 프롬프트 주입과 합쳐지면, 자료 문서 안에 숨긴 지시 한 줄이 모델에게 .env를 읽게 만들 수 있다.

골격의 read_doc()에는 경로 검사가 없다. 확장자가 .md이고 파일이 있으면 읽는다. 그래서 ../../README.md라는 이름을 받으면 data/자료/에서 두 단계 위로 올라가 저장소의 README.md를 읽고, 오류가 아닌 정상 결과(is_error가 False)로 돌려준다. ../../.env는 확장자가 .md가 아니어서 「문서가 없다」는 오류가 나지만, 그것은 방어가 아니라 우연이다. 이 구멍은 7-5절에서 직접 재현하고 7-6절(TODO 4)에서 검사를 두 겹으로 넣어 막는다.

resolve()는 ..와 심볼릭 링크를 풀어 실제 절대 경로를 만든다. 1차 검사만으로 충분해 보여도 2차 검사를 두는 까닭은, 누군가 자료 폴더 안에 link.md -> ../../.env.md 같은 링크를 만들어 두면 이름은 깨끗한데 실제 위치는 밖이기 때문이다. 테스트 test_read_doc_rejects_symlink_escape가 이 경우를 만든다. 심볼릭 링크를 만들 권한이 없는 Windows 계정에서는 이 테스트가 건너뛰어진다(0-2절의 1 skipped).

5-4. 오류를 is_error로 돌려주기

도구가 실패했을 때 프로그램이 할 수 있는 일은 둘이다. 예외를 올려 루프를 멈추거나, 오류를 결과로 돌려주어 모델이 대처하게 하는 것이다. 공식 문서는 후자를 권한다. 도구 실행이 실패하면 content에 오류 내용을 넣고 "is_error": true를 붙여 돌려준다[A13].

{
  "type": "tool_result",
  "tool_use_id": "toolu_fake_01",
  "content": "'자격증.md' 문서가 없다. 읽을 수 있는 문서: 01_현장실습_안내.md, 02_취업지원센터_이용안내.md, ...",
  "is_error": true
}

문서는 필수 인자가 빠진 것 같은 잘못된 호출에 오류 결과를 돌려주면 모델이 빠진 정보를 채워 2~3번 다시 시도한 뒤 사용자에게 사과한다고 설명한다[A13]. 오류 문장은 “failed” 같은 막연한 말 대신 무엇이 잘못되었고 다음에 무엇을 하면 되는지 적으라고 한다. 예로 든 문장은 “Rate limit exceeded. Retry after 60 seconds.”이다[A13]. read_doc이 없는 문서 이름에 문서 목록을 함께 돌려주는 것이 이 원칙의 적용이다.

run_tool()은 어떤 경우에도 예외를 밖으로 내지 않는다.

[파일: agent_loop/tools.py] run_tool()

def run_tool(name, args, tools):
    """도구 하나를 실행하고 ToolOutcome을 돌려준다. 어떤 경우에도 예외를 밖으로 내지 않는다."""
    tool = tools.get(name)
    if tool is None:
        return ToolOutcome(f"알 수 없는 도구 '{name}'이다. 쓸 수 있는 도구: {', '.join(tools)}", True)
    errors = validate(tool.definition["input_schema"], args)
    if errors:
        return ToolOutcome("입력 오류: " + " ".join(errors), True)
    try:
        return ToolOutcome(tool.handler(args))
    except ToolError as error:
        return ToolOutcome(str(error), True)
    except Exception as error:  # 예상하지 못한 오류도 루프를 멈추지 않는다. 내부 내용은 모델에게 보내지 않는다
        return ToolOutcome(f"도구 실행 중 오류가 났다({type(error).__name__}). 다른 방법을 쓰거나 사용자에게 알린다.", True)

오류를 네 갈래로 나누었다.

갈래 원인 모델에게 가는 문장 모델이 할 수 있는 일
없는 도구 모델이 도구 이름을 지어냈다 쓸 수 있는 도구 목록 맞는 도구로 다시
입력 오류 스키마에 어긋난 인자 어긋난 점 모두 인자를 고쳐 다시
ToolError 처리 함수가 판단한 실패(없는 문서, 거부된 경로) 처리 함수가 쓴 문장 다른 이름으로 다시, 또는 포기
그 밖의 예외 코드의 결함, 외부 장애 예외의 종류 이름만 다른 방법, 또는 사용자에게 알림

마지막 갈래에서 예외 메시지 원문을 보내지 않는 데 주의한다. 예외 메시지에는 내부 경로, 쿼리, 때로는 비밀 정보가 들어간다. 모델에게 보낸 글은 대화 기록에 남고, 그 기록은 로그나 사용자 화면으로 나갈 수 있다. 테스트 test_unexpected_exception_does_not_leak가 예외 메시지의 내부 경로가 결과에 들어가지 않는지 본다. Agent SDK의 사용자 정의 도구는 처리 함수가 잡지 않은 예외를 그 메시지 원문으로 모델에게 보낸다고 문서는 설명한다[S3]. 원문 그대로 보내지 않으려면 처리 함수 안에서 잡아 is_error로 문장을 직접 써야 한다.

5-5. 결과의 크기

도구 결과는 대화 기록에 남아 다음 회차부터 매번 다시 전송된다. 그래서 결과의 크기도 설계한다. 「Writing tools for agents」는 큰 출력을 쪽 나누기, 거르기, 자르기로 제한하라고 하고, Claude Code가 도구 응답을 기본 25,000토큰으로 제한한다고 밝힌다[E6]. 자를 때는 자른 사실과 범위를 좁히는 방법을 함께 알리라고 한다[E6].

  • search_jobs: 공고 본문(description)을 빼고 여섯 필드만 돌려준다. limit는 기본 5, 최대 10이다. 전체 건수(total)를 함께 돌려주어 더 있다는 것을 알린다.
  • read_doc: MAX_DOC_CHARS(2,000자)를 넘으면 앞부분만 돌려주고 …(잘림: 전체 N자 가운데 앞 2000자)를 붙인다.

data/자료/의 문서는 모두 2,000자보다 짧아 실제로는 잘리지 않는다. 테스트는 한도를 100자로 낮추어 자르는 동작을 확인한다(test_read_doc_truncates_long_text).

6. 모의 모델로 루프 테스트하기

6-1. 모의 모델을 먼저 쓰는 까닭

에이전트 루프의 코드는 두 가지가 섞이면 시험하기 어렵다. 하나는 루프 자체의 정확성(결과의 짝, 종료 조건, 상한, 오류 처리)이고, 다른 하나는 모델의 판단(어느 도구를 어떤 인자로 부르는가)이다. 실제 모델을 넣으면 같은 질문에도 경로가 달라지고, 호출마다 비용이 들고, 키가 없거나 한도에 닿으면 시험 자체가 멈춘다.

모의 모델은 정해진 응답을 정해진 순서로 돌려준다. 모델의 판단을 고정해 두면 루프의 정확성만 따로 시험할 수 있다. 2장에서 다룬 테스트 더블(test double)의 한 종류이며, 2026년 2학기판 LLM 8주차의 MockLLMAdapter(각본을 차례로 돌려주는 가짜)와 같은 생각이다. 기준 저장소가 LLM_FAKE=1로 모의 응답을 내는 것도 같은 까닭이다(집필 기준 7절).

비교 실제 모델 모의 모델(FakeModel)
같은 입력의 결과 달라질 수 있다 언제나 같다
비용과 키 호출마다 비용, 키 필요 없음
속도 회차마다 수 초 테스트 39개가 1초 안팎

만들 수 있는 상황 드물게 일어나는 상황은 재현이 어렵다 폭주, 잘림, 경로 탈출 시도를 마음대로 만든다

마지막 줄이 특히 중요하다. 실제 모델이 ../../.env를 읽으려 하거나 같은 도구를 끝없이 부르는 상황은 드물게 일어나고 재현하기 어렵다. 그러나 그런 상황에서의 동작이 바로 운영 요건(1장의 보안, 신뢰성)이 묻는 것이다. 모의 모델로는 그 상황을 매번 같은 모양으로 만들어 회귀 테스트로 지킬 수 있다.

6-2. FakeModel의 구조

agent_loop/fake_model.py는 골격에서 완성되어 있다. 핵심은 create() 메서드 하나이다. 실제 모델 어댑터(ClaudeModel)와 같은 이름, 같은 인자, 같은 모양의 반환값을 가지므로 루프는 둘을 구별하지 않는다.

[파일: agent_loop/fake_model.py] FakeModel.create()

    def create(self, system, messages, tools):
        self.requests.append({"system": system, "messages": copy.deepcopy(messages),
                              "tools": copy.deepcopy(tools)})
        if not self.script:
            raise FakeModelExhausted(f"모의 응답 {len(self.requests) - 1}개를 다 썼는데 또 불렸다.")
        item = self.script[0] if (self.repeat_last and len(self.script) == 1) else self.script.pop(0)
        response = item(messages) if callable(item) else copy.deepcopy(item)
        for block in response["content"]:
            if block["type"] == "tool_use" and not block.get("id"):
                block["id"] = f"toolu_fake_{self._next_id:02d}"
                self._next_id += 1
        return response
  • self.requests: 받은 요청(대화 기록, 도구 정의)을 복사해 남긴다. 테스트가 요청마다 도구 정의가 실렸는지, 몇 번 불렸는지 본다.
  • FakeModelExhausted: 각본보다 많이 불리면 예외를 낸다. 루프가 끝나야 할 때 끝나지 않으면 드러난다.
  • repeat_last: 마지막 응답을 끝없이 되풀이한다. 폭주(runaway)를 만든다.
  • 함수 칸: 지금까지의 대화 기록을 읽어 응답을 만든다. 마지막 답을 도구 결과에서 만든다(_final_answer).
  • id 채우기: tool_use 블록에 toolu_fake_01부터 차례로 붙인다. 결과의 tool_use_id 짝 검사에 쓴다.

copy.deepcopy로 요청을 복사하는 까닭은, 루프가 같은 messages 목록에 계속 덧붙이기 때문이다. 복사하지 않고 참조만 남기면 모든 요청 기록이 마지막 상태로 보인다.

함수 칸 _final_answer는 대화 기록에서 search_jobs와 read_doc의 결과를 찾아 답 문장을 만든다. 기준 저장소의 llm.fake_reply()가 프롬프트 안의 자료만 보고 규칙으로 답을 만드는 것과 같은 방식이다. 그래서 모의 모델의 답에 실제 공고 이름(바람개비IoT)이 들어가고, 테스트는 “도구 결과가 답까지 전달되었는가”를 확인할 수 있다.

7-7. 5단계: 위험한 도구와 사람 승인

파일 쓰기, 메시지 보내기, 결제, 배포처럼 바깥을 바꾸고 되돌리기 어려운 도구는 모델이 요청해도 사람이 승인해야 실행되게 한다. 「Building effective agents」는 필요하면 사람에게 확인을 받도록 설계하라고 하고, Claude Code는 권한 모드와 권한 규칙으로 무엇을 묻지 않고 실행할지 정한다[E1][C21]. tools.py의 확장 도구 save_note(상담 메모를 agent_loop/notes/에 저장)는 정의에 needs_approval=True가 붙어 있어, execute()가 실행 전에 approver를 부른다.

8-1. 매 회차 다시 보내는 기록

  1. 기록은 회차마다 커진다. normal에서 질문 86자로 시작한 기록이 3회차에는 1,668자가 되었다. 도구 결과(401자, 561자)와 모델의 요청이 쌓였기 때문이다. runaway는 같은 결과가 매번 쌓여 회차마다 약 980자씩 늘었다.
  2. 보낸 총량은 회차 수의 제곱에 가깝게 는다. 회차 k에 보내는 양은 앞선 모든 회차의 결과를 담으므로, n회차까지 보낸 총량은 대략 n(n+1)/2 배로 커진다. 상한을 6에서 20으로 올리면 비용은 세 배가 아니라 그 이상으로 는다.

확인 13 출력에서 normal의 회차별 기록이 세 값으로 커지고, runaway의 증가 폭이 거의 일정하며(약 980자), 두 기록의 고정분이 같다. 이 관찰을 루프대조.md 1절 아래의 해당 줄에 적는다.

9. ReAct와 API 도구 사용

9~11절은 읽기이다. 명령과 출력은 교수 화면의 것을 읽고, 표를 보며 agent_loop/루프대조.md의 2~4절을 채운다. 직접 실행해 보고 싶으면 같은 명령을 가상 환경을 켠 저장소에서 쳐도 된다. 모두 모델을 부르지 않는다.

9-1. ReAct

ReAct는 Yao 등이 2022년에 제안하고 ICLR 2023에 발표한 방법이다[R1]. 언어 모델이 추론(reasoning)과 행동(acting)을 번갈아 만들게 하여, 추론이 행동을 이끌고 행동의 결과(관찰)가 다음 추론을 고치게 한다. 형식은 생각(Thought) → 행동(Action) → 관찰(Observation)의 반복이다.

API에 도구 사용 기능이 생기기 전에는 이것을 글의 서식으로 구현하였다. 모델에게 “생각: / 행동: / 입력:” 세 줄로만 답하라고 지시하고, 프로그램이 그 글을 읽어 행동을 고르고, 관찰을 글 끝에 이어 붙여 다시 묻는다. 2026년 2학기판 LLM 8주차에서 그 루프를 골격 위에 완성하였다. 키트의 참고/react_text_loop.py가 그 완성본이다.

[파일: ~/kits/Agent_09주차/참고/react_text_loop.py] parse_action()

def parse_action(text):
    """모델의 글에서 (행동, 입력)을 골라낸다. 행동 줄이 없으면 글 전체를 최종 답으로 본다."""
    action, arg = None, ""
    for line in text.splitlines():
        if line.startswith("행동:"):
            action = line[len("행동:"):].strip()
        elif line.startswith("입력:"):
            arg = line[len("입력:"):].strip()
    if action is None:
        return "finish", text
    return action, arg

모델이 서식을 조금만 벗어나도(예: “행동:”, “Action:”) 행동을 찾지 못하고 글 전체를 최종 답으로 처리한다. 인자도 "1100000,20"처럼 쉼표로 구분한 문자열이어서 도구가 직접 나누어 읽어야 한다.

10-2. 인증

Agent SDK와 이 장의 loop.py는 API 키로 인증한다. Agent SDK 문서는 사전 승인이 없는 한 Agent SDK로 만든 에이전트를 포함해 제3자 개발자가 자기 제품에서 claude.ai 로그인이나 그 사용량 한도를 쓰게 하는 것을 허용하지 않는다고 밝히고, API 키 인증을 쓰라고 한다[A11][S5]. Claude Code의 「Legal and compliance」도 OAuth 인증(계정 로그인)은 구독 구매자가 Claude Code와 Anthropic의 앱을 쓰기 위한 것이고, Agent SDK를 쓰는 개발자는 Claude Console이나 지원되는 클라우드 제공자의 API 키를 써야 한다고 적는다[D1].

정리하면 Claude Code는 계정 로그인으로 쓰고, loop.py와 sdk_agent.py는 .env의 ANTHROPIC_API_KEY(각자 발급한 경우)로 인증한다(부록 A-16-2). Agent SDK는 .env를 스스로 읽지 않으므로[S5] sdk_agent.py가 load_dotenv()로 읽는다. 키를 ~/.bashrc에 export하지 않는 것은 터미널의 Claude Code까지 계정 로그인 대신 그 키를 쓰게 되기 때문이다(부록 A-5-3). Agent SDK에는 모의 모드가 없으므로 sdk_agent.py는 키가 없거나 LLM_FAKE=1이면 시작하지 않는다. 다른 자격 증명으로 넘어가지 않게 하기 위해서이다.

    """tools.py의 ToolOutcome을 SDK 처리 함수의 반환 형식으로 바꾼다."""

11. Claude Code 안에서 일어나는 일

11-1. Claude Code의 루프

Claude Code 문서는 작업을 받은 Claude가 맥락 모으기(gather context), 행동하기(take action), 결과 확인하기(verify results)의 세 단계를 오가며 일한다고 설명한다[C21]. 세 단계는 정해진 순서가 아니라 도구 호출의 연속이며, 파일 읽기, 편집, 테스트 실행이 모두 이 장의 tool_use → 실행 → tool_result 한 바퀴이다. Agent SDK 문서도 SDK가 Claude Code를 움직이는 것과 같은 실행 루프를 돌린다고 밝힌다[S1]. 이 장의 루프와 Claude Code를 짝지으면 다음과 같다.

PreToolUse에서는 도구 호출을 막고, PostToolUse에서는 도구가 이미 실행되었으므로 표준 오류의 내용을 Claude에게 보여 줄 뿐이며, Stop에서는 멈추지 못하게 하여 대화를 잇게 한다[C12]. 6장에서 보호 파일을 막는 훅을 PreToolUse에, 테스트를 돌리는 훅을 PostToolUse에 둔 까닭이 이 자리의 차이이다.

11-4. 권한의 평가 순서

Claude가 도구를 요청하면 Claude Code는 정해진 순서로 그 호출을 검사한다. Agent SDK 문서는 그 순서를 여섯 단계로 적는다[S4].

순서 단계 이 단계가 하는 일
1 훅 훅이 호출을 거부하거나 넘긴다. 훅이 allow를 돌려주어도 다음의 거부·묻기 규칙 단계는 그대로 평가된다
2 거부 규칙 disallowed_tools나 설정 파일의 거부 규칙에 맞으면 거부한다. bypassPermissions 모드여도, 훅이 allow를 돌려주었어도 거부된다
3 묻기 규칙 설정 파일의 ask 규칙에 맞으면 승인 콜백(사람)에게 넘긴다
4 권한 모드 bypassPermissions는 대부분 승인, acceptEdits는 작업 폴더 안의 파일 편집을 승인, default와 dontAsk는 다음 단계로
5 허용 규칙 allowed_tools나 설정 파일의 허용 규칙에 맞으면 승인한다
6 승인 콜백 앞에서 정해지지 않은 호출을 can_use_tool 콜백(대화형에서는 사람)에게 묻는다. dontAsk에서는 이 단계 없이 거부한다

이 순서에서 두 가지를 기억한다.

  1. 거부가 허용보다 먼저이다. 3장에서 .env 읽기를 거부 규칙에 둔 것은 어떤 허용 규칙이나 모드로도 풀리지 않는다.
  2. 훅은 모든 호출을 본다. 허용 규칙으로 자동 승인되는 호출은 승인 콜백에 가지 않지만 PreToolUse 훅은 거친다. 문서는 허용 규칙이나 acceptEdits, bypassPermissions가 승인하는 호출까지 검사하려면 PreToolUse 훅을 쓰라고 한다[S4]. 6장의 보호 파일 훅이 권한 규칙과 별도로 필요한 까닭이다.

이 장의 execute()도 같은 순서를 따른다. 훅(pre_tool_hooks)을 먼저 보고, 다음에 승인(needs_approval, approver)을 보고, 마지막에 실행 안의 검사(run_tool())를 한다. 거부 규칙과 허용 규칙의 층은 단순하게 줄였다.

11-5. 서브에이전트

서브에이전트는 루프의 관점에서 도구 하나이다. Claude Code는 Agent 도구로 서브에이전트를 부르고, 서브에이전트는 자기만의 컨텍스트 창에서 일하며 끝나면 요약을 돌려준다[C21]. Agent SDK 문서도 서브에이전트는 최종 응답만 돌려주므로 주 에이전트의 맥락에는 하위 작업의 전 과정이 아니라 요약만 쌓인다고 설명한다[S1].

정리

  • 에이전트 루프는 모델 호출 → 도구 요청(tool_use) → 프로그램이 실행 → 결과(tool_result)를 돌려줌 → 반복 → 끝(end_turn 또는 상한)이다. 모델은 요청서를 쓰고, 실행과 검사와 거부는 프로그램이 한다.
  • 도구의 이름, 설명, 입력 스키마는 프롬프트의 일부이다. 설명에는 무엇을 하는지, 언제 쓰고 언제 쓰지 않는지, 무엇을 돌려주지 않는지를 쓴다.
  • tool_result는 user 메시지에 담고, tool_use_id로 짝을 맞추며, 한 응답의 결과는 모두 메시지 하나에 넣는다. 결과 앞에 글을 넣지 않고, 생각 블록은 받은 그대로 돌려보낸다.
  • 정상 종료는 end_turn뿐이다. 회차에 상한을 두고, 상한에 닿으면 답을 지어내지 않고 종료 사유를 남긴다.
  • 모델이 만든 인자는 믿지 않는 입력이다. 스키마로 형과 범위를, 처리 함수로 도메인 규칙(경로)을 검사하고, 실패는 예외 대신 is_error 결과로 돌려 모델이 대처하게 한다. 위험한 도구는 사람의 승인이 없으면 실행하지 않는다.
  • 대화 기록은 회차마다 다시 보내므로 비용이 회차 수보다 빠르게 는다. 결과를 작게 하고, 하위 작업은 서브에이전트로 떼어 요약만 받는다.
  • Agent SDK와 Claude Code는 같은 루프를 대신 돌리며, 훅과 권한 규칙과 서브에이전트는 그 루프의 정해진 자리(실행 전, 권한 판정, 실행 후, 종료 직전, 도구 하나)에 끼어든다.

개념 점검

  1. 모델의 응답에 tool_use 블록이 두 개 있다. 프로그램이 다음 요청에 보내야 하는 user 메시지의 모양을 tool_use_id를 넣어 적어라.
  2. stop_reason이 max_tokens이고 마지막 블록이 tool_use인 응답을 받았다. 이 도구 요청을 실행하면 안 되는 까닭과, 공식 문서가 권하는 처리를 설명하라.
  3. 도구 정의에 strict: true를 두었는데도 read_doc의 처리 함수 안에 경로 검사를 남기는 까닭을 두 가지 들어라.
  4. 최대 반복 상한을 6에서 30으로 올렸을 때 생길 수 있는 문제 두 가지를 이 장의 실행 기록(회차별 기록 크기)을 근거로 설명하라.
  5. Claude Code에서 허용 규칙 Bash(git commit *)에 맞는 호출이 있다. 이 호출에 대해 PreToolUse 훅, 거부 규칙, 승인 콜백 가운데 어느 것이 실행되고 어느 것이 실행되지 않는지 11-4절의 순서로 설명하라.
