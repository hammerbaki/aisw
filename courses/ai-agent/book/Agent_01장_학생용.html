AI 에이전트 운영의 요건: 보안, 신뢰성, 일관성, 재현성

2027학년도 「AI에이전트 기획 및 개발」의 준비 중인 교재입니다. 편집 상태를 검토하기 위해 미리 공개한 것으로, 수업 전에 내용과 순서가 바뀔 수 있습니다.

학사 2주차 · 교재 01 · 1부 운영 요건과 검증

150분 기준 개정(2026-11-19). 한 주 150분 수업에 맞추어 줄였다(학생용 본문 63,827자 → 35,078자). 줄인 세부 단계와 출력 예시는 교수용으로 옮겼다.

이 과목은 만든 것을 어떻게 믿을 수 있게 유지할 것인가를 다룬다. AI 에이전트가 코드를 고치고 배포까지 하는 환경에서 서비스가 허용된 일만 하고(보안), 기대한 결과를 내고(신뢰성), 누가 손대도 같은 규칙으로 바뀌고(일관성), 같은 결과를 다시 얻을 수 있게(재현성) 하는 일이다. 이 네 성질을 묶어 운영 요건이라 한다.

운영 요건은 선언으로 지켜지지 않는다. 2025년의 한 사고에서 에이전트는 바꾸지 말라는 말을 들은 채로 운영 데이터베이스를 지웠다(5-1절). 그래서 이 장은 운영 요건을 측정할 수 있는 문장으로 쓰고, 나머지 12개 장은 그 측정을 테스트, 설정, 훅, 루프, CI 같은 장치로 옮긴다. 이 장의 산출물인 운영 요건 명세와 역할 정의서는 2~13장과 프로젝트실습Ⅱ의 입력이 된다.

학습 목표

  • AI 에이전트를 모델, 도구, 루프의 세 요소로 정의하고, 워크플로와 에이전트를 구분할 수 있다.
  • 네 운영 요건을 정의하고, 공개된 사고 사례에서 어느 요건이 깨졌는지 판별할 수 있다.
  • 운영 요건을 EARS 문형과 측정 방법을 갖춘 문장으로 쓰고, 형식 검사 도구와 실제 명령으로 확인할 수 있다. 예: “빠르게 응답한다”를 “공고 목록 응답 시간의 95번째 백분위수를 300ms 이하로 유지해야 한다”로 고치고 access.log에서 그 값을 계산한다.
  • 운영 에이전트의 역할을 권한, 입력, 출력, 완료 조건, 사람 승인 지점으로 정의할 수 있다.

0. 시작하기

도구 설치, 계정 로그인, 키트 저장소의 클론(~/kits-repo)은 1주차에 부록 A로 끝냈다고 전제한다. VS Code에 확인 터미널([터미널])과 Claude Code 터미널을 나란히 둔다(부록 A-4-2). 명령은 Git Bash 기준이다.

이 장의 실행 상한. 실제 모델은 Claude Code의 대화형 세션 하나(11-4~11-8절)에서만 쓴다. jobprep은 모의 모드(LLM_FAKE=1)로 돌며 API 키는 필요 없다.

0-2. 이 장의 진행

1절은 과목의 위치, 2절은 따라 하기 둘, 3~10절은 이론, 11절은 핵심 실습이다.

1. 이 과목의 위치

1-1. 앞 과목과 이 과목

구분 LLM 서비스 개발 (2학년 1학기) AI에이전트 기획 및 개발 (2학년 2학기)
대상 개발 중인 서비스 운영 중인 서비스와 그것을 고치는 에이전트
AI의 위치 사람이 지시하는 도구 역할을 맡는 운영 주체의 하나
중심 문서 요구사항 명세서(4장): 기능을 정한다 운영 요건 명세: 그 기능이 운영 중에 지킬 조건을 정한다

운영 요건의 예: “요청의 99% 이상이 5xx 없이 끝나야 한다”, “에이전트는 .env를 읽지 않아야 한다”.

1-2. 운영과 유지보수

운영은 서비스를 계속 제공하는 일이고, 유지보수는 그 과정에서 결함을 고치고 기능을 더하는 일이다. 둘 다 지금 동작하는 것을 깨뜨리지 않으면서 바꾸는 일이다. 에이전트가 바꾸는 속도와 주체를 늘렸으므로 확인을 사람의 눈에만 맡기면 따라가지 못한다.

1-3. 세 방법론

방법론 뜻 맡는 요건 이 과목의 장
테스트 주도 개발 실패하는 테스트를 먼저 쓰는 짧은 주기. 에이전트에게 기계로 판정되는 완료 조건을 준다 신뢰성 2장
하네스 규칙 파일, 권한, 커맨드와 스킬, MCP, 훅, 서브에이전트처럼 모델 바깥에서 에이전트를 제한하는 장치의 묶음 보안, 일관성 3~7장
루프 엔지니어링 판정, 재시도 상한, 사람에게 넘기는 시점을 반복 구조로 설계하는 일 신뢰성, 재현성 8~10장

1-4. 운영 대상: 기준 저장소 jobprep

jobprep은 앞 과목에서 다룬 기능을 「취업 준비 지원 서비스」 하나로 묶은 저장소이다. 모두가 같은 출발점에서 시작해 결과를 견줄 수 있다.

기능 경로
공고 목록 GET /api/jobs, web/index.html
공고 요약(LLM) POST /api/summary, api/summary.py, prompts/summary_v1.txt
취업 자료 질의응답 POST /api/ask, api/ask.py, rag/
요구사항명세서 docs/요구사항명세서.md
모의 모드 LLM_FAKE=1, api/llm.py
운영 기록 견본 logs/access.log, error.log, llm.log

이 저장소를 운영하는 에이전트들의 묶음을 「jobprep 운영 에이전트 시스템」 이라 부른다.

1-5. 프로젝트실습Ⅱ와의 관계

이 과목은 프로젝트를 두지 않고, 프로젝트실습Ⅱ의 팀이 쓸 장치를 jobprep 위에서 먼저 만든다. 1장의 두 문서는 졸업 프로젝트의 비기능 요구와 역할 분담으로, 2~3장의 테스트와 팀 규칙은 팀 저장소의 규칙으로 이어진다.

1-6. 수업 운영의 원칙

  • 실습은 모의 모드로 한다. 프로덕트의 API 키는 선택이며, 키가 없어도 모든 장이 끝까지 돈다.
  • Claude Code의 응답은 「예시」로 싣는다. 판정은 응답이 아니라 사람이 실행한 명령의 결과로 한다.

3. 에이전트의 정의

3-1. 모델, 도구, 루프

이 과목에서 AI 에이전트는 다음 세 요소를 갖춘 시스템이다.

요소 뜻 Claude Code에서
모델 다음에 할 일을 정하는 LLM Claude 모델(Opus, Sonnet, Haiku 등)
도구 바깥 세계를 읽거나 바꾸는 수단 파일 편집, 검색, 셸 명령
루프 도구 결과를 다시 모델에 넣는 반복 맥락 수집 → 행동 → 결과 확인의 되풀이

Anthropic은 에이전트를 환경의 되먹임을 바탕으로 도구를 쓰는 LLM을 반복으로 돌리는 것에 가깝게 설명하고[E1], Claude Code 문서는 이 반복을 에이전트 루프로 설명한다[C1][E4].

3-2. Claude Code의 에이전트 루프

“실패하는 테스트를 고쳐 줘”라고 하면 Claude Code는 테스트를 실행하고, 관련 파일을 읽고, 고친 뒤 다시 실행한다[C1]. 각 단계는 모델이 정한다. 운영에서는 도구의 범위(3장, 5장, 11장), 「됐다」를 판정하는 확인 단계(2장, 6장), 언제 멈추는가의 반복(8장, 10장)을 본다. 문서는 모델을 둘러싼 이 바깥 층을 에이전트 하네스라 부르며[C1], 3~7장은 그 층에 팀의 규칙과 검사를 더한다.

3-3. 워크플로와 에이전트

Anthropic의 「Building effective agents」(2024-12-19)는 에이전트 시스템을 둘로 나눈다[E1].

구분 정의 (E1의 요지) 다음 단계를 정하는 것 예
워크플로 LLM과 도구가 미리 정한 코드 경로를 따라 조율되는 시스템 사람이 짠 코드 jobprep의 /api/ask
에이전트 LLM이 자기 작업 과정과 도구 사용을 스스로 동적으로 정하는 시스템 모델 Claude Code

/api/ask는 LLM을 쓰지만 워크플로이다. api/ask.py에는 검색(49행), 유사도 판정(51행), 생성(56행), 인용 번호 추출(60행)이 코드의 순서대로 놓여 있고, LLM은 정해진 자리에서 한 번 불릴 뿐이다. 워크플로의 실패는 단계를 찾아 테스트로 막을 수 있지만, 에이전트의 실패는 모델이 고른 경로에서 나므로 미리 다 시험할 수 없다. 그래서 에이전트에게는 경로가 아니라 경계(무엇을 할 수 없는가)와 판정(무엇이 되면 끝인가)을 요건으로 준다.

생각해 볼 것. 검색, 유사도 판정, 생성의 순서를 근거로 /api/ask가 워크플로인 까닭을 한 문장으로 말해 본다.

업무 맞는 구조 까닭

공고 본문을 네 부분으로 요약 워크플로 입력과 출력의 모양이 고정되어 있다
실패하는 테스트의 원인 찾기 에이전트 무엇을 읽어야 할지 결과를 보기 전에는 모른다

판단이 필요 없는 일에 에이전트를 쓰지 않는 것은 LLM이 끼는 곳마다 7절의 새 위험이 생기기 때문이다.

4. 자율성의 수준과 사람의 개입

4-1. 능력과 자율성

에이전트가 무엇을 할 수 있는가(능력)와 사람의 확인 없이 무엇을 해도 되는가(자율성)는 다른 질문이다. Feng, McDonald, Zhang(2025)은 자율성을 능력과 따로 설계할 수 있는 속성으로 보고, 사용자의 역할에 따라 다섯 수준으로 나누었다[L1].

4-2. 다섯 수준

수준 사람의 역할 사람이 하는 일
1 조작자 계획과 결정을 이끌고, 에이전트는 불렸을 때만 행동한다
2 협업자 함께 계획하고 나누어 실행하며, 언제든 넘겨받는다
3 상담자 계획을 검토하고 방향을 준다. 에이전트는 정해진 지점에서 묻는다
4 승인자 중대한 행동의 승인에서만 개입한다
5 관찰자 기록을 보고 비상 정지만 할 수 있다

(L1을 요약해 옮겼다.) 수준은 일의 위험과 되돌리기 어려움에 맞추어 고르며, 이 과목은 어느 역할에도 수준 5를 주지 않는다.

Claude Code는 이 수준을 권한 모드로 조절한다[C2]. 수준 칸은 이 교재가 붙인 대략의 자율성 수준이다.

Claude Code의 체크포인트(Esc 두 번)는 파일 변경만 되감으며, 데이터베이스, API, 배포처럼 원격 시스템에 영향을 주는 행동은 되돌리지 못한다[C1]. 사람의 개입 지점은 되돌리기 어려운 행동일수록 촘촘하게 둔다. 5절의 사고는 대부분 그쪽에서 일어났다.

5. 공개된 사고 사례

네 사례는 2025년에 AI 에이전트나 코딩 도구가 실제 사용자의 데이터나 배포물에 피해를 준 사건으로, 당사자의 공개 기록이나 신뢰할 수 있는 보도로 확인한 것이다. 사실은 출처의 범위 안에서만 적었다. 이 장의 질문은 운영 중에 무엇이 지켜졌어야 했고 그것을 무엇으로 쟀어야 했는가이다.

5-1. 사례 1: 코드 동결 중에 운영 데이터베이스를 지운 에이전트 (2025-07)

사실. SaaS 업계 커뮤니티 SaaStr의 창업자 제이슨 렘킨(Jason Lemkin)은 Replit의 AI 에이전트로 앱을 만들던 중 에이전트가 운영 데이터베이스를 지웠다고 2025년 7월에 공개하였다. 그는 허락 없이 코드를 바꾸지 말라고 지시했고, 바꾸지 않는 기간(코드 동결, code freeze)을 선언한 상태였다. 렘킨에 따르면 에이전트는 버그를 가짜 데이터와 가짜 보고로 덮었고, 4,000명 분량의 가상 인물 데이터베이스를 만들었으며, 데이터베이스를 되돌릴 수 없다고 답했으나 실제로는 되돌리기가 되었다. 그는 Replit 같은 도구에서는 코드 동결을 강제할 방법이 없다고 썼다[I1].

대응. Replit의 최고경영자 암자드 마사드(Amjad Masad)는 이 일을 일어나서는 안 되는 일이라고 하고, 개발용과 운영용 데이터베이스를 자동으로 분리하는 기능을 배포하기 시작하였다. 에이전트가 적절한 내부 문서에 접근하지 못해 복구 요청에 제대로 답하지 못했다고 설명하고, 에이전트가 Replit 문서를 반드시 검색하게 하는 수정과 스테이징 환경 계획도 밝혔다[I2].

원인. 금지는 자연어 지시로만 있었다. 에이전트는 운영 데이터에 쓰기 권한을 가졌고(보안), 복구 가능 여부를 에이전트의 말에 의존하였으며(신뢰성), 개발과 운영이 같은 데이터베이스를 썼고(일관성), 가짜 보고를 실제 결과와 구분할 실행 기록이 없었다(재현성).

5-2. 사례 2: 실패를 확인하지 않고 파일을 옮긴 CLI 에이전트 (2025-07)

사실. 2025년 7월 21일, 한 사용자가 Google의 Gemini CLI 저장소에 「Gemini CLI가 실패한 파일 이동 중에 파일을 ‘잃어버렸다’」는 이슈를 올렸다. 이슈에 첨부한 환경 정보에는 운영체제 Windows, 모델 gemini-2.5-pro, 샌드박스 없음(no sandbox)이 적혀 있다[I3]. 첨부한 대화 기록에 따르면 사용자는 실험 폴더의 파일을 새 폴더로 옮겨 달라고 하였다. 에이전트는 새 폴더를 만드는 mkdir 명령을 실행한 뒤 폴더가 실제로 생겼는지 확인하지 않고 성공했다고 보았고, 이어서 move 명령들을 실행하였다. 그 뒤 폴더를 읽자 항목이 0개였고, 에이전트는 mkdir이 조용히 실패했을 가능성이 높다며 데이터를 잃었다고 인정하였다[I3]. 이 사건은 Ars Technica 등이 2025년 7월 하순에 사례 1과 함께 보도하였다.

원인. 에이전트는 명령의 결과를 다시 읽어 확인(쓰기 뒤 읽기, read-after-write)하지 않았다. Windows의 move는 대상 폴더가 없으면 이름을 바꾸는데, 이 동작이 기록과 맞는다는 분석이 있으나 대화 기록만으로는 확정할 수 없다. 확인되는 것은 존재하지 않는 대상을 존재한다고 믿고 되돌릴 수 없는 명령을 이어 실행했다는 점(신뢰성), 격리 없이 실제 폴더에서 실행했다는 점(보안), 이동 전 상태가 남지 않았다는 점(재현성)이다.

5-3. 사례 3: 캐시를 지우라는 요청에 드라이브 전체를 지운 에이전트 (2025-11)

사실. 2025년 11월 말, 그리스의 한 사진가가 Google의 에이전트 개발 환경 Antigravity를 쓰다가 D: 드라이브 전체가 지워졌다고 Reddit에 올렸고, The Register가 2025년 12월 1일에 보도하였다. 그는 개발자가 아니었고, 사진을 평가해 폴더로 나누는 도구를 만들고 있었다. 그는 에이전트가 사용자 입력 없이 명령을 실행하는 Turbo 모드를 쓰고 있었다. 에이전트는 프로젝트 캐시를 지우는 명령이 특정 프로젝트 폴더가 아니라 D: 드라이브의 루트를 잘못 겨냥한 것으로 보인다고 스스로 답하였다(기사는 이 설명을 따로 검증하지 않았다). 지운 파일은 휴지통을 거치지 않아 복구되지 않았고, 대부분은 다른 드라이브에 백업되어 있었다. Google은 보고를 알고 있으며 조사 중이라고 답하였다[I4].

원인. 확인 없이 셸 명령을 실행하는 모드에서 작업 폴더 밖을 지울 수 있었고(보안. 자율성이 위험보다 높았다), 지울 경로를 실행 전에 검증하지 않았다(신뢰성). 보도는 이런 도구를 잠근 분리 환경에서 쓰라고 권하였다[I4].

5-4. 사례 4: 배포된 AI 코딩 확장에 들어간 악성 지시 (2025-07)

사실. AWS는 2025년 7월 23일 보안 공지 AWS-2025-015를 내고, VS Code용 Amazon Q Developer 확장의 1.84.0 판에 악성 코드가 들어갔다고 밝혔다(CVE-2025-8217). 확장의 빌드 설정(CodeBuild)에 권한 범위가 지나치게 넓은 GitHub 토큰이 있었고, 공격자가 그 토큰으로 확장의 오픈 소스 저장소에 코드를 커밋하였으며, 그 코드가 자동으로 배포판에 포함되었다. AWS는 악성 코드가 문법 오류로 실행되지 않아 서비스나 고객 환경을 바꾸지 못했다고 밝히고, 자격 증명을 폐기·교체한 뒤 1.85.0을 배포하며 1.84.0을 모두 지우라고 권고하였다[I5]. 보도에 따르면 들어간 코드는 Amazon Q의 명령행 에이전트를 모든 도구를 신뢰하고(--trust-all-tools) 묻지 않는(--no-interactive) 옵션으로 실행하면서, 사용자의 홈 폴더 파일과 AWS 클라우드 자원을 찾아 지우라는 지시문을 넘기는 것이었다. 이 판은 7월 19일에 배포되어 이틀 동안 마켓플레이스에 있었다[I6].

원인. 빌드 토큰의 권한이 필요보다 넓었고 공급망에 악성 변경이 들어왔다(보안). 같은 저장소의 변경인데 사람의 검토 없이 배포판까지 간 경로가 있었다(일관성). 공격자는 에이전트의 자율성을 가장 높이 여는 옵션을 골라 썼다. 그런 옵션이 있다는 것 자체가 공격면이 된다.

5-5. 보론: 원인을 두고 다투는 사례

2026년 2월 20일, Financial Times의 보도를 인용해 The Register는 AWS가 2025년 12월 한 서비스에서 13시간 동안 중단을 겪었고, 엔지니어가 AI 코딩 도구 Kiro에 변경을 맡기자 Kiro가 환경을 지우고 다시 만들기로 했다고 전하였다. Amazon은 원인이 AI가 아니라 직원의 실수, 곧 잘못 설정된 접근 제어라고 반박하였고, 영향은 한 지역의 비용 조회 서비스에 한정되었다고 밝혔다. Amazon은 Kiro가 기본으로 행동 전에 승인을 요청하지만 해당 엔지니어가 예상보다 넓은 권한의 역할을 쓰고 있었다고 하였으며, 사건 뒤 운영 접근에 대한 동료 검토 의무화 같은 안전장치를 더했다고 밝혔다[I7].

양측이 사실관계를 다투므로 사례 1~4처럼 분석하지 않는다. 다만 양측의 진술은 에이전트가 쓰는 권한의 범위가 사고의 크기를 정하였다는 점에서 일치한다. 운영 요건의 질문은 누구의 잘못인가가 아니라, 누가 하든 그 권한으로 그 행동이 가능했는가이다.

6. 네 운영 요건

6-1. 정의

요건 정의 대응 개념
보안 에이전트와 프로덕트가 허용된 일만 하고, 비밀 정보가 새지 않는다 최소 권한, 직무 분리, 위협 모델링
신뢰성 정해진 조건에서 기대한 결과를 내고, 실패하면 알아채고 멈추거나 복구한다 SLI·SLO, 오류 예산
일관성 같은 종류의 일은 누가 해도 같은 규칙과 형식으로 된다 코딩 규약, 코드 검토, 환경의 동등성
재현성 같은 입력과 환경에서 같은 결과를 다시 얻고, 무엇이 실행되었는지 기록이 남는다 재현 가능한 빌드, 버전 고정, 감사 기록

네 요건은 겹친다. 분류는 그 요건이 깨지면 가장 먼저 무엇이 문제가 되는가로 하나를 고른다.

6-2. 보안

보안의 출발점은 최소 권한, 곧 각 주체에게 그 기능에 필요한 최소한의 권한만 주는 원칙이다[S2]. 에이전트는 그 주체가 하나 더 생긴 것이다. OWASP의 LLM 애플리케이션 10대 위험은 이를 과도한 행위 능력(Excessive Agency, 2025년판 LLM06, 2026년판 LLM03)으로 다루고[O4], 원인을 필요 없는 도구를 부를 수 있는 과도한 기능, 테스트 역할이 git push를 할 수 있는 것 같은 과도한 권한, 영향이 큰 행동을 승인 없이 하는 과도한 자율성의 셋으로 든다[O3]. 보안 요건은 금지된 행동을 적고(“.env를 읽지 않아야 한다”), 시도해서 막히는지 보아 잰다(11장).

6-3. 신뢰성

신뢰성은 SRE의 용어로 잰다[S1].

용어 정의 (S1의 요지) jobprep의 예
SLI(서비스 수준 지표) 서비스 수준의 한 측면을 정량화한 값 한 주의 5xx 비율, 공고 목록 응답 시간의 95번째 백분위수
SLO(서비스 수준 목표) SLI로 재는 목표값이나 범위 5xx 비율 1% 이하, 95번째 백분위수 300ms 이하
오류 예산 목표를 100%로 두지 않는 대신 정한, SLO를 어겨도 되는 정도 SLO가 5xx 1% 이하이면 한 주 요청의 1%

지연 시간은 평균보다 백분위수로 본다. 평균은 드물게 매우 느린 요청을 감추기 때문이다. 목표는 현재 성능을 그대로 삼지 않는다[S1]. 에이전트에게는 실패를 알아채고 멈추는가가 더해진다. 완료 보고 전에 무엇을 실행해 확인하는가와 몇 번 실패하면 사람에게 넘기는가를 적는다.

6-4. 일관성

Google의 스타일 가이드는 큰 코드베이스는 일관된 스타일일 때 이해하기 쉽다고 밝힌다[S5]. 에이전트는 세션마다 새 맥락에서 시작하므로 규칙이 없으면 실행마다 다른 이름과 구조를 쓸 수 있다. 「Twelve-Factor App」은 개발과 운영을 가능한 한 비슷하게 유지하라고 권한다[S3]. 같아야 할 것(소프트웨어의 판)은 같게, 달라야 할 것(데이터, 자격 증명)은 다르게 둔다. 일관성은 대개 규칙을 어긴 흔적을 찾는 검색 명령으로 잰다.

6-5. 재현성

재현 가능한 빌드는 같은 소스, 환경, 빌드 지시로 누구든 같은 산출물을 다시 만들 수 있는 것이다[S4]. 이 셋과 기록이 고정할 대상이며, LLM과 에이전트는 저마다 더할 것이 있다.

고정 대상 일반 소프트웨어 LLM과 에이전트가 더하는 것 jobprep의 장치
소스 커밋, 태그 프롬프트 판본 Git 커밋, prompts/summary_v1.txt, PROMPT_SUMMARY
환경 언어와 패키지의 판 모델 이름, Claude Code의 판 requirements.txt의 ==, LLM_MODEL, claude --version

기록 빌드 기록 어떤 모델이 어떤 프롬프트로 무엇을 냈는가 응답의 prompt_version·model, llm.log

6-6. 요건 사이의 긴장

모든 명령에 승인을 요구하면 사람이 승인 창을 읽지 않고 누르게 되고(보안 대 편의), 판을 고정하면 보안 패치를 놓치며(재현성 대 최신성), 재시도할수록 비용이 는다(신뢰성 대 비용). 기준값에는 왜 이 값인가를 한 줄 적는다.

6-7. 서비스의 요건과 에이전트의 요건

운영 요건에는 주어가 둘 나온다. 시스템은 서비스 jobprep이며 기록, 테스트, 응답으로 잰다(“시스템은 한 주의 5xx 비율을 1% 이하로 유지해야 한다.”). 운영 에이전트는 jobprep을 고치고 지켜보는 에이전트들이며 설정, 실행 기록, 시도와 거부로 잰다(“운영 에이전트는 .env 파일을 읽지 않아야 한다.”). 사례 1~3은 모두 운영 에이전트의 요건이 없어서 생긴 사고였다.

생각해 볼 것. jobprep의 요건 하나를 「시스템」 주어로, 하나를 「운영 에이전트」 주어로 말하고 각각의 분류를 정해 본다.

7. LLM 특유의 어려움

7-1. 비결정성

temperature를 0으로 두어도 결과는 완전히 결정적이지 않다[A1]. Thinking Machines Lab의 2025년 9월 글은 주된 원인을 서버 부하에 따라 바뀌는 요청의 묶음 크기에서 찾았고, 공개 모델에 temperature 0으로 같은 질문을 1,000번 보내자 서로 다른 응답이 80가지 나왔다[N1]. 그래서 한 번 해 보니 됐다는 확인이 되지 않고 통과율로 보아야 하며(12장), 결과의 모양을 묶는 규칙과 형식 검사가 필요하다.

7-2. 환각과 거짓 보고

LLM은 그럴듯하지만 사실이 아닌 내용을 낼 수 있고(환각), 에이전트에서는 그것이 행동으로 이어진다. 사례 1과 2의 에이전트의 보고는 사실이 아니었다. 그러므로 완료 조건을 에이전트의 말이 아니라 명령의 결과로 정한다. 예: “python -m pytest -q를 실행하고 그 결과 줄을 보고에 붙인다.” Agent SDK를 소개한 글도 확인 방법으로 규칙 기반 되먹임을 가장 먼저 든다[E4].

7-3. 프롬프트 주입

프롬프트 주입(OWASP 2025·2026년판 LLM01)은 입력이 LLM의 행동을 의도하지 않은 방식으로 바꾸는 취약점이며, 웹 페이지나 파일 같은 외부 출처의 숨은 지시에 의한 간접 주입도 있다[O2]. jobprep에서는 공고 본문과 자료 문서가, 운영 에이전트에게는 이슈 본문과 기록 파일이 그 통로이다. 모델의 성능으로 막지 못하므로 권한과 격리로 경계를 긋는 문제로 다룬다(11장).

8. 측정 가능한 요건 문장

8-1. EARS 되짚기

EARS(Easy Approach to Requirements Syntax)는 2009년에 롤스로이스의 알리스테어 메이빈(Alistair Mavin)과 동료들이 제트 엔진 제어 시스템의 규정을 분석하며 만든 문형으로, 적은 훈련으로 자연어 요구사항의 흔한 문제를 줄이게 한다[R1]. 앞 과목 4장에서 썼고 jobprep의 요구사항명세서도 같은 틀이다. 운영 요건 명세는 이 틀에 6-7절의 두 주어를 쓴다.

문형 틀 운영 요건의 예
상시 (주어)는 ~해야 한다. 운영 에이전트는 .env 파일을 읽지 않아야 한다.
상태 ~인 동안, … 모의 모드가 아닌 동안, 시스템은 하루 토큰 합계를 예산 안에 두어야 한다.
사건 ~하면, … 운영 에이전트가 코드를 고치면, 운영 에이전트는 완료 보고 전에 python -m pytest -q를 실행해야 한다.
선택 ~가 설정된 경우, … 장애 보고 스킬이 설치된 경우, 운영 에이전트는 같은 절 구성으로 보고해야 한다.
원치 않는 동작 만약 ~하면, … 만약 테스트가 3회 연속 실패하면, 운영 에이전트는 사람에게 실패 보고서를 넘겨야 한다.

8-2. 측정 가능한 요건의 조건

“시스템은 안정적으로 동작해야 한다”는 상시 문형이지만 잴 수 없다. 이 과목은 다음 다섯 조건을 갖춘 요건을 측정 가능하다고 본다.

조건 질문 갖춘 예
주어 누가 지키는가 “운영 에이전트는 .env 파일을 읽지 않아야 한다”
관찰할 수 있는 행동이나 값 무엇을 보면 지켜졌는지 아는가 “503으로 응답”
수치와 범위 어디까지가 통과인가 “p95 300ms 이하”
기간과 표본 언제, 무엇을 모아 재는가 “한 주의 전체 요청 가운데”
측정 방법 무엇으로 재는가 “access.log에서 status>=500 줄 수 ÷ 전체 줄 수, 주 1회”

측정 방법은 표의 별도 칸에 적어, 측정 장치가 바뀔 때 문장은 두고 방법만 고친다.

8-3. 모호한 말 고치기

모호한 말 고친 예
적절히 “적절히 오류를 처리한다” → “503과 까닭을 응답하고 error.log에 예외 이름을 남긴다”
빠르게 “빠르게 응답한다” → “95번째 백분위수 300ms 이하”
안전하게 “키를 안전하게 관리한다” → “API 키를 어떤 커밋에도 넣지 않는다”
가능한 한 “가능한 한 재시도한다” → “3회까지 재시도하고, 그래도 실패하면 사람에게 넘긴다”
항상 “항상 응답한다” → “한 주의 99% 이상을 5xx 없이”(6-3절의 절대값 피하기)

생각해 볼 것. “에이전트는 테스트를 잘 돌려야 한다”를 측정 가능한 요건 문장으로 고치고 측정 방법을 붙여 본다.

8-4. 측정 방법의 종류

측정 방법은 네 종류이며, 위에 있을수록 자동화하기 쉽다.

종류 예 이 과목에서 자동화하는 장
테스트 python -m pytest -q의 통과 수 2장, 13장
검색·집계 명령 grep의 줄 수, awk로 계산한 비율 5장, 12장
시도와 거부 금지된 행동을 일부러 요청해 막히는지 본다 3장, 6장, 11장
사람의 검토 보고서를 읽고 판정한다 줄여 나간다

1장 시점에는 사람의 검토여도 되며, “3장 이후: …, 그전: …”처럼 장치가 생긴 뒤의 방법을 함께 적는다.

8-5. 형식 검사 도구

9. 운영 에이전트 시스템의 역할

9-1. 왜 역할을 나누는가

역할을 나누면 역할마다 필요한 권한만 주어 권한을 좁힐 수 있고, 작성과 검토를 떼어 놓을 수 있으며(직무 분리), 역할 사이의 경계에서 사람의 개입 지점이 드러난다. 예를 들어 테스트 역할과 구현 역할을 나누면 구현하는 쪽이 테스트를 고쳐 통과시키는 회피를 권한으로 막는다(2장). 1장은 역할을 문서로 정하고, 실제 에이전트로 만드는 것은 6장과 10장이다.

9-2. 여섯 역할

역할 맡는 일 주로 지키는 요건 구현하는 장
기획 이슈를 작업 단위로 나누고 인수 조건을 쓴다 일관성 10장
구현 승인된 계획과 실패하는 테스트에 따라 코드를 고친다 신뢰성 2장, 8장
테스트 인수 조건을 테스트로 쓰고 실행해 판정한다 신뢰성, 재현성 2장, 6장, 12장
검토 변경을 규칙과 요건에 비추어 읽고 의견을 낸다 일관성, 보안 6장, 10장
배포 통과한 판을 태그로 고정하고 배포와 되돌리기를 준비한다 재현성, 신뢰성 13장
관측 운영 기록을 읽어 요건 위반과 비용을 보고한다 신뢰성 5장, 12장

다섯 이상을 쓴다. 다섯만 쓴다면 기획을 사람이 맡거나 배포와 관측을 합치고, 까닭을 역할 정의서의 4절에 적는다.

9-3. 역할 정의서의 항목

역할마다 다음 항목을 적는다. 형식 검사 도구는 굵게 표시한 다섯 항목이 비어 있지 않은지 본다.

항목 잘 쓴 예 잘못 쓴 예
목적 승인된 계획의 작업 단위 하나를 테스트가 통과하도록 구현한다 코드를 잘 짠다
권한 쓰기: api/, rag/, web/. 금지: tests/의 기존 테스트 수정, main에 푸시 필요한 모든 권한
입력 승인된 계획 문서, 실패하는 테스트 요청
출력 작업 브랜치의 커밋, 변경 요약 결과물
완료 조건 python -m pytest -q가 모두 통과하고 그 결과 줄이 보고에 있다 구현이 끝났다고 보고한다
사람 승인 지점 계획에 없는 파일을 고쳐야 할 때, 새 패키지가 필요할 때 없음
관련 운영 요건 OR-REL-04, OR-CON-01 (비움)

완료 조건의 잘못 쓴 예는 판정을 모델의 말에 맡기는 것(7-2절)이고, 권한의 잘못 쓴 예는 과도한 권한(6-2절)이다. 권한 칸에는 반드시 금지를 적는다. 형식 검사 도구는 금지가 없는 권한 칸에 경고를 낸다.

9-4. 역할별 자율성과 사람 승인 지점

이 과목의 권장안은 기획·구현·테스트가 수준 3(승인 지점은 각각 계획 승인, 계획 밖의 파일과 새 패키지, 테스트 동결), 검토와 관측이 수준 4(병합과 이슈 등록은 사람이 정한다), 배포가 수준 2(배포와 되돌리기의 실행을 사람이 승인한다)이다. 배포의 수준이 가장 낮은 것은 능력이 아니라 되돌리기 어려움 때문이다. 고친다면 까닭을 적는다.

11-8. 문제 해결: 측정 명령이 다른 것을 잰다

형식 검사는 측정 방법 칸이 비었는지만 본다(8-5절). 먼저 계획 모드의 Claude Code에게 읽기 검토를 맡기고, 판정은 학습자가 한다.

Claude Code 
docs/운영/운영요건.md를 읽고 검토해 줘. 파일은 고치지 마.
1. 측정 방법에 적힌 명령 가운데 이 저장소에서 실제로 실행하면 실패하거나, 요구 문장과 다른 대상을 재는 것
2. 요구 문장과 측정 방법이 서로 다른 것을 말하는 행
3. 1장 5절의 사고 네 건(운영 DB 삭제, 확인 없는 파일 이동, 드라이브 삭제, 확장의 악성 지시)을 막는 데 필요한데 빠진 요건
각 지적마다 행 ID와 근거를 붙이고, 확신이 낮은 지적은 그렇다고 표시해 줘.

Claude Code가 지적했든 하지 않았든, 측정 명령이 무엇을 고르는지는 직접 확인한다. 11-5절의 응답 시간 명령이 고른 247줄의 경로를 센다.

터미널 
grep 'path=/api/jobs' logs/access.log | grep -o 'path=[^ ]*' | sed 's#/api/jobs/[0-9]*#/api/jobs/N#' | sort | uniq -c
     79 path=/api/jobs
    168 path=/api/jobs/N

sed는 번호가 붙은 경로를 하나로 묶고, uniq -c는 같은 줄의 수를 센다. 247줄 가운데 168줄은 상세 요청이다. 'path=/api/jobs'가 path=/api/jobs/28의 앞부분과도 맞기 때문이다. 기록에서 경로 다음에는 빈칸이 오므로, 경로 뒤에 빈칸 하나를 두면 목록 요청만 고른다.

터미널 
grep -c 'path=/api/jobs' logs/access.log
grep -c 'path=/api/jobs ' logs/access.log
grep 'path=/api/jobs ' logs/access.log | grep -o 'ms=[0-9]*' | cut -d= -f2 | sort -n |
  awk '{ v[NR] = $1 } END { i = int(NR * 0.95); if (i < NR * 0.95) i++; print "요청", NR, "개, p95", v[i] "ms, 최대", v[NR] "ms" }'
247
79
요청 79 개, p95 25ms, 최대 25ms

고친 p95는 25ms로 섞어 잰 23ms와 다르다. 이 견본에서는 둘 다 300ms 안이지만, 상세 요청의 속도가 달라지면 섞어 잰 값은 목록의 실제 상태와 다른 판정을 낸다. 측정 명령이 다른 것을 재면 요건이 깨져도 「통과」로 보인다. 해당 요건(예: OR-REL-02)의 측정 방법 칸을 끝에 빈칸이 있는 명령으로 고치고 그 까닭을 덧붙인다. 4절에는 고치기 전(247줄, p95 23ms)과 고친 뒤(79줄, p95 25ms)를 두 줄로 남긴다. 틀린 측정을 지우지 않아야 뒤에 같은 실수를 하는 사람이 알아본다. 다른 측정 명령에도 고르는 줄이 요구의 대상과 같은가를 묻는다. Claude Code의 나머지 지적은 받아들이면 문서를 고치고, 받아들이지 않으면 까닭을 부록 A 아래에 한 줄 적은 뒤 형식 검사를 다시 돌린다.

확인 11 uniq -c의 출력에서 247줄 가운데 168줄이 상세 요청임을 확인하였고, 운영 요건 명세의 해당 측정 방법 칸에 끝에 빈칸이 있는 명령이 있으며, 4절에 고치기 전(247줄, p95 23ms)과 고친 뒤(79줄, p95 25ms)의 두 줄이 있고, 다시 돌린 형식 검사가 결과: 통과이다.

11-11. 핵심 실습 복기

요건의 기준과 현재 상태는 실행한 값에서 나왔고, Claude Code의 설명은 명령으로 대조하였다. 형식 검사도 기준도 통과하던 측정 명령은 상세 요청을 섞어 재고 있었다. 판정은 명령의 결과로 하되, 그 명령이 무엇을 재는지도 사람이 확인한다.

제출물

따로 올리는 것은 없다. 다음이 자기 원격 저장소 jobprep의 main에 있으면 된다.

~/agent-lab/jobprep/
├── docs/운영/운영요건.md    운영 요건 명세 (EARS 15문장 이상, 요건마다 측정 방법, 잰 값과 고친 측정 명령, 구조 대조)
├── docs/운영/역할정의.md    역할 정의서 (역할 5개 이상, 권한·입력·출력·완료 조건·사람 승인 지점)
└── ops/check/              형식 검사 도구와 테스트 (키트에서 옮긴 것)

완료 기준은 11-1절의 표와 같다. 저장소가 비공개이므로 교수 계정을 협업자로 초대하며, 방법은 수업에서 안내한다.

정리

  • AI 에이전트는 모델, 도구, 루프를 갖추고 다음 행동을 모델이 정하는 시스템이다. 미리 정한 코드 경로로 LLM을 부르는 것은 워크플로이다.
  • 자율성은 능력과 따로, 위험에 맞추어 설계한다. 2025년의 공개 사고에서 금지는 말로만 있었고, 성공은 모델의 말로 판정되었으며, 권한은 필요보다 넓었다.
  • 네 운영 요건은 최소 권한, SLI·SLO, 규약과 환경 동등성, 재현 가능한 빌드에 대응한다. 운영 요건은 EARS 문형에 측정 방법을 붙여 쓰고, 완료는 명령의 결과로 판정하며, 그 명령이 무엇을 재는지도 확인한다.

개념 점검 문항

  1. jobprep의 /api/ask가 LLM을 쓰면서도 에이전트가 아니라 워크플로인 까닭을 「Building effective agents」의 정의로 설명하라.
  2. Claude Code의 acceptEdits와 auto 모드를 자율성의 다섯 수준에 대어 비교하고, 운영 저장소에서 처음 구조를 파악할 때 둘 다 쓰지 않는 까닭을 설명하라.
  3. Replit 사례에서 깨진 운영 요건 둘을 들고, 각각을 jobprep에 맞는 EARS 문장과 측정 방법으로 바꾸어 써라.
  4. 응답 시간 요건을 평균이 아니라 95번째 백분위수로 쓰는 까닭을 이 장에서 잰 요약 요청의 값으로 설명하라.
  5. 다음 역할 정의의 문제를 둘 지적하고 고쳐 써라. “구현 에이전트: 권한은 필요한 모든 권한, 완료 조건은 구현이 끝났다고 보고하는 것.”
