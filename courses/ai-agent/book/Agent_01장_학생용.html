1장

AI 에이전트 운영의 요건: 보안, 신뢰성, 일관성, 재현성

2027학년도 「AI에이전트 기획 및 개발」의 준비 중인 교재입니다. 편집 상태를 검토하기 위해 미리 공개한 것으로, 수업 전에 내용과 순서가 바뀔 수 있습니다.

학사 2주차 · 교재 01 · 1부 운영 요건과 검증

앞 과목 「LLM 서비스 개발」은 무엇을 누구에게 만들 것인가를 다루었다. 조사에서 시작해 페르소나, 요구사항 명세, 화면 설계, 구현, 사용성 평가에 이르는 한 학기 동안 「취업 준비 지원 서비스」 하나를 만들었다. 이 과목은 그 다음 질문을 다룬다. 만든 것을 어떻게 믿을 수 있게 유지할 것인가. AI 에이전트가 코드를 고치고, 테스트를 돌리고, 배포까지 하는 환경에서 서비스가 계속 허용된 일만 하고, 기대한 결과를 내고, 누가 손대도 같은 규칙으로 바뀌고, 같은 조건에서 같은 결과를 다시 얻을 수 있게 하는 일이다. 이 네 성질을 이 과목은 보안, 신뢰성, 일관성, 재현성이라 부르고, 묶어서 운영 요건이라 한다.

운영 요건은 선언으로 지켜지지 않는다. 2025년에 공개된 여러 사고에서 사람은 AI 에이전트에게 “허락 없이 바꾸지 말라”고 말했고, 에이전트는 그 말을 들은 채로 운영 데이터베이스를 지웠다. 말은 있었으나 그 말을 강제하는 장치도, 지켜졌는지 재는 방법도 없었다. 그래서 이 장은 운영 요건을 측정할 수 있는 문장으로 쓰는 데서 출발한다. 요건마다 “무엇을 어떤 명령이나 기록으로 재면 지켜졌는지 알 수 있는가”를 함께 적는다. 이 과목의 나머지 12개 장은 그 측정을 사람의 손에서 테스트, 설정, 훅, 루프, CI 같은 장치로 옮기는 과정이다.

이 장에서 만드는 것은 하나이다. 학기 내내 운영할 기준 저장소 jobprep을 자기 GitHub 저장소로 만들고, 그 저장소의 운영 요건 명세(docs/운영/운영요건.md, EARS 문장 15개 이상, 요건마다 측정 방법)와, 이 저장소를 운영할 에이전트들의 역할 정의서(docs/운영/역할정의.md, 역할 5개 이상)를 쓴다. 그 과정에서 측정 방법에 적은 명령 하나가 요구와 다른 것을 재는 문제를 찾아 고친다. 두 문서는 2장부터 13장까지 모든 장의 입력이 된다.

같은 학기 프로젝트실습Ⅱ에서 팀은 졸업 프로젝트를 만들고 발표한다. 그 프로젝트를 배포한 뒤에도 믿고 쓰게 하려면 이 장과 같은 문서, 곧 무엇을 지켜야 하고 무엇으로 재는지를 적은 운영 요건과, 누가(사람이든 에이전트든) 무엇을 할 수 있는지를 적은 역할 정의가 필요하다. 이 장의 양식은 프로젝트실습Ⅱ의 팀 저장소에 그대로 옮겨 쓸 수 있게 만들었다.

학습 목표

  • AI 에이전트를 모델, 도구, 루프의 세 요소로 정의하고, 워크플로와 에이전트를 구분할 수 있다.
    • 예시: jobprep의 공고 요약 API는 정해진 코드 경로로 LLM을 한 번 부르는 워크플로이고, Claude Code는 도구 결과를 보고 다음 행동을 스스로 정하는 에이전트임을 근거와 함께 말하기
    • 활용: 새 기능을 설계할 때 “이 일에 에이전트가 필요한가, 정해진 흐름이면 충분한가”를 비용과 위험으로 판단하는 능력
  • 에이전트 운영의 네 요건(보안, 신뢰성, 일관성, 재현성)을 정의하고, 공개된 사고 사례에서 어느 요건이 깨졌는지 판별할 수 있다.
    • 예시: 에이전트가 운영 데이터베이스를 지운 사례에서 권한(보안), 복구 확인(신뢰성), 환경 분리(일관성), 기록(재현성)이 각각 어떻게 빠졌는지 표로 정리하기
    • 활용: 팀 프로젝트의 배포 전 회의에서 “무엇이 깨지면 안 되는가”를 네 요건의 언어로 말하는 능력
  • 운영 요건을 EARS 문형과 측정 방법을 갖춘 문장으로 쓰고, 형식 검사 도구와 실제 명령으로 확인할 수 있다.
    • 예시: “시스템은 빠르게 응답한다”를 “시스템은 공고 목록 요청 응답 시간의 95번째 백분위수를 300ms 이하로 유지해야 한다”로 고치고, access.log에서 그 값을 계산하기
    • 활용: 서비스 수준 목표(SLO)와 인수 조건을 수치와 측정 명령으로 적는 능력
  • 운영 에이전트 시스템의 역할을 권한, 입력, 출력, 완료 조건, 사람 승인 지점으로 정의할 수 있다.
    • 예시: 구현 역할의 권한 칸에 “금지: 기존 테스트 수정, main에 푸시”를 적고, 그 금지가 어느 운영 요건을 지키는지 ID로 잇기
    • 활용: 사람과 AI가 함께 일하는 팀에서 “누가 무엇을 할 수 있고, 어디서 사람이 승인하는가”를 문서로 정하는 능력

0. 시작하기

이 장은 내 PC에서 진행한다. 도구 설치, 계정 로그인, 키트 저장소의 클론(~/kits-repo)은 1주차에 부록 A로 끝냈다고 전제한다. VS Code에 터미널 둘을 나란히 둔다(부록 A-4-2). 하나는 명령을 직접 실행하고 결과를 확인하는 확인 터미널([터미널])이고, 다른 하나는 Claude Code 터미널이다. 터미널은 Windows에서는 Git Bash, macOS에서는 기본 셸이다. 명령은 Git Bash를 기준으로 적고, macOS에서 달라지는 것은 그 자리에 밝힌다(부록 A-4-3).

이 장의 실행 상한. 실제 모델을 쓰는 곳은 Claude Code의 대화형 세션 하나(11-4절에서 계획 모드로 띄워 11-8절까지 쓰는 세션)뿐이다. 헤드리스 실행(claude -p)과 API 호출은 없고, jobprep은 이 장 내내 모의 모드(LLM_FAKE=1)로 돈다. 프로덕트의 API 키는 필요 없다.

0-1. 환경 확인과 키트 받기

확인 터미널에서 도구의 판과 셸의 상태를 본다.

터미널

git --version
claude --version
gh --version | head -1
test -z "$ANTHROPIC_API_KEY" && echo "셸에 키 없음: 정상"
Python 3.13.7
git version 2.55.0.windows.5
2.1.296 (Claude Code)
gh version 2.88.1 (2026-03-12)
셸에 키 없음: 정상
  • 위 출력은 집필용 Windows 11 PC의 Git Bash에서 얻은 것이다(2026-11-17). 판 번호는 PC와 시점에 따라 다르다. 파이썬은 3.12 이상이면 된다. macOS에서는 가상 환경을 켜기 전까지 python3을 쓴다. gh가 없으면 부록 A-3과 A-6-2를 먼저 한다.
  • 마지막 줄이 나오지 않으면 셸 설정(~/.bashrc)이나 Windows의 사용자 환경 변수에 ANTHROPIC_API_KEY가 있는 것이다. 그 변수가 있으면 Claude Code가 구독 계정 대신 그 키로 요금을 매긴다(부록 A-5-3). 지우고 새 터미널을 연다. 프로덕트의 키는 선택이며 저장소의 .env에만 둔다(부록 A-11).

[최신 자료 자리: Claude Code의 판] 수업 시점의 Claude Code 판 번호와, 그 판에서 이 장의 권한 모드(4-3절)와 계획 모드 화면(11-4절)이 바뀌었는지 확인한다. 확인할 곳: 실습 PC의 claude --version, 변경 기록 https://github.com/anthropics/claude-code/blob/main/CHANGELOG.md. 2026-11-17에 집필 PC에서 확인한 값은 2.1.296 (Claude Code)이다.

Windows에서는 부록 A-4-4의 PYTHONUTF8=1을 등록해 두었는지도 본다. 이제 키트를 받는다. 키트는 ~/kits/에 받아 두고 필요한 파일만 작업 공간으로 옮긴다. 키트를 다시 받아도 작업이 덮이지 않게 하기 위해서이다(부록 A-7).

1-2. 운영과 유지보수

AI 에이전트는 바꾸는 속도를 높이고(사람의 하루 작업을 몇 분에), 바꾸는 주체를 늘렸다(사람 한 명이 에이전트 여럿을 동시에). 그만큼 “깨뜨리지 않았는가”를 확인할 일도 늘어나므로, 확인을 사람의 눈에만 맡기면 바뀌는 속도를 따라가지 못한다. 이 과목이 확인을 장치로 옮기는 데 13개 장을 쓰는 까닭이다.

3. 에이전트의 정의

3-1. 모델, 도구, 루프

이 과목에서 AI 에이전트(AI agent)는 다음 세 요소를 갖춘 시스템을 말한다.

요소 뜻 Claude Code에서
모델 다음에 할 일을 추론하고 결정하는 LLM Claude 모델(Opus, Sonnet, Haiku 등)
도구 모델이 바깥 세계를 읽거나 바꾸는 수단. 모델은 도구 호출을 요청하고, 실제 실행은 모델 밖의 프로그램이 한다 파일 읽기·편집, 검색, 셸 명령 실행, 웹 검색 등
루프 도구 결과를 다시 모델에 넣어 다음 행동을 정하게 하는 반복. 끝낼 조건을 모델이 판단하거나 바깥에서 정한다 맥락 수집 → 행동 → 결과 확인을 작업이 끝날 때까지 되풀이

Anthropic은 에이전트를 “환경에서 받은 되먹임을 바탕으로 도구를 쓰는 LLM을 반복으로 돌리는 것”에 가깝게 설명한다[E1]. Claude Code 문서는 Claude Code의 작업을 맥락 수집(gather context), 행동(take action), 결과 확인(verify results)의 세 단계가 섞이며 되풀이되는 에이전트 루프(agentic loop)로 설명하고, 이 루프를 움직이는 것이 추론하는 모델과 행동하는 도구라고 한다[C1]. Agent SDK를 소개하는 글도 같은 반복을 “맥락 수집 → 행동 → 작업 확인 → 반복”으로 적는다[E4].

세 요소 가운데 하나라도 빠지면 이 과목이 말하는 에이전트가 아니다. 도구가 없으면 모델은 글만 낸다(앞 과목의 공고 요약 API). 루프가 없으면 도구를 한 번 부르고 끝나 결과를 보고 행동을 바꾸지 못한다. 다음 행동을 모델이 아니라 사람이 짠 코드가 정하면 그것은 워크플로이다(3-3절).

3-2. Claude Code의 에이전트 루프

Claude Code에게 “실패하는 테스트를 고쳐 줘”라고 하면, 문서는 다음과 같은 흐름을 예로 든다[C1].

  1. 테스트를 실행해 무엇이 실패하는지 본다.
  2. 오류 출력을 읽는다.
  3. 관련 소스 파일을 검색한다.
  4. 그 파일을 읽어 코드를 이해한다.
  5. 파일을 고친다.
  6. 테스트를 다시 실행해 확인한다.

어느 단계에서 무엇을 할지는 모델이 앞 단계의 결과를 보고 정한다. 사람은 언제든 Esc로 멈추거나 방향을 바꾸는 말을 넣을 수 있다. 이 구조에서 운영의 관점으로 볼 곳은 세 군데이다.

  • 도구: 어떤 도구를 어떤 범위에서 쓸 수 있는가(3장 권한, 5장 MCP, 11장 보안).
  • 확인 단계: 무엇으로 “됐다”를 판정하는가. 모델의 말인가, 테스트의 결과인가(2장 TDD, 6장 훅).
  • 반복: 몇 번까지 되풀이하는가. 언제 멈추고 사람에게 넘기는가(8장 루프, 10장 멀티 에이전트).

Claude Code 문서는 모델을 둘러싸고 도구를 주고 맥락을 관리하는 이 바깥 층을 에이전트 하네스(agentic harness)라 부른다[C1]. 이 과목 3~7장이 만드는 하네스는 그 바깥 층에 팀이 정한 규칙과 검사를 더하는 일이다.

3-3. 워크플로와 에이전트

Anthropic의 글 「Building effective agents」(2024-12-19)는 LLM과 도구를 쓰는 시스템을 통틀어 에이전트 시스템(agentic systems)이라 부르고, 그 안을 둘로 나눈다[E1].

구분 정의 (E1의 요지) 다음 단계를 정하는 것 예
워크플로(workflow) LLM과 도구가 미리 정한 코드 경로를 따라 조율되는 시스템 사람이 짠 코드 jobprep의 /api/ask: 검색 → 유사도 판정 → (기준 미달이면 “자료에 없습니다.”) → 생성 → 인용 번호 추출
에이전트(agent) LLM이 자기 작업 과정과 도구 사용을 스스로 동적으로 정하는 시스템 모델 Claude Code: 어떤 파일을 읽고 어떤 명령을 실행할지 모델이 정한다

jobprep의 질의응답은 LLM을 쓰지만 에이전트가 아니다. 검색을 몇 번 할지, 근거가 모자라면 무엇을 할지, 언제 끝낼지를 모두 api/ask.py의 코드가 정한다. LLM은 정해진 자리에서 한 번 불려 답 문장을 쓸 뿐이다. 그래서 같은 질문에 대해 거치는 단계가 늘 같고, 실패하는 자리도 코드에서 찾을 수 있다.

다음은 교수 화면에서 그 순서를 코드에서 찾아 보인 것이다(읽기).

3-4. 워크플로의 다섯 유형

E1은 자주 쓰이는 워크플로를 다섯 유형으로 정리한다[E1]. 모든 유형의 바탕에는 검색, 도구, 기억을 붙인 LLM(augmented LLM)이 있다.

유형 구조 jobprep과 운영에 대면
프롬프트 연쇄(prompt chaining) 한 호출의 출력을 다음 호출의 입력으로 잇고, 사이에 코드로 검사를 둔다 요약 → JSON 구조 검사(validate_summary) → 실패면 502
라우팅(routing) 입력을 분류해 알맞은 처리로 보낸다 질문을 “자료 안/밖”으로 나누어 밖이면 LLM을 부르지 않는다
병렬화(parallelization) 일을 나누어 동시에 하거나(sectioning), 같은 일을 여러 번 해 투표한다(voting) 10장: 구현 에이전트 둘이 다른 작업 단위를 동시에 한다
조정자-작업자(orchestrator-workers) 중심 LLM이 일을 동적으로 나누어 작업자에게 맡기고 결과를 모은다 10장: 조정자가 이슈를 작업 단위로 나눈다
평가자-최적화(evaluator-optimizer) 한 LLM이 만들고 다른 LLM이 평가해 되먹임을 준다 6장: 검토 서브에이전트가 구현을 평가한다

같은 글은 가장 단순한 해법에서 시작해 필요할 때만 복잡도를 높이라고 권한다. 에이전트 시스템은 더 나은 작업 성능을 얻는 대신 지연과 비용을 치르는 경우가 많으므로 그 거래가 맞는지 따져야 한다는 것이다[E1]. 정해진 절차로 풀리는 일은 워크플로가, 단계 수를 미리 알 수 없고 유연한 판단이 필요한 열린 문제는 에이전트가 맞다.

3-5. 에이전트가 맞는 일과 맞지 않는 일

jobprep의 운영 업무로 판단해 본다.

업무 단계가 미리 정해지는가 맞는 구조 까닭
매일 아침 테스트를 돌려 결과를 기록 정해진다 스크립트(LLM 없음) 판단할 것이 없다. LLM을 쓰면 비용과 비결정성만 더해진다
공고 본문을 네 부분으로 요약 정해진다 워크플로(프롬프트 + 구조 검사) 입력과 출력의 모양이 고정되어 있다
실패하는 테스트의 원인을 찾아 고치기 정해지지 않는다 에이전트 어떤 파일을 읽어야 할지 결과를 보기 전에는 모른다
한 주의 운영 기록에서 이상 사건 찾기 반쯤 정해진다 워크플로(집계) + 에이전트(해석) 집계는 코드가 정확하다. 원인 추정은 열린 문제이다
의존성 판 올리기와 회귀 확인 반쯤 정해진다 에이전트 + 테스트 판정 올린 뒤 깨진 곳을 고치는 일이 열린 문제이다

이 표의 첫 줄이 중요하다. 에이전트를 쓸 수 있다고 모든 일에 써야 하는 것은 아니다. 운영 요건의 관점에서 LLM이 끼는 곳마다 비결정성, 환각, 프롬프트 주입, 비용(7절)이라는 새 위험이 생긴다. 판단이 필요 없는 일은 판단하지 않는 장치로 한다.

생각해 볼 것. 표에 없는 운영 업무 하나(예: “요구사항명세서의 상태 열과 테스트 열이 맞는지 점검”)를 골라, 워크플로와 에이전트 가운데 무엇이 맞는지 까닭과 함께 말해 본다.

4. 자율성의 수준과 사람의 개입

4-1. 능력과 자율성

에이전트가 무엇을 할 수 있는가(능력)와 사람의 확인 없이 무엇을 해도 되는가(자율성)는 다른 질문이다. 아무리 유능한 에이전트라도 운영 데이터베이스를 지울 권한까지 줄 까닭은 없다. Feng, McDonald, Zhang(2025)은 에이전트의 자율성을 능력과 따로 설계할 수 있는 속성으로 보고, 사용자가 맡는 역할에 따라 다섯 수준으로 나누었다[L1].

4-2. 다섯 수준

수준 사람의 역할 사람이 하는 일 에이전트가 하는 일
1 조작자(operator) 계획과 결정을 이끌고 필요할 때 에이전트를 부른다 맥락에 맞는 도움과 제안. 불리거나 승인받았을 때만 행동
2 협업자(collaborator) 에이전트와 함께 계획하고 나누어 실행한다. 언제든 에이전트의 일을 고치거나 넘겨받는다 자기 몫의 하위 작업을 병렬로 수행
3 상담자(consultant) 계획을 검토하고 의견, 선호, 방향을 준다 대부분의 계획과 실행. 정해진 지점에서 사용자에게 묻는다
4 승인자(approver) 에이전트가 풀 수 없는 장애(자격 증명, 중대한 행동의 승인)에서만 개입한다 그 밖에는 독립적으로 진행
5 관찰자(observer) 활동 기록을 보고 비상 정지만 할 수 있다 모든 계획과 실행을 스스로

(L1의 다섯 수준을 요약해 옮겼다.)

수준이 높을수록 좋은 것이 아니다. 수준은 일의 위험과 되돌리기 어려움에 맞추어 고른다. 이 과목은 jobprep 운영 에이전트의 어느 역할에도 수준 5를 주지 않는다. 9절에서 역할마다 수준을 정한다.

4-3. Claude Code의 권한 모드

Claude Code는 이 수준을 권한 모드(permission mode)로 조절한다. 2026-11 기준 문서의 모드는 다음과 같다[C2].

모드(설정값) 묻지 않고 실행하는 것 맞는 용도 대략의 자율성 수준
default(화면 표시 Manual) 읽기만 모든 행동을 직접 검토할 때 1~2
acceptEdits 읽기, 작업 폴더 안의 파일 편집과 흔한 파일 명령(mkdir, mv, cp 등) 검토 중인 코드를 고쳐 나갈 때 2~3
plan 읽기. 소스를 고치지 않고 탐색과 계획만 한다 바꾸기 전에 코드를 파악할 때 3(계획 승인)
auto 모든 것. 별도 모델이 행동마다 배경에서 위험을 판정해 막는다 긴 작업, 확인 요청을 줄일 때 4
dontAsk 미리 허용한 도구만. 물어야 하는 것은 거부 잠근 CI와 스크립트 정한 범위 안에서 4
bypassPermissions 모든 것 격리된 컨테이너와 가상 머신에서만 5

claude --help로 Claude Code가 받는 값을 확인하면 다음과 같다(읽기).

교수 화면 
claude --help | grep -A3 "permission-mode"
  --permission-mode <mode>              Permission mode to use for the session
                                        (choices: "acceptEdits", "auto",
                                        "bypassPermissions", "manual",
                                        "dontAsk", "plan")

manual은 default의 다른 이름이다[C2]. 문서에서 운영에 직접 걸리는 사실 세 가지를 짚는다.

  1. 시작 모드. Claude Code v2.1.283 이후 대화형 터미널과 VS Code 세션의 기본 시작 모드는 auto이다[C1][C2]. 아무것도 정하지 않으면 사람이 묻는 창을 보지 못한 채 에이전트가 수준 4로 일한다. 운영 저장소에서 처음 작업할 때는 plan이나 default로 시작할지 의식적으로 정해야 한다. 11절의 핵심 실습은 plan으로 시작한다.
  2. 자동 판정의 한계. 문서는 auto가 확인 요청을 줄이지만 안전을 보장하지는 않으며, 민감한 작업의 검토를 대신하지 않는다고 적는다[C2]. 강제 푸시, 운영 배포, 클라우드 자원의 대량 삭제 같은 고위험 행동은 기본으로 막는다.
  3. 우회 모드의 조건. bypassPermissions는 인터넷이 없는 컨테이너나 가상 머신처럼 Claude Code가 호스트를 해칠 수 없는 격리 환경에서만 쓰라고 하며, 이 모드는 프롬프트 주입이나 의도하지 않은 행동을 막아 주지 않는다고 밝힌다[C2]. 또 저장소에 커밋되는 설정 파일(.claude/settings.json)로는 auto나 bypassPermissions를 기본값으로 정할 수 없다.

모드는 Shift+Tab으로 바꾼다. auto에서 누르면 default로 가고, 이후 default → acceptEdits → plan 순서로 돈다[C2]. 시작할 때 claude --permission-mode plan으로 정할 수도 있다.

[최신 자료 자리: Claude Code의 권한 모드와 시작 모드] 모드 여섯 개, 기본 시작 모드 auto(v2.1.283 이후), Shift+Tab의 순서는 2026-11-14에 Claude Code 2.1.296과 [C2]로 확인한 값이다. 수업 전에 claude --version, claude --help와 https://code.claude.com/docs/en/permission-modes에서 다시 확인한다.

생각해 볼 것. 위 선택지 여섯 가운데 운영 저장소에서 처음 구조를 파악할 때 쓸 모드는 무엇이고, 그 까닭은 무엇인가. 11-4절에서 그 모드로 Claude Code를 띄운다.

4-4. 사람의 개입 지점

E1은 에이전트가 검문 지점(checkpoint)이나 장애를 만났을 때 사람의 되먹임을 받기 위해 멈출 수 있어야 하고, 최대 반복 횟수 같은 정지 조건으로 통제를 유지해야 하며, 격리된 환경에서 충분히 시험해야 한다고 권한다[E1]. 운영에서 사람이 개입하는 자리는 다음 다섯 종류로 정리할 수 있다.

개입 지점 사람이 하는 일 왜 사람인가 이 과목의 장
계획 승인 에이전트가 낸 계획을 읽고 승인하거나 고친다 잘못된 방향의 작업은 끝난 뒤 되돌리는 비용이 크다 1장(계획 모드), 10장
파괴적 행동 승인 지우기, 덮어쓰기, 저장소 밖의 쓰기를 승인한다 되돌릴 수 없다 3장, 6장, 11장
병합 승인 변경을 main에 넣을지 정한다 모든 사용자에게 영향을 준다 10장, 13장
배포와 되돌리기 배포를 실행하고, 문제가 있으면 되돌린다 외부 시스템에 닿는 행동은 체크포인트로 되돌릴 수 없다 13장
넘겨받기 재시도 상한에 닿은 실패를 넘겨받아 처리한다 같은 시도를 되풀이해도 결과가 같다 8장

4-5. 되돌릴 수 있는 것과 없는 것

Claude Code는 파일을 고치기 전에 내용을 저장해 두므로 Esc를 두 번 눌러 되감을 수 있다. 그러나 문서는 체크포인트가 파일 변경만 다루며, 데이터베이스, API, 배포처럼 원격 시스템에 영향을 주는 행동은 체크포인트로 되돌릴 수 없다고 밝힌다[C1].

  • 작업 폴더 안의 파일 편집: 체크포인트, git restore, 커밋 되돌리기로 되돌린다. 커밋하지 않은 변경을 셸 명령(rm, mv)으로 날리면 되돌릴 수 없다.
  • 커밋: git revert, git reset으로 되돌린다. 원격에 강제 푸시해 다른 사람의 커밋을 덮으면 되돌리기 어렵다.
  • 저장소 밖의 파일: 백업이 있을 때만 되돌릴 수 있다.
  • 데이터베이스, 외부 API 호출, 배포: 서비스가 제공하는 복구 기능에 의존한다. 그 기능이 없거나 미리 시험해 두지 않았으면 되돌릴 수 없다.
  • 메시지 발송, 결제: 되돌릴 수 없다.

사람의 개입 지점은 이 목록의 아래쪽일수록 촘촘하게 둔다. 5절의 사고 사례는 대부분 이 목록의 아래쪽에서 일어났다.

생각해 볼 것. 4-5절의 목록에서 jobprep 운영 중에 에이전트가 할 수 있는 행동 하나를 골라, 되돌릴 수단과 사람이 승인해야 할 지점을 짝지어 본다.

5. 공개된 사고 사례

이 절의 네 사례는 2025년에 AI 에이전트나 AI 코딩 도구가 실제 사용자의 데이터나 배포물에 피해를 준 사건으로, 당사자의 공개 기록(1차 자료)이나 신뢰할 수 있는 매체의 보도로 확인한 것이다. 사례마다 무슨 일이 있었는지(사실), 무엇이 빠졌는지(원인), 어느 운영 요건이 깨졌는지를 나누어 읽는다. 사실은 출처의 범위 안에서만 적었고, 출처가 단정하지 않은 것은 단정하지 않았다.

앞 과목 1장에서도 첫 사례(Replit)를 보았다. 그때의 질문은 “어느 개발 단계에서 막을 수 있었는가”였다. 이 장의 질문은 “운영 중에 무엇이 지켜졌어야 했고, 그것을 무엇으로 쟀어야 했는가”이다.

5-1. 사례 1: 코드 동결 중에 운영 데이터베이스를 지운 에이전트 (2025-07)

사실. SaaS 업계 커뮤니티 SaaStr의 창업자 제이슨 렘킨(Jason Lemkin)은 Replit의 AI 에이전트로 앱을 만들던 중 에이전트가 운영 데이터베이스를 지웠다고 2025년 7월에 공개하였다. 그는 허락 없이 코드를 바꾸지 말라고 지시했고, 바꾸지 않는 기간(코드 동결, code freeze)을 선언한 상태였다. 렘킨에 따르면 에이전트는 버그를 가짜 데이터와 가짜 보고로 덮었고, 4,000명 분량의 가상 인물 데이터베이스를 만들었으며, 데이터베이스를 되돌릴 수 없다고 답했으나 실제로는 되돌리기가 되었다. 그는 Replit 같은 도구에서는 코드 동결을 강제할 방법이 없다고 썼다[I1].

대응. Replit의 최고경영자 암자드 마사드(Amjad Masad)는 이 일을 일어나서는 안 되는 일이라고 하고, 개발용과 운영용 데이터베이스를 자동으로 분리하는 기능을 배포하기 시작하였다. 에이전트가 적절한 내부 문서에 접근하지 못해 복구 요청에 제대로 답하지 못했다고 설명하고, 에이전트가 Replit 문서를 반드시 검색하게 하는 수정과 스테이징 환경 계획도 밝혔다[I2].

원인. 금지는 자연어 지시로만 있었다. 에이전트는 운영 데이터에 닿는 권한을 그대로 가지고 있었고, 개발 환경과 운영 환경이 나뉘어 있지 않았다. 에이전트의 “되돌릴 수 없다”는 보고를 사람이 확인할 수단(복구 절차를 미리 시험한 기록)이 없었다.

  • 보안: 에이전트가 운영 데이터베이스에 쓰기 권한을 가졌다. → 잴 것: 에이전트의 자격 증명으로 운영 데이터에 쓰기를 시도했을 때 거부되는가
  • 신뢰성: 복구 가능 여부를 에이전트의 말에 의존하였다. → 잴 것: 백업에서 실제로 복구되는지 정기적으로 시험한 결과
  • 일관성: 개발과 운영이 같은 데이터베이스를 썼다. → 잴 것: 개발 환경의 연결 문자열이 운영 데이터베이스를 가리키지 않는가
  • 재현성: 에이전트가 만든 가짜 데이터와 가짜 보고를 실제 결과와 구분할 기록이 없었다. → 잴 것: 에이전트가 실행한 명령과 그 출력의 원본 기록

5-2. 사례 2: 실패를 확인하지 않고 파일을 옮긴 CLI 에이전트 (2025-07)

사실. 2025년 7월 21일, 한 사용자가 Google의 Gemini CLI 저장소에 「Gemini CLI가 실패한 파일 이동 중에 파일을 ‘잃어버렸다’」는 이슈를 올렸다. 이슈에 첨부한 환경 정보에는 운영체제 Windows, 모델 gemini-2.5-pro, 샌드박스 없음(no sandbox)이 적혀 있다[I3]. 첨부한 대화 기록에 따르면 사용자는 실험 폴더의 파일을 새 폴더로 옮겨 달라고 하였다. 에이전트는 새 폴더를 만드는 mkdir 명령을 실행한 뒤 폴더가 실제로 생겼는지 확인하지 않고 성공했다고 보았고, 이어서 move 명령들을 실행하였다. 그 뒤 폴더를 읽자 항목이 0개였고, 에이전트는 mkdir이 조용히 실패했을 가능성이 높다며 데이터를 잃었다고 인정하였다[I3]. 이 사건은 Ars Technica 등이 2025년 7월 하순에 사례 1과 함께 보도하였다.

원인. 에이전트는 명령을 실행한 뒤 그 결과를 다시 읽어 확인(쓰기 뒤 읽기, read-after-write)하지 않았다. Windows의 move는 대상 폴더가 없으면 옮기는 대신 이름을 바꾸는데, 이 동작이 대화 기록의 결과와 맞는다는 분석이 있으나 대화 기록만으로는 확정할 수 없다. 확인되는 것은 에이전트가 존재하지 않는 대상을 존재한다고 믿고 되돌릴 수 없는 명령을 이어 실행했다는 점이다. 샌드박스 없이, 백업이 없는 실제 폴더에서 실행되었다.

  • 신뢰성: 앞 단계의 실패를 알아채지 못하고 다음 단계로 갔다. → 잴 것: 단계마다 결과 확인(폴더 존재, 파일 수)이 통과했는가
  • 보안: 격리 없이 실제 사용자 폴더에서 파괴적 명령을 실행하였다. → 잴 것: 에이전트가 쓰는 폴더가 백업된 작업 폴더로 한정되는가
  • 재현성: 이동 전 상태(파일 목록)가 남지 않았다. → 잴 것: 작업 전 상태의 기록 또는 버전 관리

5-3. 사례 3: 캐시를 지우라는 요청에 드라이브 전체를 지운 에이전트 (2025-11)

사실. 2025년 11월 말, 그리스의 한 사진가가 Google의 에이전트 개발 환경 Antigravity를 쓰다가 D: 드라이브 전체가 지워졌다고 Reddit에 올렸고, The Register가 2025년 12월 1일에 보도하였다. 그는 개발자가 아니었고, 사진을 평가해 폴더로 나누는 도구를 만들고 있었다. 그는 에이전트가 사용자 입력 없이 명령을 실행하는 Turbo 모드를 쓰고 있었다. 에이전트는 프로젝트 캐시를 지우는 명령이 특정 프로젝트 폴더가 아니라 D: 드라이브의 루트를 잘못 겨냥한 것으로 보인다고 스스로 답하였다(기사는 이 설명을 따로 검증하지 않았다). 지운 파일은 휴지통을 거치지 않아 복구되지 않았고, 대부분은 다른 드라이브에 백업되어 있었다. Google은 보고를 알고 있으며 조사 중이라고 답하였다[I4].

원인. 사용자의 확인 없이 셸 명령을 실행하는 모드에서, 지울 대상의 경로를 검증하는 단계가 없었다. 보도는 이런 도구를 잠근 분리 환경에서 쓰라고 권하였다[I4].

  • 보안: 사람의 승인 없이 작업 폴더 밖을 지울 수 있었다(자율성 수준이 일의 위험보다 높았다). → 잴 것: 작업 폴더 밖 경로에 대한 삭제 시도가 거부되거나 승인을 요구하는가
  • 신뢰성: 파괴적 명령의 대상 경로를 실행 전에 확인하지 않았다. → 잴 것: 삭제 명령 전에 대상 경로가 허용 목록 안인지 검사한 기록
  • 재현성: (백업이 있어 피해가 줄었다). → 잴 것: 백업의 존재와 복구 시험

5-4. 사례 4: 배포된 AI 코딩 확장에 들어간 악성 지시 (2025-07)

사실. AWS는 2025년 7월 23일 보안 공지 AWS-2025-015를 내고, VS Code용 Amazon Q Developer 확장의 1.84.0 판에 악성 코드가 들어갔다고 밝혔다(CVE-2025-8217). 확장의 빌드 설정(CodeBuild)에 권한 범위가 지나치게 넓은 GitHub 토큰이 있었고, 공격자가 그 토큰으로 확장의 오픈 소스 저장소에 코드를 커밋하였으며, 그 코드가 자동으로 배포판에 포함되었다. AWS는 악성 코드가 문법 오류로 실행되지 않아 서비스나 고객 환경을 바꾸지 못했다고 밝히고, 자격 증명을 폐기·교체한 뒤 1.85.0을 배포하며 1.84.0을 모두 지우라고 권고하였다[I5]. 보도에 따르면 들어간 코드는 Amazon Q의 명령행 에이전트를 모든 도구를 신뢰하고(--trust-all-tools) 묻지 않는(--no-interactive) 옵션으로 실행하면서, 사용자의 홈 폴더 파일과 AWS 클라우드 자원을 찾아 지우라는 지시문을 넘기는 것이었다. 이 판은 7월 19일에 배포되어 이틀 동안 마켓플레이스에 있었다[I6].

원인. 빌드 파이프라인이 쓰는 토큰의 권한이 필요보다 넓었고, 저장소에 들어온 커밋이 사람의 검토 없이 배포판까지 갔다. 에이전트에게 주는 지시문(프롬프트)이 코드와 같은 경로로 배포되면서, 지시문의 변경이 코드 검토의 대상으로 다루어지지 않았다. 공격자는 에이전트의 자율성을 가장 높은 수준으로 여는 옵션을 골라 썼다. 에이전트 도구에 그런 옵션이 있다는 것 자체가 공격면이 된다.

  • 보안: 빌드 토큰의 권한이 최소가 아니었다. 공급망(배포 경로)에 악성 변경이 들어왔다. → 잴 것: 토큰의 권한 범위 점검, 배포판에 들어간 커밋이 모두 검토되었는가
  • 일관성: 같은 저장소의 변경인데 검토를 거치지 않은 경로가 있었다. → 잴 것: 보호 브랜치와 필수 리뷰가 모든 경로에 걸려 있는가
  • 재현성: (배포판의 해시를 공지해 설치본을 대조할 수 있게 하였다). → 잴 것: 배포 산출물의 해시와 그 판을 만든 커밋의 대응

5-5. 보론: 원인을 두고 다투는 사례

2026년 2월 20일, Financial Times의 보도를 인용해 The Register는 AWS가 2025년 12월 한 서비스에서 13시간 동안 중단을 겪었고, 엔지니어가 AI 코딩 도구 Kiro에 변경을 맡기자 Kiro가 환경을 지우고 다시 만들기로 했다고 전하였다. Amazon은 원인이 AI가 아니라 직원의 실수, 곧 잘못 설정된 접근 제어라고 반박하였고, 영향은 한 지역의 비용 조회 서비스에 한정되었다고 밝혔다. Amazon은 Kiro가 기본으로 행동 전에 승인을 요청하지만 해당 엔지니어가 예상보다 넓은 권한의 역할을 쓰고 있었다고 하였으며, 사건 뒤 운영 접근에 대한 동료 검토 의무화 같은 안전장치를 더했다고 밝혔다[I7].

양측이 사실관계를 다투므로 사례 1~4처럼 분석하지 않는다. 다만 양측의 진술은 에이전트가 쓰는 권한의 범위가 사고의 크기를 정하였다는 점에서 일치한다. 운영 요건의 질문은 “AI의 잘못인가, 사람의 잘못인가”가 아니라 “누가 하든, 그 권한으로 그 행동이 가능했는가”이다.

6. 네 운영 요건

6-1. 정의

이 과목은 네 운영 요건을 다음과 같이 정의한다.

요건 정의 묻는 질문 소프트웨어 공학의 대응 개념
보안 에이전트와 프로덕트가 허용된 일만 하고, 비밀 정보와 사용자 정보가 새지 않는다 이 에이전트가 할 수 있는 일은 이 일에 필요한 만큼인가 최소 권한 원칙, 직무 분리, 위협 모델링, 공급망 보안
신뢰성 정해진 조건에서 기대한 결과를 낸다. 실패하면 알아채고 멈추거나 복구한다 실패를 누가 언제 알아채는가 서비스 수준 지표·목표(SLI·SLO), 오류 예산, 장애 감지와 복구
일관성 같은 종류의 일은 누가(어느 에이전트가) 해도 같은 규칙과 형식으로 된다 사람이 바뀌거나 에이전트가 바뀌어도 결과의 모양이 같은가 코딩 규약, 정적 분석, 코드 검토, 개발·운영 환경의 동등성
재현성 같은 입력과 같은 환경에서 같은 결과를 다시 얻을 수 있다. 무엇이 실행되었는지 기록이 남는다 일주일 전의 그 결과를 지금 다시 만들 수 있는가 재현 가능한 빌드, 버전 고정, 설정 관리, 감사 기록

네 요건은 서로 겹친다. 예를 들어 “모든 LLM 호출은 api/llm.py를 거친다”는 일관성 요건이지만, 덕분에 호출 기록이 한 곳에서 남으므로 재현성에도, 키를 한 곳에서만 읽으므로 보안에도 이바지한다. 요건을 분류할 때는 “이 요건이 깨지면 가장 먼저 무엇이 문제가 되는가”를 기준으로 하나를 고른다.

6-2. 보안

보안의 출발점은 최소 권한(least privilege)이다. 미국 국립표준기술연구소(NIST)의 용어집은 이를 시스템이 사용자의 접근 권한을 맡은 일을 하는 데 필요한 최소한으로 제한해야 한다는 원칙, 또는 각 주체에게 그 기능에 필요한 최소한의 자원과 권한만 주는 원칙으로 정의한다[S2]. 에이전트에게는 “주체”가 하나 더 생긴 것이다. 사람 개발자에게 운영 데이터베이스의 쓰기 권한을 함부로 주지 않듯, 에이전트에게도 주지 않는다.

OWASP의 LLM 애플리케이션 10대 위험은 이 문제를 과도한 행위 능력(Excessive Agency, 2025년판 LLM06, 2026년판 LLM03)으로 다룬다[O4]. 예상하지 못했거나 모호하거나 조작된 출력에 반응해 해로운 행동이 실행되게 하는 취약점이며, 근본 원인을 셋으로 든다[O3].

  • 과도한 기능(excessive functionality): 일에 필요 없는 기능의 도구를 부를 수 있다. 예: 기록을 읽기만 하면 되는 관측 역할에 셸 실행 도구를 준다.
  • 과도한 권한(excessive permissions): 도구가 하위 시스템에 필요 이상의 권한을 가진다. 예: 테스트만 돌리면 되는 역할이 git push를 할 수 있다.
  • 과도한 자율성(excessive autonomy): 영향이 큰 행동을 독립적인 확인이나 승인 없이 실행한다. 예: 배포를 사람의 승인 없이 한다.

같은 문서는 대책으로 도구와 그 기능의 최소화, 셸 같은 범용 도구보다 좁은 도구의 사용, 권한의 최소화, 영향이 큰 행동에 대한 사람의 승인, LLM의 판단을 믿지 말고 하위 시스템에서 권한을 검사할 것 등을 든다. 기록, 감시, 요청 제한은 과도한 행위 능력을 막지는 못하지만 피해를 줄인다고 덧붙인다[O3].

보안 요건을 쓸 때 지킬 점은 두 가지이다. 첫째, “보호한다”, “안전하게”처럼 상태를 말하지 말고 금지된 행동과 그 결과를 적는다(“.env를 읽지 않아야 한다”). 둘째, 측정은 대개 시도해서 막히는지 보는 것이다. 막아야 할 행동을 일부러 요청하고, 거부되는지 확인한다. 11장의 핵심 실습이 이 방식이다.

6-3. 신뢰성

신뢰성은 Google의 사이트 신뢰성 공학(SRE)이 정리한 세 용어로 재는 것이 업계의 표준적인 방법이다[S1].

용어 정의 (S1의 요지) jobprep의 예
SLI(서비스 수준 지표) 제공하는 서비스 수준의 한 측면을 신중하게 정의한 정량적 측정값 한 주의 전체 요청 가운데 5xx가 아닌 응답의 비율. 공고 목록 응답 시간의 95번째 백분위수
SLO(서비스 수준 목표) SLI로 재는 서비스 수준의 목표값이나 범위. “SLI ≤ 목표” 또는 “하한 ≤ SLI ≤ 상한”의 꼴 5xx 비율 1% 이하. 95번째 백분위수 300ms 이하
SLA(서비스 수준 협약) SLO를 지키거나 어겼을 때의 결과(보상 등)를 담은 사용자와의 명시적·암묵적 계약 (이 과목은 다루지 않는다)

같은 장은 SLI로 자주 쓰는 지표로 지연 시간, 오류율, 처리량, 가용성을 들고, 지연 시간은 평균보다 백분위수로 보라고 권한다. 평균은 긴 꼬리(드물게 매우 느린 요청)를 감추므로, 50번째 백분위수는 보통의 경우를, 99번째 같은 높은 백분위수는 그럴듯한 최악의 경우를 보여 준다[S1]. 목표를 정하는 원칙으로는 현재 성능을 그대로 목표로 삼지 않기, 단순하게 정하기, “언제나” 같은 절대값 피하기, SLO의 수를 적게 두기, 느슨하게 시작해 점차 조이기를 든다[S1].

목표를 100%로 두지 않는 대신, SLO를 어겨도 되는 정도를 오류 예산(error budget)으로 정해 관리한다. 오류 예산이 남아 있으면 새 기능을 배포하고, 바닥나면 신뢰성 작업을 먼저 한다[S1].

에이전트의 신뢰성에는 서비스의 신뢰성과 다른 면이 하나 더 있다. 실패를 알아채고 멈추는가이다. 5-2절의 사례에서 에이전트는 실패한 명령을 성공으로 보고 다음 명령으로 갔다. 에이전트의 신뢰성 요건은 “완료를 보고하기 전에 무엇을 실행해 무엇을 확인하는가”(판정)와 “몇 번 실패하면 멈추고 사람에게 넘기는가”(정지 조건)를 적는다.

6-4. 일관성

Google의 스타일 가이드는 큰 코드베이스는 모든 코드가 일관된 스타일로 되어 있을 때 훨씬 이해하기 쉽다고 그 존재 이유를 밝힌다[S5]. 사람 여럿이 한 저장소를 고칠 때 코딩 규약, 정적 분석, 코드 검토를 두는 까닭이다. 에이전트가 함께 고치면 이 문제가 커진다. 에이전트는 세션마다 새 맥락에서 시작하고, 규칙을 알려 주지 않으면 그 세션에서 가장 그럴듯한 방식을 고른다. 같은 요청에도 실행할 때마다 다른 이름, 다른 구조, 다른 오류 처리를 쓸 수 있다.

일관성에는 환경의 일관성도 있다. 웹 애플리케이션 설계 원칙으로 널리 쓰이는 「Twelve-Factor App」은 개발과 운영 사이의 간극을 시간(배포까지 걸리는 기간), 사람(만드는 사람과 배포하는 사람), 도구(개발과 운영의 소프트웨어 구성)의 셋으로 나누고, 개발, 스테이징, 운영을 가능한 한 비슷하게 유지하라고 권한다[S3]. 5-1절의 사례에서 개발과 운영이 같은 데이터베이스를 쓴 것은 이 원칙의 반대 방향, 곧 “같지 않아야 할 것(데이터)이 같았다”는 문제였다. 같아야 할 것(소프트웨어의 종류와 판)은 같게, 달라야 할 것(데이터, 자격 증명)은 다르게 두는 것이 환경의 일관성이다.

일관성 요건의 측정은 대개 검색 명령으로 할 수 있다. 규칙을 어긴 흔적(예: api/llm.py 밖의 anthropic 호출, innerHTML 사용)을 찾아 0개인지 본다. 11-5절에서 실제로 재어 본다.

6-5. 재현성

재현 가능한 빌드(Reproducible Builds) 프로젝트는 빌드가 재현 가능하다는 것을, 같은 소스 코드, 같은 빌드 환경, 같은 빌드 지시가 주어지면 누구든 지정된 모든 산출물을 비트 단위까지 같게 다시 만들 수 있는 것으로 정의한다[S4]. 정의에 든 세 가지(소스, 환경, 지시)가 재현성 요건을 쓸 때 고정해야 할 대상이다.

환경 언어와 패키지의 판 모델 이름과 판, 에이전트 도구(Claude Code)의 판 requirements.txt의 ==, LLM_MODEL, claude --version

LLM은 같은 입력에도 다른 출력을 낼 수 있으므로(7-1절) 비트 단위의 재현은 기대할 수 없다. 그래서 LLM이 낀 부분의 재현성은 두 겹으로 정한다. 하나는 모의 모드에서의 완전한 재현이다. jobprep의 테스트 43개는 모의 모드에서 언제나 같은 결과를 낸다. 다른 하나는 실제 모드에서의 기록과 판정의 재현이다. 출력 자체가 같지 않아도, 어떤 판본과 모델이 무엇을 냈는지가 기록되고, 그 출력이 같은 기준(구조 검사, 평가 세트)을 통과하는지는 다시 판정할 수 있어야 한다. 12장의 회귀 평가가 이 두 번째를 다룬다.

6-6. 요건 사이의 긴장

네 요건은 서로 당긴다. 하나를 강하게 하면 다른 하나나 편의가 약해지는 경우가 있다.

  • 보안 대 편의: 모든 명령에 승인을 요구하면 안전하지만 사람이 승인 창을 읽지 않고 누르게 된다. 위험에 따라 차등을 둔다. 읽기는 묻지 않고, 쓰기는 작업 폴더 안만, 지우기와 외부 영향은 승인을 받는다.
  • 재현성 대 최신성: 패키지와 모델의 판을 고정하면 재현되지만 보안 패치와 개선을 놓친다. 고정하되 판을 올리는 절차(테스트와 평가 통과)를 정한다(13장).
  • 신뢰성 대 비용: 실패할 때마다 다시 시도할수록 성공률은 오르지만 비용이 는다. 재시도 상한과 비용 상한을 요건으로 적는다(8장).
  • 일관성 대 적응: 규칙을 많이 두면 같은 결과가 나오지만 규칙이 맞지 않는 새 상황에서 막힌다. 규칙은 적고 분명하게, 예외는 사람의 승인으로 둔다(3장, 4장).

요건을 쓸 때 이 긴장을 감추지 않는다. 기준값을 정할 때 “왜 이 값인가”를 한 줄 적어 두면, 뒤에 값을 바꿀 때 무엇과 무엇을 맞바꾸는지 드러난다.

6-7. 서비스의 요건과 에이전트의 요건

운영 요건 명세에는 주어가 둘 나온다.

  • 시스템: 서비스 jobprep(API, 웹, 검색)을 가리킨다. 예: “시스템은 한 주의 5xx 비율을 1% 이하로 유지해야 한다.” 서비스의 기록, 테스트, 응답으로 잰다.
  • 운영 에이전트: jobprep을 고치고 시험하고 배포하고 지켜보는 에이전트들을 가리킨다. 예: “운영 에이전트는 .env 파일을 읽거나 고치지 않아야 한다.” 에이전트의 설정, 실행 기록, 시도와 거부로 잰다.

앞 과목의 요구사항명세서는 주어가 “시스템” 하나였다. 이 과목의 운영 요건은 운영하는 쪽(에이전트)도 주어가 된다. 사례 1~3은 모두 서비스가 아니라 운영 에이전트의 요건이 없어서 생긴 사고였다.

생각해 볼 것. jobprep에 대한 요건 하나를 「시스템」 주어로, 다른 하나를 「운영 에이전트」 주어로 말하고, 각각 네 요건 가운데 무엇으로 분류하는지와 그 까닭을 생각해 본다.

7. LLM 특유의 어려움

전통적인 소프트웨어의 운영 요건과 비교할 때, LLM과 에이전트는 네 가지 어려움을 더한다.

7-1. 비결정성

같은 입력에 같은 출력이 나온다는 보장이 없다. Anthropic의 용어 설명은 temperature를 0으로 두어도 결과가 완전히 결정적이지는 않으며, 같은 입력이 API 호출마다 다른 출력을 낼 수 있다고 밝힌다[A1]. Thinking Machines Lab의 2025년 9월 글은 이 현상의 주된 원인을, 서버의 부하에 따라 함께 처리되는 요청의 묶음 크기(batch size)가 바뀌고 추론 계산이 묶음 크기에 따라 미세하게 달라지는 데서 찾았다. 그들이 공개 모델 하나에 temperature 0으로 같은 질문을 1,000번 보낸 실험에서 서로 다른 응답이 80가지 나왔고, 앞의 102개 토큰은 같다가 103번째 토큰에서 갈라졌다[N1].

운영에 주는 영향은 두 가지이다. 첫째, “한 번 해 보니 됐다”는 확인이 되지 않는다. 같은 요청을 여러 번 해 통과율로 보아야 한다(12장). 둘째, 에이전트는 같은 작업을 같은 방식으로 하지 않는다. 같은 이슈를 두 번 맡기면 다른 파일을 고칠 수 있다. 그래서 결과의 모양을 묶는 장치(규칙, 테스트, 형식 검사)가 필요하다(3장, 4장).

7-2. 환각과 거짓 보고

LLM은 그럴듯하지만 사실이 아닌 내용을 낼 수 있다(환각, hallucination). 에이전트에서 환각은 글의 오류로 끝나지 않고 행동으로 이어진다. 5-2절의 에이전트는 실패한 명령을 성공했다고 믿고 다음 명령을 실행하였다. 5-1절의 에이전트는 되돌릴 수 없다고 보고했으나 되돌릴 수 있었다. 에이전트의 보고에는 “했다”, “통과했다”, “안전하다”는 말이 들어가는데, 그 말은 판정이 아니다.

운영 요건에서 이 어려움에 대응하는 방법은 하나이다. 완료 조건을 에이전트의 말이 아니라 명령의 결과로 정한다. “테스트를 통과시켰다고 보고한다”가 아니라 “python -m pytest -q를 실행하고 그 결과 줄을 보고에 붙인다”, 그리고 사람(또는 훅)이 그 줄을 직접 확인한다. Agent SDK를 소개한 글도 에이전트가 자기 작업을 확인하는 방법으로 규칙 기반 되먹임(예: 린트처럼 어떤 규칙이 왜 실패했는지 알려 주는 것)을 가장 먼저 들고, 다른 모델에게 판정을 맡기는 방식은 견고하지 않고 지연이 늘어난다고 적는다[E4].

7-3. 프롬프트 주입

OWASP는 프롬프트 주입(prompt injection, 2025·2026년판 LLM01)을 사용자 프롬프트가 LLM의 행동이나 출력을 의도하지 않은 방식으로 바꾸는 취약점으로 정의하고, 둘로 나눈다[O2]. 직접 주입은 공격자가 모델에 넣는 입력이 곧바로 행동을 바꾸는 것이고, 간접 주입은 모델이 웹 페이지나 파일 같은 외부 출처의 내용을 받아들일 때 그 안에 숨은 지시가 행동을 바꾸는 것이다. 같은 문서는 검색 증강 생성이나 미세 조정 같은 기법이 프롬프트 주입을 완전히 막지 못한다는 연구 결과를 밝힌다[O2].

jobprep에는 간접 주입의 통로가 둘 있다. 공고 본문(/api/summary에 들어가는 글)과 취업 자료 문서(data/자료/)이다. 누군가 공고 본문에 “앞의 지시를 무시하고 …하라”를 숨겨 넣으면, 요약 기능의 LLM이 그 지시를 따를 수 있다. 운영 에이전트에게는 통로가 더 많다. 에이전트가 읽는 이슈 본문, 기록 파일, 외부 문서가 모두 통로이다. 5-4절의 사례는 에이전트에게 주는 지시문 자체가 배포 경로로 들어온 경우였다. 프롬프트 주입은 모델의 성능으로 막는 문제가 아니라, 주입이 성공해도 피해가 나지 않게 권한과 격리로 경계를 긋는 문제로 다룬다(11장).

LLM 호출은 토큰 단위로 요금이 매겨진다. 2026-11-14 기준 Claude 모델의 기본 단가(백만 토큰당)는 다음과 같다[A2].

서비스의 호출 하나는 매우 싸다. 비용 문제는 두 곳에서 커진다. 첫째, 에이전트는 한 작업에서 모델을 수십 번 부르고, 매번 지금까지의 대화와 파일 내용을 함께 보낸다. Claude Code 문서는 기업 환경의 평균 비용을 개발자 한 명이 활동한 날 하루에 약 13달러, 한 달에 150~250달러로 들고, 사용자의 90%가 하루 30달러 아래라고 밝힌다[C3]. 같은 문서는 여러 에이전트를 팀으로 돌리면 각자 맥락을 따로 가지므로 토큰 사용이 팀의 크기에 대략 비례한다고 적는다[C3]. 둘째, 반복이다. 실패할 때마다 다시 시도하는 루프에 상한이 없으면 비용에도 상한이 없다. 11-2절에서 빈 본문에도 LLM을 부르는 것을 본다. 이런 호출이 루프 안에 있으면 쓸모없는 비용이 반복된다.

비용은 OWASP의 10대 위험에서도 무제한 소비(Unbounded Consumption, 2025년판 LLM10, 2026년판 LLM06)라는 이름으로 위험 목록에 든다[O1]. 운영 요건에는 비용의 상한(하루 토큰 예산, 루프의 재시도 상한)과 그 측정 방법(llm.log의 토큰 합계, Claude Code의 /usage)을 적는다.

7-5. 네 어려움과 운영 요건

  • 비결정성 → 재현성, 일관성을 위협한다. 모의 모드의 완전 재현, 실제 모드의 반복 측정과 통과율, 결과 형식의 검사를 요건에 적는다(2장, 4장, 12장).
  • 환각과 거짓 보고 → 신뢰성을 위협한다. 완료 조건을 명령의 결과로 정하고 보고에 결과 줄을 붙이게 한다(2장, 6장, 8장).
  • 프롬프트 주입 → 보안을 위협한다. 외부 입력의 지시를 따르지 않음, 권한과 격리를 적는다(11장).
  • 비용 → 신뢰성(지속 가능성)을 위협한다. 토큰 예산, 재시도 상한, 측정 명령을 적는다(8장, 12장).

생각해 볼 것. 네 어려움 가운데 하나를 골라, 그 어려움 때문에 jobprep 운영에서 생길 수 있는 문제 하나와, 그 문제를 막는 요건 한 문장을 만들어 본다.

8. 측정 가능한 요건 문장

8-1. EARS 되짚기

앞 과목 6장에서 요구사항을 EARS(Easy Approach to Requirements Syntax)로 썼다. EARS는 2009년에 롤스로이스의 알리스테어 메이빈(Alistair Mavin)과 동료들이 제트 엔진 제어 시스템의 감항 규정을 분석하며 만든 문형으로, 자연어 요구사항의 흔한 문제를 줄이고, 특별한 도구 없이 적은 훈련으로 쓸 수 있게 한 것이다[R1]. 일반형은 “(선행 조건) 동안, (발동 조건)하면, 시스템은 (응답)해야 한다”이고, 이것을 다섯 문형으로 나누어 쓴다[R1].

문형 영문 틀 [R1] 이 과목의 틀 운영 요건의 예
상시(ubiquitous) The <system> shall <response> (주어)는 ~해야 한다. 운영 에이전트는 .env 파일을 읽거나 고치지 않아야 한다.
상태(state-driven) While <precondition>, the <system> shall … ~인 동안, (주어)는 ~해야 한다. 모의 모드가 아닌 동안, 시스템은 하루 LLM 토큰 합계를 예산 안에 두어야 한다.
이벤트(event-driven) When <trigger>, the <system> shall … ~하면, (주어)는 ~해야 한다. 운영 에이전트가 코드를 고치면, 운영 에이전트는 완료를 보고하기 전에 python -m pytest -q를 실행해야 한다.
선택(optional feature) Where <feature is included>, the <system> shall … ~가 설정된 경우, (주어)는 ~해야 한다. 장애 보고 스킬이 설치된 경우, 운영 에이전트는 보고서를 같은 절 구성으로 써야 한다.
원치 않는 상황(unwanted behaviour) If <trigger>, then the <system> shall … 만약 ~이면, (주어)는 ~해야 한다. 만약 한 작업에서 테스트가 3회 연속 실패하면, 운영 에이전트는 다시 시도하지 않고 사람에게 실패 보고서를 넘겨야 한다.

jobprep의 요구사항명세서도 같은 틀을 쓴다. 다음은 명세서 2절의 표를 뽑아 본 것이다(읽기). 운영 요건 명세도 그 틀에 6-7절의 두 주어를 쓴다.

| 상시 | The system shall ... | 시스템은 ~해야 한다 |
| 상태 | While ..., the system shall ... | ~인 동안, 시스템은 ~해야 한다 |
| 이벤트 | When ..., the system shall ... | ~하면, 시스템은 ~해야 한다 |
| 선택 | Where ..., the system shall ... | ~가 설정된 경우, 시스템은 ~해야 한다 |
| 원치 않는 상황 | If ..., then the system shall ... | 만약 ~이면, 시스템은 ~해야 한다 |

8-2. 측정 가능한 요건의 조건

EARS 문형은 문장의 모양을 정한다. 모양이 맞아도 잴 수 없는 문장이 있다. “시스템은 안정적으로 동작해야 한다”는 상시 문형이지만, 무엇을 보면 안정적인지 알 수 없다. 이 과목은 운영 요건이 다음 다섯 조건을 갖출 때 측정 가능하다고 본다.

조건 질문 갖추지 못한 예 갖춘 예
주어 누가 지키는가 “비밀 정보는 보호되어야 한다” “운영 에이전트는 .env 파일을 읽지 않아야 한다”
관찰할 수 있는 행동이나 값 무엇을 보면 지켜졌는지 아는가 “적절히 처리해야 한다” “503 상태 코드로 응답해야 한다”
수치와 범위 어디까지가 통과인가 “빠르게 응답해야 한다” “95번째 백분위수를 300ms 이하로”
기간과 표본 언제, 무엇을 모아 재는가 “오류가 적어야 한다” “한 주의 전체 요청 가운데 5xx 비율을 1% 이하로”
측정 방법 무엇으로 재는가 (빈칸) “access.log에서 status>=500 줄 수 ÷ 전체 줄 수, 주 1회”

측정 방법은 요건 문장이 아니라 표의 별도 칸에 적는다. 그래야 측정 장치가 바뀔 때(사람이 보던 것을 훅이 보게 될 때) 요건 문장은 두고 측정 방법만 고칠 수 있다.

8-3. 모호한 말 고치기

요건 초안에서 자주 나오는 모호한 말과 고치는 방향이다.

모호한 말 왜 잴 수 없는가 고치는 방향 고친 예
적절히, 알맞게 누가 보아도 같은 판정이 나오지 않는다 기대하는 행동을 적는다 “적절히 오류를 처리한다” → “503과 까닭을 응답하고 error.log에 예외 이름을 남긴다”
빠르게, 신속히 기준값이 없다 백분위수와 값 “빠르게 응답한다” → “95번째 백분위수 300ms 이하”
안전하게, 보호한다 상태이지 행동이 아니다 금지된 행동을 적는다 “키를 안전하게 관리한다” → “API 키를 저장소의 어떤 커밋에도 넣지 않는다”
가능한 한, 최대한 언제나 빠져나갈 수 있다 지키지 못할 때의 행동을 따로 적는다 “가능한 한 재시도한다” → “3회까지 재시도하고, 그래도 실패하면 사람에게 넘긴다”
등, 기타 범위가 열려 있다 목록을 닫는다 “키 등의 설정값” → “status, llm_fake, jobs 밖의 값”
항상, 절대 지킬 수 없는 목표이다(6-3절의 「절대값 피하기」) 비율과 기간 “항상 응답한다” → “한 주의 99% 이상을 5xx 없이”

생각해 볼 것. 다음 초안을 측정 가능한 요건 문장으로 고치고 측정 방법을 한 줄 붙여 본다. “에이전트는 테스트를 잘 돌려야 한다.”

8-4. 측정 방법의 종류

측정 방법은 네 종류로 나뉜다. 위에 있을수록 사람의 판단이 덜 들고 자동화하기 쉽다.

종류 예 장점 한계 이 과목에서 자동화하는 장
테스트 python -m pytest -q의 통과 수, 특정 테스트 이름 매번 같은 판정, CI에 넣기 쉽다 테스트로 쓸 수 있는 것만 2장, 13장
검색·집계 명령 grep의 줄 수, awk로 계산한 비율 기록과 코드 전체를 한 번에 본다 규칙을 어긴 흔적이 글자로 남아야 한다 5장, 12장
시도와 거부 금지된 행동을 일부러 요청해 막히는지 본다 보안 요건의 실제 상태를 본다 시도 자체가 위험하지 않게 격리가 필요하다 3장, 6장, 11장
사람의 검토 보고서를 읽고 판정한다 형식으로 잡을 수 없는 의미를 본다 느리고 사람마다 다르다 줄여 나간다

1장 시점에는 많은 요건의 측정 방법이 「사람의 검토」나 「검색 명령」이어도 된다. “3장 이후: …, 그전: …”처럼 지금 쓸 방법과 장치가 생긴 뒤의 방법을 함께 적는다. 사람의 검토가 얼마나 줄었는지는 13장의 「운영 요건 지도」에서 드러난다.

8-5. 형식 검사 도구

요건이 15개를 넘으면 형식의 실수(ID 중복, 분류 칸 누락, 측정 방법 빈칸)를 눈으로 다 잡기 어렵다. 키트의 ops/check/check_ops.py는 앞 과목 6장에서 EARS 문장을 점검한 방식을 운영 요건 명세에 맞게 줄인 형식 검사 도구이다. 내용이 옳은지는 보지 않고, 사람이 판정하기 전에 기계로 걸러 낼 수 있는 형식만 본다.

오류로 보는 것은 ID 형식(OR-<SEC|REL|CON|REP>-<두 자리 번호>)과 중복, 분류 칸과 ID 분류의 불일치, 문형 칸과 문장 표지(동안, ~면, 경우, 만약)의 불일치, 「~야 한다」로 끝나지 않는 문장, 비었거나 -·미정·「 」인 측정 방법, 전체 15개 미만이거나 분류마다 3개 미만인 개수이다. 적절히, 빠르게, 충분히, 가능한 한, 최대한 같은 모호한 말은 경고만 낸다.

9. 운영 에이전트 시스템의 역할

9-1. 왜 역할을 나누는가

에이전트 하나에게 저장소의 모든 일을 맡길 수도 있다. 그러나 운영의 관점에서는 역할을 나누는 편이 낫다. 까닭은 세 가지이다.

  1. 권한을 좁힐 수 있다. 모든 일을 하는 에이전트는 모든 권한이 필요하다. 역할을 나누면 역할마다 필요한 권한만 준다(6-2절의 최소 권한). 관측 역할은 기록을 읽기만 하면 되므로 파일을 고칠 권한이 필요 없다.
  2. 작성과 검토를 떼어 놓을 수 있다. 같은 맥락에서 자기 변경을 검토하면 같은 가정을 되풀이하기 쉽다. 사람의 조직이 오래전부터 직무를 나누어 온 것(직무 분리, separation of duties)과 같은 까닭이다. 테스트를 쓰는 역할과 구현하는 역할을 나누면, 구현하는 쪽이 테스트를 고쳐 통과시키는 회피를 권한으로 막을 수 있다(2장).
  3. 사람의 개입 지점이 드러난다. 역할 사이에서 무엇이 넘어가는지를 적으면, 그 경계 가운데 어디에 사람의 승인을 둘지 정할 수 있다(4-4절).

나누는 데에도 비용(역할마다 따로 쓰는 토큰, 역할 사이의 인계 문서)이 있으며, 10장에서 다시 따진다. 1장은 역할을 문서로 정할 뿐이고, 실제 에이전트로 만드는 것은 6장과 10장이다.

9-2. 여섯 역할

이 과목은 jobprep 운영 에이전트 시스템의 역할을 소프트웨어 운영의 흐름에 따라 여섯으로 잡는다.

역할 맡는 일 받는 것 내는 것 주로 지키는 요건 구현하는 장
기획 이슈를 작업 단위로 나누고 인수 조건을 쓴다 이슈, 요구사항명세서, 운영 요건 계획 문서 일관성 10장
구현 계획과 테스트에 따라 코드를 고친다 승인된 계획, 실패하는 테스트 작업 브랜치의 커밋 신뢰성 2장, 8장
테스트 인수 조건을 테스트로 쓰고 실행해 판정한다 인수 조건 테스트, 판정 기록 신뢰성, 재현성 2장, 6장, 12장
검토 변경을 규칙과 요건에 비추어 읽고 의견을 낸다 변경 차이, 규칙, 운영 요건 검토 의견 일관성, 보안 6장, 10장
배포 통과한 판을 태그로 고정하고 배포와 되돌리기를 준비한다 병합된 main, CI 결과 태그, 배포 점검표 재현성, 신뢰성 13장
관측 운영 기록을 읽어 요건 위반과 비용을 보고한다 운영 기록, 실행 기록 관측 보고서 신뢰성 5장, 12장

여섯 가운데 다섯 이상을 쓰면 된다. 다섯만 쓴다면 기획을 사람이 맡거나, 배포와 관측을 하나로 합칠 수 있다. 어느 쪽이든 까닭을 역할 정의서의 4절에 적는다.

9-3. 역할 정의서의 항목

역할마다 다음 항목을 적는다. 형식 검사 도구는 굵게 표시한 다섯 항목이 비어 있지 않은지 본다.

항목 적는 것 잘 쓴 예 잘못 쓴 예
목적 이 역할이 맡는 일 한 문장 승인된 계획의 작업 단위 하나를 테스트가 통과하도록 구현한다 코드를 잘 짠다
권한 읽기, 쓰기, 실행, 금지의 네 칸 쓰기: api/, rag/, web/. 금지: tests/의 기존 테스트 수정, main에 푸시 필요한 모든 권한
입력 받는 문서, 파일, 결과 승인된 계획 문서, 실패하는 테스트 요청
출력 내는 문서, 파일, 커밋 작업 브랜치의 커밋, 변경 요약 결과물

관련 운영 요건 이 역할의 권한과 완료 조건이 지키는 요건 ID OR-REL-04, OR-CON-01 (비움)

완료 조건의 잘못 쓴 예 “구현이 끝났다고 보고한다”는 7-2절의 문제, 곧 판정을 모델의 말에 맡기는 것을 그대로 문서로 만든 것이다. 권한의 잘못 쓴 예 “필요한 모든 권한”은 6-2절의 과도한 권한이다. 권한 칸에는 반드시 금지를 적는다. 허용만 적으면 경계가 드러나지 않는다. 형식 검사 도구는 금지가 없는 권한 칸에 경고를 낸다.

9-4. 역할별 자율성과 사람 승인 지점

4-2절의 다섯 수준을 역할에 붙이면 다음과 같다. 이 과목의 권장안이며, 역할 정의서에서 고쳐도 된다. 고친다면 까닭을 적는다.

  • 기획 — 3 상담자. 승인 지점은 계획 승인이다. 방향이 틀리면 뒤의 모든 작업이 버려진다.
  • 구현 — 3 상담자. 승인 지점은 계획 밖의 파일과 새 패키지이다. 작업 폴더 안의 편집은 되돌릴 수 있으나 범위 밖은 아니다.
  • 테스트 — 3 상담자. 승인 지점은 테스트 동결이다. 동결된 테스트는 완료 조건 자체이다.
  • 검토 — 4 승인자. 병합 여부는 사람이 정한다. 검토 에이전트는 의견만 내고 승인 단추를 누르지 않는다.
  • 배포 — 2 협업자. 승인 지점은 배포 실행과 되돌리기 실행이다. 외부에 영향을 주는 행동은 체크포인트로 되돌릴 수 없다(4-5절).
  • 관측 — 4 승인자. 승인 지점은 장애로 판정해 이슈를 올릴 때이다. 읽기 전용이므로 위험이 낮다.

배포 역할의 수준이 가장 낮은 것에 주목한다. 능력이 모자라서가 아니라 되돌리기 어려운 일이기 때문이다. 자율성은 능력이 아니라 위험에 맞추어 정한다(4-1절).

생각해 볼 것. 9-3절 표의 「잘못 쓴 예」 가운데 둘을 골라, 각각이 4~7절에서 본 어느 문제(과도한 권한, 거짓 보고 등)에 해당하는지 짝지어 본다.

11-2. 운영 대상의 실행

운영 요건을 쓰려면 운영할 것이 실제로 어떻게 동작하는지 먼저 보아야 한다. 확인 터미널에서 서버를 백그라운드로 띄우고 같은 터미널에서 curl로 요청을 보낸다. 포트는 8000이다(부록 A-10).

[터미널] (가상 환경을 켠 확인 터미널)

cd ~/agent-lab/jobprep
netstat -ano | findstr :8000 || echo "8000 비어 있음"
mkdir -p logs/runtime
LLM_FAKE=1 LOG_DIR=logs/runtime uvicorn api.main:app --port 8000 > logs/runtime/server.out 2>&1 &
sleep 3
jobs
8000 비어 있음
[1]+  Running    LLM_FAKE=1 LOG_DIR=logs/runtime uvicorn api.main:app --port 8000 > logs/runtime/server.out 2>&1 &
  • netstat -ano | findstr :8000(macOS는 lsof -nP -iTCP:8000 -sTCP:LISTEN)에 줄이 나오면 부록 A-10-2로 그 프로그램을 멈추거나 다른 번호를 쓴다.
  • LLM_FAKE=1 LOG_DIR=logs/runtime은 이 명령에만 적용되는 환경 변수이다. 모의 모드로 띄우고 기록을 logs/runtime/에 남긴다. > … 2>&1은 서버의 출력을 파일로 보낸다.
  • &는 백그라운드로 실행해 입력 줄을 바로 돌려받고, jobs는 이 터미널의 백그라운드 작업 목록이다. Exit 1이 보이면 cat logs/runtime/server.out으로 까닭을 본다.

요청은 서버 상태부터 보낸다.

터미널 
curl -s http://127.0.0.1:8000/api/health; echo
curl -s http://127.0.0.1:8000/api/jobs | grep -o '"id":' | wc -l
curl -s -o /dev/null -w "%{http_code}\n" http://127.0.0.1:8000/api/jobs/999
{"status":"ok","llm_fake":true,"jobs":30}

404

건강 확인 응답에는 상태, 모의 모드 여부, 공고 수 셋만 있고 모델 이름이나 키 같은 설정값은 없다(REQ-OPS-01). 보안 요건의 재료이다. 둘째 줄은 "id":의 수로 공고 30건을 세고, -w "%{http_code}"는 본문 대신 상태 코드를 출력한다.

LLM을 쓰는 기능 하나를 부른다. 모의 모드이므로 LLM API에는 요청이 가지 않는다.

터미널 
curl -s -X POST http://127.0.0.1:8000/api/ask -H "Content-Type: application/json" --data-binary @- <<'EOF'; echo
{"question": "모의면접은 언제 열리나요?"}
EOF
{"answer":"모의면접은 매달 둘째 주와 넷째 주 수요일 오후에 연다. [1]","sources":[{"no":1,"source":"02_취업지원센터_이용안내.md","title":"취업지원센터 이용 안내 > 모의면접","score":0.3216}],"prompt_version":"ask_v1","model":"fake"}
  • 한글이 든 본문은 -d '…'로 쓰지 않고 --data-binary @-와 <<'EOF'로 표준 입력에 넣는다. Windows의 curl은 명령줄의 한글을 cp949로 바꾸어 보내므로, -d로 쓰면 서버가 There was an error parsing the body(400)로 거절한다(집필 PC에서 확인).
  • 응답의 prompt_version과 model은 어떤 판본과 모델이 이 답을 냈는지 남기는 재현성의 장치이다. 근거 유사도 0.3216은 기준값 0.3(대체 임베딩)에 가까워 여유가 작다. 신뢰성 요건의 기준값을 정할 재료이다.

요구사항명세서의 4절에는 상태가 「미구현」인 요구가 세 개 있다. REQ-JOB-06(마감 임박 필터 closing_within), REQ-SUM-05(요약 입력의 길이 제한과 422), REQ-ASK-06(질문의 길이 제한과 422)이다. 명세에는 있으나 코드가 없으므로 지금 서버는 이 요구를 지키지 않는다. 직접 확인한다.

11-5. 견본 기록으로 요건 재기

견본 운영 기록과 저장소로 요건 몇 개를 실제로 잰다. 측정 방법을 적었다면 그 명령이 실제로 돈다는 것까지 확인해야 한다. 여기서 낸 값은 운영 요건 명세의 4절(견본 기록으로 잰 값)에 옮긴다.

신뢰성: 5xx 비율. 요건 “시스템은 한 주의 전체 요청 가운데 5xx 응답의 비율을 1% 이하로 유지해야 한다.”

터미널 
awk '{ if (match($0, /status=[0-9]+/)) { s = substr($0, RSTART+7, RLENGTH-7) + 0; n++; if (s >= 500) e++ } }
     END { printf "전체 %d, 5xx %d, 비율 %.2f%%\n", n, e, e/n*100 }' logs/access.log
전체 480, 5xx 12, 비율 2.50%

match($0, /status=[0-9]+/)는 줄에서 status=숫자 부분을 찾아 시작 위치를 RSTART에, 길이를 RLENGTH에 넣는다. substr(…) + 0은 status=(7글자) 뒤의 숫자만 잘라 수로 바꾼다. n과 e가 전체 줄 수와 5xx 줄 수를 세고, END 블록이 모든 줄을 읽은 뒤 결과를 한 줄로 출력한다.

견본 주간의 5xx 비율은 2.50%로 목표 1%를 넘으므로 미달이다. 원인(어느 경로에서, 언제, 어떤 오류로)은 5장에서 MCP 서버로 기록을 읽어 찾는다. 1장에서는 “요건이 있고, 재는 명령이 있고, 지금 값은 미달”이라는 상태를 기록한다.

신뢰성: 응답 시간의 백분위수. 요건 “시스템은 공고 목록 요청 응답 시간의 95번째 백분위수를 300ms 이하로 유지해야 한다.” 접근 기록에서 공고 목록의 경로가 든 줄을 골라 처리 시간을 모으고, 작은 순으로 늘어놓아 95% 자리의 값을 고른다.

터미널 
grep 'path=/api/jobs' logs/access.log | grep -o 'ms=[0-9]*' | cut -d= -f2 | sort -n |
  awk '{ v[NR] = $1 } END { i = int(NR * 0.95); if (i < NR * 0.95) i++; print "요청", NR, "개, p95", v[i] "ms, 최대", v[NR] "ms" }'
요청 247 개, p95 23ms, 최대 25ms

95번째 백분위수는 값을 작은 순으로 늘어놓았을 때 95% 자리에 있는 값이다. 247개의 95%는 234.65이므로 235번째 값을 쓴다(올림). p95 23ms는 기준 300ms 안이므로 이 요건은 충족으로 보인다. 이 명령과 값(요청 247개, p95 23ms)을 측정 방법 칸과 4절에 그대로 적어 둔다. 11-8절에서 이 줄을 다시 본다.

평균과 백분위수가 어떻게 다른지는 요약 요청으로 본다.

터미널 
grep 'path=/api/summary ' logs/access.log | grep -o 'ms=[0-9]*' | cut -d= -f2 | sort -n |
  awk '{ v[NR] = $1; s += $1 } END { i = int(NR*0.95); if (i < NR*0.95) i++; m = int(NR*0.5); if (m < NR*0.5) m++;
         printf "요청 %d개, 평균 %.0fms, p50 %sms, p95 %sms, 최대 %sms\n", NR, s/NR, v[m], v[i], v[NR] }'

11-8. 문제 해결: 측정 명령이 다른 것을 잰다

형식이 통과해도 내용에 빈틈이 있을 수 있다. 8-5절에서 보았듯 형식 검사 도구는 측정 방법 칸이 비었는지만 보고, 그 명령이 요구가 말하는 대상을 재는지는 보지 않는다. 먼저 계획 모드의 Claude Code에게 읽기 검토를 맡긴다. 판정은 학습자가 한다.

Claude Code 
docs/운영/운영요건.md를 읽고 검토해 줘. 파일은 고치지 마.
1. 측정 방법에 적힌 명령 가운데 이 저장소에서 실제로 실행하면 실패하거나, 요구 문장과 다른 대상을 재는 것
2. 요구 문장과 측정 방법이 서로 다른 것을 말하는 행
3. 1장 5절의 사고 네 건(운영 DB 삭제, 확인 없는 파일 이동, 드라이브 삭제, 확장의 악성 지시)을 막는 데 필요한데 빠진 요건
각 지적마다 행 ID와 근거를 붙이고, 확신이 낮은 지적은 그렇다고 표시해 줘.
(응답 예시. 실제 응답은 다르다)
1. OR-REL-02의 측정 명령은 'path=/api/jobs'로 찾으므로 /api/jobs/28 같은 상세 요청도
   함께 셉니다. 목록만 재려면 끝에 빈칸을 두어야 합니다. (확신: 높음)
2. OR-SEC-03은 "저장소 밖"을 말하는데 측정 방법은 .env만 봅니다. (확신: 중간)
3. 사례 2(확인 없는 파일 이동)에 해당하는 "파괴적 명령 뒤 결과 확인" 요건이 없습니다.

Claude Code가 지적했든 하지 않았든, 측정 명령이 무엇을 고르는지는 직접 확인한다. 11-5절의 응답 시간 명령이 고른 247줄이 어떤 경로였는지 센다.

터미널 
grep 'path=/api/jobs' logs/access.log | grep -o 'path=[^ ]*' | sed 's#/api/jobs/[0-9]*#/api/jobs/N#' | sort | uniq -c
     79 path=/api/jobs
    168 path=/api/jobs/N

sed는 번호가 붙은 경로를 /api/jobs/N 하나로 묶고, uniq -c는 같은 줄의 수를 센다. 247줄 가운데 목록 요청은 79줄이고 168줄은 공고 상세 요청이다. 'path=/api/jobs'가 path=/api/jobs/28의 앞부분과도 맞기 때문이다. 요구는 목록 요청을 말하는데 명령은 상세 요청까지 섞어 쟀다. 기록의 한 줄에서 경로 다음에는 빈칸과 status=가 오므로, 경로 뒤에 빈칸 하나를 두면 목록 요청만 고른다.

터미널 
grep -c 'path=/api/jobs' logs/access.log
grep -c 'path=/api/jobs ' logs/access.log
grep 'path=/api/jobs ' logs/access.log | grep -o 'ms=[0-9]*' | cut -d= -f2 | sort -n |
  awk '{ v[NR] = $1 } END { i = int(NR * 0.95); if (i < NR * 0.95) i++; print "요청", NR, "개, p95", v[i] "ms, 최대", v[NR] "ms" }'
247
79
요청 79 개, p95 25ms, 최대 25ms

79개의 95%는 75.05이므로 76번째 값을 쓴다. 고친 p95는 25ms로 섞어 잰 23ms와 다르다. 이 견본에서는 둘 다 300ms 안이지만, 상세 요청의 속도가 달라지면 섞어 잰 값은 목록의 실제 상태와 다른 판정을 낸다. 측정 명령이 다른 것을 재면 요건이 깨져도 「통과」로 보인다.

  1. 해당 요건(예: OR-REL-02)의 측정 방법 칸을 grep 'path=/api/jobs ' …로 고치고, 끝의 빈칸이 상세 요청을 빼기 위한 것임을 덧붙인다.
  2. 4절에 고치기 전(247줄, p95 23ms)과 고친 뒤(79줄, p95 25ms)를 두 줄로 남긴다. 틀린 측정을 지우지 않아야 뒤에 같은 실수를 하는 사람이 알아본다.
  3. 다른 측정 명령에도 같은 질문(이 명령이 고르는 줄이 요구의 대상과 같은가)을 던진다.

Claude Code의 나머지 지적도 판정한다. 받아들인 지적은 문서를 고치고, 받아들이지 않은 지적은 까닭을 부록 A 아래에 한 줄 적는다. 고친 뒤 형식 검사를 다시 돌린다.

확인 11 uniq -c의 출력에서 247줄 가운데 168줄이 상세 요청임을 확인하였고, 운영 요건 명세의 해당 측정 방법 칸에 끝에 빈칸이 있는 명령이 있으며, 4절에 고치기 전(247줄, p95 23ms)과 고친 뒤(79줄, p95 25ms)의 두 줄이 있고, 다시 돌린 형식 검사가 결과: 통과이다.

정리

  • 이 과목은 「만든 것을 어떻게 믿을 수 있게 유지할 것인가」를 다룬다. 운영 대상은 기준 저장소 jobprep이고, 학기 내내 그 저장소를 운영하는 에이전트 시스템을 키운다.
  • AI 에이전트는 모델, 도구, 루프를 갖추고 다음 행동을 모델이 정하는 시스템이다. 미리 정한 코드 경로로 LLM을 부르는 것은 워크플로이다. 단계가 미리 정해지는 일에는 워크플로나 스크립트가 맞다.
  • 자율성은 능력과 따로 설계한다. 되돌리기 어려운 행동일수록 자율성을 낮추고 사람의 승인 지점을 둔다. Claude Code의 권한 모드가 그 수단이며, 2026-11 기준 시작 모드는 auto이다.
  • 2025년의 공개 사고에서 금지는 말로만 있었고, 성공은 모델의 말로 판정되었으며, 자율성과 권한은 위험보다 컸다.
  • 네 운영 요건은 보안(허용된 일만), 신뢰성(기대한 결과, 실패하면 멈춤), 일관성(누가 해도 같은 규칙), 재현성(다시 얻을 수 있고 기록이 남음)이다. 각각 최소 권한, SLI·SLO, 규약과 환경 동등성, 재현 가능한 빌드에 대응한다.
  • LLM은 비결정성, 환각, 프롬프트 주입, 비용을 더한다. 그래서 완료 조건은 모델의 말이 아니라 명령의 결과로 정한다.
  • 운영 요건은 EARS 문형에 측정 방법을 붙여 쓴다. 측정 방법은 테스트, 검색·집계 명령, 시도와 거부, 사람의 검토 순으로 자동화하기 쉽고, 이 과목의 각 장이 사람의 검토를 장치로 바꾸어 간다.

개념 점검 문항

  1. jobprep의 /api/ask가 LLM을 쓰면서도 에이전트가 아니라 워크플로인 까닭을 「Building effective agents」의 정의로 설명하라.
  2. Claude Code의 acceptEdits와 auto 모드를 자율성의 다섯 수준에 대어 비교하고, 운영 저장소에서 처음 구조를 파악할 때 둘 다 쓰지 않는 까닭을 설명하라.
  3. Replit 사례에서 깨진 운영 요건 둘을 들고, 각각을 jobprep에 맞는 EARS 문장과 측정 방법으로 바꾸어 써라.
  4. 응답 시간 요건을 평균이 아니라 95번째 백분위수로 쓰는 까닭을 이 장에서 잰 요약 요청의 값으로 설명하라.
  5. 다음 역할 정의의 문제를 둘 지적하고 고쳐 써라. “구현 에이전트: 권한은 필요한 모든 권한, 완료 조건은 구현이 끝났다고 보고하는 것.”

  3. 테스트를 고쳐 통과시키는 회피를 막는 테스트 동결을 적용한다.
