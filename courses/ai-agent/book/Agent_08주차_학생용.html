AI에이전트 기획 및 개발

8장

루프 엔지니어링과 자동화

2027학년도 「AI에이전트 기획 및 개발」의 준비 중인 교재입니다. 편집 상태를 검토하기 위해 미리 공개한 것으로, 수업 전에 내용과 순서가 바뀔 수 있습니다.

학사 10주차 · 교재 08 · 3부 하네스와 루프

7장에서 1~6장의 부품(테스트, 팀 규칙, 커맨드와 스킬, MCP, 훅, 서브에이전트)을 jobprep 하나에 하네스로 조립하고, 같은 작업을 하네스가 있을 때와 없을 때로 실행해 비교하였다. 그 비교에서 일을 시작하고, 결과를 읽고, 다시 시킬지 정한 것은 모두 학습자였다. 하네스는 에이전트가 일하는 틀을 정하지만, 그 틀 안에서 일을 몇 번 돌릴지, 언제 멈출지, 실패하면 무엇을 남길지는 정하지 않는다. 사람이 자리를 비우는 순간 이 결정을 대신할 장치가 필요하다.

이 장은 그 장치, 곧 루프를 다룬다. 루프 엔지니어링(loop engineering)은 에이전트의 실행을 반복 구조로 설계하는 일이다. 무엇을 판정하고, 실패하면 무엇을 돌려보내고, 몇 번까지 다시 하고, 언제 사람에게 넘기는지를 미리 정해 코드로 적는다. 판정은 에이전트의 말(“고쳤습니다”)이 아니라 기계가 내는 종료 코드로 하고, 상한(재시도, 비용, 시간)은 에이전트가 아니라 바깥의 스크립트가 지킨다. 2장의 테스트가 완료 조건이 되고, 7장의 하네스가 시도 한 번의 틀이 된다.

이 장에서 만드는 것은 하나이다. 실패하는 테스트를 받아 Claude Code를 헤드리스로 실행해 고치게 하고, pytest로 판정해 실패하면 실패 출력을 붙여 다시 시키되, 세 번 실패하면 멈추고 보고서를 남기는 루프 ops/loop/fix_until_green.py와 그 설계서 docs/운영/루프설계서.md이다. 모든 시도는 ops/loop/logs/에 JSON 줄로 기록하고, 시도 사이의 저장소 상태는 git으로 관리한다. 실제 모델을 부르지 않고도 루프의 모든 경로(성공, 3회 실패, 비용 상한, 테스트 회피)를 확인할 수 있도록, 에이전트 명령을 가짜 에이전트로 바꿔 끼우는 자리를 둔다. 해결하는 문제도 하나이다. 에이전트가 테스트의 기대값을 바꾸면 판정 명령은 정직하게 통과를 내고 루프는 잘못된 통과를 커밋한다. 이 빈틈을 보호 경로 검사로 막은 뒤, 같은 루프로 자기 계정의 실제 에이전트를 한 번 돌린다.

프로젝트실습Ⅱ에서 팀 저장소에 반복 작업(테스트 수정, 의존성 갱신, 기록 요약)을 자동화할 때 이 장의 설계서 항목을 그대로 쓴다. 9장은 이 장에서 바깥에서 돌린 루프를 모델 안쪽에서 보는 장이다. Claude Code가 도구를 부르고 결과를 받아 다시 판단하는 에이전트 루프를 파이썬으로 직접 구현한다. 10장은 이 장의 루프를 여러 역할 에이전트가 나누어 돌리는 구조로 넓히고, 13장은 같은 루프를 GitHub Actions에서 돌린다.

학습 목표

  • 헤드리스 실행을 스크립트에서 다룬다. claude -p의 출력 형식, 결과 객체의 필드, 종료 코드를 읽고, 권한과 상한을 명령행 플래그로 정한다.
    • 예시: --output-format json의 결과에서 subtype, total_cost_usd, num_turns를 꺼내 시도의 성공 여부와 비용을 판단한다.
    • 활용: 팀의 반복 작업을 셸 스크립트나 CI 단계에 넣을 때 허용 도구와 상한을 먼저 적는다.
  • 루프를 여섯 부분으로 설계한다. 입력, 실행, 판정, 되돌림, 재시도, 종료를 나누어 정하고, 각 결정의 근거를 루프 설계서에 쓴다.
    • 예시: “판정은 pytest -q의 종료 코드로 한다. 1이면 실패 출력의 요약을 붙여 다시 시키고, 5이면 테스트 회피를 의심해 멈춘다.”
    • 활용: 사람이 매번 돌리던 일을 자동화하기 전에 설계서로 검토받는다.
  • 루프의 안전장치를 구현하고 검증한다. 재시도·비용·시간 상한, 보호 경로 검사, git으로 시도 사이의 상태 관리, JSON 줄 기록, 사람에게 넘기는 보고서를 만들고, 가짜 에이전트로 각 경로를 실행해 확인한다.
    • 예시: 가짜 에이전트가 테스트의 기대값을 바꾸어 통과시키는 시도를 루프가 버리고 되돌리는 것을 테스트로 확인한다.
    • 활용: 무인 실행이 잘못될 때(무한 반복, 테스트 회피, 비용 폭주) 어느 장치가 막는지 지도로 설명한다.
  • 루프를 자동화 체계에 배치한다. 수집 → 요약 → 통지 파이프라인을 조합하고, 예약 실행의 선택지(cron, /loop, 예약 작업, GitHub Actions)를 비교해 고른다.
    • 예시: 운영 기록에서 그날의 경고와 오류만 골라 요약하고 파일로 남기는 digest.sh를 평일 아침에 돌리는 crontab 줄을 설계서에 쓴다(등록은 교수 시연).
    • 활용: 13장에서 같은 루프를 GitHub Actions 워크플로로 옮길 때 이 장의 상한과 권한을 그대로 가져간다.

0. 시작하기

이 장은 내 PC의 ~/agent-lab/jobprep/에서 진행한다. 설치, 로그인, 키트 저장소의 클론은 부록 A로 끝냈다고 전제하고, 수업의 시작 순서는 부록 A-20을 따른다. VS Code에 터미널 둘(Windows는 Git Bash, macOS는 기본 셸)을 나란히 두고, 하나는 직접 실행하는 [터미널], 다른 하나는 Claude Code에 쓴다(부록 A-4-2). 두 터미널 모두 cd ~/agent-lab/jobprep 뒤에 가상 환경을 켜고(Windows source .venv/Scripts/activate, macOS source .venv/bin/activate), 그 뒤로는 python으로 부른다(부록 A-9-1). Windows에서 루프의 한글 출력이 깨지면 부록 A-4-4의 PYTHONUTF8=1을 등록했는지 본다.

이 장의 실행 상한. 학생이 자기 계정으로 실제 모델을 부르는 것은 6-9의 헤드리스 루프 한 번(시도 상한 3, 루프 전체 0.60달러)이다. 6-7의 함수 하나를 Claude Code에 맡긴다면 대화형 요청 하나가 더해진다. 그 밖의 claude -p 예시(2-1, 2-6, 2-8, 3-3), 7-3의 실제 요약, 8절의 예약 실행(cron), 10절의 GitHub Actions는 교수 시연이며, 그 결과는 교수가 배포한 기록(키트의 실습재료/시연기록/)으로 읽는다. 나머지 실습은 모두 가짜 에이전트로 하며 사용량을 쓰지 않는다.

0-2. 7장 산출물 확인

루프는 깨끗한 작업 트리에서만 시작하므로, 먼저 앞 장의 작업이 모두 커밋되었는지 본다.

터미널 
cd ~/agent-lab/jobprep
git status --short
ls CLAUDE.md .claude/settings.json .claude/hooks
.claude/settings.json  CLAUDE.md

.claude/hooks:
check_hooks.sh  protect.sh  protected.txt  run_tests.sh  samples  stop_gate.sh

git status --short는 아무것도 출력하지 않아야 한다. 이 장이 기대하는 것은 세 가지이다. 팀 규칙 CLAUDE.md, 권한과 훅이 든 .claude/settings.json, 보호 경로의 편집을 막는 훅이다. 7장을 마치지 못해 이 파일들이 없으면 키트의 기준 산출물을 복사해 커밋한다. 7장 결과가 있으면 이 명령 덩어리는 건너뛴다.

[터미널] (7장을 마치지 못한 경우에만)

ls .claude/settings.json || {
  cp -rn ~/kits/Agent_08주차/기준산출물/jobprep/. .
  chmod +x .claude/hooks/*.sh
  git add -A
  git commit -m "chore(claude): 7장 기준 산출물(하네스 견본) 반영"
}

a || { … }는 a가 실패했을 때만 중괄호 안을 실행한다. 작업 트리가 깨끗한 상태에서 복사하므로 git add -A는 복사한 파일만 더한다. 커밋 메시지는 3장의 저장소 규약을 따른다. 3장의 commit-msg 훅을 켠 저장소에서는 커밋할 때마다 통과 커밋: …과 검사 1건, 위반 0건 두 줄이 더 나온다. 이 장의 출력 예시에서는 그 두 줄을 뺐다. chmod +x는 macOS에서 훅을 실행 파일로 만든다. Windows의 Git Bash에서는 효과가 없지만 해가 없다.

기준 산출물의 CLAUDE.md는 팀 규칙 여덟 가지(비밀 정보는 .env에만, LLM 호출은 api/llm.py, 동결된 테스트는 고치지 않음 등)와 실행 명령(가상 환경을 켠 뒤 python -m pytest)을 담으며, 루프 안의 에이전트도 이 규칙을 읽는다. .claude/settings.json에는 권한(허용, 확인, 거부)과 훅 셋이 있다. PreToolUse 훅 protect.sh는 .claude/hooks/protected.txt에 적힌 경로(.env, .env.*(.env.example은 예외), tests/.baseline.json, .git/, data/jobs.json)와 동결된 테스트 파일의 편집을 종료 코드 2로 막는다. PreToolUse 훅이 종료 코드 2로 끝나면 도구 호출이 막히고 표준 오류의 글이 Claude에게 전달된다[C12]. PostToolUse 훅 run_tests.sh는 파이썬 파일을 고친 뒤 관련 테스트를 돌려 실패를 Claude에게 보이고, Stop 훅 stop_gate.sh는 응답을 끝내기 전에 전체 테스트를 돌린다. 셋 다 시도 안에서 작동하는 장치이고, 루프는 시도 바깥에서 같은 일을 한 번 더 확인한다(3-4).

1. 사람이 돌리는 일과 루프가 돌리는 일

1-1. 대화형 세션과 무인 실행

2~7장의 실습은 모두 대화형 세션이었다. 학습자가 Claude Code의 입력 창에 지시를 넣고, 에이전트가 일하는 것을 보다가, 권한 요청에 답하고, 결과가 이상하면 바로 고쳐 말하였다. 이 방식에서는 사람이 루프의 일부이다. 사람이 판정하고, 사람이 다시 시키고, 사람이 멈춘다.

무인 실행에서는 사람이 빠진다. 스크립트가 에이전트를 부르고, 스크립트가 결과를 판정하고, 스크립트가 다시 시킬지 멈출지 정한다. 그래서 사람이 대화 중에 하던 일을 모두 미리 코드로 적어 두어야 한다.

사람이 대화 중에 하던 일 무인 실행에서 그 일을 맡는 것 이 장의 장치
권한 요청에 “예”나 “아니요”로 답한다 명령행의 허용·거부 규칙과 권한 모드 --allowedTools, --disallowedTools, --permission-mode dontAsk (3절)

이상한 변경을 보고 되돌린다 git 브랜치, 커밋, git restore 체크포인트와 되돌림 (4-5)

이 표의 오른쪽 두 열이 이 장의 내용 전체이다. 왼쪽 열을 하나라도 빠뜨리면 무인 실행은 사람이 있을 때보다 위험해진다. 대화형 세션에서는 사람이 그 빈자리를 메웠기 때문이다.

그렇다고 사람이 완전히 빠지지는 않는다. 모범 사례 문서는 긴 작업을 Claude가 혼자 끝까지 끌고 가더라도 사람에게 남는 일이 셋이라고 정리한다. 일을 시작하는 것, 이번에 “끝”이 무엇인지 정하는 것, 마지막에 병합을 승인하는 것이다[C6]. 이 장의 루프에서도 같다. 루프를 시작하는 사람, 판정 명령과 상한을 정한 사람, 루프 브랜치를 병합하는 사람이 있다. 무인 실행은 그 사이의 반복에서만 사람을 뺀다.

1-2. 루프의 정의

Claude Code 팀의 글 「Loop engineering: Getting started with loops」는 루프를 정지 조건이 충족될 때까지 에이전트가 작업 주기를 되풀이하는 것으로 정의한다[E6]. 이 정의에서 설계할 것은 둘이다. 한 주기 안에서 무엇을 하는가, 그리고 무엇이 정지 조건인가.

루프라는 낱말은 이 과목에서 두 층에 쓰인다. 둘을 구분해 두어야 9장과 이 장이 섞이지 않는다.

  • 안쪽 루프(에이전트 루프, 9장). Claude Code의 한 번의 실행 안에서 모델이 도구를 부르고, 결과를 받아, 다시 판단한다. 모델이 도구 호출 없이 답을 내거나 턴·비용 상한에 닿으면 멈춘다.
  • 바깥 루프(이 장의 루프). 스크립트가 에이전트를 한 번 실행하고, 결과를 판정하고, 다시 실행한다. 판정 통과, 재시도 상한, 비용·시간 상한에서 멈춘다.

Agent SDK 문서는 안쪽 루프의 한 바퀴를 턴(turn)이라 부르고, 도구 호출이 있는 턴마다 하나, 마지막 텍스트 응답에 하나를 센다[C21]. 이 장의 --max-turns는 안쪽 루프의 상한이고, LOOP_MAX_ATTEMPTS는 바깥 루프의 상한이다. 두 상한은 곱해진다. 턴 상한 15, 시도 상한 3이면 최악의 경우 모델은 45번 판단한다.

안쪽 루프가 이미 있는데 바깥 루프가 왜 필요한가. 안쪽 루프는 모델이 “다 되었다”고 판단할 때 멈춘다. 그 판단이 맞는지 확인하는 것은 안쪽 루프의 일이 아니다. 7장의 하네스(편집 뒤 테스트 훅, Stop 훅)가 안쪽 루프에 판정을 끼워 넣을 수는 있지만, 그것도 같은 세션 안의 일이므로 세션이 상한에 닿거나 오류로 끝나면 함께 끝난다. 바깥 루프는 세션 바깥에 서서, 세션이 어떻게 끝났든 저장소의 실제 상태를 판정하고 다음을 정한다. 세션이 죽어도 바깥 루프는 살아 있다.

1-3. 루프의 유형

같은 글은 루프를 무엇이 시작시키고 무엇이 멈추게 하는가로 네 유형으로 나눈다[E6].

유형 시작시키는 것 멈추게 하는 것 Claude Code의 수단 알맞은 일
턴 기반 사람의 프롬프트 한 번 Claude가 끝났다고 판단하거나 정보가 더 필요할 때 대화형 세션 짧고 한 번으로 끝나는 일
목표 기반 완료 조건을 적은 명령 한 번 평가 모델이 조건 충족을 확인하거나 턴 상한 /goal 끝났는지 확인할 수 있는 큰 일
시간 기반 정해진 간격 사람이 취소하거나 일이 끝남 /loop, 예약 작업 정기 점검, 외부 시스템 감시
능동형 일정이나 사건(새 PR, 실패한 CI) 일마다 목표 충족, 전체는 사람이 끌 때까지 클라우드 예약 작업, GitHub Actions 정의가 분명하고 되풀이되는 일

이 장의 fix_until_green.py는 목표 기반 루프를 스크립트로 직접 만든 것이다. Claude Code에는 같은 일을 하는 /goal 명령이 있다. /goal은 각 턴이 끝날 때마다 작은 모델이 대화 내용을 읽고 조건이 충족되었는지 판정하며, 평가 모델은 도구를 부르지 않으므로 Claude가 대화에 드러낸 것만 보고 판단한다[C24]. 판정이 모델의 판단이므로 비결정적이다. 이 장의 루프는 판정을 pytest의 종료 코드로 한다. 같은 저장소 상태면 같은 판정이 나온다. 둘의 차이는 이 장 전체의 출발점이므로 다음 절에서 다시 정리한다.

같은 글은 단순한 해법에서 시작하라고 권하고, 코드를 쓰는 루프에는 그 코드를 검사하는 루프가 필요하다고 적는다[E6]. 루프를 만들기 전에 그 일이 정말 반복되는지, 판정할 수단이 있는지부터 묻는다.

1-4. 결정적 장치와 비결정적 장치

Claude Code의 모범 사례 문서는 Claude Code에 주는 모든 지시를 두 종류로 나눈다[C6]. 비결정적 지시는 모델이 읽고 따를지 정하는 것(프롬프트, CLAUDE.md, 스킬)이고, 결정적 지시는 하네스가 반드시 실행하는 것(훅, 거부 규칙, 관리 설정)이다. 문서는 같은 목적에 두 형태가 다 있음을 표로 보인다. 그 표를 이 장의 관점으로 옮기면 다음과 같다.

묻는 것 비결정적(모델이 정함) 결정적(하네스나 스크립트가 강제) 이 장의 선택
끝났는가 증거를 보이라는 요청, /goal, 검토 서브에이전트 테스트, 종료 코드, Stop 훅, CI pytest -q의 종료 코드
얼마나 쓰는가 노력 수준(effort), 모델 스스로의 속도 --max-turns, --max-budget-usd, 지출 한도 두 플래그와 루프 전체 예산
무엇을 건드릴 수 있는가 지시문의 “고치지 마라” 거부 규칙, 훅, 샌드박스 거부 규칙 + 훅 + 루프의 보호 경로 검사
최종 결정은 누가 하는가 Claude의 요약 보호 브랜치, 병합을 승인하는 사람 루프 브랜치를 사람이 검토하고 병합

문서는 CLAUDE.md의 한 줄을 아무리 강조해도 지켜지지 않으면 그 줄이 훅으로 가야 한다는 신호라고 적는다[C6]. 루프는 이 원칙을 반복 구조로 넓힌 것이다. 지시문에 “테스트를 고치지 마라”라고 적되, 고쳤는지는 스크립트가 git status로 확인한다.

1-5. 무인 실행 전에 답할 다섯 질문

모범 사례 문서는 작업을 혼자 돌게 두기 전에 다섯 가지를 그 작업에 비추어 확인하라고 한다[C6]. 이 장의 루프 설계서는 이 다섯 질문에 대한 답을 항목으로 나눈 것이다.

  1. 완료가 무엇인지 아는가. 실패하는 테스트가 통과로 바뀌는 것이다(설계서 1, 4절).
  2. 자기 일을 검사할 수 있는가. 시도 안에서는 PostToolUse 훅이, 시도 뒤에는 루프의 판정 명령이 테스트를 돌린다(설계서 4절).
  3. 무엇을 건드려도 되는가. 허용 도구는 읽기, 편집, pytest 실행뿐이다. 보호 경로는 거부 규칙, 훅, 루프의 검사로 세 번 막는다(설계서 3, 10절).
  4. 무엇이 멈추게 하는가. 재시도 3회, 턴 15, 시도당 0.50달러, 전체 1.00달러, 시도당 600초, 전체 1,800초이다(설계서 7절).
  5. 결과는 어디로 가고 누가 승인하는가. 통과하면 루프 브랜치에 커밋하고 사람이 검토해 병합한다. 멈추면 보고서를 남기고 사람이 판단한다(설계서 5, 8절).

다섯째 질문이 가장 자주 빠진다. 루프가 통과를 냈다고 해서 그 변경이 바로 main에 들어가지 않는다. 통과는 “테스트가 정한 조건을 만족한다”는 뜻일 뿐이고, 테스트가 정하지 않은 것(가독성, 다른 요구와의 충돌, 테스트 회피)은 사람이 본다.

1-6. 루프로 돌리지 않을 일

모든 반복 작업이 루프에 맞지는 않다. 루프로 돌리기 전에 세 가지를 묻는다.

첫째, 기계가 판정할 수 있는가. “읽기 쉬운 오류 메시지로 바꾸어라”나 “화면을 더 보기 좋게 하라”는 통과와 실패를 가르는 명령이 없다. 이런 일을 루프에 넣으면 판정을 모델에게 맡기게 되고(/goal과 같다), 루프는 모델이 만족할 때까지 돈다. 판정 명령을 먼저 만들 수 없다면, 그 일은 사람이 지켜보는 대화형 세션에서 한다.

둘째, 되돌릴 수 있는가. 이 장의 루프가 안전한 것은 실패한 시도를 git restore로 지울 수 있기 때문이다. 배포, 데이터베이스 변경, 메일이나 메신저 발송, 원격 저장소로의 푸시는 되돌릴 수 없거나 되돌리는 데 비용이 크다. 이런 동작은 루프 안에 두지 않고, 루프가 끝난 뒤 사람이 승인하는 단계로 뺀다. 이 장의 루프가 커밋은 하되 푸시와 병합은 하지 않는 까닭이다.

셋째, 실패의 값이 루프의 이득보다 작은가. 테스트 두 개를 고치는 일에 루프가 실패하면 잃는 것은 1달러와 30분이다. 같은 루프가 결제 모듈을 고치다가 테스트가 잡지 못하는 결함을 넣으면 잃는 것은 훨씬 크다. 실패의 값이 클수록 루프는 더 작은 단위로, 더 많은 사람의 검토와 함께 돈다.

2. 헤드리스 실행

2-1. claude -p의 기본형

Claude Code를 대화 화면 없이 한 번 실행하고 끝내는 방식을 헤드리스(headless) 실행이라 한다. 공식 문서의 현재 제목은 「Run Claude Code programmatically」이며, 명령행의 claude -p를 Agent SDK를 CLI로 쓰는 방법으로 설명한다[C14]. -p(또는 --print)를 붙이면 Claude Code는 프롬프트 하나를 처리하고 결과를 표준 출력에 쓴 뒤 종료한다.

교수 화면 
claude -p "api/jobs.py의 days_left 함수가 하는 일을 두 문장으로 설명하라"

이 명령은 실제 모델을 부르므로 사용량을 쓴다. 2~3절의 claude -p 예시는 꼬리표가 [교수 화면]이며 교수가 시연한다. 학습자는 같은 옵션을 받고 같은 모양의 결과를 내는 가짜 에이전트(2-5)로 같은 절차를 따르고, 실제 모델은 6-9의 루프 한 번으로만 부른다(0절의 실행 상한).

모범 사례 문서는 claude -p가 한 번 실행하고 끝나므로 CI 작업, git 훅, 셸 반복문에 Claude Code를 넣는 수단이 된다고 설명한다[C6]. 공통점은 실행을 시작하는 것이 사람의 입력이 아니라 다른 프로그램이라는 점이다. 그 프로그램은 Claude Code의 화면을 보지 못하고 표준 출력과 종료 코드만 본다. 그래서 헤드리스 실행의 설계는 곧 “다른 프로그램이 읽을 수 있는 결과”의 설계이다.

헤드리스 실행은 표준 입력을 읽는다. 앞 명령의 출력을 파이프로 넘기면 그것이 프롬프트와 함께 컨텍스트가 된다.

교수 화면 
grep ERROR logs/error.log | head -20 | claude -p "오류를 원인별로 묶어 세 줄로 요약하라" > 요약.txt

파이프로 넘기는 표준 입력은 10MB로 제한되며, 넘으면 오류와 함께 0이 아닌 종료 코드로 끝난다[C14]. 큰 입력은 파일로 저장하고 프롬프트에 경로를 적는다. 위 예처럼 grep과 head로 먼저 줄이면 입력이 작아지고 비용도 준다. 결정적으로 할 수 있는 일(고르기, 세기, 자르기)은 셸이 하고, 판단이 필요한 일(묶기, 설명하기)만 모델에 맡기는 것이 파이프라인 설계의 기본이다(7절).

7장의 측정 도구 ops/harness/run_task.sh도 claude -p로 작업 한 건을 실행하였다. 그때는 과정 전체를 남기려고 --output-format stream-json을, 편집을 묻지 않으려고 --permission-mode acceptEdits를 썼다. 사람이 결과를 한 건씩 판정하는 측정이었기 때문이다. 이 장의 루프는 스크립트가 판정하고 다음을 정하므로 선택이 다르다. 결과 객체 하나(json)와 목록 밖을 모두 거부하는 권한 모드(dontAsk)를 쓴다. 같은 명령이라도 누가 결과를 읽는가에 따라 플래그가 달라진다.

-p와 함께 쓰지 못하는 옵션도 있다. 문서는 --bg를 거부하고, 몇몇 옵션의 조합에는 충돌을 알리는 오류를 낸다고 적는다[C14]. 또 -p 모드에서는 작업 공간 신뢰 대화 상자가 뜨지 않는다. 도움말은 이 때문에 신뢰하는 폴더에서만 쓰라고 경고한다(3-5).

2-2. 출력 형식

--output-format은 세 값을 받는다[C14][C15].

  • text(기본값): 최종 응답의 글이 나온다. 사람이 읽거나 파일로 저장할 때 쓴다.
  • json: 결과 객체 하나가 나온다. 응답 글(result)과 세션 아이디, 비용, 턴 수 같은 메타데이터를 담는다. 스크립트가 성공 여부와 비용을 판단할 때 쓰며, 이 장의 루프가 쓰는 형식이다.
  • stream-json: 사건마다 JSON 한 줄이 나오고(줄 단위 JSON), 마지막 줄이 결과 객체이다. 진행 상황을 실시간으로 볼 때 --verbose와 함께 쓴다(2-8).

stream-json으로 토큰이 생성되는 대로 받으려면 --verbose와 --include-partial-messages를 함께 준다[C14]. 긴 루프를 지켜볼 때 유용하지만, 판정에 필요한 것은 마지막 결과 객체 하나이므로 이 장의 루프는 json을 쓴다.

--json-schema에 JSON 스키마를 주면 응답을 그 형식으로 받을 수 있다. 결과는 structured_output 필드에 들어가며, Claude가 요청을 거절하는 등으로 형식에 맞는 출력이 나오지 않으면 그 필드가 없으므로 쓰기 전에 있는지 확인해야 한다[C14]. 이 장의 루프는 응답 글을 판정에 쓰지 않으므로(판정은 테스트가 한다) 스키마를 쓰지 않는다.

2-3. 결과 객체의 필드

--output-format json의 결과 객체는 Agent SDK의 결과 메시지(ResultMessage)와 같은 모양이다. 문서는 모든 결과 종류가 total_cost_usd, usage, num_turns, session_id를 가진다고 적는다[C21].

필드 뜻 루프에서 쓰는 곳
type 언제나 "result" 마지막 줄이 결과인지 확인
subtype 끝난 방식(2-4의 표) 성공, 턴 상한, 비용 상한을 가른다
is_error 오류로 끝났는가 에이전트 상태를 error로 기록
result 최종 응답의 글. subtype이 success일 때만 있다 기록에 끝부분 300자만 남긴다
total_cost_usd 이 실행의 비용 추정치(달러) 루프 전체 예산에서 뺀다
num_turns 이 실행의 턴 수 기록
session_id 세션 아이디 기록. 사람이 --resume으로 이어 볼 때 쓴다
duration_ms 걸린 시간(밀리초) 참고
usage 입력·출력 토큰 수 12장의 비용 보고에서 쓴다
structured_output --json-schema를 주었을 때의 구조화 출력 쓰지 않음
stop_reason 마지막 응답에서 모델이 멈춘 까닭(end_turn, max_tokens, refusal 등) 참고

비용 필드는 클라이언트 쪽 추정치이며 실제 청구액과 다를 수 있다[C14]. --continue나 --resume으로 이어 간 실행은 앞 실행의 비용까지 합친 대화 전체의 값을 보고한다[C14]. 루프가 시도마다 새 세션을 여는 까닭 가운데 하나가 이것이다. 이어 가면 시도별 비용을 빼기로 다시 계산해야 한다.

2-4. 끝난 방식과 종료 코드

결과 객체의 subtype은 다섯 값 가운데 하나이다[C21].

subtype 일어난 일 result 필드
success 정상적으로 끝남 있음
error_max_turns --max-turns 상한에 닿음 없음
error_max_budget_usd --max-budget-usd 상한에 닿음 없음
error_during_execution 실행 중 오류로 중단됨(요청 취소 등) 없음
error_max_structured_output_retries 정해진 횟수 안에 스키마에 맞는 출력을 내지 못함 없음

프로세스의 종료 코드는 성공이면 0, 실패하면 0이 아니다. 문서는 스크립트가 이 종료 상태로 분기할 수 있다고 적고, 잘못된 플래그는 실행 전에 표준 오류로 알리지만 인증 실패처럼 실행 안에서 생긴 실패는 결과로 표준 출력에 쓴다고 구분한다[C14]. 턴 상한에 닿은 실행도 0이 아닌 코드로 끝난다[C6][C21]. kill처럼 SIGTERM으로 멈춘 실행은 종료 코드 143으로 끝나고, 진행 중이던 턴의 결과는 남지 않는다[C14].

표준 오류도 버리지 않는다. 잘못된 플래그, 설정 파일의 경고, 신뢰하지 않은 폴더의 경고(3-5)는 표준 오류로 나온다. 루프는 표준 출력의 마지막 줄을 결과 객체로 읽고, 그것이 JSON이 아니면 표준 출력과 표준 오류를 합친 끝부분을 기록의 agent_result에 남긴다. 실행이 결과 객체를 내지 못한 까닭은 대개 그 끝부분에 있다.

정리하면 루프는 두 가지를 함께 본다. 종료 코드는 “끝까지 갔는가”를, subtype은 “어떻게 끝났는가”를 알려 준다. 둘 다 “고쳐졌는가”는 알려 주지 않는다. success로 끝나고 응답에 “모든 테스트가 통과한다”고 적혀 있어도, 그것은 에이전트의 말이다. 고쳐졌는지는 4절의 판정 명령이 따로 정한다.

2-6. 대화 잇기와 시스템 프롬프트

헤드리스 실행도 대화를 이어 갈 수 있다. --continue는 가장 최근 대화를, --resume은 세션 아이디로 정한 대화를 잇는다[C14].

교수 화면 
sid=$(claude -p "api/jobs.py를 읽고 개선점을 찾아라" --output-format json | python -c 'import json,sys; print(json.load(sys.stdin)["session_id"])')
claude -p "그 가운데 테스트가 없는 것만 골라라" --resume "$sid"

루프는 시도마다 새 세션으로 시작하고, 앞 시도의 정보는 지시문에 요약해 넣는다. 세션을 이어 가면 앞 시도의 탐색 결과를 다시 쓸 수 있지만, 실패한 시도의 잘못된 가정까지 함께 이어지고 컨텍스트가 길어질수록 시도마다 비용이 커진다. 비용 문서는 긴 세션에서 매 요청이 대화 전체를 다시 보낸다고 설명한다[C19]. 루프는 “무엇을 넘길지 사람이 정한다”는 쪽을 택하였다(4-6). 실패한 시도를 사람이 살펴볼 때는 기록에 남은 session_id로 claude --resume <세션 아이디>를 실행해 그 시도의 대화를 대화형으로 열어 볼 수 있다.

--append-system-prompt는 Claude Code의 기본 시스템 프롬프트를 유지한 채 지시를 덧붙이고, --system-prompt는 기본 프롬프트를 통째로 바꾼다[C14][C15]. 긴 지시는 --append-system-prompt-file로 파일에서 읽는다. 루프는 “이 실행은 무인 루프의 한 시도이다. 사람에게 질문할 수 없다”는 짧은 문장만 덧붙인다. 기본 프롬프트를 바꾸면 도구 사용과 안전에 관한 기본 지시까지 빠지므로 쓰지 않는다.

2-7. bare 모드와 인증

--bare는 훅, 스킬, 커스텀 커맨드, 서브에이전트, 플러그인, MCP 서버, 자동 메모리, CLAUDE.md를 찾아 읽지 않고 시작한다. 문서는 이 모드가 어느 컴퓨터에서나 같은 결과가 필요한 CI와 스크립트에 쓸모 있으며, 앞으로 -p의 기본값이 될 것이라고 적는다[C14]. 대신 bare 모드는 claude.ai 로그인 정보를 읽지 않고 ANTHROPIC_API_KEY 환경 변수나 --settings로 준 apiKeyHelper로만 인증한다[C14].

두 방식을 견주면 이렇다. 보통의 claude -p는 저장소와 사용자 폴더의 CLAUDE.md, .claude/settings.json의 훅, .mcp.json, 스킬을 읽고, 계정 로그인이나 API 키로 인증한다. claude --bare -p는 명령행으로 넘긴 것(--append-system-prompt, --settings, --mcp-config 등)만 읽고, --settings로 넘긴 훅도 돌리지 않으며, API 키로만 인증한다. 앞의 것은 7장의 하네스가 시도 안에서 작동해야 하는 이 장의 루프에 맞고, 뒤의 것은 어느 컴퓨터에서나 같은 결과가 필요하고 키를 저장소의 비밀 정보로 둘 수 있는 13장의 CI에 맞는다.

이 과목은 학생 계정을 로그인으로 쓰고 API 키를 ~/.bashrc에 두지 않는다(부록 A-5-3). 그래서 이 장의 루프는 --bare를 쓰지 않는다. bare 모드에서는 훅이 돌지 않으므로, 7장의 보호 경로 훅과 편집 뒤 테스트 훅이 시도 안에서 빠진다는 점도 이유이다.

2-8. stream-json으로 진행 보기

json 출력은 실행이 끝나야 한 번에 나온다. 시도 한 번이 몇 분 걸리면 그동안 무엇을 하는지 알 수 없다. --output-format stream-json --verbose를 주면 사건이 일어날 때마다 JSON 한 줄이 나온다. 문서에 따르면 첫 사건은 대개 system/init으로, 모델, 도구, MCP 서버, 불러온 플러그인 같은 세션의 정보를 담고, 마지막 줄은 최종 응답과 비용과 세션 정보를 담은 result이다[C14]. 그 사이에 모델의 응답(assistant)과 도구 결과(user)가 오간다.

[교수 화면] (실제 모델을 부른다. 교수가 시연하고 사건 종류의 목록을 시연기록/stream-2-8.txt로 배포한다)

claude -p "python -m pytest -q를 실행하고 결과를 한 줄로 말하라" --output-format stream-json --verbose \
  --allowedTools "Bash(python -m pytest *)" --max-turns 3 \
  | python -c 'import json,sys
for line in sys.stdin:

무인 실행에서 특히 쓸모 있는 사건이 둘 있다. 하나는 system/api_retry이다. API 요청이 재시도할 수 있는 오류로 실패하면 재시도하기 전에 이 사건이 나오며, 몇 번째 시도인지(attempt), 몇 번까지 하는지(max_retries), 얼마 뒤에 하는지(retry_delay_ms), 오류의 종류(error: rate_limit, overloaded, authentication_failed 등)를 담는다[C14]. 루프의 시도가 이상하게 오래 걸리면 이 사건으로 모델 쪽의 지연인지 에이전트의 탐색인지 가를 수 있다. 다른 하나는 권한 거부이다. --permission-prompts none과 stream-json을 함께 쓰면 거부된 호출이 permission_denied 사건으로 나오고, 마지막 결과의 permission_denials에 모인다[C14]. 허용 도구를 너무 좁게 잡아 에이전트가 필요한 일을 못 한 것인지 확인할 때 쓴다.

이 장의 루프는 시도의 결과만 판단에 쓰므로 json으로 충분하다. 실제 에이전트로 루프를 처음 돌릴 때는 시도 하나를 stream-json으로 따로 실행해 보며 에이전트가 무엇을 읽고 무엇을 실행하는지 확인하는 것이 좋다. 그 관찰이 허용 도구와 턴 상한을 정하는 근거가 된다.

3. 헤드리스 실행의 권한 설계

3-1. 권한 모드

대화형 세션에서는 에이전트가 권한이 필요한 도구를 부를 때 사람에게 묻는다. 헤드리스 실행에는 물을 사람이 없다. 그래서 무엇을 묻지 않고 허용하고, 무엇을 묻지 않고 거부할지를 실행 전에 정해야 한다. 그 바탕이 권한 모드이다[C22].

모드 묻지 않고 실행되는 것 알맞은 곳
default (화면 이름 Manual, 명령행 별칭 manual) 읽기만 모든 동작을 사람이 보는 민감한 일
acceptEdits 읽기, 파일 편집, 흔한 파일 명령(mkdir, touch, mv, cp 등) 사람이 검토하는 코드의 반복 수정
plan 읽기(자동 모드가 가능하면 분류기가 승인한 명령도) 바꾸기 전에 탐색할 때
auto 모든 것, 단 배경에서 분류기가 위험한 동작을 검사 긴 작업, 승인 피로를 줄일 때
dontAsk 작업 폴더 안의 파일 읽기와 미리 허용한 도구. 물어야 할 것은 모두 거부 잠근 CI와 스크립트
bypassPermissions 모든 것 격리된 컨테이너와 가상 머신에서만

-p 실행이 어느 모드로 시작하는지는 버전에 따라 다르다. 문서는 v2.1.302부터 권한 모드를 정하지 않은 claude -p와 Agent SDK 실행이 Manual 모드로 시작하고, 승인이 필요한 호출은 허용 규칙, 훅, 콜백 등으로 승인하지 않으면 거부된다고 적는다. 그 이전 버전은 일부 환경에서 자동 모드로 시작할 수 있었다[C22]. 집필용 PC의 2.1.296은 그 이전 버전이다. 버전마다 기본값이 바뀔 수 있으므로 루프는 기본값에 기대지 않고 --permission-mode dontAsk를 명시한다.

[최신 자료 자리: -p 실행의 기본 권한 모드] 권한 모드를 정하지 않은 claude -p가 어느 모드로 시작하는지와 그 기준 판. 확인할 곳: https://code.claude.com/docs/en/permission-modes. 2026-11-15에 확인한 값: v2.1.302 이상은 Manual(default)로 시작한다. 내 PC의 판이 이 경계의 어느 쪽인지 수업 전에 확인한다.

bypassPermissions에 대해 문서는 Claude Code가 호스트 시스템을 해칠 수 없는 격리된 환경(인터넷이 없는 컨테이너, 가상 머신)에서만 쓰라고 하고, 이 모드는 프롬프트 주입이나 의도하지 않은 동작에서 아무것도 지켜 주지 않는다고 경고한다. 리눅스에서 root나 sudo로 실행하면 이 모드로 시작하지 않는다[C22]. 내 PC는 내 파일과 로그인한 계정이 있는 컴퓨터이지 격리된 환경이 아니므로 이 모드를 쓰지 않는다.

auto 모드도 -p와 함께 쓸 수 있다. 모범 사례 문서는 비대화형 실행에서 분류기가 막은 동작은 그 하나만 거부되고 Claude는 계속 일하며, 대화형 터미널과 달리 거부가 되풀이되어도 실행이 멈추지 않는다고 적는다[C6]. 분류기는 모델이므로 같은 명령을 언제나 같게 판단한다는 보장이 없다. 이 장의 루프는 허용할 것을 미리 다 알 수 있는 일(읽기, 편집, pytest 실행)이므로, 판단을 분류기에 맡기는 auto보다 목록 밖을 모두 거부하는 dontAsk가 맞다. 허용할 것을 미리 다 알 수 없는 넓은 일(의존성 갱신처럼 여러 명령이 필요한 일)이라면 auto와 작은 상한의 조합을 검토한다.

3-2. 허용, 거부, 제한의 세 플래그

헤드리스 실행에서 도구를 다루는 플래그는 셋이며, 하는 일이 다르다[C15].

플래그 하는 일 예
--allowedTools 나열한 도구(또는 규칙에 맞는 호출)를 묻지 않고 실행한다. 나열하지 않은 도구도 사라지지는 않는다 "Read,Edit,Bash(python -m pytest *)"
--disallowedTools 거부 규칙. 도구 이름만 주면 그 도구를 컨텍스트에서 없애고, Bash(rm *)처럼 범위를 주면 도구는 남기고 맞는 호출만 거부한다 "Bash(git push *),Edit(/tests/**)"
--tools 쓸 수 있는 내장 도구의 목록 자체를 정한다. ""이면 모든 도구를 끈다. MCP 도구에는 영향이 없다 --tools "" (7절의 요약 단계)

--allowedTools는 “허용 목록”이 아니라 “묻지 않을 목록”이다. 나열하지 않은 도구를 부르면 권한 모드가 처리한다. dontAsk 모드는 그것을 거부하고, acceptEdits 모드는 편집이면 허용한다. 그래서 허용 도구를 최소화하는 일은 반드시 권한 모드와 함께 설계한다.

3-3. 규칙의 문법

--allowedTools와 --disallowedTools의 값은 설정 파일의 권한 규칙과 같은 문법을 쓴다. 헤드리스 문서의 커밋 예시는 다음과 같다[C14].

교수 화면 
claude -p "스테이지된 변경을 보고 알맞은 커밋을 만들어라" \
  --allowedTools "Bash(git diff *),Bash(git log *),Bash(git status *),Bash(git commit *)"

문서가 짚는 세부는 다음과 같다.

  • 끝의 *(공백과 별표)는 앞부분이 같은 모든 명령을 뜻한다. Bash(git diff *)는 git diff로 시작하는 명령을 허용한다. 공백이 없는 Bash(git diff*)는 git diff-index까지 맞는다[C14].
  • 규칙은 거부, 확인(ask), 허용 순서로 평가되고 처음 맞는 것이 결과를 정한다. 넓은 거부 규칙은 더 구체적인 허용 규칙이 있어도 이긴다. 허용 규칙으로 거부 규칙에 예외를 만들 수 없다[C4].
  • Claude Code는 셸 연산자를 안다. Bash(safe-cmd *)를 허용해도 safe-cmd && other-cmd는 허용되지 않는다. 복합 명령은 하위 명령이 모두 허용되어야 묻지 않고 실행된다. 거부 규칙은 하위 명령 하나라도 맞으면 적용된다[C4].
  • Edit(/tests/**)의 맨 앞 /는 규칙이 정의된 곳을 기준으로 한다. 명령행 플래그로 준 규칙은 세션의 주 작업 폴더를 기준으로 하므로, 저장소 맨 위에서 실행하면 저장소의 tests/ 아래를 뜻한다[C4].

키트의 루프가 넘기는 규칙은 다음과 같다.

거부 목록의 항목마다 까닭이 있다. git reset과 git checkout은 루프가 관리하는 브랜치와 체크포인트를 에이전트가 움직이지 못하게 막는다. rm은 파일 삭제를 막는다. 에이전트가 고치기 어려운 파일을 지워 버리는 것도 테스트 회피의 한 모양이기 때문이다(9-2). Edit(/.claude/**)는 에이전트가 자기를 묶는 하네스(훅과 권한)를 고치지 못하게 하고, Edit(/ops/**)는 판정하는 쪽인 루프 스크립트를 고치지 못하게 한다. pytest를 부르는 형태를 둘(pytest, python -m pytest)씩, 인자가 없는 것과 있는 것으로 나누어 적은 까닭은 Bash 규칙이 Claude가 쓴 명령의 글자에 맞추기 때문이다(3장 4-7). 7장의 CLAUDE.md는 테스트 명령을 「가상 환경을 켠 뒤 python -m pytest」로 적고, 지시문(prompt_fix.md)은 python -m pytest -q로 적는다. 그러면 가상 환경의 파이썬은 누가 고르는가. 루프는 에이전트를 실행할 때 지금 쓰는 가상 환경의 폴더(Windows .venv/Scripts, macOS .venv/bin)를 PATH 맨 앞에 넣는다(4-3). 그래서 경로 없는 python이 곧 가상 환경의 파이썬이다. 에이전트가 .venv/Scripts/python -m pytest -q처럼 경로를 붙여 부르면 글자가 달라 허용 규칙에 맞지 않는다. 대화형 세션이었다면 확인 창이 떴을 이 호출(3장 판정 사례 13번)을 dontAsk는 묻지 않고 거부하고, 에이전트는 테스트를 돌리지 못한 채 고친다. 경로 호출을 허용 목록에 더하는 대신 경로가 필요 없게 환경을 맞춘 것이다. 운영체제마다 다른 경로(Scripts와 bin)를 규칙에 늘어놓지 않아도 된다.

Edit를 허용하면서 Edit(/tests/**)를 거부하는 것은 거부가 먼저 평가된다는 규칙에 기댄 것이다. Bash는 pytest 실행만 허용하고, dontAsk 모드가 나머지 셸 명령을 거부한다. 그런데도 Bash(git commit *)를 따로 거부한 까닭은 두 가지이다. 첫째, 사용자 설정이나 프로젝트 설정에 넓은 허용 규칙이 있으면 dontAsk가 거부하지 않는다. 명시한 거부 규칙은 그 경우에도 이긴다. 둘째, 커밋은 루프가 판정 뒤에 하는 일이다. 에이전트가 판정 전에 커밋하면 4-5의 되돌림이 그 커밋을 지우지 못한다.

3-4. 규칙은 보안 경계가 아니다

권한 문서는 Bash 규칙이 Claude가 쓴 명령의 글자를 맞추어 보는 것이며, 같은 프로그램을 다른 형태로 부르는 것은 맞추지 못한다고 분명히 적는다. 그래서 거부 규칙은 Claude가 흔히 만드는 호출을 막을 뿐 그 프로그램 둘레의 보안 경계가 아니다[C4].

문서가 드는 예는 이렇다. 거부 규칙 Bash(rm *)는 rm -rf build/를 막지만 /bin/rm -rf build/나 bash -c 'rm -rf build/'는 막지 못한다. Bash(git push *)는 git push origin main을 막지만 git -C . push origin main은 막지 못한다. Bash(curl *)도 /usr/bin/curl …이나 sh -c 'curl …'을 막지 못한다[C4]. 거부 규칙은 글자를 맞추어 볼 뿐 프로그램이 무엇을 하는지는 모른다.

문서는 명령의 글자에 기대지 않는 파일·네트워크 차단에는 샌드박스를, 명령 전체를 자기 논리로 검사하려면 PreToolUse 훅을 쓰라고 권한다[C4]. 이 장의 루프에서는 dontAsk가 허용 목록 밖의 Bash 명령을 모두 거부하므로 위 우회는 실행되지 않는다. 그래도 루프는 판정 전에 바뀐 파일을 git status로 직접 확인한다(6-7). 규칙과 훅이 무엇을 놓치든, 저장소에 남은 결과는 git이 정확히 안다.

3-5. 신뢰하지 않은 폴더에서의 -p

-p 실행은 작업 공간 신뢰 대화 상자를 띄우지 않는다. 권한 문서는 이때 저장소가 제공하는 것 가운데 무엇이 쓰이고 무엇이 쓰이지 않는지를 표로 보인다[C4]. 루프 설계에 중요한 것만 옮긴다.

  • 설정 파일의 훅과 env 블록은 쓰인다.
  • .claude/settings.json의 permissions.allow 규칙은 쓰이지 않으며, 표준 오류에 경고를 쓴다.
  • .mcp.json의 서버는 묻지 않고 연결된다.

이 세 가지가 루프 설계에 주는 결론은 둘이다. 첫째, 프로젝트 설정의 허용 규칙에 기대면 안 된다. 신뢰 여부에 따라 같은 루프가 다르게 돈다. 그래서 루프는 필요한 허용을 --allowedTools로 직접 넘긴다. 둘째, 남이 만든 저장소에서 claude -p를 돌리면 그 저장소의 훅이 내 컴퓨터에서 실행된다. 문서는 그런 경우 --setting-sources user나 --bare로 프로젝트 설정을 읽지 않게 하라고 권한다[C4]. 11장의 공급망 위험에서 다시 다룬다.

3-6. 사람이 없을 때의 권한 요청

--permission-prompts none은 권한 요청에 답할 사람이 없음을 명시한다. 이 플래그를 주면 물어야 할 호출은 모두 거부되고, Claude에게는 아무도 승인할 수 없으니 다시 시도하지 말라는 말이 전해지며, 실행은 계속된다. 문서는 SDK 앱처럼 권한 요청을 받는 쪽이 있는 실행에서 특히 중요하고, 그런 쪽이 없는 -p 실행에서는 어차피 거부되지만 Claude가 같은 요청을 되풀이하지 않게 해 준다고 설명한다[C14]. 이 플래그는 v2.1.259 이상에서 쓸 수 있다. 이 장의 루프는 dontAsk 모드로 같은 효과를 얻으므로 넣지 않았다. 루프 설계서에 넣을지는 학습자가 정한다.

사람이 고치던 파일을 루프가 git stash로 잠시 치워 두는 방법도 있다. 이 루프는 그렇게 하지 않고 시작을 거부한다. 치워 둔 변경을 루프가 끝난 뒤 되돌려 놓는 일이 실패하면(충돌, 루프의 중단) 사람의 작업이 보이지 않는 곳에 남기 때문이다. 무인 실행에서는 “알아서 처리한다”보다 “시작하지 않고 까닭을 말한다”가 안전하다.

changed_files()는 git status --porcelain의 출력에서 루프 자신이 쓰는 ops/loop/logs/와 ops/loop/reports/를 뺀 목록이다. 루프는 실행할 때마다 기록을 남기므로, 기록 폴더를 빼지 않으면 두 번째 실행부터 언제나 “깨끗하지 않음”이 된다.

4-4. 판정: 기계가 한다

판정 명령은 python -m pytest -q이다. pytest의 종료 코드는 여섯 가지이며 pytest.ExitCode로 공개되어 있다[T1].

종료 코드 pytest의 뜻 이 루프의 해석과 처리
0 모든 테스트를 모아 통과함 통과. 커밋하고 끝낸다
1 테스트를 모아 실행했고 일부가 실패함 실패. 실패 개수를 세어 진전 여부를 본다

3 실행 중 내부 오류 시작할 때 나오면 환경 문제로 멈춘다
4 명령행 사용 오류. conftest.py를 불러오지 못한 경우를 포함한다 실패로 본다. conftest.py가 불러오는 제품 코드가 깨지면 이 코드가 나온다
5 테스트를 하나도 모으지 못함 판정 불가. 테스트가 지워졌거나 경로가 바뀐 것이므로 테스트 회피를 의심하고 멈춘다

종료 코드 4의 예는 실습에서 직접 본다. jobprep의 tests/conftest.py는 api.main을 불러오므로, 에이전트가 api/jobs.py에 문법 오류를 내면 테스트가 하나도 돌기 전에 4로 끝난다. 이것을 “환경 문제”로 보고 멈추면 루프는 에이전트의 흔한 실수 하나에 매번 멈춘다. 그래서 시작할 때는 4를 받아들이고, 시도 중에도 4를 실패로 셈한다.

실패 개수는 출력의 마지막 줄에서 읽는다.

[파일: ops/loop/fix_until_green.py] (일부)

SUMMARY_PATTERN = re.compile(r"(\d+) (failed|error|errors)\b")


def count_failures(code, output):
    """실패와 오류의 개수. 통과면 0, 개수를 읽지 못하면 999(가장 나쁨)로 본다."""
    if code == 0:
        return 0
    found = SUMMARY_PATTERN.findall(output)
    return sum(int(number) for number, _ in found) if found else 999

예를 들어 마지막 줄이 43 passed in 2.82s(종료 코드 0)이면 0, 2 failed, 41 passed in 5.40s(1)이면 2, 1 failed, 3 passed, 1 error in 0.3s(1)이면 실패와 오류를 더해 2, Interrupted: 1 error during collection(2)이면 1이다. ImportError while loading conftest …(4)처럼 개수가 적히지 않은 출력은 999가 된다.

개수를 읽지 못하면 999로 둔다. “모르면 가장 나쁜 것으로 본다”는 원칙이다. 그래야 문법 오류를 낸 시도가 진전으로 잘못 남지 않는다. 이 원칙은 5-2의 비용 계산에도 똑같이 쓰인다.

판정을 모델이 아니라 테스트에 맡기는 데에는 대가가 있다. 테스트가 정하지 않은 것은 판정되지 않는다. 테스트가 약하면 루프는 약한 테스트를 통과하는 코드를 만들고 “통과”라고 보고한다. 그래서 루프의 품질은 2장의 테스트 품질을 넘지 못한다. 루프를 만들기 전에 테스트부터 만드는 까닭이다.

4-5. 되돌림: git으로 시도 사이의 상태를 관리한다

에이전트가 파일을 고친 뒤 판정이 실패하면, 그 변경을 남길지 버릴지 정해야 한다. 두 전략이 있다.

전략 방법 장점 단점
매번 처음부터 실패한 시도는 모두 버리고, 다음 시도는 늘 시작 상태에서 한다 시도가 서로 독립이다. 잘못된 변경이 쌓이지 않는다 부분적으로 고친 것도 버려진다. 실패가 여럿이면 한 시도에서 모두 고쳐야 한다
진전 누적(이 루프) 실패 개수가 줄어든 시도는 체크포인트 커밋으로 남기고, 줄지 않은 시도만 버린다 여러 실패를 나누어 고칠 수 있다 “실패 개수”가 진전의 척도로 맞지 않는 경우(다른 테스트가 새로 깨짐)를 놓칠 수 있다

이 루프는 진전 누적을 택하였다. 실패 개수가 줄었다는 것은 판정 명령이 낸 사실이므로, 모델의 “고쳤다”는 말과 달리 기계적으로 검증된다. 단점은 루프 설계서에 적고, 다른 테스트가 새로 깨지는 경우는 실패 개수가 줄지 않으므로 되돌려진다는 점을 확인해 둔다.

git 명령은 넷이다.

  1. 루프 시작: git switch -c loop/<실행 이름>으로 시작 커밋에서 루프 전용 브랜치를 만든다. main은 건드리지 않는다.
  2. 진전 또는 통과: git add -A -- <바뀐 파일>과 git commit -m "fix: 루프 … 시도 N …"으로 그 시도의 변경을 체크포인트로 남긴다. 메시지는 3장의 저장소 규약을 따르므로 commit-msg 훅이 켜진 저장소에서도 막히지 않는다.
  3. 진전 없음, 규칙 위반: 먼저 그 시도의 변경을 git diff HEAD로 attempt-N.diff 파일에 남기고, git restore --source=HEAD --staged --worktree -- .로 추적하는 파일을 마지막 커밋(체크포인트) 상태로 되돌린다.
  4. 같은 경우: 새로 생긴 파일을 지운다. git restore는 추적하지 않는 파일을 건드리지 않기 때문이다.

git restore는 작업 트리의 파일을 복원하는 명령이다. --staged는 인덱스를, --worktree는 작업 트리를 복원하고, --source는 복원할 내용을 가져올 커밋을 정한다[G16]. 두 옵션을 다 주면 둘 다 복원한다. 문서는 추적하는 경로를 다루며, 새로 만든(추적하지 않는) 파일은 그대로 둔다. 그래서 루프는 git status가 ??로 보인 파일을 따로 지운다. 지우기 전에 그 시도의 변경을 attempt-N.diff로 남기는 일은 save_diff()가 한다(6-4에서 본다).

[파일: ops/loop/fix_until_green.py] (일부)

def restore(changes):
    """마지막 커밋(체크포인트)의 상태로 되돌린다. 에이전트가 새로 만든 파일은 지운다."""
    git("restore", "--source=HEAD", "--staged", "--worktree", "--", ".")
    for status, path in changes:
        if status == "??":

def commit(changes, message):
    git("add", "-A", "--", *[path for _, path in changes])
    git("commit", "-q", "-m", message)
    return git("rev-parse", "--short", "HEAD").strip()

git clean -fd를 쓰지 않은 까닭이 있다. git clean은 추적하지 않는 파일을 모두 지우므로, 루프가 방금 쓴 기록 파일까지 지운다. 루프는 자기가 확인한 변경 목록에 든 파일만 지운다.

루프가 브랜치를 만드는 까닭은 사람의 승인 지점을 남기기 위해서이다. 통과한 루프의 결과는 loop/<실행 이름> 브랜치에 커밋으로 있고, main에는 아무것도 들어가지 않았다. 사람은 git diff <시작 커밋>..loop/<실행 이름>으로 변경을 보고 병합할지 정한다. 13장에서는 이 브랜치가 풀 리퀘스트가 되고, 사람의 검토가 보호 브랜치의 필수 리뷰가 된다.

4-6. 재시도: 실패 출력의 요약을 넘긴다

다음 시도의 에이전트는 앞 시도를 기억하지 못한다. 루프가 시도마다 새 세션을 열기 때문이다(2-6). 그래서 넘길 정보를 루프가 고른다. 이 루프가 넘기는 것은 두 가지이다.

  1. 지난 판정의 실패 출력 요약. pytest 출력에서 FAILED·ERROR로 시작하는 요약 줄과 E로 시작하는 단언 줄, 그리고 conftest를 불러오지 못했다는 줄만 고른다.
  2. 앞선 시도의 처리 기록. “시도 1: 실패 2개 → 1개, 진전이므로 커밋으로 남김”, “시도 2: 보호 경로를 고쳐 버림” 같은 한 줄씩이다.

[파일: ops/loop/fix_until_green.py] (일부)

def summarize_failures(output, limit=2000):
    """다음 시도에 넘길 실패 출력의 요약: FAILED·ERROR 줄과 E 줄을 앞에서부터, 길이 상한까지."""
    keep = [line.rstrip() for line in output.splitlines()
            if line.startswith(("FAILED ", "ERROR ", "E ")) or "Error while" in line]
    text = "\n".join(keep) if keep else "\n".join(output.strip().splitlines()[-20:])
    if len(text) > limit:
        text = text[:limit] + "\n…(줄임)"
    return text

출력 전체를 넘기지 않고 요약하는 까닭은 셋이다. 첫째, 비용이다. 테스트가 수백 개인 저장소의 출력 전체는 수만 토큰이 될 수 있고, 시도마다 그만큼 입력이 늘어난다. 비용 문서는 수만 줄짜리 기록을 그대로 읽히는 대신 ERROR 줄만 골라 넘기면 컨텍스트가 수만 토큰에서 수백 토큰으로 준다고 예를 든다[C19]. 둘째, 주의이다. 통과한 테스트의 점 수백 개는 판단에 쓸모가 없다. 셋째, 재현이다. 요약 규칙이 코드로 정해져 있으면 같은 출력에서 언제나 같은 요약이 나온다.

2,000자 상한은 이 저장소의 실패 하나가 대략 200~400자이므로 실패 대여섯 개를 담을 수 있게 정한 값이다. 상한에 닿으면 …(줄임)을 붙여, 잘린 것이 있음을 에이전트도 알게 한다. 이 값은 설계서에 근거와 함께 적는다.

넘기지 않기로 한 것도 있다. 앞 시도의 diff와 앞 시도의 응답 전문이다. 앞 시도의 diff를 넘기면 다음 시도가 실패한 방향을 피할 수 있지만, 반대로 그 방향에 끌려갈 수도 있고 지시문이 시도마다 길어진다. 이 루프는 “무엇을 했고 결과가 어땠는가”를 한 줄 기록으로만 넘기고, diff는 사람이 볼 수 있게 파일로만 남긴다(6-4). 어느 쪽이 나은지는 일의 성격에 따라 다르므로, 설계서 6절에 고른 것과 까닭을 적는다.

에이전트가 보호 경로를 고쳐 버려진 경우에는 실패 요약 앞에 그 사실을 덧붙인다. 같은 실수를 되풀이하지 않게 하려는 것이다. 이것도 비결정적 장치이다. 에이전트가 다시 같은 짓을 하면 루프는 다시 버린다.

4-7. 종료: 다섯 가지 끝

루프가 끝나는 방식은 다섯이고, 종료 코드로 구분한다. 루프를 다른 스크립트나 cron, CI가 부를 때 이 코드로 다음 단계를 정한다.

상태 뜻 종료 코드 보고서
green, already_green 판정 통과(처음부터 통과였던 경우 포함) 0 없음. 루프 브랜치를 사람이 검토한다
gave_up 재시도 상한에 닿음 1 있음
precondition 시작 조건 실패(작업 트리, 판정 명령, 에이전트 명령) 2 시도 중에 생긴 경우만
budget, time 비용 상한이나 시간 상한에 닿음 3 있음
suspicious 판정 명령이 테스트를 하나도 모으지 못함 4 있음

루프를 부르는 쪽은 이 코드로 분기한다. 셸이라면 python ops/loop/fix_until_green.py; code=$? 다음에 case $code in 0) … ;; 1|3) … ;; *) … ;; esac처럼 쓴다. 0이면 사람에게 검토할 브랜치가 있다고 알리고, 1과 3이면 보고서를 알리고, 2와 4이면 루프를 다시 부르지 말고 사람을 부른다. CI에서는 0이 아닌 코드가 그 단계를 실패로 표시한다.

0과 그 밖을 나누는 것만으로는 부족하다. 1은 “이 일은 에이전트가 세 번 해도 못 하였다”는 뜻이므로 사람이 원인을 볼 차례이고, 3은 “더 했으면 되었을지도 모른다”는 뜻이므로 예산을 늘릴지가 사람의 결정이다. 4는 루프를 다시 돌리면 안 되는 상태이다. 이 구분이 없으면 cron에 건 루프는 실패할 때마다 같은 일을 되풀이한다.

4-8. 사람 넘김: 보고서와 이슈

0이 아닌 상태로 멈추면 루프는 ops/loop/reports/<실행 이름>.md에 보고서를 쓴다. 보고서는 사람이 무엇을 결정해야 하는지에 맞추어 짜여 있다.

  • 머리: 멈춘 까닭, 시도 수, 쓴 비용, 시작 커밋, 루프 브랜치, 지금 HEAD. 사람은 지금 저장소가 어떤 상태인지 안다.
  • 시도별 기록: 시도마다 에이전트의 끝난 방식, 비용, 바꾼 파일, 판정, 실패 수, 처리. 어느 시도가 무엇을 하였는지 본다.
  • 마지막 실패 출력: 요약된 실패. 원인이 제품 코드인지, 테스트나 환경인지 가린다.
  • 사람에게 묻는 것: 원인, 체크포인트를 살릴지, 다시 돌린다면 무엇을 바꿀지. 다음 행동을 정한다.
  • 이슈로 올릴 때: gh issue create … --body-file 명령. 팀에 알릴지 정한다.

루프는 이슈를 직접 만들지 않는다. 보고서를 사람이 읽고 올리는 것이 이 루프의 설계이다. 이슈를 자동으로 만들면 같은 실패가 반복될 때 이슈가 쌓이고, 보고서에 잘못된 정보가 있으면 그대로 팀에 퍼진다. 이슈를 자동으로 만들려면 같은 제목의 열린 이슈가 있는지 먼저 확인하는 장치가 필요하다. 이 판단은 설계서의 8절에 적는다.

4-9. 루프 기록: JSON 줄

루프의 기록은 JSON Lines(JSON 줄) 형식이다. 이 형식의 규칙은 셋이다. 파일은 UTF-8이고, 한 줄은 유효한 JSON 값 하나이며, 줄의 구분은 \n이다. 권장 확장자는 .jsonl이다[J1].

이 형식이 루프 기록에 맞는 까닭은 셋이다. 한 줄에 사건 하나이므로 시도가 끝날 때마다 덧붙일 수 있고, 루프가 중간에 죽어도 앞의 기록은 온전하다. 줄마다 독립된 JSON이므로 grep으로 줄을 고르고 파이썬으로 한 줄씩 읽을 수 있다. 그리고 Claude Code 자신도 같은 형식을 쓴다. stream-json 출력과 세션의 대화 기록이 모두 줄 단위 JSON이다[C14].

기록에는 네 종류의 사건(event)이 남는다. start(설정 전체), judge(시작 판정), attempt(시도마다), end(끝)이다. 시도 한 줄의 필드는 다음과 같다.

필드 뜻
ts, run_id, event, attempt 시각, 실행 이름, 사건 종류, 시도 번호
agent_exit, agent_status, subtype 에이전트의 종료 코드, 루프가 본 상태(ok, error, timeout, no_json), 결과 객체의 subtype
cost_usd, cost_counted, turns, session_id 보고된 비용, 예산에서 뺀 비용, 턴 수, 세션 아이디
changed, protected 바뀐 파일, 그 가운데 보호 경로
judge_exit, failures 판정 명령의 종료 코드, 실패 개수
decision, commit 처리(commit, checkpoint, restore, reject, no_change), 남긴 커밋
spent_usd 이 시도까지의 누적 비용

기록을 읽는 가장 빠른 방법은 grep이다. grep '"event": "end"' ops/loop/logs/*.jsonl은 실행마다 끝 줄 하나씩을 보여 주고, grep '"decision": "reject"' ops/loop/logs/*.jsonl은 보호 경로를 고쳐 버려진 시도만 모은다. 한 줄이 사건 하나이므로 줄을 고르는 것이 곧 사건을 고르는 것이다. 더 복잡한 집계는 6-8처럼 파이썬으로 한 줄씩 읽는다.

12장에서 이 기록을 모아 에이전트 작업의 성공률과 비용을 보고한다. 그래서 필드 이름을 지금 정해 두고 바꾸지 않는다.

4-10. 지시문의 설계

루프의 지시문은 사람이 대화에서 하는 말과 다르게 써야 한다. 대화에서는 모호한 말을 해도 에이전트가 되묻거나 사람이 바로잡는다. 루프에서는 되물을 사람이 없다. prompt_fix.md는 다음 원칙으로 짰다.

  1. 완료를 명령으로 적는다. “버그를 고쳐라”가 아니라 “python -m pytest -q가 실패한다. 실패한 테스트가 통과하도록 고쳐라”이다. 모범 사례 문서는 Claude에게 통과와 실패로 답하는 검사를 주면 스스로 루프를 닫을 수 있다고 하고, 저장소에 그런 검사가 있으면 CLAUDE.md에 그 명령을 적는 것이 가장 쓸모 있는 한 줄이라고 적는다[C6].
  2. 하지 말 것을 경로로 적는다. “테스트를 함부로 고치지 마라”보다 “tests/, pytest.ini, .claude/, ops/의 파일은 고치지 않는다”가 낫다. 경로로 적은 금지는 루프의 보호 경로 목록과 같은 값에서 채워지므로({PROTECTED}), 지시와 검사가 어긋나지 않는다.
  3. 루프의 일과 에이전트의 일을 나눈다. 커밋, 푸시, 브랜치 전환은 루프의 일이라고 적는다. 에이전트가 이 일을 하면 루프의 되돌림이 깨진다.
  4. 출력의 끝을 정한다. 마지막 줄을 OK 또는 FAIL로 정해 두면 사람이 기록을 훑기 쉽다. 모범 사례 문서의 스크립트 예시도 같은 방식으로 답을 받는다[C6]. 다만 이 말로 판정하지 않는다.
  5. 넘기는 정보를 고정된 자리에 둔다. 실패 요약과 앞선 시도의 기록은 언제나 같은 제목 아래에 들어간다. 시도마다 지시문의 모양이 같아야 시도끼리 비교할 수 있다.

비용 문서도 “이 코드베이스를 개선하라” 같은 모호한 요청은 넓은 탐색을 부르고, 구체적인 요청은 적은 파일만 읽게 한다고 적는다[C19]. 지시문이 구체적일수록 턴과 비용이 준다. 6-5의 비용 상한 경로에서 시도 1이 저장소 전체를 읽느라 예산의 절반을 쓴 것이 그 반대의 예이다.

4-11. 바꿔 끼우는 자리

이 루프에서 에이전트 명령은 환경 변수 AGENT_CMD 한 곳에서만 정해진다. 기본값은 claude이고, 실습에서는 python ops/loop/fake_agent.py를 넣었다. 이렇게 바깥의 의존을 한 자리에서 바꿔 끼울 수 있게 하는 것은 이 과목에서 여러 번 본 설계이다. 기준 저장소의 api/jobs.py는 실행한 날의 날짜를 today() 한 함수에서만 얻어 테스트가 날짜를 고정할 수 있게 하고, api/llm.py는 모든 LLM 호출을 한 함수에 모아 LLM_FAKE=1이면 모의 응답을 낸다. 2장에서 다룬 테스트 더블이 루프에서는 가짜 에이전트가 된다.

바꿔 끼우는 자리가 있으면 세 가지를 얻는다. 첫째, 루프의 모든 경로를 비용 없이 결정적으로 시험할 수 있다. 실제 모델로는 “세 번 연속 실패”나 “시도 상한에 닿음”을 원할 때 만들 수 없다. 둘째, 루프의 테스트가 루프의 설계를 문서처럼 보여 준다(6-7). 셋째, 에이전트를 바꾸어도 루프는 그대로이다. 같은 결과 객체를 내는 다른 에이전트, 예를 들어 9장에서 직접 만드는 에이전트 루프도 이 자리에 넣을 수 있다.

가짜 에이전트의 한계도 분명히 해 둔다. 가짜 에이전트는 실제 에이전트가 할 수 있는 일 가운데 시나리오에 적은 것만 한다. 실제 에이전트는 훅에 막히고, 권한 거부를 받고, 예상하지 못한 파일을 만들고, 세션 중간에 오류를 낸다. 가짜 에이전트로 확인한 것은 “루프가 이런 결과를 받으면 이렇게 처리한다”까지이다. 실제 에이전트가 이런 결과를 내는지는 6-9에서 자기 계정으로 한 번 돌려 확인한다.

5. 상한의 설계

5-1. 재시도 상한

재시도 상한은 무인 반복의 가장 기본적인 안전장치이다. 2026년 2학기판 실습의 retry_loop.py는 상한(MAX_RETRIES = 3)에 닿으면 수동 개입을 요청하고 종료 코드 1로 끝났다. 이 장의 루프도 같은 값 3에서 출발한다.

셋이라는 값에는 경험적인 근거가 있다. 같은 지시와 같은 정보로 세 번 실패한 일은 네 번째에도 실패할 가능성이 크다. 에이전트에게 부족한 것이 시도 횟수가 아니라 정보(요구의 모호함, 테스트의 잘못, 환경 문제)이기 때문이다. 이때 필요한 것은 네 번째 시도가 아니라 사람의 판단이다. 반대로 실패가 여럿이고 하나씩 고쳐지는 경우에는 셋이 모자랄 수 있다. 진전 누적 전략(4-5)은 이 경우를 위해 있다. 상한을 늘리기 전에 보고서의 시도별 기록에서 실패 개수가 줄고 있었는지를 먼저 본다.

재시도 상한과 함께 정할 것이 하나 더 있다. 다시 시도할 때 무엇이 달라지는가이다. 같은 지시문과 같은 정보로 다시 시키면 모델의 출력이 확률적으로 조금 달라질 뿐이다. 이 루프는 시도마다 최신 실패 요약과 앞선 시도의 처리 기록을 넣어 지시문을 바꾼다. 시도마다 무엇이 달라지는지 말할 수 없는 재시도는 같은 동전을 다시 던지는 것과 같다. 설계서 6절은 이 물음에 대한 답이다.

5-2. 비용 상한 두 겹

비용 상한은 두 겹이다.

첫째 겹은 시도 한 번의 상한이다. 루프는 LOOP_RUN_BUDGET_USD(기본값 0.50달러)를 --max-budget-usd로 넘기고, Claude Code가 상한에 닿은 실행을 error_max_budget_usd로 끝낸다. 둘째 겹은 루프 전체의 상한이다. 루프 스크립트가 시도마다 total_cost_usd를 더해 LOOP_BUDGET_USD(1.00달러)에서 남은 예산을 계산한다. 셋째 장치는 다음 시도의 최소 예산이다. 남은 예산이 LOOP_MIN_RUN_BUDGET(0.10달러)보다 적으면 다음 시도를 시작하지 않는다.

시도 한 번의 상한은 남은 예산과 시도 상한 가운데 작은 것으로 정한다. 남은 예산이 0.38달러면 그 시도에는 0.38달러만 준다. 그리고 문서가 말한 대로 지출은 상한을 응답 하나만큼 넘을 수 있으므로(2-5), 루프 전체의 상한도 조금 넘을 수 있다. 이 넘침을 줄이려고 남은 예산이 최소 예산보다 적으면 다음 시도를 시작하지 않는다. 0.02달러로 시도를 시작하면 첫 응답에서 상한을 넘기고 아무것도 못 한 채 끝날 것이기 때문이다.

비용을 알 수 없는 시도도 있다. 시간 상한에 걸려 프로세스를 죽였거나, 출력이 JSON이 아니었거나, 에이전트가 비정상으로 끝난 경우이다. 이 루프는 이때 그 시도의 상한을 모두 쓴 것으로 센다.

[파일: ops/loop/fix_until_green.py] (일부)

    # 비용을 알 수 없으면 그 시도의 상한을 모두 쓴 것으로 센다(보수적으로 센다).
    info["cost_counted"] = info["cost_usd"] if isinstance(info["cost_usd"], (int, float)) else run_budget

0으로 세면 비용을 알 수 없는 시도가 계속될 때 루프는 예산이 줄지 않는다고 믿고 끝없이 돈다. 4-4의 “모르면 가장 나쁜 것으로 본다”와 같은 원칙이다.

예산의 크기는 무엇에 견주어 정하는가. 비용 문서는 기업 배포의 평균이 활동한 날 하루에 개발자 한 명당 약 13달러, 한 달에 150~250달러이며, 사용자의 90%가 하루 30달러 아래라고 적는다[C19]. 테스트 두 개를 고치는 일에 1달러는 그 평균의 한 조각이다. 다만 학생 계정은 구독형일 수 있고, 구독형에서는 total_cost_usd가 청구액이 아니라 사용량의 추정치이다. 그래도 상한으로 쓰기에는 충분하다. 이 값이 클수록 계정의 사용 한도에 빨리 닿는다.

[최신 자료 자리: Claude Code의 평균 비용] 비용 문서의 기업 배포 평균(활동한 날 하루, 한 달, 하루 상위 10%의 경계). 확인할 곳: https://code.claude.com/docs/en/costs. 2026-11-15에 확인한 값: 활동한 날 하루 약 13달러, 한 달 150~250달러, 사용자의 90%가 하루 30달러 미만. 5-6의 하루 최악의 비용 비교도 이 값에 기댄다.

5-3. 턴 상한

--max-turns는 시도 한 번 안에서 모델이 도구를 부르는 횟수를 제한한다. 문서의 셈법은 도구를 부른 턴마다 하나, 도구 없이 답한 마지막 턴에 하나이다. 이 마지막 턴을 셈에 넣지 않으면 실행은 error_max_turns로 끝나고 최종 응답이 없다[C21]. 문서의 예에서 실패하는 테스트를 고치는 일은 테스트 실행, 파일 읽기, 편집과 재실행, 마지막 응답의 네 턴이었다[C21].

jobprep의 실패 하나를 고치는 데 필요한 턴은 대략 테스트 실행 1, 테스트 파일과 제품 코드 읽기 2~3, 편집 1~2, 재실행 1, 마지막 응답 1로 6~8이다. 이 루프의 기본값 15는 그 두 배쯤이다. 턴 상한이 너무 작으면 고칠 수 있는 일을 못 하고 끝나며, 너무 크면 엉뚱한 탐색에 비용을 쓴다. 비용 상한이 이미 있는데 턴 상한을 따로 두는 까닭은, 턴 상한은 “같은 일을 맴도는” 실행을 비용이 크게 쌓이기 전에 끊기 때문이다.

5-4. 시간 상한

시간 상한도 두 겹이다. 시도 한 번은 600초(LOOP_ATTEMPT_TIMEOUT), 루프 전체는 1,800초(LOOP_MAX_SECONDS)이다. 시도의 시간 상한에 닿으면 루프는 에이전트 프로세스를 끝내고, 그 시도를 비용을 알 수 없는 시도로 센다. 헤드리스 문서는 SIGTERM을 받은 실행이 종료 코드 143으로 끝나며 진행 중이던 턴의 결과를 남기지 않는다고 적는다[C14].

비용 상한이 있는데 시간 상한이 왜 필요한가. 비용이 거의 들지 않는 채로 멈춰 있는 실행이 있기 때문이다. 에이전트가 끝나지 않는 명령(개발 서버, 입력을 기다리는 프로그램)을 실행하면 토큰은 쓰지 않은 채 시간만 간다. cron으로 돌리는 루프가 이렇게 멈추면 다음 실행과 겹친다.

이 값들은 루프 설계서의 7절에 그대로 옮기고, 각 값 옆에 근거를 한 문장으로 붙인다. “기본값이라서”는 근거가 아니다. 위 표에서 Claude Code가 지키는 것(시도당 턴과 비용)과 루프 스크립트가 지키는 것(재시도, 전체 비용, 두 시간 상한)을 나누어 보면, 바깥 루프가 왜 따로 있어야 하는지가 다시 드러난다.

5-6. 최악의 경우 계산

상한을 정했으면 그 상한이 허용하는 최악의 경우를 계산해 본다. 상한은 하나씩 보면 작아 보여도 곱하면 커진다.

  • 모델의 판단 횟수: 시도 3 × 턴 15 = 45번. 판단 한 번마다 대화 전체가 입력으로 다시 들어가므로, 시도 안에서는 뒤의 턴일수록 비싸다.
  • 비용: 루프 전체 상한 1.00달러에 응답 하나만큼의 넘침이 더해질 수 있다. 시도 상한을 0.50달러로 두었으므로, 시도 하나가 혼자 예산의 절반까지 쓸 수 있다.
  • 시간: 시도 3 × 600초 = 1,800초로, 루프 전체 상한과 같다. 판정 명령과 git 작업의 시간이 더해지므로 실제로는 전체 시간 상한이 먼저 닿을 수 있다.
  • 하루 동안: 이 루프를 cron으로 한 시간마다 돌리면 하루 최악의 비용은 24달러이다. 비용 문서가 적은 개발자 한 명의 평균 하루 비용(약 13달러)의 두 배쯤이다[C19].

마지막 줄이 정기 실행을 신중하게 정해야 하는 까닭이다. 루프 한 번의 상한은 루프 한 번만 지킨다. 하루, 한 달의 상한은 실행 간격과 계정의 지출 한도가 지킨다. 설계서 7절에 루프 한 번의 상한을 적었다면, 12절에는 그 루프를 얼마나 자주 돌리는지와 그에 따른 최악의 하루 비용을 함께 적는다.

루프 테스트는 jobprep이 아니라 임시 폴더의 작은 저장소(calc.py와 버그 두 개)에서 루프를 돌린다. 세 경로(성공, 3회 실패, 비용 상한), 세부(실패 출력의 전달, 알 수 없는 비용, 시간 상한, 테스트 회피), 시작 조건(더러운 작업 트리, 처음부터 통과, 에이전트 명령 없음), 기록 형식, 함수 단위(실패 개수 세기, 실패 요약, 보호 경로 판단)의 다섯 묶음이다. 테스트의 이름은 python -m pytest --collect-only -q ops/loop/tests로 볼 수 있으며, 설계서의 항목 하나가 테스트 하나 이상과 짝을 이루는지 대조해 본다.

집계에서 cheat-1과 cheat-2는 같은 시나리오인데 둘 다 green이다. 하나는 잘못된 통과이다. 기록의 status만 세면 성공률이 같아 보인다. 12장에서 에이전트의 성공률을 잴 때 “무엇이 통과로 셈되는가”를 먼저 정해야 하는 까닭이다. 가짜 에이전트의 숫자는 시나리오가 정한 것이므로 답 자체에는 뜻이 없다. 같은 집계를 6-9의 실제 기록에 돌릴 수 있게 코드를 갖추어 두는 것이 목적이다.

6-12. 핵심 실습 복기: 판정은 루프가, 결정은 사람이

  3. 멈추는 방식이 사람의 다음 일을 정한다. 종료 코드 1은 원인을 볼 차례, 3은 예산을 정할 차례, 2와 4는 루프를 다시 부르지 말 차례이다. 보고서와 attempt-N.diff가 그 판단의 재료이다.

7. [선택] 파이프라인: 수집, 요약, 통지

7-1. 파이프라인의 구성

루프만이 자동화의 모양은 아니다. 판정하고 되돌릴 필요가 없는 일, 곧 입력을 받아 한 번 처리하고 결과를 넘기는 일은 파이프라인으로 짠다. 2026년 2학기판은 실습 서버의 기록을 claude -p에 파이프로 넘겨 요약하는 골격을 다루었다. 이 장은 그 골격을 jobprep의 운영 기록(logs/)에 맞추고, 단계마다 성질을 나누어 설계한다.

단계 하는 일 성질 실패하면
수집 logs/*.log에서 그날의 WARNING·ERROR 줄만 고른다 결정적(grep) 입력 폴더가 없으면 종료 코드 2
요약 고른 줄을 에이전트에 넘겨 원인별로 묶게 한다 비결정적(모델) 에이전트가 실패하거나 결과를 읽지 못하면 “수동 확인 필요”를 쓰고 종료 코드 1
통지 요약을 ops/loop/reports/digest-<날짜>.md에 쓴다 결정적(파일 쓰기) 실제 알림(메일, 메신저)으로 바꿀 때 이 단계만 고친다

비결정적 단계는 가운데 하나뿐이다. 앞뒤를 결정적으로 짜면 모델이 다르게 답해도 파이프라인의 모양은 흔들리지 않는다. 경고와 오류가 하나도 없는 날에는 모델을 부르지 않고 “이상 없음”을 쓴다. 부를 필요가 없는 호출은 하지 않는 것이 비용 설계의 첫째이다.

7-2. digest.sh 읽기

[파일: ops/loop/digest.sh] (요약 단계)

PROMPT="표준 입력은 웹 서비스의 운영 기록 가운데 경고와 오류 줄이다. 원인별로 묶어 심각한 순서로 3줄 이내의 목록으로 요약하라. 각 줄에 건수와 시각 범위를 붙여라. 기록에 없는 원인을 지어내지 마라."
JSON=$(printf '%s\n' "$EVENTS" | $AGENT_CMD -p "$PROMPT" --output-format json --tools "" --max-turns 1 --max-budget-usd 0.10)
STATUS=$?

if [ $STATUS -ne 0 ]; then
    printf '# %s 운영 요약\n\n요약 실패: 수동 확인 필요 (에이전트 종료 코드 %s)\n' "$DAY" "$STATUS" > "$OUT"
    echo "[digest] 요약 실패(종료 코드 $STATUS) → $OUT" >&2
    exit 1
fi

이 단계의 플래그는 루프의 것과 다르다. 요약에는 도구가 필요 없다. 읽을 것은 표준 입력으로 이미 넘겼다. 그래서 --tools ""로 내장 도구를 모두 끄고[C15], 턴도 1로 묶는다. 도구가 없으면 권한 설계도 필요 없다. 파일을 읽을 수도, 명령을 실행할 수도 없기 때문이다. 허용할 도구를 고르는 일의 끝은 “도구가 필요 없게 입력을 미리 만들어 주는 것”이다.

$AGENT_CMD에 따옴표를 붙이지 않은 것은 의도이다. 셸은 따옴표 없는 변수를 빈칸에서 나누므로, AGENT_CMD="python ops/loop/fake_agent.py"가 명령 python과 인자 ops/loop/fake_agent.py로 나뉘어 실행된다. 따옴표를 붙이면 빈칸까지 포함한 하나의 이름으로 실행하려다 실패한다. 대신 경로에 빈칸이 든 명령은 이 방식으로 넣을 수 없다. 루프 스크립트(파이썬)는 같은 문제를 shlex.split()으로 푼다.

스크립트의 맨 위에는 set -uo pipefail이 있다. -u는 정의하지 않은 변수를 쓰면 오류로 멈추게 하고, -o pipefail은 파이프의 중간 명령이 실패하면 파이프 전체를 실패로 만든다. -e(아무 명령이나 실패하면 즉시 멈춤)는 넣지 않았다. grep이 아무것도 찾지 못하면 종료 코드 1을 내는데, 그것은 오류가 아니라 “이상 없음”이기 때문이다. 그래서 수집 단계의 grep에는 || true를 붙이고, 요약 단계의 종료 코드는 $?로 직접 받아 분기한다. 2026년 2학기판의 과제였던 종료 코드 분기가 이 부분이다.

요약 프롬프트의 마지막 문장 “기록에 없는 원인을 지어내지 마라”와, 결과 파일의 “원문 대조는 사람이 한다”는 같은 문제를 다룬다. 자동화된 요약도 검증 대상이다. 결과 파일은 사람이 기록 원문과 대조하기 전까지는 초안이다.

# 2027-09-08 운영 요약

요약 실패: 수동 확인 필요 (에이전트 종료 코드 1)

같은 실패를 가짜 에이전트로도 만들 수 있다. fail 시나리오의 첫 시도는 4턴이 걸리도록 적혀 있어, 턴 상한 1에 닿아 error_max_turns로 끝난다(FAKE_SCENARIO=fail로 바꾸어 실행해 본다). 실패한 날의 결과 파일이 성공한 날의 파일을 덮어쓴 것에 주목한다. 통지 단계를 실제 알림으로 바꿀 때는 실패도 알림이 가야 한다. 실패를 조용히 넘기는 파이프라인은 “아무 일도 없었다”와 “확인하지 못하였다”를 구분하지 못한다.

실제 에이전트의 요약은 교수가 AGENT_CMD 없이 DIGEST_DAY=2027-09-08 bash ops/loop/digest.sh logs로 시연하고, 결과 파일을 ~/kits/Agent_08주차/실습재료/시연기록/digest-2027-09-08.md로 배포한다. 학습자는 그 요약이 기록 원문과 맞는지 grep -h "^2027-09-08" logs/*.log | grep -E "WARNING|ERROR"의 출력과 직접 대조하고, 맞지 않는 줄이 있으면 설계서 10절의 “하나 더”에 적는다. 요약 모델은 원문에 없는 원인을 그럴듯하게 덧붙일 수 있으므로, 대조는 요약의 줄마다 원문의 줄을 하나씩 짝지어 본다. 7-3을 돌렸다면 결과 파일 ops/loop/reports/digest-*.md는 6-11 뒤에 생긴 것이므로 따로 커밋하거나 지운다. digest.sh는 Windows에서 파이썬의 출력이 UTF-8이 되도록 PYTHONUTF8=1을 스스로 켠다.

7-3 복기. 세 경우의 종료 코드(0, 0, 1)가 파이프라인의 세 상태(요약함, 부를 필요 없음, 확인하지 못함)를 가른다. 모델을 부르는 단계는 가운데 하나이고, 그 단계가 실패해도 결과 파일에는 “수동 확인 필요”가 남는다. 루프와 달리 되돌릴 것이 없으므로, 이 파이프라인의 안전장치는 상한(--max-turns 1, --max-budget-usd 0.10)과 도구를 모두 끈 것(--tools ""), 그리고 실패를 조용히 넘기지 않는 종료 코드이다.

7-4. 통지의 설계

키트의 통지 단계는 파일을 쓰는 데서 그친다. 실제 운영에서는 이 파일을 메일이나 팀 메신저로 보낸다. 그 단계를 붙일 때 정할 것이 셋 있다.

첫째, 무엇을 보내는가. 요약 전문을 보내면 읽는 사람이 원문 대조의 책임을 잊기 쉽다. 요약과 함께 건수, 대상 날짜, 원문 기록의 위치, “원문 대조는 사람이 한다”는 문장을 함께 보낸다. 비용과 세션 아이디도 붙여 두면 요약이 이상할 때 그 실행을 다시 열어 볼 수 있다.

둘째, 언제 보내는가. 매일 “이상 없음”을 보내면 사람은 곧 읽지 않게 된다. 반대로 이상이 있을 때만 보내면, 파이프라인이 아예 돌지 않은 날과 이상이 없는 날을 구분할 수 없다. 흔한 절충은 이상이 있거나 요약이 실패한 날에는 바로 보내고, 이상이 없는 날은 주 1회 묶어서 “이번 주 n일 실행, 이상 없음 n일”을 보내는 것이다.

셋째, 어디로 보내는가. 메신저의 웹훅 주소나 메일 계정은 비밀 정보이다. 스크립트나 crontab 줄에 적지 않고 .env처럼 저장소 밖의 파일이나 환경 변수에서 읽는다. 비밀 정보의 관리는 11장에서, CI의 비밀 정보는 13장에서 다룬다. 같은 날 파이프라인을 다시 돌리면 결과 파일이 덮어쓰인다는 점(7-3)도 통지와 함께 생각한다. 다시 돌린 결과를 다시 보낼지는 정해 두어야 한다.

8-1. 선택지

루프와 파이프라인을 정해진 때에 돌리는 방법은 여럿이다. Claude Code 문서는 세션 안의 /loop, 내 컴퓨터에서 도는 Desktop 예약 작업, Anthropic의 클라우드에서 도는 예약 작업을 비교하고, 어떤 세션과도 무관하게 살아남아야 하는 예약에는 클라우드 예약 작업, Desktop 예약 작업, GitHub Actions를 권한다[C23]. 여기에 macOS와 리눅스의 cron을 더해 비교한다.

방법 어디서 도는가 세션이 열려 있어야 하는가 저장소 파일 최소 간격 이 과목에서
cron macOS·리눅스 PC(Windows에는 없고 작업 스케줄러가 같은 자리) 아니요, 컴퓨터는 켜져 있어야 함 내 컴퓨터의 작업 폴더 1분 교수 시연. 줄은 설계서 12절에 쓴다
/loop 내 컴퓨터, 열린 Claude Code 세션 예. 세션이 쉬고 있을 때만 실행 세션의 작업 폴더 1분 짧은 감시(빌드, 배포 확인)
Desktop 예약 작업 내 컴퓨터(Claude 데스크톱 앱) 아니요, 컴퓨터는 켜져 있어야 함 내 컴퓨터의 파일 문서의 표 참조 다루지 않음

클라우드 예약 작업은 연구 미리보기 단계이며 claude.ai 계정에 속하고, 실행이 계정의 사용량과 한도를 쓴다[C25]. 변경은 claude/로 시작하는 브랜치에 푸시된다[C25]. 계정 단위이므로 팀이 공유하는 운영 루프의 수단으로는 맞지 않는다. 이 과목은 cron을 교수 시연으로 보이고, 팀이 함께 쓰는 예약 실행은 13장의 GitHub Actions로 한다.

8-2. cron (교수 시연)

cron은 macOS와 리눅스의 정기 실행 데몬이다. Windows에는 cron이 없다(부록 A-1-2). 이 절의 등록 명령은 교수가 macOS나 리눅스 PC에서 시연하고, 학생은 crontab 줄을 설계서 12절에 쓰는 데까지 한다. crontab의 한 줄은 다섯 개의 시각 필드(분, 시, 일, 월, 요일)와 명령으로 이루어진다[U1]. 평일 아침 8시 30분에 기록 요약을 돌리는 줄은 다음과 같다.

파일: crontab의 한 줄 
30 8 * * 1-5 cd $HOME/agent-lab/jobprep && PATH=$HOME/.local/bin:/usr/local/bin:/usr/bin:/bin bash ops/loop/digest.sh logs >> ops/loop/logs/cron-digest.log 2>&1

cron이 명령을 실행하는 환경은 대화형 셸과 다르다. crontab(5) 문서는 SHELL이 /bin/sh로 정해지고, HOME과 LOGNAME은 crontab 주인의 계정 정보에서 온다고 적는다[U1]. PATH의 기본값은 그 문서에 나오지 않으므로, 쓰는 프로그램이 있는 폴더를 줄 안에서 직접 정한다. claude가 어디에 설치되었는지는 command -v claude로 확인해 그 폴더를 PATH에 넣는다. 명령 안의 %는 cron에서 줄바꿈으로 바뀌고 그 뒤는 표준 입력으로 넘어가므로[U1], date +%F 같은 명령을 crontab 줄에 직접 쓰면 안 된다. digest.sh가 날짜를 스스로 계산하게 한 까닭이다.

함정 증상 대책
PATH가 짧다 claude: command not found가 기록 파일에 남는다 줄 안에서 PATH를 정하거나 절대 경로를 쓴다
작업 폴더가 다르다 logs/나 ops/를 찾지 못한다 줄 맨 앞에서 cd한다
출력이 사라진다 실패해도 아무 흔적이 없다 >> 기록파일 2>&1로 표준 출력과 오류를 모은다
% 명령이 중간에서 잘린다 줄 안에 %를 쓰지 않는다
로그인이 끊긴다 claude -p가 인증 실패로 끝난다 요약 실패가 기록에 남는지 확인하고, 로그인 상태를 주기적으로 본다
실행이 겹친다 앞 실행이 끝나기 전에 다음 실행이 시작한다 시간 상한을 간격보다 짧게 둔다. 필요하면 flock으로 잠근다

등록은 crontab -e로 편집기를 열어 한 줄을 넣거나, 다음처럼 기존 목록에 덧붙인다. 교수 화면에서 이 과정을 본다.

등록한 줄을 지우려면 crontab -e에서 그 줄을 지운다. crontab -r은 목록 전체를 지우므로 쓰지 않는다. Windows에서 같은 일을 하는 작업 스케줄러(schtasks, 「작업 스케줄러」 앱)는 이 과목에서 다루지 않는다. 등록하는 도구가 달라도 함정(작업 폴더, PATH, 출력이 사라짐, 로그인이 끊김, 실행이 겹침)은 위 표와 같다.

fix_until_green.py를 cron에 거는 것은 더 신중해야 한다. 루프는 브랜치를 만들고 커밋한다. 아무도 보지 않는 시각에 돌면 루프 브랜치가 쌓이고, 보고서를 읽는 사람이 없다. 루프를 정기적으로 돌린다면 보고서가 누구에게 어떻게 가는지(통지 단계)를 먼저 정한다. 그 전까지 루프는 사람이 시작하고, 정기 실행은 결과를 사람이 읽기만 하면 되는 파이프라인에 둔다.

8-3. 세션 안의 루프: /loop와 /goal

Claude Code의 대화 세션 안에도 루프를 만드는 명령이 둘 있다. 둘 다 이 장의 스크립트와 같은 문제를 다른 자리에서 푼다.

/loop는 프롬프트를 일정 간격으로 다시 실행한다. /loop 5m 배포가 끝났는지 확인하라처럼 간격을 주면 cron 식으로 바꾸어 예약하고, 간격을 빼면 Claude가 매번 1분에서 1시간 사이의 간격을 스스로 고른다[C23]. 세션이 열려 있고 쉬고 있을 때만 실행되며, 반복 작업은 만든 지 7일 뒤에 마지막으로 한 번 실행되고 스스로 지워진다. 문서는 이 만료가 잊힌 루프가 돌 수 있는 기간을 묶어 둔다고 설명한다[C23]. 한 세션에 예약 작업은 50개까지이다[C23]. 7일 만료는 이 장의 시간 상한과 같은 생각이다.

/goal은 완료 조건을 정하면 조건이 충족될 때까지 턴을 이어 간다. 판정은 작은 모델이 대화를 읽고 한다. 문서는 조건을 Claude 자신의 출력으로 보일 수 있는 것으로 쓰라고 하고(“npm test가 0으로 끝난다”처럼), 실행 시간을 묶으려면 조건에 “20턴 뒤에는 멈춘다” 같은 절을 넣으라고 권한다[C24]. 비인터랙티브 모드에서도 claude -p "/goal …"로 쓸 수 있다[C24].

두 방법은 서로 대신하지 않는다. 사람이 지켜보며 큰 작업을 끝까지 몰고 갈 때는 /goal이 편하다. 사람이 없는 시각에 돌고, 무엇을 했는지 나중에 검토해야 하는 일에는 판정과 상태와 기록을 스크립트가 쥐는 쪽이 맞다.

8-4. 예약 실행을 지켜보는 법

예약 실행은 실패해도 소리가 나지 않는다. cron은 명령의 출력을 메일로 보내지만(MAILTO)[U1], 개인 PC에는 메일을 보낼 장치가 대개 없고 있어도 그 메일을 읽는 사람이 없다. 그래서 예약 실행에는 “돌았는가”를 확인하는 장치를 따로 둔다.

가장 단순한 것은 결과 파일의 날짜이다. digest.sh는 매번 digest-<날짜>.md를 쓰므로, ls -t ops/loop/reports/digest-*.md | head -1이 그날 날짜의 파일을 보이지 않으면 그날은 돌지 않은 것이다. crontab 줄에서 출력을 모은 ops/loop/logs/cron-digest.log의 끝부분(tail -5)에는 [digest]로 시작하는 줄이 실행마다 남는다. 두 가지를 아침에 한 번 보는 것이 이 장의 수준에서 할 수 있는 감시이다.

그 다음 단계는 “돌지 않았다”를 다른 시스템이 알려 주게 하는 것이다. 정해진 시간 안에 신호가 오지 않으면 경보를 내는 방식(하트비트)이 흔하다. 12장의 관측에서 실행 기록을 모으는 방법을 다루고, 13장의 GitHub Actions에서는 실행 이력이 저장소의 화면에 남는다. 예약 실행을 하나 더할 때마다 그것을 누가, 어떻게 지켜볼지를 설계서 12절에 함께 적는다.

9. 루프가 잘못될 때

9-1. 무한 반복

상한이 없는 루프는 끝나지 않는다. 상한이 있어도 같은 실패를 상한까지 되풀이하는 것은 낭비이다. 이 장의 루프는 재시도 상한, 전체 시간 상한, 비용 상한이 각각 독립적으로 반복을 끊는다. 셋 가운데 하나만 있으면 그것이 고장 났을 때 끊을 것이 없다.

Claude Code 안의 반복 장치에도 같은 고려가 들어 있다. Stop 훅이 종료 코드 2로 Claude의 종료를 막아 계속 일하게 할 수 있지만, 도구 호출 없이 여덟 번 연속으로 막으면 Claude Code가 다음 막기를 무시하고 턴을 끝낸다[C6]. /goal도 Claude가 여러 턴 동안 도구를 쓰지 않고 평가에만 답하면 루프를 멈추고 경고를 낸다[C24]. 진전 없이 도는 것을 알아채는 장치가 반복 장치마다 붙어 있는 것이다.

이 장의 루프에 더할 수 있는 장치로는 “같은 실패 요약이 두 번 연속이면 멈춘다”가 있다. 실패 요약이 같다는 것은 에이전트가 같은 자리에서 맴돈다는 신호이다. 재시도 상한이 3이면 효과가 작지만, 상한을 늘릴 때는 함께 넣는다. 설계서 10절에 넣을지를 적는다.

9-2. 테스트 회피

테스트로 판정하는 루프에서 가장 조용한 실패는 테스트 회피이다. 6-6에서 본 기대값 변경 말고도 여러 모양이 있다.

표의 둘째 줄은 2장의 테스트 동결과 이어진다. 테스트 동결은 테스트 파일의 지문과 테스트의 수를 기준선 파일에 적어 두고, 달라지면 실패하게 하는 검사였다. 루프의 보호 경로 검사는 “테스트 파일이 바뀌었는가”를, 테스트 동결은 “테스트가 여전히 같은 것을 확인하는가”를 본다. 앞의 것은 루프 안에서, 뒤의 것은 테스트 묶음 안에서 작동하므로, 두 장치는 서로를 대신하지 않고 겹친다.

마지막 두 줄이 중요하다. 특수 처리는 제품 코드 안에서 일어나므로 경로로 막을 수 없다. 통과한 루프의 결과도 사람이 diff를 읽어야 하는 까닭이다(4-5). 루프 자체를 조작하는 것은 판정하는 쪽을 바꾸는 것이므로, 루프가 쓰는 파일은 모두 에이전트의 손이 닿지 않는 곳에 둔다.

9-3. 비용 폭주

비용이 상한 없이 늘어나는 경로는 대개 셋이다.

  • 시도 수 × 시도당 비용. 상한 없이 재시도하면 끝없이 는다. 재시도 상한과 루프 전체 비용 상한이 막는다.
  • 컨텍스트의 성장. 실패 출력 전체를 시도마다 붙이거나 세션을 이어 가면 시도마다 입력이 커진다. 실패 요약과 길이 상한(4-6), 시도마다 새 세션(2-6)이 막는다.
  • 동시 실행. cron이 앞 실행과 겹치거나 여러 저장소에서 같은 루프가 돌면 비용이 곱해진다. 시간 상한, 잠금, 계정 단위의 지출 한도가 막는다.

비용 문서는 긴 세션에서 사용량이 늘어나는 까닭으로 긴 컨텍스트, 캐시 누락, 세션에 걸린 예약 작업(쉬는 동안에도 컨텍스트 전체를 보낸다)을 든다[C19]. 세션 안의 /loop를 긴 대화에 걸어 두지 말라는 모범 사례 문서의 경고도 같은 까닭이다[C6]. 이 장의 루프는 시도마다 새 세션으로 시작하므로 앞 시도의 컨텍스트가 쌓이지 않는다.

9-4. 그 밖의 실패

  • 판정의 비결정성. 같은 코드에서 테스트가 때로 통과하고 때로 실패한다(시각, 네트워크, 실행 순서에 기대는 테스트). 루프는 이 흔들림을 진전이나 퇴보로 잘못 읽는다. 테스트를 고정해야 한다. jobprep은 today()를 바꿔 끼우고 모의 모드로 LLM을 부르지 않는다.
  • 환경 오염. 시도가 만든 파일, 캐시, 설치한 패키지가 다음 시도에 남는다. 되돌림이 새 파일까지 지우고, 패키지 설치는 허용하지 않는다.
  • 에이전트 명령의 변화. Claude Code가 갱신되어 플래그나 기본값이 바뀐다(3-1의 -p 기본 모드가 그 예이다). 루프가 기본값에 기대지 않고 모든 플래그를 명시하고, 13장에서 버전을 고정한다.
  • 입력에 숨은 지시. 테스트 출력, 기록, 이슈 본문에 에이전트를 조종하는 문장이 섞인다. 11장의 간접 프롬프트 주입이다. 이 장의 루프는 허용 도구가 작아 피해 범위가 작다.

마지막 줄은 11장의 예고이다. 루프는 테스트 출력을 그대로 지시문에 붙인다. 테스트 출력에는 테스트가 다루는 데이터가 섞일 수 있다. 공고 본문처럼 바깥에서 온 글이 테스트 출력에 실리면, 그 글 속의 문장이 에이전트에게는 지시처럼 읽힐 수 있다. 허용 도구를 최소화하는 일은 비용과 실수를 줄일 뿐 아니라, 이런 조종이 성공했을 때의 피해 범위를 줄인다.

9-5. 루프를 고치는 순서

루프가 기대대로 돌지 않을 때 상한부터 늘리는 것은 흔한 실수이다. 상한을 늘리면 같은 실패를 더 비싸게 되풀이할 뿐이다. 보고서와 기록을 읽은 뒤 다음 순서로 고친다.

  1. 판정을 의심한다. 판정 명령이 정말 원하는 것을 재는가. 테스트가 약하거나 흔들리면 무엇을 고쳐도 소용이 없다. 2장의 테스트로 돌아간다.
  2. 입력을 고친다. 지시문이 완료 조건, 금지, 맥락을 담고 있는가. 실패 요약이 원인을 가리킬 만큼의 정보를 담는가. 6-5처럼 에이전트가 탐색에 예산을 쓰면 지시문에 파일 이름과 함수 이름을 더 적는다.
  3. 권한을 고친다. 기록의 permission_denials나 에이전트의 응답에서 필요한 도구가 막혔는지 본다. 막혔다면 그 도구를 가장 좁은 규칙으로 더한다. 넓게 열지 않는다.
  4. 상한을 고친다. 위 셋을 확인한 뒤에도 진전이 있었는데 상한에 닿았다면, 그때 상한을 늘린다. 보고서의 시도별 실패 수가 줄고 있었는지가 근거이다.
  5. 루프로 돌리지 않는다. 위를 다 해도 안 되면 그 일은 1-6의 기준에 맞지 않는 것이다. 사람이 대화형 세션에서 한다.

이 순서는 기록이 있어야 따를 수 있다. 시도별 지시문, 버린 시도의 diff, 판정의 종료 코드, 비용이 모두 남아 있으므로, 루프가 왜 실패했는지를 다시 돌리지 않고도 분석할 수 있다. 6-9의 실제 실행이 통과하지 못했다면 그 기록으로 이 순서를 한 번 따라가 본다.

8절과 9절을 읽었으면 루프 설계서의 남은 두 절을 채운다. 10절(실패 양상과 대책)은 9-1~9-4의 표에서 이 루프에 해당하는 행과 6-6의 테스트 회피를, 12절(예약 실행)은 8-1의 선택지와 8-2의 crontab 줄(cd, PATH, 출력 리다이렉션)과 5-6의 하루 최악 비용을 근거로 한다.

터미널

git commit -m "docs(ops): 루프 설계서 10절과 12절"

10. [선택] GitHub Actions에서 같은 루프

이 절은 [선택]이며 읽기만 한다. 13장에서 실제로 만든다.

10-1. 같은 구조, 다른 자리

13장에서 다룰 지속적 통합은 이 장의 루프를 GitHub의 실행기로 옮긴 것으로 볼 수 있다. Claude Code의 GitHub Actions 연동은 저장소의 워크플로 안에서 Claude Code를 실행하는 액션 anthropics/claude-code-action@v1이다. prompt 입력을 주면 언급을 기다리지 않고 바로 실행하는 자동화 모드가 되고, claude_args로 명령행 인자를 넘긴다[C20]. 인증은 저장소의 비밀 정보 ANTHROPIC_API_KEY(API 키) 또는 CLAUDE_CODE_OAUTH_TOKEN(구독 토큰)으로 한다[C20].

이 장의 루프 GitHub Actions에서

--max-turns, --allowedTools claude_args: "--max-turns 15 --allowedTools ..."

문서는 비용을 줄이는 방법으로 claude_args에 --max-turns를 두어 반복을 제한하고, 워크플로 수준의 시간 제한과 GitHub의 동시 실행 제어를 쓰라고 권한다[C20]. GitHub의 워크플로 문법 문서는 예약 워크플로가 기본적으로 UTC로 돌고 가장 짧은 간격이 5분이며, concurrency가 같은 그룹의 작업을 한 번에 하나만 돌게 한다고 적는다[G13].

10-2. 워크플로의 모양 (읽기만)

다음은 13장에서 다룰 워크플로의 모양이다. 이 장에서는 실행하지 않는다. 공식 문서의 예약 실행 예시를 이 장의 상한과 권한에 맞추어 고친 것이다.

[파일: .github/workflows/fix-loop.yml] (13장 예고, 읽기만)

name: Fix failing tests (예고)
on:
  workflow_dispatch:          # 사람이 버튼으로 시작한다
jobs:
  fix:
    runs-on: ubuntu-latest
    timeout-minutes: 30       # 루프 전체 시간 상한
    concurrency:
      group: fix-loop         # 같은 루프가 겹쳐 돌지 않게
    permissions:
      contents: write
      pull-requests: write
      id-token: write
    steps:
      - uses: actions/checkout@v6
      - uses: anthropics/claude-code-action@v1
        with:
          anthropic_api_key: ${{ secrets.ANTHROPIC_API_KEY }}
          prompt: "python -m pytest -q가 실패한다. tests/는 고치지 말고 제품 코드를 고쳐 풀 리퀘스트를 열어라."
          claude_args: |
            --max-turns 15
            --allowedTools "Read,Edit,Bash(python -m pytest *)"

[최신 자료 자리: 워크플로의 액션 판] anthropics/claude-code-action과 actions/checkout의 주 판(위 예시의 @v1, @v6)과 claude_args, 인증 입력의 이름. 확인할 곳: https://code.claude.com/docs/en/github-actions, 각 액션의 GitHub 저장소. 2026-11-14에 문서의 예시에서 확인한 값이다. 13장에서 실행하기 전에 다시 확인한다.

[그림 자리: GitHub Actions의 실행 화면] 저장소의 Actions 탭에서 Fix failing tests 워크플로를 수동으로 실행한 화면. Run workflow 단추, 실행 목록, 작업의 시간 상한과 단계 로그가 보이게 찍는다. 13장에서 실제로 실행한 뒤 찍는다. 찍을 곳: 브라우저, github.com의 학습자 저장소.

이 모양에는 이 장의 루프가 가진 것 가운데 빠진 것이 있다. 판정 뒤의 되돌림, 시도별 기록, 보호 경로 검사이다. 액션 한 번은 시도 한 번이다. 13장에서는 이 빈자리를 CI의 필수 검사(테스트가 통과해야 병합 가능)와 보호 브랜치(사람의 리뷰 없이 병합 불가)로 채운다. 판정을 에이전트의 바깥에 두는 원칙은 그대로이다.

문서는 예약 실행이 기본 브랜치에서만 돌고, 공개 저장소에서는 60일 동안 활동이 없으면 예약이 꺼진다고 적는다. 또 봇이 트리거한 실행은 allowed_bots에 넣지 않으면 거부하여, 봇끼리 Claude를 서로 부르는 반복을 막는다[C20]. 무한 반복을 막는 장치가 여기에도 있다.

10-3. 로컬 루프를 CI로 옮길 때 바뀌는 것

같은 루프라도 내 PC에서 돌 때와 GitHub의 실행기에서 돌 때 바뀌는 것이 있다.

  • 인증. 내 PC에서는 학생 계정의 로그인을 쓴다. CI에서는 사람이 로그인할 수 없으므로 API 키나 구독 토큰을 저장소의 비밀 정보로 넣는다. 키는 워크플로 파일에 적지 않고 secrets로만 참조한다[C20].
  • 상태. 실행기는 실행마다 저장소를 새로 받는다. 루프 브랜치, 기록, 보고서가 다음 실행에 남지 않는다. 기록을 남기려면 실행의 산출물로 올리거나 풀 리퀘스트에 붙여야 한다.
  • 설정의 출처. 실행기의 사용자 폴더에는 아무 설정도 없다. 저장소의 .claude/settings.json과 CLAUDE.md만 읽힌다. 어느 컴퓨터에서나 같은 결과가 필요하면 --bare로 시작하고 필요한 것만 명령행으로 넘긴다(2-7).
  • 비용의 주인. 학생 계정의 사용량이 아니라 저장소에 넣은 키의 주인(학과의 작업 공간)에 비용이 쌓인다. GitHub Actions의 실행 시간도 따로 든다[C20]. 시간 제한과 동시 실행 제어가 비용 상한의 일부가 된다.
  • 승인. 로컬 루프에서는 사람이 루프 브랜치를 보고 병합하였다. CI에서는 보호 브랜치와 필수 리뷰가 그 일을 강제한다. 사람의 승인이 습관이 아니라 저장소의 규칙이 된다.

바뀌지 않는 것은 설계서의 뼈대이다. 판정은 기계가 하고, 상한은 바깥에서 지키고, 기록은 남기고, 되돌릴 수 없는 일은 사람이 승인한다.

정리

  • 루프 엔지니어링은 에이전트의 실행을 반복 구조로 설계하는 일이다. 입력, 실행, 판정, 되돌림, 재시도, 종료의 여섯 부분을 나누어 정한다.
  • 판정은 기계가 한다. 에이전트의 결과 객체는 “끝까지 갔는가”를, 판정 명령의 종료 코드는 “고쳐졌는가”를 알려 준다. 둘은 다르다.
  • 헤드리스 실행의 권한은 허용 도구의 최소화와 dontAsk 같은 명시적 권한 모드로 짠다. 거부 규칙은 보안 경계가 아니므로 결과를 git으로 다시 확인한다.
  • 상한은 겹으로 둔다. 재시도, 턴, 비용, 시간 상한을 Claude Code와 루프 스크립트가 나누어 지키고, 모르는 값은 가장 나쁜 것으로 센다.
  • git은 시도 사이의 상태를 관리한다. 루프 브랜치에서 진전은 커밋으로 남기고, 진전이 없거나 규칙을 어긴 시도는 git restore로 버린다. 병합은 사람이 한다.
  • 루프의 모든 시도는 JSON 줄로 기록하고, 멈추면 사람이 결정할 것을 담은 보고서를 남긴다.
  • 정기 실행은 결과를 사람이 읽는 파이프라인부터 건다. cron, /loop, 예약 작업, GitHub Actions는 어디서 도는지와 무엇이 살아남는지로 고른다.

개념 점검

  1. 이 장의 루프에서 에이전트의 결과 객체가 subtype: "success"이고 응답 끝이 OK인데도 그 시도를 되돌리는 경우는 언제인가. 무엇을 근거로 되돌리는가.
  2. --allowedTools "Edit"와 --disallowedTools "Edit(/tests/**)"를 함께 주었을 때 tests/test_jobs.py의 편집은 어떻게 처리되는가. 그 까닭은 무엇인가.
  3. pytest가 종료 코드 5를 냈을 때 이 루프가 재시도하지 않고 멈추는 까닭은 무엇인가.
  4. 시도 한 번의 비용 상한을 --max-budget-usd 0.50으로 주었는데 기록된 비용이 0.53달러이다. 이것은 루프의 결함인가. 루프 전체 예산을 설계할 때 이 사실을 어떻게 반영하는가.
  5. cron에 fix_until_green.py를 걸기 전에 정해야 할 것은 무엇인가. 루프가 이미 보고서를 쓰는데도 그것이 필요한 까닭을 설명하라.

다음 장 안내
