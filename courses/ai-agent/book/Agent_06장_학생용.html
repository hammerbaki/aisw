AI에이전트 기획 및 개발

6장

훅과 서브에이전트

2027학년도 「AI에이전트 기획 및 개발」의 준비 중인 교재입니다. 편집 상태를 검토하기 위해 미리 공개한 것으로, 수업 전에 내용과 순서가 바뀔 수 있습니다.

학사 7주차 · 교재 06 · 2부 하네스의 부품

2026-11-19에 150분 기준으로 줄였다(학생용 본문 63,971자 → 33,443자). 명령의 출력은 2026-11-14~19에 Windows 11의 Git Bash(GNU bash 5.3.15)와 파이썬 3.13.7에서 얻었다.

앞 장까지 jobprep 저장소에 하네스의 부품을 더하였다. 그러나 CLAUDE.md의 규칙과 스킬의 절차는 모델이 따르기로 판단할 때만 지켜진다. 대화가 길어지면 모델은 “테스트를 고치지 않는다”는 규칙을 잊고 테스트를 고쳐 통과시킬 수 있다.

이 장은 이 약점을 두 장치로 메운다. 훅(hook)은 정해진 시점에 사람이 정한 프로그램을 반드시 실행하여 규칙을 프로그램의 판정으로 옮긴다. 서브에이전트(subagent)는 자기 컨텍스트와 도구 목록을 가진 전담 에이전트로, 검토를 고칠 권한이 없는 다른 컨텍스트에 맡긴다. 이 장에서는 보호 파일을 지키고 편집 뒤에 테스트를 강제하는 훅과, 심어 둔 위반으로 성능을 확인한 검토 전담 서브에이전트를 만든다.

학습 목표

  • 지시와 강제를 구분하고, 규칙마다 알맞은 장치를 고른다.
    • 예시: “.env를 고치지 않는다”는 거부 규칙과 훅으로, “커밋 메시지는 한국어로 쓴다”는 CLAUDE.md로 둔다.
    • 활용: 7장의 하네스 설계서에 부품마다 “막는 실패”를 적는다.
  • 훅의 입력(표준 입력의 JSON)과 출력(종료 코드, JSON)을 이해하고 훅 스크립트를 읽고 고친다.
    • 예시: file_path가 tests/.baseline.json이면 종료 코드 2로 편집을 막는다.
    • 활용: 11장의 주입 대책과 13장의 CI 검사.
  • 훅을 Claude Code 없이 시험하고 고장을 진단한다.
    • 예시: check_hooks.sh의 견본 18개가 모두 PASS인지 본 뒤 등록하고, Windows의 경로 꼴로 생기는 조용한 고장을 견본으로 드러낸다.
    • 활용: 훅을 고칠 때마다 같은 점검을 다시 돌린다.
  • 검토 전담 서브에이전트를 정의하고 성능을 측정한다.
    • 예시: 1회차 기록에서 위반 5건 중 3건을 찾고 오탐 1건을 낸 까닭을 정의의 문장에서 찾아 고친다.
    • 활용: 10장의 검토 역할 에이전트, 12장의 에이전트 평가.

0. 시작하기

이 장은 내 PC에서 진행한다. 이론 사이에 따라 하기 둘(4-3절, 7절)이 있고 10절이 핵심 실습이다(6절은 [선택]). VS Code에 확인 터미널([터미널])과 Claude Code 터미널을 나란히 두고 둘 다 ~/agent-lab/jobprep에서 가상 환경을 켠다(부록 A-4-2).

이 장의 실행 상한. 실제 모델은 대화형 세션에서만 부르며 요청은 다섯이다. 훅 관찰 셋(7-3절 하나, 10-2절 둘), 서브에이전트 목록 확인 하나(10-3절), 고친 자기 검토자의 투입 한 번(10-7절)이다. 같은 정의를 여러 번 돌리는 검토자 실행은 교수 시연이며 키트의 시연기록/으로 읽는다. jobprep은 모의 모드(LLM_FAKE=1)로 돈다.

1. 지시와 강제

1-1. CLAUDE.md는 지켜지지 않을 수 있다

Claude Code 문서는 Claude가 CLAUDE.md를 “강제되는 설정이 아니라 컨텍스트로” 다룬다고 적고, 행동을 확실히 막으려면 PreToolUse 훅을 쓰라고 권한다[C3][B1]. 규칙이 지켜지지 않는 상황은 넷이다. 목표가 부딪힐 때(통과시키라는 요구 앞에서 기대값을 바꿈), 대화가 길 때(처음 읽은 규칙보다 최근의 요청이 앞섬), 규칙이 애매할 때(“비밀 정보를 조심한다”는 .env.example을 고쳐도 되는지 말하지 않음), 읽은 자료에 지시가 섞일 때(11장의 간접 프롬프트 주입)이다.

그래서 지킬 확률을 높이는 지시(instruction)와, 규칙을 모델 밖의 프로그램으로 옮겨 어기는 행동을 막는 강제(enforcement)를 구분한다.

1-2. 강제의 층

층 장치 판정 장
지시 CLAUDE.md, .claude/rules/, 스킬 모델 3, 4
권한 규칙 settings.json의 permissions Claude Code 3
훅 settings.json의 hooks와 스크립트 사람이 쓴 프로그램 6
샌드박스 운영체제 수준의 격리 운영체제 11
사후 검사 테스트, 검토, CI 프로그램과 사람 2, 6, 13

아래로 갈수록 판정이 모델에서 멀어진다. 권한 규칙은 Read(./.env)처럼 도구와 경로 패턴의 목록이고 훅은 조건을 판정하는 스크립트이므로, “동결 기록에 든 파일이면 막는다”처럼 다른 파일을 읽어야 하는 조건은 훅으로 쓴다[C4][C12].

1-3. 규칙의 모양과 두는 곳

“매번 X를 하면 Y를 한다”는 훅에, “절대 X를 하지 않는다”는 권한 규칙과 훅에, 여러 단계의 절차는 스킬에, 판단이 필요한 품질 기준(“오류를 숨기는 처리인가”)은 검토에 둔다[B1]. 검토는 구현한 대화와 같은 컨텍스트에서 하면 자기 작업을 자기가 보는 셈이므로 서브에이전트에게 맡긴다.

1-4. 이 장에서 강제로 옮길 규칙

3장 CLAUDE.md의 규칙 여섯을 층에 나눈다. RV1~RV6은 9절의 검토 규칙 번호이다(1장의 역할 ID와 겹치지 않게 V를 붙였다).

규칙 권한 규칙 훅 검토자
RV1 키는 .env에만 Read(./.env) 거부 protect.sh가 .env 편집을 막음 코드에 적힌 키
RV2 LLM 호출은 api/llm.py로만 직접 호출, 모델 이름
RV3 화면 글은 textContent로만 innerHTML
RV4 동결된 테스트를 고치지 않음 protect.sh, 동결 검사 skip, 기대값 완화
RV5 오류를 숨기지 않음 예외를 삼키는 처리
RV6 테스트는 모의 모드로 run_tests.sh의 LLM_FAKE=1 실제 API를 부르는 테스트

빈칸이 강제의 빈틈이다. RV2, RV3, RV5는 패턴으로는 쉽게 비켜 가므로 검토자가, 검토자가 놓친 것은 사람이 메운다.

2. 훅의 구조

2-1. 훅의 생명 주기

훅은 정해진 시점(이벤트)에 설정의 매처(matcher)가 맞으면 실행되는 처리기(handler)이며, 대부분은 셸 명령이다. Claude Code는 이벤트의 정보를 JSON으로 넘기고 처리기는 허용이나 차단을 돌려준다[C12].

sequenceDiagram
    participant U as 사용자
    participant C as Claude Code
    participant H as 훅
    participant T as 도구(Edit, Bash 등)
    U->>C: 프롬프트 입력
    C->>H: UserPromptSubmit
    H-->>C: 허용 또는 차단, 덧붙일 맥락
    loop 모델이 도구를 쓰는 동안
        C->>H: PreToolUse (tool_name, tool_input)
        H-->>C: 종료 코드 0이면 진행, 2이면 차단
        C->>C: 권한 규칙 확인
        C->>T: 도구 실행
        T-->>C: 결과
        C->>H: PostToolUse (tool_response)
        H-->>C: 실패를 알리면 Claude가 읽는다
    end
    C->>H: Stop (stop_hook_active)
    H-->>C: 멈춤 허용, 또는 block으로 이어 가기
    C-->>U: 응답

PreToolUse는 도구가 실행되기 전에 돌므로 막을 수 있고, PostToolUse는 실행된 뒤에 돌므로 알릴 뿐이다. Stop은 모델이 끝내려는 순간에 돌므로 모델을 다시 일하게 할 수 있다.

2-2. 훅 이벤트

문서에는 30개가 넘는 이벤트가 있다[C12]. 이 과목에서 쓰는 것은 다음과 같다.

이벤트 언제 종료 코드 2의 효과
UserPromptSubmit 프롬프트가 모델에게 가기 전 프롬프트를 막는다
PreToolUse 도구 호출 직전 호출을 막는다. 글이 Claude에게 간다
PostToolUse 도구 호출이 성공한 직후 막지 못한다. 글이 Claude에게 간다
SubagentStop, Stop 서브에이전트나 주 에이전트가 끝나려 할 때 이어 가게 한다

[최신 자료 자리: 훅 이벤트와 처리기의 종류] 이벤트 목록, 처리기 type과 기본 제한 시간(2-5절). 확인할 곳 https://code.claude.com/docs/en/hooks. 2026-11-14 값: 이벤트 30개 이상, 처리기 다섯 가지, Claude Code 2.1.296. 수업 전에 다시 확인한다.

2-3. 설정 형식

훅은 설정 파일의 hooks 키에 세 층(이벤트, 매처 그룹, 처리기)으로 적는다[C12].

파일: .claude/settings.json (훅 부분) 
{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [
          {
            "type": "command",
            "command": "\"$CLAUDE_PROJECT_DIR\"/.claude/hooks/protect.sh",
            "timeout": 30
          }
        ]
      }
    ]
  }
}

“PreToolUse에서 도구가 Edit나 Write이면 protect.sh를 실행하고 30초를 넘기면 중단한다”로 읽는다. hooks 객체를 새로 만들어 덮어쓰면 앞의 이벤트가 사라진다. 팀이 지킬 훅은 커밋하는 .claude/settings.json에, 개인의 훅은 .claude/settings.local.json에 둔다(부록 A-13).

2-4. 매처 규칙

도구 이벤트의 matcher는 도구 이름과 맞춘다[C12]. 생략이나 "*"는 모두와 맞고, 글자·숫자·_·-·|만으로 된 매처는 이름 목록(Edit|Write), 그 밖의 글자가 섞이면 정규식(mcp__jobprep-ops__.*)이다. 매처는 대소문자를 구별하므로 edit|write는 아무 도구와도 맞지 않는다. 또 매처는 도구만 고르므로 Write만 걸면 기존 파일의 부분 수정(Edit)이나 셸의 echo > a.txt(Bash)에서는 돌지 않는다.

2-5. 처리기의 종류

처리기의 type은 command(셸 명령), http, mcp_tool, prompt(모델이 판정), agent(검증 에이전트, 실험 기능)의 다섯이다[C12][C12a]. 모델이 판정하는 처리기는 결과가 매번 같지 않고 사용량이 든다. 이 장은 패턴으로 판정할 규칙은 command 훅으로, 뜻을 읽어야 할 규칙은 서브에이전트 검토로 나눈다.

2-6. 명령의 형식과 $CLAUDE_PROJECT_DIR

command에 args 배열을 함께 쓰면 셸을 거치지 않는 exec 형식, 없으면 셸이 해석하는 셸 형식이다[C12]. 스크립트 경로는 $CLAUDE_PROJECT_DIR(세션을 시작한 프로젝트의 루트)로 시작하는 절대 경로로 쓴다. Claude가 cd로 옮겨 가도 이 값은 바뀌지 않는다. 공백이 든 경로를 위해 변수를 큰따옴표로 감싸며, 위 설정의 \"는 JSON 문자열 안의 큰따옴표이다.

2-7. Windows에서 훅이 도는 셸

셸 형식의 명령은 macOS와 리눅스에서는 sh -c, Windows에서는 Git Bash가, Git Bash가 없으면 PowerShell이 해석한다[C12]. 그래서 Git for Windows가 없는 PC에서는 .sh 훅이 돌지 않고 편집은 그대로 진행된다[C17].

차이 내용 이 장의 대처
경로의 꼴 file_path가 역슬래시로 온다. 슬래시로 쓴 비교는 아무것도 막지 못한다[C12] 슬래시로 바꾸고 /c/…는 cygpath -m으로 C:/…로(4-2절)
대소문자 .ENV와 .env는 같은 파일이다 대소문자 구별 없이 비교
파이썬 훅은 가상 환경을 켜지 않은 셸에서 돈다 .venv/Scripts/python.exe를 먼저(부록 A-9-2)
실행 권한 Windows의 Git은 chmod +x를 기록하지 않는다 git add --chmod=+x(7-2절)

exec 형식은 실제 .exe가 필요한데 가상 환경의 경로가 운영체제마다 달라 팀 설정에 적기 어렵다. 그래서 셸 형식의 bash 스크립트를 쓴다.

[최신 자료 자리: Windows에서 훅을 실행하는 셸] 셸 형식 훅의 해석기(Git Bash, 없으면 PowerShell), shell 필드, 역슬래시 경로. 확인할 곳 https://code.claude.com/docs/en/hooks, https://code.claude.com/docs/en/setup. 2026-11-17 값은 위 본문과 같다(2.1.296). 수업 전에 다시 확인한다.

3. 훅의 입력과 출력

3-1. 입력: 표준 입력의 JSON

command 훅은 이벤트의 정보를 표준 입력으로 받으므로 스크립트는 INPUT="$(cat)"으로 시작한다. 들어오는 필드는 다음과 같다[C12].

이벤트 들어오는 필드
모든 이벤트 session_id, cwd, hook_event_name 등
PreToolUse tool_name(도구 이름), tool_input(도구에 넘길 인자)
PostToolUse 위의 둘과 tool_response(도구의 결과)
Stop stop_hook_active

파일 도구의 file_path는 절대 경로이다. 키트의 견본 하나를 연다(__PROJECT__는 저장소 경로로 바꿀 자리이다).

터미널 
cat ~/kits/Agent_06장/hooks/samples/pre_edit_env.json
{
  "session_id": "sample-session",
  "transcript_path": "C:/Users/student/.claude/projects/sample/sample-session.jsonl",
  "cwd": "__PROJECT__",
  "permission_mode": "default",
  "hook_event_name": "PreToolUse",
  "tool_name": "Edit",
  "tool_input": {"file_path": "__PROJECT__/.env", "old_string": "LLM_FAKE=1", "new_string": "LLM_FAKE=0", "replace_all": false},
  "tool_use_id": "toolu_sample_01"
}

“Claude가 .env를 고쳐 모의 모드를 끄려 한다”는 상황이다.

3-2. 출력: 종료 코드

종료 코드 뜻 표준 오류
0 막을 까닭이 없다. 표준 출력이 JSON이면 결정으로 읽힌다 Claude에게 보이지 않는다
2 막는 오류 막는 이유로 Claude에게 전달된다(PreToolUse)
그 밖(1 등) 막지 않는 오류 대화 기록에 hook error로 보인다. 동작은 진행된다

마지막 줄이 가장 흔한 실수의 원인이다. 셸의 습관대로 exit 1을 쓰면 훅은 오류를 기록할 뿐 편집을 막지 않는다. 막으려면 반드시 exit 2이다[C12]. 또 PreToolUse의 0은 “허락”이 아니라 “반대하지 않음”이며, 그 뒤에 권한 규칙과 확인 창이 이어진다[C12a].

3-3. 출력: JSON

더 섬세한 결정은 종료 코드 0과 표준 출력의 JSON 객체 하나로 돌려준다[C12a]. PreToolUse는 hookSpecificOutput 안의 permissionDecision으로, PostToolUse와 Stop은 맨 위 층의 decision과 reason으로 결정한다.

파일: PreToolUse 훅의 JSON 출력 예 
{
  "hookSpecificOutput": {
    "hookEventName": "PreToolUse",
    "permissionDecision": "deny",
    "permissionDecisionReason": "tests/.baseline.json은 동결 기록이므로 고치지 않는다."
  }
}
permissionDecision 효과
allow 확인 창을 건너뛴다. 거부·확인 규칙은 그대로다
deny 도구 호출을 막는다. 이유는 Claude에게 간다
ask 사용자에게 확인 창을 띄운다
defer 비대화형(-p) 실행에서만. 도구 호출을 보존한 채 차례를 끝낸다

훅이 여럿이면 가장 엄격한 결정이 이긴다. JSON이 무시되는 흔한 까닭은 필드의 층이 틀린 경우(그 필드만 조용히 무시된다)와 표준 출력이 {로 시작하지 않는 경우(~/.bashrc의 echo)이다[C12a].

생각해 볼 것. 종료 코드 0으로 끝나며 위 JSON을 출력하는 PreToolUse 훅은 편집을 막는가. permissionDecision을 맨 위 층으로 옮기면 어떻게 되는가.

3-4. 훅과 권한 모드

PreToolUse 훅은 모든 권한 모드에서 먼저 돈다. bypassPermissions로 시작해도 훅이 막으면 막히고, 훅의 allow는 거부 규칙을 풀지 못한다[C12a][C4]. 훅은 권한 모드를 바꾸어도 풀리지 않는 정책이다.

4. 보호 파일 훅: PreToolUse

4-1. 무엇을 보호하는가

보호 파일은 에이전트가 고치면 판정 기준이나 안전장치가 무너지는 파일이다.

경로 까닭
.env, .env.* (.env.example 제외) 실제 API 키. 고치면 모의 모드가 꺼지거나 키가 바뀐다
tests/.baseline.json, 동결된 테스트 파일 동결 기록과 완료 조건. 고쳐서 통과시키면 회피이다
.git/ 안의 파일 저장소의 기록. 도구로 고칠 까닭이 없다
data/jobs.json 운영 데이터. 사람이 검수한 뒤에만 바뀐다

새 테스트 파일은 막지 않는다. 목록이 지나치게 넓으면 정상 작업이 막혀 결국 사람이 훅을 끈다.

4-2. protect.sh 읽기

protect.sh는 ① 경로의 꼴을 맞추는 함수, 파이썬 선택, 입력 읽기 ② .. 경로 차단 ③ 저장소 기준의 상대 경로 ④ 보호 목록과 동결 기록 대조 ⑤ 결정의 다섯 부분이다.

파일: .claude/hooks/protect.sh (일부) 경로의 꼴, 우회 차단, 상대 경로

생략한 부분(...)은 가상 환경의 파이썬으로 입력의 file_path를 꺼낸다(jq는 Git for Windows에 없다). 여기서 눈여겨볼 원칙은 실패 시 닫힘(fail closed)이다. 파이썬이 없거나 JSON을 읽지 못하면 “모르겠으니 막는다”(종료 코드 2)를 고른다. 보호 훅이 고장 난 채로 통과시키면 보호가 사라진 줄도 모르기 때문이다. 반대로 알리는 훅인 5절의 테스트 훅은 조용히 통과시킨다. 훅마다 고장 났을 때 넘어질 방향을 정해 둔다.

②는 문서의 보안 수칙 “경로 우회를 막는다”를 따른다[C12]. api/../.env는 .env이지만 글자로는 api/로 시작하므로 ..이 든 경로를 막는다. to_slash는 cygpath가 ..을 미리 풀지 않도록 이 검사 뒤에 부른다.

파일: .claude/hooks/protect.sh (일부) 보호 목록, 동결 기록, 결정 
BLOCKED=""
if [ -f "$LIST" ]; then
  while IFS= read -r line || [ -n "$line" ]; do
    line="${line%$'\r'}"
    line="${line%%#*}"                          # 줄의 주석을 지운다
    line="${line#"${line%%[![:space:]]*}"}"     # 앞 공백을 지운다
    line="${line%"${line##*[![:space:]]}"}"     # 뒤 공백을 지운다

fi

[[ "$REL" == $line ]]의 오른쪽은 따옴표가 없어 글롭 패턴(.git/*)으로 비교되고, ! 줄은 예외(!.env.example)이다. 생략한 부분은 동결 기록의 파일이면 막는다. 둘째 줄처럼 막힌 뒤에 할 일을 적지 않으면 모델은 sed -i 같은 다른 길로 고치려 할 수 있다. 훅의 오류 글은 모델에게 주는 프롬프트이다.

5. 편집 뒤 테스트 훅: PostToolUse

5-1. PostToolUse의 성질

PostToolUse 훅은 도구 호출이 성공한 직후에 돈다. 편집은 되돌릴 수 없고, 결과를 검사해 종료 코드 2와 표준 오류로 알리면 Claude가 읽고 고친다[C12]. 모델은 “고친 뒤 테스트를 돌린다”는 지시를 건너뛸 수 있지만 훅은 잊지 않는다.

5-2. 관련 테스트 고르기

훅 한 번은 파이썬과 FastAPI를 새로 불러오므로 Windows의 집필 PC에서 10초를 넘었다. 그래서 고친 파일과 관련된 테스트만 돌린다.

고친 파일 돌리는 테스트

api/llm.py test_llm.py, test_summary.py, test_ask.py(여러 기능이 거친다)
그 밖의 .py tests 전체
.py가 아닌 파일 돌리지 않는다

2장의 tests/test_closing_within.py처럼 대응에 없는 테스트는 커밋 전의 전체 실행(또는 6절의 Stop 훅)이 메운다.

5-3. run_tests.sh 읽기

run_tests.sh는 fastapi가 설치된 파이썬이 필요하므로 JOBPREP_PYTHON, .venv/Scripts/python.exe, .venv/bin/python의 순으로 고른다(훅은 가상 환경을 물려받지 않아 python만 쓰면 No module named fastapi가 날 수 있다). 이어서 python -m py_compile로 문법을 검사하고[P1], 2장의 검사기가 있으면 동결 검사를 돌린다(Bash로 테스트를 고친 경우도 드러난다). 마지막이 테스트와 보고이다.

파일: .claude/hooks/run_tests.sh (일부) 테스트와 보고 
cd "$ROOT" || exit 0
OUT="$(LLM_FAKE=1 PYTHONIOENCODING=utf-8 "$PY" -m pytest -q -x --no-header --tb=short --show-capture=no -p no:cacheprovider $TARGETS 2>&1)"
STATUS=$?

if [ "$STATUS" -eq 0 ] || [ "$STATUS" -eq 5 ]; then   # 5: 모을 테스트가 없음
  echo "run_tests.sh: $REL →$TARGETS 통과"
  exit 0
fi

{
  echo "테스트 실패: $REL 을 고친 뒤$TARGETS 이(가) 통과하지 않는다."
  printf '%s\n' "$OUT" | tail -n 25
  echo "테스트 파일을 고쳐 통과시키지 말고 구현을 고친다."
} >&2
exit 2

-x는 첫 실패에서 멈추고 --tb=short는 역추적을 줄인다[T1][T2]. --show-capture=no가 없으면 실패 보고가 요청 기록으로 채워져 tail -n 25가 실패 이유를 잘라 낸다(집필 중에 겪었다). 마지막 줄은 2장의 테스트 회피를 막는 지시이다.

6. [선택] Stop 훅과 무한 반복

이 절은 [선택]이며 핵심 실습에서는 Stop 훅을 등록하지 않는다. 반복 끊기는 8장의 루프에서 다시 쓴다.

6-1. Stop 이벤트와 stop_gate.sh

Stop 훅은 주 에이전트가 응답을 마치려는 순간에 돈다[C12]. decision: "block"과 reason을 돌려주면 Claude는 reason을 다음 지시로 받아 일을 이어 간다. 이것으로 “테스트가 통과하기 전에는 끝내지 않는다”를 강제할 수 있다. 다만 응답마다 돌므로 설명만 물어도 전체 테스트가 돈다.

파일: .claude/hooks/stop_gate.sh (일부) 
ACTIVE="$(printf '%s' "$INPUT" | PYTHONIOENCODING=utf-8 "$PY" -c '
import json, sys
data = json.load(sys.stdin)
sys.stdout.write("true" if data.get("stop_hook_active") else "false")
' 2>/dev/null)" || ACTIVE="true"   # 입력을 읽지 못하면 멈춤을 허용한다(반복을 만들지 않는다)

if [ "$ACTIVE" = "true" ]; then
  echo "stop_gate.sh: 이미 한 번 이어 가게 하였으므로 멈춤을 허용한다." >&2
  exit 0
fi
...

생략한 부분은 전체 테스트가 실패하면 실패 요약을 담은 {"decision": "block", ...}을 출력한다. 이 훅은 입력을 읽지 못하면 멈춤을 허용한다(실패 시 열림). 고장 난 채로 계속 막으면 끝나지 않는 반복에 빠지기 때문이다.

6-2. 반복 끊기

Stop 훅이 막으면 Claude가 이어 가고, 다시 끝내려 할 때 Stop 훅이 또 돈다. 입력의 stop_hook_active는 이미 이어 가는 중이면 true이므로, stop_gate.sh는 이어 가게 하는 것을 한 번만 하고 그래도 못 고친 문제는 사람에게 넘긴다(8장). Claude Code도 도구 호출 없이 연속 8번 막히면 차단을 무시하지만, 도구를 부르면 횟수가 0으로 돌아가므로 안전망일 뿐이다[C12][C12a].

[최신 자료 자리: Stop 훅의 연속 차단 상한] 확인할 곳 https://code.claude.com/docs/en/hooks. 2026-11-14 값: 8회, 환경 변수 CLAUDE_CODE_STOP_HOOK_BLOCK_CAP. 수업 전에 다시 확인한다.

6-3. Stop 훅을 켤 때와 끌 때

구현을 맡기고 결과만 받는 작업에서는 켤 만하다. 그러나 TDD의 Red 단계에서는 의도된 실패를 보고 구현을 시작해 버리므로 개인 설정(.claude/settings.local.json)에 둔다. 등록하려면 7-2절의 merge_hooks.py 명령에서 대상을 settings.local.json으로, 조각을 훅설정_stop.json으로 바꾼다.

확인 6 디버그 기록에 PreToolUse:와 PostToolUse:의 Hooks: 줄이 있고 명령에 protect.sh와 run_tests.sh가 보이며, git status --short에 README.md가 남아 있지 않다. 찾지 못하였으면 7-4절의 표에서 찾은 원인을 검토자검증.md 1절 아래에 적는다.

7-5. 훅의 보안

훅은 사용자의 권한 그대로 셸 명령을 실행하므로[C12] 공격의 통로도 된다. 남의 저장소를 받아 Claude Code를 열면 그 저장소의 .claude/settings.json에 든 훅이 내 계정으로 돈다. 훅이 curl로 내 ~/.ssh를 보낸다면 Claude에게 아무것도 시키지 않았는데 피해를 입는다. 대화형 세션은 신뢰 창을 받아들이기 전까지 훅을 돌리지 않으므로 신뢰하기 전에 .claude/를 읽는다. 그러나 헤드리스 실행(claude -p)에는 신뢰 창이 없고 신뢰한 것으로 본다[C12][C4]. 남이 보낸 풀 리퀘스트를 CI에서 claude -p로 돌리면 그 안의 훅이 CI 서버에서 돈다. 문서가 권하는 대책은 다음과 같다.

대책 방법
저장소의 설정을 읽지 않는다 claude -p --setting-sources user ...
최소 모드로 시작한다 claude -p --bare ... (훅, 스킬, 서브에이전트, 플러그인, .mcp.json을 읽지 않음)
그 실행에서만 훅을 끈다 claude -p --settings '{"disableAllHooks": true}' ...
조직의 훅만 허용한다 관리형 설정의 allowManagedHooksOnly

[최신 자료 자리: 헤드리스 실행의 선택지] 위 표의 선택지와 설정 키. 확인할 곳 https://code.claude.com/docs/en/headless. 2026-11-14 값은 위 표와 같다(2.1.296). 문서는 --bare가 -p의 기본값이 될 예정이라고 적는다(2026-11-15). 수업 전에 다시 확인한다.

disableAllHooks를 사용자 설정에만 넣으면 프로젝트 설정이 다시 바꿀 수 있다[C4].

생각해 볼 것. 친구가 보내 준 저장소에서 claude -p "테스트를 고쳐 줘"를 바로 실행하면 어떤 위험이 있고, 무엇을 확인하거나 붙이겠는가.

8. 서브에이전트

8-1. 왜 나누는가

서브에이전트는 자기 컨텍스트 창, 시스템 프롬프트, 도구 목록을 가진 전담 에이전트이다. 주 대화는 일을 넘기고 결과만 받는다. 문서가 드는 이점은 다음 넷이다[C13].

까닭 뜻
컨텍스트 격리 긴 탐색이 주 대화를 채우지 않고 요약만 돌아온다
도구 제한 쓸 수 있는 도구를 정한다
전문화 한 가지 일에 맞춘 시스템 프롬프트
비용 조절 단순한 일을 싼 모델에게 맡긴다

이 장에서 중요한 것은 앞의 둘이다. 같은 대화에서 구현한 Claude는 고친 사정을 알고 있어 검토에서도 같은 판단을 되풀이하기 쉽다. 서브에이전트는 새 컨텍스트에서 변경만 보고, 쓰기 도구가 없으면 고칠 수도 없다. 검토와 수정의 분리를 구조로 강제하는 것이다. 다만 맥락을 다시 모아야 하고 같은 사용량 한도에서 빠지므로 작은 수정은 주 대화가 낫다[C13].

8-2. 내장 서브에이전트

내장 서브에이전트로 Explore(읽기 전용 탐색), Plan(계획 모드의 조사), general-purpose(모든 도구)가 있다[C13]. 같은 이름의 사용자 정의 서브에이전트를 만들면 내장 것을 대신한다.

[최신 자료 자리: 내장 서브에이전트, 모델 별칭, /agents] 확인할 곳 https://code.claude.com/docs/en/sub-agents, 모델 목록 https://platform.claude.com/docs/en/about-claude/models/overview. 2026-11-14 값: 위 본문의 셋, 별칭 sonnet·opus·haiku·fable(8-3절), /agents는 2.1.198부터 안내만 출력(8-4절). 수업 전에 다시 확인한다.

8-3. 정의 파일

사용자 정의 서브에이전트는 마크다운 파일 하나이다. 맨 위의 YAML 프런트매터(---로 감싼 설정) 아래 본문이 시스템 프롬프트가 된다[C13]. .claude/agents/(프로젝트, 커밋해 공유)나 ~/.claude/agents/(개인)에 둔다.

필드 뜻 이 장의 검토자
name(필수) 고유한 이름 reviewer
description(필수) Claude가 언제 일을 넘길지 판단하는 글 무엇을, 언제 검토하는지
tools 허용 목록. 생략하면 모든 도구를 물려받는다 Read, Grep, Glob
model sonnet, opus, haiku, fable, 모델 ID, inherit inherit

이 밖에 disallowedTools, hooks, isolation(10장) 등이 있다. Claude Code는 모르는 필드를 조용히 무시하므로 disallowed_tools처럼 철자를 틀리면 효과만 사라진다[C13]. 그래서 check_agent.py로 프런트매터를 검사한다.

8-4. 호출

서브에이전트를 부르는 방법은 넷이다[C13].

방법 예 특징
자동 위임 없음 요청과 description이 맞으면 Claude가 스스로 넘긴다
자연어로 지명 “reviewer 서브에이전트로 검토하라” Claude가 대개 그 서브에이전트를 쓴다
@ 언급 @"reviewer (agent)" 검토하라 그 서브에이전트가 반드시 돈다

측정할 검토는 @ 언급으로 부른다. /agents는 2.1.198부터 안내만 내므로 정의 파일을 직접 쓴다[C13a]. 정의를 고치면 다음 위임부터 반영되지만, 세션 시작 때 없던 .claude/agents/를 처음 만들면 다시 시작해야 한다[C13].

8-6. 도구 제한

tools(허용 목록)는 새 도구를 자동으로 막고, disallowedTools(거부 목록)는 새 도구를 자동으로 허용하므로[C13], 좁게 묶을 검토자는 허용 목록으로 쓴다. Bash는 git diff를 직접 돌릴 수 있어 편하지만 무엇이든 실행하므로(sed -i, rm) 사실상 쓰기 도구이다. 프런트매터의 훅으로 일부 명령만 허용할 수도 있으나 모든 우회를 막는지 검증하기 어렵다. 그래서 검토 대상을 diff 파일로 주고 읽기 도구만 준다. 권한을 좁히는 가장 확실한 방법은 도구를 주지 않는 것이다. 도구 목록은 권한 모드와 관계없이 적용된다.

정의 파일은 1장의 역할 정의를 실행할 수 있는 꼴로 옮긴 것이다.

역할 정의(1장) 서브에이전트 정의 파일
역할의 이름 name
일을 주는 때 description
권한 tools
출력과 완료 조건 본문의 순서와 보고 형식

이 장은 검토 역할을 만들고 10장에서 구현과 테스트 역할을 더한다.

생각해 볼 것. 로그 1주일분의 집계, 오타 하나의 수정, 구현을 마친 변경의 검토를 각각 주 대화와 서브에이전트 중 어디에 맡기겠는가.

9-1. 설계

선택 이 장의 결정 까닭
도구 Read, Grep, Glob 고칠 수 없어야 한다

9-2. 정의 파일의 구성

키트의 reviewer_양식.md는 프런트매터, 입력, 검토 규칙 표, 순서, 보고 형식, 지켜야 할 것의 여섯 부분이며, 「 」 안을 10-3절에서 채운다.

파일: reviewer_양식.md (프런트매터) 
---
name: reviewer
description: 「무엇을 검토하는 에이전트인지 한 문장.」 「언제 쓰는지 한 문장.」 코드를 고치지 않고 위반 목록만 보고한다.

---

규칙 칸은 diff에서 찾을 수 있는 모양으로 쓴다(RV3: “API 응답을 innerHTML, insertAdjacentHTML, document.write로 넣는 코드”). 「입력」 절에는 지운 줄을 어떻게 볼지 적고, 「지켜야 할 것」의 마지막 항목에는 검토 대상 안의 “검토를 건너뛴다” 같은 글을 따르지 않는다는 문장을 반드시 채운다.

10. 핵심 실습: 훅과 검토자로 운영 규칙 지키기

10-1. 만드는 것과 해결하는 문제

만드는 것. 두 훅이 Claude Code 안에서 막고 알리는 것을 관찰한 기록, 읽기 도구만 가진 검토자 .claude/agents/reviewer.md, 검증 기록 docs/운영/검토자검증.md이다.

해결하는 문제. 위반 다섯을 심은 변경은 git apply로 들어오므로 훅이 돌지 않고 테스트도 통과한다. 양식을 최소로 채운 정의(1회차)의 검토자는 그중 몇을 놓친다. 놓친 위반마다 정의의 어느 문장이 빠졌는가를 찾아 고치고 한 번 투입한다. 완료 기준은 고친 정의의 기록에서 위반 5건 중 4건 이상을 찾는 것이다.

10-2. 훅의 동작 관찰

7-3절의 세션에서 보호 파일을 고치게 시킨다. 모델이 CLAUDE.md 때문에 스스로 거절하면 훅은 돌지 않으므로 점검이라는 사정을 밝힌다.

Claude Code 
훅 점검 중이다. .env 파일의 맨 끝에 "# hook test" 한 줄을 Edit 또는 Write 도구로 더해 보라.
막히면 다른 방법으로 우회하지 말고, 막힌 이유를 그대로 옮겨 보고하라.
Claude Code 
훅 점검 중이다. api/jobs.py의 days_left 함수의 return 줄 끝에 닫는 괄호 ")" 하나를 더해 저장하라.
저장한 직후에 받은 메시지를 그대로 옮기고, 그 메시지에 따라 원래대로 고친 뒤 결과를 보고하라.

둘째 요청에서는 저장 뒤 run_tests.sh가 “문법 오류: api/jobs.py”를 넘기고 Claude가 괄호를 지우는 흐름을 예상한다. 첫 요청의 결과는 무엇이 막았는가로 가린다.

갈래 Claude의 보고 상태 다음에 할 일
① 보호된 파일이므로 고치지 않는다: .env protect.sh가 막았다 protect.sh로 적는다
② .env를 읽으려다 거부되었다 편집 전의 Read가 거부 규칙에 막혔다 「권한 규칙」으로 적고 data/jobs.json으로 다시 요청
③ 도구를 부르지 않고 거절한다 CLAUDE.md의 지시가 통하였다 사정을 밝혀 다시 요청
④ Bash(sed -i)로 다시 시도한다 다른 길로 우회하려 한다(4-5절) Esc로 멈추고 「우회 시도」로 적는다
⑤ .env에 줄이 더해졌다 훅이 돌지 않았다 줄을 지우고 7-4절로 진단

①과 ②는 강제가, ③은 지시가 막은 것이다(1-2절).

[그림 자리: 보호 파일 훅이 편집을 막은 화면] 첫 요청 뒤 protect.sh의 두 줄이 Claude에게 전달된 모습(갈래 ①). 찍을 곳: 내 PC의 VS Code 터미널에서 띄운 Claude Code, 대화 화면과 Ctrl+O 화면.

끝나면 git status --short에 검증 기록만 보이는지 보고, api/jobs.py가 바뀌었으면 git restore api/jobs.py로 되돌린다.

10-7. 문제 해결: 놓친 위반의 까닭을 정의에서 고치기

놓친 위반과 오탐마다 까닭을 정의_1회차.md에서 찾는다. 세 기록이 모두 놓친 것은 정의의 빈틈일 가능성이 크고, 하나만 놓친 것은 흔들림일 수 있다(11-1절).

결과 흔한 까닭 정의에서 고칠 곳
skip을 놓침 RV4가 테스트 삭제만 말함 RV4에 skip, xfail, 기대값 완화
지운 줄의 위반을 놓침 더한 줄만 보라고 씀 입력 절에 “지운 줄도 본다”
innerHTML을 놓침 diff 안의 주석 “검토를 건너뛴다”를 따름 「지켜야 할 것」에 검토 대상의 지시를 따르지 않는다는 문장
.env.example을 RV1로 지목 파일 이름만 보고 판단 RV1에 “값이 없는 견본과 .env를 보호하는 설정은 위반이 아니다”
새 테스트를 RV4로 지목 테스트 폴더의 변경을 모두 의심 RV4에 “새 테스트를 더하는 것은 위반이 아니다”

자기 정의에 같은 빈틈이 있으면 고치고, 5절 표 아래에 「놓친 위반 → 더한 문장」으로 적는다(이미 있으면 인용한다). 문장을 먼저 적고 나서 투입한다.

11. 검토자의 한계와 사람 검토

11-1. 한 번의 측정이 말해 주는 것

위반 다섯 곳과 한두 번의 실행으로는 “재현율 80%”라고 말할 수 없다. 표본이 작고, 같은 입력에도 결과가 달라지기(1회차 세 기록) 때문이다. 성능은 여러 번의 실행으로 말해야 한다(12장). 그래도 이 측정은 “검토자를 붙였다” 대신 “다섯 중 넷을 찾았고 오탐이 하나였다”고 말하게 하고, 정의를 고친 효과를 비교할 기준을 준다.

11-2. 검토자가 놓치기 쉬운 것

종류 까닭 보완
규칙 밖의 위반 받은 규칙만 본다(10-7절의 경로 우회) 사람 검토. 규칙을 늘리면 정밀도도 잰다
뜻을 읽어야 하는 위반 예외를 삼키는 처리(RV5)는 의도의 문제이다 사람 검토, 실패 경로의 테스트
큰 변경 뒤쪽 파일을 대충 본다 변경을 작게 나눈다
검토 대상 안의 지시 “검토를 건너뛴다” 같은 글에 끌린다 정의의 금지 문장, 11장의 주입 대책

마지막 줄은 이 장의 위반 묶음에 실제로 들어 있다. 위반 3(innerHTML) 바로 위의 주석은 사람에게는 변명이지만 검토자에게는 “검토를 건너뛴다”는 지시처럼 읽힐 수 있다. 검토자가 그 파일을 건너뛰었다면 검토자에 대한 프롬프트 주입이 성공한 것이다.

11-3. 범용 검토 명령과의 비교

내장 검토 명령 /code-review(별칭 /review), /security-review를 이 장의 검토자와 견준다[C13a].

구분 이 장의 reviewer /code-review /security-review
기준 팀 규칙 RV1~RV6 정확성 버그(일반 기준) 보안 취약점(일반 기준)
고치는가 고치지 못한다(도구 없음) --fix를 주면 고친다 보고만 한다
측정 심어 둔 위반으로 잰다 따로 재야 한다 같다
강점 팀만의 규칙을 안다 규칙에 없는 논리 오류를 찾을 수 있다 보안 관점의 폭이 넓다

11-4. 사람 검토가 맡는 것

검토자의 「위반 0건」은 승인이 아니다. 규칙에 비추어 문제를 찾지 못했다는 보고일 뿐이다. 요구와 설계의 적합성(새 폴더 ops/), 운영의 영향(실제 API를 부르는 스크립트의 비용)은 검토자가 모르고, 재현율이 1이 아닌 한 놓친 것도 있다. 병합은 사람이 책임지며, 13장의 보호 브랜치와 사람의 승인으로 제도가 된다.

생각해 볼 것. 「위반 0건」을 보고한 풀 리퀘스트를 그대로 병합하면 안 되는 까닭을 이 장에서 잰 재현율과 정밀도로 말해 본다.

자주 하는 실수와 해결

훅이 돌지 않거나 막지 못하면 7-4절의 표를 먼저 본다.

증상 원인 해결
.env 견본이 막히지 않고 0 P가 다른 저장소를 가리킨다 P=$(pwd)를 저장소에서 다시 정의
모든 편집이 「JSON을 읽지 못하였으므로」 막힌다 훅이 고른 파이썬이 돌지 않는다 .venv를 확인하거나 HOOK_PYTHON(테스트 훅은 JOBPREP_PYTHON)에 경로를 준다
bash: $'\r': command not found 스크립트가 CRLF로 저장되었다 VS Code에서 CRLF를 LF로 바꾼다
git apply --3way가 충돌한다 앞 장에서 같은 곳을 고쳤다 git reset --hard로 되돌리고 git switch main 뒤 교수에게 알린다

제출물

다음이 개인 저장소(~/agent-lab/jobprep)의 main에 커밋되고 푸시되어 있으면 된다. .claude/settings.local.json과 .review/는 커밋하지 않는다.

정리

  • CLAUDE.md의 규칙은 모델이 판단해 따르는 지시이다. 반드시 지킬 규칙은 권한 규칙과 훅으로 옮겨 프로그램이 판정하게 한다.
  • 훅은 이벤트에서 매처가 맞으면 도는 처리기이다. 입력은 표준 입력의 JSON이고 출력은 종료 코드와 JSON이다. 막으려면 exit 2이다. PreToolUse는 막고, PostToolUse는 알리고, Stop은 이어 가게 한다.
  • Windows의 훅은 Git Bash로 돌고 경로가 역슬래시로 온다. 꼴과 대소문자를 맞추지 않은 훅은 오류 없이 통과시킨다. 막는 훅은 고장 나면 막는 쪽으로 설계한다.
  • 훅은 도구 호출만 지키며 사용자 권한으로 돈다. 남의 저장소는 신뢰하기 전에 .claude/를 읽는다.
  • 읽기 도구만 가진 서브에이전트에게 검토를 맡기면 검토와 수정의 분리를 구조로 강제한다. 검토자도 심어 둔 위반으로 재현율과 정밀도를 재고, 놓친 까닭을 정의의 문장에서 고친다. 「위반 0건」은 승인이 아니다.

개념 점검

  1. CLAUDE.md에 “tests/.baseline.json을 고치지 않는다”고 적어 두었는데도 이것을 훅으로 다시 막는 까닭을, 1-1절의 네 상황 중 둘을 들어 설명하라.
  2. PreToolUse 훅 스크립트가 .env 편집을 막으려고 echo "금지" >&2; exit 1로 끝난다. 이 훅이 걸린 상태에서 Claude가 .env를 고치려 하면 어떤 일이 일어나는가. 고치려면 무엇을 바꾸어야 하는가.
  3. 다음 설정에서 잘못된 곳 두 군데를 찾아라. {"hooks": {"PreToolUse": [{"matcher": "edit|write", "hooks": [{"type": "command", "command": ".claude/hooks/protect.sh"}]}]}}
  4. Windows에서 보호 파일 훅이 case "$FILE_PATH" in "$ROOT"/*)로 저장소 안의 파일인지 가른다. Claude Code가 넘긴 file_path가 C:\Users\…\jobprep\.ENV일 때 이 훅이 아무것도 막지 못하게 되는 까닭 두 가지를 쓰고, 각각 어떻게 고치는지 쓰라.
  5. 검토 전담 서브에이전트의 정의 파일에 tools를 쓰지 않은 경우와 tools: Read, Grep, Glob을 쓴 경우의 차이를 쓰고, 검토자를 같은 대화의 Claude가 아니라 서브에이전트로 두는 까닭 두 가지를 쓰라.
