학사 4주차 · 교재 03 · 1부 운영 요건과 검증

앞 장에서는 운영 요건 명세의 요구 셋을 테스트로 바꾸고, Claude Code가 그 테스트를 통과시키게 하였다. 테스트가 완료 조건이 되자 에이전트의 결과를 「돌아가는가」가 아니라 「기준을 통과하는가」로 판정할 수 있게 되었다. 그러나 테스트가 정하는 것은 결과뿐이다. 같은 테스트를 통과하는 구현이라도 키를 코드에 적었는지, 화면에 글을 HTML로 끼워 넣었는지, 커밋 메시지를 어떤 형식으로 남겼는지는 테스트가 말해 주지 않는다. 이런 것은 팀의 규칙이 정한다.

규칙은 혼자 일할 때는 머릿속이나 개인 설정에 있어도 문제가 드러나지 않는다. 팀이 같은 저장소에서 일하고, 사람마다 자기 Claude Code 세션을 쓰기 시작하면 사정이 달라진다. 한 사람의 개인 설정에만 있던 규칙은 다른 사람의 세션에 없고, 대화로만 한 지시는 다음 세션에 남지 않는다. 1장에서 정의한 운영 요건 가운데 일관성(같은 종류의 일은 누가 해도 같은 규칙과 형식으로 된다)은 규칙이 저장소에 있어야 지켜지고, 재현성은 설정이 저장소에 있어야 지켜진다.

이 장에서 만드는 것은 하나이다. 기준 저장소 jobprep에 팀이 함께 쓰는 규칙 일체를 넣는다. Claude Code가 매 세션 읽는 지시(CLAUDE.md와 경로별 규칙 둘), Claude Code가 강제하는 권한 설정(.claude/settings.json), 사람과 GitHub가 집행하는 저장소 규약(규약 문서, PR 템플릿, CODEOWNERS)이다. 해결하는 문제도 하나이다. 규칙이 없는 저장소의 결과(교수 시연 기록)에서 어긋남 하나를 골라, 같은 요청을 자기 규칙에서 다시 보내 그것이 막혔는지 세어 docs/운영/규칙비교.md에 기록한다.

이 장의 파일들은 프로젝트실습Ⅱ의 팀 저장소의 출발점이 되고, 이후 장에서 자란다. 4장은 절차를 스킬로, 6장은 지시로 부족한 규칙을 훅으로 옮기고, 7장은 이 모두를 하네스로 묶어 효과를 다시 잰다.

학습 목표

  • 지시(CLAUDE.md, 경로별 규칙)와 설정(settings.json)의 차이를 설명하고, 각각의 계층과 우선순위를 말할 수 있다.
    • 예시: 「팀 설정은 git push를 확인하게 하고 내 개인 설정은 허용한다면 어떻게 되는가」에 deny → ask → allow의 평가 순서로 답하기
    • 활용: 규칙이 지켜지지 않을 때 그 규칙이 어느 파일에서 읽혔는지부터 확인하는 습관
  • 확인할 수 있는 문장, 실행 명령, 이유를 갖춘 팀 CLAUDE.md와 경로별 규칙을 쓸 수 있다.
    • 예시: 「깔끔하게 짠다」를 「api/와 rag/의 기록은 logging으로 남기고 print를 쓰지 않는다. 이유: 운영 기록의 형식을 지킨다」로 고쳐 쓰기
    • 활용: 새 팀원이나 새 에이전트가 같은 규칙으로 일을 시작하게 하는 저장소
  • 권한 규칙(allow, ask, deny)을 문서의 문법으로 쓰고, 개인 설정과 팀 설정을 나누어 저장소에 올릴 것만 올릴 수 있다.
    • 예시: .env 읽기 거부, git push 확인, 강제 푸시 거부를 .claude/settings.json에 적고 판정 사례 23개로 검사하기
    • 활용: 에이전트가 허용된 일만 하게 만드는 첫 번째 장치(11장의 보안에서 다시 쓴다)
  • 저장소 규약(브랜치 이름, 커밋 메시지, PR 템플릿, CODEOWNERS, 리뷰 규칙)을 문서로 정하고, 규칙이 있을 때와 없을 때를 같은 요청으로 비교할 수 있다.
    • 예시: 규칙 없음의 기록에서 innerHTML 위반(R4)을 골라, 같은 요청을 자기 규칙에서 다시 보내 0건인지 세기
    • 활용: 규칙의 효과를 재고, 효과가 없는 규칙은 고치거나 다른 장치로 옮기는 운영

0. 시작하기

이 장은 내 PC의 ~/agent-lab/jobprep/에서 진행한다. 설치, 로그인, 키트 저장소의 클론은 부록 A로 끝냈다고 전제하고, 수업의 시작 순서는 부록 A-20을 따른다. VS Code에 터미널 둘(Windows는 Git Bash, macOS는 기본 셸)을 나란히 두고, 하나는 직접 실행하는 [터미널], 다른 하나는 Claude Code에 쓴다(부록 A-4-2). 두 터미널 모두 cd ~/agent-lab/jobprep 뒤에 가상 환경을 켜고(Windows source .venv/Scripts/activate, macOS source .venv/bin/activate), 그 뒤로는 python으로 부른다(부록 A-9-1).

이 장의 실행 상한. 실제 모델은 대화형 Claude Code로만 부르고, 핵심 실습의 요청 넷(10-3의 CLAUDE.md 점검, 10-4의 경로별 규칙 확인, 10-5의 .env.local 거부 시험, 10-7의 검증 요청 하나)으로 그친다. 10-7의 검증 요청은 규칙을 고친 경우에만 한 번 더 보낸다. 같은 요청 둘을 규칙 없음과 규칙 있음의 두 조건에서 모두 돌린 비교는 교수 시연 기록(키트의 시연기록/)으로 읽는다. 헤드리스 실행(claude -p)과 프로덕트의 API 호출은 없고, 테스트는 모두 모의 모드로 돈다.

0-1. 키트 받기

키트는 키트 저장소에서 저장소 밖의 ~/kits/로 받는다(부록 A-7-3). cp -rn은 이미 있는 파일을 덮어쓰지 않으므로 다시 실행해도 받은 키트에 적은 것이 지워지지 않는다.

터미널 
git -C ~/kits-repo pull
mkdir -p ~/kits
cp -rn ~/kits-repo/Agent_03주차 ~/kits/
ls ~/kits/Agent_03주차
README.md  githooks  ops  견본  기준산출물  시연기록  양식

시연기록/은 교수가 수업 전에 올리는 규칙 유무 비교의 기록이다. 없으면 10-2절 전에 위 명령을 다시 실행한다. 양식/의 파일은 일부러 CLAUDE.md 같은 제자리 이름을 쓰지 않았다. 키트 폴더에서 Claude Code를 실행해도 양식이 규칙으로 읽히지 않게 하기 위해서이다.

[최신 자료 자리: Claude Code의 판, 명령 이름, 권장 값] 2026-11-17 확인 값: Claude Code 2.1.296. 이 장의 /memory, /context all, /status, /permissions, /init, /export, claude doctor, Loaded … 줄, CLAUDE.md 200줄 미만 권장, Windows의 PowerShell 도구는 이 판과 공식 문서를 따랐다. 확인할 곳: https://code.claude.com/docs/en/commands, https://code.claude.com/docs/en/memory, https://code.claude.com/docs/en/tools-reference, 내 PC의 claude --version.

  3. 사용자 파일은 프로젝트 파일보다 앞. 사용자 ~/.claude/CLAUDE.md의 지시는 프로젝트 지시보다 먼저 들어간다.

2-3. 가져오기와 주석

@ 가져오기. CLAUDE.md 안에 @경로를 쓰면 그 파일이 펼쳐져 함께 읽힌다. 경로는 작업 폴더가 아니라 가져오는 파일을 기준으로 해석하고, 가져온 파일이 다시 가져오는 것은 네 단계까지 된다[C1]. 경로에 빈칸이 있으면 빈칸마다 역슬래시를 붙인다. 백틱으로 감싼 `@README`와 코드 블록 안의 @는 가져오지 않는다.

- 요구와 상태는 @docs/요구사항명세서.md 에 있다      ← 명세서 전체가 함께 읽힌다
- 규약은 `docs/운영/저장소규약.md`를 따른다           ← 글자로만 남는다

가져오기는 긴 파일을 나누어 관리하는 데 도움이 되지만 컨텍스트를 줄이지는 않는다. 가져온 파일도 매번 함께 읽히기 때문이다[C1]. 그래서 이 장의 팀 CLAUDE.md는 명세서를 가져오지 않고 경로를 백틱으로 적어, 필요할 때 Claude가 열어 보게 한다.

저장소 밖의 파일을 가져오면(예: @~/.claude/my-notes.md) Claude Code는 그 프로젝트에서 처음 한 번 승인 창을 띄운다. 다른 사람이 커밋한 CLAUDE.md가 내 홈 폴더의 파일을 끌어들이는 것을 막기 위해서이다[C1].

HTML 주석. 블록 단위의 <!-- --> 주석은 컨텍스트에 넣기 전에 지워진다[C1]. 사람에게 남기는 관리 메모(「이 파일을 고치려면 PR을 연다」)를 토큰을 쓰지 않고 둘 수 있다. 코드 블록 안의 주석은 지워지지 않는다.

AGENTS.md. 여러 코딩 도구가 함께 읽는 AGENTS.md는 CLAUDE.md류의 파일이 하나도 없을 때만 대신 읽힌다. 둘을 함께 쓰려면 CLAUDE.md에 @AGENTS.md를 적는다[C1].

2-4. 무엇이 읽혔는지 확인하기

규칙이 지켜지지 않으면 문장을 고치기 전에 그 파일이 읽혔는지부터 본다. Claude Code 안에서 쓰는 명령은 다음과 같다[C1][C8].

  • /memory: 사용자와 프로젝트 범위의 CLAUDE.md, CLAUDE.local.md 위치 목록을 보이고(아직 없는 파일도 보인다), 고른 파일을 편집기로 연다. 자동 메모리를 켜고 끈다.
  • /context all: 컨텍스트를 차지하는 항목의 목록이다. 「Memory files」 아래에 시작할 때 읽힌 CLAUDE.md와 CLAUDE.local.md가 나온다.
  • 화면의 Loaded … 줄: 하위 폴더의 CLAUDE.md나 경로별 규칙이 작업 중에 읽힐 때 경로와 함께 나온다.
  • /doctor prompt-audit: 지시 파일끼리 어긋나거나 없는 파일을 가리키는 곳을 찾아 보고한다. 파일은 고치지 않는다.

3. 설정 파일의 계층과 우선순위

3-1. 지시와 설정은 무엇이 다른가

CLAUDE.md에 「.env를 읽지 않는다」라고 적는 것과 .claude/settings.json에 Read(./.env) 거부 규칙을 적는 것은 뜻은 같아 보여도 작동이 다르다. 문서는 둘을 이렇게 나눈다. 설정의 규칙은 Claude가 무엇을 하기로 하든 클라이언트가 집행하고, CLAUDE.md의 지시는 Claude의 행동을 이끌 뿐 집행 장치가 아니다[C1]. 권한 규칙은 모델이 아니라 Claude Code가 집행하며, 프롬프트나 CLAUDE.md의 지시는 Claude Code가 무엇을 허용하는지를 바꾸지 못한다[C3].

3-3. 우선순위와 합치기

같은 키가 여러 곳에 있으면 위의 것이 이긴다. 높은 것부터 적으면 다음과 같다[C2].

  1. 관리 설정. 사용자, 프로젝트, 로컬 파일이나 --settings로 덮어쓸 수 없다.
  2. 명령줄. claude --settings <파일 또는 JSON>. 그 세션에만 적용된다.
  3. 프로젝트 로컬. .claude/settings.local.json
  4. 공유 프로젝트. .claude/settings.json
  5. 사용자. ~/.claude/settings.json

여기에 세 가지 예외가 붙는다.

  • 목록은 합친다. permissions.allow 같은 목록 키가 여러 파일에 있으면 하나를 고르지 않고 모두 합친다. 그래서 각 파일은 다른 파일의 항목을 지우지 못하고 더할 수만 있다[C2].
  • 거부는 어디에 있든 이긴다. 권한 규칙은 deny → ask → allow 순서로 평가되므로, 어느 범위의 거부 규칙이든 다른 범위의 허용보다 먼저 맞는다. 사용자 설정이 허용하고 프로젝트 설정이 거부하면 거부된다. 반대로 사용자 설정의 거부도 프로젝트의 허용을 막는다[C3].
  • 환경 변수는 이 층에 없다. 같은 동작을 정하는 셸 환경 변수와 설정 키가 둘 다 있으면 어느 쪽이 이기는지는 짝마다 정해져 있다. 예를 들어 셸에서 내보낸 ANTHROPIC_MODEL은 어느 파일의 model보다 우선한다[C2].

장면 3을 이 규칙으로 다시 보면, 팀이 .claude/settings.json에 Bash(git push *)를 ask로 적어 두는 순간 가의 로컬 파일에 있는 같은 allow 규칙은 힘을 잃는다. ask가 allow보다 먼저 평가되기 때문이다. 문서도 「Yes, and don’t ask again을 골랐는데 계속 묻는다」는 증상의 원인으로 이것을 든다[C2].

3-4. 공유 프로젝트 설정에만 있는 조건

팀 파일 .claude/settings.json은 저장소에서 온다. 저장소는 남이 쓴 것일 수 있으므로, Claude Code는 이 파일의 일부를 바로 믿지 않는다[C3].

  • 작업 공간 신뢰. 팀 파일의 permissions.allow와 permissions.additionalDirectories는 그 폴더의 신뢰 확인 창을 받아들인 뒤에야 적용된다. deny와 ask는 제한만 하므로 바로 적용된다.
  • 효과가 없는 값. permissions.defaultMode의 auto와 bypassPermissions는 프로젝트와 로컬 파일에서 효과가 없다. 사용자나 관리 설정, 또는 --permission-mode로 정한다[C2].
  • 저장소 파일에서 무시되는 키. 설정 색인의 범위 열이 User, Managed 등인 키는 저장소 파일에 적어도 적용되지 않는다. 원격 측정(OpenTelemetry) 내보내기 변수도 팀 파일의 env에서는 대부분 무시된다[C2][C6].
  • 로컬 파일의 위치. 저장소의 하위 폴더에서 시작해도 로컬 파일은 저장소 루트의 것을 읽고 쓴다(Windows 등 몇 가지 예외가 있다)[C2].

신뢰 확인 창은 대화형 터미널에서만 뜨고, claude -p나 SDK 세션에서는 뜨지 않는다. 8장의 헤드리스 실행에서 이 차이를 다시 본다.

3-5. 설정이 읽혔는지 확인하기

  • /status. Claude Code 안에서 실행하면 Status 탭의 「Setting sources」 줄에 이 세션이 읽은 설정 파일이 나온다(예: User settings, Project settings, Project local settings). 어떤 파일이 어떤 키를 주었는지까지는 보여 주지 않는다[C2].
  • claude doctor. 셸에서 실행하는 점검 명령이다. 지금 폴더의 설정 파일을 신뢰 확인 없이 읽고, JSON이 깨진 파일을 「Invalid settings」 아래에 보고한다. 모델을 부르지 않는다.
  • 시작할 때의 경고. 대화형 세션을 시작할 때 JSON이 깨진 파일은 Settings Error 창으로, 규칙 하나만 잘못된 경우는 Settings Warning으로 알린다. 경고의 경우 그 항목만 건너뛰고 나머지는 적용한다[C2]. 헤드리스 실행(claude -p)은 창을 띄우지 않고 깨진 파일을 건너뛴다(8장).

4. 권한 규칙

4-1. 세 목록과 평가 순서

settings.json의 permissions 아래에는 세 목록이 있다[C3][C5].

  • allow: 묻지 않고 실행한다. 예: "Bash(python -m pytest *)"
  • ask: 실행할 때마다 확인 창을 띄운다. 확인 창을 건너뛰는 모드(acceptEdits, bypassPermissions)에서도 묻는다. 예: "Bash(git push *)"
  • deny: 실행하지 못하게 한다. 예: "Read(./.env)"

평가 순서는 deny → ask → allow이고, 이 순서에서 처음 맞는 것이 결과이다. 규칙이 얼마나 구체적인지는 순서를 바꾸지 않는다[C3]. 그러므로 넓은 거부 규칙 Bash(aws *)는 좁은 허용 규칙 Bash(aws s3 ls)에 맞는 호출까지 막는다. 허용 규칙으로 거부 규칙에 예외를 뚫을 수 없다. ask와 allow 사이도 같다.

거부 규칙이 도구 이름만 적은 것(Bash)이면 그 도구는 Claude의 컨텍스트에서 아예 빠져, Claude는 그 도구가 있다는 것조차 모른다. 범위를 적은 거부 규칙(Bash(rm *))은 도구를 남겨 두고 맞는 호출만 막는다[C3].

어느 목록에도 맞지 않는 호출은 권한 모드(4-5)의 기본 동작을 따른다. 기본(Manual) 모드에서 파일 읽기와 내장 읽기 전용 명령(ls, cat, grep, git status, git log 등)은 묻지 않고, 파일 편집과 그 밖의 셸 명령은 묻는다[C3].

4-2. 규칙의 모양

규칙은 도구 또는 도구(지정자)의 모양이다. 지정자 안의 괄호는 글자 그대로이므로 따로 처리하지 않는다[C3].

규칙 맞는 것
Bash 또는 Bash(*) 모든 셸 명령
Bash(npm run build) 정확히 npm run build
Bash(npm run *) npm run으로 시작하는 명령(npm run 자체도)
Read(./.env) 지금 폴더의 .env 읽기
Edit(/docs/**) 프로젝트의 docs/ 아래 파일 편집
WebFetch(domain:example.com) example.com으로의 가져오기
mcp__github__get_* github MCP 서버의 get_으로 시작하는 도구(5장)

도구 이름은 화면에 보이는 이름이 아니라 정식 이름을 쓴다. 화면에 「Stop Task」로 보이는 도구의 정식 이름은 TaskStop이며, 화면 이름으로 쓴 거부 규칙은 맞지 않는다. 이런 오타는 세션을 시작할 때 경고로 알려 준다[C3].

Write(경로), Glob(경로), Grep(경로)처럼 경로를 단 규칙은 받아들여지지만 실제로는 맞추어지지 않는다. 파일 쓰기는 Edit(경로)로, 검색은 Read(경로)로 적는다[C3]. 이 장의 lint_rules.py는 이런 규칙에 「주의」를 출력한다.

4-3. Bash 규칙

Bash 규칙의 *는 공백을 포함한 아무 글자에 맞는다. 문서의 예를 옮기면 다음과 같다[C3].

규칙 맞는 명령 맞지 않는 명령
Bash(npm run build) npm run build npm run build --watch
Bash(npm run *) npm run build, npm run test --watch, npm run npm install
Bash(git log * main) git log --oneline main git log main
Bash(ls *) ls -la, ls lsof
Bash(ls*) ls -la, lsof

규칙을 읽는 요령은 셋이다.

  1. 별표는 하위 명령 뒤에 둔다. git log --oneline main에서 git은 프로그램, log는 하위 명령이다. 별표 앞의 글자가 규칙의 범위를 정하므로 Bash(git log *)는 git log만, Bash(git *)는 모든 git 명령을 허용한다. Bash(git * main)처럼 하위 명령 자리에 별표가 있으면 git push origin main이나 -c 옵션으로 다른 프로그램을 실행하는 git 명령까지 맞는다. Claude Code는 이런 허용 규칙에 시작 경고를 낸다[C3].
  2. 끝의 *(빈칸과 별표)는 맨 명령도 덮는다. 별표가 그것 하나뿐일 때만 그렇다. 빈칸도 규칙의 일부이므로 Bash(ls *)는 lsof에 맞지 않는다. Bash(ls:*)는 Bash(ls *)와 같은 옛 표기이다.
  3. 복합 명령은 나누어 본다. &&, ||, ;, |, &, 줄바꿈으로 이어진 명령은 하위 명령마다 판정한다. 하위 명령이 모두 허용되어야 묻지 않고 실행되고, 하나라도 거부나 확인 규칙에 맞으면 그 규칙이 적용된다. 그래서 Bash(safe-cmd *)를 허용해도 safe-cmd && other-cmd는 허용되지 않는다[C3].

Bash 규칙에는 분명한 한계가 있다. 규칙은 Claude가 쓴 명령의 글자에 맞추어 보는 것이지, 그 프로그램 자체를 감싸는 경계가 아니다. 문서는 다음 예를 든다[C3].

규칙(deny 또는 ask) 막는 것 막지 못하는 것
Bash(curl *) curl https://example.com /usr/bin/curl https://example.com, sh -c 'curl https://example.com'
Bash(rm *) rm -rf build/ /bin/rm -rf build/, bash -c 'rm -rf build/'
Bash(git push *) git push origin main git -C . push origin main

막지 못한 명령은 다른 규칙과 권한 모드의 기본 동작으로 넘어간다. 기본 모드라면 확인 창이 뜨므로 사람이 볼 기회는 남는다. 그러나 확인 창을 건너뛰는 모드에서는 그대로 실행될 수 있다. 명령의 글자와 관계없이 막아야 하는 것은 샌드박스(운영체제 수준의 파일·네트워크 격리)나 PreToolUse 훅(6장)으로 막는다[C3]. 이 장의 거부 규칙은 「에이전트가 보통 쓰는 모양」을 막는 첫 번째 울타리로 생각한다.

4-4. Read와 Edit 규칙

파일 규칙의 경로는 .gitignore와 같은 패턴 문법을 쓴다[C3]. 앞부분의 모양에 따라 기준이 달라진다.

패턴 뜻 예
//경로 파일 시스템 루트에서의 절대 경로 Read(//etc/**)
~/경로 홈 폴더 기준 Read(~/.ssh/**)
/경로 그 설정 파일의 기준 폴더(프로젝트 설정이면 작업 폴더) Edit(/docs/**)
경로 또는 ./경로 지금 폴더 기준 Read(./.env), Read(*.env)
  • /Users/alice/file은 절대 경로가 아니다. 한 개의 빗금은 설정 파일의 기준 폴더를 뜻한다. 절대 경로는 빗금 둘(//)로 쓴다. 사용자 설정(~/.claude/settings.json)의 /secrets/**는 프로젝트가 아니라 ~/.claude/secrets/**를 가리킨다[C3].
  • 빗금이 없는 파일 이름은 어느 깊이에서나 맞는다. Read(.env)는 Read(**/.env)와 같다. Read(./.env)는 지금 폴더의 .env만이다.
  • *는 경로 한 마디 안, **는 여러 폴더에 걸친다.
  • 한 목록 안에서 !로 시작하는 패턴은 앞에 나온 규칙에서 그 경로를 빼낸다. Read(./.env.*) 다음에 Read(!.env.example)을 두면 .env.local은 거부되고 견본 파일 .env.example은 읽을 수 있다. ! 규칙이 앞에 오면 아무것도 빼내지 못하고, 다른 설정 파일의 거부도 풀지 못한다[C3].

Read 거부 규칙은 Claude의 파일 읽기 도구뿐 아니라 cat, head, tail처럼 Claude Code가 알아보는 파일 명령과 < 파일 같은 리디렉션에도 적용되고, 같은 경로의 편집과 새 파일 쓰기도 막는다. 그러나 파일 이름을 적지 않고 읽는 명령(grep -r 무엇 .)이나, 파이썬·노드 스크립트가 스스로 파일을 여는 경우에는 적용되지 않는다[C3][C5]. 문서의 팀 설정 예시는 이 틈을 샌드박스로 메운다[C6]. 샌드박스는 11장에서 다룬다.

4-5. 권한 모드

권한 모드는 규칙에 맞지 않는 호출을 어떻게 다룰지를 정한다[C4].

설정 값 화면 이름 동작
default Manual 대부분의 동작 전에 묻는다. 명령줄에서는 manual이라는 별칭도 받는다
acceptEdits Accept edits 작업 폴더 안의 파일 편집과 mkdir, touch, mv, cp 같은 흔한 파일 명령을 묻지 않는다
plan Plan 읽고 탐색해 계획을 쓰되 소스 파일을 고치지 않는다. 계획을 승인한 뒤에 고친다
auto Auto 일상적인 확인 없이 진행하고, 셸 명령과 네트워크 요청 같은 동작은 배경의 분류기가 요청과 맞는지 검사한다
dontAsk Don’t ask 확인이 필요할 호출을 모두 거부한다. 미리 허용된 것만 실행한다
bypassPermissions Bypass permissions 확인을 건너뛴다. 컨테이너나 가상 머신 같은 격리된 환경에서만 쓴다
  • 바꾸는 법. 세션 중에는 Shift+Tab으로 default → acceptEdits → plan 순으로 돌린다(dontAsk는 이 순환에 나오지 않는다). 시작할 때는 claude --permission-mode plan처럼 준다. 새 세션의 기본값은 permissions.defaultMode로 정한다[C4].
  • 시작 모드. 2026-11 문서에 따르면 터미널과 VS Code에서는 Claude Code 2.1.283 이상에서 auto 모드로 시작하고(그 계정에서 auto 모드를 쓸 수 있을 때), claude -p와 SDK는 default로 시작한다[C4]. 화면 아래의 모드 표시(예: ⏸ manual mode on)로 지금 모드를 늘 확인한다.
  • ask 규칙과 보호 경로. ask 규칙에 맞는 호출은 어느 모드에서도 묻는다. .git, .claude, .vscode, .husky 같은 보호 경로와 .bashrc, .mcp.json 같은 보호 파일의 쓰기는 default와 acceptEdits 모드에서 묻고, permissions.allow 규칙으로 미리 허용되지 않는다[C4]. 에이전트가 자기 규칙 파일을 조용히 고치지 못하게 하는 장치이다.
  • 우회 모드 끄기. permissions.disableBypassPermissionsMode를 "disable"로 두면 그 설정이 적용되는 세션에서 bypass 모드를 쓸 수 없다. 이 키는 어느 범위에서나 동작하므로 팀 파일에 두어도 된다[C3].

Claude Code 안의 /permissions는 지금 적용되는 모든 규칙과 각 규칙이 온 설정 파일을 보여 주고, 규칙을 더하거나 지울 수 있게 한다[C3][C8]. 10-5절에서 팀 파일의 규칙이 「Project settings」에서 왔는지 이 화면으로 확인한다.

4-7. Windows에서 규칙이 맞는 법

Windows에서 Claude Code는 셸 명령을 Git Bash로 실행하고, 파일 경로는 C:\Users\… 모양을 쓴다. 규칙을 쓸 때 다음 넷을 안다[C3][C11].

  1. 파일 경로는 POSIX 모양으로 바꾼 뒤 맞춘다. Windows에서 C:\Users\alice는 /c/Users/alice로 바뀐 뒤 규칙과 견주어진다. 그래서 절대 경로 규칙은 Read(//c/Users/alice/secrets/**)처럼 빗금 둘과 소문자 드라이브 글자로 쓴다. 드라이브 어디에 있든 .env를 막으려면 Read(//c/**/.env), 모든 드라이브라면 Read(//**/.env)이다[C3]. 팀 설정은 사람마다 사용자 폴더가 다르므로 ./.env, ./data/**처럼 작업 폴더 기준으로 쓰고, 역빗금(\)은 쓰지 않는다.
  2. Bash 규칙은 Claude가 Git Bash에 쓴 명령의 글자에 맞춘다. 가상 환경을 켠 터미널에서 Claude Code를 띄우면 Claude는 대개 python -m pytest -q로 부르고, 이것은 허용 규칙 Bash(python -m pytest *)에 맞는다. 같은 일을 .venv/Scripts/python -m pytest -q처럼 경로를 붙여 부르면 글자가 달라 맞지 않고, 기본 동작(확인)으로 넘어간다. 확인 창이 뜨는 쪽으로 어긋나므로 위험하지는 않지만, 허용이 기대대로 동작하지 않는 흔한 까닭이다. 그래서 CLAUDE.md의 실행 명령에도 「가상 환경을 켠 뒤 python으로」를 적는다(10-3).
  3. Windows에는 PowerShell 도구가 따로 있다. Git Bash가 설치된 Windows에서는 Claude Code가 PowerShell 명령을 직접 실행하는 PowerShell 도구를 기본으로 켠다. Bash(…) 규칙은 이 도구를 제한하지 않는다(PowerShell에는 PowerShell(Remove-Item *) 같은 자기 규칙이 있다). 그래서 어느 설정 파일에든 Bash 거부 규칙이 하나라도 있으면(범위를 적은 것도) 그 세션에서는 PowerShell 도구가 꺼진다. 거부한 일을 PowerShell로 돌아가 하지 못하게 하기 위해서이다. CLAUDE_CODE_USE_POWERSHELL_TOOL=1이나 PowerShell(…) 규칙을 두면 다시 켜지므로, 그때는 같은 뜻의 PowerShell 규칙을 따로 적는다[C11]. 이 장의 팀 설정은 PowerShell 규칙을 두지 않는다.
  4. macOS에서는 1과 3이 해당하지 않는다. 경로는 처음부터 POSIX 모양이고, PowerShell 도구는 따로 켜야만 쓴다[C11]. 두 운영체제에서 같은 뜻이 되게 하려면 상대 경로와 python으로 시작하는 명령 규칙을 쓴다.

[최신 자료 자리: Windows의 경로 정규화와 PowerShell 도구] 2026-11-17 문서 확인 값: 경로는 /c/Users/…로 바꾸어 맞추고, Git Bash가 있는 Windows에서 PowerShell 도구(미리 보기)는 기본으로 켜지며 Bash 거부 규칙이 있으면 꺼진다. 확인할 곳: [C3] 「How path patterns match」, [C11] 「PowerShell tool」.

Claude Code의 샌드박스는 macOS, 리눅스, WSL2에서 돌고 Windows 자체에서는 돌지 않는다. 이 과목은 샌드박스를 11장에서 설명과 교수 시연으로 다룬다(부록 A-1-2).

확인 3 모의기의 다섯 줄이 차례로 허용, 확인, 거부, 확인, 거부이고, 표의 「예상」 열이 채워져 있으며, 예상과 다른 줄마다 까닭이 적혀 있다.

5-1. 무엇을 넣고 무엇을 빼는가

CLAUDE.md는 매 세션 전체가 읽힌다. 그 안의 모든 줄은 관계없는 작업에서도 Claude의 주의를 조금씩 차지한다. 문서는 그래서 이 파일에 Claude가 코드만 읽어서는 알 수 없는 것만 두라고 한다[C7].

넣는다 빼거나 다른 곳에 둔다
이 저장소에서 작업을 확인하는 정확한 명령: 테스트, 테스트 하나만 돌리는 법, 검사 폴더 구조와 함수 목록. Claude가 저장소를 읽어 안다[C7]

규칙을 언제 더할지도 문서가 기준을 준다. Claude가 같은 실수를 두 번째 할 때, 코드 리뷰에서 이 저장소에 대해 Claude가 알았어야 할 것이 나올 때, 지난 세션에 했던 정정을 또 할 때, 새 팀원에게도 같은 설명이 필요할 때이다[C1]. 처음부터 모든 규칙을 예측해 적으려 하지 않고, 반복이 확인된 것만 올리는 방식이 유지 비용이 가장 낮다.

5-2. 구성

이 과목의 팀 CLAUDE.md는 다섯 부분으로 쓴다. 앞 과목에서 쓴 네 절(개요, 실행 명령, 작업 규칙, 금지)에 「이유」를 더한 것이다.

  1. 개요. 무엇을 하는 저장소인지 두세 문장과, 요구와 운영 문서가 있는 곳. 모르는 부분을 추측으로 채우는 것을 막는다.
  2. 실행 명령. 테스트, 테스트 하나, 서버, 검사의 정확한 명령. 에이전트가 스스로 결과를 확인할 수단을 주고, 명령을 추측해 틀리는 것을 막는다.
  3. 작업 규칙. 매번 말로 하던 지시와 이 저장소만의 방식. 반복 지시를 매 세션 읽히게 한다.
  4. 금지. 하면 안 되는 것. 경계를 알린다. 반드시 막아야 하는 것은 설정에도 적는다.
  5. 이유. 작업 규칙과 금지 항목 끝의 「이유: …」. 모델이 규칙의 목적을 알고 예외를 판단하게 하고, 사람이 규칙을 고칠 때 근거가 된다.

5-3. 확인할 수 있는 문장

문서는 확인할 수 있을 만큼 구체적으로 쓰라고 하며 다음 예를 든다[C1]. 「코드를 알맞게 정리한다」가 아니라 「들여쓰기는 빈칸 둘」, 「변경을 시험한다」가 아니라 「커밋하기 전에 npm test를 돌린다」, 「파일을 정돈한다」가 아니라 「API 처리기는 src/api/handlers/에 둔다」. jobprep에 옮기면 다음과 같다.

확인하기 어려운 문장 확인할 수 있는 문장

5-4. 이유 붙이기

Claude 문서의 프롬프트 작성 지침은 지시 뒤에 맥락이나 동기, 곧 그 행동이 왜 중요한지를 설명하면 Claude가 목표를 더 잘 알고 더 알맞은 응답을 낸다고 적는다[A1]. 같은 문서는 「줄임표를 절대 쓰지 마라」보다 「응답을 음성 합성기가 읽으므로 줄임표를 쓰지 않는다. 합성기는 줄임표를 읽는 법을 모른다」가 낫다는 예를 든다.

CLAUDE.md에서도 같다.

- `print`를 쓰지 않는다.
- `api/`와 `rag/`의 기록은 `logging`의 `jobprep.*` 기록기로 남기고 `print`를 쓰지 않는다.
  이유: 운영 기록의 형식(`logs/README.md`)을 지킨다.

이유가 있으면 세 가지가 달라진다.

  1. 적용 범위를 스스로 판단한다. 이유가 「운영 기록의 형식」이면, Claude는 일회성 진단 스크립트(ops/ 아래의 명령행 도구)에서 화면에 결과를 찍는 print는 이 규칙의 대상이 아니라고 판단할 수 있다.
  2. 비슷한 경우로 넓힌다. 「키가 들어 있다」는 이유는 .env.local이나 다른 비밀 파일에도 같은 태도를 끌어낸다.
  3. 사람이 규칙을 고칠 수 있다. 이유가 없는 규칙은 왜 있는지 몰라 지우지도 고치지도 못하고 쌓인다. 이유가 사라진 규칙은 지운다.

이 장의 lint_rules.py는 「금지」 절의 모든 항목에 「이유:」가 있는지 검사한다. 작업 규칙에는 이유를 강제하지 않지만, 까닭이 분명하지 않은 규칙에는 붙인다.

  • 200줄 미만. 문서는 파일 하나를 200줄 미만으로 하라고 권한다. 길수록 컨텍스트를 더 쓰고 지시를 따르는 정도가 떨어진다. 권장 길이를 넘으면 시작할 때와 /status에서 경고가 나온다[C1].

6. 경로별 규칙

6-1. .claude/rules/

저장소 일부에만 해당하는 규칙을 CLAUDE.md에 두면, 그 부분과 관계없는 작업에서도 매 세션 읽힌다. .claude/rules/ 폴더의 마크다운 파일은 이런 규칙을 주제별로 나누어 담는다. 폴더 안의 .md 파일은 하위 폴더까지 모두 찾아 읽고, 파일 하나에 주제 하나를 두며, 이름은 testing.md, api-design.md처럼 내용을 드러내게 짓는다[C1].

머리말(frontmatter)에 paths가 없는 규칙 파일은 시작할 때 .claude/CLAUDE.md와 같은 우선순위로 읽힌다. 곧 CLAUDE.md를 여러 파일로 나눈 것과 같다. paths가 있으면 맞는 파일을 다룰 때만 읽힌다[C1].

~/agent-lab/jobprep/
├── CLAUDE.md                  저장소 전체의 규칙. 매 세션
└── .claude/
    ├── settings.json          권한(설정)
    └── rules/
        ├── api.md             paths: api/**/*.py   → api/의 파이썬 파일을 다룰 때
        └── tests.md           paths: tests/**/*.py → tests/의 파이썬 파일을 다룰 때

6-2. paths 머리말

규칙 파일 맨 위의 --- 두 줄 사이에 YAML로 paths를 적는다. Claude Code가 규칙 파일에서 읽는 머리말 필드는 paths 하나뿐이고, 다른 필드는 오류 없이 무시한다. 머리말은 컨텍스트에 넣기 전에 떼어 낸다[C1].

---
paths:
  - "api/**/*.py"
---
# api/ 규칙

- 잘못된 입력은 LLM을 부르기 전에 422로 거절한다.

패턴은 규칙 파일의 .claude 폴더를 가진 폴더(곧 저장소 루트)를 기준으로 한다. 문서의 예는 다음과 같다[C1].

  • **/*.ts: 어느 깊이에 있든 .ts 파일. *.md도 어느 깊이에 있든 .md 파일이다.
  • src/**/*: src/ 아래의 모든 파일.
  • /*.md: 기준 폴더 바로 아래의 .md 파일만.
  • src/components/*.tsx: src/components/ 바로 아래의 .tsx 파일만.
  • src/**/*.{ts,tsx}: 중괄호 펼치기. .ts와 .tsx 두 패턴이 된다.

주의할 점이 셋 있다.

  1. YAML이 깨지면 조용히 넓어진다. 머리말을 YAML로 읽지 못하면 Claude Code는 머리말을 무시하고 그 규칙을 paths가 없는 것처럼, 곧 매 세션 읽는다. 오류는 claude --debug로 본다[C1]. 흔한 원인은 따옴표이다. YAML에서 따옴표 없이 *로 시작하는 값은 별칭(alias) 표시로 읽히므로 paths: **/*.py는 YAML 오류가 되고, 그 규칙은 전역 규칙이 된다. 패턴은 언제나 큰따옴표로 감싼다. 이 장의 lint_rules.py는 따옴표 없이 YAML 특수 문자로 시작하는 값을 실패로 알린다.
  2. 맞는 파일이 없는 패턴은 아무 일도 하지 않는다. web/**/*.js를 frontend/**로 잘못 적으면 그 규칙은 영영 읽히지 않는다. 이 장의 lint_rules.py는 패턴마다 저장소에서 맞는 파일 수를 세어, 0이면 실패로 알린다.
  3. [는 문자 범위의 시작이다. 파일 이름에 [가 있으면 \[로 쓴다[C1].

6-3. 언제 읽히는가

경로별 규칙은 Claude가 맞는 파일에 읽기(Read), 쓰기(Write), 편집(Edit) 도구를 쓸 때 읽힌다. cat이나 head로 파일 하나를 보는 것도 읽기로 친다[C1]. 읽히면 화면에 Loaded .claude/rules/api.md 같은 줄이 나온다. 반대로 말하면, 파일 목록만 훑거나 다른 폴더만 다루는 작업에서는 읽히지 않는다. 그래서 다음 순서가 생길 수 있다.

  1. Claude가 api/main.py에 엔드포인트를 더하기로 계획한다(아직 규칙을 모른다).
  2. api/main.py를 연다. 이때 api.md가 읽힌다.
  3. 규칙에 따라 계획을 고친다.

계획 단계에서부터 지켜야 하는 규칙이면 CLAUDE.md에 둔다. 경로별 규칙은 「그 파일을 다룰 때 알면 되는 것」에 맞는다.

위치 읽히는 때 맞는 규칙 jobprep의 예
CLAUDE.md 매 세션 시작 어떤 작업에든 적용되는 것. 실행 명령 LLM 호출은 api/llm.py만, .env 금지
.claude/rules/*.md (paths 있음) 맞는 파일을 다룰 때 특정 폴더나 파일 종류에만 해당하는 것 새 테스트의 요구 마커
하위 폴더의 CLAUDE.md 그 폴더의 파일을 다룰 때 모듈마다 팀이 다르거나 규칙이 크게 다를 때 (쓰지 않는다)
스킬 .claude/skills/*/SKILL.md 부르거나 요청이 설명과 맞을 때 여러 단계의 절차 장애 보고서 쓰기(4장)

경로별 규칙과 하위 폴더의 CLAUDE.md는 읽히는 때가 비슷하다. 차이는 관리 방식이다. 경로별 규칙은 .claude/rules/ 한 곳에 모여 있어 찾기 쉽고, 한 파일이 여러 폴더({api,rag}/**/*.py)를 덮을 수 있다. 하위 폴더 CLAUDE.md는 그 폴더를 맡은 사람이 관리하기 쉽다. 이 과목은 경로별 규칙만 쓴다.

2 새 테스트에 요구 마커 @pytest.mark.req(id="REQ-…")를 붙인다

판단의 질문은 둘이다. 「이 규칙은 어떤 작업에든 적용되는가」(그렇다면 CLAUDE.md), 「예외가 하나도 없어야 하는가」(그렇다면 설정이나 훅, 그리고 CLAUDE.md에 요약). 3번과 10번처럼 둘 다에 해당하는 규칙은 두 곳에 둔다. 9번은 검색 평가(REQ-ASK-05)를 지키려는 것이지만 지금까지 청크 크기를 바꾼 일이 없으므로 보류가 알맞다.

분류한 결과는 10-3과 10-4에서 CLAUDE.md와 경로별 규칙을 채울 때 그대로 쓴다.

7. 개인 설정과 팀 설정의 구분

7-1. 무엇을 어디에

Claude Code 문서의 디렉터리 참조는 파일마다 커밋할 것인지를 표시한다[C9]. 이 장의 파일을 그 기준으로 나누면 다음과 같다.

파일 범위 저장소에 넣는 것 예
CLAUDE.md 팀 올린다 팀이 합의한 지시 실행 명령, 작업 규칙, 금지
.claude/rules/*.md 팀 올린다 경로별 지시 api.md, tests.md
.claude/settings.json 팀 올린다 팀의 권한, 훅, 플러그인 .env 읽기 거부, git push 확인
CLAUDE.local.md 나, 이 저장소 올리지 않는다 이 저장소에서만 쓰는 개인 지시 「작업을 마치면 바뀐 파일과 테스트 결과 줄만 짧게 보고한다」(내 보고 방식)
.claude/settings.local.json 나, 이 저장소 올리지 않는다 개인 예외, 공유 전의 시험 자주 띄우는 uvicorn의 허용
~/.claude/CLAUDE.md 나, 모든 저장소 홈 폴더(저장소 밖) 모든 프로젝트의 개인 선호 「설명은 짧게 한다」
~/.claude/settings.json 나, 모든 저장소 홈 폴더(저장소 밖) 테마, 기본 모델, 개인 권한 편집기 모드

판단의 질문은 하나이다. 「이 규칙이 없으면 다른 팀원의 결과가 달라지는가.」 그렇다면 팀 파일에 올린다. 내 화면, 내 PC에서만 맞는 값, 내 습관처럼 다른 사람의 결과와 관계없는 것만 개인 파일에 둔다. 장면 3(개인 허용)이 위험했던 까닭은 「푸시는 사람이 확인한다」는 팀의 결과에 관계되는 약속이 개인 파일에서 바뀌었기 때문이다.

7-2. .gitignore에 넣는 까닭

Claude Code는 확인 창의 「Yes, and don’t ask again」으로 로컬 설정 파일을 처음 쓸 때, 그 저장소가 이 파일을 아직 무시하지 않으면 **/.claude/settings.local.json을 전역 제외 파일에 더한다. 전역 제외 파일은 git 설정의 core.excludesFile이고, 이 값이 없으면 ~/.config/git/ignore이다[C2]. 이것은 이 컴퓨터, 이 사용자의 설정이다. 다른 팀원의 컴퓨터, 손으로 파일을 만든 경우, 다른 도구가 파일을 만든 경우에는 무시되지 않는다. CLAUDE.local.md는 Claude Code가 대신 무시 목록에 넣어 주지 않는다[C1].

그러므로 두 파일을 저장소의 .gitignore에 적는다. 저장소의 .gitignore는 커밋되어 모든 클론에 같이 간다.

7-3. 따라 하기 2: 개인 파일 만들기와 제외

먼저 개인 파일 둘을 만든다. 하나는 이 저장소에서 나만 쓰는 보고 방식의 지시이고, 다른 하나는 내가 API 서버를 자주 띄우므로 uvicorn을 묻지 않게 하는 개인 허용이다. 둘 다 다른 팀원의 결과를 바꾸지 않는다.

터미널 
cd ~/agent-lab/jobprep
mkdir -p .claude
cat > .claude/settings.local.json <<'EOF'
{
  "permissions": {
    "allow": [
      "Bash(uvicorn *)"
    ]
  }
}
EOF
printf '# 개인 지시 (이 컴퓨터, 이 저장소에서만)\n- 작업을 마치면 바뀐 파일 목록과 python -m pytest -q의 결과 줄만 짧게 보고한다\n' > CLAUDE.local.md
git status --short
?? .claude/
?? CLAUDE.local.md

두 파일이 「추적하지 않는 파일」(??)로 보인다. 이 상태에서 git add -A나 git add .를 하면 장면 4가 된다. 무시 규칙이 있는지 git check-ignore -v로 확인한다. -v는 어느 파일의 몇째 줄 규칙이 그 경로를 무시하게 하였는지 알려 준다[G7].

터미널 
git check-ignore -v .claude/settings.local.json CLAUDE.local.md; echo "종료 코드 $?"
종료 코드 1

종료 코드 1은 「주어진 경로 가운데 무시되는 것이 없다」는 뜻이다[G7]. 이 PC에서 이미 Claude Code가 로컬 설정 파일을 쓴 적이 있으면 첫 줄에 전역 제외 파일의 경로가 나올 수 있다. 그래도 저장소의 .gitignore에는 넣는다.

터미널 
cat >> .gitignore <<'EOF'

# Claude Code 개인 설정: 팀 설정은 CLAUDE.md와 .claude/settings.json으로 공유한다
.claude/settings.local.json
CLAUDE.local.md
EOF
git check-ignore -v .claude/settings.local.json CLAUDE.local.md; echo "종료 코드 $?"
git status --short
python ops/rules/lint_rules.py | grep C4
git add .gitignore
git commit -m "chore: 개인 설정 파일을 git 추적에서 제외"
.gitignore:26:.claude/settings.local.json   .claude/settings.local.json
.gitignore:27:CLAUDE.local.md   CLAUDE.local.md
종료 코드 0
 M .gitignore
통과 C4 .claude/settings.local.json은(는) .gitignore에 의해 무시된다
통과 C4 CLAUDE.local.md은(는) .gitignore에 의해 무시된다
[chore/team-rules 7022b26] chore: 개인 설정 파일을 git 추적에서 제외
 1 file changed, 4 insertions(+)

두 파일은 .gitignore의 26, 27번째 줄에 의해 무시되고, git status에는 .gitignore의 변경만 보인다. .claude/ 폴더 자체는 무시하지 않는다. 그 안의 settings.json과 rules/는 팀 파일이기 때문이다. lint_rules.py는 무시 규칙이 저장소의 .gitignore가 아니라 이 PC의 전역 제외 파일에서만 온 경우를 실패로 센다. 다른 팀원의 PC에서는 무시되지 않기 때문이다.

확인 4 git check-ignore -v가 두 파일을 .gitignore의 줄 번호와 함께 출력하고, git status --short에 두 개인 파일이 보이지 않으며, git log --oneline -1이 chore: 개인 설정 파일을 git 추적에서 제외이다.

7-4. 이미 올라간 개인 파일 내리기

장면 4처럼 개인 파일이 이미 커밋되었다면 .gitignore에 적는 것만으로는 부족하다. 무시 규칙은 아직 추적하지 않는 파일에만 적용된다. 추적을 멈추되 내 컴퓨터의 파일은 남기려면 --cached를 붙인다.

[터미널] (개인 파일을 이미 커밋한 경우에만)

git rm --cached .claude/settings.local.json CLAUDE.local.md
git commit -m "chore: 개인 설정 파일을 저장소에서 내림"

이렇게 해도 과거 커밋에는 파일이 남는다. 개인 설정에 비밀 정보가 들어 있었다면 내리는 것으로 끝나지 않고 그 비밀(키, 토큰)을 폐기하고 새로 발급해야 한다. 비밀 정보의 관리는 11장과 13장에서 다룬다.

8. 저장소 규약

8-1. 규약이 하는 일

지시와 설정은 에이전트가 일하는 동안, 저장소 규약은 그 결과가 저장소에 들어올 때 작동한다. 규약을 정해 두면 세 가지를 얻는다.

  1. 이력을 읽을 수 있다. 「요약 API의 응답 형식은 언제 바뀌었는가」를 git log --grep "^feat(api)"로 찾는다.
  2. 자동화할 수 있다. 커밋의 종류로 판 번호를 올리고 릴리스 노트를 만든다. 검사를 기계로 돌린다(13장의 CI).
  3. 검토가 알맞은 사람에게 간다. 규칙 파일이 바뀌면 규칙 파일의 소유자에게 검토 요청이 간다.

규약은 docs/운영/저장소규약.md 한 곳에 원본을 둔다. CLAUDE.md에는 요점(커밋 첫 줄의 모양, 규약 문서의 위치)만 적는다. 같은 내용을 두 곳에 길게 적으면 한쪽만 고쳐져 어긋난다.

8-2. 브랜치 이름

이 과목의 규약은 <종류>/<설명>이다. 종류는 feat, fix, docs, test, refactor, chore, ci 가운데 하나이고, 설명은 영문 소문자, 숫자, 하이픈으로 쓴다(feat/closing-within, chore/team-rules). 브랜치 이름에 한글을 쓰지 않는 까닭은 셸과 URL에서 따옴표와 인코딩 문제를 피하기 위해서이다. 브랜치 하나는 목적 하나이다.

뒤의 장은 종류 셋을 더 쓴다. 8장은 루프 실험에 loop/<이름>(예: loop/success-1)과 연습에 practice/<이름>을 쓰고, 10장은 에이전트 하나가 맡은 작업에 agent/<이슈>-<작업>(예: agent/issue-07-t1)을 쓴다. 10장에서 이슈 하나의 작업을 모으는 통합 브랜치는 feat/issue-07처럼 feat이다. 키트의 check_commits.py는 처음부터 이 세 종류도 허용하므로, 뒤의 장에서 규약과 검사 도구를 다시 고치지 않는다.

8-3. 커밋 메시지: Conventional Commits

Conventional Commits 1.0.0은 커밋 메시지의 구조를 다음과 같이 정한다[K1].

<type>[optional scope]: <description>

[optional body]

[optional footer(s)]
  • 종류(type). feat(기능 추가)와 fix(결함 수정)는 명세가 정한다. build, chore, ci, docs, style, refactor, perf, test 등은 명세가 허용하고 @commitlint/config-conventional(Angular 관례 바탕)이 권하는 것이다[K1].
  • 범위(scope). 선택. 괄호 안의 명사로 코드베이스의 부분을 가리킨다(feat(api):).
  • 설명. 콜론과 빈칸 뒤에 변경의 요약을 쓴다.
  • 본문과 꼬리말. 선택. 각각 앞에 빈 줄 하나를 둔다. 꼬리말은 토큰: 값이고, 토큰의 빈칸은 하이픈으로 쓴다(Reviewed-by).
  • 하위 호환을 깨는 변경. 콜론 앞의 !(feat(api)!:) 또는 꼬리말 BREAKING CHANGE: 설명. 꼬리말의 이 토큰은 대문자여야 한다.

명세는 커밋 종류를 유의적 버전(Semantic Versioning)과 잇는다. fix는 PATCH, feat는 MINOR, 하위 호환을 깨는 변경은 종류와 관계없이 MAJOR에 해당한다[K1]. 13장의 릴리스 태그에서 이 대응을 쓴다.

jobprep의 규약은 명세 위에 몇 가지를 더 정한다. 명세는 요소의 대소문자를 가리지 않지만(BREAKING CHANGE 제외)[K1], 이 저장소는 종류를 소문자로 쓴다. 설명은 한국어로 쓰고 끝에 마침표를 찍지 않으며, 첫 줄은 72자 이하로 한다. 요구와 관련된 커밋은 꼬리말에 Refs: REQ-…를 적는다. 범위는 api, rag, web, tests, docs, ops, claude(규칙과 설정 파일)를 쓴다. 요구 하나를 시험하거나 구현하는 커밋은 2장에서처럼 범위에 요구 ID를 쓴다(test(REQ-JOB-06): …, feat(REQ-JOB-06): …).

feat(api): 공고 목록에 마감 임박 필터 추가

closing_within=N이면 오늘부터 N일 안에 마감되는 공고만 돌려준다.

Refs: REQ-JOB-06

8-4. PR 템플릿

PR 템플릿은 PR을 열 때 본문에 자동으로 채워지는 마크다운 파일이다[G1]. 파일 이름은 pull_request_template.md이고 저장소 루트, docs/, 숨은 폴더 .github/ 가운데 한 곳에 둔다[G2]. 여러 템플릿이 필요하면 PULL_REQUEST_TEMPLATE/ 하위 폴더에 두고, PR을 만드는 주소의 template 질의 매개변수로 고른다[G2].

가장 자주 놓치는 조건은 이것이다. 템플릿은 저장소의 기본 브랜치(main)에 있어야 쓰인다[G1][G2]. 이 장에서 템플릿을 처음 더하는 PR은 템플릿이 아직 main에 없으므로, 그 PR의 본문에는 템플릿이 자동으로 채워지지 않는다. 이 PR은 GitHub CLI의 --template 옵션(gh pr create --template .github/pull_request_template.md)으로 로컬 파일을 본문의 출발점으로 쓴다(10-8).

[최신 자료 자리: GitHub의 화면 이름과 기능 범위] 이 장의 「Files changed」 탭, 보호 브랜치의 「Require review from Code Owners」, 템플릿과 CODEOWNERS의 위치, 비공개 저장소에서 코드 소유자를 쓸 수 있는 플랜은 2026-11-14의 GitHub Docs를 따랐다. 확인할 곳: [G1], [G2], [G5]의 주소, https://docs.github.com/en/get-started/learning-about-github/githubs-plans.

8-5. 이슈 템플릿

이슈 템플릿은 .github/ISSUE_TEMPLATE/에 둔다. 입력 칸을 가진 이슈 양식은 YAML로 쓰고 name, description, body 세 키로 시작해야 하며, 같은 폴더의 config.yml에 blank_issues_enabled: false를 두면 빈 이슈를 막는다[G3][G4]. 10장에서 조정자 에이전트가 읽을 이슈의 형식을 맞추는 데 쓸 수 있으며, 이 장의 핵심 실습에는 넣지 않는다.

8-7. 리뷰 규칙과 규칙 파일의 검토

jobprep의 리뷰 규칙은 다음과 같다(규약 4절).

  1. 모든 PR은 작성자가 아닌 사람 1명 이상의 승인을 받는다. GitHub에서 PR 작성자는 자기 PR을 승인할 수 없다[G6]. 개인 저장소에서 혼자 일하는 동안에는 PR 템플릿의 점검표로 자기 검토를 하고 기록을 남긴다. 팀 저장소(프로젝트실습Ⅱ)에서는 이 규칙이 그대로 적용된다.
  2. CODEOWNERS에 소유자가 있는 경로를 바꾸면 그 소유자의 검토를 받는다.
  3. 규칙 파일을 바꾸는 PR은 무엇을 왜 바꾸었는지와 lint_rules.py의 결과를 적는다.
  4. 에이전트가 만든 변경도 같은 기준으로 리뷰한다. 완료 보고가 아니라 diff와 검사 결과를 본다.

3번이 이 장의 주제와 직결된다. 규칙 파일은 문서처럼 보이지만 코드보다 영향이 넓다.

  • CLAUDE.md의 한 줄은 그 저장소에서 일하는 모든 사람의 모든 에이전트 세션에 들어간다.
  • .claude/settings.json의 허용 규칙 하나는 모든 팀원의 에이전트가 묻지 않고 할 수 있는 일을 늘린다. 예를 들어 "Bash(git *)"를 허용 목록에 넣는 변경은 강제 푸시를 포함한 모든 git 명령의 확인을 없앤다.
  • 남이 만든 저장소의 규칙 파일에는 의도하지 않은 지시가 들어 있을 수 있다. Claude Code가 저장소 밖 파일의 가져오기와 팀 파일의 허용 규칙에 신뢰 확인을 두는 까닭이다(2-3, 3-4). 저장소에 들어온 글이 에이전트의 지시가 되는 문제(프롬프트 주입)는 11장에서 다룬다.

그래서 규칙 파일은 코드와 같은 검토를 받는다. 소유자가 있고(CODEOWNERS), 바꾼 까닭이 남고(PR 템플릿의 칸), 기계 검사가 있다(lint_rules.py). 규칙 파일의 판을 태그(rules-v1)로 표시해 두면 「이 결과는 어느 판의 규칙에서 나왔는가」를 나중에 재현할 수 있다.

8-8. 규약의 강제: commit-msg 훅

커밋 메시지 규약은 사람과 에이전트가 커밋하는 순간에 검사할 수 있다. git의 commit-msg 훅은 git commit이 부르는 스크립트로, 제안된 메시지가 든 파일의 이름을 인자로 받고, 0이 아닌 값으로 끝나면 커밋을 멈춘다[G8]. 훅 폴더는 기본으로 .git/hooks이고 core.hooksPath 설정으로 바꿀 수 있다[G8].

여기서 「팀에 공유되지 않는 설정」의 예가 하나 더 나온다. .git/hooks의 훅은 저장소를 클론할 때 복사되지 않는다[G9]. core.hooksPath도 저장소의 .git/config에 들어가는 로컬 설정이라 커밋되지 않는다. 그래서 훅 스크립트는 저장소의 .githooks/에 커밋하고, 각자 클론마다 한 번 git config core.hooksPath .githooks를 실행한다. 이 명령은 저장소 규약에 적어 둔다.

운영체제에 따라 다른 점이 둘 있다.

  • 실행 권한. macOS와 리눅스의 git은 실행 권한이 없는 훅을 오류 없이 무시한다[G8]. 그래서 chmod +x를 빠뜨리면 규약을 어긴 메시지가 조용히 커밋된다. Windows의 Git Bash는 실행 권한과 관계없이 훅을 돌리지만, 파일 시스템에 실행 권한이 없어 git add가 파일 모드를 100644로 기록한다. 그대로 커밋하면 이 저장소를 macOS에서 클론한 팀원의 훅은 돌지 않는다. Windows에서는 git update-index --chmod=+x로 실행 권한을 커밋에 기록한다(10-6).
  • 훅이 부르는 파이썬. 훅은 가상 환경을 켜지 않은 채 돈다. 키트의 훅은 .venv/Scripts/python.exe(Windows)를 먼저, 없으면 .venv/bin/python(macOS)을 찾는다(부록 A-9-2). 병합 커밋(Merge branch …)은 검사하지 않는다.

commit-msg 훅은 git commit --no-verify로 건너뛸 수 있다[G8]. 사람에게는 이것이 필요한 탈출구이지만, 에이전트가 훅을 건너뛰는 것은 막아야 한다. 그래서 10절의 팀 설정에 Bash(git commit *--no-verify*) 거부 규칙을 넣는다. 별표를 옵션의 양쪽에 두어 git commit --no-verify -m …과 git commit -m … --no-verify를 모두 덮는다. 거부 규칙이므로 별표가 하위 명령 뒤에 오지 않아도 범위가 넓어지는 위험이 없다. 이 규칙도 4-3의 한계를 가진다. 같은 뜻의 짧은 옵션 git commit -n은 맞지 않는다. 사람이 마지막으로 보는 자리는 PR 검토와 13장의 CI이다. 훅은 10-6에서 켠다.

9. 규칙 유무 비교의 방법

9-1. 무엇을 비교하는가

규칙을 만들었다고 해서 효과가 있는 것은 아니다. 지시는 모델이 따르지 않을 수 있고(1-2), 규칙의 문장이 모호하거나 위치가 잘못되면 읽히지도 않는다(2-4, 6-3). 규칙의 효과는 재어 보아야 안다. 이 장의 비교는 단순하다.

  • 같은 요청을 두 저장소에 보낸다. 하나는 규칙이 없는 tdd-1 시점, 하나는 규칙을 모두 넣은 시점(10절의 chore/team-rules, 첫 판은 태그 rules-v1)이다.
  • 결과에서 규칙 위반의 수를 센다. 셀 수 있는 규칙만 센다.
  • 함께 테스트의 통과 여부를 본다. 규칙을 지키느라 기능이 깨졌다면 좋은 결과가 아니다.

7장은 이 비교를 작업 3건으로 넓히고, 12장은 반복 실행의 분산까지 다룬다.

9-5. 결과를 규칙으로 되돌리기

비교의 목적은 숫자가 아니라 규칙을 고치는 데 있다. 위반이 남은 규칙마다 다음 순서로 판단한다.

  1. 읽혔는가. 그 규칙의 파일이 세션에 들어갔는지 본다(/context all, Loaded 줄). 읽히지 않았다면 위치를 고친다(예: 계획 단계부터 필요한 규칙을 경로별 규칙에서 CLAUDE.md로).
  2. 문장이 확인할 수 있는가. 모호한 문장이면 5-3의 방식으로 고친다.
  3. 이유가 있는가. 이유가 없어 예외로 판단되었다면 이유를 붙인다.
  4. 예외가 없어야 하는가. 그렇다면 지시가 아니라 설정이나 훅으로 옮긴다. R5(보호 경로)는 이미 거부 규칙이 있다. R7(테스트 없이 코드 변경)은 6장에서 편집 뒤 테스트를 돌리는 훅으로, R10(커밋 메시지)은 8-8의 commit-msg 훅으로 강제한다.
  5. 그대로 둔다. 위반이 드물고 비용이 작으면 PR 검토에 맡긴다.

이 판단을 docs/운영/규칙비교.md의 마지막 표에 적는다.

정리

  • 팀 규칙은 세 층이다. 지시(CLAUDE.md, .claude/rules/)는 모델이 읽고 판단하고, 설정(.claude/settings.json)은 Claude Code가 강제하고, 저장소 규약(규약 문서, PR 템플릿, CODEOWNERS, 커밋 훅)은 사람과 Git·GitHub가 집행한다.
  • CLAUDE.md는 관리 정책, 사용자, 프로젝트, 로컬의 네 위치가 있고, 찾은 파일은 모두 이어 붙여 읽힌다. 충돌을 풀어 주는 규칙은 없으므로 범위마다 겹치지 않게 쓴다.
  • 설정은 관리 > 명령줄 > 로컬 > 프로젝트 > 사용자 순으로 우선하고, 목록은 합쳐진다. 권한 규칙은 deny → ask → allow 순서로 평가되므로 어느 범위의 거부든 다른 범위의 허용을 이긴다.
  • Bash와 Read 규칙은 명령과 경로의 글자에 맞출 뿐 프로그램을 감싸는 경계가 아니다. Windows에서는 경로가 /c/… 모양으로 바뀐 뒤 맞추어지고, Bash 거부 규칙이 있으면 PowerShell 도구가 꺼진다. 남은 틈은 훅(6장)과 샌드박스(11장)가 맡는다.
  • 좋은 CLAUDE.md는 짧고(200줄 미만), 확인할 수 있는 문장으로 쓰고, 정확한 실행 명령을 담고, 규칙에 이유를 붙인다. Claude가 코드를 읽어 알 수 있는 것은 쓰지 않는다.
  • 개인 설정(CLAUDE.local.md, settings.local.json)은 저장소의 .gitignore로 뺀다. 「이 규칙이 없으면 다른 팀원의 결과가 달라지는가」가 팀 파일과 개인 파일을 가르는 질문이다.
  • 규칙을 만든 것과 문제가 풀린 것은 다르다. 규칙 없음에서 생긴 어긋남이 같은 요청에서 다시 나오지 않는지로 판정하고, 남으면 위치, 문장, 이유, 강제 여부를 고친다.

개념 점검 문항

  1. 사용자 설정에 "allow": ["Bash(git push *)"], 팀 설정에 "ask": ["Bash(git push *)"], 로컬 설정에 "deny": ["Bash(git push --force *)"]가 있다. git push origin main과 git push --force origin main은 각각 어떻게 판정되는가. 까닭을 평가 순서로 설명하라.
  2. 「.env를 읽지 않는다」를 CLAUDE.md에만 둔 경우와 Read(./.env) 거부 규칙으로만 둔 경우, 각각 막지 못하는 상황을 하나씩 들라.
  3. 다음 CLAUDE.md 줄을 확인할 수 있는 문장과 이유로 고쳐 쓰라. 「API 코드는 깔끔하고 안전하게 작성한다.」
  4. Windows의 팀원이 팀 설정에 "allow": ["Bash(.venv/Scripts/python -m pytest *)"]를 적어 올렸다. macOS의 팀원과 가상 환경을 켠 Windows 팀원의 세션에서 이 규칙은 각각 어떻게 작동하는가. 팀 설정에는 어떻게 쓰는 것이 알맞은가.
  5. CODEOWNERS가 다음과 같을 때 .claude/settings.json의 소유자는 누구인가. 「/.claude/ @a」 다음 줄에 「* @b」. 의도대로 고치려면 어떻게 하는가.
