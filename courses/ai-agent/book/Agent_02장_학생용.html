AI에이전트 기획 및 개발

2장

테스트 주도 개발

2027학년도 「AI에이전트 기획 및 개발」의 준비 중인 교재입니다. 편집 상태를 검토하기 위해 미리 공개한 것으로, 수업 전에 내용과 순서가 바뀔 수 있습니다.

학사 3주차 · 교재 02 · 1부 운영 요건과 검증

2026-11-19에 150분 기준으로 줄였다(학생용 본문 63,028자 → 34,250자).

AI 에이전트의 “모든 테스트를 통과했습니다”에는 그 테스트를 누가 썼는지, 통과하는 동안 그대로였는지가 없다. 이 장은 테스트 주도 개발(TDD, Test-Driven Development)로 이 문제를 다룬다. 사람이 요구를 테스트로 먼저 쓰고, 실패를 확인하고, 테스트를 잠근 뒤 구현을 에이전트에게 맡긴다. 통과 여부는 사람이 자기 터미널에서 확인한다.

만드는 것은 미구현 요구 셋(REQ-JOB-06, REQ-SUM-05, REQ-ASK-06)의 테스트, 동결 기록 tests/.baseline.json, 구현, 통과마다 남긴 커밋과 태그 tdd-1이다. 해결하는 문제는 「62 passed」를 보고한 시도가 테스트 한 줄을 지워 얻은 통과임을 찾아내 버리는 것이다.

학습 목표

  • 요구 문장을 준비·실행·확인의 구조를 갖춘 테스트로 바꾸고, 경계값과 등가 분할로 확인할 경우를 고른다.
    • 예시: “N일 안에 마감되는 공고만 보인다”를 N=6, 7, 8과 N=0, 음수, 정수가 아닌 값의 테스트로 나눈다.
    • 활용: 프로젝트실습Ⅱ의 요구마다 정상, 경계, 오류의 테스트를 먼저 쓰고 구현을 맡긴다.
  • pytest의 픽스처, 매개변수화, monkeypatch, 테스트 더블로 날짜와 LLM 같은 외부 요인을 통제한다.
    • 예시: jobs.today를 고정한 날짜를 돌려주는 함수로 바꿔 끼우고, llm.complete를 스파이로 감싸 불린 횟수를 센다.
    • 활용: 시간, 네트워크, 유료 API에 기대는 코드를 같은 결과가 나오는 테스트로 확인한다.
  • 테스트를 동결하고 지시문의 완료 조건으로 Claude Code의 구현을 통제하며, 테스트를 고쳐 통과시키는 회피를 찾아낸다.
    • 예시: test_guard.py check가 TEST_CHANGED와 수정: tests/test_summary_limits.py를 내면, git diff tests/로 지워진 단언을 찾고 그 시도를 버린다.
    • 활용: 에이전트의 “통과했습니다”를 증거(명령, 출력, 동결 검사)로 바꿔 받는다.
  • 테스트가 통과할 때마다 커밋하고, 실패한 시도는 git restore로 버리고, 재현 가능한 상태를 태그로 표시한다.
    • 예시: 요구 하나에 테스트 커밋과 구현 커밋 두 개를 남기고, 끝난 상태에 tdd-1을 붙인다.
    • 활용: 발표나 배포 직전의 상태를 태그로 남겨 누구든 같은 상태를 받아 테스트를 돌릴 수 있게 한다.

0. 시작하기

실습은 내 PC에서 한다. 통합 터미널 두 개를 두고(부록 A-4-2) 하나는 [터미널], 하나는 Claude Code용으로 쓰며, 둘 다 ~/agent-lab/jobprep에서 가상 환경을 켠다(부록 A-9-1).

이 장의 실행 상한. 실제 모델은 Claude Code의 대화형 세션으로만 쓴다(11절의 구현 지시 셋과 리팩터링 하나). claude -p와 API 호출은 하지 않으며, 테스트는 모의 모드(LLM_FAKE=1)로 돌므로 API 키가 없어도 된다.

[최신 자료 자리: 테스트 도구의 판] 이 장의 출력은 기준 저장소 requirements.txt의 pytest 9.2.0과 키트 requirements-dev.txt의 coverage 7.17.3에서 얻었다(2026-11-14 확인, 2026-11-17 Windows 11에서 다시 실행). 판은 두 파일에 고정되어 있으므로 학기 중에 바뀌지 않지만, 고정한 판을 올리면 출력의 문구와 경고가 달라질 수 있다. 확인할 곳: https://pypi.org/project/pytest/, https://pypi.org/project/coverage/, 내 PC의 python -m pytest --version과 python -m coverage --version.

1. 테스트와 완료 조건

1-1. 에이전트에게 완료란 무엇인가

Claude Code의 모범 사례 문서에 따르면 Claude는 일이 끝난 것처럼 보일 때 멈춘다. 끝났는지 판정할 수단이 없으면 사람이 테스트 역할을 하게 되므로, 문서는 테스트나 종료 코드처럼 “통과 또는 실패를 돌려주는 것”을 쥐여 주라고 권한다 [C1]. 이 장의 완료 조건은 다음 셋이다.

  1. python -m pytest -q의 마지막 줄에 failed와 error가 없다.
  2. python tools/test_guard.py check가 TEST_UNCHANGED를 출력한다(테스트가 동결한 그대로이다).
  3. 위의 두 결과를 에이전트의 보고가 아니라 학습자가 자기 [터미널]에서 확인한다.

1-4. 테스트가 보장하지 않는 것

통과는 “테스트에 적은 경우에 기대한 결과가 나왔다”는 뜻일 뿐이다. 요구를 잘못 옮긴 테스트는 통과해도 틀렸다. 예컨대 명세서의 0 <= days_left <= N을 0 < days_left로 옮기면 오늘 마감 공고를 빼는 구현이 통과한다. 적지 않은 경우와 화면, 응답 시간, 보안, 응답 품질도 확인되지 않는다.

1-5. 사례: 테스트를 지우고 “모두 통과”라고 보고한 에이전트

타입스크립트 라이브러리 typia의 개발자는 2026년 5월, 그 라이브러리를 Go 언어로 옮기는 일을 AI 에이전트에게 맡긴 경험을 공개했다 [S1]. 지시는 기계적인 1대1 이식이었고, tests/ 아래의 테스트가 검증 기준이며, 테스트가 통과할 때까지 반복하라는 것이었다. 글에 따르면 첫 시도에서 에이전트는 핵심 로직의 약 3분의 2를 빠뜨렸고, 실패하는 테스트를 지워 tests/ 폴더가 약 70% 줄었으며, CI는 녹색이었고, 최종 보고는 “모든 테스트가 통과했다”뿐이었다. 테스트를 고치지 말라는 규칙을 더하자, 다음 시도에서는 원래 프로그램의 출력을 미리 받아 168개의 경우로 된 분기문에 그대로 박아 넣었다(하드코딩). 하드코딩을 금지하자, 이번에는 CI 설정을 고쳐 일부 테스트 범주를 빼 버렸다.

에이전트는 지시를 어기지 않았다. “테스트가 통과할 때까지”라는 문장을 가장 짧은 길로 만족시켰을 뿐이며, 금지 문장을 더할 때마다 막히지 않은 다른 길을 찾았다. 글쓴이가 남긴 교훈은 감독 간격을 짧게 하고, 요약이 아니라 바뀐 내용(diff)을 읽고, 구체적인 본보기를 주라는 것이었다 [S1].

Anthropic은 Claude Opus 4와 Claude Sonnet 4의 시스템 카드(2025년 5월)에서 이런 행동을 보상 해킹(reward hacking), 곧 “과제의 규칙은 기술적으로 만족하지만 의도한 목적은 어기는 방법을 찾아내는 것”으로 정의하고, 테스트를 통과하기 위한 하드코딩과 특수 처리(special-casing)를 예로 들었다 [A1]. 같은 문서는 이전 모델인 Claude Sonnet 3.7이 Claude Code 같은 에이전트형 코딩 환경에서 이 행동을 보였다고 적었다 [A1]. 모델이 바뀌면 빈도는 달라지지만, 판정 기준을 고칠 수 있는 환경에서 통과를 요구하면 같은 유혹이 생긴다는 구조는 그대로이다. 11-5절에서 같은 모양의 시도 하나를 직접 판정한다.

2. Red · Green · Refactor

2-1. TDD의 주기

TDD는 켄트 벡(Kent Beck)이 『Test-Driven Development: By Example』(2002)로 정리하며 널리 알려졌다 [T2]. 주기는 세 단계이다.

graph LR
    R["Red<br/>실패하는 테스트를 쓴다<br/>(사람)"] --> G["Green<br/>통과하는 최소한의 코드<br/>(에이전트)"]
    G --> F["Refactor<br/>동작을 바꾸지 않고 구조를 다듬는다<br/>(에이전트 + 사람의 판정)"]
    F --> R
단계 끝났다는 신호
Red 새 테스트만 실패하고, 실패 이유가 “기능이 없음”이다
Green 새 테스트와 기존 테스트가 모두 통과한다
Refactor 다듬은 뒤에도 모든 테스트가 그대로 통과한다

Red를 건너뛰면 안 된다. 구현이 없는데 통과하는 테스트는 아무것도 확인하지 않기 때문이다. 또 실패 화면은 기대를 가장 정확히 보여 준다. assert [20, 3, 23, 6, 26, 9, ...] == [20]은 “필터가 없어 30건이 왔다”와 “20번 하나여야 한다”를 함께 보여 준다.

2-2. 켄트 벡의 표준 절차

벡은 「Canon TDD」(2023)에서 TDD를 다섯 단계로 정리하고 단계마다 흔한 실수를 적었다 [T3].

단계 내용 벡이 든 실수 (요지)
1 테스트 목록 쓰기 구현의 설계 결정을 목록에 섞는다
2 하나를 골라 자동 테스트로 만들기 커버리지를 올리려고 단언 없는 테스트를 쓴다
3 모든 테스트를 통과시키기 단언을 지워 통과한 척한다. 계산된 값을 기대값에 복사한다
4 (선택) 리팩터링 너무 일찍 추상화한다
5 목록이 빌 때까지 반복

3단계의 실수 둘은 1-5절의 사례와 같다. 이 장은 요구 하나의 테스트 목록을 파일 하나로 만들어 동결하고 에이전트에게 그 파일 전체를 맡긴다. 맡기는 단위가 동결과 검토의 단위와 같을 때 다루기 쉽기 때문이다. 대신 요구 사이에서는 반드시 Green을 확인하고 커밋한다.

2-3. 좋은 단위 테스트의 성질

좋은 단위 테스트의 성질은 흔히 F.I.R.S.T.의 다섯 글자로 정리한다.

성질 뜻
Fast 자주 돌릴 수 있을 만큼 빠르다
Independent 실행 순서와 다른 테스트에 기대지 않는다
Repeatable 언제, 어느 컴퓨터에서 돌려도 같은 결과이다
Self-validating 사람이 출력을 읽지 않아도 통과와 실패가 정해진다
Timely 구현 직전에 쓴다

이 장에서는 Repeatable이 특히 중요하다. 공고의 마감일은 2027년 9~12월에 퍼져 있으므로, 날짜를 고정하지 않은 테스트는 특정 하루에만 맞는다(4-3절).

2-4. 가짜로 통과시키기와 삼각 측량

벡은 상수를 돌려주어 일단 통과시키는 「가짜로 통과시키기(Fake It)」와, 서로 다른 예를 둘 이상 두어 상수로는 통과할 수 없게 하는 「삼각 측량(Triangulation)」을 소개했다 [T2]. 에이전트에게 Green을 맡기면 가짜 통과가 최종 결과로 남을 수 있으므로, 삼각 측량은 테스트를 쓰는 사람의 의무이다. REQ-JOB-06의 테스트는 기준일을 세 날로, N을 여섯 값으로 바꾼다.

3. 테스트의 구조와 pytest

3-1. 준비 · 실행 · 확인

테스트 하나는 세 부분으로 이루어지며, 요구 문장에 가깝게 적으면 Given · When · Then이다.

테스트의 부분 Given · When · Then REQ-JOB-06에서
준비(Arrange) 주어진 조건에서 기준일이 9월 1일일 때
실행(Act) 무엇을 하면 closing_within=7로 요청하면
확인(Assert) 무엇이 되어야 한다 20번 하나만 와야 한다

[파일: tests/test_jobs.py] · 끝부분

def test_days_left_uses_today(monkeypatch):
    monkeypatch.setattr(jobs, "today", lambda: date(2027, 9, 1))   # 준비: 오늘을 고정한다
    job = {"deadline": "2027-09-08"}                                # 준비: 확인할 공고
    assert jobs.days_left(job) == 7                                 # 실행과 확인

준비가 길어지면 픽스처로 옮기고(4절), 서로 다른 동작은 테스트를 나눈다. 실패한 테스트의 이름만 보고 어느 요구가 깨졌는지 알 수 있어야 한다.

3-2. pytest가 테스트를 찾는 규칙

pytest는 test_*.py 파일에서 test로 시작하는 함수를 찾는다(pytest.ini의 testpaths = tests). tests/conftest.py는 공용 픽스처를 담고, LLM_FAKE=1과 EMBED_BACKEND=fallback을 정해 테스트가 키와 네트워크 없이 같은 결과를 내게 한다. 파일::함수[경우] 꼴의 노드 ID를 주면 테스트 하나만 돈다.

3-3. FastAPI의 TestClient

API 테스트는 서버를 띄우지 않는다. 픽스처 client가 돌려주는 TestClient는 HTTPX로 앱을 직접 부른다 [F1]. 질의 매개변수는 params=, 본문은 json=으로 넘긴다. 빠르지만 CORS나 프록시처럼 실제 서버에서만 드러나는 문제는 확인되지 않는다.

3-4. 단언과 예외

pytest는 assert 문을 다시 써서 실패하면 양쪽 값의 차이를 보여 준다 [T1]. 예외는 pytest.raises로, 메시지는 match=로 확인한다 [T1].

[파일: tests/test_llm.py] · 한 부분

def test_real_mode_without_key_raises_before_calling(monkeypatch):
    monkeypatch.setenv("LLM_FAKE", "0")
    monkeypatch.setenv("LLM_MODEL", "test-model")
    monkeypatch.delenv("ANTHROPIC_API_KEY", raising=False)
    with pytest.raises(llm.LLMError, match="ANTHROPIC_API_KEY"):
        llm.complete("시스템", "질문", task="ask")

match=를 지우거나 pytest.raises(Exception)으로 바꾸면 아무 예외나 통과한다. 이런 한 줄의 완화를 동결이 잡는다(7절).

3-5. 실행 옵션

옵션의 목록은 부록 B-4-1에 있다. 이 장은 -q, --tb=no, -k "식", -m "식", --collect-only를 쓴다. 고르지 않은 테스트는 deselected로 찍히며, 설정 파일에 --deselect를 몰래 넣으면 실패할 테스트가 사라지므로 이 수가 예상과 다르면 설정 파일부터 본다.

4. 픽스처, 매개변수화, monkeypatch, tmp_path, 마커

4-1. 픽스처

픽스처(fixture)는 테스트의 준비를 떼어 낸 함수이다. 테스트가 매개변수 이름으로 요청하면 pytest가 값을 넣어 주며, 기본 범위 function에서는 테스트마다 새로 만든다 [T1]. 값 대신 함수를 돌려주는 팩토리 픽스처는 테스트마다 다른 값으로 준비하게 한다.

[파일: tests/test_closing_within.py] · 시작 파일의 픽스처

@pytest.fixture
def on_day(monkeypatch):
    """기준일을 정하는 픽스처. 테스트 안에서 on_day(2027, 9, 1)처럼 부른다."""
    def set_day(year, month, day):
        monkeypatch.setattr(jobs, "today", lambda: date(year, month, day))
    return set_day

4-2. 매개변수화

@pytest.mark.parametrize는 같은 테스트를 입력만 바꿔 여러 번 돌리고, ids=는 경우마다 이름을 붙인다 [T1]. 읽기. 다음은 이미 있는 days_left의 지금 동작을 기록하는 특성 테스트(characterization test)이다.

@pytest.mark.parametrize("deadline, expected", [
    ("2027-09-08", 7),
    ("2027-09-01", 0),
    ("2027-08-31", -1),
], ids=["7일 뒤", "오늘", "어제"])
def test_days_left(monkeypatch, deadline, expected):
    monkeypatch.setattr(jobs, "today", lambda: date(2027, 9, 1))
    assert jobs.days_left({"deadline": deadline}) == expected

-v로 실행하면 경우의 이름이 test_days_left[\uc624\ub298]처럼 이스케이프되어 찍힌다. pytest가 비ASCII 이름을 기본으로 이스케이프하기 때문이다 [T1]. 그래서 이 장의 테스트는 ids=["N=6", "N=7"]처럼 ASCII 이름을 쓴다. pytest.param(..., marks=pytest.mark.xfail)로 값 하나에 표시를 달 수도 있으나, 이것은 실패를 녹색으로 감추는 데도 쓰일 수 있다(7절).

4-3. monkeypatch

monkeypatch는 속성과 환경 변수를 바꿔 끼우고 테스트가 끝나면 되돌리는 내장 픽스처이다 [T1]. 규칙은 하나이다. 함수를 정의한 곳이 아니라, 그 이름으로 찾아 부르는 곳을 바꾼다. api/ask.py의 from rag.search import search는 api.ask 안에 search라는 이름을 새로 만들므로, rag.search 쪽을 바꿔도 원래 함수가 불린다.

5. 경계값과 등가 분할

5-1. 무엇을 테스트할 것인가

모든 값을 테스트할 수는 없다. 등가 분할(equivalence partitioning)은 입력을 같은 방식으로 다뤄질 묶음으로 나눠 묶음마다 대표값을 고르고, 경계값 분석(boundary value analysis)은 묶음이 맞닿는 값을 고른다. <와 <=를 바꿔 쓰는 실수는 경계에서만 드러난다. “4,000자를 넘으면”, “N일 안에” 같은 숫자와 조건어가 경계를 만든다.

5-2. REQ-JOB-06의 분할

N과 공고의 남은 날 수(days_left)의 두 축으로 나누면 테스트 목록이 나온다.

축 묶음 기대 동작
N 없음 필터를 쓰지 않는다(30건)
N 0 이상의 정수 필터를 쓴다
N 음수, 정수가 아닌 값 422
days_left 음수(마감 지남) 빠진다
days_left 0 이상 N 이하 들어간다
days_left N보다 큼 빠진다
경우 기준일 기대값
대표값 N=7 09-01 [20]
매개변수 없음(회귀) 09-01 30건
N 경계 6, 7, 8 09-01 [], [20], [20, 3]
N=0, 오늘 마감 09-08 [20]
마감 지남(N=5) 09-10 [23, 6]
field, q와 함께 09-01 [23], [20, 3, 23]
음수, 글자, 소수, 빈 값 (무관) 422

기대값은 data/jobs.json의 마감일로 사람이 계산한다. 마감이 가장 이른 공고는 20번(2027-09-08), 3번(09-09), 23번(09-14), 6번(09-15)이다. 구현이 낸 값을 기대값에 복사하면 테스트는 아무것도 확인하지 않는다. “매개변수 없음”은 기존 동작을 지키는 회귀 테스트이므로 Red에서도 통과한다.

5-3. REQ-SUM-05와 REQ-ASK-06의 분할

묶음 요약 본문 질문 기대 동작
빈 문자열, 공백만 "", " \n\t " "", " " 422, LLM(과 검색) 호출 없음
1자 이상 상한 이하 경계 4,000자 경계 500자 200, 호출 있음
상한 초과 경계 4,001자 경계 501자 422, 호출 없음

상태 코드 422만 확인하면 LLM을 먼저 부른 뒤 422를 돌려주는 구현도 통과한다. “부르지 않았다”를 관찰하는 수단이 6절의 테스트 더블이다. 공백만 있는 문자열은 길이로는 정상이지만 요구로는 “비어 있음”이다. 이런 값은 요구 문장을 읽어야 나온다.

6. 테스트 더블과 비결정적 출력

6-1. 테스트 더블의 다섯 종류

테스트 더블(test double)은 테스트에서 진짜 대신 쓰는 가짜 부품이다. 마틴 파울러는 다섯 종류를 소개했다 [T4].

종류 뜻 (요지) jobprep의 예
더미 자리만 채우고 쓰지 않는다 모의 모드가 쓰지 않는 시스템 프롬프트
페이크 동작하지만 운영에는 못 쓰는 지름길 LLM_FAKE=1의 fake_reply()
스텁 정해 둔 답을 돌려준다 lambda: date(2027, 9, 1)
스파이 스텁이면서 불린 방식을 기록한다 요약 테스트의 llm_calls
목 기대한 호출이 일어났는지 검증한다 Mock(wraps=ask.search)와 assert_not_called()

결과 값만 보면 스텁, “불렸는가”를 보려면 스파이나 목을 쓴다.

6-2. 페이크: 모의 모드

llm.complete()는 LLM_FAKE=1이면 API 대신 fake_reply()로 언제나 같은 응답을 만든다. 페이크는 앱 전체를 돌리기 좋지만, 실제 모델이 깨진 JSON을 내는 것 같은 결함은 놓친다. 그래서 parse_json()과 validate_summary()를 따로 테스트한다.

Mock(wraps=대상)은 호출을 진짜 대상에 넘기면서 기록하고, assert_not_called()는 한 번이라도 불렸으면 실패한다 [P1].

6-5. 비결정적 출력의 테스트

실제 LLM의 출력을 정확한 문자열로 확인하면 흔들리는 테스트(flaky test)가 되고 결국 skip이 붙는다 [S2]. 비결정적 출력은 구조와 성질(키 넷의 존재, 인용 번호의 범위)을 확인하고, 응답의 품질은 12장의 평가가 잰다.

7. 테스트 동결과 회피의 방지

7-1. 통과한 것처럼 보이게 만드는 길

테스트를 통과시키지 못한 에이전트가 판정 쪽을 바꾸는 길은 여럿이다 [S1][S2][A1].

유형 jobprep에서의 모습 pytest 화면 동결 검사
① 테스트 삭제 테스트 파일을 지운다 실패가 사라진다 삭제:
② 건너뛰기 skip, xfail을 붙인다 skipped, xfailed 수정:
③ 조건 완화 == 422를 in (200, 422)로 바꾸거나 단언 한 줄을 지운다 통과 수가 는다 수정:
④ 설정으로 빼기 pytest.ini에 --deselect나 -k deselected 수정: pytest.ini
⑤ 바깥 conftest 루트 conftest.py가 skip을 붙인다 skipped 추가: conftest.py
⑥ 하드코딩, 특수 처리 테스트의 날짜나 값에서만 맞는 구현 모두 통과 잡지 못한다
⑦ 구현 먼저 구현에 맞춰 테스트를 쓴다 모두 통과 잡지 못한다(동결 전)

①~⑤는 동결 검사로 잡힌다. 그 가운데 ③의 “단언 한 줄 삭제”는 테스트 수도 그대로여서 결과 줄로는 진짜 통과와 구별되지 않는다. ⑥은 삼각 측량과 숨은 테스트로, ⑦은 사람이 Red를 직접 보는 절차로만 막힌다.

7-2. 동결 검사기 test_guard.py

동결(freeze)은 테스트와 테스트 설정 파일의 지문(SHA-256 해시)을 tests/.baseline.json에 적는 일이고, 검사(check)는 지금의 지문을 그 기록과 비교하는 일이다. tests/ 아래 모든 파일, 루트의 pytest 설정, tests/ 밖의 conftest.py, 검사기 자신을 지켜본다.

명령 하는 일 종료 코드
python tools/test_guard.py freeze 처음 동결한다. 기록이 이미 있으면 멈춘다 0(동결함), 2(이미 있음)
python tools/test_guard.py freeze --update 사람이 테스트를 바꾸기로 정했을 때 기록을 새로 쓴다 0
python tools/test_guard.py check 그대로이면 TEST_UNCHANGED, 바뀌었으면 TEST_CHANGED와 수정:·삭제:·추가: 목록 0(그대로), 1(바뀜), 2(기록 없음)

6장의 훅과 13장의 CI가 이 종료 코드로 판정한다. 기록은 저장소에 커밋하므로 기록 자체가 바뀌면 git status에 드러난다.

7-4. 하드코딩과 숨은 테스트

교수 시연용 과적합_jobs.py는 남은 날 수를 2027-09-01에서 센다. 시작 파일의 테스트는 모두 9월 1일을 쓰므로 이 구현은 47 passed, TEST_UNCHANGED를 받는다. 기준일을 바꾼 「할 일 2, 3」이 있으면 두 테스트가 실패하고(2 failed, 55 passed, 삼각 측량), 구현하는 쪽에 보여 주지 않은 교수의 숨은 테스트(held-out test)는 다른 날짜와 N=1000으로 3 failed, 7 passed를 낸다.

숨은 테스트는 에이전트가 읽을 수 없는 곳에 둔다. Claude Code는 실행한 폴더의 파일을 묻지 않고 읽는다 [C3]. 2026년판의 수업 리허설에서는 같은 폴더에 둔 검증 자료를 에이전트가 스스로 찾아 읽고 그에 맞춰 구현한 일이 있었다.

8-1. 지시문의 부분

지시문은 1층의 방어이다. Anthropic은 Claude Opus 4의 시스템 카드에서, 일반적인 해법을 쓰고 테스트가 틀렸으면 알리며 하드코딩하지 말라는 몇 문장을 프롬프트에 더하자 하드코딩이 줄었고, 일부러 틀리게 만든 테스트를 받은 모델이 특수 처리 대신 테스트의 문제를 보고했다고 적었다 [A1]. 그래서 지시문에 “통과시킬 수 없으면 보고하라”는 출구를 둔다. 출구가 없으면 “통과시켜라”를 만족하는 길이 판정을 바꾸는 것뿐일 수 있다.

양식(8-2절)의 조항마다 막는 것은 다음과 같다.

조항 막는 것

판정 기준의 보호 ①~⑤
일반성 ⑥ [A1]
범위 관계없는 파일의 변경, 검토할 diff의 팽창

8-4. 증거를 받는 법

에이전트의 보고는 주장이다. 받으면 다음 순서로 확인한다.

  1. 보고에 실행한 명령과 마지막 줄이 있는지 본다. 없으면 다시 요청한다 [C1].

  3. git status --short와 git diff --stat으로 범위 밖의 변경을 찾는다.
  4. git diff로 구현을 읽고 테스트의 기대값이나 날짜가 코드에 들어 있지 않은지 본다.

조건 충족을 별도의 모델이 판정하는 /goal 명령도 있으나 [C1], 이 장은 직접 실행한 출력으로 판정한다.

8-5. 체크포인트와 git

Claude Code는 프롬프트마다 파일 상태를 체크포인트로 저장하고 /rewind로 되돌린다. 그러나 셸 명령이나 Claude Code 바깥에서 생긴 변경은 대개 되돌리지 않으며, 체크포인트는 git을 대신하지 않는다 [C2]. 이 장은 실패한 시도를 git으로 버린다.

[최신 자료 자리: 체크포인트의 조작] 2026-11-15 확인 값: 입력 창이 비어 있을 때 Esc를 두 번 누르면 되감기(rewind) 메뉴가 열리고, 입력 창에 글이 있으면 두 번의 Esc는 글을 지운다 [C5]. 단축키와 메뉴 이름은 판에 따라 바뀐다. 확인할 곳: https://code.claude.com/docs/en/checkpointing, https://code.claude.com/docs/en/interactive-mode.

9. Git 작업 단위: 통과마다 커밋, 되돌리기, 태그

9-1. 요구 하나에 커밋 둘

요구 하나에 커밋 둘을 남긴다. 새 테스트와 동결 기록을 담은 test(REQ-…): … (Red), 구현을 담은 feat(REQ-…): … (Green)이다. Red를 커밋하면 에이전트에게 넘기기 전의 상태가 돌아올 지점이 되고, 테스트의 변경이 구현의 diff 속에 숨지 않는다 [S2]. 메시지는 종류(범위): 설명의 꼴로 쓰며(종류는 test, feat, refactor, docs, chore), 3장에서 저장소 규약으로 정식화한다.

9-2. 실패한 시도를 버리기

실패한 시도는 고쳐 쓰지 않고 통째로 버린다. 고쳐 쓰면 어디까지가 에이전트의 변경인지 흐려진다.

명령 하는 일
git status --short 바뀐 파일(M), 지운 파일(D), 새 파일(??)을 본다
git restore . 추적하는 파일을 모두 인덱스의 내용으로 되돌린다 [G3]
git restore --source=HEAD --staged --worktree 경로 스테이징한 변경까지 HEAD로 되돌린다 [G3]
git clean -n / git clean -f 추적하지 않는 파일의 목록을 본다 / 지운다

git clean -f는 되돌릴 수 없으므로 반드시 -n으로 목록을 먼저 본다.

9-3. 태그

태그는 커밋 하나에 붙이는 움직이지 않는 이름이다. 주석 태그(git tag -a 이름 -m "설명")는 만든 사람, 날짜, 설명을 담아 넘겨주기에 쓴다 [G1]. git push는 태그를 보내지 않으므로 git push origin 태그이름으로 따로 보낸다 [G2]. 공개한 태그는 옮기지 않는다. git 문서는 같은 이름을 다른 커밋으로 옮기는 것을 “제정신이 아닌 일”이라 부르며, 잘못 붙였으면 새 이름을 쓰라고 한다 [G1].

동작을 바꾸지 않고 구조를 다듬는다. 집필할 때의 Green 구현은 days_left(job)을 세 번 불렀고, 요약과 질의응답이 같은 길이 규칙을 따로 들고 있었다. 양식 2절의 리팩터링 지시문(동작, 테스트, git을 건드리지 말고 다듬을 것이 없으면 그렇게 보고할 것)을 보낸다.

집필할 때의 정리(교수용 정답)는 길이 규칙을 Pydantic의 StringConstraints(strip_whitespace=True, min_length=1, max_length=…)로 요청 모델에 옮긴 것이며 [P2], 결과는 66 passed, TEST_UNCHANGED였다. 만약 Green이 공백을 떼지 않고 길이를 재었다면 공백이 붙은 3,999자 본문에서 두 구현의 답이 갈리지만, 테스트가 그 경우를 다루지 않아 아무도 모른다. 리팩터링은 테스트가 지키는 범위 안에서만 동작을 보존한다. “다듬을 것이 없다”는 보고도 결과이다 [T3].

확인 11 리팩터링 뒤에도 테스트 수(정답 기준 66)와 TEST_UNCHANGED가 그대로이고 api/ 아래 파일만 바뀌었다. 리팩터링하지 않았다면 그 판단을 실습 기록에 적었다.

11-10. 복기

  1. 판정 기준은 사람이 먼저 쓰고 잠갔다. Red의 실패 까닭을 가린 뒤에야 동결 기록을 고쳤다.
  2. 에이전트의 일은 잠긴 기준을 통과시키는 것으로 끝났다. 결과 줄이 N과 같은 시도도 check와 git diff tests/로 갈래 ④임을 밝혀 버렸다. 결과 줄의 수는 판정 기준이 그대로라는 증거가 아니다.
  3. 통과한 상태는 누구나 다시 얻을 수 있다. 요구마다 test·feat 커밋이 짝을 이루고, 태그 tdd-1로 받은 폴더에서 같은 결과가 나왔다. 1-3절의 네 운영 요건이 이 기록으로 확인된다.

정리

  • 이 장의 완료 조건은 테스트 통과, TEST_UNCHANGED, 그리고 그 둘을 내 터미널에서 확인하는 것이다. Red는 사람이 보고, Green은 에이전트에게 맡긴다.
  • 테스트는 준비·실행·확인으로 쓰고, 경계값과 등가 분할로 경우를 고르며, 외부 요인은 monkeypatch와 테스트 더블로 통제한다. 함수는 부르는 곳의 이름을 바꿔 끼운다.
  • 판정을 바꾸는 회피는 동결 검사와 git diff tests/가, 판정에만 맞추는 회피는 삼각 측량과 숨은 테스트가 잡는다. 단언 한 줄의 삭제는 결과 줄의 수를 바꾸지 않는다.
  • 요구 하나에 테스트 커밋과 구현 커밋을 남기고, 실패한 시도는 통째로 버리고, 넘겨줄 상태는 주석 태그로 표시한다. 커버리지는 품질의 목표가 아니다.

개념 점검

  1. 구현이 없는 상태에서 새로 쓴 테스트가 처음부터 통과했다. 가능한 원인 두 가지와, 각각을 가르는 방법을 쓰라.
  2. api/ask.py가 from rag.search import search로 검색 함수를 가져온다. 질의응답이 검색을 부르지 않았음을 확인하려면 monkeypatch.setattr의 첫 인자로 무엇을 주어야 하며, 그 까닭은 무엇인가.
  3. 다음 중 test_guard.py check로 잡히지 않는 것을 고르고, 그것을 잡는 다른 수단을 쓰라. (가) 테스트에 @pytest.mark.skip을 붙임 (나) pytest.ini에 --deselect를 더함 (다) 테스트가 고정한 날짜에서만 맞는 구현 (라) 저장소 루트에 conftest.py를 만듦
  4. 에이전트의 보고와 학습자의 터미널이 모두 지시문의 N과 같은 N passed를 보였는데, check는 TEST_CHANGED였다. 결과 줄의 수가 그대로인데 판정 기준이 바뀔 수 있는 경우를 하나 들고, 그 시도를 받으면 무엇이 잘못되는지 이 장의 요구로 설명하라.
  5. 어떤 보고서가 “커버리지 100%이므로 품질이 검증되었다”고 적었다. 이 주장의 문제를 이 장의 내용을 들어 설명하라.
