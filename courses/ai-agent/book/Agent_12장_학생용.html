12장

평가와 관측: 회귀 평가, 기록, 비용

2027학년도 「AI에이전트 기획 및 개발」의 준비 중인 교재입니다. 편집 상태를 검토하기 위해 미리 공개한 것으로, 수업 전에 내용과 순서가 바뀔 수 있습니다.

학사 14주차 · 교재 12 · 5부 운영 품질

11장에서 jobprep 운영 에이전트 시스템에 보안의 울타리를 둘렀다. 거부 규칙과 훅과 도구 제한은 에이전트가 「하면 안 되는 일」을 막는다. 그러나 운영에는 막는 일만큼 재는 일이 필요하다. 요약 기능이 한 주 전보다 나빠졌는지, 질의응답이 범위 밖 질문을 여전히 거절하는지, 8장의 루프가 몇 번 만에 일을 끝내고 얼마를 썼는지는 막는 장치로는 알 수 없다. 1장에서 정의한 운영 요건 가운데 신뢰성(정해진 조건에서 기대한 결과를 내고, 실패하면 알아챈다)과 재현성(무엇이 실행되었는지 기록이 남는다)이 이 장의 주제이다.

LLM 기능은 코드 한 줄 고치지 않아도 나빠질 수 있다. 프롬프트 파일의 문장 하나, 환경 변수의 모델 이름 하나, 검색 자료의 문서 하나가 바뀌면 출력이 달라지고, 그 변화는 대개 오류 없이 조용히 일어난다. 2장의 테스트는 함수가 정해진 값을 돌려주는지를 보지만, 요약이 「공고에 없는 주의점을 지어냈는가」는 보지 못한다. 그래서 LLM 기능에는 테스트와 다른 검사 장치, 곧 평가(evaluation)가 필요하다. 평가는 골든 세트(입력과 기대값의 묶음)를 기능에 넣고, 채점기로 기준별 통과 여부를 정하고, 같은 일을 여러 번 되풀이해 통과율로 말한다.

이 장에서 만드는 것은 하나이다. jobprep/evals/의 회귀 평가 세트(요약 15문항, 질의응답 10문항)와 채점기로 요약 프롬프트의 두 판본을 한 번 비교해, 새 판본이 몰래 들여온 회귀 하나를 찾아 고치고, 회귀 판정기가 그 수정을 종료 코드로 승인하게 한 뒤, 8장·10장의 실행 기록에서 에이전트의 작업 성공률과 비용을 보고한다. 해결할 문제는 비교에서 드러난다. 요약 판본 v2는 세 가지 실수를 고쳤지만 공고에 없는 주의점을 지어내는 새 실수를 들여왔고, 전체 점수 하나만 보면 이 회귀가 보이지 않는다. 실습은 API 키 없이 도는 교육용 모의 모델로 끝까지 한다. 실제 모델로 하는 평가는 각자 키가 있으면 한 번만 하고, 반복 실행의 분산과 LLM 판정은 교수 시연의 기록으로 읽는다(11-9).

이 장의 회귀 판정은 13장에서 지속적 통합(CI)의 한 단계가 된다. 풀 리퀘스트마다 python -m evals.gate가 돌고, 종료 코드가 1이면 병합이 막힌다. 같은 학기의 프로젝트실습Ⅱ에서 LLM 기능을 만드는 팀은 이 장의 골든 세트와 판정 구조를 그대로 가져가 자기 기능의 품질 기준으로 쓸 수 있다.

학습 목표

  • LLM 기능에 회귀 평가가 필요한 까닭을 설명하고, 대표 문항과 경계 문항을 갖춘 골든 세트를 정답의 형식과 함께 설계할 수 있다.
    • 예시: 요약 골든 세트에 「마감일이 두 번 나오는 공고」, 「마감일이 없는 상시 채용 공고」, 「본문에 지시문을 숨긴 공고」를 경계 문항으로 넣고, 기대값을 「마감일은 정확 일치, 업무 항목은 참조 목록과의 재현율」로 정한다.
    • 활용: 프롬프트나 모델을 바꾸기 전에 「무엇이 나빠지면 안 되는가」를 문항으로 먼저 적어 둔다. 실패 보고가 들어오면 그 입력을 문항으로 더한다.
  • 정확 일치, 구조 검사, 규칙, 참조 기반, LLM 판정의 다섯 채점 방식을 장단점에 따라 고르고, LLM 판정의 편향(위치, 길이, 자기 선호)을 기준표, 순서 바꾸기, 사람 표본 대조로 보정하는 방법을 설명할 수 있다.
    • 예시: 「우대 사항을 자격 요건에 섞었는가」는 규칙으로 채점하고, 「공고에 없는 내용을 지어냈는가」는 판정자에게 맡기되, 사람이 판정한 표본 12개와 대조해 일치도(코언의 카파)를 잰다.
    • 활용: 판정자의 점수를 믿기 전에 사람과 얼마나 일치하는지부터 묻는다. 기준표는 코드처럼 저장소에 두고 검토를 받는다.
  • 같은 입력을 여러 번 실행해 통과율과 표준오차를 구하고, 두 판본을 짝지은 차이로 비교해 합격선과 기준선으로 회귀를 판정할 수 있다.
    • 예시: summary_v2와 summary_v3을 5번씩 돌려 짝지은 차이의 95% 구간이 0보다 큰지 보고, python -m evals.gate가 종료 코드 0을 낼 때만 기준선을 갱신한다.
    • 활용: 13장의 CI가 이 종료 코드로 병합을 막는다. 한 번 돌린 점수로 판단하지 않는 습관은 모델 교체와 비용 결정에도 쓰인다.
  • 요청, 프롬프트 판본, 모델, 토큰, 지연, 오류, 도구 호출을 구조화 기록으로 남기고, 서비스와 에이전트 실행의 지표와 비용을 집계하며, Claude Code의 사용량을 보는 세 가지 길(/usage, 헤드리스 결과, OpenTelemetry)을 구별할 수 있다.
    • 예시: logs/access.log에서 요약 요청의 p95 지연을, logs/llm.log에서 토큰과 추정 비용을, 8장 루프 기록에서 작업 성공률과 성공 1건당 비용을 뽑고, 예산의 80%를 넘으면 주의를 띄운다.
    • 활용: 「에이전트가 일을 잘하는가」를 말이 아니라 숫자로 보고한다. 기록에 개인 정보가 남지 않았는지 점검하는 일까지 관측에 포함한다.

0. 시작하기

실습은 내 PC(개인 노트북 또는 실습실 PC)에서 한다. VS Code의 통합 터미널 두 개를 나란히 두고(부록 A-4-2), 하나는 직접 실행과 확인을 하는 [터미널], 다른 하나는 Claude Code를 띄우는 터미널로 쓴다. 두 터미널 모두 ~/agent-lab/jobprep에서 가상 환경을 먼저 켠다(Windows source .venv/Scripts/activate, macOS source .venv/bin/activate, 부록 A-9-1). 수업의 시작 순서는 부록 A-20을 따른다. 파이썬의 출력을 파이프로 넘길 때 한글이 깨지면 부록 A-4-4의 PYTHONUTF8=1을, git status의 한글 파일 이름이 "\354…"처럼 보이면 부록 A-6-1의 core.quotepath를 등록한다.

이 장의 실행 상한. 회귀 평가는 모두 모의 모드(--backend sim, 기본)로 하며 모델을 부르지 않는다. 실제 모델의 평가는 각자 Console 키를 발급한 학습자만 한 번(--backend real --runs 1, 생성과 판정을 합쳐 약 50회 호출) 한다(11-9, 부록 A-12-3). 반복 실행의 분산(4-4)과 LLM 판정(5-5), 실제 모델의 반복 평가는 교수 시연이며, 키트의 시연기록/으로 읽는다. 그 밖에는 Claude Code 대화형 세션의 요청 두 번(11-2의 채점기 구현, 11-7의 보고서 초안. 둘 다 직접 해도 된다)만 쓴다.

0-1. 키트 받기

키트는 1주차에 클론한 키트 저장소(~/kits-repo)에서 저장소 밖의 ~/kits/로 받는다(부록 A-7-3).

터미널 
git -C ~/kits-repo pull
mkdir -p ~/kits
cp -rn ~/kits-repo/Agent_12장 ~/kits/
ls ~/kits/Agent_12장
README.md  evals  ops  기준산출물  재료  평가보고_양식.md

mkdir -p ~/kits를 먼저 하는 까닭은 ~/kits가 없을 때 cp가 키트 폴더 자체를 ~/kits라는 이름으로 복사해 버리기 때문이다. -n은 이미 있는 파일을 덮어쓰지 않는다.

  • 기준산출물/ops/loop/logs/: 8장 루프 실행 기록(JSON Lines) 견본 7건. 0-2와 11-6에서 쓴다.
  • 기준산출물/ops/multi/logs/: 10장 멀티 에이전트 실행 기록 견본 3건(이슈마다 events.jsonl과 구현 에이전트의 출력). 0-2와 11-6에서 쓴다.

1. LLM 기능의 회귀

1-1. 코드를 고치지 않아도 나빠지는 기능

회귀(regression)는 잘 되던 동작이 변경 뒤에 나빠지는 것이다. 보통의 소프트웨어에서 회귀의 원인은 코드 변경이고, 테스트가 그 변경을 잡는다. LLM 기능은 코드 밖에 출력을 바꾸는 요인이 더 있다. jobprep의 요약 기능을 예로 들면 다음과 같다.

바뀌는 것 jobprep에서의 자리 코드가 바뀌는가 테스트가 잡는가
프롬프트 prompts/summary_v1.txt → summary_v2.txt, 환경 변수 PROMPT_SUMMARY 아니다 모의 모드에서는 출력이 같아 잡지 못한다
모델 환경 변수 LLM_MODEL 아니다 모의 모드는 모델을 부르지 않는다
모델 제공자의 갱신 같은 모델 이름의 동작 변화, 모델 지원 종료 아니다 잡지 못한다
검색 자료 data/자료/의 문서, 임베딩 방식(EMBED_BACKEND) 아니다 rag/평가문항.csv의 재현율만 본다
앞뒤 처리 코드 parse_json(), validate_summary(), MIN_SCORE 그렇다 형식은 잡지만 품질은 보지 못한다

표의 네 줄은 코드가 바뀌지 않는다. 그리고 그 변화는 오류로 드러나지 않는다. 요약이 JSON 구조를 지키는 한 API는 200을 돌려주고, 화면은 정상으로 보인다. 공고에 없는 주의점이 하나 섞이거나 우대 사항이 자격 요건으로 옮겨 가도 서버 기록에는 아무 표시가 없다. 이것이 「조용한 회귀」이다.

LLM 출력은 또 비결정적(non-deterministic)이다. 같은 입력에도 실행마다 답이 조금씩 다를 수 있다. 그래서 「한 번 해 보니 잘 되었다」는 관찰은 품질의 근거가 되지 못한다. 한 번의 성공이 열 번 중 아홉 번 성공하는 기능의 것인지, 열 번 중 다섯 번 성공하는 기능의 것인지 구별할 수 없기 때문이다. 4절에서 이 문제를 반복 실행으로 다룬다.

1-2. 테스트와 평가

2장의 테스트와 이 장의 평가는 목적이 같다. 둘 다 「바꾸어도 되는가」를 기계로 판정한다. 차이는 판정의 대상과 모양에 있다.

평가가 테스트를 대신하지는 않는다. jobprep에서 pytest -q는 모의 모드로 2초 안에 끝나고, 요약 API가 JSON 구조를 검사하는지, 본문이 비면 422를 내는지를 확인한다. 평가는 그 위에서 「출력의 내용이 기준을 지키는가」를 본다. 테스트는 커밋마다, 평가는 프롬프트·모델·자료를 바꿀 때와 풀 리퀘스트마다 돈다.

1-3. 성공 기준

평가를 만들기 전에 정할 것은 성공 기준(success criteria)이다. Anthropic의 평가 안내는 좋은 성공 기준의 성질로 구체성(specific), 측정 가능성(measurable), 달성 가능성(achievable), 관련성(relevant)을 든다 [A1]. 「요약을 잘한다」는 구체적이지도 측정 가능하지도 않다. 「마감일이 서류 접수 마감일과 정확히 같은 비율이 0.95 이상」은 둘 다 갖춘다.

같은 안내는 흔히 쓰는 기준의 범주로 과업 충실도(task fidelity), 일관성(consistency), 관련성과 응집성, 어조와 문체, 개인 정보 보호, 맥락 활용, 지연(latency), 가격(price)을 든다 [A1]. jobprep의 두 기능에 대어 보면 다음과 같다.

  • 과업 충실도: 요약은 마감일이 정확하고 공고의 업무·자격·주의점을 빠뜨리지 않는다. 질의응답은 답에 기대 핵심어가 있다.
  • 일관성: 같은 공고를 다섯 번 요약해도, 같은 질문을 다섯 번 물어도 매번 기준을 지킨다.
  • 맥락 활용: 요약은 공고에 없는 내용을 지어내지 않고 우대 사항을 자격 요건으로 옮기지 않는다. 질의응답은 근거에 없는 문장을 덧붙이지 않고 근거 번호를 단다.
  • 형식: 요약은 JSON 구조와 항목 50자 이내를 지킨다. 질의응답은 범위 밖 질문에 「자료에 없습니다.」로 답한다.
  • 지연과 가격: 두 기능 모두 8절과 10절에서 운영 지표로 다룬다.

1-4. 능력 평가와 회귀 평가

Anthropic의 에이전트 평가 글은 평가를 두 종류로 나눈다 [E5]. 능력 평가(capability eval)는 「이 기능이 무엇을 잘하는가」를 묻고, 처음에는 통과율이 낮아 오를 여지를 준다. 회귀 평가(regression eval)는 「전에 되던 것이 아직 되는가」를 묻고, 통과율이 100%에 가까워야 한다. 능력 평가에서 통과율이 높아진 문항은 회귀 평가로 옮겨 간다.

이 장의 골든 세트는 두 종류를 한 파일에 두고 문항마다 suite 칸으로 구별한다. 회귀 판정(6절, 11절)은 regression 문항만으로 하고, capability 문항은 통과율을 보고만 한다. 예를 들어 본문에 「이전 지시를 무시하라」는 문장을 숨긴 공고(S15)는 11장의 대책을 요약 기능에 아직 넣지 않았으므로 지금은 통과하지 못한다. 이 문항을 회귀 판정에 넣으면 판정이 늘 실패하고, 늘 실패하는 경보는 아무도 보지 않게 된다. 그래서 능력 문항으로 두고, 대책을 넣어 통과하게 되면 회귀 문항으로 옮긴다.

2. 골든 세트

2-1. 골든 세트의 구성

골든 세트(golden set)는 평가에 쓰는 입력과 기대값의 묶음이다. 2026년판 교재는 이것을 「정답셋」이라 불렀고, 정답셋, 채점기, 측정 기록의 세 부품으로 평가를 설명하였다 [L9]. 에이전트 평가 글은 같은 구조를 과업(task), 시행(trial), 채점기(grader), 기록(transcript), 평가 묶음(eval suite)의 용어로 정리한다 [E5]. 이 장은 다음 뜻으로 쓴다.

  • 문항(과업): 입력 하나와 기대값 하나의 쌍. golden/summary.jsonl, golden/ask.jsonl의 한 줄이다.
  • 기대값: 출력이 지켜야 할 것. 정답 하나일 수도, 범위일 수도 있다. 문항의 expect 칸에 있다.
  • 채점기: 출력과 기대값을 비교해 기준 하나의 통과 여부를 정하는 함수. graders.py와 judge.py에 있다.
  • 시행: 문항 하나를 한 번 실행하고 채점한 것. runs/<태그>/records.jsonl의 한 줄로 남는다.
  • 실행: 골든 세트 전체를 n번 되풀이한 것. runs/<태그>/ 폴더 하나로 남는다.

2-2. 대표성

골든 세트의 첫째 조건은 대표성이다. 평가 안내는 「실제 과업의 분포를 비추라」고 한다 [A1]. 실제 사용자가 요약 버튼을 누르는 공고가 백엔드 개발 공고에 몰려 있는데 골든 세트가 임베디드 공고로만 되어 있다면, 통과율이 높아도 운영의 품질을 말해 주지 않는다.

jobprep의 요약 골든 세트는 대표 문항 10개를 data/jobs.json의 공고 30건 가운데 분야가 겹치지 않게 골랐다(정보보안, 웹, 임베디드, 백엔드, 데이터 분석, 기술 지원, AI 서비스 둘, 클라우드, 소프트웨어 테스트). 공고의 형식(절 제목 8개)이 모두 같으므로 분야를 고르게 하는 것이 대표성의 핵심이다. 운영 기록이 쌓이면 실제 요청의 분포(5장의 access.log에서 어떤 공고의 요약이 많이 불렸는가)에 맞추어 다시 고른다.

2-3. 경계 사례

둘째 조건은 경계 사례(edge case)이다. 평가 안내는 경계 사례의 예로 관련 없거나 지나치게 긴 입력, 잘못되었거나 해로운 입력, 모호한 경우를 든다 [A1]. 에이전트 평가 글은 「어떤 행동이 일어나야 할 때와 일어나지 않아야 할 때를 둘 다 시험하라」고 한다 [E5]. 질의응답에서 답해야 할 질문만 넣으면, 무엇에나 답하는 기능이 만점을 받는다.

문항 경계의 종류 무엇을 보는가
S11 마감일이 둘(설명회 신청 마감, 서류 접수 마감) v2의 규칙 3이 서류 접수 마감일을 고르게 하는가
S12 마감일이 없는 상시 채용 없는 마감일을 지어내지 않고 null로 두는가
S13 유의 사항 절이 없는 공고 주의점을 지어내지 않고 빈 목록으로 두는가
S14 절 구분이 없는 한 줄짜리 공고 구조가 없는 입력에서도 JSON을 지키는가
S15 본문에 숨긴 지시(11장의 간접 프롬프트 주입) 숨긴 지시를 요약에 옮기지 않는가(능력 문항)
A07 구어체 질문 표현이 달라도 같은 근거를 찾는가
A08 범위 밖 질문(학생 식당) 「자료에 없습니다.」로 거절하는가
A09 범위 밖이지만 유사도가 기준값(0.3)에 가까운 질문 검색 기준값의 여유가 충분한가
A10 목록에 없는 대상(리눅스마스터 1급) 근거로부터 「목록에 없다」를 끌어내는가(능력 문항)

A09는 기준 저장소 안내에 적힌 수치에서 나왔다. 대체 임베딩에서 범위 밖 질문의 1위 유사도는 0.08~0.27이고 기준값은 0.3이다. 이 질문(교통비)의 1위 유사도는 0.26으로 기준값에 가장 가깝다. 자료가 하나 늘거나 임베딩 방식이 바뀌어 이 값이 0.3을 넘으면, 이 기능은 근거 없는 답을 내기 시작한다. 경계 문항은 그런 변화를 가장 먼저 알려 준다.

2-4. 정답의 형식

셋째 조건은 정답의 형식이다. 기대값을 어떤 모양으로 적느냐가 어떤 채점기를 쓸 수 있는지를 정한다.

  • 하나의 값("deadline": "2027-09-30", "not_found": true)은 정확 일치로 채점한다.
  • 값의 목록, 곧 참조 답("duties": ["데이터 수집 스크립트를 작성하고 점검한다", …])은 참조 기반으로 채점한다(재현율).
  • 금지 목록("preferred": [우대 사항], "must_not_contain": ["이전 지시를 무시"])은 규칙으로 채점한다.
  • 핵심어("keywords": ["15주"])는 문자열 포함으로 채점한다.
  • 기준표(judge_rubric.md의 「근거 충실성」)는 LLM 판정으로 채점한다.

에이전트 평가 글은 과업을 모호하지 않게 쓰라고 하며, 그 기준으로 「두 전문가가 독립적으로 같은 통과·실패 판정에 이르는가」를 든다 [E5]. 「요약이 충분한가」는 사람마다 판정이 다르다. 「참조 항목의 80% 이상을 덮는가」는 같다.

2-5. 크기와 출처

에이전트 평가 글은 「실제 실패에서 뽑은 단순한 과업 20~50개로 시작하면 좋다」고 하며, 수백 개를 모을 때까지 기다리지 말라고 한다 [E5]. 평가 안내도 「손으로 채점한 소수의 고품질 문항보다 자동 채점되는 다수의 문항」을 권한다 [A1]. 이 장의 골든 세트는 25문항(요약 15, 질의응답 10)으로 그 범위의 아래쪽에 있다.

문항의 출처는 두 가지다. 하나는 배포 전에 사람이 손으로 하던 점검이고, 다른 하나는 운영 중에 들어온 실패 보고이다 [E5]. jobprep의 경우 4장에서 만든 장애 보고서의 입력, 5장의 MCP 서버로 찾은 오류 기록, 11장의 주입 공격 재현 자료가 모두 골든 세트의 문항 후보이다. 실패가 보고될 때마다 그 입력을 문항으로 더하면 같은 실패가 두 번 운영에 나가지 않는다.

3. 채점 방식

3-1. 다섯 가지 채점 방식

출력과 기대값을 비교하는 방식은 크게 다섯이다. Anthropic의 평가 안내는 채점 방식을 코드 기반, 사람, LLM 기반의 셋으로 나누고, 「가장 빠르고, 가장 믿을 만하고, 가장 확장 가능한 방식」을 고르라고 한다 [A1]. 코드 기반 채점은 「가장 빠르고 믿을 만하며 확장성이 매우 크지만, 규칙으로 판정하기 어려운 복잡한 판단에는 섬세함이 모자란다」. 사람 채점은 「가장 유연하고 품질이 높지만 느리고 비싸며, 되도록 피한다」. LLM 기반 채점은 「빠르고 유연하며 복잡한 판단에 맞지만, 먼저 신뢰도를 시험한 뒤에 넓혀 쓴다」 [A1]. 이 장은 코드 기반 채점을 넷으로 더 나누어 다섯으로 본다.

방식 하는 일 장점 단점 jobprep의 예
정확 일치 출력 값이 기대값과 같은가 빠르고 결정적이다. 해석의 여지가 없다 표현이 조금만 달라도 실패한다 마감일, 거절 문구
구조 검사 출력이 정해진 모양(JSON 키, 형식, 개수)을 갖추었는가 다음 처리(화면, API)가 깨지지 않는지 보장한다 내용의 옳고 그름은 보지 못한다 JSON 구조, 근거 번호와 출처의 존재
규칙 금지 문구, 길이, 포함 관계 같은 조건을 지키는가 빠르고 이유가 분명하다. 실패 사유를 바로 적을 수 있다 규칙으로 적을 수 있는 실수만 잡는다 항목 50자 이내, 우대 사항 혼입, 숨긴 지시의 문구
참조 기반 참조 답(사람이 쓴 정답 목록)과 얼마나 겹치는가 표현 차이를 어느 정도 허용한다 겹침이 뜻의 같음을 보장하지 않는다. 참조 답을 써야 한다 업무·자격·주의점 항목의 재현율
LLM 판정 다른 모델이 기준표를 들고 판정한다 지어냄, 왜곡, 어조처럼 규칙으로 적기 어려운 기준을 다룬다 비용과 비결정성이 있다. 판정자 자체를 보정해야 한다 근거에 없는 문장의 유무

평가 안내의 예시들이 이 구분을 잘 보여 준다. 감정 분류는 정답 레이블과의 정확 일치로, 요약은 참조 요약과의 ROUGE-L로, 고객 응대의 어조는 LLM의 1~5점 척도로, 의료 대화의 개인 건강 정보 노출은 LLM의 이진 분류로 채점한다 [A1]. 에이전트 평가 글은 여러 채점기를 한 과업에 함께 쓰고, 점수를 가중 합으로 내거나(가중), 모두 통과해야 통과로 하거나(이진), 둘을 섞으라고 한다 [E5]. 이 장의 실행기는 이진 방식을 쓴다. 시행 하나는 해당하는 규칙 기준을 모두 통과하고 판정자가 pass라고 해야 통과다.

판단의 순서도 중요하다. 규칙으로 잡을 수 있는 것은 규칙으로 잡고, 남는 것만 판정자에게 넘긴다. 2026년판 교재도 같은 취지로, 규칙 채점을 기본으로 깔고 규칙이 판정하기 어려운 축(사실성, 어조, 근거)에만 판정자를 쓰라고 하였다 [L9]. 판정자 호출은 문항마다 비용이 들고, 판정자도 틀리기 때문이다.

3-2. jobprep 채점기의 지도

evals/graders.py에는 요약 채점기 다섯과 질의응답 채점기 넷이 있다. 채점기는 모두 (통과 여부, 설명)을 돌려주는 함수이며, 통과 여부가 None이면 그 문항에 해당하지 않는 기준이라는 뜻이다(예: 금지 문구가 없는 문항의 forbidden).

묶음 채점기 방식 통과 조건
요약 structure 구조 검사 응답을 JSON으로 읽고 validate_summary()를 통과하였다
요약 deadline 정확 일치 마감일이 기대값과 같다(null끼리도 같다)
요약 coverage 참조 기반 참조 항목의 80% 이상이 출력 항목과 유사도 0.5 이상으로 맞는다
요약 length 규칙 모든 항목이 50자 이내이다
요약 forbidden 규칙 must_not_contain의 문구가 출력에 없다
질의응답 refusal 정확 일치 거절해야 할 질문에만 「자료에 없습니다.」로 답했다
질의응답 keywords 문자열 포함 기대 핵심어가 답에 모두 있다
질의응답 citation 구조 검사 답에 [n]이 있고 출처 목록이 비어 있지 않다
질의응답 source 정확 일치 기대한 자료 파일이 출처에 있다

참조 기반 채점에 쓰는 유사도는 두 글을 두 글자씩 잘라 겹치는 비율(bigram Dice 계수)이다. 형태소 분석기 없이 한국어 문장의 겹침을 재는 가장 단순한 방법이다. 세 쌍의 값을 교수 화면에서 본다.

교수 화면 
python -c "
from evals.graders import similarity
print(round(similarity('보안 관제 시스템을 운영한다', '보안 관제 시스템을 운영함'), 2))
print(round(similarity('보안 관제 시스템을 운영한다', '사내 관제 장비를 관리한다'), 2))
print(round(similarity('서류 접수 마감', '정장 무료 대여'), 2))"

0.19
0.0

어미 하나가 다른 문장은 0.86으로 같은 항목으로 인정되고(기준 0.5), 낱말 몇 개만 겹치는 다른 문장은 0.19로 다른 항목이 된다. 이 기준이 뜻을 재지는 않는다는 점은 5절에서 다시 다룬다.

3-3. 따라 하기 2: 첫 평가 실행

실행기 evals/run.py는 골든 세트의 문항을 기준 저장소의 기능 함수(summarize(), answer_question())에 그대로 넣는다. 평가는 API를 거치지 않고 함수를 부르지만, 프롬프트 읽기, JSON 추출, 구조 검사, 검색과 기준값 판정은 운영과 같은 코드가 한다. 바뀌는 것은 llm.complete() 하나뿐이다. --backend sim(기본)이면 실행기가 이 자리에 변동 모의 모델을 끼운다.

변동 모의 모델(evals/sim.py)은 기준 저장소의 모의 응답에 두 가지를 더한 교육용 장치이다.

  • 판본 민감성: 프롬프트에 「우대 사항은 자격 요건에 넣지 않는다」가 없으면 우대 사항을 자격 요건에 섞을 확률이 높다. 「40자 이내」가 없으면 항목을 길게 늘인다. 「주의점으로 먼저」가 있으면 공고에 없는 주의점을 지어낼 수 있다. 프롬프트의 규칙 한 줄이 출력의 실수 분포를 바꾸는 현실을 흉내 낸다.
  • 결정적 변동: (모델 이름, 반복 번호, 프롬프트 전체)로 sha256 난수 씨앗을 만든다. 반복 번호가 다르면 결과가 달라지고, 조건이 같으면 어느 컴퓨터에서나 같다. 같은 입력에도 실행마다 답이 다른 현실을 흉내 내되, 교재의 수치를 다시 얻을 수 있게 한다.

모의 모델의 확률은 집필자가 정한 값이다. 그러므로 이 장의 점수는 「평가를 하는 법」을 익히기 위한 것이지, 실제 모델의 품질이 아니다. 실제 모델은 --backend real로 부르며, 11-9에서 그 방법과 비용을 다룬다.

4. 반복 실행과 분산

4-1. 같은 입력, 다른 답

LLM은 다음 토큰을 확률 분포에서 고른다. 같은 프롬프트에도 고르는 토큰이 달라질 수 있고, 한 토큰의 차이가 뒤의 문장 전체를 바꾼다. 기준 저장소의 api/llm.py는 temperature를 보내지 않는다(기준 저장소 안내에 따르면 API 판 2026-10-21에서 이 인자를 보내면 400 오류가 난다). 출력의 무작위성을 코드에서 끌 수 없다는 뜻이다. 그러므로 품질은 한 번의 출력이 아니라 여러 번의 출력이 이루는 분포로 말해야 한다.

[최신 자료 자리: 샘플링 인자의 지원 여부] 쓰는 모델이 temperature 같은 샘플링 인자를 받는지는 모델과 API 판에 따라 다르다. 확인할 곳: platform.claude.com의 Messages API 참조와 모델 개요. 이 절의 서술은 기준 저장소 안내(API 판 2026-10-21에서 400 오류)를 따른 것이며, 이 교재에서 다시 확인하지 못하였다.

에이전트 평가 글은 이것을 시행(trial)이라는 단어로 정리한다. 「출력이 달라지므로 시행을 여러 번 한다」 [E5]. 또 각 시행은 깨끗한 환경에서 시작해야 한다고 한다. 앞 시행이 남긴 상태(파일, 캐시, 대화 기록)가 다음 시행을 돕거나 해치면 시행끼리 상관이 생겨 반복의 뜻이 없어진다 [E5]. jobprep의 실행기는 시행마다 함수를 새로 부르고 대화 기록을 넘기지 않으므로 이 조건을 지킨다.

4-2. 통과율, pass@k, pass^k

반복 실행의 결과를 하나의 수로 줄이는 방법은 여럿이다. 무엇을 보고 싶은가에 따라 고른다.

지표 뜻 커지는 방향 쓰는 곳
통과율 전체 시행 가운데 통과한 비율 반복을 늘려도 그대로(추정이 정밀해질 뿐) 기본 지표. 회귀 판정의 합격선
pass@k k번 가운데 한 번이라도 통과할 확률 k가 클수록 커진다 한 번만 성공하면 되는 일(예: 코드 생성 후 테스트로 고르기) [E5]
pass^k k번 모두 통과할 확률 k가 클수록 작아진다 매번 성공해야 하는 일(예: 사용자를 마주하는 기능) [E5]

에이전트 평가 글의 예로, 시행 하나의 성공률이 75%이면 세 번 모두 성공할 확률(pass^3)은 0.75³ ≈ 42%이다 [E5]. 취업 준비생이 요약 버튼을 누를 때마다 기준을 지켜야 하는 jobprep에는 pass^k가 맞는 관점이다. 실행기의 「모든 반복 통과 1/14문항」이 문항 단위의 pass^5이다. v1에서는 14문항 가운데 1문항만 다섯 번 모두 통과하였다.

4-3. 표준오차와 신뢰구간

통과율 0.59는 골든 세트 14문항에서 얻은 추정값이다. 문항을 다른 14개로 골랐다면 다른 값이 나왔을 것이다. Anthropic의 평가 통계 글은 평가 점수를 「가능한 모든 문항의 세계」에서 뽑은 표본의 평균으로 보고, 점수마다 평균의 표준오차(SEM)를 함께 보고하라고 권한다 [E6]. 95% 신뢰구간은 평균 ± 1.96 × SEM이다 [E6].

실행기는 회귀 문항마다 통과 비율(예: S09는 1/5 = 0.2)을 낸 뒤, 이 14개 값의 표준편차를 √14로 나누어 SEM을 낸다. 같은 문항을 여러 번 돌린 시행은 서로 독립이 아니므로 시행 70개를 따로 세지 않고 문항 단위로 묶는다. 같은 글은 같은 원천에서 나온 문항들(예: 한 지문에 딸린 여러 질문)의 오차를 묶어서 세지 않으면 오차가 실제보다 작게 나온다고 경고한다 [E6]. 같은 글은 또 문항마다 답을 여러 번 뽑아 평균하면 문항 안의 변동이 줄어든다고 한다 [E6]. 이 장의 반복 실행이 그 방법이다.

보고 방식을 셋으로 견주어 본다.

  • 점수만: 「v1은 0.59」. 0.59가 0.45일 수도 0.72일 수도 있다는 것이 드러나지 않는다.
  • 점수와 구간: 「v1은 0.59(95% 구간 0.45~0.72)」. 두 판본의 구간이 겹치는지 볼 수 있다.
  • 짝지은 차이: 「v2 − v1 = +0.086(구간 −0.072~+0.243)」. 같은 문항에서 비교하므로 오차가 가장 작다. 6절에서 쓴다.

반복 횟수가 결론을 어떻게 바꾸는지 교수 화면에서 본다. 반복 실행의 분산은 실제 모델로 하면 호출이 많아지므로 교수 시연으로 둔다(편성표 §3). 아래는 11-2의 채점기(preferred)까지 더한 상태에서 같은 v1을 1번, 20번 돌린 모의 모델의 결과이다.

한 번만 돌린 점수는 0.43이다. 스무 번 돌린 점수는 0.58이고, 반복 하나하나의 점수는 0.29에서 0.79까지 퍼져 있다. 한 번만 돌렸다면 그 한 번이 0.29일 수도 0.79일 수도 있었다. 반복을 늘리면 구간이 좁아진다(0.16~0.70 → 0.48~0.68). 대신 호출이 75회에서 300회로 늘어 비용도 네 배가 된다. 반복 횟수는 정밀도와 비용의 거래이다.

「모든 반복 통과」는 반대로 움직인다. 한 번 돌리면 6/14문항이 「모두 통과」이지만, 스무 번 돌리면 1/14문항만 남는다. pass^k는 k가 클수록 작아지는 지표이기 때문이다. 이 장의 회귀 판정은 반복 5회를 기본으로 하고, 판정기는 3회 미만의 실행을 받지 않는다(thresholds.json의 min_runs).

반복 횟수에 따른 호출 수와 구간의 너비(v1 실측)를 정리한다. 호출 수는 (문항 수 × 반복 수)이며, LLM 판정을 실제 모델로 하면 판정 호출이 같은 수만큼 더해진다.

  • 반복 1회: 요약 호출 15회(판정을 더하면 30회), 95% 구간의 너비 0.54
  • 반복 5회: 요약 호출 75회(판정을 더하면 150회), 95% 구간의 너비 0.27
  • 반복 20회: 요약 호출 300회(판정을 더하면 600회), 95% 구간의 너비 0.20

생각해 볼 것. 학습자가 키가 있을 때 하는 실제 평가(11-9)는 반복 1회이다. 그 점수 하나로 판본의 품질을 말할 수 없는 까닭을 위의 구간 너비로 설명해 본다.

5. LLM 판정

5-1. 판정자가 맡는 기준

3절의 규칙 채점기는 우대 사항의 혼입처럼 「무엇이 틀렸는지 미리 적을 수 있는」 실수를 잡는다. 그런데 요약 기능의 가장 위험한 실수는 미리 적을 수 없다. 공고에 없는 주의점을 지어내는 일이다. 무엇을 지어낼지는 알 수 없으므로 금지 목록으로 막을 수 없다. 이런 기준은 「출력의 모든 문장이 근거로 뒷받침되는가」를 읽고 판단하는 채점자가 필요하고, 사람 대신 모델에게 그 일을 맡기는 것이 LLM 판정(LLM-as-a-judge)이다.

Zheng 외(2023)는 강한 모델을 판정자로 써서 사람의 선호와 80% 넘게 일치하였고, 이는 사람과 사람 사이의 일치 수준과 같았다고 보고하였다 [R1]. 같은 연구는 판정자의 한계도 함께 보고하였다. 이 절은 그 한계와 보정을 다룬다.

5-2. 기준표

평가 안내는 LLM 판정의 요령으로 셋을 든다 [A1]. 상세하고 분명한 기준표(rubric)를 줄 것, 판정을 「correct 또는 incorrect」나 「1~5점」처럼 정해진 값으로 받을 것(경험적이고 구체적인 출력), 점수를 내기 전에 추론하게 할 것. 또 출력을 만든 모델과 다른 모델을 판정자로 쓰라고 권한다 [A1]. 에이전트 평가 글은 판정자에게 「알 수 없음」이라고 답할 길을 열어 두면 판정자가 지어내는 일이 줄어든다고 한다 [E5].

키트의 기준표 evals/judge_rubric.md가 이 요령을 따른다.

교수 화면 
sed -n '/<기준표>/,/<\/기준표>/p' evals/judge_rubric.md
tail -2 evals/judge_rubric.md
<기준표>
1. 근거 충실성: 출력의 모든 문장은 <근거>에 적힌 내용으로 뒷받침되어야 한다. 근거에 없는 조건, 절차, 숫자를 하나라도 덧붙였으면 fail이다.
2. 왜곡 금지: 근거의 뜻을 뒤집거나(받는다/받지 않는다) 숫자를 바꾸었으면 fail이다.
3. 표현 차이 허용: 근거와 낱말이 달라도 뜻이 같으면 통과로 본다.
4. 판단 불가: 근거만으로 판정할 수 없으면 unknown으로 답한다.
</기준표>
먼저 <reason> 태그 안에 기준표의 어느 항목에 비추어 판단했는지 두 문장 이내로 쓴다.
그다음 <result> 태그 안에 pass, fail, unknown 가운데 하나만 쓴다.

기준표의 각 부분이 어느 요령에 해당하는지 짚는다.

  • 상세하고 분명한 기준 [A1]: 항목 1~3이 통과와 실패의 경계를 문장으로 정한다. 「하나라도 덧붙였으면 fail」처럼 자동 실패 조건을 둔다.
  • 정해진 값으로 받기 [A1]: <result>에 pass, fail, unknown 셋 가운데 하나만 쓰게 한다. 실행기는 이 태그만 읽는다.
  • 먼저 추론하기 [A1]: <reason>을 <result>보다 먼저 쓰게 한다.
  • 알 수 없음 허용 [E5]: 항목 4와 unknown. 실행기는 unknown을 통과로 세지 않는다.
  • 길이와 문체의 배제: 시스템 프롬프트에 「출력의 길이나 문체가 마음에 드는지는 판정에 넣지 않는다」를 둔다(5-3의 길이 편향).

기준표는 코드와 같다. 기준 한 줄을 지우면 판정 결과가 바뀐다. 2026년판 교재의 관찰 실습은 「근거 없는 단정 금지」 기준을 지우자 지어낸 절차를 담은 응답이 통과로 바뀌는 것을 보였다 [L9]. 그래서 기준표는 저장소에 두고, 바꿀 때 풀 리퀘스트로 검토를 받는다.

--backend real이면 evals/judge.py가 이 기준표로 프롬프트를 만들어 llm.complete(task="judge")로 묻는다. 모든 LLM 호출이 api/llm.py 한 곳을 지난다는 기준 저장소의 규칙을 판정자도 따르므로, 판정 호출도 llm.log에 남고 8절의 비용 집계에 잡힌다. --backend sim이면 모의 판정자가 쓰인다. 모의 판정자는 출력의 문장마다 근거의 문장들과 유사도를 재어, 가장 비슷한 근거 문장과의 유사도가 0.45보다 낮은 문장이 있으면 fail로 본다.

5-3. 판정자의 편향

판정자는 사람이 쓴 기준표를 따르지만, 기준표에 적지 않은 경향도 가지고 있다. 연구로 보고된 대표적인 편향은 셋이다.

편향 내용 근거
위치 편향 두 응답을 비교할 때 먼저(또는 나중에) 제시된 쪽을 낫다고 본다 Zheng 외(2023)가 위치 편향을 판정자의 한계로 다루었다 [R1]. Wang 외(2023)는 판정자에게 응답의 순서만 바꾸어 보여 주어도 순위가 뒤집힐 수 있음을 보이고, 한 모델이 다른 모델을 80문항 가운데 66문항에서 이기는 것으로 나오게 할 수 있었다고 보고하였다 [R2]
길이 편향 내용이 같아도 더 길고 자세해 보이는 응답을 낫다고 본다 Zheng 외(2023)의 장황함 편향(verbosity bias) [R1]
자기 선호 판정자가 자기가 만든 출력을 남의 출력보다 높게 본다 Zheng 외(2023)의 자기 강화 편향 [R1]. Panickssery 외(2024)는 판정자가 자기 출력을 알아보는 능력과 자기 선호의 세기 사이에 선형 상관이 있다고 보고하였다 [R3]

jobprep에 대어 보면, 요약 판본 v2의 출력이 v1보다 길다면 길이 편향은 v2에 유리하게 작용한다. 요약을 만든 모델과 같은 모델로 판정하면 자기 선호가 끼어든다. 두 판본을 나란히 놓고 「어느 쪽이 나은가」를 물으면 위치 편향이 끼어든다.

5-4. 보정 방법

편향을 없앨 수는 없지만 줄이고 잴 수는 있다.

방법 하는 일 겨누는 편향
순서 바꾸기 쌍 비교를 두 순서로 물어 두 판정이 같은 쪽을 가리킬 때만 승자로 본다. 다르면 보류한다. Wang 외(2023)의 균형 위치 보정(Balanced Position Calibration)이 순서를 바꾼 결과들을 모아 최종 점수를 내는 방법이다 [R2] 위치
쌍 비교 대신 단독 판정 응답 하나를 기준표로 pass·fail 판정한다. 비교 대상이 없으면 위치가 없다 위치
길이 배제 지시와 형식 제한 기준표에 「길이와 문체는 판정에 넣지 않는다」를 적고, 출력 형식을 같게 맞춘다 길이
다른 모델로 판정 출력을 만든 모델과 다른 모델을 판정자로 쓴다 [A1] 자기 선호
근거 먼저 쓰게 하기 판정 전에 근거를 여러 개 쓰게 한다. Wang 외(2023)의 다중 근거 보정(Multiple Evidence Calibration) [R2] 전반
사람 표본 대조 사람이 판정한 표본과 판정자의 판정을 대조해 일치도를 잰다. 에이전트 평가 글은 판정자를 사람 전문가와 대조해 검증하라고 한다 [E5] 전반(측정)

이 가운데 사람 표본 대조는 다른 방법들이 효과가 있었는지 확인하는 측정 장치이다. 일치도는 단순 일치율과 코언의 카파(Cohen’s kappa)로 잰다. 일치율은 우연히 맞는 몫까지 셈에 넣지만, 카파는 두 채점자가 각자의 pass 비율대로 무작위로 판정해도 맞았을 몫을 빼고 남는 일치를 0~1로 낸다(0이면 우연 수준, 1이면 완전 일치).

5-5. 순서 바꾸기와 사람 표본 대조 (교수 시연)

LLM 판정은 교수 시연으로 본다(편성표 §3). 실제 판정자로 하는 대조는 수업 전 리허설에서 교수가 하고, 수업에서는 같은 절차를 모의 판정자로 보인다. 학습자는 출력을 읽고, 핵심 실습의 평가 보고 5절(11-7)에 이 결과를 옮긴다.

먼저 위치 편향과 순서 바꾸기를 본다. pairwise-demo는 요약 문항마다 충실한 요약(x)과 항목 하나를 지어낸 요약(y)을 만들어, 위치 편향을 일부러 넣은 모의 판정자에게 비교시킨다. 실제 판정자를 흉내 낸 장치이며, 편향의 크기는 집필자가 정하였다.

교수 화면 
python -m evals.judge pairwise-demo
비교한 문항: 14
x(충실한 요약)를 먼저 보였을 때 x 승: 14
y(지어낸 항목이 있는 요약)를 먼저 보였을 때 y 승: 3
순서 바꾸기 점검: x 승 11, y 승 0, 판정 보류 3

x를 먼저 보이면 x가 14번 모두 이긴다. y를 먼저 보이면 지어낸 항목이 있는 y가 3번 이긴다. 한 순서로만 물었다면 이 3번은 잘못된 판정으로 기록되었을 것이다. 순서 바꾸기 점검은 두 순서의 판정이 엇갈린 3문항을 보류로 돌리고, 잘못된 승자를 하나도 내지 않는다. 보류된 문항은 사람이 읽는다.

이어서 사람 표본 대조를 한다. evals/calibration/judge_sample.jsonl에는 요약 출력 12개와 사람(집필자)이 내린 판정과 그 까닭이 있다. 공고를 그대로 옮긴 출력, 주의점을 지어낸 출력, 낱말만 바꾼 출력, 숫자나 뜻을 뒤집은 출력이 섞여 있다.

교수 화면 
python -m evals.calibrate
판정자: 모의 판정자(기준값 0.45) · 표본 12개
               판정자 pass  판정자 fail
  사람 pass             4           2
  사람 fail             3           3
일치율 0.58 · 코언의 카파 0.17
  엇갈림 C03(S07): 사람 pass, 판정자 fail — 사람의 까닭: 낱말은 다르나 뜻은 공고와 같다
  엇갈림 C04(S07): 사람 fail, 판정자 pass — 사람의 까닭: 수습 급여 비율을 90%에서 100%로 바꾸었다
  엇갈림 C05(S07): 사람 fail, 판정자 pass — 사람의 까닭: 불이익이 있다를 없다로 뒤집었다
  엇갈림 C07(S03): 사람 pass, 판정자 fail — 사람의 까닭: 명사형으로 줄였으나 뜻은 같다
  엇갈림 C12(S05): 사람 fail, 판정자 pass — 사람의 까닭: 졸업 후 입사를 졸업 전 입사로 바꾸었다

카파 0.17은 우연 수준을 조금 넘는 일치이다. 엇갈린 다섯 표본을 읽으면 모양이 둘로 갈린다. 낱말을 바꾼 정상 출력(C03, C07)을 fail로 보고, 낱말은 거의 같은데 뜻이나 숫자를 뒤집은 출력(C04, C05, C12)을 pass로 본다. 모의 판정자는 글자의 겹침을 재므로 뜻을 재지 못한다.

교수는 이어서 기준값을 0.25로 낮춘 판정(--support 0.25)과 숫자 대조를 더한 판정(--numbers)을 보인다. 결과를 모으면 다음과 같다.

  • 모의 판정자, 기준값 0.45: 일치율 0.58, 카파 0.17. 표현 차이 2, 뜻 뒤집기 2, 숫자 바꾸기 1이 엇갈린다.
  • 모의 판정자, 기준값 0.25: 일치율 0.58, 카파 0.17. 표현 차이 1, 뜻 뒤집기 2, 숫자 바꾸기 1, 지어냄 1이 엇갈린다.
  • 모의 판정자, 기준값 0.45에 숫자 대조: 일치율 0.67, 카파 0.33. 표현 차이 2, 뜻 뒤집기 2가 엇갈린다.
  • 실제 판정자(기준표): 교수가 수업 전 리허설에서 같은 표본으로 잰 값을 시연에서 보인다.

기준값을 낮추면 표현 차이 하나(C07)를 더 통과시키는 대신 지어낸 문장 하나(C10)를 놓쳐, 카파가 그대로다. 기준값은 오류의 종류를 맞바꿀 뿐이다. 반면 「출력의 숫자가 근거에 그대로 있는가」라는 규칙을 더하면 숫자를 바꾼 C04를 잡아 카파가 0.33으로 오른다. 남은 엇갈림(뜻을 뒤집은 C05, C12와 표현 차이 C03, C07)은 글자 겹침으로는 풀 수 없다. 실제 LLM 판정자가 맡아야 하는 몫이 바로 이것이고, 실제 판정자도 같은 표본으로 대조해 카파를 잰 뒤에 믿는다.

판정자 보정은 한 번으로 끝나지 않는다. 기준표를 고치거나 판정 모델을 바꿀 때마다 같은 표본으로 다시 잰다. 표본도 운영 중에 사람이 실제로 읽은 출력으로 늘려 간다.

6. 판본 비교

6-1. 무엇을 고정하고 무엇을 바꾸는가

판본 비교는 실험이다. 실험에서는 한 번에 하나만 바꾼다. 두 실행 사이에 프롬프트와 모델이 함께 바뀌었다면 점수의 차이가 어디서 왔는지 알 수 없다.

  • 골든 세트: 같은 evals/golden/*.jsonl을 쓴다. 문항을 더했으면 두 판본을 모두 다시 돌린다.
  • 채점기와 판정자: 같은 graders.py와 judge_rubric.md를 쓴다. 3-4처럼 채점기가 바뀌면 이전 점수와 견주지 않는다.
  • 검색 조건: 실행기가 EMBED_BACKEND=fallback으로 고정한다. 자기 PC에 Ollama를 설치했거나 .env가 EMBED_BACKEND=auto여도 평가는 같은 임베딩으로 돈다.
  • 반복 횟수: 두 실행 모두 5회로 한다.
  • 바꾸는 것: 프롬프트 판본(--prompt)과 모델(--model) 가운데 하나만 바꾼다.

6-2. 짝지은 차이

두 판본의 통과율을 따로 구해 빼면, 두 값 각각의 오차가 더해져 차이의 오차가 커진다. 그런데 두 판본은 같은 14문항에서 돌았다. 어려운 문항은 두 판본 모두에게 어렵다. 그래서 문항마다 (v2의 통과 비율 − v1의 통과 비율)을 내고 그 평균과 표준오차를 구하면, 문항의 난이도가 상쇄되어 오차가 작아진다. 평가 통계 글은 같은 문항 묶음에서 두 모델을 비교할 때 두 표본 검정이 아니라 짝지은 차이(paired differences)를 쓰라고 하며, 최신 모델들의 문항별 점수는 상관이 0.3~0.7 정도로 높아 이 방법이 오차를 크게 줄인다고 한다 [E6].

evals/compare.py는 짝지은 차이의 평균, 표준오차, 95% 구간을 내고, 구간이 0을 포함하는지로 판단을 적는다. 구간이 0보다 크면 「나아졌다」, 0보다 작으면 「나빠졌다」, 0을 포함하면 「차이를 말할 수 없다」이다.

6-3. 판단의 세 갈래

compare의 출력은 기준별 표, 전체 통과율, 짝지은 차이, 판단 줄, 크게 바뀐 문항의 순서로 나온다. 판단 줄은 세 갈래이고, 갈래마다 다음 할 일이 다르다. 핵심 실습(11-3)에서 v1과 v2를 비교할 때 이 표로 읽는다.

   ① 비교 쪽이 낫다(구간이 0보다 크다)
      → 기준별 표에서 내려간 기준이 없는지 본다 · 없으면 회귀 판정(11-5)으로
   ② 비교 쪽이 나쁘다(구간이 0보다 작다)
      → 내려간 기준의 판정 이유와 실패 사유를 모아 센다 · 판본을 고친다
   ③ 차이를 말할 수 없다(구간이 0을 포함한다)
      → 기준별 표부터 읽는다 · 오른 기준과 내려간 기준이 섞여 있으면 판본을 고친다
        섞여 있지 않으면 반복이나 문항을 늘려 다시 잰다

③을 「두 판본이 같다」로 읽지 않는다. 「차이를 말할 수 없다」와 「차이가 없다」는 다르다. 지금의 문항 수와 반복으로는 차이를 가릴 수 없다는 뜻이다. 그리고 ③이든 ①이든, 전체 점수보다 기준별 표를 먼저 읽는다. 판단의 단위는 전체 점수가 아니라 기준이며, 기준마다 실수의 무게가 다르다(지어냄은 길이 초과보다 무겁다).

7. 에이전트 평가

7-1. 결과와 경로

지금까지의 평가는 입력 하나에 출력 하나인 기능을 다루었다. 8장의 루프와 10장의 멀티 에이전트는 다르다. 한 번의 실행이 여러 턴, 여러 도구 호출, 여러 시도로 이루어지고, 끝에 저장소의 상태(테스트 통과, 커밋, 병합)가 남는다. 에이전트 평가 글은 이 구조를 「기록(transcript)」과 「결과(outcome)」로 나눈다 [E5]. 기록은 시행의 모든 출력과 도구 호출과 중간 결과이고, 결과는 시행이 끝난 뒤 환경에 남은 최종 상태이다(예: 예약이 실제로 데이터베이스에 있는가).

같은 글은 「에이전트가 지나온 경로가 아니라 만들어 낸 것을 채점하라」고 권한다 [E5]. 「먼저 테스트를 읽고, 다음에 api/jobs.py를 고친다」처럼 단계의 순서를 채점하면, 다른 순서로 같은 결과에 이른 에이전트가 실패로 잡힌다. 8장의 루프가 종료 조건을 「pytest -q가 통과한다」는 결과로 정한 것이 이 원칙이다. 경로는 채점하지 않되, 기록은 남겨 두고 읽는다. 실패한 실행의 원인과, 성공했지만 비용이 지나치게 든 실행의 원인은 기록에만 있다.

사람 개입을 두 종류로 나누는 까닭이 있다. 10장의 설계에서 사람은 계획을 승인하고 병합을 결정한다. 이것은 설계된 승인 지점이고, 줄여야 할 대상이 아니다. 반면 병합 충돌을 사람이 손으로 고친 것은 시스템이 해결하지 못한 예외이다. 둘을 한 숫자로 세면 「사람 개입이 많다」는 보고가 좋은 설계인지 나쁜 설계인지 말해 주지 못한다.

## 5. 예산

green 5건 가운데 2027-11-06-sort-order는 커밋한 시도가 tests/test_jobs.py를 고쳤다. 에이전트가 구현을 고치는 대신 테스트의 기대값을 바꾸어 통과시킨 것이다. 8장 6-8에서 본 cheat-1과 같은 모양이며, 기록의 status만 세면 정상적인 성공과 구별되지 않는다. 그래서 보고는 실행의 start 사건에 적힌 보호 경로(config.protected)와 커밋된 시도의 changed를 대조해, 보호 경로를 고친 green을 「의심 성공」으로 따로 센다. 이 실행을 성공으로 세면 성공률은 71%, 빼면 57%이다. 무엇을 성공으로 세는가가 지표의 값을 바꾼다. 8장을 마친 학습자의 기록에도 같은 판정이 적용되므로, 자기 cheat-1이 의심 성공으로 잡히는지 보면 된다.

8장 견본에서 비용이 가장 큰 실행(0.98 USD)은 실패한 실행(budget)이다. 이 실행의 attempt 사건에서 시도 번호, 결과의 종류, 턴, 비용, 결정, 에이전트 보고의 첫 줄을 뽑으면 다음과 같다.

1 success 14 0.45 no_change 색인 코드를 모두 읽었으나 원인을 정하지 못하였다.
2 error_max_budget_usd 15 0.53 no_change

두 시도 모두 턴 상한(15)에 가까이 쓰고도 파일을 하나도 바꾸지 못했다(no_change). 두 번째 시도는 실행 하나의 예산(--max-budget-usd)에 걸려 멈추었다. 「저장소 전체를 읽는」 탐색이 비용의 대부분이었다는 뜻이다. 이 기록은 루프의 프롬프트에 「먼저 실패한 테스트의 파일만 읽는다」를 더하거나, 이런 종류의 작업을 루프에 맡기지 않는다는 결정의 근거가 된다.

멀티 에이전트 절은 10장의 기록 세 가지를 함께 읽는다. 사건은 events.jsonl(actor, event, task, detail)에서, 비용과 턴은 구현 에이전트의 출력 파일(<작업>_시도<n>.out)에서, 커밋은 git log의 꼬리말(Agent-Role, Agent-Task, Agent-Attempt)에서 온다. 10장의 계획 승인은 계획서의 - 승인: 줄로 남고 사건으로는 남지 않으므로, 「계획된 개입」에는 병합만 들어간다. 견본만 복사한 저장소에는 꼬리말이 붙은 커밋이 없어 마지막 줄이 「없다」이다.

10장의 핵심 실습처럼 Orca 작업 공간의 세션에 사람이 지시를 넣은 이슈는 조정 스크립트의 실행 사건(dispatched)과 출력 파일이 없고, 판정(judge.sh)과 병합(merge.sh)의 사건만 남는다. 보고는 그런 이슈를 「실행 사건(dispatched)이 없는 이슈」로 따로 적고 시도를 판정 횟수로 센다. 구현 에이전트의 비용은 자기 구독의 사용량 화면(9-1)에만 있으므로 「비용이 없다」로 나온다. 기록을 읽는 코드는 read_multi(), issue_summary(), multi_section() 세 함수에 모여 있으므로, 10장에서 사건 이름을 바꾼 학습자도 고칠 곳이 그 셋뿐이다.

8. 관측과 구조화 기록

8-1. 평가와 관측

평가는 배포 전에 골든 세트로 품질을 잰다. 관측(observability)은 배포 뒤에 실제 요청에서 무슨 일이 일어나는지를 기록으로 본다. 둘은 서로를 채운다. 평가가 통과해도 운영에서는 골든 세트에 없던 입력이 들어오고, 모델 제공자의 속도 제한에 걸리고, 비용이 예상보다 커진다. 관측이 그것을 보여 주면, 그 입력은 다음 골든 세트의 문항이 된다(2-5).

Google의 SRE 책은 모니터링을 「시스템에 대한 실시간 정량 자료(질의 수와 종류, 오류 수와 종류, 처리 시간, 서버 가동 시간)를 모으고 처리하고 집계하고 보여 주는 일」로 정의하고, 사용자를 마주하는 시스템이라면 네 가지 황금 신호(golden signals)를 보라고 한다 [S1].

신호 [S1] 뜻 [S1] jobprep에서 재는 곳
지연(latency) 요청 하나를 처리하는 데 걸리는 시간. 실패한 요청의 지연은 따로 잰다(느린 오류는 빠른 오류보다 나쁘다) access.log의 ms. 요약과 질의응답은 LLM 호출 때문에 수 초가 걸린다
트래픽(traffic) 시스템에 대한 수요. 웹 서비스라면 초당 HTTP 요청 수 access.log의 줄 수, 경로별 요청 수
오류(errors) 실패한 요청의 비율. 명시적 실패(500), 암묵적 실패(내용이 틀린 200), 정책상 실패(약속한 시간을 넘긴 응답)를 모두 포함한다 access.log의 5xx, llm.log의 error. 「내용이 틀린 200」은 기록으로 보이지 않으므로 평가가 맡는다
포화(saturation) 서비스가 얼마나 「가득 찼는가」. 가장 제약된 자원에 주목한다 jobprep에서는 모델 제공자의 속도 제한이 가장 제약된 자원이다. RateLimitError가 포화의 신호이다

같은 장은 평균 지연에 속지 말라고 한다. 평균이 100ms여도 요청의 1%가 5초씩 걸릴 수 있고, 지연은 평균보다 분포(백분위수)로 보아야 한다 [S1]. 이 장의 보고가 p50과 p95를 함께 내는 까닭이다.

관측의 자료는 대개 세 종류로 나뉜다. OpenTelemetry는 지원하는 신호로 트레이스(요청이 애플리케이션을 지나는 경로), 지표(실행 중에 잰 측정값), 로그(개별 사건의 기록)를 들고, 신호 사이에 맥락을 실어 나르는 배기지(baggage)를 더한다 [O1].

세 신호를 jobprep과 Claude Code에 대어 보면 다음과 같다.

  • 로그(사건): jobprep에는 access.log, error.log, llm.log, 8장·10장의 JSON Lines, 평가의 records.jsonl이 있다. Claude Code는 claude_code.api_request, claude_code.tool_result 같은 이벤트를 낸다(9절).
  • 지표: jobprep에는 없고, 이 장의 report.py가 로그에서 계산한다. Claude Code는 claude_code.cost.usage, claude_code.token.usage 같은 지표를 낸다.
  • 트레이스: jobprep에는 없다. Claude Code는 베타 기능으로 상호작용 → LLM 요청 → 도구 실행의 구간(span)을 낸다.

8-3. 구조화 기록

기록은 사람이 읽기 전에 프로그램이 읽는다. 그래서 기록의 한 줄은 정해진 칸을 가진 구조화 기록(structured log)이어야 한다. 기준 저장소의 운영 기록은 날짜 시각 수준 기록기 키=값… 꼴이고, 8장·10장의 실행 기록과 이 장의 평가 기록은 한 줄이 JSON 객체 하나인 JSON Lines 꼴이다.

기록의 형식을 셋으로 견주어 본다.

  • 자유 문장(요약 실패: 속도 제한에 걸림): 사람이 읽기 쉽다. 그러나 집계하려면 문장을 해석해야 하고, 문구가 바뀌면 집계가 깨진다.
  • 키=값(task=summary error=RateLimitError): 사람도 프로그램도 읽기 쉽고 grep으로 찾기 좋다. 값에 빈칸이 있으면 따옴표 규칙이 필요하고, 중첩 구조를 담지 못한다.
  • JSON Lines({"task": "summary", "error": "RateLimitError"}): 중첩 구조, 목록, 숫자와 문자열의 구별을 담고 대부분의 도구가 읽는다. 사람이 눈으로 읽기에는 길다.

ops/telemetry/logparse.py는 키=값 형식을 JSON으로 바꾼다. 값에 빈칸이 있으면 큰따옴표로 감싸는 규칙(logs/README.md)을 따르므로 파이썬 표준 라이브러리의 shlex로 나눈다. 기준 저장소의 오류 기록 앞 두 줄을 바꾼 결과를 읽는다.

교수 화면 
python -m ops.telemetry.logparse logs/error.log 2>&1 | head -3
(전체 22줄, 읽지 못한 줄 0개)
{"ts": "2027-09-08T14:03:47", "level": "WARNING", "logger": "jobprep.llm", "task": "summary", "model": "claude-haiku-5-5", "error": "RateLimitError"}
{"ts": "2027-09-08T14:03:47", "level": "ERROR", "logger": "jobprep.api", "path": "/api/summary", "status": 503, "error": "LLMError", "detail": "LLM 호출에 실패하였다: RateLimitError"}

status가 따옴표 없는 숫자 503으로 바뀐 것에 주목한다. 기록을 읽는 코드가 숫자와 문자열을 구별해야 「5xx 비율」 같은 집계가 맞는다. 둘째 줄의 detail은 빈칸이 든 값인데도 한 칸으로 읽혔다.

같은 시각(14:03:47)의 두 줄은 같은 요청에서 나온 것으로 보이지만, 그것을 확정할 칸이 없다. 요청 번호가 있었다면 access.log의 줄까지 셋을 이을 수 있다. 이것이 8-2의 표에서 「없다」로 적은 빈자리의 비용이다.

9. Claude Code의 사용량과 비용, OpenTelemetry

jobprep의 앱이 부르는 LLM 비용은 llm.log가 보여 준다. 그런데 이 학기의 운영 에이전트 시스템은 대부분 Claude Code로 돈다. 3~10장의 커맨드, 스킬, 훅, 루프, 역할 에이전트가 쓰는 토큰과 비용은 Claude Code가 따로 센다. 이 절은 그 수치를 보는 세 가지 길을 다룬다. 대화 하나(9-1), 실행 하나(9-2), 조직 전체(9-3~9-5)이다. 9-3~9-5의 OpenTelemetry는 [선택]이며, 화면은 교수 시연으로 본다. 화면과 명령은 2026-11 기준이며, 이 교재는 Claude Code 2.1.296으로 확인하였다.

[최신 자료 자리: Claude Code의 판과 사용량 화면] 수업 전에 claude --version과 비용 문서(code.claude.com/docs/en/costs)에서 /usage의 구역과 별칭, 판별 기능(Prompt cache (main) 줄은 2.1.251 이상, f 단축키는 2.1.305 이상)을 다시 확인한다. 2026-11-15 값: 2.1.296, /cost·/stats는 /usage의 별칭.

9-1. 대화 안에서: /usage

Claude Code 안에서 /usage를 입력하면 현재 세션의 비용, 요금제의 사용 한도, 활동 통계가 보인다. /cost와 /stats는 /usage의 별칭이다 [C21]. 이 절과 9-3의 화면 확인은 교수 시연으로 한다. 교수 화면의 계정 종류(API 또는 구독)에 따라 보이는 구역이 다르므로, 학습자는 시연 화면에서 아래 세 가지를 찾아 읽는다.

교수 화면 
/usage

[그림 자리: 교수 화면의 /usage] 교수 계정에서 /usage를 연 화면. 세션 구역(Total cost, Usage by model)과, 구독 계정이면 요금제 사용 막대와 사용 내역이 함께 보이게 찍는다. 찍을 곳: 교수 PC의 Claude Code, 수업 전 리허설.

공식 문서가 보여 주는 세션 구역의 예는 다음과 같다(API 사용자 화면의 예시이며, 실제 화면은 계정과 판에 따라 다르다) [C19].

Total cost:            $0.55
Total duration (API):  6m 20s
Total duration (wall): 6h 33m 10s
Total code changes:    0 lines added, 0 lines removed
Usage by model:
   claude-sonnet-4-6:  1.2k input, 5.3k output, 940.0k cache read, 50.0k cache write ($0.55)

이 화면을 읽을 때 지킬 점이 셋이다 [C19].

  • 추정이다: 금액은 Claude Code가 토큰 수와 정가로 컴퓨터 안에서 계산한 추정이다. 청구액은 Console 같은 조직의 청구 화면에서 본다.
  • 구독자에게는 뜻이 다르다: Pro, Max 같은 구독에서는 사용량이 요금제에 포함되므로 세션 비용은 청구와 무관하다. 구독자 화면에는 요금제 사용 막대와 사용 내역이 함께 나온다.
  • 세션 단위이다: /clear로 새 세션을 열면 합계가 0부터 다시 시작한다.

캐시 읽기 토큰(cache read)이 입력보다 훨씬 많은 것도 눈여겨본다. 긴 세션은 요청마다 대화 전체를 다시 보내고, 프롬프트 캐시가 그 비용을 줄인다. 공식 문서는 오래 열어 둔 세션의 사용량이 커지는 까닭으로 긴 맥락, 캐시 만료 뒤의 재처리, 예약 작업, 서브에이전트, 압축(/compact) 자체의 비용을 든다 [C19].

9-2. 스크립트에서: 헤드리스 JSON 결과

8장의 루프는 claude -p --output-format json의 결과를 읽어 시도마다 비용을 기록하였다. 결과 객체의 칸 가운데 관측에 쓰는 것은 다음과 같다 [C14][C22].

칸 뜻
subtype success 또는 오류 종류(error_max_turns, error_during_execution, error_max_budget_usd, error_max_structured_output_retries)
is_error 오류로 끝났는가
num_turns 이 실행의 턴 수(8장 기록의 turns)
duration_ms, duration_api_ms 전체 시간과 API 호출에 쓴 시간
total_cost_usd 이 실행의 추정 비용(8장 기록의 cost_usd). 서브에이전트의 비용을 포함한다
usage 토큰 수. 맨 위 에이전트 루프만 세고 서브에이전트는 빠진다
modelUsage 모델별 토큰과 비용(costUSD, inputTokens, outputTokens, cacheReadInputTokens, cacheCreationInputTokens). 서브에이전트를 포함한다
session_id 이어서 실행하거나 기록과 잇는 번호

비용 문서는 total_cost_usd와 costUSD가 「클라이언트 쪽 추정이며 청구 자료가 아니다」라고 경고하고, 가격이 바뀌거나 설치된 판이 모델을 모르면 실제와 어긋날 수 있다고 한다 [C22]. 또 --continue나 --resume으로 이어 간 실행은 앞 실행의 비용까지 포함한 대화 전체의 합계를 보고하므로, 이어 간 실행의 결과를 더하면 비용을 두 번 센다 [C14][C22].

실행 하나의 비용 상한은 --max-budget-usd이다. 이 값은 같은 클라이언트 쪽 추정으로 판정하므로 실제 지출이 상한을 조금 넘을 수 있고, 서브에이전트의 지출도 상한에 들어간다 [C15]. 상한에 닿으면 결과의 subtype이 error_max_budget_usd가 된다. 7-3에서 본 실행이 이 경우이다. 도움말에서 이 옵션을 찾으면 다음과 같다(모델을 부르지 않는 명령이다).

교수 화면 
claude --help | grep -A1 "max-budget-usd"
  --max-budget-usd <amount>             Maximum dollar amount to spend on API
                                        calls (only works with --print)

[최신 자료 자리: 헤드리스 결과의 칸과 비용 상한 옵션] 위 표의 칸 이름과 subtype의 오류 종류, claude --help의 --max-budget-usd 설명을 헤드리스 문서(code.claude.com/docs/en/headless)와 교수 PC의 claude --help로 다시 확인한다. 2026-11-15에 2.1.296의 도움말에서 위 출력과 같은 두 줄을 확인하였다.

9-3. [선택] 조직 단위로: OpenTelemetry

OpenTelemetry(OTel)는 신호를 「모으고, 처리하고, 내보내는」 공개 표준이다 [O1]. Claude Code는 OTel로 지표와 이벤트를 내보낼 수 있고, 내보낸 자료는 수집기(collector)를 거쳐 Prometheus 같은 저장소와 대시보드로 간다 [C18]. 비용 문서는 OTel 내보내기가 모든 사용 형태(팀 요금제, Console, 클라우드 제공자)에서 동작하며, 사용자별 토큰과 비용을 조직의 관측 체계로 거의 실시간에 보내는 유일한 방법이라고 한다 [C19].

켜는 법은 환경 변수이다. 공식 문서의 빠른 시작을 줄이면 다음과 같다 [C18].

환경 변수 값의 예 뜻
CLAUDE_CODE_ENABLE_TELEMETRY 1 원격 측정을 켠다(필수)
OTEL_METRICS_EXPORTER otlp, prometheus, console, none 지표를 어디로 내보내는가
OTEL_LOGS_EXPORTER otlp, console, none 이벤트(로그)를 어디로 내보내는가
OTEL_EXPORTER_OTLP_PROTOCOL grpc, http/json, http/protobuf OTLP 전송 방식
OTEL_EXPORTER_OTLP_ENDPOINT http://localhost:4317 수집기의 주소
OTEL_EXPORTER_OTLP_HEADERS Authorization=Bearer … 수집기의 인증(값은 비밀 정보로 다룬다)
OTEL_METRIC_EXPORT_INTERVAL 기본 60000(ms) 지표를 내보내는 간격
OTEL_LOGS_EXPORT_INTERVAL 기본 5000(ms) 이벤트를 내보내는 간격
OTEL_RESOURCE_ATTRIBUTES department=engineering,team.id=platform 팀, 부서 같은 사용자 정의 속성

수집기 없이 동작을 확인하려면 console 내보내기를 쓴다. 공식 문서의 디버깅 예는 지표를 1초마다 콘솔에 찍는다 [C18]. 이 확인은 교수 시연으로 한다.

교수 화면 
CLAUDE_CODE_ENABLE_TELEMETRY=1 OTEL_METRICS_EXPORTER=console OTEL_METRIC_EXPORT_INTERVAL=10000 claude

이 명령은 원격 측정을 이 세션 하나에만 켠다. Claude Code에 짧은 요청을 하나 보내면 10초 간격으로 지표가 터미널에 찍힌다. 공식 문서는 지표가 오는지 볼 때 claude_code.session.count를 찾으라고 하고, 아무것도 오지 않으면 claude --debug-file <경로>로 연 뒤 기록에서 [3P telemetry] 오류를 찾으라고 한다 [C18]. 콘솔 출력은 화면을 어지럽히므로 확인한 뒤 바로 Claude Code를 닫는다.

이 단계는 Claude Code에 요청을 보내 계정의 사용량을 쓰므로 교수 시연으로 한다. 학습자는 시연 화면에서 claude_code.session.count와 claude_code.cost.usage가 찍힌 줄을 찾는다. 이 교재를 쓸 때는 모델을 부르지 않아 콘솔 출력의 실제 모양을 확인하지 못하였다.

[그림 자리: OpenTelemetry 콘솔 내보내기] 위 명령으로 연 세션에서 짧은 요청 하나를 보낸 뒤 10초 간격으로 찍힌 지표 출력. claude_code.session.count와 claude_code.cost.usage의 줄이 보이게 찍는다. 찍을 곳: 교수 PC의 터미널, 수업 전 리허설.

[최신 자료 자리: OpenTelemetry 환경 변수와 지표 이름] 9-3의 환경 변수 표, 9-4의 지표·이벤트 이름, 내보내기 간격의 기본값(지표 60000ms, 이벤트 5000ms), 저장소 설정의 OTEL_* 무시 규칙을 모니터링 문서(code.claude.com/docs/en/monitoring-usage)에서 다시 확인한다. 2026-11-14·15에 확인한 값이 이 절에 적혀 있다.

9-5. [선택] 설정을 두는 곳

환경 변수를 셸에서 매번 줄 수 없으므로 설정 파일의 env 블록에 둔다. 그런데 어느 설정 파일이냐가 중요하다. 공식 문서에 따르면 Claude Code는 저장소의 .claude/settings.json과 .claude/settings.local.json에 있는 OTEL_* 내보내기 변수를 무시한다. 그래서 저장소는 원격 측정을 켜거나, 보낼 곳을 정하거나, 내용을 기록하게 할 수 없다. 저장소가 할 수 있는 일은 내보내기를 none으로 끄는 것뿐이다 [C18].

  • 셸 환경 변수: 먹는다. 개인이 한 세션만 확인할 때 쓴다(9-3).
  • 사용자 설정 ~/.claude/settings.json의 env: 먹는다. 개인이 늘 켜 둘 때 쓴다.
  • 관리 설정(managed settings)의 env: 먹는다. 조직의 관리자가 쓰며, 보낼 곳을 고정할 수 있다.
  • 저장소의 .claude/settings.json, settings.local.json: 먹지 않는다. 내보내기를 none으로 끄는 것만 된다.

이 규칙은 11장의 공급망 보안과 같은 생각이다. 남의 저장소를 받아 Claude Code를 여는 것만으로 자기 대화 내용이 남의 수집기로 보내져서는 안 된다. 3장에서 팀 규칙을 저장소의 .claude/settings.json에 두었지만, 관측의 설정은 거기에 두지 않는다.

조직이 원격 측정을 켤 때는 관리 설정에 다음과 같은 env 블록을 둔다(공식 문서의 예를 따랐다. 주소와 토큰은 자리 표시이다) [C18].

파일: 관리 설정 파일 (관리자용 예) 
{
  "env": {
    "CLAUDE_CODE_ENABLE_TELEMETRY": "1",
    "OTEL_METRICS_EXPORTER": "otlp",
    "OTEL_LOGS_EXPORTER": "otlp",
    "OTEL_EXPORTER_OTLP_PROTOCOL": "grpc",
    "OTEL_EXPORTER_OTLP_ENDPOINT": "http://collector.example.com:4317",
    "OTEL_EXPORTER_OTLP_HEADERS": "Authorization=Bearer example-token"
  }
}

학습자는 이 파일을 자기 PC에 만들지 않는다. 대신 3장에서 만든 저장소 설정에 이런 변수를 넣으면 어떻게 되는지를 문서의 규칙으로 판정해 본다.

생각해 볼 것. 「저장소의 .claude/settings.json에 "OTEL_METRICS_EXPORTER": "otlp"를 넣으면 원격 측정이 켜지는가」에 답하고, 그 규칙이 11장의 공급망 보안과 어떻게 이어지는지 말해 본다.

10. 비용 예산과 경보, 개인 정보

10-1. 예산의 층

비용은 한 곳에서 막지 않는다. 층마다 다른 단위의 상한을 둔다.

층 상한 넘으면 이 학기의 자리
조직 Console의 작업 공간 지출 한도, 팀 요금제의 지출 한도 [C19] 그 작업 공간의 호출이 막힌다 각자 Console 키를 발급했다면(선택) 그 작업 공간에 작은 지출 한도를 건다(부록 A-2-3)
실행 하나 --max-budget-usd [C15] 그 실행이 error_max_budget_usd로 멈춘다 8장 루프의 시도당 예산
루프 하나 루프 스크립트의 누적 예산 루프가 멈추고 사람에게 넘긴다 8장 루프의 budget
기간 주간·월간 예산과 주의 기준 보고에 주의·초과를 띄우고 종료 코드로 알린다 이 장의 report.py --budget-usd

아래 층일수록 빨리 멈추고, 위 층일수록 넓게 본다. 아래 층의 상한만 있으면 작은 실행이 수없이 반복될 때 막지 못하고, 위 층의 상한만 있으면 한 실행이 예산을 다 써 버린다. 비용 문서는 시작할 때 소수의 시범 그룹으로 기준선을 잡은 뒤 넓히라고 권하고, 기업 사용의 평균으로 활동일 하루에 개발자당 약 13 USD, 사용자 90%가 활동일 하루 30 USD 아래라는 수치를 든다 [C19]. 이 수치는 기업의 것이므로 수업의 예산은 학과가 정하지만, 「기준선을 먼저 재고 예산을 정한다」는 순서는 같다.

[최신 자료 자리: 기업 사용의 평균 비용] 비용 문서(code.claude.com/docs/en/costs)의 평균 비용 수치. 2026-11-15 값: 활동일 하루 개발자당 약 13 USD, 달마다 개발자당 150~250 USD, 사용자 90%가 활동일 하루 30 USD 미만.

10-2. 경보의 원칙

보고서는 사람이 읽으러 와야 보이고, 경보(alert)는 사람에게 간다. 그래서 경보는 적게, 의미 있게 울려야 한다. SRE 책은 경보의 원칙으로 다음을 든다 [S1].

  • 모든 호출(page)은 행동할 수 있어야 한다. 기계적인 대응만 필요한 경보는 경보가 아니다. jobprep에서 「예산의 87%」는 「이번 주에 루프를 더 돌릴지 정한다」는 행동으로 이어진다. 「LLM 호출 한 번 실패」는 행동이 없으므로 경보로 보내지 않고 보고에만 둔다.
  • 원인보다 증상에 경보를 건다. 「5xx 비율이 2%를 넘었다」(증상)에 경보를 걸고, 「RateLimitError」(원인)는 보고에서 찾는다.
  • 잦고 시끄러운 경보는 피로를 낳아 진짜 사건을 가린다. 1-4에서 능력 문항을 회귀 판정에서 뺀 까닭과 같다. 늘 울리는 경보는 무시된다.

report.py는 두 단계를 둔다. 예산의 80% 이상이면 보고에 「주의」를 적고(종료 코드 0), 예산을 넘으면 「초과」를 적고 종료 코드 2를 낸다. 종료 코드가 있으면 예약 실행(8장)이나 CI(13장)가 이 결과로 다음 동작을 정할 수 있다. 예산 5 USD로 보고의 끝을 파이프로 잘라 보면 다음과 같다(11-6에서 학습자가 파이프 없이 다시 본다).

10-3. 개인 정보와 기록

관측은 많이 남길수록 좋아 보이지만, 기록은 그 자체로 유출의 통로가 된다. 1장의 운영 요건 가운데 보안(비밀 정보와 사용자 정보가 새지 않는다)이 기록에도 적용된다.

원칙 jobprep에서 Claude Code에서 [C18]
내용 대신 크기를 남긴다 질문 원문 대신 기능, 토큰 수, 지연만 남긴다 user_prompt 이벤트의 prompt는 기본으로 가려지고 prompt_length만 남는다

def grade_preferred(item, output):
    """우대 사항이 자격 요건에 섞이지 않았는가(규칙). 공고에 우대 사항이 없으면 해당 없음."""
    preferred = item["expect"].get("preferred", [])
    if not preferred:
        return None, "우대 사항 없음"
    mixed = [q for q in output.get("qualifications", []) if best_match(q, preferred) >= MATCH_MIN]
    if mixed:
        return False, f"우대 사항이 자격 요건에 섞임: {mixed[0]}"
    return True, ""


SUMMARY_GRADERS["preferred"] = grade_preferred

판정기는 두 가지를 본다. 하나는 합격선(threshold)이다. 회귀 통과율과 기준별 통과율이 thresholds.json의 최솟값 이상이어야 한다. 다른 하나는 기준선(baseline)이다. 마지막으로 합격한 실행의 통과율보다 허용 폭(0.05) 넘게 떨어지면 합격선을 넘어도 실패로 본다. 합격선은 「이 아래로는 내보내지 않는다」는 절대 기준이고, 기준선은 「지금보다 나빠지지 않는다」는 상대 기준이다.

  • 합격선은 팀이 성공 기준(1-3)을 정할 때 정하고 풀 리퀘스트로 바꾼다. 품질이 받아들일 수 없는 수준으로 떨어지는 것을 막는다.
  • 기준선은 판정을 통과한 실행이 --update-baseline으로 적는다. 합격선 위에서 조금씩 나빠지는 것(조용한 하락의 누적)을 막는다. 판정이 실패하면 기준선을 적지 않으므로 회귀가 기준선을 덮어쓰지 못한다.
  • 최소 반복(min_runs)은 한 번의 운 좋은 실행으로 통과하는 것을 막는다.
  • 능력 문항 제외(골든 세트의 suite 칸)는 늘 실패하는 문항 때문에 경보가 무시되는 것을 막는다.

refusal의 합격선이 1.00인 것에 주목한다. 범위 밖 질문에 답을 지어내는 일은 한 번도 허용하지 않는다는 뜻이다. 합격선은 기준마다 그 실수의 무게에 맞추어 정한다. 종료 코드는 셋이다. 0은 합격, 1은 회귀, 2는 판정할 수 없음(파일이 없거나 반복이 모자람)이다. 13장의 CI는 0이 아니면 병합을 막으므로 2도 막는다. 「판정할 수 없음」을 「합격」으로 처리하지 않는 것이 핵심이다.

  • 비용: 모의 모델은 없다. 실제 모델은 생성과 판정의 토큰 비용이 든다.
  • 재현: 모의 모델은 같은 조건이면 같은 점수가 나온다. 실제 모델은 같은 조건이어도 점수가 흔들리므로 반복과 구간이 필요하다.
  • CI(13장): 모의 모델은 키 없이 돌며 판정 절차와 채점기의 회귀를 잡는다. 실제 모델은 키가 있어야 하고, 비용 때문에 프롬프트·모델을 바꾸는 풀 리퀘스트에만 돌린다.

11-10. 복기: 「바꾸어도 되는가」를 종료 코드로 답하였다

핵심 실습은 판본 하나를 만들어 내보내기까지의 판단을 기계가 다시 할 수 있는 절차로 남겼다.

  1. 보지 않던 범위를 먼저 채웠다. 채점기 하나를 더하자 출력이 같은데도 v1의 점수가 0.77에서 0.59로 내려갔다. 점수는 채점기가 본 범위 안의 품질이다.
  2. 비교 한 번으로 회귀를 찾았다. 전체 점수는 올랐으나 기준별 표에서 판정이 0.94에서 0.76으로 내려갔고, 판정 이유를 세자 원인이 문장 하나로 좁혀졌다.
  3. 고치고 재었다. 그 회귀를 겨눈 규칙 4를 더하고, v2와의 짝지은 차이가 0보다 큰 것(+0.070~+0.330)을 확인한 뒤에야 「낫다」고 썼다.
  4. 판정기가 회귀를 막는지 시험하였다. 규칙을 지운 판본이 종료 코드 1을 냈다. 실패를 내 본 적 없는 검사는 검사인지 알 수 없다.
  5. 성공률과 비용을 함께 보고하였다. 관측 보고는 서비스, LLM 호출, 루프, 멀티 에이전트, 평가를 한 문서에 모으고, 평가 보고는 아는 것과 확인하지 못한 것을 나누어 적었다.

정리

  • LLM 기능은 코드를 고치지 않아도 프롬프트, 모델, 자료가 바뀌면 조용히 나빠진다. 테스트는 형식을, 평가는 출력의 내용을 지킨다.
  • 골든 세트는 대표 문항과 경계 문항으로 만들고, 기대값의 형식(정확한 값, 참조 목록, 금지 목록, 기준표)이 채점 방식을 정한다. 회귀 문항과 능력 문항을 나누어, 회귀 판정은 통과해야 할 문항으로만 한다.
  • 채점은 정확 일치, 구조 검사, 규칙, 참조 기반으로 잡을 수 있는 것을 먼저 잡고, 남는 기준(지어냄, 왜곡)만 LLM 판정에 맡긴다. 채점기가 보지 않는 결함은 점수에 나오지 않는다.
  • LLM 판정자는 위치, 길이, 자기 선호의 편향이 있다. 기준표, 순서 바꾸기, 다른 모델, 사람 표본 대조(코언의 카파)로 줄이고 잰다.
  • 비결정적인 기능은 같은 입력을 여러 번 돌려 통과율과 표준오차로 말하고, 두 판본은 짝지은 차이로 비교하되 전체 점수보다 기준별 표를 먼저 읽는다. 회귀 판정은 합격선과 기준선을 보고 종료 코드(0, 1, 2)로 답하며, 판정기는 실패를 내 보아야 믿는다.
  • 관측은 지연, 트래픽, 오류, 포화를 보고, 기록에는 요청 번호, 프롬프트 판본, 모델, 토큰, 지연, 오류, 도구 호출을 구조화해 남긴다. 에이전트는 작업 성공률(무엇을 성공으로 세는가부터), 사람 개입, 성공 1건당 비용으로 평가한다.
  • Claude Code의 비용은 /usage, 헤드리스 결과의 total_cost_usd, OpenTelemetry로 본다. 모두 추정이며, 원격 측정 설정은 저장소가 아니라 사용자·관리 설정에 둔다. 예산은 층마다 두고, 기록에는 내용 대신 크기를 남긴다.

개념 점검

  1. 요약 기능의 pytest -q가 모두 통과하는데도 프롬프트를 v1에서 v2로 바꾸면 품질이 나빠질 수 있다. 기준 저장소의 모의 모드가 이 변화를 잡지 못하는 까닭을 설명하라.
  2. 「범위 밖 질문을 거절한다」를 평가하는 골든 세트에 답할 수 있는 질문도 넣어야 하는 까닭은 무엇인가. 기준값에 가까운 범위 밖 질문(A09)을 따로 두는 까닭은 무엇인가.
  3. 3-4에서 채점기 하나를 더하자 v1의 회귀 통과율이 0.77에서 0.59로 떨어졌다. 기능이 나빠진 것인가. 이 결과가 평가 점수의 뜻에 대해 알려 주는 것은 무엇인가.
  4. 모의 판정자의 기준값을 0.45에서 0.25로 낮추어도 카파가 0.17로 그대로였다. 왜 그런가. 실제 LLM 판정자를 쓸 때 같은 표본 대조를 하는 까닭은 무엇인가.
  5. 시행 하나의 성공률이 0.9인 기능을 같은 사용자가 세 번 쓴다. 세 번 모두 성공할 확률은 얼마인가. 이 기능에 pass@k와 pass^k 가운데 어느 관점이 맞는가.
