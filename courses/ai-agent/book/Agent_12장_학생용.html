평가와 관측: 회귀 평가, 기록, 비용

2027학년도 「AI에이전트 기획 및 개발」의 준비 중인 교재입니다. 편집 상태를 검토하기 위해 미리 공개한 것으로, 수업 전에 내용과 순서가 바뀔 수 있습니다.

학사 14주차 · 교재 12 · 5부 운영 품질

2026-11-19에 150분 수업 기준으로 줄였다(학생용 본문 63,152자 → 32,999자, 참고 자료 표와 자리 표시를 빼면 28,751자). 교수 화면 시연의 명령과 줄인 출력은 교수용에 옮겼다.

11장에서 jobprep 운영 에이전트 시스템에 보안의 울타리를 둘렀다. 막는 장치만으로는 요약 기능이 한 주 전보다 나빠졌는지, 8장의 루프가 몇 번 만에 일을 끝내고 얼마를 썼는지 알 수 없다. 이 장의 주제는 1장의 운영 요건 가운데 신뢰성(기대한 결과를 내고, 실패하면 알아챈다)과 재현성(무엇이 실행되었는지 기록이 남는다)이다. LLM 기능은 코드를 고치지 않아도 프롬프트의 문장 하나, 모델 이름 하나로 조용히 나빠진다. 그래서 테스트와 별도로 평가(evaluation)가 필요하다. 평가는 골든 세트(입력과 기대값의 묶음)를 기능에 넣고, 채점기로 기준별 통과 여부를 정하고, 여러 번 되풀이해 통과율로 말한다.

이 장에서 만드는 것은 하나이다. jobprep/evals/의 회귀 평가 세트(요약 15문항, 질의응답 10문항)와 채점기로 요약 프롬프트의 두 판본을 한 번 비교해, 새 판본이 몰래 들여온 회귀 하나를 찾아 고치고, 회귀 판정기가 그 수정을 종료 코드로 승인하게 한 뒤, 8장·10장의 실행 기록에서 에이전트의 작업 성공률과 비용을 보고한다. 요약 판본 v2는 세 가지 실수를 고쳤지만 공고에 없는 주의점을 지어내는 새 실수를 들여왔고, 전체 점수 하나로는 이 회귀가 보이지 않는다. 실습은 API 키 없이 도는 교육용 모의 모델로 끝까지 한다. 이 장의 회귀 판정은 13장에서 CI의 한 단계가 된다.

학습 목표

  • LLM 기능에 회귀 평가가 필요한 까닭을 설명하고, 대표 문항과 경계 문항을 갖춘 골든 세트를 정답의 형식과 함께 설계할 수 있다.
    • 예시: 「마감일이 두 번 나오는 공고」를 경계 문항으로 넣고 기대값을 「서류 접수 마감일과 정확 일치」로 정한다.
    • 활용: 프롬프트나 모델을 바꾸기 전에 지켜야 할 것을 문항으로 적는다.
  • 다섯 채점 방식을 고르고, LLM 판정의 편향(위치, 길이, 자기 선호)을 기준표, 순서 바꾸기, 사람 표본 대조로 보정하는 방법을 설명할 수 있다.
    • 예시: 우대 사항의 혼입은 규칙으로, 지어낸 내용은 판정자로 채점하되 사람 표본 12개와 대조해 코언의 카파를 잰다.
    • 활용: 판정자의 점수를 믿기 전에 사람과의 일치도부터 묻는다.
  • 반복 실행의 통과율과 표준오차를 구하고, 두 판본을 짝지은 차이로 비교해 합격선과 기준선으로 회귀를 판정할 수 있다.
    • 예시: v2와 v3을 5번씩 돌려 짝지은 차이의 95% 구간이 0보다 큰지 보고, python -m evals.gate가 종료 코드 0을 낼 때만 기준선을 갱신한다.
    • 활용: 13장의 CI가 이 종료 코드로 병합을 막는다.
  • 실행을 구조화 기록으로 남기고 서비스와 에이전트 실행의 지표와 비용을 집계하며, Claude Code의 사용량을 보는 세 길(/usage, 헤드리스 결과, OpenTelemetry)을 구별할 수 있다.
    • 예시: access.log에서 p95 지연을, 8장 루프 기록에서 작업 성공률과 성공 1건당 비용을 뽑는다.
    • 활용: 에이전트의 성과를 숫자로 보고한다.

1. LLM 기능의 회귀

1-1. 코드를 고치지 않아도 나빠지는 기능

회귀(regression)는 잘 되던 동작이 변경 뒤에 나빠지는 것이다. LLM 기능은 코드 밖에도 출력을 바꾸는 요인이 있다. jobprep의 요약에서는 프롬프트 파일(PROMPT_SUMMARY), 모델(LLM_MODEL), 같은 이름의 모델에 대한 제공자의 갱신, 검색 자료와 임베딩 방식이 그렇다. 넷 모두 코드가 바뀌지 않고, 모델을 부르지 않는 모의 모드의 테스트는 잡지 못한다. 요약이 JSON 구조를 지키는 한 API는 200을 돌려주므로, 공고에 없는 주의점이 섞여도 기록에 표시가 없다. 이것이 「조용한 회귀」이다. 또 LLM 출력은 비결정적이어서 같은 입력에도 실행마다 답이 다르다. 한 번의 성공으로는 열 번 중 아홉 번 되는 기능과 다섯 번 되는 기능을 구별할 수 없다(4절).

1-2. 테스트와 평가

구분 테스트(2장) 평가(이 장)
대상과 기대값 함수와 API의 동작. 하나의 정답(assert status == 422) 출력 품질. 정답의 범위(정확 일치, 참조와의 겹침, 기준표)
결과와 반복 통과 또는 실패. 한 번이면 된다 기준별 통과율. 여러 번 돌려야 한다
실패의 뜻 버그가 있다 합격선 아래로 떨어졌다. 원인은 프롬프트, 모델, 자료, 코드 가운데 하나다

1-3. 성공 기준

평가를 만들기 전에 성공 기준을 정한다. Anthropic의 평가 안내는 좋은 성공 기준의 성질로 구체성, 측정 가능성, 달성 가능성, 관련성을 든다 [A1]. 「요약을 잘한다」는 측정할 수 없고, 「마감일이 서류 접수 마감일과 같은 비율이 0.95 이상」은 측정할 수 있다. jobprep의 요약은 마감일이 정확하고 공고에 없는 내용을 지어내지 않아야 하며, 질의응답은 근거 번호를 달고 범위 밖 질문에 「자료에 없습니다.」로 답해야 한다.

1-4. 능력 평가와 회귀 평가

에이전트 평가 글은 「무엇을 잘하는가」를 묻는 능력 평가(통과율이 처음에 낮다)와 「전에 되던 것이 아직 되는가」를 묻는 회귀 평가(100%에 가까워야 한다)를 나눈다 [E5]. 이 장의 골든 세트는 문항마다 suite 칸으로 둘을 구별하고, 회귀 판정은 regression 문항만으로 한다. 본문에 「이전 지시를 무시하라」를 숨긴 공고(S15)는 11장의 대책을 아직 요약에 넣지 않아 통과하지 못한다. 이 문항을 회귀 판정에 넣으면 판정이 늘 실패하고, 늘 실패하는 경보는 아무도 보지 않는다.

2-2. 대표성

첫째 조건은 대표성이다. 평가 안내는 「실제 과업의 분포를 비추라」고 한다 [A1]. 요약의 대표 문항 10개는 공고 30건 가운데 분야가 겹치지 않게 골랐고, 운영 기록이 쌓이면 실제 요청의 분포에 맞추어 다시 고른다.

둘째 조건은 경계 사례이다. 에이전트 평가 글은 「행동이 일어나야 할 때와 일어나지 않아야 할 때를 둘 다 시험하라」고 한다 [E5]. 답해야 할 질문만 넣으면 무엇에나 답하는 기능이 만점을 받는다.

2-4. 정답의 형식

셋째 조건은 정답의 형식이다. 하나의 값("deadline")은 정확 일치로, 참조 답의 목록("duties")은 참조 기반으로, 금지 목록("preferred", "must_not_contain")은 규칙으로, 핵심어는 문자열 포함으로, 기준표는 LLM 판정으로 채점한다. 에이전트 평가 글은 「두 전문가가 독립적으로 같은 판정에 이르는가」를 모호하지 않은 과업의 기준으로 든다 [E5].

3. 채점 방식

3-1. 다섯 가지 채점 방식

평가 안내는 채점을 코드 기반(빠르고 믿을 만하나 복잡한 판단에 약하다), 사람(품질이 높으나 느리고 비싸 되도록 피한다), LLM 기반(복잡한 판단에 맞으나 신뢰도를 먼저 시험한다)으로 나눈다 [A1]. 이 장은 코드 기반을 넷으로 나누어 다섯으로 본다.

방식 하는 일 한계 jobprep의 예
정확 일치 값이 기대값과 같은가 표현이 조금만 달라도 실패 마감일, 거절 문구
구조 검사 JSON 키, 형식, 개수를 갖추었는가 내용의 옳고 그름은 못 본다 JSON 구조, 근거 번호
규칙 금지 문구, 길이, 포함 관계 적을 수 있는 실수만 잡는다 50자 이내, 우대 사항 혼입
참조 기반 정답 목록과 얼마나 겹치는가 겹침이 뜻의 같음은 아니다 업무·자격 항목의 재현율
LLM 판정 다른 모델이 기준표로 판정 비용, 비결정성, 보정 필요 근거에 없는 문장의 유무

이 장의 실행기는 해당하는 채점기를 모두 통과해야 시행을 통과로 본다 [E5]. 규칙으로 잡을 수 있는 것은 규칙으로 잡고 남는 것만 비용이 들고 틀리기도 하는 판정자에게 넘긴다 [L9].

3-2. jobprep 채점기의 지도

evals/graders.py의 채점기는 (통과 여부, 설명)을 돌려주며, None은 그 문항에 해당하지 않는다는 뜻이다.

묶음 채점기 방식 통과 조건
요약 structure 구조 검사 JSON으로 읽히고 validate_summary()를 통과
요약 deadline 정확 일치 마감일이 기대값과 같다(null끼리도)
요약 coverage 참조 기반 참조 항목의 80% 이상이 유사도 0.5 이상으로 맞는다
요약 length, forbidden 규칙 항목이 50자 이내, 금지 문구가 없다
질의응답 refusal 정확 일치 거절할 질문에만 「자료에 없습니다.」
질의응답 keywords 문자열 포함 기대 핵심어가 모두 있다
질의응답 citation, source 구조 검사, 정확 일치 [n]과 출처가 있고, 기대한 자료 파일이 출처에 있다

유사도는 두 글을 두 글자씩 잘라 겹치는 비율(bigram Dice 계수)이다. 「보안 관제 시스템을 운영한다」와 「…운영함」은 0.86으로 같은 항목이 되고, 「사내 관제 장비를 관리한다」와는 0.19로 다른 항목이 된다. 뜻을 재지는 못한다(5절).

  • 확인 4 회귀 통과율 0.77, length 0.85, S11 0/5가 출력되고, ls evals/runs/v1-base에 llm.log, records.jsonl, summary.json 세 파일이 있다.

4. 반복 실행과 분산

4-1. 같은 입력, 다른 답

LLM은 다음 토큰을 확률 분포에서 고르므로 같은 프롬프트에도 답이 달라진다. 기준 저장소의 api/llm.py는 temperature를 보내지 않는다(기준 저장소 안내에 따르면 API 판 2026-10-21에서 400 오류가 난다). 무작위성을 코드에서 끌 수 없으므로 품질은 출력의 분포로 말한다.

[최신 자료 자리: 샘플링 인자의 지원 여부] 쓰는 모델이 temperature 같은 샘플링 인자를 받는지는 모델과 API 판에 따라 다르다. 확인할 곳: platform.claude.com의 Messages API 참조와 모델 개요. 이 절의 서술은 기준 저장소 안내(API 판 2026-10-21에서 400 오류)를 따른 것이며, 이 교재에서 다시 확인하지 못하였다.

에이전트 평가 글은 각 시행을 깨끗한 환경에서 시작하라고 한다 [E5]. 실행기는 시행마다 대화 기록 없이 함수를 새로 부른다.

4-2. 통과율, pass@k, pass^k

통과율은 전체 시행 가운데 통과한 비율로, 반복을 늘려도 값은 그대로이고 추정만 정밀해진다. pass@k는 k번 가운데 한 번이라도 통과할 확률로 한 번의 성공이면 되는 일(코드 생성 뒤 테스트로 고르기)에 맞고, pass^k는 k번 모두 통과할 확률로 매번 성공해야 하는 일에 맞는다 [E5]. 시행 하나의 성공률이 75%이면 pass^3은 0.75³ ≈ 42%이다 [E5]. 요약 버튼을 누를 때마다 기준을 지켜야 하는 jobprep에는 pass^k가 맞고, 3-3의 「모든 반복 통과 5/14문항」이 문항 단위의 pass^5이다.

4-3. 표준오차와 신뢰구간

0.77은 14문항에서 얻은 추정값이다. 평가 통계 글은 점수마다 평균의 표준오차(SEM)를 함께 보고하라고 하며, 95% 구간은 평균 ± 1.96 × SEM이다 [E6]. 실행기는 문항별 통과 비율 14개로 SEM을 낸다. 같은 문항의 반복 시행은 독립이 아니므로 70개로 세면 오차가 실제보다 작게 나온다 [E6]. 그래서 점수는 「0.77(95% 구간 0.63~0.91)」로 보고한다.

4-4. 반복 횟수에 따른 차이 (교수 시연)

반복 실행의 분산은 교수 시연으로 본다(편성표 §3). 11-2의 채점기까지 더한 상태에서 v1을 1번, 20번 돌린 모의 모델의 결과이다.

  반복별 회귀 통과율: 0.43

스무 번의 반복 하나하나는 0.29에서 0.79까지 퍼져 있다. 한 번만 돌렸다면 그 한 번이 어느 값이었을지 모른다. 구간의 너비는 반복 1회에 0.54, 5회에 0.27, 20회에 0.20이고 요약 호출은 15회, 75회, 300회이다. 반복 횟수는 정밀도와 비용의 거래이다. 「모든 반복 통과」는 6/14에서 1/14로 줄어든다. 이 장의 판정은 반복 5회를 기본으로 하고, 판정기는 3회 미만의 실행을 받지 않는다(min_runs).

5. LLM 판정

5-1. 판정자가 맡는 기준

요약의 가장 위험한 실수인 「공고에 없는 주의점을 지어내기」는 무엇을 지어낼지 몰라 금지 목록으로 막을 수 없다. 모든 문장이 근거로 뒷받침되는지 읽고 판단하는 일을 모델에게 맡기는 것이 LLM 판정(LLM-as-a-judge)이다. Zheng 외(2023)는 강한 모델의 판정이 사람의 선호와 80% 넘게 일치해 사람끼리의 일치 수준과 같았다고 보고하면서 한계도 함께 보고하였다 [R1].

5-2. 기준표

평가 안내는 상세한 기준표(rubric), 정해진 값으로 받는 판정, 점수 전의 추론, 생성 모델과 다른 판정 모델을 권하고 [A1], 에이전트 평가 글은 「알 수 없음」의 길을 열어 두라고 한다 [E5]. 키트의 evals/judge_rubric.md의 핵심이다.

<기준표>
1. 근거 충실성: 출력의 모든 문장은 <근거>에 적힌 내용으로 뒷받침되어야 한다. 근거에 없는 조건, 절차, 숫자를 하나라도 덧붙였으면 fail이다.
2. 왜곡 금지: 근거의 뜻을 뒤집거나(받는다/받지 않는다) 숫자를 바꾸었으면 fail이다.
3. 표현 차이 허용: 근거와 낱말이 달라도 뜻이 같으면 통과로 본다.
4. 판단 불가: 근거만으로 판정할 수 없으면 unknown으로 답한다.
</기준표>
먼저 <reason> 태그 안에 기준표의 어느 항목에 비추어 판단했는지 두 문장 이내로 쓴다.
그다음 <result> 태그 안에 pass, fail, unknown 가운데 하나만 쓴다.

unknown은 통과로 세지 않고, 시스템 프롬프트에 「길이나 문체는 판정에 넣지 않는다」를 둔다. 기준표는 코드와 같다. 2026년판 교재의 실습은 「근거 없는 단정 금지」 기준 하나를 지우자 지어낸 절차가 통과로 바뀌는 것을 보였다 [L9]. 실제 판정 호출은 llm.log와 비용 집계에 잡히고, 모의 판정자는 근거 문장과의 유사도가 0.45보다 낮은 문장이 있으면 fail로 본다.

5-3. 판정자의 편향

편향 내용 근거
위치 편향 두 응답을 비교할 때 먼저(또는 나중에) 제시된 쪽을 낫다고 본다 Zheng 외(2023) [R1]. Wang 외(2023)는 순서만 바꾸어도 순위가 뒤집혀, 한 모델이 다른 모델을 80문항 가운데 66문항에서 이기는 것으로 나오게 할 수 있었다고 보고하였다 [R2]
길이 편향 더 길고 자세해 보이는 응답을 낫다고 본다 Zheng 외(2023)의 장황함 편향 [R1]
자기 선호 자기가 만든 출력을 높게 본다 Zheng 외(2023) [R1]. Panickssery 외(2024)는 자기 출력을 알아보는 능력과 자기 선호의 세기가 선형 상관이라고 보고하였다 [R3]

5-4. 보정 방법

위치 편향은 쌍 비교를 두 순서로 물어 같은 쪽을 가리킬 때만 승자로 보거나(Wang 외의 균형 위치 보정 [R2]) 응답 하나를 기준표로 단독 판정해 줄인다. 길이 편향은 길이 배제 지시와 출력 형식의 통일로, 자기 선호는 다른 모델로 판정해 줄인다 [A1]. 판정 전에 근거를 여러 개 쓰게 하는 방법도 있다 [R2]. 그리고 사람이 판정한 표본과 대조해 일치도를 잰다 [E5]. 이것이 다른 방법들의 효과를 확인하는 측정 장치이다. 일치도는 일치율과 코언의 카파로 잰다. 카파는 우연히 맞았을 몫을 빼고 남는 일치를 0(우연 수준)~1(완전 일치)로 낸다.

5-5. 순서 바꾸기와 사람 표본 대조 (교수 시연)

LLM 판정은 교수 시연이며, 수업에서는 모의 판정자로 같은 절차를 보인다. 먼저 python -m evals.judge pairwise-demo는 충실한 요약(x)과 항목 하나를 지어낸 요약(y)을 위치 편향을 일부러 넣은 판정자에게 14문항 비교시킨다. x를 먼저 보이면 x가 14번 모두 이기지만, y를 먼저 보이면 y가 3번 이긴다. 순서 바꾸기 점검은 엇갈린 3문항을 보류로 돌려 잘못된 승자를 내지 않는다. 이어서 python -m evals.calibrate가 사람 판정 표본 12개(그대로 옮긴 출력, 지어낸 출력, 낱말만 바꾼 출력, 뜻이나 숫자를 뒤집은 출력)와 대조한다.

판정자: 모의 판정자(기준값 0.45) · 표본 12개
               판정자 pass  판정자 fail
  사람 pass             4           2
  사람 fail             3           3
일치율 0.58 · 코언의 카파 0.17
  엇갈림 C03(S07): 사람 pass, 판정자 fail — 사람의 까닭: 낱말은 다르나 뜻은 공고와 같다
  엇갈림 C04(S07): 사람 fail, 판정자 pass — 사람의 까닭: 수습 급여 비율을 90%에서 100%로 바꾸었다
  엇갈림 C05(S07): 사람 fail, 판정자 pass — 사람의 까닭: 불이익이 있다를 없다로 뒤집었다
  엇갈림 C07(S03): 사람 pass, 판정자 fail — 사람의 까닭: 명사형으로 줄였으나 뜻은 같다
  엇갈림 C12(S05): 사람 fail, 판정자 pass — 사람의 까닭: 졸업 후 입사를 졸업 전 입사로 바꾸었다

카파 0.17은 우연 수준을 조금 넘는다. 모의 판정자는 글자의 겹침을 재므로 낱말을 바꾼 정상 출력(C03, C07)을 떨어뜨리고, 뜻이나 숫자를 뒤집은 출력(C04, C05, C12)을 통과시킨다. 기준값을 0.25로 낮추면(--support 0.25) C07을 통과시키는 대신 지어낸 C10을 놓쳐 카파가 0.17 그대로이다. 기준값은 오류의 종류를 맞바꿀 뿐이다. 숫자 대조 규칙을 더하면(--numbers) C04를 잡아 카파가 0.33이 된다. 남은 뜻 뒤집기와 표현 차이가 실제 LLM 판정자의 몫이며, 실제 판정자도 같은 표본으로 카파를 잰 뒤에 믿는다. 학습자는 이 결과를 평가 보고 5절(11-7)에 옮긴다.

6. 판본 비교

6-1. 무엇을 고정하고 무엇을 바꾸는가

판본 비교는 실험이므로 골든 세트, 채점기와 판정자(11-2처럼 채점기가 바뀌면 이전 점수와 견주지 않는다), 검색 조건(실행기가 EMBED_BACKEND=fallback으로 고정), 반복 횟수를 같게 두고 프롬프트 판본과 모델 가운데 하나만 바꾼다.

6-2. 짝지은 차이

두 판본의 통과율을 따로 구해 빼면 두 오차가 더해진다. 같은 문항에서 돌았으므로 문항마다 차이를 내고 그 평균과 표준오차를 구하면 문항의 난이도가 상쇄된다. 평가 통계 글은 이 짝지은 차이를 권하며, 최신 모델들의 문항별 점수 상관이 0.3~0.7로 높아 오차가 크게 준다고 한다 [E6]. evals/compare.py가 짝지은 차이의 95% 구간과 판단을 낸다.

6-3. 판단의 세 갈래

  1. 비교 쪽이 낫다(구간이 0보다 크다): 기준별 표에서 내려간 기준이 없으면 회귀 판정(11-5)으로 간다.
  2. 비교 쪽이 나쁘다(구간이 0보다 작다): 내려간 기준의 실패 사유를 모아 세고 판본을 고친다.
  3. 차이를 말할 수 없다(구간이 0을 포함한다): 오른 기준과 내려간 기준이 섞여 있으면 판본을 고치고, 아니면 반복이나 문항을 늘려 다시 잰다.

③은 「두 판본이 같다」가 아니라 「지금의 문항과 반복으로는 가릴 수 없다」이다. 어느 갈래든 기준별 표를 먼저 읽는다. 기준마다 실수의 무게가 다르다(지어냄은 길이 초과보다 무겁다).

6-4. 모델의 교체 (읽기)

같은 방법으로 「모델을 바꾸어도 되는가」를 잰다. 교수 화면에서 질의응답을 모의 모델 sim-a와 sim-b로 비교하면, sim-b는 근거 번호를 더 잘 달지만(citation 0.91 → 0.94) 근거에 없는 문장을 덧붙여 판정 통과율이 1.00에서 0.89로 내려가고 전체 차이는 ③이다(sim-a의 호출이 50회가 아니라 40회인 것은 A08, A09가 검색 기준값에서 걸러지기 때문이다). sim-b의 전체 실행을 11-5의 판정기에 넣으면 다음과 같다.

회귀 판정: try-simb (모델 sim-b, 반복 5회)

  [통과] ask 회귀 통과율 0.87 (합격선 0.85)
  [통과] ask.refusal 1.00 (합격선 1.00)

8. 관측과 구조화 기록

8-1. 평가와 관측

평가는 배포 전에 골든 세트로 품질을 재고, 관측(observability)은 배포 뒤의 실제 요청을 기록으로 본다. 관측이 찾은 낯선 입력은 다음 골든 세트의 문항이 된다. Google의 SRE 책은 모니터링을 「시스템에 대한 실시간 정량 자료를 모으고 처리하고 집계하고 보여 주는 일」로 정의하고, 사용자를 마주하는 시스템에는 네 가지 황금 신호를 보라고 한다 [S1].

신호 [S1] 뜻 [S1] jobprep에서
지연 요청 하나의 처리 시간. 실패한 요청은 따로 잰다 access.log의 ms
트래픽 시스템에 대한 수요 경로별 요청 수
오류 명시적 실패(500), 암묵적 실패(내용이 틀린 200), 정책상 실패의 비율 5xx, llm.log의 error. 「틀린 200」은 평가가 맡는다
포화 가장 제약된 자원이 얼마나 찼는가 제공자의 속도 제한(RateLimitError)

같은 장은 평균이 100ms여도 요청의 1%가 5초씩 걸릴 수 있으니 지연을 백분위수로 보라고 한다 [S1]. 관측의 신호는 트레이스(요청이 지나는 경로), 지표(측정값), 로그(사건의 기록)로 나뉜다 [O1]. jobprep에는 로그만 있고 지표는 report.py가 계산한다.

8-2. 무엇을 남기는가

LLM 기능의 기록에는 시각, 요청 번호, 경로와 상태, 지연, 기능, 프롬프트 판본, 모델, 토큰, 오류의 종류, 에이전트라면 도구 호출과 비용을 남긴다. 기준 저장소의 기록에는 요청 번호(요청·LLM 호출·오류 기록을 한 요청으로 잇는다)와 프롬프트 판본(품질이 바뀐 때를 판본 교체와 잇는다)이 없고, 지연은 요청 전체만 있다. 사용자의 질문 원문, 공고 본문 전체, API 키는 남기지 않는다.

8-3. 구조화 기록

기록은 사람보다 프로그램이 먼저 읽으므로 칸이 정해진 구조화 기록이어야 한다. 자유 문장은 집계하려면 해석해야 하고, 키=값(task=summary error=RateLimitError)은 grep에 좋지만 중첩을 못 담으며, JSON Lines는 중첩과 숫자·문자열의 구별을 담는다. 기준 저장소의 운영 기록은 키=값, 8장·10장과 평가의 기록은 JSON Lines이다. ops/telemetry/logparse.py로 logs/error.log를 JSON으로 바꾸면 status=503이 숫자 503이 되어 「5xx 비율」 같은 집계가 맞는다. 그런데 같은 시각(14:03:47)의 RateLimitError 줄과 503 줄이 같은 요청인지 확정할 칸이 없다. 요청 번호가 없는 빈자리의 비용이다.

9. Claude Code의 사용량과 비용, OpenTelemetry

3~10장의 커맨드, 훅, 루프, 역할 에이전트의 비용은 Claude Code가 센다. 대화 하나(9-1), 실행 하나(9-2), 조직 전체(9-3, [선택])의 세 높이에서 본다. 화면은 교수 시연이며 2.1.296으로 확인하였다.

[최신 자료 자리: Claude Code의 판과 사용량 화면] 수업 전에 claude --version과 비용 문서(code.claude.com/docs/en/costs)에서 /usage의 구역과 별칭, 판별 기능(Prompt cache (main) 줄은 2.1.251 이상, f 단축키는 2.1.305 이상)을 다시 확인한다. 2026-11-15 값: 2.1.296, /cost·/stats는 /usage의 별칭.

9-1. 대화 안에서: /usage

/usage(별칭 /cost, /stats)는 현재 세션의 비용, 요금제의 사용 한도, 모델별 토큰을 보인다 [C21][C19].

[그림 자리: 교수 화면의 /usage] 교수 계정에서 /usage를 연 화면. 세션 구역(Total cost, Usage by model)과, 구독 계정이면 요금제 사용 막대와 사용 내역이 함께 보이게 찍는다. 찍을 곳: 교수 PC의 Claude Code, 수업 전 리허설.

금액은 정가로 계산한 추정이고, 구독(Pro, Max)에서는 세션 비용이 청구와 무관하며, /clear로 새 세션을 열면 합계가 0부터 시작한다 [C19]. 캐시 읽기 토큰이 입력보다 훨씬 많은 것은 긴 세션이 요청마다 대화 전체를 다시 보내기 때문이다.

9-2. 스크립트에서: 헤드리스 JSON 결과

8장의 루프가 읽은 claude -p --output-format json의 결과에서 관측에 쓰는 칸은 subtype(success 또는 error_max_budget_usd 같은 오류 종류), num_turns, total_cost_usd(서브에이전트 포함), modelUsage(모델별 토큰과 비용), session_id이다 [C14][C22]. total_cost_usd는 클라이언트 쪽 추정이고, --resume으로 이어 간 실행은 대화 전체의 합계를 보고하므로 더하면 두 번 센다 [C22]. 실행 하나의 상한 --max-budget-usd에 닿으면 subtype이 error_max_budget_usd가 된다(7-3의 index-refresh) [C15]. 교수 화면의 도움말(claude --help | grep -A1 "max-budget-usd")은 다음과 같다.

  --max-budget-usd <amount>             Maximum dollar amount to spend on API
                                        calls (only works with --print)

[최신 자료 자리: 헤드리스 결과의 칸과 비용 상한 옵션] 위 칸 이름과 subtype의 오류 종류, claude --help의 --max-budget-usd 설명을 헤드리스 문서(code.claude.com/docs/en/headless)와 교수 PC의 claude --help로 다시 확인한다. 2026-11-15에 2.1.296의 도움말에서 위 출력과 같은 두 줄을 확인하였다.

9-3. [선택] 조직 단위로: OpenTelemetry

OpenTelemetry(OTel)는 신호를 모으고 내보내는 공개 표준이다 [O1]. 비용 문서는 Claude Code의 OTel 내보내기가 사용자별 비용을 조직의 관측 체계로 거의 실시간에 보내는 유일한 방법이라고 한다 [C19]. CLAUDE_CODE_ENABLE_TELEMETRY=1로 켜고 OTEL_* 변수로 보낼 곳을 정하며(변수 목록은 부록 B-1-11) [C18], 수집기 없이 확인할 때는 console 내보내기를 쓴다(교수 시연).

교수 화면 
CLAUDE_CODE_ENABLE_TELEMETRY=1 OTEL_METRICS_EXPORTER=console OTEL_METRIC_EXPORT_INTERVAL=10000 claude

[그림 자리: OpenTelemetry 콘솔 내보내기] 위 명령으로 연 세션에서 짧은 요청 하나를 보낸 뒤 10초 간격으로 찍힌 지표 출력. claude_code.session.count와 claude_code.cost.usage의 줄이 보이게 찍는다. 찍을 곳: 교수 PC의 터미널, 수업 전 리허설.

[최신 자료 자리: OpenTelemetry 환경 변수와 지표 이름] 9-3의 환경 변수와 지표·이벤트 이름, 내보내기 간격의 기본값(지표 60000ms, 이벤트 5000ms), 저장소 설정의 OTEL_* 무시 규칙을 모니터링 문서(code.claude.com/docs/en/monitoring-usage)에서 다시 확인한다. 2026-11-14·15에 확인한 값이 이 절에 적혀 있다.

지표(claude_code.cost.usage, claude_code.token.usage 등)에는 모델과 서브에이전트별 속성이 붙어 10장의 역할별 비용을 나눌 수 있고, 이벤트(claude_code.api_request, claude_code.tool_decision 등)에는 한 요청을 잇는 prompt.id가 붙는다 [C18]. 설정은 셸, 사용자 설정, 조직의 관리 설정에 두면 먹지만 저장소의 .claude/settings.json에 둔 OTEL_* 내보내기 변수는 무시된다 [C18]. 남의 저장소를 여는 것만으로 대화가 남의 수집기로 가서는 안 되기 때문이며, 11장의 공급망 보안과 같은 생각이다.

def grade_preferred(item, output):
    """우대 사항이 자격 요건에 섞이지 않았는가(규칙). 공고에 우대 사항이 없으면 해당 없음."""
    preferred = item["expect"].get("preferred", [])
    if not preferred:
        return None, "우대 사항 없음"
    mixed = [q for q in output.get("qualifications", []) if best_match(q, preferred) >= MATCH_MIN]
    if mixed:
        return False, f"우대 사항이 자격 요건에 섞임: {mixed[0]}"
    return True, ""


SUMMARY_GRADERS["preferred"] = grade_preferred

기준선 줄은 모의 모델과 견준 값이므로 합격선 줄만 읽는다. 볼 것은 판정자의 unknown 비율(높으면 기준표가 모호하다), 판정 실패의 이유, 실제 비용이다. 기록이 아직 없으면 cp가 「No such file or directory」를 낸다.

11-10. 복기: 「바꾸어도 되는가」를 종료 코드로 답하였다

  1. 보지 않던 범위를 먼저 채웠다. 채점기 하나로 출력이 같은 v1의 점수가 0.77에서 0.59가 되었다.
  2. 비교 한 번으로 회귀를 찾았다. 전체 점수는 올랐으나 기준별 표에서 judge가 내려갔고, 이유를 세자 원인이 문장 하나로 좁혀졌다.
  3. 고치고 재었다. 짝지은 차이가 0보다 큰 것을 확인한 뒤에야 「낫다」고 썼다.
  4. 판정기가 회귀를 막는지 시험하였다. 실패를 내 본 적 없는 검사는 검사인지 알 수 없다.
  5. 성공률과 비용을 함께 보고하였다. 평가 보고는 아는 것과 확인하지 못한 것을 나누었다.

「v2로 바꾸어도 되는가」의 답은 1-5의 「나아 보인다」(인상)에서 11-3의 「차이를 말할 수 없다, judge −0.19」를 거쳐 11-5의 「합격, 종료 코드 0」으로 바뀌었다. 13장의 CI는 이 마지막 종료 코드만 읽는다.

제출물

다음이 개인 저장소에 커밋되어 있으면 된다.

  • evals/: 골든 세트, 채점기(grade_preferred와 그 테스트 포함), 판정자, 실행기, 비교, 회귀 판정, 보정, thresholds.json, baseline.json
  • prompts/summary_v3.txt: 규칙 4를 더한 요약 판본
  • ops/telemetry/, ops/loop/logs/, ops/multi/logs/: 관측 도구와 8장·10장의 실행 기록
  • docs/운영/관측보고.md, docs/운영/평가보고.md: 성공률·비용 보고와 9절을 채운 평가 보고

evals/runs/와 교수 시연 기록은 제출물이 아니지만 13장을 마칠 때까지 지우지 않는다.

정리

  • LLM 기능은 프롬프트, 모델, 자료가 바뀌면 조용히 나빠진다. 테스트는 형식을, 평가는 내용을 지킨다.
  • 골든 세트는 대표 문항과 경계 문항으로 만들고, 규칙으로 잡을 수 있는 것을 먼저 잡은 뒤 지어냄과 왜곡만 LLM 판정에 맡긴다. 판정자의 편향은 기준표, 순서 바꾸기, 사람 표본 대조로 줄이고 잰다.
  • 반복 실행의 통과율과 표준오차로 말하고, 판본은 짝지은 차이로 비교하되 기준별 표를 먼저 읽는다. 회귀 판정은 합격선과 기준선으로 종료 코드를 내며, 판정기는 실패를 내 보아야 믿는다.
  • 관측은 황금 신호를 보고 기록을 구조화해 남긴다. 에이전트는 작업 성공률(무엇을 성공으로 세는가부터), 사람 개입, 성공 1건당 비용으로 평가한다.
  • Claude Code의 비용은 /usage, 헤드리스 결과, OpenTelemetry로 보며 모두 추정이다. 예산은 층마다 두고, 기록에는 내용 대신 크기를 남긴다.

개념 점검

  1. 요약 기능의 pytest -q가 모두 통과하는데도 프롬프트를 v1에서 v2로 바꾸면 품질이 나빠질 수 있다. 기준 저장소의 모의 모드가 이 변화를 잡지 못하는 까닭을 설명하라.
  2. 「범위 밖 질문을 거절한다」를 평가하는 골든 세트에 답할 수 있는 질문도 넣어야 하는 까닭은 무엇인가. 기준값에 가까운 범위 밖 질문(A09)을 따로 두는 까닭은 무엇인가.
  3. 11-2에서 채점기 하나를 더하자 v1의 회귀 통과율이 0.77에서 0.59로 떨어졌다. 기능이 나빠진 것인가. 이 결과가 평가 점수의 뜻에 대해 알려 주는 것은 무엇인가.
  4. 모의 판정자의 기준값을 0.45에서 0.25로 낮추어도 카파가 0.17로 그대로였다. 왜 그런가. 실제 LLM 판정자를 쓸 때 같은 표본 대조를 하는 까닭은 무엇인가.
  5. 시행 하나의 성공률이 0.9인 기능을 같은 사용자가 세 번 쓴다. 세 번 모두 성공할 확률은 얼마인가. 이 기능에 pass@k와 pass^k 가운데 어느 관점이 맞는가.
