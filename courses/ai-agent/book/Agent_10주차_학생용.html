멀티 에이전트 운영 시스템의 설계: 역할 분담과 병렬 작업

2027학년도 「AI에이전트 기획 및 개발」의 준비 중인 교재입니다. 편집 상태를 검토하기 위해 미리 공개한 것으로, 수업 전에 내용과 순서가 바뀔 수 있습니다.

학사 12주차 · 교재 10 · 4부 멀티 에이전트 운영

1장에서 「jobprep 운영 에이전트 시스템」의 역할을 기획, 구현, 테스트, 검토, 배포, 관측으로 나누어 역할 정의서에 적었다. 그 뒤 2~9장은 그 시스템의 부품을 하나씩 만들었다. 2장의 테스트는 완료 조건이 되었고, 3장의 규칙과 권한은 모든 에이전트가 따르는 공통 규약이 되었으며, 6장의 검토 서브에이전트는 작성자와 다른 맥락에서 변경을 읽는 검토자가 되었다. 7장은 그 부품을 하네스로 조립했고, 8장은 판정과 재시도와 사람 넘김이 있는 루프를 만들었으며, 9장은 그 루프가 API 수준에서 어떻게 도는지 직접 구현했다. 지금까지는 에이전트 하나가 일하고 사람이 그 결과를 판정하는 구조였다.

이 장은 과목의 주축이다. 역할 정의서의 역할들을 실제로 움직이는 역할 에이전트로 만들고, 그 에이전트들이 하나의 이슈를 나누어 맡아 병렬로 일한 뒤 판정을 거쳐 사람의 승인으로 병합되는 운영 시스템을 설계하고 돌린다. 여러 에이전트를 쓰는 일은 에이전트 하나를 쓰는 일보다 언제나 낫지 않다. 토큰이 몇 배로 들고, 에이전트 사이에 정보가 새거나 엇갈리며, 같은 파일을 동시에 고치면 서로의 일을 덮어쓴다. 그래서 이 장의 절반은 「언제 나누는가」와 「나눈 일이 어떻게 충돌하지 않게 하는가」를 다룬다.

이 장에서 만드는 것은 하나다. jobprep의 이슈 ISSUE-07(관심 공고 내보내기 기능과 그 API)을 조정자가 계획서와 작업 카드로 나누고, 구현 에이전트 둘이 각자의 git worktree와 브랜치에서 동시에 구현하고, 테스트 에이전트와 검토 에이전트가 판정한 뒤 사람이 정한 순서로 병합하는 한 바퀴다. 그 과정에서 .claude/agents/의 역할 에이전트 정의(planner, implementer, tester, reviewer), 조정 스크립트 ops/multi/, 설계서 docs/운영/멀티에이전트설계.md, 인계 문서와 실행 기록이 저장소에 남는다. 수업에서는 구현 에이전트 자리에 정답 변경을 적용하는 가짜 에이전트를 넣어 모델 없이도 같은 흐름이 끝까지 돌게 하고, 실제 Claude Code로 바꾸어 넣는 방법을 함께 보인다.

같은 학기 프로젝트실습Ⅱ의 팀은 사람 여럿과 에이전트 여럿이 한 저장소에서 동시에 일한다. 이 장의 작업 분할 기준, worktree와 브랜치 규칙, 인계 문서의 양식, 병합 순서와 충돌 처리는 그 팀 저장소에 그대로 옮겨 쓸 수 있다. 이어지는 11장은 이 시스템의 보안 경계를, 12장은 실행 기록과 비용을, 13장은 이 흐름을 지속적 통합으로 옮기는 일을 다룬다.

학습 목표

  • 작업의 성질을 보고 단일 에이전트와 멀티 에이전트 가운데 무엇을 쓸지 판단하고, 그 판단의 근거를 비용과 실패 유형으로 설명할 수 있다.
    • 예시: 「요약 API의 프롬프트를 고쳐 정확도를 높인다」는 파일 하나에 몰린 순차 작업이므로 에이전트 하나로 하고, 「내보내기 API와 웹 단추를 함께 만든다」는 계약을 정하면 파일이 겹치지 않으므로 둘로 나눈다고 판단한다.
    • 활용: 프로젝트실습Ⅱ에서 팀원과 에이전트에게 일을 나눌 때, 나누어서 얻는 시간과 늘어나는 조정 비용을 같은 표로 비교한다.
  • 역할 정의서의 역할을 Claude Code의 서브에이전트 정의 파일로 옮기고, 역할마다 권한, 도구, 입력, 출력, 완료 조건을 정할 수 있다.
    • 예시: 1장 역할 정의서의 R2 구현을 .claude/agents/implementer.md로 옮기면서 도구를 Read, Grep, Glob, Edit, Write, Bash로 한정하고, 「tests/를 고치지 않는다」를 지시문과 판정 검사 양쪽에 둔다.
    • 활용: 팀의 「역할」을 문서가 아니라 실행되는 정의로 만들어, 누가 실행해도 같은 권한과 형식으로 일하게 한다(운영 요건의 일관성).
  • 계획서, 작업 카드, 결과 보고로 에이전트 사이의 인계를 설계하고, 소유 파일 단위로 작업을 나누어 병렬 작업의 충돌을 계획 단계에서 막을 수 있다.
    • 예시: ISSUE-07을 T1(API: api/export.py, api/main.py)과 T2(웹: web/js/export.js, web/index.html)로 나누고, 둘 다 고치고 싶어 하는 docs/요구사항명세서.md는 조정자가 병합 뒤에 한 번 고치도록 계획서에 적는다.
    • 활용: 대화 기록이 남지 않는 에이전트에게도, 새로 합류한 팀원에게도 같은 카드 한 장으로 일을 넘긴다.
  • git worktree와 에이전트별 브랜치로 작업 공간을 분리해 병렬로 일하고, 판정과 병합 순서와 충돌 처리를 스크립트로 자동화하되 병합은 사람이 승인하게 할 수 있다.
    • 예시: prepare.sh로 .claude/worktrees/issue-07-t1과 -t2를 만들고, run_issue.sh로 두 구현을 동시에 돌려 판정한 뒤, merge.sh ISSUE-07 T1 T2로 T1, T2 순서로 병합한다. 충돌이 나면 스크립트가 병합을 되돌리고 멈춘다.
    • 활용: 13장의 지속적 통합에서 같은 판정(범위, 동결, 테스트, 검토)을 풀 리퀘스트마다 돌린다.

0. 시작하기

실습 서버 접속, 터미널 두 개의 배치, Claude Code 로그인은 부록 A의 절차를 따른다. 이 절은 키트를 받고, 앞 장 산출물을 확인하고, 키트의 파일을 저장소로 옮긴다.

0-1. 키트 받기

서버 터미널 
mkdir -p ~/kits
cp -rn "$KIT_HOME/Agent_10주차" ~/kits/
ls ~/kits/Agent_10주차
README.md  jobprep  기준산출물  양식

mkdir -p ~/kits를 빼고 cp -rn을 실행하면, ~/kits가 없는 계정에서는 키트 폴더 자체가 ~/kits라는 이름으로 복사되어 이 장의 경로가 모두 어긋난다. -n은 이미 있는 파일을 덮어쓰지 않으므로 같은 명령을 다시 실행해도 받아 둔 파일은 그대로다.

0-2. 앞 장 산출물 확인

이 장은 1장의 역할 정의서, 6장에서 만들고 7장에서 규칙을 더한 검토 서브에이전트, 8장의 루프 스크립트를 입력으로 받는다(편성표 §6). 7장에서 조립한 CLAUDE.md와 .claude/settings.json도 모든 역할 에이전트가 따르는 공통 규칙으로 쓰인다. 저장소가 main에 있고 깨끗한지 함께 본다.

서버 터미널 
cd ~/agent-lab/jobprep
git switch main
git status --short
ls CLAUDE.md .claude/settings.json docs/운영/역할정의.md .claude/agents/reviewer.md
ls ops/loop/
Already on 'main'
.claude/agents/reviewer.md  .claude/settings.json  CLAUDE.md  docs/운영/역할정의.md

git status --short가 아무것도 출력하지 않아야 한다. 출력이 있으면 앞 장의 작업을 커밋하거나 git restore로 되돌린 뒤 진행한다. 이 장의 스크립트는 깨끗하지 않은 작업 공간에서 시작하기를 거부한다(7절).

ops/loop/의 logs와 reports는 8장에서 루프를 돌린 학습자에게만 있다. 파일이 없다는 오류가 나면 키트의 기준 산출물을 복사한다. cp -rn은 있는 파일을 덮어쓰지 않으므로, 자기 산출물이 일부라도 있으면 그 파일은 보존되고 빠진 파일만 채워진다. CLAUDE.md와 .claude/settings.json이 없으면(7장의 하네스가 없으면) 8장 키트의 기준 산출물(7장에서 조립한 하네스)을 먼저 복사한다.

서버 터미널 
cp -rn ~/kits/Agent_08주차/기준산출물/jobprep/. .   # CLAUDE.md, .claude/settings.json이 없을 때만
cp -rn ~/kits/Agent_10주차/기준산출물/. .
git status --short                                   # 새로 생긴 파일(??)만 확인한다
git add -A
git commit -m "chore: 앞 장 기준 산출물(1·6~8장 견본) 반영"

git status --short에는 복사된 파일만 ??로 보여야 한다. 자기 산출물이 있던 파일은 그대로 남으므로 목록에 나오지 않는다. 작업 트리가 깨끗한 상태에서 복사하였으므로 git add -A는 복사한 파일만 더한다. 커밋 메시지는 3장의 저장소 규약(종류(범위): 설명)을 따른다. 3장의 commit-msg 훅을 켠 저장소에서는 규약에 맞지 않는 메시지의 커밋이 멈춘다. 이 장의 조정 스크립트가 만드는 커밋(구현 에이전트의 커밋, merge.sh의 병합 커밋)도 같은 규약을 따른다. 훅을 켠 저장소에서는 커밋할 때마다(merge.sh의 병합을 포함해) 통과 커밋: …과 검사 1건, 위반 0건 두 줄이 더 나온다. 이 장의 출력 예시에서는 그 두 줄을 뺐다.

1. 단일 에이전트의 한계와 멀티 에이전트의 비용

1-1. 에이전트 하나가 부딪히는 세 한계

1장에서 에이전트를 「모델 + 도구 + 루프」로 정의했다. 그 정의의 에이전트 하나에게 저장소 운영 전체를 맡기면 세 가지 한계에 부딪힌다.

첫째는 컨텍스트이다. 에이전트는 대화 하나의 컨텍스트 창 안에서 일한다. 파일을 읽고, 테스트를 돌리고, 기록을 훑을 때마다 그 내용이 컨텍스트에 쌓인다. Anthropic의 연구 시스템에서는 대화가 20만 토큰을 넘으면 앞부분이 잘리므로, 주도 에이전트가 자기 계획을 따로 저장해 두어야 했다[E2]. Claude Code의 서브에이전트는 이 문제에 대한 답 하나다. 서브에이전트는 자기 컨텍스트 창에서 일하고, 검색 결과나 기록처럼 긴 출력은 그 안에 남기며, 마지막 요약만 주 대화로 돌려준다[C13].

둘째는 전문화이다. 에이전트 하나는 시스템 프롬프트 하나와 도구 묶음 하나를 가진다. 같은 에이전트가 계획도 쓰고, 코드도 고치고, 자기 코드를 검토도 하면, 검토할 때도 구현할 때의 가정을 그대로 들고 온다. 6장에서 검토 서브에이전트를 따로 둔 까닭이 이것이었다. 역할마다 시스템 프롬프트, 허용 도구, 권한을 따로 두면 「구현 역할은 테스트를 고칠 수 없다」, 「검토 역할은 파일을 쓸 수 없다」 같은 경계를 지시가 아니라 설정으로 만들 수 있다[C13].

셋째는 병렬성이다. 에이전트 하나는 한 번에 한 가지 일을 한다. 서로 기다릴 필요가 없는 일 둘이 있어도 차례로 처리한다. Anthropic의 연구 시스템은 주도 에이전트가 하위 에이전트 3~5개를 동시에 띄우고, 하위 에이전트가 다시 도구 여러 개를 동시에 부르게 하여 복잡한 질문의 조사 시간을 최대 90%까지 줄였다고 보고했다[E2].

한계 에이전트 하나에서 생기는 일 멀티 에이전트의 대응 jobprep에서의 예
컨텍스트 읽은 파일과 출력이 쌓여 앞의 결정이 밀려나거나 잘린다 작업마다 새 컨텍스트, 결과는 요약이나 파일로 돌려준다 구현 에이전트는 자기 작업 카드와 관련 파일만 읽는다
전문화 같은 가정으로 쓰고 검토한다. 모든 일에 같은 권한을 준다 역할마다 지시문, 도구, 권한을 따로 둔다 검토 에이전트는 읽기 도구만, 구현 에이전트는 tests/를 못 고친다
병렬성 독립된 일도 차례로 한다 독립된 작업을 동시에 실행한다 API(T1)와 웹 단추(T2)를 두 작업 공간에서 동시에 만든다

1-2. 멀티 에이전트의 세 비용

나누면 얻는 것이 있는 만큼 치르는 것도 있다.

토큰. 에이전트는 같은 질문을 채팅으로 할 때보다 약 4배, 멀티 에이전트 시스템은 약 15배의 토큰을 썼다[E2]. 같은 글에서 웹 검색 평가(BrowseComp)의 성능 차이 가운데 80%를 토큰 사용량 하나가 설명했다고 하였으니, 토큰을 더 쓰면 결과가 나아지는 과제가 있다는 뜻이기도 하다. 그래서 그 글은 멀티 에이전트를 과제의 가치가 늘어난 비용을 감당할 만큼 클 때 쓰라고 한다[E2]. Claude Code 문서도 에이전트 팀이 세션 하나보다 토큰을 훨씬 많이 쓰며, 팀원이 계획 모드로 일할 때 표준 세션의 약 7배를 쓴다고 적고 있다[C19]. 학생 계정의 사용량 한도 안에서 실습하는 이 과목에서는 이 비용이 곧 수업 진행의 제약이 된다.

조정. 일을 나누려면 누군가 나누는 방법을 정하고, 나눈 조각을 넘기고, 돌아온 결과를 합쳐야 한다. 지시가 모호하면 하위 에이전트들이 같은 조사를 되풀이했다. 연구 시스템의 초기판에서는 반도체 공급 문제를 맡은 하위 에이전트 하나가 2021년 자동차 반도체 위기를 조사하는 동안 다른 둘이 2025년 공급망을 똑같이 조사했다[E2]. 주도 에이전트가 하위 에이전트들이 모두 끝나기를 기다리는 동기식 실행은 그 자체로 병목이 되었다[E2].

충돌. 둘 이상의 에이전트가 같은 파일을 고치면 나중에 쓴 쪽이 앞의 변경을 덮어쓴다. Claude Code 문서는 에이전트 팀에서 「두 팀원이 같은 파일을 고치면 덮어쓰기가 일어난다」고 경고하고, 팀원마다 다른 파일 묶음을 맡기라고 권한다[C23]. 같은 파일이 아니어도, 따로는 맞는 두 변경을 합치면 깨지는 경우가 있다(7-4의 의미 충돌).

비용 근거 이 장의 대책
토큰 채팅 대비 에이전트 약 4배, 멀티 에이전트 약 15배[E2]. 에이전트 팀은 계획 모드에서 약 7배[C19] 나눌 가치가 있을 때만 나눈다(2절). 실습은 가짜 에이전트로 돌린다
조정 모호한 위임은 중복 작업을 낳는다. 동기식 대기는 병목이 된다[E2] 계획서와 작업 카드에 목표, 계약, 경계, 완료 조건을 쓴다(5절)
충돌 같은 파일의 동시 편집은 덮어쓰기를 낳는다[C23] 소유 파일 단위 분할, worktree와 브랜치 분리, 병합 순서(7절)

1-3. 멀티 에이전트 시스템은 어디서 실패하는가

2025년 3월에 공개된 연구 「Why Do Multi-Agent LLM Systems Fail?」은 널리 쓰이는 멀티 에이전트 프레임워크 7개의 실행 기록 1,600여 건을 분석해 실패 유형을 분류했다[M1]. 전문가들이 기록 150건에서 분류 체계(MAST)를 만들었고, 주석자 사이의 일치도는 Cohen의 kappa 0.88이었다. 분류는 세 범주, 열네 가지 실패 유형으로 되어 있다.

범주 실패 유형(일부) 이 장의 대책
시스템 설계(FC1) 작업 명세 위반, 역할 명세 위반, 같은 단계의 반복, 대화 기록 유실, 종료 조건을 모름 작업 카드의 「하지 않는 것」과 「완료 조건」, 시도 상한(8장)
에이전트 사이의 불일치(FC2) 대화 초기화, 확인 질문을 하지 않음, 과제 이탈, 정보를 넘기지 않음, 다른 에이전트의 입력 무시, 추론과 행동의 불일치 계약을 먼저 정하고(5절), 결과 보고의 「계약과 다른 점」과 「요청」 칸

같은 연구는 사례 연구에서 역할 명세를 고치거나 높은 수준의 검증 단계를 더하는 것만으로 과제 성공률이 올랐지만, 그것으로 모든 실패가 사라지지는 않았다고 보고한다[M1]. 이 장의 설계는 이 표의 오른쪽 열을 하나씩 구현하는 일이다. 모델이 좋아지는 것을 기다리기보다, 실패가 생기는 자리마다 문서와 검사를 두는 것이다.

2. 멀티 에이전트의 판단 기준

2-1. 가장 단순한 해법부터

Anthropic은 에이전트 시스템을 만들 때 가장 단순한 해법을 먼저 찾고, 복잡성은 결과를 분명히 낫게 만들 때만 더하라고 권한다[E1]. 멀티 에이전트는 그 복잡성의 끝에 있다. 연구 시스템의 글도 멀티 에이전트가 잘 맞는 일과 맞지 않는 일을 나누어 적는다. 여러 방향을 동시에 파고드는 너비 우선 조사, 컨텍스트 하나에 다 들어가지 않는 정보, 복잡한 도구가 많은 일에는 잘 맞는다. 반대로 모든 에이전트가 같은 맥락을 공유해야 하는 일이나 에이전트 사이의 의존이 많은 일에는 맞지 않으며, 대부분의 코딩 과제가 조사 과제보다 병렬로 나눌 부분이 적다고 적었다[E2]. Claude Code 문서도 순차적인 작업, 같은 파일의 편집, 의존이 많은 작업에는 세션 하나나 서브에이전트가 더 낫다고 한다[C23].

2-2. 다섯 질문

이 장은 다음 다섯 질문으로 판단한다. 설계서 양식의 1절이 이 표이다.

질문 「예」이면 「아니오」이면
① 작업이 서로 기다리지 않는 부분으로 나뉘는가 병렬로 나눌 수 있다 나누어도 차례로 돌 뿐이다. 파이프라인이나 에이전트 하나
② 한 에이전트의 컨텍스트에 다 들어가지 않는가 하위 에이전트가 읽고 요약하게 한다 컨텍스트를 나눌 까닭이 없다
③ 역할마다 다른 권한과 도구가 필요한가 역할 에이전트로 나눈다(검토자, 테스트 작성자) 같은 권한이면 나누어도 경계가 생기지 않는다
④ 병렬로 줄어드는 시간이 늘어나는 토큰과 조정보다 값진가 나눈다 에이전트 하나로 한다
⑤ 나눈 결과를 기계로 판정할 수 있는가 판정을 자동화하고 사람은 병합만 본다 사람이 모든 결과를 읽어야 하므로 나눈 이득이 줄어든다

①과 ④가 「아니오」이면 다른 질문의 답과 상관없이 나누지 않는다. ③만 「예」이면 병렬이 아니라 역할 분리(생성자-검토자, 3절)로 충분하다. ⑤가 「아니오」인 작업(예: 장애 보고서의 문장 다듬기)은 나누어도 사람의 검토 부담이 줄지 않는다.

3. 구조의 유형

3-1. 네 가지 구조

여러 에이전트를 묶는 방식은 몇 가지 유형으로 정리된다. Anthropic의 「Building effective agents」는 워크플로 패턴으로 프롬프트 사슬, 라우팅, 병렬화(구획 나누기와 투표), 조정자-작업자, 평가자-최적화자를 든다[E1]. 이 장은 그 가운데 운영에 쓰이는 넷을 쓴다.

구조 원래 이름[E1] 흐름 잘 맞는 경우 jobprep의 예
조정자-작업자 orchestrator-workers 조정자가 일을 나누어 작업자에게 맡기고 결과를 모은다 하위 작업을 미리 다 알 수 없을 때. 여러 파일에 걸친 코딩 변경 이슈를 계획서로 나누고 구현 에이전트 둘에게 맡긴다
파이프라인 prompt chaining 앞 단계의 출력이 다음 단계의 입력이 된다. 단계 사이에 관문을 둔다 고정된 단계로 깔끔하게 나뉠 때 계획 → 인수 테스트 → 구현 → 판정 → 병합
생성자-검토자 evaluator-optimizer 한쪽이 만들고 다른 쪽이 평가해 돌려보낸다 평가 기준이 분명하고 되풀이가 품질을 올릴 때 구현 → 판정 거부 → 재작업(8장 루프의 확장)
경쟁 후 선택 parallelization: voting 같은 일을 여럿이 따로 하고 기준으로 하나를 고른다 답이 불확실하고 여러 시도를 비교할 가치가 있을 때 원인 모를 장애에 가설별 조사, 같은 카드를 두 번 구현해 나은 쪽 병합

조정자-작업자와 프롬프트 사슬의 차이는 「누가 단계를 정하는가」이다. 프롬프트 사슬은 단계가 코드에 고정되어 있고, 조정자-작업자는 조정자가 입력을 보고 하위 작업을 정한다. Anthropic은 조정자-작업자의 예로 「여러 파일을 복잡하게 바꾸는 코딩 제품」을 든다[E1]. 연구 시스템은 이 구조에 인용을 붙이는 전용 에이전트를 더해, 조정자-작업자 뒤에 파이프라인 한 단계를 이은 모양이다[E2].

flowchart LR
    I[이슈] --> P[조정자: 계획서와 작업 카드]
    P --> W1[작업자 T1]
    P --> W2[작업자 T2]
    W1 --> J{판정}
    W2 --> J
    J -->|거부| W1
    J -->|거부| W2
    J -->|통과| H[사람: 병합]

3-2. 경쟁 후 선택의 비용

경쟁 후 선택은 같은 일을 N번 하므로 비용도 N배이다. 그 대신 고르는 기준이 기계로 판정되면(테스트 통과, 변경 줄 수, 실행 시간) 사람의 판단 없이 고를 수 있다. Claude Code 문서는 에이전트 팀의 사례로, 원인을 모르는 버그에 팀원 다섯을 붙여 서로의 가설을 반박하게 하는 「경쟁 가설」 조사를 든다[C23]. 한 조사자가 그럴듯한 설명 하나를 찾고 멈추는 「닻 내림」을 막기 위해서다. 구현 과제에 쓸 때는 두 결과가 모두 통과하면 무엇으로 고를지(예: 변경 줄 수가 적은 쪽, 새 의존이 없는 쪽)를 미리 정해 두어야 한다. 정하지 않으면 결국 사람이 둘을 다 읽는다.

3-3. Claude Code의 병렬 실행 방법

Claude Code는 2026-11 기준으로 여러 일을 동시에 하는 방법을 다섯 가지로 정리한다[C22]. 이름과 화면은 판마다 바뀔 수 있다.

방법 조정하는 쪽 작업 공간 분리 상태 이 장에서
서브에이전트 세션 안의 Claude가 위임하고 요약을 받는다 isolation: worktree를 정하면 작업마다 worktree 정식 역할 에이전트의 정의 형식(4절), 세션 조정자(8-2)
에이전트 보기(agent view) 사람이 백그라운드 세션을 띄우고 살핀다(claude --bg, claude agents) 편집 전에 세션마다 worktree로 옮긴다 연구 미리보기 8-1에서 소개
에이전트 팀 주도 세션이 팀원에게 일을 나누고 작업 목록과 메시지로 맞춘다 나누지 않는다. 팀원마다 파일을 나누어야 한다 실험 기능, 기본은 꺼짐 8-2에서 소개
동적 워크플로 스크립트가 서브에이전트 여럿을 돌리고 결과를 교차 확인한다 서브에이전트 설정에 따른다 문서에 있음 다루지 않는다
프로젝트 클라우드의 대화 하나가 스레드를 띄운다 클라우드 환경 공개 베타 다루지 않는다

이 밖에 worktree는 「세션마다 따로인 git 체크아웃」을 주는 보조 도구이고, /batch는 큰 변경 하나를 worktree로 격리한 서브에이전트 5~30개로 나누는 기본 스킬이다[C22]. 이 장의 중심 실습은 이 가운데 어느 하나에 묶이지 않도록, 조정을 저장소의 스크립트(ops/multi/)와 문서(인계 문서)로 만든다. 스크립트가 부르는 에이전트 명령만 바꾸면 사람, Claude Code 세션, 헤드리스 실행 어느 쪽으로도 같은 흐름을 돌릴 수 있다(8절).

3-4. ISSUE-07의 구조

ISSUE-07은 네 구조를 섞는다. 바깥은 파이프라인(계획 → 테스트 → 구현 → 판정 → 병합)이고, 구현 단계 안은 조정자-작업자(작업 둘)이며, 판정과 재작업 사이는 생성자-검토자이다. 경쟁 후 선택은 쓰지 않는다. 계약과 인수 테스트가 답을 하나로 정하므로 같은 일을 두 번 할 가치가 없다.

      B --> C[tester: 인수 테스트 Red]

      end
      E1 --> F[판정: 테스트·범위·동결·검토]
      E2 --> F
      F -->|거부, 상한 3회| E1
      F -->|거부, 상한 3회| E2
      F -->|통과| G{사람: 병합 순서와 승인}

    end

4. 역할 정의서의 재검토

4-1. 문서의 역할에서 실행되는 역할로

1장의 역할 정의서는 역할마다 권한, 입력, 출력, 완료 조건, 사람 승인 지점을 적은 문서였다. 문서는 사람이 읽고 따르는 것이다. 이 장은 같은 내용을 에이전트가 실행될 때 실제로 적용되는 곳으로 옮긴다. 옮길 곳은 네 군데다.

역할 정의서의 항목 옮기는 곳 강제되는가
역할(목적) 정의 파일의 name, description, 본문 첫 문단 위임할 때 Claude가 description을 보고 고른다[C13]
권한: 도구 정의 파일의 tools, disallowedTools 예. 목록에 없는 도구는 쓸 수 없다[C13]
권한: 명령과 경로 .claude/settings.json의 permissions.deny, 훅, 판정 스크립트 예. 다만 settings.json은 모든 역할에 같이 적용된다
입력 지시문(작업 카드의 경로), 정의 본문의 「일하는 순서」 아니오. 지시이다
출력 결과 보고 양식, 커밋 메시지 규약 판정의 「보고」 항목이 있는지만 본다
완료 조건 작업 카드의 「완료 조건」, 판정 스크립트의 검사 판정이 기계로 확인한다
사람 승인 지점 계획서의 승인 줄, merge.sh를 사람이 실행 예. 승인 줄이 없으면 prepare.sh가 멈춘다

이 표의 마지막 열이 핵심이다. 6장에서 「지시(CLAUDE.md)」와 「강제(훅)」를 나누었듯이, 역할의 경계도 지시문에만 두면 에이전트가 어길 수 있다. MAST의 「역할 명세 위반」(FM-1.2)이 바로 그 실패이다[M1]. 이 장은 같은 경계를 지시문(정의 본문)과 검사(판정 스크립트) 두 곳에 둔다. 예를 들어 「구현 역할은 tests/를 고치지 않는다」는 implementer.md 본문에 지시로 있고, judge.sh의 「동결」 항목이 실제로 바뀐 파일을 보고 거부한다.

4-2. 서브에이전트 정의 파일의 형식

역할 에이전트는 Claude Code의 서브에이전트 정의 파일로 만든다. 서브에이전트는 YAML 프런트매터가 붙은 마크다운 파일이고, 본문이 그 에이전트의 시스템 프롬프트가 된다[C13]. 서브에이전트는 Claude Code의 기본 시스템 프롬프트를 받지 않고, 이 본문과 기본 환경 정보만 받는다는 점에 주의한다[C13]. 본문이 곧 그 에이전트가 아는 전부이므로, 역할 정의서의 내용을 빠짐없이 옮겨야 한다.

필드 뜻 이 장의 쓰임
name 고유한 이름(필수). :를 쓸 수 없다 planner, implementer, tester, reviewer
description 언제 위임할지(필수). Claude가 이 글을 보고 고른다 역할의 범위와 「하지 않는 일」을 함께 적는다
tools 허용 도구 목록. 없으면 모든 도구를 물려받는다 검토자는 Read, Grep, Glob만
disallowedTools 거부 도구 목록. tools보다 먼저 적용된다 쓰지 않는다(4-3)
model sonnet, opus, haiku, fable, 전체 모델 이름, inherit 구현·기획·테스트는 sonnet, 검토는 6장의 정의를 따른다
permissionMode 권한 모드. 주 대화가 acceptEdits, auto, bypassPermissions이면 그쪽이 우선한다 쓰지 않는다. 실행하는 쪽(8절)이 정한다
maxTurns 에이전트 턴의 상한. 닿으면 결과를 「일부」로 표시해 돌려준다 기획·테스트 20, 구현 30
isolation worktree이면 임시 git worktree에서 실행한다 8-2에서 소개
hooks 이 에이전트에만 적용되는 훅 11장에서 쓴다
memory 대화를 넘어 남는 기억 폴더 쓰지 않는다(재현성)

표는 2026-11-14에 공식 문서에서 확인한 필드의 일부이다[C13]. 문서는 「여러 단어로 된 필드 이름은 camelCase이고, 알 수 없는 필드는 소리 없이 무시된다」고 적는다[C13]. 3장에서 다룬 settings.json처럼 오류가 나지 않으므로, allowed-tools처럼 철자를 틀리면 도구 제한이 아무 경고 없이 사라진다. 키트의 ops/multi/check_agents.py가 이 실수를 찾는다.

정의 파일을 두는 곳에 따라 우선순위가 다르다. 같은 이름이 둘이면 조직의 관리 설정, --agents 명령행 옵션, 프로젝트의 .claude/agents/, 사용자의 ~/.claude/agents/, 플러그인의 agents/ 순서로 앞의 것이 쓰인다[C13].

역할 에이전트는 팀이 함께 쓰는 정의이므로 프로젝트의 .claude/agents/에 두고 저장소에 커밋한다. 3장의 규칙(팀 설정은 저장소에, 개인 설정은 저장소 밖에)을 그대로 따른다. 개인이 ~/.claude/agents/implementer.md를 두어도 프로젝트 쪽이 우선하므로 팀의 정의가 쓰인다.

4-3. 도구 제한의 함정

disallowedTools에 Bash(git push *)처럼 조건을 붙이면, 문서에 따르면 그 명령만이 아니라 Bash 도구 전체가 빠진다[C13]. 「git push만 막고 테스트는 돌리게 하자」는 의도로 쓰면 구현 에이전트가 pytest를 돌리지 못한다. 명령 단위로 막으려면 3장의 settings.json permissions.deny나 훅을 쓴다. 다만 settings.json은 그 저장소의 모든 세션과 모든 역할에 같이 적용된다. 「구현 역할만 tests/를 못 고친다」처럼 역할마다 다른 경로 제한은 settings.json으로 표현할 수 없다. 테스트 역할은 tests/에 새 파일을 써야 하기 때문이다.

이 장은 역할별 경로 제한을 두 겹으로 둔다. 첫째, 정의 본문의 「하지 않는 것」(지시). 둘째, 판정 스크립트의 「범위」와 「동결」 검사(사후 강제). 사전 강제가 필요하면 정의 파일의 hooks 필드로 그 에이전트에만 적용되는 PreToolUse 훅을 붙일 수 있다[C13]. 11장 보안에서 이 방법을 쓴다.

5. 인계 문서

5-1. 왜 문서로 넘기는가

서브에이전트는 새 컨텍스트로 시작한다. 주 대화의 기록도, 앞에서 읽은 파일도 보지 못한다. 시작할 때 받는 것은 자기 시스템 프롬프트, Claude가 써 준 위임 메시지, CLAUDE.md 파일, git 상태 요약, 미리 읽게 한 스킬뿐이다[C13]. 에이전트 팀의 팀원도 주도 세션의 대화 기록을 물려받지 않는다[C23]. 헤드리스로 실행하는 구현 에이전트(8-3)는 지시문 한 줄과 저장소의 파일만 받는다.

그래서 에이전트 사이의 인계는 「무엇을 넘기는가」를 설계하는 일이다. Anthropic의 연구 시스템은 주도 에이전트가 하위 에이전트에게 일을 맡길 때 네 가지를 주게 했다. 목표, 출력 형식, 쓸 도구와 자료에 대한 안내, 분명한 작업 경계이다[E2]. 이 넷이 빠진 짧은 지시가 1-2의 중복 조사를 낳았다. 또 하위 에이전트의 결과를 대화로 전달하면 단계마다 정보가 줄고 바뀌는 「전화 놀이」 문제가 생기므로, 결과는 외부 저장소(파일)에 두고 가벼운 참조만 넘기게 했다[E2].

이 장의 인계 문서는 세 가지이다.

문서 쓰는 쪽 → 읽는 쪽 담는 것 위치
계획서 planner → 사람(승인), tester, 조정자 목표와 범위, 정한 것, 계약, 작업 분할, 공유 파일, 병합 순서, 위험 docs/운영/인계/ISSUE-07/계획서.md
작업 카드 planner → implementer, 판정 스크립트 작업 하나의 목표, 계약, 소유 파일, 인수 테스트, 하지 않는 것, 완료 조건 …/T1_카드.md, …/T2_카드.md
결과 보고 implementer → 조정자, 사람 바꾼 파일, 확인한 명령과 결과, 계약과 다른 점, 요청, 남은 위험 …/T1_보고.md, …/T2_보고.md

세 문서 모두 저장소에 커밋된다. 결과 보고는 구현 에이전트가 자기 작업 브랜치에 커밋하므로, 병합되면 코드와 함께 통합 브랜치로 들어온다. 대화가 끝나도, 세션이 바뀌어도, 다른 사람이 이어받아도 같은 문서를 본다.

이슈는 사용자의 말로 쓰여 있다. 계획서는 이것을 에이전트가 판정할 수 있는 말로 바꾼다. 특히 「정하지 않은 것」은 계획서에서 반드시 닫는다. 닫지 않고 구현 에이전트 둘에게 넘기면, 둘이 서로 다른 답을 정한다. 예를 들어 API를 만드는 T1은 「없는 번호는 건너뛴다」로, 웹을 만드는 T2는 「없는 번호가 있으면 404를 보여 준다」로 정하면, 둘 다 자기 테스트를 통과하는데 합치면 동작이 맞지 않는다. MAST의 「확인 질문을 하지 않음」(FM-2.2)과 「추론과 행동의 불일치」(FM-2.6)가 이렇게 생긴다[M1]. 확인 질문을 할 수 없는 무인 실행에서는 계획 단계가 질문에 답해 두는 유일한 자리이다.

5-3. 계약

계획서의 핵심은 계약(contract)이다. 병렬로 일하는 작업이 서로의 결과를 기다리지 않으려면, 한 작업의 출력이 다른 작업의 입력이 되는 자리의 모양을 먼저 정해야 한다. ISSUE-07에서는 API의 경로, 매개변수, 응답 형식, 오류가 계약이다. 견본 계획서의 3절이 그 계약이다.

## 3. 계약 (작업 사이의 약속)

| 항목 | 내용 |

계약은 문장으로만 두지 않고 인수 테스트로 고정한다. T1의 계약은 tests/test_favorites_export.py가, T2의 계약은 tests/test_web_export.py가 잰다. 테스트가 먼저 있으면 계약과 다른 구현은 판정에서 걸린다. 2장의 「테스트가 완료 조건이다」를 작업 사이의 약속으로 넓힌 것이다.

5-5. 결과 보고

결과 보고 양식은 짧다. 조정자와 사람이 대화 기록을 열지 않고 이 보고와 커밋만 보고 판단하게 하려는 것이다.

양식의 뒷부분은 「계약과 다른 점」, 「요청 (소유 파일 밖에서 필요한 일)」, 「남은 위험」 세 칸이다. 「요청」 칸이 소유 파일 규칙의 짝이다. 구현 에이전트가 소유 밖의 파일을 고쳐야 한다고 판단하면, 고치지 않고 여기에 적는다. 조정자는 요청을 모아 공유 파일을 한 번에 고친다(7-1). MAST의 「정보를 넘기지 않음」(FM-2.4)을 양식의 칸으로 막는 것이다[M1].

양식의 「확인」 칸에는 실행한 명령과 결과의 마지막 줄을 그대로 붙인다. 그래도 보고에 적힌 「완료」를 그대로 믿지는 않는다. 이 과목의 출발점이 「결과를 믿게 해 주는 것은 에이전트의 말이 아니라 사람이 정해 둔 완료 조건」이었다. 9절의 실행에서 구현 에이전트가 「결과: 완료」라고 보고했는데 판정이 거부하는 장면을 보게 된다.

  • 확인 12 이슈 카드의 「정하지 않은 것」 셋이 견본 계획서 2절의 어느 줄에서 닫혔는지 설계서 4절 아래에 한 줄씩 적었다. 그리고 견본 계획서에 없는 질문 하나(예: CSV의 열 순서를 바꾸고 싶을 때 누가 정하는가)를 더 적었다.

6. 컨텍스트 격리와 공유 상태

6-1. 각 에이전트가 보는 것

멀티 에이전트 시스템에서는 「누가 무엇을 보는가」를 표로 그려 두어야 한다. 보지 못하는 것은 문서로 넘겨야 하고, 보지 말아야 하는 것은 막아야 하기 때문이다.

실행 방식 대화 기록 CLAUDE.md, 규칙 저장소 파일 다른 에이전트의 작업 결과가 돌아가는 곳
주 세션 전부 읽는다 기본 작업 공간 서브에이전트의 요약 사람
서브에이전트 보지 못함. 위임 메시지만 읽는다(omitClaudeMd로 끌 수 있다) 주 세션과 같은 작업 공간. isolation: worktree이면 임시 worktree 보지 못함 주 세션에 요약

서브에이전트와 팀원에 대한 내용은 Claude Code 문서를 따랐다[C13][C23]. 마지막 줄은 이 장의 설계이다. 구현 에이전트는 다른 작업의 진행을 보지 못하고, 볼 필요도 없다. 계약이 있기 때문이다. 다른 작업의 결과가 필요하다는 것은 계획이 작업을 잘못 나누었다는 신호이다.

6-2. 공유 상태

에이전트들이 컨텍스트를 나누지 않는 대신, 상태는 저장소에서 나눈다. 이 장의 공유 상태는 세 가지이다.

  • 저장소(커밋과 브랜치): 코드, 테스트, 인계 문서. 각 역할이 자기 브랜치에 쓰고, 진실의 원천은 통합 브랜치 feat/issue-07이다.
  • 이슈: 요청과 논의. 사람이 쓴다. 실제 운영에서는 GitHub 이슈이고, 이 장은 ops/multi/이슈/의 파일로 대신한다.
  • 실행 기록: 누가 언제 무엇을 했는가와 판정. 조정 스크립트가 ops/multi/logs/ISSUE-07/에 쓴다.

「진실의 원천」이 하나여야 한다. 계획서를 고쳤으면 통합 브랜치에 커밋해야 하고, 작업 공간들은 그 커밋에서 갈라져야 한다. 조정 스크립트가 계획서와 카드를 작업 공간의 파일이 아니라 통합 브랜치의 커밋(git show feat/issue-07:경로)에서 읽는 까닭이다. 작업 공간에 있는 카드는 에이전트가 고칠 수 있지만, 통합 브랜치의 카드는 사람이 승인한 그대로다.

6-3. 공유하지 않는 것

worktree는 파일을 나누지만 모든 것을 나누지는 않는다. git 문서에 따르면 연결된 worktree들은 저장소를 공유하며, HEAD, 인덱스 같은 작업 공간별 파일만 따로 가진다. refs/로 시작하는 참조(브랜치, 태그)는 모두 공유된다[G15]. Claude Code 문서는 여기에 더해, worktree 세션에서 「다시 묻지 않기」로 승인한 Bash 규칙이 기본 작업 공간의 .claude/settings.local.json에 저장되어 모든 worktree에 적용되고, 프로젝트 범위로 설치한 플러그인도 함께 쓰인다고 적는다(윈도우 등 일부 환경은 예외)[C21].

반대로 저장소에 없는 파일은 worktree에 따라가지 않는다. .env가 대표적이다. worktree는 커밋된 파일만 새로 꺼내므로, .gitignore에 있는 .env는 새 작업 공간에 없다. 이 장의 구현 에이전트에게는 오히려 바람직하다. 테스트는 모의 모드로 돌므로 키가 필요 없고, 키가 없으면 새어 나갈 것도 없다. Claude Code는 .worktreeinclude 파일(.gitignore 문법)에 적은 무시된 파일을 새 worktree로 복사해 주는 기능이 있지만[C21], 이 장에서는 쓰지 않는다. 키가 필요한 작업이 생기면 11장의 위협 모델에서 먼저 따진다.

무엇 작업 공간 사이에 근거
커밋, 브랜치, 태그 공유한다. 한 곳에서 만든 브랜치가 다른 곳에서도 보인다 [G15]
HEAD, 인덱스, 작업 파일 따로 가진다 [G15]
.gitignore의 파일(.env, .venv/) 따라가지 않는다 worktree는 커밋된 파일만 꺼낸다
Claude Code의 「다시 묻지 않기」 승인 공유한다(기본 작업 공간의 settings.local.json) [C21]
훅의 ${CLAUDE_PROJECT_DIR} EnterWorktree로 들어간 세션에서는 처음 시작한 곳을 가리킨다 [C21]

마지막 줄은 6장의 훅을 쓰는 학습자가 알아야 한다. 세션이 worktree로 옮겨 가도 ${CLAUDE_PROJECT_DIR}는 처음 시작한 기본 작업 공간을 가리키므로, 훅이 그 경로의 파일을 검사하면 엉뚱한 작업 공간을 보게 된다. 문서는 훅 입력 JSON의 cwd 필드를 읽으라고 권한다[C21]. 이 장처럼 worktree 안에서 claude를 새로 시작하면 그 worktree가 곧 프로젝트 폴더이므로 이 문제는 생기지 않는다.

7. 병렬 작업의 충돌 방지

7-1. 작업 분할의 기준

병렬 작업의 충돌은 대부분 계획 단계에서 막을 수 있다. 이 장은 다섯 가지 기준으로 작업을 나눈다.

기준 내용 어기면 생기는 일 지키게 하는 장치
소유 파일 한 파일의 소유자는 작업 하나이다. 작업은 파일 묶음으로 정의한다 같은 파일의 동시 편집, 병합 충돌, 덮어쓰기 prepare.sh가 카드의 소유 파일 겹침을 거부한다. judge.sh의 「범위」
계약 우선 작업 사이에 주고받는 것을 계획서에서 먼저 정하고 인수 테스트로 고정한다 서로 다른 가정, 합치면 맞지 않는 동작 인수 테스트
공유 파일은 한 곳에서 여러 작업이 고치고 싶은 파일(명세서, 변경 기록, 설정)은 조정자가 병합 뒤에 한 번 고친다 같은 줄 근처를 여럿이 고쳐 충돌 카드의 「하지 않는 것」, 보고의 「요청」
작업별 인수 테스트 테스트 파일도 작업마다 나눈다 한 작업만 병합된 상태에서 판정할 수 없다 카드의 - 인수 테스트: 줄, ignore_args
의존은 순서로 앞 작업의 결과를 봐야 하는 작업은 나누지 않거나 뒤로 미룬다 기다리는 작업, 다시 하는 작업 계획서의 「의존」 열, 병합 순서

ISSUE-07에서 api/main.py는 T1만 고친다. 명세서는 아무 작업도 고치지 않고, 계획 단계에서 새 요구를 「미구현」으로 더해 둔 뒤 병합이 끝나면 조정자가 상태를 고친다. T2(웹)는 T1(API)이 아직 없어도 계약만 보고 일한다. 브라우저에서 실제로 내려받는 것은 둘 다 병합된 뒤에야 확인할 수 있으므로, 그 확인은 사람의 몫으로 계획서의 「위험」에 적었다.

7-2. git worktree

git worktree는 저장소 하나에 작업 공간(체크아웃)을 여럿 두는 기능이다. git init이나 git clone으로 만든 처음 작업 공간을 기본 작업 공간(main worktree), git worktree add로 더한 것을 연결된 작업 공간(linked worktree)이라 한다. 연결된 작업 공간은 저장소를 공유하고, HEAD와 인덱스 같은 작업 공간별 파일만 따로 가진다[G15]. 저장소를 여러 번 복제하는 것과 달리 커밋과 브랜치가 하나의 저장소에 있으므로, 한 작업 공간에서 만든 커밋을 다른 작업 공간에서 바로 병합할 수 있다. 에이전트마다 작업 공간을 하나씩 주면, 에이전트들은 서로의 파일을 건드리지 않고 같은 저장소에 커밋한다. Claude Code 문서가 병렬 세션을 worktree로 나누라고 권하는 까닭이다[C16][C21].

명령 하는 일
git worktree add -b <새 브랜치> <경로> [<시작점>] 새 브랜치를 만들어 그 경로에 꺼낸다

7-4. 브랜치 이름과 병합 순서

이 장의 브랜치 이름은 3장 저장소 규약(feat/<요약> 등)을 따르면서, 에이전트가 만든 브랜치를 구별하는 agent/ 접두어를 더한다.

  • 통합 브랜치 feat/issue-07: 사람과 조정자가 커밋한다(계획서, 인수 테스트, 병합 커밋, 명세서 갱신).
  • 작업 브랜치 agent/issue-07-t1, agent/issue-07-t2: 구현 에이전트 하나가 커밋한다.

feat/issue-07/t1처럼 통합 브랜치 아래에 작업 브랜치를 두고 싶어지지만, git에서는 그렇게 할 수 없다. 브랜치 이름은 .git/refs/heads/ 아래의 경로처럼 다루어지므로, feat/issue-07이라는 브랜치가 있으면 feat/issue-07/t1을 만들 수 없다.

서버 터미널 
git branch feat/issue-09
git branch feat/issue-09/t1
git branch -d feat/issue-09
fatal: cannot lock ref 'refs/heads/feat/issue-09/t1': 'refs/heads/feat/issue-09' exists; cannot create 'refs/heads/feat/issue-09/t1'
Deleted branch feat/issue-09 (was ba07900).

3장의 저장소 규약 문서에 「에이전트의 작업 브랜치는 agent/<이슈>-<작업>(영문 소문자와 숫자, 예: agent/issue-07-t1)」을 한 줄 더한다. 3장의 검사기 ops/rules/check_commits.py --branch는 종류 agent를 이미 허용하므로 feat/issue-07과 agent/issue-07-t1은 통과하고, agent/ISSUE-07-T1처럼 대문자를 쓰면 거부한다. 규약에 없는 브랜치 이름은 13장의 보호 규칙과 CI 설정에서 빠지기 쉽다. 7-2의 연습 브랜치는 같은 규약의 practice/ 종류를 쓴다.

병합 순서는 다음 원칙으로 정한다.

  1. 의존되는 작업을 먼저 넣는다. ISSUE-07은 웹(T2)이 API(T1)를 부르므로 T1이 먼저다.
  2. 병합할 때마다 그 상태에서 테스트를 돌린다. merge.sh는 병합을 커밋하기 전에(--no-commit) 테스트를 돌리고, 실패하면 병합을 되돌린다.
  3. 병합 커밋을 남긴다(--no-ff). 빨리 감기(fast-forward)로 합치면 어느 커밋이 어느 작업에서 왔는지 그래프에서 사라진다. --no-commit은 빨리 감기에서는 멈출 수 없으므로 --no-ff와 함께 써야 한다[G16].
  4. 작은 작업, 위험이 작은 작업을 먼저 넣는다. 뒤에 넣는 작업이 충돌을 풀 책임을 진다.

따로는 통과하는 두 변경을 합치면 깨지는 경우를 의미 충돌이라 한다. 글자가 겹치지 않으므로 git은 충돌로 알리지 않는다. 예를 들어 T1이 함수 이름을 바꾸고 T2가 옛 이름을 부르면, 두 브랜치는 각자 테스트를 통과하지만 합치면 깨진다. 병합할 때마다 테스트를 돌리는 원칙 2가 이것을 잡는다. 키트의 스크립트 테스트 test_merge_rolls_back_when_combined_tests_fail이 이 경우를 재현한다.

7-5. 충돌이 났을 때

계획을 잘해도 충돌은 생긴다. 공유 파일을 소유 규칙 없이 고쳤거나, 통합 브랜치가 그사이 바뀌었을 때다. 두 작업이 같은 변경 기록 파일의 같은 자리에 한 줄씩 더하는 경우를 재현한다.

서버 터미널 
printf '# 변경 기록\n\n- 2027-11-15: 기준 저장소\n' > CHANGELOG.md
git add CHANGELOG.md && git commit -q -m "docs: 변경 기록"
git -C ../wt-a merge -q main && git -C ../wt-b merge -q main

git -C ../wt-b commit -q -am "docs: T2 변경 기록"

git merge --no-ff -m "chore: practice/b 병합" practice/b

충돌을 처리하는 길은 둘이다.

  1. 되돌리고 작업 브랜치에서 푼다. git merge --abort로 병합을 되돌린 뒤, 그 작업의 작업 공간에서 git merge <통합 브랜치>로 충돌을 풀고 커밋하고, 다시 판정을 받는다. 풀이가 작업의 판정을 다시 거친다.
  2. 통합 브랜치에서 바로 푼다. 충돌 파일을 고치고 git add 뒤 git commit 또는 git merge --continue로 끝낸다[G16]. 사람이 직접, 아주 작은 충돌을 풀 때 쓴다.

merge.sh는 첫째 길을 따른다. 충돌하면 git merge --abort로 병합 전 상태로 되돌리고 충돌 파일을 알린 뒤 종료 코드 3으로 멈춘다. 둘째 길은 풀이가 판정을 거치지 않으므로, 충돌을 푼 결과에 테스트가 깨져도 알 수 없다. 이 장은 첫째 길을 연습한다.

서버 터미널 
git merge --abort
git status --short
git -C ../wt-b merge main
Auto-merging CHANGELOG.md
CONFLICT (content): Merge conflict in CHANGELOG.md
Automatic merge failed; fix conflicts and then commit the result.

git merge --abort 뒤의 git status --short가 아무것도 보이지 않아야 한다. 병합을 시작할 때 커밋하지 않은 변경이 있었다면 --abort가 그것을 온전히 되살리지 못할 수 있으므로[G16], 이 장의 스크립트는 병합 전에 작업 공간이 깨끗한지부터 확인한다.

이제 충돌은 T2의 작업 공간 ../wt-b로 옮겨졌다. 에디터로 ../wt-b/CHANGELOG.md를 열어 표시줄 세 개를 지우고 두 줄을 모두 남긴다. 실제 운영에서는 이 풀이를 구현 에이전트에게 「직전 판정의 거부 사유」와 함께 다시 맡길 수도 있다.

7-7. Claude Code의 worktree 기능

이 장의 스크립트는 git 명령으로 worktree를 직접 만든다. Claude Code에도 같은 일을 하는 기능이 있다. 2026-11-14에 문서와 이 PC의 Claude Code 2.1.296의 claude --help로 확인한 내용이다.

기능 내용 근거
claude --worktree <이름> (-w) .claude/worktrees/<이름>/에 worktree-<이름> 브랜치로 worktree를 만들고 그 안에서 세션을 시작한다. 이름을 빼면 자동으로 짓는다 [C21], claude --help
시작점 기본은 원격의 기본 브랜치(origin/HEAD, 보통 main). 설정 worktree.baseRef를 "head"로 하면 지금 HEAD에서 갈라진다 [C21]
끝낼 때 바뀐 것이 없으면 이름 없는 세션의 worktree와 브랜치를 지운다. 바뀐 파일이나 새 커밋이 있으면 남길지 묻는다. -p 실행은 정리하지 않는다 [C21]
.worktreeinclude .gitignore 문법으로 적은 무시된 파일(.env 등)을 새 worktree로 복사한다 [C21]
서브에이전트 isolation: worktree 서브에이전트마다 임시 worktree를 준다. 바뀐 것이 없으면 끝날 때 지운다 [C13][C21]
격리 검사 worktree 세션에서 기본 작업 공간의 파일을 편집하거나, 기본 작업 공간에서 git을 실행하는 명령을 막는다. 다만 cp나 리디렉션으로 쓰는 것은 추적하지 않는다 [C21]

시작점이 중요하다. 이 장은 계획서와 인수 테스트를 통합 브랜치 feat/issue-07에 먼저 커밋하고, 작업 브랜치를 거기서 갈라낸다. Claude Code의 --worktree나 isolation: worktree는 기본값이 원격의 기본 브랜치이므로, 그대로 쓰면 구현 에이전트가 계획서와 인수 테스트가 없는 main에서 시작한다. worktree.baseRef를 "head"로 두거나, 이 장처럼 git worktree add로 시작점을 정해 만든 작업 공간 안에서 claude를 실행해야 한다. 문서도 특정 브랜치에서 시작하려면 git으로 직접 만들라고 안내한다[C21].

마지막 줄의 「격리 검사」는 보안 장치가 아니라 실수 방지 장치이다. 문서는 이 검사가 셸 명령이 쓰는 파일을 추적하지 않는다고 분명히 적는다[C21]. worktree는 에이전트끼리 서로의 일을 덮어쓰지 않게 할 뿐, 악의적이거나 속은 에이전트를 가두지 않는다. 그 일은 11장의 권한, 샌드박스, 훅이 맡는다.

8. 조정의 구현

8-1. 세 가지 조정자

조정자(orchestrator)는 계획을 받아 작업을 나누어 주고, 결과를 모아 판정에 넘기고, 실패하면 돌려보내는 쪽이다. 같은 역할을 사람, Claude Code 세션, 스크립트가 맡을 수 있다.

조정자 작업을 나누어 주는 법 장점 한계 이 장에서
사람 터미널마다 작업 공간에 들어가 claude를 띄우고 카드를 넘긴다 가장 단순하다. 진행을 눈으로 보고 바로 고친다 사람의 시간이 든다. 작업이 늘면 놓친다 8-2 (교수 시연)
Claude Code 세션 주 세션이 서브에이전트나 팀원에게 위임한다 자연어로 지시한다. 하위 작업을 상황에 맞게 정한다 조정 자체가 모델의 판단이라 매번 다를 수 있다. 토큰이 든다 8-3 (소개)
스크립트 ops/multi/가 정해진 순서로 준비, 실행, 판정을 되풀이한다 같은 입력에 같은 순서. 기록이 남는다. 조정에 토큰이 들지 않는다 계획에 없는 상황에서는 멈추고 사람에게 넘길 뿐이다 8-4, 9절(중심 실습)

세 방식은 서로 배타적이지 않다. 이 장의 중심 실습은 「계획은 planner(모델), 승인은 사람, 준비·실행·판정은 스크립트, 병합은 사람」으로 섞었다. 판단이 필요한 곳에 모델을, 되풀이와 기록이 필요한 곳에 스크립트를, 되돌리기 어려운 결정에 사람을 둔 것이다. 1장의 「워크플로와 에이전트의 구분」[E1]으로 보면, 바깥 흐름은 코드로 고정된 워크플로이고 그 안의 구현 단계만 에이전트이다.

8-2. 사람이 조정자일 때

사람이 조정할 때도 작업 공간과 인계 문서는 같다. 9-4까지 진행해 작업 공간이 준비된 뒤라면, 터미널 둘을 열고 각각 다음을 한다.

서버 터미널 1 
cd ~/agent-lab/jobprep/.claude/worktrees/issue-07-t1
claude --agent implementer
Claude Code 
이 작업 공간은 이슈 ISSUE-07의 작업 T1 전용이다. 작업 카드 docs/운영/인계/ISSUE-07/T1_카드.md를 읽고 그대로 수행하라. 카드의 소유 파일 밖의 파일은 고치지 않는다. 끝나면 결과 보고를 docs/운영/인계/ISSUE-07/T1_보고.md에 쓰고, 소유 파일만 git add 하여 커밋하라. 푸시와 병합은 하지 않는다.

claude --agent implementer는 세션 전체를 implementer 정의로 실행한다[C13]. 정의의 도구 제한과 본문이 주 세션에 적용되므로, 역할의 경계를 사람이 매번 말로 하지 않아도 된다. 둘째 터미널에서는 issue-07-t2와 T2 카드로 같은 일을 한다. 두 세션이 일하는 동안 사람은 셋째 터미널에서 bash ops/multi/status.sh ISSUE-07로 진행을 본다. 두 세션이 끝나면 judge.sh부터는 9절과 같다.

Claude Code의 에이전트 보기(agent view)를 쓰면 터미널 여럿 대신 화면 하나에서 백그라운드 세션들을 띄우고 살필 수 있다. claude --bg "<지시>"로 백그라운드 세션을 시작하고, claude agents로 목록과 상태를 본다[C24]. 백그라운드 세션은 파일을 고치기 전에 .claude/worktrees/ 아래의 자기 worktree로 옮겨 가지만, 이미 연결된 worktree 안에서 시작한 세션은 그 자리에서 일한다[C24]. 이 기능은 2026-11 기준 연구 미리보기이다.

교수 시연: 실제 Claude Code 세션 둘을 동시에 돌리면 계정의 사용량도 두 배로 들고, 모델의 결과가 사람마다 달라 판정과 병합을 함께 따라가기 어렵다. 그래서 이 절은 교수가 화면에서 두 세션을 나란히 띄워 보이는 시연으로 한다. 학습자는 시연을 보면서 두 세션이 서로의 대화를 보지 않고 카드만 읽고 일한다는 점과, status.sh의 「변경」 열이 바뀌는 순서를 관찰한다. 같은 흐름은 9-5에서 가짜 에이전트로 직접 돌리고, 시연의 실행 기록은 10-4에서 읽는다.

8-3. Claude Code 세션이 조정자일 때

주 세션이 조정하면 하위 작업은 서브에이전트로 위임된다. 기본 작업 공간에서 feat/issue-07을 꺼낸 상태로 세션을 열고, 이렇게 지시할 수 있다.

Claude Code 
planner 에이전트에게 ops/multi/이슈/ISSUE-07.md의 계획서와 작업 카드를 docs/운영/인계/ISSUE-07/에 쓰게 하라. 승인 줄은 「- 승인 대기」로 둔다. 다 쓰면 내가 계획서를 읽고 승인할 때까지 멈춘다.

승인한 뒤에는 「tester 에이전트로 인수 테스트를 쓰고 Red를 확인하라」, 「implementer 에이전트 둘에게 T1, T2 카드를 각각 맡겨 병렬로 실행하라. 각자 별도의 worktree에서 일하게 하라」로 이어 간다. 서브에이전트를 worktree에서 실행하려면 정의 파일에 isolation: worktree를 두거나 그렇게 지시한다[C21]. 이때 7-7에서 본 시작점 문제가 있다. 서브에이전트의 worktree는 기본값으로 원격의 기본 브랜치에서 갈라지므로, 프로젝트 설정 .claude/settings.json에 "worktree": {"baseRef": "head"}를 두어 지금 HEAD(통합 브랜치)에서 갈라지게 해야 한다[C21]. 또 Claude Code가 만든 worktree의 브랜치 이름은 이 장의 규칙(agent/issue-07-t1)과 다르므로, 판정과 병합은 주 세션이 tester와 reviewer에게 다시 위임해야 한다.

에이전트 팀은 한 걸음 더 나간다. 주도 세션이 팀원을 띄우고, 팀원들은 공유 작업 목록에서 일을 가져가고, 서로 메시지를 주고받는다[C23]. 2026-11 기준 실험 기능이며, 설정이나 환경 변수에서 CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1로 켠다. 팀원을 정의 파일의 역할로 띄울 수 있고(「implementer 에이전트 유형으로 팀원을 띄워라」), 팀원이 일을 끝내려 할 때 도는 TaskCompleted 훅, 쉬려 할 때 도는 TeammateIdle 훅으로 품질 관문을 둘 수 있다[C23]. 다만 에이전트 팀은 팀원을 worktree로 나누지 않으므로, 팀원마다 다른 파일 묶음을 맡기는 일이 전적으로 계획에 달려 있다[C22][C23]. 팀원 사이의 메시지는 사람의 승인을 대신할 수 없다는 점도 문서에 적혀 있다. 한 팀원이 거부된 동작을 다른 팀원에게 넘겨 우회할 수 없다[C23].

정리하면, 서브에이전트에 isolation: worktree를 쓰면 작업 공간은 서브에이전트마다 나뉘고 조정은 주 세션이 한다(정식 기능). 에이전트 팀은 작업 공간을 나누지 않고 주도 세션과 공유 작업 목록이 조정하며, 품질 관문은 훅과 사람이 맡는다(실험 기능). 이 장의 스크립트는 prepare.sh가 작업 공간을 나누고, 판정은 judge.sh가, 병합은 사람이 merge.sh로 한다.

세션 조정자의 실행은 집필할 때 실제 모델을 부르지 않아 확인하지 못하였다. 이 절도 교수 시연으로 본다.

8-4. 스크립트가 조정자일 때: ops/multi

이 장의 중심 실습은 스크립트가 조정한다. 스크립트의 전체 지도는 다음과 같다.

스크립트 하는 일 실패하면
prepare.sh 이슈 작업… 시작 조건(깨끗함, 통합 브랜치, 승인, 카드, 소유 겹침)을 확인하고 작업마다 worktree와 브랜치를 만든다 아무것도 만들지 않고 종료 코드 2
dispatch.sh 이슈 작업… 작업 공간마다 AGENT_CMD를 동시에 실행하고 모두 끝나기를 기다린다 에이전트가 0이 아닌 코드로 끝나면 종료 코드 1
judge.sh 이슈 작업 커밋, 범위, 동결, 보고, 테스트, 검토의 여섯 항목을 판정하고 판정 파일을 쓴다 「거부」, 종료 코드 1
run_issue.sh 이슈 작업… 준비 → 실행 → 판정을 거부된 작업만 시도 상한까지 되풀이한다 상한에 닿으면 사람에게 넘기고 종료 코드 1
merge.sh 이슈 작업… 판정과 커밋을 대조한 뒤 적은 순서로 병합한다. 병합마다 테스트 충돌 3, 테스트 실패 4. 둘 다 그 병합을 되돌린다
status.sh 이슈 작업 공간, 앞섬과 뒤짐, 판정, 병합 여부를 표로 보인다
cleanup.sh 이슈 작업… 병합된 작업의 worktree와 브랜치를 지운다 병합되지 않았거나 변경이 남은 작업은 건너뛴다

병렬 실행의 핵심은 dispatch.sh의 몇 줄이다.

grep -n '&$\|wait "\|PROMPT+=' ops/multi/dispatch.sh

44행의 끝에 붙은 &가 에이전트를 백그라운드로 띄운다. 괄호 안의 cd는 그 하위 셸에서만 작업 공간으로 옮겨 가므로, 스크립트 자신은 기본 작업 공간에 머문다. 53행의 wait는 그 작업의 프로세스가 끝나기를 기다리고 종료 코드를 받는다. 모든 작업을 먼저 띄우고 나서 차례로 기다리므로, 실행은 동시에 일어난다. 41행은 재시도일 때 직전 판정 파일의 표를 지시문에 붙인다. 구현 에이전트가 자기 작업 공간 밖의 파일(판정 파일은 기본 작업 공간에 있다)을 읽지 않아도 되게 하려는 것이다.

AGENT_CMD만 바꾸면 같은 스크립트가 가짜 에이전트로도, 실제 Claude Code로도 돈다. AGENT_CMD="python ops/multi/fake/impl_agent.py"는 가짜 구현 에이전트로, 정답 변경을 적용하고 결과 보고를 쓰고 커밋하며 FAKE_SCENARIO로 실패를 흉내 낸다. AGENT_CMD="bash ops/multi/claude_impl.sh"는 실제 Claude Code를 헤드리스(claude -p … --agent implementer)로 실행한다.

실제 Claude Code를 부르는 감싸개를 본다.

서버 터미널 
sed -n '/^PROMPT=/,$p' ops/multi/claude_impl.sh
PROMPT="${*: -1}"
exec claude -p "$PROMPT" \
  --agent implementer \
  --permission-mode acceptEdits \
  --permission-prompts none \
  --allowedTools "Bash(python -m pytest *),Bash(pytest *),Bash(.venv/bin/python -m pytest *),Bash(.venv/bin/pytest *),Bash(git add *),Bash(git commit *),Bash(git status *),Bash(git diff *)" \
  --disallowedTools "Bash(git push *),Bash(git merge *),Bash(git rebase *),Bash(git reset *),Bash(git switch *),Bash(git checkout *)" \
  --max-budget-usd "${AGENT_BUDGET_USD:-0.50}" \
  --output-format json
옵션 뜻 근거
-p "$PROMPT" 대화 없이 지시문 하나를 처리하고 끝낸다. 지시문을 옵션보다 앞에 두었다. 여러 값을 받는 옵션(--allowedTools) 뒤에 두면 지시문이 그 옵션의 값으로 읽힐 수 있다 [C14], claude --help
--agent implementer 세션을 implementer 정의로 실행한다 [C13], claude --help
--permission-mode acceptEdits 파일 편집은 묻지 않고 허용한다. 다른 셸 명령은 허용 규칙이 있어야 한다 [C14]
--permission-prompts none 물을 사람이 없으므로, 물어야 할 요청은 거부하고 다시 시도하지 말라고 알린다 [C14]
--allowedTools 테스트, 스테이징, 커밋, 상태 보기만 묻지 않고 허용한다 [C14]
--disallowedTools 병합, 푸시, 되돌리기, 브랜치 이동을 막는다 claude --help
--max-budget-usd 시도 한 번의 비용 상한(8장) claude --help
--output-format json 결과와 함께 total_cost_usd 같은 실행 정보를 JSON으로 남긴다. dispatch.sh가 이것을 출력 파일에 저장한다 [C14]

허용 규칙을 감싸개 파일에 둔 까닭은 규칙에 빈칸(Bash(python -m pytest *))이 들어가기 때문이다. AGENT_CMD="claude -p --allowedTools Bash(python -m pytest *)"처럼 문자열 하나에 담으면, 스크립트가 그 문자열을 빈칸에서 잘라 명령으로 만들 때 규칙이 쪼개진다. 셸에서 인자를 다루는 이 함정은 에이전트 자동화에서 자주 만난다.

감싸개는 집필할 때 문법 검사(bash -n)와, 가짜 claude 명령으로 인자가 의도한 순서로 넘어가는지만 확인하였다. 실제 모델을 부르는 실행은 확인하지 못하였다. 이 장의 실습은 가짜 에이전트로 끝까지 진행하고, 두 감싸개(claude_impl.sh, claude_review.sh)로 실제 모델을 부르는 실행은 교수 시연으로 본다. 학습자는 이 두 감싸개를 실행하지 않고 읽기만 한다. 시연이 남긴 실행 기록은 교수가 배포하며, 10-4에서 같은 방법으로 읽는다.

  • 확인 16 dispatch.sh에서 에이전트를 백그라운드로 띄우는 줄과 기다리는 줄의 번호를 찾았고, claude_impl.sh가 지시문을 옵션보다 앞에 두는 까닭을 한 문장으로 설명할 수 있다(설계서 3절의 「조정」 행에 적는다).

통합...작업의 점 셋은 「두 브랜치가 갈라진 지점부터 작업 브랜치까지」의 차이이다. 점 둘(통합..작업)로 비교하면, 그사이 통합 브랜치에 다른 작업이 병합되었을 때 그 변경까지 이 작업의 변경처럼 보인다. 작업 하나의 범위를 재려면 점 셋을 써야 한다.

검토의 기본 명령은 rule_review.py이다. 기계로 확실히 가릴 수 있는 팀 규칙 넷(웹의 innerHTML, api/llm.py 밖의 anthropic, 키처럼 보이는 문자열, 기록에 요청 본문)만 본다. 검토기의 번호 W1~W4는 검토자의 검토 규칙 RV3, RV2, RV1, RV7에 차례로 대응한다. LLM 검토자를 쓰려면 REVIEW_CMD="bash ops/multi/claude_review.sh"로 바꾼다(이 장에서는 교수 시연). 둘을 함께 쓸 수도 있다. 규칙 검토기는 싸고 빠르고 늘 같은 결과를 내므로 먼저 걸러 내고, LLM 검토자는 계약과 의도를 읽어야 하는 문제를 본다. 6장에서 심어 둔 위반으로 검토자를 검증했듯이, 규칙 검토기도 9절의 「첫 시도 실패」 시나리오로 검증한다.

판정 파일에는 판정한 커밋의 해시가 남는다. merge.sh는 병합하기 전에 이 해시와 작업 브랜치의 끝 커밋을 대조해, 판정 뒤에 커밋이 더해졌으면 병합을 거부한다. 「통과 판정을 받은 뒤 몰래 고친 변경」이 병합되는 것을 막는 장치이다.

10-3. 사람의 승인 지점

이 장의 시스템에서 사람이 반드시 관여하는 곳은 넷이다. 1장의 역할 정의서에서 「사람 승인 지점」으로 적었던 것을 실제 장치로 만든 것이다.

승인 지점 장치 승인 없이 진행하면
계획 승인 계획서의 - 승인: 줄. 없으면 prepare.sh가 멈춘다 잘못 나눈 작업이 병렬로 퍼진다. 고치는 비용이 작업 수만큼 커진다
인수 테스트 커밋 사람이 테스트를 읽고 커밋한다(tester 정의는 커밋하지 않는다) 아무것도 재지 않는 테스트가 완료 조건이 된다
병합 사람이 merge.sh를 실행한다. 스크립트 조정자(run_issue.sh)는 병합하지 않는다 판정을 통과했지만 의도와 다른 변경이 들어간다
main 반영과 배포 사람이 main에 병합하거나 풀 리퀘스트를 승인한다(13장)

승인 지점을 어디에 둘지는 「되돌리기 어려운가」와 「영향이 퍼지는가」로 정한다. 작업 공간 안의 커밋은 언제든 버릴 수 있으므로 에이전트에게 맡긴다. 통합 브랜치로의 병합은 다른 작업의 출발점이 되므로 사람이 한다. Claude Code의 에이전트 보기도 백그라운드 세션에게 main에 푸시하거나 강제 푸시하거나 병합하지 말라고 지시하며, 풀 리퀘스트의 검사가 통과하면 사람이 검토하고 병합하라고 안내한다[C24].

승인은 사람이 직접 해야 한다. 에이전트 팀 문서는 다른 에이전트가 보낸 메시지를 「사람이 보낸 것이 아님」으로 표시하고, 팀원이 사람 대신 권한 요청을 승인하거나 동의를 줄 수 없다고 적는다[C23]. 이 장의 스크립트에서도 승인 줄은 통합 브랜치의 커밋에서 읽는다. 구현 에이전트가 자기 작업 공간의 계획서에 승인 줄을 써 넣어도 아무 효과가 없다.

넷째 줄은 6장 검토자의 「지켜야 할 것」에 이미 대책 하나가 있다. 검토 대상 안의 주석이나 문자열에 적힌 지시(「이미 승인되었다」)를 따르지 않는다는 규칙이다. 이 장의 판정은 거기에 더해 검토 결과 한 줄만으로 통과시키지 않는다. 범위, 동결, 테스트가 모두 기계로 판정되고, 그 위에 사람의 병합 승인이 있다. 한 겹이 속아도 다른 겹이 남는 구조이다.

정리

  • 멀티 에이전트는 컨텍스트, 전문화, 병렬성이라는 단일 에이전트의 한계를 푸는 대신 토큰(채팅의 약 15배), 조정, 충돌의 비용을 치른다. 「일이 서로 기다리지 않는 부분으로 나뉘는가」와 「나누어 얻는 것이 비용보다 큰가」가 「아니오」이면 나누지 않는다.
  • 구조는 조정자-작업자, 파이프라인, 생성자-검토자, 경쟁 후 선택으로 나뉜다. 운영 시스템은 대개 이것들을 섞는다. ISSUE-07은 파이프라인 안에 조정자-작업자를 두고, 판정과 재작업을 생성자-검토자로 엮었다.
  • 역할 정의서의 역할은 서브에이전트 정의 파일(.claude/agents/)로 옮긴다. 도구는 정의의 tools로 강제하고, 역할별 경로 제한은 지시문과 판정 검사의 두 겹으로 둔다. 알 수 없는 필드는 소리 없이 무시되므로 정의를 검사한다.
  • 에이전트 사이의 인계는 계획서, 작업 카드, 결과 보고로 한다. 계약을 먼저 정하고 인수 테스트로 고정하면, 작업들이 서로를 기다리지 않고 병렬로 일한다. 문서의 일부(소유 파일, 인수 테스트 줄)는 스크립트가 읽는 인터페이스이다.
  • 병렬 작업의 충돌은 계획 단계에서 막는다. 작업은 소유 파일 단위로 나누고, 공유 파일은 조정자가 병합 뒤에 한 번 고친다. 작업마다 git worktree와 agent/ 브랜치를 주고, 의존되는 작업부터 병합하며, 병합마다 테스트를 돌린다.
  • 조정자는 사람, Claude Code 세션, 스크립트가 맡을 수 있다. 판단은 모델에, 되풀이와 기록은 스크립트에, 되돌리기 어려운 결정(계획 승인, 병합)은 사람에게 둔다.
  • 실패는 판정에서 잡고, 시도 상한에서 사람에게 넘긴다. 실행 기록과 커밋 꼬리말이 「누가 무엇을 했는가」에 답한다. worktree는 실수를 막을 뿐 보안 격리가 아니다.
