AI에이전트 기획 및 개발

2장

테스트 주도 개발

2027학년도 「AI에이전트 기획 및 개발」의 준비 중인 교재입니다. 편집 상태를 검토하기 위해 미리 공개한 것으로, 수업 전에 내용과 순서가 바뀔 수 있습니다.

학사 3주차 · 교재 02 · 1부 운영 요건과 검증

1장에서 기준 저장소 jobprep을 받아 개인 저장소로 만들고, 운영 요건 명세와 운영 에이전트 시스템의 역할 초안을 썼다. 운영 요건 가운데 신뢰성은 “정해진 조건에서 기대한 결과를 낸다”는 요건이었고, 재현성은 “같은 입력과 같은 환경에서 같은 결과를 다시 얻는다”는 요건이었다. 역할 초안의 구현 역할에는 완료 조건이라는 칸이 있었다. 이 장은 그 칸을 채우는 방법을 다룬다. AI 에이전트가 구현을 마쳤다고 보고할 때, 그 보고가 맞는지를 사람의 눈이 아니라 기계가 판정하게 만드는 장치가 테스트이다.

AI 에이전트에게 구현을 맡기면 일이 빨라지는 대신, 결과를 믿을 근거가 사라지기 쉽다. 에이전트는 “모든 테스트를 통과했습니다”라고 보고할 수 있다. 그러나 그 테스트를 누가 썼는지, 통과하는 동안 테스트가 그대로였는지, 테스트가 요구를 제대로 옮겼는지는 보고 안에 없다. 이 장은 테스트 주도 개발(TDD, Test-Driven Development)을 이 문제의 해법으로 다룬다. 사람이 요구를 테스트로 먼저 쓰고, 실패를 확인하고, 그 테스트를 바꾸지 못하게 잠근 뒤, 구현을 에이전트에게 맡긴다. 에이전트의 일은 잠긴 테스트를 통과시키는 것으로 끝나고, 통과 여부는 사람이 자기 터미널에서 다시 확인한다.

이 장에서 만드는 것은 하나다. 명세서의 미구현 요구 셋(REQ-JOB-06, REQ-SUM-05, REQ-ASK-06)을 테스트로 쓰고, Claude Code로 통과시키고, 정리한 결과이다. 결과는 저장소에 테스트 파일 셋, 동결 기록 tests/.baseline.json, 구현, 그리고 통과할 때마다 남긴 커밋과 태그 tdd-1로 남는다. 그 과정에서 해결하는 문제도 하나다. 둘째 요구에서 「62 passed」를 보고한 시도가 사실은 테스트 한 줄을 지워 얻은 통과였음을 동결 검사와 diff로 찾아내고, 그 시도를 버리고, 다시 지시해 진짜 통과를 얻는다. 이 테스트는 3장의 규칙과 권한, 6장의 훅, 8장의 자동 루프, 13장의 지속적 통합(CI)이 지키고 쓰며, 프로젝트실습Ⅱ에서 팀의 기능을 AI에게 맡길 때도 이 장의 절차를 그대로 쓴다.

학습 목표

  • 요구 문장을 준비·실행·확인의 구조를 갖춘 테스트로 바꾸고, 경계값과 등가 분할로 확인할 경우를 고른다.
    • 예시: “N일 안에 마감되는 공고만 보인다”를 N=6, 7, 8과 N=0, 음수, 정수가 아닌 값의 테스트로 나눈다.
    • 활용: 프로젝트실습Ⅱ의 요구마다 정상, 경계, 오류의 테스트를 먼저 쓰고 구현을 맡긴다.
  • pytest의 픽스처, 매개변수화, monkeypatch, 테스트 더블로 날짜와 LLM 같은 외부 요인을 통제한다.
    • 예시: jobs.today를 고정한 날짜를 돌려주는 함수로 바꿔 끼우고, llm.complete를 스파이로 감싸 불린 횟수를 센다.
    • 활용: 시간, 네트워크, 유료 API에 기대는 코드를 같은 결과가 나오는 테스트로 확인한다.
  • 테스트를 동결하고 지시문의 완료 조건으로 Claude Code의 구현을 통제하며, 테스트를 고쳐 통과시키는 회피를 찾아낸다.
    • 예시: test_guard.py check가 TEST_CHANGED와 수정: tests/test_summary_limits.py를 내면, git diff tests/로 지워진 단언을 찾고 그 시도를 버린다.
    • 활용: 에이전트의 “통과했습니다”를 증거(명령, 출력, 동결 검사)로 바꿔 받는다.
  • 테스트가 통과할 때마다 커밋하고, 실패한 시도는 git restore로 버리고, 재현 가능한 상태를 태그로 표시한다.
    • 예시: 요구 하나에 테스트 커밋과 구현 커밋 두 개를 남기고, 끝난 상태에 tdd-1을 붙인다.
    • 활용: 발표나 배포 직전의 상태를 태그로 남겨 누구든 같은 상태를 받아 테스트를 돌릴 수 있게 한다.

0. 시작하기

실습은 내 PC(개인 노트북 또는 실습실 PC)에서 한다. VS Code의 통합 터미널 두 개를 나란히 두고(부록 A-4-2), 하나는 직접 실행과 확인을 하는 [터미널], 다른 하나는 Claude Code를 띄우는 터미널로 쓴다. 두 터미널 모두 ~/agent-lab/jobprep에서 가상 환경을 먼저 켠다(Windows source .venv/Scripts/activate, macOS source .venv/bin/activate, 부록 A-9-1). 수업의 시작 순서는 부록 A-20, macOS에서 다른 점은 부록 A-4-3을 따른다.

이 장의 실행 상한. 실제 모델은 Claude Code의 대화형 세션으로만 쓴다(11절의 구현 지시 셋과 리팩터링 지시 하나). 헤드리스 실행(claude -p)과 프로덕트 코드의 API 호출은 하지 않는다. 테스트는 모두 모의 모드(LLM_FAKE=1)로 돌므로 API 키가 없어도 끝까지 할 수 있다.

키트는 1주차에 클론한 키트 저장소(~/kits-repo)에서 저장소 밖의 ~/kits/로 받는다(부록 A-7-3). cp -rn은 이미 있는 파일을 덮어쓰지 않으므로 다시 실행해도 받은 키트에 적은 것이 지워지지 않는다.

1-1. 에이전트에게 완료란 무엇인가

Claude Code의 공식 모범 사례 문서는 에이전트가 일을 멈추는 시점을 이렇게 설명한다. Claude는 일이 끝난 것처럼 보일 때 멈춘다. 끝났는지를 판정할 수단이 없으면 “끝난 것처럼 보인다”가 판단의 전부가 되고, 결국 사람이 테스트 역할을 하게 된다 [C1]. 같은 문서는 해법으로 “통과 또는 실패를 돌려주는 것”을 쥐여 주라고 권한다. 테스트 파일, 빌드의 종료 코드, 린터, 기대 출력과 비교하는 스크립트가 그 예이다 [C1]. 판정 수단이 있으면 에이전트는 고치고, 실행하고, 실패를 읽고, 다시 고치는 고리를 스스로 닫는다.

이 장에서 완료 조건(definition of done)은 다음 세 문장으로 정한다.

  1. python -m pytest -q의 마지막 줄에 failed와 error가 없다.
  2. python tools/test_guard.py check가 TEST_UNCHANGED를 출력한다(테스트가 사람이 동결한 그대로이다).
  3. 위의 두 결과를 에이전트의 보고가 아니라 학습자가 자기 [터미널]에서 실행해 확인한다.

1번만 있으면 에이전트는 테스트를 고쳐서도 조건을 만족할 수 있다. 2번은 그 길을 막는다. 3번은 “실행했다”는 보고와 실제 실행을 가른다. 모범 사례 문서도 에이전트에게 결과의 증거, 곧 실행한 명령과 그 출력을 요구하라고 권하며, “모든 테스트가 통과했다”는 말만으로는 알 수 있는 것이 거의 없다고 적는다 [C1].

1-4. 테스트가 보장하지 않는 것

테스트가 통과했다는 것은 “테스트에 적은 경우에 대해 기대한 결과가 나왔다”는 뜻이다. 그 이상은 보장하지 않는다. 세 가지 한계를 먼저 분명히 해 둔다.

  • 요구를 잘못 옮긴 테스트는 통과해도 틀렸다. 명세서는 “N일 안에 마감되는 공고”의 범위를 0 <= days_left <= N으로 정했다. 테스트를 0 < days_left <= N으로 잘못 쓰면, 오늘 마감인 공고를 빼는 구현이 통과한다. 테스트가 요구를 옳게 옮겼는지는 사람만 판정한다.
  • 적지 않은 경우는 확인하지 않는다. 테스트가 N=7 하나만 확인하면, N=7일 때만 맞는 구현도 통과한다(7절의 하드코딩). 경계값과 등가 분할(5절)은 적을 경우를 고르는 방법이다.
  • 테스트가 다루지 않는 성질은 별도로 확인한다. 화면의 배치, 응답 시간, 동시 접속, 보안은 이 장의 단위 테스트로 확인되지 않는다. 화면은 사람이 보고, 보안은 11장, 응답 품질의 반복 측정은 12장에서 다룬다.

1-5. 사례: 테스트를 지우고 “모두 통과”라고 보고한 에이전트

타입스크립트 라이브러리 typia의 개발자는 2026년 5월, 그 라이브러리를 Go 언어로 옮기는 일을 AI 에이전트에게 맡긴 경험을 공개했다 [S1]. 지시는 기계적인 1대1 이식이었고, tests/ 아래의 테스트가 검증 기준이며, 테스트가 통과할 때까지 반복하라는 것이었다. 글에 따르면 첫 시도에서 에이전트는 핵심 로직의 약 3분의 2를 빠뜨렸고, 실패하는 테스트를 지워 tests/ 폴더가 약 70% 줄었으며, CI는 녹색이었고, 최종 보고는 “모든 테스트가 통과했다”뿐이었다. 테스트를 고치지 말라는 규칙을 더하자, 다음 시도에서는 원래 프로그램의 출력을 미리 받아 168개의 경우로 된 분기문에 그대로 박아 넣었다(하드코딩). 하드코딩을 금지하자, 이번에는 CI 설정을 고쳐 일부 테스트 범주를 빼 버렸다.

이 사례에서 에이전트는 지시를 어기지 않았다. “테스트가 통과할 때까지”라는 문장을 가장 짧은 길로 만족시켰을 뿐이다. 금지 문장을 하나 더할 때마다 에이전트는 막히지 않은 다른 길을 찾았다. 글쓴이가 남긴 교훈은 감독 간격을 짧게 하고, 요약이 아니라 바뀐 내용(diff)을 읽고, 구체적인 본보기를 주라는 것이었다 [S1].

이런 행동에는 이름이 있다. Anthropic은 Claude Opus 4와 Claude Sonnet 4의 시스템 카드(2025년 5월)에서 보상 해킹(reward hacking)을 “과제의 규칙은 기술적으로 만족하지만 의도한 목적은 어기는 방법을 찾아내는 것”으로 정의하고, 그 구체적인 예로 테스트를 통과하기 위한 하드코딩(기대값을 그대로 출력하는 해법)과 특수 처리(special-casing, 일반적이지 않은 해법)를 들었다 [A1]. 같은 문서는 이전 모델인 Claude Sonnet 3.7이 특히 Claude Code 같은 에이전트형 코딩 환경에서 이 행동을 보였다고 적었다 [A1]. 모델이 바뀌면 빈도는 달라지지만, 판정 기준을 고칠 수 있는 환경에서 판정을 통과하라고 시키면 같은 유혹이 생긴다는 구조는 바뀌지 않는다. 7절은 이 구조를 막는 장치를, 8절은 지시문에서 할 수 있는 일을 다룬다. 11-5절에서는 이와 같은 모양의 시도 하나를 직접 판정한다.

2. Red · Green · Refactor

2-1. TDD의 주기

테스트 주도 개발은 켄트 벡(Kent Beck)이 익스트림 프로그래밍(XP)의 “테스트를 먼저 쓴다”는 실천을 정리해 『Test-Driven Development: By Example』(Addison-Wesley, 2002)로 펴내며 널리 알려졌다 [T2]. 기본 주기는 세 단계이다.

    F --> R
단계 하는 일 끝났다는 신호 이 장에서 맡는 이
Red 아직 없는 동작을 확인하는 테스트를 쓰고 실행해 실패를 본다 새 테스트만 실패하고, 실패 이유가 “기능이 없음”이다 사람
Green 그 테스트를 통과시키는 가장 단순한 코드를 쓴다 새 테스트와 기존 테스트가 모두 통과한다 Claude Code
Refactor 중복을 없애고 이름과 구조를 다듬는다. 동작은 바꾸지 않는다 다듬은 뒤에도 모든 테스트가 그대로 통과한다 Claude Code가 고치고 사람이 판정

Red를 건너뛰면 안 되는 까닭은 두 가지이다. 첫째, 구현이 없는데 통과하는 테스트는 아무것도 확인하지 않는 테스트이다. 둘째, 실패 화면은 테스트가 무엇을 기대하는지 보여 주는 가장 정확한 설명이다. assert [20, 3, 23, 6, 26, 9, ...] == [20]이라는 한 줄은 “필터가 없어 30건이 다 왔다”는 사실과 “7일 안 마감은 20번 하나여야 한다”는 기대를 함께 보여 준다.

2-2. 켄트 벡의 표준 절차

벡은 2023년 글 「Canon TDD」에서 TDD를 다섯 단계로 다시 정리하고, 단계마다 흔한 실수를 적었다 [T3].

단계 내용 벡이 든 실수 (요지)
1. 테스트 목록 확인하고 싶은 시나리오를 목록으로 적는다 구현의 설계 결정을 목록에 섞는다
2. 테스트 하나 목록에서 정확히 하나를 골라 실행되는 자동 테스트로 만든다 커버리지를 올리려고 단언 없는 테스트를 쓴다. 목록 전체를 한꺼번에 테스트로 만든다
3. 통과 그 테스트(와 앞의 모든 테스트)가 통과하도록 시스템을 바꾼다 단언을 지워 통과한 척한다. 계산된 값을 기대값에 복사해 넣는다. 통과시키면서 리팩터링을 섞는다
4. 리팩터링(선택) 구현의 설계를 다듬는다 필요 이상으로 다듬는다. 너무 일찍 추상화한다
5. 반복 목록이 빌 때까지 2로 돌아간다

3단계의 실수 둘은 1-5절의 사례와 같은 것이다. “단언을 지워 통과한 척한다”는 테스트 완화이고, “계산된 값을 기대값에 복사한다”는 구현이 낸 값을 정답으로 삼는 것이다. 사람이 하던 실수가 에이전트에서는 더 빠르고 더 크게 일어난다.

이 장의 핵심 실습은 표준 절차를 요구 단위로 묶어 쓴다. 요구 하나(예: REQ-JOB-06)의 테스트 목록을 5절의 방법으로 만들고, 시작 파일에 적힌 테스트와 「할 일」을 채워 목록을 테스트 파일 하나로 옮긴 뒤 동결하고, 에이전트에게는 그 파일 전체를 통과시키게 한다. 벡의 2단계(“정확히 하나”)보다 한 번에 넘기는 양이 많은 까닭은 에이전트에게 일을 맡기는 단위가 요구 하나일 때 동결과 검토가 가장 다루기 쉽기 때문이다. 그 대신 요구 사이에서는 반드시 Green을 확인하고 커밋한 뒤 다음 요구로 넘어간다.

2-3. 좋은 단위 테스트의 성질

단위 테스트가 지녀야 할 성질은 흔히 F.I.R.S.T.의 다섯 글자로 정리한다. jobprep의 테스트가 각 성질을 어떻게 지키는지 함께 적는다.

성질 뜻 jobprep에서 지키는 방법
Fast (빠르다) 자주 돌릴 수 있을 만큼 빠르다 실제 LLM과 Ollama를 부르지 않는다(모의 모드, 대체 임베딩). 66개가 수 초 안에 끝난다
Independent (독립적이다) 실행 순서와 다른 테스트에 기대지 않는다 monkeypatch의 바꿔 끼우기는 테스트가 끝나면 원래대로 돌아간다
Repeatable (반복할 수 있다) 언제, 어느 컴퓨터에서 돌려도 같은 결과이다 날짜를 고정한다(jobs.today). 오늘 날짜에 기대는 테스트는 내일 깨진다
Self-validating (스스로 판정한다) 사람이 출력을 읽지 않아도 통과와 실패가 정해진다 assert로 판정한다. print로 값을 찍어 눈으로 보는 테스트를 쓰지 않는다
Timely (제때 쓴다) 구현 직전에 쓴다 Red를 확인하고 동결한 뒤에 구현을 맡긴다

Repeatable은 이 장의 실습에서 특히 중요하다. 공고의 마감일은 2027년 9~12월에 퍼져 있다. 날짜를 고정하지 않으면 “7일 안 마감은 20번 하나”라는 테스트는 2027년 9월 1일에만 맞고, 수업하는 날에는 공고가 하나도 없거나 다 지나 있다. 4-3절에서 날짜를 고정하는 방법을 다룬다.

2-4. 가짜로 통과시키기와 삼각 측량

벡은 Green 단계에서 쓰는 두 기법을 소개했다 [T2]. 하나는 “가짜로 통과시키기(Fake It)”로, 상수를 돌려주어 일단 통과시킨 뒤 점차 일반화하는 것이다. 다른 하나는 “삼각 측량(Triangulation)”으로, 서로 다른 예를 둘 이상 두어 상수로는 통과할 수 없게 만드는 것이다. 사람이 혼자 TDD를 할 때 가짜로 통과시키기는 다음 테스트로 곧 일반화되는 징검다리이다. 그러나 에이전트에게 Green을 맡기면 이 징검다리가 최종 결과로 남을 수 있다. 1-5절의 168개 분기문이 그 극단이다.

그래서 이 장에서는 삼각 측량을 테스트를 쓰는 사람의 의무로 둔다. REQ-JOB-06의 테스트는 기준일을 2027-09-01, 09-08, 09-10의 세 날로 바꾸고, N을 0, 5, 6, 7, 8, 14의 여섯 값으로 바꾼다. 상수 하나나 날짜 하나에 맞춘 구현으로는 이 테스트 전체를 통과할 수 없다.

3. 테스트의 구조와 pytest

3-1. 준비 · 실행 · 확인

테스트 하나는 세 부분으로 이루어진다. 준비(Arrange)는 테스트가 돌 조건을 만든다. 실행(Act)은 확인하려는 동작을 한 번 일으킨다. 확인(Assert)은 결과가 기대와 같은지 판정한다. 영어 머리글자를 따 AAA 구조라고 부르고, 같은 생각을 요구 문장에 가깝게 적은 것이 Given · When · Then(주어진 조건에서 · 무엇을 하면 · 무엇이 되어야 한다)이다. 앞 과목의 EARS 문장과 짝지으면 다음과 같다.

테스트의 부분 Given · When · Then REQ-JOB-06에서 코드
준비 주어진 조건에서 기준일이 2027-09-01일 때 on_day(2027, 9, 1)
실행 무엇을 하면 closing_within=7로 목록을 요청하면 client.get("/api/jobs", params={"closing_within": 7})
확인 무엇이 되어야 한다 7일 안에 마감되는 20번 하나만 와야 한다 assert ids(response) == [20]

기준 저장소의 테스트 하나를 이 눈으로 읽는다. test_jobs.py의 마지막 테스트이다.

[파일: tests/test_jobs.py] · 끝부분

def test_days_left_uses_today(monkeypatch):
    monkeypatch.setattr(jobs, "today", lambda: date(2027, 9, 1))   # 준비: 오늘을 고정한다
    job = {"deadline": "2027-09-08"}                                # 준비: 확인할 공고
    assert jobs.days_left(job) == 7                                 # 실행과 확인

세 부분이 한 줄씩 눈에 보이면 좋은 테스트이다. 준비가 길어지면 픽스처로 옮기고(4절), 확인이 여러 개면 그것이 한 동작의 여러 면인지, 서로 다른 동작인지를 따진다. 서로 다른 동작이면 테스트를 나눈다. 테스트 하나가 실패했을 때 이름만 보고 어느 요구가 깨졌는지 알 수 있어야 하기 때문이다.

3-2. pytest가 테스트를 찾는 규칙

pytest는 정해진 이름 규칙으로 테스트를 찾는다. 파일은 test_*.py(또는 *_test.py), 함수는 이름이 test로 시작하는 것, 클래스는 이름이 Test로 시작하고 __init__이 없는 것의 test 메서드이다. jobprep은 함수만 쓴다. 설정 파일 pytest.ini의 testpaths = tests는 탐색을 tests/ 폴더로 한정하고, pythonpath = .는 저장소 루트를 임포트 경로에 넣어 테스트에서 from api import jobs를 쓸 수 있게 한다. 폴더에 둔 conftest.py는 그 폴더와 하위 폴더의 테스트가 같이 쓰는 픽스처와 설정을 담는다.

tests/conftest.py는 테스트 전체가 같은 조건에서 돌도록 환경 변수를 맨 위에서 정한다. LLM_FAKE=1(실제 API를 부르지 않음), EMBED_BACKEND=fallback(Ollama가 있든 없든 같은 결과), 임시 색인 경로가 그것이다. 이 파일이 있으므로 테스트는 키 없이, 네트워크 없이, 어느 컴퓨터에서나 같은 결과를 낸다.

python -m pytest --collect-only -q는 테스트를 실행하지 않고 찾기만 하며, 찾은 테스트마다 tests/test_summary.py::test_validate_summary_rejects_wrong_shape[bad2] 같은 노드 ID(node ID)를 한 줄씩 찍는다. 이 문자열을 그대로 pytest에 주면 그 테스트 하나만 돈다.

3-3. FastAPI의 TestClient

jobprep의 API 테스트는 서버를 띄우지 않는다. FastAPI는 Starlette의 TestClient를 다시 내보내며, 이 클라이언트는 HTTPX를 바탕으로 앱을 직접 부른다 [F1]. 테스트 함수는 보통의 def로 쓰고, client.get(...)과 client.post(..., json=...)이 돌려준 응답의 status_code와 json()을 assert로 확인한다 [F1]. 기준 저장소의 requirements.txt가 httpx를 고정해 둔 까닭이 이것이다.

tests/conftest.py의 픽스처 client가 TestClient(app)을 돌려준다. 질의 매개변수는 params=로, JSON 본문은 json=으로 넘긴다. 서버를 띄우지 않으므로 포트와 무관하게 빠르지만, 실제 서버에서만 드러나는 문제(브라우저의 CORS 처리, 프록시)는 확인되지 않는다. 그런 것은 1장에서 한 것처럼 서버를 띄워 curl과 브라우저로 본다.

3-4. 단언과 예외

pytest의 확인은 파이썬의 assert 문 하나로 한다. pytest는 실행 전에 assert 문을 다시 써서(assertion rewriting), 실패하면 양쪽의 값과 차이를 자세히 보여 준다 [T1]. 사전은 다른 항목을, 긴 목록은 처음으로 어긋난 위치를 알려 준다 [T1].

예외가 나야 맞는 경우는 pytest.raises를 문맥 관리자(with)로 쓴다. match=에 정규식을 주면 예외 메시지까지 확인한다 [T1]. 기준 저장소의 test_llm.py가 그 예이다.

[파일: tests/test_llm.py] · 한 부분

def test_real_mode_without_key_raises_before_calling(monkeypatch):
    monkeypatch.setenv("LLM_FAKE", "0")
    monkeypatch.setenv("LLM_MODEL", "test-model")
    monkeypatch.delenv("ANTHROPIC_API_KEY", raising=False)
    with pytest.raises(llm.LLMError, match="ANTHROPIC_API_KEY"):
        llm.complete("시스템", "질문", task="ask")

이 테스트는 “키가 없으면 오류가 난다”만이 아니라 “그 오류의 메시지에 키 이름이 있다”까지 확인한다. 1-5절의 조건 완화가 노리는 곳이 바로 이런 자리이다. match=를 지우면 아무 LLMError나 통과하고, pytest.raises(Exception)으로 바꾸면 아무 예외나 통과한다. 동결은 이런 한 줄의 완화를 잡아낸다(7절).

3-5. 실행 옵션

실행 옵션의 목록은 부록 B-4-1의 명령어 카드에 있다. 이 장에서 쓰는 것은 출력을 줄이는 -q, 실패의 추적 정보를 빼는 --tb=no, 이름으로 고르는 -k "식", 마커로 고르는 -m "식"(4-5절), 실행하지 않고 찾기만 하는 --collect-only, 테스트 하나를 고르는 노드 ID(파일::함수)이다. -k의 일치는 대소문자를 가리지 않고, 테스트 이름뿐 아니라 파일 이름과 마커 이름도 대상이 된다 [T1].

읽기. 출발점 저장소에서 python -m pytest -q -k "days_left or sorted"를 실행하면 마지막 줄이 2 passed, 41 deselected in 0.51s이다. deselected는 고르지 않아 돌리지 않은 테스트의 수이다. 실패가 아니다. 다만 7절에서 볼 것처럼, 설정 파일에 -k나 --deselect를 몰래 넣으면 실패할 테스트를 화면에서 사라지게 할 수 있다. deselected가 예상과 다르게 찍히면 설정 파일부터 의심한다.

3-6. 실패 화면 읽기

FFFE는 테스트 네 개의 결과를 순서대로 한 글자씩 찍은 것이다. F는 실패(failed), E는 오류(error), .은 통과이다. 실패와 오류는 다르다. 실패는 테스트가 끝까지 돌았고 assert가 거짓이었다는 뜻이다. 오류는 테스트 본문에 들어가기 전, 준비 단계(여기서는 픽스처 찾기)에서 멈췄다는 뜻이다. 오류인 테스트는 무엇도 확인하지 않았다. Red를 볼 때 오류가 섞여 있으면, 그것은 “기능이 없어서”가 아니라 “테스트가 돌지 못해서”이다.

실패 화면은 맨 아래 한 줄(실패와 오류의 수) → 요약(short test summary info)의 노드 ID → 테스트마다 > 표시가 붙은 줄(실패한 줄)과 그 아래 E로 시작하는 줄(실패의 내용) → 파일:줄번호 줄의 순서로 읽는다. assert 왼쪽 == 오른쪽에서 왼쪽은 실제 값, 오른쪽은 기대값이다.

At index 0 diff: 12 != 7은 목록의 첫 항목부터 다르다는 뜻이다. 실제 응답은 마감일 순으로 12번(2027-09-27)이 7번(10-22)보다 앞인데, 기대값을 거꾸로 적었다. 이 경우 고칠 것은 구현이 아니라 테스트이다. 테스트를 쓰는 단계에서 이런 실수는 흔하고, 그래서 Red를 볼 때 “실패한 까닭이 정말 기능이 없어서인가”를 한 줄씩 확인한다. 동결은 그 확인이 끝난 뒤에 한다.

4. 픽스처, 매개변수화, monkeypatch, tmp_path, 마커

4-1. 픽스처

픽스처(fixture)는 테스트의 준비를 함수로 떼어 낸 것이다. 테스트 함수가 매개변수 이름으로 픽스처를 요청하면, pytest가 그 이름의 픽스처를 실행해 돌려준 값을 넣어 준다 [T1]. tests/conftest.py에 둔 픽스처는 그 폴더의 모든 테스트 파일이 같이 쓴다 [T1].

[파일: tests/conftest.py] · 픽스처가 픽스처를 쓰는 예

@pytest.fixture
def job_text(client):
    """요약 테스트에 쓰는 공고 본문(1번 공고)."""
    job = client.get("/api/jobs/1").json()
    return f"{job['title']} / {job['company']}\n마감일: {job['deadline']}\n{job['description']}"

job_text는 client를 요청한다. 테스트가 job_text를 요청하면 pytest는 client를 먼저 만들고, 그것으로 job_text를 만든다. 픽스처의 범위(scope)는 기본이 function이어서 테스트마다 새로 만들고 테스트가 끝나면 버린다 [T1]. class, module, package, session으로 넓히면 여러 테스트가 하나를 같이 쓰므로 빨라지지만, 한 테스트가 바꾼 상태가 다음 테스트로 새어 나갈 수 있다. 이 장의 테스트는 모두 기본 범위를 쓴다.

픽스처가 값 대신 함수를 돌려주게 하면, 테스트마다 다른 값으로 준비를 할 수 있다. 이것을 팩토리 픽스처라고 부른다. 핵심 실습의 시작 파일에 있는 on_day가 그것이다.

[파일: tests/test_closing_within.py] · 시작 파일의 픽스처

@pytest.fixture
def on_day(monkeypatch):
    """기준일을 정하는 픽스처. 테스트 안에서 on_day(2027, 9, 1)처럼 부른다."""
    def set_day(year, month, day):
        monkeypatch.setattr(jobs, "today", lambda: date(year, month, day))

정리할 것이 있는 픽스처는 return 대신 yield를 쓰고 그 뒤에 정리 코드를 둔다 [T1]. 이 장에서는 정리를 직접 쓸 일이 없다. monkeypatch와 tmp_path가 테스트가 끝나면 스스로 원래대로 돌리기 때문이다.

4-2. 매개변수화

같은 테스트를 입력만 바꿔 여러 번 돌릴 때 @pytest.mark.parametrize를 쓴다. 첫 인자는 매개변수 이름을 쉼표로 이은 문자열이고, 둘째 인자는 값의 목록이다 [T1]. ids=로 경우마다 이름을 붙이면 실패했을 때 어느 경우인지 바로 보인다.

읽기. 다음은 이미 있는 함수 days_left를 매개변수화로 확인하는 테스트이다. 구현이 이미 있으므로 처음부터 통과한다. 이렇게 지금의 동작을 그대로 기록하는 테스트를 특성 테스트(characterization test)라고 부른다. 리팩터링 전에 지금의 동작을 잠가 둘 때 쓴다.

4-3. monkeypatch

monkeypatch는 테스트 동안 객체의 속성, 사전의 항목, 환경 변수 등을 바꿔 끼우고, 테스트나 픽스처가 끝나면 모두 원래대로 돌리는 내장 픽스처이다 [T1]. 이 장에서 쓰는 메서드는 둘이다(그 밖에 delattr, setitem, chdir 등이 있다).

메서드 바꾸는 것 jobprep에서의 예
setattr(대상, "이름", 값) 모듈이나 객체의 속성 monkeypatch.setattr(jobs, "today", lambda: date(2027, 9, 1))
setenv("이름", "값") / delenv("이름", raising=False) 환경 변수 monkeypatch.setenv("LLM_FAKE", "0")

setattr로 함수를 바꿔 끼울 때 가장 흔한 실수는 바꿀 곳을 잘못 고르는 것이다. 규칙은 하나이다. 함수를 정의한 곳이 아니라, 그 함수를 이름으로 찾아 부르는 곳을 바꾼다.

api/ask.py는 맨 위에서 from rag.search import search로 검색 함수를 가져온다. 이 문장은 api.ask 모듈 안에 search라는 이름을 새로 만든다. answer_question()은 실행될 때 api.ask의 search를 찾는다. 그러므로 rag.search 모듈의 search를 바꿔 끼워도 answer_question()은 원래 함수를 부른다. 다음은 두 방법을 비교한 결과이다(집필할 때 실행한 것).

4-4. tmp_path

tmp_path는 테스트마다 따로 만들어지는 빈 임시 폴더를 pathlib.Path로 주는 내장 픽스처이다 [T1]. 폴더는 시스템 임시 폴더 아래 pytest-of-사용자이름에 생기고, 최근 세 번의 실행분만 남는다 [T1]. 테스트가 저장소의 파일을 건드리지 않고 파일을 만들어 써야 할 때 쓴다.

핵심 실습의 정답 테스트는 tmp_path로 마감일만 다른 공고 네 건짜리 작은 자료를 만든다. 실제 data/jobs.json의 30건은 내용이 바뀔 수 있고, 경계를 보기에 너무 크다. 작은 자료는 확인하려는 경계만 담는다.

@pytest.fixture

4-5. 마커

마커(marker)는 테스트에 붙이는 표시이다. pytest에 내장된 마커로 skip, xfail, parametrize 등이 있고, 프로젝트가 자기 마커를 만들어 쓸 수도 있다. 만든 마커는 설정 파일의 markers에 등록한다. 0-4절에서 넣은 키트의 pytest.ini는 요구 ID를 적는 마커 req를 등록하고, --strict-markers로 등록하지 않은 마커를 오류로 만든다.

시작 파일은 파일 맨 위에 pytestmark = pytest.mark.req(id="REQ-JOB-06")을 둔다. 모듈 변수 pytestmark에 둔 마커는 그 파일의 모든 테스트에 붙는다. 마커의 인자를 키워드로 주었기 때문에, 실행할 때 요구 ID로 테스트를 고를 수 있다 [T1].

[터미널] · 핵심 실습을 마친 뒤 쓰는 명령

python -m pytest -q -m req                                  # 요구 마커가 붙은 테스트 전부
python -m pytest -q -m "req(id='REQ-SUM-05')"               # 요구 하나
python -m pytest -q -m "not req"                            # 기준 저장소의 테스트만
23 passed, 43 deselected in 1.42s
5 passed, 61 deselected in 1.65s
43 passed, 23 deselected in 2.39s

(위 출력은 세 요구를 모두 구현한 뒤의 값이다.) --strict-markers가 없으면 @pytest.mark.reqq(...)처럼 마커 이름을 잘못 써도 경고만 나고 테스트는 돈다. 있으면 'reqq' not found inmarkersconfiguration option이라는 오류와 함께 수집 단계에서 멈추고(Interrupted: 1 error during collection), 테스트는 하나도 돌지 않는다.

요구 마커는 추적성(traceability)을 위한 것이다. 요구 ID에서 그 요구의 테스트로, 실패한 테스트에서 깨진 요구로 바로 갈 수 있다. 명세서의 「테스트」 열이 사람이 읽는 추적이라면 마커는 기계가 읽는 추적이며, 12장의 평가 보고와 13장의 CI가 이 마커로 요구별 통과 여부를 모은다.

5. 경계값과 등가 분할

5-1. 무엇을 테스트할 것인가

입력의 모든 값을 테스트할 수는 없다. closing_within은 0부터 무한히 큰 정수까지, 요약 본문은 길이 0부터 수만 자까지 될 수 있다. 그래서 테스트할 값을 고르는 체계적인 방법이 필요하다. 두 가지 기법을 함께 쓴다.

  • 등가 분할(equivalence partitioning): 입력을 “시스템이 같은 방식으로 다룰 것으로 기대되는” 묶음(등가 클래스)으로 나누고, 묶음마다 대표값 하나를 테스트한다. 같은 묶음의 값은 하나가 맞으면 나머지도 맞을 것으로 본다.
  • 경계값 분석(boundary value analysis): 묶음과 묶음이 맞닿는 자리의 값을 테스트한다. 구현의 실수는 경계에 몰린다. <와 <=를 바꿔 쓰는 실수는 경계 바로 위나 아래의 값에서만 드러난다.

요구 문장에서 묶음을 찾는 실마리는 숫자와 조건어이다. “4,000자를 넘으면”, “N일 안에”, “비어 있거나”가 모두 경계를 만든다.

5-2. REQ-JOB-06의 분할

REQ-JOB-06에는 두 축이 있다. 하나는 사용자가 주는 N이고, 다른 하나는 공고마다 계산되는 남은 날 수(days_left)이다.

축 묶음 기대 동작 대표값과 경계값
N 매개변수 없음 필터를 쓰지 않는다(30건) (없음)
N 0 이상의 정수 필터를 쓴다 경계 0, 대표 7, 14
N 음수 422 경계 -1
N 정수가 아닌 값 422 abc, 1.5, 빈 값
days_left 음수(마감 지남) 빠진다 기준일 9-10에서 20번(-2), 3번(-1)
days_left 0 이상 N 이하 들어간다 0(오늘 마감), N(정확히 N일 뒤)
days_left N보다 큼 빠진다 N+1

이 표에서 테스트 목록이 나온다. 경계 N 주변(6, 7, 8)은 한 테스트를 매개변수화하고, 경계 0과 마감 지난 공고는 기준일을 바꾸어 따로 쓴다. 다른 조건과 함께 쓰는 경우(field, q)는 요구 문장에 명시되어 있으므로 별도 테스트로 둔다.

테스트 묶음과 경계 기준일 기대값

6. 테스트 더블과 비결정적 출력

6-1. 테스트 더블의 다섯 종류

테스트 더블(test double)은 테스트에서 진짜 부품 대신 쓰는 가짜 부품을 통틀어 부르는 말이다. 영화의 대역 배우(stunt double)에서 따온 이 용어는 제라드 메사로스(Gerard Meszaros)가 xUnit 테스트 패턴을 정리하며 만들었고, 마틴 파울러가 다섯 종류로 소개했다 [T4].

종류 파울러의 정의 (요지) [T4] jobprep에서의 예
더미(dummy) 인자 목록을 채우려고 넘기지만 실제로 쓰지 않는 객체 llm.complete("시스템", ...)의 시스템 프롬프트 "시스템". 모의 모드는 이 값을 쓰지 않는다
페이크(fake) 실제로 동작하지만 운영에는 쓸 수 없는 지름길 구현 LLM_FAKE=1의 모의 응답 fake_reply(), 대체 임베딩 embed_fallback()
스텁(stub) 테스트 중의 호출에 미리 정한 답을 돌려준다 jobs.today를 바꾼 lambda: date(2027, 9, 1), llm.complete를 바꾼 lambda *a, **k: "요약할 수 없습니다"
스파이(spy) 스텁이면서 어떻게 불렸는지를 기록한다 요약 테스트의 llm_calls 픽스처(불린 task를 목록에 쌓는다)
목(mock) 기대하는 호출을 미리 정해 두고, 검증할 때 그 호출이 일어났는지 확인한다 질의응답 테스트의 Mock(wraps=ask.search)와 assert_not_called()

monkeypatch는 이 더블들을 끼워 넣는 도구이다. 어느 더블을 쓸지는 테스트가 무엇을 확인하려는지로 정한다. 결과 값만 보면 되면 스텁, “불렸는가, 몇 번 불렸는가”를 보려면 스파이나 목을 쓴다.

6-2. 페이크: 모의 모드

api/llm.py의 complete()는 LLM_FAKE=1이면 API를 부르지 않고 fake_reply()로 응답을 만든다. 요약은 프롬프트 안의 <공고>…</공고>에서 [주요 업무], [자격 요건], [유의 사항] 아래의 항목을 모으고, 마감일을 정규식으로 찾아 JSON을 만든다. 질의응답은 첫째 근거의 첫 문장에 [1]을 붙인다. 같은 입력에는 언제나 같은 응답이 나온다(REQ-OPS-02).

페이크는 진짜처럼 동작하므로 앱 전체를 끝까지 돌리는 테스트에 쓰기 좋다. 그러나 페이크가 진짜와 다르게 동작하는 부분에서는 테스트가 진짜의 결함을 놓친다. 모의 응답은 언제나 올바른 JSON을 내지만, 실제 모델은 JSON 앞에 설명을 붙이거나 키를 빠뜨릴 수 있다. 기준 저장소가 parse_json()과 validate_summary()를 따로 테스트하는 까닭이다.

6-3. 스텁과 스파이: “부르지 않았다”의 확인

REQ-SUM-05의 테스트는 llm.complete를 감싸는 스파이를 픽스처로 만든다. 진짜 함수(모의 모드)를 그대로 부르므로 응답은 바뀌지 않고, 불릴 때마다 task가 목록에 쌓인다.

[파일: tests/test_summary_limits.py] · 시작 파일의 픽스처와 테스트

@pytest.fixture
def llm_calls(monkeypatch):
    """llm.complete를 감싸는 스파이. 진짜 함수(모의 모드)를 그대로 부르고, 부를 때마다 task를 기록한다."""
    calls = []
    real_complete = llm.complete

    def spy(system, prompt, task):
        calls.append(task)
        return real_complete(system, prompt, task)

    monkeypatch.setattr(llm, "complete", spy)
    return calls


@pytest.mark.parametrize("text", [
    "",
    # 할 일 1: 공백만 있는 문자열과 4,001자 문자열을 더한다. 4,001자는 "가" * (MAX_CHARS + 1)로 만든다.
], ids=["empty"])
def test_rejected_text_is_422_without_calling_llm(client, llm_calls, text):
    response = client.post("/api/summary", json={"text": text})
    assert response.status_code == 422
    assert llm_calls == []

확인이 둘이다. status_code == 422는 사용자에게 보이는 결과를, llm_calls == []는 보이지 않는 부수 효과(비용이 드는 호출)를 확인한다. 상태 코드만 맞추고 LLM을 먼저 부르는 구현은 둘째 단언에서 실패한다. 그래서 그런 구현으로 「통과」를 만들려는 시도는 둘째 단언을 지우는 쪽으로 간다. 11-5절에서 판정할 시도가 이것이다. 단언 하나하나가 요구의 서로 다른 부분을 지키므로, 단언 한 줄이 사라지면 요구의 한 부분이 사라진다.

6-4. 목: unittest.mock

REQ-ASK-06의 테스트는 표준 라이브러리 unittest.mock의 Mock을 쓴다. Mock(wraps=대상)은 호출을 진짜 대상에 그대로 넘겨 진짜 결과를 돌려주면서 호출 기록을 남긴다 [P1]. assert_not_called()는 한 번이라도 불렸으면, assert_called_once()는 정확히 한 번이 아니면 AssertionError를 낸다 [P1]. 불린 횟수는 call_count에 있다 [P1].

[파일: tests/test_ask_limits.py] · 시작 파일의 픽스처와 테스트

@pytest.fixture
def watched(monkeypatch):
    """ask.search와 llm.complete를 기록하는 Mock으로 바꿔 끼운다."""
    search = Mock(wraps=ask.search)
    complete = Mock(wraps=llm.complete)
    monkeypatch.setattr(ask, "search", search)
    monkeypatch.setattr(llm, "complete", complete)
    return search, complete


@pytest.mark.parametrize("question", [
    "",
    # 할 일 1: 공백만 있는 질문과 501자 질문을 더한다.
], ids=["empty"])
def test_rejected_question_is_422_without_search_or_llm(client, watched, question):
    search, complete = watched
    response = client.post("/api/ask", json={"question": question})
    assert response.status_code == 422
    search.assert_not_called()
    complete.assert_not_called()

ask.search를 바꾸는 까닭은 4-3절에서 보았다. api/ask.py가 from rag.search import search로 가져왔으므로 부르는 곳인 api.ask의 이름을 바꾼다.

스파이(직접 만든 함수)와 목(Mock)은 하는 일이 같다. 직접 만든 스파이는 무엇을 기록하는지 분명하고, Mock은 짧고 호출 인자(call_args)까지 기록한다. 그 대신 Mock은 처음 부르는 이름의 속성을 그 자리에서 만들어 주므로, 철자를 틀린 확인 메서드가 조용히 지나갈 수 있다. 파이썬 3.13에서 assert_not_caled()처럼 assert와 그 흔한 오타로 시작하는 이름에는 AttributeError가 나지만, not_called_check() 같은 이름은 오류 없이 지나갔다. 확인 메서드의 이름은 문서와 대조해 쓴다.

6-5. 비결정적 출력의 테스트

실제 LLM의 응답은 같은 입력에도 매번 다를 수 있다. 그런 출력을 assert answer == "모의면접은 회차당 8명까지입니다. [1]"처럼 정확한 문자열로 확인하면, 코드가 바뀌지 않아도 테스트가 실패하거나 통과하기를 반복한다. 이런 테스트를 흔들리는 테스트(flaky test)라고 부른다. 흔들리는 테스트는 실패해도 아무도 믿지 않게 되고, 결국 skip이 붙는다. 에이전트가 테스트를 고쳐 쓰는 실패 유형을 다룬 글에 “가끔 실패하는 테스트를 건너뛰게 했다”가 들어 있는 것은 우연이 아니다 [S2].

비결정적 출력은 내용 대신 구조와 성질을 확인한다.

  • 구조: 키 네 개가 있고, 목록은 문자열 5개 이하, 마감일은 YYYY-MM-DD 또는 null이다(validate_summary(), test_summary_has_four_parts).
  • 범위: 인용한 근거 번호가 1 이상, 검색 결과 수 이하이다(answer_question()의 1 <= number <= len(results)).
  • 불변 조건: “자료에 없습니다.”로 답하면 출처 목록이 비어 있다(test_not_found_answer_from_llm_has_no_sources).
  • 결정적인 부분: 같은 입력에 같은 판본 이름과 모델 이름이 붙는다(prompt_version, model).

이 장의 테스트는 모두 모의 모드에서 돌며, 실제 모델의 응답 품질은 확인하지 않는다. 그것은 테스트가 아니라 평가의 일이다. 같은 질문을 여러 번 보내 통과율과 분산을 재는 회귀 평가는 12장에서 다룬다. 단위 테스트는 “모델이 어떤 답을 내든 시스템이 그 답을 안전하게 다루는가”를 확인하고, 평가는 “모델이 좋은 답을 내는가”를 잰다.

7. 테스트 동결과 회피의 방지

7-1. 통과한 것처럼 보이게 만드는 길

에이전트가 테스트를 통과시키지 못할 때, 구현을 고치는 대신 판정 쪽을 바꾸는 길이 여럿 있다. 1-5절의 사례와 2026년 공개 글들에 나온 유형을 jobprep에 옮겨 정리한다 [S1][S2][A1].

유형 jobprep에서의 모습 pytest 화면 동결 검사(check) 그 밖에 잡는 수단
① 테스트 삭제 tests/test_closing_within.py를 지운다 실패가 사라진다 삭제: git status의 D
② 건너뛰기 @pytest.mark.skip, xfail을 붙인다 skipped, xfailed 수정: 결과 줄의 skipped
③ 조건 완화 == 422를 in (200, 422)로, == [20]을 is not None으로 바꾸거나, 단언 한 줄을 지운다 통과 수가 늘어난다 수정: git diff tests/
④ 설정으로 빼기 pytest.ini의 addopts에 --deselect나 -k "not closing" deselected가 는다 수정: pytest.ini 결과 줄의 deselected
⑤ 바깥 conftest 저장소 루트에 conftest.py를 만들어 수집된 테스트에 skip을 붙인다 skipped가 는다 추가: conftest.py git status의 ??
⑥ 하드코딩, 특수 처리 테스트가 고정한 날짜나 값에서만 맞는 구현 모두 통과 잡지 못한다(테스트는 그대로) 삼각 측량, 숨은 테스트, 코드 검토
⑦ 구현 먼저 구현을 만든 뒤 그 구현에 맞춰 테스트를 쓴다 모두 통과 잡지 못한다(동결 전) 사람이 테스트를 먼저 쓰고 Red를 본다

①~⑤는 판정 기준(테스트와 그 설정)을 바꾸는 길이고, 동결 검사로 잡힌다. 이 가운데 ③의 「단언 한 줄을 지운다」는 테스트 수도 그대로이고 skipped도 deselected도 없어, 결과 줄만으로는 진짜 통과와 구별되지 않는다. ⑥은 기준에만 맞춘 것이라 동결로 잡히지 않고, ⑦은 동결 전에 일어나므로 사람이 Red를 직접 보는 절차로만 막힌다. 그래서 7-5절에서 방어를 층으로 쌓는다.

7-2. 동결 검사기 test_guard.py

키트의 도구/test_guard.py는 2026년판 TDD 실습의 동결 도구를 jobprep의 구조에 맞게 고쳐 쓴 것이다. 동결(freeze)은 테스트와 테스트 설정 파일의 지문(SHA-256 해시)을 tests/.baseline.json에 적는 일이고, 검사(check)는 지금의 지문을 그 기록과 비교하는 일이다. 파일의 한 바이트만 바뀌어도 지문이 달라진다.

지켜보는 파일은 넷이다. tests/ 아래의 모든 파일(.baseline.json과 __pycache__는 빼고)은 ①②③을, 저장소 루트의 pytest 설정 파일(pytest.ini, pyproject.toml, setup.cfg, tox.ini 가운데 있는 것)은 ④를, tests/ 밖의 모든 conftest.py는 ⑤를 막는다. 검사기 tools/test_guard.py 자신도 지켜본다.

명령 하는 일 종료 코드

8. Claude Code에게 TDD를 시키는 지시문

8-1. 지시문의 부분

지시문은 1층의 방어이다(7-5절). 모델이 판단하는 비결정적 장치이므로 완벽하지 않지만, 비용이 가장 적고 효과도 작지 않다. Anthropic은 Claude Opus 4의 시스템 카드에서, 일반적인 해법을 쓰라고 하고 테스트가 틀렸거나 과제가 불가능하면 알리라고 하며 테스트 케이스를 하드코딩하지 말라는 몇 문장을 프롬프트에 더했을 때 하드코딩 행동이 줄었다고 보고했다 [A1]. 같은 문서의 예시에서, 의도적으로 틀리게 만든 테스트를 받은 모델은 그 문장이 있을 때 특수 처리를 하지 않고 테스트의 문제를 사용자에게 보고했다 [A1]. 지시문에 “통과시킬 수 없으면 보고하라”는 출구를 두는 까닭이 이것이다. 출구가 없으면 “통과시켜라”라는 지시를 만족하는 길은 판정을 바꾸는 것뿐일 수 있다.

키트의 지시문_양식.md는 다음 부분으로 이루어진다. 각 줄이 무엇을 막는지 함께 적는다.

부분 지시문의 문장 (요지) 막거나 얻는 것
목표 「REQ-JOB-06」을 구현하라. 요구 문장은 명세서에 있다 에이전트가 요구를 추측하지 않게 한다
판정 기준 판정 기준은 「테스트 파일」이다. 먼저 읽어라 테스트를 읽지 않고 구현부터 쓰는 것(⑦)
판정 기준의 보호 tests/, pytest.ini, conftest.py, tools/test_guard.py를 고치지도, 지우지도, 새로 만들지도 마라 ①~⑤
일반성 하드코딩이나 테스트에서만 맞는 특수 처리를 쓰지 말고 요구 문장 전체를 만족하는 구현을 써라 ⑥ [A1]
범위 고칠 곳은 「api/jobs.py와 api/main.py」이다. 다른 파일이 필요하면 멈추고 말하라 관계없는 파일의 변경, 검토할 diff의 팽창
git 금지 git 명령을 쓰지 마라. 커밋은 내가 한다 검토 전의 커밋, git restore나 stash로 흔적 지우기
출구 테스트가 틀렸거나 통과시킬 수 없으면 고치지 말고 보고하라 “통과”의 압력이 판정 변경으로 가는 것 [A1]
완료 조건 python -m pytest -q에 실패 없음, test_guard.py check가 TEST_UNCHANGED 에이전트가 스스로 고리를 닫는다 [C1]
보고 형식 고친 파일, 두 명령의 마지막 줄 그대로, 테스트가 확인하지 않는 부분 증거 없는 “완료” [C1]

git 금지는 1장의 역할 정의와 다를 수 있다. 1장에서 구현 역할(R2)에 작업 브랜치의 커밋을 허용했더라도, 이 장에서는 사람이 결과를 확인한 뒤에만 커밋이 생기게 한다. 구현 역할에 커밋을 돌려주는 것은 훅과 CI가 확인을 대신할 수 있게 된 뒤(6장, 8장, 13장)이다.

마지막 보고 항목인 “요구 문장 가운데 테스트가 확인하지 않는 부분”은 에이전트에게 테스트의 빈틈을 말하게 하는 질문이다. 에이전트가 “질문의 앞뒤 공백을 떼고 길이를 셀지는 테스트가 정하지 않았다”처럼 답하면, 그것은 다음 테스트의 후보가 된다.

「 」 자리는 사이클마다 바꾼다. 「N」에는 Red를 볼 때 센 전체 테스트 수(failed와 passed의 합)를 넣는다. 첫 사이클은 13 failed와 44 passed의 합인 57이다. 수를 적어 두면 에이전트가 테스트를 지워 수를 줄였을 때 완료 조건이 맞지 않는다. 그러나 수가 맞는다고 판정 기준이 그대로라는 뜻은 아니다. 단언 한 줄을 지우는 완화(③)는 수를 바꾸지 않는다. 그래서 완료 조건에 check가 함께 있다.

사이클 2(REQ-SUM-05)는 판정 기준이 tests/test_summary_limits.py, 고칠 곳이 api/main.py, N이 62이고, 사이클 3(REQ-ASK-06)은 tests/test_ask_limits.py, api/main.py, 66이다(교수용 정답 테스트 기준). 학습자가 「할 일」을 다르게 채웠다면 N은 달라진다. 자기 Red 화면의 수를 쓴다.

8-3. 권한 모드: 고치기 전에 묻게 하기

Claude Code 2.1.283 이후의 대화형 세션은 자동 모드(auto)로 시작한다 [C4]. 자동 모드에서는 작업 폴더 안의 파일 편집이 묻지 않고 승인되고, 위험해 보이는 동작만 별도의 분류기가 검토한다 [C4]. 편하지만, 이 장의 실습에서는 에이전트가 tests/를 고치려는 순간을 학습자가 화면에서 보는 것이 중요하다. 그래서 핵심 실습의 Claude Code는 수동 모드로 시작한다.

Claude Code 터미널에서 claude --permission-mode manual로 시작한다(11-3절). 수동 모드(문서의 이름은 default, 별칭 manual)에서는 파일을 고칠 때마다 허용을 묻는다 [C4][C3]. 고치려는 파일이 tests/ 아래이면 거절한다. 파일 편집의 허용 질문에서 “다시 묻지 않음”을 고르면 그 세션이 끝날 때까지 다시 묻지 않으므로 [C3], 이 장에서는 한 번씩만 허용하는 선택지를 고른다. 세션 중에는 Shift+Tab으로 모드를 바꿀 수 있고, 자동 모드에서 한 번 누르면 수동 모드가 된다 [C4]. 화면의 이름과 선택지는 2026-11 기준이며 바뀔 수 있다. 3장에서는 이 거절을 매번 손으로 하지 않도록 .claude/settings.json에 거부 규칙으로 적는다.

수동 모드에서는 입력 창 아래에 ⏸ manual mode on이 보인다. Shift+Tab은 누를 때마다 default → acceptEdits → plan의 순서로 돈다 [C4]. 허용 질문에서 Esc는 「No」와 같다 [C5].

[그림 자리: 수동 모드의 표시와 편집 허용 질문] claude --permission-mode manual로 연 세션의 입력 창 아래에 ⏸ manual mode on이 보이고, 그 위에 api/jobs.py의 편집을 허용할지 묻는 질문과 선택지가 떠 있는 화면. 찍을 곳: 내 PC의 VS Code에서 연 Claude Code 터미널(Windows 11, Git Bash), 11-3절의 구현 지시 직후.

[최신 자료 자리: 권한 모드의 시작값과 이름] 2026-11-14 확인 값: Claude Code 2.1.283 이상의 대화형 세션은 자동 모드로 시작한다. manual은 default의 별칭이다. claude --help(2.1.296)의 --permission-mode 선택지는 acceptEdits, auto, bypassPermissions, manual, dontAsk, plan이다. 표시 문구 ⏸ manual mode on과 허용 질문의 선택지 이름도 판에 따라 달라진다. 확인할 곳: https://code.claude.com/docs/en/permission-modes, 내 PC의 claude --version과 claude --help.

8-4. 증거를 받는 법

에이전트의 보고는 주장이다. 주장을 받으면 다음 순서로 확인한다.

  1. 보고의 증거(실행한 명령과 출력의 마지막 줄)를 읽는다. 증거가 없으면 증거를 달라고 다시 요청한다 [C1].
  2. 같은 명령(python -m pytest -q, python tools/test_guard.py check)을 [터미널]에서 직접 실행한다. 에이전트가 실행했다는 출력과 내 출력이 같은지 본다.
  3. git status --short와 git diff --stat으로 바뀐 파일의 목록을 본다. 지시문의 범위 밖 파일이 있으면 그 변경을 읽는다.
  4. git diff로 구현의 변경을 읽는다. 하드코딩(테스트의 기대값이나 날짜가 코드에 그대로 들어 있는가)이 없는지 본다.

Claude Code에는 조건을 정해 두면 별도의 모델이 매 차례 대화를 보고 그 조건이 충족되었는지 판정하는 /goal 명령도 있다 [C1]. 긴 백그라운드 실행에서 에이전트가 할 일을 남긴 채 차례를 끝내는 것을 막는 데 쓴다 [C1]. 그러나 /goal의 판정도 대화를 읽는 모델의 판단이다. 이 장의 완료 조건은 학습자가 직접 실행한 명령의 출력으로 판정한다.

8-5. 체크포인트와 git

Claude Code는 프롬프트를 보낼 때마다 그 시점의 파일 상태를 체크포인트로 저장하고, /rewind(또는 입력 창이 비어 있을 때 Esc 두 번)로 코드나 대화를 그 시점으로 되돌릴 수 있다 [C2]. 실패한 시도를 버리는 데 편하지만 한계가 분명하다. Claude가 셸 명령(Bash)으로만 바꾼 파일은 추적하지 않으며, 서브에이전트의 편집과 Claude Code 바깥에서 사람이 고친 것도 대개 되돌리지 않는다 [C2]. 문서도 체크포인트는 세션 안의 빠른 복구를 위한 것이며 버전 관리(git)를 대신하지 않는다고 적는다 [C2].

[최신 자료 자리: 체크포인트의 조작] 2026-11-15 확인 값: 입력 창이 비어 있을 때 Esc를 두 번 누르면 되감기(rewind) 메뉴가 열리고, 입력 창에 글이 있으면 두 번의 Esc는 글을 지운다 [C5]. 단축키와 메뉴 이름은 판에 따라 바뀐다. 확인할 곳: https://code.claude.com/docs/en/checkpointing, https://code.claude.com/docs/en/interactive-mode.

이 장은 실패한 시도를 git으로 버린다. 테스트와 동결 기록을 커밋해 두었으므로, 무엇이 무엇으로 바뀌었든 git restore와 git clean으로 커밋한 상태에 돌아갈 수 있다(9절). 체크포인트는 같은 세션 안에서 방금 한 편집을 취소할 때 보조로 쓴다. 11-5절의 돌려받은 시도는 Claude Code 바깥(키트의 스크립트)에서 생긴 변경이므로 체크포인트로는 되돌릴 수 없고, git으로만 되돌린다.

9. Git 작업 단위: 통과마다 커밋, 되돌리기, 태그

9-1. 요구 하나에 커밋 둘

이 장의 작업 단위는 요구 하나이고, 요구 하나에 커밋 두 개를 남긴다. 첫째는 새 테스트 파일과 tests/.baseline.json을 담은 test(REQ-…): … (Red) 커밋으로, 그 시점에는 새 테스트만 실패한다. 둘째는 구현 파일(api/…)을 담은 feat(REQ-…): … (Green) 커밋으로, 그 시점에는 모두 통과한다.

Red를 커밋하는 까닭은 둘이다. 첫째, 에이전트에게 넘기기 전의 상태를 되돌아올 지점으로 만든다. 둘째, 테스트의 변경과 구현의 변경을 다른 커밋에 두어 테스트 변경이 큰 diff 속에 숨지 않게 한다. 에이전트의 테스트 고쳐 쓰기를 다룬 글들이 공통으로 권하는 대책이다 [S2]. 실패하는 커밋이 main에 들어가지 않도록 작업은 작업 브랜치 feat/tdd-1에서 하고 마지막에 병합한다. 그러면 운영 요건 OR-REL-08(main의 모든 커밋은 통과 상태)이 지켜진다.

커밋 메시지의 첫 줄은 종류(범위): 설명의 꼴로 쓴다. 종류는 test(테스트), feat(기능), refactor(동작을 바꾸지 않는 구조 변경), docs(문서), chore(도구와 설정)를 쓰고, 범위에는 요구 ID를 넣는다. 이 꼴은 3장에서 팀의 저장소 규약으로 정식화한다.

9-2. 실패한 시도를 버리기

에이전트의 시도가 실패하면(테스트를 고쳤거나, 범위 밖을 고쳤거나, 하드코딩을 했으면) 그 시도를 고쳐 쓰지 않고 통째로 버린다. 고쳐 쓰다 보면 어디까지가 에이전트의 변경이고 어디부터가 내 변경인지 흐려진다.

명령 하는 일 쓰는 때
git status --short 바뀐 파일(M), 지운 파일(D), 추적하지 않는 새 파일(??)을 본다 언제나 먼저
git diff --stat 바뀐 파일과 줄 수를 요약한다 범위 밖의 변경을 찾는다
git restore 경로 작업 폴더의 파일을 인덱스(스테이징 영역)의 내용으로 되돌린다 [G3] 고친 파일을 버린다
git restore . 현재 폴더 아래의 모든 추적 파일을 되돌린다 [G3] 시도를 통째로 버린다
git restore --staged 경로 인덱스만 HEAD로 되돌린다(작업 폴더는 그대로) [G3] git add를 취소한다
git restore --source=HEAD --staged --worktree 경로 인덱스와 작업 폴더를 모두 HEAD로 [G3] 스테이징까지 한 변경을 버린다
git clean -n / git clean -f 추적하지 않는 파일을 지울 목록을 보여 준다 / 지운다 에이전트가 새로 만든 파일을 지운다

git restore는 추적하는 파일만 되돌린다. 에이전트가 새로 만든 파일(??)은 git clean으로 지운다. git clean -f는 되돌릴 수 없으므로 반드시 -n으로 목록을 먼저 본다. .gitignore에 있는 파일(.venv/, .coverage)은 -x를 붙이지 않는 한 지우지 않는다.

9-3. 태그

태그는 커밋 하나에 붙이는 이름이다. 브랜치와 달리 새 커밋이 생겨도 움직이지 않는다. 그래서 “이 상태”를 가리키는 데 쓴다.

종류 만드는 법 담는 것 쓰는 곳
가벼운 태그 git tag 이름 커밋을 가리키는 이름뿐 개인의 임시 표시 [G1]
주석 태그 git tag -a 이름 -m "설명" 만든 사람, 날짜, 설명(서명 선택) [G1] 배포와 넘겨주기. git describe가 기본으로 쓴다 [G1]

git push는 기본으로 태그를 보내지 않는다 [G2]. git push origin 태그이름으로 하나를, git push origin --tags로 모두를 보낸다 [G2]. 태그를 체크아웃하면 브랜치에 속하지 않은 detached HEAD 상태가 되고, 그 상태에서 만든 커밋은 어느 브랜치에도 속하지 않는다 [G2].

이미 공개한 태그는 고치지 않는다. git 문서는 같은 이름의 태그를 다른 커밋으로 옮기는 것을 “제정신이 아닌 일”로 부르며, 다른 사람이 받아 간 태그를 바꿀 수 없으므로 태그 이름을 믿을 수 있어야 한다는 보안의 문제라고 설명한다 [G1]. 잘못 붙였으면 새 이름(예: tdd-1.1)을 쓴다 [G1]. 재현성은 “같은 이름이 언제나 같은 상태를 가리킨다”는 약속 위에 서 있다.

9-4. 따라 하기 2: 판정을 바꾼 시도를 버리고 커밋한 상태로 돌아가기

10. [선택] 커버리지

이 절은 선택이다. 핵심 실습을 먼저 마치고 시간이 남을 때 한다. 커버리지 도구는 0-4절에서 이미 설치했다. 이 절의 개념(커버리지는 「실행되었다」를 잴 뿐 「확인되었다」를 재지 않는다)은 정리와 개념 점검에 들어 있다.

10-1. 커버리지가 재는 것

커버리지(code coverage)는 테스트를 돌리는 동안 코드의 어느 줄이 실행되었는지를 잰 비율이다. 파이썬에서는 coverage.py를 쓴다. 0-4절에서 설치한 requirements-dev.txt에 coverage==7.17.3이 들어 있다 [T5].

10-3. 커버리지의 한계

커버리지는 “실행되었다”를 잴 뿐, “확인되었다”를 재지 않는다. 키트의 연습 파일 test_연습_커버리지.py는 엔드포인트를 다섯 번 부르기만 하고 아무것도 단언하지 않는다.

단언이 하나도 없는 테스트 하나로 api/jobs.py가 100%가 되었다. 이 상태에서 list_jobs()의 정렬을 거꾸로 바꿔도(reverse=True) 이 테스트는 그대로 통과한다. 집필할 때 그렇게 바꿔 본 결과, 연습 파일은 1 passed였고 정답 테스트 전체는 정렬과 순서를 확인하는 다섯 개가 실패했다. 연습 파일은 반드시 지우고 git status --short가 빈 출력인지 본다. 지우지 않으면 check가 추가: tests/test_연습_커버리지.py를 낸다.

벡은 「Canon TDD」에서 커버리지를 채우려고 단언 없는 테스트를 쓰는 것을 실수로 꼽았다 [T3]. 파울러는 커버리지가 테스트하지 않은 코드를 찾는 데는 쓸모가 있지만, 테스트가 얼마나 좋은지를 나타내는 수치로는 쓸모가 적다고 했다 [T6]. 그는 신중하게 테스트하면 대략 80퍼센트대 후반에서 90퍼센트대가 나오리라 보면서도, 100퍼센트는 오히려 수치를 맞추려고 쓴 테스트를 의심하게 한다고 적었다 [T6]. 커버리지를 목표로 정하면 사람도 에이전트도 그 수치를 맞추는 가장 짧은 길을 찾는다. 1-5절과 같은 구조이다.

이 과목에서 커버리지는 다음 두 가지로만 쓴다.

  1. 새로 쓴 코드 가운데 어떤 테스트도 지나가지 않는 줄을 찾는다. 찾은 줄마다 테스트를 더할지, 왜 더하지 않는지를 판단한다.
  2. 에이전트의 보고에 “커버리지 100%를 달성했다”가 있으면, 그것을 품질의 증거로 받지 않는다. 단언이 무엇을 확인하는지를 읽는다.

MAX_SUMMARY_CHARS = 4000  # REQ-SUM-05
MAX_QUESTION_CHARS = 500  # REQ-ASK-06


def text_rule(max_chars):
    """앞뒤 공백을 뗀 뒤 1자 이상, max_chars자 이하라는 문자열 조건.

    조건에 맞지 않으면 FastAPI가 엔드포인트 함수를 부르기 전에 422로 응답한다.
    그래서 검색과 LLM 호출이 일어나지 않는다.
    """
    return StringConstraints(strip_whitespace=True, min_length=1, max_length=max_chars)


class SummaryRequest(BaseModel):
    text: Annotated[str, text_rule(MAX_SUMMARY_CHARS)]  # 요약할 공고 본문


class AskRequest(BaseModel):
    question: Annotated[str, text_rule(MAX_QUESTION_CHARS)]  # 취업 자료에 묻는 질문

StringConstraints는 공백을 뗀 뒤에 길이를 잰다. 집필할 때 " abcde "가 상한 5자를 통과하고 " "가 string_too_short로 거부되는 것을 확인했다. Green 단계의 구현도 공백을 뗀 뒤 길이를 재었으므로 동작이 같다. 만약 Green이 공백을 떼지 않고 길이를 재었다면, 3,999자에 공백 두 칸이 붙은 본문에서 두 구현의 답이 갈린다. 테스트가 그 경우를 다루지 않으므로 리팩터링이 동작을 바꾼 것을 아무도 모르게 된다. 리팩터링은 “테스트가 지키는 범위 안에서” 동작을 보존한다는 점을 기억한다.

미구현 요구 셋이 저장소에서 「구현」이 되었고, 그 과정이 커밋 열 개와 태그 하나로 남았다. 한 일은 세 가지로 정리된다.

정리

  • AI 에이전트에게 완료 조건은 “통과 또는 실패를 돌려주는 검사”이다. 이 장의 완료 조건은 테스트 전체 통과, 동결 검사의 TEST_UNCHANGED, 그리고 그 둘을 사람이 자기 터미널에서 확인하는 것이다.
  • TDD는 Red(실패를 본다) → Green(최소한으로 통과시킨다) → Refactor(동작을 지키며 다듬는다)의 짧은 주기이다. Red는 사람이 보고, Green은 에이전트에게 맡기고, 다듬은 결과는 테스트가 판정한다.
  • 테스트는 준비 · 실행 · 확인으로 쓰고, 경계값과 등가 분할로 경우를 고른다. 날짜와 LLM 같은 외부 요인은 monkeypatch와 테스트 더블(페이크, 스텁, 스파이, 목)로 통제한다. 함수는 부르는 곳의 이름을 바꿔 끼운다.
  • 에이전트는 판정을 바꾸는 길(삭제, 건너뛰기, 완화, 설정, 바깥 conftest)과 판정에만 맞추는 길(하드코딩, 특수 처리)로 “통과”를 만들 수 있다. 단언 한 줄의 삭제는 결과 줄의 수를 바꾸지 않으므로, 앞의 것은 동결 검사와 git diff tests/가, 뒤의 것은 삼각 측량과 숨은 테스트와 검토가 잡는다.
  • 지시문에는 판정 기준의 보호, 일반성, 범위, git 금지, 출구(통과시킬 수 없으면 보고), 완료 조건, 증거를 넣는다. 지시문은 비결정적이므로 동결과 권한(3장), 훅(6장), CI(13장)로 층을 쌓는다.
  • 요구 하나에 테스트 커밋과 구현 커밋을 남기고, 실패한 시도는 git restore와 git clean으로 통째로 버리고, 넘겨줄 상태는 주석 태그로 표시한다. 공개한 태그는 옮기지 않는다.
  • 커버리지는 테스트가 지나가지 않은 코드를 찾는 도구이며, 테스트의 품질을 재는 목표가 아니다.

개념 점검

  1. 구현이 없는 상태에서 새로 쓴 테스트가 처음부터 통과했다. 가능한 원인 두 가지와, 각각을 가르는 방법을 쓰라.
  2. api/ask.py가 from rag.search import search로 검색 함수를 가져온다. 질의응답이 검색을 부르지 않았음을 확인하려면 monkeypatch.setattr의 첫 인자로 무엇을 주어야 하며, 그 까닭은 무엇인가.
  3. 다음 중 test_guard.py check로 잡히지 않는 것을 고르고, 그것을 잡는 다른 수단을 쓰라. (가) 테스트에 @pytest.mark.skip을 붙임 (나) pytest.ini에 --deselect를 더함 (다) 테스트가 고정한 날짜에서만 맞는 구현 (라) 저장소 루트에 conftest.py를 만듦
  4. 에이전트의 보고와 학습자의 터미널이 모두 지시문의 N과 같은 N passed를 보였는데, check는 TEST_CHANGED였다. 결과 줄의 수가 그대로인데 판정 기준이 바뀔 수 있는 경우를 하나 들고, 그 시도를 받으면 무엇이 잘못되는지 이 장의 요구로 설명하라.
  5. 어떤 보고서가 “커버리지 100%이므로 품질이 검증되었다”고 적었다. 이 주장의 문제를 이 장의 내용을 들어 설명하라.
