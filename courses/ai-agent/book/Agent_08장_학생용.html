루프 엔지니어링과 자동화

2027학년도 「AI에이전트 기획 및 개발」의 준비 중인 교재입니다. 편집 상태를 검토하기 위해 미리 공개한 것으로, 수업 전에 내용과 순서가 바뀔 수 있습니다.

학사 10주차 · 교재 08 · 3부 하네스와 루프

150분 기준 개편(2026-11-19). 2026-11-19에 150분 수업 기준으로 줄였다(학생용 본문 78,481자 → 34,421자. 줄이기 전 값은 코드 울타리를 바르게 센 값이다). 명령의 출력은 2026-11-16~17에 집필용 PC(Windows 11, Git Bash)에서 얻은 실제 출력이며, 실제 모델을 부르는 실행의 결과는 싣지 않았다.

7장의 비교에서 일을 시작하고, 결과를 읽고, 다시 시킬지 정한 것은 학습자였다. 사람이 자리를 비우면 이 결정을 대신할 루프가 필요하다. 루프 엔지니어링(loop engineering)은 무엇을 판정하고, 실패하면 무엇을 되돌리고, 몇 번까지 다시 하고, 언제 사람에게 넘기는지를 미리 코드로 적는 일이다. 판정은 에이전트의 말이 아니라 종료 코드로 하고, 상한은 바깥의 스크립트가 지킨다.

이 장에서 만드는 것은 실패하는 테스트를 Claude Code의 헤드리스 실행으로 고치게 하고, pytest로 판정해 실패하면 다시 시키되, 세 번 실패하면 멈추고 보고서를 남기는 루프 ops/loop/fix_until_green.py와 설계서 docs/운영/루프설계서.md이다. 해결하는 문제는, 에이전트가 테스트의 기대값을 바꾸면 판정 명령이 정직하게 통과를 내고 루프가 잘못된 통과를 커밋한다는 것이다. 이를 보호 경로 검사로 막은 뒤 실제 에이전트로 한 번 돌린다.

학습 목표

  • 헤드리스 실행을 스크립트에서 다룬다. claude -p의 출력 형식, 결과 객체, 종료 코드를 읽고 권한과 상한을 플래그로 정한다.
  • 루프를 여섯 부분으로 설계한다. 입력, 실행, 판정, 되돌림, 재시도, 종료를 나누어 정하고 근거를 설계서에 쓴다.
  • 루프의 안전장치를 구현하고 검증한다. 상한, 보호 경로 검사, git 상태 관리, JSON 줄 기록, 보고서를 가짜 에이전트로 경로마다 확인한다.
  • 루프를 자동화 체계에 배치한다. 수집 → 요약 → 통지 파이프라인을 짜고 예약 실행의 선택지를 비교해 고른다.

0-2. 7장 산출물 확인

루프는 깨끗한 작업 트리에서만 시작한다.

터미널 
cd ~/agent-lab/jobprep
git status --short

git status --short는 빈 출력, ls는 CLAUDE.md, 설정, 훅 폴더를 보여야 한다. 없으면 기준 산출물을 복사해 커밋한다.

[터미널] (7장을 마치지 못한 경우에만)

ls .claude/settings.json || {
  cp -rn ~/kits/Agent_08장/기준산출물/jobprep/. .
  chmod +x .claude/hooks/*.sh
  git add -A
  git commit -m "chore(claude): 7장 기준 산출물(하네스 견본) 반영"
}

a || { … }는 a가 실패했을 때만 중괄호 안을 실행한다(3장 commit-msg 훅의 두 줄은 출력 예시에서 뺐다). 훅 protect.sh는 보호 경로의 편집을 종료 코드 2로 막고(표준 오류의 글이 Claude에게 간다[C12]), run_tests.sh와 stop_gate.sh는 테스트를 돌린다. 이들은 시도 안의 장치이고, 루프는 바깥에서 한 번 더 확인한다(3-4).

1. 사람이 돌리는 일과 루프가 돌리는 일

1-1. 대화형 세션과 무인 실행

무인 실행에서는 사람이 대화 중에 하던 일을 모두 미리 코드로 적어야 한다.

사람이 하던 일 무인 실행의 장치
권한 요청에 답한다 허용·거부 규칙과 dontAsk (3절)
“다 됐다”는 말에 테스트를 돌려 본다 판정 명령 pytest -q의 종료 코드 (4-4)

그래도 일을 시작하고, 「끝」을 정하고, 병합을 승인하는 것은 사람의 몫이다[C6].

1-2. 루프의 정의

Claude Code 팀의 글 「Loop engineering: Getting started with loops」는 루프를 정지 조건이 충족될 때까지 작업 주기를 되풀이하는 것으로 정의한다[E6]. 안쪽 루프(9장)는 실행 한 번 안에서 모델이 도구를 부르고 다시 판단하는 것이고 한 바퀴가 턴이다[C21]. 바깥 루프(이 장)는 스크립트가 에이전트를 실행하고 판정하고 다시 실행한다. 턴 상한 15와 시도 상한 3은 곱해져 최악의 경우 45번 판단한다. 안쪽 루프는 모델의 「다 되었다」로 멈추고, 바깥 루프는 저장소의 실제 상태를 판정한다.

1-3. 루프의 유형

같은 글은 루프를 네 유형으로 나눈다[E6].

유형 시작시키는 것 멈추게 하는 것 Claude Code의 수단
턴 기반 사람의 프롬프트 한 번 Claude가 끝났다고 판단하거나 정보가 더 필요할 때 대화형 세션
목표 기반 완료 조건을 적은 명령 한 번 평가 모델이 조건 충족을 확인하거나 턴 상한 /goal
시간 기반 정해진 간격 사람이 취소하거나 일이 끝남 /loop, 예약 작업
능동형 일정이나 사건(새 PR, 실패한 CI) 일마다 목표 충족, 전체는 사람이 끌 때까지 클라우드 예약 작업, GitHub Actions

fix_until_green.py는 목표 기반 루프이다. /goal은 작은 모델이 대화를 읽고 판정하므로[C24] 비결정적이고, 이 루프는 종료 코드로 판정하므로 같은 상태면 같은 판정이 나온다.

1-4. 결정적 장치와 비결정적 장치

모범 사례 문서는 모델이 따를지 정하는 비결정적 지시(프롬프트, CLAUDE.md)와 하네스가 반드시 실행하는 결정적 지시(훅, 거부 규칙)를 나눈다[C6]. 이 장의 장치는 모두 결정적이다. 지시문에 「테스트를 고치지 마라」라고 적되, 고쳤는지는 스크립트가 git status로 확인한다.

1-5. 무인 실행 전에 답할 다섯 질문

작업을 혼자 돌게 두기 전에 완료, 자기 검사, 건드릴 범위, 멈추는 조건, 결과의 행선지와 승인자를 확인하라는 다섯 질문[C6]이 설계서의 항목이 된다.

1-6. 루프로 돌리지 않을 일

판정 명령이 없는 일(「화면을 보기 좋게」), 되돌릴 수 없는 일(배포, 발송, 원격 푸시), 실패의 값이 큰 일은 루프에 넣지 않거나 더 작은 단위로 사람의 검토와 함께 돌린다. 이 루프가 푸시와 병합을 하지 않는 까닭이다.

2. 헤드리스 실행

2-1. claude -p의 기본형

대화 화면 없이 한 번 실행하고 끝내는 방식을 헤드리스(headless) 실행이라 한다[C14]. claude -p "api/jobs.py의 days_left 함수가 하는 일을 두 문장으로 설명하라"처럼 -p를 붙이면 결과를 표준 출력에 쓰고 끝난다. 2~3절의 예시는 교수가 시연한다. 실행을 시작한 프로그램은 표준 출력과 종료 코드만 보며, 표준 입력도 읽으므로(10MB 제한) 고르고 세는 일은 셸이 하고 판단만 모델에 넘긴다[C14].

2-2. 출력 형식

--output-format은 text(기본값), 결과 객체 하나의 json(이 루프), 사건마다 한 줄의 stream-json(2-8)을 받는다[C15]. --json-schema의 structured_output은 없을 수 있으므로 확인하고 쓴다[C14].

2-3. 결과 객체의 필드

결과 객체는 Agent SDK의 결과 메시지와 같은 모양이다[C21].

필드 뜻 루프에서 쓰는 곳
type 언제나 "result" 마지막 줄이 결과인지 확인
subtype 끝난 방식(2-4) 성공, 턴 상한, 비용 상한을 가른다
is_error 오류로 끝났는가 에이전트 상태를 error로 기록
result 최종 응답의 글. success일 때만 있다 기록에 끝부분만 남긴다
total_cost_usd 이 실행의 비용 추정치(달러) 루프 전체 예산에서 뺀다
num_turns 이 실행의 턴 수 기록
session_id 세션 아이디 사람이 --resume으로 이어 볼 때
usage 입력·출력 토큰 수 12장의 비용 보고

--resume으로 이은 실행은 대화 전체의 비용을 보고한다[C14]. 루프가 시도마다 새 세션을 여는 까닭이다.

2-4. 끝난 방식과 종료 코드

subtype은 다섯 값 가운데 하나이다[C21].

subtype 일어난 일
success 정상적으로 끝남
error_max_turns --max-turns 상한에 닿음
error_max_budget_usd --max-budget-usd 상한에 닿음
error_during_execution 실행 중 오류로 중단됨
error_max_structured_output_retries 스키마에 맞는 출력을 내지 못함

종료 코드는 성공이면 0이고, 턴 상한에 닿은 실행도 0이 아니다[C21]. 잘못된 플래그는 표준 오류로, 인증 실패는 결과로 표준 출력에 나온다[C14]. 마지막 줄이 JSON이 아니면 루프는 출력의 끝을 agent_result에 남긴다. 이 둘은 「끝까지 갔는가」와 「어떻게 끝났는가」를 알려 줄 뿐 「고쳐졌는가」는 판정 명령(4-4)이 정한다.

2-6. 대화 잇기와 시스템 프롬프트

--continue와 --resume <세션 아이디>는 대화를 잇는다[C14]. 루프는 시도마다 새 세션을 열고 앞 시도의 정보는 지시문에 요약해 넣는다. 이으면 실패한 가정이 이어지고 비용이 커진다[C19]. 실패한 시도는 기록의 session_id로 사람이 claude --resume해 연다. --append-system-prompt는 기본 시스템 프롬프트에 덧붙이고 --system-prompt는 바꾼다[C15]. 루프는 「무인 루프의 한 시도이다. 질문할 수 없다」만 덧붙인다.

2-7. bare 모드와 인증

--bare는 훅, 스킬, MCP 서버, CLAUDE.md를 읽지 않고 API 키로만 인증한다[C14]. 13장의 CI에 맞지만, 계정 로그인을 쓰고(부록 A-5-3) 7장의 훅이 작동해야 하는 이 루프는 쓰지 않는다.

2-8. stream-json으로 진행 보기

stream-json --verbose는 system/init에서 result까지 사건마다 한 줄을 낸다. system/api_retry는 재시도한 API 오류를, --permission-prompts none과 함께면 permission_denials가 거부된 호출을 담는다[C14]. 교수가 시연하고 시연기록/stream-2-8.txt로 배포한다.

[그림 자리: stream-json 사건 목록] 교수 화면에서 stream-json 사건의 종류를 찍는 명령(교수용 시연 A)을 실행한 터미널. 첫 줄 system init, 가운데의 assistant와 user가 번갈아 오는 줄, 마지막 줄 result success가 한 화면에 보이게 찍는다. 찍을 곳: 교수 PC의 VS Code 터미널(Git Bash). 배포 파일 시연기록/stream-2-8.txt와 같은 실행이어야 한다.

3. 헤드리스 실행의 권한 설계

3-1. 권한 모드

헤드리스 실행에는 권한 요청에 답할 사람이 없으므로 권한 모드로 미리 정한다[C22].

모드 묻지 않고 실행되는 것
default (Manual), plan 읽기만
acceptEdits 읽기, 파일 편집, 흔한 파일 명령
auto 모든 것, 단 분류기가 위험한 동작을 검사
dontAsk 작업 폴더 안의 읽기와 미리 허용한 도구. 나머지는 거부(잠근 CI와 스크립트)
bypassPermissions 모든 것(격리된 컨테이너와 가상 머신에서만)

v2.1.302부터 모드를 정하지 않은 claude -p는 Manual로 시작하고, 이전 판은 일부 환경에서 자동 모드로 시작할 수 있었다[C22]. 집필 PC의 2.1.296은 이전 판이므로 루프는 --permission-mode dontAsk를 명시한다.

[최신 자료 자리: -p 실행의 기본 권한 모드] 권한 모드를 정하지 않은 claude -p가 어느 모드로 시작하는지와 그 기준 판. 확인할 곳: https://code.claude.com/docs/en/permission-modes. 2026-11-15에 확인한 값: v2.1.302 이상은 Manual(default)로 시작한다. 내 PC의 판이 이 경계의 어느 쪽인지 수업 전에 확인한다.

허용할 것을 미리 다 아는 이 장의 일에는 dontAsk가 맞다. auto의 분류기는 모델이라 판단이 늘 같지 않고[C6], bypassPermissions는 프롬프트 주입에서 아무것도 지켜 주지 않는다[C22].

3-2. 허용, 거부, 제한의 세 플래그

헤드리스 실행에서 도구를 다루는 플래그는 셋이다[C15].

플래그 하는 일
--allowedTools 나열한 도구(또는 규칙에 맞는 호출)를 묻지 않고 실행한다
--disallowedTools 거부 규칙. 도구 이름만 주면 도구를 없애고, Bash(rm *)처럼 범위를 주면 그 호출만 거부한다
--tools 내장 도구의 목록 자체를 정한다. ""이면 모두 끈다

--allowedTools는 「허용 목록」이 아니라 「묻지 않을 목록」이며, 나열하지 않은 것은 권한 모드가 처리한다.

3-3. 규칙의 문법

끝의 *는 앞부분이 같은 모든 명령이며 공백 없는 Bash(git diff*)는 git diff-index까지 맞는다[C14]. 규칙은 거부, 확인, 허용 순서로 평가되어 허용으로 거부에 예외를 만들 수 없고, 명령행 규칙의 맨 앞 /는 작업 폴더 기준이다[C4].

[파일: ops/loop/fix_until_green.py] (일부)

# 시도 한 번에 에이전트가 쓸 수 있는 도구. 나머지는 --permission-mode dontAsk가 거부한다.
ALLOWED_TOOLS = [
    "Read", "Edit", "Bash(pytest)", "Bash(pytest *)",
    "Bash(python -m pytest)", "Bash(python -m pytest *)",
]
# 허용 목록과 겹쳐도 거부가 먼저다. 루프가 할 일(커밋)과 위험한 명령, 보호 경로의 편집을 막는다.
DENIED_TOOLS = [
    "Bash(git commit *)", "Bash(git push *)", "Bash(git reset *)", "Bash(git checkout *)",
    "Bash(rm *)", "Edit(/tests/**)", "Edit(/.claude/**)", "Edit(/ops/**)", "Read(/.env)",
]

거부 목록은 루프의 브랜치(git reset, git checkout), 파일 삭제(rm, 9-2), 하네스와 판정하는 쪽(.claude/, ops/), 비밀 정보(.env)를 지킨다. 커밋은 판정 뒤 루프의 일이므로 따로 거부한다.

pytest의 꼴을 넷으로 적은 것은 Bash 규칙이 글자에 맞추기 때문이다(3장 4-7). 루프가 가상 환경의 폴더(.venv/Scripts, .venv/bin)를 에이전트의 PATH 맨 앞에 넣으므로(4-3) 경로 없는 python으로 충분하다. 에이전트가 .venv/Scripts/python -m pytest -q처럼 부르면, 대화형이었다면 확인 창이 떴을 호출(3장 판정 사례 13번)을 dontAsk가 거부한다.

3-4. 규칙은 보안 경계가 아니다

규칙은 글자를 맞출 뿐 bash -c 'rm -rf build/'나 git -C . push origin main 같은 다른 꼴은 막지 못한다[C4]. 이 루프에서는 dontAsk가 이를 거부하지만, 루프는 판정 전에 바뀐 파일을 git으로 직접 확인한다(6-7).

겹 장치 언제 작동하는가 무엇에 기대는가
1 지시문의 “고치지 마라” 모델이 읽을 때 모델의 판단(비결정적)
2 거부 규칙 Edit(/tests/**) 도구 호출 직전 경로 글자의 일치
3 PreToolUse 훅 protect.sh 도구 호출 직전 훅 스크립트의 논리
4 루프의 protected_changes() 시도가 끝난 뒤, 판정 전 git이 아는 실제 변경

3-5. 신뢰하지 않은 폴더에서의 -p

-p는 신뢰 대화 상자를 띄우지 않는다. 신뢰하지 않은 폴더에서는 훅은 쓰이지만 permissions.allow는 쓰이지 않고 .mcp.json의 서버는 묻지 않고 연결된다[C4]. 그래서 루프는 허용을 --allowedTools로 넘기며, 남의 저장소에서는 --setting-sources user나 --bare를 쓴다(11장) [C4].

3-6. 사람이 없을 때의 권한 요청

--permission-prompts none(v2.1.259 이상)은 물어야 할 호출을 거부한다[C14]. 이 루프는 dontAsk로 같은 효과를 얻는다.

def count_failures(code, output):
    """실패와 오류의 개수. 통과면 0, 개수를 읽지 못하면 999(가장 나쁨)로 본다."""

4-5. 되돌림: git으로 시도 사이의 상태를 관리한다

실패한 시도를 늘 버리면 시도가 독립이지만 부분적으로 고친 것도 버려진다. 이 루프는 실패 개수가 줄어든 시도를 체크포인트로 남기는 진전 누적을 택하였다. 다만 하나를 고치며 다른 것을 깨뜨린 시도를 진전으로 볼 수 있다.

  1. 루프 시작: git switch -c loop/<실행 이름>으로 루프 전용 브랜치를 만든다. main은 건드리지 않는다.
  2. 진전 또는 통과: 바뀐 파일만 git add -A -- <파일> 하고 git commit -m "fix: 루프 … 시도 N …"(3장 규약)으로 남긴다.
  3. 진전 없음, 규칙 위반: 변경을 attempt-N.diff로 남기고 git restore --source=HEAD --staged --worktree -- .로 되돌린 뒤 새 파일(??)을 지운다.

git restore는 추적하지 않는 파일을 건드리지 않는다[G16]. git clean -fd는 기록까지 지우므로 쓰지 않는다. 루프 브랜치는 사람의 승인 지점이며 13장에서 풀 리퀘스트가 된다.

4-10. 지시문의 설계

루프에는 되물어 줄 사람이 없다. prompt_fix.md의 원칙은 다음과 같다.

  1. 완료를 명령으로 적는다. 「버그를 고쳐라」가 아니라 「python -m pytest -q가 통과하도록 고쳐라」이다. 통과와 실패로 답하는 검사가 있으면 Claude가 스스로 루프를 닫을 수 있다[C6].
  2. 하지 말 것을 경로로 적는다. {PROTECTED}가 보호 경로 목록에서 채워지므로 지시와 검사가 어긋나지 않는다.
  3. 루프의 일과 에이전트의 일을 나눈다. 커밋, 푸시, 브랜치 전환은 루프의 일이다.
  4. 모양을 고정한다. 마지막 줄의 OK/FAIL과 같은 제목 아래의 실패 요약은 시도끼리 비교하기 쉽게 한다.

모호한 요청은 넓은 탐색을 부른다[C19]. 6-5에서 시도 1이 아무것도 고치지 못한 채 예산의 절반을 쓴 것이 그 예이다.

4-11. 바꿔 끼우는 자리

에이전트 명령은 AGENT_CMD 한 곳에서만 정해진다. 그래서 실제 모델로는 원할 때 만들 수 없는 경로(세 번 연속 실패 등)를 비용 없이 결정적으로 시험한다. 가짜로 확인하는 것은 「루프가 이런 결과를 받으면 이렇게 처리한다」까지이며, 실제 에이전트의 행동은 6-9에서 본다.

5. 상한의 설계

5-1. 재시도 상한

2026년 2학기판처럼 3에서 출발한다. 같은 지시와 정보로 세 번 실패한 일은 넷째에도 실패할 가능성이 크다. 부족한 것이 횟수가 아니라 정보이기 때문이다. 실패가 여럿이면 진전 누적이 맡고, 시도마다 최신 실패 요약으로 지시문이 바뀐다.

5-2. 비용 상한 두 겹

첫째 겹은 시도 한 번의 상한(0.50달러, --max-budget-usd)으로 Claude Code가 지키고, 둘째 겹은 루프 전체의 상한(1.00달러)으로 루프가 시도마다 total_cost_usd를 더해 지킨다. 시도의 상한은 남은 예산과 시도 상한 가운데 작은 것이다. 지출은 응답 하나만큼 넘을 수 있으므로(2-5) 남은 예산이 LOOP_MIN_RUN_BUDGET(0.10달러)보다 적으면 다음 시도를 시작하지 않는다.

비용을 알 수 없는 시도(시간 상한, JSON이 아닌 출력)는 상한을 모두 쓴 것으로 센다(cost_counted). 0으로 세면 루프가 끝없이 돌 수 있다. 예산의 크기는 비용 문서의 평균(개발자 한 명의 활동한 날 하루 약 13달러[C19])에 견준다. 구독형 계정의 total_cost_usd는 청구액이 아니라 사용량의 추정치이지만 상한으로는 충분하다.

[최신 자료 자리: Claude Code의 평균 비용] 비용 문서의 기업 배포 평균(활동한 날 하루, 한 달, 하루 상위 10%의 경계). 확인할 곳: https://code.claude.com/docs/en/costs. 2026-11-15에 확인한 값: 활동한 날 하루 약 13달러, 한 달 150~250달러, 사용자의 90%가 하루 30달러 미만. 5-6의 하루 최악의 비용 비교도 이 값에 기댄다.

5-3. 턴 상한

마지막 응답 턴을 셈에 넣지 않으면 실행은 최종 응답 없이 error_max_turns로 끝난다[C21]. 실패 하나를 고치는 데 6~8턴이 들고 기본값 15는 그 두 배쯤이다. 턴 상한은 같은 일을 맴도는 실행을 비용이 쌓이기 전에 끊는다.

5-4. 시간 상한

시도는 600초, 루프 전체는 1,800초이다. 상한에 닿은 시도는 끝내고 비용을 알 수 없는 시도로 센다. 끝나지 않는 명령(개발 서버 등)은 토큰을 쓰지 않으므로 비용 상한으로 끊을 수 없다.

PROMPT="표준 입력은 웹 서비스의 운영 기록 가운데 경고와 오류 줄이다. 원인별로 묶어 심각한 순서로 3줄 이내의 목록으로 요약하라. 각 줄에 건수와 시각 범위를 붙여라. 기록에 없는 원인을 지어내지 마라."

STATUS=$?

if [ $STATUS -ne 0 ]; then

함정 증상 대책
PATH가 짧다 claude: command not found가 기록 파일에 남는다 줄 안에서 PATH를 정하거나 절대 경로를 쓴다

실행이 겹친다 앞 실행이 끝나기 전에 다음 실행이 시작한다 시간 상한을 간격보다 짧게, 필요하면 flock

보호 경로 검사(파일이 바뀌었는가)와 테스트 동결(같은 것을 확인하는가)은 겹친다. 특수 처리는 경로로 막을 수 없으므로 통과한 루프의 diff도 사람이 읽는다.

9-3. 비용 폭주

비용은 시도 수 × 시도당 비용(재시도와 전체 상한), 컨텍스트의 성장(요약의 길이 상한, 새 세션), 동시 실행(시간 상한, 잠금, 지출 한도)으로 늘어난다[C19].

9-4. 그 밖의 실패

  • 판정의 비결정성. 시각이나 네트워크에 기대는 테스트는 흔들린다. jobprep은 today()와 LLM 모의 모드로 고정한다.
  • 에이전트 명령의 변화. 판이 바뀌면 기본값이 바뀐다(3-1). 플래그를 모두 명시한다.
  • 입력에 숨은 지시. 테스트 출력에 섞인 바깥의 글이 지시처럼 읽힐 수 있다(11장). 허용 도구가 작으면 피해가 작다.

9-5. 루프를 고치는 순서

상한부터 늘리면 같은 실패를 더 비싸게 되풀이한다. 기록을 읽고 다음 순서로 고친다.

  1. 판정을 의심한다. 테스트가 약하거나 흔들리면 무엇을 고쳐도 소용이 없다.
  2. 입력을 고친다. 지시문과 실패 요약에 파일과 함수 이름을 더 적는다(6-5).
  3. 권한을 고친다. 막힌 도구는 가장 좁은 규칙으로 더한다.
  4. 상한을 고친다. 시도별 실패 수가 줄고 있었을 때만 늘린다.
  5. 루프로 돌리지 않는다. 1-6의 기준에 맞지 않는 일이다.

이제 설계서의 10절(9-1~9-4와 6-6)과 12절(8-1, 8-2의 crontab 줄, 5-6의 하루 최악 비용)을 채우고 git commit -m "docs(ops): 루프 설계서 10절과 12절"로 커밋해 푸시한다.

확인 13 docs/운영/루프설계서.md의 10절에 테스트 회피를 포함한 실패 양상 셋 이상과 막는 장치가, 12절에 고른 예약 방법과 cd·PATH·출력 리다이렉션이 든 crontab 줄과 하루 최악 비용이 있고, 이 변경이 커밋되어 원격에 푸시되었다.

정리

  1. 이 장의 루프에서 에이전트의 결과 객체가 subtype: "success"이고 응답 끝이 OK인데도 그 시도를 되돌리는 경우는 언제인가. 무엇을 근거로 되돌리는가.
