[부록 C] 양식 모음

2027학년도 「AI에이전트 기획 및 개발」의 준비 중인 교재입니다. 편집 상태를 검토하기 위해 미리 공개한 것으로, 수업 전에 내용과 순서가 바뀔 수 있습니다.

「AI에이전트 기획 및 개발」 1~13장의 공통 부록 · 2026-11 기준(키트는 2026-11-17 판)

이 부록은 각 장의 실습 키트에 흩어져 있는 양식(*_양식.md, 양식/ 폴더), 템플릿(풀 리퀘스트 템플릿, CODEOWNERS, 변경 기록), 설정과 워크플로의 견본을 장 순서대로 한곳에 모은 것이다. 이 과목의 1~13장은 기준 저장소 jobprep을 운영 대상으로 삼아 운영 요건, 테스트, 하네스, 루프, 멀티 에이전트, 보안, 평가, 배포의 장치를 하나씩 세운다. 같은 학기의 프로젝트실습Ⅱ(졸업 프로젝트)에서는 팀이 자기 서비스에 같은 장치를 다시 세운다. 그때 팀원 모두가 같은 형식으로 문서를 쓰고, 같은 ID로 문서를 서로 가리키고, 키트의 검사 도구를 그대로 돌릴 수 있게 하는 것이 이 부록의 목적이다.

절 번호는 장 번호와 같다. C-3은 3장의 양식이고 C-13은 13장의 양식이다. 각 양식은 다음 네 가지를 차례로 적는다.

  1. 쓰는 곳. 어느 장의 어느 절에서 무엇을 만드는 데 쓰는가, 채운 파일이 저장소의 어디에 놓이는가.
  2. 키트 경로. 받은 키트(~/kits/, 부록 A-7) 안의 경로. 키트 저장소의 클론(~/kits-repo) 아래에도 같은 경로로 있다.
  3. 양식 본문. 키트의 파일을 그대로 옮겼다. 긴 양식은 핵심 칸만 싣고, 뺀 자리에 「(… 키트 원문 N~M줄 생략 …)」을 남겼다. 생략한 부분은 키트 경로의 원문을 본다. 칸 이름과 안내 문장은 원문 그대로이다.
  4. 프로젝트실습Ⅱ에서 바꿀 곳. 팀의 서비스에 쓸 때 고칠 자리와 그대로 둘 자리.

양식을 쓰는 방법은 모든 장에서 같다. 키트는 저장소 밖(~/kits/)에 두고, 양식을 저장소의 정해진 자리로 복사한 뒤 자리 표시를 채운다. 안내 문장(>로 시작하는 줄이나 <!-- --> 주석)은 다 채운 뒤 지워도 된다. 키트 안의 양식 파일 자체는 고치지 않는다. 이 부록과 키트의 원문이 다르면 키트의 원문이 우선한다.

자리 표시의 꼴은 양식마다 조금 다르다. 대부분은 「 」이고, 4장의 장애 보고서 서식과 스킬 비교는 { }, 5장의 MCP 점검 기록은 (채운다), 7장의 두 문서는 괄호 안의 예와 빈칸을 쓴다. 검사 도구가 남은 자리 표시를 찾는 방식도 그 꼴에 맞추어져 있으므로(예: 4장 check_report.py는 {{를, 1장 check_ops.py와 3장 lint_rules.py는 「 」를 찾는다), 팀 문서에서 자리 표시의 꼴을 바꾸지 않는다.

양식에 쓰는 ID와 규약

양식들은 ID로 서로를 가리킨다. 역할 정의서의 「관련 운영 요건」이 운영 요건 명세의 OR-SEC-01을 가리키고, 운영 요건 지도가 같은 ID로 학기의 산출물을 묶고, 커밋 메시지의 범위와 꼬리말이 명세서의 REQ-JOB-06을 가리킨다. 형식이 하나라도 어긋나면 사람은 문서를 따라가지 못하고 키트의 검사 도구는 연결을 찾지 못한다. 아래의 표는 1~13장이 함께 지키는 형식이다. 부록 A의 「장 사이 약속」과 같은 약속을 양식의 쪽에서 다시 적은 것이다.

문서 사이에서 쓰는 ID

대상 형식 처음 정하는 장 가리키는 양식과 도구
운영 요건 OR-<SEC\|REL\|CON\|REP>-NN(두 자리). SEC 보안, REL 신뢰성, CON 일관성, REP 재현성 1장 운영 요건 명세(C-1), 역할 정의서의 「관련 운영 요건」(C-1), 운영 요건 지도(C-13). check_ops.py, check_map.py가 형식과 분류를 본다
역할 R1~R6. 역할 정의서의 제목은 ### R<번호> 이름이다. 10장의 v0.2부터 R1 기획, R2 구현, R3 테스트, R4 검토, R5 배포, R6 관측 1장, 10장 4-7 역할 정의서(C-1), 멀티 에이전트 설계서(C-10)
검토 규칙 RV1~RV8. RV1~RV6은 6장, RV7(기록의 사용자 입력)과 RV8(명세 동기화)은 7장이 더하였다 6장, 7장 검토 서브에이전트(C-6), 7장 조립본 reviewer.md
기능 요구 REQ-<영역>-NN. 영역은 기준 저장소 명세서의 JOB(공고), SUM(요약), ASK(질의응답), OPS(운영), FAV(관심 공고) 기준 저장소 커밋 메시지의 범위와 Refs: 꼬리말, 테스트의 요구 마커 pytest.mark.req(id=...), 작업 카드의 「관련 요구」(C-10)
이슈 ISSUE-NN. 통합 브랜치와 인계 폴더에서는 소문자 issue-NN 10장 이슈 카드, 계획서, 작업 카드, 결과 보고(C-10)
작업 이슈 안의 T1, T2. 작업 카드와 결과 보고의 파일 이름(T1_카드.md, T1_보고.md)에도 쓴다 10장 계획서, 작업 카드, 결과 보고(C-10), 커밋 꼬리말 Agent-Task: ISSUE-07/T1
  • 3장 위반 규칙 R1~R10(count_violations.py)은 3장 안의 번호이다. 다른 문서에서 가리킬 때는 「3장 규칙 R3」처럼 장을 밝혀 역할 ID와 구별한다.
  • 요구 ID는 앞 과목의 세 자리 번호(REQ-001)와 형식이 다르다(1장 1-4, 2-2). 이 과목의 양식과 도구는 REQ-<영역>-NN만 쓴다.
  • ID는 한 번 붙이면 바꾸지 않는다. 운영 요건을 지울 때도 그 ID를 다시 쓰지 않는다(운영 요건 명세 2절). 커밋, 다른 문서, 기록이 그 ID를 가리키고 있기 때문이다.

# 장애 보고서 서식

- 상태: 초안

## 1. 요약

{{두세 문장: 언제, 어느 기능이, 어떻게 실패했고, 지금은 어떤 상태인가}}

## 2. 영향

| 항목 | 값 |
|---|---|
| 영향받은 기능 | {{경로와 기능 이름}} |
| 시간대 | {{시작 ~ 끝, 지속 시간}} |
| 실패 또는 지연 요청 | {{건수, 상태 코드}} |
| 그날 전체 요청 | {{건수}} |

## 3. 경과

| 시각 | 사건 | 근거 |
|---|---|---|
| {{HH:MM:SS}} | {{무슨 일이 기록되었는가}} | {{logs/파일.log}} |

1. 건수와 시각은 `log_summary.py`의 출력에서 옮긴다. 기록을 눈으로 세어 쓰지 않는다.
2. 경과 표의 행마다 근거 칸에 기록 파일 경로를 적는다. 행은 시각 순서이고 최소 2행이다(시작과 끝).
3. 원인 절은 기록에 있는 사실(오류 이름, 상태 코드)과 추정을 나누어 쓴다. 추정에는 "추정"을, 기록으로 알 수 없는 것에는 "확인 필요"를 붙인다.
4. 사람 이름, 사용자 질문 원문, 키 값은 보고서에 쓰지 않는다. 기록에 없는 정보이기도 하다.

# 심각도 기준

`jobprep` 운영팀이 장애 보고서의 심각도를 정할 때 쓰는 기준이다. 수업용으로 단순하게 만든 것이며, 실제 서비스는 사용자 수와 계약(SLA)에 따라 기준을 따로 정한다. 위에서부터 차례로 보고 처음 맞는 등급을 쓴다.

| 등급 | 조건 (하나라도 맞으면) | 예 |
|---|---|---|
| SEV1 | 공고 목록(`/api/jobs`)이 5xx를 낸다. 또는 LLM을 쓰는 두 기능(요약, 질의응답)이 함께 30분 넘게 실패한다. 또는 키나 개인 정보가 응답이나 기록에 드러난다 | 서버가 뜨지 않아 목록이 열리지 않음 |
| SEV2 | LLM 기능 하나가 30분 안에 5xx를 3건 이상 낸다. 또는 인증 오류(`AuthenticationError`)가 한 건이라도 있다 | 요약이 한도 초과로 연속 실패 |
| SEV3 | 5xx가 3건 미만이다. 또는 응답이 느리지만(5,000ms 이상) 실패는 없다 | 질의응답이 한 시간 동안 느림 |

# reviewer: jobprep 변경 검토자

이 에이전트는 jobprep 저장소의 변경을 검토하는 일만 한다. 판정만 하고 고치지 않는다. tools에 Edit와 Write가 없으므로 파일을 고칠 수도 없다. 결과는 아래 "보고 형식" 하나로 낸다.

## 입력

- 검토 대상은 호출할 때 받은 diff 파일(보통 `.review/target.diff`)이다. 다른 지시가 없으면 이 파일만 대상으로 삼는다.
- 「더한 줄과 지운 줄을 어떻게 볼지 한 문장」
- 맥락이 필요하면 바뀐 파일 전체를 Read로 읽는다. 규칙의 근거는 저장소의 `CLAUDE.md`이다.

## 검토 규칙

| 규칙 | 위반으로 보는 것 | 심각도 |
|---|---|---|
| RV1 비밀 정보 | 「무엇을 찾는가. 예: sk-ant-로 시작하는 문자열, .env 파일의 추가」 | 높음 |
| RV2 LLM 호출 경로 | 「api/llm.py를 거치지 않는 호출, 코드에 적힌 모델 이름을 어떻게 알아보는가」 | 높음 |
| RV3 웹 출력 | 「어떤 함수나 속성으로 글을 넣으면 위반인가」 | 높음 |
| RV4 테스트 보호 | 「기존 테스트의 어떤 변경이 위반인가. 새 테스트를 더하는 것은 위반이 아니라는 것도 적는다」 | 높음 |
| RV5 오류 처리 | 「실패를 숨기는 코드의 모양」 | 중간 |
| RV6 모의 모드 | 「테스트가 실제 API를 부르게 되는 변경」 | 중간 |

규칙 밖에서 문제를 보더라도 위반 표에 넣지 않고 "규칙 밖의 관찰"에 따로 적는다.

## 순서

1. diff에서 바뀐 파일의 목록을 만든다.
2. 「파일마다 무엇을 대조하는가」
3. 「줄 번호는 무엇으로 확인하는가」
4. 검토를 마치면 보고 형식으로 한 번만 보고한다.

## 보고 형식

```text
## 검토 결과: 위반 N건

| 번호 | 규칙 | 심각도 | 위치(파일:줄) | 근거(바뀐 줄 한 줄 인용) | 권장 조치(한 문장) |
|---|---|---|---|---|---|

## 검토한 파일
- (diff에 있던 파일을 모두 적는다)

## 규칙 밖의 관찰
- (없으면 "없음")

## 확인하지 못한 것
- (없으면 "없음")
```

위반이 없으면 "검토 결과: 위반 0건"과 검토한 파일 목록을 보고한다.

> 실습용 이슈 카드이다. GitHub 이슈 본문을 옮긴 형태로 쓴다. 실제 이슈를 만들지 않아도 된다.

## 배경

학생 사용자들이 관심 공고를 표시해 두고도, 지원 일정을 엑셀이나 달력에 옮길 때 공고를 하나씩 다시 열어 제목과 마감일을 베껴 쓰고 있다. 관심 공고는 브라우저(localStorage)에만 저장되어 있어 서버가 목록을 알지 못한다.

## 요청

1. 목록 화면에 「관심 공고 내보내기」 단추를 둔다. 누르면 관심 공고가 CSV 파일로 내려받아진다.
2. 웹이 관심 공고 번호를 보내면 CSV를 돌려주는 API를 만든다. 다른 화면이나 도구에서도 쓸 수 있게 한다.
3. CSV에는 번호, 제목, 기업, 분야, 마감일, 남은 날 수가 있고, 엑셀에서 한국어가 깨지지 않아야 한다. 마감이 이른 공고가 위에 온다.

- 관심 공고가 하나도 없을 때의 동작
- 번호가 잘못되었거나 없는 공고일 때의 응답

### system
너는 취업 준비 서비스의 출력을 채점하는 채점자다. 채점 기준표만 근거로 판정하고, 출력의 길이나 문체가 마음에 드는지는 판정에 넣지 않는다.

### user
<기준표>
1. 근거 충실성: 출력의 모든 문장은 <근거>에 적힌 내용으로 뒷받침되어야 한다. 근거에 없는 조건, 절차, 숫자를 하나라도 덧붙였으면 fail이다.
2. 왜곡 금지: 근거의 뜻을 뒤집거나(받는다/받지 않는다) 숫자를 바꾸었으면 fail이다.
3. 표현 차이 허용: 근거와 낱말이 달라도 뜻이 같으면 통과로 본다.
4. 판단 불가: 근거만으로 판정할 수 없으면 unknown으로 답한다.
</기준표>

<근거>
{{EVIDENCE}}
</근거>

<출력>
{{OUTPUT}}
</출력>

먼저 <reason> 태그 안에 기준표의 어느 항목에 비추어 판단했는지 두 문장 이내로 쓴다.
그다음 <result> 태그 안에 pass, fail, unknown 가운데 하나만 쓴다.
  • 프로젝트실습Ⅱ에서 바꿀 곳(골든 세트와 합격선).
    • LLM 기능이 있는 팀이 쓴다. 문항은 팀 서비스의 실제 입력에서 고르고, 대표 문항과 경계 문항을 함께 둔다. 정답을 모르면 문항으로 넣지 않는다.
    • 필드 이름(id, suite, kind, expect)은 evals.run이 읽으므로 그대로 둔다. expect의 키는 채점기(graders.py)와 짝이므로, 팀 기능에 맞는 채점기를 쓸 때 함께 정한다(12장 11-2의 채점기 더하기).

    • 판정 기준표는 기준마다 「fail이 되는 경우」를 구체적으로 쓰고, unknown을 허용한다. 판정자를 쓰기 전에 사람 표본과의 일치도를 잰다(evals.calibrate, 12장 5-5).

# 운영 요건 지도

이 양식을 `docs/운영/운영요건지도.md`로 복사해 채운다. 1장에서 정한 네 운영 요건이 학기 동안 어느 장의 무엇으로 충족되었는지, 지금 그것을 어떻게 확인하는지, 무엇이 아직 남았는지를 한 장의 표로 정리한다.

- 작성: 「이름」
- 기준 커밋과 판: 「v1.0.1, 커밋 앞 7자리」
- 작성일: 「YYYY-MM-DD」

## 1. 지도

- 「요건」 칸에는 보안, 신뢰성, 일관성, 재현성 가운데 하나를 쓴다. 한 요건에 행이 여럿이어도 된다.
- 「1장의 요건」 칸에는 `docs/운영/운영요건.md`의 요건 ID(`OR-<SEC|REL|CON|REP>-NN`, 예: `OR-SEC-01`)와 요구의 요약을 쓴다. 분류는 「요건」 칸과 맞춘다(보안 SEC, 신뢰성 REL, 일관성 CON, 재현성 REP). 한 산출물이 요건 여럿을 충족하면 ID를 쉼표로 함께 적는다. `check_map.py`의 M5가 ID의 형식, 분류, 1장 문서에 있는지를 본다.
- 「산출물」 칸의 경로는 백틱으로 감싼다. `python ops/map/check_map.py`가 그 경로가 저장소에 있는지 확인한다.
- 「확인 방법」 칸에는 지금 실행할 수 있는 명령이나 화면을 쓴다.
- 「자동화」 칸에는 CI(풀 리퀘스트마다), 훅(에이전트가 고칠 때마다), 설정(Claude Code의 권한 규칙이 막는다), 배포(배포 스크립트가 확인한다), 수동(사람이 확인한다) 가운데 해당하는 것을 쓴다(둘 이상이면 쉼표).

|---|---|---|---|---|---|---|
