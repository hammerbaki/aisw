2027학년도 「AI에이전트 기획 및 개발」의 준비 중인 교재입니다. 편집 상태를 검토하기 위해 미리 공개한 것으로, 수업 전에 내용과 순서가 바뀔 수 있습니다.

학사 4주차 · 교재 03 · 1부 운영 요건과 검증

2026-11-19에 150분 수업 기준으로 줄였다(학생용 본문 63,733자 → 32,946자).

앞 장의 테스트는 결과만 정한다. 키를 코드에 적었는지, 화면에 글을 HTML로 끼워 넣었는지, 커밋 메시지의 형식은 어떠한지는 팀의 규칙이 정한다. 한 사람의 개인 설정에만 있는 규칙은 다른 팀원의 세션에 없으므로, 운영 요건의 일관성과 재현성은 규칙이 저장소에 있어야 지켜진다.

이 장은 기준 저장소 jobprep에 팀 규칙 일체, 곧 지시(CLAUDE.md와 경로별 규칙 둘), 권한 설정(.claude/settings.json), 저장소 규약(규약 문서, PR 템플릿, CODEOWNERS)을 넣는다. 해결할 문제는 규칙이 없는 저장소의 결과(교수 시연 기록)에서 어긋남 하나를 골라, 같은 요청을 자기 규칙에서 다시 보내 그것이 막혔는지 세는 것이다.

학습 목표

  • 지시(CLAUDE.md, 경로별 규칙)와 설정(settings.json)의 차이를 설명하고, 각각의 계층과 우선순위를 말할 수 있다.
    • 예시: 「팀 설정은 git push를 확인하게 하고 내 개인 설정은 허용한다면 어떻게 되는가」에 deny → ask → allow의 평가 순서로 답하기
    • 활용: 규칙이 지켜지지 않을 때 읽힌 파일부터 확인하는 습관
  • 확인할 수 있는 문장, 실행 명령, 이유를 갖춘 팀 CLAUDE.md와 경로별 규칙을 쓸 수 있다.
    • 예시: 「깔끔하게 짠다」를 「api/와 rag/의 기록은 logging으로 남기고 print를 쓰지 않는다. 이유: 운영 기록의 형식을 지킨다」로 고쳐 쓰기
    • 활용: 새 팀원과 에이전트가 같은 규칙으로 시작하는 저장소
  • 권한 규칙(allow, ask, deny)을 문서의 문법으로 쓰고, 개인 설정과 팀 설정을 나누어 저장소에 올릴 것만 올릴 수 있다.
    • 예시: .env 읽기 거부, git push 확인, 강제 푸시 거부를 .claude/settings.json에 적고 판정 사례 23개로 검사하기
    • 활용: 에이전트가 허용된 일만 하게 하는 첫 장치(11장)
  • 저장소 규약(브랜치 이름, 커밋 메시지, PR 템플릿, CODEOWNERS, 리뷰 규칙)을 저장소에 두고 훅으로 강제하며, 규칙이 있을 때와 없을 때를 같은 요청으로 비교할 수 있다.
    • 예시: 규칙 없음의 기록에서 innerHTML 위반(R4)을 골라, 같은 요청을 자기 규칙에서 다시 보내 0건인지 세기
    • 활용: 효과가 없는 규칙을 고치거나 다른 장치로 옮기는 운영

0. 시작하기

이 장은 내 PC의 ~/agent-lab/jobprep/에서 진행하고 시작 순서는 부록 A-20을 따른다. 두 터미널([터미널]과 Claude Code) 모두 가상 환경을 켠 뒤 python으로 부른다(부록 A-9-1). 1~9절은 이론과 따라 하기 셋(4-8, 7-3, 8-9), 10절은 핵심 실습이다.

이 장의 실행 상한. 실제 모델에는 대화형 Claude Code로 요청 셋만 보낸다(10-4, 10-5, 10-6). 10-6에서 규칙을 고친 경우에만 하나를 더 보낸다. 두 조건을 모두 돌린 비교는 교수 시연 기록으로 읽는다.

0-1. 키트 받기

키트는 저장소 밖의 ~/kits/로 받는다(부록 A-7-3). cp -rn은 있는 파일을 덮어쓰지 않으므로 다시 실행해도 된다. 시연기록/이 없으면 10-2 전에 다시 받는다. 양식/의 파일은 규칙으로 읽히지 않게 일부러 제자리 이름을 쓰지 않았다. 명령은 0-2에 있다.

[최신 자료 자리: Claude Code의 판, 명령 이름, 권장 값] 2026-11-17 확인 값: Claude Code 2.1.296. 이 장의 /memory, /context all, /status, /permissions, /init, /export, claude doctor, Loaded … 줄, CLAUDE.md 200줄 미만 권장, Windows의 PowerShell 도구는 이 판과 공식 문서를 따랐다. 확인할 곳: https://code.claude.com/docs/en/commands, https://code.claude.com/docs/en/memory, https://code.claude.com/docs/en/tools-reference, 내 PC의 claude --version.

1. 팀에서 깨지는 규칙

1-1. 다섯 장면

두 사람(가, 나)이 각자 Claude Code를 쓸 때 흔히 생기는 장면이다. 모두 규칙이 한 사람에게만 있어서 생긴다.

장면 일어난 일 처방
1 실행 명령 가의 사용자 CLAUDE.md에만 테스트 명령이 있어, 나의 세션은 Git Bash에 없는 python3을 부르다 실패한다 팀 CLAUDE.md(5절)
2 대화의 지시 대화로 한 「print 대신 logging」이 다음 세션에는 없다 경로별 규칙(6절)
3 개인 허용 가가 git push에 「Yes, and don’t ask again」을 골라 로컬 설정에 허용이 저장되었다[C2]. 「푸시는 사람이 확인한다」는 말로만 있었다 팀 설정의 ask(4절)
4 개인 파일 커밋 나는 git add -A로 개인 설정 파일을 올렸다 .gitignore(7절)
5 형식 없는 이력 커밋 메시지가 「수정」, 「Update summary.py」로 제각각이다 저장소 규약(8절)

Claude Code 문서는 이 구분을 비결정적 지시와 결정적 지시로 설명한다[C7]. CLAUDE.md는 모델이 읽고 스스로 판단하므로 대개 따르지만 보장은 없고, 훅과 거부 규칙은 모델의 결정과 관계없이 Claude Code가 매번 집행한다. 문서는 절대 일어나면 안 되는 일만 결정적 장치로 옮기고, 예외가 있을 수 있는 지침은 모델이 판단하도록 CLAUDE.md에 두라고 권한다. 저장소 규약은 에이전트 바깥에서 결과가 커밋과 PR로 들어오는 입구를 거른다. 지시를 어기면 결과를 보고야 알고, 설정을 어기면 호출이 거부되며, 규약을 어기면 커밋이 멈추거나 PR이 걸린다.

이 장의 규칙은 일관성(같은 요청의 위반 수로 잰다), 보안(.env 읽기 거부, 강제 푸시 거부), 재현성(설정을 저장소에 두고 판을 태그 rules-v1로 표시), 신뢰성(CLAUDE.md의 실행 명령으로 에이전트가 스스로 테스트)에 기여한다.

3. 설정 파일의 계층과 우선순위

3-1. 지시와 설정은 무엇이 다른가

CLAUDE.md의 「.env를 읽지 않는다」와 .claude/settings.json의 Read(./.env) 거부 규칙은 작동이 다르다. 설정의 규칙은 Claude가 무엇을 하기로 하든 Claude Code가 집행하고, 지시는 행동을 이끌 뿐 집행 장치가 아니다[C1][C3]. 설정은 엄격한 JSON이라 주석이나 끝의 쉼표가 있으면 문법 오류이고, 여러 범위가 겹치면 이어 붙이지 않고 우선순위로 정한다.

3-2. 네 범위

설정도 범위가 넷이다[C2]. 관리 설정(조직이 배포[C10]), 사용자 ~/.claude/settings.json, 공유 프로젝트 .claude/settings.json(커밋하면 팀원 모두), 프로젝트 로컬 .claude/settings.local.json(나, 이 프로젝트)이다. 로컬 파일은 「Yes, and don’t ask again」을 처음 고를 때 생긴다.

3-3. 우선순위와 합치기

같은 키는 관리 설정 > 명령줄(claude --settings) > 프로젝트 로컬 > 공유 프로젝트 > 사용자 순으로 높은 쪽이 이긴다[C2]. 다만 permissions.allow 같은 목록은 합치므로 각 파일은 다른 파일의 항목을 지우지 못한다. 그리고 권한 규칙은 합친 목록에서 deny → ask → allow 순서로 평가되므로 거부는 어느 범위에 있든 이긴다[C3]. 장면 3에서 팀 설정에 Bash(git push *)를 ask로 적으면 가의 로컬 allow 규칙은 힘을 잃는다.

3-4. 공유 프로젝트 설정에만 있는 조건

팀 파일은 남의 저장소에서 올 수 있으므로, 팀 파일의 permissions.allow는 신뢰 확인 창을 받아들인 뒤에야 적용되고 deny와 ask는 바로 적용된다. defaultMode의 bypassPermissions는 프로젝트 파일에서 효과가 없다[C2][C3].

3-5. 설정이 읽혔는지 확인하기

/status의 「Setting sources」에 이 세션이 읽은 설정 파일이 나온다[C2]. 셸의 claude doctor는 모델을 부르지 않고 JSON이 깨진 설정 파일을 「Invalid settings」 아래에 보고하며, 대화형 세션은 시작할 때 Settings Error 창을 띄운다.

읽기(교수 화면). 끝에 쉼표가 남은 설정("deny": ["Read(./.env)",])을 python -m json.tool로 읽으면 Illegal trailing comma before end of array: line 3 column 28 (char 48)과 종료 코드 1로 끝나고, claude doctor는 그 파일을 Invalid or malformed JSON으로 보고한다(2026-11-17). 둘 다 규칙의 뜻은 검사하지 않으므로 그것은 lint_rules.py로 잡는다.

4. 권한 규칙

4-1. 세 목록과 평가 순서

allow는 묻지 않고 실행하고, ask는 확인 창을 건너뛰는 모드에서도 매번 묻고, deny는 실행하지 못하게 한다[C3]. 평가는 deny → ask → allow 순서로 처음 맞는 것이 결과이며, 구체적인 규칙이 먼저 오지 않는다. 그래서 넓은 거부 Bash(aws *)는 좁은 허용 Bash(aws s3 ls)까지 막는다. 맞는 규칙이 없으면 권한 모드(4-5)의 기본 동작을 따른다.

4-2. 규칙의 모양

규칙은 도구 또는 도구(지정자)이다. Bash(npm run *)는 npm run으로 시작하는 명령, Read(./.env)는 지금 폴더의 .env 읽기, Edit(/docs/**)는 프로젝트 docs/ 아래의 편집에 맞는다[C3]. 도구 이름은 화면 이름이 아니라 정식 이름(예: TaskStop)으로 쓰고, 파일 쓰기는 Write(경로)가 아니라 Edit(경로)로 적는다. lint_rules.py는 맞추어지지 않는 모양에 「주의」를 출력한다.

4-3. Bash 규칙

Bash 규칙의 *는 공백을 포함한 아무 글자에 맞는다. Bash(npm run *)는 npm run build와 npm run에 맞고, Bash(ls *)는 빈칸도 규칙의 일부이므로 lsof에 맞지 않는다[C3]. 별표는 하위 명령 뒤에 둔다(Bash(git * main)은 git push origin main까지 맞는다). 복합 명령(&&, ;, |)은 하위 명령마다 판정해, 하나라도 거부나 확인에 맞으면 그 규칙이 적용된다.

Bash 규칙은 명령의 글자에 맞출 뿐 프로그램을 감싸는 경계가 아니다[C3].

규칙(deny 또는 ask) 막는 것 막지 못하는 것
Bash(curl *) curl https://example.com /usr/bin/curl …, sh -c 'curl …'
Bash(rm *) rm -rf build/ /bin/rm -rf build/, bash -c 'rm -rf build/'
Bash(git push *) git push origin main git -C . push origin main

막지 못한 명령은 기본 동작으로 넘어가므로 확인을 건너뛰는 모드에서는 실행될 수 있다. 글자와 관계없이 막을 것은 샌드박스나 훅(6장)이 맡고, 거부 규칙은 첫 번째 울타리이다.

4-4. Read와 Edit 규칙

파일 규칙의 경로는 .gitignore와 같은 패턴을 쓴다[C3]. //경로는 절대 경로, ~/경로는 홈 폴더, /경로는 설정 파일의 기준 폴더, ./경로는 지금 폴더 기준이다. 빗금이 없는 이름은 어느 깊이에서나 맞는다(Read(.env)는 Read(**/.env)). 같은 목록에서 ! 패턴은 앞의 규칙에서 경로를 빼내므로, Read(./.env.*) 다음의 Read(!.env.example)은 견본만 읽게 한다.

Read 거부는 cat, head처럼 Claude Code가 알아보는 파일 명령과 같은 경로의 편집에도 적용된다. 그러나 이름을 적지 않는 명령(grep -r 무엇 .)이나 파이썬 스크립트가 스스로 여는 파일에는 적용되지 않으며[C3], 문서는 이 틈을 샌드박스(11장)로 메운다[C6].

4-5. 권한 모드

권한 모드는 규칙에 맞지 않는 호출을 다루는 방식이다[C4]. default(Manual)는 대부분 묻고, acceptEdits는 작업 폴더 안의 편집을 묻지 않고, plan은 계획만 쓰고, auto는 배경의 분류기가 검사하며 진행하고, bypassPermissions는 확인을 건너뛰므로 격리된 환경에서만 쓴다. Shift+Tab으로 바꾸고 화면 아래의 표시로 확인한다. .claude 같은 보호 경로의 쓰기는 allow로 미리 허용되지 않으며, 팀 파일의 permissions.disableBypassPermissionsMode: "disable"은 bypass 모드를 막는다[C3].

[최신 자료 자리: 권한 모드의 이름과 시작 모드] 2026-11-15 확인 값: 2.1.283 이상의 대화형 세션은 auto로 시작하고, Shift+Tab을 auto에서 처음 누르면 default가 된 뒤 default → acceptEdits → plan으로 돈다. 표시는 ⏸ manual mode on, ⏵⏵ accept edits on. 확인할 곳: https://code.claude.com/docs/en/permission-modes.

4-6. /permissions 대화 상자

Claude Code 안의 /permissions는 적용되는 모든 규칙과 그 출처 파일을 보여 준다[C3][C8]. 10-5에서 팀 규칙의 출처를 확인한다.

4-7. Windows에서 규칙이 맞는 법

Windows에서 Claude Code는 셸 명령을 Git Bash로 실행한다. 규칙을 쓸 때 셋을 안다[C3][C11].

  1. 경로는 POSIX 모양으로 바꾼 뒤 맞춘다. C:\Users\alice는 /c/Users/alice가 되므로 절대 경로는 Read(//c/Users/alice/**)로 쓴다. 팀 설정은 ./.env처럼 작업 폴더 기준으로 쓴다.
  2. Bash 규칙은 명령의 글자에 맞춘다. 가상 환경을 켠 터미널에서 띄운 Claude Code는 대개 python -m pytest로 불러 허용 규칙에 맞지만, .venv/Scripts/python처럼 경로를 붙이면 맞지 않는다. 그래서 CLAUDE.md에도 「가상 환경을 켠 뒤 python으로」를 적는다.
  3. PowerShell 도구가 따로 있다. Git Bash가 있는 Windows에서는 PowerShell 도구가 기본으로 켜지고 Bash(…) 규칙은 이를 제한하지 않으므로, Bash 거부 규칙이 하나라도 있으면 그 세션의 PowerShell 도구가 꺼진다. 환경 변수나 PowerShell(…) 규칙으로 다시 켜면 같은 뜻의 PowerShell 규칙을 따로 적는다[C11].

macOS에서는 1과 3이 해당하지 않는다. 두 운영체제에 같은 뜻이 되게 상대 경로와 python으로 시작하는 규칙을 쓴다.

[최신 자료 자리: Windows의 경로 정규화와 PowerShell 도구] 2026-11-17 문서 확인 값: 경로는 /c/Users/…로 바꾸어 맞추고, Git Bash가 있는 Windows에서 PowerShell 도구(미리 보기)는 기본으로 켜지며 Bash 거부 규칙이 있으면 꺼진다. 확인할 곳: [C3] 「How path patterns match」, [C11] 「PowerShell tool」.

5-1. 무엇을 넣고 무엇을 빼는가

CLAUDE.md는 매 세션 전체가 읽혀 모든 줄이 Claude의 주의를 차지하므로, 문서는 코드만 읽어서는 알 수 없는 것만 두라고 한다[C7].

넣는다 빼거나 다른 곳에 둔다

팀 CLAUDE.md는 개요, 실행 명령, 작업 규칙, 금지의 네 절에 규칙마다 「이유: …」를 붙인 다섯 부분으로 쓴다. 금지 가운데 반드시 막을 것은 설정에도 적는다.

5-3. 확인할 수 있는 문장

문서는 「변경을 시험한다」가 아니라 「커밋하기 전에 npm test를 돌린다」처럼 확인할 수 있게 쓰라고 한다[C1].

확인하기 어려운 문장 확인할 수 있는 문장
보안에 신경 쓴다 .env를 읽거나 출력하거나 커밋하지 않는다
LLM 호출을 잘 관리한다 LLM 호출은 api/llm.py의 complete()만 거친다
화면을 안전하게 만든다 웹 화면에 글을 넣을 때는 textContent(web/js/common.js의 el())만 쓴다

테스트를 꼼꼼히 한다 기능을 바꾸기 전에 실패하는 테스트를 tests/에 먼저 쓴다

오른쪽 문장은 결과를 보고 지켰는지 판정할 수 있고, 9절의 위반 검사기도 이런 문장만 셀 수 있다.

Claude 문서는 지시 뒤에 그 까닭을 설명하면 Claude가 목표를 더 잘 안다고 적는다[A1]. 「print를 쓰지 않는다. 이유: 운영 기록의 형식을 지킨다」로 쓰면, Claude는 ops/의 명령행 도구가 화면에 찍는 print는 대상이 아니라고 스스로 판단할 수 있다. 이유가 없는 규칙은 사람도 왜 있는지 몰라 고치지 못하고 쌓인다. lint_rules.py는 금지 항목마다 「이유:」가 있는지 검사한다.

5-5. 짧게 쓰기

문서는 파일을 200줄 미만으로 하라고 권한다[C1]. 지켜지지 않는 줄에 「IMPORTANT」를 덧붙이기보다, 파일을 줄이거나 예외가 없어야 할 규칙을 훅이나 거부 규칙으로 옮긴다. 강조를 쌓으면 오히려 규칙을 지나치게 적용한다[C7].

5-6. /init으로 초안 받기

/init은 초안을 만들거나 고칠 곳을 제안한다[C1]. 초안은 폴더 구조를 길게 설명하므로 할 일은 대개 줄을 지우는 것이다[C7].

6. 경로별 규칙

6-1. .claude/rules/

저장소 일부에만 해당하는 규칙은 .claude/rules/의 마크다운 파일에 주제별로 담는다[C1]. 머리말에 paths가 없으면 CLAUDE.md처럼 시작할 때, 있으면 맞는 파일을 다룰 때만 읽힌다. 이 장은 api.md와 tests.md를 만든다.

6-2. paths 머리말

맨 위의 --- 두 줄 사이에 YAML로 paths를 적는다. 읽히는 머리말 필드는 paths 하나뿐이다[C1].

---
paths:
  - "api/**/*.py"
---
# api/ 규칙

- 잘못된 입력은 LLM을 부르기 전에 422로 거절한다.

패턴은 저장소 루트 기준이다(src/**/*.{ts,tsx} 등). 머리말을 YAML로 읽지 못하면 Claude Code는 머리말을 무시하고 그 규칙을 매 세션 읽는다. 오류 없이 조용히 넓어지는 것이다[C1]. 따옴표 없는 paths: **/*.py는 YAML 오류가 되므로 패턴은 큰따옴표로 감싼다. 맞는 파일이 없는 패턴은 아무 일도 하지 않는다. lint_rules.py는 두 경우를 실패로 알린다.

6-3. 언제 읽히는가

경로별 규칙은 Claude가 맞는 파일을 읽거나 고칠 때 읽히고, 화면에 Loaded .claude/rules/api.md 같은 줄이 나온다[C1]. 그래서 계획 단계부터 지킬 규칙은 CLAUDE.md에 둔다.

6-4. 어디에 둘 것인가

위치 읽히는 때 맞는 규칙 jobprep의 예
CLAUDE.md 매 세션 시작 어떤 작업에든 적용 실행 명령
.claude/rules/*.md 맞는 파일을 다룰 때 특정 폴더에만 해당 요구 마커
스킬 부르거나 요청이 맞을 때 여러 단계의 절차 장애 보고서(4장)
.claude/settings.json 언제나 예외 없이 지킬 것 .env 읽기 거부
훅 정해진 시점마다 매번 일어나야 할 것 편집 뒤 테스트(6장)

6-5. 연습: 규칙 후보의 분류

다음 열 개의 후보를 6-4의 표로 둘 곳을 정한다. 「보류」는 반복이 확인되지 않아 두지 않는 것이다.

번호 규칙 후보 둘 곳
1 테스트는 가상 환경을 켠 뒤 python -m pytest -q로 돌린다
2 새 테스트에 요구 마커 @pytest.mark.req(id="REQ-…")를 붙인다
3 .env는 읽지 않는다
4 엔드포인트의 오류는 HTTPException으로 내고 detail은 한국어 한 문장으로 쓴다

판단의 질문은 「어떤 작업에든 적용되는가」(그렇다면 CLAUDE.md)와 「예외가 하나도 없어야 하는가」(그렇다면 설정이나 훅, 그리고 CLAUDE.md에 요약)이다. 3번과 10번은 두 곳에 둔다. 결과는 10-3과 10-4에서 쓴다.

7. 개인 설정과 팀 설정의 구분

7-1. 무엇을 어디에

CLAUDE.md, .claude/rules/, .claude/settings.json은 팀 파일로 올리고, CLAUDE.local.md(예: 보고를 짧게 하라는 내 지시)와 .claude/settings.local.json(예: uvicorn의 개인 허용)은 올리지 않는다[C9]. 판단의 질문은 「이 규칙이 없으면 다른 팀원의 결과가 달라지는가」이다. 그렇다면 팀 파일에, 내 PC의 값이나 습관만 개인 파일에 둔다.

7-2. .gitignore에 넣는 까닭

Claude Code는 로컬 설정 파일을 처음 쓸 때 그것을 이 컴퓨터의 전역 제외 파일에 더할 뿐이고[C2], CLAUDE.local.md는 넣어 주지도 않는다[C1]. 다른 팀원의 컴퓨터에는 효과가 없으므로 두 파일을 저장소의 .gitignore에 적는다.

7-3. 따라 하기 2: 개인 파일 만들기와 제외

개인 파일 둘을 만들고 git check-ignore -v(어느 파일의 몇째 줄이 무시하게 하였는가[G7])로 확인한다.

터미널 
mkdir -p .claude
cat > .claude/settings.local.json <<'EOF'
{
  "permissions": {
    "allow": [
      "Bash(uvicorn *)"
    ]
  }
}
EOF
printf '# 개인 지시 (이 컴퓨터, 이 저장소에서만)\n- 작업을 마치면 바뀐 파일 목록과 python -m pytest -q의 결과 줄만 짧게 보고한다\n' > CLAUDE.local.md
git status --short

?? .claude/
?? CLAUDE.local.md
종료 코드 1

종료 코드 1은 「무시되는 것이 없다」는 뜻이며, 이대로 git add -A를 하면 장면 4가 된다. .gitignore에 두 줄을 더한다.

.claude/ 폴더 자체는 무시하지 않는다. 그 안의 settings.json과 rules/는 팀 파일이기 때문이다.

7-4. 이미 올라간 개인 파일 내리기

무시 규칙은 추적하지 않는 파일에만 적용되므로, 이미 커밋한 개인 파일은 git rm --cached <파일> 뒤 커밋으로 추적을 멈춘다. 과거 커밋에는 남으므로 비밀 정보가 있었다면 키를 폐기하고 새로 발급한다(11장).

8. 저장소 규약

8-1. 규약이 하는 일

저장소 규약은 결과가 저장소에 들어올 때 작동하며, 이력 찾기(git log --grep "^feat(api)"), 릴리스 노트(13장), 검토의 배정을 가능하게 한다. 원본은 docs/운영/저장소규약.md 한 곳에 두고 CLAUDE.md에는 요점만 적는다.

8-2. 브랜치 이름

규약은 <종류>/<설명>이다. 종류는 feat, fix, docs, test, refactor, chore, ci이고, 설명은 영문 소문자, 숫자, 하이픈으로 쓴다(chore/team-rules). 뒤의 장이 쓰는 loop/, practice/, agent/도 check_commits.py가 허용한다.

8-3. 커밋 메시지: Conventional Commits

Conventional Commits 1.0.0은 첫 줄을 <type>[optional scope]: <description>으로 정하고, 빈 줄 뒤에 선택적 본문과 꼬리말을 둔다[K1]. 하위 호환을 깨는 변경은 ! 또는 꼬리말 BREAKING CHANGE:로 표시하며, 명세는 fix를 PATCH, feat를 MINOR, 호환을 깨는 변경을 MAJOR에 대응시킨다(13장의 릴리스 태그). jobprep은 여기에 더해 종류를 소문자로, 설명을 한국어로 마침표 없이 쓰고, 첫 줄을 72자 이하로 하며, 요구와 관련된 커밋에는 꼬리말 Refs: REQ-…를 적는다.

8-6. CODEOWNERS

CODEOWNERS(.github/, 루트, docs/ 가운데 한 곳)는 경로마다 소유자를 정하고, 그 경로를 바꾸는 PR에 소유자의 검토 요청을 보낸다[G5]. 한 줄은 패턴과 소유자이며, 마지막으로 맞는 줄이 이기므로 넓은 패턴을 위에 둔다. ! 부정과 [ ] 문자 범위는 쓸 수 없다.

/.claude/                 @GitHub아이디
/CODEOWNERS               @GitHub아이디

CODEOWNERS 자신에도 소유자를 둔다. 검토의 강제(보호 브랜치)는 13장에서 한다.

8-7. 리뷰 규칙과 규칙 파일의 검토

jobprep의 리뷰 규칙(규약 4절)은 작성자가 아닌 사람의 승인, 소유자의 검토, 에이전트의 변경도 diff로 리뷰하기, 규칙 파일을 바꾸는 PR에는 까닭과 lint_rules.py의 결과를 적기이다. 작성자는 자기 PR을 승인할 수 없으므로[G6] 개인 저장소에서는 점검표가 자기 검토의 기록이다.

규칙 파일은 코드보다 영향이 넓다. "Bash(git *)" 허용 하나는 모든 팀원의 에이전트가 강제 푸시까지 묻지 않게 한다. 그래서 규칙 파일에는 소유자, 바꾼 까닭, 기계 검사, 판의 태그(rules-v1)를 둔다.

8-8. 규약의 강제: commit-msg 훅

commit-msg 훅은 메시지 파일을 받아 0이 아닌 값으로 끝나면 커밋을 멈춘다[G8]. .git/hooks는 클론할 때 복사되지 않으므로[G9] 훅은 저장소의 .githooks/에 커밋하고 클론마다 git config core.hooksPath .githooks를 실행한다. macOS의 git은 실행 권한이 없는 훅을 조용히 무시하므로, Windows에서는 git update-index --chmod=+x로 실행 권한을 커밋에 남긴다.

훅은 git commit --no-verify로 건너뛸 수 있으므로[G8] 팀 설정에 Bash(git commit *--no-verify*) 거부 규칙을 넣는다. 짧은 옵션 -n은 맞지 않으므로(4-3) 마지막 자리는 PR 검토와 CI이다.

9. 규칙 유무 비교의 방법

9-1. 무엇을 비교하는가

규칙을 만들었다고 효과가 있는 것은 아니다. 지시는 따르지 않을 수 있고(1-2), 위치가 잘못되면 읽히지도 않는다(6-3). 그래서 같은 요청을 규칙이 없는 tdd-1과 규칙을 넣은 시점(rules-v1)에 보내, 셀 수 있는 위반의 수와 테스트의 통과를 함께 본다. 7장은 이 비교를 작업 여러 건으로, 12장은 반복 실행으로 넓힌다.

9-2. 조건의 통제

규칙 말고는 모두 같게 한다. 시작 코드는 규칙 파일만 다르고, 요청은 글자 그대로 새 세션에 보내며, 판, 모델, 권한 모드(예: Accept edits)를 /status로 확인해 적는다. 그래도 실행한 사람(교수와 학습자)이 다르고, 모델은 같은 조건에서도 결과가 매번 다르다. 한 번의 비교는 경향만 보여 주므로 diff를 읽어 위반의 자리와 까닭을 적는다.

9-3. 위반을 세는 법

count_violations.py는 시작점부터 HEAD까지의 변경과 커밋 메시지에서 셀 수 있는 위반 열 가지를 센다.

R1 LLM 호출은 api/llm.py만 거친다 R6 키 값(sk-ant-…)을 넣지 않는다
R2 모델 이름을 코드에 적지 않는다 R7 코드를 바꾸면 테스트도 바꾼다

정리

  • 팀 규칙은 세 층이다. 지시는 모델이 판단하고, 설정은 Claude Code가 강제하고, 저장소 규약은 사람과 Git·GitHub가 집행한다.
  • 지시 파일은 모두 이어 붙여 읽히고, 설정은 범위의 우선순위를 따르되 권한 목록은 합쳐 deny → ask → allow로 평가된다. 그래서 어느 범위의 거부든 허용을 이긴다.
  • 권한 규칙은 명령과 경로의 글자에 맞출 뿐이며, 남은 틈은 훅(6장)과 샌드박스(11장)가 맡는다.
  • 좋은 CLAUDE.md는 짧고, 확인할 수 있는 문장과 실행 명령과 이유를 담는다. 개인 설정은 .gitignore로 뺀다.
  • 규칙을 만든 것과 문제가 풀린 것은 다르다. 어긋남이 같은 요청에서 다시 나오지 않는지로 판정한다.

개념 점검 문항

  1. 사용자 설정에 "allow": ["Bash(git push *)"], 팀 설정에 "ask": ["Bash(git push *)"], 로컬 설정에 "deny": ["Bash(git push --force *)"]가 있다. git push origin main과 git push --force origin main은 각각 어떻게 판정되는가. 까닭을 평가 순서로 설명하라.
  2. 「.env를 읽지 않는다」를 CLAUDE.md에만 둔 경우와 Read(./.env) 거부 규칙으로만 둔 경우, 각각 막지 못하는 상황을 하나씩 들라.
  3. 다음 CLAUDE.md 줄을 확인할 수 있는 문장과 이유로 고쳐 쓰라. 「API 코드는 깔끔하고 안전하게 작성한다.」
  4. Windows의 팀원이 팀 설정에 "allow": ["Bash(.venv/Scripts/python -m pytest *)"]를 적어 올렸다. macOS의 팀원과 가상 환경을 켠 Windows 팀원의 세션에서 이 규칙은 각각 어떻게 작동하는가. 팀 설정에는 어떻게 쓰는 것이 알맞은가.
  5. CODEOWNERS가 다음과 같을 때 .claude/settings.json의 소유자는 누구인가. 「/.claude/ @a」 다음 줄에 「* @b」. 의도대로 고치려면 어떻게 하는가.
