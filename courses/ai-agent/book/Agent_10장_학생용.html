AI에이전트 기획 및 개발

10장

멀티 에이전트 운영 시스템의 설계: 역할 분담과 병렬 작업

2027학년도 「AI에이전트 기획 및 개발」의 준비 중인 교재입니다. 편집 상태를 검토하기 위해 미리 공개한 것으로, 수업 전에 내용과 순서가 바뀔 수 있습니다.

학사 12주차 · 교재 10 · 4부 멀티 에이전트 운영

1장에서 「jobprep 운영 에이전트 시스템」의 역할을 기획, 구현, 테스트, 검토, 배포, 관측으로 나누어 역할 정의서에 적었다. 그 뒤 2~9장은 그 시스템의 부품을 하나씩 만들었다. 2장의 테스트는 완료 조건이 되었고, 3장의 규칙과 권한은 모든 에이전트가 따르는 공통 규약이 되었으며, 6장의 검토 서브에이전트는 작성자와 다른 맥락에서 변경을 읽는 검토자가 되었다. 7장은 그 부품을 하네스로 조립했고, 8장은 판정과 재시도와 사람 넘김이 있는 루프를 만들었으며, 9장은 그 루프가 API 수준에서 어떻게 도는지 직접 구현했다. 지금까지는 에이전트 하나가 일하고 사람이 그 결과를 판정하는 구조였다.

이 장은 과목의 주축이다. 역할 정의서의 역할들을 실제로 움직이는 역할 에이전트로 만들고, 그 에이전트들이 하나의 이슈를 나누어 맡아 병렬로 일한 뒤 판정을 거쳐 사람의 승인으로 병합되는 운영 시스템을 설계하고 돌린다. 여러 에이전트를 쓰는 일은 에이전트 하나를 쓰는 일보다 언제나 낫지 않다. 토큰이 몇 배로 들고, 에이전트 사이에 정보가 새거나 엇갈리며, 같은 파일을 동시에 고치면 서로의 일을 덮어쓴다. 그래서 이 장의 절반은 「언제 나누는가」와 「나눈 일이 어떻게 충돌하지 않게 하는가」를 다룬다.

이 장에서 만드는 것은 하나다. jobprep의 이슈 ISSUE-07(관심 공고 내보내기 기능과 그 API)을 계획서와 작업 카드로 나누고, 내 PC의 Orca에서 작업마다 git worktree와 브랜치를 하나씩 만들어 자기 계정의 Claude Code 세션 둘이 나란히 구현하게 한 뒤, 판정 스크립트로 판정하고 사람이 정한 순서로 병합하는 한 바퀴다. 두 작업은 같은 변경 기록 파일의 끝에 한 줄씩 더하므로 뒤의 병합에서 충돌이 하나 난다. 그 충돌을 뒤 작업의 작업 공간에서 풀고 다시 판정을 받아 병합하는 것이 이 장에서 해결하는 문제다. 그 과정에서 역할 에이전트 정의(.claude/agents/), 판정·병합 스크립트(ops/multi/), 설계서, 인계 문서와 실행 기록이 저장소에 남는다. 같은 흐름을 스크립트가 조정하는 길은 원리로 읽고 교수 시연으로 본다.

같은 학기 프로젝트실습Ⅱ의 팀은 사람 여럿과 에이전트 여럿이 한 저장소에서 동시에 일한다. 이 장의 작업 분할 기준, worktree와 브랜치 규칙, 인계 문서의 양식, 병합 순서와 충돌 처리는 그 팀 저장소에 그대로 옮겨 쓸 수 있다. 이어지는 11장은 이 시스템의 보안 경계를, 12장은 실행 기록과 비용을, 13장은 이 흐름을 지속적 통합으로 옮기는 일을 다룬다.

학습 목표

  • 작업의 성질을 보고 단일 에이전트와 멀티 에이전트 가운데 무엇을 쓸지 판단하고, 그 판단의 근거를 비용과 실패 유형으로 설명할 수 있다.
    • 예시: 「요약 API의 프롬프트를 고쳐 정확도를 높인다」는 파일 하나에 몰린 순차 작업이므로 에이전트 하나로 하고, 「내보내기 API와 웹 단추를 함께 만든다」는 계약을 정하면 파일이 겹치지 않으므로 둘로 나눈다고 판단한다.
    • 활용: 프로젝트실습Ⅱ에서 팀원과 에이전트에게 일을 나눌 때, 나누어서 얻는 시간과 늘어나는 조정 비용을 같은 표로 비교한다.
  • 역할 정의서의 역할을 Claude Code의 서브에이전트 정의 파일로 옮기고, 역할마다 권한, 도구, 입력, 출력, 완료 조건을 정할 수 있다.
    • 예시: 1장 역할 정의서의 R2 구현을 .claude/agents/implementer.md로 옮기면서 도구를 Read, Grep, Glob, Edit, Write, Bash로 한정하고, 「tests/를 고치지 않는다」를 지시문과 판정 검사 양쪽에 둔다.
    • 활용: 팀의 「역할」을 문서가 아니라 실행되는 정의로 만들어, 누가 실행해도 같은 권한과 형식으로 일하게 한다(운영 요건의 일관성).
  • 계획서, 작업 카드, 결과 보고로 에이전트 사이의 인계를 설계하고, 소유 파일 단위로 작업을 나누어 병렬 작업의 충돌을 계획 단계에서 막을 수 있다.
    • 예시: ISSUE-07을 T1(API: api/export.py, api/main.py)과 T2(웹: web/js/export.js, web/index.html)로 나누고, 둘 다 고치고 싶어 하는 docs/요구사항명세서.md는 조정자가 병합 뒤에 한 번 고치도록 계획서에 적는다.
    • 활용: 대화 기록이 남지 않는 에이전트에게도, 새로 합류한 팀원에게도 같은 카드 한 장으로 일을 넘긴다.
  • Orca의 작업 공간(git worktree)과 에이전트별 브랜치로 병렬 작업을 돌리고, 판정 스크립트로 결과를 판정하며, 병합 충돌을 작업 쪽에서 풀어 사람이 정한 순서로 병합할 수 있다.
    • 예시: Orca에서 feat/issue-07을 출발점으로 작업 공간 둘을 만들어 세션 둘에 카드를 넘기고, judge.sh로 판정한 뒤 merge.sh ISSUE-07 T1 T2로 병합한다. T2에서 충돌이 나면 T2의 작업 공간에서 풀고 다시 판정한다.
    • 활용: 13장의 지속적 통합에서 같은 판정을 풀 리퀘스트마다 돌린다.

0. 시작하기

내 PC의 VS Code와 Git Bash(macOS는 터미널, 부록 A-4), 키트 저장소(부록 A-7), 가상 환경(부록 A-9), Claude Code의 로그인(부록 A-5)은 부록 A의 절차를 따른다. 이 장은 Orca가 필요하다. 설치와 PC 자원의 확인은 부록 A-17-1, A-17-2를 10장 전 주에 마친다. 파이썬 출력을 파이프로 넘기는 명령이 있으므로 PYTHONUTF8=1(부록 A-4-4)을 등록해 둔다. 터미널은 둘을 쓴다. 하나는 직접 명령을 치는 [터미널]이고, 다른 하나는 9절에서 Orca가 작업 공간마다 여는 [Orca 작업 공간 터미널]이다.

이 장의 실행 상한. 실제 모델은 9절에서 Orca의 작업 공간 둘에 여는 Claude Code 대화형 세션 둘에서만 부른다. 작업마다 시도는 2회까지이다(첫 시도와, 판정이 거부했을 때 한 번 더). 계획서와 인수 테스트는 가짜 에이전트가 쓰며, planner 에이전트를 대화형으로 한 번 불러 보는 것은 [선택]이다. 스크립트 조정자로 실제 모델을 무인으로 되풀이해 돌리는 실행(8-4)과 Orca의 오케스트레이션은 교수 시연이며, 그 기록은 키트의 시연기록/으로 읽는다. jobprep의 LLM 호출은 이 장 내내 모의 모드(LLM_FAKE=1)이므로 API 키가 필요 없다.

1. 단일 에이전트의 한계와 멀티 에이전트의 비용

1-1. 에이전트 하나가 부딪히는 세 한계

1장에서 에이전트를 「모델 + 도구 + 루프」로 정의했다. 그 정의의 에이전트 하나에게 저장소 운영 전체를 맡기면 세 가지 한계에 부딪힌다.

첫째는 컨텍스트이다. 파일을 읽고 테스트를 돌리고 기록을 훑을 때마다 그 내용이 컨텍스트 창에 쌓인다. Anthropic의 연구 시스템에서는 대화가 20만 토큰을 넘으면 앞부분이 잘리므로 주도 에이전트가 계획을 따로 저장해야 했다[E2]. Claude Code의 서브에이전트는 자기 컨텍스트 창에서 일하고 긴 출력은 그 안에 남긴 채 요약만 주 대화로 돌려준다[C13].

둘째는 전문화이다. 같은 에이전트가 계획하고 구현하고 자기 코드를 검토하면, 검토할 때도 구현할 때의 가정을 그대로 들고 온다. 6장에서 검토 서브에이전트를 따로 둔 까닭이다. 역할마다 시스템 프롬프트, 허용 도구, 권한을 따로 두면 「구현 역할은 테스트를 고칠 수 없다」, 「검토 역할은 파일을 쓸 수 없다」 같은 경계를 설정으로 만들 수 있다[C13].

셋째는 병렬성이다. 에이전트 하나는 한 번에 한 가지 일을 한다. 서로 기다릴 필요가 없는 일 둘이 있어도 차례로 처리한다. Anthropic의 연구 시스템은 주도 에이전트가 하위 에이전트 3~5개를 동시에 띄우고, 하위 에이전트가 다시 도구 여러 개를 동시에 부르게 하여 복잡한 질문의 조사 시간을 최대 90%까지 줄였다고 보고했다[E2].

한계 에이전트 하나에서 생기는 일 멀티 에이전트의 대응 jobprep에서의 예
컨텍스트 읽은 파일과 출력이 쌓여 앞의 결정이 밀려나거나 잘린다 작업마다 새 컨텍스트, 결과는 요약이나 파일로 돌려준다 구현 에이전트는 자기 작업 카드와 관련 파일만 읽는다
전문화 같은 가정으로 쓰고 검토한다. 모든 일에 같은 권한을 준다 역할마다 지시문, 도구, 권한을 따로 둔다 검토 에이전트는 읽기 도구만, 구현 에이전트는 tests/를 못 고친다
병렬성 독립된 일도 차례로 한다 독립된 작업을 동시에 실행한다 API(T1)와 웹 단추(T2)를 두 작업 공간에서 동시에 만든다

1-2. 멀티 에이전트의 세 비용

나누면 얻는 것이 있는 만큼 치르는 것도 있다.

토큰. 에이전트는 같은 질문을 채팅으로 할 때보다 약 4배, 멀티 에이전트 시스템은 약 15배의 토큰을 썼다[E2]. 같은 글에서 웹 검색 평가(BrowseComp)의 성능 차이 가운데 80%를 토큰 사용량 하나가 설명했다고 하였으니, 토큰을 더 쓰면 결과가 나아지는 과제가 있다는 뜻이기도 하다. 그래서 그 글은 멀티 에이전트를 과제의 가치가 늘어난 비용을 감당할 만큼 클 때 쓰라고 한다[E2]. Claude Code 문서도 에이전트 팀이 세션 하나보다 토큰을 훨씬 많이 쓰며, 팀원이 계획 모드로 일할 때 표준 세션의 약 7배를 쓴다고 적고 있다[C19]. 학생 계정의 사용량 한도 안에서 실습하는 이 과목에서는 이 비용이 곧 수업 진행의 제약이 된다.

조정. 일을 나누려면 누군가 나누는 방법을 정하고, 나눈 조각을 넘기고, 돌아온 결과를 합쳐야 한다. 지시가 모호하면 하위 에이전트들이 같은 조사를 되풀이했다. 연구 시스템의 초기판에서는 반도체 공급 문제를 맡은 하위 에이전트 하나가 2021년 자동차 반도체 위기를 조사하는 동안 다른 둘이 2025년 공급망을 똑같이 조사했다[E2]. 주도 에이전트가 하위 에이전트들이 모두 끝나기를 기다리는 동기식 실행은 그 자체로 병목이 되었다[E2].

충돌. 둘 이상의 에이전트가 같은 파일을 고치면 나중에 쓴 쪽이 앞의 변경을 덮어쓴다. Claude Code 문서는 에이전트 팀에서 「두 팀원이 같은 파일을 고치면 덮어쓰기가 일어난다」고 경고하고, 팀원마다 다른 파일 묶음을 맡기라고 권한다[C23]. 같은 파일이 아니어도, 따로는 맞는 두 변경을 합치면 깨지는 경우가 있다(7-4의 의미 충돌).

비용 근거 이 장의 대책
토큰 채팅 대비 에이전트 약 4배, 멀티 에이전트 약 15배[E2]. 에이전트 팀은 계획 모드에서 약 7배[C19] 나눌 가치가 있을 때만 나눈다(2절). 실습의 실제 모델은 세션 둘, 작업마다 시도 2회로 묶는다
조정 모호한 위임은 중복 작업을 낳는다. 동기식 대기는 병목이 된다[E2] 계획서와 작업 카드에 목표, 계약, 경계, 완료 조건을 쓴다(5절)
충돌 같은 파일의 동시 편집은 덮어쓰기를 낳는다[C23] 소유 파일 단위 분할, worktree와 브랜치 분리, 병합 순서, 작업 쪽에서의 충돌 풀이(7절, 9-6)

[최신 자료 자리: 에이전트 팀의 토큰 배수] 에이전트 팀이 계획 모드에서 표준 세션의 약 7배를 쓴다는 값은 Claude Code 문서 「Manage costs effectively」(https://code.claude.com/docs/en/costs)의 2026-11-14 서술이다. 판이 바뀌면 배수가 달라질 수 있으므로 수업 전에 다시 확인한다. 연구 시스템의 약 4배·15배[E2]는 2025-06-13에 공개된 글의 값이므로 바뀌지 않는다.

세 비용 밖에서 병렬의 수를 묶는 것이 기계의 자원이다. 에이전트는 모델의 답을 기다리는 동안 자원을 거의 쓰지 않지만, 테스트를 돌리는 동안에는 CPU 코어 하나 안팎과 수백 MB의 메모리를 쓴다. 병렬 수가 코어 수를 넘으면 작업들이 코어를 다투어 각자 느려지고 병렬의 이득이 사라진다. 이 과목은 각자의 PC에서 동시에 돌리는 에이전트를 2개로 둔다(9절의 Orca 작업 공간 둘). 자기 PC의 코어 수(nproc)와 비어 있는 메모리를 재는 법과, 모자랄 때 두 세션의 테스트를 번갈아 돌리는 기준은 부록 A-17-2에 있다. 병렬 수를 늘리면 사용량도 그만큼 는다. 이 장의 실행 상한(세션 둘, 작업마다 시도 2)은 계정의 사용량과 PC의 자원을 함께 본 값이다.

2. 멀티 에이전트의 판단 기준

2-1. 가장 단순한 해법부터

Anthropic은 가장 단순한 해법을 먼저 찾고, 복잡성은 결과를 분명히 낫게 만들 때만 더하라고 권한다[E1]. 멀티 에이전트는 그 복잡성의 끝에 있다. 연구 시스템의 글은 너비 우선 조사, 컨텍스트 하나에 다 들어가지 않는 정보, 복잡한 도구가 많은 일에 멀티 에이전트가 잘 맞고, 모든 에이전트가 같은 맥락을 공유해야 하거나 의존이 많은 일에는 맞지 않는다고 적었다[E2]. Claude Code 문서도 순차 작업, 같은 파일의 편집, 의존이 많은 작업에는 세션 하나나 서브에이전트가 낫다고 한다[C23].

2-2. 다섯 질문

이 장은 다음 다섯 질문으로 판단한다. 설계서 양식의 1절이 이 표이다.

질문 「예」이면 「아니오」이면
① 작업이 서로 기다리지 않는 부분으로 나뉘는가 병렬로 나눌 수 있다 나누어도 차례로 돌 뿐이다. 파이프라인이나 에이전트 하나
② 한 에이전트의 컨텍스트에 다 들어가지 않는가 하위 에이전트가 읽고 요약하게 한다 컨텍스트를 나눌 까닭이 없다
③ 역할마다 다른 권한과 도구가 필요한가 역할 에이전트로 나눈다(검토자, 테스트 작성자) 같은 권한이면 나누어도 경계가 생기지 않는다
④ 병렬로 줄어드는 시간이 늘어나는 토큰과 조정보다 값진가 나눈다 에이전트 하나로 한다
⑤ 나눈 결과를 기계로 판정할 수 있는가 판정을 자동화하고 사람은 병합만 본다 사람이 모든 결과를 읽어야 하므로 나눈 이득이 줄어든다

①과 ④가 「아니오」이면 다른 질문의 답과 상관없이 나누지 않는다. ③만 「예」이면 병렬이 아니라 역할 분리(생성자-검토자, 3절)로 충분하다. ⑤가 「아니오」인 작업(예: 장애 보고서의 문장 다듬기)은 나누어도 사람의 검토 부담이 줄지 않는다.

다섯 질문과 함께 보는 기준이 하나 있다. 병렬은 읽기(조사·검토)에 강하고, 쓰기는 worktree로 격리해야 병렬이 된다. 파일을 읽고 요약만 돌려주는 일은 여럿이 같은 저장소를 동시에 읽어도 서로를 해치지 않는다. Anthropic의 연구 시스템 글은 코딩 과제에는 「진짜로 병렬화할 수 있는 작업」이 조사보다 적다고 적었고[E2], Claude Code 문서는 병렬 조사는 경로가 서로 의존하지 않을 때 잘 맞으며[C13] 파일을 고치는 병렬 세션에는 각자의 worktree를 주라고 한다[C21]. 이 장도 같다. 검토(읽기)는 판정이 차이를 넘겨 주므로 작업 공간을 따로 만들지 않고, 구현(쓰기)은 작업마다 worktree와 브랜치를 준다(7절).

3. 구조의 유형

3-1. 네 가지 구조

여러 에이전트를 묶는 방식은 몇 가지 유형으로 정리된다. Anthropic의 「Building effective agents」는 워크플로 패턴으로 프롬프트 사슬, 라우팅, 병렬화(구획 나누기와 투표), 조정자-작업자, 평가자-최적화자를 든다[E1]. 이 장은 그 가운데 운영에 쓰이는 넷을 쓴다.

구조 원래 이름[E1] 흐름 잘 맞는 경우 jobprep의 예
조정자-작업자 orchestrator-workers 조정자가 일을 나누어 작업자에게 맡기고 결과를 모은다 하위 작업을 미리 다 알 수 없을 때. 여러 파일에 걸친 코딩 변경 이슈를 계획서로 나누고 구현 에이전트 둘에게 맡긴다
파이프라인 prompt chaining 앞 단계의 출력이 다음 단계의 입력이 된다. 단계 사이에 관문을 둔다 고정된 단계로 깔끔하게 나뉠 때 계획 → 인수 테스트 → 구현 → 판정 → 병합
생성자-검토자 evaluator-optimizer 한쪽이 만들고 다른 쪽이 평가해 돌려보낸다 평가 기준이 분명하고 되풀이가 품질을 올릴 때 구현 → 판정 거부 → 재작업(8장 루프의 확장)
경쟁 후 선택 parallelization: voting 같은 일을 여럿이 따로 하고 기준으로 하나를 고른다 답이 불확실하고 여러 시도를 비교할 가치가 있을 때 원인 모를 장애에 가설별 조사, 같은 카드를 두 번 구현해 나은 쪽 병합

조정자-작업자와 프롬프트 사슬의 차이는 「누가 단계를 정하는가」이다. 프롬프트 사슬은 단계가 코드에 고정되어 있고, 조정자-작업자는 조정자가 입력을 보고 하위 작업을 정한다. Anthropic은 조정자-작업자의 예로 「여러 파일을 복잡하게 바꾸는 코딩 제품」을 든다[E1]. 연구 시스템은 이 구조에 인용을 붙이는 전용 에이전트를 더해, 조정자-작업자 뒤에 파이프라인 한 단계를 이은 모양이다[E2].

    P --> W1[작업자 T1]

3-2. 경쟁 후 선택의 비용 [선택]

경쟁 후 선택은 같은 일을 N번 하므로 비용도 N배이고, 둘 다 통과하면 무엇으로 고를지 미리 정해야 한다. 정하지 않으면 결국 사람이 둘을 다 읽는다. Claude Code 문서는 원인 모를 버그에 팀원 다섯을 붙여 가설을 서로 반박하게 하는 예를 든다[C23].

3-3. Claude Code의 병렬 실행 방법 [선택]

Claude Code는 2026-11 기준으로 여러 일을 동시에 하는 방법을 다섯 가지로 정리한다[C22]. 이름과 화면은 판마다 바뀔 수 있다.

4. 역할 정의서의 재검토

4-1. 문서의 역할에서 실행되는 역할로

1장의 역할 정의서는 역할마다 권한, 입력, 출력, 완료 조건, 사람 승인 지점을 적은 문서였다. 문서는 사람이 읽고 따르는 것이다. 이 장은 같은 내용을 에이전트가 실행될 때 실제로 적용되는 곳으로 옮긴다. 옮길 곳은 네 군데다.

역할 정의서의 항목 옮기는 곳 강제되는가
역할(목적) 정의 파일의 name, description, 본문 첫 문단 위임할 때 Claude가 description을 보고 고른다[C13]
권한: 도구 정의 파일의 tools, disallowedTools 예. 목록에 없는 도구는 쓸 수 없다[C13]
권한: 명령과 경로 .claude/settings.json의 permissions.deny, 훅, 판정 스크립트 예. 다만 settings.json은 모든 역할에 같이 적용된다
입력 지시문(작업 카드의 경로), 정의 본문의 「일하는 순서」 아니오. 지시이다
출력 결과 보고 양식, 커밋 메시지 규약 판정의 「보고」 항목이 있는지만 본다
완료 조건 작업 카드의 「완료 조건」, 판정 스크립트의 검사 판정이 기계로 확인한다
사람 승인 지점 계획서의 승인 줄, merge.sh를 사람이 실행 예. 승인 줄이 없으면 prepare.sh가 멈춘다

이 표의 마지막 열이 핵심이다. 역할의 경계를 지시문에만 두면 에이전트가 어길 수 있다. MAST의 「역할 명세 위반」(FM-1.2)이다[M1]. 그래서 같은 경계를 지시문과 검사 두 곳에 둔다. 「구현 역할은 tests/를 고치지 않는다」는 implementer.md 본문의 지시이면서, judge.sh의 「동결」 항목이 실제로 바뀐 파일을 보고 거부하는 검사이다.

4-2. 서브에이전트 정의 파일의 형식

역할 에이전트는 Claude Code의 서브에이전트 정의 파일로 만든다. 서브에이전트는 YAML 프런트매터가 붙은 마크다운 파일이고, 본문이 그 에이전트의 시스템 프롬프트가 된다[C13]. 서브에이전트는 Claude Code의 기본 시스템 프롬프트를 받지 않고, 이 본문과 기본 환경 정보만 받는다는 점에 주의한다[C13]. 본문이 곧 그 에이전트가 아는 전부이므로, 역할 정의서의 내용을 빠짐없이 옮겨야 한다.

permissionMode, hooks, memory 권한 모드, 이 에이전트에만 적용되는 훅, 대화를 넘어 남는 기억 폴더 쓰지 않는다(훅은 11장)

[최신 자료 자리: 서브에이전트 정의의 필드와 모델 별칭] 필드 목록과 model에 쓸 수 있는 별칭을 확인할 곳은 https://code.claude.com/docs/en/sub-agents이다. 필드는 2026-11-14에 문서로, 별칭은 2026-11-15에 이 PC의 Claude Code 2.1.296 claude --help(--model 설명이 fable, opus, sonnet을 예로 든다)로 확인하였다. 새 모델이 나오면 별칭이 가리키는 모델이 바뀐다.

표는 2026-11-14에 공식 문서에서 확인한 필드의 일부이다[C13]. 문서는 「여러 단어로 된 필드 이름은 camelCase이고, 알 수 없는 필드는 소리 없이 무시된다」고 적는다[C13]. 3장에서 다룬 settings.json처럼 오류가 나지 않으므로, allowed-tools처럼 철자를 틀리면 도구 제한이 아무 경고 없이 사라진다. 키트의 ops/multi/check_agents.py가 이 실수를 찾는다.

같은 이름의 정의가 여럿이면 조직의 관리 설정, --agents 옵션, 프로젝트의 .claude/agents/, 사용자의 ~/.claude/agents/, 플러그인 순서로 앞의 것이 쓰인다[C13].

역할 에이전트는 팀이 함께 쓰는 정의이므로 프로젝트의 .claude/agents/에 두고 커밋한다(3장의 규칙). 개인의 ~/.claude/agents/implementer.md보다 프로젝트 쪽이 우선한다.

4-3. 도구 제한의 함정

disallowedTools에 Bash(git push *)처럼 조건을 붙이면, 문서에 따르면 그 명령만이 아니라 Bash 도구 전체가 빠진다[C13]. 「git push만 막고 테스트는 돌리게 하자」는 의도로 쓰면 구현 에이전트가 pytest를 돌리지 못한다. 명령 단위로 막으려면 3장의 settings.json permissions.deny나 훅을 쓴다. 다만 settings.json은 그 저장소의 모든 세션과 모든 역할에 같이 적용된다. 「구현 역할만 tests/를 못 고친다」처럼 역할마다 다른 경로 제한은 settings.json으로 표현할 수 없다. 테스트 역할은 tests/에 새 파일을 써야 하기 때문이다.

이 장은 역할별 경로 제한을 두 겹으로 둔다. 첫째, 정의 본문의 「하지 않는 것」(지시). 둘째, 판정 스크립트의 「범위」와 「동결」 검사(사후 강제). 사전 강제가 필요하면 정의 파일의 hooks 필드로 그 에이전트에만 적용되는 PreToolUse 훅을 붙일 수 있다[C13]. 11장 보안에서 이 방법을 쓴다.

5. 인계 문서

5-1. 왜 문서로 넘기는가

서브에이전트는 새 컨텍스트로 시작한다. 받는 것은 자기 시스템 프롬프트, 위임 메시지, CLAUDE.md, git 상태 요약, 미리 읽게 한 스킬뿐이다[C13]. 에이전트 팀의 팀원도 주도 세션의 대화 기록을 물려받지 않고[C23], 헤드리스 구현 에이전트는 지시문 한 줄과 저장소의 파일만 받는다.

그래서 에이전트 사이의 인계는 「무엇을 넘기는가」를 설계하는 일이다. Anthropic의 연구 시스템은 주도 에이전트가 하위 에이전트에게 일을 맡길 때 네 가지를 주게 했다. 목표, 출력 형식, 쓸 도구와 자료에 대한 안내, 분명한 작업 경계이다[E2]. 이 넷이 빠진 짧은 지시가 1-2의 중복 조사를 낳았다. 또 하위 에이전트의 결과를 대화로 전달하면 단계마다 정보가 줄고 바뀌는 「전화 놀이」 문제가 생기므로, 결과는 외부 저장소(파일)에 두고 가벼운 참조만 넘기게 했다[E2].

이 장의 인계 문서는 세 가지이다.

문서 쓰는 쪽 → 읽는 쪽 담는 것 위치
계획서 planner → 사람(승인), tester, 조정자 목표와 범위, 정한 것, 계약, 작업 분할, 공유 파일, 병합 순서, 위험 docs/운영/인계/ISSUE-07/계획서.md
작업 카드 planner → implementer, 판정 스크립트 작업 하나의 목표, 계약, 소유 파일, 인수 테스트, 하지 않는 것, 완료 조건 …/T1_카드.md, …/T2_카드.md
결과 보고 implementer → 조정자, 사람 바꾼 파일, 확인한 명령과 결과, 계약과 다른 점, 요청, 남은 위험 …/T1_보고.md, …/T2_보고.md

세 문서 모두 저장소에 커밋된다. 결과 보고는 구현 에이전트가 자기 작업 브랜치에 커밋하므로, 병합되면 코드와 함께 통합 브랜치로 들어온다. 대화가 끝나도, 세션이 바뀌어도, 다른 사람이 이어받아도 같은 문서를 본다.

## 정하지 않은 것

- 관심 공고가 하나도 없을 때의 동작
- 번호가 잘못되었거나 없는 공고일 때의 응답
- 한 번에 내보낼 수 있는 공고 수

이슈는 사용자의 말로 쓰여 있고, 계획서는 이것을 판정할 수 있는 말로 바꾼다. 특히 「정하지 않은 것」은 계획서에서 반드시 닫는다. 닫지 않으면 T1은 「없는 번호는 건너뛴다」, T2는 「404를 보여 준다」처럼 서로 다른 답을 정해, 둘 다 자기 테스트를 통과하는데 합치면 맞지 않는다. MAST의 「확인 질문을 하지 않음」(FM-2.2)과 「추론과 행동의 불일치」(FM-2.6)이다[M1]. 무인 실행에서는 계획 단계가 질문에 답해 두는 유일한 자리이다.

5-3. 계약

계획서의 핵심은 계약(contract)이다. 병렬로 일하는 작업이 서로의 결과를 기다리지 않으려면, 한 작업의 출력이 다른 작업의 입력이 되는 자리의 모양을 먼저 정해야 한다. ISSUE-07에서는 API의 경로, 매개변수, 응답 형식, 오류가 계약이다. 견본 계획서의 3절이 그 계약이다.

터미널 
sed -n '/## 3\. 계약/,/## 4\./p' ops/multi/견본/ISSUE-07/계획서.md
## 3. 계약 (작업 사이의 약속)

| 항목 | 내용 |
|---|---|
| 경로 | `GET /api/favorites/export?ids=3,1` (`ids`: 쉼표로 구분한 공고 번호) |
| 성공 | 200, `Content-Type: text/csv; charset=utf-8`, `Content-Disposition: attachment; filename="favorites.csv"` |
| 본문 | BOM(`﻿`)으로 시작. 머리줄 `id,title,company,field,deadline,days_left`, 행은 마감일 오름차순 |
| 오류 | 422(번호 형식, 개수), 404(없는 공고, `detail`에 번호) |
| 웹 | `web/js/export.js`가 `loadFavorites()`로 번호를 읽어 위 주소를 연다. 단추의 id는 `export-favorites` |

경로를 `/api/jobs/export`로 하지 않은 까닭: `GET /api/jobs/{job_id}`가 먼저 등록되어 있어 `export`가 공고 번호로 해석되면 422가 난다. ...

마지막 문단은 계획 단계에서 피한 함정이다. FastAPI는 등록한 순서대로 경로를 맞춰 보므로, /api/jobs/export를 끝에 더하면 앞의 /api/jobs/{job_id}가 먼저 맞고 export를 정수로 바꾸지 못해 422가 난다. 계약에서 겹치지 않는 경로를 정해 두면 두 작업 모두 기존 경로의 순서를 신경 쓸 필요가 없다. 계약은 공유 파일(api/main.py)의 위험을 줄이는 설계이기도 하다.

계약은 문장으로만 두지 않고 인수 테스트로 고정한다. T1의 계약은 tests/test_favorites_export.py가, T2의 계약은 tests/test_web_export.py가 잰다. 테스트가 먼저 있으면 계약과 다른 구현은 판정에서 걸린다. 2장의 「테스트가 완료 조건이다」를 작업 사이의 약속으로 넓힌 것이다.

5-4. 작업 카드

작업 카드는 받는 에이전트가 계획서를 읽지 않아도 일을 끝낼 수 있게 쓴다. 견본 T1 카드의 머리 부분을 본다.

- 인수 테스트: `tests/test_favorites_export.py`

카드의 「하지 않는 것」은 1-3의 실패 표에서 나온다(명세서는 조정자가 고친다, tests/를 고치지 않는다, 기존 경로의 동작을 바꾸지 않는다). 「완료 조건」은 판정이 실제로 보는 것과 같은 말로 쓴다. 카드에 없는 조건으로 판정하면 에이전트가 맞출 수 없고, 판정에 없는 조건은 지켜졌는지 아무도 모른다.

5-5. 결과 보고

결과 보고 양식은 짧다. 조정자와 사람이 대화 기록을 열지 않고 이 보고와 커밋만 보고 판단하게 하려는 것이다.

양식의 뒷부분은 「계약과 다른 점」, 「요청 (소유 파일 밖에서 필요한 일)」, 「남은 위험」이다. 「요청」 칸이 소유 파일 규칙의 짝이다. 소유 밖의 파일을 고쳐야 하면 고치지 않고 여기에 적고, 조정자가 모아 한 번에 고친다(7-1). MAST의 「정보를 넘기지 않음」(FM-2.4)을 칸으로 막는 것이다[M1].

양식의 「확인」 칸에는 실행한 명령과 결과의 마지막 줄을 붙인다. 그래도 보고의 「완료」를 그대로 믿지 않는다. 결과를 믿게 해 주는 것은 에이전트의 말이 아니라 사람이 정해 둔 완료 조건이다. 9-5의 예시에서는 「결과: 완료」라고 보고한 작업을 판정이 거부한다.

생각해 볼 것. 이슈 카드의 「정하지 않은 것」 셋이 견본 계획서 2절의 어느 줄에서 닫혔는지 설계서 4절 아래에 한 줄씩 적는다. 그리고 견본 계획서에 없는 질문 하나(예: CSV의 열 순서를 바꾸고 싶을 때 누가 정하는가)를 더 적는다.

6. 컨텍스트 격리와 공유 상태

6-1. 각 에이전트가 보는 것

멀티 에이전트 시스템에서는 「누가 무엇을 보는가」를 표로 그려 두어야 한다. 보지 못하는 것은 문서로 넘겨야 하고, 보지 말아야 하는 것은 막아야 하기 때문이다.

실행 방식 대화 기록 CLAUDE.md, 규칙 저장소 파일 다른 에이전트의 작업 결과가 돌아가는 곳
주 세션 전부 읽는다 기본 작업 공간 서브에이전트의 요약 사람
서브에이전트 보지 못함. 위임 메시지만 읽는다(omitClaudeMd로 끌 수 있다) 주 세션과 같은 작업 공간. isolation: worktree이면 임시 worktree 보지 못함 주 세션에 요약
에이전트 팀의 팀원 보지 못함. 생성 지시만 읽는다 주도 세션과 같은 작업 공간(분리하지 않음) 메시지와 공유 작업 목록 주도 세션과 다른 팀원
이 장의 구현 세션(Orca 작업 공간의 implementer) 자기 세션의 대화만. 시작은 지시문 한 덩어리 작업 공간의 CLAUDE.md를 읽는다 자기 worktree 보지 못함 결과 보고 파일과 커밋

서브에이전트와 팀원은 Claude Code 문서를 따랐다[C13][C23]. 마지막 줄은 이 장의 설계이다. 구현 세션은 다른 작업의 진행을 볼 필요가 없다. 계약이 있기 때문이다. 다른 작업의 결과가 필요하다면 계획이 작업을 잘못 나눈 것이다.

6-2. 공유 상태

에이전트들이 컨텍스트를 나누지 않는 대신, 상태는 저장소에서 나눈다. 이 장의 공유 상태는 세 가지이다.

  • 저장소(커밋과 브랜치): 코드, 테스트, 인계 문서. 각 역할이 자기 브랜치에 쓰고, 진실의 원천은 통합 브랜치 feat/issue-07이다.
  • 이슈: 요청과 논의. 사람이 쓴다. 실제 운영에서는 GitHub 이슈이고, 이 장은 ops/multi/이슈/의 파일로 대신한다.
  • 실행 기록: 누가 언제 무엇을 했는가와 판정. 판정·병합 스크립트가 ops/multi/logs/ISSUE-07/에 쓴다.

「진실의 원천」이 하나여야 한다. 계획서를 고쳤으면 통합 브랜치에 커밋해야 하고, 작업 공간들은 그 커밋에서 갈라져야 한다. 판정 스크립트가 카드를 작업 공간의 파일이 아니라 통합 브랜치의 커밋(git show feat/issue-07:경로)에서 읽는 까닭이다. 작업 공간에 있는 카드는 에이전트가 고칠 수 있지만, 통합 브랜치의 카드는 사람이 승인한 그대로다.

6-3. 공유하지 않는 것 [선택]

worktree는 파일을 나누지만 모든 것을 나누지는 않는다. 연결된 worktree들은 저장소와 참조(브랜치, 태그)를 공유하고 HEAD와 인덱스만 따로 가진다[G15]. 반대로 저장소에 없는 파일은 따라가지 않는다. .gitignore에 있는 .env는 새 작업 공간에 없다. 키가 없으면 새어 나갈 것도 없다. 무시된 파일을 복사해 주는 .worktreeinclude[C21]는 쓰지 않는다. 작업 공간 터미널에서 기본 작업 공간의 가상 환경을 켜는 까닭(9-4)도 .venv가 따라가지 않기 때문이다.

Claude Code의 「다시 묻지 않기」 승인은 작업 공간 사이에 공유되고, EnterWorktree로 들어간 세션에서는 훅의 ${CLAUDE_PROJECT_DIR}가 처음 시작한 곳을 가리킨다[C21]. worktree 안에서 claude를 새로 시작하면(9-4) 이 문제는 생기지 않는다.

7. 병렬 작업의 충돌 방지

7-1. 작업 분할의 기준

병렬 작업의 충돌은 대부분 계획 단계에서 막을 수 있다. 이 장은 다섯 가지 기준으로 작업을 나눈다.

기준 내용 어기면 생기는 일 지키게 하는 장치
소유 파일 한 파일의 소유자는 작업 하나이다. 작업은 파일 묶음으로 정의한다 같은 파일의 동시 편집, 병합 충돌, 덮어쓰기 계획 검토(사람), prepare.sh의 소유 겹침 거부, judge.sh의 「범위」
계약 우선 작업 사이에 주고받는 것을 계획서에서 먼저 정하고 인수 테스트로 고정한다 서로 다른 가정, 합치면 맞지 않는 동작 인수 테스트
공유 파일은 한 곳에서 여러 작업이 고치고 싶은 파일(명세서, 변경 기록, 설정)은 조정자가 병합 뒤에 한 번 고치는 것이 기본이다. 작업에 맡길 때는 카드에 「- 공유 파일:」로 적고, 병합 때의 충돌을 계획서의 위험에 적는다 같은 줄 근처를 여럿이 고쳐 충돌 카드의 「하지 않는 것」과 「- 공유 파일:」, 보고의 「요청」
작업별 인수 테스트 테스트 파일도 작업마다 나눈다 한 작업만 병합된 상태에서 판정할 수 없다 카드의 - 인수 테스트: 줄
의존은 순서로 앞 작업의 결과를 봐야 하는 작업은 나누지 않거나 뒤로 미룬다 기다리는 작업, 다시 하는 작업 계획서의 「의존」 열, 병합 순서

ISSUE-07에서 api/main.py는 T1만 고친다. 명세서는 아무 작업도 고치지 않고, 계획 단계에서 새 요구를 「미구현」으로 더해 둔 뒤 병합이 끝나면 조정자가 상태를 고친다. T2(웹)는 T1(API)이 아직 없어도 계약만 보고 일한다.

변경 기록(docs/운영/변경기록.md)은 다르게 다루었다. 견본 계획서는 두 작업이 각자 그 파일의 맨 끝에 자기 줄 하나를 더하게 했다. 변경과 그 기록을 같은 커밋에 두면, 작업을 버릴 때 기록도 함께 버려지고 기록 줄도 판정을 거친다. 대가는 충돌이다. 두 줄이 같은 자리(끝)에 들어가므로 뒤에 병합하는 T2에서 부딪힌다. 계획서는 이 충돌을 위험으로 적고 푸는 길을 정해 두었고, 9-6에서 실제로 푼다. 실무에서는 변경 기록을 작업마다 다른 파일(조각 파일)에 쓰고 릴리스 때 모아 이 충돌을 없애기도 한다.

7-2. git worktree

git worktree는 저장소 하나에 작업 공간(체크아웃)을 여럿 두는 기능이다. git init이나 git clone으로 만든 처음 작업 공간을 기본 작업 공간(main worktree), git worktree add로 더한 것을 연결된 작업 공간(linked worktree)이라 한다. 연결된 작업 공간은 저장소를 공유하고, HEAD와 인덱스 같은 작업 공간별 파일만 따로 가진다[G15]. 저장소를 여러 번 복제하는 것과 달리 커밋과 브랜치가 하나의 저장소에 있으므로, 한 작업 공간에서 만든 커밋을 다른 작업 공간에서 바로 병합할 수 있다. 에이전트마다 작업 공간을 하나씩 주면, 에이전트들은 서로의 파일을 건드리지 않고 같은 저장소에 커밋한다. Claude Code 문서가 병렬 세션을 worktree로 나누라고 권하는 까닭이다[C16][C21]. 9절에서 Orca가 만드는 작업 공간도 git worktree이다.

명령 하는 일
git worktree add -b <새 브랜치> <경로> [<시작점>] 새 브랜치를 만들어 그 경로에 꺼낸다
git worktree add <경로> <기존 브랜치> 기존 브랜치를 그 경로에 꺼낸다. 다른 작업 공간이 이미 쓰는 브랜치이면 거부한다
git worktree list [--porcelain] 작업 공간 목록. 기본 작업 공간이 맨 앞이다. --porcelain은 스크립트용 형식
git worktree remove <경로> 깨끗한 작업 공간만 지운다. 바뀐 파일이나 추적하지 않는 파일이 있으면 거부한다
git worktree prune 폴더를 직접 지워 버린 작업 공간의 관리 정보를 정리한다

다음은 교수가 연습용 복제본(~/wt-practice)에서 작업 공간 둘을 만든 화면이다(읽기)[G15]. 복제본에서 하는 것은 거부와 충돌을 일으켜도 실습 저장소의 역사가 바뀌지 않게 하려는 것이다.

7-3. worktree가 막아 주는 것

worktree는 몇 가지 실수를 git 수준에서 막는다. 같은 복제본에서 교수가 일부러 일으킨 거부 셋이다(읽기).

교수 화면

git worktree remove ../wt-a

fatal: '../wt-a' contains modified or untracked files, use --force to delete it
거부 막는 사고
같은 브랜치를 두 작업 공간에서 꺼내지 못한다 두 에이전트가 같은 브랜치에 번갈아 커밋해 서로의 HEAD를 어긋나게 하는 일. git 문서는 다른 작업 공간이 이미 꺼낸 브랜치로는 새 작업 공간을 만들지 않는다고 적는다[G15]

worktree 폴더를 git worktree remove 대신 탐색기나 rm -rf로 지우면, 관리 정보가 .git/worktrees/에 남아 git worktree list에 prunable로 보인다. git worktree prune -v가 그것을 지우며 알린다(-n을 붙이면 지우지 않고 보이기만 한다)[G15]. 다음은 같은 복제본에서 작업 공간 wt-c의 폴더만 지운 뒤의 화면이다(읽기).

7-4. 브랜치 이름과 병합 순서

이 장의 브랜치 이름은 3장 저장소 규약(feat/<요약> 등)을 따르면서, 에이전트가 만든 브랜치를 구별하는 agent/ 접두어를 더한다.

  • 통합 브랜치 feat/issue-07: 사람과 조정자가 커밋한다(계획서, 인수 테스트, 병합 커밋, 명세서 갱신).
  • 작업 브랜치 agent/issue-07-t1, agent/issue-07-t2: 구현 에이전트 하나가 커밋한다.

feat/issue-07/t1처럼 통합 브랜치 아래에 작업 브랜치를 두고 싶어지지만, git에서는 그렇게 할 수 없다. 브랜치 이름은 .git/refs/heads/ 아래의 경로처럼 다루어지므로, feat/issue-07이라는 브랜치가 있으면 feat/issue-07/t1을 만들 수 없다(fatal: cannot lock ref 'refs/heads/feat/issue-07/t1': 'refs/heads/feat/issue-07' exists).

3장의 저장소 규약 문서에 「에이전트의 작업 브랜치는 agent/<이슈>-<작업>(영문 소문자와 숫자, 예: agent/issue-07-t1)」을 한 줄 더한다. 3장의 검사기 ops/rules/check_commits.py --branch는 종류 agent를 이미 허용하므로 feat/issue-07과 agent/issue-07-t1은 통과하고, agent/ISSUE-07-T1처럼 대문자를 쓰면 거부한다. 9-3에서 Orca의 브랜치 이름을 직접 적는 까닭이다.

병합 순서는 다음 원칙으로 정한다.

  1. 의존되는 작업을 먼저 넣는다. ISSUE-07은 웹(T2)이 API(T1)를 부르므로 T1이 먼저다.
  2. 병합할 때마다 그 상태에서 테스트를 돌린다. merge.sh는 병합을 커밋하기 전에(--no-commit) 테스트를 돌리고, 실패하면 병합을 되돌린다.
  3. 병합 커밋을 남긴다(--no-ff). 빨리 감기(fast-forward)로 합치면 어느 커밋이 어느 작업에서 왔는지 그래프에서 사라진다. --no-commit은 빨리 감기에서는 멈출 수 없으므로 --no-ff와 함께 써야 한다[G16].
  4. 작은 작업, 위험이 작은 작업을 먼저 넣는다. 뒤에 넣는 작업이 충돌을 풀 책임을 진다.

따로는 통과하는 두 변경을 합치면 깨지는 경우를 의미 충돌이라 한다. 글자가 겹치지 않으므로 git은 충돌로 알리지 않는다. 예를 들어 T1이 함수 이름을 바꾸고 T2가 옛 이름을 부르면, 두 브랜치는 각자 테스트를 통과하지만 합치면 깨진다. 병합할 때마다 테스트를 돌리는 원칙 2가 이것을 잡는다. 키트의 스크립트 테스트 test_merge_rolls_back_when_combined_tests_fail이 이 경우를 재현한다.

7-5. 충돌이 났을 때

계획을 잘해도 충돌은 생긴다. 공유 파일을 함께 고쳤거나, 통합 브랜치가 그사이 바뀌었을 때다. 다음은 7-2의 복제본에서 두 작업이 같은 변경 기록 파일의 끝에 한 줄씩 더한 뒤 차례로 병합한 화면이다(읽기).

교수 화면 
git merge --no-ff -q -m "chore: practice/a 병합" practice/a
git merge --no-ff -m "chore: practice/b 병합" practice/b
git status --short
git diff --name-only --diff-filter=U
cat CHANGELOG.md
Auto-merging CHANGELOG.md
CONFLICT (content): Merge conflict in CHANGELOG.md
Automatic merge failed; fix conflicts and then commit the result.
UU CHANGELOG.md

<<<<<<<에서 =======까지가 지금 브랜치(이미 첫 작업이 들어간 쪽)의 내용이고, =======에서 >>>>>>>까지가 들여오는 브랜치의 내용이다[G16]. UU는 「양쪽에서 고쳐 합치지 못함」이다. --diff-filter=U는 충돌한 파일만 보이므로 스크립트가 충돌 파일을 알릴 때 쓴다.

충돌을 처리하는 길은 둘이다.

  1. 되돌리고 작업 브랜치에서 푼다. git merge --abort로 병합을 되돌린 뒤, 그 작업의 작업 공간에서 git merge <통합 브랜치>로 충돌을 풀고 커밋하고, 다시 판정을 받는다. 풀이가 작업의 판정을 다시 거친다.
  2. 통합 브랜치에서 바로 푼다. 충돌 파일을 고치고 git add 뒤 git commit 또는 git merge --continue로 끝낸다[G16]. 사람이 직접, 아주 작은 충돌을 풀 때 쓴다.

merge.sh는 첫째 길을 따른다. 충돌하면 병합을 되돌리고 충돌 파일을 알린 뒤 종료 코드 3으로 멈춘다. 둘째 길은 풀이가 판정을 거치지 않으므로 풀이가 테스트를 깨도 알 수 없다. --abort는 병합 전에 커밋하지 않은 변경이 있었으면 그것을 온전히 되살리지 못할 수 있으므로[G16], 스크립트는 병합 전에 작업 공간이 깨끗한지부터 본다. 충돌을 푸는 것은 표시줄을 지우는 일이 아니라 두 변경의 의도를 합치는 판단이다. 변경 기록이라면 두 줄을 모두 남기는 것이 풀이이다(9-6).

7-6. Claude Code의 worktree 기능 [선택]

Claude Code에도 worktree를 만드는 기능이 있다(2026-11-14, 문서와 Claude Code 2.1.296의 claude --help로 확인).

claude --worktree <이름>(-w)은 .claude/worktrees/<이름>/에 worktree-<이름> 브랜치로 작업 공간을 만들고 그 안에서 세션을 시작한다. 시작점은 기본이 원격의 기본 브랜치(보통 main)이고, 설정 worktree.baseRef를 "head"로 하면 지금 HEAD에서 갈라진다. 세션을 끝낼 때 바뀐 것이 없으면 지우고 있으면 남길지 묻는다. 서브에이전트 정의에 isolation: worktree를 두면 서브에이전트마다 임시 worktree를 준다. 기본 작업 공간의 파일 편집과 그곳에서의 git 실행을 막는 격리 검사가 있으나, cp나 리디렉션은 추적하지 않는다[C13][C21].

[최신 자료 자리: Claude Code의 판과 worktree 옵션] 실습 PC의 claude --version과 claude --help에서 -w, --worktree, --bg, agents 명령이 있는지 확인하고, 설정 worktree.baseRef는 https://code.claude.com/docs/en/worktrees에서 확인한다. 2026-11-15 집필 PC의 값: Claude Code 2.1.296, 세 옵션과 명령이 모두 있다.

시작점이 중요하다. 기본값 그대로면 계획서와 인수 테스트가 없는 main에서 시작하므로, 특정 브랜치에서는 git으로 직접 만든다[C21]. 9-3의 Orca도 같다. 「격리 검사」는 실수 방지 장치일 뿐 보안 장치가 아니다. 속은 에이전트를 가두는 일은 11장의 권한, 샌드박스, 훅이 맡는다.

8. 조정의 구현

8-1. 세 가지 조정자

조정자(orchestrator)는 계획을 받아 작업을 나누어 주고, 결과를 모아 판정에 넘기고, 실패하면 돌려보내는 쪽이다. 같은 역할을 사람, Claude Code 세션, 스크립트가 맡을 수 있다.

조정자 작업을 나누어 주는 법 장점 한계 이 장에서
사람(Orca 위에서) 작업 공간마다 claude를 띄우고 카드를 넘긴다 가장 단순하다. 진행을 눈으로 보고 바로 고친다 사람의 시간이 든다. 작업이 늘면 놓친다. 상한과 기록을 사람이 지킨다 8-2, 9절(핵심 실습)
Claude Code 세션 주 세션이 서브에이전트나 팀원에게 위임한다 자연어로 지시한다. 하위 작업을 상황에 맞게 정한다 조정 자체가 모델의 판단이라 매번 다를 수 있다. 토큰이 든다 8-3 [선택]
스크립트 ops/multi/가 정해진 순서로 준비, 실행, 판정을 되풀이한다 같은 입력에 같은 순서. 기록이 남는다. 조정에 토큰이 들지 않는다 계획에 없는 상황에서는 멈추고 사람에게 넘길 뿐이다 8-4(원리, 교수 시연)

세 방식은 서로 배타적이지 않다. 이 장의 핵심 실습은 「계획은 planner, 승인은 사람, 작업 공간과 세션은 Orca 위의 사람, 판정은 스크립트, 병합은 사람」으로 섞었다. 판단이 필요한 곳에 모델을, 되풀이와 기록이 필요한 곳에 스크립트를, 되돌리기 어려운 결정에 사람을 둔 것이다. 바깥 흐름은 정해진 워크플로이고 그 안의 구현 단계만 에이전트이다[E1].

8-2. 사람이 조정자일 때: Orca

사람이 조정할 때도 작업 공간과 인계 문서는 같다. 작업 공간마다 터미널에서 claude --agent implementer로 세션을 띄워 카드를 넘긴다. 이 옵션은 세션 전체를 implementer 정의(도구 제한과 본문)로 실행한다[C13]. 작업 공간 둘과 세션 둘을 터미널 여러 개로 관리하면 어느 창이 어느 작업인지 놓치기 쉽다. 이 장은 그 일을 Orca에 맡긴다.

Orca는 macOS, Windows, 리눅스에서 도는 무료 공개 소프트웨어(MIT)로, 작업마다 git worktree를 만들고 그 안에서 Claude Code 같은 CLI 에이전트를 나란히 실행하는 에이전트 개발 환경(ADE)이다[O3]. 이 과목은 내 PC의 저장소를 Orca에서 로컬로 연다. Orca에는 계정이 필요 없고, Orca의 터미널에서 실행한 Claude Code가 각자의 구독 계정을 쓴다(부록 A-17). Orca를 쓸 때 알아 둘 성질은 넷이다. 모두 Orca 문서의 작업 공간 절에 있다[O1].

  1. 실제 git worktree. Orca의 작업 공간은 모두 git worktree이다. 그래서 7절의 설명이 그대로 맞고, 무엇을 만들었는지는 늘 [터미널]의 git worktree list로 확인한다.
  2. 출발점의 기본값. 출발점(Branch from)의 기본은 대개 origin/main이다. 계획서와 인수 테스트가 있는 통합 브랜치에서 갈라지려면 반드시 바꾼다. 7-6의 --worktree와 같은 함정이다.
  3. 삭제. Orca에서 작업 공간을 지우면 확인을 받은 뒤 worktree 폴더와 브랜치를 함께 지운다.
  4. 자동 정리. 작업 공간의 자동 정리 규칙(Settings → Workspace Cleanup)은 기본으로 꺼져 있고, 켜면 맞는 작업 공간이 몇 초 안에 지워질 수 있다. 이 과목에서는 켜지 않는다.

[최신 자료 자리: Orca의 판과 이 장이 쓰는 화면 이름] 확인할 곳: https://github.com/stablyai/orca/releases, https://orca.dev/docs/model/worktrees. 2026-11-16에 확인한 값: 최신 판 v1.4.261, 작업 공간 만들기의 「Branch from」, 「Advanced」의 「Branch name」, 프로젝트 추가의 「Add a new project」, 「Run on」, 자동 정리 규칙의 기본값 꺼짐. 작업 공간 폴더가 디스크의 어디에 만들어지는지와 Windows에서 작업 공간 터미널이 어느 셸로 열리는지는 문서에 없었다. 수업 전에 설치된 판의 화면과 대조한다.

Orca는 계획 승인을 확인하지 않고, 소유 파일의 겹침을 보지 않으며, 결과를 판정하지 않고, 판정한 커밋과 병합할 커밋을 대조하지 않는다. 그 자리를 이 장은 저장소의 스크립트(8-5)와 사람으로 채운다(9-9).

Claude Code의 에이전트 보기(agent view)를 쓰면 claude --bg "<지시>"로 백그라운드 세션을 띄우고 claude agents로 목록과 상태를 본다[C24]. 2026-11 기준 연구 미리보기이다.

오케스트레이션은 교수 시연으로 본다. Orca의 오케스트레이션은 조정자 에이전트가 작업을 만들고 작업자 에이전트를 각자의 작업 공간에 띄워 완료 보고를 받는 실험 기능이다(Settings → Experimental)[O2]. 조정자와 작업자가 각자 모델을 불러 사용량을 사람이 예측하기 어렵다. 작업을 멈춰 세우는 결정 관문(decision gate)도 조정자가 답하므로 사람의 승인이 아니다(10-3). 문서도 작업자 결과의 병합 방법은 적지 않는다[O2].

[최신 자료 자리: Orca 오케스트레이션의 상태] 확인할 곳: https://orca.dev/docs/cli/orchestration, 설치된 판의 orca skills get orchestration --full. 2026-11-16에 확인한 값: 실험 기능이며 Settings → Experimental에서 켠다. 같은 날 문서에는 실험 기능 패널과 그 스위치를 잠시 쓸 수 없다는 안내가 있었다.

8-3. Claude Code 세션이 조정자일 때 [선택]

주 세션이 조정하면 하위 작업은 서브에이전트로 위임된다. 예를 들어 「planner 에이전트로 계획서와 카드를 쓰고 승인을 기다려라」, 승인 뒤에는 「implementer 에이전트 둘에게 T1, T2 카드를 맡겨 각자의 worktree에서 병렬로 실행하라」고 지시한다. 서브에이전트를 worktree에서 실행하려면 정의에 isolation: worktree를 두고, 프로젝트 설정에 "worktree": {"baseRef": "head"}를 두어 통합 브랜치에서 갈라지게 해야 한다(7-6)[C21]. 에이전트 팀은 주도 세션이 팀원을 띄우고 공유 작업 목록과 메시지로 맞추는 실험 기능(CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1)이며, 팀원을 worktree로 나누지 않으므로 파일 분할이 전적으로 계획에 달려 있다[C22][C23]. 팀원 사이의 메시지는 사람의 승인을 대신하지 못한다[C23]. 세션 조정자는 집필할 때 실행해 확인하지 못하였으므로 교수 시연으로 본다.

8-4. 스크립트가 조정자일 때: ops/multi [읽기]

같은 흐름을 스크립트가 조정할 수도 있다. 사람이 작업 공간을 만들고 세션에 카드를 넣고 상한을 세던 일을 ops/multi/의 스크립트가 한다. 실제 모델을 무인으로 되풀이해 부르므로 교수 시연으로 보고(실행 상한), 학습자는 원리를 읽는다. 핵심 실습에서는 이 가운데 judge.sh, merge.sh, status.sh만 쓴다.

스크립트 하는 일 실패하면
prepare.sh 이슈 작업… 시작 조건(깨끗함, 통합 브랜치, 승인, 카드, 소유 겹침)을 확인하고 작업마다 worktree와 브랜치를 만든다. 공유 파일은 「공유」 줄로 알린다 아무것도 만들지 않고 종료 코드 2
dispatch.sh 이슈 작업… 작업 공간마다 AGENT_CMD를 동시에 실행하고 모두 끝나기를 기다린다 에이전트가 0이 아닌 코드로 끝나면 종료 코드 1
judge.sh 이슈 작업 커밋, 범위, 동결, 보고, 테스트, 검토의 여섯 항목을 판정하고 판정 파일을 쓴다 「거부」, 종료 코드 1
run_issue.sh 이슈 작업… 준비 → 실행 → 판정을 거부된 작업만 시도 상한까지 되풀이한다 상한에 닿으면 사람에게 넘기고 종료 코드 1
merge.sh 이슈 작업… 판정과 커밋을 대조한 뒤 적은 순서로 병합한다. 병합마다 테스트 충돌 3, 테스트 실패 4. 둘 다 그 병합을 되돌린다
status.sh 이슈 작업 공간, 앞섬과 뒤짐, 판정, 병합 여부를 표로 보인다
cleanup.sh 이슈 작업… 병합된 작업의 worktree와 브랜치를 지운다 병합되지 않았거나 변경이 남은 작업은 건너뛴다

병렬 실행의 핵심은 dispatch.sh의 몇 줄이다.

교수 화면 
grep -n '&$\|wait "\|PROMPT+=' ops/multi/dispatch.sh
36:  PROMPT+="카드의 소유 파일과 공유 파일 밖의 파일은 고치지 않는다. 끝나면 결과 보고를 $REPORT에 쓰고, "

41:    PROMPT+=$'\n\n직전 판정의 거부 사유를 먼저 고친다.\n'"$(sed -n '/^| 항목/,/^$/p' "$VERDICT")"
44:  ( cd "$DIR" && "${CMD[@]}" "$PROMPT" ) > "$OUT" 2>&1 &

44행의 끝에 붙은 &가 에이전트를 백그라운드로 띄운다. 괄호 안의 cd는 그 하위 셸에서만 작업 공간으로 옮겨 가므로, 스크립트 자신은 기본 작업 공간에 머문다. 53행의 wait는 그 작업의 프로세스가 끝나기를 기다리고 종료 코드를 받는다. 모든 작업을 먼저 띄우고 나서 차례로 기다리므로, 실행은 동시에 일어난다. 41행은 재시도일 때 직전 판정 파일의 표를 지시문에 붙인다. 9-5에서 사람이 판정표를 세션에 붙여 넣는 일을 스크립트가 하는 것이다.

AGENT_CMD만 바꾸면 같은 스크립트가 가짜 에이전트로도, 실제 Claude Code로도 돈다. AGENT_CMD="python ops/multi/fake/impl_agent.py"는 가짜 구현 에이전트로, 정답 변경을 적용하고 결과 보고를 쓰고 커밋하며 FAKE_SCENARIO로 실패를 흉내 낸다. AGENT_CMD="bash ops/multi/claude_impl.sh"는 실제 Claude Code를 헤드리스로 실행하는 감싸개이다.

교수 화면 
sed -n '/^PROMPT=/,$p' ops/multi/claude_impl.sh
PROMPT="${*: -1}"
exec claude -p "$PROMPT" \
  --agent implementer \
  --permission-mode acceptEdits \
  --permission-prompts none \
  --allowedTools "Bash(python -m pytest *),Bash(pytest *),Bash(git add *),Bash(git commit *),Bash(git status *),Bash(git diff *)" \
  --disallowedTools "Bash(git push *),Bash(git merge *),Bash(git rebase *),Bash(git reset *),Bash(git switch *),Bash(git checkout *)" \
  --max-budget-usd "${AGENT_BUDGET_USD:-0.50}" \
  --output-format json

감싸개는 지시문을 -p 바로 뒤, 옵션보다 앞에 둔다. 여러 값을 받는 옵션(--allowedTools) 뒤에 두면 지시문이 그 옵션의 값으로 읽힐 수 있다. --agent implementer는 세션을 implementer 정의로 실행하고, --permission-mode acceptEdits는 파일 편집만 묻지 않고 허용하며, --permission-prompts none은 물을 사람이 없으므로 물어야 할 요청을 거부하게 한다. --allowedTools는 테스트·스테이징·커밋·상태 보기만 허용하고 (python은 가상 환경을 켠 셸의 것이다), --disallowedTools는 병합·푸시·되돌리기·브랜치 이동을 막으며, --max-budget-usd는 시도 한 번의 비용 상한(8장), --output-format json은 total_cost_usd 같은 실행 정보를 남긴다[C14]. 9-4에서 사람이 세션의 권한 질문에 답하던 일을 이 옵션들이 대신한다.

[최신 자료 자리: 헤드리스 실행의 옵션] 감싸개가 쓰는 옵션의 이름과 선택지는 판마다 바뀔 수 있다. 시연 전에 claude --help와 https://code.claude.com/docs/en/headless로 확인한다. 2026-11-15 집필 PC(2.1.296)의 값: --permission-prompts의 선택지는 host와 none, --max-budget-usd와 --output-format은 --print(-p)에서만 쓰이며 --output-format의 선택지는 text, json, stream-json이다.

허용 규칙을 AGENT_CMD 문자열이 아니라 감싸개 파일에 둔 까닭은 규칙에 빈칸(Bash(python -m pytest *))이 들어가기 때문이다. 스크립트가 AGENT_CMD를 빈칸에서 잘라 명령으로 만들 때 규칙이 쪼개진다. 교수 시연에서 이 스크립트 조정자로 ISSUE-07을 돌리면, 9-6에서 학습자가 만나는 것과 같은 충돌에서 merge.sh가 멈춘다. 스크립트도 충돌을 풀지는 못한다. 되돌리고 사람에게 넘길 뿐이다.

통합...작업의 점 셋은 「두 브랜치가 갈라진 지점부터 작업 브랜치까지」의 차이이다. 점 둘(통합..작업)로 비교하면, 그사이 통합 브랜치에 다른 작업이 병합되었을 때 그 변경까지 이 작업의 변경처럼 보인다. 작업 하나의 범위를 재려면 점 셋을 써야 한다.

검토의 기본 명령은 규칙 검토기 rule_review.py이다. 기계로 확실히 가릴 수 있는 팀 규칙 넷(웹의 innerHTML, api/llm.py 밖의 anthropic, 키처럼 보이는 문자열, 기록에 요청 본문)만 본다. 검토기의 번호 W1~W4는 검토자의 검토 규칙 RV3, RV2, RV1, RV7에 차례로 대응한다. LLM 검토자를 쓰려면 REVIEW_CMD="bash ops/multi/claude_review.sh"로 바꾼다(교수 시연). 규칙 검토기는 싸고 늘 같은 결과를 내므로 먼저 걸러 내고, LLM 검토자는 의도를 읽어야 하는 문제를 본다.

판정 파일에는 판정한 커밋의 해시가 남는다. merge.sh는 병합하기 전에 이 해시와 작업 브랜치의 끝 커밋을 대조해, 판정 뒤에 커밋이 더해졌으면 병합을 거부한다. 「통과 판정을 받은 뒤 몰래 고친 변경」이 병합되는 것을 막는 장치이며, 9-6에서 충돌을 푼 커밋을 다시 판정해야 하는 까닭이기도 하다.

judge.sh는 작업 공간을 작업 브랜치 이름(agent/issue-07-t1)으로 git worktree list에서 찾는다. 그래서 Orca가 작업 공간을 어디에 어떤 폴더 이름으로 두었든 그대로 판정한다.

9-10. 핵심 실습 복기

이슈 하나를 계획에서 main까지 옮겼다. 한 일은 세 가지로 정리된다.

  1. 나누기 전에 약속을 정하였다. 계획서가 「정하지 않은 것」을 닫고, 계약을 인수 테스트로 고정하고, 소유 파일이 겹치지 않게 나누었다. 두 구현은 서로를 보지 않고도 합쳐졌다. 공유 파일 하나는 충돌을 알고 받아들였고, 그 충돌을 계획서가 정한 길로 풀었다.
  2. 에이전트의 말이 아니라 판정이 진행을 정하였다. 결과 보고의 「완료」가 아니라 판정 파일이 통과와 거부를 정했고, 판정은 커밋 번호와 함께 남았다. 충돌을 푼 커밋도 판정을 다시 거쳤다.
  3. 되돌리기 어려운 결정은 사람이 하였다. 계획 승인 커밋, 판정표를 넘기는 재시도와 상한, merge.sh 실행, 충돌의 풀이가 사람의 몫이었다. Orca가 대신한 것은 작업 공간과 세션을 나란히 놓는 일이었다.
   남은 것                              답하는 질문
   계획서의 「- 승인:」 커밋             누가 언제 이 분할을 승인했는가
   판정_T*_<커밋>.md                    무엇을 근거로 거부하고 통과시켰는가
   Merge branch 'feat/issue-07' into …  충돌을 어디서 풀었는가
   병합 커밋 둘(T1 → T2)                어떤 순서로, 매번 테스트를 거쳐 합쳤는가

되짚어 볼 것 하나. 계획서 4절에서 api/main.py를 T2에도 소유하게 했다면 무엇이 달라졌을지 설계서 9절 아래에 한 줄로 적는다. 스크립트 조정자였다면 어디서 멈추었고, Orca 방식에서는 어디서 처음 드러났을지를 함께 적는다.

10-3. 사람의 승인 지점

이 장의 시스템에서 사람이 반드시 관여하는 곳은 넷이다. 1장의 역할 정의서에서 「사람 승인 지점」으로 적었던 것을 실제 장치로 만든 것이다.

승인 지점 장치 승인 없이 진행하면
계획 승인 계획서의 - 승인: 줄과 승인 커밋. 스크립트 조정자는 없으면 prepare.sh가 멈추고, Orca 방식에서는 사람이 확인한다 잘못 나눈 작업이 병렬로 퍼진다. 고치는 비용이 작업 수만큼 커진다
인수 테스트 커밋 사람이 테스트를 읽고 커밋한다(tester 정의는 커밋하지 않는다) 아무것도 재지 않는 테스트가 완료 조건이 된다
병합 사람이 merge.sh를 실행한다. 충돌을 푸는 것도 사람이다. 스크립트 조정자(run_issue.sh)와 Orca는 병합하지 않는다 판정을 통과했지만 의도와 다른 변경이 들어간다
main 반영과 배포 사람이 main에 병합하거나 풀 리퀘스트를 승인한다(13장)

승인 지점을 어디에 둘지는 「되돌리기 어려운가」와 「영향이 퍼지는가」로 정한다. 작업 공간 안의 커밋은 언제든 버릴 수 있으므로 에이전트에게 맡기고, 다른 작업의 출발점이 되는 통합 브랜치로의 병합은 사람이 한다. Claude Code의 에이전트 보기도 백그라운드 세션에게 main에 푸시하거나 병합하지 말고 사람이 검토해 병합하라고 안내한다[C24].

승인은 사람이 직접 해야 한다. 에이전트 팀 문서는 팀원이 사람 대신 권한 요청을 승인할 수 없다고 적는다[C23]. 이 장의 스크립트도 승인 줄과 카드를 통합 브랜치의 커밋에서 읽으므로, 구현 에이전트가 자기 작업 공간의 계획서에 승인 줄을 써 넣어도 효과가 없다. Orca의 결정 관문(8-2)도 조정자가 답하므로 사람의 승인을 대신하지 않는다.

정리

  • 멀티 에이전트는 컨텍스트, 전문화, 병렬성의 한계를 푸는 대신 토큰, 조정, 충돌의 비용을 치르고, 병렬의 수는 PC의 코어와 메모리에도 묶인다. 일이 서로 기다리지 않게 나뉘지 않거나 나눈 이득이 비용보다 작으면 나누지 않는다. 병렬은 읽기에 강하고, 쓰기는 worktree로 격리한다.
  • 구조는 조정자-작업자, 파이프라인, 생성자-검토자, 경쟁 후 선택이며 운영 시스템은 이것들을 섞는다.
  • 역할은 서브에이전트 정의 파일로 옮기고, 도구는 tools로, 역할별 경로 제한은 지시문과 판정 검사의 두 겹으로 둔다.
  • 인계는 계획서, 작업 카드, 결과 보고로 한다. 계약을 인수 테스트로 고정하면 작업들이 서로를 기다리지 않는다.
  • 충돌은 계획에서 막는다. 소유 파일 단위로 나누고, 공유 파일은 조정자가 한 번 고치거나 충돌을 위험으로 적어 둔다. 충돌이 나면 작업 쪽에서 풀고 다시 판정한다.
  • 판단은 모델에, 되풀이와 기록은 스크립트에, 되돌리기 어려운 결정은 사람에게 둔다. Orca가 작업 공간과 세션을 맡아도 카드, 판정, 사람의 병합은 저장소에 남는다.
  • 실패는 판정에서 잡고 상한에서 사람에게 넘긴다. 다 쓴 worktree는 지우기 전에 git status를 본다. worktree는 보안 격리가 아니다.

개념 점검

  1. ISSUE-07에서 명세서(docs/요구사항명세서.md)는 어느 작업의 소유 파일로도 넣지 않았고, 변경 기록(docs/운영/변경기록.md)은 두 작업의 공유 파일로 넣었다. 두 공유 파일을 다르게 다룬 까닭과 각 방식의 대가는 무엇인가?
  2. api/main.py의 엔드포인트 다섯 개를 각각 고치는 일을 에이전트 다섯에게 병렬로 맡기면 안 되는 까닭을 2절의 다섯 질문 가운데 둘을 들어 설명하라.
  3. 서브에이전트 정의의 프런트매터에 allowed-tools: Read, Grep이라고 쓰면 어떤 일이 일어나는가? 그 실수를 실행 전에 어떻게 찾는가?
  4. 9-6에서 T2의 충돌을 풀어 커밋한 뒤 바로 merge.sh를 실행하면 거부된다. 거부의 까닭과, 이 거부가 막는 사고는 무엇인가?
  5. 같은 ISSUE-07을 스크립트 조정자(run_issue.sh)로 돌릴 때와 Orca로 돌릴 때, 사람이 맡는 일은 어떻게 달라지는가? 두 방식에서 똑같이 남는 것 둘을 들어라.
