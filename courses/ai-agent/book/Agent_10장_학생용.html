멀티 에이전트 운영 시스템의 설계: 역할 분담과 병렬 작업

2027학년도 「AI에이전트 기획 및 개발」의 준비 중인 교재입니다. 편집 상태를 검토하기 위해 미리 공개한 것으로, 수업 전에 내용과 순서가 바뀔 수 있습니다.

학사 12주차 · 교재 10 · 4부 멀티 에이전트 운영

150분 기준 축약(2026-11-19). 150분 수업 기준으로 줄였다(학생용 본문 63,954자 → 35,685자). 출력은 2026-11-17에 Windows 11의 Git Bash에서 얻었고, 실제 모델이 만들 출력은 「예시」로 밝혔다.

1장에서 「jobprep 운영 에이전트 시스템」의 역할을 역할 정의서에 적었고, 2~9장에서 그 부품(테스트, 규약, 검토 서브에이전트, 하네스, 루프)을 만들었다. 이 장은 과목의 주축으로, 역할을 실제로 움직이는 역할 에이전트로 만들고, 그 에이전트들이 이슈 하나를 나누어 병렬로 구현한 뒤 판정을 거쳐 사람의 승인으로 병합되는 운영 시스템을 설계한다. 여러 에이전트는 토큰을 몇 배로 쓰고 같은 파일을 동시에 고치면 서로의 일을 덮어쓰므로, 이 장의 절반은 「언제 나누는가」와 「충돌하지 않게 나누는 법」이다.

핵심 실습은 이슈 ISSUE-07(관심 공고 내보내기 기능과 그 API)을 계획서와 작업 카드로 나누고, 내 PC의 Orca에서 작업마다 git worktree를 만들어 자기 계정의 Claude Code 세션 둘이 나란히 구현하게 한 뒤, 판정하고 사람이 정한 순서로 병합하는 한 바퀴이다. 두 작업이 같은 변경 기록 파일의 끝에 한 줄씩 더하므로 뒤의 병합에서 충돌이 나며, 그것을 뒤 작업의 작업 공간에서 풀고 다시 판정받아 병합하는 것이 이 장에서 해결하는 문제이다. 이 방법은 프로젝트실습Ⅱ의 팀 저장소에 그대로 옮겨 쓴다.

학습 목표

  • 작업의 성질을 보고 단일 에이전트와 멀티 에이전트 가운데 무엇을 쓸지 판단하고, 그 근거를 비용과 실패 유형으로 설명할 수 있다.
    • 예시: 요약 프롬프트 수정은 파일 하나에 몰린 순차 작업이므로 하나로, 내보내기 API와 웹 단추는 계약을 정하면 파일이 겹치지 않으므로 둘로 나눈다.
  • 역할 정의서의 역할을 서브에이전트 정의 파일로 옮기고, 역할마다 도구와 완료 조건을 정할 수 있다.
    • 예시: R2 구현을 implementer.md로 옮겨 도구를 한정하고, 「tests/를 고치지 않는다」를 지시문과 판정 검사 양쪽에 둔다.
  • 계획서, 작업 카드, 결과 보고로 인계를 설계하고, 소유 파일 단위로 나누어 충돌을 계획 단계에서 막을 수 있다.
    • 예시: ISSUE-07을 T1(api/)과 T2(web/)로 나누고, 명세서는 조정자가 병합 뒤에 한 번 고친다.
  • Orca의 작업 공간과 에이전트별 브랜치로 병렬 작업을 돌리고, 판정하며, 병합 충돌을 작업 쪽에서 풀어 사람이 정한 순서로 병합할 수 있다.
    • 예시: judge.sh, merge.sh ISSUE-07 T1 T2로 판정·병합하고, T2가 충돌하면 T2의 작업 공간에서 풀고 다시 판정한다.

0. 시작하기

실습 환경은 부록 A(A-4, A-5, A-7, A-9)를 따르고 PYTHONUTF8=1(A-4-4)을 등록해 둔다. Orca의 설치와 PC 자원의 확인(A-17-1, A-17-2)은 10장 전 주에 마친다. 터미널은 직접 치는 [터미널]과 Orca가 작업 공간마다 여는 [Orca 작업 공간 터미널]을 쓴다.

이 장의 실행 상한. 실제 모델은 9절의 Orca 작업 공간 둘에서 여는 Claude Code 대화형 세션 둘에서만 부르며, 작업마다 시도는 2회까지이다. 계획서와 인수 테스트는 가짜 에이전트가 쓴다. 스크립트 조정자의 무인 실행(8-4)과 Orca의 오케스트레이션은 교수 시연이다. jobprep은 모의 모드(LLM_FAKE=1)이므로 API 키가 필요 없다.

1. 단일 에이전트의 한계와 멀티 에이전트의 비용

1-1. 에이전트 하나가 부딪히는 세 한계

한계 에이전트 하나에서 생기는 일 멀티 에이전트의 대응
컨텍스트 읽은 파일과 출력이 쌓여 앞의 결정이 잘린다 작업마다 새 컨텍스트, 결과는 요약이나 파일로 돌려준다
전문화 같은 가정으로 쓰고 검토한다 역할마다 지시문, 도구, 권한을 따로 둔다[C13]
병렬성 독립된 일도 차례로 한다 독립된 작업을 동시에 실행한다

Anthropic의 연구 시스템에서는 대화가 20만 토큰을 넘으면 앞부분이 잘려 계획을 따로 저장해야 했고, 하위 에이전트 3~5개를 동시에 띄워 조사 시간을 최대 90% 줄였다[E2].

1-2. 멀티 에이전트의 세 비용

비용 근거 이 장의 대책
토큰 채팅 대비 에이전트 약 4배, 멀티 에이전트 약 15배[E2]. 에이전트 팀은 계획 모드에서 약 7배[C19] 나눌 가치가 있을 때만(2절)
조정 모호한 위임은 중복 작업을 낳는다. 동기식 대기는 병목이 된다[E2] 카드에 목표, 계약, 경계, 완료 조건(5절)
충돌 같은 파일의 동시 편집은 덮어쓰기를 낳는다[C23] 소유 파일 분할, worktree, 병합 순서(7절)

[최신 자료 자리: 에이전트 팀의 토큰 배수] 에이전트 팀이 계획 모드에서 표준 세션의 약 7배를 쓴다는 값은 Claude Code 문서 「Manage costs effectively」(https://code.claude.com/docs/en/costs)의 2026-11-14 서술이다. 판이 바뀌면 배수가 달라질 수 있으므로 수업 전에 다시 확인한다. 연구 시스템의 약 4배·15배[E2]는 2025-06-13에 공개된 글의 값이므로 바뀌지 않는다.

병렬의 수는 PC 자원에도 묶인다. 테스트를 돌리는 에이전트는 코어 하나 안팎을 쓰므로 병렬 수가 코어 수를 넘으면 이득이 사라진다. 실행 상한(세션 둘, 시도 2)은 계정의 사용량과 PC의 자원(부록 A-17-2)을 함께 본 값이다.

2. 멀티 에이전트의 판단 기준

2-1. 가장 단순한 해법부터

Anthropic은 가장 단순한 해법을 먼저 찾고, 복잡성은 결과를 분명히 낫게 만들 때만 더하라고 권한다[E1]. 멀티 에이전트는 너비 우선 조사에 맞고, 같은 맥락을 공유하거나 의존이 많은 일, 같은 파일의 편집에는 맞지 않는다[E2][C23].

2-2. 다섯 질문

설계서 양식의 1절이 이 표이다.

질문 「예」이면 「아니오」이면
① 작업이 서로 기다리지 않는 부분으로 나뉘는가 병렬로 나눈다 차례로 돌 뿐이다
② 한 에이전트의 컨텍스트에 다 들어가지 않는가 하위 에이전트가 요약한다 나눌 까닭이 없다
③ 역할마다 다른 권한과 도구가 필요한가 역할 에이전트로 나눈다 경계가 생기지 않는다
④ 병렬로 줄어드는 시간이 늘어나는 토큰과 조정보다 값진가 나눈다 에이전트 하나
⑤ 나눈 결과를 기계로 판정할 수 있는가 사람은 병합만 본다 사람이 모두 읽는다

①과 ④가 「아니오」이면 다른 답과 상관없이 나누지 않는다. ③만 「예」이면 역할 분리(생성자-검토자)로 충분하다.

함께 보는 기준: 병렬은 읽기(조사·검토)에 강하고, 쓰기는 worktree로 격리해야 병렬이 된다. 코딩 과제에는 진짜로 병렬화할 수 있는 부분이 조사보다 적다[E2]. 이 장은 검토에는 작업 공간을 따로 만들지 않고, 구현에는 작업마다 worktree를 준다[C21].

3. 구조의 유형

3-1. 네 가지 구조

Anthropic은 워크플로 패턴으로 프롬프트 사슬, 라우팅, 병렬화(구획 나누기와 투표), 조정자-작업자, 평가자-최적화자를 든다[E1]. 이 장은 그 가운데 넷을 쓴다.

구조(원래 이름[E1]) 흐름과 jobprep의 예
조정자-작업자(orchestrator-workers) 조정자가 입력을 보고 일을 나누어 맡긴다. 이슈를 구현 에이전트 둘에게 나눈다
파이프라인(prompt chaining) 앞 단계의 출력이 다음 입력이 된다. 계획 → 테스트 → 구현 → 판정 → 병합
생성자-검토자(evaluator-optimizer) 만들고 평가해 돌려보낸다. 판정 거부 → 재작업
경쟁 후 선택(parallelization: voting) 같은 일을 여럿이 하고 하나를 고른다. 원인 모를 장애의 가설별 조사

조정자-작업자와 사슬의 차이는 「누가 단계를 정하는가」이다. 사슬은 단계가 코드에 고정되고, 조정자-작업자는 조정자가 하위 작업을 정한다[E1].

3-2. 경쟁 후 선택의 비용 [선택]

같은 일을 N번 하므로 비용도 N배이고, 둘 다 통과하면 무엇으로 고를지 미리 정해야 한다. 정하지 않으면 결국 사람이 둘을 다 읽는다[C23].

3-3. Claude Code의 병렬 실행 방법 [선택]

Claude Code는 서브에이전트, 에이전트 보기(사람이 띄우는 백그라운드 세션), 에이전트 팀(작업 공간을 나누지 않는 실험 기능), 동적 워크플로와 프로젝트를 병렬 실행 방법으로 든다[C22].

[최신 자료 자리: 병렬 실행 방법의 이름과 상태] 각 방법의 상태와 에이전트 팀을 켜는 환경 변수를 확인할 곳은 Claude Code 문서 「Run agents in parallel」(https://code.claude.com/docs/en/agents)과 「Orchestrate teams of Claude Code sessions」(https://code.claude.com/docs/en/agent-teams)이다. 2026-11-15에 확인한 값: 에이전트 보기는 연구 미리보기(Research preview), 에이전트 팀은 실험 기능이며 기본으로 꺼져 있고 CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1로 켠다, 프로젝트는 Pro·Max·Ultra 요금제의 공개 베타이다. 8-2와 8-3의 서술도 이 값에 따른다.

4-2. 서브에이전트 정의 파일의 형식

역할 에이전트는 YAML 프런트매터가 붙은 마크다운 파일로 만들며 본문이 그 에이전트의 시스템 프롬프트가 된다. 서브에이전트는 기본 시스템 프롬프트를 받지 않으므로[C13] 역할 정의서의 내용을 본문에 빠짐없이 옮긴다.

필드 뜻
name, description 고유한 이름, 언제 위임할지(필수)
tools 허용 도구 목록. 없으면 모든 도구를 물려받는다
disallowedTools 거부 도구 목록

[최신 자료 자리: 서브에이전트 정의의 필드와 모델 별칭] 필드 목록과 model에 쓸 수 있는 별칭을 확인할 곳은 https://code.claude.com/docs/en/sub-agents이다. 필드는 2026-11-14에 문서로, 별칭은 2026-11-15에 이 PC의 Claude Code 2.1.296 claude --help(--model 설명이 fable, opus, sonnet을 예로 든다)로 확인하였다. 새 모델이 나오면 별칭이 가리키는 모델이 바뀐다.

## 판정 형식 (10장)

멀티 에이전트 판정(`ops/multi/judge.sh`)에서 불릴 때는 `.review/target.diff` 대신 표준 입력으로 통합 브랜치와

- 첫 줄에 `판정: 통과` 또는 `판정: 거부`만 쓴다. 심각도 「높음」인 위반이 하나라도 있으면 `판정: 거부`이다.

7-2. git worktree

git worktree는 저장소 하나에 작업 공간(체크아웃)을 여럿 두는 기능이다. git clone으로 만든 기본 작업 공간과 git worktree add로 더한 연결된 작업 공간은 저장소를 공유하고 HEAD와 인덱스만 따로 가진다[G15]. 복제와 달리 한 작업 공간의 커밋을 다른 작업 공간에서 바로 병합할 수 있으므로, 에이전트마다 작업 공간을 주면 서로의 파일을 건드리지 않고 같은 저장소에 커밋한다[C16][C21]. 명령은 부록 B-2-5에 있다. 연결된 작업 공간의 .git은 기본 작업 공간의 .git/worktrees/<이름>을 가리키는 파일이고, git branch의 +는 다른 작업 공간이 꺼내 쓰는 브랜치이다.

7-3. worktree가 막아 주는 것

git은 다음 셋을 거부한다[G15].

거부 git의 메시지 막는 사고
같은 브랜치를 두 작업 공간에 꺼낸다 is already used by worktree 두 에이전트의 번갈아 커밋
작업 공간이 쓰는 브랜치를 지운다 cannot delete branch 일하는 중인 브랜치의 소실
바뀐 파일이 있는 작업 공간을 지운다 contains modified or untracked files 커밋하지 않은 일의 소실

이 장의 cleanup.sh는 --force를 쓰지 않는다. 반면 Orca는 git이 지우지 못하면 강제 삭제를 권하므로[O1], 누르기 전에 그 작업 공간의 git status를 보는 것이 사람의 몫이다. 폴더를 rm -rf로 지우면 관리 정보가 남아 prunable로 보이며 git worktree prune -v가 정리한다.

7-4. 브랜치 이름과 병합 순서

통합 브랜치 feat/issue-07에는 사람과 조정자가, 작업 브랜치 agent/issue-07-t1, -t2에는 구현 에이전트 하나가 커밋한다. feat/issue-07/t1처럼 통합 브랜치 아래에는 둘 수 없다(cannot lock ref). 3장의 저장소 규약에 「에이전트의 작업 브랜치는 agent/<이슈>-<작업>(영문 소문자와 숫자)」을 더한다.

병합 순서의 원칙은 넷이다. ① 의존되는 작업을 먼저 넣는다(T2가 T1의 API를 부르므로 T1 먼저). ② 병합마다 테스트한다. merge.sh는 커밋 전에(--no-commit) 테스트하고 실패하면 되돌린다. ③ 병합 커밋을 남긴다(--no-ff). 빨리 감기로 합치면 어느 커밋이 어느 작업에서 왔는지 사라진다[G16]. ④ 뒤에 넣는 작업이 충돌을 풀 책임을 진다. 따로는 통과하는 두 변경을 합치면 깨지는 의미 충돌(T1이 함수 이름을 바꾸고 T2가 옛 이름을 부르는 경우)은 git이 알리지 못하므로 원칙 ②가 잡는다.

7-5. 충돌이 났을 때

충돌한 파일에서 <<<<<<< HEAD부터 =======까지는 지금 브랜치, 그 아래 >>>>>>>까지는 들여오는 브랜치의 내용이다[G16]. git diff --name-only --diff-filter=U는 충돌한 파일만 보인다. 처리하는 길은 둘이다. 첫째, git merge --abort로 되돌린 뒤 그 작업 공간에서 git merge <통합 브랜치>로 풀고 다시 판정을 받는다. 둘째, 통합 브랜치에서 바로 고치고 커밋한다. 둘째 길은 풀이가 판정을 거치지 않는다. merge.sh는 첫째 길을 따라 충돌하면 병합을 되돌리고 종료 코드 3으로 멈춘다. 충돌을 푸는 것은 표시줄을 지우는 일이 아니라 두 변경의 의도를 합치는 판단이다.

7-6. Claude Code의 worktree 기능 [선택]

claude --worktree <이름>(-w)은 .claude/worktrees/<이름>/에 작업 공간을 만들고 세션을 시작한다. 시작점은 원격의 기본 브랜치이며, 설정 worktree.baseRef를 "head"로 하면 지금 HEAD이다[C21].

[최신 자료 자리: Claude Code의 판과 worktree 옵션] 실습 PC의 claude --version과 claude --help에서 -w, --worktree, --bg, agents 명령이 있는지 확인하고, 설정 worktree.baseRef는 https://code.claude.com/docs/en/worktrees에서 확인한다. 2026-11-15 집필 PC의 값: Claude Code 2.1.296, 세 옵션과 명령이 모두 있다.

기본값이면 계획서가 없는 main에서 시작한다. 9-3의 Orca도 같은 함정이 있다. Claude Code의 격리 검사는 cp나 리디렉션을 추적하지 않는 실수 방지 장치일 뿐이다[C21].

8. 조정의 구현

8-1. 세 가지 조정자

조정자 장점 한계

핵심 실습은 작업 공간과 세션은 Orca 위의 사람, 판정은 스크립트, 승인과 병합은 사람이 맡도록 섞었다[E1].

8-2. 사람이 조정자일 때: Orca

사람이 조정할 때는 작업 공간마다 claude --agent implementer(세션 전체를 implementer 정의로 실행[C13])로 세션을 띄워 카드를 넘긴다. 작업 공간과 세션을 터미널 여럿으로 관리하면 놓치기 쉬우므로 이 장은 그 일을 Orca에 맡긴다.

Orca는 macOS, Windows, 리눅스에서 도는 무료 공개 소프트웨어(MIT)로, 작업마다 git worktree를 만들고 그 안에서 Claude Code 같은 CLI 에이전트를 나란히 실행하는 에이전트 개발 환경(ADE)이다[O3]. 계정이 필요 없고, Orca의 터미널에서 실행한 Claude Code가 각자의 구독 계정을 쓴다(부록 A-17). 알아 둘 성질은 넷이다[O1].

  1. 실제 git worktree. Orca의 작업 공간은 모두 git worktree이다. 무엇을 만들었는지는 늘 [터미널]의 git worktree list로 확인한다.
  2. 출발점의 기본값. 출발점(Branch from)의 기본은 대개 origin/main이다. 계획서와 인수 테스트가 있는 통합 브랜치에서 갈라지려면 반드시 바꾼다.
  3. 삭제. Orca에서 작업 공간을 지우면 확인을 받은 뒤 worktree 폴더와 브랜치를 함께 지운다.
  4. 자동 정리. 자동 정리 규칙(Settings → Workspace Cleanup)은 기본으로 꺼져 있고, 켜면 맞는 작업 공간이 몇 초 안에 지워질 수 있다. 이 과목에서는 켜지 않는다.

[최신 자료 자리: Orca의 판과 이 장이 쓰는 화면 이름] 확인할 곳: https://github.com/stablyai/orca/releases, https://orca.dev/docs/model/worktrees. 2026-11-16에 확인한 값: 최신 판 v1.4.261, 작업 공간 만들기의 「Branch from」, 「Advanced」의 「Branch name」, 프로젝트 추가의 「Add a new project」, 「Run on」, 자동 정리 규칙의 기본값 꺼짐. 작업 공간 폴더가 디스크의 어디에 만들어지는지와 Windows에서 작업 공간 터미널이 어느 셸로 열리는지는 문서에 없었다. 수업 전에 설치된 판의 화면과 대조한다.

Orca는 계획 승인, 소유 파일의 겹침, 결과의 판정, 판정한 커밋과 병합할 커밋의 대조를 하지 않는다. 그 자리를 저장소의 스크립트(8-5)와 사람이 채운다. Claude Code의 에이전트 보기(claude --bg, claude agents)도 사람 조정자의 도구이다(연구 미리보기)[C24].

오케스트레이션은 교수 시연으로 본다. Orca의 오케스트레이션은 조정자 에이전트가 작업자 에이전트를 각자의 작업 공간에 띄워 완료 보고를 받는 실험 기능이다(Settings → Experimental)[O2]. 사용량을 예측하기 어렵고, 결정 관문(decision gate)에도 조정자가 답하므로 사람의 승인이 아니며(10-3), 문서는 병합 방법을 적지 않는다[O2].

[최신 자료 자리: Orca 오케스트레이션의 상태] 확인할 곳: https://orca.dev/docs/cli/orchestration, 설치된 판의 orca skills get orchestration --full. 2026-11-16에 확인한 값: 실험 기능이며 Settings → Experimental에서 켠다. 같은 날 문서에는 실험 기능 패널과 그 스위치를 잠시 쓸 수 없다는 안내가 있었다.

정리

  • 멀티 에이전트는 컨텍스트, 전문화, 병렬성의 한계를 푸는 대신 토큰, 조정, 충돌의 비용을 치른다. 나눈 이득이 비용보다 작으면 나누지 않는다. 병렬은 읽기에 강하고, 쓰기는 worktree로 격리한다.
  • 역할은 서브에이전트 정의 파일로 옮기고, 역할별 경로 제한은 지시문과 판정 검사의 두 겹으로 둔다.
  • 인계는 계획서, 작업 카드, 결과 보고로 하며, 계약을 인수 테스트로 고정한다.
  • 충돌은 계획에서 막는다. 소유 파일 단위로 나누고, 공유 파일의 충돌은 위험으로 적어 둔다. 충돌이 나면 작업 쪽에서 풀고 다시 판정한다.
  • 되풀이와 기록은 스크립트에, 되돌리기 어려운 결정은 사람에게 둔다. Orca가 작업 공간과 세션을 맡아도 카드, 판정, 사람의 병합은 저장소에 남는다.

  1. ISSUE-07에서 명세서(docs/요구사항명세서.md)는 어느 작업의 소유 파일로도 넣지 않았고, 변경 기록(docs/운영/변경기록.md)은 두 작업의 공유 파일로 넣었다. 두 공유 파일을 다르게 다룬 까닭과 각 방식의 대가는 무엇인가?
  2. api/main.py의 엔드포인트 다섯 개를 각각 고치는 일을 에이전트 다섯에게 병렬로 맡기면 안 되는 까닭을 2절의 다섯 질문 가운데 둘을 들어 설명하라.
  3. 서브에이전트 정의의 프런트매터에 allowed-tools: Read, Grep이라고 쓰면 어떤 일이 일어나는가? 그 실수를 실행 전에 어떻게 찾는가?
  4. 9-6에서 T2의 충돌을 풀어 커밋한 뒤 바로 merge.sh를 실행하면 거부된다. 거부의 까닭과, 이 거부가 막는 사고는 무엇인가?
  5. 같은 ISSUE-07을 스크립트 조정자(run_issue.sh)로 돌릴 때와 Orca로 돌릴 때, 사람이 맡는 일은 어떻게 달라지는가? 두 방식에서 똑같이 남는 것 둘을 들어라.
