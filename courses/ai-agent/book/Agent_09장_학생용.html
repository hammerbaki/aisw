[9장] 에이전트 루프의 구조: API와 도구 호출

AI에이전트 기획 및 개발

9장

에이전트 루프의 구조: API와 도구 호출

2027학년도 「AI에이전트 기획 및 개발」의 준비 중인 교재입니다. 편집 상태를 검토하기 위해 미리 공개한 것으로, 수업 전에 내용과 순서가 바뀔 수 있습니다.

학사 11주차 · 교재 09 · 3부 하네스와 루프

150분 기준으로 줄인 판(2026-11-19). 줄이고(학생용 본문 63,777자 → 34,815자), 줄인 세부 단계와 출력은 교수용으로 옮겼다. 명령의 출력은 2026-11-17에 Windows 11의 Git Bash와 파이썬 3.13.7(PYTHONUTF8=1)에서 얻은 것이다.

8장의 바깥 루프에서 Claude Code 한 번의 실행은 안을 들여다보지 않는 상자였다. 이 장은 그 상자를 연다. Claude Code가 파일을 읽고 명령을 실행하고 결과를 보아 다음 행동을 정하는 반복은 Claude API의 도구 사용(tool use) 위에서 돈다. 모델은 「이 도구를 이 인자로 실행해 달라」는 요청서만 쓰고, 실행은 모델을 감싼 프로그램이 한다.

핵심 실습(7절)에서는 그 프로그램을 jobprep 저장소의 agent_loop/로 만든다. 도구 두 개(search_jobs, read_doc)를 쓰고 최대 반복 상한, 인자 검증, 오류 결과, 사람 승인을 갖춘 최소 에이전트 루프이며, 모의 모델로 테스트한다. 그 과정에서 골격의 문서 읽기 도구가 ../../README.md 같은 이름으로 자료 폴더 밖의 파일을 읽는 경로 탈출을 재현하고 막는다.

학습 목표

  • 에이전트 루프의 한 바퀴를 메시지 수준에서 설명할 수 있다.
    • 예시: tool_use 블록의 id와 tool_result 블록의 tool_use_id가 짝을 이루고, 결과가 user 역할로 돌아간다는 것을 저장된 JSON에서 가리킨다.
    • 활용: 에이전트가 이상하게 행동할 때 어긋난 왕복을 기록에서 찾는다.
  • 도구 정의를 쓰고, 모델이 만든 인자를 검증할 수 있다.
    • 예시: search_jobs의 설명에 「언제 쓰지 않는가」를 넣고, ../../README.md 같은 인자를 코드가 거부하게 한다.
    • 활용: 졸업 프로젝트에서 LLM에게 조회나 파일 읽기를 맡길 때 모델을 믿지 않고도 안전하게 열어 준다.
  • 종료 조건, 최대 반복 상한, 오류 결과, 사람 승인을 갖춘 최소 루프를 구현하고 모의 모델로 테스트할 수 있다.
    • 예시: 끝없이 도구만 부르는 모의 모델을 넣어 루프가 상한에서 멈추는지 확인한다.
    • 활용: 비용 없이 에이전트 코드를 회귀 테스트하는 방법으로 12장(평가)과 13장(CI)에 이어진다.
  • 직접 구현한 루프를 Agent SDK와 Claude Code의 구조에 대응시킬 수 있다.
    • 예시: pre_tool_hooks가 PreToolUse 훅, approver가 권한 확인, MAX_TURNS가 SDK의 max_turns에 해당한다고 표로 정리한다.
    • 활용: 10장에서 역할 에이전트의 통제를 어느 자리에 둘지 고른다.

설치와 키트 저장소의 클론(~/kits-repo)은 부록 A로 끝냈다고 전제한다. 확인 터미널([터미널])과 Claude Code 터미널 모두 가상 환경을 켜고(부록 A-9-1), Windows에서는 PYTHONUTF8=1 등록(부록 A-4-4)을 확인한다. 실행 상한: 핵심 실습과 모든 확인은 모의 모델로 키 없이 끝난다. 직접 만든 프로그램은 계정 로그인이 아니라 API 키로만 인증하므로[D1][S5], 실제 API는 Console의 키를 발급한 학습자만 7-9절의 명령 하나를 1회 실행하고(부록 A-12-3), Agent SDK 판은 교수 시연이다.

1. 에이전트 루프

1-1. 모델 호출 한 번과 에이전트

앞 과목의 질의응답 기능처럼 무엇을 검색하고 언제 끝낼지를 코드가 정하는 구조를 Anthropic은 워크플로(workflow)라 부르고, 모델이 스스로 과정과 도구 사용을 정하는 구조를 에이전트(agent)라 부른다[E1].

1-2. 루프의 다섯 단계

에이전트 루프의 한 바퀴는 다섯 단계이다[A2].

  1. 모델 호출. 프로그램이 질문, 도구 목록, 지금까지의 대화 기록을 Messages API로 보낸다.
  2. 도구 요청. 모델이 답 대신 tool_use 블록(도구 이름과 인자)을 돌려준다. stop_reason은 tool_use이다.
  3. 프로그램이 실행. 프로그램이 인자를 검사하고 도구를 실행한다.
  4. 결과 돌려주기. 실행 결과를 tool_result 블록으로 대화 기록에 붙이고 1로 돌아간다.
  5. 끝. 모델이 도구 없이 답하면(end_turn) 끝낸다. 정해 둔 횟수에 닿아도 끝낸다.
sequenceDiagram
    participant P as 프로그램 (agent_loop/loop.py)
    participant M as 모델 (Messages API)
    participant T as 도구 (tools.py)
    P->>M: ① 질문 + 도구 목록 + 대화 기록
    M-->>P: ② tool_use (search_jobs, {"field": "AI 서비스"})
    P->>T: ③ 인자 검사 후 실행
    T-->>P: 공고 목록(JSON 문자열)
    P->>M: ④ 대화 기록 + tool_result
    M-->>P: ② tool_use (read_doc, {"name": "05_…md"})
    P->>T: ③ 실행
    T-->>P: 문서 본문
    P->>M: ④ 대화 기록 + tool_result
    M-->>P: ⑤ 답 (end_turn)

코드에서 ①은 model.create(...), ③은 execute()와 run_tool(), ④는 messages.append(...), ⑤는 return AgentResult(...)이다. ②만 모델이 하고 나머지는 프로그램이 한다.

1-3. 모델은 도구를 실행하지 않는다

공식 문서는 모델이 스스로는 아무것도 실행하지 않는다고 밝힌다. 모델은 구조화된 요청을 내고 실행은 애플리케이션의 코드가 하며, 모델은 도구의 정의와 결과만 본다[A2]. 따라서 실행 여부의 최종 결정권은 프로그램에 있고(6장의 훅과 3장의 권한 규칙이 동작하는 근거), 모델이 만든 인자는 사용자 입력처럼 믿지 않는 입력이다(5절). 2026년 2학기판 LLM 7주차의 계산 도구 실습에서 모델이 음수 금액을 이상하다고 보고 되물은 일이 있었다. 그것은 모델의 판단이었지 코드의 방어가 아니었고, 다시 물으면 음수 합계가 그대로 나올 수 있었다. 방어는 매번 같은 결과를 내는 코드에 둔다.

1-4. 안쪽 루프와 바깥 루프

8장의 스크립트가 claude -p를 한 번 부르면 Claude Code는 그 안에서 이 장의 루프를 여러 바퀴 돌린다.

항목 바깥 루프 (8장) 안쪽 루프 (9장)
반복의 단위 Claude Code 실행 한 번 모델 호출 한 번
판정하는 것 pytest의 결과 응답의 stop_reason
상한 시도 3회(LOOP_MAX_ATTEMPTS) 회차 6회(MAX_TURNS)

Claude Code 문서는 모델을 둘러싸고 도구와 맥락을 관리하는 층을 에이전트 하네스(agentic harness)라 부르며[C21], loop.py는 가장 작은 하네스 본체이다.

생각해 볼 것. 다섯 단계를 모델이 하는 것과 프로그램이 하는 것으로 나누고, 8장의 시도 상한과 MAX_TURNS가 각각 무엇의 횟수인지 말해 본다.

2. Messages API와 도구 정의

2-1. 요청의 구성

Messages API는 POST /v1/messages로 모델을 부른다[A1]. 루프는 매 회차 model, max_tokens(2048), system, messages(대화 기록 전체), tools를 보낸다. API는 상태를 기억하지 않으므로(stateless) 프로그램이 기록 전체를 매번 다시 보낸다[A1]. 파이썬 SDK anthropic은 2.0.0부터 API 버전 2026-10-21을 쓰며[A18], 이 버전에서는 temperature를 보내면 기본값이어도 400 오류가 난다[A19]. 옛 예제를 붙여 쓸 때는 API 버전부터 본다.

[최신 자료 자리: 파이썬 SDK와 API 버전] anthropic의 최신 판과 그 판이 보내는 API 버전, 그 버전의 금지 매개변수. 확인할 곳: https://pypi.org/project/anthropic/, [A18], [A19]. 2026-11-15에 확인한 값: PyPI 최신 2.8.0, API 버전 2026-10-21.

2-2. 도구 정의의 항목

사용자 정의 도구는 다음 항목으로 정의한다[A12].

description 예(권장) 무엇을 하고 언제 쓰는지 적은 평문
input_schema 예 인자의 모양을 정하는 JSON Schema 객체
input_examples 아니오 스키마에 맞는 입력 예시의 배열

2-3. 설명은 곧 프롬프트이다

API는 tools를 받으면 도구 정의로 특별한 시스템 프롬프트를 만들어 모델에게 주며[A12], 모델은 코드가 아니라 이 정의만 보고 부를지 정한다. 공식 문서는 도구 성능에 가장 큰 영향을 주는 요인으로 자세한 설명을 꼽고, 무엇을 하는가, 언제 쓰고 언제 쓰지 않는가, 인자의 뜻, 돌려주지 않는 정보를 3~4문장 이상으로 쓰라고 한다[A12]. 「Writing tools for agents」는 새로 온 동료에게 설명하듯 쓰라고 한다[E6]. 정의는 회차마다 다시 실리는 토큰 비용이기도 하다(Haiku 5.5의 도구 사용 시스템 프롬프트는 auto일 때 286토큰[A10]). 골격의 search_jobs는 설명이 0자여서 모델이 이름만 보고 짐작해서 부르며, 7-4절에서 채운다.

[최신 자료 자리: 도구 사용 시스템 프롬프트의 토큰과 강제 호출] 모델별 토큰 표와 any·tool을 받지 않는 모델(2-4). 확인할 곳: [A10], [A12]. 2026-11-15에 확인한 값: Haiku 5.5는 286·406토큰, Opus 5.5와 Sonnet 5.5는 auto·none 286토큰이고 any·tool 칸이 비어 있다.

2-4. 도구 선택 방식: tool_choice

tool_choice는 auto(모델이 정한다. 기본값), any·tool(도구를 반드시 부른다), none 가운데 하나이며, 강제 호출은 2026-11-14 기준 Opus 5.5와 Sonnet 5.5 등에서 400이다[A12]. 이 장의 루프는 도구가 필요 없으면 바로 답하도록 auto를 쓰고, 도구를 덜 쓰는 경향은 시스템 프롬프트로 조절한다[A10].

4. 종료 조건과 최대 반복 상한

4-1. stop_reason의 값

성공 응답의 stop_reason은 모델이 생성을 멈춘 까닭이다. 2026-11-14 기준 문서는 일곱 값을 든다[A15].

값 뜻 이 장의 루프
end_turn 응답을 자연스럽게 마쳤다 답으로 끝낸다
tool_use 도구를 부른다 실행하고 다음 회차
max_tokens 출력 한도에 닿았다 답으로 쓰지 않고 멈춘다
stop_sequence 지정한 멈춤 문자열이 나왔다 멈춘다
pause_turn 서버 도구의 내부 반복이 상한에 닿았다 서버 도구를 쓰지 않아 생기지 않음
refusal 응답을 거절하였다 멈춘다
model_context_window_exceeded 응답이 컨텍스트 창을 채웠다 멈춘다

루프를 이어 가는 값은 tool_use[A2], 정상 종료는 end_turn뿐이다. max_tokens의 글은 중간에서 끊긴 것이며, 마지막 블록이 잘린 tool_use이면 한도를 올려 다시 요청하라고 문서는 권한다. refusal은 HTTP 200으로 오므로 예외 처리로는 잡을 수 없다[A15].

4-2. 루프의 종료 조건

루프가 끝나는 경우는 다음과 같으며, 이 값이 AgentResult.stop에 들어간다.

종료 조건 답(answer) 종료 코드
end_turn 모델이 도구 없이 답했다 마지막 응답의 글 0
max_turns 회차가 상한에 닿았다 없음(None) 1
max_tokens 응답이 출력 한도에서 잘렸다 잘린 글(참고용) 1
refusal 등 그 밖의 stop_reason 있으면 글 1
tool_use_without_block tool_use인데 블록이 없다 없음 1

끝나는 길에 모두 이름을 붙이면 12장의 평가가 종료 사유별로 결과를 세고, 다른 스크립트가 종료 코드로 성공을 가를 수 있다.

4-3. 최대 반복 상한

stop_reason만으로 끝을 정하면, 모델이 같은 검색이나 같은 잘못된 인자를 되풀이할 때 루프가 끝나지 않는다. 「Building effective agents」는 최대 반복 횟수 같은 멈춤 조건을 두라고 한다[E1]. 이 장의 질문은 3회차면 끝나므로, 오류 회복과 추가 호출의 여유를 더해 MAX_TURNS를 6으로 정했다. 너무 낮으면 정상 작업이 끊기고 너무 높으면 폭주한 루프가 비용을 쓴다. Agent SDK는 같은 장치를 max_turns로, 비용 상한을 max_budget_usd로 둔다[S1].

4-4. 상한에 닿았을 때 할 일

상한에 닿은 루프는 답을 지어내지 않고 stop을 max_turns로 남긴다. 원인은 대개 모호한 도구 설명, 도구로 답할 수 없는 질문, 정말로 긴 작업(10장에서 나눈다) 가운데 하나이며, 회차 기록(AgentResult.log)의 도구, 인자, 오류 여부로 가린다.

생각해 볼 것. 4-2절의 표로 runaway(끝없이 도구만 부른다)와 truncated(출력 한도에서 잘린다)의 stop 값과 종료 코드를 예상해 적어 두고, 7-2절과 7-3절에서 맞춰 본다.

표의 위 다섯 줄은 스키마로 표현할 수 있어 validate()가 막고, 아래 세 줄은 처리 함수가 검사한다.

5-2. 스키마 검사와 strict 모드

validate()는 JSON Schema의 일부 어휘만 다루는 작은 검사기로, 어긋난 점을 모두 모아 돌려준다. {'field': 'AI', 'limit': 50}에는 허용값 오류와 'limit'는 10 이하여야 한다. 받은 값: 50.을 함께 돌려주므로 모델은 한 번의 재시도로 둘을 고칠 수 있다. 도구 정의에 "strict": true를 두면 API가 출력을 스키마에 맞게만 생성한다[A16]. 그래도 코드의 검사는 남긴다. strict는 도메인 규칙을 보장하지 않고, 같은 도구가 strict 없는 경로(모의 모델, MCP 클라이언트)로도 불리며, 지원하지 않는 어휘가 있을 수 있다.

5-3. 경로 제한

받은 이름을 그대로 경로에 붙이는 파일 도구에는 ../../.env처럼 상위 폴더로 올라가 허용된 폴더 밖을 읽는 경로 탈출(path traversal)이 생긴다. 11장의 간접 프롬프트 주입과 합쳐지면 자료에 숨긴 지시 한 줄이 모델에게 .env를 읽게 만들 수 있다. 골격의 read_doc()은 ../../README.md를 정상 결과로 돌려주며, ../../.env가 걸리는 것은 확장자 덕분의 우연이다. 막는 검사는 두 겹이다. 1차는 이름에 /, \, .., :가 있으면 거부한다. 2차는 (DOCS_DIR / name).resolve()가 DOCS_DIR.resolve() 안에 있는지(Path.is_relative_to) 본다. resolve()는 심볼릭 링크를 풀므로, 이름은 깨끗하지만 자료 폴더 안의 링크가 밖을 가리키는 경우까지 막는다.

5-4. 오류를 is_error로 돌려주기

공식 문서는 도구가 실패하면 루프를 멈추지 말고 오류 내용에 "is_error": true를 붙여 돌려주라고 한다. 모델은 빠진 정보를 채워 2~3번 다시 시도한 뒤 사과한다. 오류 문장은 「Rate limit exceeded. Retry after 60 seconds.」처럼 무엇이 잘못되었고 무엇을 하면 되는지 적는다[A13]. run_tool()은 어떤 경우에도 예외를 밖으로 내지 않는다.

def run_tool(name, args, tools):
    """도구 하나를 실행하고 ToolOutcome을 돌려준다. 어떤 경우에도 예외를 밖으로 내지 않는다."""
    tool = tools.get(name)
    if tool is None:
        return ToolOutcome(f"알 수 없는 도구 '{name}'이다. 쓸 수 있는 도구: {', '.join(tools)}", True)
    errors = validate(tool.definition["input_schema"], args)
    if errors:

    try:

    except ToolError as error:
        return ToolOutcome(str(error), True)
    except Exception as error:  # 예상하지 못한 오류도 루프를 멈추지 않는다. 내부 내용은 모델에게 보내지 않는다
        return ToolOutcome(f"도구 실행 중 오류가 났다({type(error).__name__}). 다른 방법을 쓰거나 사용자에게 알린다.", True)

ToolError 처리 함수가 판단한 실패 처리 함수가 쓴 문장

예외 원문을 보내지 않는 것은 원문에 내부 경로나 비밀 정보가 들어갈 수 있고, 모델에게 보낸 글은 기록에 남아 화면으로 나갈 수 있기 때문이다. Agent SDK의 사용자 정의 도구는 잡지 않은 예외를 원문으로 보내므로[S3] 처리 함수 안에서 잡는다.

9. ReAct와 API 도구 사용

9~11절은 읽기이다. 교수 화면의 명령과 출력을 보고 루프대조.md의 2~4절을 채운다. 모두 모델을 부르지 않으므로 저장소에서 쳐 보아도 된다.

9-1. ReAct

ReAct는 Yao 등이 2022년에 제안하고 ICLR 2023에 발표한 방법으로, 모델이 추론(reasoning)과 행동(acting)을 번갈아 만들게 하여 행동의 결과(관찰)가 다음 추론을 고치게 한다[R1]. API에 도구 사용이 생기기 전에는 모델에게 「생각: / 행동: / 입력:」 세 줄로 답하게 하고 프로그램이 그 글을 읽어 행동을 골랐다.

9-2. 글 서식 루프의 실행 (읽기)

키트의 참고/react_text_loop.py는 2026년 2학기판 LLM 8주차에서 완성한 그 루프이다. 교수 화면에서 python ~/kits/Agent_09장/참고/react_text_loop.py mock을 실행하면 모의 모델이 부가세 계산과 할인 계산을 차례로 부르고 finish로 답한다. 모델의 글을 읽는 부분은 다음과 같다.

def parse_action(text):
    """모델의 글에서 (행동, 입력)을 골라낸다. 행동 줄이 없으면 글 전체를 최종 답으로 본다."""
    action, arg = None, ""
    for line in text.splitlines():
        if line.startswith("행동:"):
            action = line[len("행동:"):].strip()
        elif line.startswith("입력:"):
            arg = line[len("입력:"):].strip()
    if action is None:
        return "finish", text
    return action, arg

모델이 「행동:」처럼 서식을 조금만 벗어나도 행동을 찾지 못하고 글 전체를 답으로 처리한다. 인자도 쉼표로 구분한 문자열이어서 도구가 직접 나누어야 한다.

9-3. 글 서식과 API 도구 사용의 대조

루프의 일 글 서식 ReAct API 도구 사용 (loop.py)
모델이 도구를 고른다 모델이 쓴 「행동:」 줄을 프로그램이 읽는다 응답의 tool_use 블록(name)
인자를 검사한다 한 줄 문자열. 도구가 직접 나눈다 JSON 객체. 스키마로 검사, strict로 보장 가능
결과를 돌려준다 「관찰: …」을 프롬프트 끝에 이어 붙인다 tool_result 블록(tool_use_id로 짝)
반복을 끝낸다 행동이 finish stop_reason이 end_turn
서식을 벗어나면 파싱 실패 → 글 전체를 답으로 서식이 API의 구조이므로 벗어날 수 없다

공식 문서는 모델의 출력에서 결정을 뽑으려고 정규식을 쓰고 있다면 그 결정은 도구 호출이어야 했다는 신호라고 말한다[A2]. 글 서식이 하던 일은 API가 구조로 넘겨받았고, 생각·행동·관찰을 번갈아 하는 ReAct의 생각은 에이전트 루프의 기본 모양으로 남았다.

10. Claude Agent SDK와의 비교

10-1. Agent SDK

Claude Agent SDK는 Claude Code를 움직이는 것과 같은 도구, 에이전트 루프, 컨텍스트 관리를 파이썬과 타입스크립트에서 쓰게 하는 도구 모음이다[A11]. 원래 이름은 Claude Code SDK였고 2025년 9월에 바뀌었다[E4]. 이 장은 claude-agent-sdk 0.2.182를 고정한다. 진입점 query()는 메시지를 하나씩 내는 비동기 반복자이고 루프는 그 안에서 돈다[S2]. 사용자 정의 도구는 @tool과 create_sdk_mcp_server()로 프로세스 안 MCP 서버를 만들어 등록한다[S3].

[최신 자료 자리: Agent SDK의 판] claude-agent-sdk의 최신 판과 함께 든 Claude Code의 판, 설치 크기. 확인할 곳: https://pypi.org/project/claude-agent-sdk/, [S5]. 2026-11-15에 확인한 값: PyPI 최신 0.2.182(Claude Code 2.1.325 포함).

10-2. 인증

Agent SDK 문서는 사전 승인 없이 제3자 개발자가 자기 제품에서 claude.ai 로그인이나 그 사용량 한도를 쓰게 하는 것을 허용하지 않으며 API 키 인증을 쓰라고 한다[A11][S5]. Claude Code의 「Legal and compliance」도 계정 로그인은 구독자가 Claude Code와 Anthropic의 앱을 쓰기 위한 것이라고 적는다[D1]. 그래서 loop.py와 sdk_agent.py는 .env의 ANTHROPIC_API_KEY로 인증한다(부록 A-16-2). 키를 ~/.bashrc에 export하면 터미널의 Claude Code까지 그 키를 쓰게 되므로 하지 않는다(부록 A-5-3).

10-3. sdk_agent.py 읽기

키트의 참고/sdk_agent.py는 같은 에이전트의 SDK 판이며 도구의 정의와 검사는 tools.py를 그대로 쓴다. 처리 함수는 run_tool()의 결과를 {"content": [...], "is_error": ...} 형식으로 돌려주기만 하고, tool_result와 짝 맞추기는 SDK가 한다[S3]. SDK에는 모의 모드가 없어 키가 없으면 시작하지 않는다. 설치(약 357MB)와 처리 함수의 테스트는 교수 화면으로 보며, 직접 하려면 부록 A-16을 따른다(선택).

SDK 판은 교수가 시연하고 출력을 시연기록/sdk_출력.txt로 올린다. 도구 요청과 [훅 PreToolUse] 줄이 짝지어지면 훅이 두 도구에 모두 걸린 것이다. 결과 메시지의 subtype은 success, error_max_turns, error_max_budget_usd 등이며, 한도에 닿으면 query()가 결과 메시지를 낸 뒤 예외를 올린다[S1].

11-4. 권한의 평가 순서

Claude Code는 도구 요청을 정해진 순서로 검사한다. Agent SDK 문서는 그 순서를 여섯 단계로 적는다[S4].

순서 단계 하는 일
1 훅 거부하거나 넘긴다. allow여도 거부·묻기 규칙은 평가된다
2 거부 규칙 맞으면 거부한다. bypassPermissions여도 거부된다
3 묻기 규칙 맞으면 승인 콜백(사람)에게 넘긴다
4 권한 모드 bypassPermissions는 대부분, acceptEdits는 작업 폴더 안의 편집을 승인
5 허용 규칙 맞으면 승인한다
6 승인 콜백 남은 호출을 사람(can_use_tool)에게 묻는다. dontAsk에서는 거부한다

거부가 허용보다 먼저이므로 3장에서 거부 규칙에 둔 .env 읽기는 어떤 허용 규칙이나 모드로도 풀리지 않는다. 또 허용 규칙으로 자동 승인되는 호출도 PreToolUse 훅은 거치므로, 그런 호출까지 검사하려면 훅을 쓴다[S4]. 6장의 보호 파일 훅이 권한 규칙과 별도로 필요한 까닭이다. execute()도 훅, 승인, 실행 안의 검사의 순서를 따른다.

11-5. 서브에이전트

서브에이전트는 루프의 관점에서 도구 하나이다. Claude Code는 Agent 도구로 서브에이전트를 부르고, 서브에이전트는 자기만의 컨텍스트 창에서 일한 뒤 요약을 돌려주므로 주 에이전트의 맥락에는 요약만 쌓인다[C21][S1]. 키트의 참고/subagent_sketch.py에서 부모의 도구 ask_researcher는 새 messages로 run_agent()를 한 번 더 돌리고 자식의 마지막 답만 돌려준다.

def ask_researcher(args):
    child = run_agent(args["question"], scenario("normal"))   # 새 messages, 자식만의 도구
    children.append(child)
    return child.answer or f"하위 에이전트가 답하지 못하였다(종료={child.stop})."

교수 화면에서 이 스크립트를 실행하면, 자식은 3회차 동안 도구를 두 번 부르며 1,874자의 기록을 쌓지만 부모의 기록은 570자이다. 부모는 자식의 마지막 답 한 문단만 받는다. 자식은 부모의 기록을 보지 못하므로 일을 맡길 때 필요한 맥락을 질문에 모두 담아야 한다. 이 구조가 10장의 역할 에이전트로 이어진다.

11-6. Stop 훅과 바깥 루프

6장의 Stop 훅은 이 장의 루프로 말하면 end_turn에서 return 하기 전에 테스트를 돌리고, 실패하면 결과를 user 메시지로 붙여 다음 회차로 가는 것이다. 8장의 바깥 루프는 같은 일을 실행이 끝난 뒤에 한다. 안쪽에서 되돌리면 맥락이 이어지지만 기록이 커지고, 바깥에서 되돌리면 깨끗하게 다시 시작하지만 맥락을 요약해 넘겨야 한다. 어느 쪽이든 상한이 필요하다(훅은 stop_hook_active, 스크립트는 재시도 횟수).

정리

  • 에이전트 루프는 모델 호출 → 도구 요청(tool_use) → 프로그램이 실행 → 결과(tool_result) → 반복 → 끝이다. 모델은 요청서를 쓰고 실행과 거부는 프로그램이 한다.
  • 도구의 이름, 설명, 스키마는 프롬프트의 일부이다. 설명에는 언제 쓰지 않는지와 돌려주지 않는 것을 쓴다.
  • tool_result는 user 메시지에 담아 tool_use_id로 짝을 맞추고, 한 응답의 결과는 메시지 하나에 넣는다.
  • 정상 종료는 end_turn뿐이다. 상한에 닿으면 답을 지어내지 않고 종료 사유를 남긴다.
  • 모델이 만든 인자는 믿지 않는다. 스키마와 처리 함수로 검사하고 실패는 is_error로 돌려주며, 위험한 도구는 사람의 승인 없이 실행하지 않는다.
  • 대화 기록을 회차마다 다시 보내므로 비용은 회차 수보다 빠르게 는다.
  • Agent SDK와 Claude Code는 같은 루프를 대신 돌리며, 훅과 권한 규칙과 서브에이전트는 그 루프의 정해진 자리에 끼어든다.

개념 점검

  1. 모델의 응답에 tool_use 블록이 두 개 있다. 프로그램이 다음 요청에 보내야 하는 user 메시지의 모양을 tool_use_id를 넣어 적어라.
  2. stop_reason이 max_tokens이고 마지막 블록이 tool_use인 응답을 받았다. 이 도구 요청을 실행하면 안 되는 까닭과, 공식 문서가 권하는 처리를 설명하라.
  3. 도구 정의에 strict: true를 두었는데도 read_doc의 처리 함수 안에 경로 검사를 남기는 까닭을 두 가지 들어라.
  4. 최대 반복 상한을 6에서 30으로 올렸을 때 생길 수 있는 문제 두 가지를 이 장의 실행 기록(회차별 기록 크기)을 근거로 설명하라.
  5. Claude Code에서 허용 규칙 Bash(git commit *)에 맞는 호출이 있다. 이 호출에 대해 PreToolUse 훅, 거부 규칙, 승인 콜백 가운데 어느 것이 실행되고 어느 것이 실행되지 않는지 11-4절의 순서로 설명하라.
